# Pull request review

### Review and recording

A review assesses its stated scope across description fidelity, plan fidelity, functionality gaps, introduced technical debt, and introduced security issues. An ordinary review covers the full open pull request; a staged complex-feature review may be limited to one implementation commit and its subplan. Within its scope, a review reads and judges every line that is added, changed, or removed, in every kind of file, and checks each file of a repeated pattern on its own rather than sampling a few. It also checks every promise: the goal, decisions, changes, tests, documentation edits, and verification steps of the pull request's own plan; each fix plan a repair added; and each claim and verification step in the description. A wrong change-set statistic in the description, such as a commit, file, or line count or a commit SHA, is proposed for removal rather than correction, and a correct one is not a finding on its own. There is no limit on the number of findings it records. A minor finding is recorded with a low severity rather than dropped. Its report states how many changed files and promise items it covered. It records new findings in the review backlog on that pull request's branch and leaves the pull request open. Existing findings are preserved and duplicates are not recorded again. The review does not implement its findings.

### The review backlog

The review backlog is one flat list of findings with no status grouping. Every entry in it is ready to work, and the order entries appear in is their priority: new findings are added to the end, and moving an entry up is how it is prioritised. An entry leaves the list when it is resolved or when someone decides against it, since deleting an entry is how a finding is declined. Once the last entry goes, the backlog returns to its empty form — the leading comment and heading it carries on master — rather than being removed from the branch.

### Follow-up work

Every new finding directs its implementation through the work-pull-request-issue workflow. The proposal gives the explicit reviewed PR number and a concrete issue summary as a backlog-entry selector, followed by an implementation and verification plan. Follow-up work repairs one recorded entry on that same open PR's head branch without merging it.

The same route applies to all five review dimensions, including security. References to other tasks provide detection guidance only; they do not redirect implementation to another task or substitute a human-only handoff. Previously recorded entries are not rewritten by a later review solely to change their routing.

### Review cycle after building a feature

Building a feature from a ready plan doesn't stop once its pull request is open. The full pull request is reviewed against the completed plan, and its findings are resolved one at a time in file order. Each review and each repair runs separately from the work that wrote the code. Standalone repair follows the normal selection cutoff: without a selector it chooses the first entry rated below 7/10, and if a selector names an entry rated 7/10 or higher, the run stops. The feature-building workflow defines a separate, scoped exception for its own delegated review cycle; that exception does not change the standalone repair rule. After the backlog empties, the pull request is reviewed again. The cycle repeats until a review adds no findings and the backlog is empty. The pull request is then updated so its description, plan, specs, and help match the final code ([[pull-request-updating]]). It stays open throughout and is never merged by the workflow.

A subplan built as part of a complex feature skips all three of those closing stages: opening the pull request, the review cycle, and the update. The complex-feature workflow runs its own staged reviews and its own update for the whole feature.

### Staged reviews for complex features

The staged feature workflow accepts a ready source plan at any honest complexity from 1–10. Plans rated 1–5 remain intact as a single work unit, without decomposition or duplicate plans; plans rated 6–10 are decomposed into ordered subplans rated 1–5. Each subplan's rating is recorded during decomposition by the formula-based rating task rather than by judgment, and a subplan it rates 6 or higher is split again and each piece rated the same way. Both routes publish the canonical source plan first, improve each work unit immediately before implementation, publish and review its implementation, resolve findings, and complete the full pull-request review and update stages. The single-plan route improves and implements the same canonical plan in place, preserving its identity for later updates.

When a complex feature is split into subplans, all initial subplans are published to one open pull request before implementation begins. The original feature plan moves to the completed plans in that same first commit, so it is the pull request's own plan and an update finds it the way it finds any pull request's plan ([[pull-request-updating]]). Each subplan is improved and published immediately before its implementation. After each implementation commit is pushed, its review is limited to that commit against the corresponding subplan; the aggregate pull request is not reviewed during these cycles.

Findings from each focused review are added to the pull-request backlog and resolved one at a time in file order. Every finding from that review is resolved before any other review runs. A resolution review follows. It checks each resolved finding against what its entry proposed, and checks the repairs for regressions, without reviewing the subplan from scratch. Anything still unresolved, or broken by a repair, is recorded and resolved the same way, and another resolution review follows. The next subplan does not begin until a resolution review adds no findings, its predecessor and all resulting repairs are published, and the backlog is empty. Once every subplan has completed this cycle and the canonical plan and pull-request description match the finished feature, the aggregate pull request is reviewed. Its findings are also resolved one at a time before another full review. Full review and repair cycles continue until a review adds no findings and the backlog is empty. When every finding a review records asks only for a correction to the pull-request description, the corrections are made and the work proceeds without another review of any kind, as long as the repairs changed nothing else on the branch and the description shows each correction. If any finding calls for another change, the normal follow-up review runs. The pull request remains open throughout.

### Behavioral testing after complex-feature review

After the initial pull-request update and full review, the complex-feature workflow runs behavioral testing on the same open pull request. Every recorded finding is repaired separately in backlog order before testing runs again. Repairs to the description also require another test pass. The cycle ends only when a completed test pass adds no findings and the backlog is empty; an unavailable browser, incomplete test run, blocked repair, or failed publication prevents completion.

The pull request is updated again after the test cycle so its description and canonical plan reflect the repairs. Code repairs identified by this final update go through testing again before another final update. Testing, repairs, and updates preserve their normal safeguards and leave the pull request open.

### Final complex-feature recovery

Before completion, the feature's published head is checked for conflicts with its primary branch, local validation failures, and failing GitHub checks. Conflicts go through the conflict-resolution workflow on that same open pull request; local or current-head CI failures go through the build-repair workflow in pull request mode. Both preserve their normal repair scope and verification safeguards. An unsupported primary branch or blocked repair prevents completion.

Any recovery that changes the branch requires another behavioral test/repair cycle and final update, followed by fresh validation of the new published head. Successful local validation and configured GitHub jobs for that head or its current merge commit are required; missing, stale, skipped, cancelled, inaccessible, or unfinished checks cannot establish success. Recovery is bounded to three final verification sequences; unresolved failures or conflicts leave the pull request open with a blocked report. The workflow never merges, closes, or replaces the feature pull request.
