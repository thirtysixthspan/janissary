### Application config

Native application command settings are stored separately from `config.json` in `~/.janissary/commands.json`, with `.janissary/commands.json` as a whole-file project override. See [[application-commands]] for the file format, fallback behavior, and edit rules.

Application settings are stored in `.janissary/config.json`, except the notification toggles and per-type alerts, which live in `.janissary/notifications.json` (see "Notification configuration" below). On first launch a default file of each kind is created if it does not exist. Both are loaded after the `.janissary/` subdirectories are initialized and before the `App` component renders.

| Setting | Type | Default | Description |
| ------- | ---- | ------- | ----------- |
| `transcriptMaxLines` | `number` | `25000` | Maximum number of `LogEntry` objects retained per tab's transcript. When exceeded, the oldest entries are dropped (the most recent N are kept). Applied in both `appendLog` and `updateCurrentTab` so all log mutation paths are capped. |
| `maxToolTurns` | `number` | `20` | The maximum number of command steps a single ACP tool loop may run. A fresh config writes the key out, and a config that predates it gains the key the next time it is loaded. Like `clipboardHistoryMaxEntries`, a value that is not a positive whole number falls back to `20`. Every tool loop reads it as its step budget, including core prompts, subagent attempts, agent runs, and remote-hosted loops; the command-exchange primer states the same number. No runtime command changes the setting; edit `.janissary/config.json` directly. See [[acp]]. |
| `tabNameMaxLength` | `number` | `16` | Maximum displayed length of an inactive tab name, including its trailing ellipsis when shortened. It is a display limit only: agent and harness routing labels keep their full name, and file-backed tabs retain their full filename, shortening either only for display. |
| `activeTabNameMaxLength` | `number` | `50` | Maximum displayed length of the focused tab name, including its trailing ellipsis when shortened. The active central tab and the visible entry in each sidebar use this limit. |
| `clipboardHistoryMaxEntries` | `number` | `15` | How many entries the clipboard-history popup keeps (see [[clipboard-history]]). The oldest entries are dropped once the cap is exceeded, and lowering it trims what is already held. Unlike every other number here, a well-typed but meaningless value — `0`, a negative, a fraction — falls back to the default rather than being taken literally, because "how many entries to keep" has no sensible zero or fraction. There is no runtime command to change this — the user edits `.janissary/config.json` directly. |
| `sandboxWorkspaces` | `boolean` | `true` | Whether workspaced tabs (`shell --workspace`, `harness --workspace`) are confined to their workspace clone by a Seatbelt sandbox (macOS only). The escape hatch for when confinement causes trouble. |
| `logEnabled` | `boolean` | `true` | Whether harness and shell session transcript files under `.janissary/transcripts/harness/` and `.janissary/transcripts/shell/`, asciicast recordings under `.janissary/recordings/` (harness, ssh, and shell tabs), and activity logs under `.janissary/logs/activity/` are written at all (see [[harness-recording]] § Session transcripts and § Scope, [[activity-log]], and `shell-tab.md` § Text transcript). With it false no harness tab, local or remote, no ssh tab, and no shell tab writes a transcript file or a recording, and no activity log entry is written; a shell tab draws no **Open transcript** button, and each of those tabs' recording flags reads **not recording**. Monitors keep receiving transcript entries either way, and a harness tab still reads its screen, approves, and resumes. Recording is off for every kind of tab alike: a shell echoes what is typed back into its terminal, so a secret typed on a command line (`export TOKEN=…`) reaches a shell tab's recording, and turning this off is the way to keep it off disk. It does not stop the launch sweep that ages out older files, and it does not govern capture files or server logs: captures and the per-run server logs under `.janissary/logs/server/` are still written and swept whether it is true or false (see [[cli]]). The setting is read when a harness or ssh tab opens and when a shell terminal is adopted into its tab, and activity logging reads it on every append, so a change applies to tabs opened after the next launch. A fresh config writes the key out, and a config that predates it gains the key the next time it is loaded. A value that is not a boolean falls back to `true`. |
| `logRetentionInDays` | `number` | `7` | How many days the launch sweep keeps a harness or shell transcript, a harness capture file under `.janissary/captures/`, a recording under `.janissary/recordings/`, an activity log under `.janissary/logs/activity/`, or a per-run server log under `.janissary/logs/server/` (see [[cli]]), measured from the file's last modification. With `0` it keeps none of these from earlier runs, except a server log last modified within the hour before launch. Server logs use a cutoff that is the earlier of `logRetentionInDays` days before launch and one hour before launch, so that one-hour floor holds even at `0` and a log the launcher is still polling can't be swept out from under it. The sweep runs once at launch, keeps any file last modified at or after launch regardless of the value, and considers only regular files directly inside each directory: `.txt` files for transcripts and captures, `.cast` files for recordings, `.json` files for activity logs, and `.log` files for server logs. For server logs that means only regular `.log` files directly inside `.janissary/logs/server/`; the `latest.log` symlink is never deleted. Each directory is swept on its own, so a sweep that fails for one directory does not stop the others. The value is read once at launch, so a change applies at the next launch. A fresh config writes the key out, and a config that predates it gains the key the next time it is loaded. A negative, fractional, or non-number value falls back to `7`; `0` is valid. |
| `syntaxTheme` | `string` | `"github-dark"` | The active syntax-highlighting theme for editor tabs, set via `syntax theme <name>`. Applies globally across every open editor tab. |
| `theme` | `string` | `"dark"` | The active application color theme, set via `theme <name>`. Applies to the entire window chrome — see `application-themes.md`. Independent of `syntaxTheme`. |
| `osNotifications` | `boolean` | `true` | Master switch for every type's configured browser desktop banner. The browser must have been granted notification permission separately; Janissary never requests it. |
| `terminalBell` | `boolean` | `true` | Master switch for every type's configured bundled MP3 cue, separately from banners. Browser autoplay restrictions may prevent playback before interaction. |
| `terminalBellVolumeSuccess`, `terminalBellVolumeWarning`, `terminalBellVolumeError` | `number` | `0.8` each | Per-category cue volume between 0 and 1. Invalid or out-of-range values independently fall back to 0.8. |
| `syncPaths` | `string[]` | `["product/backlog/", "product/plans/"]` | Project-relative paths kept automatically synced with GitHub (see `editor-tab.md` → "GitHub syncing"). Each entry is an exact file path, a directory path ending in `/` (covering every file under it, at any depth), or a `*` wildcard pattern matching one path segment. There is no runtime command to change this — the user edits `.janissary/config.json` directly. |
| `externalViewers` | `object` | `{ "video": "QuickTime Player" }` | The external application each opener hands a file to, keyed by opener name (see `open.md`). Each value is a macOS application name; an empty or missing entry means the file goes to the operating system's default handler for its type. The video, audio, and PDF plugins read their `video`, `audio`, and `pdf` entries. A user-supplied map replaces the default wholesale. There is no runtime command to change this — the user edits `.janissary/config.json` directly. |
| `pluginSettings` | `object` | `{}` | Each tab plugin's own remembered preferences, keyed by plugin id. Each value is a JSON object whose shape belongs to that plugin; an entry that is not an object is dropped without affecting the others. A plugin reads and replaces only its own entry, through the `readSettings` and `saveSettings` capabilities (see `tab-plugins.md`). Today only the search tab writes one: `{ "search": { "regex": bool, "matchCase": bool, "wholeWord": bool } }`, the tab's three toggles (see `search-tab.md`). |
| `mcpPort` | `number` | *(absent)* | An optional hand-edited override for the port the local MCP server listens on, taking precedence over the port persisted by the server manager. The override is never written into the server's saved state, even on a first start, so removing the key returns the server to a saved or freshly drawn port (see [[mcp-server]]). Only a whole number from 1 to 65535 is read; `0`, a fraction, a non-number, and out-of-range values are treated as absent, so the persisted port applies. The key is deliberately not written into a fresh config and is never added by the missing-key backfill — edit `.janissary/config.json` directly to set it. |

If `.janissary/config.json` exists but is not valid JSON, a warning is printed to stderr and the application falls back to defaults for that session. The corrupt file is left on disk untouched, so a user's edits are not silently discarded. A valid JSON file is decoded setting by setting: a value with the wrong type falls back to that setting's default without discarding valid neighbors. Count-style settings such as `clipboardHistoryMaxEntries` and `maxToolTurns` also fall back when the value is well-typed but meaningless — zero, a negative, or a fraction. `logRetentionInDays` takes `0` as a valid value but still falls back on a negative or a fraction. Removed `terminalBellMute*` keys are ignored. The retired `recordShellTabs` key is ignored too, and is dropped from the file whenever Janissary next writes it for another reason (a missing-key backfill, the `notifications` move, or a saved setting such as a theme); its presence alone never causes a rewrite. Loading an older or partial config normally does not rewrite the file; the exception is a missing `maxToolTurns`, `logEnabled`, or `logRetentionInDays` key, whose default is written while preserving every other key. A failed backfill write is silent.

### Notification configuration

The notification event toggles and per-type alerts live in `.janissary/notifications.json`, not in `config.json`. A fresh file is written with every setting in it: an `events` object holding `stateChange`, `scheduleFire`, `agentStart`, `rateLimited`, and `commandDisabled` (all `false`), plus `systemScheduleFire` and `modelsRefresh` (both `true`); and an `alerts` object keyed by each notification type's own hyphenated name, each entry carrying `desktop` (`boolean`) and `sound` (`"success"`, `"warning"`, `"error"`, or `"none"`). The ambient types default to no banner and no sound; the other defaults are the cues and banners described in [[notifications]] § Desktop alerts and bell sounds. The master switches `osNotifications`, `terminalBell`, and the three cue volumes remain in `config.json`.

This file follows the same rules as `config.json`: invalid JSON warns on stderr, uses defaults for the session, and leaves the file untouched; each field decodes independently, so a malformed toggle or alert entry falls back on its own without discarding valid neighbors; unknown event names and non-object entries are dropped. A missing `alerts` map, or individual event types missing from it, is written in with defaults on load while preserving other keys and entries; a complete file is left byte-for-byte untouched, and a failed write is silent.

On an upgrade, a `notifications` section still in `config.json` seeds this file, keeping its hand-edited values, and is removed from `config.json` the next time that file is written. The durable notification trail that used to live at the state root has moved to `.janissary/logs/notifications.json` (see [[notifications]] § The notification record); the two files are distinct, and the config file is not read as a record.

Some settings can be changed at runtime through a command (currently `syntaxTheme`, via `syntax theme <name>`, and `theme`, via `theme <name>`). A change like this atomically replaces `config.json`, preserving any other keys already in the file, and updates the running application only after that replacement succeeds. If the write fails, the file and running setting both keep their previous value and a warning reports the failure.

`pluginSettings` is also written at runtime, by a plugin saving its own entry — the search tab does so when its toggles change. The write is the same atomic replacement, preserving every other key and every other plugin's entry. A failed write reports nothing to the user; the plugin is told it failed and carries on with its settings unsaved.
