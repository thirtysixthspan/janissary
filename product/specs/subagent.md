# Subagent

### Invocation forms

`subagent` starts a background agent run for a named role, gives it an existing AI task file or an assignment written inline in the context, plus optional extra directions, and hands a distilled result back to whoever started it. The command token is matched regardless of case. A person uses the flag form; an agent in an `ask` or `tell` session uses the JSON form.

The flag form is `subagent --role <role> [--task <file.md>] [--context <text>]`. The task is optional: when it is omitted, the context carries the whole assignment; when both are supplied, the context is extra directions appended after the task file. Flags may appear in any order, and a role or context containing spaces is written as one quoted value; escaped matching quotes are preserved as literal characters. The JSON form is one line holding an object, `subagent {"role":"<role>","context":"<text>"}` when the task is omitted or `subagent {"role":"<role>","task":"<file.md>","context":"<text>"}` when it is present; context may be empty when a task is supplied, and embedded newlines in string values are escaped so the command stays on one line. Form selection happens before decoding: an argument whose first non-space character is `{` is JSON, and everything else — including arrays, scalars, and quoted JSON — is flags.

Only `role`, `task`, and `context` are accepted. Unknown or removed fields and flags (including model and effort), repeated or valueless flags, extra positional text, non-string values, invalid JSON, a missing or whitespace-only role, an explicitly blank task, and an invocation with neither a task nor a non-blank context are refused. String contents pass through unchanged; trimming is used only to decide whether a required value is present.

### Usage errors

Bare `subagent` and every flag-form failure return exactly `Usage: subagent --role <role> [--task <file.md>] [--context <text>]`. Every JSON-form failure returns exactly `Usage: subagent {"role":"<role>","context":"<text>"}`. Which form a caller must use, and how a refusal reaches it, is decided by the caller policy below.

### Caller policy and immediate refusals

An invocation is an ACP caller only when its `acpTool` marker is exactly true; every other caller — typed, scheduled, queued, plugin command, system schedule, or a role marker without that true marker — is a person. The caller kind decides the required form regardless of the tab's view: an ACP caller must use the JSON form and a person the flag form. A missing, malformed or wrong-form argument returns that caller's own usage line and starts nothing, even when the text looked like the other form. Stopping there precedes role lookup and launch.

For a valid caller and form, the role is read fresh, by trimmed case-insensitive name, from the roles file at the tab's launch root with built-in roles as fallback. An unknown role returns `Subagent: unknown role "<trimmed input>".`; the decoded role is trimmed only for that message. A role with no enabled entries returns `Subagent: the <canonical role> role lists no models.`, using the canonical spelling. Enabled entries keep their stored order, duplicates and effort from any harness, and the role's settings object and saved command grants are left unchanged.

A person receives a refusal as one background reply under the original line — the invocation's echo line when present, otherwise the resolved command — with a fresh background id, no record and no receipt. An ACP caller receives the refusal text directly and no human reply. The same handling applies to any synchronous launch error, reported in the source's exact words with no added prefix or punctuation, including an unavailable ACP session, a missing, closing or stale caller, and a disposed run manager. A caller whose tab is missing, closing, or from an earlier incarnation gets no human reply and no run. A successful launch returns its record receipt to a person and an empty string to an ACP caller; failures after that receipt belong only to the run's later completion, never a second immediate refusal.

### Command primer

The caller-facing primer teaches the one-line JSON grammar with escaped newlines, that the task is optional when the context carries the whole assignment, that the command returns nothing immediately and does not block, and that results arrive later as new prompts each holding one JSON object. A `started` message carries `status`, the canonical `role`, `sessionId`, and `callerId`, and means the subagent is running in the background. A completion carries `status`, `sessionId`, `callerId`, and `output`. Session ids are provider ids; a failed completion may carry a null session id, and a `started` message may be skipped when its completion overtakes it. Provider ids are taken from the agent's own handshake rather than minted by Janissary, so a run whose handshake never completes has none; that provider id stays separate from the internal session identity that prompts and `startAcp` report. Completion statuses are `completed` (finished successfully), `partial` (stopped at the tool-loop limit), `failed` (the output is the source error), and `terminated` (stopped). The primer lists no roles and consults no role descriptions.

### Provider ids on remote runs

On a remote run the far side reports the provider id as soon as its `newSession` succeeds, ahead of effort configuration and readiness, so a failed effort setup cannot discard an id whose handshake already completed. A normal readiness frame may carry the same id as an optional field, but readiness timing is unchanged. A caller keeps the first id it observes for `started` and the most recent id from a completed handshake for an outcome, with no id meaning `null`; none of these ids is the internal session identity. Across a sequence of role entries the coordinator reports the first handshake id to its observer exactly once and carries the most recently observed id into the result. A later handshake replaces that id without a second observation, and a later failure that never reached a handshake leaves it unchanged. The coordinator never reuses a nullable attempt result id as a run-level identity, and callbacks from an entry already disposed of cannot replace the current id.

### Message contract

A `started` message holds exactly the fields `status`, `role`, `sessionId`, and `callerId`, in that order, with the status set to `started` and the role set to the canonical role name. A completion holds exactly the fields `status`, `sessionId`, `callerId`, and `output`, in that order, with a status of `completed`, `partial`, `failed`, or `terminated`. A completion carries no role and a `started` message carries no output. Both ids are the provider ids the harness reported for the subagent and its caller. They pass through verbatim: no id is minted, replaced with an internal session identity, or inferred, and a completion whose subagent never completed a handshake carries a null session id.

Each delivered message is one physical JSON line whose fields appear in the order above. Output is JSON-escaped so embedded newlines, quotes, and backslashes stay on that line, and decoding the line recovers the original text. Internal run, caller-incarnation, caller-role, and session-identity values are never part of the delivered message.

### Caller ownership

At launch a subagent captures its caller's role (`ask` or `tell`), the caller session's internal identity token, and the caller's provider id as a snapshot. Later changes to the launch options or to the caller session do not change that snapshot. The captured provider id stays distinct from the internal session identity, and none of the captured values is written into the run's durable record or its monitor view.

### Pending delivery queue

Messages waiting for a caller form a queue owned by that caller tab and role. The `ask` and `tell` roles on one tab, and the same role on two different tabs, hold independent queues. Within a role, messages are appended in arrival order. When a completion for a run is queued, any `started` message for that same run still waiting in the queue is dropped; other runs' waiting `started` messages and already-queued completions keep their positions and relative order, and the completion is appended at the tail. A `started` already taken out for delivery is unaffected. Queues never merge messages, replace an earlier position with a completion, or deduplicate completions. The queue holds pending messages only: it does not send a head message or start a prompt.

### Session-bound delivery

A queued message is admitted only while the caller tab is the same live incarnation, its role session still holds the identity captured at launch, and the agent manager is not shutting down. A message that fails this check is dropped without a prompt, echo or reply, and the next ready message is considered in its place. Once admitted, the one-line JSON is the prompt's complete logical input: no role prefix or wrapper is added, and the ordinary tool primer still precedes it at the provider boundary. The message then behaves like any other prompt in the caller role — a refusal is its reply, a reset may answer `ACP session closed.`, and fallback may answer from a replacement session.

One message runs per prompt in arrival order within each tab and role, and each publishes its own background reply under the echo `<caller role> ← subagent:<canonical role> <status>` before the next starts. A queued `started` that has not been dispatched is dropped by its own completion, but one already dispatched keeps its own prompt before that completion. Reset, session close, dead agents and fallback all clear that session's queue and terminate its still-live subagents before settlement; a label reused for a later tab incarnation receives neither a stale prompt nor an old reply.

### Human wording

The Markdown reply for a started subagent is exactly `Subagent <role> started.` The completion reply is exactly `Subagent <role> <status>.`, followed by two newline characters and then the output verbatim. The output is the extracted final result, so the delimiters and any reasoning or tool-call text outside them are never shown. The role keeps its canonical spelling and spacing. Output text — Markdown, indentation, trailing whitespace, and an empty output — is preserved without an added suffix and without removing the blank line. Neither reply prints a session id, and no caller or session ids are needed to format either reply.

### Task prompt

A subagent is told it is a subagent and asked to finish with a self-contained final result for the agent that launched it. It is also told to write that result between `<final_result>` and `</final_result>` tags, to keep reasoning, thoughts, and tool calls outside the tags, and to write nothing after the closing tag; the tags and everything outside them are not returned to the caller. The task text follows verbatim, then the optional context verbatim. When no task file is named, the context is the assignment and appears once as the task text, with no second copy appended as extra directions; no task file is looked up, locally or remotely. The task prompt does not repeat the command protocol primer and adds no summarizing turn or output cap.

### Single-entry execution

One admitted role entry drives one attempt through a local or remote session. Its launch forwards the entry's command, arguments, environment and session metadata unchanged. Locally the session is confined to the run's clone and uses the captured caller's offline setting, with no approval-granting options, separate effort, installed skills or autonomous flag; provider permission requests stay denied. Remotely it uses the caller's already-established channel and its selected workspace label, with a transport address private to that attempt that is never used as a provider id. Neither form discovers a channel, provisions a clone, registers an ACP resource, or chooses another entry.

The attempt's logical input is the subagent lead-in, the task text and the optional context, recorded once. The first prompt in the durable record includes the same command primer the subagent receives at the provider boundary, prepended to that logical input, so the connection tab shows the complete input the model was given; the loop still prepends the primer only once on the raw first prompt, leaving the recorded and loop inputs identical. That primer names the standard harness tools that are disabled, such as `bash` and `shell`, and tells the agent not to call them. The snapshot uses the `ask` shape, the canonical role name, the role's commands with `subagent` removed, and the captured native settings; mutable role and native settings are not read again during the attempt, and no `subagent` row is added.

The result reports the final-result contents of the latest completed turn: the trimmed text of the last complete `<final_result>` tag pair, with the tags and any surrounding reasoning or tool-call text discarded, and tags matched case-insensitively. When that turn has no complete pair, its text is reported unchanged, so verbatim output — including empty, whitespace-only, and trailing-whitespace answers — survives and an empty tag pair stays an empty answer. Whether any turn completed, and why the attempt ended, are reported separately as answered, capped, error or terminated. An answered attempt is completed, a capped attempt is partial, and every other ending is failed or terminated with the source error text unchanged, including the exact message for a harness with no adapter. Chunks, thoughts, tool results and commands never become the final output; a capped result carries no explanatory suffix. A failure before any turn reports no completed turn, while a failure after one keeps that flag set. The exact provider session id reported by the harness is retained as soon as it arrives, even if effort selection or readiness then fails; connection errors, loop errors, synchronous setup or observer throws, and disposal never replace an already-chosen status, output, turn flag or id.

Provider activity and native command start/result activity are recorded separately from the terminal output, with remote workspace steps tagged by the selected host. The command text is written to the record feed as the command begins, before its result is available, and stays there even when the command fails or the attempt is aborted; the result is appended as a separate, later tool entry only when the command completes. Acquired sessions close exactly once, whether the attempt ends by answer, termination, abort, adoption or explicit disposal. One resource is registered for the whole execution before any entry is driven, even when no entry has an adapter. It holds only the current session, is closed when the run tears down, and never keeps a session after its attempt has returned. Disposal before any other ending selects terminated with `Subagent terminated.`; a failed or unacknowledged close becomes a cleanup warning beside the result instead of replacing it, and a run's own teardown waits for the attempt's allocation. Cleanup warnings from every attempt are appended in order, including identical warnings from separate sessions; they never change fallback eligibility, status, output or identity, and later run settlement does not report them again.

### Role fallback execution

The coordinator drives the role's already-enabled entries in their stored order using one snapshot of the role name, entries, commands and native settings captured before the first entry starts. Later edits to roles, grants or settings cannot change an execution already under way, and no model availability check, current-session promotion or task re-resolution happens between entries. Each entry gets a fresh session with the same captured invocation, directory, context, offline flag and selected remote target.

An entry that fails before any turn completed is eligible for fallback: the next entry is admitted first, and only then is the fallback notice written to activity. A failure after any completed turn is final, even an empty or command-only turn, and reports only that attempt's source error. With exactly one eligible failure the output is that failure's source text unchanged; when every eligible failure is exhausted the output lists each entry in order beneath the role's canonical name. Unsupported harnesses keep their exact adapter message. No `Agent`, `Subagent` or `ACP` prefix is added to a source error. A completed or partial answer is returned verbatim, including empty and whitespace text and without a stopped-after suffix.

Termination takes priority over everything else. An ended or aborted run, a closed resource or a terminated attempt stops the sequence, answers exactly `Subagent terminated.`, and preserves the latest reported id and accumulated warnings without a fallback notice or a replacement session. The coordinator returns execution facts only: it does not settle the run, set its terminal answer, close the record, queue messages or write a human reply. Settling and delivery remain the work of later layers.

### Records and names

A subagent run's durable record carries the canonical role name. Its title is `Subagent: <task filename>` from the task selector captured at launch, without the ACP title cap; a run with no task file is titled `Subagent: inline`. Later task resolution, a task snapshot replacement, and caller renames never change it. In the connections tab, and as its own connection tab's title, the record is named `subagent:<canonical role>`. In the caller's connections popup it appears as an ACP-kind row titled `Subagent: <task filename>` while the run is live, with no ACP reference, and leaves the popup when the run ends. Ordinary agent and ACP names are unchanged.

A run stopped at the tool-loop limit closes its record with the `Partial` outcome, which reads `Partial` as a terminal status in the connections list, the connection tab, and the agent monitor. It owns the first outcome like `Completed` and does not abort the run's controller. A terminated subagent record saves `Subagent terminated.` as its answer, regardless of an earlier response; an ordinary agent run saves `Agent terminated.` instead.

### Workspace ownership

A subagent run always uses a fresh workspace. It never borrows the caller's directory and never selects a named workspace, even when the caller is running in a tracked workspace. The run and its durable record are published synchronously at launch with the canonical role name and the original task selector, while the clone is scheduled for a later turn. The clone's creator reference transfers to the run's lease, so releasing the run deletes only that clone and leaves the caller's tracked workspace intact. Cleanup cancels provisioning and waits for clone readiness before releasing the lease. A run that ends before cloning begins schedules no clone and reports `git clone cancelled.` through readiness. A workspace refusal or a clone failure settles the record failed with the original error and no fabricated prompt. A run-creation refusal is instead propagated as a failed launch result with no clone and no durable record created — the run and its record are never published, so there is no record to settle. A final lease-removal failure is only a cleanup warning. This is the internal run-launch contract; it does not by itself wire a public subagent launch.

### Background launch and receipt

Launching a subagent publishes its durable run and record synchronously and returns a receipt immediately: a fresh reply identifier, a record kind, the record's own identifier, and the name `subagent:<canonical role>`. No clone, task lookup, session or execution happens before that receipt reaches the caller. The launch inputs — the captured caller, canonical role settings and enabled entries, the exact command line, context, offline state and remote target — are snapshotted at that moment; later edits to the invocation, settings or caller do not change the run. The first enabled entry supplies the record's model, and its effort is the supplied effort or `default` when omitted.

After the receipt, launch and settlement continue independently of the prompt that invoked it. Aborting the invoking prompt never terminates the subagent; only Terminate, the caller tab closing, the caller session closing, or shutdown do. A caller whose tab is missing, closing or stale is refused with no run and no provisioning. An ACP-tool caller with no caller role, internal session identity or provider id is refused with exactly `Subagent: caller session is not available.` and starts nothing; a person caller needs none of that metadata. Provisioning, task-resolution and executor failures after publication become the run's completion, never a rejected receipt. Concurrent launches for the same role keep distinct run ids, records, clones and replies.

### Replies and settlement

A started message is published once, only while the run is live and only for the first real provider handshake; a run that fails before that handshake sends no started message and reports a null session id. A person caller receives the started and completion as background replies appended under the original command line: the started reply carries a fresh background id and no record, while the completion carries the receipt's reply id and a link to the run's record. Replies are suppressed once the caller tab is closed, closing or a new incarnation, including a reused label. An ACP caller receives the same two messages as queued deliveries under the captured caller role with the captured provider id, and receives no human replies; the internal session identity is never serialized into a reply.

All post-creation work settles through one path. Provisioning, resolution or executor errors are reported with their original text, unchanged and without a fabricated prompt, added prefix, warning suffix or extra reply. An unexpected executor rejection additionally aborts the run's own controller before failed settlement so the failed attempt's resources can drain; a normal returned failure introduces no such abort. The run closes with the executor's status and response, which pass through verbatim — empty, whitespace-only, Markdown and multiline output all survive. Cleanup warnings from execution and settlement are aggregated side by side and never change the status, output or record answer. Only a recorded terminated outcome overrides the result with exactly `Subagent terminated.`; an aborted signal alone does not. Completion is latched and published once after cleanup has drained, so late callbacks cannot send a second reply.

### Remote clone lifecycle

A remote caller's run is published before any clone is requested or channel lease acquired. Its execution location stays the caller's captured directory in the durable metadata until a clone directory is returned; resolution then selects the clone by the label it was created with while execution metadata uses the returned directory, and no remote path is inferred or written back onto the run. Startup is admitted only while the run is live and the captured channel still owns the caller's label; a replaced or missing channel is refused with `Remote connection unavailable.` before any lease or request. Termination before startup, or between admission and queued startup, starts neither a lease nor a clone request and settles readiness as cancelled.

Once admitted, startup takes one channel lease, releases it if the run ends before the request is sent, and submits the clone creation; its allocation ends as soon as the request, cancellation and release ownership are installed, not when the clone becomes ready. A cancelled or failed pending creation requests release before awaiting the create result, then drains both; a late success after cancellation never becomes ready or reaches task lookup. If the run ends while the creation is still outstanding, the final release rejects any unsettled readiness as cancelled rather than leaving it pending, so settlement always delivers exactly one terminal completion; a directory returned afterwards is ignored and never reaches task lookup. Releasing the clone is shared and one-shot: repeated finishes, reentrant cancellation and late success cannot release twice or restart work, and a lost channel may leave the far-side clone until it shuts down.

A ready clone is released only after the execution it admitted finishes independently and reports no transport or session cleanup warning. A false or missing close acknowledgment, any cleanup warning, or an unexpected executor rejection retains the clone for the far side's eventual shutdown; outcome and output stay unchanged either way. Final release waits only on that independent execution barrier, never on the run's settlement or cleanup, so an active termination can finish execution while cleanup waits. Task-resolution failure with no admitted execution releases the clone normally. The channel lease is always the last thing dropped, including on retention or release failure. These operations run in registration order, and the run's final release happens after its other resources, including ACP cleanup.

### Boundaries

The grammar, messages, human wording, pending queue, and task prompt are pure. They neither register the command nor check grants, workspaces or command vocabulary. Caller kind, form, role and enabled-model policy, immediate refusals and the launch call are owned by the command-policy helper that the command's run delegates to. The registry, vocabulary, global disabled gate and public help remain outside it.

### Public registration

One command named `subagent` is registered in the command registry. Its first-token match is the exact, case-insensitive `subagent` word, so bare, flag, JSON, and malformed suffix forms all reach it while `subagents` and `subagent-x` do not. It declares the bare and valid-flag samples, carries the same core-response and ACP-tab availability metadata as `ask` and `tell`, and its run is the caller-policy helper itself: it preserves all four arguments and the helper's result unchanged and adds no parsing, caller decision, role lookup, launch call, or reply of its own. The command is offered wherever `ask` and `tell` are available, and `help subagent` describes the human flag form, the agent JSON form, the immediate empty agent output and later messages, the canonical-role Markdown replies and record link, the caller-specific usage and refusals, and the fresh-clone task boundary.

`subagent` is the one-word entry in the published native command vocabulary and owns one native tool in the caller-side ACP tool table, included only when the caller role grants it. That makes the earlier caller-policy, primer, receipt, delivery, human-reply, and disabled-gate contracts reachable from both a typed command and an `ask` or `tell` tool loop. A subagent's own tool table omits `subagent` whatever its role grants, so it cannot launch a subagent of its own. This registration changes no wire or protocol version.
