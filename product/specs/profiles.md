## Profiles

A profile is a reusable, named set of AI harnesses and the tabs that support them for a particular use case (writing code, surfing the web, authoring a book, a specific task). Profiles are managed by `src/profiles.ts` and the `profile` command (`src/commands/profile.ts`).

### Storage

Project profiles live in a top-level `profiles/` directory (its path is set by `initProfileDir` in `src/profiles.ts`), kept separate from `.janissary/` so they are committable and are **not** cleared on launch. Janissary never creates it; a project author adds it by hand. Janissary also ships built-in profiles in its own `profiles/` directory. Profile reads search the project first and then the Janissary installation, so a project file with the same name overrides the built-in file. Each profile is a single JSON file named in dasherized text (e.g. `writing-code.json`), or a runscript named `<name>.rs` (see Runscript profiles below). Within one directory a `<name>.rs` wins over a `<name>.json`, but the project still wins over the installation whatever the kind, so a project `foo.json` overrides a built-in `foo.rs`. `resolveProfile` in `src/profiles.ts` makes that choice. Its root object has one ordered **`tabs`** array holding every tab the profile opens, plus two profile-level keys that are not tabs: `monitors` and `layout`. An unrecognized top-level key is ignored, reserving that namespace for future config.

Each element of `tabs` names its kind with a root-level **`type`**, one of `harness`, `editor`, `files`, `notifications`, `schedules`, `plugin`, `image`, `markdown`, `page`, or `ssh`. A `harness` entry carries its own `name` field supplying its tab label; the other types derive their label the way the equivalent command does. Array position is not the launch order — `number` still orders the launch, and array position only breaks ties between entries with equal (or absent) numbers.

A harness entry names which binary to launch with a **`tool`** field (`claude`, `opencode`, or `codex`) — `type` is reserved for the tab kind — and supports:

- **model** — passed to the harness binary's `--model` flag, verbatim. Validated at launch against the known model catalog for that harness; an unknown model is reported (`Unknown model "<model>" for harness "<tool>" — add it to harness-models.json.`) and the entry is skipped, same as an unknown tool.
- **effort** — the effort level, verbatim, like `harness <name> --effort <level>`. Not validated against any fixed set of levels, and translated to whichever flag the target harness understands (claude `--effort`, codex `-c model_reasoning_effort=<level>`, opencode has none and drops it).
- **workspace** — launch in a fresh workspace clone. Defaults to true when omitted; set it to false to opt out.
- **browser** — start the tab's end-to-end browser, as the `harness` command does by default (see End-to-end browser in `harness.md`). Defaults to true when omitted, matching the command; `false` is the entry form of `--no-browser`.
- **autoApprove** — auto-approve the harness's own permission prompts. Defaults to true when omitted, since claude, opencode, and codex all support it. An entry that explicitly sets it to true for a harness without auto-approve support would be reported and skipped, same as an unknown harness or model. Works with or without `workspace`, but without it the launch reports a security warning notification, since prompts are then approved unattended with no sandbox.
- **autoResume** is *not* a profile field: a harness entry has none, so a profile-opened tab gets the launch default for auto-resume — on for opencode and codex, off for a harness with no recognized limit screen.
- **offline** — add a network-deny rule to the tab's sandbox profile, like `harness <name> --offline` (only meaningful alongside `workspace`).
- **remote** — an `on <address>` destination (see `remote-server.md`), launching this entry on another host. Implies `workspace`. A remote entry carries no `cwd` — a remote workspace path is neither under the local root nor meaningful on this machine — and the remote server resolves a fresh workspace at launch. An address that fails validation is reported and the entry is skipped, same as an unknown tool.
- **cwd** — starting directory (default: the issuing tab's cwd), expanded the same way the `files` command's path argument is — `$root` resolves to the launch directory and `~` to home, so a `cwd` can be written portably instead of as a literal absolute path.
- **run** — a list of commands typed into the harness once, shortly after launch (each becomes a one-shot schedule entry that fires on the first scheduler tick and then disappears from the schedule panel).
- **schedule** — a list of authored tab-schedule lines in the `schedule` command grammar, minus the `in <tab>` clause (the tab is implicitly this entry's own tab). A line that fails to parse, or that includes an `in <tab>` clause, is reported in the launch output and skipped; a duplicate schedule name within one entry keeps the first and reports the rest. A valid `system` schedule parse is reported and skipped as `Schedule "<raw>" for "<harness>" cannot target system schedules.` before tab-only fields are inspected. Malformed system grammar is reported with `Usage: schedule system NAME <form> script <name> | schedule system list | schedule system cancel <name> | schedule system clear`. Profile schedule lines cannot create, list, cancel, or clear project system schedules.

Every entry that takes a place in the tab strip — `harness`, `editor`, `plugin`, `image`, `markdown`, `page`, and `ssh` — carries its tab presentation as flat keys alongside `type`: `color` (the dot color), `number` (tab order; entries are opened in `number` order), `group` (an explicit group number this entry belongs to — see Tab grouping below), `groupColor`, `pane`, and `focus`. `pane` is either `left` or `right`; omitting it means left. If a launch has eligible tabs in both panes, the center action area opens split. Any main-area entry may set `focus: true`; after launch, the focused entry with the lowest tab number is active and the other pane selects one of its own tabs. If none declares focus, the first newly opened profile tab is active. A docked `files`, `schedules`, or `plugin` entry has no strip position and carries no presentation, and a `notifications` entry's own `focus` means something different (see below).

A harness entry's schedule and one-shot `run` commands are **memory-only**: no tab's state is saved, so closing the tab, quitting the app, or the harness process exiting ends the loop, and a launch does not restore it (see Harness Tab § Lifecycle). Re-running `profile launch <name>` recreates the whole setup from the profile file, which remains the single source of truth.

A harness entry's `run`/`schedule` commands are typed into the harness's own terminal, so they must be things that harness understands — not janissary commands. To start a janissary-level construct like a monitor as part of a profile, use the profile-level `monitors` key below.

### Malformed profiles

A profile file is validated once, in full, before any tab is opened. If the file is not valid JSON, its root is not an object, any element of `tabs` is missing its `type` or names an unrecognized one, any element is not a structurally valid entry of its own type (e.g. a harness lacking a string `name` or `tool`, or carrying a non-string `cwd`, a non-boolean `offline`, or a `run` or `schedule` that is not an array of strings — refused here rather than failing part-way through the launch), or `monitors`/`layout` has the wrong shape, `profile launch` reports `Profile "<name>" is malformed.` and opens **nothing** — no partial launch.

This structural check is distinct from the semantic launch-time checks. "Malformed" means the file's *shape* is wrong. The launcher's per-entry semantic checks are unchanged: an unknown harness tool, an unknown model, `autoApprove` on a harness without auto-approve support, and unparseable `schedule`/`run` lines are each reported and that one entry skipped while the rest launch. A structurally valid file naming an unknown model is not malformed — it launches, skipping that entry.

### Runscript profiles

A profile directory may hold a runscript, a `<name>.rs` file in the same format as a project runscript (see [[scheduling]]): one command per line, with blank lines and `#` comment lines dropped. `profile launch <name>` runs it instead of opening tabs, even when a `<name>.json` sits beside it. A runscript with no `.json` beside it is a profile too: it launches, and `profile list` and the picker list it. The runscript is run by `launchProfileRunscript` in `src/profile/runscript.ts`.

Its lines are queued to the managed system shell in one batch, exactly as `execute <name>` queues a project runscript, so they share that shell's FIFO with scheduled and manual runs and can be shell commands or Janissary commands. On success nothing is printed, matching `execute`. An empty runscript queues nothing and prints nothing. If the system shell cannot start, it reports its own failure and the launch adds nothing.

Any entry at `<name>.rs` claims the name, including a symlink. The runscript reader refuses a symlink or other non-regular file, as it does for project runscripts, and the launch reports `Could not read runscript for profile "<name>".`. It never falls back to the `.json` file. A runscript removed between being found and being read reports `No profile named "<name>".`.

A runscript profile opens no tabs, so the relaunch rule, monitors, layout, grouping, and placement do not apply, and the `.json` beside it is never read. A malformed `.json` next to a `.rs` is therefore never reported. A runscript line `profile launch <name>` naming its own profile runs the same runscript again rather than reaching the `.json`; nothing detects that loop.

### Profile-level monitors

A profile may declare monitors under a `monitors` key — a JSON array of `{ name, persona, targets }` objects, where `targets` is a list of authored target words in the `monitor` command grammar (`group:<n>` or a tab label; an empty list is inline mode). Each monitor's `name` is its runtime identity, distinct from its persona: two monitors may share a persona yet coexist under different names, and a relaunch refreshes the one whose owner and name match. `name` may be omitted, in which case it defaults to the persona. Once every profile entry is open, each monitor is started from the tab `profile launch` was issued from as `monitor <persona> <targets…>`, so its targets resolve against the complete tab list (including the just-opened entries). Being owned by the issuing tab rather than by a profile entry, a monitor keeps running when the profile's own tabs are closed; it stops when the issuing tab closes or via `unmonitor` from that tab.

Starting is **idempotent across relaunch**: before starting each monitor, any existing monitor with the same owner and name is stopped, so re-running `profile launch <name>` refreshes the monitors rather than reporting `Already monitoring`. Each monitor's outcome — started (with its resolved targets) or the parse/validation error that skipped it — is included in the launch report.

### Profile-level file navigator

A profile may declare one or more file-navigator tabs with `"type": "files"` entries. `dock` places the tree in that sidebar (`left`/`right`); `in` roots it at the named tab's working directory instead of the default; `path` sets a literal root, with `$root` resolving to the profile launch directory and `~` to home; and `details` selects the per-row detail (`name`, `size`, `modified`, or `permissions` — see [[file-navigator-tab]]). Omit `details` for the default `name` mode. When `in` is omitted, the tree uses the profile's first newly opened tab, or the tab that issued `profile launch` if no new tab opened. A profile path remains literal even when it is a directory named `print`, `expand`, or another file-navigator clause or view keyword, or when it contains whitespace, quotes, or a trailing backslash. An entry with no `in` or `path` uses the selected default tab's working directory; an absolute path such as `$root` is independent of that tab. Because a docked tree is never the active tab, opening and docking one of these can move focus away from the first newly opened tab to the nearest non-docked tab — the same invariant `files left`/`files right` already has outside of profiles.

An entry with no `dock` opens into the center tab strip like any other tab, and so also carries the usual presentation keys (`number`, `group`, `groupColor`, `color`, `pane`, `focus`), opening in its authored group, order, and pane. A docked entry has no strip position and carries none of them.

The `in` value is the tab's plain label, including any whitespace or quote characters in that label.

### Restoring a tree's view

A `files` entry may also record the tree's own view, as four keys holding paths relative to that tree's root: `expanded` (the directories that were open), `cursor` (the row holding the keyboard cursor), `anchor` (the range-selection anchor), and `selected` (every highlighted row). On launch each is replayed: a listed directory that still resolves is expanded, and a listed row that is still visible is re-highlighted, with the cursor row scrolled into view.

Restoring is **best effort and silent**. A directory or row that no longer exists is simply dropped, and nothing about the restore appears in the launch report — the same way a vanished expanded directory is dropped on any ordinary tree rebuild. If nothing survives, the tree opens with no cursor. A navigator whose root does not exist yet (the waiting-for-path case) restores nothing, and the restore is not retried when the directory later appears.

Restoring a selection does **not** move keyboard focus. The restored rows render highlighted, but which tab is active and which element holds focus stay exactly as the profile's own `focus` rules decide — a docked navigator is never the active tab, and it does not start stealing focus now. A restored selection is applied once, so an ordinary state refresh afterwards never overwrites a selection the user has since changed by hand.

The command-line form in [[file-navigator-tab]] restores the same view parts on a local tree. Unlike a profile relaunch, it changes only the parts its clauses name; profile launch continues to replace the whole cursor, anchor, and selection, clearing an unmentioned part.

### Profile-level editor tabs

A profile may declare editor tabs with `"type": "editor"` entries, each supporting `path`, `in`, and `line`. Each opens the named file in the plain-text editor after the profile entries and file navigators are open. `path` is required; `$root` expands to the launch directory, `~` to home, and another relative path resolves from the working directory of `in` or, when omitted, the profile's first newly opened tab — falling back to the issuing tab when the launch opened no tab of its own, the same as a `files` entry. `line` places the cursor on that line, and the usual presentation keys — `number`, `group`, `pane`, `focus` — apply. Although editor tabs are created after the harness entries, the tab strip's final order is not "entries then editors" — once everything is open, an editor tab's `number` places it among the entries' tabs, so a lower-numbered editor tab sits ahead of a higher-numbered entry. An editor with no authored `number` keeps its created-order position at the end of the group, after every numbered tab. An editor's `group` places it into that group directly, the same as a harness entry's own `group` (see Tab grouping below); an editor with no authored group joins the launch's default group.

A path that does not yet exist opens an empty, unsaved editor buffer, which creates the file only when saved. Relaunching the profile reopens each declared path; an already-open file reuses its editor tab and moves the cursor to the requested line instead of creating a duplicate. A `path` covered by GitHub syncing (see Editor Tab) opens as a synced editor exactly as typing `edit <file>` on that same path would, provisioning or reusing the shared sync workspace on demand — so an editor entry authored with the project-relative source path, not a path inside the sync workspace itself, is what makes a profile-launched synced tab show real content instead of an empty buffer.
If the editor refuses a path, such as a file above the editor's size limit, the refusal is reported
normally and that entry is not placed, focused, or reported as an opened editor tab. Other active
tabs remain where they are.

### Profile-level plugin, page, and ssh tabs

A profile may declare three further tab kinds, each opened by issuing the same command a user would type: `"type": "plugin"` takes an `id` naming the bundled tab plugin that owns the tab (`image`, `markdown`, `video`) plus the `path` it was opened on, and an optional `dock` (`left`/`right`) that opens the tab docked into that sidebar instead of in the tab strip, `"type": "page"` takes a `url`, and `"type": "ssh"` takes a `destination` plus an optional `options` list holding the remaining tokens of the original `ssh` invocation, so a relaunch reconnects with the same flags. Paths expand exactly as an editor entry's `path` does. None of these entries authors a `name`: each tab's label is derived at open time the way `open` and `ssh` derive it. They open after the editor tabs and take part in the same placement pass, so they honor `number`, `group`, `pane`, and `focus` like an editor entry does.

`"type": "image"` and `"type": "markdown"` are the older spellings of a plugin entry from before those views became bundled plugins. Both are still accepted and launch identically to `{"type": "plugin", "id": "image"}` and `{"type": "plugin", "id": "markdown"}`.

Relaunching matches these tabs by identity rather than by label: an ssh tab to the same destination is closed first and reported as relaunched, so exactly one tab per entry is left. A plugin tab opened by the same plugin on the same subject — the same file, or the same web address — is instead reused in place, and still moves into its authored group and position. A plugin entry with no subject — a `shell` tab, say — opens a new tab each time, and it is that new tab that moves into the entry's group and position: a shell already open, the launch shell included, is never taken for it. If the command opens nothing, the fallback cannot select the launch shell or managed system shell for placement, grouping, docking, or focus. A `shell` entry opens its shell without a workspace, as `shell --no-workspace` would, so a profile never starts a workspace clone once per saved shell; an entry cannot ask for one. An entry that opens no tab — a path that does not exist, an ssh invocation that does not parse — is reported and skipped while the rest of the launch continues; a plugin entry reports the plugin by name (`Could not open image tab "…"`).

### Profile-level notifications tab

A profile may declare that the notifications tab should open on launch with a `"type": "notifications"` entry, where `dock` docks the feed into that sidebar (`left`/`right`) and `focus` (only meaningful alongside `dock`) makes the notifications tab the visible one in that sidebar's internal tab-switcher, overriding the default "most recently docked tab wins" behavior — useful when a file navigator or the schedules tab is also docked to the same side. Once every profile entry is open, each entry opens or docks the singleton notifications tab, mirroring the `notifications [left|right]` command. Because the notifications tab is a singleton, more than one entry simply re-docks the same feed.

### Profile-level schedules tab

A profile may declare that the schedules tab should open on launch with a `"type": "schedules"` entry, where `dock` docks the list into that sidebar (`left`/`right`). Because the schedules tab is a singleton, more than one entry simply re-docks the same list. The schedules list is supplied by a bundled plugin, so a `plugin` entry naming that plugin means exactly the same thing; a `"type": "schedules"` entry keeps working.

### Profile-level layout

A profile may declare the size of the application window, the left/right sidebars, and the split between the upper action-tab area and the lower reporting-tab area under a `layout` key. Its value is the layout object directly: `{ "sidebar": { "left": 320, "right": 280 }, "tabAreaPct": 75, "window": { "width": 1440, "height": 900 } }`. The left/right sidebar widths are grouped into a `sidebar` object parallel to `window`; `window.width`/`window.height` are pixels; `sidebar.left`/`sidebar.right` are pixels; `tabAreaPct` is 0-100 and is the upper action area's share of the vertical split.

The `layout` command can set these sizes during a run. `layout reporting <percent>` names the lower reporting area's share, so `layout reporting 0` and `layout reporting 100` correspond to `tabAreaPct` values of 100 and 0.

The layout is applied once every entry is open, on **every** `profile launch`, including a relaunch — it always overrides whatever the user had manually resized things to. Any dimension the `layout` key doesn't mention resets to the app's built-in default (1280x800 window, 300px sidebars, and a 20% reporting-section height) rather than being left at whatever it currently is. Sizes are applied exactly as specified, even if they exceed the manual-drag limits on sidebars or the reporting split, or the screen's own bounds — a profile's numbers are trusted as authoritative. (A malformed `layout` field makes the whole profile malformed — see Malformed profiles above.)

When the server was started with `--no-open` (no application window opened), the window-size portion of `layout` is ignored entirely — no resize attempt and no report note — while the sidebar/tab-area sizes still apply to any connected browser client. Window-size restoration remains reliable while the managed browser is still completing other startup work.

### `profile launch <name>`

Typing bare `profile launch` (no name) opens a picker listing profiles from the project and the Janissary installation in two labeled sections, Project first and Janissary second. Each section lists the profile names of that source alphabetically, one row per name whether it comes from a `.json` file, a `.rs` runscript, or both; a subdirectory inside a `profiles/` directory is never listed, so the picker is a flat list of launchable profiles with no directory rows to expand. A same-named built-in profile is omitted when the project supplies an override, and an empty source's section is omitted. The profile list travels with the app's state updates and, like the task list (see [[task-picker]]), the server re-reads the two profile directories at most once per second, so a profile file created on disk can take up to about a second to appear in the picker. Mirroring the `tasks` picker's interaction, arrow keys move the selection while skipping section headers, Enter or a click populates the command line with `profile launch <name>` without submitting it (so it can be reviewed or edited first), and Escape closes it. When a profile is added or removed while the picker is open, the selection is kept on a real profile row exactly as the task picker keeps its own (see [[task-picker]]): it moves off a section header or back inside a shorter list by position, a key pressed before that correction renders only re-seats it without picking, and Escape always closes.

The command is placed in the bar that opened the picker, including a docked shell's own bar, and is never submitted by the selection. If that tab closes while the picker is open, selection does not insert the command into another tab. On a harness tab, selection sends the command directly to that harness's PTY.

A runscript profile runs its runscript instead (see Runscript profiles). Otherwise, opens a tab for each entry in the named profile, in `number` order. For a harness entry, a harness tab is opened directly (see Harness Tab) with the entry's model, starting directory, and workspace flag. Profile-level editor tabs open next, then the plugin, page, and ssh tabs; a plugin tab (a web page included) opens through its plugin's activation, so the launch waits for it before placing and focusing tabs. Once every main-area tab from this launch is open, the whole set is reordered in the tab strip by `number` (every kind together, an unnumbered tab sorting last, after every numbered one), and the focused main-area entry with the lowest tab number becomes active; when none declares focus, the first newly opened tab remains active. A missing profile returns `No profile named "<name>".`, a malformed one returns `Profile "<name>" is malformed.`, and one declaring no tabs at all returns `Profile "<name>" has no tabs.`.

**Relaunching.** A profile may be launched more than once. Before opening any entry, every currently open tab whose label matches an entry in the profile is closed first (killing its PTYs/shells, dropping its schedule, and removing its workspace clone), and then every entry opens fresh — so a relaunch always gets a new process, a schedule re-based to "now", and a new workspace clone where applicable. An entry named `system` in any casing is reserved and is skipped before any tab lookup or close side effect; the launch report lists it exactly as `system (reserved for the system tab)`. The other exception is the tab `profile launch` was issued from: it is never closed, and if the profile names an entry matching its label, that entry is reported and skipped instead, so the launch report always has a tab to land in.

**Name clashes.** A harness entry's `name` is treated as a typed name: it is never renamed with a `-2` suffix. After the relaunch rule above has closed matching tabs, an entry whose name is still in use — by an open tab, by a live row in the sessions tab, or, for a remote entry, by something running on its host — posts the same `Cannot launch "<name>": …` refusal to the notifications feed that a typed launch does, attributed to the tab `profile launch` was issued from. The entry is then listed under `Skipped:` in the launch report as `<name> (launch refused — see notifications)`, and the remaining entries still open. A leftover workspace folder under an entry's name is removed before its clone, as for any launch (see `workspaced-agent.md` and `remote-server.md`).

Each main-area tab joins the group its own `group` key authors, when set. Any entry or editor that authors no group instead shares one default new group (the next free group number). A group's bar color is fixed to the color of whichever tab lands in it first during this launch — or, when the launch joins a group already open on screen, that group's existing color — so each group of tabs reads as its own band, distinct from other groups already open and from other profiles. Tabs sharing a group are kept contiguous in the tab strip. See Tab grouping.

### `profile list`

Lists the available project profiles followed by built-in Janissary profiles (each `profiles/*.json` and `profiles/*.rs` file with its extension stripped, a name with both files listed once, and each source sorted), or `No profiles.` when neither source has any. A project profile hides a same-named built-in profile.

### `profile` command

`profile` launches a set of harnesses and the tabs that support them, described in a profile file. See the Profiles section. `profile launch <name>` opens a tab for each entry in the named profile, closing and reopening any tab that collides with a relaunch; `profile list` lists the available profiles. Malformed invocations, including an unrecognized subcommand, return `Usage: profile launch <name> | profile list`.
If an asynchronous launch fails, its issuing transcript receives one
`Profile command failed: <reason>.` result instead of leaving the command unfinished.

### Group names

Every tab presentation may carry `groupName` beside its numeric `group` ID. `profile launch` restores that name with the same ID. An older profile without `groupName` uses `launch` for ID 1 and `group-<id>` for another explicit ID; an entry without a `group` uses the name assigned to the profile's newly allocated group.
