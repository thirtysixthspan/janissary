### State directory

No tab's state is written under `.janissary/`: shell and harness tabs, like every other tab, are live and in-memory, and no launch recreates them (see `application-state.md`).

On every `janus` launch the per-run directories — browser logs, git-failure output, and the workspace directory — are recursively deleted before rendering. Recordings under `.janissary/recordings/`, harness capture files under `.janissary/captures/`, activity logs under `.janissary/logs/activity/` (see [[activity-log]]), per-run server logs under `.janissary/logs/server/`, and harness and shell transcripts under `.janissary/transcripts/harness/` and `.janissary/transcripts/shell/` are kept across launches and swept by age at launch instead (see `harness-recording.md` § File naming and lifecycle and § Session transcripts, [[harness]] § Screen capture, and `shell-tab.md` § Text transcript). Server logs are swept as regular `.log` files directly inside their directory, using a cutoff that is the earlier of `logRetentionInDays` days before launch and one hour before launch; the one-hour floor holds even when the setting is `0`, and the `latest.log` symlink is exempt. See [[cli]] for how each run's log is named and when the link is repointed.

Concurrent `janus` processes are only safe when targeting distinct directories. A PID lock file at `.janissary/lock` prevents two processes from sharing one directory at the same time, so the second process cannot clear state out from under the first. On shutdown, the lock is removed only while it still holds the shutting-down process's pid; a lock that another starter took over in the meantime is left in place, so that starter keeps the directory. The lock refuses a recorded pid only when this user can still signal it, so two instances running under different accounts in one shared directory are both admitted — and the remote-sessions record file (see `sessions-tab.md`) is therefore named per account, `remote-sessions.<account-hash>.json`, with each instance writing only its own and a load merging every account's file into one list. The pre-keying `remote-sessions.json` is read the same way, so a parked session survives the upgrade untouched.

System schedules are durable project data at `.janissary/system-schedules.json`; runscripts live at `.janissary/scripts/`. Neither path is part of the per-run clear registry, so schedule data and scripts survive startup cleanup. The project-owned schedule list loads after local shell preparation, recovers missed entries before the scheduler starts, and is independent of tab lifetime. When saving schedules in a Git project, Janissary honors existing ignore rules or adds narrow entries to that repository's local exclude file. It never rewrites the project's `.gitignore`, and refuses to save when either target is already tracked.

### Hosts files

Saved hosts are durable configuration at `~/.janissary/hosts.json`, overridden by the project's `.janissary/hosts.json` in the same whole-file way as `roles.json` and `commands.json`: a usable project file replaces the home file entirely, including an empty object, which explicitly holds zero hosts. The two files are never merged. When no file exists, the catalog is empty and the first save creates the file in effect.

A project file that cannot be read or decoded does not take effect — the home file is used instead — while an unusable home file leaves no hosts available and refuses saves. Janissary never rewrites an unusable file to repair it. Each unusable file consulted is reported once as `Hosts file <path> is unusable: <problem>.`; the notice is repeated only when the problem changes or returns after the file is fixed. Successful saves replace only the file in effect, preserve every other entry, and leave an unusable project file's bytes untouched.
