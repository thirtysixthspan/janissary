# ACP

ACP is a core service for starting and querying Agent Client Protocol connections. Shell tabs use it through their command bar and a settled Markdown reply beneath the typed line. Live activity belongs to the connection tab, not an in-tab response panel. Any tab plugin can request the scoped core API without owning a terminal. Harness tabs have no ACP command or prose route. Monitors, conversations, and editor queries retain their separate sessions over the shared protocol transport.

## Availability and plugin API

A plugin requests `startAcp`, `promptAcp`, and `resetAcp` in its declaration. Each capability is bound to that plugin's own answering tab, or its own invoking tab when there is no answering tab. It cannot start or query a different plugin's tab or a shell tab that invoked its command. An unavailable or disabled owner returns the ordinary request rejection `ACP tab is unavailable.`.

- `startAcp()` begins or reuses the tab's connection and returns `{ model }`, the identity of the session it began or reused, or `{ error }`. Startup is lazy and the handshake may still be pending. It takes an optional request: `startAcp({ withoutTools: true })` records that the tab's session runs without a tool table, so no browser, question, or database command can run on it and no reply line is recognized as one. The request belongs to the tab, so it holds for every prompt on that session and is forgotten only when the tab closes.
- `promptAcp(prompt)` runs the core database/browser/question loop and resolves with the final answer. Connection startup is automatic if needed. Provider and tool wait time belongs to core and is exempt from the plugin handler deadline.
- `promptAcpResult(prompt)` runs the same prompt and resolves with a result rather than a string: the reply and the session that produced it, or the reason there was none. A refusal resolves with a line of prose, so a caller handed one string cannot tell an answer from a refusal without reading its text. A result may also carry an optional `recordId`, the id of the connection record that holds the final attempt's prompt block: the answering model's record, or the last model's record when every model failed and that attempt created one. If the last attempt fails before creating a record, it carries no id, even when an earlier attempt created a record. Refusals also carry none.
- `resetAcp()` closes the connection and returns whether one existed. It settles in-flight requests and prevents obsolete callbacks from updating a replacement prompt.

A plugin requesting `promptAcp` supports the core `ask`, `ask reset`, `tell`, and `tell reset` commands. The shell requests all three operations. `ask` commands and plugin capabilities continue to address the `ask` role by default; the `tell` commands use the `tell` role. Core callers can run one `ask` and one `tell` prompt at the same time; a second prompt for the same role is refused while that role is active. A terminal, `spawnTerminal`, and `hostsCommandBar` are not prerequisites for the ACP API. Core owns protocol I/O, session lifecycle, tools, transcript state, and settlement. There is no ACP plugin or client response hook. Plugins retain their scoped transcript-snapshot action and completed background-reply subscription.

## Commands

`ask <prompt>` queries the current supported tab's ask-role connection. Bare `ask` prints `Usage: ask <prompt>.`. `ask reset` ends only that role's connection and reports `ACP session reset — next ask prompt will start fresh.`, or `No active ACP session to reset.`. `tell <prompt>` instructs the tell-role agent to carry out a task and briefly report what it did; bare `tell` prints `Usage: tell <prompt>.`. Its primer includes `The user is instructing you to carry out a task. Do it with the commands available to you, then briefly report what you did.` after the tool primer and its tool-availability line and before the Markdown instruction. `tell reset` ends only the tell-role connection and reports `ACP tell session reset — next tell prompt will start fresh.`, or `No active ACP tell session to reset.`. The command was formerly named `acp`; that word is no longer a command, so `acp <prompt>` and `acp reset` are unknown commands.

Each prompt and reset confirmation is one completed background reply beneath the exact line typed, with no immediate duplicate. Resetting a role interrupts only that role's prompt, producing two distinct replies: the original prompt's one `ACP session closed.` reply and the reset invocation's one confirmation. Resetting again reports that role's no-session message once.

A shell `ask` or `tell` prompt does not hold its command bar. The shell echoes the exact command line that was typed as soon as the command is accepted, and other lines keep working while it runs. When it settles, the shell writes exactly one Markdown reply. It goes directly beneath that echo when nothing else has reached the terminal since; otherwise it goes at the current bottom of the output beneath a second echo of the line, so it still reads correctly after other commands ran in between. [[shell-tab]] gives the placement rules. That happens once for an answer, a same-role refusal with `ACP: a prompt is already running.`, a usage line, an `ACP error: …` line, `ACP session closed.` after reset or close, and `ACP: prompt cancelled.` after cancellation. A second prompt for the same role while it is running is refused without disturbing the active prompt, and nothing queues. Callbacks arriving after settlement add no second reply.

The shell's ordinary application-command dispatcher recognizes these commands and marks their replies as core-rendered, so dispatch itself adds no immediate terminal line. Unclaimed shell-bar lines still go to zsh; use an explicit `ask` or `tell` prefix to query the connection. See [[shell-tab]].


## Provider and model

The `ask` role's model entries and native-command grants come from the roles file in effect — the project's `.janissary/roles.json` when it exists, otherwise `~/.janissary/roles.json` — matched by name trimmed and in any case. The settings are read once for each logical prompt and reused by every model attempt for that prompt; a file edit affects the next prompt. Reading never creates a roles file. When the effective file has no `ask` role, both entries and grants come from the built-in `ask` role. When an existing role has no entries, its model entries fall back to the built-in defaults, but its own grants are retained: an empty or missing `commands` list grants no tools. The built-in model entries are `opencode` `opencode-go/deepseek-v4.1-flash` at `medium`, `claude` `claude-haiku-4-5` at `high`, and `codex` `gpt-6-luna` at `high`. A nonempty stored entry list does not fall back to built-in models if every stored model is disabled. See [[roles]].

Each entry launches its harness's ACP agent. `opencode` runs `opencode acp` with the entry's model. `claude` runs the Claude Agent ACP adapter bundled with Janissary with the entry's model. Its effort is passed as `CLAUDE_THINKING_EFFORT` for parity with the deprecated adapter, but neither adapter reads it, so the effort has no effect. `codex` runs the Codex ACP adapter bundled with Janissary, with the entry's model and, when set, its reasoning effort; the model and effort reach the adapter through its `CODEX_CONFIG` setting, and a role launch also starts codex in its read-only mode. Neither adapter is fetched through `npx`: both are found in the install's own `node_modules/.bin`, which is searched ahead of PATH. If a bundled adapter is missing there, that model fails to start and the request uses the existing role model fallback, even when the server or interactive-shell PATH contains a same-named executable. An adapter found there runs with the directory of the Node that runs Janissary added to the front of its PATH when that PATH neither lists that directory nor resolves `node` to the Node that runs Janissary, so the adapter starts even when Janissary was launched without `node` on its PATH; the rest of PATH is kept as it was. Both adapters are pinned to exact versions, and the names a role launch runs are the command names those pinned packages declare, so an adapter update that renames its command is caught before release rather than sending role launches to an unpinned copy on PATH. An entry naming any other harness fails at once with `ACP error: no ACP adapter for harness "<name>".`. `opencode` must be installed and on PATH; every harness must be signed in. A bare agent command missing from the server's own PATH is looked up on the PATH the user's interactive shell sets up, so an agent installed through a version manager's rc-file setup starts the same way it does in the user's terminal. The agent then runs with that PATH.

An agent outside a workspace, such as a monitor session or a session on a tab with no workspace, receives the configured `claude-token`, `opencode-token`, `kilo-token`, and `gemini-token` credentials in its environment under the same variables a workspaced tab gets, so an `opencode` that was never signed in on the machine still authenticates from a token file. A token file's value takes precedence over the same variable exported in the server's environment. The GitHub token is never handed to such an agent; it stays workspace-only. A workspaced session receives every credential through the workspace, as before. See [[workspaced-agent]].

### Model fallback

A request tries the selected role's open session first, when there is one, then that role's other entries in order. A model fails a request when the request would settle unanswered before that model completed a reply turn because the agent could not start, exited, or returned an error during the handshake or the prompt — missing credentials, exhausted credits, or a rate limit, for example — or because its harness has no adapter. The failed session is closed, the transcript shows `ACP: <harness> <model> failed — trying <harness> <model>.`, and the request runs again on the next entry, which starts a fresh conversation. Once a model has completed a reply turn the request stays with it: a later error is reported as usual, so a tool the agent ran is never run twice. Refusals, cancellation, and reset or close never fall back.

Before each attempt, ACP filters the selected role's ordered entries against the current model catalog. Disabled entries are skipped, including that role's open session's current model; if it became disabled, that session is closed and the next enabled entry is tried. The request fails only after every enabled entry has been tried. With more than one entry tried it settles with `ACP: every model in the <role> role failed.` followed by one `- <harness> <model>: <error>` line per attempt; with one entry it settles with that entry's own error. The last model's session stays open after a prompt error, as any prompt error leaves a viable session. Each role reuses its own answered model and session on later prompts. A role with no enabled entries refuses with `ACP: the <role> role lists no models.`. `startAcp` starts the ask role's open enabled session or first enabled entry that can be launched and reports that entry's model; its first prompt still falls back if that model fails.

The session's configured provider/model appears in its connection row after the handshake. Role connections deny every internal tool in two layers, always, with no opt-out. First, each harness turns off its built-in tools as far as its own configuration allows. `opencode` keeps its built-in tools in the model's list and denies every call through a deny-all permission setting, `skill` included, so a model can still try one and be refused; `claude` starts with an empty session tool set; and `codex` starts in its read-only mode with web search, its shell tools, and its other built-in tool features disabled, so it never offers them and its approvals are still asked. Codex's file-edit tool has no off switch and stays behind the read-only mode's approval. Any other harness is refused at launch today. If a harness later gains an ACP adapter in `acpLaunchForEntry` but no deny-all entry in `internalToolDenial` (`src/acp/internal-tools.ts`), it would run with the second layer alone and no warning. A role session hosted on a remote machine gets both layers: the remote launch request carries the same built-in-tool configuration, session options included. Second, the shared ACP transport denies every permission request a role session's agent raises; only a separate consumer's own allowlist, such as a monitor's web tools, or an autonomous run approves one. A denied request on an `ask` or `tell` session appears in its connection record as a `permission` activity entry carrying the refused tool call. A request refused because its prompt was cancelled or the session closed records nothing.

## Connection lifecycle

Every successful core-tab handshake begins a durable project-scoped record for that role, including plugin-owned ask sessions and the launcher summarizer. The configured model, role, and original owner name are captured then. Existing records without a role remain readable with their saved title and name. Local connection startup remains lazy: starting alone need not finish a handshake or create a record. An accepted first prompt is reserved before handshake and recorded before any activity. Each logical prompt has one block across tool turns and cold-start retry; a prompt that falls back to another model leaves its block, answered with the error, in the failed session's closed record and continues in a block of the next session's record. Refusals create no block and never settle another request. Native message, thought, tool, plan, and permission activity retains exact whitespace, without duplicating display chunks. Host commands and results are ordered tool entries. See [[acp-records]].

Core keeps a separate connection and record for each role on a tab. It starts each connection on demand, reuses it across that role's prompts, and closes only the selected role on reset. Closing a tab, losing its shared remote transport, plugin teardown, or shutdown closes all of its role connections. A local subprocess starts in the tab's working directory at connection creation; a workspaced tab passes its workspace and offline confinement to the existing sandbox. A changed directory does not replace an already-open conversation. See [[sandbox]]. Local agent cleanup sends a graceful termination signal to its owned ACP process group and awaits exit before releasing the execution workspace. If the process tree does not exit within one second, cleanup escalates to a forceful signal; if exit still cannot be confirmed within five seconds, cleanup reports a warning and continues releasing resources without replacing the task outcome. A process-group existence probe that fails with a permission error is treated as present, not as confirmed exit, so it follows the same bounded shutdown and warning path.

`AcpManager` in `src/acp/manager.ts` owns prompt orchestration. An overlapping prompt is refused with `ACP: a prompt is already running.`, without cancelling the existing one. A reset or close settles a pending call with `ACP session closed.`. A fatal connection error is shown and the session is forgotten; the next prompt starts fresh. A prompt-level error leaves a viable session intact, including rate limits. Every one of those settles with a result saying which kind of line it is, so a caller that acts on what it is handed can tell a refusal from an answer.

A session carries an identity minted when it is created and forgotten when it is closed, and `startAcp` reports it beside the model. A caller that primed one session — a persona, a trust delimiter — compares it to learn that the session it is now talking to is a different one, because a replacement arrives with nothing the previous one was told.

### Cancellation

Core cancellation returns false when no logical request is active and starts no connection. Otherwise it aborts that request's host loop and active or queued question immediately, preserving unrelated questions. Concurrent calls share one cancellation. Running browser or database work may still complete; its late result cannot dispatch another command or provider turn.

The request stays reserved for its role and `Running` until both the native cancellation notification write and the original provider turn finish. Provider completion does not release the turn while its cancellation notification is still pending, and notification completion alone is not provider drain. Another prompt for that role during the interval receives `ACP: a prompt is already running.`; the other role may continue independently. Final native activity stays in the cancelling block. After both boundaries complete, the request settles once with `ACP: prompt cancelled.`, becomes `Idle`, and a later prompt reuses the same session identity and record UUID. Cancellation before handshake finishes initialization on the viable session but never sends the cancelled prompt or a notification with an undefined session id. Native permission requests after cancellation are denied as cancelled.

Reset or close wins during drain, settles immediately with `ACP session closed.`, closes the record, and releases cancellation callers. Fatal loss also settles and closes once. A cancellation-send rejection, including one after provider completion, closes the failed session with `ACP: cancellation failed: <reason>` and does not settle as a successful cancellation. There is no cancellation timeout or forced process kill for a healthy provider: one that never drains stays reserved until reset, close, or fatal loss. A shell prompt settled this way still produces exactly one background reply. This backend operation adds no command, plugin capability, or button.

Pending requests and current records are kept separately for each role on the tab. Transcript entries and record ownership stay tab-wide, so role sessions continue to appear in the shared transcript and connections list. Each prompt updates only the running entry it created, even when role streams interleave; immutable replacements retain that prompt's entry identity. The tab remains busy until every active ask or tell prompt and shell command settles; one operation settling never hides another that is still active or finalizes another role's or a shell entry. Existing transcript limits and persistence behavior remain in force; saved records without role metadata are not migrated or renamed.

## Answers, activity, and questions

The shell shows the settled answer as sanitized GitHub-flavored Markdown and adds a pointer-operated marker to accepted `ask` and `tell` echoes. The marker opens the role's live connection tab while the prompt runs and becomes a link to the answering record after settlement; [[shell-tab]] describes its placement and edge cases. The shell has no ACP response panel, streaming activity, or Reset ACP button. Thinking, tool steps, live activity, and prompt history appear in the connection tab. The shell's tab dot still blinks during the operation. See [[connections-tab]].

The connections panel's ACP rows open or focus the corresponding connection tab when they carry a durable record or the tab's own live ACP reference. Rows that offer a transcript snapshot keep that separate button, and clicking it never opens the record tab. See [[connection]].

Role resets are available through `ask reset` and `tell reset`, each closing only its matching role. The connection tab's **Close session** action closes the role shown by that record, and `connections close acp:ask:<model>` or `connections close acp:tell:<model>` closes the named role. A legacy `connections close acp:<model>` target still selects ask. Transcript snapshot actions remain available without a response panel. File and web links in Markdown replies retain their existing targets.

Questions use the existing core question panel and answer protocol. A centre tab's question is shown once when that tab is current. Any selected active docked plugin tab shows its pending question, even before any ACP response exists and without a plugin hook, terminal, or command bar. A hidden docked body does not raise one; returning to it restores a still-pending question. The question's tab/id determine where the answer goes. See [[agent-questions]].

Reset or close aborts the current ACP request's question, whether active or queued, and preserves unrelated questions. An aborted loop does not issue another provider prompt after a tool returns. Calls without an abort signal retain the existing question lifecycle.

The connections panel lists core sessions as `acp:<role>:<provider/model>`, with separate ask and tell rows, and its close action targets the row's role. The transcript snapshot button remains available on surfaces that offer one and uses the existing shared tab transcript; monitor and editor transcript scopes retain their own recorded exchanges. See [[connection]].

## Autonomous tool loop

Each user prompt receives primers for every tool owner granted by that prompt's role. The allow-list line `Only these commands are allowed: <commands>.` lists only granted commands whose effective agent access is enabled for that prompt, in native-command catalog order and deduplicated. Unknown grant strings are ignored. A granted owner keeps its group primer even when all of its commands are excluded, and the allow-list line is omitted when no command remains. When at least one command remains, the allow-list line is followed by `You have no built-in tools; use only the commands listed here.`. When none remains, `You have no tools; answer in prose.` takes the allow-list line's place, right after any group primers. A role with no recognized grants receives no tool table or group primers, so its primer starts with the no-tools line. The allow-list and primer are built when the model attempt starts, from `runCorePrompt`'s `coreSnapshot`: one `AcpRunSnapshotRow` per native command from the prompt's captured native-command settings, or no rows when no settings manager or settings snapshot is available. The settings are read once for each logical prompt and reused by every model attempt for that prompt: `AcpManager.run` reads `managers.nativeCommandSettings.current()` once before the first model attempt and carries the value on the attempt record, so a fallback rebuilds the same rows. `gateCommand`, extraction, and the allow-list read that snapshot only. A settings change applies from the next prompt, as does a change to a role's grants or name. A missing settings manager or row allows the command.

`runAcpToolLoop` in `src/acp/loop.ts` streams each turn, extracts the last recognized granted-owner command line, runs it, and feeds the result back until there is a final answer or eight tool steps have run.

The tools are declared once in `src/acp/tool-table.ts`: browser, question, file, then database. Their order controls command ownership; the database entry stays last because its `match` is the fall-through for a command no other tool recognizes. Extraction selects the reply's last recognized tool line. Fences and common prompt prefixes are tolerated. Only the final occurrence of an emitted command is removed from the displayed reply. A command is matched against the case-insensitive native vocabulary, with trailing arguments accepted. `gateCommand` in `src/acp/tool-table.ts` checks each emitted command against the prompt's snapshot, not the live settings. A command whose setting in that snapshot is disabled, or whose agent access there is off, returns exactly `Command is disabled: <command>.` as a normal tool result and is recorded as one tool step. That check runs before the role-grant refusal, so a disabled command the role did not grant reports the disabled refusal. A missing settings manager or setting row allows the command. A command already running is not interrupted.

The prompt's snapshot is not the only guard on the caller side. A caller-side command still passes `refuseDisabledCommand` in `src/native-commands/dispatch-policy.ts` when `dispatchNativeLine` dispatches it, so a command disabled mid-prompt is refused on its next caller-side run with `Command is disabled: <command>.` and the `command-disabled` notification; a change to agent access has no live guard. A workspace command such as `file read` does not pass the dispatcher, so the prompt's snapshot governs it for the rest of the prompt.

A known command from an included tool owner that is enabled and has agent access on, but that the role did not grant, returns `Command not allowed for role "<role>": <subcommand>.` as a normal tool result; it is recorded and consumes one of the eight steps. A disabled or agent-off command returns `Command is disabled: <command>.` before the role check, even when the role did not grant it. A command from an omitted owner or an unknown subcommand is not extracted, and unknown commands cannot fall through to the database runner. A cold, empty first reply is retried once in the same transcript entry.

`browser …`, `question …`, and `db sqlite …` commands are caller-side: when enabled and granted they are dispatched through the ordinary command dispatcher rather than calling a browser, database, or question service directly. A workspace command such as `file read` does not pass the dispatcher: it goes to `readFileInTab` on a local tab or `readWorkspaceCommand` on the far side, which is why a typed read and an agent read share one root and one set of messages. ACP dispatch has no plugin capture deadline, so a pending question or slow browser call is not settled by one. The command's normal browser, database, file, or question output is returned to the loop; only the single `acp: true` tool transcript entry is added, with no interactive or appended duplicate. Cancellation aborts a pending question, which resolves `Question cancelled.`; browser and database work may still finish, but its late result and the next provider turn are suppressed.

A session a plugin started with `withoutTools` builds no tool table at all, regardless of role grants. Its primer carries only the no-tools line `You have no tools; answer in prose.`, no reply line is read as a command, and an emitted command has nothing that runs it — the loop answers with the reply as prose. This policy belongs to the tab and applies to every prompt on it, including prompts typed with `ask` or `tell`, until the tab closes. A typed prompt command on an unrestricted tab uses that role's filtered table.

Tool results are recorded as ACP steps and appear in the connection tab as expandable thought and tool entries. When the tool loop reaches its cap, the settled shell reply and the record's final answer end with a trailing `(stopped after 8 tool steps)` paragraph rather than a separate transcript entry. Arbitrary shell commands are not ACP tools. A remote tab or a remote agent run executes the loop on the host running its agent, so workspace reads resolve against that host's clone; database, browser, and question execution remains on the machine running Janissary and travels back as the tool result.

### File read

`file read <path> [--offset <line>] [--limit <lines>]` is both a typed application command and a tool in the autonomous loop. `parseFileRead` in `src/file-read/command.ts` accepts one path token and the optional flags; `--offset` defaults to 1 and `--limit` to 2000. One read prints at most 2000 lines, and a file over 5 MB is refused. The path is a single whitespace-free token relative to the root. `help file` is its typed reference page; this section states the behavior both forms share.

A local tab reads its workspace directory, or its launch or project directory when it has no workspace. A remote tab reads its remote clone through the `read-lines` operation and never local disk. The loop's workspace tool reads that same root on the host running the loop: `readFileInTab` locally, `readWorkspaceCommand` in `src/file-read/read.ts` on the far side. Writes and edits use that same far-side root through `runFileMutation` with the remote machine's local filesystem.

Containment and secrets are checked before the file is read. An absolute path, a path that leaves the root, or a symbolic link resolving outside it returns `Outside the workspace: <path>.`. A `.env` or `.env.*` file and any path containing a run from `SECRET_DENY_PATHS` are refused anywhere in the workspace, and a path under the real home directory matching the same table is also refused. Any of them returns `Secret file: <path>.`. The reader names the path as typed.

Output is numbered lines: each line is prefixed by its number, padded to the width of the last line number and followed by a tab. A trailing carriage return is dropped. A line longer than 2000 code points is cut and ends with `…`. An empty file prints `(empty file)`. A partial read ends with `(showing lines <first>-<last> of <total>; continue with --offset <last+1>)`. An offset past the end prints `Offset past end of file (<total> lines): <path>.`, so a one-line file reads `(1 lines)`.

A failure prints one line naming the path as typed:

- `File not found: <path>.` for a missing path, and for a file that exists but cannot be read, such as one without read permission.
- `Is a directory: <path>.`
- `Not a text file: <path>.` for binary content, text that is not valid UTF-8, or anything that is not a regular file or directory.
- `File too large (>5 MB): <path>.`
- `Outside the workspace: <path>.`
- `Secret file: <path>.`
- `Offset past end of file (<total> lines): <path>.`

A typed read on a remote tab can also print `Remote connection unavailable.`, `The remote connection ended.`, or `The remote machine did not answer in time.`. Malformed arguments print `Usage: file read <path> [--offset <line>] [--limit <lines>]`.

A typed read's output carries no host tag. The loop's workspace step is the only place the tag appears.

### Typed file writes and edits

`file write <JSON>` and `file edit <JSON>` are typed application commands that share the `file` command and its root choice: a local tab writes under its workspace, or the project directory when it has none, and a remote tab writes only in its remote workspace, printing `Remote connection unavailable.` rather than ever falling back to the local disk. A write takes `path`, `content`, and an optional `expectedHash` and creates missing parent folders; an edit takes `path`, `oldString`, `newString`, and an optional `replaceAll`, and replaces exact text that must match once unless `replaceAll` is true. Each prints exactly one line: `Wrote <path>.`, `Edited <path> (<count> replacements).`, or a failure line naming the path as typed, with control characters and bidirectional formatting controls escaped so the line stays one line and shows the path in its true order. A path outside the root prints `Outside the workspace: <path>.`; a missing or ambiguous match prints `No matching text: <path>.` or `Multiple matches: <path>; set replaceAll to true.`; other refusals print `<reason>: <path>.`; a dropped or slow remote connection prints its connection line unchanged; and a malformed remote reply, such as an edit reporting zero replacements, prints `Invalid remote filesystem operation result.: <path>.` and is never reported as success. Bad or incomplete JSON prints `Usage: file write <JSON>` or `Usage: file edit <JSON>` and changes nothing. File content never appears in the output. A typed mutation consults no role grant; history and transcripts record the command text as typed.

The file tool's primer is exactly `FILE_READ_PRIMER` from `src/file-read/command.ts`:

```
To read a file in the workspace, end your reply with one line:
file read <path> [--offset <line>] [--limit <lines>]
Paths are relative to the workspace root. The output is numbered lines, at most 2000 per read; use --offset to continue a long file.
```

`file read` is granted by default to the `ask` and `tell` roles by `src/plugins/roles/roles-file.ts`: ask grants seven commands and tell grants twelve, including `file write` and `file edit`.

### File write and edit tools

`file write` and `file edit` are native commands, listed after `file read`, and a role can grant them like any other command; the built-in `tell` role grants both by default, the built-in `ask` role grants neither, and a saved role keeps the grants it lists. They belong to the same file tool as `file read`, which is included when a role grants any of the three. The file tool's primer is composed from the grants: the read primer when `file read` is granted, then the mutation primer when `file write` or `file edit` is granted, separated by a blank line, so a role granting only a mutation gets no read text. The mutation primer tells the agent to end its reply with one `file write {...}` or `file edit {...}` line whose JSON stays on that line. The allow-list line still names only granted commands with agent access.

The reply's last `file write` or `file edit` line is recognized as a command even when its JSON is incomplete, so a malformed request is gated and answered with the usage line rather than shown as the final answer. The gate is unchanged: a disabled or agent-inaccessible row refuses with `Command is disabled: <command>.`, an ungranted mutation refuses with `Command not allowed for role "<role>": <command>.`, each step counts toward the eight-step cap, a `withoutTools` tab exposes no file tools, and granting a mutation does not re-enable any harness built-in tool.

A granted mutation in a local session runs on the workspace through the same runner as the typed command, so it writes under the tab's workspace (or through the tab's remote connection when a local fallback session runs on a remote tab) and returns that command's one-line result, failure line, or usage text to the agent. No approval question is asked and no waiting state is added; refusal comes only from grants and command settings. A prompt cancelled before the step runs writes nothing; a mutation that already committed is not undone, its late result and the next provider turn are suppressed, and nothing retries it. Transcript entries and connection records may contain the mutation command text. A granted mutation in a remote-hosted loop runs on the remote machine against its workspace through its local filesystem, is reported as a workspace step (so it carries the `[<host>] ` tag), and never crosses to the caller. The autonomous agent path still refuses every mutation.

The loop prefixes a workspace step's text with `[<host>] ` exactly when the session is a remote ACP session and the step reports `workspace: true`. `tagged` in `src/acp/run-prompt.ts` builds that prefix from the tab's remote host. It is not enough that the tab is remote: `AcpSessionManager` can fall back to a local session on a remote tab, and that session's workspace step is not a far-side step. The transcript entry's `input` carries the tag, and both `tool` activity lines in the connection record, the command line and the result line, carry it. Caller-side steps, gate refusals, and typed `file read` output are untagged. A remote agent run tags its workspace steps the same way; [[agent-command]] states the run-specific rule.

## Remote connections

A remote shell or other remote plugin tab uses its existing channel and workspace for the ACP agent. The local side reads the selected role (`ask` or `tell`), chooses the model, and sends the launch request; the remote hosts the ACP client and runs the tool loop in the workspace clone, so prompt text, turns, and tool steps cross SSH instead of JSON-RPC. Workspace commands resolve against the clone, while database, browser, and question commands still execute on the machine running Janissary and their results return over the channel. Tabs sharing one channel still have independent ACP session ids.

Before the channel is attached, the operation refuses with `ACP: the remote session is still connecting.`. Transport loss closes the tracked core ACP connection and its record locally, settling any pending prompt. Other remote processes retain their existing recovery policy. After the channel is ready, another core request creates a new transport identity and record. Late updates from detached or replaced sessions are ignored. The existing remote platform confinement rules remain unchanged. Remote shell tabs offer `ask`, `ask reset`, `tell`, and `tell reset` through their command bar; harness tabs remain terminal surfaces. See [[remote-server]].

Closing a remote ACP session waits for the remote child process to exit before reporting it released. If exit is not observed within five seconds, release is reported as uncertain and an owning agent run records a cleanup warning. Repeated and concurrent closes share one shutdown attempt.

## Errors and notifications

Fatal errors are shown as `ACP: <message>` and forget the connection. Existing bounded stderr details remain available: the last 2000 characters, restricted to the last ten lines. Prompt errors appear as `ACP error: <message>` in the settled shell background reply and in the record's prompt block. Existing start, state-change, and rate-limit notification events remain in use.

## Shared consumers

Monitors, conversations, and editor persona queries remain separate ACP consumers, with their existing model choices, workspaces, permission policies, and lifecycle. They do not acquire the shell's tab session or enter its tool loop. See [[monitoring]], [[conversations]], and [[editor-tab]].

### Authentication outside workspaces

ACP sessions in ordinary shells receive the configured harness API tokens and a private copy of the saved ChatGPT login for OpenCode. The private login lasts for that ACP subprocess and is removed when it exits or fails to start. An explicit launch data-location setting takes precedence. Workspace sessions continue to share their workspace-owned login.

### Confinement

Every ACP subprocess requests the existing workspace sandbox. Workspace sessions use their clone as the boundary; ordinary shell and monitor sessions use their working directory. Ordinary sessions keep private temporary files and OAuth data inside project runtime storage and remove them when the subprocess exits. Offline settings remain in force. Confinement requires macOS Seatbelt and the enabled sandbox setting, with the existing harness runtime and credential exceptions.
