# File navigator: copy, cut, and paste files with Ctrl+C / Ctrl+X / Ctrl+V

**Complexity: 7/10** — a new RPC and three new server modules, a new client clipboard store plus hook, a change to the shape of the per-tab undo history (tagged union across four server files), removal of an existing dialog surface in favor of notifications across every file operation, and a mandatory extraction from `FileNavigatorTab.tsx` before any of it fits under the file-size limit.

## Summary

The file navigator can move files by dragging, delete them with Backspace, and rename them with Cmd+R, but there is no way to duplicate a file or relocate one without a mouse gesture — dragging is the only route into a different directory, and nothing at all duplicates a file in place. This adds the missing clipboard verbs: `Ctrl+C` copies the current selection, `Ctrl+X` cuts it, and `Ctrl+V` pastes into the directory the keyboard cursor sits in. One file or many, files or directories, within one navigator or across two navigators rooted anywhere on disk.

The clipboard is app-wide and lives on the client, so a selection copied in one navigator pastes into any other. Pasting back into the source's own directory duplicates with the codebase's existing `-2` naming (`report.md` → `report-2.md`); pasting onto an existing name anywhere else raises the same Overwrite/Skip/Cancel dialogs the drag-move flow already uses. A paste is one step on the tab's existing undo stack, so `Cmd+Z` reverses it. Failures stop being reported through the modal failure dialog: every file-navigator operation — copy, paste, move, delete, and an undo/redo replay — now reports its failures as a line in the notifications feed instead, and `web/src/FileNavigatorFailureDialog.tsx` is deleted.

## Design decisions

1. **Paste target.** `Ctrl+V` pastes into the directory implied by the keyboard cursor, using exactly the rule New file and New directory already use — `newFileTargetDir(rows, cursor)` in `web/src/file-navigator-new-file.ts`, called from `web/src/FileNavigatorTab.tsx:75` (`createNewFile`) and `:79` (`createNewDirectory`): a directory row pastes inside that directory, a file row pastes into its containing directory, and no cursor — or the `..` row — pastes at the tree root.

2. **App-wide clipboard, client-side.** The clipboard is a module-level store in the shape of `web/src/file-navigator-selection-registry.ts` (`const selections = new Map(...)` plus exported publish/clear/collect functions), holding **absolute** paths plus the mode (`copy` or `cut`). Every mounted navigator subscribes to it, so copying in one navigator and pasting in another works even when the two trees are rooted at unrelated paths. The server stays stateless about the clipboard — the paste RPC carries the paths.

3. **What `Ctrl+C` captures.** The normalized selection: the same `normalizeOperationPaths(rows, selected)` result (`web/src/useFileNavigatorSelection.ts:56`) that delete and drag-move already operate on — duplicates removed, `..` excluded, descendants of a selected directory dropped — mapped from tree-relative rows to absolute paths through the navigator's `files.absoluteRoot`. `Ctrl+C` with an empty selection leaves the clipboard untouched; `Ctrl+V` with an empty clipboard is a silent no-op.

4. **Cut is armed, visible, and single-use.** `Ctrl+X` stores the same normalized selection with mode `cut`. Rows on the clipboard render dimmed in **every** navigator that shows them, until the paste lands or a later `Ctrl+C`/`Ctrl+X` replaces the clipboard. The paste moves rather than copies. After a successful cut-paste the clipboard empties, so a second `Ctrl+V` does nothing. Pasting a cut back into its own directory is a silent no-op — the same rule `moveBatch` already applies at `src/file-navigator/batch.ts:79` (`attempted = normalized.filter((source) => parentPath(source.rel) !== destinationPath)`).

5. **Collisions.** Pasting a copy into the source's own directory always auto-renames — duplicating a file is the point of the gesture, so it never prompts and never overwrites. Every other collision reuses the existing move dialogs unchanged: `"<name>" already exists here. Overwrite it?` with Overwrite/Cancel for a single item, and `Some items already exist in "<folder>".` with Overwrite all / Skip conflicts / Cancel for a batch — the two titles built in `web/src/useFileNavigatorMoveOperations.ts:71` and `:86`, rendered by `web/src/MoveConflictDialog/MoveConflictDialog.tsx`.

6. **Duplicate naming.** `report.md` → `report-2.md` → `report-3.md`, matching the `untitled-2.md` convention the app already uses — and reusing the function that implements it, `nextFreeName(dir, name)` at `src/editor/next-free-name.ts:7`, which already splits base from extension and probes upward. It is already imported outside the editor (`src/open-file-manager.ts:7`), so a second cross-area import is established practice.

7. **Undo.** A paste is one step on the tab's existing per-tab undo/redo stack (`undoStack`/`redoStack` on `FilesTabState`, `src/file-navigator/state.ts:18-19`). Undoing a copy-paste deletes exactly the items that paste created, with no confirmation; undoing a cut-paste moves them back, as moves already do. Redo re-applies either. This deliberately narrows the spec's current "Deletions are not covered by undo/redo" sentence (`product/specs/file-navigator-tab.md`, "Undoing and redoing a move") to user-initiated deletes — an undo may now delete what its own paste created.

8. **History steps become a tagged union.** `MoveGroup` (`src/file-navigator/moves.ts:8`) is today the only history step and holds tree-relative `{ from, to }` pairs, which cannot express a cut-paste whose source lay outside the pasting tab's root. The stack element type becomes `HistoryStep = MoveGroup | PasteGroup`, where the paste step carries **absolute** source/destination pairs plus its mode. `applyStackMove` keeps handling `MoveGroup` untouched; `replayHistory` (`src/file-navigator/manager-history.ts:9`) branches on the tag and routes a paste step to new replay logic. Absolute pairs mean a cross-root cut-paste undoes exactly like a same-root one — no special case, no silent "this one isn't undoable" hole.

9. **Failures are notifications, not dialogs.** Every file-navigator operation failure — copy, paste, move, delete, and an undo/redo replay, batch and single-item alike — is posted to the notifications feed rather than shown in a modal. `web/src/FileNavigatorFailureDialog.tsx` and its test are deleted. One line per operation, attributed to the navigator tab: `Could not copy 2 of 5 items: notes.md, src`, naming the failing rows in selection order and truncating past three names with `… and N more` so one paste is always one feed line. The verb is `copy` for a copy-paste, `move` for a cut-paste, a drag-move, and a move replay, and `delete` for a delete.

10. **Where the notification is posted.** From the controller wrappers in `src/controller/file-navigator.ts`, not from the manager: every RPC funnels through that file, and each wrapper already resolves `index` → `label` (`managers.tab.tabs[index]?.label`), which is exactly the two things `notify` needs. To make that funnel uniform, `FileNavigatorManager.move` and `.delete` (`src/file-navigator/manager.ts:102` and `:166`), which today return `void`, return a `BatchResult`-shaped value instead (`{ total: 1, failedPaths: [] }` on success, `{ total: 1, failedPaths: [relPath] }` on failure), so the single-item paths report like the batch ones.

11. **Accepted consequence of decision 9.** Notifications are drop-if-closed — `notify` (`src/notifications.ts:99`) returns immediately when the notifications tab is not open — so a failed operation is reported nowhere when the feed is closed. This was raised and confirmed as the intended behavior: no dialog fallback, consistent with every other notification in the app.

12. **A vanished source is a failure.** A clipboard entry whose source no longer exists when the paste runs counts toward both `<total>` and `<failed>` and is named in the report — the user asked for it and it did not happen. Likewise a copied directory whose paste destination lies inside itself, mirroring the guard `moveBatch` applies at `src/file-navigator/batch.ts:87` (`isSameOrDescendantPath(destinationPath, source.rel)`).

13. **One RPC for both modes.** Copy-paste and cut-paste go through a single new `pasteFileNavigatorItems` call rather than reusing `moveFileNavigatorItems` for the cut case, because the clipboard's sources are absolute and may originate outside the pasting tab's root — which the existing tree-relative move RPC cannot express. Its reply reuses the existing `BulkMoveResult` union (`src/protocol.ts:34`), so the client's conflict-preflight handling is the one it already has.

14. **Containment is asymmetric.** The paste destination must resolve inside the pasting tab's root, exactly as `moveBatch` requires today; the **sources** must not, since an app-wide clipboard is the whole point. `paste.ts` therefore validates destination and sources by different rules — the destination through the shared `realDirectory` helper, the sources by a plain `lstatSync` existence check.

15. **Chord capture.** `Ctrl+C`, `Ctrl+X`, and `Ctrl+V` join `Cmd+Z`/`Cmd+N`/`Cmd+R` as chords the focused tree captures for itself (`handleTreeChord`, `web/src/file-navigator-chords.ts:14`) instead of letting them reach the window-level bindings, and `product/specs/file-navigator-tab.md`'s chord-capture paragraph names them.

## Ordering

The three parts land in this order so typecheck and tests stay green at each checkpoint:

1. **Extraction only, no behavior change** — move `FileNavigatorTab.tsx`'s `onKeyDown` body into a new hook (see below). `check-diff` green before continuing.
2. **Failure reporting moves to notifications** — the `file-operation` event, `operation-report.ts`, the manager/controller return-value changes, and the deletion of `FileNavigatorFailureDialog`. This is self-contained and testable without any paste code.
3. **The clipboard feature itself** — store, chords, hook, RPC, paste batch, history step. It reports its failures through the mechanism step 2 already put in place.

## Proposed changes

**Step 1 — extraction (no behavior change)**

- **`web/src/FileNavigatorTab.tsx`** is at roughly 191 non-blank, non-comment lines against the 200-line `max-lines` cap, so it cannot absorb the paste wiring as it stands. Extract its `onKeyDown` handler (`:111-154` — the rename guard, chord branch, delete branch, nav-key branch, and type-ahead branch, plus the `typeahead` ref and the `TYPEAHEAD_RESET_MS`/`ROW_HEIGHT_PX`/`PRINTABLE` constants it owns) into a new **`web/src/useFileNavigatorKeyDown.ts`** hook that takes the rows, selection, and the action callbacks and returns the handler. This follows the precedent already recorded in `file-navigator-chords.ts`'s own header comment — that module exists for exactly this reason.

**Step 2 — failure reporting**

- **`src/notifications.ts`**: add `file-operation` to `NotificationEventType` (`:13`), list it in `shouldNotify`'s always-eligible switch (`:38-42`) — it reports a direct user action, so it bypasses both the config toggles and focus suppression — and return its detail verbatim from `notificationText` (`:79-81`), as `manual` does.
- **`src/file-navigator/operation-report.ts`** (new): a pure `operationFailureText(verb, result)` building `Could not <verb> <failed> of <total> items: <names>` — names in selection order, truncated past three with `… and N more` — plus a `reportOperationFailure(managers, label, verb, result)` that no-ops on an empty `failedPaths` and otherwise calls `notify(managers, 'file-operation', label, text)`. Kept pure-plus-thin-wrapper so the text is testable without a `Managers`.
- **`src/file-navigator/manager.ts`**: `move` (`:102`) and `delete` (`:166`) return a `BatchResult` instead of `void`, per decision 10. Their early returns (`!state`, self/descendant rejection, `moveItem` failure, `deleteItem` failure) become failure results rather than bare returns.
- **`src/controller/file-navigator.ts`**: every wrapper that can fail — `moveFileNavigatorItem`, `moveFileNavigatorItems`, `deleteFileNavigatorItem`, `deleteFileNavigatorItems`, `undoFileNavigatorItem`, `redoFileNavigatorItem` — calls `reportOperationFailure` with the resolved label before returning. The undo/redo wrappers report only when the result carries `failedPaths` and no `conflict`/`conflicts` (a conflict is a question for the user, not a failure). `src/controller.ts:173-178` already delegates its same-named methods straight to these wrappers, so reporting inside the wrapper covers both routes with no second call site.
- **Client**: delete `web/src/FileNavigatorFailureDialog.tsx` and `web/src/FileNavigatorFailureDialog.test.tsx`. `web/src/useFileNavigatorMoveOperations.ts` drops `failure`, `applyResult`, `dismissFailure`, `reportFailure`, and the `FileNavigatorFailure` type; `web/src/useFileNavigatorDrag.ts:44` still spreads `...moves`, so its consumers lose those keys with it. `web/src/useFileNavigatorDelete.ts` drops its `onFailure` parameter and its `.then(...)` reporting, and `web/src/FileNavigatorTab.tsx:45` calls it as `useFileNavigatorDelete(client, index)`. `web/src/FileNavigatorOverlays.tsx` drops the `drag.failure` branch (`:66-74`) and no longer needs `focusTree` for it (it is still used elsewhere — keep the prop).
- **`product/specs/file-navigator-tab.md`**: the move section ("Moving files by drag-and-drop", `Could not move <failed> of <total> items.`) and the delete section (`Could not delete <failed> of <total> items.`) replace their result-dialog wording with the notification line; the undo/redo section's conflict wording is unchanged but its failure wording follows suit.
- **`product/specs/notifications.md`**: the "Events that notify" list gains `file-operation` (and its "Ten event types" count becomes eleven), described as always-on and untoggleable, alongside `manual`/`auto-approve`.

**Step 3 — the clipboard feature**

- **`web/src/file-navigator-clipboard.ts`** (new): the app-wide clipboard store. Holds a mode (`'copy' | 'cut'`) and an ordered list of absolute paths; exposes a setter, a snapshot getter, a clear, and a subscribe function so navigators re-render when it changes (React's `useSyncExternalStore`, since the value lives outside React — the snapshot must be referentially stable between changes or the store will loop). Also exposes a membership query taking a navigator's absolute root and a tree-relative path, so a row can ask "am I on a pending cut?" without each navigator recomputing the whole set.
- **`web/src/file-navigator-chords.ts`**: three new cases in `handleTreeChord` — `c` and `x` write the current normalized selection into the clipboard with the matching mode, `v` invokes the paste handler — added to the `ChordHandlers` type as callbacks so this module keeps knowing nothing about the client. All three return `true` so `FileNavigatorTab` prevents default and stops propagation, as it already does for the existing chords.
- **`web/src/useFileNavigatorPaste.ts`** (new hook): owns the paste flow, mirroring `useFileNavigatorMoveOperations`. Computes the destination from the cursor via `newFileTargetDir`, issues the `pasteFileNavigatorItems` request, and on a `conflictPaths` reply holds a pending-conflict record whose retry re-issues the same request with `overwrite-all` or `skip-conflicts` (the same two-policy retry `retry()` implements at `useFileNavigatorMoveOperations.ts:112`). Clears the clipboard after a successful cut-paste, never after a copy-paste. Exposes the pending conflict for `FileNavigatorOverlays` and the cut-path membership for the row class.
- **`web/src/FileNavigatorTab.tsx`**: instantiate the paste hook, pass its handlers into the key-down hook's chord callbacks, and hand its pending conflict to `FileNavigatorOverlays`.
- **`web/src/file-navigator-row-class.ts`** + **`web/src/theme.css`**: a `cut` modifier on the row class string (composed like the existing `selected`/`cursor`/`drop-target` at `:19`), styled as reduced opacity.
- **`web/src/FileNavigatorOverlays.tsx`**: no second dialog branch — the existing `MoveConflictDialog` element at `:41` is fed by whichever of the two hooks has a conflict pending, with the matching overwrite/skip/cancel handlers, keeping `onSkip` conditional on a multi-item conflict as it already is at `:45`. The two can never be pending at once: a paste needs keyboard focus in the tree, which no in-flight drag gesture leaves available.
- **`src/protocol.ts`**: add `pasteFileNavigatorItems` to the RPC union beside `moveFileNavigatorItems` (`:244`), with params `{ index, sources, destinationPath, mode, policy? }` — `index` the pasting navigator's tab, `sources` absolute paths, `destinationPath` tree-relative to that tab's root, `mode` `'copy' | 'cut'`, `policy` the existing `BulkConflictPolicy`. Reply type: the existing `BulkMoveResult`.
- **`src/file-navigator/batch-paths.ts`** (new): `containedPath`, `realDirectory`, `exists`, and `duplicateNames`, moved out of `batch.ts` (`:15,43,54,63`) so both batch modules share one implementation. `batch.ts` is at roughly 134 effective lines and cannot also host the paste logic; the extraction takes it down to roughly 95.
- **`src/file-navigator/paste.ts`** (new): `pasteBatch(root, sources, destinationPath, mode, policy)`. Normalizes absolute sources (dedupe; drop any source nested inside another selected source directory, reusing `isSameOrDescendantPath` from `src/file-navigator/index.ts`; `lstatSync` each, marking a vanished one invalid); resolves the destination through `realDirectory`; rejects a directory source whose destination lies within itself; treats a copy whose source directory *is* the destination as an auto-rename case resolved through `nextFreeName` rather than a conflict, and the same case for a cut as a skip; preflights the remaining collisions and returns `{ conflictPaths }` when `policy` is undefined; otherwise performs each item and returns `BatchResult` plus the resulting pairs and a `mutated` flag, matching `moveBatch`'s `MoveManyResult` contract. Keep the normalization, the conflict preflight, and the per-item loop as three named helpers — one function doing all three will trip `sonarjs/cognitive-complexity`.
- **`src/file-navigator/filesystem.ts`**: a `copyItem(source, destination, overwrite)` alongside `moveItem` (`:39`), thin over `node:fs`'s `cpSync` — `{ recursive: true, errorOnExist: true, force: false }` normally, and an `rmSync` of the destination followed by the same copy when `overwrite` is true, since `cpSync`'s own `force` merges directories rather than replacing them. Deliberate ceiling: unlike `moveReplacingDestination` (`:14`), this does not stage a backup first, so an overwrite that fails midway leaves the destination gone. That is acceptable because the source still exists (nothing is lost, unlike a failed move) and the operation is reported as a failure; the upgrade path, if it ever bites, is the same backup-then-restore dance `moveReplacingDestination` already implements.
- **`src/file-navigator/moves.ts`**: add the `PasteGroup` step type and the exported `HistoryStep` union of decision 8, plus the replay function for a paste step — undo of a copy step removes its created destinations, undo of a cut step renames them back to their absolute sources, redo re-applies. `applyStackMove` is untouched.
- **`src/file-navigator/state.ts:18-19`**: `undoStack`/`redoStack` become `HistoryStep[]`.
- **`src/file-navigator/manager-history.ts`**: `HistoryState`'s stacks take the union, and `replayHistory` branches on the step's tag before choosing `applyStackMove` or the paste replay. Its single-entry collapsing (`:29-31`) applies to move steps only.
- **`src/file-navigator/manager-batch.ts`**: `pasteMany(state, sources, destinationPath, mode, policy, rebuild)` beside `moveMany`/`deleteMany` — calls `pasteBatch`, pushes the resulting step onto `undoStack`, clears `redoStack`, rebuilds when `mutated`.
- **`src/file-navigator/manager.ts`**: a `paste(label, sources, destinationPath, mode, policy)` method beside `moveMany` (`:113`), a thin delegate to `pasteMany`. The file is at roughly 186 effective lines — keeping this a five-line delegate is what keeps it under the cap.
- **`src/controller/file-navigator.ts`** and **`src/message-handler-file-navigator.ts`**: the index→label wrapper and the deferred-reply case for `pasteFileNavigatorItems`, following `moveFileNavigatorItems` exactly (`:32` and `:33`), with the wrapper also calling `reportOperationFailure` from step 2. Add the method name to the `FileNavigatorMessage` `Extract<...>` union at `src/message-handler-file-navigator.ts:13`.
- **`product/specs/file-navigator-tab.md`**: a new "Copying, cutting, and pasting" section covering the clipboard, the paste target rule, cut dimming and single-use, same-directory duplication with `-2`, and cross-navigator paste; the keyboard-interactions table gains `Cmd+C`/`Cmd+X`/`Cmd+V` rows; the chord-capture paragraph below it names them; the "Undoing and redoing a move" section records that a paste is one undoable step and narrows its "Deletions are not covered by undo/redo" sentence to user-initiated deletes.

All new `src/` imports carry `.js` extensions per the NodeNext rule in `CLAUDE.md`.

## Out of scope

- **OS clipboard interop** — `Ctrl+C` does not write paths to the system clipboard as text, and `Ctrl+V` does not accept files copied from Finder or Explorer. In-app clipboard only.
- Any dialog fallback for reporting a failure while the notifications feed is closed (see design decision 11).
- Changing how the drag-and-drop move gesture itself works; it gains only the new failure reporting.
- A visible clipboard indicator anywhere outside the dimmed cut rows — no status text, no header affordance, no clipboard entry in the tab's own header buttons.
- Persisting the clipboard across a browser reload or into a profile.
