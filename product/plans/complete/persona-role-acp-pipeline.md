# Personas name an ACP role and editor agent uses the ask/tell ACP pipeline

**Complexity: 7/10** — ~215 added lines across 16 production files (eight source modules plus eight bundled personas) and 17 distinct requirements, driving p=7.06.

## Goal

AI personas declare an ACP role on the first line of their file instead of a harness/model/variant directive and a `tools:` allowlist. Every session a persona opens — an in-editor suggestion, a monitor, or the launcher summarizer — runs through the same core ACP role pipeline the `ask` and `tell` commands use: the declared role's model entries, fallback, command grants, and deny-all internal-tool layers apply, and the role's grants run through the core tool loop on the priming prompt. Personas keep their bodies as the startup prompt; only their configuration and launch path changed. The editor `>` request line and its hunk results, `ask` and `tell`, and the roles file format are unchanged. The built result also carries the declared role on the durable connection record, prints persona error placeholders literally in the transcript, keeps one death hook per consumer on a shared role slot, re-binds a still-usable shared session without re-priming, reports role failures only through the notification feed, clears a capability's remembered role on reset, and resolves subagent caller identity from a persona's own slot.

## Requirements

1. A persona declares `[//]: # role: <name>` as its only configuration line; the harness/model/variant directive and the `tools:` line no longer configure anything.
2. The role a persona declares configures its ACP connection.
3. Editor suggestions run through the core ACP role pipeline shared with `ask` and `tell`, not a raw session prompt.
4. All three bundled persona families — editor, monitor, and launcher — declare a role; none keeps the old directive.
5. Monitor and launcher-summarizer sessions also run through that core pipeline, not a separate simple launcher. A monitor's primer runs through the core tool loop on the priming prompt; its periodic flush prompts post directly to that session and their replies are parsed for suggestions rather than executed as commands.
6. A persona session uses its role's command grants and the same command tool loop as `ask` and `tell` on the priming prompt; a role that grants no commands leaves the session tool-less.
7. Editor `>` requests keep naming a persona, and that persona's declared role configures the session.
8. The directive is exactly `[//]: # role: <name>` on the first line, with any nonempty trimmed name accepted at load time.
9. An unknown role starts no session and produces no reply; the only signal is `Persona "<persona>" requests unknown role "<role>".`
10. A role with no enabled model entries starts no session and produces no reply; the only signal is `Persona "<persona>" finds no enabled models in role "<role>".`
11. A persona file without a valid directive fails to load, is not listed for completion, and reports exactly `Persona "<name>": expected first line [//]: # role: <role>.`
12. An old `[//]: # tools: ...` line left in a persona file is ordinary prompt body text, with no error.
13. Every bundled persona declares the `ask` role.
14. Any role name that resolves through the effective roles file, including a custom role, is a valid declaration; names match trimmed and case-insensitively.
15. The editor `>` request line and hunk results, the `ask` and `tell` commands, and the roles file format stay unchanged.
16. Persona sessions get one slot per role name on a tab, so two personas declaring different roles on one tab keep separate sessions and exchanges while two personas naming the same role share one.
17. The launcher summarizer's declared role configures its connection's models, while the tab's `withoutTools: true` mode still keeps it from running any command.
18. A core connection record opened for a persona session carries the declared role verbatim in an optional, validated `declaredRole` field; the built-in `role` field stays limited to `ask` and `tell` with its strict validation unchanged, and row/window projections and connections names prefer the declared role.
19. The rendered transcript shows the `<role>` and `<persona>` placeholders of a persona error literally instead of dropping them as markup.
20. Per-slot death hooks are deduplicated by caller identity: a repeated request from one persona replaces its hook, distinct consumers sharing a slot keep one each, and a connection death reaches each exactly once.
21. When two monitors on one owner share a role and one respawns, a still-usable shared session is re-bound without re-priming; when it truly died it is closed once, one fresh session is primed, and every sibling adopts it.
22. A monitor whose persona role is unknown or has no enabled models emits only the core notification; no `monitor <persona>:` failure line is appended to the owner tab.
23. `resetAcp` clears the capability's remembered role to the `ask` default, so a following `startAcp` with no request and its `promptAcpResult` use `ask`; the launcher's explicit role is unaffected.
24. When a persona prompt's reply issues a granted `subagent` command, the caller role, internal identity, and provider id resolve from that persona's own slot when no `ask`/`tell` session is open, while `ask`/`tell` keep priority.
25. The monitoring and editor-persona user documentation matches the role-first format: no web-tools opt-in directive, no "each persona gets its own connection" claim, and the exact load error.

## Design decisions

- Persona configuration is a single first line. `parseDirective` requires the exact `[//]: # role: ` prefix and a nonempty trimmed remainder, throws the load error above otherwise, and returns the role string; the removed harness and tool parsers leave no second configuration path. `Persona` is `{ name, role, body }`, with the body holding every line after the first, so a leftover `tools:` line is read as prompt text. `listPersonas` reads each candidate's first line and omits an invalid file from completion.
- The launcher plugin parses its own persona because a plugin cannot import host internals. `readPersonaBody` and `readPersonaRole` share one reader that requires the same first-line format, raises the same exact load error, returns only the body, and works for both a project's file and the shipped fallback.
- The core ACP entry takes a role name string rather than only the two built-in roles; `ask` and `tell` keep their defaults and their transcript receipts through `runAcpCommand`. `startCoreSession` owns the tab, connecting, and fallback logic for `AcpManager.start`, and `launchableEntries` exposes the catalog-filtered queue to persona prompts.
- `promptPersonaRole` resolves the declared role with `knownRoleSettings`, then enters the ordinary core prompt attempt: model fallback, the two deny-all internal-tool layers, the role's native-command grants, connection records, and the tool loop are the same as for `ask` and `tell`. An unresolved role and a role with no enabled entries each post one exact `manual` notification, return a refusal without appending a request reply, and start no session; no new notification event is introduced.
- A declared role string is carried on the durable record as an optional `declaredRole` field on the `acp` source and projected row, validated as an optional nonempty string, rather than widening the core `role` field. `promptPersonaRole` uses the default core role plus `declaredRole` for the record source while keeping the custom role on the request and state; `recordConnectionName` prefers `declaredRole` for the `acp:<role>:<owner>` label, the connections wire contract accepts it on acp record rows and window sources but rejects it on agent and live rows, and legacy records keep their shape and names. Strict `ask`/`tell` validation is untouched.
- Persona error lines are angle-bracket-escaped in the transcript's markdown renderer before parsing, the same way single-line `Usage:` replies are, so the literal `<role>` placeholder prints while markdown links and intentional raw HTML elsewhere keep rendering. The server message string stays exact; no general escaping is added.
- Persona session state lives on the tab record as `personaRoles`, keyed by the declared role name, and holds the session, current prompt, hooks, record ids, and recorded exchange. `PersonaRoleSessionManager` owns that slot's connection, lazy creation, recording, transcript, close, and disposal; a connection error is dropped unless it comes from the slot's current session, then forgets the slot, emits one dirty state, and calls the composite hook. Death hooks are keyed per slot by caller identity — the persona name for persona prompts, the hook object otherwise — so a repeated prompt replaces its hook while distinct consumers are all reached once; `forget` clears them on every teardown.
- Editor suggestions go through `promptPersonaRole` with the persona body and role. The first request on a slot primes with the persona body and the hunk format; later requests send only the buffer block and request text. Parsing hunks, the review UI, and the `editor-suggest` failure notification are unchanged; a role configuration failure resolves with no hunks and adds no second notification.
- `EditorAcpManager` is the editor-facing view of those role-keyed sessions. It keeps the persona name beside each role slot so connection rows keep naming what the user typed (`<persona> (acp)`, plain text), and wraps the core death hook. It stores the `AcpSession` it bound so its own death handler can still reach the current request's hook after the core owner has forgotten the slot; a late error from a closed or replaced session is ignored, and a death after a settled reply posts the single `<persona>: <message>` notification. Request failures without a death leave the session open.
- Monitors enter the same core entry with their persona body, suggestion format, and trust framing; their connection-info line reports the role entry's provider and model. The persona subprocess launcher and its `allowedTools` path are gone, along with the spawn-function injection. A role configuration failure clears `inFlight` and emits only the core notification, with no owner-tab failure line. Respawn and stop share the same sibling check: a still-usable shared session is re-bound (respawn only resets that monitor's own context and posts no second primer), while a dead slot is closed once, one fresh session is primed, and every sibling is re-pointed to it; stopping releases a role slot only when no other live monitor on the same owner uses it.
- A granted `subagent` call resolves its caller from the persona slot: the persona runtime records the provider id reported at handshake, and the caller lookups fall back to the tab's current slot for role, internal identity, and provider id after the ask/tell path, leaving the unresolved-session error for callers with no identity at all.
- The launcher passes its persona's declared role into `startAcp` alongside `{ withoutTools: true }`. The capability records the role on the tab and `promptAcpResult` prompts under that same role rather than a fixed `ask` word, so the connection and its prompts cannot diverge. `resetAcp` closes the tab and resets the remembered role to `ask`, while `startAcp` keeps applying an explicit role. A role-start refusal is translated into the persona notification, and the summarize intent leaves that failure to the notification instead of reporting it a second time. The session still builds no tool table and runs no command.
- No new protocol message, RPC, client control, notification event, or roles file field is introduced, and no other user-visible surface changes. The PR description, the affected specs, and the two user-documentation pages are corrected to the delivered behavior, including the plain-text connection row, the server-side model fact, the scoped monitor tool-loop claim, and the role-first persona format.

## Assumptions

1. Personas are markdown files under `ai/personas/<kind>/<name>.md`, keyed by filename, with the first line a role directive and the remaining lines the startup prompt.
2. A role is an arbitrary role-name string on the persona path; the built-in `ask` and `tell` remain the defaults for shell commands and other callers.
3. Role entries and command grants are read fresh for each prompt, with built-in fallbacks when a role is missing or has no entries, and model entries are filtered against the current catalog.
4. Role names resolve by trimmed, case-insensitive comparison against the effective roles file, with the stored spelling reported back.
5. A role session denies every harness internal tool in two layers and runs native commands only through the shared tool loop on the priming prompt.
6. A tab's runtime is the home of per-agent state, so persona sessions, their prompts, and their connection records live there rather than in a controller-owned map.
7. Connection records, activity, settlement, and dirty-state notifications are core services that persona sessions reuse; no persona-specific transport is added.
8. A tab plugin may only use the published capability contract, so the launcher's reader and role wiring stay inside its plugin code.

## Implementation steps

Persona loading reads the role from the exact first-line directive, keeps all later lines as the body, omits invalid files from `listPersonas`, and converts all eight bundled personas to `ask`. The launcher plugin applies the same contract independently through its own reader and shipped fallback. Monitor test fixtures are reduced to the current `{ name, role, body }` shape without changing any assertion.

The core ACP entry accepts a role name string. `promptPersonaRole` resolves settings, reports the two notification-only failures, and runs the role's launchable entries through the shared prompt and record path. Its record source uses the default core role plus a validated `declaredRole` string, threaded through acp-record types, validation, projection, the record feed, the connections shared validators and wire contract, so a custom role opens a valid record and names it without loosening strict `ask`/`tell` validation. `PersonaRoleSessionManager` owns role-keyed slots on the tab runtime, with session identity, recorded exchanges, connection-error handling, close, tab release, and disposal; its death hooks are keyed by caller so repeated prompts do not multiply notices. `AcpManager` exposes the entry queue and releases persona slots on tab close, and the capability's `resetAcp` resets its remembered role after closing.

Editor suggestions enter that entry with the persona body and role while keeping first-turn priming, hunk parsing, and the request line. `EditorAcpManager` maps a persona's role to its slot for connection rows and transcripts, and keeps its own session binding so a death after a settled reply still reaches the request hook once. The transcript markdown renderer escapes persona error lines so the `<role>` placeholder prints literally. Monitors enter the same entry with their persona body, suggestion format, and trust framing; the old subprocess launcher and spawn injection are removed, a role failure stays notification-only, respawn re-binds a usable shared session without re-priming and re-points siblings to a single fresh one, and stopping releases the slot unless a same-role sibling on that owner still uses it. A granted subagent call resolves its caller from the persona slot's stored provider id and identity.

The launcher passes the declared role into `startAcp` with `withoutTools: true`; the capability remembers the role for `promptAcpResult`, translates a role-start refusal into the persona notification, and the summarize intent does not notify twice. Specs describing persona directives, monitor and editor sessions, launcher summarization, roles, connection rows, records, and caller identity match the role-backed path, the two user-documentation pages are rewritten from them, and the PR description is corrected to the plain-text row, the server-side model fact, and the priming-scoped tool-loop claim. Tests cover the new loader, the core entry and slots, all three consumers, record metadata, transcript rendering, and the notification-only failures.

## Out of scope

The editor `>` request line, its edit-hunk result format, and the rest of the editor UI stay as they are. The `ask` and `tell` commands, their notification text, the roles file format, the notification event set, and the launcher's reply shape, framing, and cursors are unchanged. Strict `ask`/`tell` record-source validation and the built-in role vocabulary are not widened; only the optional declared role is added, with no new schema version, protocol message, or UI control. General angle-bracket escaping for transcript lines is not added. `stopMonitor`'s survivor rule and each monitor's independent context reset are unchanged, and there is no runtime tool loop on monitor flushes. No new protocol message, RPC, or client control is added, and no monitor target, report routing, or `monitor ask` behavior changes. Only persona file format, persona loading, and the launch paths for persona sessions change, plus the specs, user docs, PR description, and tests that describe them.

## Verification

Run `$janissary/scripts/run.mjs check-diff` to confirm no lint, typecheck, or test regression from the changed server modules, plugin, web renderer, specs, and tests.

Then check against a running app: define a role with a distinct enabled model whose grants include a native command, set an editor persona's first line to `[//]: # role: <that role>`, open an editor tab, and issue a `>` suggestion. The suggestion must come through that model, the connections window must show a plain-text `<persona> (acp)` row with no model id, a second persona declaring a different role must open a second row, a missing role must produce the exact unknown-role notification with no answer in the editor, and a malformed persona must show its load error with the literal `<role>` placeholder. Repeat with a monitor and with the launcher summarizer: each must use the declared role's model, the summarizer must still run without a tool table, a role with no enabled models must produce only its exact notification, and a monitor configuration failure must add no owner-tab line. A role whose grants are empty must use the no-tools primer. Two monitors sharing a role must survive one's respawn on a single session without a second primer, and a granted subagent call from a persona must launch with that slot's caller identity. Closing and reopening a persona connection, stopping and restarting a monitor, and killing an agent between editor requests must each start a fresh session, with the editor death reported once.
