# Roles tab

**Complexity: 5/10** — a new bundled tab plugin (server activation plus a two-column native-drag client), one additive host capability that hands the plugin the harness launch catalog plus one shared effort-levels constant, and a JSON file layer with home/project precedence and default-file creation; every mechanism is precedented in the launcher, search, and conversations plugins, and the drag interaction uses the browser's own drag-and-drop rather than a custom gesture.

Implementation notes:

- The file layer reads through the shared `readJsonConfigFile` and writes through the shared `writeJsonConfigFile`, both in `src/plugins/files.ts` — the one host file module the plugin import boundary admits to a concrete plugin, alongside `../api.js`. `writeJsonConfigFile` delegates to `atomicWriteFile`, so a failed replacement leaves the previous file and its permissions exactly as they were and removes its temporary output; the roles writer keeps its directory creation and answers success or failure rather than throwing.
- The pure role-list edits live in `src/plugins/roles/role-edits.ts` (each refusing a bad request by throwing the contract's `TabPluginRejection`), keeping `activate.ts` under the 200-line limit.
- `src/plugins/roles/ordered-json.ts` holds two pure helpers: a scanner that recovers the top-level key order from the file's source text — skipping escaped strings and nested values — and a serializer that writes each role name and value independently, so the file's member order and keys such as `__proto__` or integer-looking names round-trip through the reader and the writer alike. Value decoding stays with `JSON.parse`, which keeps last-value semantics for a repeated key.
- Two pieces of the card are their own modules because the card has no room for either and both are worth testing on their own: `web/src/plugins/roles/useRoleDraft.ts` is the shared hook behind the name and description fields, and `web/src/plugins/roles/EntryPicker.tsx` is the harness/model/effort picker, which owns its three selections and unmounts when it closes.
- `activate(home?)` takes an optional home directory as a test seam, mirroring the search plugin's optional scan reader.
- The capability is composed in `src/plugins/context.ts`, beside `projectFileList` and `tabActivity`. Master moved that group's implementations into `context.ts` and left `src/plugins/file-capabilities.ts` uncalled, so the capability sits beside the code it composes with.

Per the backlog: "Add a roles command that opens a roles tab. The roles tab serves as a configuration tool for mapping models and harnesses onto named roles and role descriptions that can be used by humans and AI tasks when deciding which models to launch for which tasks. for example, the role 'planning' is assigned Codex, GPT-6.1-Sol, xhigh, and Claude Code, Opus 5.5, and xhigh, with the description 'Research and development of plans for new product features.'. Roles map to an ordered list of models/harness/effort/variant. the roles should be stored in ~/.janissary/roles.json and overriden entirely (without merging) for a project when .janissary/roles.json is present. a default roles should be created by the tab when it is not otherwise present. default roles should include planning, research, code review, implementation, and documentation. models from harness-models.json should be available in the interface to be easily added to and taken from various roles."

The point of the feature is a single place where the mapping from a named role (planning, research, code review, implementation, documentation) to concrete harness/model/effort choices is written down once, so a human or an AI task deciding which model to launch for a task reads the role's ordered list instead of remembering which harness runs which model. The file format is the durable output; the tab is the editor for it.

## Design decisions

Established by the feature text:

- Roles are stored in `~/.janissary/roles.json`. A project's `.janissary/roles.json`, when present, replaces the home file entirely — no merging of individual roles between the two files.
- A `roles` command opens the roles tab, parallel to the `search` command's center-strip plugin tab.
- The tab is a configuration tool: it maps named roles, each with a description, to an ordered list of harness/model/effort entries.
- When no roles file exists, the tab creates one holding the default roles: planning, research, code review, implementation, and documentation.
- The example role from the feature text: the role `planning` carries the description `Research and development of plans for new product features.` and two ordered entries — Codex `gpt-6-sol` at effort `xhigh`, and Claude Code `claude-opus-5-5` at effort `xhigh`.
- The interface draws its model choices from the harness model catalog (`harness-models.json`, with the project override `.janissary/harness-models.json` honored by the existing loader), so every model the interface offers is one a harness launch would accept.

Settled with the user:

- **The tab is a center-strip tab.** `roles` opens or focuses its singleton tab in the center strip; the tab is never docked, so the command claims no `left`/`right` argument. (Chosen over a dockable sidebar tab.)
- **One scrolling list of role cards.** Every role is a card showing its name, description, and ordered harness/model/effort rows, edited in place; there is no list/detail split and no selection step before an edit. (Chosen over a master-detail layout.)
- **Configuration tool only.** Nothing consumes the roles file in this version: no launch dialog, no command flag, no ACP integration. Humans and AI tasks read `roles.json` itself. (Chosen over a harness-dialog role picker or a `--role` flag.)
- **Entries carry harness, model, and effort only.** The feature text's "variant" is dropped: a hand-written file gains no fourth field, and nothing is stored that no surface reads. (Chosen over an optional verbatim variant.)
- **Write-through persistence.** Every edit writes the effective roles file first and republishes the tab payload only after the write succeeds, so the tab never shows a state the file does not hold; there is no Save button and no unsaved state to lose. (Chosen over an explicit save.)
- **The write is atomic and preserves permissions.** A failure after partial temporary output, or a failed replacement, leaves the previous file's bytes untouched and removes what it wrote, so a failed save never costs the user the configuration they already had. (Chosen over writing the destination in place.)
- **The home file is the default store.** When neither file exists, the tab creates `~/.janissary/roles.json` holding the five default roles; a project's `.janissary/roles.json` stays an opt-in override. (Chosen over creating the project file.)
- **A broken file falls back along the chain.** A broken project file falls back to the home file, a broken home file to the defaults; the tab shows the roles it is using plus one line naming the problem and the file it found, and leaves the broken file on disk untouched. (Chosen over defaults-only fallback or an error state that blocks editing.)
- **The tab names the file in effect.** Each view of the list says whether it is editing the home file or the project override. (Chosen over editing without a visible destination.)
- **The command takes no argument.** Bare `roles` opens or focuses the tab; `roles` with an argument is answered `Usage: roles`. (Chosen over a `roles <name>` direct-open form.)
- **Role names are unique case-insensitively.** A name is trimmed and must be nonempty; adding or renaming to a name another role already holds case-insensitively is refused with `A role named "<name>" already exists.` and nothing is written. (Chosen over allowing duplicates.)
- **Entries are added by dragging from the catalog.** The tab shows the harness model catalog — every harness with its models from `harness-models.json` — and dragging a model from it into a role card appends that harness/model entry to the role's ordered list. A role holds as many entries as the user drags in, and the same drag gesture reorders entries within a role and roles within the list. (Chosen over dropdown-based entry editing.)
- **Effort is a fixed dropdown per entry, and a choice in the picker.** Each entry carries an effort chosen from a default (no effort stored) plus `low`, `medium`, `high`, `xhigh`, and `max` — the New harness dialog's set, which this feature gives one shared home so the two surfaces cannot drift. The add-entry picker offers the same three choices, so an entry is created at the effort its author chose rather than at the default, which would otherwise cost a second persisted edit on a row that has just been created. (Chosen over free-text effort.)
- **The picker owns its selections and unmounts when it closes.** That is what makes "a choice never carries to the next entry" a property of the component tree rather than a rule to remember; a harness change still clears the model and the effort inside it, for the same reason it always did. (Chosen over holding the picker's state in the card.)
- **The tab is two columns: catalog left, roles right.** The catalog column lists every harness with its models from the loaded catalog, always visible beside the roles list, so a model is never more than one drag away. (Chosen over a catalog section above the list.)
- **Every role card has an add-entry picker as well as the drag path.** A + control opens a small harness/model/effort picker so an entry can be added without a pointer; dragging from the catalog stays the fast path. (Chosen over drag-only.)
- **A drop lands anywhere on the card.** Dropping a catalog model over a populated card appends an entry whether the pointer is over the card's own space, over one of its entry rows, or over a control inside one; a zone ends a gesture only when it handles it, so a row passes a drag it does not own up to the card around it. Every drop appends; nothing is replaced in place, so replacing a model is a remove plus an add. (Chosen over replace-on-entry-drop, and over a drop that silently does nothing over a nested row.)
- **An entry is removed by its × button or by dragging it out.** Both gestures work: the × button is one click, and dragging the entry out of its role card removes it. (Chosen over × only or drag-out only.)
- **A new role is created by an add-role control.** It appends a card with an editable, empty name field; roles are named by typing, never by dragging. (Chosen over a drag-onto-new-role zone.)
- **A refused name stays in the field it was typed in.** The creation control closes only once the server accepts the name, so a duplicate can be corrected and committed again; an answer that arrives after the user has typed something newer does not wipe the newer text. (Chosen over clearing the field before the answer.)
- **The five default role descriptions.** `planning` keeps the feature text's description. The tab writes `Research, comparison, and information gathering for a task or question.` for `research`, `Review of code changes for correctness, style, and risk.` for `code review`, `Implementation of an approved plan or a described change.` for `implementation`, and `Writing and updating specs, plans, and user or developer documentation.` for `documentation`.
- **The empty list reads `No roles yet.`** beside the always-visible add-role control.
- **A broken file's line names the file, the problem, and the fallback.** The format is `roles.json <problem> at <path> — showing <fallback>.`, where the fallback is the other file in the chain or the default roles, e.g. `roles.json is not valid JSON at /Users/me/.janissary/roles.json — showing default roles.`
- **The unusable-file refusal belongs to the file in effect.** A problem about a file the tab fell back from is shown but does not disable editing: the whole file that took its place takes the edit, and the broken one stays untouched. Only a file in effect that decoded nothing, or that dropped something, refuses with `roles.json at <path> is unusable — fix the file before editing roles.` (Chosen over refusing on any problem line, which named a healthy file unusable.)
- **The tab's title is `roles`.** Lowercase, matching the command and the other plugin tab titles.
- **The file is an object keyed by role name.** Each role is `{ "description": "<string>", "entries": [ { "harness": "<name>", "model": "<id>" }, … ] }`, with `"effort"` present on an entry only when the entry stores a non-default effort. The object's key order is the role order, so a reorder rewrites the file with the keys in their new order; the tab never depends on any other order. (Chosen over an array of role objects.)
- **The file's member order and every accepted name round-trip.** The textual key order is recovered from the source and each key and value is written independently, so `__proto__`, integer-looking names, escaped quotes, and names the tab would not itself accept all survive a reread, a rename, and a publication — and numeric names are never sorted numerically. (Chosen over re-deriving the order from `JSON.parse`, which cannot answer for a key it did not decode.)
- **The launcher rail gains a Roles entry.** The built-in default command set gains `{ "icon": "faUserTag", "label": "Roles", "command": "roles" }` — the icon is added to the launcher's registered set — so a project that never wrote a `launcher.json` shows it. (Chosen over leaving the rail unchanged.)
- **The role list may be empty.** Deleting the last role is an ordinary edit that writes an empty list; the tab shows an empty state with an add affordance. (Chosen over requiring at least one role.)
- **The default `planning` role ships with the feature text's two entries.** Codex `gpt-6-sol` at effort `xhigh` and Claude Code `claude-opus-5-5` at effort `xhigh`; the other four default roles start with empty entry lists. (Chosen over all five starting empty.)
- **A partially damaged file keeps what decodes on screen, and refuses every edit.** A malformed role or entry is dropped and counted while the usable remainder opens; only a file where nothing survives falls back along the chain — the launcher's partial-loss rule applied to roles. While the damaged file is the one in effect, an edit is refused with the same `roles.json at <path> is unusable — fix the file before editing roles.` the wholly-unusable case uses, because writing from a partly decoded read would rewrite the whole file and silently discard the dropped parts the tab had just reported. The file is left exactly as it is until it is fixed by hand.
- **A refusal the server answers is shown in the tab.** A duplicate name, a missing role or index, an unusable file, and a failed write all arrive as a rejection, and the tab renders the server's own words in one line under the source line, fed through a single setter shared by the composition and the role card. The line clears on the next edit raised, so a message never lingers over a state it no longer describes.
- **An editable field follows the stored value it has not been typed over.** One shared hook carries the text a field shows, the baseline that text was written against, and whether it is clean; a republished value is followed while the field is clean, so an untouched field never commits text the file does not hold. (Chosen over seeding the inputs from props once, which let a blur write one client's stale text back over another's accepted edit.)
- **A conflict is raised only for text that displaced somebody's typing.** A stored value arriving under a genuine active draft replaces it and says so; the value this client has just saved coming back in the next publication is the draft itself and is followed silently, because nothing was displaced. (Chosen over reporting any republished value that differed from the baseline, which reported a conflict after every description save.)
- **A description edit carries the text it was written against.** The client cannot see the window between another client's write landing on disk and its payload reaching this one, so `describe-role` carries the stored description it saw and the server refuses a stale edit rather than applying it; the guard requires the field, so no caller can omit it. (Chosen over an optional precondition, or a client-only check.)
- **Positional entry edits carry the whole ordered entry list the user saw.** A removal, a reorder, and an effort change each travel with the list they were made against, a drag with the list from when the gesture began; the server compares length and every entry's harness, model, and effort inside the serialized edit queue, and a changed list is refused with a retry rather than applied to whatever now holds that position. (Chosen over persistent entry identifiers, and over acting on a position alone.)
- **A stored effort the catalog does not offer is shown as its own option.** The file stores any effort string verbatim, so the effort `<select>` renders one extra option carrying the stored value when it is outside the fixed levels; without it a hand-written effort such as `ultra` would read as though the entry held none.
- **The shared contract declares no imports.** The client reaches `src/plugins/roles/shared.ts` through `@shared/plugins/roles/shared`, so an import there is a runtime dependency from a browser chunk into the server plugin API; the object predicate the guards need is hand-written beside them, and a test walks the client entry's static import graph to prove the tab's browser safety is a property of the source. (Chosen over the server API's `isRecord`, which is what the thirteen sibling contracts still use.)
- **The payload guard validates every level it claims to.** `catalog.models` is accepted only as a record whose every own value is an array of strings — the shape `LaunchCatalog` declares and the tab consumes two ways — so a malformed list is refused at the boundary rather than reaching `Object.entries(...).map` as a render failure. The roles the file holds stay outside that check: a stale entry is left unflagged. (Chosen over asserting the top level only.)
- **The JSON config reader is shared with the launcher.** The read-parse-decode core both config-file plugins need lives once as `readJsonConfigFile` in `src/plugins/files.ts` — the one host file module the plugin import boundary admits to a concrete plugin — with each caller supplying its decoder, its wording for a parsed-but-unusable file, and its own fallback policy, which the two deliberately keep different.

Established by existing behavior in this codebase:

- A bundled tab plugin is the existing way to contribute a command-opened tab with its own payload and client component: `src/plugins/<id>/{manifest,shared,activate}.ts` plus `web/src/plugins/<id>/`, registered in `src/plugins/catalog.ts`, `src/plugins/loaders.ts`, and `web/src/plugins/registry.tsx`. A center-strip plugin tab claims its command, opens through `openOrFocusTab`, and never calls `dockTab` — the search plugin at `src/plugins/search/` is the precedent.
- The launcher plugin is the precedent for a JSON-backed configuration tab whose file lives in the project's `.janissary/` and can be replaced wholesale by a home-directory `~/.janissary/` copy, including creating the file with defaults when it is absent.
- The harness model catalog is owned by `src/harness/models.ts` (`loadHarnessModels`, `modelsFor`, `isKnownModel`), loaded once at startup from `src/main.ts` (the `loadHarnessModels(cwd)` call) and therefore immutable for a run; the project override is `.janissary/harness-models.json`. The New harness dialog offers effort levels `low`, `medium`, `high`, `xhigh`, and `max` plus a default with no `--effort` flag, and passes an effort level through verbatim.
- Plugin commands are listed in the `help.md` Commands table in alphabetical order, and the table is checked by `src/commands.test.ts`.
- A concrete server plugin may statically import only `../api.js`, `../files.js`, and the two documented opener helpers — every other `../` import is refused by `eslint.plugin-boundaries.mjs` (the `src/plugins/*/**` `no-restricted-imports` rule), so the roles plugin cannot reach `src/harness/models.ts` itself.
- A concrete client plugin may import only its client `../api`, its own `@shared/plugins/roles/shared` contract, and `../shared.css`; the file-navigator drag hook (`web/src/file-navigator/useFileNavigatorDrag.ts`) is therefore a pattern to mirror, not a module to import.

## Proposed changes

**One additive host capability plus one shared constant.** The roles tab must show the same harness/model catalog the harness launch dialog uses, and the plugin import boundary (`eslint.plugin-boundaries.mjs`) forbids reaching `src/harness/models.ts` from a plugin, so the host publishes the launch vocabulary to plugins. Put the effort set in a new pure module `src/harness/effort-levels.ts` — a constant `EFFORT_LEVELS` holding `low`, `medium`, `high`, `xhigh`, and `max`, with no imports so the web bundle can hold it — and switch the New harness dialog's local constant at `web/src/harness/HarnessLaunchDialog.tsx` to import it through `@shared/harness/effort-levels.js` — the client reaches it because every `@shared` alias (`web/tsconfig.json` paths, `web/vite.config.ts` resolve, the `client` project in `vitest.config.ts`) already resolves the `src/` tree for runtime values, the way `syntax-themes.ts` is reached today. Then add `harnessLaunchCatalog(): { models: Record<string, string[]>; efforts: string[] }` to the `TabPluginServerCapabilities` interface in `src/plugins/api.ts` (documented beside `projectFileList` as a pull of host-owned, startup-loaded data), add the name to the `TabPluginCapabilityName` union and the `CAPABILITIES` record in `src/plugins/api-capabilities.ts`, and implement it in the capability object `createPluginContext` builds in `src/plugins/context.ts` — models built from `HARNESS_NAMES` (from `src/harness/index.ts`) and `modelsFor` (from `src/harness/models.ts`), efforts from the new constant, answering an empty model map while the plugin is disabled the way `projectFileList` answers its empty values. This is additive — an optional new capability keeps `TAB_PLUGIN_API_VERSION` at 2 — and the frozen v1 fixture is untouched. The roles tab's payload carries the catalog the activation pulled, so the client never fetches it itself.

**A new bundled tab plugin named `roles`:**

- `src/plugins/roles/shared.ts` — the payload and intent types, the schema-version constant, and the hand-written guards, declaring no imports at all: the client reaches this contract through `@shared/plugins/roles/shared`, so an import here is a runtime dependency from a browser chunk into a server module, and `ai/guidelines/plugins-tabs.md` requires a shared contract to stay import-free. The object predicate the guards need is therefore hand-written beside them rather than imported from `../api.js`, as the thirteen sibling contracts still do. The payload carries the decoded roles, the effective file's source (`home`, `project`, or `default`) and path, an optional problem line, and the launch catalog (`models` and `efforts`) the activation pulled; `isRolesPayload` requires `catalog.models` to be a record whose every own value is an array of strings, because the catalog column and the picker both consume that inner half. The intent guards are: `isAddRoleIntent`/`isRenameRoleIntent` (`{ name }` / `{ name, next }`, both nonempty trimmed strings), `isDescribeRoleIntent` (`{ name, description, expected }`, where `expected` is the description the edit was written against), `isDeleteRoleIntent` (`{ name }`), `isMoveRoleIntent` (`{ name, to }`, `to` a whole index), `isAddEntryIntent` (`{ role, entry }` where the entry is `{ harness, model }` plus an optional `effort` string), and the three positional entry intents — `isSetEntryEffortIntent`, `isRemoveEntryIntent`, and `isMoveEntryIntent` — each of which carries `expected`, the whole ordered entry list the edit was made against. Every guard rejects arrays and `null` where an object is required and validates every field, per the house guard rules.
- `src/plugins/roles/manifest.ts` — the pure declaration: id `roles`, its own semantic version, `TAB_PLUGIN_API_VERSION`, a payload schema version of 1, `tabLabelPrefix: 'roles'`, empty `fileExtensions`, the `roles` command claim, and the capabilities `openOrFocusTab`, `updateTab`, `originTab`, `harnessLaunchCatalog`, `rejectRequest`, and `reportFailure`.
- `src/plugins/roles/ordered-json.ts` — the two pure helpers that keep the file's shape: `orderedJsonKeys`, recovering the top-level member order from the validated source text by scanning past escaped strings and nested values, and `serializeRoles`, writing each role name and value independently into the object shape the reader expects. `src/plugins/files.ts` passes the source text to every config decoder as a second argument so the roles reader can use it; the launcher's decoder ignores it.
- `src/plugins/roles/roles-file.ts` — the file layer, taking `(home, root)` as parameters so tests need no home-directory mocking, mirroring `readLauncherFile`'s signature style. It resolves the project file at `<root>/.janissary/roles.json` and the home file at `<home>/.janissary/roles.json`, with the project file replacing the home file wholesale when it exists — including when it holds an empty object, which is an explicit choice of zero roles rather than a fallback. A missing pair creates the home file with the five default roles (each with its settled description, `planning`'s entries seeded with the two entries from the feature text's example). Decoding is strict per role and per entry following `commands-file.ts`'s partial-loss pattern: a role whose value is not an object, a non-string description, a non-array entries list, or a malformed entry is dropped and counted, and the usable remainder is served; only when nothing usable remains does the wrong-shape path fire, falling back along the chain (broken project file to the home file, broken home file to the defaults) with a one-line problem in the settled format. An unreadable or invalid-JSON file falls back the same way and is left untouched. A read also carries `unusablePath` — the path of the file in effect when that file is the damaged one — which is what lets the activation tell a problem about the file it skipped from a problem about the file on screen. The read-parse-decode core it shares with the launcher lives once in `src/plugins/files.ts` as `readJsonConfigFile(filePath, fileName, decode, unusable)`, which answers the decoded value or one canned problem line for a read failure, a parse failure, or a parsed value the decoder rejects; the roles layer supplies `decodeRoles` and the wording `is not a set of roles`. Writes go through the shared `writeJsonConfigFile`, so a replacement failure preserves the destination and its permissions and removes the temporary file; the write reports success or failure and never throws.
- `src/plugins/roles/activate.ts` — the activation, built like the search plugin's (command → `openOrFocusTab`, `noFileOpener` opener, `defineIntents` table). The command resolves the root as `capabilities.originTab()?.root ?? process.cwd()`, answers `roles` with any argument with the rejection `Usage: roles`, then reads the effective file and opens or focuses the singleton tab under instance key `roles` with title `roles`. Each intent handler serializes on a private promise chain — one intent's read-modify-write finishes before the next begins, so two rapid edits cannot interleave and lose one — then reads the file in effect, applies the edit (refusing a duplicate role name with `A role named "<name>" already exists.`), writes, and on success republishes the payload so the tab shows exactly what the file holds. It refuses the edit outright when the read answered `source: 'default'` or carried an `unusablePath` — a file that decoded nothing, or that dropped something, would be rewritten wholesale from the decoded part — with `roles.json at <path> is unusable — fix the file before editing roles.`, naming that path and leaving that file untouched; a fallback read of a whole file carries a problem line but no `unusablePath`, so it takes the edit. A failed write answers the intent as a rejection with `Could not write roles.json at <path>.` and leaves the payload unchanged. The three positional entry intents first check their `expected` snapshot against the freshly read role, republishing the current roles and refusing with `The entries of role "<name>" changed elsewhere — retry the edit on the current list. Nothing was written.` when it no longer matches.
- `src/plugins/roles/role-edits.ts` — the nine pure role-list edits (add, rename, describe, delete, move a role; add, set-effort, remove, move an entry), each answering the new list or refusing a bad request — a name already taken, a role or index that is not there, a description written against text the file no longer holds — by throwing the contract's `TabPluginRejection`, plus `matchesEntrySnapshot`, the pure ordered-list comparison the activation uses for the positional preconditions. The activation spells no check twice.
- `web/src/plugins/roles/index.tsx` — the client entry, default-exporting the roles component and named-exporting `isPayload` from the shared contract through `@shared/plugins/roles/shared`, plus its own `roles.css` (loaded from the entry, as `schedules.css` is).
- `web/src/plugins/roles/RolesTab.tsx` — the composition: the catalog column (every harness from the payload's catalog with its models) beside the roles column (the source line, the payload's problem line, the refusal line an edit earns, the role cards, the add-role control, and the `No roles yet.` empty state). It holds one refusal state, cleared by the next edit it raises and set by the catch on any rejection, and passes the setter to each card so one path serves every control. The creation control awaits its own `add-role` rather than firing and forgetting, so a refused name stays in the field and is cleared only while it still holds the submitted text; the same name is never submitted twice, and a name typed while an answer is in flight is not wiped by it.
- `web/src/plugins/roles/useRoleDraft.ts` — the hook behind both editable fields of a card: the text the field shows, the baseline that text was written against, and whether the draft is clean. It returns `{ value, set, revert, commit, conflicted }`; `commit()` answers `null` while the draft is clean and `{ text, baseline }` once it is not, and `revert()` restores the baseline. The follow-the-server adjustment uses React's render-phase "adjusting state when a prop changes" form, so a clean field never paints one frame of the old text, and `conflicted` is set only when the new value displaced a draft that was neither the baseline nor the text just saved.
- `web/src/plugins/roles/EntryPicker.tsx` — the add-entry picker as its own component: harness, model, and effort selects plus Add and Cancel. It takes the catalog's `models` and `efforts`, owns the three selections, clears the model and the effort when the harness changes, and reports the chosen triple through `onAdd`.
- `web/src/plugins/roles/RoleCard.tsx` — one role card: the editable name and description, both `useRoleDraft` hooks, the ordered entry rows with their effort dropdowns (each rendering the stored effort as its own option when it is outside the catalog's levels), the per-entry remove button, the entry picker, the drop highlight, and the refusal it hands the tab through the `onRefusal` prop. Every positional control carries the displayed entry list, and a conflict raised by either draft goes to the tab from one effect. Extracted so no file approaches the 200-line limit by compaction.
- `web/src/plugins/roles/roles-dnd.ts` — the drag-and-drop plumbing in one small module: the drag payload (which catalog model, which entry with the list the gesture began against, which role is being dragged), the three native handlers the components attach (`draggable`/`onDragStart` to begin, `onDragOver` to allow and highlight a drop zone, `onDrop` to finish), and the intent each completed gesture raises. It uses the browser's own HTML5 drag-and-drop rather than a pointer gesture: an in-tab drop needs no live transform, no measured rects, and no cross-surface drop handles — the machinery `useTabReorder` and `useFileNavigatorDrag` carry for dragging between windows and into PTYs — so three handlers replace a threshold, window listeners, and a disposer. A nested entry row ends a gesture only when the gesture is a sibling reorder it owns, and only then does it consume the event, so a catalog model or a role grip dropped over a row lands on the card. The pointer-gesture modules are the pattern's reference and are not importable from a plugin (`eslint.plugin-boundaries.mjs`).

**Registration and documentation.** The manifest joins `tabPluginCatalog` (`src/plugins/catalog.ts`, which also widens `ProductionTabPluginId`), the activation joins the literal server loader map in `src/plugins/loaders.ts`, and the client entry joins `clientPluginLoaders` in `web/src/plugins/registry.tsx` — the existing parity tests (`src/plugins/loaders.test.ts`, `web/src/plugins/registry.test.tsx`) then fail if any map is missed. `help.md` gains its `roles` row between `rename` and `schedule` (alphabetical, enforced by `src/commands.test.ts`). `DEFAULT_LAUNCHER_COMMANDS` in `src/plugins/launcher/commands-file.ts` gains `{ id: 'roles', icon: 'faUserTag', label: 'Roles', command: 'roles' }`, which also seeds `janus init` (`src/project/init.ts` builds its file from the same constant), and `faUserTag` joins the launcher's registered icon set in `web/src/plugins/launcher/launcher-icons.ts`. The launcher's own config read moves onto the shared `readJsonConfigFile`, with its problem wording and its empty-file fallback policy unchanged. Specs and user docs: a new `product/specs/roles.md` describing the file format, precedence, defaults, and every refusal verbatim; the bundled-plugin mention in `product/specs/tab-plugins.md`; the default-rail paragraph in `product/specs/launcher.md`; and a new user-documentation page `documentation/user-documentation/tab-types/roles.md` with its sidebar entry in `documentation/.vitepress/config.mts`.

## Out of scope

Declined in gap research against the mature products that own this capability:

- **Launch flags on entries.** Codex profiles (developers.openai.com/codex/local-config) and Roo Code's API profiles (docs.roocode.com/features/api-configuration-profiles) bundle approval policy, sandbox mode, thinking budget, and provider settings into each named profile; this plan's entries stay harness/model/effort only, because nothing in this version consumes even the model.
- **A launch surface that consumes roles.** Continue's active-model-per-role dropdowns (docs.continue.dev/customize/model-roles/intro), Cline's Plan/Act model switching (docs.cline.bot/core-workflows/plan-and-act), and Codex's own profile-picker gap (github.com/openai/codex/issues/22160) all expose named configurations where models are chosen; this version is the configuration tool only.
- **A sticky last-used role.** Roo remembers the last profile per mode and per task (docs.roocode.com/basic-usage/using-modes); the New harness dialog already remembers its selections in memory for the run.
- **Agent-facing role descriptions for spawn selection.** Codex's `agents.<name>.description` carries role guidance for spawned agents (developers.openai.com/codex/config-reference); the ready backlog's ACP sub-agent skill feature owns the spawning surface, and `product/specs/roles.md` documents the file for it.
- **Stale-entry warnings.** aider warns about models whose metadata it does not know and Codex refuses unknown models; a hand-edited file naming a model outside the loaded catalog is left unflagged in this version, and the payload guard deliberately keeps that case open.
- **Free-text effort on a new entry.** The per-entry dropdown is where an out-of-catalog value stays visible and editable; the picker chooses from what the host published.

Other exclusions:

- Any consumer of the roles file: no launch dialog, command flag, or ACP skill reads roles in this feature. The tab is the configuration tool only.
- Merging a project's roles.json with the home file — the project file replaces the home file entirely, per the feature text.
- Editing `harness-models.json` itself; the tab consumes the catalog the loader already produced.
- Docking the roles tab into a sidebar.
- Reordering roles or entries from the keyboard: the add-entry picker and the remove button are pointer-free, but reordering rides the drag gesture alone. The named ceiling is a keyboard reorder path (per-row up/down controls) if one is ever asked for; nothing in this feature blocks adding it later.
- Re-reading roles.json on a timer or reacting to an external edit made while the tab is open; the payload is built when the tab opens and after each of the tab's own writes. What the fields do follow is the published payload, so a second window on the same file is synchronized without a watcher.
- Persistent entry identifiers, a revision counter, or any cross-process filesystem arbitration for the entry preconditions; the whole displayed list is what travels with the edit.
- Automatic replay of a refused edit, and merging a conflicting draft the way a text editor would: the stored value wins and the line says so.
- Repairing a damaged roles file on the user's behalf, and changing the payload contract or the plugin API for anything else here.
