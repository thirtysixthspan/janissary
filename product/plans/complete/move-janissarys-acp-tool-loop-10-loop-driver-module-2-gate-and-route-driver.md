## Design decisions

- **Signatures.** All in `src/acp/drive-loop.ts`:
  - `driveToolLoop(session, prompt, snapshot, host, events, signal)` returns `void`, like `runAcpToolLoop`. `session` is `AcpLoopSession`, `prompt` the user's text, `snapshot` the core variant `Extract<AcpRunSnapshot, { kind: 'core' }>`, `host` an `AcpToolHost`, `events` an `AcpLoopHandlers`, and `signal` a required `AbortSignal`.
  - `runToolLoop(session, prompt, snapshot, host, events, signal)` has the same parameters and return, and in this subplan only calls `driveToolLoop`. It is the one entry point the local side will call (subplans 11 and 13). Subplan 23 adds the branch that hands a remote session to the far side and widens `session` to admit `RemoteAcpSession`.
  - The snapshot parameter is core-only here so no untested agent branch exists. Subplan 12 widens both functions to the full `AcpRunSnapshot` union when it adds the agent kind; that widening breaks no caller.
- **The core loop options.** `driveToolLoop` wraps `runAcpToolLoop` (`src/acp/loop.ts`, unchanged) and passes it, in `AcpLoopDeps`:
  - `tools`: `createAcpToolTable(snapshot.grants)`, or `[]` when `snapshot.withoutTools`, as `runCorePrompt` does at `src/acp/run-prompt.ts:84` "`snapshot.withoutTools ? [] : createAcpToolTable(snapshot.grants)`". `tools` is not itself an `AcpLoopDeps` field: `driveToolLoop` builds it once, as a local typed `AcpTool[]` (mutable, because `corePrimer` and `toolExtractor` take `AcpTool[]`), and the same array feeds `primer`, `extractCommand`, and the runner's gate, so the three can never disagree.
  - `primer`: `corePrimer(snapshot, tools)` (piece 10.1).
  - `extractCommand`: `toolExtractor(tools)`.
  - `maxSteps`: `CORE_MAX_STEPS`, an exported constant of 8, passed explicitly. `runAcpToolLoop`'s own `?? 8` default stays as it is. Subplan 16 relies on the constant to send no step count, and subplan 21 calls `events.finished(reason, CORE_MAX_STEPS)` with it, so both sides use one value.
  - `signal`: the `signal` parameter.
  - `runCommand`: the gate-then-route runner below.
- **The host** is a new exported type `AcpToolHost` in `src/acp/types.ts`, beside `AcpLoopHandlers`: `runCaller(command)` and `runWorkspace(command)`, each returning the step's output as `string | Promise<string>`, the same return type as `AcpLoopDeps.runCommand`. It lives in `types.ts` so `src/remote/acp-session.ts` (subplans 21–23) can import the type without importing the driver.
- **The runner** is a module-private function in `drive-loop.ts` that closes over `snapshot`, `tools`, `host`, `events`, and the remembered step, built inside `driveToolLoop` and passed as `runCommand`. Its shape is `coreToolRunner` at `src/acp/run-prompt.ts:40` (gate, `'refusal' in decision` narrowing, then `decision.runsOn`), minus the `notify` call and the `Managers` dispatch. For each command `runAcpToolLoop` hands it:
  1. It calls `gateCommand(snapshot, tools, command)` (`src/acp/tool-table.ts`, "`gateCommand(snapshot: AcpRunSnapshot, tools: readonly AcpTool[], command: string)`"; the core snapshot and the mutable `tools` both pass) first, because `startCommand` needs the side. A gate throw (`No ACP tool matched command: …`) propagates out of `runCommand` synchronously, reaches `runAcpToolLoop`'s catch, and becomes the `error` event as today. No `startCommand` fires for it. Today `runCorePrompt` records the command before the gate throws, but the extractor only yields commands some tool owns, so the throw is unreachable in practice and the lost record line is not a behavior change anyone sees.
  2. It fires `events.startCommand?.(command, workspace)` before anything runs, refusals included. `workspace` is `decision.runsOn === 'workspace'`, and `false` for a refusal: a refused step ran nowhere, so it is never tagged as a remote workspace step (subplan 24). This matches today's `recordTool(command)` before the runner, which is what shows a step while a question is pending.
  3. A refusal returns its `refusal` text as the step's result, so it is one completed step that consumes one of the eight (source decision 6). Neither host function is called. The driver raises no notification; the `command-disabled` notification stays in `coreToolRunner` until subplan 11 moves it into the `ranCommand` handler on `refused === 'disabled'`.
  4. Otherwise it returns `host.runWorkspace(command)` or `host.runCaller(command)` by `decision.runsOn`.
  5. It remembers the step's `workspace` and `refused` in one closure variable of type `{ workspace: boolean; refused?: 'disabled' }`, assigned right after the gate returns and before `startCommand` fires (so before either host function runs). `refused` is the refusal's `decision.refused` (present only for the disabled refusal) and absent for a routed step. `runAcpToolLoop` runs one command at a time and calls `ranCommand` only after `runCommand` returned without throwing, so a single variable is enough and is always set when `ranCommand` reads it.

  Piece 10.3 wraps step 4's promise result for the after-abort rejection case; until then a host rejection, before or after an abort, reaches `runAcpToolLoop`'s catch and becomes `error`, as it does for any `runCommand` today.
- **Events.** The driver passes `runAcpToolLoop` a handlers object that forwards `startTurn`, `chunk`, `endTurn`, `finished`, and `error` to `events` unchanged. Its `ranCommand(command, result)` forwards as `events.ranCommand(command, result, workspace, refused)` from the remembered step, always with four arguments: `refused` is passed positionally and is `undefined` except for a disabled refusal, so a recording handler sees `[command, result, workspace, undefined]` for every other step. The object needs no `startCommand` member, because `runAcpToolLoop` never calls one; the runner calls `events.startCommand?.(…)` directly. The driver adds no `active()` or abort guard of its own on events (see piece 10.3 for cancellation).
- **`AcpLoopHandlers` gains two additive, optional members** (`src/acp/types.ts`):
  - `ranCommand` becomes `(command, result, workspace?, refused?)`, with `workspace?: boolean` and `refused?: 'disabled'` (the same literal as the `refused` member of `AcpGateDecision` in `tool-table.ts`). Write the `'disabled'` literal in `types.ts`; do not import `AcpGateDecision` there, because `tool-table.ts` already imports `AcpRunSnapshot` from `types.ts`. An absent `workspace` means false. The driver always passes `workspace`, and `refused` is `'disabled'` only for a disabled refusal (see Events). Optional parameters keep `runAcpToolLoop`'s own two-argument call (`src/acp/loop.ts` "`h.ranCommand(command, result)`"), `guardAcpHandlers`, the handler literals in `runCorePrompt` and `executeAgentRun` (`src/agent/execute.ts`), and every test handler and `AcpLoopHandlers` cast (`src/acp/loop.test.ts`, `src/acp/manager.test.ts`, `src/acp/manager-fallback.test.ts`, `src/agent/execute.test.ts`) compiling unchanged.
  - Each new parameter and member gets a one-line comment in the style of the existing ones in `AcpLoopHandlers` (for example "`// A command was auto-run; show it and its result.`").
  - A new optional `startCommand?: (command: string, workspace: boolean) => void`. Optional, so `executeAgentRun`'s handler literal needs no placeholder before subplan 13 replaces it.
  - The parameter order is the one subplans 18 and 22 already use: `startCommand(command, false)`, `ranCommand(command, output, false)`, `ranCommand(command, result, workspace, refused)`.
- **`guardAcpHandlers` is untouched here** (`src/acp/guard-handlers.ts`). It forwards only `(command, result)` and has no `startCommand`, which is harmless because nothing routes driver events through it yet. Subplan 11 passes the new event and arguments through it.
- **Session.** The driver passes `session` to `runAcpToolLoop` as given. Any `active()` wrapper around a local session's provider callbacks stays the caller's job (subplan 11 keeps the one `runCorePrompt` builds today).
- **Purity** (shared with pieces 10.1 and 10.3; the rule is stated in 10.1). This piece adds `runAcpToolLoop` from `./loop.js` (which imports `command-line.ts` and `error-text.ts`, neither reaching `Managers`), `createAcpToolTable`, `toolExtractor`, and `gateCommand` from `./tool-table.js` (added to the existing `toolPrimer, type AcpTool` import line), and the `AcpLoopSession`, `AcpLoopHandlers`, and `AcpToolHost` types from `./types.js` (added to the existing `AcpRunSnapshot` type import). Nothing outside the 10.1 list.
- **Agent kind and `extractAgentCommand`.** Out of this subplan. Subplan 12 adds the agent branch and moves `extractAgentCommand` and its fence helpers from `src/agent/command-tools.ts` to a pure `src/agent/command-extract.ts`; `drive-loop.ts` does not import `src/agent/` here.

## Tests

Extend `src/acp/drive-loop.test.ts` (from piece 10.1) with a new `describe('driveToolLoop', …)` block, beside the existing `corePrimer` one. Use a scripted fake session copied from `makeSession` in `src/acp/loop.test.ts` (synchronous replies, records every prompt sent), a recording handlers object like its `makeHandlers` that also records `startCommand` and all four `ranCommand` arguments, and a host whose `runCaller` and `runWorkspace` are `vi.fn()` returning plain strings. With a synchronous session and synchronous host results the whole loop runs synchronously, so assertions follow the `driveToolLoop` call with no awaiting (piece 10.3 adds the promise-returning host cases). Pass a fresh `new AbortController().signal`. Do not mock `./loop.js` here. Build snapshots with the file's existing `coreSnapshot` helper, so `roleName` equals the role. Expect `8` literally in the cap and `finished` cases rather than importing `CORE_MAX_STEPS`, so a change to the constant is caught.

- routing: with grants `['db sqlite query']`, a `db sqlite query movies SELECT 1` reply calls `runCaller` exactly once with that command and never `runWorkspace`; with grants `['file read']`, a `file read notes.md` reply calls `runWorkspace` and never `runCaller`; in each, the second prompt the session receives contains the host's returned text (the loop's "`Output of \`<command>\`:`" follow-up);
- events in order for one caller step and a plain-text second reply: `startTurn(true)`, `chunk`, `endTurn`, `startCommand(command, false)`, `ranCommand(command, result, false, undefined)`, then for the follow-up turn `startTurn(false)`, `chunk`, `endTurn`, then `finished('answered', 8)`; the `file read` step reports `true` in both `startCommand` and `ranCommand`;
- refusals: grants `['db sqlite query']` with the row `{ name: 'db sqlite query', effectiveEnabled: true, effectiveAgentAccess: false }` gives one step whose `ranCommand` result is `Command is disabled: db sqlite query.` with `workspace: false` and `refused: 'disabled'`; an `ask` snapshot with grants `['db sqlite list']` (so the database tool is in the table) emitting `db sqlite query movies SELECT 1` gives `Command not allowed for role "ask": db sqlite query.` with `workspace: false` and `refused` undefined; in both `startCommand(command, false)` fires first, neither calls a host function, and the refusal text is fed back in the follow-up prompt;
- the step cap: a session that always replies `db sqlite query movies SELECT 1` (grants `['db sqlite query']`) calls `runCaller` eight times, records eight `ranCommand` events, and ends with `finished('capped', 8)`.

No driver test covers a gate throw. The driver's extractor only yields a command some tool in the same table recognizes, and that tool's `match` claims it, so the throw cannot be reached through `driveToolLoop`. The throw itself is covered by `src/acp/tool-table.test.ts`, and a throwing `runCommand` becoming `error` by `src/acp/loop.test.ts`.
