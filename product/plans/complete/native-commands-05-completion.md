# Native commands: completion filtering

**Complexity: 4/10** — the change reaches every completion path and adds a first-token command source, so correctness depends on catching each entry point and preserving argument and path behavior.

## Goal

Hide disabled application commands and subcommands from host completion while retaining their help entries.

## Decisions and dependencies

- Depends on inventory, settings, and server enforcement (work units 1–4). Use the same canonical metadata and effective parent settings as dispatch, including aliases and the selected command owner. Preserve existing completer semantics for arguments, paths, and explicitly requested shell execution.
- The host completion engine has no first-token command-name completion today: `src/completion/index.ts:66` falls through to `completeFilePath` for the first word. This unit adds a first-token candidate source from the canonical inventory so enabled command names are offered and disabled ones can be hidden. It does not add subcommand completers for commands that have none today, including `db`, `question`, `open`, `plugins`, `profile`, `queue`, `theme`, and `notifications`.
- Build the policy once in `src/controller/completion.ts:9` `complete`, which is shared by the `complete` RPC (`src/message/handler.ts:60`) and the plugin `completeLine` capability (`src/plugins/line-capabilities.ts:85`), and apply it inside `completeCommandLine`. Do not add a second filter in `src/plugins/line-capabilities.ts` or the shell plugin.
- Read `managers.nativeCommandSettings?.current()` once per completion request. Do not call `refresh()`, read `commands.json`, subscribe, or cache across requests. A missing manager or row means enabled, matching `src/native-commands/dispatch-policy.ts:18-20`. Use `effectiveEnabled` only; `agentAccess` does not affect human completion.
- Resolve the words already typed before the cursor through `resolveApplicationCommand`, after dropping one leading `/` exactly as `src/resolve.ts:28` does. If the longest matching form is disabled, return the existing empty result immediately. This suppresses argument and path completion under a disabled command or native child without a guard in every handler. Skip this guard for `!` lines.
- A disabled fixed form that is not yet typed is filtered separately only where a candidate resolves to a different canonical name. Today that is `completeBrowserCommand`: `browser content`, `browser goto`, and `browser eval` are native rows, while `browser use`, `browser window close`, and the other browser words resolve to the `browser` row. Filter each argument-1 word by its full form; the `close` word after `window` resolves to the `browser` row and is covered by the command guard. Leave window ids and every other argument value alone.
- Shared canonical names (`search`, `ask`, `tell`) share one setting exactly as dispatch does; disabling the name hides every owner and form with that canonical name. Do not add per-owner keys.
- While `help` is enabled, do not filter `help` output, `help/commands.md`, or `listHelpPages`: disabled commands stay listed and their pages stay completable. When `help` itself is disabled, its command word and page completion are suppressed like any other disabled command.
- Explicit shell execution is outside policy. A first token beginning with `!` is not an application command and keeps the existing fallback completion; `!` lines never pass through the command guard. Do not add first-token command completion for a leading `/`: `/` is also an absolute-path prefix, so a token beginning with `/` keeps the existing path completion.
- First-token command completion applies only to a non-empty bare word with no `/`, `\`, or quote. It merges enabled command names and aliases with the existing filesystem candidates, command candidates first, and uses the existing candidate/combine formatting. An empty token keeps the existing filesystem behavior. Candidate matching stays case-sensitive like `completeWord`.
- Do not add `Command.available` or tab-capability filtering; that is a separate execution constraint, and completion keeps its existing context behavior.
- The plugin capability and wire shape do not change: `completeLine` already returns the host completion result, and the web shell picker (`web/src/plugins/shell/useShellCompletion.ts`) consumes the same result unchanged. No new RPC, topic, config field, or notification event.
- New modules under `src/completion/` and `src/native-commands/policy.ts` stay under the 200-line `max-lines` limit and use `.js` relative imports. Do not grow `src/completion/files.ts` past the limit; extract its generic candidate helpers rather than duplicating them.

## Proposed changes

1. Extract the disabled-row lookup from `src/native-commands/dispatch-policy.ts:16-21` into a shared pure helper named `disabledApplicationCommand(input, snapshot)` in `src/native-commands/policy.ts`: drop one leading `/`, resolve with `resolveApplicationCommand`, find the snapshot row by canonical `row.name`, and return the row only when `effectiveEnabled` is false. Keep `dispatch-policy.ts`'s existing registered-command/help guard before the lookup so dispatch does not treat an arbitrary argument-bearing line such as `quit now` as a disabled `quit`, and do not change the exact `Command is disabled: <name>.` message or notification behavior.
2. Add `src/completion/command-policy.ts` with `allows(input)` built on `disabledApplicationCommand`, plus `commandNameCandidates(snapshot)`: the sorted, deduplicated first words of every enabled form and alias, excluding the `shell` row's `!` form. An unresolved input, missing snapshot, or missing row is allowed; with no snapshot, derive the candidate list from `listApplicationCommands()` as all-enabled. The module never reads files or managers.
3. Extract the generic candidate type, quoted-name formatting, path candidates, combine helper, and their unchanged-result helper from `src/completion/files.ts` into `src/completion/candidates.ts`, and have `files.ts` import them. Reuse that helper for the first-token merge; do not duplicate the suffix or longest-common-prefix logic.
4. Add a first-token completer named `completeApplicationCommandName(cursor, policy, cwd)` in `src/completion/command-names.ts` and run it first in `completeCommandLine` when `argumentIndex === 0`. It filters `commandNameCandidates` by the typed token, combines them with the token-filtered `pathCandidates` (commands first, then files), and returns the combined result. Return `null` only for a declined token (empty, `!`, `/`, quote, or path separator) so the existing chain and fallback run unchanged.
5. Thread a `CompletionPolicy` through `src/controller/completion.ts` into `completeCommandLine` as an optional final argument, defaulting to an all-enabled policy so existing direct test calls stay valid. The controller builds it from `managers.nativeCommandSettings?.current()` once per request. Update `src/plugins/shell-capabilities.test.ts:289`'s exact call assertion to include it.
6. In `completeCommandLine`, after reading the cursor and before the handler chain, apply the prefix guard from the decisions: build the typed prefix from `cursor.preceding`, skip `!` lines, call the policy's `allows` with that prefix, and return the existing empty result when it reports a disabled row. This is the only command-level guard; do not repeat it in each handler.
7. Pass the policy to `completeBrowserCommand(cursor, connections, policy)` as an additional argument and filter its argument-1 subcommand words by their full form (`browser <word>`); the `close` word after `window` resolves to the `browser` row, so the command guard already covers it. Leave window ids unchanged. No other existing completer needs a per-candidate check because its fixed words resolve to the typed command's own canonical name, and no other handler signature changes.
8. Update `product/specs/tab-completion.md` with the first-token command rules and disabled filtering, adding an `### Application command names` subsection after the intro at `:16` and before `### File navigator command (files)` at `:20`. Update the `### Help pages (help)` section at `:44` to state that disabled commands stay completable while help is enabled. Update `product/specs/application-commands.md` with the help-retains/completion-hides behavior, and `documentation/user-documentation/command-bar/tab-completion.md` to match. Do not change the plugin capability contract, wire shape, or `help` output.
