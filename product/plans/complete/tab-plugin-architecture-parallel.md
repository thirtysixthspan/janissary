# Tab plugin architecture (parallel plan)

**Complexity: 9/10** — a first-of-its-kind extension subsystem on both sides, with a versioned wire envelope, lazy activation under concurrency and timeouts, a failure and disposal lifecycle, an async widening of the whole command path, two new commands, and an end-to-end migration of a shipped tab.

## Summary

Add a versioned tab-plugin seam for bundled plugins, then move the video opener, video tab, and frame capture onto it as the first plugin. The host reads static declarations without importing any plugin behavior. It activates a plugin's server module and its client chunk only when `open <video-file>` or the new `video <path>` command actually needs them. Video behavior does not change. A new `plugins` command prints the declared catalog with each plugin's state, so a plugin that never fires is diagnosable without reading logs.

This is the parallel plan requested alongside `product/plans/draft/tab-plugin-architecture.md`. It targets the same feature and reaches it by a different route in three ways that matter. Plugin client code lives under `web/src/plugins/`, which means no changes to tsconfig, vitest, ESLint, stylelint, Knip, FTA, jscpd, opengrep, or `check-diff`. The host API is one integer, because a bundled-only catalog cannot experience version skew at runtime. And a disabled plugin owns no tabs, which removes the need for any in-body failure UI on the client.

## Design decisions

**Video is the first and only migration.** The video opener, the video tab, the capture RPC, and the external-player fallback all move behind the seam. Image, Markdown, editor, page, file navigator, notifications, schedules, monitor, harness, SSH, agent, and shell tabs stay exactly where they are. Video is the right first plugin because it is the only existing view that exercises every part of the contract at once: a lazily fetched client chunk, a mount that must survive tab switches without remounting, a client to server intent, and a configured external viewer.

**A plugin spans two directories, and no build or test configuration changes.** Server code goes in `src/plugins/<id>/`. The payload and intent contract goes in `src/plugins/<id>/shared.ts`, which the client imports through the existing `@shared` alias. Client code goes in `web/src/plugins/<id>/`. Every existing gate already covers both trees: `vitest.config.ts:14` and `:77` for the two test projects, `eslint.config.mjs:121`, `:136`, and `:144` for the NodeNext, bundler, and React Hooks overrides, `package.json:44` for stylelint, `knip.json` for dead-code scanning, and `package.json:37`, `:40`, `:56` for FTA, jscpd, and opengrep. `scripts/check-diff.mjs:25` and `:26` key on the `src/` and `web/` prefixes, so a plugin change already routes to the right checks. The cost is that one plugin is not one directory. The payoff is that no plugin file is ever checked by the wrong toolchain, and nothing in section 7 of the companion plan needs to happen.

**Plugins contribute file openers and commands.** A declaration may claim file extensions, each with an optional content type, and one command name. Resolving a claimed extension through `open`, or matching a declared command's first token, is what triggers activation. Nothing else does. Supporting async plugin commands means widening `Command.run` at `src/commands/types.ts:8` to allow a promise and threading that promise through the `open` command, `OpenFileManager`, `runOpenCommand`, `CommandManager.executeCommand`, and `CaptureManager.dispatchMatchedCommand`.

**A failed plugin stays disabled until Janissary restarts.** An incompatible API version, a rejected import, an activation throw, an activation timeout, an invalid plugin-produced payload, a failed client chunk, a render exception, or a guarded handler failure all disable that one plugin. The host records the reason, disposes what the plugin acquired, and never imports or calls it again in that process. Every later attempt returns the recorded reason. Other plugins and the rest of the app keep running.

**A disabled plugin owns no tabs.** A failure before mount opens no tab at all. A failure after a tab already exists closes every open tab belonging to that plugin and releases their served-file references. This gives one rule instead of two, and it means the client ships an error boundary that reports a failure but no in-body failure view. The originating transcript and the notifications feed carry the whole explanation.

**The failure message reads `Tab plugin "video" disabled: <reason>.`** The reason is reduced to a single actionable line with no stack. Trailing terminal punctuation is trimmed so the line ends with exactly one period.

**Plugin failures follow the existing notification policy unchanged.** A new `plugin-failure` entry joins `NotificationEventType` at `src/notifications.ts:14` as an explicit event, so it bypasses focus suppression and is always eligible. The feed receives it only when the notifications tab is already open. `src/notifications-tab.ts:34` drops it otherwise. Nothing buffers it and nothing creates that tab. The originating transcript always receives it.

**The video plugin contributes a `video <path>` command that does exactly what `open <video-file>` does.** Same parser, same glob expansion, same existence checks, same transcript provenance. A playable container opens and focuses a video tab. An external-only container goes to the configured player. `video` is a second route into one handler, not a second behavior, so there is one execution path.

**`plugins` prints one line per declared plugin.** The command takes no arguments. Each line reads from static declarations plus recorded host state: id, plugin version, required API version, state (`declared`, `active`, or `disabled`), activation duration in milliseconds once activated, and the recorded reason when disabled. The command never imports or activates anything.

**A plugin's shared contract module is self-contained.** `src/plugins/<id>/shared.ts` declares its payload types, its intent types, its schema version, and its own hand-written guards, and it imports nothing. It lives under `src/` because the client reaches it through the `@shared` alias, which resolves to `src/` in all three places architecture principle 7 requires them to agree: `web/tsconfig.json:13` (`"@shared/*": ["../src/*"]`), `web/vite.config.ts:13` (`resolve: { alias: { '@shared': … } }`), and `vitest.config.ts:73` (the `client` project's matching alias). No alias change is needed. The no-imports rule matters because this is the first shared module the client imports for runtime values that would otherwise carry relative `.js` specifiers into a bundler-resolution project. Every existing runtime-shared module already avoids that: `src/search-matches.ts:1` imports only a type, and `src/app-themes.ts:1` carries a comment requiring it stay import-free for exactly this reason. Follow that rule rather than testing whether the bundler happens to remap `.js` to `.ts`.

## Proposed changes

### 1. Define the v1 contract

Add `src/plugins/api.ts` as the host-owned contract module, with no barrel file anywhere under `src/plugins/`. It exports `TAB_PLUGIN_API_VERSION` as a single integer, the static `TabPluginDeclaration` type, the server activation module shape, the activation result and its optional `dispose`, and the two capability types. It references the wire envelope and the two request types owned by `src/protocol.ts` rather than redeclaring them.

One integer is enough, and pretending otherwise would be dishonest. Only bundled plugins ship, so a plugin and the host are always the same build and version skew cannot occur at runtime. The check's real job is to make a frozen fixture fail loudly the moment the contract breaks. Additive changes (a new optional declaration field, a new capability function, a new lifecycle hook) leave the integer alone because every existing plugin keeps working. Any removal, rename, type tightening, payload-meaning change, or observable ordering change bumps it, and bumping it is by definition a breaking change. `src/plugins/api.ts` states that rule in prose next to the constant.

A declaration carries the plugin id, the plugin's own semver string, the API version it was written against, the payload schema version as a positive integer, the tab label prefix, one map from each claimed file extension to an optional content type, an optional file-navigator edit gesture, an optional contributed command name, and the capability names it requests. A command claim is a case-insensitive first token matched on a word boundary. Declarations are pure data modules with no top-level side effects and no executable predicates, so the host can reject a plugin, route to it, or print it in `plugins` without importing a line of behavior.

One extension-to-content-type map replaces the two separate extension and MIME claim lists an earlier shape would have needed. The opener registry reads its keys, the MIME composition reads the entries that name a type, and a duplicate content-type claim becomes impossible because a duplicate extension is already rejected. The tab title is not declared, because the payload factory returns it per tab and a video tab is titled after its file. The requested capability names are not decorative: the host rejects a declaration naming a capability v1 does not define, which is what stops a plugin drifting ahead of the contract silently.

V1 has exactly one tab-view mechanism. A plugin tab is a live in-memory center action tab that can split and stays mounted while inactive. The host owns the label, dot color, group and group color, insertion position, active index, focus, pane placement, closing, and visibility. The plugin supplies a display title, a stable instance key, a versioned payload, and a body component. Every v1 plugin tab is persistent, because video requires it and a per-plugin mount policy is an optional declaration field that can be added later as an additive change.

The server capability exposes five functions and nothing else: append a line to the originating transcript, open or focus a plugin tab, read the configured external viewer name for this plugin id, hand a file to the OS detached, and report a failure. It never receives `Managers`, the controller, a tab object, the WebSocket, or a general filesystem capability. Video keeps reading file metadata with `node:fs` directly and keeps calling `humanSize` from `src/openers/size.ts` as a documented pure utility, because turning a pure formatter into a host callback would widen the contract for nothing.

The open-or-focus function takes the stable instance key first and a payload factory second. The host checks the key against its open tabs synchronously, and calls the factory only when a new tab is genuinely needed. The factory receives a small tab-resources object whose only member registers a served file. This is deliberate and it fixes a real bug: today `src/openers/video.ts:45` calls `context.registerFile(file)` while building the payload, before `src/tab/openers.ts:32` discovers the video is already open, so reopening an already-open video leaks a second entry into the registry every time. Registering through the factory also means the host knows exactly which references belong to which tab, which is what makes generic cleanup possible.

The client capability exposes four things: build an authenticated resource URL from a served-file ref, send a tab-scoped intent and await its reply, render the host's split action node, and report a client-side failure. The label is bound by the host, so a plugin component cannot target another tab. No plugin receives `JanusClient`, a raw socket, or a private host UI module.

Add two `no-restricted-imports` override blocks to `eslint.config.mjs`, one for `src/plugins/**` and one for `web/src/plugins/**`, banning deep imports into host modules while allowing Node built-ins, external packages, `src/plugins/api.ts`, the client plugin API module, and the plugin's own shared contract. Add a matching rule stopping core and shared modules from statically importing a concrete plugin entry, which is what keeps plugin chunks out of the entry bundle.

`src/plugins/api.ts` documents the four things `ai/guidelines/plugins.md:51` requires of every extension point. Resolution: openers resolve first match on extension, commands resolve first match on the declared first token, and core routes always resolve before plugin routes. Ordering: core openers precede plugin openers and core commands precede plugin commands, and duplicate extension or command claims are rejected at registry-build time so array position never silently decides anything. Async semantics: each handler is awaited under a budget, and separate invocations may overlap exactly as opener calls do today, because v1 adds no host-side work queue. Empty return: a handler that returns nothing completed without opening a tab, which is not an error.

### 2. Build the static catalog and the two lazy loaders

Add `src/plugins/catalog.ts` holding the production declaration list. It statically imports manifest modules only, never behavior. Add `src/plugins/loaders.ts` mapping each declared id to one literal dynamic import of `src/plugins/<id>/activate.js`. Literal imports keep every module visible to Node, TypeScript, Knip, and Vite while executing none of them. Add `web/src/plugins/registry.tsx` pairing each id with one literal dynamic import of `web/src/plugins/<id>/index.tsx`, and creating its `React.lazy` wrapper once at module scope so a state broadcast can never remount a playing video by producing a fresh component type.

Do not add `import.meta.glob`, runtime path construction, filesystem discovery, or a second client-side declaration list. A catalog test pins declaration and loader parity in both directions, so a missing loader is a test failure rather than a runtime surprise. If a loader is somehow absent anyway, the first activation attempt disables that plugin through the ordinary failure path.

### 3. Add the guarded host to Managers

Add `src/plugins/host.ts` with `TabPluginHost`, and register it on `ManagerRegistry` at `src/managers.ts:28` as `plugins`. Construct it in `createManagers` at `src/controller/create-managers.ts:32` before the managers that consume plugin contributions. `src/controller.ts:146` (`shutdown`) already disposes managers in reverse construction order, so consumers release their references before the host disposes each activated plugin, and disposal is idempotent. V1 defines no disposal order between plugins because it supports no plugin dependencies.

The host owns compatibility checking, registration of static contributions, one in-flight activation promise per plugin, activated state, disabled state, timing, guarded calls, intent routing, tab teardown for a disabled plugin, and disposal. Concurrent first requests share one activation promise, so activation runs exactly once. When a timeout wins and the import or activation later resolves anyway, the host ignores the late result and disposes it immediately rather than quietly re-enabling the plugin.

Server activation gets a 1000 ms budget. Each user-initiated server handler or intent gets 5000 ms. On the client, the chunk import and the first mount share one 5000 ms deadline rather than two sequential timers. Build all three with `AbortSignal.timeout` and `Promise.race` from the runtime. The repo has no timeout helper today and does not need one for three call sites, so do not hand-roll a timer wrapper or add a dependency. None of this sits on a per-keystroke, transcript-chunk, or `emitState` path, so no handler multiplies against a high call count. The host records each plugin's actual activation duration and final state, and exposes them through one read-only status lookup that the `plugins` command and the tests both use. There is no plural listing API beyond what that command needs.

Split the host across focused modules so each file stays under 200 lines: `src/plugins/host.ts` for state and the public methods, `src/plugins/activate.ts` for the compatibility check and the guarded activation with its timeout and late-resolution disposal, `src/plugins/guard.ts` for the single call wrapper every host-to-plugin call passes through, and `src/plugins/context.ts` for building the per-invocation server capability bound to an originating tab label and command text.

The tab payload does carry a schema version, because it is broadcast and revalidated on every render.

Giving client failures their own method avoids reserving a magic name prefix inside the intent namespace, and it means the intent validator never needs to know host-reserved names exist. Both methods pass through the existing token, Host, and Origin guards and the existing RPC reply path. No plugin opens a socket or registers a route.

Malformed client input on either method returns an ordinary RPC validation error and does not disable anything. Only a throw, a rejection, a timeout, or an invalid result from plugin code crosses the failure boundary.

## Out of scope

- Third-party, user-installed, package-discovered, or filesystem-discovered plugins. Only bundled plugins listed in the catalog load.
- Plugin installation, update, enable/disable, permission, or configuration UI. The `plugins` command reads state and changes nothing.
- Hot reload, or re-enabling a disabled plugin before a restart.
- Sandboxing or process isolation. Bundled plugins run at host trust. Narrow capabilities contain mistakes and are not presented as a security boundary.
- Extension points other than tab views and the opener or command triggers that create them. No pipeline hooks, notification hooks, transport, themes, or menus.
- Migrating image, Markdown, editor, page, file navigator, notifications, schedules, monitor, harness, SSH, agent, or shell tabs.
- A per-plugin mount policy. Every v1 plugin tab is persistent.
- Generic per-plugin configuration. The video plugin keeps only the existing `externalViewers.video` setting.
- Persisting or restoring plugin tabs across `--relaunch` or in profiles.
- Any change to video playback, capture naming, external-player behavior, native controls, split support, or background playback.
- Plugin-local CSS conventions. Video keeps its rules in the single existing stylesheet.
