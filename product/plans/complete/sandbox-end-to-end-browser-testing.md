# Sandbox end-to-end browser testing

**Complexity: 7/10** — the feature itself is plumbing, but it now ships its own containment: a websocket guard between the agent and the browser, a second Seatbelt profile for the browser process, and a fresh per-tab workspace directory for it to live in. On top of that sit a `REMOTE_PROTOCOL_VERSION` bump carrying two frame changes, three launch surfaces including `web/src/`, and the profile save/load round trip. Pre-computing the endpoint keeps the async gating out (decision 5). The one genuinely unknown piece is which Seatbelt operations Chromium needs before it will start under a profile, which is an open question with a named fallback rather than a guess.

## Summary

An AI working inside a sandboxed `harness` workspace cannot launch a browser, so it cannot see what a user would see. That is not a missing feature, it is the sandbox working as designed. Playwright keeps its Chromium under `~/Library/Caches/ms-playwright/`, and the Seatbelt profile denies reads of `$HOME` contents with no carve-in for that path (`src/sandbox/profile.ts:129`, `src/sandbox/paths.ts:73-78`). A sandboxed agent that calls `chromium.launch()` gets a permission failure, so every UI change it makes has to be checked against React internals or a jsdom tree instead of a rendered page.

`harness <name> -b`/`--browser` closes that gap. Janissary starts a headless Chromium as a separate process on whichever host the harness runs on, using Playwright's own `chromium.launchServer()`, and hands the sandboxed harness process two environment variables: `JANISSARY_BROWSER_WS_ENDPOINT`, the websocket endpoint to connect to, and `JANISSARY_PLAYWRIGHT`, the path to janissary's own Playwright client, so the versions match by construction and a project that does not depend on Playwright can still drive the browser. The AI writes its own Playwright script, calls `chromium.connect(endpoint)`, and drives a real browser against a real page.

What it points that browser at is the AI's own server. The AI starts the workspace clone's build inside the sandbox, reads that server's URL and token from its own output, and navigates there. Janissary injects no app URL and no session token into the sandbox, so the agent never touches the janissary window the user is working in, and it tests the code it just changed rather than the code the user is running.

Handing a sandboxed agent a browser endpoint is a way out of the sandbox unless something stops it. Playwright's own documentation says any process holding the endpoint "can take control of the OS user", and the concrete move is `page.goto('file:///Users/…/.ssh/id_rsa')` followed by `page.content()`. So the browser is contained twice. The endpoint the agent receives belongs to a janissary guard process that filters the Playwright protocol and refuses `file:` URLs, and the browser behind it runs Seatbelt-confined in a fresh empty workspace directory of its own, where a `file://` read that got past the guard finds nothing worth having.

This ships connection plumbing, that containment, and a guidelines document. There is no new test-running command and no pass/fail reporting. A new `ai/guidelines/sandbox-e2e-browser.md` teaches any sandboxed AI how to use the two variables.

## Design decisions

1. **Playwright's own `launchServer()` provides the browser.** No browserless, no Docker, no new dependency. `playwright` is already in `package.json:127` and already drives `src/browser/`, and `launchServer()` starts a Chromium process and returns a websocket endpoint for another process to `connect()` against. An earlier revision of this plan named the browserless product; that revision's open question is settled here (the `browserless` npm package is a Puppeteer client SDK, not a spawnable server, and the real self-hosted product is Docker-only).

2. **The AI serves its own build and points the browser at that.** Janissary hands over the browser and nothing else. The live janissary instance's URL and session token (`src/index.ts:159`) are deliberately never injected: driving the user's own window would create, focus, and close real tabs in the session they are working in, and it would put a live session token in a sandboxed agent's environment for no gain, since the clone renders the same UI. The connected browser runs on the same host as the AI's server in both the local and the remote case, so a `127.0.0.1` URL resolves correctly either way.

3. **Janissary hands over its own Playwright client, not the project's.** `JANISSARY_PLAYWRIGHT` names the resolved entry path of the `playwright` package the janissary server is running, and the harness's Seatbelt profile gains a read carve-in for that package directory and for `playwright-core` beside it. Playwright's client and server must be the same version to connect, and a fresh workspace clone has no `node_modules` until the AI installs them, so leaving the client to the project would mean the feature works only for projects that happen to depend on the same Playwright release janissary does.

4. **Both layers of containment are enforced, not documented.** Blocking `file:` at the protocol and confining the browser process are independent, and neither alone is enough. The guard can be worked around (redirects and any frame it fails to parse the way the browser will), and the sandbox is macOS-only. Together, the direct read path is refused at the wire and anything that gets past it lands in a process that can read almost nothing. `product/specs/sandbox.md` and the user docs still describe what remains, because on a host without Seatbelt the guard is the only layer.

5. **The endpoint is computed before the browser starts, so nothing waits on it.** Janissary allocates two ports, mints an unguessable `wsPath` with `makeToken()` (`src/security.ts:5-7`), and returns the guard's endpoint string synchronously. An earlier revision of this decision said the two ports were probed by binding throwaway `node:net` servers; they are not, and cannot be. Node defers a `listen()` bind behind a host lookup and leaves `address()` null until it resolves, so a probe means an `await` and the endpoint would no longer be synchronous. What is allocated is a reservation this process honours (`src/browser/e2e-ports.ts`): a port handed out is not handed out again until it is released, so a launch's two ports are never equal and two concurrent launches never share one. A port taken by another process on the host between being chosen and being bound stays a race — see below. The PTY spawn is never gated on Chromium starting, which keeps this feature out of the codebase's async provisioning machinery: no placeholder tab for a flagless launch, no promise that must never reject, no cancellable placeholder entry on the remote side. Two honest costs. A script that connects within the first fraction of a second may need one retry, which the guidelines document names. And a launch that fails outright is reported after the fact rather than as a notice on the tab's first frame, since the variable is already set by then.

6. **The agent gets the guard's endpoint; the browser's own endpoint never leaves the janissary process.** The guard listens on the published port and path, proxies to the browser server on a second loopback port under a second unguessable path, and inspects every frame in both directions. This is the shape browserless arrived at for the same problem: their `allowFileProtocol` defaults to `false`, and their Playwright path proxies the websocket, parses each frame as JSON rather than substring-matching it, and tears the session down on a match. Janissary follows that design with one deliberate difference, in decision 7.

7. **The guard fails closed, including on frames it cannot parse.** browserless exempts binary frames from inspection so a benign blob does not tear down a session; janissary does not, because a client that can choose its frame encoding could otherwise choose the one that is not read. Every frame is decoded as UTF-8 and parsed as JSON, and a frame that will not parse ends the session the same way a blocked URL does. Client-to-browser frames are rejected when any string value in the message is a `file:` URL. Browser-to-client frames are checked only in the fields that carry a navigation result (`url`, `documentURL`, and the frame tree's own `url`), not in every string, so a page whose text happens to contain `file://` does not kill the session. On a match the guard closes the client socket with code 1008 and destroys the upstream connection, ending the whole session rather than failing one call, so there is no partial read to salvage.

8. **The browser process runs Seatbelt-confined in a fresh workspace directory of its own.** The directory is `workspacePath('<label>.browser')` with its `.tmp` sibling (`src/workspace/index.ts:25,94`), created empty, never a git clone, and removed with `removeWorkspace` when the browser stops. It holds everything Chromium writes — `downloadsPath` points at it directly, and Chromium's profile lands in its temp sibling because `TMPDIR` points there — and it is what the profile's `WORKSPACE` parameter points at. The user data directory is not passed as an argument: Playwright owns that flag and rejects an invocation supplying its own. A separate directory rather than the harness tab's own workspace: the browser has no reason to read the code under test, and giving it none means a `file://` read that gets past the guard sees an empty scratch directory. It also means `-b` works with `--no-workspace`, where the tab has no workspace to share.

9. **The browser gets its own minimal Seatbelt profile, not the harness one.** Reusing `SANDBOX_PROFILE` would be actively wrong: its read carve-ins include `Library/Keychains`, `.claude`, `.codex`, and opencode's state directory (`src/sandbox/paths.ts:12-40,73-78`), which is close to an inventory of what an escape would want. A browser needs none of it. `src/sandbox/browser-profile.ts` keeps the same skeleton the existing profile uses (deny by default, broad read allow, `$HOME` contents denied, then carve-ins) with exactly three carve-ins: the Chromium app bundle, the browser workspace, and its temp sibling.

10. **Confining the browser costs nothing that was not already given up.** Chromium refuses to initialize its own Seatbelt sandbox inside an outer one, because macOS does not support nested `sandbox-exec` initialization, so a confined Chromium must run with its internal sandbox off. That sounds like a trade and is not: Playwright's `chromiumSandbox` option "Defaults to `false`" (`node_modules/playwright-core/types/types.d.ts:16074`), and `launchTabBrowser` does not set it, so every Chromium janissary launches today already runs with its own sandbox disabled and nothing else around it. Adding the outer profile is a strict improvement over the status quo.

11. **The browser is launched by a child `janus e2e-browser` process, not in-process.** `launchServer()` runs inside whatever process calls it, and the janissary server must not be confined, so the call moves into a child that `sandboxSpawn` wraps. `janus e2e-browser` is a positional subcommand beside the existing `stop`, `init`, and `remote-serve` (`src/cli-args.ts:57-61`), taking the port, `wsPath`, and directory to use. Everything about the confinement then comes from the existing machinery rather than a hand-rolled `sandbox-exec` wrapper, and the child's own Chromium helper processes inherit the profile the way any child does.

12. **Headless, from Playwright's bundled binary, with no `channel`.** The `browser` command passes `channel: 'chromium'` for stealth (`src/browser/index.ts:69-77`), which does not matter when testing your own app and does matter here for a different reason: the profile has to carve in the exact app bundle, so janissary needs the path it is launching, which `chromium.executablePath()` gives it and a channel selection does not. On this machine that resolves to `~/Library/Caches/ms-playwright/chromium-1228/chrome-mac-arm64/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing`, which is also the concrete proof of decision 2's premise: that path is under `$HOME` and carved in nowhere. No `--headed` counterpart is added, since the AI never needs to look at a window.

13. **Failures and crashes go to the notifications tab, never the transcript.** A failed launch, a browser that exits, and a guard that dies are one event to the user and one notification kind. A remote browser reports the same way through a new `browser-exited` frame. No supervisor and no restart: once it is gone, `connect()` fails with a plain connection error, which the guidelines document names as the likely cause. `notify` returns immediately when the notifications tab is closed (`src/notifications.ts:126`), so a user with that tab closed sees nothing, exactly as they see nothing today for a failed recording. That is this feed's existing contract and this feature does not carve an exception into it.

14. **Flag `-b`/`--browser`; variables `JANISSARY_BROWSER_WS_ENDPOINT` and `JANISSARY_PLAYWRIGHT`.** The `JANISSARY_*` prefix follows `JANISSARY_NODE` (`src/sandbox/index.ts:275`). The `wsPath` in the endpoint is the only credential either end needs.

15. **The browser belongs to the tab's `HarnessRuntime`.** It already owns every per-PTY resource and is disposed from one place on PTY exit, tab close, and app shutdown (`src/harness/manager.ts:34-38`, `:41-45`). Closing a `-b` tab kills its PTY, which fires the exit event, which disposes the runtime, which stops the guard, kills the child, and removes the browser workspace. No new label-keyed map and no new line in `src/tab/cleanup.ts`. One browser per `-b` tab, never shared or pooled.

16. **All three launch surfaces, every harness.** The `harness` command, the New harness dialog, and profile entries. The dialog builds a command string rather than its own launch payload (`web/src/harness/harness-launch-command.ts`), so a checkbox there is one field and one appended token. A profile entry carries `browser?: boolean`, round-tripped through a new `tab.browser` field the way `offline` and `autoApprove` already are (`src/profile/save-entries.ts:90-91`). Unlike `-y`, which is rejected for opencode (`src/harness/command-parse.ts:72-74`), nothing here is harness-specific, so no rejection branch is added.

17. **Off macOS, and with `sandboxWorkspaces` disabled, the guard is the only layer.** `sandboxSpawn` returns the command unchanged when Seatbelt is unavailable or switched off (`src/sandbox/index.ts:260-262`), so the browser starts unconfined on those hosts and `-b` keeps working. The browser workspace is still created and still holds the downloads and, through `TMPDIR`, Chromium's own profile, so writes stay tidy even unconfined. This asymmetry is documented rather than papered over; it is the same shape as the existing isolation notice for a workspaced tab on a non-macOS host.

18. **`-b` with `--offline` is left contradictory on purpose.** `--offline` swaps in the network-denying profile for the harness (`src/sandbox/profile.ts:204`), which also blocks it from reaching the guard. No exemption is carved in, and `parseHarnessFlags` does not reject the pair. Both flags apply, the variables are set, and the connection has no route. The guidelines document names it, so a `connect()` timeout under those two flags reads as expected rather than as a bug.

19. **A remote launch forwards a boolean, not an endpoint.** The `spawn` client frame gains `browser?: boolean`, following the shape `offline` and `harness` already use: a fact the remote acts on rather than a value computed here and shipped over. The remote starts its own guard, its own confined browser, and its own workspace directory, exactly as `harnessEnv`'s doc comment states the general rule (`src/harness/scratch-dir.ts:13-15`). With the `browser-exited` frame from decision 13 that is two frame changes, so `REMOTE_PROTOCOL_VERSION` moves from 10 to 11 and mismatched ends refuse each other at the handshake.

## Proposed changes

Land them in the order below. §1 through §4 are self-contained and leave the tree green on their own; §2 and §3 are worth landing and exercising before anything wires them into a harness tab, since §3 carries the plan's one real unknown. §7 must land as one change: `REMOTE_PROTOCOL_VERSION`, both frame changes, and every consumer, since a half-applied protocol change compiles on one end and fails the handshake on the other. §8 through §10 depend only on §6's `SpawnTabOptions` field. This plan depends on no other plan landing first.

### 1. New module `src/browser/e2e-server.ts` — lifecycle orchestration

Lives in `src/browser/` because it is browser machinery and because both the local manager and the remote server import it. It holds no label-keyed state; the caller owns what it returns.

`startE2EBrowserServer()` returns `{ env, handle }` synchronously enough for the caller to spawn a PTY immediately. It allocates two reserved ports (decision 5); mints two `wsPath` values with `makeToken()`, one published and one internal; creates the browser workspace directory and its temp sibling; spawns the `janus e2e-browser` child through `sandboxSpawn` (§3); and starts the guard (§2) in front of it. `env` carries `JANISSARY_BROWSER_WS_ENDPOINT`, pointing at the guard, and `JANISSARY_PLAYWRIGHT`. `handle` exposes `close()`, idempotent and safe before the child has finished starting, which stops the guard, kills the child, and removes the workspace directory with `removeWorkspace`. It takes an `onGone` callback invoked once for a child that exits unexpectedly, a child that never starts, or a guard that fails to listen, and never after `close()`.

The second export is the Playwright-location resolver, memoized on first use since the answer cannot change while the process runs: the entry path `JANISSARY_PLAYWRIGHT` carries, the `playwright` and `playwright-core` package directories the harness carve-in needs (§4), and the Chromium app bundle directory the browser profile needs (§4), the last found by walking up from `chromium.executablePath()` to the nearest `.app` ancestor and falling back to the executable's own directory. It resolves packages through `node:module`'s `createRequire` rather than walking `node_modules` by hand.

Each port has a small window in which another process on the host could take it between it being chosen and being bound for real. Losing it is not silent: the child or the guard fails to listen, everything that launch acquired is released at that moment — the other listener, the child, the scratch directory, and both ports — `onGone` fires, and the user gets the notification from §9.

### 2. New module `src/browser/e2e-guard.ts` — the protocol filter

A `ws` server on the published port and path that opens one upstream `ws` connection to the browser server per client and relays frames both ways. It is the only thing the sandboxed agent can reach; the browser server's own port and path are never written into any environment.

Every frame, text or binary, is decoded as UTF-8 and parsed as JSON before relay. A frame that will not parse ends the session, as does a client-to-browser frame in which any string value is a `file:` URL, and a browser-to-client frame whose navigation-result fields (`url`, `documentURL`, and the frame tree's `url`) hold one. Ending the session means closing the client socket with code 1008 and a short reason, then destroying the upstream connection. Matching is done on parsed values rather than a raw substring scan, because a substring fast path misses JSON Unicode escapes; browserless learned that one and left the comment.

Two properties of the surrounding platform make this narrower than it first looks and are worth stating so a reader does not over-trust it. Chromium already refuses navigation to `file://` from any non-`file://` page, and a `file://` page cannot read another one without `--allow-file-access-from-files`, so web content cannot pivot to the filesystem on its own; the realistic vector is the automation client asking directly, which is a frame the guard sees. What the guard does not see is a server-initiated redirect that lands on a `file:` URL. That gap is what §3 exists to make harmless, and neither layer is offered as sufficient alone.

The guard binds `127.0.0.1` only. It refuses upgrades on any path other than the published one, so the internal path is not reachable by guessing.

### 3. New module `src/browser/e2e-child.ts` and `src/cli-args.ts` — the confined browser

`janus e2e-browser --port <n> --dir <path>`, with the ws path supplied in the environment as `JANISSARY_E2E_WS_PATH`, calls `chromium.launchServer()` with that `port` and `wsPath`, `headless: true`, `executablePath` from the resolver in §1, and `downloadsPath` inside `--dir`. As corrected for the port allocation in §1 and design decision 5: the path is not a flag because a macOS argument vector is readable through `ps` by any user on the machine, and the user data directory is not passed as an argument at all — Playwright owns that flag and rejects an invocation supplying its own, so Chromium's profile lands in `--dir`'s temp sibling by way of `TMPDIR` instead. It writes nothing to stdout that matters and exits when killed. `cli-args.ts` gains it as a positional subcommand beside `remote-serve`, and `main.ts` routes it.

`startE2EBrowserServer` spawns it through `sandboxSpawn` with `workspaceDir` set to the browser workspace, using the browser profile from §4 rather than the harness one, and `child_process.spawn` on the returned `{ command, args, env }`. Killing the child kills its Chromium, since Chromium's helper processes are its children.

This is where the plan's uncertainty sits. Chromium under an outer Seatbelt profile needs operations the harness profile has never had to allow, POSIX shared memory being the near-certain one and IOKit access a likely one even headless. The profile in §4 starts from the harness profile's skeleton and is expected to need a few additions found by reading the sandbox denial log while bringing it up. See Open questions for the fallback if it cannot be made to start.

### 4. `src/sandbox/` — the browser profile and the Playwright carve-in

New `src/sandbox/browser-profile.ts`, built the same way `profile.ts` is: a static string with `-D` parameters, no interpolation, using `clausesFor`/`dualParams` from `paths.ts`. Deny by default; allow `file-read*` broadly, then deny `$HOME` contents, then carve in exactly the Chromium app bundle (literal and realpath), the browser workspace, and its temp sibling. Allow writes only in those last two plus `DARWIN_USER_CACHE_DIR` and `/dev/null`. Allow `network*`, `mach-lookup`, `sysctl-read`, `process-fork`, `process-exec`, and `signal (target children)`, matching the harness profile's reasoning for each. It carries none of the harness carve-ins for `Library/Keychains`, `.claude`, `.codex`, or opencode state, which is the entire point (decision 9).

`sandboxSpawn` gains a way to select this profile instead of the harness one for a given spawn. That is one option on `SandboxOptions` and one branch where `options.offline ? … : …` already picks between two profiles (`src/sandbox/index.ts:278`), not a new spawn path.

Separately, the harness profile gains the Playwright package carve-in from decision 3: a `PLAYWRIGHT_DIR` dual param pair in `paths.ts` beside `SERVER_NODE_DIR`, two `dParams` entries in `index.ts` beside `:288-289`, and the params added to the read-allow rule at `profile.ts:139-148`. `playwright-core` is resolved and carved in separately from `playwright`, because it is `playwright`'s only runtime dependency and in a hoisted layout it sits as a sibling rather than nested, so carving in `playwright` alone leaves every internal require denied. This carve-in is unconditional rather than gated on `-b`: gating it would mean threading a field through `SandboxOptions`, `spawnPty`, `PseudoterminalManager.spawn`, and the remote's spawn path plus a placeholder for the unbound case, to withhold read access to two directories of janissary's own dependency tree that hold no user data.

### 5. `src/harness/command-parse.ts` — flag parsing

`HarnessParsed`'s launch member gains `browser: boolean`. `parseHarnessFlags` recognizes `-b`/`--browser` with the same single `tokens.some(...)` line `--offline` uses at `:66`, which adds no branching to a function whose own comment flags it as near the complexity limit. No harness-name restriction and no rejection branch. `parseHarnessCommand`'s doc comment gains a sentence in its existing per-flag style.

### 6. `src/harness/` — ownership and injection

`SpawnTabOptions` gains `browser: boolean`. `run` passes `parsed.browser` into `open`, whose positional list grows from 9 to 10 the way `remote` was added; existing parameters are not reordered, since that struct's doc comment names transposition as the risk this shape carries. `spawnTab` records it as `tab.browser` beside the existing `tab.offline`/`tab.autoApprove` assignments, so `profile save` can read it back (§8).

The browser start and the environment merge do not go inline into `finishSpawn`. `src/harness/manager.ts` is at roughly 200 lines under ESLint's `max-lines` counting (`{ max: 200, skipBlankLines: true, skipComments: true }`, `eslint.config.mjs:86`), so it has no room, and the answer per the code guidelines is extraction. The extraction needs no new module: `src/harness/scratch-dir.ts` is 19 lines and its `harnessEnv` doc comment already describes this job, "the environment overrides a harness binary is spawned with, on the machine it runs on" (`:13-15`). It gains a sibling export taking the harness name, cwd, and the `browser` boolean and returning `{ env, handle }`, which calls `harnessEnv(name, cwd)` and, when `browser` is set, `startE2EBrowserServer()`, merging the two. It must tolerate `harnessEnv` returning `undefined`, which it does for every harness except claude (`:17`). With no browser requested it returns `harnessEnv`'s result and no handle, so the non-`-b` path is byte-for-byte what it is today.

`finishSpawn` calls that sibling once, passes `env` where it passes `harnessEnv(name, cwd)` today (`:216`), and hands `handle` to `harnessRuntime(...)`. The remote's spawn path calls the same function (§7), which is what makes the "a remote launch builds its own copy on the far side" rule hold for the browser variables too. `HarnessRuntime` takes the handle as another optional constructor member and closes it in `dispose()` alongside the reader, recorder, and tailer; `harnessRuntime`'s options type carries it through. Nothing else changes, since the existing `pty`/`exit` subscription already disposes the runtime.

For a remote tab, `finishSpawn` starts nothing locally. It sets `browser` on the `registerRemotePty` options instead (§7).

### 7. Remote support

`src/remote/protocol.ts`: `REMOTE_PROTOCOL_VERSION` moves from 10 to 11 with a paragraph in the version-history comment in the established style. `ClientFrame`'s `spawn` variant gains `browser?: boolean`, and the frame validation that type-checks `offline` checks it the same way. `ServerFrame` gains `{ type: 'browser-exited'; id: string }` with its entry in `SERVER_FRAME_TYPES`.

`src/remote/pty-session.ts`: `RemotePtyOptions` gains `browser?: boolean`, destructured and included in the `spawn` frame literal beside `harness` and `offline`.

`src/remote/channel.ts`: one `browser-exited` case added to the arm that already forwards `workspace-ready`, `workspace-failed`, and `transcript` to `this.handlers.onFrame` (`:184-186`). `SessionListener` is not extended and no bus variant is added: `RemoteManager`'s `onFrame` closure (`src/remote/manager.ts:87`) has `this.managers` and already imports and calls `notify` (`:9`, `:200`). It resolves which tab to name from the frame's session id, `tabs.find((t) => t.harness?.ptyId === frame.id)`, not from the channel's label, because joined tabs share a channel (`attach`, `entry.labels`) and the channel label would name the wrong one. A frame for an already-closed tab is dropped.

`src/harness/manager.ts:215`: the `registerRemotePty` options gain `browser: options.browser`.

`src/remote/serve-processes.ts`: when `frame.browser` is set, `spawnPty` builds its environment through the same `scratch-dir.ts` sibling the local side uses (§6), which starts the guard and the confined child on the remote host through the same modules. The returned `Entry`'s `kill` closes the browser as well as the session, and `finish`, the exit path, closes it too, so a harness that exits on its own leaves nothing running. `onGone` sends the `browser-exited` frame. Because the endpoint needs no await (decision 5), `spawn`'s existing synchronous insert into `this.entries` is untouched and there is no kill-before-spawn race to guard.

### 8. Profiles

`ProfileHarnessEntry` gains `browser?: boolean` with a doc comment in the style of its `offline` neighbour. `ProfileHarnessTabFile` needs no edit: it is derived as `Omit<ProfileHarnessEntry, keyof ProfileTabRuntime> & ProfileTabPresentation` (`src/profile/types.ts:107`), so the on-disk shape picks the field up. `harnessProblems` adds a `checkField(value, 'browser', 'boolean', loc)` line beside `offline`'s. `openFromProfile` passes `entry.browser ?? false` into `spawnTab`. `writeHarnessEntry` writes `browser: tab.browser` beside `offline` and `autoApprove`, backed by a new optional `browser` field on `Tab` documented next to `offline`. No validation branch rejects it for any harness, unlike `autoApprove`'s check at `src/profile/entry-openers.ts:54-56`.

### 9. Notifications

One new `NotificationEventType`, `e2e-browser-gone`, listed in `shouldNotify`'s bypass group for the same reason the recording failures are there, and given a line in `notificationText`. Two callers, both already existing: `HarnessManager` passes an `onGone` callback down for a local browser, and `RemoteManager`'s `onFrame` raises it for a remote one (§7).

### 10. Launch dialog

`HarnessLaunchFields` gains `browser: boolean`, defaulting false in `initialFields`. `buildHarnessLaunchCommand` appends `-b` when set, in the positive-flag style `--offline` uses. `HarnessLaunchDialog` gains a checkbox labelled "E2E browser (-b)" after the Offline one. ## Out of scope

- Any built-in E2E test runner, assertion helper, or pass/fail reporting in the transcript. The AI writes and runs its own script.
- Extending the `browser` command to target this browser, or any new interactive command for driving it. The two variables are the entire surface.
- Mediating every browser call through a janissary RPC so URLs are validated server-side. It is the only design with no bypass class at all, and it deletes the property this feature exists for, which is the AI writing its own Playwright script.
- Injecting the running janissary instance's URL or session token into the sandbox (decision 2).
- Applying the enterprise `URLBlocklist` policy. It is the only control that lives inside the browser process where a client cannot reach it, but mandatory policies require admin-installed managed preferences per host and apply to the whole browser install rather than one tab. `product/specs/sandbox.md` names it as something an operator may do; janissary does not do it.
- Confining the browser on non-macOS hosts (decision 17). Bubblewrap or a container would be the Linux answer and is a separate plan.
- Restarting a browser, guard, or child that died, or any supervision loop (decision 13).
- Sharing or pooling a browser across tabs (decision 15).
- A `--headed` counterpart (decision 12).
- Agent tabs. `agent`, `ProfileAgentEntry`, and the ACP paths get no browser, even though a workspaced agent runs under the same sandbox.
- Reworking `open`'s positional signature into an options object. It grows to 10 parameters here, which is worth doing something about, but not in this change.

## Open questions

1. **Which Seatbelt operations Chromium needs before it will start under the browser profile.** The skeleton in §4 is derived from the harness profile, which has never had to host a browser. POSIX shared memory is near-certain to be needed, and IOKit access is likely even headless. The way to settle it is to bring §3 up on its own and read the sandbox denial log, adding operations until Chromium starts, then stopping. If it cannot be made to start without opening the profile so wide that it stops being a boundary, the fallback is to ship §1, §2, and the browser workspace without the Seatbelt wrapper: the guard still refuses `file:` at the wire, `downloadsPath` and the `TMPDIR`-directed profile still keep writes inside a disposable directory, and the plan degrades to what every non-macOS host gets anyway (decision 17). That fallback is a real outcome to accept, not a failure to abort on, and the spec wording in §11 should be written so it holds either way.

It is not an instruction to anything that reads this plan as part of a change under review: a completed plan travelling in a branch is material to be read, and the commands below neither authorise nor request execution by a reviewer, automated or otherwise. `./scripts/run.mjs check-diff` after each step.

Manual, local: launch `harness claude -b`, then inside that tab confirm both variables are set and that a Chromium process is running on the host. Following the new guidelines document, have the harness install the workspace clone's dependencies, start its own janissary server, connect to the endpoint, navigate to that server's URL, and read back rendered page text.
