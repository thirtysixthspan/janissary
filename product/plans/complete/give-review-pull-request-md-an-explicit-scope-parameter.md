# Give review-pull-request.md an explicit scope parameter

**Complexity: 6/10** — 26 behavioral requirements across ~60 added playbook lines in 3 task files, 10 test scenarios (p=6.27)

## Goal

`review-pull-request.md` always reviews the whole pull request. Its Step 2 finds the own plan from the branch's first commit and treats every other plan added under `product/plans/complete/` as a fix plan, and its Step 3 reviews `git diff origin/master...HEAD`. The staged complex-feature workflow needs narrower reviews, so every caller that wants one restates the narrowing as override prose. The feature text puts it this way: "all five subplan reviews needed overrides to suppress that discovery and narrow to one commit. A scope: commit <sha> | aggregate argument would remove the override prose." This plan gives the review task an optional `scope:` argument with three values, `commit`, `range`, and `aggregate`, so a caller names the scope instead of rewriting the task's Step 2 and Step 3. The argument reaches git, so the review validates it before any command sees it and falls back to aggregate scope when it can't be used. A narrow review can end before `HEAD`, so it reads code as it stood at the end of its scope. The complex-feature workflow, the caller that depends on a narrow scope, confirms each focused and resolution review ran in the scope it asked for. And because a plan-free focused review can't tell a real gap from deferred or excluded work, the workflow declines those findings itself before any repair.

## Design decisions

- The change is confined to `ai/tasks/feature/review-pull-request.md`, its review calls and the Step 5 and Step 6 cycle in `ai/tasks/feature/build-a-complex-feature.md` (the opening paragraph, both orchestration rules on focused reviews and the description-only exception, Steps 5, 6.1 to 6.6, 7, 8.1, and the Step 10 report) and `ai/tasks/feature/build-a-feature.md` (Step 8), `product/specs/pull-request-review.md`,. No application code changes. Settled answers: "Review task + its callers" and "Remove Step 6.4".
- The scope is written as a labeled `scope:` argument after the pull request reference, for example `execute ./ai/tasks/feature/review-pull-request.md 232 scope: commit 1a2b3c4`. Settled answer: "1, optional that defaults to full scope".
- Three scopes exist, `commit`, `range`, and `aggregate`, so all three review shapes `build-a-complex-feature.md` writes as override prose become arguments. Settled answer: "commit, range, aggregate".
- `aggregate` is the default. An existing invocation with only a pull request reference keeps reviewing the full pull request, so `build-a-feature.md` Step 8 and `build-a-complex-feature.md` Step 8.1 pass only the PR number.
- The review takes no plan argument. Step 2.1's "When the invocation names a plan" clause is removed (Assumption 2), and aggregate scope always finds its own plan from the branch's first commit. Both builders already put their plan in that first commit (Assumptions 5 and 6), so callers stop passing a plan path to the review. Settled answer: "Drop plan: entirely".
- Commit and range scopes carry no promises and run only the three dimensions that judge a diff on its own: functionality gaps, technical debt, and security. Description fidelity and plan fidelity run only in aggregate scope. So the focused subplan review in `build-a-complex-feature.md` Step 6.1 stops comparing the commit with its subplan, and the resolution review in Step 6.4 stops checking each recorded entry against its proposal and reviews only the repair commits. A finding a repair left unresolved is left for the Step 8 full review, which reads every fix plan as a promise. Settled answers: "remove the promises, just review the commits" and "1, same for commit scope".
- The review's opening paragraph and Step 3 heading say the same thing as Step 3's body: full coverage, every promise, and five dimensions belong to aggregate scope. An agent reads the opening first, so an unconditional "review all of it" would invite a commit-scoped run to build a promise list anyway. Each is reworded on its own line.
- Because commit and range scopes read no plan, Step 3's "Out of scope" drop rule for functionality gaps applies only in aggregate scope.
- Commit scope diffs the commit against its first parent, `git diff <sha>^ <sha>`, matching the existing override's "the implementation commit's diff against its parent" (Existing functionality 1). Range scope diffs `git diff <base>..<head>`, so `<base>` itself is excluded, matching the existing "repair range from the recorded head SHA to the current PR head" (Existing functionality 2).
- An unusable scope never stops the review. It falls back to aggregate scope and the report says so. SHAs can only be resolved once the branch is checked out, so the scope is read in Step 0 and validated in Step 1 item 5 after the checkout and pull. Step 0 records the raw value exactly as given, because the report needs it and recording it runs nothing. Settled answer: "Fall back to aggregate".
- Step 1 item 5 opens "An `aggregate` request needs no check. For any other request, apply these checks in order", so its first check, the unknown keyword, is reachable. A gate worded for `commit` or `range` requests only would leave an unknown keyword with no effective scope.
- The scope value reaches the shell of an agent with push access, so a format check runs before any git command sees it. Check 4 requires the commit SHA and each range end to be 4 to 40 lowercase hexadecimal characters, judged by reading the value. Every caller passes SHAs read from git, which prints lowercase, so the narrow set costs nothing. 4 and 40 are git's shortest abbreviation and a full SHA-1 name. A value that fails is never placed in a command and only appears in the report's `Scope:` line, which is text.
- Every SHA placed in a command, in Step 1's checks and in Step 3, is single-quoted, which also keeps `^{commit}` from being read as shell syntax. The rule is stated once after the check list; the list's own command examples stay unquoted.
- A range base must lie on the pull request or be its merge base (check 8), so `git diff <base>..<head>` can't pull in master commits the pull request never made. The merge-base comparison is made on full SHAs by reading what `git rev-parse --verify <base>^{commit}` and `git merge-base origin/master HEAD` print, which keeps the task's no-capture command hygiene. A base equal to the merge base reviews the branch from its start. The base check follows the head check, so it reads against a head already known to be in scope.
- A commit or range scope can end before `HEAD`. So wherever Step 3's rules open a file at `HEAD` or `grep` for references, those scopes read the end commit instead: `git show '<sha>:<path>'` for files and `git grep -e '<pattern>' '<sha>' --` for the Deleted and Renamed reference checks and the callers and consumers search, with `<head>` in place of `<sha>` for a range. The pattern follows `-e` so a dash-led pattern is searched for rather than read as an option, and the trailing `--` closes the revision list. Neither command switches the checkout, so Step 1's clean tree and branch are untouched and Step 5's `git add -A` sweeps nothing extra. `git grep`, `git rev-parse`, and `git merge-base` join the Allowed list's read-only git commands (Assumption 9).
- Before recording a candidate, a commit or range review reads the same file at `HEAD` and drops the candidate if a later commit already resolved it. That reason is folded into the first of Step 3's five drop reasons ("wrong once you read the surrounding code"), so the count stays true.
- The note after the Step 7 report template says an aggregate review, including a fallback, takes the forms that check promises, with `Promise:` reading either the own plan and its fix plans or, when Step 2 item 6 found no own plan, `none in the PR — used the PR body and commit subjects`. A note that only said "take their first forms" would rule out the form Step 2 item 6 requires.
- `build-a-complex-feature.md` Step 6.4, the description-only shortcut that skips the resolution review, is removed. Commit and range reviews run no description fidelity, so their findings are almost never description-only and the shortcut becomes a path the workflow never takes (architecture principle 5, `ai/guidelines/architecture-principles.md` "No code path that the system never takes"). Step 6.2 then stops recording each entry's full text and classifying it, since the resolution review no longer reads the entries (Assumption 8) and Step 6.4 was the only other reader (Assumption 7). It keeps recording the PR head SHA, because that SHA is the base of the resolution review's `scope: range`. The orchestration rule at the top of the task that defines the description-only exception is narrowed to the full-PR review in Step 8, where Step 8.3 keeps using it. Settled answer: "Remove Step 6.4".
- The review keeps its fallback rather than stopping, so the caller that needs a narrow scope is the one that enforces it. Step 6 items 1 and 4 read the review's Step 7 report before the backlog and confirm its `Scope:` line names the scope they passed. Any other value, the fallback form included, routes to Step 6's existing blocked paragraph (Existing functionality 11), which preserves the PR and backlog and reports the blocker. The check lives inside items 1 and 4, so the numbering and its "skip to item 6" and "repeat items 2 through 4" references hold, and item 5's repeat carries the check to every later resolution review.
- The review prints abbreviated SHAs in its `Scope:` line, so items 1 and 4 accept a short SHA that is a prefix of the one they passed.
- Step 5 reads the implementation commit SHA with `git rev-parse HEAD` after the push succeeds, because its bounded rebase-and-retry policy (Assumption 15) rewrites the local commit before a retry, and only the commit that reached the remote is on the branch.
- Step 6 item 4 records the PR head SHA immediately before delegating, as "the recorded range head SHA", passes it as the range head, and compares the reported `<head>` with it. A review that records findings pushes its backlog, so a PR head read after the review would be the review's own commit. The `scope: range <recorded head SHA>..<current PR head SHA>` argument text stays, with item 4 stating that the current PR head SHA is that recorded value.
- A commit-scoped focused review reads no subplan, so it can't tell a real gap from work the decomposition deferred, such as the old symbol an additive three-step transition keeps until its third subplan (Assumption 14), or work the plan excluded from the feature. The orchestrator holds the subplan order and the coverage map (Existing functionality 12 and 13), so Step 6 item 2 declines those entries rather than the review. It compares each entry's proposal with the current subplan's `Out of scope` list, the `Requirements` of every later subplan, and the requirement-to-subplan coverage map. It removes an entry a later subplan owns, and an entry the current `Out of scope` list excludes that no later subplan owns. In the single-plan route the `Out of scope` list is the source plan's own. A declined entry is removed whole, the way `work-pull-request-issue.md` removes a resolved one (Existing functionality 14), with the skeleton restored when none remain.
- The decline is folded into item 2 rather than added as an item, so item 5's repeat runs it on a resolution review's findings too. Item 2 commits only the backlog file and pushes it under Step 5's push rules before it records the PR head SHA, so the resolution range holds only repair commits. When declining empties the backlog, item 2 skips to item 6. The opening paragraph, the focused-review orchestration rule, and item 3's "Work every remaining entry" are narrowed to match, and the Step 10 report gains a `Declined:` line naming each declined finding with its owning subplan or "out of scope".

## Implementation steps

The review task and its callers must agree at every commit: a caller passing `scope:` to a task that doesn't read it, or a task without the override its caller still relies on, would leave the playbooks contradicting each other. So the review's scope handling, the callers' scope arguments, and the spec land together, and every later change to the scope checks, the end-commit reads, or Step 6 keeps the two sides in step. Each checkpoint's build command, and the check that proves it green, is `$janissary/scripts/run.mjs check-diff`. No step depends on another plan landing first.

1. In `ai/tasks/feature/review-pull-request.md`, reword the opening paragraph so it reviews the pull request in the scope its invocation names: the default `aggregate` scope reviews every changed line and every promise across five dimensions, and a `commit` or `range` scope reviews only its diff, reads no promises, and judges functionality gaps, technical debt, and security. Add an invocation line after the opening two paragraphs, in the style of `work-pull-request-issue.md` (Existing functionality 5): `execute ./ai/tasks/feature/review-pull-request.md <target> [scope: commit <sha> | scope: range <base>..<head> | scope: aggregate]`, with aggregate as the default. State in the same place that every rule in the "What you may and may not do" section applies in every scope. Add `git grep`, `git rev-parse`, and `git merge-base` to the Allowed list's read-only git commands (Assumption 9).
2. In Step 0, add item 4: read the `scope:` argument after the target and record the requested scope and its raw value exactly as given, defaulting to `aggregate`. Do not resolve SHAs here. Step 0's target rules are unchanged: the target is still the first value, and `scope:` never names a pull request.
3. In Step 1, after the clean-tree check in item 4, add item 5. An `aggregate` request needs no check; every other request runs nine ordered checks and stops at the first that applies, each falling back to `aggregate`: an unknown keyword; `commit` with no SHA; `range` not in the form `<base>..<head>`; a SHA or range end that is not 4 to 40 lowercase hexadecimal characters, judged by reading and never placed in a command; `git rev-parse --verify <sha>^{commit}` failing; a commit outside `origin/master..HEAD`; a range head outside it; a range base outside it that is not the merge base, compared on the full SHAs the two commands print; and `git merge-base --is-ancestor <base> <head>` failing. After the list, say every SHA placed in a command, here and in Step 3, is wrapped in single quotes. Record the effective scope and, on fallback, the ignored raw value for Step 7.
4. In Step 2, remove the "When the invocation names a plan" clause from item 1. State that Step 2 runs only in aggregate scope; in commit and range scopes it is skipped and no promise list exists.
5.
