# Visualizations tab and visualization plugin

**Complexity: 8/10** — a first-of-its-kind surface on both sides: a new host domain that fetches a remote or local source, parses it, keeps it current on a timer, and drives a two-stage model interview; a fourth host topic and a fourteen-action union; a hand-written SVG chart renderer with five mark kinds; and a dependency-free PNG and PDF export path. No new dependency and no new protocol RPC — the wire additions are view types on the existing `pluginIntent` path, and the model channel is the ACP pool conversations already owns.

Janissary can show a file someone else made, and it can hold a conversation with a model, but it cannot take a data source and draw something out of it. This plan adds both halves: a host-owned `VisualizationsManager` that fetches a source, hands a sample of it to an ACP model, interviews the user about what to chart, and keeps the resulting chart current; and a bundled tab plugin that renders the index of saved visualizations and each visualization's chart, its questions, its chat, and its exports.

The shape follows conversations exactly, because conversations already solved the two hard problems this feature needs: a model reached without a tab, and a durable per-subject record with its own sandboxed agent workspace. A `visualizations` command opens a singleton index tab ordered by recent activity, one tab per visualization is keyed by that visualization's id, and every mutation travels back to the host as a narrow topic action. Nothing about charts, fetching, or the model leaks into the plugin.

The chart is a specification, not generated code. The model answers with a small declarative spec — a kind, an x column, a y column, an optional series column, a title, optional axis labels — which the client draws as SVG from the table the server already holds. That keeps the risky surface (an LLM writing code that runs) out of the feature, makes the output a value that can be validated against the real columns before it is shown, and makes export a rendering concern rather than a code-generation one.

## Design decisions

**The index and the visualization tabs are two tabs of one bundled plugin.** The index is a singleton under the fixed instance key `visualizations`; each visualization's tab is keyed by its own id, so opening the same one twice focuses the tab that is already open. That is the conversations arrangement (`src/plugins/conversations/activate.ts`, `const LIST_KEY = 'conversations'`, and `openPluginTab`'s focus-or-create in `src/tab/openers.ts`) rather than a new one, so the tab bookkeeping, the `updateTab` repaint, and the profile restore all behave the way a user of `conversations` already expects.

**The plugin owns no state and never reaches a model.** Everything the model does happens in a host-owned `VisualizationsManager`, reached only through the `visualizations` topic's actions — the same seam conversations uses for its `send`. This is forced, not preferred: `eslint.plugin-boundaries.mjs` lets a server plugin import only `../api.js`, `../files.js`, and two named opener helpers, so a plugin cannot reach `connectAcp` at all. It also means the plugin needs **no new capability**, so `TAB_PLUGIN_API_VERSION` stays at 1, the thirteen-capability count in `documentation/developer-documentation/tab-plugins.md` stays true, and `src/plugins/documentation.test.ts` keeps passing untouched. The plugin's declared capability set is the seven conversations already declares: `openOrFocusTab`, `updateTab`, `dockTab`, `topicData`, `topicAction`, `rejectRequest`, `reportFailure`.

**A data source is one line: an `http`/`https` URL or a local file path.** The two are told apart by the scheme rules `normalizeWebUrl` already applies (`src/openers/web-target.ts`, which rejects `javascript:`, `file:`, `ftp:`, and anything else non-http before defaulting a bare host to `https`). Nothing else is accepted, and there is no configuration file listing sources: the user types a URL, pastes one, or names a path.

**The server fetches; the client never does.** Two reasons, and the second is the one that settles it. A browser cannot fetch an arbitrary origin the user pasted without that origin sending CORS headers, so a client-side fetch would work only for sources that happen to be permissive — which is the opposite of "as easy as possible". And the app's security posture is a loopback-bound server with a token and a Host/Origin guard, so an outbound request the local user asked for fits inside the existing threat model exactly as `openExternally` does. The fetch is bounded: `http`/`https` only, no credentials, cookies, or authorization headers of any kind are ever sent, a fixed timeout, a response body cap, and a redirect limit.

**Two source formats: JSON and delimited text.** JSON must be an array of flat objects, or an object with a single array-of-objects property — the two shapes an API returns in practice. Delimited text must be header-led, with the delimiter sniffed from `,`, tab, `;`, or `|` on the first line. Anything else is recorded as a failure whose message names the format and what was found. Both parsers are pure and are where the format knowledge lives.

**The table is inferred, not declared.** Column names come from the first object or the header line; a column's type is `number` when every non-empty value in it parses as a finite number, `boolean` when every value is one of the two boolean spellings, and `string` otherwise. Dates are deliberately *not* inferred — a date column stays a string, so a line chart over it is a category axis, which is honest and much simpler than timezone reasoning. An empty table, a table with no columns, or a table with no numeric column is a recorded failure, because none of them can be charted and guessing would produce a blank chart.

**The interview is the model asking and the user answering one question at a time.** Creating a visualization fetches the source, builds a table, and makes one model call with a sample: the column names, their inferred types, a few rows, the row count, and the source. The model replies with a *series* of questions about what to visualize and how — which measure, which comparison, which grouping, what to call it. The tab shows the current question with the model's suggested answers as one-click options plus a free-text field; answering advances to the next. When the last answer is in, a second call asks for the chart itself. This is the flow the feature asks for, and the one-question-at-a-time shape is what makes it answerable by someone who has not written a chart before.

**A question carries suggestions, and free text is always available.** Each question holds its prompt and up to four suggested answers; the user's answer is stored as text either way. Clicking a suggestion is two interactions; typing is one, and typing remains possible because the useful answer is often none of the suggested ones. A visualization with no questions left and no chart shows a single line saying the model had no questions to ask rather than an empty region.

**The model produces a chart specification, never code.** The specification names one of five kinds — `bar`, `line`, `area`, `scatter`, `pie` — an x column, a y column, an optional series column that splits the marks into one line or bar per distinct value, a title, and optional x and y axis labels. Before it is stored, the specification is narrowed through a guard *and* checked against the real table: the x, y, and series columns must exist, the y column must be numeric, and a pie must have a non-numeric x. A specification that fails is not stored and the model's accompanying text is shown instead, so the user sees what happened and can ask again. This is the whole reason the feature is safe to hand to a model: what the model produces is a value, checked against the data, and a value the client already knows how to draw.

**A domain failure is recorded on the record, never thrown at the plugin.** A source that will not fetch, a body that will not parse, a table that cannot be charted, a model that answers with something unusable, a chart the user then changed — each becomes an `error` string on the visualization, rendered in its tab, and each leaves the plugin running. The plugin is disabled only for a contract failure, which is what `reportFailure` is for. Conversations already draws this line with its per-turn `error` field (`src/conversations/responder.ts`, `fail`), and reusing that discipline means the plugin's own failure surface stays empty.

**Real time is a server-side poll, off until asked for.** A visualization's refresh interval is a number of seconds, and `0` means off — the default, so a visualization costs one fetch and then nothing. A non-zero interval makes the manager re-fetch on a timer, re-parse, replace the stored table, and emit the topic, which repaints every open tab of that visualization. The interval is offered as a fixed set of choices (off, 10s, 30s, 1m, 5m) rather than a free number, because the shape of the tab is "keep this current" and not "run a data pipeline". The tab shows when the data was last read and offers a one-shot refresh, so a poll the user did not intend is always visible and always overridable. A poll that fails records the failure and keeps the previous table, so a flaky endpoint leaves a working chart on screen.

**The tab payload is bounded, because the whole view is re-broadcast.** `emitState` ships every tab's payload on essentially every mutation (`architecture-principles.md` §8 names this as the known weakness), so a visualization that put a million rows in its payload would tax every keystroke in every tab. The payload therefore carries at most **500 rows** and at most **32 columns** of the fetched table, and the window also carries the true total row count so the tab can say `showing 500 of 12,043 rows`. Five hundred is comfortably past what a bar chart can render legibly and past what a scatter needs to show a trend. This is a deliberate bound, not a target: the real fix is the delta-and-sequence transport principle 8 asks for, which is an architecture change well outside this feature, and the bound is what keeps the feature from depending on that change not happening.

**Export is client-side and dependency-free.** The chart is already an SVG element in the document, so PNG is a detached `Image` drawing that SVG into a canvas at a chosen scale, then `toBlob('image/png')`, and the download itself is an object URL plus a synthesized anchor carrying `download` — the platform's own answer, with no download helper written. PDF is a small pure writer: one page, one image XObject sized to fill it, an optional `/FlateDecode` filter when `CompressionStream` is available and raw samples when it is not. The ceiling is worth stating: the unfiltered fallback means a 1600×1000 chart at 2× scale is roughly 5 MB, while the deflate path every browser this app targets provides brings it to a few hundred kilobytes. `package.json` gains no dependency for either, which matters here more than usual: a charting or PDF library would be a supply-chain addition to a feature whose whole appeal is being able to trust what a model produced. The writer is a pure function over pixel samples, so it is testable without a canvas, and its correctness property — that every cross-reference offset points at its own object — is directly assertable.

**Each visualization gets its own empty agent workspace, created on first use.** The model is tool-less (no `allowedTools`, so `decidePermission` refuses every request) and is fed its sample as prompt text, so it needs no directory to do its job. It gets one anyway, for the same reason a conversation does: it is the third layer of a defence whose first two are the tool denial and the capability narrowing, and a shared scratch directory would put every visualization's agent inside one carve-in. The directory is created on the first agent call rather than at creation, so an abandoned visualization leaves nothing on disk, and it is removed with the rest of the directory on delete, together with its `~/.claude.json` trust entry.

**The ACP session pool is shared with conversations, not copied.** `src/conversations/sessions.ts` is already a generic pool over `(id, model pair, workspaceDir, hooks)` with lazy connect, reuse, per-id close, and `dispose` — nothing in it is conversation-specific but its name and location. A second copy for visualizations is the duplication `ai/guidelines/plugins.md` §13 and the project's one-definition rule both forbid, so the pool moves to `src/acp/session-pool.ts` and both managers import it. The move is behavior-preserving and lands as its own first checkpoint, before anything else references it.

**Model choice is per visualization, seeded from the catalog.** A new visualization starts on the first pair `availableConversationModels()` offers — the same `claude`/`opencode` catalog a conversation uses — and the tab's header carries a selector grouped by harness, exactly as `web/src/plugins/conversations/model-pairs.ts` does. It deliberately does **not** share the conversations store's `last-used-model.json`: that file belongs to the conversations domain, and reading it from here would couple two features for a convenience nobody asked for. Changing the pair ends the current session, so the next call re-primes under the new one.

**The stored record is one JSON document in one directory.** `~/.janissary/visualizations/<id>/visualization.json` holds the schema version, id, title, timestamps, the source line, the model pair, the refresh interval, the questions and answers, the chart specification, the bounded table, the last-read time, and any error. Its siblings are the empty workspace and that workspace's temp directory. Written atomically through `src/atomic-write.ts` after every completed step, exactly as a conversation record is, because an interrupted write must leave a valid record behind. Home-level rather than project-level, so an ordinary launch's recursive state sweep never destroys a saved visualization. A directory with a missing or malformed document is skipped with one warning and left alone, matching how `ConversationStore` treats the same case. Listing scans the directory and parses one document per visualization, memoized until something changes; that is a linear parse at the scale one user's visualizations reach, and the upgrade path if it ever is not is a summary index file at the top of the tree, exactly as `ConversationStore` records — not needed now and deliberately not built.

**The source may be changed only while there is no chart.** Setting a new source discards the interview and its answers and starts over. Once a chart exists, changing the source would silently invalidate the answer the user gave to every question, so the control is hidden then rather than offered and warned about. This is what makes a failed fetch recoverable: the tab is editable from the moment it opens.

**Renaming and deleting behave as they do for conversations.** Double-clicking the title in the metadata row renames it through the host's own `InlineEditInput`, trimmed and capped at 60 characters, and a blank commit changes nothing. Deleting from the index asks first, then removes the record, the workspace, and the trust entry. A tab whose visualization is deleted while open stays open, showing what it had, with every control disabled and a line saying the visualization was deleted — the same resolution conversations settled on, and its composer is disabled rather than removed so the layout does not jump.

## Autonomous decisions

This run executes `ai/tasks/plan-a-new-feature.md` unattended, so every question that task's question phases would have put to a user is answered here instead. Each answer is recorded with the evidence it rests on, per the run's decision policy: the supplied feature description first, then the binding project instructions and guidelines, then the relevant specs, then verified behavior in this repository. No answer below claims a user approved it.

**Primary flow.** The supplied description says a user should be able to "point AI at a data source", have the AI "parse and understand the source", and see the AI "present a series of questions". That fixes the shape: name a source, the model reads it, the model asks, the user answers. Two routes into that flow were considered. A second claimed command (`visualize <source>`) would type well but splits one feature's entry point across two command claims for no gain, because a declaration claims one command name. The chosen route keeps the single `visualizations` command and adds two non-command entries: the index's ➕ field, and a `Visualize this` entry in the default context menu that takes the source straight from a text selection. The second is the cheapest route in the whole application and is already the established pattern for exactly this shape — `Chat about this` in `src/plugins/conversations/manifest.ts`. Recorded decision: one command, two non-command entries.

**Primary flow, continued.** The description asks for "a visualization tab" and "visualization tabs", plural, and calls the index "an index of existing visualizations, similar to conversations". Two tabs of one plugin follows directly, and the singleton-plus-per-subject arrangement is read off `src/plugins/conversations/activate.ts` rather than invented.

**Edge cases.** Each was decided against existing behavior rather than left open, because each has a precedent in the feature being modeled:

- *The source cannot be read.* Recorded as an error on the record and shown in the tab, the way a failed conversation turn is (`src/conversations/responder.ts`, `fail`). The plugin is not disabled, because a bad URL is a domain outcome and `reportFailure` is reserved for a broken plugin.
- *The model answers with something unusable.* Recorded as an error; the visualization stays in the tab. Never a cast, never a partially-applied chart.
- *The model names a column the table does not have.* Refused at the boundary, the reply is shown instead, and the user can ask again.
- *The tab is closed mid-question or mid-answer.* The in-flight call and the refresh timer for that tab are dropped, the same way `ConversationsManager.cancelClosedConversations` handles a closed conversation. The record and its answers survive, so reopening resumes the interview.
- *The visualization is deleted from the index while its tab is open.* The tab stays open with its controls disabled and a line saying it was deleted. This is the resolution `product/specs/conversations.md` already records for the same situation, so a second answer here would be a gratuitous difference.
- *The source stops responding during a poll.* The previous table stays on screen and the failure is recorded. Clearing a working chart because one poll failed is the wrong trade.
- *The user answers a question with something none of the suggestions said.* Accepted. Suggestions are shortcuts, not a closed set, and the useful answer is often not one of them.
- *Two visualizations point at the same source.* Allowed. They are separate records with separate charts; nothing is shared, so there is no conflict to resolve.
- *An empty or unchartable table.* Refused at parse time with a reason naming what was missing, rather than producing a chart with no marks.

**Scope boundary.** The description's six requirements — index tab, plugin-implemented visualization tabs, an easy external source, an AI interview about graph type and variables, chat-driven modification, PNG and PDF export, and real-time fetching — are all in. Everything else named in "Out of scope" was considered and excluded, and each exclusion is recorded there with its reason. The two worth calling out here: a charting library is excluded because the description asks for a *plugin* implementing visualization tabs, and a hand-written renderer is what keeps the feature free of the supply-chain surface a library would add; and a source is a URL or a file rather than a database query, because the description says "external data source" and `db` already owns local databases.

**Naming and wording.** Fixed exactly, matching the existing voice:

- the command is `visualizations`, matching the `conversations` and `schedules` commands it sits beside;
- the index's empty state is `No visualizations yet`, matching `No conversations yet` and `No schedules yet`;
- a title lookup miss is `No visualization matching "<title>".`, matching the conversations wording exactly, including the trailing period;
- the context-menu entry is `Visualize this`, matching `Chat about this`;
- the ➕ control's tooltip is `New visualization`, matching `New conversation`;
- an uncharted visualization with no questions left says `The model had no questions to ask`, and one whose table is chartable but has no chart yet says `No chart yet`;
- a visualization whose source is truncated says `showing <n> of <total> rows`, lower case, because it continues the sentence the metadata row starts.

**Implementation decisions.** `2b`'s four checks are all "yes" — a new subsystem, a new topic and action union, a timer-driven refresh and a streaming push path, and no existing precedent for charting — so the implementation questions were worked too, and each answer is a decision in "Proposed changes" rather than an open choice: the domain is a host-owned manager reached through topic actions because the plugin import boundary forbids the plugin from reaching ACP; the session pool moves rather than being copied because the project's one-definition rule forbids the second copy; the new code lands in six checkpoints because each is independently verifiable; and the new client code splits into `chart/` and `export/` subdirectories because the components would otherwise breach the 200-line limit.

## Proposed changes

**Checkpoint 1 — share the ACP session pool.** Move the class at `src/conversations/sessions.ts` to `src/acp/session-pool.ts`, renaming it to say what it is, and repoint `src/conversations/manager.ts` and `src/conversations/sessions.test.ts` at the new location. Nothing else changes: the same lazy connect, the same `connectAcp` options, the same `close`/`dispose`. Delete the old file rather than re-exporting from it, per `imports-and-barrel-files.md`. This lands alone and is behavior-preserving, so the existing conversations suite is the proof it broke nothing.

**Checkpoint 2 — the wire types and the topic.** A new `src/protocol/visualizations.ts` declares the views a plugin and a client may see: a summary (id, title, updatedAt), a question (prompt plus its suggestions, with the answer when given), a chart turn (the user's query, the model's reply, the pair that answered, the error, the streaming flag — the same fields `ConversationTurnView` has, because a modification conversation is a conversation), a table (columns with names and types, rows, the true total, the truncated flag), and a window carrying those plus the visualization's own metadata. It is its own module rather than more declarations inline in `src/protocol.ts` (113 lines today) because that directory already holds one file per domain — `protocol/schedule.ts`, `protocol/sessions.ts`, `protocol/plugin.ts` — and a feature adding view types belongs in its own. `src/protocol.ts` composes and re-exports it, and `src/plugins/api.ts` re-exports the ones a plugin needs beside `ConversationsView`, since the plugin import boundary forbids reaching `../protocol.js` directly. `src/plugins/api-topics.ts` gains `'visualizations'` in the topic union and the notification table, a `TabPluginNotification` arm, and the action union: `create`, `load`, `setSource`, `setModel`, `rename`, `delete`, `startInterview`, `answer`, `revise`, `cancel`, `setRefresh`, `refreshNow`. Add the matching bus channel beside `ConversationsEvent` in `src/bus.ts`, and the `TOPIC_SOURCES` entry in `src/plugins/topics.ts` whose `act` is one `actOnVisualizations` switch modelled on `actOnConversations`. Inert on its own and exercisable by tests with no plugin present.

`startInterview` is not scope creep: it is the recovery path for a call that failed or that came back unusable, and without it the only way back is editing the source, which is a worse answer to "try that again". It is one action and one intent because there is nothing else to it.

**Checkpoint 3 — the host domain.** A new `src/visualizations/` holds ten modules, each under the 200-line limit. Six are the ones the shape of the work called for; four more were extracted from them as they grew, and each earns its own place:

`source.ts` is pure. It classifies a source line into a URL or a path using `normalizeWebUrl`'s scheme rules, and states which of the two it is. No I/O.

`fetch.ts` is the effectful half: it reads a URL with `redirect: 'follow'` bounded by a manual redirect count, `signal` from a fixed timeout, no request headers beyond a `User-Agent`, and a body read that stops at a byte cap. It reads a local path through `readFileSync` with a size check first. It returns text or a reason, never throws at the caller. Its `fetch` implementation is a parameter with the platform's as its default, so its test drives every branch — the cap, the timeout, the redirect limit, the status check, and the header check — from a stub with no network and no listening server, which is why this feature needs no HTTP test fixture.

`table.ts` is pure. It parses JSON text into a table, parses delimited text into a table, infers each column's type, and caps columns and rows. It also holds the one check that genuinely belongs beside the parsing — refusing a table with no rows or no numeric column, since a column's type is what makes it unusable.

`ingest.ts` is pure, and is text to a table or to the reason it is not one. It is apart from `table.ts` because the format decision is a different question from the parsing: whether a body beginning like JSON should be reinterpreted as delimited text when its JSON turns out to be malformed is a judgement about what a source is, not about how a table is read, and it deserves a name of its own.

`chart-spec.ts` is pure, and is the gate between a model's reply and a chart a user sees. It is apart from `prompts.ts` because it answers "may this be stored" while `prompts.ts` answers "what did it say", and a validation rule drifting into a parser is how a guard ends up trusting a shape it should refuse.

`prompts.ts` is pure. It builds the three prompts: the opening one carrying the sample and asking for questions, the closing one carrying the answers and asking for the chart, and the modification one carrying the current chart and the user's query. Each states the exact shape wanted and that the reply is one JSON object and nothing else. It also holds the parser: strip a fenced block if one is present, `JSON.parse`, and narrow through a guard — never a cast, because model output is untrusted input.

`interview.ts` is the responder, modelled on `ConversationResponder` but state-machine shaped rather than turn shaped. It holds the set of visualizations with a call in flight, refuses a second one, and on completion routes the accumulated text through `prompts.ts` to produce either questions, a chart, or a plain reply.

It accumulates chunks without coalescing them on a timer, which is a deliberate departure from the conversation responder. There is nothing to render from a partial reply, because a partial reply is half a JSON object, so a coalescing tick would bound a buffer nothing reads before the whole buffer is read at once. Accumulating and reading once is both simpler and the same cost.

A chart that fails validation is not stored and the reason is recorded instead, exactly once — an earlier version committed the reason and then committed again without it, which cleared it. Failures set the error and close the session, and a rate limit is recognized through `isRateLimitError`.

`refresh.ts` owns one timer for every visualization, which is part of why the manager could stay inside the file-size limit. It polls only what a tab is open for, so a saved visualization is never fetched behind the user's back, and it re-arms itself after every commit, because the interval and the open set both change through one.

`index.ts` owns which records are known and which of them have a tab on screen, and it is where the payload bound actually lives: a window carries the table, and every tab's payload is re-broadcast on essentially every mutation, so a table kept for a tab the user closed would be a cost paid by every keystroke in every tab from then on. The open set is read off the tabs themselves on every pass rather than tracked there, so it cannot drift from them.

`store.ts` and `manager.ts` complete the domain. The store is `ConversationStore` with a different record: same directory shape, same atomic write, same skip-and-warn scan, same id assertion, plus the bounded table and the workspace pair. The manager is `ConversationsManager` with the differences the decisions above name — it owns the refresh timers, it can set a source, and it drives the interview instead of a plain turn. It is registered as `visualizations` in `ManagerRegistry`, positioned in `MANAGER_DISPOSE_ORDER` immediately after `conversations` (it depends on the same pool and the same bus, and must release its timers before the bus is cleared), and constructed in `createManagers` next to `conversations`. It has no `closeTab(label)` and is not in `MANAGER_TAB_RELEASE`; instead it subscribes to `tab:removed` and drops the timer for a closed tab and the in-flight call with it, the same way `ConversationsManager` cancels a closed conversation's stream.

**Checkpoint 4 — the server plugin.** `src/plugins/visualizations/manifest.ts` claims id `visualizations`, tab label prefix `visualizations`, no file extensions, the command `visualizations`, the topic, a `defaultMenu` entry labelled `Visualize this`, and the seven capabilities. `shared.ts` is import-free and declares the schema version, the two payload kinds (`list` and `visualization`), every intent payload type, and the hand-written guards — re-declaring the view shapes the way every other bundled plugin's `shared.ts` does, with a test pinning them against the protocol types the way `src/plugins/schedules/shared.test.ts` does. `activate.ts` follows the conversations shape rather than `defineDockableList`, because the command has a title branch and the payload discriminant splits the intents; it uses `defineIntents` per kind where the accepted set does not depend on the kind. `tabs.ts` holds the tab bookkeeping: mint an id and open, open an existing one, and repaint every open tab from a topic notification — the list key with the payload alone, each visualization key with its title and payload. `Visualize this` creates a visualization from the selection as its source. Register the manifest in `src/plugins/catalog.ts` and the loader in `src/plugins/loaders.ts`.

**Checkpoint 5 — the client plugin.** `web/src/plugins/visualizations/index.tsx` default-exports the component and named-exports the guard, dispatching on the payload kind. `VisualizationList.tsx` is `ConversationList.tsx` with the ➕ control replaced by a source field that creates a visualization from what is typed, and the rows carrying the title, the last-read time, and a delete button. It drives its selection through the shared `useListSelection` and `nextListSelection` and needs no keys module of its own: the click rule is the one line `conversation-list-keys.ts` exists to hold, so it is written inline as the `decide` callback `rowClicked` already takes, rather than promoted into shared for a single line. `VisualizationTab.tsx` composes the metadata row (title, model selector, the source line, refresh control, export buttons, split action) above whichever of three regions applies: the question being asked, the chart, or the failure. `VisualizationQuestion.tsx` renders one question with its suggestions as buttons beside a free-text field. `VisualizationChat.tsx` is the modification conversation, built on `CommandBarShell` and the promoted `useStickToBottom`. Register the entry in `web/src/plugins/registry.tsx` with its schema literal, pinned by `registry.test.tsx` as the others are, and pin the plugin's manifest to declare every capability its activation uses and nothing more, as `src/plugins/sessions/shared.test.ts` does.

The chart and export code sit in two subdirectories of the plugin, because both are several files and neither belongs in a component. Note that a client plugin may import only `../api`, `../shared.css`, and its own shared contract — the `web/src/plugins/*/**` rule in `eslint.plugin-boundaries.mjs` — so a sibling plugin's directory is unreachable even for a module in `web/src/shared/`. `useStickToBottom` is therefore moved to `web/src/shared/stick-to-bottom.ts` as a second real consumer warrants, and then published to plugins through `web/src/plugins/api.ts`, exactly as the command bar, the selection hooks, and the dialog already are. A plugin reaching into `web/src/shared/` directly would trip the rule, and moving the file is what makes the promotion possible at all. Intra-plugin imports such as `./chart/points` do not start with `../` and are unaffected.

`chart/scale.ts` is pure and holds the two scales a chart needs — a linear one for a numeric axis with its tick values, and a band one for a category axis.

`chart/points.ts` is pure and turns a table plus a specification into the marks a chart draws: one entry per row, grouped into series when a series column is named, and aggregated into slices summing the y column when the kind is a pie. It is where a non-numeric value in the y column is dropped, so no component has to decide what to do with one. It also holds the extent calculation, beside the values whose extent it computes rather than in the module that maps an extent onto pixels, because the two change for different reasons.

`chart/Axes.tsx` draws the axis lines, ticks, and labels from a prepared scale. `chart/CartesianChart.tsx` draws bar, line, area, and scatter as one frame over prepared marks, branching only in the mark it emits per point — those four share a frame, a scale pair, and a point list, and splitting them into four components would duplicate all three. `chart/PieChart.tsx` draws the slices, which share nothing with a Cartesian frame. `chart/ChartSvg.tsx` is the frame the other two sit in: title, plot area with margins, a legend when there is more than one series, and the empty message when there is nothing to draw. No chart component reads the table or decides a domain; all of that arrives prepared.

`export/pdf.ts` is the pure writer: page, contents stream, one `/DeviceRGB` image XObject at 8 bits per component, and a cross-reference table whose offsets the tests assert point at the object each one names — the property that decides whether a reader opens the file.

`export/download.ts` is the browser wiring around it, and it is where `CompressionStream`, the detached `Image`, the canvas, `toBlob`, and the object-URL anchor live. It is one module rather than three because every one of those is a browser API and the writer beside it has none, which is exactly what lets the writer's test be a plain function call. The compressed body is produced by the caller and handed to the writer, so the writer stays synchronous and knows a filter exists only because it was given one.

**Ordering and constraints.** Each new `src/` import carries the `.js` extension; catalog and metadata lookups use `??` rather than `||`; nothing narrows parsed JSON with a cast. Each of the six checkpoints above leaves typecheck and tests green on its own, which is what makes the order safe. The client files are the most likely to hit the 200-line limit, and the split above is the plan's answer — a component that grew instead would be extracting a subcomponent, never compacting.

**Specs and documentation.** A new `product/specs/visualizations.md` describes the command grammar, the index, the three tab regions, the interview, the chat, export, refresh, the source rules and their failure messages, model selection, storage, and the workspace the agent runs in. `product/specs/tab-plugins.md` gains a `### Bundled visualizations plugin` section beside the conversations one, and its topic paragraph gains the fourth topic. `product/specs/context-menu.md` gains the `Visualize this` entry beside `Chat about this`. `product/specs/sandbox.md` gains a line recording that a visualization's ACP agent is confined to a workspace belonging to no tab. `product/specs/acp.md` gains a line recording that a visualization's session is a third use of the same channel alongside the `acp` command's and a conversation's. `documentation/developer-documentation/tab-plugins.md` gains the `visualizations` topic in the section that lists them — which also corrects that section's claim that v1 defines one topic, `schedules`, which stopped being true when conversations and sessions shipped. `documentation/user-documentation/command-bar/plugins.md` gains the new line in its sample output and its count, which currently says nine. `help.md` gains a `visualizations` row beside `conversations`. `product/specs/application-config.md` is untouched: this feature adds no setting.

## Out of scope

- **A charting library, or any new dependency.** `package.json` is untouched. The chart grammar is five kinds over three column roles, which is what a model can be trusted to produce and what a reviewer can read; a library would add a large dependency to the one feature whose point is that nothing untrusted runs.
- **A scatterplot matrix, a histogram, a box plot, a heat map, or a stacked chart.** Five kinds is the grammar; adding one is a new arm in `points.ts`, a new component, and a new spec line.
- **The source being a database, a spreadsheet, or a live query.** The `db` tab already opens SQLite, and a visualization that queried one would need its own connection lifecycle and credential handling. A source is a URL or a file.
- **A source the client fetches directly**, and therefore any CORS-shaped workaround, a proxy, or an allow-list of permitted origins. The server fetches, and it fetches whatever the local user asked for.
- **Server-rendered charts.** The chart is SVG in the document, which is what makes PNG and PDF export a rendering step rather than a headless-browser problem.
- **Editing the chart by hand.** The chart is whatever the model said, refined by asking. A field-by-field editor over the specification is a different feature; the specification being a plain value is what would make it possible later.
- **Sharing, embedding, or publishing a visualization**, and a permalink form of a source. Every visualization is local to the machine that made it, like a conversation.
- **Automatic refresh on file changes, or a `watch` command.** Refresh is a timer over a fetch, chosen per visualization. Watching a local file means a directory watcher per visualization and a lifecycle this feature does not otherwise have.
- **Sharing one workspace between visualizations.** Rejected rather than deferred, for the reason the conversations plan gives: it would put every visualization's agent inside one sandbox carve-in.
- **`--relaunch` restore.** The visualizations on disk survive; the open tabs do not, exactly as for conversations.
- **A connections-panel row for a visualization's session**, and streaming *reasoning* text — only the reply the model streams as answer text is shown.
