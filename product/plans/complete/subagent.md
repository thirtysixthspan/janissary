# Subagent

**Complexity: 9/10** — ~1040 added lines, 46 files edited, 44 requirements, 59 test scenarios (p=9.02)

`subagent` starts a background agent run for a named role, gives it an optional AI task file or an assignment written inline in the context plus optional extra directions, asks it to finish with a delimited self-contained final result, and hands the extracted result back to whoever started it. A person types it in a command bar with flags and reads Markdown; an agent in an `ask` or `tell` session emits it with a JSON argument, gets nothing back at once, and later receives a `started` message and then a normalized completion message, each delivered to its own session as a new prompt. The point is orchestration: one agent can hand research or review to a cheaper or more suitable model, keep working, and pick up the answer when it lands. The feature's own success test is an orchestrator launching a research subagent with a query and receiving its result.

## Design decisions

Each decision comes from the feature text ("feature text"), from existing behavior ("from precedent"), or from a user answer ("user decision").

- **Two invocation forms (feature text, narrowed by user decision).** A person runs `subagent --role <type> [--task <file.md>] [--context <text>]` and receives Markdown-formatted text. An agent in an ACP session runs `subagent <json>`, where the JSON object carries `role` and `context`, and optionally `task`. The task is optional: when it is omitted the context carries the whole assignment; when both are supplied the context is extra directions appended after the task file. The feature text's `--model`/`--effort` flags and `model`/`effort` JSON fields are removed (user decision): the role alone decides the model and effort.
- **ACP callers (user decision).** `subagent` joins the native ACP command vocabulary (`NATIVE_ACP_COMMANDS`) as a grant any role may list. An `ask` or `tell` session can emit it when its role grants it. The built-in `tell` role grants it by default. Saved roles files are not changed and keep the grants they list. A subagent cannot launch its own subagents in this version, whatever its role grants. A plugin tab's `ask` session started through the `promptAcp` capability (`src/plugins/acp-capabilities.ts`) is an `ask` caller like any other and follows every rule below.
- **Human flow (user decision).** A person types the flag form in a command bar. The bar is not held. A Markdown reply says the subagent started once its session's handshake completes, matching the asynchronous `started` message. When the subagent finishes, a second Markdown reply in the same tab carries its status and output. The command is offered where `ask` and `tell` are (`available: acpAvailable`, `src/acp/availability.ts`), because both replies are background replies that only those tabs render.
- **Human reply wording (user decision).** The started reply is `Subagent <role> started.` The completion reply is `Subagent <role> <status>.` (`completed`, `partial`, `failed`, or `terminated`), then a blank line, then `output` rendered as Markdown. Neither reply prints a session id. Instead the person reaches the subagent's connection tab through a link (placement settled in the UI design section). `<role>` in every reply, message, and name is the role's canonical name as the roles file in effect spells it (`AcpRoleSettings.name`); only the unknown-role refusal echoes the trimmed input.
- **Caller kind (user decision).** Who invoked the command decides how it behaves. A launch from an `ask`/`tell` tool loop is an ACP caller and must use the JSON form. A typed launch is a person and must use the flag form. The wrong form is refused with that caller's own usage line: the JSON usage line for an ACP caller, the flag usage line for a person. An invocation is an ACP caller exactly when its `CommandInvocationContext.acpTool` is `true`, which only `dispatchNative` in `src/acp/run-prompt.ts:43` sets; every other dispatcher (typed, scheduled, queued, plugin capability) is a person.
- **Other callers (user decision).** A subagent's tool table never includes `subagent`, whatever its role grants, so it is neither in that subagent's primer nor extracted from its replies. An `agent` run that requests `janissary subagent …` receives `Agent: command not permitted: <command>.`, where `<command>` is the whole command line as sent (user decision), with or without a skill grant, the same template the `agent` run's `file write` refusal uses in this version.
- **Fields (feature text).** `role` selects the subagent's role. `task`, when supplied, names an existing AI Markdown file whose contents run as the subagent's instructions; when omitted, no task file is looked up and `context` is used directly as the instructions. `context` supplies extra parameters, directions, or context for the task, or the whole assignment when no task is named. `role` is required, and at least one of `task` and `context` must be present and non-blank.
- **Nothing returned at once (user decision, changing the feature text).** The `subagent <json>` command returns empty tool output the moment it runs and never blocks the caller's loop. The feature text had it return the `started` object immediately; instead, both `started` and the completion arrive later as asynchronous messages.
- **Started message (feature text, made asynchronous by user decision).** `{"status":"started","role":…,"sessionId":…,"callerId":…}` is delivered once the subagent's ACP session has completed its handshake.
- **Ids (user decision).** `sessionId` is the subagent's provider ACP session id, the id the harness reports at handshake (the `newSession` response's `sessionId`, `src/acp/index.ts:135`). `callerId` is the calling `ask`/`tell` session's provider ACP session id. Neither is minted by Janissary.
- **Refusals before a run exists (user decision).** A usage line, `Subagent: unknown role "<role>".`, `Subagent: the <role> role lists no models.`, and `Command is disabled: subagent.` are the command's immediate tool output, like every other native command refusal, and no asynchronous message follows. For a person, the same text is the command's only reply. `Command is disabled: subagent.` never reaches the command's `run`: for an ACP caller the gate produces it (`gateCoreCommand`, `src/acp/tool-table.ts:122`), for a person the dispatcher does (`refuseDisabledCommand`, `src/native-commands/dispatch-policy.ts:20`).
- **Failure before any handshake (user decision).** When a launch fails before any session completes a handshake (the clone fails, the task does not resolve, every model fails to start), no `started` is sent. The caller receives a `failed` completion with `"sessionId":null` and the error as `output`, delivered like any completion. The human form shows `Subagent <role> failed.` and the error.
- **Ids across fallback (user decision).** Only the first `started` is ever sent, carrying the first session to complete a handshake. If model fallback later replaces that session, no new `started` is sent, and the completion carries the id of the session that produced the outcome, which may differ from the id in `started`. When the outcome comes from a failure, that is the most recent session to complete a handshake, or `null` when none did.
- **Completion message (feature text).** When the subagent finishes, its caller receives `{"status":…,"sessionId":…,"callerId":…,"output":…}`. `output` is a distilled result, not raw intermediate steps. It is delivered asynchronously over ACP to the caller's session id.
- **Delivery to an ACP caller (user decision).** Janissary delivers each asynchronous message to the caller's session as a new prompt in the caller's role (`ask` or `tell`). If that role has a prompt running, delivery waits until it settles. The agent's reply to the delivered prompt appears in the caller tab like any other ask/tell reply.
- **Delivery order (user decision).** Waiting messages form a per-role queue on the caller tab, in the order they became ready, and go out one per prompt. `started` goes out as its own prompt, like a completion, unless it is still queued when that subagent's completion is queued; then the `started` is dropped and the completion alone goes out (user decision). A typed `ask` or `tell` prompt keeps today's rule: while that role has any prompt running, delivered or typed, it is refused with `ACP: a prompt is already running.` and never queued.
- **Caller session ends (user decision).** When a role's session ends without its tab closing (`ask reset`, `tell reset`, or the session closing), the subagents that session launched are terminated and its queued completions are dropped, so a fresh session never receives results it did not ask for. Closing the caller tab terminates every subagent it launched (from precedent: closing a caller terminates its agent runs). "The session closing" includes every path through `AcpSessionManager.close` (`src/acp/session-manager.ts:106`): a reset, a dead agent, model fallback inside a caller prompt (`AcpManager.settleAttempt`, `src/acp/manager.ts:143`), and a model the catalog no longer lists (`AcpManager.queueFor`, `src/acp/manager.ts:156`).
- **Delivered prompt text (user decision).** The prompt sent to the caller's session is exactly the message's JSON object on one line, `{"status":"started",…}` or `{"status":…,"sessionId":…,"callerId":…,"output":…}`, with no lead-in. The `subagent` primer explains what such a message means.
- **Primer (user decision).** The `subagent` tool primer teaches the JSON grammar, that the task is optional when the context carries the assignment, that the command returns nothing, and the `started` and completion messages that arrive later. It does not list the available roles; the user or the task text names the role. The roles spec's rule that no agent consults a role description stays true. The ordinary core primer the subagent receives at the provider boundary names the standard harness tools that are disabled, such as `bash` and `shell`, and tells it not to call them, so it does not spend a turn on a denial.
- **Recorded first prompt (user decision).** The durable record's first prompt block holds the same command primer the subagent receives at the provider boundary, prepended to the lead-in, task text, and optional context, so the connection tab shows the complete input the model was given. The loop still prepends the primer only once on the raw first prompt, leaving the recorded and loop inputs identical; the primer names the disabled harness tools as described above.
- **Statuses (feature text).** `started` means the subagent's session is up and it is running in the background. `completed` means it finished successfully. `partial` means a turn limit stopped its output before it finished.
- **Output (user decision, refined by a later repair).** The task prompt tells the subagent to write its final result between `<final_result>` and `</final_result>` tags, to keep reasoning, thoughts, and tool calls outside them, and to write nothing after the closing tag; the tags and everything outside them are not returned. On `completed`, `output` is the trimmed contents of the last complete, case-insensitive tag pair, with the tags and any surrounding reasoning or tool-call text discarded. When the turn has no complete pair the text is returned unchanged, preserving verbatim output — including empty, whitespace-only, and trailing-whitespace answers — and an empty pair stays an empty answer. There is no extra summarizing turn and no size cap. "Final reply text" is the last turn's display text as the loop reports it through `endTurn` (the extracted command line already removed by `filterCommandFromDisplay`, `src/acp/loop.ts:81`).
- **Turn limit (user decision).** A subagent uses the tool loop's cap of 8 commands (`CORE_MAX_STEPS`, `src/acp/drive-loop.ts:14`, which `driveToolLoop` passes as `maxSteps` for a core snapshot). When it hits the cap, the completion is `partial` and `output` is the last reply text, without the `(stopped after 8 tool steps)` suffix, because the status already says so. That suffix is added only by `runCorePrompt`'s `finished` handler (`src/acp/run-prompt.ts:127`), which a subagent does not use.
- **Failure and termination statuses (user decision).** Besides `started`, `completed`, and `partial`, a completion can carry `failed` or `terminated`, matching the `agent` run outcomes. On `failed`, `output` is the error text exactly as its source produced it, with no added prefix (for example `Agent: unknown task "x.md".`, a harness's `ACP error: …`, or the `ACP: every model in the <role> role failed.` list). On `terminated`, `output` is `Subagent terminated.`
- **Empty final reply (user decision).** Unlike `agent` runs, an empty final reply is not a failure: the completion is `completed` with an empty `output`, as role sessions accept an empty answer.
- **Role limits (feature text).** A subagent is limited to the tools and models its role specifies.
- **File grants (user decision).** A subagent honors every file command its role grants (`file read`, `file glob`, `file grep`, `file write`, `file edit`), against its own clone only, through the same workspace runners role sessions use. Unlike `agent` runs, which refuse all but `file read` in this version, nothing granted is refused. Writes stay in the clone and never reach the caller's tree. The runners are the root-taking ones a remote role session's far side already uses (`src/remote/serve-acp-loop.ts:45`: `runFileMutation` with a `LocalFileSystemPort`, `globWorkspaceCommand`, `grepWorkspaceCommand`, `readWorkspaceCommand`), not the local tab-bound `readFileInTab`/`globFilesInTab`/`grepFilesInTab`/`mutateFileInTab`, which always read the tab's own `workspaceDir ?? launchDir` (`localReadRoot`, `src/file-read/tab-read.ts:7`) and cannot be pointed at a clone.
- **Model selection (user decision).** The role handles model selection, fallback style. The subagent tries the role's enabled entries in order, any harness the role lists (`opencode`, `claude`, `codex`), each at the effort its entry stores, and falls back to the next entry when one fails to start, as `ask` and `tell` do (`attemptOrder`, `fallbackNotice`, `exhaustedError` in `src/acp/ask-role.ts`). There is no per-launch model or effort override. "Enabled" means the entry passes `managers.models.isKnownModel(harness, model)`, the filter `AcpManager.queueFor` applies (`src/acp/manager.ts:154`). The effort travels inside the launch `acpLaunchForEntry` builds (`src/acp/launch.ts:39`); the subagent does not pass `connectAcp`'s `effort` option.
- **Unknown or empty role (user decision).** The role is matched by name, trimmed and in any case, in the roles file in effect, with the built-in roles as fallback (`readRoleSettings`). An unknown role is refused at launch with `Subagent: unknown role "<role>".` A role with no enabled entries is refused at launch with `Subagent: the <role> role lists no models.` A refused launch creates no run. The built-in roles are not changed, so `research`, `code review`, `implementation`, and `documentation` need entries added in the roles tab before they can run a subagent.
- **Strict input (user decision).** Unknown JSON fields (including the removed `model` and `effort`), unknown flags (including `--model` and `--effort`), non-string values, a missing or empty `role`, a present but empty `task`, a blank `context` when no task is supplied, and invalid JSON are all refused before anything runs. A refused input creates no run.
- **Input error wording (user decision).** The argument picks the form: one starting with `{` is the JSON form, anything else is the flag form. Bare `subagent`, and every flag-form problem (unknown flag, missing value, repeated flag, missing `--role`, or neither `--task` nor `--context`), prints `Usage: subagent --role <role> [--task <file.md>] [--context <text>]`. Every JSON-form problem (invalid JSON, a top level that is not an object, unknown field, non-string value, missing or empty `role`, or neither `task` nor `context`) prints `Usage: subagent {"role":"<role>","context":"<text>"}`. Combined with the caller-kind rule, an ACP caller always sees the JSON usage line and a person always sees the flag usage line.
- **Task errors (user decision).** When a task file is named, it is resolved inside the fresh clone after the run exists, as with `agent`. An unknown, ambiguous, or out-of-bounds task therefore arrives as a `failed` completion. Its `output` is the resolver's own message, unchanged, e.g. `Agent: unknown task "x.md".` A fresh clone is a clone of `origin`, so a task file that exists only uncommitted in the caller's tree does not resolve; the installed `ai/tasks/` fallback still applies. When no task file is named, no task resolution happens locally or remotely: the context is the subagent's instructions, and the run's title is `Subagent: inline`.
- **No run limit (user decision).** Any number of subagents may run at once. Nothing caps them per tab or application-wide.
- **Where it runs (feature text).** Every subagent runs in the background, in a fresh workspace, on the same machine as the calling agent, whether that machine is local or remote.
- **Visibility (feature text).** ACP connections for subagents are shown in the connections tab.
- **Code sharing (feature text).** The command is close in nature to the existing `agent` command, and code paths are shared with it wherever they can be.
- **Roles (from precedent).** A role in the roles file in effect (`.janissary/roles.json` over `~/.janissary/roles.json`) is an ordered list of `harness`/`model`/`effort` entries plus a `commands` list of native ACP grants, read fresh and never created by consumers (`product/specs/roles.md`, `readRoleSettings` in `src/acp/ask-role.ts`). The root is `managers.tab.launchDir`, as `AcpManager.run` reads it (`src/acp/manager.ts:83`).

## Proposed changes

The decisions below describe the feature as delivered. Each is either a user decision or a mechanical consequence of the surrounding code. The implementation covered the full ordered sequence: grammar and primers, role lookup, records and naming, partial outcomes, local and remote provider ids, fresh workspaces, shared workspace runners, caller invocation context, receipt markers, delivered-prompt echoes, session-bound delivery, the remote clone service, frames and workspace selectors, single-entry and fallback execution, background launch, command policy and native integration, the tell default grant, and end-to-end verification. Each behavior owner shipped its spec and focused tests, and the integration seams were verified against the real tool loop.

### Vocabulary and grants

- `subagent` is appended to `NATIVE_ACP_COMMANDS` in `src/plugins/roles/shared.ts`, which adds it to the roles tab's **Add command** list and the Commands settings automatically. The vocabulary grows by one; the stated counts are listed under Specs and docs, and Order of work covers rebasing onto the `file-patch` and `web-search` plans, which each add one too.
- `subagent` is a one-word native command, which none of the existing ones is. Native command declarations now live in `COMMAND_FORMS` (`src/commands/forms.ts`), which `buildApplicationCommands` (`src/application-commands.ts`) reads to emit builtin rows, while it emits a native row per vocabulary entry. A `subagent` declaration is required by the vocabulary/forms parity test but would emit a second row with the same name; settings key by name, so the agent-access toggle would land on one row while the gate read the other. `buildApplicationCommands` therefore skips builtin-row generation for any core command that is also a native ACP command, leaving a single native row (`kind: 'native'`, `nativeTool: 'subagent'`, no parent) that carries both the Enabled and the Agent access toggles. Multiword builtin commands and their parents are unchanged. That row satisfies the claims test (`src/application-commands.claims.test.ts`), and `resolveApplicationCommand('subagent --role …')` resolves to it for the typed disabled check.
- The built-in `tell` role in `DEFAULT_ROLES` (`src/plugins/roles/roles-file.ts`) grants `subagent`. Saved files are untouched.
- `nativeCommandTool` in `src/acp/native-commands.ts` gains a `subagent` owner (an explicit branch before the `'question'` fall-through at line 18, and `'subagent'` added to `APPLICATION_COMMAND_NATIVE_TOOLS` in `src/shared/application-commands.ts:1`, which types the owner and feeds the client's `NATIVE_TOOLS` validation in `src/plugins/commands/shared.ts:48`). `createAcpToolTable` in `src/acp/tool-table.ts` gains a caller-side `subagent` entry with its own primer (`SUBAGENT_PRIMER`), included when the role grants it.
- The `subagent` entry sits before the `database` entry, whose `match: () => true` must stay last (`tool-table.ts:68`). Its `match` and `isCommandLine` accept a line whose first word is `subagent`, whatever follows, so a flag-form line from an agent is extracted and then refused with the JSON usage line rather than read as a final answer. `SUBAGENT_PRIMER` and the line predicate live in a new import-light `src/subagent/primer.ts`, because `tool-table.ts` is loaded by the remote server and must not pull in managers (`tool-table.ts:16`).
- The subagent's snapshot `grants` omit `subagent`, and that is the one mechanism that keeps a subagent from launching subagents (user decision; the builder gets no drop option). `corePrimer`'s "Only these commands are allowed" list and `gateCoreCommand` read `snapshot.grants`, and a remote subagent's far side builds its table from `frame.snapshot.grants` alone (`src/remote/serve-acp-loop.ts:98` → `driveToolLoop`, `drive-loop.ts:66`), so the entry is never built, primed, or gated in for a subagent, locally or remotely.
- The `agent` run's command gate (`src/agent/command-tools.ts`) refuses `subagent` with `Agent: command not permitted: <command>.`, echoing the whole command line, whatever the skill grants. The check goes in `runGrantedAgentCommand` beside the file refusals; `gateAgentCommand` in `tool-table.ts` already routes a non-file line to `runsOn: 'caller'`, and the far side of a remote agent run forwards it to the same local `runGrantedAgentCommand`, so this one site covers local and remote agent runs. It uses the same template as the file refusals there.

### Command and parser

- `src/subagent/parse.ts` holds the pure `parseSubagentCommand(text)`, which returns `{ form: 'flags' | 'json', role, task?, context? }` or `{ error }` carrying one of the two usage lines. `task` is optional and `role` plus at least one non-blank `task` or `context` is required; the two usage lines show the bracketed flag form and the minimal no-task JSON form. No I/O, per principle 4.
- `src/commands/subagent.ts` is the one `Command` definition, registered in `src/commands/index.ts`. Its `run` parses, checks the role (`knownRoleSettings`, below, then the model catalog's enabled filter as `AcpManager.queueFor` applies it), and either returns the refusal text or calls `launchSubagent`. For an ACP caller it returns empty output; for a person it returns nothing at once and the replies arrive later.
- The command is `coreResponse: true`, `available: acpAvailable`, with `samples` such as `subagent` and `subagent --role research --task t.md` (checked by `src/commands.test.ts`). `coreResponse` is what makes a shell tab echo the typed line and hand the dispatch result to the marker code (`web/src/plugins/shell/useShellSubmit.ts:97`).
- Unknown versus known role: `readRoleSettings` answers an empty role for an unknown name and cannot tell the two apart (`ask-role.ts:40`), so `src/acp/ask-role.ts` gains `knownRoleSettings(root, name, home)`, answering `undefined` when neither the roles file in effect nor `DEFAULT_ROLES` has that name and otherwise exactly what `readRoleSettings` answers.
- What `run` returns. For an ACP caller: the refusal string, or `''` once a run exists. `dispatchNative` (`src/acp/run-prompt.ts:56`) today returns `result.output` for every `coreResponse` command, which is always `''`, so it changes to return a string `result` first. No other `coreResponse` command (`ask`, `tell`, `ask reset`, `tell reset`) is a native command, so no other tool output changes. For a person: a refusal is appended as a background reply (`{ input: line, output, background: <fresh id> }`, no record) and `run` returns nothing, so no marker is drawn. A launch returns the record receipt described under Human replies.
- The calling role. Nothing in the invocation says whether `ask` or `tell` emitted the command. `CommandInvocationContext` (`src/commands/types.ts:6`) and `InvocationOptions` (`src/command/invocation.ts:6`) gain an optional `acpRole`, which `dispatchNative` sets from `request.role` and `childInvocationContext` copies. `run` reads the caller's internal session identity with `managers.acp.sessionIdentity(label, role)` and its provider id (`callerId`) with `managers.acp.providerSessionId(label, role)`, described under Provider session ids.

### Launch and execution (`src/subagent/`)

- `launch.ts` creates an `AgentRun` through `AgentRunManager.create`, so the subagent gets the run's identity, abort, owned resources, caller incarnation, durable record, connections row, and Terminate. The run carries subagent metadata: the role name, and for an ACP caller the caller role and that role's session identity at launch. It provisions a fresh shallow clone with `prepareAgentWorkspace` under a new "always fresh" option, so a tracked caller directory is never borrowed. When a task file is named it resolves the task with `resolveAgentSnapshot` and no skills; when omitted it skips task resolution locally and remotely, uses the context as the snapshot's task text, and writes the stable selector `inline` into the placeholder snapshot so the record is titled `Subagent: inline` from the receipt onward. Task errors settle the run `failed`.
- The "always fresh" option skips both the `workspaceName` branch and the `acquireAgentLease(callerDir)` borrow attempt (`workspace-execution.ts:16-27`) and goes straight to `workspace.create` with `workspaceCloneOptions(AGENT_CLONE_DEPTH)`. It is passed through `startLocalAgentRun`, which the subagent reuses for the run creation and the `workspace-provision` resource rather than copying them; `startLocalAgentRun`'s trailing parameters become one options object carrying `workspaceName`, `fresh`, and `subagentRole`, and `launchAgent` (`launch.ts:132`) is updated to match. Releasing the run's lease deletes the clone (`acquireAgentLease`'s last release calls `removeWorkspaceStrict`), which is what keeps the clone's writes out of the caller's tree.
- `AgentRunOptions` (`src/agent/run.ts:17`) gains `subagentRole?: string`, passed into the record metadata (`validateAgentRecordMetadata`, `AgentRecordFeed`). The record's `model` is the first enabled entry's model and the run's `effort` is that entry's effort or `default`; `command` is the invocation line.
- Order inside `launchSubagent`: capture the caller (`managers.agent.captureCaller`), create the run and its clone, return the receipt to `run` synchronously, and continue in the background. The run is never linked to the invocation's `signal`: for an ACP caller that is the calling prompt's abort (`dispatchNative` passes `request.abort.signal`), which `settleAcpPrompt` aborts when the prompt ends (`src/acp/response.ts:90`), and linking it as `linkRunToCaller` does for agent runs would terminate every subagent the moment its caller's prompt finished. Termination comes only from Terminate, the caller tab closing, the caller session closing, and shutdown.
- `execute.ts` holds the role-entry loop. For each enabled entry in order it builds the launch with `acpLaunchForEntry`, starts a background session with every internal tool denied as role sessions do (`internalToolDenial`), with `cwd` and confinement root set to the clone, and drives the loop through `runToolLoop` (next bullet) with the role's grants (minus `subagent`) and the default 8-step cap. A model that fails before completing a reply turn is closed and the next entry is tried, under the same rule and helpers `AcpManager` uses (`attemptOrder`, `fallbackNotice`, `exhaustedError` from `src/acp/ask-role.ts`). Fallback notices go to the run's record activity. Workspace commands run against the clone and caller-side commands run in the caller's captured invocation context, as agent runs already do.
- Loop entry point: `execute.ts` calls `runToolLoop` (`src/acp/drive-loop.ts:86`), which drives `runAcpToolLoop` through `driveToolLoop` for a local session and hands the run to the far side for a remote one; calling `runAcpToolLoop` directly would skip the gate, the primer, and the remote path. The snapshot is `kind: 'core'` with `roleName` set to the subagent role's canonical name, `grants` the role's `commands` minus `subagent`, `rows` built from `managers.nativeCommandSettings?.current()` the way `coreSnapshot` builds them (`run-prompt.ts:29`; that row mapping is exported from `run-prompt.ts` as a small helper rather than copied), and `withoutTools: false`. Its `role` field is `ask` (user decision), so `corePrimer` adds no tell instruction and the subagent's own lead-in alone asks for the self-contained final result; the grants still come from the subagent's role through `grants` and `roleName`. The session options are `connectAcp`'s `cwd` and `workspaceDir` both set to the clone, `offline` as captured from the caller tab when the launch receipt was published (so a later flag change cannot alter the run), and the launch's `env` and `sessionMeta`. `autonomous` is left unset (user decision): the session behaves like a role session, so `decidePermission` denies every provider permission request and only granted native commands run, and its handshake happens on its first prompt, which the subagent sends at once. On a remote host the session is therefore not marked run-only.
- Host. `runWorkspace` uses the root-taking runners against the clone; the body of `host.runWorkspace` at `src/remote/serve-acp-loop.ts:45-53` moves into a new shared `src/acp/workspace-runner.ts` (`runWorkspaceCommandIn(dir, command, signal)`) that both the far side and the subagent call, so the routing exists once. `runCaller` dispatches through `managers.command.dispatchNativeLine(run.caller.label, command, invocation)` with an invocation built like `launch.ts:154` (`runId: run.id`, `caller: run.caller`, `signal: run.abortController.signal`) plus `acpTool: true` and `awaitResult: true`, so `db`, `browser`, and `question` take their ACP-tool paths (`src/commands/db.ts:9`, `browser.ts:8`, `question.ts:7`) and tabs the commands create are tracked to the run (`CommandManager.trackRunTabs`); the result maps to text as `dispatchNative` maps it.
- Fallback rule. An entry fails when `acpLaunchForEntry` answers `undefined`, when the connection's `onError` fires, or when the loop's `error` fires, before the first `endTurn`; that entry's session is shut down and the next entry starts with a fresh session. After an `endTurn` any error settles `failed`. With one entry the failure text is that entry's error; with several, `exhaustedError(failures, role)`, whose `role` parameter widens from `AcpRole` to `string` because it is used only in text. One `acp:<runId>` resource, registered once, shuts down whichever session is current, as `execute.ts:102` does for agent runs.
- The prompt is the subagent primer, then the task text, then the context; with no task file the context is the task text and is not appended twice. The primer tells the agent it is a subagent, to finish with a self-contained final result for the agent that launched it between `<final_result>` and `</final_result>` tags with reasoning and tool calls outside them, and gives the role's command primers. The first prompt written to the durable record is that same command primer, prepended to the lead-in, task text, and optional context, so the connection tab shows the complete raw provider input while the loop prepends the primer only once. The core primer names the standard harness tools that are disabled, such as `bash` and `shell`, and forbids calling them.
- "The role's command primers" are `corePrimer`'s output, which `runAcpToolLoop` prepends to the first prompt on its own (`loop.ts:39`); the subagent's lead-in, task text, and context are the loop's user prompt, built by `subagentTaskPrompt` beside the other subagent texts in `src/subagent/primer.ts` (no separate module for one string builder) and recorded with `run.record?.prompt`. `SUBAGENT_PRIMER` (the caller's tool primer) and this lead-in are different texts.
- The first `onSessionStarted` from any entry queues the `started` message; later ones do not. Settling maps the loop result to `completed`, `partial` (the loop reported `capped`; the suffix is not added), `failed`, or `terminated`, closes the record with that outcome, and queues the completion carrying the answering session's id, or `null` when no session ever started.
- Settling goes through `settleAgentRun` with the mapped outcome, and a run already finished `terminated` wins, as `launch.ts:164-166` does. The completion is queued exactly once, after cleanup. Who receives it: a person caller gets the completion reply; an ACP caller gets a delivery through `AcpManager.deliver`.
- `partial` is a run outcome: `AgentOutcome` (`src/agent/run.ts:9`) gains `'partial'`, `AgentRunView['status']` (`src/agent/types.ts:31`) gains `'Partial'`, and `AgentRun.setStatus`/`finish` and `AgentRecordFeed.finish` (`src/agent/record-feed.ts:36`) map it to `Partial`. `AgentRecordFeed.finish` writes `Subagent terminated.` rather than `Agent terminated.` as a subagent record's terminated answer.
- Every acquired resource (clone lease, ACP process or remote session, remote clone) is registered on the run and released by its one cleanup, per principle 6.

### Provider session ids

- `connectAcp` in `src/acp/index.ts` takes an `onSessionStarted(sessionId)` callback fired right after `newSession`. The session handle gets no id accessor (user decision); the callback is the only way the id leaves the session. `AcpSessionManager` records the id from that callback and exposes the current role session's provider id, which supplies `callerId`.
- The callback is an optional field on `AcpOptions` (`src/acp/types.ts:32`), fired at `index.ts:135` once `sessionId` is assigned and before effort selection. `AcpSessionManager.session` records the id on the role's `CoreSession` holder from the callback (both the `connectAcp` and the `createRemoteAcpSession` branches, `session-manager.ts:78-93`), and `providerSessionId(label, role)` reads it. A role session's handshake runs on its first prompt, so by the time its loop emits `subagent` the id is always present.
- `createRemoteAcpSession` in `src/remote/acp-session.ts` takes the same callback. The far side (`src/remote/serve-acp.ts`) reports the id as soon as its `newSession` succeeds, ahead of effort selection and readiness, so a failed effort setup cannot discard an id whose handshake already completed.
- That report is a server-only `acp-session-started` frame carrying the transport address and the provider id; `acp-ready` gains the same id as an optional field while its readiness timing is unchanged. `RemoteAcp.open` captures the first live id it sees from `onSessionStarted`, whether on the notification or on ready, and reports at most one id per session. The frame types and catalogs gain `acp-session-started` and their decoders accept it (`src/remote/frame/decode-acp.ts`, `src/remote/frame/decode.ts`), `AcpSessionListener` (`src/remote/channel/acp.ts`) routes it only to the listener owning that transport address, and `RemoteAcpHooks` gains `onSessionStarted`. A peer that cannot report before readiness leaves `acp-ready` without the field; the exact-version handshake refuses that pairing.

### Delivery to an ACP caller

- The caller tab's ACP role runtime (`acpRoleRuntime`, `src/acp/role-state.ts`) gains a FIFO queue of pending subagent messages. `AcpManager` (already 208 raw lines) gains a thin `deliver(label, role, message)` that forwards to a new `src/acp/subagent-delivery.ts`: it appends the message, dropping that subagent's still-queued `started` when the message is its completion, and runs the head at once when the role has no prompt running. When any prompt for that role settles, `AcpManager` runs the next queued message. Each delivery is an ordinary `run` of the one-line JSON with a delivered-prompt receipt, so records, fallback, and the busy refusal for typed prompts all behave as they do today.
- Line budget: `src/acp/manager.ts` counts 192 lines under `max-lines`' rules, so it gains only the `deliver` delegate and one drain call; everything else lives in `subagent-delivery.ts`. The drain call goes in `settleAttempt` after `attempt.onDone(…)` (`manager.ts:148`) — the one place every prompt of `AcpManager`'s, typed or delivered, settles for good — and runs in a `queueMicrotask` so the settling prompt's own bookkeeping (`settleAcpPrompt`'s `messageBus` emit, the typed prompt's background reply) finishes first. Each queued message carries the subagent run id, the caller incarnation, and the captured session identity.
- A delivery runs like `runAcpCommand` (`src/acp/response.ts:49`): mint a `replyId`, call `managers.acp.promptResult(label, json, role, { appendRefusalToTranscript: false, replyId })`, and on settle append `appendAcpBackgroundReply` with the echo line `<role> ← subagent:<subagent role> <status>` as its input and the role's answering record. A delivery `run` refuses (a remote channel still connecting, a role that now lists no models) is not retried; the refusal is that echo's reply.
- A delivery for a caller whose role session identity no longer matches the one captured at launch is dropped.
- The identity check (`managers.acp.sessionIdentity(label, role)` equal to the captured one, the tab present with the captured incarnation and not `runtime.closing`) runs once, just before a message would run: at once when the role is idle, otherwise when it reaches the head. A stale message that waits in the queue is dropped there, which is the same outcome as refusing it on entry. Every delivery is also dropped once `AgentRunManager` is disposing, read through a new public `disposing` getter on it: at shutdown `agent` is disposed first (`MANAGER_DISPOSE_ORDER`, `src/managers.ts:96`) while `acp` is still up, and a `terminated` completion would otherwise start a fresh ACP prompt during shutdown.
- When a role session closes (`ask reset`, `tell reset`, or the session closing), `AcpManager.close` clears that role's queue and terminates, through `AgentRunManager.finish`, every live subagent whose captured caller is that tab incarnation, role, and session identity. Tab close already terminates the caller's runs.
- `close` is inherited from `AcpSessionManager` (`src/acp/session-manager.ts:106`, 145 counted lines), so the hook goes there: before calling `settleAcpPrompt`, when a holder exists, it calls into `subagent-delivery.ts` with the holder's `identity` to clear the queue and terminate that session's subagents. Clearing first matters, because `settleAcpPrompt` finishes the running prompt, whose settle triggers a drain. A role with no holder has no subagents to end.

## UI design

The feature extends three existing surfaces and adds no new tab, panel, or key binding: the shell tab's command-line decoration for `ask`/`tell` (`product/specs/shell-tab.md`, `web/src/plugins/shell/useShellReplyWriters.ts`), the connections list and connection tab (`product/specs/connections-tab.md`, `web/src/plugins/connections/`), and the caller's connections popup (`web/src/shared/status-windows/StatusPanels.tsx`).

- **Link to the connection tab (user decision).** A shell `subagent --role …` line gets the same decoration an `ask`/`tell` line gets, one cell after its echoed text. While the subagent runs it reads `Thinking` beside a spinning icon. Once the subagent settles it becomes a `see thought process` link. Both open or focus the subagent's connection tab at its newest history. The tooltip and accessible name are `Open <connection name>`. Because a subagent's durable record exists from launch, the marker always has a target. The decoration follows the existing marker rules: it is not terminal text, it is hidden in the alternate buffer, and it does not survive a reload, dock, or undock. A refusal before a run exists gets no marker.
- **Reply placement (user decision).** Each of a typed `subagent`'s two replies follows the shell's existing core-reply placement rule on its own. The started reply usually lands directly under the echoed line. The completion then lands at the current bottom under a repeated echo of the line, because the started reply was written in between. Both the original and the repeated echo carry the marker.
- **Delivered prompt echo (user decision).** When a `started` or completion message is delivered to a caller's role session, the caller's shell tab writes an echo line `<role> ← subagent:<subagent role> <status>`, for example `tell ← subagent:research completed`, as that prompt's line. It carries the usual `ask`/`tell` marker, linking to the caller role's own record, and the agent's reply goes beneath it under the existing placement rules. The echo and its `Thinking` marker appear when delivery starts, carried by the extended pending-name push (see Human replies).
- **Naming (user decision).** A subagent record's Name, in the connections list and as its connection tab's title, is `subagent:<role>`. Its record title, used in tooltips, the caller's connections popup row, and `Delete "<title>"?`, is `Subagent: <task filename>`.
- **Partial state (user decision).** A subagent record that ended `partial` reads `Partial` in the connections list and connection tab. It counts as closed: it sorts into the closed group and reads muted, like `Completed`, `Failed`, and `Terminated`. This adds one record status value.
- **From precedent.** A running subagent appears in its caller's connections popup as an ACP-kind row titled `Subagent: <task filename>` and leaves it when the run ends. That row is the keyboard route to the connection tab, since the shell marker is pointer-only. The connection tab offers **Terminate** while the run is live and **Focus tab** while the caller tab is open, exactly as for agent runs. Long names ellipsize as they already do. No key binding is added, so nothing collides with `help/keys.md`. (The popup row comes from `ownRecord` in `AgentRunManager.create`, `src/agent/manager.ts:57`, with no new code.)

Client code stays where the surfaces it extends already live; this feature adds no new client feature directory. The server owns every piece of subagent state (run, status, record, queue), per `ai/guidelines/architecture-principles.md` §1, and the client only renders the projections it is sent.

## Out of scope

Each boundary is a user decision.

- Nesting: a subagent cannot launch subagents.
- Per-launch model or effort overrides; the role decides both.
- An agent-monitor tab for a subagent (the `agent` command's `in a tab`).
- Skills for subagents.
- Choosing a host or workspace; a subagent always runs in a fresh workspace on the caller's machine.
- A `subagent cancel` or status command for the caller agent. A person can still stop a subagent with Terminate in its connection tab.
- Delivery across an app restart. Running subagents end at shutdown, as agent runs do.
- A limit on how many subagents run at once.
- A role list in the primer.
- A new command field, flag, or protocol shape for the final-result contract: the delimiters are prompt guidance and an extraction rule, thoughts and tool calls remain recorded as activity, and the caller-facing primer sees only extracted content.
- Changes to recorded activity, the server, or the tool loop for connection-tab formatting: inline tool-call parsing and command/reply grouping are view-local to `web/src/plugins/connections/`.
- New user-documentation pages for any of the above: the specs and the two help pages were corrected in place.
