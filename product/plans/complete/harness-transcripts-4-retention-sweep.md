# Keep harness transcripts across launches and reap them after `logRetentionInDays` days

**Complexity: 4/10** — 8 requirements, 3 production files edited, ~22 added lines, 5 test scenarios (p=5.09)

## Goal

The feature text says a harness transcript "should persist for N number of days where N is determined by a new configuration flag", that "a log reaper process that runs in the background on launch should be responsible for clearing out transcripts older than n days", and that "harness transcripts should not be removed when the application is halted". After subplan 3, `.janissary/transcripts/harness/` is still deleted wholesale at every launch. This subplan removes that clear and starts a background sweep at launch that deletes only transcripts last modified more than `logRetentionInDays` days before launch.

Source plan: `product/plans/complete/harness-transcripts.md` (the retention half of implementation step 3 and the retention parts of step 5). Run order: 4 of 5. Depends on `product/plans/ready/harness-transcripts-1-log-config-settings.md` (the `logRetentionInDays` field on `Config`, decoded as a non-negative integer), `product/plans/ready/harness-transcripts-2-generic-reaper.md` (`reapFilesOlderThan` in `src/state/reaper.ts`), and `product/plans/ready/harness-transcripts-3-move-transcript-directory.md` (the `.janissary/transcripts/harness/` directory, the updated test paths, and the spec sentences this subplan rewrites). All three must have landed before this subplan starts; without them it does not typecheck.

## Requirements

1. `.janissary/transcripts/harness/` is not cleared at launch (source Requirement 4; feature text: "should persist for N number of days").
2. No harness transcript is deleted when the application stops (source Requirement 5; feature text: "harness transcripts should not be removed when the application is halted").
3. Once per launch, a background sweep deletes harness transcripts whose last-modified time is more than `logRetentionInDays` days before launch (source Requirement 17, launch wiring; feature text: "A log reaper process that runs in the background on launch"; user answers: "Last modified", "Once per launch").
4. A `logRetentionInDays` of `0` makes the launch sweep delete every harness transcript last modified before launch (source Requirement 8, sweep half; user answer: "0 = delete at launch").
5. The sweep runs whether `logEnabled` is true or false (source Requirement 18; user answer: "Yes, still reap").
6. The sweep never delays startup: boot starts it and continues to start the server without waiting for it (source Requirement 19).
7. The sweep's cutoff is never later than launch, so it never deletes a file last modified at or after launch, including when `logRetentionInDays` is `0` (source Requirement 20, wrapper half; the strict `mtime < cutoff` comparison is subplan 2's Requirement 2).
8. A failure inside the sweep never crashes or stops boot (source design decision: "a rejection handler that swallows, so boot never waits on or crashes from the sweep").

## Design decisions

- `src/harness/transcript-file.ts` owns the harness call into the reaper through an exported `reapHarnessTranscripts(launchedAt, days)` wrapper, typed `(number, number) => Promise<void>`, so the directory path and retention arithmetic stay with the directory's owner (user answer: "transcript-file.ts wrapper").
- The wrapper is an `async` function, so any throw inside it becomes a rejection the caller's handler absorbs rather than a synchronous throw out of `boot()`. It awaits `reapFilesOlderThan(<its directory>, '.txt', cutoff)` with the cutoff `launchedAt - days * DAY_MS`. `DAY_MS` is a module-private constant `86_400_000`, written with numeric separators like `src/schedule/parsing.ts:9` `d: 86_400_000` (Existing functionality 6). With `days` of `0` the cutoff is `launchedAt` itself (Requirements 4 and 7).
- The wrapper does not validate `days`. Subplan 1's decoder already guarantees a non-negative safe integer, and an invalid JSON file falls back to the default `7` (Assumption 8).
- The wrapper returns without calling the reaper when the directory has not been initialized (empty string), the same guard `clearHarnessTranscriptDirectory` uses today (Assumption 6), so it can never sweep the process's working directory. The reaper would also no-op on an empty string (Existing functionality 1), but the guard is the transcript module's own contract and is what its test pins.
- Measure a transcript's age by its file mtime (last append), not by the timestamp in its name, so a long-running or recently ended session is never reaped mid-use (user answer: "Last modified"). The reaper from subplan 2 already does this.
- `src/main.ts` keeps the `Config` returned by `loadConfig(cwd)` in a local named `config`, and on the line directly after `clearStateDirectories();` (before the `webDir` bundle check) starts `reapHarnessTranscripts(Date.now(), config.logRetentionInDays)` without awaiting it, prefixed with `void` and followed by `.catch(() => {})`, the way `src/agent/launch.ts:44` fires `finish(...)` (Existing functionality 3). A one-line comment above it says the sweep runs in the background and boot never waits on it. `main.ts` gains no new config import (Assumption 4). The call is unconditional and reads only `logRetentionInDays`, which is what satisfies Requirement 5.
- `Date.now()` is taken at the call, after the state directories are initialized and before the server starts. No tab exists until the server is up and no launch recreates tabs (Assumption 10), so no file of this run exists yet, and every file this run writes has an mtime at or after the cutoff.
- Sweep once per launch, not on a recurring timer (user answer: "Once per launch"). Ceiling: an instance left running for days keeps files older than N days until the next launch. Upgrade path: call the same wrapper again from an unref'd daily interval started beside it in `main.ts`, with no change to the reaper.
- Only the full `janus` boot sweeps. `janus remote-serve`, `e2e-browser`, `stop`, and `init` return before `initStateDirectories` runs (Assumption 9), and a remote harness tab's transcript is written by the local tailer into the local directory, which the local launch sweeps.
- Stop clearing harness transcripts at launch by removing the `clear` from the `harnessTranscript` registry entry, the way `remoteSessions` and `notificationRecord` are kept across launches, with a comment matching theirs on why it has no clear (Assumption 3). Remove `clearHarnessTranscriptDirectory` from `src/harness/transcript-file.ts`, since nothing calls it any more, together with its import in `src/state/dirs.ts`, its mock entries in `src/state/dirs.test.ts`, and its describe block and import in `src/harness/transcript-file.test.ts` (Assumption 5).
- `src/harness/transcript-file.ts` imports from `src/state/reaper.ts`, and the reaper imports nothing from `src/harness/` (Existing functionality 1), so the existing `src/state/dirs.ts` → `src/harness/transcript-file.ts` import does not become a cycle.

## Out of scope

- A recurring sweep while the app runs (user answer: "Once per launch").
- Sweeping from `janus remote-serve` or any subcommand that returns before the state directories are initialized.
- No migration or cleanup of a legacy `.janissary/harness-transcripts/` directory (user answer: "Ignore it").
- Shell-tab text transcripts, recordings, captures, and the daily activity log keep their current clear-at-launch or retention behavior; `logRetentionInDays` does not govern them (user answer: "Harness transcripts only").
- The `logEnabled` write gate: subplan 5. This subplan must not make the sweep depend on `logEnabled`.
- Documentation follow-up feature candidate: the user documentation's harness transcript section (retention by `logRetentionInDays`, the launch sweep) and the configuration reference. User and developer documentation is owned by `update-documentation.md`, not by a feature PR or plan.

## Verification

1. `$janissary/scripts/run.mjs check-diff`
2. **Transcripts survive a restart.** From the checkout, run `npm run build` first, because `bin/janus.mjs` runs `dist/main.js` whenever it exists (Assumption 11). In a scratch project, launch with `node bin/janus.mjs <scratch>`, open `harness claude`, `harness codex`, and `harness opencode`, and send each one prompt so `.janissary/transcripts/harness/` holds one file per tab. Stop with `node bin/janus.mjs stop <scratch>` and launch again the same way: all three files are still there, unchanged. A failure looks like any file gone after the stop or the relaunch.
3. **The sweep ages files out without stalling startup.** With Janissary stopped, backdate one transcript by ten days with `touch -t` and a stamp from `date -v-10d +%Y%m%d%H%M` (macOS) or `date -d '10 days ago' +%Y%m%d%H%M` (Linux), and add a backdated `notes.md` and a backdated subfolder holding a backdated `.txt`. Relaunch with the default config: within a few seconds the backdated transcript is gone, the others remain, `notes.md` and the subfolder with its file remain, and the UI opened without waiting. Set `"logRetentionInDays": 0` in `.janissary/config.json` and relaunch: every `.txt` file from earlier runs is deleted, and a harness opened in this run still gets a file that survives until the next launch. A failure looks like the backdated file surviving, a current-run file deleted, a subfolder or non-`.txt` file removed, or startup stalling.
4. **Sweep runs with `logEnabled` false.** Set `"logEnabled": false` and `"logRetentionInDays": 7`, backdate one transcript by ten days, and relaunch: the backdated file is deleted (Requirement 5).
5. **Missing directory.** Stop Janissary, delete `.janissary/transcripts/harness/` entirely, and relaunch: Janissary starts normally and `.janissary/log/server.log` holds no error or stack trace from the sweep. A failure looks like a startup error or an unhandled-rejection trace in that log.
