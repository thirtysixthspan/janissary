# Fanout a prompt across N isolated agents in one tab

**Complexity: 7/10** — a new core tab view carried through `src/protocol.ts`, the tab record, the view guards, the wire projection and the client view layering, plus a new manager holding N concurrent git clones and N concurrent ACP sessions with their own per-member lifecycle and a new permission mode for what those sessions may do. Nothing in it is a new idea: the tab-view shape copies the harness tab, the N-sessions-in-one-tab keying copies `EditorAcpManager`, the per-session workspace and model copies `ConversationSessions`, and the clone lifecycle copies `WorkspaceManager`. The number is driven by how many surfaces have to agree and by the one genuinely security-sensitive addition, not by anything difficult in itself.

Running one prompt across several fresh isolated workspaces and lining the answers up to compare, the way Cursor 3's `/best-of-n` runs the same task in parallel across multiple models, each in its own isolated worktree, then compares outcomes. A `fanout <model>... <prompt>` command should cover the whole shape in one action: provision each member's workspace, open an agent connection in each, deliver the same prompt to all of them, and show the answers together.

Today a user comparing approaches opens tabs by hand and reads across them. Every building block exists separately — a workspaced `agent` tab clones its own disposable workspace, an ACP session returns a final answer to whoever asked, and the conversations feature already lets a person pick a harness and model per conversation — but nothing runs one prompt across several isolated workspaces and puts the answers side by side.

## Design decisions

Settled by the feature text, by existing behavior, and by the user's answers during planning.

**One new core tab view, not a plugin and not N tabs.** The comparison is a single tab of a new kind holding N agent connections, which is what the user asked for and which is also the smaller shape: the previous direction — N harness tabs in a group plus a bundled comparison plugin — needed a new host topic on the plugin contract, a new bus channel, a second user command to reach the plugin, a plugin instance-key scheme, and a run lifecycle to keep alive on its own. A core view needs none of that, and `EditorAcpManager` already proves the hard part: an editor tab holds one live ACP session per persona, N at once, keyed by a composite string.

**The tab copies the harness tab's shape exactly**, because that is the closest working precedent for a view with server-owned lifecycle. A `view` discriminant on the `Tab` record (`src/tab/types.ts:256`), a payload type beside the other five (`HarnessView`, `src/tab/types.ts:56`), a narrowing guard in `src/tab/view-guards.ts:18` beside the four others, a wire type in `TabView` (`src/protocol/tab.ts:58`), a projection in `buildTabView` (`src/tab/view.ts:32`), a creator, and a client branch in `MountedViewLayers` (`web/src/MountedViewLayers.tsx:62`) rather than in `ViewTabBody`, which renders only the files and notifications bodies and returns `null` for everything else. It is called a multi-agent tab throughout: view `'multiagent'`, payload `multiagent`, manager `MultiAgentManager`, modules under `src/multiagent/`, client feature directory `web/src/multiagent/`.

**The creator follows `addEditorTab`, and the harness tab's own creator is the odd one out.** `addEditorTab` (`src/tab/creators.ts:33`) is the creator that takes a unique label, a distinct dot color, the creator's group and group color, and hands off to `finalizeTab`, and it is the one to copy. The harness tab's creator, `makeHarnessTab` (`src/tab/index.ts:40`), lives in the tab module's index instead and takes a pre-built `HarnessView`, so it is the precedent for the view's shape and not for its creation.

**The tab is called `multi-agent` in the strip, and the command that opens it is `fanout`.** The command is the verb and the tab is the noun, so they are allowed to differ, and they do here: `multi-agent`, `multi-agent-2` in the strip, titled with the prompt cut to the tab-name limit so a user with three open comparisons can tell them apart. The view discriminant is `'multiagent'`, the payload `multiagent`, the manager `MultiAgentManager`, the modules `src/multiagent/`, and the client feature directory `web/src/multiagent/`.

**A member is one opencode model, and the member list is the leading tokens that name one.** `resolveAcpModel` already reads the opencode list out of the same `harness-models.json` catalog a harness tab validates `--model` against (`modelsFor`, `src/harness/models.ts:43`), so a member is written `opencode:google/gemini-3.1-flash-lite` and validated against that list. The `opencode:` prefix is kept even though only one harness qualifies, for two reasons: it says which agent runs, and it keeps the member list recognizable as a list when a model name is wrong. A delimiter of "any leading token naming a catalog model" would fold a typo into the prompt and run a zero-member comparison instead of reporting the model that was not found.

**Only opencode can be a member, because that is the only ACP this feature uses.** `acpLaunchFor` (`src/acp/launch.ts:11`) can also drive claude, and codex is in the model catalog, but a member is an opencode model and the plan builds nothing for the other two. The `opencode:` prefix means a second harness is a widening of the grammar and the catalog rather than a change to it. The model travels as `OPENCODE_CONFIG_CONTENT` in the spawned process's environment rather than as an argument, so N members on N models are N processes with N environments and there is no shared-process contention to design around.

**A member works in its own clone, and that is the only reason the clone is worth its cost.** A Janissary ACP agent is not a coding agent: `decidePermission` cancels every tool request unless an allowlist names it (`src/acp/tools.ts`), so an agent tab's ACP agent is given the browser, question and database tools by Janissary's own tool table and has the agent's own tools denied. A member that inherited that would answer in prose and never touch its workspace, which would make N concurrent clones N concurrent copies of a repository nobody writes to. So a member's connection is the one ACP path that also approves the agent's own tool calls, and the confinement is what makes that safe to do: each member's process is Seatbelt-confined to its own disposable clone (`sandboxSpawn`, `src/sandbox/index.ts`), denied every secret path, and deniable of the network by the same `--offline` a workspaced tab already honors. The grant is a new mode in `decidePermission` plus a new opt-in field on `AcpOptions`, both reachable only from this path, and it is pinned by tests — including one that a member tab's approval does not leak into an ordinary agent tab, and one that a member's process is in fact confined to its own directory.

**That confinement is asked about rather than assumed, because it is conditional and the grant is not.** `sandboxSpawn` returns its command and arguments unchanged when there is no `workspaceDir`, when the `sandboxWorkspaces` toggle is off, and when `sandbox-exec` is not on the host — which on any non-macOS machine is every spawn. An ordinary workspaced tab has the same absent sandbox and no approved tools, so it can do nothing either way; this would be the first path where "no sandbox" stops being harmless. So the grant is decided from the same test `sandboxSpawn` applies internally, read through `sandboxNotice` — the helper a workspaced tab's own transcript already carries for exactly this — and a member that would not be confined is marked `failed` with that reason instead of being connected. Refusing rather than degrading is the point: a member exists to work in a disposable clone under a boundary, and a row saying why it did not run is a better outcome than an unrestricted agent pointed at the user's own checkout.

**The members' connections are keyed per member inside the tab, not per tab label.** `AcpManager` keys its sessions by tab label and holds exactly one per tab (`src/acp/manager.ts:59`, `:88`), so it cannot host eight; it stays as it is, and a multi-agent tab's eight sessions live in the new manager. `EditorAcpManager` is the shape to copy: a composite key of the tab label and a discriminator (`src/editor/acp-manager.ts:11`), a `closeTab` that prefix-scans and kills them all, and — the part that matters most — an identity guard in the death path so a dead predecessor cannot drop its successor (`src/editor/acp-manager.ts:56`).

**Each member's workspace is its own clone, and the tab's own `workspaceDir` stays empty.** `Tab.workspaceDir` is a single scalar (`src/tab/types.ts`) and the close walk releases exactly one through it (`src/tab/cleanup.ts`), so eight clones cannot live there. They live in the new manager, and it releases them from its own `closeTab(label)`, which the walk already calls for every manager named in `MANAGER_TAB_RELEASE` (`src/managers.ts`). `WorkspaceManager` itself has no such limit: `create(name)` returns `{ dir, ready }` synchronously and refcounts by `dir` (`src/workspace/manager.ts`), so N distinct names give N clones under one tab.

**A member's workspace name carries its index, so the names are distinct by construction rather than in practice.** They must be distinct because `pending` and `cancel(name)` are keyed by name, and each is `<tab label>-<model with / replaced by ->-<member index>`: a model-derived part so the folder is readable, a label part so two runs cannot collide on it, and the index because folding `/` to `-` is not injective. A project overriding `.janissary/harness-models.json` can carry both `a/b` and `a-b`, which would otherwise derive one name for two members — and because `WorkspaceManager` keys its `refs` and `pending` maps by name, the second `create` would overwrite the first's entries, leaving two members handed one clone to write into concurrently, one member's cancel reaching the other's clone, and whichever settled first deleting the other's pending entry. The bundled catalog cannot collide, which is exactly why relying on that was not good enough. `workspaceLabelError` (`src/workspace/label.ts`) validates the result before `create` is called rather than after a clone it would never have made.

**Each member's clone is also that member's sandbox boundary, and that is the one place today's wiring has to change.** `AcpManager.session` takes `cwd` as a parameter but reads `workspaceDir` and `offline` off the tab, which is right for one session per tab and wrong for eight in one tab: a session pointed at a clone it is not confined to would look workspaced and not be. The new registry passes `cwd` and `workspaceDir` per member, exactly as `ConversationSessions.session` already does. The directory is bound once, after the confinement check has established it, and used for both — so the value the sandbox confines and the value the process starts in are the same value by construction, with no assertion standing in for a fact the compiler cannot check on the one security-sensitive line in the feature. Nothing below that needs to change: `sandboxSpawn` is a pure function of `(workspaceDir, offline, tokens, command, args, env)` and every other input it consults is a process-level constant, so eight concurrent invocations are safe. Token injection follows `workspaceDir` rather than the tab, so every member of a confined run is authenticated, which is what a confined agent tab is today.

**A member is prompted as soon as its clone is ready, and the clone readiness is the only gate.** `WorkspaceManager.create` hands back a `ready` promise before the clone has run, so the manager prompts each member in that promise's continuation. An ACP session needs no other waiting: `connectAcp`'s `prompt` already awaits its own handshake internally (`src/acp/index.ts:97-110`), so the scheduler hack a harness launch needs — a one-shot run entry retried every tick until the tab is running — has no role here and is not used.

**The answer is the final text, not the stream.** `PromptHandlers` gives `onChunk`, `onEnd` and `onError`, and the fanout ignores `onChunk` for rendering: chunks accumulate into a closure variable and touch neither the member nor the bus. The reason is the wire — `emitState` broadcasts the entire view on essentially every mutation, and an ACP chunk is one mutation, so eight streaming members would each multiply whole-state broadcasts and each would carry eight partial answers. A member row shows its state while it works and its answer when it finishes, which is what "lining the answers up to compare" asks for. This is a deliberate ceiling, not an oversight: if live progress is wanted later, it is the 100 ms trailing coalesce `ConversationResponder` already uses, added the same way.

**A settled member is announced, because a payload nobody is told about is a payload no client receives.** Each terminal transition — `onEnd`, `onError`, and a connection-level death — emits a state change after writing the member, the way `EditorAcpManager` emits after mutating the same kind of state. The single-shot write is what makes this cheap: a member is written once, so a run of eight produces eight broadcasts rather than one per chunk. The member's transition to `running` needs no emit of its own, because the caller announces it when the clone lands.

**Closing the tab is the entire teardown, so there is no cancel command.** A multi-agent tab holds nothing durable: its clones are disposable, its answers are its payload, and its connections die with it. The ordinary close walk kills the sessions and releases the clones, and that is precisely what a cancel would have done. So the feature is one command, `fanout`, rather than a start form, a cancel form and a separate way to reopen the comparison.

**The tab joins the group of the tab it was created from** rather than allocating a new one, which is the inheritance rule an agent tab already follows (`src/profile/place-agent.ts:30`). One tab needs no band of its own, so `product/specs/tabs.md`'s grouping text needs no change and the contiguity invariant is untouched.

**The tab's label is `multi-agent`, suffixed by the existing unique-label machinery**, and its display title is the prompt truncated to the tab-name limit — `title` is the field for a display name that differs from the label (`src/tab/types.ts:259`).

**A row shows its state and nothing else while the member works.** The states are `cloning`, `running`, `answered` and `failed`, and there is no `waiting` and no `closed`: a member is asked the instant its clone is ready, and a member whose session dies is `failed` with the reason, because a connection that has gone cannot be revived within the run. A member that is still working shows its state word and no text, which is what keeps the payload small; the answer appears whole, when it lands.

**The payload carries the prompt and the members; the clone directories stay on the server, and the clone count is derived rather than stored.** `buildTabView` deliberately does not spread `editorDraft`, `pageSnapshot` or `sessionTerminated` for exactly this reason, and the multi-agent payload follows the same rule: a path the client has no business holding is not in it. Each member is projected field by field rather than spread, so a field added to the server record cannot quietly start broadcasting itself. The number of clones still in flight is not on the payload at all — it is counted at projection time from the member states the projection is already reading. Storing it would have been a second answer to the same question that could disagree with the first, and did: a count written when the tab opened froze there, so a finished run reported its clones as still cloning for the life of the tab.

**N is bounded at 1 to 8.** Each member is a real `git clone` of the repository's `origin`, so the count is a disk and time cost as much as a comparison width. A count outside the range is refused with a usage error before any clone is started.

**One bad member does not sink the run.** A member naming a harness ACP has no adapter for, a model that harness's catalog does not carry, or a member repeated, is skipped and the rest of the run proceeds. Its row reads `failed` with the reason, because a comparison of eight where one model has been retired is still worth reading. A run whose every member was refused opens no tab and reports why.

**Remote members are out of scope for this version.** The remote ACP path is one session per remote tab by construction — `createRemoteAcpSession` is keyed by an id the local side mints once per tab (`src/acp/manager.ts:99`), and the far side's holder says so in as many words: "Each tab still gets exactly one, which is the limit the local side enforces" (`src/remote/serve-acp.ts:11`). Putting N members on a far host means changing both sides of that limit, and one workspace per remote tab, which is separate work on a feature that is already the width it is.

**`fanout` behaves the same on every path that dispatches a command.** `product/specs/command-routing.md` requires every built-in to resolve identically whether typed into a tab, sent to another agent as a `command` message, or asked of it as a `request`, and `resolveCommand` (`src/resolve.ts:29`) gives that for free. A run started by another tab's `request` therefore really does provision its workspaces, exactly as `close` really does close another tab, and the run's summary and skipped members come back as the captured reply. Refusing it from a message would contradict the spec, so it is not refused.

## Proposed changes

Described as contracts and module names, in prose. The decisions those contracts implement are all settled above.

**`src/commands/fanout.ts`** — the command's one definition, added to `coreCommands` in `src/commands/index.ts:41`. It matches `/^fanout\b/i`, declares samples so the registry priority test covers it, appends its own usage errors to the issuing tab's transcript the way `send` and `broadcast` do, and delegates to `managers.multiAgent`. It opens no tab itself.

**`src/fanout/parse.ts`** — pure. Turns the command line into a run request: the member list and the prompt, or a usage error. It reads the member list as every leading token of the form `word:rest` whose `word` names a harness from `HARNESS_NAMES`, requires that harness to be `opencode`, and takes the whole rest of the line as the prompt. It enforces the 1-to-8 bound, requires at least one member, requires a prompt, and reports `Usage: fanout opencode:<model>... <prompt>` verbatim. No I/O, no state. A leading token naming a harness other than `opencode` is a usage error rather than the start of the prompt, because the user plainly meant it as a member.

**A leading token whose prefix names no harness begins the prompt**, which is the one place this grammar departs from the shape rule above, and it is settled here as an autonomous decision. Shape alone would swallow a prompt that opens with a colon — `fanout opencode:a fix: the flaky logout test` would read `fix:` as a member naming an unknown harness and refuse the run. Keying the member test on `HARNESS_NAMES` keeps that prompt deliverable and loses nothing: the only tokens it stops treating as members are ones naming no harness, and those are exactly the tokens the plan's own rationale protects. So `fanout opencode:a fix: the bug` prompts every member with `fix: the bug`, and `fanout claude:m go` is still refused by name.

**`src/multiagent/types.ts`** — the server-side member record `MultiAgentMember`: its index, its model, its clone directory, its state, its error, and its answer once there is one. Plus `MultiAgentMemberState` and the server-side payload `MultiAgentRun`, which holds the prompt and the members and nothing else — the number of clones in flight is counted from their states at projection time rather than stored beside them, which is the only way that number cannot disagree with the states it summarizes.

**`src/multiagent/workspaces.ts`** — provisions the N clones through `managers.workspace.create`, one distinct name per member, and releases them. `memberWorkspaceName` derives the name as `<tab label>-<model with / replaced by ->-<member index>`, so a model-derived part keeps the folder readable, a label part keeps two runs from colliding, and the index makes the names distinct by construction rather than in practice — folding `/` to `-` is not injective, and a project overriding the model catalog can otherwise put two members in one clone. `workspaceLabelError` then refuses a name that could never be one folder, before `create` is called rather than after a clone it would never have made. A member already refused when the list was resolved against the catalog is skipped outright — that refusal is authoritative, and provisioning it anyway would clone and prompt a model that does not exist. Otherwise it awaits each `ready`, reporting a failed clone as that member's `failed` with the reason rather than ending the run and announcing that it gave up, since the two refusals above it are covered by the caller's own emit but this one lands long after it. It defers the release to a macrotask exactly as the tab-close walk does, because a recursive removal of a full clone is slow enough to freeze the UI.

**`src/multiagent/sessions.ts`** — `MultiAgentSessions`, the member connection registry: sessions keyed by `${label}:${member index}`, the composite key copied from `EditorAcpManager`, with a `closeTab` that prefix-scans. It creates each session through `connectAcp` with that member's own `cwd` and its own `workspaceDir` — bound once from the same value, so the directory the sandbox confines and the directory the process starts in cannot come apart — its model in `OPENCODE_CONFIG_CONTENT`, and the own-tools opt-in, then prompts it. The opt-in is asked for only once the spawn is known to be confined: `sandboxNotice` is the same helper, applying the same test, that `sandboxSpawn` applies internally, and a member that would not be confined is marked `failed` with that reason and given no session at all. It is where the identity guard lives — a death handler that checks the session it is closing is still the one registered for that member before dropping it — because that is the discipline `EditorAcpManager` uses and the one that keeps a dead predecessor from taking its successor with it.

It holds the `AcpSession` and not the `AcpInfo` a session's handshake reports, because the member's model is already the one the run resolved and nothing reads the reported pair: there is no connection-panel row for a member, so a stored `AcpInfo` would be a field with no reader.

**Chunks accumulate into a local, never onto the member.** That is what "the fanout ignores `onChunk`" means in practice: `onChunk` appends to a closure variable and touches neither the member nor the view, so a streaming turn still broadcasts nothing, and `onEnd` writes the finished answer and the state exactly once. `onError` writes `failed` with the reason and leaves the session alone, because a prompt that failed is not a connection that died.

**`src/acp/tools.ts` and `src/acp/types.ts`** — a second decision mode beside `decidePermission`'s web-tool allowlist, answering an agent's own tool call with `allow_always` in preference to `allow_once` so a multi-step task is not stopped at every step, gated by a new `ownTools?: boolean` field on `AcpOptions` that no existing caller sets. `connectAcp` passes it to the decision, and nothing else about the connection changes. The web-tool allowlist is untouched, so a monitor and a persona are unaffected. The grant is asked for only once the member's spawn is known to be confined — because the decision mode is what makes confinement load-bearing rather than merely tidy — which is the condition the `src/multiagent/sessions.ts` entry above describes.

**`src/multiagent/manager.ts`** — `MultiAgentManager`, added to `ManagerRegistry`, `createManagers` and both `MANAGER_DISPOSE_ORDER` and `MANAGER_TAB_RELEASE` (ahead of `workspace` in the dispose order, because it releases clones through it). It resolves the members against the catalog, opens the comparison tab, provisions the clones, prompts each member as its own clone lands, and holds the answers. Its `run` returns what happened — the new tab, how many members are running, and the refusal reasons — which is what the command's transcript line is built from and what `capture` answers a `request` with. The running count is taken **after** provisioning, not before: a clone that could not start fails its member there, and a summary that counted it as running would report a run that is not happening. It declares `closeTab(label)` to kill every member session and release every member clone, and `dispose()` for the same sweep at shutdown.

**`src/tab/types.ts`** — the `view` discriminant gains `'multiagent'`, and the record gains a `multiagent?: MultiAgentRun` payload. The payload is present only when `view === 'multiagent'`, stated in the record's own prose the way the other five are.

**`src/tab/index.ts`** — `makeMultiAgentTab`, beside the other `make*Tab` builders the creator calls: the tab is titled with the prompt and carries the run, its own `workspaceDir` stays empty because the N clones live in the manager, and it carries the issuing tab's `offline`.

**`src/tab/view-guards.ts`** — `isMultiAgentTab`, in the same shape as the four beside it, so no consumer recovers the payload with a non-null assertion.

**`src/tab/creators.ts`** and **`src/tab/unique-labels.ts`** — `addMultiAgentTab`, following `addEditorTab` rather than the harness tab's own `makeHarnessTab`, which lives in `src/tab/index.ts:40`: `uniqueMultiAgentLabel` for the label (`multi-agent`, `multi-agent-2`, …), a distinct dot color, the creator's group and group color, and `finalizeTab`'s insertion and focus. `finalizeTab` titles the tab with the prompt, and the client truncates that for the strip through the `tabNameMaxLength` it already applies to every `title` — so the server keeps the whole prompt and no new truncation rule is needed.

**`src/tab/openers.ts`** — `openMultiAgentTab`, beside `openFilesTab`, returning the new tab's label: the key the run's clones and connections are held under and what `close` addresses.

**`src/tab/view.ts`** — project the payload into `TabView`, carrying the prompt and the members and **not** the clone directories. Each member is projected field by field rather than spread, beside the comment already there for the other server-only fields, so adding a field to the server record cannot quietly start broadcasting it. The clone-in-flight count is counted here, from the members being projected, rather than read off the payload.

**`src/protocol/tab.ts`** and **`src/protocol.ts`** — the wire type `MultiAgentView` beside the other view payloads, its member type `MultiAgentMemberView` beside it, and both re-exported through the barrel the client imports as `@shared/protocol`. The server and wire payloads are named apart for the same reason `RemoteTarget` and `RemoteTargetView` are: only one of the two is ever put on the wire.

**`web/src/shared/tab/view-guards.ts`** — `isMultiAgentTabView`, the wire-side narrowing guard `MountedViewLayers` selects on, beside `isHarnessTabView` and the rest.

**`web/src/multiagent/`** — the client feature directory, flat, as a feature this size should be: `format.ts` (pure — the word for a state, whether a row has a result, and the one-line run summary), `useMemberAnswers.ts`, `MemberRow.tsx`, and `MultiAgentTab.tsx`. The hook earns its name: each answer is rendered through the transcript's own `renderMarkdown` and parsed **once**, when it first lands, cached against the exact text it came from — the mounted layers re-render on every state broadcast, and re-parsing eight answers on each would be the cost the wire-side decision above was made to avoid. `MemberRow` renders a model, a state word, and then either the answer as markdown or the reason there is none. **`MountedViewLayers.tsx`** gains the branch beside the harness, editor and plugin ones — not `ViewTabBody`, which renders only the files and notifications bodies — so a tab holding N live connections stays mounted across tab switches, and `indexedTabs(tabs, isMultiAgentTabView)` gives it the same shape the other branches have.

**`src/completion/`** — `completeFanoutMember` in `handlers.ts`, added to the chain in `index.ts` beside `completeHarnessModel`, completing `opencode:` from `modelsFor('opencode')` so a model id is never typed from memory, plus its precedence-ordered rule in `product/specs/tab-completion.md`. It fires only on a token that already names the harness, so a bare `fanout` is still the start of a prompt and still falls through to the filesystem rule, and a prompt word beginning with `opencode` is not hijacked into a member. The new rule is numbered between the existing harness-model rule and the filesystem-path rule, so the filesystem rule is renumbered to follow it.

**`help.md`** — a row for `fanout` in the command table.

## Tests

Following the conventions of the areas touched, colocated as `*.test.ts` / `*.test.tsx`:

- **The parser**, as pure functions: a well-formed run, a missing prompt, an empty member list, a count outside 1 to 8, a member whose harness is not `opencode`, a prompt opening with a colon, and the exact usage wording.
- **Member resolution**: a known model, a model the catalog does not carry, a repeated model, a run whose every member was refused opening no tab, and the workspace name derivation — a slashed model, an unslashed one, two labels, two members of one run, and a slashed model against an unslashed one that must not collide — plus that a member refused at resolution is never cloned and never prompted.
- **Provisioning**: N clones under one tab with N distinct names, one member's clone failing without ending the run, a name that cannot be one folder refused before `create`, and every clone released when the tab closes, including one still in flight.
- **Session creation**: each member's session is spawned with that member's own cwd and `workspaceDir`, its model in `OPENCODE_CONFIG_CONTENT`, and the own-tools opt-in set; the two are the same value; the `offline` flag carried through; and an ordinary agent tab's spawn setting none of them, which the unchanged behaviour of every other `connectAcp` caller already covers.
- **The confinement gate**: a member on a host reporting isolation available is spawned with the opt-in; a member on one reporting it unavailable is not spawned at all, reads `failed` with the isolation reason, and announces it; and a member with no workspace of its own is refused by name.
- **The tool decision**: a member's own tool call is approved, preferring `allow_always` over `allow_once` and falling back to `allow_once`; an ordinary agent tab's own tool call is still cancelled; the web-tool allowlist behaves exactly as before for a monitor and for a member; and a member whose session has no opt-in still denies.
- **Prompt delivery**: a member is prompted once, and only once its clone is ready; a clone that fails is never prompted.
- **Answers**: `onEnd` sets the answer and the state, `onError` sets `failed` with the reason, and `onChunk` changes nothing on the member — and emits nothing, since the write is single-shot.
- **The announcement**: each of `onEnd`, `onError` and a connection-level death emits a state change, and a chunk and a superseded session's death emit none.
- **The identity guard**: a member whose session dies is marked failed and dropped, and a later session for the same member is not dropped by the earlier one's death.
- **Close and dispose**: closing the tab kills every member session and releases every clone, and leaves another tab's run alone; a sweep at shutdown does the same for what is left.
- **The payload guard** and the view projection, including that no clone directory reaches `TabView`, that no other view carries the payload at all, and that the clone-in-flight count is counted from the members' current states rather than read from a stored value.
- **The creator and its label**: the tab joins the creator's group, is titled with the prompt, leaves its own `workspaceDir` empty, and a second run is labelled `multi-agent-2`.
- **The command**: the run reported into the issuing tab's transcript, a usage error reported there instead, and the summary answered back for a run asked of it as a `request`.
- **The client**: rows render, states read as words, an answer renders as markdown, and a member with no answer renders its state alone; `MountedViewLayers` selects a multi-agent tab by its wire guard and keeps it mounted and hidden across a tab switch, the way it already does for the harness, editor and plugin bodies.
- **Completion**: `opencode:` completes a model from the catalog, a second member completes beside the first, and a bare `fanout` still falls through to the filesystem rule.
- The existing registry priority test in `src/commands.test.ts` covers the new command once it declares samples.

## Out of scope

- **Judging, scoring or ranking the answers.** The tab lines answers up for a person to read. It does not pick a winner, score them, or diff two answers against each other.
- **Diffing or merging what the members changed.** That is a separate declined backlog item, and this feature reports answers, not changes to a repository.
- **Sending a second prompt into a tab that already has one.** A run is one command, one prompt, one set of members.
- **A cancel command.** Closing the tab is the teardown.
- **Harnesses other than opencode.** claude has an ACP adapter and codex has none, but a member is an opencode model and the plan builds nothing for the others.
- **Remote members.** Putting N connections on a far host means changing the one-session-per-remote-tab limit on both sides of the channel.
- **Live streaming of a member's answer as it is produced.** A row shows its state and nothing else while the member works; the upgrade path is the existing 100 ms coalesce.
- **Widen what an ordinary `agent` tab's ACP agent may do.** The new tool approval is opt-in per connection and no existing caller sets it.
- **Restoring a run on relaunch.** Like a harness tab, a multi-agent tab is in-memory only.

### Declined at gap review

Six gaps were researched against Cursor's `/best-of-n` and Agents Window, amux, agi-cli, Superset and Cline, and the user declined all six. They are recorded here so that no later phase proposes them again for this feature.

- **A per-workspace setup command run in each member's clone before it is prompted.** Cursor runs a project-supplied setup list as each worktree is created — `.cursor/worktrees.json`, whose `setup-worktree` key takes shell commands or a script path, with `npm ci`, copying `.env` and running migrations as its own examples (cursor.com/docs/configuration/worktrees). `WorkspaceManager.create` (`src/workspace/manager.ts:30`) clones and does nothing else, and no install step exists anywhere under `src/workspace/`, so a member's clone holds no dependencies. The consequence is recorded rather than fixed: a member asked to run the project's tests cannot, and its answer is reasoning about code rather than evidence from running it.
- **Keeping the member you picked.** Cursor keeps each run's checkout after the agent finishes — "you can keep working in the worktree, create a commit or PR from that checkout, or bring the result back into your main workspace" — with `/apply-worktree` and `/delete-worktree` beside `/worktree`; Orca "compare, annotate, and merge the best result". Nothing here carries a winner forward: the payload holds answers, the clones are released when the tab closes, and the tab's teardown kills the sessions.
- **Per-member elapsed time, and per-member token spend.** agi-cli's session list puts cost and duration beside each session; amux's dashboard shows a live status dot, the last output snippet and current token spend per session, on the reasoning that "if one session is consuming 5x the tokens of others, it's either working on a legitimately harder task or it's stuck in a loop". The member record carries no timestamps. Token spend is not merely absent from the payload but absent from the application: Janissary records no ACP usage anywhere, so pricing a member is a separate feature and not a row on this one.
- **A concurrency cap that queues the members beyond it.** Cline states the need plainly: "This can overwhelm system resources and API rate limits… a concurrency limit of 5, so only 5 agents execute at a time, with the remaining tasks queued until a slot opens up" (cline/cline discussion #10049). Cursor likewise exposes a setting for how many agents run at once. The 1-to-8 bound is the only limit here, and all N clones and N sessions are provisioned at once.
- **A different prompt per member.** Cursor documents `/best-of-n` for "Try multiple approaches for a hard change", and its best-of-n skill launches one runner per approach with that approach's own prompt. The grammar here varies only the model, so the member list and the prompt are two independent lists with no way to pair them.
- **`git worktree` member workspaces instead of independent clones.** Every product compared isolates with a worktree — Cursor creates "a separate checkout for that agent", Superset runs agents "each in its own git worktree" — while `WorkspaceManager` makes an independent `git clone`, so N members cost N copies of the object store and N clone times. Declined because it changes shared workspace machinery, and because a member whose agent now holds its own write tools would work in a checkout sharing `.git` with every other member, which weakens the isolation the tool approval rests on.
