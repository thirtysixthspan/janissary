# Web search 5: the provider catalog, the guarded registry, the v1 fixture, and the provider reference page

**Complexity: 6/10** — ~150 added lines, 20 requirements, 22 test scenarios, no existing source files edited (p=6.04)

The fifth slice of the `web search` feature (source plan: `./product/plans/complete/web-search.md`). It turns the bundled providers into plugins behind a static catalog and a registry that reads manifests only: it resolves which providers a search should try, checks each manifest's API version before importing anything, activates a provider module on first use, guards every call across the boundary, and disables a provider for the rest of the process when it fails as a plugin. A frozen `fixture-v1` provider and its compatibility test pin API version 1, and a developer reference page documents the contract for plugin authors. The search core (`./product/plans/complete/web-search-6-search-core.md`) drives this registry.

## Design decisions

Carried verbatim from the source plan where they apply.

- **Where providers come from (user decision).** Bundled only, as with tab plugins and editor plugins: providers ship in the Janissary build and are listed in one static catalog. Adding a backend is a new provider module plus one catalog entry, with no edit to the core pipeline, the command, or the ACP code. There is no filesystem discovery, npm loading, or third-party installation. Providers are trusted code.
- **Plugin shape (user decision).** `providers/catalog.ts` lists one static manifest per bundled provider — its id (the name `--provider` and every message use), the provider API version it was written against, the `PROJECT_TOKENS` name it uses, and an `activate` function that dynamically imports its module. The registry reads manifests only, which is all that `--provider` validation, the unknown-provider line, completion, the no-provider lines, and the API version check need; a provider whose manifest names a different API version is refused without importing anything, and a compatible module is imported the first time a search uses it and reused afterwards (Node's module cache, no cache of our own). Every call across the boundary is guarded. A `fixture-v1` provider and a compatibility test freeze API version 1.
- **Catalog order.** `[tavilyManifest, tinyfishManifest]`; `activate` is `() => import('./tavily.js')` and so on.
- **Provider auto-selection (user decision).** `--provider auto`, the default, walks the registered providers in registry order (Tavily, then TinyFish, then any later-registered plugin), skipping any without a token file.
- **Provider names (user decision).** `--provider` names match case-insensitively, and `auto` is reserved for auto-selection. An unknown name prints `Web search: unknown provider "<name>" (available: auto, tavily, tinyfish).`, listing `auto` and then every registered provider in registry order, and sends nothing. The unknown name is echoed as typed.
- **No provider configured (user decision).** With no token file for any provider, an auto search prints `Web search: no provider configured.`; an explicit `--provider <name>` whose token file is missing prints `Web search: provider "<name>" is not configured.`. Nothing is sent.
- **Plugin failure (user decision).** When a provider module fails to import, requires a different provider API version, or its `search` throws anything other than a normal HTTP, timeout, network, or decoding failure, that attempt fails with reason `provider failed: <first line of the error>` (or `requires provider API <n>` for a version mismatch), so an auto search falls back as usual. The provider is then disabled for the rest of that server process: auto skips it, an explicit `--provider <name>` prints `Web search failed (<name>): <reason>.` without sending anything, and one notification, `Web search provider "<name>" disabled: <reason>.`, appears in the notifications tab, as editor plugin failures do. A disabled provider stays disabled until the server restarts; there is no re-enable command, since a bundled provider only breaks with a bad build.
- **Who shows the notification.** The registry calls the caller's `reportDisabled(name, reason)` exactly once per disabled provider; the caller decides how to show it. The local typed path posts the notification (`./product/plans/ready/web-search-10-typed-command.md`). On a remote machine no `reportDisabled` is passed, so the reason appears only in failure lines, since the far side has no notifications tab.
- **Registry ownership.** `registry.ts` exports `createProviderRegistry(manifests)`, which returns an object that owns the disabled set (and each disabled provider's reason), so a test builds its own registry over a fixture catalog instead of resetting shared state. Creating it does no I/O and imports no provider.
- **Registry methods.** `providerNames()` (manifest ids, catalog order); `resolveAttempts(name, tokens)` returning the ordered providers to try (one for an explicit name, every configured, non-disabled provider for `auto`) or the unknown-provider, not-configured, disabled-provider failure, or no-provider line; `runAttempt(manifest, request, capability, reportDisabled?)` which checks the manifest's `apiVersion` against `WEB_SEARCH_PROVIDER_API_VERSION` first (a mismatch is a plugin failure with reason `requires provider API <n>`, and nothing is imported), then activates the module, calls `search` inside a guard, and classifies the outcome as results, an expected failure (a `ProviderRequestError`), an abort, or a plugin failure. A plugin failure adds the manifest id to the disabled set and calls the caller's `reportDisabled(name, reason)` once.
- **What `<n>` is.** In `requires provider API <n>`, `<n>` is the version the manifest names.
- **Provider capability (from `ai/guidelines/plugins.md` §1).** `runAttempt` hands the provider only the request and the capability (`apiKey`, `fetch`, `signal`).
- **Versioned, documented plugin API (feature text, `ai/guidelines/plugins.md`).** The provider plugin contract carries its own API version, a static declaration, a fixture plugin, a failure test, and a reference page for plugin authors.
- **Barrel rule.** `src/web-search/fixture-v1/` does not re-export anything; only the three files named in `ai/guidelines/imports-and-barrel-files.md` may, and none of them is touched. The lint rule enforcing this is the `ignores: ['src/protocol.ts', 'src/plugins/api.ts', 'src/plugins/fixture-v1/activate.ts']` block in `eslint.config.mjs`; no `export … from` anywhere in this slice.

Decisions this pass adds, grounded in the repo:

- **Where `reportDisabled` goes (decision).** The registry is process-wide (held in `search.ts` by slice 6) while `reportDisabled` differs per caller (local typed path vs. far side), so it is a per-call argument: `runAttempt(manifest, request, capability, reportDisabled?)`. It is optional; when absent, disabling still happens and nothing is reported.
- **Resolution result (decision).** `resolveAttempts` returns a discriminated union: `{ kind: 'attempts', manifests }` (non-empty, in catalog order) or `{ kind: 'line', line }` with the full text to print. `providerNames()` returns a fresh `string[]`.
- **Name matching (decision).** The requested name is compared with `toLowerCase()` against `auto` and against each manifest id; manifest ids are lowercase. `AUTO` and `Auto` mean auto. Lines about a known provider print its manifest id (`--provider Tavily` → `provider "tavily" is not configured.`); only the unknown-provider line echoes the name as typed.
- **Configured (decision).** A provider is configured when `tokens[manifest.token]` is a non-empty string. The loader in `src/project/tokens.ts` already drops whitespace-only files, so no trimming here.
- **Explicit-name check order (decision).** Unknown → disabled → not configured. A disabled provider returns `Web search failed (<id>): <stored reason>.` whether or not its token is present, because the disabled state is a property of the build, not of the token.
- **Auto when every configured provider is disabled (decision).** The source plan does not say; printing `no provider configured` would be false. Auto with at least one configured provider, all of them disabled, returns the failure lines as if each had just been tried with its stored reason: one provider gives `Web search failed (<id>): <reason>.`; two or more give `Web search: every provider failed.` followed by one `- <id>: <reason>` line each, in catalog order. `Web search: no provider configured.` is reserved for no configured provider at all. The line shapes are slice 6's failure lines; this slice adds the one formatter both use (see Proposed changes) so the two cannot drift.
- **Abort (decision, from slice 4).** When `activate` or `search` rejects (or throws synchronously) and `capability.signal?.aborted` is true, the outcome is an abort carrying the original error unchanged, whatever that error is; it never disables and never reports. The abort check runs before every other classification. A `search` that resolves is results even if the signal fired meanwhile; the core decides what to do with a late answer.
- **Expected failure.** A rejection that is `instanceof ProviderRequestError` (`src/web-search/contract.ts`, slice 2) is an expected failure whose reason is its `message`, unchanged. It never disables.
- **Plugin failure text (decision).** Every other throw from `activate` or `search` gives reason `provider failed: ${errorFirstLine(error)}`, using `errorFirstLine` from `src/error-text.ts` — the helper both plugin hosts disable on (`src/plugins/host.ts` `record.reason = errorFirstLine(error)`, `src/plugins/failure.ts` `pluginFailureMessage`), which strips trailing sentence punctuation so the reason reads cleanly before the `.` of `Web search failed (<name>): <reason>.` and falls back to `Unknown failure`. Not `firstLine` from `src/models/providers/result.ts`: that one is the HTTP-reason helper slice 4 uses.
- **Guarding the boundary (decision).** Besides throws, two resolved shapes are plugin failures: `activate()` resolving to a module whose `provider.search` is not a function (`provider failed: module has no provider`), and `search` resolving to something that is not an array (`provider failed: search did not return an array`). Entries inside the array are not validated; `normalizeResults` (slice 2) runs on them in the core, and the contract types bind bundled code at typecheck.
- **Disable once (decision).** On a plugin failure, if the id is not yet in the disabled map, record `id → reason` and call `reportDisabled?.(id, reason)`; if it already is (two concurrent searches failing the same provider), keep the first reason and do not call `reportDisabled` again. Either way the attempt's outcome is the plugin failure with this attempt's reason. An attempt already in flight when its provider is disabled is not cancelled.
- **Catalog invariants (decision).** `createProviderRegistry` does not validate its input at runtime (a throw at module load would take the host down). Instead a test asserts the real catalog's ids are unique, lowercase, and never `auto`, and that every manifest's `apiVersion` equals `WEB_SEARCH_PROVIDER_API_VERSION`.
- **Fixture pins the literal version (decision).** `fixtureV1Manifest.apiVersion` is the literal `1`, not `WEB_SEARCH_PROVIDER_API_VERSION`, so bumping the constant makes the compatibility test fail — which is the §11 definition of a breaking change. (The tab-plugin fixture uses its constant; here the literal is the point.)

## Proposed changes

All relative imports carry `.js`. Land in this order so typecheck stays green: `failure-lines.ts`, `registry.ts`, `providers/catalog.ts`, the fixture, then the docs.

- **`src/web-search/failure-lines.ts`** (new, ~10 counted lines) — `formatFailures(failures)` over a non-empty `{ name, reason }[]`: one entry gives `Web search failed (<name>): <reason>.`; two or more give `Web search: every provider failed.` and one `- <name>: <reason>` line each, joined with `\n`. Used here for the disabled lines; slice 6 (`./product/plans/complete/web-search-6-search-core.md`) imports it for its failure lines instead of writing its own.
- **`src/web-search/providers/catalog.ts`** (new) — `tavilyManifest`, `tinyfishManifest` (ids `tavily`, `tinyfish`; `apiVersion: WEB_SEARCH_PROVIDER_API_VERSION`; `token` `'tavily'` / `'tinyfish'`; `activate: () => import('./tavily.js')` / `import('./tinyfish.js')`), and the ordered array `webSearchProviderCatalog = [tavilyManifest, tinyfishManifest]`. Module top level holds data only; the only runtime import is the version constant, and the provider modules are reached only through `import()`. Once this lands, slice 4's provider modules are consumed by a non-test module.
- **`src/web-search/registry.ts`** (new, ~100 counted lines) — `createProviderRegistry(manifests)` with `providerNames`, `resolveAttempts`, and `runAttempt` as decided above; the disabled state is a `Map<string, string>` (id → reason) closed over by the returned object. Exports the types `ProviderRegistry`, `AttemptResolution` (the `resolveAttempts` union), and `AttemptOutcome`, a discriminated union on `kind`: `'results'` (`results: WebSearchResult[]`), `'failed'` (`reason`, expected failure), `'aborted'` (`error`, the original rejection), `'plugin-failed'` (`reason`). Keep `runAttempt` under `sonarjs/cognitive-complexity` by giving the throw classification its own unexported function. If the module passes ~170 counted lines, move `runAttempt`'s guard and classification into `src/web-search/attempt.ts` and import it.
- **`src/web-search/fixture-v1/provider.ts`** (new) — exports `provider`: its `search` calls `capability.fetch` exactly once (URL `https://fixture-v1.invalid/search?q=<query>` built with `URL`/`searchParams`, header `Authorization: Bearer <apiKey>`, `signal: capability.signal`), does not read the response, and resolves to a fixed two-entry `WebSearchResult[]` whose first title echoes the request's `query`. Imports only `import type` from `../contract.js`. Frozen: a change that breaks it is a major API bump by definition.
- **`src/web-search/fixture-v1/manifest.ts`** (new) — `fixtureV1Manifest`: id `fixture-v1`, literal `apiVersion: 1`, token `'tavily'` (any real `ProjectTokenName`; the test supplies the token), `activate: () => import('./provider.js')`, typed `satisfies WebSearchProviderManifest`. Not in the production catalog.
- **`documentation/developer-documentation/web-search-providers.md`** (new, title "Web search providers") — the provider plugin reference `ai/guidelines/plugins.md` §12 requires, shaped like `editor-plugins.md` (which opens with "Smallest working example", then "Files to add", the reference, "Validation and failure", "Trust and limits"): the simplest working provider first (the fixture's shape, with its manifest and catalog entry), then the contract types, the capability object (`apiKey`, `fetch`, optional `signal`; no token files or host state), resolution and ordering (by name case-insensitively, or first configured in catalog order with `auto`), async semantics (sequential, each awaited; `[]` is an answer), failure classification (`ProviderRequestError` falls back; any other throw, a missing provider export, or a non-array disables until restart with the `provider failed: …` reason; abort never disables) and the notification, the 30-second per-attempt budget from `requestJson`, and API version 1 with the fixture rule. Follow `ai/guidelines/developer-documentation.md`.
- **`documentation/.vitepress/config.mts`** — one sidebar item `{ text: "Web search providers", link: "/developer-documentation/web-search-providers" }` directly after the "Overlay plugins" item.
- **`documentation/developer-documentation/index.md`** — one bullet, `[Web search providers](/developer-documentation/web-search-providers) — writing a search provider plugin`, appended after the "Workspace sandbox" bullet.

## Tests

Vitest `server` project, colocated; no test touches the network. Fake manifests use ids `tavily` and `tinyfish` with `vi.fn()` `activate`s resolving to in-test modules, so call counts prove laziness.

- **`src/web-search/registry.test.ts`** (new), each against a registry built over a test catalog with fake manifests:
  - `providerNames()` returns ids in catalog order.
  - Lazy activation: building the registry and calling `providerNames()` and `resolveAttempts` never calls `activate`; the first `runAttempt` does.
  - `resolveAttempts('auto', tokens)` lists configured providers in catalog order and skips unconfigured ones (a token of `''` counts as absent); with none configured it returns `Web search: no provider configured.`; `AUTO` behaves as `auto`.
  - An explicit name matches case-insensitively (`Tavily`); an unknown name returns `Web search: unknown provider "<name>" (available: auto, tavily, tinyfish).` with the name as typed (`Bing` stays `Bing`); a known but unconfigured one returns `Web search: provider "tinyfish" is not configured.` with the manifest id even when typed `TinyFish`.
  - A manifest version mismatch (`apiVersion: 2`) is refused without calling `activate`, with reason `requires provider API 2`.
  - An import failure (an `activate` that rejects with `new Error('Cannot find module.\nat …')`) and a `search` that throws a plain `Error` each fail the attempt with `provider failed: <first line>` (trailing `.` stripped); a synchronous throw from `search` is classified the same way.
  - A module without a `provider.search` function gives `provider failed: module has no provider`; a `search` resolving to a non-array gives `provider failed: search did not return an array`.
  - Each plugin failure disables the provider: a later auto resolution skips it; a later explicit resolution returns `Web search failed (<id>): <reason>.` even with its token present; `reportDisabled` is called exactly once with `(id, reason)` across repeated failures and keeps the first reason; omitting `reportDisabled` still disables.
  - Auto with both providers configured and both disabled returns `Web search: every provider failed.` with both stored reasons in catalog order; with one configured and disabled it returns `Web search failed (<id>): <reason>.`.
  - A `ProviderRequestError('HTTP 429 Too Many Requests')` is a `'failed'` outcome with that reason and does not disable; a rejection while `capability.signal` is aborted is `'aborted'` with the same error object, even when that error is a `ProviderRequestError` or a plain `Error`, and neither disables nor reports.
  - A successful `search` is `'results'` with the provider's array unchanged, including `[]`.
  - A registry with every provider broken still answers `providerNames()` and `resolveAttempts` (the host keeps running).
  - The real `webSearchProviderCatalog`: ids `['tavily', 'tinyfish']` in order, unique, lowercase, none `auto`; every `apiVersion` equals `WEB_SEARCH_PROVIDER_API_VERSION`; tokens `'tavily'` / `'tinyfish'`. This test reads the manifests only and does not call `activate`.
- **`src/web-search/failure-lines.test.ts`** (new) — one failure gives the single line; two give the header and two `- ` lines in order.
- **`src/web-search/fixture-v1/compatibility.test.ts`** (new) — the frozen v1 fixture's manifest registers in a registry built over `[fixtureV1Manifest]` (`providerNames()` is `['fixture-v1']`, `resolveAttempts('fixture-v1', { tavily: 'k' })` returns it), and a representative `runAttempt` with a fake `fetch` returns `'results'` with the two fixed entries, the query echoed, and the fake `fetch` called once with `Bearer k` and the capability's signal. Fails if the contract version moves off 1.
