# System schedules 12: system grammar and profile schedule isolation

**Complexity: 4/10** — a new discriminated parser branch, system-owner routing, profile isolation, exact command/help/spec/doc wording, and focused integration coverage across existing server seams.

The five schedule forms reuse existing pure time parsing. This change adds a system grammar branch, routes it to plan 11's persisted owner, and keeps profile-authored schedules tab-only.

## Goal

Extend the pure schedule parser with the `system` subspace and migrate all parser consumers without changing tab grammar. Source: `product/plans/ready/add-system-schedules.md`.

## Decisions and dependencies

- Dependencies: completed plans 07 (strict runscript names, file reading and versioned storage) and 11 (persisted owner and boot integration). Plan 06's tab-capture/profile-relaunch isolation is separate from these profile-authored schedule-line rules. Plan 13 owns top-level runscript commands/completion; 14 owns aggregate schedules UI; 15 owns the creation dialog; 16 owns the full browser E2E.
- Add `schedule system NAME <form> script <name>` with all five existing time forms, plus `schedule system list`, `cancel <name>`, and `clear`. `system` immediately after `schedule` always selects this subspace, so it cannot be a tab timer name. `in system` retains its ordinary tab-target meaning.
- Parse results gain a `system` discriminant while existing tab variants retain their current shapes. The system creation parser reuses the existing form parser/time math, then requires exactly the trailing `script <valid-name>` clause; it accepts no bare shell/application command and no `in TAB` clause. Reuse `isRunscriptName` from `src/schedule/system/runscript.ts`; parser validation is pure and must not read files.
- Match grammar keywords case-insensitively, as the existing parser does, but preserve the authored schedule and script names. A valid system schedule name may repeat. System `cancel <name>` removes all matching names; `list` preserves owner order, and `clear` affects only system entries. Use plan 11's owner methods `list`, `add`, `cancelByName`, and `clear`; do not mutate storage or duplicate owner logic in the command.
- Every malformed `schedule system` line returns exactly `Usage: schedule system NAME <form> script <name> | schedule system list | schedule system cancel <name> | schedule system clear`. This includes malformed forms, missing/extra `script` clauses, and trailing arguments. Keep the current tab usage and specific invalid-time/date/interval behavior for tab lines unchanged. `system` immediately after `schedule` is reserved case-insensitively; `in system` remains a tab target.
- `src/commands/schedule.ts` remains the only command definition and routes the parsed system variant to `managers.systemSchedule`. Before `add`, read the named script with plan 07's `readRunscript` against `managers.tab.launchDir` and refuse a missing file with `No runscript named "<name>".`; do not mutate the owner on refusal. If an existing script cannot be safely read, refuse with `Could not read runscript "<name>".` and do not mutate the owner. On a successful add, print `Scheduled <name> system: <spec> (script <script>).`. Use exact management results: `No scheduled command "<name>" in system.`, `No scheduled commands in system.`, and `Cleared <n> scheduled commands in system.` (including zero as the no-schedules message and plural `commands` for one cleared entry). On owner save failure, print `Could not save system schedule.` for add and `Could not save system schedules.` for cancel/clear; never report success. Keep all tab-route behavior unchanged.
- The system subspace is project-scoped, so route it directly through `managers.systemSchedule` from the existing application command dispatcher; do not call `resolveTargetTab` or `canRunSchedules` for it. Preserve those eligibility checks for every tab-owned operation. The invoking tab receives command output as it does for the current `schedule` command.
- A successful `schedule system list` formats entries with existing `formatSchedule` (`<name>  <spec>  (next: <when>)  script <name>`); an empty list instead returns `No scheduled commands in system.`. A successful cancel returns `Cancelled <name> in system.` once at least one matching entry was removed. `clear` returns the decided empty message when there are no entries; otherwise its exact `Cleared <n> scheduled commands in system.` message uses the number removed.
- Extend the existing command completion pipeline for the `schedule system` grammar. Complete `system`, `list`, `cancel`, and `clear` in their valid positions; complete `cancel <name>` from distinct current system schedule names in sorted order; complete `at`, `on`, and `every` form keywords and the `day`/weekday alternatives where they occur; complete `script` names from `catalogRunscripts` only after the `script` clause. Obtain the catalog from the project root and current schedule names from `managers.systemSchedule` through the existing completion controller (`src/controller/completion.ts`); keep normal filesystem completion and tab-target completion intact. Completion must not write state. An absent scripts directory yields no name suggestions; an unsafe/unreadable catalog also yields no script-name suggestions without failing the completion request or falling through to filesystem completion for the script-name slot.
- Profile-authored `schedule` lines remain tab-only. In `buildHarnessSchedule`, report and skip every valid `system` parse result before inspecting its `action`, `target`, `entry`, or `name`; use `Schedule "<raw>" for "<harness>" cannot target system schedules.`. Malformed system lines use the exact parser usage report through the existing parse-error path. Do not allow profile lines to create, list, cancel, or clear project schedules. Preserve duplicate-first behavior, ordinary `run` one-shots, and tab-only recurring harness scope. Profile launch/relaunch remains an in-app operation; application restart neither restores these tab timers nor launches a profile.
