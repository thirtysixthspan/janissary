# Native commands: client intercepts and end-to-end verification

**Complexity: 4/10** — one server-state projection, one narrow report RPC, and several existing intercept and chord call sites must observe the same snapshot without duplicating policy, then be verified across the completed feature.

## Goal

Make client-side command pickers and the keyboard shortcuts that invoke application commands honor the same effective application-wide availability as server dispatch, and verify the full feature across its boundaries. The server remains authoritative; client gating is presentation only.

## Decisions and dependencies

- Depends on completed and published units 1–9: `product/plans/complete/native-commands-01-inventory.md` through `-09-roles.md`. Reuse the canonical inventory, `nativeCommandSettings` snapshot, `command-disabled` event, `commands` topic, Commands tab, and Roles restriction mapping; do not add another inventory, settings reader, notification event, topic, or policy service.
- The wire contract is a projection, not a second policy. Add a required `disabledApplicationCommands` field to `StateEvent` in `src/protocol/events.ts` (re-exported by `src/protocol.ts` and consumed through `@shared/protocol`). It holds only the normalized `name`, `aliases`, and `forms` of rows whose `effectiveEnabled` is false. It carries no saved `enabled`, no `effectiveAgentAccess`, no `nativeTool`, and no `parent`; `NativeCommandSettingsManager.createSnapshot` at `src/native-commands/manager.ts:63` has already folded parent and agent effects into `effectiveEnabled`. Put the shared row type in the import-free `src/shared/application-commands.ts`.
- Build the projection with a pure helper in a new `src/native-commands/state.ts` so `src/state/event.ts:10` `buildStateEvent` stays thin and the projection is testable without a controller. A hand edit of `commands.json` reaches client gating only on the next `refresh` (the Commands tab opener) or edit, matching the service's read points in unit 2; server dispatch still refuses from its own snapshot.
- Re-broadcast state on every successful settings publication. Subscribe `nativeCommandSettings` to the existing `messageBus` `state: dirty` event once in `src/controller/create-managers.ts:50` `createManagers`, after the manager is constructed at `:51`, so both `edit` and `refresh` reach every client through the existing `src/controller/events.ts:11` path. Do not add a bus channel, file watcher, per-client cache, or a second notification path; `dispose` already clears the manager's listeners.
- Client matching is pure and local to the browser. Add `web/src/shared/command-availability.ts` exporting `disabledApplicationCommand(input, rows)`: drop one leading `/`, skip input starting with `!`, normalize by trimming, collapsing whitespace, and lowercasing exactly as `src/application-commands.ts:37` does, then return the canonical row whose `name`, alias, or form is the longest word-boundary match. When two rows match the same longest form, prefer the row whose canonical name equals the matched form, mirroring `canonicalFormMatch` at `src/application-commands.ts:73`, so `question ask` and `question approve` stay on their native rows rather than the builtin `question` row. Do not import `src/application-commands.ts`, `src/native-commands/*`, or a second command table into `web/src`; the published rows are the only input. Shared names such as `search` remain one setting, and a disabled parent is already represented by every effectively disabled child row.
- Command bar gating happens once, in `useAppCommandLine` at `web/src/shared/command-bar/AppCommandBar.tsx:82`, before `classifyCommandBarSubmit` at `web/src/shared/command-bar/classify-submit.ts:49`. When the line resolves to a disabled row, return `false` so the line runs to the server, whose dispatch refusal at `src/command/manager.ts:32` and `:108` records exactly `Command is disabled: <command>.` and emits the existing notification. This covers `quit`, `close`, `theme`, `hist`, `queue`, `tasks`, `syntax theme`, and `profile launch` from the main shell bar and every plugin bar. `nav` and plugin-contributed overlay words such as `clip` are not application commands and stay ungated. Enabled lines keep today's classification, quit/save guards, picker opening, and source-visible suppression.
- The shell plugin handles two application-command words before the shared intercept: `opensShellHistory` and `transcriptSearchQuery` in `web/src/plugins/shell/useShellSubmit.ts:57` and `:62`. When the policy reports `hist` or `search` disabled, skip those local routes so the line reaches the server and is refused instead of opening the shell history or terminal find overlay. The check runs after `routeFor` returns `application`, so `!` lines and the bare `clear` route at `web/src/plugins/shell/command-line-rules.ts:12` still reach the shell even when `clear` is disabled; both remain outside policy, as explicit shell execution already is.
- Expose the policy to plugin bodies through the existing `AppCommandBar` seam rather than a new capability. Add an optional `disabledApplicationCommand(line)` query to `AppCommandBarState` at `web/src/shared/command-bar/app-command-bar-scope.ts:8` and a required field of the same name on `AppCommandBar` at `:36`, defaulted to a no-op by `scopeAppCommandBar` at `:61`. `useShellSubmit` uses it only to skip its two local routes. This is additive and client-only: `TAB_PLUGIN_API_VERSION` stays 3, no payload schema changes, and plugin bodies that do not call it are unaffected.
- Keyboard shortcuts are gated by the same published rows. Extend each `APP_CHORDS` entry at `web/src/shared/app-chords.ts:30` with an optional canonical `command`: `ctrl+r` → `hist`, `ctrl+e` → `queue`, `ctrl+a` → `tasks`, `meta+shift+f` → `search`, `meta+t` → `shell`. In `handleChordKeys` at `web/src/useWindowKeys.ts:170`, check that command before `chords.run` and before the app opener; when disabled, call `preventDefault`, report the blocked command, and return `true`. Checking before `chords.run` is what stops the shell plugin's claimed `ctrl+r`/`meta+t` at `src/plugins/shell/manifest.ts:22` from bypassing policy while enabled behavior and shortcut ownership stay unchanged. `ctrl+g`, `meta+p`, `meta+f`, and `shift+tab` name no command and stay ungated. Keep the existing `isComposing` guard: a composing key never reports a blocked command.
- Add one core RPC, `reportBlockedCommand`, with `{ text, tab }` and an `ack` reply. It is a report, not a dispatch: add it to `src/protocol/core-rpc.ts:15` `CoreRpcCall`, `src/client-message.ts:7` `CLIENT_METHOD_CONTRACTS`, `src/client-params/core.ts:21` `CORE_PARAMS`, and a case in `src/message/handler.ts:22`. `ControllerCore.reportBlockedCommand` ignores a `tab` that is not open, then calls the existing `refuseDisabledCommand` at `src/native-commands/dispatch-policy.ts:21` with the text; that re-resolves against the current server snapshot, no-ops when the command is enabled, and otherwise emits the existing `command-disabled` ambient event through `notify` at `src/notifications/index.ts:194`. Do not add a client toast, transcript line, new event, or new config field.
- Attribute a blocked shortcut to the focused tab when the key event is inside one (`chordTabLabel` at `web/src/useWindowKeys.ts:164`), otherwise to the active tab's label carried in the key-handler snapshot. If no tab label is known, block the chord and skip the report. The server only uses the label when `managers.tab.byLabel` finds an open tab.
- The client's list is a live projection, not a security boundary. A stale client can at worst block an enabled keypress with no notification (the server no-ops) or open a picker whose line the server then refuses; it can never execute a disabled command. A blocked shortcut with `notifications.events.commandDisabled` off or the originating tab active is intentionally silent, because the ambient event keeps its existing default-off and focus-suppression rules.
- Land in this order so each checkpoint typechecks: add the shared row type, projection helper, `StateEvent` field, and broadcast first; then the client matcher and state plumbing; then command-bar and shell-local gating; then chord gating and the report RPC; then specs and integration tests. The required `StateEvent` field is the one change that touches many test fixtures, so make it with the type change rather than as a follow-up.

## Out of scope

- Creating, renaming, deleting, or defining custom commands; per-role overrides of the global controls; blocking arbitrary operating-system shell commands.
- Direct tab-close gestures that use `closeTab` rather than a command: `Cmd+W`/`Ctrl+W` on a non-last tab, the tab-strip close control, and dock controls. Only command-bar submissions (including the shell-local `hist`/`search transcript` routes) and the command-backed entries in `APP_CHORDS` are gated. `Cmd+W` on the last tab still opens the quit confirmation; confirming dispatches `quit`, so a disabled `quit` is refused there like anywhere else.
- `nav`, Quick Open (`Cmd+P`), editor find (`Cmd+F`), section navigation (`Shift+Tab`), tab navigation (`Ctrl+G`), and plugin-contributed overlay words such as `clip`; none is an application command.
- The shell's `!` escape and bare `clear` route; both stay shell behavior.
- File watching or continuous reload of `commands.json`; hand edits apply on the next refresh or edit, matching unit 2.
- A new notification event, alert default, config field, client toast, or transcript entry for blocked shortcuts; the existing `command-disabled` ambient event and server delivery path are the only notification surface.
- Any change to server dispatch policy, completion filtering, ACP filtering, the Commands tab, or Roles; units 1–9 own those.
- `agentAccess` affecting human command-bar controls; the published list is built from `effectiveEnabled` only.
- A `TAB_PLUGIN_API_VERSION` bump, payload schema change, or new plugin capability for the client-only `AppCommandBar` query.
