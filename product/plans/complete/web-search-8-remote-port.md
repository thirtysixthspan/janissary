# Web search 8: the near side's `webSearch` port method and the far side's token provisioning

**Complexity: 4/10** — ~35 added lines across 4 production files, 5 requirements, 7 new test scenarios; most of the change is a behavior-preserving move of two method bodies (p=5.12)

The eighth slice of the `web search` feature (source plan: `./product/plans/complete/web-search.md`). It finishes the remote transport the typed command needs. The near side gains `remoteWebSearch` and a one-line `RemoteFileSystemPort.webSearch` that sends the `web-search` operation and returns its text; `web-search` joins the long-running request set so a far-side fallback is not cut off; and the far side's provisioning hands the workspace's merged tokens to `RemoteFileNavigators`, so the operation context added in `./product/plans/complete/web-search-7-remote-operation.md` carries real tokens. `port.ts` is at the 200-line limit, so the same change moves two private method bodies into `port-reads.ts`.

## Dependencies

- `./product/plans/complete/web-search-1-command-grammar.md` — the `WebSearchCommand` type (`query`, `numResults`, `maxChars`, `depth: WebSearchDepth`, `provider`, all required) exported from `src/web-search/command.ts`.
- `./product/plans/complete/web-search-3-provider-tokens.md` — the `tavily` and `tinyfish` rows in `PROJECT_TOKENS` that the merged token set now carries. The feature's single protocol bump (42 → 43) is that slice's; this slice changes no protocol version.
- `./product/plans/complete/web-search-7-remote-operation.md` — the `'web-search'` member of `RemoteFilesystemOperation`, its argument type `WebSearchCommand` in `RemoteFilesystemArgumentsByOperation` and its `{ text }` result (`src/remote/protocol-frames.ts`, `src/remote/filesystem/result-decoders.ts`), and the fourth `RemoteFileNavigators` constructor parameter `tokens: ProjectTokens = {}`. Without slice 7, `LONG_RUNNING` (typed `ReadonlySet<RemoteFilesystemOperation>`) and the `request('web-search', …)` call do not typecheck, so this slice lands after it.

All 14 web-search slices ship on one pull request; the ordering above is the order the implementer applies them in so typecheck and tests stay green at each checkpoint.

## Design decisions

Carried verbatim from the source plan where they apply.

- **Port method.** `remoteWebSearch(request, args)` in `port-reads.ts` sends `web-search` and returns its `text`; `RemoteFileSystemPort` gains a one-line `webSearch(args)` delegating to it, as `globPaths` delegates to `remoteGlobPaths`. `webSearch` is not added to the `FileSystemPort` interface: only the remote port needs it, since a local tab calls `webSearch` directly.
- **Signatures (decision).** `remoteWebSearch(request: RemoteRequest, args: WebSearchCommand): Promise<string>` takes no `paths` and no `root`: the operation is path-free, so nothing is mapped and there is no absolute-path pre-check (unlike `remoteGlobPaths`). `RemoteFileSystemPort.webSearch(args: WebSearchCommand): Promise<string>` is the method slice 10's `searchWebInTab` calls as `port.webSearch(parsed)` inside `withRemoteTabPort`. `WebSearchCommand` is a type-only import from `../../web-search/command.js` in both files.
- **Wire arguments (decision).** `remoteWebSearch` sends a fresh object holding exactly `query`, `numResults`, `maxChars`, `depth`, and `provider` copied from `args`, never `args` itself, so a caller's object with extra keys cannot widen the frame — the same exactness `remoteGlobPaths` keeps (and the existing glob test asserts with `Object.keys`). Every field is sent, none conditionally, because all five are required on the wire.
- **The 200-line limit.** `port.ts` is at exactly 200 lines as ESLint's `max-lines` counts them (`skipBlankLines`, `skipComments`; verified by running ESLint with a lower cap), so the three added lines for `webSearch` cannot go in without a move. The same change moves the private `pasteRemote` (`src/file-navigator/remote/port.ts`, `private async pasteRemote(`) and `createItem` (`private async createItem(`) bodies into exported `remotePaste(request, paths, root, sources, destination, mode, policy?)` and `remoteCreateItem(request, paths, root, destination, operation)` helpers in `port-reads.ts`, taking `this.requester()` and `this.paths` as `remoteGlobPaths` does, and leaving `paste`, `createFile`, and `createDirectory` as one-line delegations. The bodies move unchanged: paste maps only `destination` through `paths.to` and sends `sources` as they arrived; create maps `destination` out, keeps the two `request('create-file', …)` / `request('create-directory', …)` branches (so each call keeps its literal operation type), returns a refusal unchanged, and maps a success's `path` back through `paths.from`. That removes about 17 counted lines and adds about 4 (the method plus the type import), leaving `port.ts` near 187.
- **The `file patch` overlap (decision).** `./product/plans/ready/file-patch.md` prescribes the same extraction (its `port.ts` step) and is not on master: `port.ts` still holds both private methods. Whichever plan lands second skips the move. The check is concrete: if `port.ts` no longer has `pasteRemote` and `createItem` when this slice starts, and `port-reads.ts` already exports `remotePaste` and `remoteCreateItem`, add only `remoteWebSearch` and `webSearch`. `port-reads.ts` is at 71 counted lines and ends near 95 with this slice's three helpers (plus about 5 more if file patch's `remoteApplyPatch` joins it), so it stays far under the limit and no further module is needed. Update its header comment ("`RemoteFileSystemPort`'s line read, glob, write and text edit, extracted …") to also name the paste, create, and web search sends.
- **Deadline.** `web-search` joins `LONG_RUNNING` in `src/file-navigator/remote/port-requests.ts`, because the default 60-second `REQUEST_DEADLINE_MS` equals two 30-second provider attempts (`PROVIDER_TIMEOUT_MS`, slice 4) and would cut a far-side fallback off. It is appended at the end of the set literal; the comment above `REQUEST_DEADLINE_MS` that lists the long operations ("git, search, bulk moves and pastes, history replay, whole-file transfers, text edits") gains "web searches".
- **Provisioning.** `src/remote/serve-provision.ts` passes the merged `tokens` it already computes to `RemoteFileNavigators`, as it does to `RemoteAcp`. A forwarded value wins over the remote's own file and the remote's own file is the fallback; a search on a remote machine uses the merged token set of the workspace it runs in. Because the third constructor parameter (`filesystem: FileSystemPort = new LocalFileSystemPort()` in `src/remote/serve-file-navigator.ts`) sits before `tokens`, the call becomes `new RemoteFileNavigators(emit, result.dir, new LocalFileSystemPort(), tokens)`, with `LocalFileSystemPort` imported from `../file-navigator/filesystem-port.js` (the same import `serve-file-navigator.ts` uses). Passing `undefined` for the third argument is not used, since it reads as an accident.
- **Connection failures.** A dropped or slow connection rejects with the existing reasons (`The remote connection ended.`, `The remote machine did not answer in time.`); the port does not catch them, so the typed command can print them unchanged. Because the `web-search` descriptor has no `refusal` (slice 7), `refusalValueFor` does not classify it, so `settle` and `unavailableResult` in `port-requests.ts` reject rather than resolve; a port already disposed or whose workspace never resolved rejects with `The remote file navigator is closed.` (`CLOSED_REASON`). No new error path is added.

## Proposed changes

- **`src/file-navigator/remote/port-reads.ts`** — `remoteWebSearch` as decided above, resolving to the result's `text`; `remotePaste` and `remoteCreateItem` holding the moved bodies unchanged in behavior; imports of `BulkConflictPolicy` (`../../protocol.js`), `PasteManyResult` (`../paste.js`), and `WebSearchCommand` (`../../web-search/command.js`) as types, all with `.js`; header comment updated.
- **`src/file-navigator/remote/port.ts`** — `webSearch(args)` delegating to `remoteWebSearch(this.requester(), args)`, placed after `globPaths`; `paste`, `createFile`, and `createDirectory` delegating to the moved helpers; the two private methods removed; the `./port-reads.js` import gains the three helper names.
- **`src/file-navigator/remote/port-requests.ts`** — `'web-search'` added to `LONG_RUNNING`; the deadline comment names web searches.
- **`src/remote/serve-provision.ts`** — `new RemoteFileNavigators(emit, result.dir, new LocalFileSystemPort(), tokens)` plus the `LocalFileSystemPort` import. The file is at 94 counted lines.
- **`product/specs/remote-server.md`** — in the request-deadline paragraph ("Work that really runs on the remote — a pull, a commit, a search, … and a text edit — is given ten minutes"), add a web search to the list, noting that it covers a search that falls back across providers. The tokens on the operation context are already described by slice 7's addition to the "Protocol version 43 adds…" paragraph (forwarded tokens win over the remote's own files); do not repeat it.

## Tests

- **`src/file-navigator/remote/port.test.ts`** — a new `describe('RemoteFileSystemPort.webSearch')` beside the `globPaths` one: `webSearch` sends a `web-search` request whose `args` has exactly the keys `query`, `numResults`, `maxChars`, `depth`, `provider` with the given values (even when the passed object carries an extra key), and resolves to the reply's `text`; a channel that closes (`port.onClose()`) while the request waits rejects with `The remote connection ended.`; a disposed port rejects with `The remote file navigator is closed.` without sending a request. The existing "maps only the paste destination…", "maps a created file's path back onto the tree", "maps a created directory's path back onto the tree", and "returns a create refusal as it stands…" cases already cover the moved helpers and must pass unchanged; no new paste/create cases.
- **`src/file-navigator/remote/port-requests.test.ts`** — in the existing case asserting `requestDeadline('git-pull')` and friends, add `expect(requestDeadline('web-search')).toBe(LONG_REQUEST_DEADLINE_MS)`.
- **`src/remote/serve-provision.test.ts`** — `vi.mock('../web-search/search.js', …)` with a `webSearch` mock resolving to a fixed string. One case writes `<root>/.janissary/tavily-token` and `<root>/.janissary/tinyfish-token`, calls `loadProjectTokens(root, <empty temp home>)` (never the real home), provisions with forwarded `{ tavily: 'tvly-forwarded' }`, then on the captured `ProvisionedWorkspace.files` calls `open('f1')` and `request(…)` with a valid `web-search` frame; the mock's deps `tokens` match `{ tavily: 'tvly-forwarded', tinyfish: <the own file's value> }` — forwarded wins, own file is the fallback. A second case with no token files and no forwarded tokens sees no `tavily` or `tinyfish` key. Each case removes the files and reloads tokens in `finally`, as the `serve.test.ts` precedent does.
