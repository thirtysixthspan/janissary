# Add a `file patch` command for ACP tell sessions

**Complexity: 8/10** — ~680 added lines, 16 files edited, 36 requirements, 50 test scenarios (p=8.29)

`file patch` lets a person or an autonomous ACP agent apply one multi-file change in a single operation: add, update, move, or delete several files at once instead of issuing a separate `file write` or `file edit` for each. The change is a marker-delimited patch text (`*** Add File: <path>`, `*** Update File: <path>`, `*** Delete File: <path>`), applied as one logical transaction: every section applies or none does, so a failed hunk never leaves the tree half-changed. It joins `file read`, `file glob`, `file grep`, `file write`, and `file edit` as the sixth subcommand of the existing `file` command and the existing ACP file tool, and it runs against the same root those commands use — the local workspace, the launch directory, or a remote tab's remote clone — never falling back to the local machine for a remote tab. It lets an agent batch a refactor, such as renaming a module across many files or scaffolding a feature's file set, into one concise, reviewable operation.

## Design decisions

Each decision comes from the feature text, from existing behavior ("from precedent"), or from a user answer ("user decision").

- **Command name.** `file patch`, the sixth subcommand of the existing `file` command (`src/commands/file.ts`), after `file read`, `file glob`, `file grep`, `file write`, and `file edit`; the ACP file tool and the application-command table each have six `file` rows, and the native vocabulary lists `file patch` after `file edit` and before `web search`.
- **Who can run it.** A native ACP command available to `tell` sessions (feature text), and also a typed application command, matching how `file write` and `file edit` are both.
- **Default grants (user decision).** The built-in `tell` role grants `file patch` beside `file write` and `file edit`, giving it all sixteen native commands; the built-in `ask` role does not grant it and keeps its ten, which include `web search`. Saved roles files are not changed and keep the grants they list.
- **Input form (user decision).** `file patch <JSON>`, where the JSON is one object `{"patchText":"<text>"}` kept on one line with newlines written as `\n`, the same grammar, extraction, and escaping rules as `file write` and `file edit`. No raw multi-line form.
- **Envelope (user decision).** `*** Begin Patch` as the first line and `*** End Patch` as the last line are optional; the text is accepted with or without them, and the primer shows them.
- **Operations.** Add, update, and delete, plus a move through `*** Move to:`; delete-plus-add remains a valid way to move (feature text).
- **Move marker (user decision).** An `*** Update File: <old>` line may be followed directly by `*** Move to: <new>`, optionally followed by hunks, which renames the file and applies the hunks in one section without re-sending the file's content.
- **Add sections.** The body after `*** Add File: <path>` is the complete new content of the file, written with every line prefixed by `+` (user decision), as in the Codex and opencode formats, so a content line beginning with `***` is never mistaken for a marker. A body line without the `+` prefix is a malformed-patch error. Adding a path that already exists is an error, unless an earlier section of the same patch deletes or moves away that path, which is how a patch overwrites a file (user decision); the same rule applies to a `*** Move to:` target. There is no overwrite flag. Missing parent folders are created (feature text).
- **Empty sections (user decision).** An Add with no `+` lines creates an empty (zero-byte) file. An Update with neither hunks nor a `*** Move to:` line is `Malformed patch at line <n>: Update File needs a hunk or Move to`, an additional structural problem beside those under Failure wording.
- **Update sections.** The body after `*** Update File: <path>` is a set of `@@` / context / `-` / `+` hunks naming exactly which lines are removed and inserted. A hunk that does not cleanly match the current file content is an error (feature text).
- **Match strictness (user decision).** A hunk's context and `-` lines are first matched against the file exactly; if there is no exact match, the search is retried ignoring trailing whitespace on each line. No further fuzzing (trimmed lines, Unicode punctuation folding).
- **Hunk placement (user decision).** Hunks are searched in order, each search starting after the previous hunk's matched position. An `@@ <text>` header first moves the search to the next line equal to `<text>` (under the same exact-then-trailing-whitespace rule); a bare `@@` does not move it. The first match wins — Codex semantics, so models' existing habits work. A first hunk may omit its `@@` line, as Codex accepts; later hunks need one.
- **Bounded search (user decision).** Each `applyHunks` call splits the text once and searches it through a line index built for that snapshot: an exact-text table of interned line ids and sorted positions, plus a trailing-whitespace table built only when an exact lookup fails. Each table carries two polynomial rolling-hash prefix arrays, so an `@@` anchor is a binary search for the next position at or after the current one, and a hunk block is compared only at candidate positions whose hash matches. Candidates are visited in ascending order and verified line by line, so the chosen match is exactly the first match a nested scan would choose and a hash collision cannot change the result. Cost grows with the file and patch sizes together rather than their product, and an anchored hunk does not scan from its position to the end of the file. An insertion-only patch on a large file pays nothing beyond splitting the text, because each table is built lazily on the first search that needs it.
- **Volume case (user decision).** On a volume that ignores letter case, two patch sections naming the same path the patch itself creates in different case act on one place: a second Add fails `File already exists` with nothing changed, and an Update or Delete through the other spelling changes the one file. Planned folders fold the same way, so differently cased spellings of one missing folder are created once under the first spelling, and a move destination or intermediate hop can share a planned folder. The view decides the volume's behavior once per run with a read-only probe of an existing root entry, falling back to the root's own basename and then its nearest existing ancestor directories; a toggled spelling that is absent or names a different device/inode is conclusive evidence of a case-sensitive volume, while an entry it cannot canonicalize (such as a broken symbolic link) is skipped and only no evidence at all answers case-sensitive. A case-sensitive volume keeps every spelling distinct.
- **First-named rows (user decision).** Each place records the order in which a non-implicit resolution first names it; an implicit link target records none until a section names it, and naming it again leaves the first ordinal alone. Rows are emitted in that order, so following a link in an earlier section does not move the target ahead of paths named earlier, and a target reached only through a link and never named still gets no row. Places with no ordinal, such as handwritten test fixtures, keep their insertion order after every named place.
- **Line endings (user decision).** An updated file keeps its existing line ending (a CRLF file stays CRLF, judged from the file's first line ending) and its existing final-newline state. An added file is written with LF line endings and a final newline. An `*** End of File` line inside a hunk anchors that hunk to the end of the file. There is no `\ No newline at end of file` marker.
- **Delete sections.** `*** Delete File: <path>` has no body. Deleting a path that does not exist is an error (feature text). The delete record keeps the entry's link text and a snapshot of its content as it was when deleted, so a later Add at the same path cannot mutate the bytes a restore will write.
- **Section order (user decision).** Sections apply in order against an in-memory view of the tree, so a later section sees what earlier sections produced: the same path may appear in several sections (two Updates apply one after the other; an Update then a Delete removes the file), and Delete-then-Add is how the overwrite rule works. Nothing touches disk until every section has applied to the view.
- **Atomicity.** All sections apply as one transaction; any failed section fails the whole patch and the tree is left exactly as it was (feature text).
- **Links, BOM, and permissions (user decision).** As write and edit: an Update writes through an in-root symbolic link to its target (via `resolveMutationTarget`); a Delete removes the link itself, never its target; a `*** Move to:` renames the link; an Update keeps the file's permission bits and byte-order mark; an Add gets default permissions and no mark. A Delete-then-Add of a file drops its earlier mark. No mode marker.
- **Symlinked root (user decision).** The view resolves its root once with `realpathSync.native`, falling back to the given spelling when that throws, and expresses a followed link's target relative to that canonical root. A root opened through a symbolic link therefore behaves as the directory it resolves to: an Update through an in-root link changes the link's target, a Delete removes the link and leaves its target, and a Move moves the link itself. Every resolved target still passes through `resolveMutationTarget`, so the containment, protected, secret, and file-type refusals all still apply, including to a link whose target lies outside the real root.
- **Emptied folders (user decision).** A folder left empty by a Delete or a Move stays in place; the patch only touches files. A restore after a failure while applying does remove folders the patch itself created.
- **Exact content.** Indentation and newlines in the bodies are preserved exactly (feature text).
- **Success output (user decision).** A header `Patched <n> files:` (`Patched 1 file:` for one, `Patched 0 files:` when every change cancels out) followed by one git-style row per path in the order a section first names it: `A <path>` for a path that did not exist before and does now, `M <path>` for one that existed before and after, `D <path>` for one that existed before and does not now, and `R <old> -> <new>` for a file that existed before the patch and was renamed by a surviving move whose destination did not exist before the patch. A destination that existed before the patch, including one deleted or moved away earlier in the same patch, keeps its own net row: `M` when it exists at the end, `D` when it does not; the origin reports `D`. Each path is listed once with its net change; a path added and then deleted by the same patch gets no row; a chain of moves collapses to one `R` from its origin to its final place; a file the patch itself added and then moved reports `A` at its final place. File content never appears. Paths are shown as typed, escaped by `displayPath` like write/edit lines.
- **Failure output (user decision).** One line naming the first failing section by its 1-based number and its marker, the reason, and for a hunk mismatch the hunk's first context or `-` line, then `No files were changed.`, e.g. `Patch failed at section 2 (Update File: src/a.ts): No matching text for hunk starting "const x = 1;". No files were changed.` Sections are checked in order and the first failure wins.
- **Failure wording (user decision).** Bad or incomplete JSON prints `Usage: file patch <JSON>` and changes nothing. A structural error prints `Malformed patch at line <n>: <problem>. No files were changed.`, where `<n>` is the 1-based line of the patch text and `<problem>` is one of `unknown marker "<line>"`, `Add File lines must start with "+"`, `hunk lines must start with " ", "-", or "+"`, `Move to must follow Update File`, `missing path`, `no file sections`, or `Update File needs a hunk or Move to`. A section failure's reason is either a patch rule — `File not found` (Update or Delete of a missing path), `File already exists` (Add or Move to an existing path), or `No matching text for hunk starting "<line>"` (the hunk's first context or `-` line, or its `@@` anchor text when the anchor is not found) — or a policy or filesystem reason from the same checks write and edit use, such as `Outside the workspace`, `Protected file`, `Secret file`, `Is a directory`, `Not a text file`, `File too large (>5 MB)`, `Filesystem error ENOTDIR; check the item and destination, then try again`, a permission denial, a vanished path, or any other `fileOperationReason` text. Quoted lines are escaped like `displayPath` so the output stays one line.
- **Remote rejection wording (user decision).** A remote rejection that is not one of the connection lines prints `Patch failed: <reason>.`, with the final period not doubled when the reason already ends in one (for example `Patch failed: Invalid remote filesystem operation result.`), and with no promise about the tree, because the far side may already have applied the patch. Patch text that is not well formed is refused near side before it can be re-encoded as a different patch, and prints `Patch failed: Not a text file.` without sending a frame.
- **Size limits (user decision).** The JSON argument is capped at 5 MB (`FILE_POLICY_MAX_BYTES`), checked after it parses as JSON and before the patch text is parsed and printed as `Patch too large (>5 MB). No files were changed.`, while a malformed oversized argument gets the usage line. Every file a section reads or writes is capped at 5 MB, reported as `File too large (>5 MB)` for that section. There is no cap on the number of sections or on the total written.
- **Failure while applying (user decision).** Every check runs against the in-memory view before anything touches disk, so normal failures change nothing. If a disk operation fails while the validated patch is being written, the files already changed are restored, including a path the patch vacated and a later section re-created, whose original bytes, permissions, and link text come from the kept delete record; a rename into that path has its own undo. When the restore succeeds the line is `Patch failed while applying: <reason>: <path>. No files were changed.`; when the restore itself fails it is `Patch failed while applying: <reason>: <path>. Some files may have been changed.`, without listing them. The path is the typed path the failed step reports.
- **Commit and restore (user decision).** Validation reads each touched file once (bounded at 5 MB by `readBoundedRegularFile`) and keeps its original bytes and permission bits in memory. The commit creates the planned folders, unlinks deleted entries, replays rename steps in section order, and writes each result with `atomicWriteFile`; on a failure it restores the originals in reverse order and removes folders the patch created. A folder index maps each planned folder to the first typed place under it, so a failed folder reports a path the user recognizes. No backup files are written to disk. A failed restore keeps the original failure's reason and path and still runs the remaining undo steps.
- **Concurrency (user decision).** Validation and commit run synchronously, with the sync helpers `writeToolTextFile` and `editToolTextFile` already use, so no other server work (another session's patch, an editor save) can interleave with a patch. Outside processes are not guarded, as with write and edit today. A patch is not cancellable once it starts; an ACP cancel suppresses only its late result and the next provider turn, as for write and edit. Ceiling: a patch touching many large files blocks the event loop for its whole run; the upgrade path, if that shows up as lag, is running `applyPatchText` in a worker behind the same `FileSystemPort.applyPatch` contract.
- **Result.** A per-file summary of which files were created, modified, moved, or deleted on success; an informative, actionable error on malformed markers, unknown operations, non-matching hunks, or missing files (feature text).
- **Authorization (from precedent).** The ACP gate grants or refuses `file patch` by its native command name, like `file write` and `file edit`: `Command is disabled: file patch.` or `Command not allowed for role "<role>": file patch.`. Every affected path, including a `*** Move to:` target, is subject to the same path rules as `file write` (`resolveMutationTarget`), and `.git` / `.janissary` paths fail with `Protected file`.
- **Paths outside the root (user decision).** A section whose path or `*** Move to:` target resolves outside the root fails the patch with `Outside the workspace`, exactly as write and edit refuse it. The feature text's external-directory permissions are out of scope; Janissary has no such permission.
- **Agent runs (user decision).** Not in this version. `gateAgentCommand` in `src/acp/tool-table.ts` refuses any `file patch` line with `Agent: command not permitted: <command>.`, with or without the `file` grant, as it refuses `file write`, `file edit`, `file glob`, and `file grep`; `runGrantedAgentCommand` in `src/agent/command-tools.ts` refuses the same lines with the same text as defense in depth, so a patch never runs in the caller's directory.
- **Remote tabs (user decision).** A new `apply-patch` mutation operation in `MUTATION_OPERATIONS` (`src/remote/filesystem/operations.ts`) carries the patch text to the far side, which parses, validates, and commits it with the same local runner a local tab uses and returns the output. Its argument is exactly one `patchText`, base64-encoded UTF-8 with a leading byte order mark kept as text; its result is a non-empty `{ text }`. The operation names no refusal shape and no paths of its own, so a connection failure rejects with its reason and each section path is contained on the far side. The transaction runs entirely on the far side, so a dropped connection cannot leave a half-applied patch. `FileSystemPort` gains an `applyPatch` method (local: run in place; remote: send the operation through `remoteApplyPatch`, which refuses ill-formed text before encoding it). A patch is long-running and gets the long request deadline. `apply-patch` is protocol version 45: version 44 already carries `web-search` and the Tavily and TinyFish token names, so a version-44 peer is refused at the handshake. Connection failures print the existing lines (`Remote connection unavailable.`, `The remote connection ended.`, `The remote machine did not answer in time.`) and never fall back to the local disk.
- **Workspace root (from precedent and feature text).** The same root as `file write`: a local tab's workspace or project directory, a remote tab's remote clone only (never the local disk), and in the ACP loop the workspace of the host running the loop (`runsOn: 'workspace'`).
- **Primer (user decision).** When a role grants `file patch`, the file tool's primer includes this text after the mutation primer (or after the read, glob, and grep primers when neither write nor edit is granted), separated by a blank line:
  - `To change several files in one step, end your reply with one line:`
  - `file patch {"patchText":"<patch>"}`
  - ``The patch is applied all-or-nothing. Inside it: `*** Add File: <path>` then the new content with every line prefixed by `+`; `*** Delete File: <path>` with no body; `*** Update File: <path>`, optionally `*** Move to: <new path>`, then hunks: an `@@` line (optionally `@@ <a line that comes before the change>`) followed by lines starting with ` ` (unchanged context), `-` (removed), or `+` (added). Give about 3 context lines around each change.``
  - `Example: file patch {"patchText":"*** Begin Patch\n*** Update File: src/a.ts\n@@\n const a = 1;\n-const b = 2;\n+const b = 3;\n*** Delete File: old.txt\n*** End Patch"}`
  - ``A patch answers `Patched <n> files:` followed by one `A`/`M`/`D`/`R` row per file.``
- **Follow-up prompt (user decision).** The prompt that feeds a patch's result back to the agent names the command as `file patch <path>, <path>, …`, listing each section's path (and a `*** Move to:` target as `<old> -> <new>`) in patch order with no content, or bare `file patch` when the JSON or the patch text is malformed. History, transcripts, and recordings keep the full command, as for write and edit.
- **Completion (from precedent).** Command-bar completion does not offer `patch`, as it offers neither `write` nor `edit`; `FILE_SUBCOMMANDS` in `src/completion/file-read.ts` is unchanged.
- **Documentation.** The exact marker format and hunk syntax are documented in the agent primer and `help/file.md` so an agent can author a patch on its first try (feature text).

## Proposed changes

A patch is one more file mutation, so it rides the existing mutation path end to end: anything that already treats `file write`/`file edit` as a mutation (the ACP file tool, both loop hosts, the agent-run refusals) picks up `file patch` through one widened predicate, and the follow-up prompt delegates to a patch-specific description. The parse/apply core, the hunk index, the output lines, the typed runner, and the remote operation are new.

### New `src/file-patch/` feature directory (server)

- **`command.ts`** — `isFilePatchCommandLine(line)` (`/^file\s+patch(\s|$)/i`), `FILE_PATCH_USAGE` (`Usage: file patch <JSON>`), `FILE_PATCH_PRIMER` (the primer text under Design decisions), and `parseFilePatchCommand(input)` returning the patch text or a usage/size error line. The JSON object takes exactly one key, `patchText`, a string; any other key, a missing key, or a non-string value is a usage error. The argument is validated as JSON first and then checked against `FILE_POLICY_MAX_BYTES`, so a malformed oversized argument gets the usage line and a well-formed oversized one prints `Patch too large (>5 MB). No files were changed.`. Also `describePatchCommand(input)` producing the follow-up-prompt form (`file patch <path>, <old> -> <new>, …`, or bare `file patch` when the JSON or patch text is malformed).
- **`parse.ts`** — pure `parsePatchText(text)` returning an ordered list of sections (`add` with content lines, `delete`, `update` with an optional move target and a list of hunks) or a `{ line, problem }` structural error. Strips an optional `*** Begin Patch` first line and `*** End Patch` last line; splits on `\n` (a `\r` before it is dropped so CRLF-typed patches parse, while a lone final carriage return is kept); recognizes `*** Add File: `, `*** Delete File: `, `*** Update File: `, `*** Move to: `, `@@`, and `*** End of File` lines; every other `*** ` line is `unknown marker`. Paths are taken verbatim after the marker's `: ` with surrounding whitespace trimmed; an empty one is `missing path`. A `*** Move to:` is accepted only directly after its Update marker; an Update that closes with no hunks and no move is `Update File needs a hunk or Move to`. Hunk bodies are parsed by `parse-hunks.ts`.
- **`parse-hunks.ts`** — pure `parseHunks(bodyLines, endLine?)` turning an Update body into `PatchHunk[]` or the first hunk-structure error. A hunk starts at an `@@` line with an optional exact anchor; a first hunk may omit `@@`; every hunk line starts with ` `, `-`, or `+`; `*** End of File` marks a hunk and ends it; a blank line, a bad prefix, or an empty hunk is `hunk lines must start with " ", "-", or "+"` at the lowest applicable line.
- **`hunk-search.ts`** — `createLineSearch(lines)` returning `findLine(line, from)` and `findBlock(block, from, endOfFile)`. It builds the exact line table lazily and the trailing-whitespace table only when an exact lookup first fails, so an insertion-only patch on a large file does no indexing work. Each table maps a key to an interned numeric id and its sorted positions, with two polynomial rolling-hash prefix arrays and matching power arrays over those ids. `findLine` binary-searches the next position at or after `from`; `findBlock` starts from the first line's positions, skips starts whose block hash differs, verifies each remaining candidate line by line in ascending order, and handles the empty block and the single end-of-file position. The chosen match is exactly the first match a nested scan would choose.
- **`hunks.ts`** — pure `applyHunks(text, hunks)` returning new text or the first failing hunk's first context-or-`-` line (or its anchor text). It splits the text once, builds one `createLineSearch` index for that snapshot, and routes anchors and blocks through it, leaving the exact-then-trailing-whitespace rule, sequential search, `*** End of File` anchoring, and forward assembly of original lines and replacements unchanged, so a very large hunk never exceeds the argument-count limit. It detects the file's line ending (first `\r\n` vs `\n`) and its final-newline state, works on the split lines, keeps context lines' own text, and rejoins with the same ending and final-newline state.
- **`view-entry.ts`** — the exported `PatchContent` and `PatchPlace` types (`implicit?`, `firstNamed?`, requested and resolved location, existed/exists, link text, missing folders, content), `placeKeys` (canonical content key, link location and identity, missing folders), and `readPatchContent` (one bounded read, strict decode, BOM detection, original bytes, and permission mode). A symbolic link becomes a place at its own location with its link text and a content entry at the target's real path.
- **`volume-case.ts`** — `volumeIgnoresCase(root)`: a read-only probe that toggles one ASCII letter in an existing entry's name and compares the two spellings by device/inode and canonical realpath. A toggled spelling that is absent, or that resolves to a different entry, is a conclusive `false`; a stat or realpath failure after both spellings matched is inconclusive and moves the probe to the next lettered entry. The probe walks root entries, then the root's own basename under its parent, then the entries of its nearest existing ancestors, and answers `false` only when nothing is conclusive. It writes nothing.
- **`view.ts`** — `PatchViewReads` (`places`, `plannedFolders`, `folderKey`) and `PatchView extends PatchViewReads` (`resolve`, `resolveLink`, `setExists`, `contents`). `createPatchView(root, caseInsensitive = volumeIgnoresCase(root))` keeps maps for places, contents, links, and a case-folded place index that exists only on a case-insensitive volume, plus a counting map of planned-folder claims and a memoized shallowest-first list. `resolve` runs `resolveMutationTarget` and the planned-folder checks, reads each file once on first touch, shares one place between spellings of a path and between a link and its `dev`/`ino` identity, and assigns the next first-named ordinal on every non-implicit resolution. `setExists` is the only way existence changes: it applies the change, adds or removes the place's missing-folder claims, and invalidates the memo. `resolveLink` follows a moved link's lexical target relative to the canonical root. `plannedFolders()` derives the deduplicated, depth-sorted list from existing places and rebuilds only on demand after an existence change; `folderKey` folds a folder's case exactly when the cached volume decision says the volume ignores case.
- **`sections.ts`** — `applySections(view, sections)` applying Add, Update, Delete, and Move sections in order and returning `{ ok: true, changes, rows }` or the first failure with its 1-based section number, marker, and either a finished reason or a hunk line. Add checks `File already exists`, Delete and Update check `File not found`, hunks go through `applyHunks`, every link place goes through `section-steps.ts`, and the result text goes through the write/edit text checks. Existence changes go through `view.setExists`; a delete records the place, its link text, and a copy of its content object; a link that was deleted and re-added gets fresh content and loses its link text. It dispatches a `*** Move to:` Update to `moves.ts`, and an entry-only Delete or move-without-hunks skips following a moved link whose target is missing.
- **`moves.ts`** — `moveSection`: resolves the source and target, checks the source exists and the target does not, applies hunks to the source's content, records the move chain and the vacated place, and updates the view through `setExists` so the target carries the source's link text and content. A Move keeps a link a link and keeps an existing file's permission bits; a deleted link that was re-added as a regular file and then moved is recorded as an off-disk chain with the replaced link remembered.
- **`move-chains.ts`** — `createMoveRegistry`, `recordMove`, `retargetLink`, `survives`, and `showsRename`. Chains keep an origin, current place, travelling content, link flag, on-disk flag, hops in section order, and insertion ordinal; heap-backed indexes keep recording and lookup efficient as the number of moves grows. A chain that ends where it started survives but replays no rename.
- **`section-steps.ts`** — the shared section checks and record helper: `followLink` (follows links through the view, re-targets a moved link, detects cycles and missing targets with `Not a text file`), `freshContent`, `checkText` (via `encodeToolText`), and `recordWrite`. The record carries no link-target bookkeeping, because nothing reads it.
- **`changes.ts`** — `PatchChanges` (`folders`, `deletes`, `writes`, `moves`), `PatchRecord` (`deletes`, `writes`, `moves`, `removedByDelete`), and `buildPatchChanges(view: PatchViewReads, record)` deriving the change list from the final view and the apply-time record. Deletes carry the place and a snapshot of its link text and content; writes carry the final text, BOM flag, reported place, and an optional final place for a moved file. A recorded delete is kept when its place existed and is not the origin of an active chain, and either the place is absent at the end, was explicitly deleted, or is not the origin of a chain that returned to it; a kept entry is the only holder of the original bytes, mode, and link text for restore, while a chain ending where it started leaves the path untouched. The folder list merges the view's planned folders with the move destinations' missing folders through `view.folderKey`, keeping the first spelling and the existing depth order.
- **`rows.ts`** — `PatchRow` (`A`, `M`, `D` with one path; `R` with two) and `patchRows`, which orders places by `firstNamed` (unknown ordinals after known ones, preserving the input order of handwritten fixtures), derives net rows from the places and move chains, skips implicit link targets and destinations, and uses a move chain's origin and final place for an `R` row only when `showsRename` says the destination is new.
- **`commit-operations.ts`** — the `CommitOperations` seam (`mkdir`, `writeFile`, `unlink`, `rename`, `rmdir`, `symlink`, `chmod`) and the default object built from `node:fs` and `atomicWriteFile`, so tests can inject a failure.
- **`restore.ts`** — the `UndoRecord` union and `restoreChanges`, which walks records in reverse, runs each undo in its own `try`, keeps going after a failure, and treats a created folder that is no longer empty as not a failure.
- **`commit.ts`** — `commitChanges(changes, operations?)` and `CommitOutcome`. Four phases: create the planned folders, unlink deleted entries, replay rename steps in section order, then write each result with `atomicWriteFile`. A folder index maps each planned folder to the first typed place under it so a failed folder reports a path. On any thrown error it restores the completed steps in reverse, removes the folders it created, and returns `{ restored, reason, path }`.
- **`apply.ts`** — `applyPatchText(root, text)`: parse, build and apply the view, commit, and format the success rows or failure line. Synchronous; it is what `LocalFileSystemPort.applyPatch` and the far-side operation both call, so local and remote output are produced by the same code.
- **`messages.ts`** — the output builders and constants: `patchSuccessText`, `malformedPatchLine`, `sectionFailureLine`, `applyingFailureLine`, `patchRejectionLine`, and `withFinalPeriod`. Escaping, the `Outside the workspace` mapping, and the two "changed" endings live here.
- **`tab-patch.ts`** — `runFilePatch(port, root, input)`: parse the argument, return its usage or size line without touching the port, otherwise `await port.applyPatch(root, patchText)`. A pass-through connection message returns unchanged; any other rejection becomes `Patch failed: <reason>.`.
- **`src/file-patch/*.test.ts`** — the colocated suites for the modules above (listed under Tests).

### Order of work

The modules layer from pure to effectful. `parse.ts`, `parse-hunks.ts`, `hunk-search.ts`, and `hunks.ts` are pure and do no I/O; `volume-case.ts` and `view-entry.ts` read the volume and each touched file once, and `view.ts` holds the in-memory tree, its planned folders, and its first-named order. `sections.ts`, `moves.ts`, `move-chains.ts`, `section-steps.ts`, `changes.ts`, and `rows.ts` apply sections to the view and derive the change list and rows. `commit-operations.ts`, `restore.ts`, `commit.ts`, and `apply.ts` write the change list and restore on failure. `command.ts`, `messages.ts`, `tab-patch.ts`, and the wiring expose the result to the typed command and the ACP loop. `src/file-write/command.ts` stays small: its patch-aware edits are one import, the widened predicate, and the `describeLoopCommand` delegation, and patch-specific code lives in `src/file-patch/command.ts`.

## Out of scope

- A raw multi-line patch form in ACP replies or the command bar (user decision).
- External-directory permissions; outside-root paths are refused (user decision).
- Fuzzy matching beyond trailing whitespace (user decision).
- An overwrite flag; overwriting is Delete-then-Add (user decision).
- A `\ No newline at end of file` marker and a file-mode marker (user decisions).
- Removing folders emptied by a patch (user decision).
- `file patch` in `agent` command runs (user decision).
- Command-bar completion of `patch` (from precedent).
- Guarding against outside processes changing files mid-patch, and on-disk backups that survive a crash (user decisions).
- Binary file content (from precedent: tool writes are text only).
- Falling back to the local machine for a remote tab (feature text).
- Case folding on a volume that distinguishes case, and detecting every exotic filesystem; the probe answers case-sensitive when it has no evidence.
- Reusing a hunk index across separate `applyHunks` calls; each call receives a new text snapshot, so it builds its own.
- Typechecking test files; `tsconfig.json` still excludes `**/*.test.*`, so the narrowed view contract is compiler-checked in production only.
