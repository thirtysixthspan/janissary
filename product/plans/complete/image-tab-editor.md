# Image tab editor

**Complexity: 7/10** — the novel part is one new subsystem, the canvas editing surface with its pointer-driven crop geometry, across four client modules; the rest is bounded by what already exists — two additive plugin-API extensions, a dispatch change to the core `edit` command with four existing call sites riding on it, and widening the app's existing unsaved-changes guard, dialog, and handle map rather than building any of them.

The backlog entry asks to "bring in or duplicate https://github.com/unlayer/react-image-editor for the image tab." Investigation settled that question decisively: `@unlayer/react-image-editor@1.0.1` is a thin React wrapper that injects `https://cdn.unlayer.com/image-editor/embed.js` and calls `window.ImageEditor.createEditor()`. The editor itself is not in the MIT-licensed tarball — it is Unlayer's hosted product, gated by `projectId` and an encrypted `licenseUrl` entitlement, with AI features that call their API. Janissary's own Content-Security-Policy (`src/index.ts:19`) is `default-src 'self'; script-src 'self'; img-src 'self'`, so the CDN script, its fonts and stickers, and its API calls are all blocked; adopting the package means opening `script-src`, `img-src`, and `connect-src` to a third-party origin and making image editing require network access. This plan therefore takes the *duplicate* branch: a native editing surface built inside the existing bundled image plugin, with no third-party dependency, no CSP change, and no network at all.

The image tab today (`product/specs/image-tab.md`, `web/src/plugins/image/ImageTab.tsx`) is a read-only view: a metadata header, zoom, and pan, answering no intents and declaring no command. This plan gives it a second mode. An **Edit** control in the header flips the same tab from viewer to editor; a canvas replaces the `<img>`; a toolbar offers **crop**, **rotate**, **flip horizontal**, **flip vertical**, and **resize**; and a **Save** writes the result as a new numbered file beside the original — `photo.jpg` becomes `photo.edit-1.png` — through the same tab-bound intent path the video plugin's frame capture already uses (`src/plugins/video/shot.ts`). Nothing is ever overwritten. The scope is deliberately geometry-only: no draw, text, shapes, stickers, frames, filters, or AI.

The editor is reachable three ways, all landing in the same place. Beyond the header control, `edit <image>` reaches it because the core `edit` command learns to dispatch by file type, and Shift+double-click on an image row in the file navigator reaches it for free — that gesture already sends the literal `edit <path>` command (`web/src/FileNavigatorTab.tsx:68`), so no plugin-API gesture change is needed for it.

## Design decisions

**The editor is duplicated natively, not brought in.** No `@unlayer/react-image-editor` dependency, no CDN, no CSP relaxation, no licence question. The editing surface is a plain `<canvas>` inside the existing image plugin, so `open photo.png` works identically on a machine with no network. This costs more implementation work than adopting the package and buys back a self-contained, offline, licence-clean app — the property that made the CSP as tight as it is.

**The first version does geometry only.** Crop, rotate 90° (either direction), flip horizontal, flip vertical, and resize. Every one of these is a pixel-geometry transform expressible as a `drawImage` onto a sized canvas, so the editor needs no vector overlay object model, no selection handles for text or shapes, no font loading, and no filter pipeline. Draw, text, shapes, stickers, frames, and filters are out of scope for this version.

**Saving writes a new numbered file beside the original and never overwrites.** `photo.jpg` saves as `photo.edit-1.png`, then `photo.edit-2.png`, taking the lowest number not already on disk, exactly as the video plugin's capture writes `clip.shot-1.png`. The server owns the destination and the filename; the client ships only pixels. The original is never modified, so a bad crop costs nothing, and a JPEG never loses quality to repeated re-encoding because it is never written back.

**Every save is a PNG, whatever the source format.** A JPEG, GIF, WebP, BMP, AVIF, ICO, or SVG all save as `.edit-<n>.png`. This follows from the canvas: it holds RGBA pixels and `toDataURL('image/png')` is the lossless way out. Two consequences are accepted rather than worked around, because they are predictable and the original always survives: an **animated GIF flattens to the frame the canvas decoded** (its first), and an **SVG rasterizes** at the size it was rendered, losing its vector nature. Editing is offered for every format the viewer opens — no format silently lacks an Edit control — and PNG-only output matches the video plugin's save exactly.

**Edits are an ordered operation list replayed from the original pixels, with full undo and redo.** The editor holds the decoded source image plus a list of operations; the canvas is rendered by replaying that list from the source every time. Nothing is destructively baked in until Save. `Cmd+Z` (`Ctrl+Z`) steps back one operation and `Cmd+Shift+Z` (`Ctrl+Shift+Z`) steps forward again — the same chord pair the file navigator already uses for its move undo (`product/specs/file-navigator-tab.md:298`). Redo is discarded when a new operation is applied after an undo, which is the ordinary stack behavior.

**Crop and resize are direct manipulation with live numbers.** Choosing **Crop** puts an adjustable rectangle on the canvas that the user drags out and nudges by its edges and corners; choosing **Resize** drags the image's corner. Both display the resulting pixel dimensions live while dragging, so the user sees exactly what they will get without typing anything. There are no numeric entry fields in this version — the viewer is already a drag-and-wheel surface, and this keeps the editor consistent with it.

**A successful save confirms in the header and leaves the editor open.** The header names the file written for a few seconds and then clears, precisely as the video plugin's capture confirmation does (`web/src/plugins/video/useVideoShot.ts:8`, a 4000 ms window). Edits stay live, so the user can keep working and save again as `-2`. The tab keeps the original image's identity — it does not switch to the saved file, so names never chain into `photo.edit-1.edit-1.png`.

**Leaving edit mode or closing the tab with unsaved edits raises the app's existing save-changes dialog.** A crop is real work, unlike a scroll position, so it is not discarded silently the way zoom and pan are. This reuses the editor tab's unsaved-changes machinery wholesale rather than building a confirmation of its own: `SaveChangesDialog`, with its three buttons — **Save**, **Don't Save**, **Cancel** — reached through the `guardRef` close guard in `web/src/CloseSaveGuard.tsx:21`. **Save** in that dialog means what Save means everywhere in this feature: write the next numbered PNG, then close. The behavior specced for editor tabs at `product/specs/editor-tab.md:136` ("Closing with unsaved changes") therefore becomes true of image tabs too, including that it fires from the tab strip's × button, from Cmd+W, and from typing `close`/`exit`.

**All three of the app's close paths are covered, not just the per-tab one.** The per-tab path (× button, Cmd+W, `close`/`exit`) runs through `closeTab` and the guard; `quit` and closing the last tab bypass that guard entirely and are caught by `useUnsavedQuitGuard` via `anyDirtyEditor` (`web/src/dirtyEditors.ts:8`); closing the browser tab or window is caught by that hook's `beforeunload` arming (`web/src/useUnsavedQuitGuard.ts:22`). An image tab with unsaved edits must be visible to all three, or the feature ships a hole on the two paths that are easiest to miss. `product/specs/quit-confirmation.md` describes the whole-app prompt this feeds.

**The tab strip shows an unsaved-changes marker.** A tab with unsaved edits shows a dirty indicator beside the image's file name. The marker means *unsaved changes* only — being in edit mode with nothing changed shows nothing — so it never becomes a type marker by another name. Two things make this a knowing exception rather than an oversight, and both were raised before it was chosen. It contradicts `[[tab-label-no-markers]]`, which `product/specs/image-tab.md:109` currently cites to say "no type or status marker is appended — the name only". And it diverges from the editor tab, which today marks unsaved changes only by enabling its own save button (`product/specs/editor-tab.md:39`) and adds nothing to the tab strip. The reason accepted for both: with several image tabs open, unsaved work in a tab that is not on screen is otherwise invisible. The editor tab is deliberately **not** changed to match — that is a separate decision about a different tab.

**Core `edit` dispatches by file type.** One `edit` verb, not a second command. `edit photo.png` opens the image editor; `edit src/index.ts` keeps today's plain-text behavior. This is what makes the file navigator's Shift+double-click, the quick-open picker (`web/src/useQuickOpen.ts:51`), transcript file links (`web/src/file-link.ts:119`), and the transcript-line open control (`web/src/transcript-line.tsx:101`) all reach the image editor without changing any of them — they all send `edit <path>` already. The accepted consequence is that **`edit photo.png` can no longer open a PNG as raw text**; there is no escape hatch for that in this version.

**Shift+double-click on an image row opens the image editor.** It follows from the dispatch decision above rather than from any change to the navigator or to the plugin API's `editGesture` field (`src/plugins/api.ts:108`), which stays the single-valued `'open external'` it is today. `product/specs/file-navigator-tab.md:166` documents the current image exception ("open it in the plain-text editor... even for files whose normal opener is a viewer (images)") and is updated to describe the new destination.

**A `:line` suffix on an image path is ignored.** `edit photo.png:42` parses the line number as it does for any file (`src/commands/edit.ts:11`) and the image editor discards it — an image has no lines. The path still opens.

## Proposed changes

**Routing `edit` by type.** `OpenFileManager.edit` (`src/open-file-manager.ts:41`) currently resolves the target and hands it straight to `openInEditor`, bypassing the opener registry — that bypass is the whole point of the command. It gains one check before that: resolve the file's extension against the static plugin declarations and, when it belongs to a plugin that declares it edits its own files, dispatch to that plugin's edit presentation instead. Resolution reads the declaration catalog only and must not activate the plugin, matching the rule the selection-action resolution already follows. Everything else about `edit` is unchanged: path expansion, the sync-path branch, and the plain-text fallback for every other extension.

**Declaring an edit presentation.** `TabPluginDeclaration` (`src/plugins/api.ts:97`) gains an optional boolean marking the plugin as the editor for the file types it claims, and the `opener` on `TabPluginActivation` (`src/plugins/api.ts:207`) gains an optional third presentation beside `inline` and `external`, receiving the file and the server capabilities. A declaration carrying the flag with no handler is caught in `validateActivation` (`src/plugins/activate.ts:36`) and disables the plugin with that reason — the identical rule and the identical moment the `selectionAction` case at `src/plugins/activate.ts:44`–`:46` (`contributes "…" but provides no selectionAction handler`) is caught, and its message should be worded to match. Both additions are optional, so every other manifest and activation still typechecks and `TAB_PLUGIN_API_VERSION` stays at 1. Deliberately *not* done: widening `editGesture` (`src/plugins/api.ts:108`) from its single `'open external'` value. The navigator gesture already routes through the `edit` command, so widening that enum would add a second mechanism for something the first already covers.

**The image payload carries a mode.** `ImagePayload` (`src/plugins/image/shared.ts`) gains an **optional** mode field distinguishing a tab opened as a viewer from one opened as an editor, absent meaning viewer, with its type guard extended to match. `IMAGE_PAYLOAD_SCHEMA_VERSION` stays at **1** and the pinned literal in `web/src/plugins/registry.tsx:73` is untouched. The version guards a contract change between a server and a client that could disagree; bundled plugins ship inside the same build, so they never can, and an optional field an older reader would ignore is not that kind of change anyway. Bumping would mean editing the constant, the registry literal, and the test in `registry.test.tsx` that pins one against the other, for no behavior. The ceiling is explicit: the first change to this payload that *removes* a field, retypes one, or changes what an existing field means does have to bump it, and the field-addition exemption stops there. The image plugin's new edit presentation calls `openOrFocusTab` under the same instance key the inline presentation uses — the file path — so `edit photo.png` on an image already open as a viewer focuses that tab and flips it to edit mode through `updateTab` rather than opening a second one. The manifest requests `updateTab` in addition to what it already asks for.

**Saving an edit.** A new `src/plugins/image/edit.ts` exporting a function that takes the tab's server-owned image path and a PNG data URL, picks the next free `<base>.edit-<n>.png` in that directory, writes it, and returns the basename written. It rejects anything that is not a PNG data URL. The numbering logic is close enough to `nextShotName` (`src/plugins/video/shot.ts:10`) that duplicating it would trip the duplication check `npm run check` runs, so that function is generalized first: a shared helper takes the directory, the source filename, and the separator token (`shot` or `edit`) and returns the next free numbered sibling, and `src/plugins/video/shot.ts` is rewritten to call it. This is a decision, not a contingency — one rule for "numbered file beside an original" belongs in one place. The other candidate for reuse, `nextFreeName` (`src/editor/next-free-name.ts`), is deliberately **not** the base: `shot.ts:8` already records why, and the reason still holds — it starts from a candidate name and appends a suffix only once that name is taken, while these always carry a number and use a different separator. The implementer should not re-litigate that.

**The image plugin answers one intent.** `src/plugins/image/activate.ts` currently refuses everything (`:44`, `unknown image intent "…"`). It gains a `save-edit` intent taking a PNG data URL, calling the save function with the authoritative tab payload's path, and returning the written basename. An unknown intent name or a malformed payload stays a `rejectRequest`, leaving the plugin running; a tab payload failing its own guard stays a `reportFailure`. The client never names a destination, a filename, or a directory. The manifest's capability list is unchanged for this — it already requests `rejectRequest` and `reportFailure`.

**Refusing a host-initiated close.** A plugin can close its own tab today (`web/src/plugins/api.ts:22`, `close()`) but cannot refuse a close the host initiated, which is what an unsaved edit needs. The app already has the whole mechanism for this, built for editor tabs, and the plan extends it rather than adding a parallel one. `TabPluginClientCapabilities` (`web/src/plugins/api.ts:6`) gains one additive field: a way for a plugin to register a dirty handle for its own tab, **shaped exactly like `EditorTabHandle`** (`web/src/EditorTab.tsx:24`, `{ isDirty(): boolean; save(): Promise<void>; focus(): void }`) so the guard code needs no new shape to reason about. The host owns everything else — it decides when to ask and draws `SaveChangesDialog` itself; the plugin supplies only the handle. That split is deliberate: a plugin must not render its own modal over the app, choose a host dialog's wording, or block a close indefinitely. The handle is registered on mount and dropped on unmount, so a reopened tab never inherits stale dirty state. Additive, so `TAB_PLUGIN_API_VERSION` stays at 1 and no other plugin changes — a plugin that registers nothing behaves exactly as today.

**Generalizing the guard to reach plugin tabs — one map, not two.** Plugin dirty handles go into the **existing `editorHandles` map** (`web/src/App.tsx:112`), renamed to reflect that it now holds any dirty-capable tab handle. A second parallel map was considered and rejected as the larger change: it would have to be created in `App.tsx`, threaded through `AppMain.tsx` to both consumers, and consulted alongside the first at four lookup sites. Reusing the one map costs almost nothing, because every existing reader already goes through the handle's three methods and nothing else — `CloseSaveGuard.tsx:24`, `:37`, `:50` and `AppMain.tsx:102` (`onFocusEditor`) all just look up by label and call `isDirty`, `save`, or `focus`. That is exactly why the plugin handle is `EditorTabHandle`-shaped.

The whole change is then three small edits. `PluginTabLayer` registers and drops the handle with the same ref-callback pattern `MountedViewLayers.tsx:75` already uses for editor tabs (set on a handle, delete on null), so a closed or remounted tab never leaves stale dirty state behind. `anyDirtyEditor` (`web/src/dirtyEditors.ts:8`) has one editor-specific clause — the `tab.editor &&` filter at `:9` — which is dropped so the query answers for any tab with a registered handle, and the function is renamed to match; its two call sites in `useUnsavedQuitGuard` (`:24`, `:33`) follow. `CloseSaveGuard`'s guard function (`web/src/CloseSaveGuard.tsx:21`–`:27`) and its three dialog handlers then need **no change at all**: **Save** calls the image editor's save, which writes the numbered PNG and then closes. Nothing about the editor tab's behavior changes.

**The edit model.** A new `web/src/plugins/image/edit-model.ts` holding the operation types (crop with its rectangle, rotate with its direction, flip with its axis, resize with its target dimensions), the ordered list plus its undo cursor, and pure functions to append an operation, step the cursor back and forward, and compute the output dimensions a list produces from a given source size. Keeping this pure and DOM-free is what makes the geometry testable without a canvas — dimensions after a rotate-then-crop are arithmetic, not rendering. Undo and redo are the cursor alone: stepping back moves it, stepping forward moves it, and appending truncates the list at it. The app's existing `UndoBuffer` (`web/src/editor/undo.ts:11`) is deliberately not reused — it is a snapshot stack typed to `EditorState` with keystroke coalescing, a cap, and a `seal` for cursor moves, none of which an op list needs, and generalizing it would mean touching the text editor's undo to gain nothing.

**Rendering the model.** A new `web/src/plugins/image/edit-render.ts` with the single function that replays an operation list from the decoded source image onto a canvas context, and the one that flattens the current state to a PNG data URL for saving. Every operation is native canvas work — a `drawImage` onto a sized canvas, under a transform for rotate and flip and with a source rectangle for crop, and `toDataURL('image/png')` for the flatten — so nothing here computes pixels by hand and no imaging library is involved. It is the only module that touches a canvas, and it is separate from the model both to keep each file well inside the 200-line limit and so that a change to how an operation is drawn cannot change what the operation means.

**The editor body.** A new `web/src/plugins/image/ImageEditor.tsx` rendering the toolbar above the canvas stage, and a `web/src/plugins/image/CropOverlay.tsx` for the drag rectangle and its edge and corner handles, which the resize gesture reuses for its corner drag. A `web/src/plugins/image/useImageEdit.ts` hook owns the model state, the undo and redo key bindings (consulting the host's `active` flag before acting, as a mounted-but-hidden plugin tab must), the dirty flag it reports to the host, the save intent call, and the timed confirmation. `ImageTab.tsx` keeps the header and switches between the existing viewer stage and the editor body on the payload's mode; the header gains the **Edit** control beside the split action, a **Save** control and the dimension readout while editing, and a **Done** control to leave edit mode. Splitting the work this way keeps every file inside the 200-line limit — `ImageTab.tsx` is at 100 lines today and the editor is the larger half.

**Styling.** New rules in `web/src/theme.css` for the toolbar, the canvas stage, the crop overlay and its handles, the dimension readout, and the save confirmation, alongside the existing `.image-*` rules rather than replacing them. The viewer's zoom badge, stage, and metadata rules are untouched.

**Ordering.** Land the two plugin-API extensions first — the declaration's edit presentation with its activation validation, then the client's dirty handle and the guard generalization — so the plugin has something to compile against. The guard generalization must land as one step: the map's rename, the rename of `anyDirtyEditor` and the dropping of its `tab.editor` clause, and its two call sites in `useUnsavedQuitGuard` all typecheck only together. Then the shared numbered-sibling helper and the video plugin's move onto it, which must also land together or `src/plugins/video/shot.test.ts` breaks. Then the optional payload mode, the server-side save and its intent. Then the client model and renderer, then the editor body and the header controls. Then the `edit` dispatch in `OpenFileManager` last — it is the step that changes what the navigator gesture, the quick-open picker, and transcript file links do, so it lands only once there is something for them to reach. Every new `src/` import carries the `.js` extension per the NodeNext rule, and payload field lookups use `??` rather than `||`.

**Specs.** Rewrite the body of `product/specs/image-tab.md` to cover the two modes, the Edit control, the five operations, undo and redo, the save-as-numbered-PNG rule and its flattening consequences for animated GIF and SVG, the unsaved-changes dialog, and the dirty marker — including an explicit note at `:109` that the marker is a recorded exception to the `[[tab-label-no-markers]]` rule that sentence currently cites. Update `product/specs/tab-plugins.md:113` (the bundled-image-plugin section), which today says the plugin "answers no intents" and "declares no command and no file-navigator edit gesture"; document the new edit presentation in the declaration section and the plugin's ability to register unsaved work with the host. Update `product/specs/editor-tab.md:3`, where the `edit` command is defined as opening "a plain-text file", and `:136` ("Closing with unsaved changes"), noting that the same dialog now covers image tabs; and `product/specs/open.md` for the dispatch-by-type rule and the loss of raw-text editing for image files. Update `product/specs/quit-confirmation.md` so the whole-app prompt accounts for unsaved image edits. Update `product/specs/file-navigator-tab.md:166` (Shift+double-click) and `:417` (Shift+Enter), where the image exception is described as opening the plain-text editor.

## Tests

Server tests are colocated as `src/**/*.test.ts` and client tests as `web/src/**/*.test.tsx`, mirroring the image and video plugins' existing files.

- The shared numbered-sibling helper — numbering starts at 1, takes the lowest free number, skips a name already on disk, frees a deleted number for reuse, and produces `.shot-<n>.png` and `.edit-<n>.png` from the same code path. The existing `src/plugins/video/shot.test.ts` cases must still pass unchanged against the rewritten `nextShotName`.
- `src/plugins/image/edit.test.ts` — a valid PNG data URL writes beside the source path and returns the basename; a non-PNG data URL and a bare base64 string are both rejected; a second save writes `-2` without touching `-1`; the destination is derived from the payload path alone and never from anything the caller supplies.
- `src/plugins/image/activate.test.ts` — extend for the new surface: the edit presentation opens a tab in edit mode under the file-path instance key; the same file already open as a viewer is focused and flipped through `updateTab` rather than opening a second tab; `save-edit` with a valid payload writes and returns the name; a malformed `save-edit` payload and an unknown intent name both reject without disabling; an invalid tab payload reports failure.
- Declaration validation around `validateActivation` (`src/plugins/activate.ts:36`) — a declaration marking itself an editor with no edit handler disables the plugin at activation with that reason, alongside the existing `selectionAction` case, and the image manifest's claims still collide with no other bundled plugin's.
- `src/open-file-manager.test.ts` (or the `edit` command's own test file) — `edit photo.png` dispatches to the image plugin rather than the plain-text editor; `edit src/index.ts` and `edit Makefile` still reach `openInEditor`; `edit photo.png:42` opens the editor and discards the line number; resolving an image extension does not activate the plugin; the sync-path branch is unaffected.
- `web/src/plugins/image/edit-model.test.ts` — appending an operation truncates a pending redo; undo and redo step the cursor without mutating the list; output dimensions after a rotate, after a crop, after a resize, and after a rotate-then-crop sequence are correct; a crop rectangle clamped to the image bounds cannot produce a zero or negative dimension.
- `web/src/plugins/image/ImageEditor.test.tsx` — the toolbar offers all five operations; each applies and updates the dimension readout; `Cmd+Z` and `Cmd+Shift+Z` step back and forward and neither fires while the host reports the tab hidden; Save sends `save-edit` with a PNG data URL and shows the returned filename, which clears after the confirmation window; an invalid save result reports failure; a crop drag produces the rectangle the released pointer describes and clamps at the image edges.
- `web/src/plugins/image/ImageTab.test.tsx` — extend for the mode switch: a viewer-mode payload renders the existing zoom-and-pan stage with the zoom keys live and no toolbar; an edit-mode payload renders the editor; the Edit and Done controls move between them; the viewer's zoom, pan, and orientation behavior is unchanged in viewer mode.
- `web/src/CloseSaveGuard.test.tsx` — extend for the per-tab path: a plugin tab with a registered dirty handle raises `SaveChangesDialog` on close; **Save** calls the handle's `save` and then closes, **Don't Save** closes without saving, **Cancel** closes nothing and returns focus; a plugin tab with no handle, and one whose handle reports clean, close immediately; every existing editor-tab case still passes unchanged.
- The two bypass paths, in the tests covering `useUnsavedQuitGuard` and `dirtyEditors` — a dirty plugin tab makes `quit` and closing the last tab raise the whole-app unsaved prompt instead of the plain quit dialog, and arms `beforeunload`; a clean one does neither; a dirty *editor* tab still does both, so dropping the `tab.editor` clause widened the query without breaking it, and a tab with no registered handle at all still reads clean.
- `web/src/plugins/PluginTabLayer.test.tsx` — the dirty handle is registered on mount under the tab's label and dropped on unmount, so a reopened tab never inherits stale dirty state and a closed tab leaves nothing in the map.
- `web/src/plugins/image/ImageEditor.test.tsx`, for leaving edit mode — Done with unsaved edits raises the dialog and each of its three buttons does the right thing; Done with no edits leaves immediately; a save clears the dirty state so the next Done does not ask.

## Out of scope

- **The `@unlayer/react-image-editor` dependency and any CSP relaxation.** No third-party editor, no `cdn.unlayer.com`, no `projectId` or licence file, and no change to `src/index.ts:19`.
- **Draw, text, shapes, stickers, frames, and filters.** Geometry only. These need an overlay object model, selection handles, font loading, or a filter pipeline, none of which this version builds.
- **The AI assistant.** No AI features of any kind, and no outbound network call from the editor.
- **Overwriting the original.** There is no save-in-place and no destructive save. Every save is a new numbered file.
- **Output formats other than PNG.** No JPEG quality slider, no WebP output, no format picker, and no preserving an animated GIF's frames or an SVG's vector nature through an edit.
- **Numeric entry for crop and resize.** Both are drag gestures with a live readout; there are no typed width, height, or offset fields, and no aspect-ratio lock or preset sizes.
- **Persisting an in-progress edit.** The tab stays a live in-memory view: an unsaved operation list is not persisted, not restored by `--relaunch`, and not captured by a profile beyond the file a profile already records for a plugin tab.
- **Editing more than one image at a time.** No batch operations, and the file navigator's selection-action contribution is not used — the selection route stays audio's alone.
- **An escape hatch for editing an image as raw text.** `edit photo.png` opens the image editor with no way to force today's plain-text behavior for that path.
- **Changing the editor tab.** The editor tab's own dirty behavior is untouched: it gains no tab-strip marker, and its dialog, guard, and specced behavior stay exactly as they are. Only the guard's *lookup* is generalized to see plugin tabs too.

## Open questions

None. The three question rounds settled every point the plan turns on: native duplication over the CDN package, geometry-only scope, numbered `.edit-<n>.png` saves beside the original, all three entry points with core `edit` dispatching by type, confirm-before-discard on both exits, PNG output for every source format, full undo and redo, drag-with-live-numbers for crop and resize, save leaving the editor open with a header confirmation, and a dirty marker in the tab strip. The last of those is a knowing exception to `[[tab-label-no-markers]]`; it was raised as such before being chosen, and is recorded in the spec rather than left implicit.
