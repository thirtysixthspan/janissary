# Keep recordings across launches, reap them by age, and gate them on logEnabled

**Complexity: 7/10** — 22 requirements, 22 production files across server and client, ~65 added lines (p=7.24)

## Goal

The feature text: "The recordings in ./janissary/recordings should persist for N number of days where N is determined by the configuration logRetentionInDays flag in .janissary/config.json. logEnabled should gate recording. the log reaper process that runs in the background on launch should be responsible for clearing out recordings older than n days. recordings should not automatically be removed when the application is launched or halted, only when reaped. Prexisting code to save recordings should be updated and used for the implementation of the current feature."

Every asciicast recording Janissary writes lands in `.janissary/recordings/`, and that whole directory used to be deleted at every launch. This change stops clearing it. A single day-to-cutoff helper, `reapFilesOlderThanDays` in `src/state/retention.ts`, now owns the rule all four launch sweeps share, and one unawaited `startLaunchSweeps` call in `src/main.ts` starts the recordings, captures, and both transcript sweeps with one launch time and one day count, each with its own swallowing rejection handler so a failure in one directory cannot stop the others. `logEnabled` becomes the one switch for whether harness, ssh, and shell tabs record, which retires the shell-only `recordShellTabs` key. A tab that will not record says so with a plain `not recording` flag from the moment it opens.

## Requirements

1. `.janissary/recordings/` is not cleared at launch ("recordings should not automatically be removed when the application is launched or halted, only when reaped").
2. Nothing deletes recordings when the application halts ("not automatically be removed when the application is ... halted").
3. A recording is kept for `logRetentionInDays` days, measured from its last modification ("should persist for N number of days where N is determined by the configuration logRetentionInDays flag").
4. A `logRetentionInDays` of `0` deletes every recording last modified before launch (the shared key's existing meaning, "with `0` keeping none from earlier runs").
5. The recording sweep runs once per launch, started with the other three through one unawaited `startLaunchSweeps` call in `src/launch-sweeps.ts` ("the log reaper process that runs in the background on launch should be responsible for clearing out recordings older than n days").
6. The recording sweep never delays startup ("runs in the background on launch").
7. The recording sweep never deletes a recording last modified at or after launch, including when `logRetentionInDays` is `0` (the cutoff the existing sweeps share).
8. The recording sweep runs at launch whether `logEnabled` is true or false (user answer: "Always reap"), and each sweep has its own swallowing rejection handler so one failure cannot stop the others.
9. The recording sweep deletes only regular `*.cast` files directly inside `.janissary/recordings/`, including a `.cast` that another tool put there (user answer: "Direct .cast files").
10. The recording sweep never deletes a subdirectory, a symbolic link, or a file with another extension in `.janissary/recordings/` (user answer: "Direct .cast files").
11. With `"logEnabled": false`, a named-harness tab writes no recording, whether it is local or remote ("logEnabled should gate recording"; user answer: "All three, drop key").
12. With `"logEnabled": false`, an ssh tab writes no recording (user answer: "All three, drop key").
13. With `"logEnabled": false`, a shell tab writes no recording (user answer: "All three, drop key").
14. With `"logEnabled": false`, a harness tab still gets its screen reader, capture wiring, and transcript tailer. Only the recorder is withheld ("logEnabled should gate recording" gates recording only).
15. With `"logEnabled": false`, no `harness recording failed`, `ssh recording failed`, or `shell recording failed` notification is raised, because no recorder exists to fail.
16. `recordShellTabs` is no longer a config key. A `config.json` that carries it is decoded as if it were absent, and a shell tab records exactly when `logEnabled` is true (user answer: "All three, drop key").
17. A fresh `config.json` no longer writes `recordShellTabs` (user answer: "All three, drop key").
18. When Janissary writes an existing `config.json` for any other reason (a missing-key backfill, the `notifications` move, or a `theme`/`syntax`/plugin-settings update), the `recordShellTabs` key is removed from what it writes (user answer: "Ignore, strip on write").
19. Loading a `config.json` that carries `recordShellTabs` does not, on that account alone, rewrite the file (user answer: "Ignore, strip on write" — removal happens on a write made for another reason).
20. `play <name>` resolves to the newest recording of that name on disk, from any run, including while `logEnabled` is false (user answer: "Yes, newest any run").
21. With `"logEnabled": false`, the recording flag on a harness, ssh, or shell tab is drawn plain and inert, never green, with the tooltip and accessible name `not recording`, from the moment the tab opens and for its whole life (user answers: "\"not recording\" not highlighted in green", "Plain, inert, new label").
22. With `"logEnabled": true`, a tab that has not yet produced output keeps its plain flag labeled `recording` (user answer: "Plain, inert, new label" — "The pre-output plain flag keeps \"recording\"").
23. All four age sweeps delegate to one `reapFilesOlderThanDays` helper that owns the single day-to-cutoff rule, the single `DAY_MS`, and the uninitialized-directory guard; each wrapper only supplies its directory and extension.
24. A shell tab of a plugin whose declaration asks for `recordsTerminal` is marked `recordingOff` by `openPluginTab` when the tab is minted, before its first state broadcast and before any terminal is handed to recording, even while the tab is still provisioning its workspace clone or remote connection.
25. The shell plugin's `not recording` fact is pinned from the tab envelope through `PluginBody`, `usePluginCapabilities`, and `createPluginClientCapabilities` to `ShellTabMeta`, and the harness tab's from `HarnessView` through `HarnessTab` to `HarnessTabMeta`.

## Design decisions

- Extend the existing recording writer, `HarnessRecorder` and `src/harness/recording-file.ts`, rather than adding a new one. The recorder itself is unchanged. The gate sits where each recorder is constructed ("Prexisting code to save recordings should be updated and used"; Assumption 4).
- Stop clearing recordings by removing the `clear` from the `harnessRecording` registry entry, as the capture and transcript entries already do (Existing functionality 4).
- Share `logRetentionInDays` rather than adding a recording-only key (feature text; user answer: "No UI, timer, new key").
- One helper owns the day-to-cutoff rule. `reapFilesOlderThanDays` in `src/state/retention.ts` holds the single `DAY_MS`, returns early for an uninitialized directory, and calls `reapFilesOlderThan` with `launchedAt - days * DAY_MS`. Each of the four wrappers is a one-line delegation that forwards its own directory and extension. `src/state/reaper.ts` and its tests stay untouched, and the four wrapper tests keep passing through the real helper.
- One `startLaunchSweeps(launchedAt, days)` call in `src/launch-sweeps.ts` starts all four sweeps with the same launch instant, unawaited, each with its own swallowing `.catch`. It lives beside `src/main.ts` rather than in `src/state/` because it imports the feature owners. `boot` calls it once, so a failure in one directory does not stop the others and startup never waits. The cutoff is fixed at launch time minus `logRetentionInDays` days, so a recording written during the current run is never reaped. Ceiling: a run that stays up for weeks keeps every recording it writes until the next launch.
- Reuse `reapFilesOlderThan` unchanged with the `.cast` extension (user answer: "Direct .cast files"; Existing functionality 1).
- The sweep ignores `logEnabled` (user answer: "Always reap").
- `logEnabled` gates all three recorder kinds, and `recordShellTabs` is removed outright rather than kept as a second shell gate (user answer: "All three, drop key"). A project that had `"recordShellTabs": false` but `logEnabled` true starts recording shell tabs again. That is the accepted consequence of dropping the key.
- Strip the retired key on write only. `loadConfig`'s existing rewrite (backfill or `notifications` move) and `updateConfig`'s merge both delete `recordShellTabs` from the object they serialize. No new write is triggered just because the key is present (user answer: "Ignore, strip on write"; Assumption 9).
- `logEnabled` is read when each tab's recorder would be constructed: at a harness tab's spawn, an ssh tab's spawn, and when a shell tab is minted. Config is loaded once per launch and no runtime command changes `logEnabled`, so a change applies from the next launch (Assumption 10).
- A tab that will not record carries that fact as a server-owned `recordingOff: true` on the `Tab`. `buildTabView` mirrors it onto the harness view and the plugin view the way it mirrors `recording` today, so the client never reads config to draw the flag (Assumption 11, `ai/guidelines/architecture-principles.md` §1). A harness tab and an ssh tab get it when the tab is created, in `spawnTab` and `SshManager`, not when the recorder is built, so a provisioning tab already says so. A shell tab gets it in `openPluginTab`'s mint callback, before the first state broadcast and whether or not a terminal was started (Assumption 5).
- The recorder factories `harnessRuntime` and `sshRuntime` in `src/harness/observers.ts` read `logEnabled` only to withhold the recorder. They never touch `recordingOff`, so one fact has one writer per tab kind.
- The `recordsTerminal` declaration lookup moved from `TabManager.recordTerminal` into a concrete `recordsTerminals(pluginId)` method on `TabOpeningState`, exposed through `OpenTarget`. `recordTerminal` calls it, and `openPluginTab` calls it to decide whether to mark the minted tab. `TabManager` stays at 199 counted lines, one under the 200-line `max-lines` limit.
- The shell gate lives in `TerminalRuntimeManager.registerShellObservers`, which only returns early when `logEnabled` is false. It no longer looks up or marks the tab; the opener is the shell tab's single writer of `recordingOff`.
- The plugin API gains an additive, optional `recordingOff` capability field beside `recording`, so the shell plugin's own metadata row can draw the same flag. Being additive, it does not move the plugin API version (`ai/guidelines/plugins.md`).
- `RecordingFlag` gains an "off" state: the existing plain, non-focusable span with the label `not recording`, which overrides any `onOpen`. The pre-output plain state keeps `recording` (user answer: "Plain, inert, new label").
- `play` is unchanged. It already picks the newest `<name>-<stamp>.cast`, and with recordings kept across launches that now spans runs (user answer: "Yes, newest any run"; Assumption 7).
- The pull request description is authored from the final code, tests, and specs rather than carried over from the plan commit. Every behavior example, screenshot claim, and Do/Expect line names the code path or test assertion that proves it, and claims with no test are marked checked by hand only. The description names `reapFilesOlderThanDays`, `startLaunchSweeps`, and `openPluginTab` where those are the current code paths.

## Assumptions

1. Every recording is written into one directory: `src/harness/recording-file.ts` sets `recordingDirectory` under `.janissary/recordings`.
2. Every recording file name ends in `.cast`: `harnessArtifactFilename(label, startedAt, '.cast')`.
3. The `harnessRecording` entry in `src/state/dirs.ts` has no `clear`; `clearStateDirectories()` clears only the entries that declare one, while the recording entry is initialized like the other kept directories.
4. Harness, ssh, and shell recorders are each built in one factory in one module: `harnessRuntime` and `sshRuntime` in `src/harness/observers.ts` and `shellRuntime` in the terminal runtime. The runtime already accepts no recorder.
5. The shell gate is `registerShellObservers` in `src/terminal-runtime/manager.ts`, called unconditionally by `TabManager.recordTerminal`, which first checks `recordsTerminals(pluginId)` from `src/tab/opening-state.ts`. The open-time mark is set in `openPluginTab`'s mint callback in `src/tab/openers.ts`, which runs after `addPluginTab` mints the tab and before `activate` publishes the dirty state.
6. `recordShellTabs` is no longer declared or decoded. It is deleted from the object in `loadConfig`'s rewrite and in `updateConfig`'s merge, both in `src/config.ts`.
7. `play <name>` already picks the newest recording of a session by its timestamped name: `findRecording` in `src/play/recording-search.ts`.
8. Nothing deletes recordings on shutdown. The launch clear is gone; the only remover is the age sweep started from `boot`.
9. Janissary writes an existing `config.json` from two places: `loadConfig`'s backfill or `notifications` rewrite, and `updateConfig`'s merge. Both strip the retired key.
10. No runtime command changes `logEnabled`. `updateConfig` is called only for `syntaxTheme`, `theme`, and `pluginSettings`.
11. A tab's recording facts are mirrored from the tab onto the harness view and the plugin view in one function, `buildTabView` in `src/tab/view.ts`, which omits each key rather than sending empty or false.
12. Both metadata rows draw the one shared flag component: `HarnessTabMeta` and `ShellTabMeta`, both in `web/src/`.
13. The schedule storage integration suite uses `.janissary/browser-logs/` as its launch-cleared sentinel; browser logs keep a launch clear.
14. A harness tab exists and draws its flag before its PTY spawns, and an ssh tab is created the same way. A shell tab is created through `openPluginTab` before its terminals are handed to recording.
15. `src/tab/manager.ts` is at 199 counted lines of the 200-line `max-lines` limit, while `src/tab/opening-state.ts` has room for the moved lookup.
16. The plugin client capabilities are assembled in one builder that passes `recording` and `recordingOff` through independently: `createPluginClientCapabilities` in `web/src/plugins/plugin-client-capabilities.ts` and the forwarded key list in `web/src/plugins/usePluginCapabilities.tsx`.
17. The four wrappers are `reapHarnessRecordings`, `reapHarnessCaptures`, `reapHarnessTranscripts`, and `reapShellTranscripts`, each forwarding its directory and extension to `reapFilesOlderThanDays`.
18. `startLaunchSweeps` takes `launchedAt` as a parameter so a test can pin it; `boot` passes `Date.now()` once, so all four sweeps share one launch instant.

## UI design

1. **Placement.** The flag stays in its existing slot, first in the metadata row's `tab-flags` group, on harness and ssh tabs (`HarnessTabMeta`) and shell tabs (`ShellTabMeta`). No new surface is added.
2. **Off state.** With `logEnabled` false, the flag is the existing plain film icon, never green, rendered as a non-interactive `span` with `role="img"` (user answer: "Plain, inert, new label").
3. **Wording.** The off flag's tooltip (`title`) and accessible name (`aria-label`) are exactly `not recording`. The pre-output plain flag and the green flag keep `recording` (user answer: "Plain, inert, new label").
4. **Interaction.** The off flag cannot be pressed and does not open a player, even if an `onOpen` handler is supplied.
5. **Keyboard and focus.** The off flag is not focusable and is skipped by Tab, as the pre-output span already is. No key binding is added or changed.
6. **States.** A tab has exactly one of three flag states: off (`not recording`, plain), pending (`recording`, plain, before first output, `logEnabled` true), or recorded (`recording`, green button). A tab opened under `logEnabled` false stays off for its whole life, including while a shell is still provisioning its clone or connection.
7. **Visual consistency.** The off state reuses the `tab-flag tab-recording` classes of the existing plain span, so it needs no new CSS or icon.
8. **Code placement.** The flag stays in `web/src/shared/RecordingFlag.tsx` and its label in `web/src/shared/tab/flag-display.ts`, both shared because two features draw them (`ai/guidelines/react-code-organization.md`). Whether a tab records is server-owned state carried on the tab view, never derived from config on the client (`ai/guidelines/architecture-principles.md` §1).
