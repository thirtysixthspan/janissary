# feat: local Janissary MCP server that lets harnesses ask the user through the question panel

**Complexity: 9/10** — ~1,250 added lines across 24 edited files, ~60 requirements spanning a new server, three harness integrations and a remote relay (p=8.85)

## Goal

Run a local-only MCP server inside the main Janissary process so AI harnesses (claude, opencode, codex) can ask the user a question through Janissary's own question panel instead of through the harness. The server serves one tool, `question`, and is structured so exposing another Janissary command later is one registry entry. A remote harness gets an MCP endpoint on its own host, inside that session's `janus remote-serve`, which relays each call over the session's existing connection to the local Janissary to run. Feature text: "The model is intended to expose all janissary commands, but be limited to just one command `question` at the moment. The intended goal is to allow harnesses to questions the user via the janissary question functionality rather than via the harness."

## Requirements

Server

1. The MCP server runs inside the main application process — feature text: "setup a MCP server for janissary run from the main application process - local only."
2. The server listens on loopback only (`127.0.0.1`) and serves plain HTTP with no TLS certificate; only `/mcp` is served, other paths getting 404 — user answer: "Plain HTTP on loopback": "Serve HTTP on 127.0.0.1 only".
3. Every request requires the server's bearer token in the `Authorization` header; one server-wide token authenticates every harness — user answer: "requests require auth token"; "One server-wide token for every harness."
4. The HTTP guard refuses a present-but-wrong `Origin` with 403, a missing or wrong bearer token with 401, and a non-JSON POST with 415 before the SDK handler runs.
5. The token is persisted beside the port under `.janissary/mcp.json` with mode `0o600`, in a credential separate from the application's session token, and survives a Janissary restart — user answer: "Stable port + persisted token".
6. On its first start a project picks a free loopback port and saves it; every later start reuses the saved port and token — user answer: "Pick free once, persist".
6a. With neither a saved port nor an `mcpPort` override, that first-start port is drawn from the same guard range below `BROWSER_PORT_BAND_FIRST` that browser guards use (the `65280–65535` band is denied to confined harnesses), normalized below the band when a draw lands inside it, and reserved in the shared in-process pool so a browser guard can never claim it; saved ports and hand-edited overrides stay authoritative, the reservation is held once the listener is published, and a draw that cannot be bound gives the reservation back.
7. An `mcpPort` config key overrides the saved port: only an integer from 1 to 65535 is read, anything else decodes as absent, and the key is never backfilled or written into a fresh config — user answer: "An `mcpPort` config key can override it."
8. A port that is already taken stops the server from starting while Janissary runs normally — user answer: "If the port is taken, the server reports it and doesn't start."
9. A failed start records exactly one notification `MCP server failed to start: <reason>` with the reason verbatim; the manager exposes `status()`, `localLaunch()` and `dispose()`, is registered in `MANAGER_DISPOSE_ORDER` ahead of `questions`, and leaves `localLaunch()` undefined on failure — user answer: "Notify; launch w/o MCP": "Janissary starts normally".

Tool

10. The server advertises exactly one MCP tool, `question`, registered from a one-entry tool registry through the SDK handler — feature text: "be limited to just one command `question` at the moment"; user answer: "One `question` tool, kind arg".
11. The `question` tool takes `tab`, `kind` (`ask` or `approve`), `question`, and, for `approve`, `options` — user answer: "arguments {tab, kind: "ask"|"approve", question, options?}".
12. Validation runs before any panel opens and maps each failure to an MCP tool result with `isError: true`; the handler also maps an executor result with `isError: true` to the same shape and forwards the request's `AbortSignal` as the executor's third argument.
13. The four exact error texts are `No tab named "<tab>".`, `kind must be "ask" or "approve".`, `question must not be empty.`, and `approve needs at least one option.` — user answer: "Specific sentences".
14. Tab resolution uses `byLabelOrAlias`, so a label or alias works; an unknown tab returns `No tab named "<tab>".` and registers nothing — user answer: "MCP tool error + message".
15. The question opens the panel on the tab named by `tab`; any authenticated caller can name any open tab and a token is not bound to a tab — feature text: "the question dialog should show up on the calling harness tab - tab must be provided by the caller"; user answer: "No per-tab binding".
16. The tool returns the user's answer as its text result; a user Cancel returns `Question cancelled.` — established behavior: `product/specs/agent-questions.md` § Cancellation.
17. The first call marks the harness view's `mcpUsed` flag and emits a dirty state, so the metadata flag turns green for the tab's life — user answer: "Plain, green once used".
18. An MCP cancellation or a closed connection from the caller aborts its registered question and withdraws the panel, showing the next queued question for that tab if any — user answer: "Withdraw + notify".
19. Withdrawal records the notification `Question from <tab> withdrawn` only while the question is still pending: a named abort handler checks a `settled` flag and a `finally` block removes the listener on every settlement path, so an abort after an answer or a panel Cancel records nothing — user answer: "also record a notification `Question from <tab> withdrawn`".

Unread and notifications

20. A question on a tab that is not focused sets that tab's unread flag through a dedicated `markUnreadQuestion` path that applies the dock, active-tab and secondary-pane checks but not the awaiting-ACP suppression, so the badge appears while the asking agent's ACP query is still open — feature text: "throw the unread flag on the tab if it is not focused"; user answer: "All questions".
21. The `Question from <tab>` notification is still recorded alongside the unread flag, and ordinary `markUnread` callers keep their awaiting-ACP suppression — user answer: "The notification stays".
22. `mcp-failed` and `question-withdrawn` are explicit notification events: `mcp-failed` renders its detail verbatim with an `error` cue, `question-withdrawn` renders `Question from <tab> withdrawn` with a `warning` cue, both have default desktop banners, no config toggle, and one-line rationale comments in `EXPLICIT_EVENTS`, and both bypass focus suppression.

Harness launch

23. Every harness launch receives the server's connection and authentication details through a per-harness fragment that names environment variables only, never a literal token — feature text: "the server should expose its connection and authentication details to all harnesses".
24. Each harness lists the server under the name `janissary`; claude uses `--mcp-config` inline JSON with `${VAR}` references and no `--strict-mcp-config`, codex uses dotted `-c mcp_servers.janissary.*` keys, and opencode uses an inline config layer with `{env:...}` references and `oauth: false` — user answer: "Server name `janissary`".
25. The launch settings give the question tool a week to wait: claude's `timeout`, codex's `tool_timeout_sec=604800`, and opencode's `timeout.execution`; the server sends no progress heartbeats.
26. `harnessSpawnEnv` adds `JANISSARY_TAB` (the tab's label), `JANISSARY_MCP_URL` and `JANISSARY_MCP_TOKEN` in `harnessEnv`'s environment on the host where the harness runs; claude also gets `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0` and `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT=0`.
27. A `harness … --no-mcp` launch and an `--offline` launch receive no MCP flags and no MCP environment variables; the parser accepts `--no-mcp` with the negative form winning if both forms appear — user scope extra: "`--no-mcp` launch flag".
28. A harness launched while the server is not running receives no MCP flags or variables; one `mcp` decision computed from the flag, `--offline` and `localLaunch()` drives both the command fragment and the environment so they cannot disagree — user answer: "Harnesses launched while it's down get no MCP flags or variables."
29. The New harness dialog has an **MCP server (--no-mcp to disable)** checkbox after **E2E browser**, checked by default; unchecking it adds `--no-mcp` when not offline, and checking **Offline** clears and disables it, re-enabling it when Offline clears.
30. A harness tab launched with MCP config shows a two-state `mcp`/`mcpInUse` metadata flag using the `faServer` glyph, plain from launch and green after the first call; colocated tests pin both the server-side derivation and the rendered glyph, tooltip and active class.
31. When the current harness tab's question resolves while focus is inside the panel (leaving focus on `document.body`), `useQuestionFocusReturn` calls `focusCenterVisibleTab` to return focus to that tab's terminal; focus elsewhere is left alone.

`mcp` command

32. An `mcp` command reports the server's state from `status()` — user scope extra: "`mcp` status command".
33. While the server runs, `mcp` prints the four lines `status: running`, `url: http://127.0.0.1:<port>/mcp`, `port: <port>`, `tools: question`; while not running it prints only `status: not running` and `reason: <reason>` — user answer: "Key/value block"; "status + reason".
34. The `mcp` command reads only `status()` and never prints the token — user scope extra: "without printing the token".

Remote

35. While a remote session is connected, a far-side MCP endpoint serves harnesses on the remote host, inside that session's `janus remote-serve` — user answer: "what we want is for an establish connection to a remote machine, where a harness is being run, for a mcp server to be available."
36. The endpoint is created lazily on the first `spawn` with `mcp: true`, mints its own token with `makeToken`, claims a loopback port from a reserved band, serves `/mcp` through the same guard and handler, and keeps both listener and token for the process's life so they survive a detach — user answer: "the mcp server could be remote".
37. The far-side connection and token reach the harness through `harnessSpawnEnv` on the far side; the local server's persisted token never leaves the local machine — user answer: "Far side mints its own"; "The local server's persisted token never leaves this machine".
38. Each call is relayed back to the local Janissary as an `mcp-call` frame over the session's existing connection and answered with a correlated `mcp-result`; the local side runs the same local executor a local call uses, deduplicates re-sends by `call` id, and a remote harness can only run commands on the local process — user answer: "but pass commands back to the local machine for execution"; feature text: "can only run commands on the local process."
39. A detached remote session's harness gets no MCP access: its calls fail after the grace window, and a deliberate Detach is not signalled to the far side — user answer: "dettached sessions will not have access to the janissary mcp".
40. The remote protocol is version 49, adding `mcp-call` (`call`, `tool`, `args`) and `mcp-result` (`call`, `text`, `isError`) frames with `args`/`text` declared as base64 text fields and codec decode cases; the `spawn` frame carries an `mcp?: boolean` that the decoder validates and preserves, including an explicit `false`, so the far side starts its endpoint.
40a. The same version 49 also admits an `mcp-cancel` server frame keyed by the `call` id with no base64 field: the far side sends it from the caller-abort handler and from each grace-expiry `fail()` before rejecting, while an answered call sends none; the codec decodes it, the channel classifier routes it to `mcpRelay.cancel`, and the relay aborts that call's `AbortController` so the local executor withdraws the panel, records `Question from <tab> withdrawn`, promotes the next queued question and leaves an already-answered call unaffected. The far side's link gate lets `mcp-cancel` through while detached so an expiry during a link loss is queued by the detached peer; a cancel for an unknown id or a second cancel changes nothing.
41. `mcp-call` arguments cross the wire through exactly one base64 pass: the far side puts plain `JSON.stringify(args)` in the frame and the codec performs the only encoding; a malformed frame is answered locally with `Malformed MCP arguments: <args>` as an `isError` result, registers nothing, and never throws out of the channel handler.
41a. A parsed argument value that is not a non-null, non-array object — `null`, a string, an array, a number or a boolean — gets that same exact `Malformed MCP arguments: <args>` `isError` answer at the relay before any `AbortController` or pending entry is created, so it opens no question, holds no call id, and lets a later valid call with the same id register and answer from its own execution.
42. A far-side endpoint's port bind failure is contained to that endpoint: an `'error'` listener records the reason before `listen()`, `launch()` throws instead of publishing an unbound address, the reason is reported through `output` frames to the colliding harness and to every later harness that asks for that endpoint, the claimed port is released in `dispose()`, and the session and its other tabs keep running.
42a. The bind outcome is a per-endpoint promise settled by the server's `listening` and `error` events; `launch()` awaits it and re-sends the stored reason to its own caller before throwing, and `RemoteProcesses.spawn` creates and launches the endpoint before `harnessSpawnEnv` builds the environment, passing the resolved launch into `spawnPty`, so a failed bind places no unbound `JANISSARY_MCP_URL` in a harness and is reported by the existing exit-code-1 branch.
43. Calls hold through a lost link for a 60-second grace window, one-second ticks, starting when the link drops even for a call already delivered to the local side and still waiting for an answer — user answer: "Hold with a grace window".
44. The link-loss signal is a real predicate threaded from `DetachedPeer.linked()` (sink installed and not stopped) through `RemoteServer.linked()` (peer's state, or stdout writability and a detach flag before a peer exists) into `ProvisionContext` and `RemoteProcesses` and into `FarSideMcp`; a single watcher polls it while calls are pending, starts the window on a false reading, and is restarted after a successful in-window re-send so a second drop also expires.
45. A link that returns within the window re-sends every waiting call under its original `call` id and delivers the answer once; a call made during the window waits like an in-flight one — user answer: "Hold over reconnect".
46. When the window ends with no link, every waiting call fails with the tool error `Janissary is not connected.`, and a call made while detached fails at once with the same text before any `mcp-call` frame is sent, so it leaves no question for a later attach — user answer: "If no link returns in time, they fail"; "calls made while detached fail the same way at once".
47. Once a link exists again (reconnect or Attach), new calls relay normally — follows from requirement 35.

## Design decisions

- The `question` tool is an ordinary blocking MCP tool call whose result is the user's answer, not MCP elicitation. Elicitation renders in the harness's own UI, and the 2026-07-28 protocol revision removes the server-to-client request channel it uses. The tool callback awaits the existing `Questions.register` so queueing, notifications and cancellation behave as they already do. Sources: https://code.claude.com/docs/en/mcp.md, https://opencode.ai/docs/mcp-servers.md, https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28.md, https://developers.cloudflare.com/agents/model-context-protocol/guides/migrate-to-mcp-sdk-v2/
- Each harness is pointed at the server per launch, without writing the user's own harness config, and reads the bearer token from an environment variable rather than argv: claude through `--mcp-config` inline JSON with `${VAR}` expansion (no `--strict-mcp-config`, which would drop the user's own servers), codex through per-server dotted `-c mcp_servers.janissary.*` keys (never a whole-table override), and opencode through an inline `OPENCODE_CONFIG_CONTENT` layer with `{env:...}` references and `oauth: false`, verified against the installed 2.x binary. The token reference is single-quoted with `shellQuote` so it stays unexpanded in argv, while the codex URL double-quotes `$JANISSARY_MCP_URL` for the launching shell. The token variable name avoids the `ANTHROPIC_*` prefix that claude blanks in headers. Sources: https://code.claude.com/docs/en/cli-reference, https://code.claude.com/docs/en/mcp.md, https://learn.chatgpt.com/docs/config-file/config-advanced, https://learn.chatgpt.com/docs/extend/mcp.md?surface=cli, https://opencode.ai/v1/docs/config/, https://opencode.ai/docs/mcp-servers.md
- Each harness's MCP tool timeout is raised per server at launch so a question waiting on a human is not abandoned (codex `tool_timeout_sec` defaults to 60 s; claude aborts an HTTP call idle for 5 minutes and moves a call running past 2 minutes to the background; opencode's execution timeout defaults to 12 h). This is done with launch settings alone: claude's idle abort and auto-background are switched off through its two environment variables, so the server needs no progress-heartbeat code.
- The MCP listener binds loopback only and serves plain HTTP behind a guard that refuses a present-but-wrong Origin, requires the bearer token in the `Authorization` header, and rejects a non-JSON POST. It reuses `originAllowed` and `tokenMatches` from `src/security.ts`, adds a `bearerToken(request)` header helper, and uses a credential separate from the application's session token, as `product/specs/harness.md` requires. The remote hop is encrypted by SSH, so no TLS is used.
- The MCP protocol layer is the official TypeScript SDK v2 — `@modelcontextprotocol/server@2.4.0` with `@modelcontextprotocol/node@2.1.2` — using the stateless `createMcpHandler(() => createServer())` wrapped by `toNodeHandler()` behind Janissary's own guard on a `node:http` server; every new package version passes `check-malicious-package` before it is added. The builder maps validation errors and executor-reported errors to `isError` tool results and forwards the request abort signal unchanged.
- MCP code is a new core subsystem under `src/mcp/`: the request guard, the SDK handler factory, and a tool registry in which each tool is declared once with its input schema (today only `question`). The local process owns `managers.mcp` (`McpManager`) that starts the server and executes tools; `janus remote-serve` mounts the same handler factory with an executor that relays each call to the local side instead.
- The relay uses two remote frames modelled on the existing `acp-tool-request` / `acp-tool-result` pair: a far-side `mcp-call` carrying a correlation id, tool name and plain JSON arguments, and a local `mcp-result` echoing that id with the text result and an `isError` flag. The frame codec owns the single base64 encoding pass, so a malformed frame is answered locally rather than thrown. Adding the frames bumps the remote protocol version to 49.
- The far side mints its own token, claims an ephemeral loopback port from a reserved band, and keeps both for the process's life; no SSH port forward is used. Its `'error'` listener makes a bind collision a contained, reported failure of one endpoint rather than an unhandled error that kills the session; the stored reason is replayed to every harness refused on that endpoint, through existing `output` frames and the spawn catch.
- The no-link signal is a local predicate threaded from the detached peer's installed sink through the server and provisioning context into the send callback and the endpoint's watcher. A held call never enters the peer's replay buffer, so an attach cannot deliver it twice; the far side's `resend()` is the single delivery. The detached refusal is checked before any frame is built.
- Question unread marking is a dedicated path so a pending question badges its tab while an ACP query is still open, without relaxing the awaiting-ACP suppression for ordinary output. The withdrawal notification is gated on the question still being pending and its listener is detached on settlement, so it is recorded only for genuine withdrawals. The focus-return hook is a new web module called from `App.tsx`, not a change to `QuestionPanel`.
- Colocated tests deliberately pin the two-state MCP flag, the handler's registration/error/signal contract, the remote-launch decision at the spawn seam, the link-state predicates, the channel's final-close hook across all five close paths, and the bind-failure and second-drop recovery paths, so each behavior has an assertion beside its code.
- The first-start port is drawn from the existing browser-guard range below `BROWSER_PORT_BAND_FIRST` and reserved in the same in-process `reserved` set through the existing `claimPort` walk, so a confined harness can reach it and a browser guard cannot take it; saved ports and `mcpPort` overrides remain authoritative and the reservation is released on a failed bind, a disposal before publication, or a persistence failure.
- The relay checks the shape of parsed remote arguments immediately after `JSON.parse` and before the pending write, answering non-object JSON with the same `Malformed MCP arguments` text used for a parse failure, so a malformed call claims no id and a later valid call on that id still registers.
- A per-endpoint bind-outcome promise settled by `listening`/`error` lets `launch()` observe a bind that completes after construction returns; endpoint creation and launch move ahead of `harnessSpawnEnv` so the harness environment is built only from a resolved launch and a failed bind becomes a failed spawn rather than a dead address.
- Remote cancellation travels as an `mcp-cancel` server frame within version 49, not a new version: the far side sends it from the abort listener and `fail()`, the relay aborts that call's controller, and the local executor's existing settlement guard decides whether a withdrawal is recorded; the frame is exempt from the detached link gate so an expiry while detached is queued for attach, and channel close still drops entries without sending a cancel.
- The pull request description documents this remote cancellation path: the version-49 frame list names `mcp-cancel` beside `mcp-call` and `mcp-result`, and it states that a caller abort or a grace-window expiry withdraws the local question, closes its panel, records `Question from <tab> withdrawn` and promotes the next queued question while an answered call is unaffected.

## Implementation steps

The delivered server is built in these layers, each self-contained and green on its own.

1. Unread for every question: the `Questions` change callback marks a non-focused tab unread through `markUnreadQuestion`, beside the notification, using the visibility checks without the awaiting-ACP check; `product/specs/agent-questions.md` and `product/specs/tabs.md` describe the badge.
2. Dependencies: `@modelcontextprotocol/server@2.4.0` and `@modelcontextprotocol/node@2.1.2` were audited before being added to `dependencies`, with `--audit ./package-lock.json` passing.
3. `src/mcp/` core: `tools.ts` registry with the single `question` definition and `{ text, isError }` executor contract; `question-tool.ts` with the four exact error texts; `handler.ts` registering every registry entry through `createMcpHandler(() => createServer())`, mapping validation and executor errors to `isError` results and forwarding the request signal; `guard.ts` returning 403/401/415; `bearerToken` added to `src/security.ts`.
4. ## UI design

1. The feature reuses the existing non-modal question panel (`web/src/shared/questions/QuestionPanel.tsx`) on the named tab, rendered by `web/src/MountedViewLayers.tsx` for the current tab.
2. A question panel opening on a harness tab takes keyboard focus by the existing rule (Cancel for `approve`, the text field for `ask`). When the current harness tab's question resolves while focus is inside the panel, `useQuestionFocusReturn` returns focus to that harness terminal through `focusCenterVisibleTab`; focus anywhere else is left alone.
3. The unread flag is the existing tab-strip unread badge, now raised for a pending question even while its ACP query is open.
4. A harness tab launched with MCP config shows an MCP flag in its metadata row, plain from launch and green after the first call, for local and remote tabs alike.
5. The flag uses the `faServer` glyph in the `tabFlagDisplay` registry with the `tab-flag--active` green class for the in-use state.
6. The New harness dialog's **MCP server** checkbox sits after **E2E browser**, checked by default, cleared and disabled by **Offline** and re-enabled when Offline clears.
7. The feature adds no key bindings.
8. A remote reconnect does not change the flag state; the connection plug shows the reconnect and a pending question panel stays up.

## Out of scope

- Exposing any Janissary command other than `question` — feature text: "limited to just one command `question` at the moment."
- A second tool in the registry or per-tool validators; the handler registers whatever the registry declares.
- MCP access for a detached remote session, automatic reattach when a detached harness asks a question, and any protocol change to Detach — user answer: "dettached sessions will not have access to the janissary mcp."
- Network-facing HTTPS, a TLS certificate, and an `mcpHost` override — superseded by the user's decision to keep remote traffic on the session's own connection.
- SSH port forwarding (`ssh -R`) and Unix-socket relays — superseded by a far-side MCP endpoint that relays commands in band.
- Binding a token to a tab — user answer: "Env label + shared token".
- Progress-heartbeat traffic just to keep a waiting call alive; per-harness launch timeouts cover it, and claude's idle/background overrides are launch settings.
- Editing the documentation site or user documentation; behavior documentation lives in `product/specs/` and the in-app help pages.
- A new config key, port range or CLI flag for the reachable-port draw, and any migration of ports already persisted in a project — a saved band port is still used verbatim.
- A protocol version bump for `mcp-cancel`, a new cancellation API in the MCP SDK, or any change to how a harness times out its own tool call.
- Any change to the one-endpoint-per-session lifetime, the far side's hold/re-send/grace timings, its token, or the local manager's own collision handling.
- Change-set statistics, commit counts or SHAs in the pull request description.

## Verification

Run `$janissary/scripts/run.mjs check-diff` after each implementation step. Use the running app for the manual checks and run the named tests for the controlled remote cases.

1. Start the app and type `mcp`. Expect `status: running`, a `url: http://127.0.0.1:<port>/mcp` line, `port:` and `tools: question`, with no token. A failure looks like `status: not running` with a `reason:`.
2. Open `harness claude as asker`. In the harness, enter: `Wait 10 seconds, then call the Janissary question tool with {"tab":"asker","kind":"approve","question":"Ship it?","options":["yes","no"]}.` Switch to another tab before the call. With `asker` still in the background, verify its unread badge and the `Question from asker` notification. Then select `asker` and check that its server flag is green and that the approval panel offers **yes**, **no**, and **Cancel**, with focus on **Cancel**. Clicking **yes** returns `yes` to Claude and moves focus back to the terminal. A failure looks like Claude asking in its own UI, a timeout error, or a missing badge or panel.
3. Repeat step 2 with `harness codex as codex-check` and `harness opencode as opencode-check`. Use `codex-check` or `opencode-check` as the request's `tab` and keep `kind: "approve"`. Leave each approval unanswered for more than two minutes before answering. Both harnesses should still receive the selected option.
4. Open `harness claude as off --offline`, then open the New harness dialog. In the `off` tab, claude's `/mcp` lists no `janissary` server. In the dialog, checking **Offline** clears and disables **MCP server**, and unchecking it re-enables the checkbox.
5. Send a `question` call with a bad `kind`, an empty question, an `approve` with no options, or an unknown `tab`, and confirm each returns its exact error text with no panel; cancel a call from the harness and confirm the panel is withdrawn with a `Question from <tab> withdrawn` line and no line for a question the user already answered.
6. In the local Janissary command bar, run `harness claude as far on <host>` against a configured remote host. Repeat step 2's approval with `tab: "far"`. The panel opens on the local `far` tab and the answer returns to remote Claude. Request another approval and leave it pending. Detach the session from the Sessions tab and Attach within a minute. The panel reappears once on the rebuilt `far` tab. Detach again and wait past 60 seconds. The pending call fails in Claude with `Janissary is not connected.` If a second drop happens after an in-window re-send and no answer arrives, the call still fails with the same text. They confirm that each affected harness gets its stored bind failure before exiting, the remote session keeps serving, and the failed endpoint releases its reservation.
8. A port in `65280–65535` or a harness timeout shows the reachable-port draw did not take effect.

10. On a remote harness, abandon a pending question and confirm the local panel closes, a `Question from <tab> withdrawn` line appears and the next queued question for that tab takes its place; repeat after answering a question and confirm no withdrawal line appears for it.
