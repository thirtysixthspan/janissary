# Arranging tabs from the command line

**Complexity: 5/10** — server-only, with no new RPC or persistence field, but seven forms each carry their own edge cases, three existing operations need focus-preserving variants, the split-pane selection rules need real care, and the change spans a new notification event, a shared quoted-token reader, completion, help, specs, and user documentation.

## Summary

Feature request (verbatim from `product/backlog/features.md`): "Arranging tabs from the command line. add `tab move <tab> <position>`, `tab pane <tab> left|right`, `tab color <tab> <#hex>`, `tab group <tab> <id|name>`, and `tab dock <tab> left|right`. Each would find its tab the way `tab focus` and `close` do, by label or alias. `tab move` would keep the rule that a tab moves only within its group. `tab group` would insert the tab after the last member of its new group, so groups stay contiguous. `tab dock` would refuse a kind that can't dock, such as a harness or editor tab (`sidebars.md` § Docking). `tab split <tab>` would put the tab on a split view."

Everything about where a tab sits can be changed with the mouse: drag a label to reorder it, press Split to move it to the other pane, and use the dock-cycle control to dock it. A profile can set all of it too, including a tab's dot color and group. The command-line feature gives runscripts, scheduled commands, and other tabs the same arrangement controls through the eight `tab` forms, while preserving focus except where docking the active tab requires a center tab to take focus or undocking must establish the first center selection.

## Design decisions

Each decision is settled by the feature text, behavior the app already has, or the user's answer, as stated. The behavior recorded here is the behavior implemented on this branch.

### Forms

1. **The forms are subcommands of the existing `tab` command.** `src/commands/tab.ts` claims the whole `tab` token with `match: (input) => /^tab(?:\s|$)/i.test(input)`, including malformed forms (`application-commands.md` § `tab`), so no new registry entry is needed and no other command can shadow these forms.
2. **Seven new forms.** The six from the feature text are `tab move <tab> <position>`, `tab pane <tab> left|right`, `tab color <tab> <#hex>`, `tab group <tab> <id|name>`, `tab dock <tab> left|right`, and `tab split <tab>`. The user added a seventh, `tab undock <tab>`, so a command can bring a docked tab back to the center strip. The user chose a separate form over making `tab pane` undock, over a `center` side for `tab dock`, and over leaving undocking out. Keywords and sides match without regard to case, like every other command.
3. **`<tab>` is always required.** Each form names its target, as the feature text writes them, so `tab color #ff0000` is malformed rather than meaning the tab it was typed in. The user chose this over defaulting to the issuing tab. A runscript always names its target, so nothing is ambiguous.

### Finding the tab

4. **The target tab is found by label or alias.** Each form resolves `<tab>` the way `tab focus` and `close` do, through `resolveTarget` in `src/commands/resolve-target.ts`: the first tab in the full tab array whose label or display alias matches, ignoring case, hidden tabs included. A miss prints `No tab named "<name>".` in the transcript, the same reply those commands give.
5. **A tab name with spaces is quoted, in every form.** A display title may contain spaces (`tabs.md` § Tab display alias), and so may a label. Such a name must be quoted, so `tab move "review notes" 2` and `tab focus "review notes"` target the first tab shown as `review notes`. A one-word name may be written bare or quoted. Quoting reads single or double quotes through `readToken` in `src/command/quoted-token.ts`, with a backslash escaping the matching quote inside a quoted value and a quote allowed to open mid-token. An empty quoted name (`""`) is malformed. The same quoting rule lets `tab group` take a multiword group name as one selector token. Generic command-target completion may still insert a spaced display name without quotes; see Design decision 28 and the divergence recorded for review.
6. **`tab focus` changes with it.** Today `tab focus` takes the whole rest of the line (`/^tab\s+focus\s+(.+)$/i`), so `tab focus review notes` focuses `review notes`. Under Design decision 5 that input has an extra word and prints `Usage: tab focus <name>.` The user chose this over keeping `tab focus` unquoted. Its other behavior is unchanged: success is silent, and focusing reveals a hidden system tab through `managers.tab.setActiveTab`. Nothing in the codebase builds a spaced `tab focus` line; the only generated ones are `tab focus system` in `scripts/e2e/system-schedules-execution.mjs` and `scripts/e2e/system-schedules-restart.mjs`, which stay valid.
7. **A group selector is one token.** `tab group` takes a single selector token, like the `in group <name|id>` clause. A multiword group name can be quoted; numeric selectors must be positive safe integers. `isValidGroupSelector` in `src/tab/groups.ts` rejects `0` and IDs past `Number.MAX_SAFE_INTEGER`.

### What each form does

8. **Arranging preserves focus except where a selection must be established.** A runscript or a `send` can rearrange the strip while the user keeps working in their own tab. The sidebar rule that a docked tab is never active (`sidebars.md` § The active-tab invariant) means docking the active tab moves focus to the nearest center tab. If `tab undock` runs when there is no active center tab, selection repair activates the newly undocked tab. The user chose these outcomes over focusing every arranged tab and over matching each mouse gesture. Mouse paths retain their current behavior: a drag focuses the dragged tab (`reorderTabToOp` in `src/tab/navigation-commands.ts`), and a mouse undock makes the tab active (`applyDock` with `null`). That's why the command can't call `reorderTabTo`, `moveTabToOtherPane`, or `setDock(…, null)` as they stand: each of those moves focus. A form that reorders the tab array keeps the active tab by label, so `activeTab` is recomputed with `findIndex` after the reorder.
9. **`tab move` places a center tab within its group and pane.** `<position>` is a 1-based place among the tab's strip mates, so `tab move notes 1` makes `notes` the first center tab of its group and pane. In a split, the strip is the tab's own pane. The tab takes the array index of the mate now at that place, using the same remove-then-insert behavior as a drag. `computeReorderTo` in `src/tab/reorder.ts` cannot be reused because it refuses a hidden tab (Design decision 21).
10. **A position past the end moves the tab last.** Any whole number from 1 up is accepted, and one past the last place moves the tab to the end of its strip mates, so a runscript doesn't need to know the group's size. 0, a negative number, and anything that isn't a whole number are malformed. The user chose this over refusing.
11. **`tab move` on a visible docked tab reorders it in its sidebar.** Its mates are every tab record docked on the same side, of any group, including a hidden docked system tab. The command changes the tab's full-array position to the selected mate's position; undocking preserves that position, so it can differ from the tab's center group order. Hidden docked targets use the hidden-tab rule in Design decision 21 instead. The user chose sidebar ordering over refusing visible docked tabs or waiting for an undock.
12. **`tab pane` puts a tab in the named pane.** `tab pane <tab> right` moves the tab to the right pane, opening a split when there is none, the same transition the Split button runs. On a strip with no split every tab is in the left pane, so `tab pane <tab> left` there does nothing. Moving the last tab out of a pane collapses the split, as it does today (`tabs.md` § Split tab strips).
13. **`tab split` is the Split button.** `tab split <tab>` moves the tab to the other pane through the same transition as `moveTabToOtherPane` (`moveToOtherPane` in `src/tab/split.ts`), opening a split when there is none and collapsing it when the tab was the last one in its pane. The user chose this over dropping `tab split` and over a form that only opens a split.
14. **A moved tab shows in its new pane unless that pane holds the active tab.** The selection after `tab pane` or `tab split` follows four rules. First, when the moved tab is the active tab, it stays active in its new pane, and the pane it left shows the tab `moveToOtherPane` restores there, exactly as the Split button leaves it. Second, when a tab that isn't active moves out of the active tab's pane, it becomes the visible tab of the other pane. On a strip with no split that's always the case, so the new right pane shows it and the active tab stays on the left. Third, when a tab that isn't active moves into the active tab's pane, the active tab stays shown and the moved tab joins that pane's strip behind it. The other pane keeps its visible tab, or, when the moved tab was that visible tab, shows its most recently focused remaining tab (`recentLabel` in `src/tab/split-selection.ts`). Fourth, when the move empties a pane, the split collapses and nothing is secondary. A tab made the visible secondary has its unread badge cleared by `repairPaneSelections`, the same as any tab left showing in the other pane (`tabs.md` § Unread badge). The user chose this over a moved tab that never takes the view.
15. **`tab color` changes the dot only.** The tab's dot takes the new color and the group bar keeps its fixed color (`tabs.md` § Fixed color). The user chose this over also recoloring the bar. The value is `#` plus six hex digits in any case, applied exactly as typed even when it's close to another tab's color. It's stored as typed; the parser only checks its shape. A profile's `color` is different: `distinctColor` in `src/tab/colors.ts` swaps it for a palette color when it's too close to one on screen. The user chose the exact six-digit form over also accepting `#rgb` and over nudging like a profile. `profile save` writes the new color, since it captures dot colors live (`profiles.md` § Saving).
16. **`tab group` moves a tab into a group.** The tab is removed and reinserted after the last member of its new group with `insertTabInGroup` in `src/tab/utils.ts`, the placement a newly created tab gets, so groups stay contiguous. A brand-new group has no members, so `insertTabInGroup` puts the tab at the end of the array. The tab keeps its pane and its dock. A name or ID no open group has creates the group, through `resolveTabGroup` in `src/tab/groups.ts` with no creator and the tab's own dot color as the fallback color. An unknown name gets the next free ID, and an unknown positive ID is created and named `group-<id>`. The tab is then the group's first member, so the bar takes its dot color, as a first member's does. Joining an existing group takes that group's ID, name, and bar color from `resolveTabGroup`. A group the tab leaves empty is gone, as when its last member closes. A monitor targeting `group:<n>` starts or stops watching the tab as it joins or leaves, since group targets track membership live (`monitoring.md`). The user chose creating over refusing.
17. **`tab dock` refuses a kind that can't dock.** The kinds that can dock are the file navigator (`view: 'files'`), the notifications tab (`view: 'notifications'`), and any bundled-plugin tab (`view: 'plugin'`, which covers the schedules tab and every shell tab) (`sidebars.md` § Docking). A harness tab (which includes an ssh tab), an editor tab, a monitor reporting tab, and any tab with no `view` can't. The server's `setDock` (`src/tab/operations.ts`) checks no kind today, because every caller is already a dockable tab's own control, so the refusal is new and sits in the command path, not in `setDock`. Docking into a side that holds a tab of the same kind displaces that occupant back to the center without activating it, as `applyDock` in `src/tab/dock.ts` does today.
18. **`tab dock` refuses the last tab in the center strip.** A shell is a plugin tab, so `tab dock janus left` could otherwise leave the strip with no tab. The check counts `isCenterActionTab` tabs: docking a center tab is refused when it's the only one. A hidden tab isn't in the strip, so docking one never trips this check. The user chose refusing over allowing an empty strip.
19. **`tab undock` brings a docked tab back to the center strip.** It clears the dock and places the tab in the focused pane (`focusedPane` in `src/tab/split-selection.ts`), preserving its full-array position (Design decision 11). It doesn't become active (Design decision 8), and a badge it carries stays until the user visits it. When no center tab is active, which a hidden `system` shell plus docked tabs can leave, `repairSelections` makes the undocked tab active, since a strip with a tab always has an active one.
20. **A monitor reporting tab takes move and color only.** It sits in the lower reporting strip with its own dot and bar, drawn by the same `TabStrip`. It belongs to group 0, which `src/monitor/window.ts` documents as "reporting tabs sit outside the action-tab group system", and reporting tabs are kept at the end of the tab array so action-tab indices never shift. `tab move` reorders it among the reporting tabs, which all share group 0, the same group-0 exemption `computeReorderTo` already makes. `tab color` sets its dot only, like any tab's (Design decision 15). Its bar was set to its dot color at creation and keeps that old color, which the user chose over recoloring a monitor's bar too. `tab group` is refused, so a monitor stays outside the group system; the user chose this over moving it into the group, after the improvement pass found group 0. `tab pane` and `tab split` are refused, since a monitor never sits in a center pane, and `tab dock` is refused (Design decision 17).
21. **A hidden tab is arranged while it stays hidden.** For the managed `system` shell while hidden, `tab move`, `tab color`, `tab group`, and `tab dock` change its placement, color, or group without revealing it. For `tab move`, the hidden target uses itself and the center tabs of its group and pane, even when docked; this rule takes precedence over visible-docked sidebar ordering. `tab pane`, `tab split`, and `tab undock` are refused, since each would place a hidden tab in a pane. The user chose this over refusing every form or revealing the tab first.
22. **A form that's already done does nothing, silently.** `tab pane` to the tab's own pane, `tab dock` to its own side, `tab undock` on a center tab, `tab group` to its own group, and `tab move` to its own place all change nothing, emit no state event, and succeed. The user chose this over a notification saying nothing changed. A refusal is checked before the already-done case, so `tab pane` on a hidden tab is refused even though a hidden tab's pane is `left`.

### Replies

23. **Success prints nothing.** Every arranging form is silent when it succeeds, like `tab focus` (`application-commands.md`). The user chose this over a confirmation line. It keeps a runscript's transcript quiet.
24. **Refusals go to the notifications feed, not the transcript.** A well-formed form the app can't carry out sends one notification and writes nothing to the transcript. The user chose this for the last-tab refusal, then for every refusal, over printing them in the transcript. Usage lines and `No tab named "<name>".` still print in the transcript, as they do for every command. Only `tab dock`, `tab pane`, `tab split`, `tab undock`, and `tab group` can refuse; `tab move` and `tab color` always succeed once parsed. The lines are short, as the user chose over lines with a reason and lines with a fix:
    - `Cannot dock "<name>".` for a kind that can't dock (Design decision 17) and for the last center tab (Design decision 18).
    - `Cannot group "<name>".` for a monitor tab (Design decision 20).
    - `Cannot move "<name>" to a pane.` for `tab pane` and `tab split` on a tab that isn't split-eligible (`isSplitEligibleTab` in `src/tab/placement.ts` is false for a docked, hidden, notifications, or monitor tab), and when no second tab can share the split. That last case is when there's no split and fewer than two split-eligible tabs, the case `moveToOtherPane` returns `undefined` for.
    - `Cannot undock "<name>".` for a hidden tab (Design decision 21).
    `<name>` is the name as the user typed it, without its quotes, the same text `No tab named "<name>".` shows.
25. **The refusals use a new explicit `tab` notification event.** It has no config toggle, bypasses focus suppression, and is attributed to the tab the command ran in, like `open-unsupported`, which also moved a command's refusal out of the transcript. Its `notifications.alerts` entry defaults to a desktop banner with the `warning` cue. The existing config backfill (`application-config.md`, "event types missing from `alerts`") adds the `tab` key to an older `.janissary/config.json` on the next start, with no code change. The user chose a new event over a feed-only default and over reusing `manual`.
26. **A malformed known subcommand prints its own usage line.** A missing or extra word, an unterminated quote, an empty quoted name, an unknown side, a position that isn't a whole number from 1 up, a color that isn't `#rrggbb`, and an invalid group selector each print that subcommand's line, exactly:
    - `Usage: tab focus <name>.`
    - `Usage: tab move <tab> <position>.`
    - `Usage: tab pane <tab> left|right.`
    - `Usage: tab split <tab>.`
    - `Usage: tab color <tab> <#rrggbb>.`
    - `Usage: tab group <tab> <id|name>.`
    - `Usage: tab dock <tab> left|right.`
    - `Usage: tab undock <tab>.`
    The user chose per-subcommand lines over one line for every mistake.
27. **Bare `tab` and an unknown subcommand print one summary line.** It reads exactly `Usage: tab focus|move|pane|split|color|group|dock|undock <tab> [argument].` An unterminated quote in the subcommand position itself, as in `tab "focus`, also prints it. The user chose this over printing all eight lines.
28. **Completion follows each target's meaning.** Tab completes the subcommand after `tab`, then a target's label or display title, and `left`/`right` after `tab pane <tab>` and `tab dock <tab>`. A tab name with whitespace is wrapped in double quotes, so typing `"rev` and Tab completes `"review notes" `. The `tab` completer counts preceding words with the shared quoted-token reader, so a quoted name with spaces counts as one word; while the cursor is inside an unfinished quoted name, completion leaves the input unchanged. Position, color, and group arguments receive no `tab`-specific completion. The same label-and-title list feeds generic target completion for `send`, `queue`, `close`/`exit`, and the `schedule ... in <tab>` clause. Those generic handlers do not quote whitespace: `close` accepts the full remainder as a target, but `send`, `queue`, and `schedule` parse one whitespace-delimited target token, so a spaced name offered there is not accepted as a whole target. `monitor` and `unmonitor` target completion is separate: it offers labels of other action tabs and one sorted `group:<n>` selector per action-tab group, not display titles. A display title can still be typed and resolves as a target. The behavior is pinned in the completion specification and the `help keys` assertion.
29. **One combined help row.** The `help/commands.md` row for `tab focus <name>` is replaced by one `tab` row, with all eight forms:
    `` | `tab` | `tab focus <name>`, `tab move <tab> <position>`, `tab pane <tab> left\|right`, `tab split <tab>`, `tab color <tab> <#rrggbb>`, `tab group <tab> <id\|name>`, `tab dock <tab> left\|right`, `tab undock <tab>` arrange a named tab | ``
    It sorts as `tab`, where the old row sat, between `syntax` and `tasks`. The row still contains `` `tab focus <name>` ``, which `src/commands.test.ts` asserts. The user commands table carries the same row.

### How it runs

30. **Parse pure, execute effectful.** A pure parser turns the input into a structured form or `{ error }`, and the command's `run` does the effects (architecture principle 4).
31. **One tab-manager entry point.** The command reaches the arranging operations through one `TabManager` method rather than one per form. The operations live in `src/tab/arrange.ts` over the existing `TabOperationsPort` (`src/tab/operations.ts`), the way `src/tab/user-close.ts` does. `TabManager` exposes the fields that port needs.

## Proposed changes

### Server

- **`src/command/quoted-token.ts`** holds `readToken`, `skipSpaces`, and their shared `Token` type, extracted unchanged from `src/agent/command-parser.ts`. `readToken` returns `undefined` for an unterminated quote. `src/agent/command-parser.ts` imports these helpers without re-exporting them; its `tokenize`, which stops at `execute`, remains local.
- **`src/tab/arrange.ts`** exports `TabArrangement`, a discriminated union of the seven changes, and `arrangeTab(port, label, change)`. It returns `false` for a refusal and `true` for success, including already-complete requests. State changes emit `{ type: 'dirty' }`; no-ops emit nothing.
  - Color: sets `dotColor` to the value as typed.
  - Group: refuses a monitor tab (`isReportingTab`); otherwise resolves the group per Design decision 16, sets `group`, `groupName`, and `groupColor`, removes the tab, reinserts it with `insertTabInGroup` (which renumbers), and restores `activeTab` by the previously active label.
   - Move: finds the tab's strip mates per Design decisions 9, 11, 20, and 21, in array order, and clamps the position to their count. Hidden targets use center mates before the docked sidebar rule; visible docked targets use all same-side docked records. When the mate at that place is the tab itself it does nothing. Otherwise it moves the tab to that mate's full-array index by remove-then-insert, using `removeTabAt` from `src/tab/reorder.ts` and `renumberTabs`, then restores `activeTab` by label.
  - Pane and split: refuses a tab that isn't split-eligible; for pane, does nothing when `centerPane` already equals the side. Otherwise it calls `moveToOtherPane` for the moved array, refuses when that returns `undefined`, and picks `activeTab` (by label) and `secondaryTabLabel` per the four rules in Design decision 14 before calling `repairSelections`.
  - Dock: refuses a kind that can't dock (`isDockableTab`) and the last center tab; does nothing when already docked on that side; otherwise calls `setDock(port, index, side)` from `src/tab/operations.ts`, which already handles displacement, the active-tab invariant, and the split replacement.
  - Undock: refuses a hidden tab; does nothing for a tab that isn't docked; otherwise clears `dock`, sets `pane` from `focusedPane`, leaves `activeTab` alone, and calls `repairSelections`. It never calls `applyDock` with `null`, which would make the tab active.
   The move and pane steps are private helpers in this module, since each has a single caller.
- **`src/tab/dock.ts`** defines `isDockableTab(tab)`, true for `view` `'files'`, `'notifications'`, or `'plugin'`, beside `applyDock`.
- **`src/tab/manager.ts`** exposes `arrangeTab(label, change)`, delegating to `arrangeTab(this, label, change)` in `src/tab/arrange.ts`.
- **`src/commands/parse-tab.ts`** is a pure parser. `parseTabCommand(input)` reads words with `readToken` and returns a focus form, an arrangement target and change, or an error line from Design decision 26 or 27. It checks exact word counts, positive safe-integer positions, six-hex-digit colors, case-insensitive sides, and nonempty group selectors. Quoted multiword target and group names are one token. Usage constants escape angle brackets so Markdown rendering displays placeholders literally. It exports `TAB_SUBCOMMANDS`, the eight keywords used by completion, and imports `TabArrangement` as a type only.
- **`src/commands/tab.ts`**. `run` parses. A parse error appends its line through `appendCommandOutput`, as today. The focus form resolves its target and calls `setActiveTab`, as today. Every other form resolves its target with `resolveTarget` and calls `managers.tab.arrangeTab(target.label, change)`. When that returns `false`, it calls `notify(managers, 'tab', tab.label, …)` with the line from Design decision 24 for that form and appends nothing. `samples` gains one input per new form, such as `tab move notes 2` and `tab dock "review notes" left`, so `src/commands.test.ts` checks them for shadowing.
- **`src/notifications/index.ts`**, **`src/notifications/alert-defaults.ts`**, **`src/notifications/format.ts`** define the explicit `tab` event, its `{ desktop: true, sound: 'warning' }` default, and its detail text formatter.
- **`src/tab/lookup.ts`**, **`src/tab/manager.ts`**, **`src/controller/completion.ts`**, **`src/completion/target-handlers.ts`**, and **`src/completion/index.ts`**. `allLabelOrAliasNames` returns each tab's label and display title in tab order, removing case-insensitive duplicates while preserving the first spelling. The controller passes that list to the existing completion chain, so generic target completions now include display titles as well as labels. `completeTabCommand` adds the eight subcommands, quoted target completion, and `left`/`right` suggestions after `pane` and `dock`. It uses `TAB_SUBCOMMANDS` and the shared quoted-token reader. Generic completions do not quote spaced candidates (Design decision 28).

### Docs and specs

- **`help/commands.md`, `help/tab.md`, and `help/keys.md`**. The combined row replaces `tab focus <name>`; the detailed page covers all eight forms, quoting, group selectors, refusals, no-ops, and exact usage; the key reference covers tab completion and display-title candidates while distinguishing monitor target candidates, which remain tab labels and group selectors.
- **`documentation/user-documentation/command-bar/commands.md`**. The same row replaces the `tab focus <name>` row. The `## tab focus` section becomes `## tab`: its spaced example becomes `tab focus "review notes"`, it gains one example per new form, and its usage paragraph gives the per-form and summary lines and the four notification lines.
- **`documentation/user-documentation/command-bar/tab-completion.md`**. The target-completion table adds `tab` subcommands, label/display-title target names, and pane/dock side candidates; existing generic target rows now include display aliases.
- **`documentation/user-documentation/getting-started/tabs.md`**. In § Switching and reordering, the `tab focus review notes` example becomes `tab focus "review notes"`, and the sentence saying the full text after `focus` is the name says a name with spaces is quoted. Add `tab move` there, `tab pane` and `tab split` to § Working in two panes, and `tab dock`/`tab undock` to the sidebar paragraph near the top. Mouse undocking makes the tab active; `tab undock` leaves focus unchanged unless no center tab is active. ### Implementation order

The implementation is organized around shared parsing, notifications, tab operations, command routing, completion, and the descriptions of their behavior:

1. `src/command/quoted-token.ts` supplies shared token reading to the agent and tab parsers.
2. The explicit `tab` notification is registered with its defaults and formatter.
3. `src/tab/arrange.ts` implements the placement changes and is exposed through `TabManager.arrangeTab`.
4. `src/commands/parse-tab.ts` and `src/commands/tab.ts` parse and dispatch the eight forms.
5. Completion uses the shared parser tokens and target-name list.
6. Specs, help, and user documentation describe the resulting behavior.

## Out of scope

- Moving a center tab out of its group with `tab move`. That's `tab group`'s job (Design decision 9); a visible docked tab follows its sidebar order (Design decision 11).
- Docking a harness, editor, or monitor tab (Design decision 17).
- Recoloring a group's bar (Design decision 15).
- Defaulting `<tab>` to the tab the command was typed in (Design decision 3).
- Changing what the mouse gestures do to focus (Design decision 8).
- Naming or renaming a group. That's the separate "Naming a group from the command line" backlog entry.
- Quote-aware completion for every command. Only `tab` completion quotes spaced target names (Design decision 28); generic target completions surface spaced display names without quoting them.
- Moving a monitor tab into a group, and recoloring a monitor tab's bar (Design decision 20).
