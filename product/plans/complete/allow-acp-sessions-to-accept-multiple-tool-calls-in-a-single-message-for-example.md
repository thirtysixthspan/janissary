# allow acp sessions to accept multiple tool calls in a single message, for example:

**Complexity: 6/10** — ~130 added production lines across 7 files, 10 behavioral requirements, 18 test scenarios (p=6.33)

## Summary

An ACP agent that needs several independent commands for one investigation — the backlog's example is a `file grep`, `file glob`, another `file grep`, `file list`, and another `file glob` issued together — used to spend one provider round trip per command. The delivered tool loop now accepts several commands in one reply: the agent puts each command in its own `janissary` fenced block, every closed block in one reply forms a batch that the host runs in parallel, and each finished command comes back as its own follow-up message. A single block remains valid and still means one command, so existing agents keep working unchanged. The change lives entirely in the shared ACP tool loop, so every consumer — local ask/tell prompts, plugin-owned sessions, agent runs, subagent attempts, and remote-hosted loops — inherits it through `driveToolLoop` / `runToolLoop`. There are no new wire frames, commands, or tabs.

Review of the batch loop also corrected how its work is shown and taught. Every command primer now demonstrates a fenced example for each command it documents, the agent's whole reply keeps its command fences in the displayed text, and ask and tell preambles tell the model to gather all command input before writing its final answer or summary. On the recording side, the transport primer is stored once as the first block's preamble, every reply is captured in arrival order, and a tool command and its result carry a phase and originating command so a batch's results pair with the right commands even out of order. The connection tab shows those blocks as plain-text sections with no Markdown and no duplicated final answers, and its clipboard button opens the record's own JSON file. No command, flag, key binding, or web UI command changed.

## Design decisions established by the feature text or existing behavior

- The feature extends the existing ACP tool loop, not a new subsystem. The example is an agent emitting several file-search commands in one message; it asks for no new transport, tab, command, or user interface.
- Product decision (primary flow): the agent puts **each command in its own `janissary` fenced block**, and all the closed blocks in one reply are the batch. A single block remains valid and means one command. Blocks are identified in order of appearance, but execution is not ordered (next decision).
- Product decision (batch execution): commands in one reply **run in parallel**. The command protocol primer tells the agent that commands in the same batch run at the same time and must not depend on one another's results.
- Product decision (result delivery): **each command sends its own follow-up message to the agent as soon as it finishes**, so the agent can act on a partial result before the rest of the batch drains. Each result is recorded as its own tool entry in the connection record as it completes, with the existing `Output of <command>:` block and closing instruction lines unchanged. Follow-ups are delivered through one serialized pump because `startTurn`/`chunk`/`endTurn` model a single current transcript turn: each command enqueues one result and the pump sends them one at a time in completion order. A new batch extracted from a follow-up joins the same queue behind results already waiting.
- Product decision (failures): a command that throws, rejects, or is refused is **just another result**. Its error or refusal text is delivered in its own follow-up like any other output, the remaining commands keep running, and the run ends only when the agent replies with no commands or the cap is hit. A thrown or rejected command uses the existing `ACP error: <message>` line and no longer settles the run as `failed`; that reason stays in the handler union for other producers.
- Product decision (cap boundary): when a batch is larger than the remaining step budget, **run only the commands that fit** and return a refusal as its own follow-up for each over-budget command. The cap is never exceeded. The refusal text is exactly `ACP: step limit reached; command not run.` Refusals are held in a pending list and flushed into the serialized result pump only once no command is in flight, so executed-command results are delivered before the refusals for skipped commands. Hitting the cap sets a pending-cap flag; a later reply with no commands finishes as `answered` only when the result queue is empty, nothing is in flight, and no cap was hit — otherwise the pump drains the remaining follow-ups and the run finishes as `capped`.
- Product decision (step cap): **each command counts as one step** against the step budget, even when a batch runs in parallel; a batch of five consumes five steps. A correction does not consume the budget, and this version sets no cap on corrections. The budget is configurable: `maxToolSteps()` in `src/acp/drive-loop.ts` reads `maxToolTurns` from `.janissary/config.json` (default 20) and supplies it to both the primer and the loop, so `runAcpToolLoop`'s own default of eight applies only to direct callers with no budget injected.
- Product decision (malformed blocks): **an empty `janissary` block, a block holding more than one command start, or a labelled fence left unclosed corrects the whole reply** in both core sessions and agent runs — send the correction prompt and run none of its commands. An **unowned command** corrects the whole reply only in core sessions, where `toolExtractor` in `src/acp/tool-table.ts` rejects the reply when no granted tool owns every command; agent runs extract with the raw `extractCommandBlock` in `src/acp/command-block.ts`, so a recognized but ungranted command is kept as an ordinary batch member and refused on its own by the agent gate while the rest of the batch continues. A reply with no `janissary` block at all is still a final answer (`absent` in `extractCommandBlock` at `src/acp/command-block.ts`), not a correction.
- Product decision (scope): **every consumer of the shared tool loop** accepts multiple commands — local ask/tell, plugin-owned sessions, agent runs, subagent attempts, and remote-hosted loops. The far side drives the same loop through `driveToolLoop` in `src/remote/serve-acp-loop.ts`, so it is included.
- Product decision (per-command metadata): each `ranCommand` event carries the host (`workspace`) and refusal (`refused`) decision of the command that actually completed, not the last command launched. Because batches launch in parallel and settle out of order, `gatedRunner` in `src/acp/drive-loop.ts` binds each decision to its own result through a completion queue consumed when that result is recorded; identical command text keeps its own decision. `startCommand` calls and `runCommand`'s `string | Promise<string>` contract are unchanged.
- Product decision (protocol wording): **rewrite the command protocol and correction wording from scratch** around parallel batches, with the new terminology used in the primer and in `product/specs/acp.md`. The group of commands in one reply is called a **batch**. The correction sentence is exactly: ``Your reply must contain one or more commands, each inside its own ```janissary fenced block. Try again.``
- Product decision (primer text): `commandProtocolPrimer(maxSteps)` emits exactly the four-bullet primer recorded in Design decisions, with the configured cap in the last line, and the spec quotes it.
- Product decision (fenced examples): every tool primer demonstrates each command it documents with a real `janissary` fenced-block example. `commandExample(command)` in `src/acp/command-example.ts` is the single source of the three-line fence shape, imported by every primer; existing prose, syntax lines, warnings, and reply strings are untouched, bare `Example:` lines become labelled fenced blocks, and each documented command in a multi-command primer gets its own block.
- Product decision (agent-facing preambles): with several commands possible in one reply, an `ask` session's primer adds `ASK_INSTRUCTION` — gather all command input before the final response, which must answer the user's question — after the command-exchange protocol and before the Markdown instruction, only when tools are available. The `tell` role's `TELL_INSTRUCTION` now directs the model to gather all command input and execute all tasks before a final summary that summarizes the work done. Both keep their placement, and a no-tools ask session carries no gathering line.
- Product decision (displayed reply): the loop emits the agent's whole reply through `h.endTurn(buffer)` with matched labelled blocks and their fences intact, so the message shown in the connection tab and transcript contains the commands the agent wrote along with prose before, between, and after the blocks. No block-stripping helper remains; command extraction still runs from the same buffer.
- Product decision (recorded context and replies): the transport primer the model receives is stored once as the first block's `preamble` while `prompt` keeps the user's own text, so the title still comes from the prompt and the connection tab can show the complete provider input as a section. Every non-empty `endTurn` reply is appended to the block's ordered `replies` without settling it, so an early reply does not stop later tool activity; settlement seeds a single reply only when none was captured. `preamble` and `replies` are optional, so older records keep rendering and the payload schema version is unchanged. A tool activity carries an optional `toolPhase: 'command' | 'reply'` and a reply's `toolCommand`, so a batch's results pair with their commands by name rather than adjacency, with legacy adjacent pairing as the fallback.
- Product decision (connection tab presentation): a connection tab renders no Markdown in any section — preamble and every activity entry read verbatim, with only JSON pretty-printing and inline `<function_calls>` parsing as special presentations, and no clickable web links. Each block shows a collapsed `preamble` section first when one was stored, then an expanded `query` section, then its activity entries; captured replies and the final answer are not repeated in the tab. Thought and tool entries start collapsed, query and messages stay expanded, and a reader's toggle survives streamed updates. Every section shares one styling. A tool's command and its reply share one collapsible section labelled `command` and `reply`.
- Product decision (record access): the record tab's clipboard button is **Open record JSON** on every record — it opens `.janissary/connections/<id>.json` in an editor tab through a host-mediated topic action, refuses visibly when the record or file is gone, and no longer depends on an ACP session reference. Popup-row transcript snapshot buttons are a separate surface and keep their behavior.
- The loop is deliberately pure control flow: rendering, command execution, extraction, the primer, the step cap, and the abort signal are injected dependencies. The batch aggregation, serialized result pump, cap accounting, and per-command metadata stay inside that seam rather than reaching into live session state.
- The agent-facing contract is stated in `commandProtocolPrimer` in `src/acp/command-protocol.ts`, the per-tool primers, and the specs (`product/specs/acp.md`, `product/specs/agent-command.md`); quoted strings are character-for-character identical to the code.
- Each tool step is recorded as a `tool` activity entry in the connection record (command and reply as consecutive entries), and `h.ranCommand` in the loop is the hook that records it. Running several commands in one turn still produces one such entry per command.
- No new client/server protocol message is implicated by the feature text. Remote ACP loops already carry multiple `acp-tool-request`/`acp-tool-result` frames per session, so a turn with several commands reuses that correlation rather than adding a frame type.

## Proposed changes

1. **Extraction contract, `src/acp/command-block.ts` and `src/acp/types.ts`.** `extractCommandBlock` and `findCandidate` collect **every** closed `janissary` fence, in appearance order, instead of tracking the last one. `CommandBlockResult`'s valid `batch` variant carries one command and its `CommandBlockSpan` per block (`commands: readonly { command: string; span: CommandBlockSpan }[]`); `mistake` and `absent` are unchanged. `isCommandStart` remains the command-start test so a command whose arguments span several lines stays one command, and a block with zero or two-or-more command starts or an unclosed labelled fence makes the whole reply a `mistake`. A reply with no labelled block still returns `absent`. `AcpLoopDeps.extractCommand` is widened to this result; this is the seam both extraction call sites use.
2. **Granted-tool filtering and budget wiring, `src/acp/tool-table.ts` and `src/acp/drive-loop.ts`.** `toolExtractor` applies ownership to each extracted block and returns the whole-reply `mistake` when any block is unowned, rather than `absent`. Both extraction providers in `driveToolLoop` carry the batch result: `toolExtractor(tools)` for a core snapshot and `(text) => extractCommandBlock(text, snapshot.askUser)` for an agent snapshot, keeping `snapshot.askUser` flowing. `corePrimer` and the loop are both driven by `maxToolSteps()`, which reads `maxToolTurns` from `.janissary/config.json` (default 20); no fixed per-owner step constant remains. `ASK_INSTRUCTION` and the extended `TELL_INSTRUCTION` are appended in `corePrimer` in their role-specific slots.
3. **Batch orchestration, `src/acp/loop.ts`.** `runAcpToolLoop` launches all extracted commands in parallel with the injected `maxSteps` budget (falling back to eight only for direct callers), consumes one step per command, and refuses each over-budget command in its own follow-up with `ACP: step limit reached; command not run.` Refusals are held in a `pendingRefusals` list and flushed into the result queue by `flushRefusals()` only when nothing is in flight — called from `deliver` after the result is pushed and at the end of `launchBatch` after `launching = false` — so executed results are delivered before the refusals for skipped commands. Straddling the cap sets `pendingCap`; a reply with no block finishes as `answered` only when the queue is empty, nothing is in flight, and no cap was hit, otherwise the pump keeps draining and finishes as `capped`. One follow-up per finished command is delivered through a serialized result pump in completion order, using the existing `Output of <command>:` block and verbatim closing lines; each command is recorded through `h.ranCommand` as it completes. A thrown or rejected command becomes its `ACP error: <message>` result instead of a `failed` outcome. A whole-reply `mistake` sends `CORRECTION_PROMPT` without spending a step. `h.endTurn(buffer)` emits the whole reply with its command fences intact; the cold-start retry is unchanged.
4. **Agent-facing wording, `src/acp/command-protocol.ts`, the tool primers, and the specs.** `commandProtocolPrimer(maxSteps)` emits the exact four-bullet primer recorded in Design decisions, with the configured cap in the last line; `corePrimer` assembles it only when a command remains. `CORRECTION_PROMPT`, the over-budget refusal, and every primer's existing prose and reply strings stay verbatim. `commandExample(command)` in `src/acp/command-example.ts` produces the single fenced shape, and each of the fourteen primer sites imports it and adds one labelled fenced example for every command it documents, converting existing bare examples into fences. `product/specs/acp.md`, `product/specs/agent-command.md`, `product/specs/acp-records.md`, `product/specs/connections-tab.md`, and `product/specs/embedded-web-page.md` describe the batch loop, its quoted strings, the fenced examples, the ask/tell instructions, and the recording and presentation changes; quoted strings are character-for-character identical to the code.
5. **Remote forwarding, `src/remote/serve-acp-loop.ts`.** `startRemoteLoop` drops the single `forwarded` flag and correlates through the existing `pending` request-number map, whose entries now carry the command and a settled flag. `runCaller` records the command when it creates the pending entry; `toolResult` ignores a duplicate result and otherwise resolves or rejects that entry; `ranCommand` consumes the single pending entry whose command matches and is settled, and skips the far-side `acp-tool-step`, while workspace commands and gate refusals still emit their normal step even when their text happens to match a pending caller command. Abort rejects and clears all pending entries. No wire frame or frame type changed.
6. **Per-command metadata, `src/acp/drive-loop.ts`.** `gatedRunner` replaces the shared `step` slot with a completion queue local to one `driveToolLoop` invocation. Each command's `DrivenStep` is pushed when its result settles — at call time for a synchronous result, a synchronous throw, or a refusal, and in both handlers of a settled promise — and the loop's `ranCommand` wrapper consumes the next queued step to pass its `workspace` and `refused` to `events.ranCommand`, using a neutral `{ workspace: false }` when the queue is empty. `startCommand` arguments, `runCommand`'s return contract, event ordering, error results, and abort behaviour are unchanged.
7. **Recorded context, replies, and pairing, `src/acp-records/` and the producers.** Add optional `preamble` and `replies` to a connection block and optional `toolPhase` / `toolCommand` to tool activities, accept them in the durable and payload guards, and `reply(id, text)` / `activity(..., phase, command)` in the record store. Core prompts, agent runs, and subagent attempts store the raw prompt with the primer as `preamble` on the first block only and append each non-empty `endTurn` reply; settlement seeds one reply when none was captured. `coreActivity`, `AgentRecordFeed.activity`, the ask/tell record feeds, and the three tool-loop producers forward the phase and originating command so a batch's command and result pair by name.
8. **Connection tab presentation and record access, `web/src/plugins/connections/`.** `ConnectionHistory` renders the stored preamble first as a collapsed section, then the query as an expanded section, then activity entries, with no Markdown renderer, no link routing, and no captured-reply or answer sections; every section shares the `.connections-activity` styling and a tool's command and reply share one labelled collapsible section paired by phase. The `janissary`-fence helper and its test are removed with the Markdown path. The metadata bar's clipboard icon is **Open record JSON** on every record and sends an `open-record-json` intent that the host resolves to the record's durable file, with visible refusals for a missing record or file. `help/connections.md` and `help/tell.md` carry the matching notes.

## Out of scope

- New wire frames, RPCs, client commands, or command-bar changes. Parallel batches reuse the existing `acp-tool-request` correlation and need no new frame.
- Changing the cap's value or configuration semantics, the cold-start retry, or other loop behavior unrelated to accepting several commands per reply. The configurable `maxToolTurns` budget is adopted as the single source for primer and loop, not redefined by this feature.
- Changing how a reply with no `janissary` block is handled — it remains a final answer — or removing the correction for an empty, multiple-command, unowned, or unclosed block.
- A configurable batch size distinct from the step cap, a per-command timeout, or a per-result message format other than the existing `Output of` block.
- A payload schema-version bump or migration of records already stored on disk; legacy single-answer records keep rendering through the fallback.
- Changing how replies are captured on the server beyond this loop, or the shell tab's rendering of settled answers.
- The popup-row transcript snapshot buttons and the core `openAcpTranscript` RPC, which keep their behavior.
- User documentation under `documentation/` and other help pages; only the command notes that directly describe the changed preamble and connection-tab behavior were updated.
