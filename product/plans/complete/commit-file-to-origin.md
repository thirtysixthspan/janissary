# Commit file to origin

**Complexity: 6/10** — no single part is novel: the pull button established the whole end-to-end path, and `GitSync` already contains every git command this needs. The number comes from breadth and from two tight spots. Breadth: a new RPC threaded through seven server layers, a new remote filesystem operation with a protocol bump, a second three-state status on the tree payload, a new overlay component, and a menu entry. The tight spots are `src/file-navigator/remote-port.ts` (at ~194 of its 200 counted lines, so this plan's method forces an extraction) and the whole-tree form's staging pathspec, which is silently wrong if written the obvious way.

Backlog text: *"add a 'commit file to origin' menu item in the file navigator context menu that will build and push a commit with the selected file or files. add a commit changes to origin button in the file navigator metadata bar that is the flipped version of the pull from origin button. It should take all changes and commit them to origin. failures should be reported in the notifications tab. the push to origin should be similarly animated to the pull from origin button. the color red on the button should be used to indicate failure."*

The file navigator can already bring a repository up to date from `origin` — the header's **Pull from origin** button runs `git pull` at the tree's own root, refreshes the whole view, flashes its own outcome on the button face, and records one line in the notifications feed (`product/specs/file-navigator-tab.md:652`–`:685`). There is no way back out. A user who edits a file from the navigator, sees its row turn yellow, and wants that change on `origin` has to leave the app for a terminal. The completed plan that built the pull button named "a `git push` counterpart button" as explicitly out of its scope (`product/plans/complete/file-navigator-git-pull-button.md:148`); this feature is that counterpart.

It arrives on two surfaces. A **Commit to origin** entry in a row's context menu builds and pushes a commit carrying the selected file or files. A **Commit changes to origin** button in the header — the pull button's mirror, sitting beside it — does the same for every change in the tree's repository. Both ask for a commit message first, both report their outcome the way the pull already does: one line in the notifications tab, and the button's own face spinning while the work runs, turning green when it lands and red when it fails.

## Design decisions

Settled by the backlog text, by behavior the file navigator already has, or by the user's answers to the first question round. Everything still open is in **Open questions** below, not guessed at here.

**The header button is the pull button flipped, not a new kind of control.** The backlog text says so directly: "the flipped version of the pull from origin button", "similarly animated", "the color red on the button should be used to indicate failure". That fixes a great deal without further invention — the pull button is a three-state server-owned status (`FileNavigatorPullStatus = 'pulling' | 'pulled' | 'error'`, `src/tab/types.ts:144`) carried on the tree's payload, rendered as a `files-pull--<status>` modifier class, spinning via the shared `icon-spin` keyframe while in flight and coloured with `--success` / `--error` once settled, then returned to rest by a three-second flash timer (`src/file-navigator/manager-pull.ts:10`, `FLASH_MS = 3000`). The commit button is the same mechanism with a second field, a second set of modifier classes, and an upward-pointing icon.

**Failures go to the notifications tab through the event that already carries them.** `file-operation` is the navigator's own notification event (`src/notifications.ts:38`); it has no config toggle and bypasses focus suppression, so it records a line even when the tree is the active tab (`product/specs/notifications.md:113`–`:128`). `product/specs/notifications.md:96`–`:98` already documents the pull as the one `file-operation` case that also reports a success. A commit and push is the same kind of user-armed, one-shot, reportable action, so it reports through the same event rather than introducing a new one.

**The work runs on the server, at the tree's own root.** The navigator never runs git in the browser. The pull reaches git through `FileSystemPort.pull` (`src/file-navigator/filesystem-port.ts:69`), the single seam that hides local-from-remote from `FileNavigatorManager`; the local implementation calls `pullRoot` in `src/git/pull.ts:23`, and the remote implementation sends a `git-pull` filesystem operation over the channel (`src/file-navigator/remote-port.ts:89`). A commit and push belongs on the same seam for the same reason: the outcome text is only knowable on the host that ran it.

**Clicks are coalesced server-side, and a coalesced click reports nothing.** `runPull` returns early when the tab's status is already `'pulling'` (`src/file-navigator/manager-pull.ts:28`), because overlapping git invocations collide on git's own lockfiles. A commit and push holds the index and `.git/HEAD` at least as hard, so the same in-flight guard applies — and, as with the pull, an ignored click posts no notification, since nothing happened.

**The user is asked for a commit message, in a field that already holds the answer.** Both surfaces open a small single-line pop-up over the tree, pre-filled with a generated default and editable before it is sent: `Enter` commits and pushes, `Escape` cancels with nothing written, and those two keys are the only things that close it. This is deliberately not the pull's one-click gesture — a pull takes what is already there, while a commit writes a permanent record that a generated message would make useless — but it costs one keystroke rather than a form, because the default is already correct for the common case. The pre-filled text is `commit: <filename>` for a single file, and `commit: <n> files` for a multi-row selection or the header button's whole-tree form; `src/git/sync.ts:98` (`sync: ${filename}`) is the established shape for a generated message in this codebase and this follows it with its own verb. An empty or whitespace-only message cancels rather than committing, the same silent no-op the rename field already applies to an unchanged name (`product/specs/file-navigator-tab.md:466`–`:468`).

**A blur does not cancel the message field.** This is the one place it deliberately departs from `FileSearchPopup.tsx:55`'s `onBlur={onClose}` and from the rename field, both of which dismiss on losing focus. What those two would discard is a search query or a filename the user can retype in seconds; what this one would discard is a sentence they composed. Clicking away therefore leaves the pop-up open with its text intact, and only `Enter` and `Escape` decide its fate. The cost is one inconsistency in a tab that otherwise dismisses overlays on blur, and it is worth paying once for the only overlay here whose contents cannot be reconstructed from what is on screen.

**Because the message is typed on the client, it travels with the RPC.** The server never prompts. The commit RPC carries the message the user approved, so the whole server-side flow stays the fire-and-forget shape every other navigator action has, and nothing needs a round trip to ask a question mid-operation.

**A push rejected because `origin` moved ahead is retried behind a rebase.** The cycle is the one `GitSync` already runs at `src/git/sync.ts:70`–`:82`: commit, then `git pull --rebase`, then push. A rebase that hits a conflict is abandoned with `git rebase --abort` (`src/git/sync.ts:109`–`:112`), leaving the branch as it was, and the failure is reported like any other. Someone else having pushed in the meantime is the ordinary case, not an error worth handing back to the user, and the alternative — failing and leaving an unpushed local commit behind — makes the button's red state mean two very different things. The rebase runs *after* the commit rather than before it, so the user's working tree is never reordered by an action they have not yet confirmed.

**The push names nothing, exactly as the pull names nothing.** `git push` runs bare, with no remote and no refspec, for the reason `src/git/pull.ts:16`–`:22` gives for the bare `git pull`: the navigator's root is an arbitrary checkout, and the branch's configured upstream is the only thing that knows where its commits belong. `src/git/sync.ts:117`'s explicit `origin HEAD:master` is not copied — it is correct only because its clone's branch is known to be `master`, which is exactly what is not knowable here. This makes the commit button the precise mirror of the pull button: whatever `git pull` in that directory would take from, `git push` sends to.

**A branch with no upstream fails, and says so in git's own words.** Nothing is auto-configured: there is no `--set-upstream`, no inferred `origin <branch>`, and no branch is published as a side effect of committing. `git pull --rebase` is the step that fails first on such a branch, so the failure arrives before the push is ever attempted and before a commit has been pushed anywhere — the button turns red and the notification reads `Could not commit:` followed by git's own "no upstream branch" text, which already names the `--set-upstream` command that fixes it. The local commit remains, so nothing is lost; the user sets the upstream once, from a terminal, and the button works from then on. Publishing a branch is branch management, which is out of scope below.

**The context-menu entry acts on the selected file or files.** The backlog text says "the selected file or files". That makes it the second entry in the menu — after **Delete** — whose scope is the selection rather than the right-clicked row (`product/specs/file-navigator-tab.md:251`–`:257`, `web/src/file-navigator/file-navigator-menu-items.ts:4`–`:7`). It follows Delete's rule exactly, as implemented at `web/src/file-navigator/file-navigator-menu-actions.ts:81`–`:85`: the whole selection when the clicked row belongs to it, and `normalizeOperationPaths(files.rows, new Set([row.path]))` for the clicked row alone otherwise. `normalizeOperationPaths` (`web/src/file-navigator/useFileNavigatorSelection.ts:58`) is what drops descendants of selected directories, so selecting a folder and a file inside it stages the folder once rather than naming the child twice.

**The entry joins the Rename/Delete group.** It sits directly after **Delete**, in the group that already holds the two entries that change something permanently, rather than opening a fifth group. That keeps the menu's existing four dividers exactly where they are — the entry count in `product/specs/file-navigator-tab.md:259` moves from ten to eleven, but "in four groups" stays true — and puts it with the other entries a user pauses before choosing.

**Visibility follows the branch text.** The pull button renders only when the tree's payload carries a branch (`web/src/file-navigator/FileNavigatorTab.tsx:128`, `onPull={files.branch ? intents.pull : undefined}`, inside the header element at `:124`–`:133`) — the same quiet degradation the GitHub button and the branch text itself use. Outside a git repository, or on a tree still waiting for its root, there is nothing to commit to and no button. The mirror button follows the same rule; so does the menu entry.

**Fire-and-forget over the indexed navigator RPC.** Every navigator action is a `FileNavigatorRpcCall` answered with `'ack'` (`src/protocol/file-navigator.ts:51`, `src/client-message.ts:34`); the real outcome arrives later as a state broadcast and a notification line. Nothing about this feature needs a synchronous reply, so it follows the same path rather than inventing a request/response one.

**Directories are committable.** Right-clicking a folder, or a selection containing one, commits everything beneath it. This costs nothing at the git layer — `git add` takes a directory argument and stages its whole subtree — and it is why the commit does *not* go through `resolveSelectionPaths` (`src/file-navigator/selection-action.ts:41`), which deliberately refuses anything that is not a file (`:36`, `statSync(absolute).isFile()`) because a plugin's selection action is only ever offered for files. The commit uses `containedPath` instead; see **Containment** below. It is therefore unlike **Edit**, which is absent for directory rows because a directory has nothing to open as text.

**The button shows success as well as failure.** The backlog text names only red, but the button is the pull button's mirror and the pull's vocabulary is three states, not two: spinning while the work runs, `--success` green when it lands, `--error` red when it does not, then back to rest after the flash window (`web/src/theme.css:752`–`:754`, `src/file-navigator/manager-pull.ts:10`). A button that only ever reacts to failure would leave a successful commit indistinguishable from a click that never registered.

**Nothing to commit is reported, not swallowed.** A clean tree, or a selection whose files are all unchanged, records its own notification line rather than being a silent no-op. This is the one place this feature deliberately differs from the coalescing rule above: a coalesced click reports nothing because a commit really is running, whereas a user who typed a message and pressed Enter has armed an action and is owed an answer about why nothing happened. `src/git/sync.ts:96` already detects exactly this condition (`git diff --cached --quiet` exits zero when nothing is staged).

**Remote trees get the same two surfaces.** A navigator rooted in a remote workspace already has the pull button, git-status colouring, and every filesystem operation (`product/specs/file-navigator-tab.md:100`–`:105`), and the commit runs on the host that owns the checkout for the same reason the pull does. This is what makes the new remote filesystem operation and the `REMOTE_PROTOCOL_VERSION` bump part of this plan rather than a follow-up.

**The exact user-visible wording is fixed here.** The context-menu entry reads `Commit to origin`, for one row and for many alike — the label does not change with the selection's size, so the menu never has two spellings of one entry. The header button's resting tooltip is `Commit changes to origin`, and its three status tooltips are `Commit changes to origin: committing`, `Commit changes to origin: committed`, and `Commit changes to origin: failed — see notifications`, following the record in `web/src/file-navigator/FileNavigatorPullButton.tsx:6`–`:12` exactly, including its failure tooltip's pointer at the notifications tab. The notification lines are `Committed to origin: <git summary>` on success, falling back to the bare `Committed to origin` when git said nothing, and `Could not commit: <git error>` on failure — the same two-line shape `src/file-navigator/pull-report.ts:10`,`:15` produces for the pull, with git's own words carried through in both. A commit with nothing to commit reads exactly `Nothing to commit`: it is neither of the other two outcomes, so it borrows neither stem, and the notification's own provenance header already names the tab it came from. The commit-message field's pre-filled text is `commit: <filename>` or `commit: <n> files` as described above.

## Proposed changes

Described in prose; the implementer writes the code. Placement follows what the pull already does at each layer, so every name below has a sibling in the repo to copy.

**Landing order.** Two steps are not free to move. The `remote-port-git.ts` extraction lands **first**, on its own, with no behavior change — `src/file-navigator/remote-port.ts` is over the line limit the moment a method is added to it, so doing this as a separate green checkpoint keeps every later step's `check-diff` readable. The `src/tab/types.ts` / `src/protocol.ts` / `state.ts` status fields land **second**, because the payload writer, the manager flow, and the button all fail to typecheck without them. After that the server chain (git module → port → remote operation → RPC → controller → manager flow) and the client chain (button → intent → menu entry → message field) can land in either order, since each half typechecks against a status field that already exists.

**A git module for the commit-and-push cycle.** A new `src/git/commit.ts`, beside `src/git/pull.ts` and `src/git/sync.ts`, exports the operation the navigator arms: stage the paths it was given (or everything, for the header button's whole-tree form), commit, and push. It uses `execFile` with argument arrays and no shell, the way every other module in `src/git/` does, and it rejects with git's own error rather than degrading quietly — the rule `src/git/pull.ts:16`–`:22` states for an action the user explicitly asked for. It runs with the server's own environment, as the pull does — the tree's root is the user's own checkout with the user's own credential helpers, and a push from it should authenticate exactly as `git push` typed in a terminal there would. `GitSync`'s `GH_TOKEN` injection (`src/git/sync.ts:88`) is deliberately not copied: it exists because the shared `git-sync` clone has its `origin` rewritten to HTTPS and its credential helper replaced with `gh auth git-credential` during provisioning (`src/workspace/index.ts:163`–`:177`), which is true of a provisioned workspace and not of an arbitrary tree root. It writes **no** summary helper of its own: `pullSummary` (`src/git/pull.ts:11`) is already exported, already tested, and is nothing more than "the last non-empty line of stdout" — which is the informative line for `git commit` (the diffstat total under its `[branch abc1234] <message>` header) exactly as it is for `git pull`. `src/git/commit.ts` imports it. The name reads as pull-specific at the new call site; that is the whole cost, and it is smaller than a second copy of a four-line function with a second set of tests. If a third caller ever wants it, that is the point to move it somewhere neutrally named — not before.

The sequence is the one `GitSync` already runs, with three differences.

*Staging is scoped to the navigator's root.* It stages the paths it was given; the header button's whole-tree form is the only caller that passes none, and it stages **`git add -A -- .` with `cwd` set to the tree's root, not the bare `git add -A` at `src/git/sync.ts:93`**. This distinction is the easiest thing in this plan to get silently wrong: since git 2.0 a bare `git add -A` updates the *entire repository* regardless of the working directory, so a navigator rooted at `src/` inside this repo would commit changes under `web/` and `documentation/` that the tree never showed. `GitSync` gets away with the bare form only because its root *is* the repository root. The `-- .` pathspec makes the button commit exactly what the tree displays, which is also how the tree decides what to colour — `changedPaths` scopes its own status query the same way and for the same stated reason (`src/git/status.ts:66`–`:69`).

*Nothing staged is an answer, not a skip.* `git diff --cached --quiet` (`src/git/sync.ts:96`) is the check — it exits zero when there is nothing staged — but where `commitIfChanged` silently skips the commit, this module resolves with a distinguishable nothing-to-commit result so the manager has something to report, and runs no commit, no rebase, and no push.

*The rebase names no remote or branch.* `src/git/sync.ts:107` hardcodes `git pull --rebase origin master` because its clone's branch is known; this module runs a bare `git pull --rebase` for the same reason `pullRoot` runs a bare `git pull` (`src/git/pull.ts:16`–`:22`): the navigator's root is an arbitrary checkout, and the branch's configured upstream is what should decide. `git rebase --abort` on failure, and the swallowed-abort behavior, carry over from `src/git/sync.ts:109`–`:112` unchanged. The push is bare too — `['push']`, no remote and no refspec, not `src/git/sync.ts:117`'s `['push', 'origin', 'HEAD:master']`. On a branch with no configured upstream the bare `git pull --rebase` is what fails, before the commit has been pushed anywhere; that rejection is returned as-is, so the notification carries git's own "no upstream branch" text rather than a message this module composes. Nothing here configures an upstream.

**The port gains the operation.** `FileSystemPort` (`src/file-navigator/filesystem-port.ts:69`) gains `commit(root, message, relPaths)` alongside `pull`, resolving with the outcome summary and rejecting with git's error — the "raw work with nowhere to put a reason" group `pull`'s own comment at `:65`–`:68` names, alongside `readFile`. `LocalFileSystemPort` (`:129`) delegates to the new git module after resolving each path with `containedPath`.

**`RemoteFileSystemPort` needs an extraction before it can take the method.** `src/file-navigator/remote-port.ts` counts ~194 of its 200 permitted lines (`max-lines` is an **error**, not a warning — `eslint.config.mjs:86`), so adding a method to it fails the build. Move `gitMetadata` (`:80`–`:83`) and `pull` (`:89`) into a new `src/file-navigator/remote-port-git.ts` and add `commit` there, following the split the directory already uses (`remote-port-history.ts`, `-paths.ts`, `-requests.ts`, `-watchers.ts`, all 11–40 lines). The extracted functions take the bound `request` and the `RemotePortPaths` instance as parameters, the way `mapRemoteHistory` (`remote-port-history.ts`) already takes a mapping function, leaving three one-line delegations behind. **This extraction lands first**, before anything else touches the file.

**The remote commit must map its paths.** `pull` ignores its `root` because the far side pulls its own workspace root, but a commit names paths, and the far side resolves them against the *workspace* root rather than the navigator's. Each selected path therefore goes through `await this.paths.to(root, relPath)` before it crosses the wire, exactly as `delete-many` does at `src/file-navigator/remote-port.ts:137`–`:138`. Sending tree-relative paths unmapped is the failure mode this closes: on a navigator rooted below the workspace root it would stage the wrong files, or none, while every layer reported success. The whole-tree form sends an empty array and the far side scopes itself to `context.root`, which is already the navigator's own remote root.

## Out of scope

Boundaries the backlog text already draws, plus the ones the pull button's own plan drew and this counterpart inherits.

- **Any conflict-resolution UI.** A rebase that conflicts is abandoned with `git rebase --abort` and reported, per the design decision above; nothing in this version helps the user resolve it. The tree's existing conflict colouring already surfaces conflicted files, and the resolution happens in an editor or a terminal.
- **Recovering from a rebase-abort that itself fails.** `src/git/sync.ts:110`–`:111` already swallows that case, and this plan copies the behavior rather than improving on it: the original push error is the one the user is shown, because it is the one that explains what happened.
- **Branch management.** Creating, switching, or publishing a branch, or choosing a remote other than `origin`. The backlog text says "to origin". In particular: a branch with no configured upstream is **not** published by committing — no `--set-upstream`, no inferred `origin <branch>`. It fails with git's own error, per the design decision above, and this is restated here because auto-configuring the upstream is the obvious convenience to assume this plan includes.
- **Staging as a separate user-visible step.** There is no index view, no stage/unstage affordance, and no partial-hunk selection — the two entry points are "these files" and "everything". A file the user had already staged by hand is committed along with everything else the action stages; the navigator does not preserve a partially-staged index.
- **A commit-message history, template, or multi-line body.** The field is one line, pre-filled, and remembers nothing between invocations.
- **Amending, reverting, or undoing a commit.** A commit that has been pushed is not on the navigator's undo/redo stack, which covers moves and pastes only (`product/specs/file-navigator-tab.md:409`–`:431`).
- **A commit history or log view.** The header's GitHub button already opens the repository's commits page (`product/specs/file-navigator-tab.md:643`–`:650`).
- **Progress detail beyond the three button states.** No percentage, no byte count, no object count — the same boundary `file-navigator-pull-button-status.md:121` drew.
- **Any change to what the pull does, how its clicks are coalesced, or what it reports.** The two actions share modules and CSS but not behavior.
- **Committing from anywhere other than a file navigator tab.** No command, no chord, no editor-tab affordance.
