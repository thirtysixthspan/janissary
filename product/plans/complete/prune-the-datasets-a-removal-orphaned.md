# Prune the datasets a removal orphaned, even when some other id in the same list was wrong

`remove` in `src/visualizations/agent.ts` pruned only when `refused` was empty — when every id in the batch named a chart. `reply.ts` accepts up to sixteen arbitrary strings in `remove`, so one invented id beside a real one is the ordinary shape of a batch that got something wrong, and the whole batch then skipped the pruning. Each such turn left an acquired file's dataset holding a slot of the eight with nothing reading it, permanently for that record: after seven of them every chart naming a new file was refused with "this one already reads them all" while only the source was in use. Wasted capacity rather than an unreadable record, but a refusal the user cannot explain from anything on screen.

The condition was load-bearing for nothing. `pruned` keeps the datasets a remaining chart still reads — plus the source — so the datasets that survive a partly-refused batch are exactly the ones in use, and the chart that was really removed is gone either way. Pruning now runs after the loop unconditionally, and the reason is stated where it is decided.

Two cases in `src/visualizations/agent.test.ts`, one for each direction. The first removes a real id beside an invented one and asserts the data that chart was the only reader of is gone; it fails against the previous rule, which left it. The second is the one that could have broken: a removal list of nothing but a wrong id, against a chart reading a file dataset, asserting the dataset the chart is still drawing from is untouched — pruning on a refusal would have deleted the data on screen.
