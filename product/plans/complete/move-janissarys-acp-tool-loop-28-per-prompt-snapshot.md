# ACP tool loop 28 — one native-command snapshot per logical prompt

**Complexity: 5/10** — ~21 added production lines across 3 files, 6 requirements and 6 test scenarios; the score is driven by the per-prompt capture moving through the attempt record and by the required `Attempt` extraction (p≈4.93)

Run order: 28 of 28 in the ACP tool loop series. Source plan: `product/plans/complete/move-janissarys-acp-tool-loop.md`, decision 4 — "Local roles and settings are authoritative, snapshotted per prompt": the local side snapshots the effective native-command settings once for each logical prompt, the primer, allow-list, extraction, and gate use that snapshot for the whole prompt, and a settings change made mid-prompt takes effect from the next prompt. Depends on subplans 1 through 27, all landed on PR #1992: subplan 8 introduced `coreSnapshot` and the per-prompt gate, subplan 11 switched `runCorePrompt` to `runToolLoop`, subplan 21 added the remote session path that receives the snapshot, and subplan 26 wrote the current specs. This subplan supersedes subplan 26's per-model-attempt wording by restoring the code the wording should have described.

The delivered code builds the native-command rows in `coreSnapshot` in `src/acp/run-prompt.ts`, which reads `managers.nativeCommandSettings?.current()` once per `runCorePrompt` invocation. `AcpManager.attempt` calls `runCorePrompt` once per model attempt, so when a model fails before replying and the manager falls back to the next role entry, the fallback attempt reads settings again. A settings change made during the fallback therefore reaches that same logical prompt, contrary to decision 4, and `src/acp/manager.test.ts` currently pins that behavior with three `settingsCurrent` reads across the first prompt, the fallback, and the next prompt. The specs now describe the accidental scope as "for each model attempt." This subplan moves the single read to the start of `AcpManager.run`, carries the captured value on the attempt record through every fallback, and restores both the code and the specs to the source plan's promise. It does not weaken the promise: the snapshot is genuinely one per logical prompt, and the next prompt reads afresh.

## Design decisions

- **Capture point.** `AcpManager.run` reads `this.managers.nativeCommandSettings?.current()` exactly once, after the `if (refusal || !settings || queue.length === 0)` guard has returned, when `settings` and `queue` are known good, and immediately before calling `this.attempt(...)`; it stores the result on the `Attempt` record. A refused prompt therefore reads nothing, and no code below `run` reads settings again to build a snapshot during the prompt; the dispatcher's live guard is the one deliberate re-read, described below. Each `run` call is one logical prompt, so concurrent `ask` and `tell` prompts capture independently. `prompt` and `promptResult` both go through `run`, so this covers every caller.
- **What is captured.** The captured value is the `CommandSettingsSnapshot` returned by `NativeCommandSettingsManager.current()`, not a derived row list. `coreSnapshot` remains the single place that maps `NATIVE_ACP_COMMANDS` through `effectiveCommandSetting`, so the mapping rules and the missing-row default stay in one module. `CommandSettingsSnapshot` and its `commands` array are readonly, and the real manager replaces the whole snapshot object on publish (`this.snapshot = snapshot` in `NativeCommandSettingsManager.publish`), so holding the reference is a true capture; a later edit or refresh cannot mutate it. The snapshot is still turned into a core `AcpRunSnapshot` once per model attempt, but always from the same captured settings object. "One snapshot per prompt" means one settings read per prompt, not one object construction per prompt.
- **Missing settings manager.** Represent it explicitly as `undefined` on the `Attempt` and pass `undefined` to `runCorePrompt`. `coreSnapshot` keeps today's rule: an undefined value produces an empty `rows` list, and `gateCommand` allows a native command with no row, so a granted command still runs and still appears in the allow-list. Do not substitute an all-enabled settings object and do not make the parameter optional with a fallback read: either would make "no manager" indistinguishable from "not supplied" and leave a second read path open. `Managers.nativeCommandSettings` is declared required in `src/managers.ts:72`, so this `undefined` branch is what partial managers and test stubs exercise; keep the optional chaining and do not make the registry field optional.
- **Carry through fallback.** `settleAttempt` requeues the next model with `this.attempt(label, { ...attempt, queue: rest, failures })`. Adding the captured value to `Attempt` means every fallback inherits it with no extra plumbing. The role name and grants stay fixed as today: the `AcpPendingPrompt` is rebuilt per attempt from `attempt.settings`, which was read once in `run`. `withoutTools` stays as today, read from the tab runtime when `coreSnapshot` runs; this subplan captures native-command settings only, and the override's timing is unchanged.
- **coreSnapshot contract.** `coreSnapshot(runtime, request, nativeSettings)` takes the captured `CommandSettingsSnapshot | undefined` instead of `Managers`. It no longer has access to a live settings manager, so it cannot accidentally re-read. `runCorePrompt` gains the same value as a required parameter and passes it through; it keeps every other responsibility (host runners, transcript handlers, settlement, cancellation checks) unchanged. The comment above `coreSnapshot` today says the authority is "read once"; move that statement to the capture in `AcpManager.run`, because the helper will no longer read anything.
- **Dispatcher guard unchanged.** `dispatchNative` still calls `managers.command.dispatchNativeLine`, whose `refuseDisabledCommand` reads current settings at dispatch time. Disabling a command mid-prompt still refuses the next caller-side run of it with `Command is disabled: <command>.` and the `command-disabled` notification. Agent-access changes, and workspace commands such as `file read` that never pass the dispatcher, are governed by the captured snapshot until the next prompt. That is exactly source decisions 4 and 5: the prompt snapshot is authoritative for the loop, the dispatcher keeps its own live guard.
- **Effect timing.** A settings change made at any point after a prompt starts, including between a failed attempt and its fallback, changes that prompt's captured snapshot only from the next logical prompt; the dispatcher's live disabled guard is the one mid-prompt exception. The next `ask` or `tell` calls `run` again and captures the then-current settings.
- **No wire or remote change.** The captured settings only change how the core `AcpRunSnapshot` is built on the local side. The snapshot that crosses the wire and the far-side loop that consumes it are unchanged.

## Proposed changes

- `src/acp/manager.ts` is at the 200-line `max-lines` cap today (ESLint counts 200 non-blank, non-comment lines), so it cannot take the new capture without an extraction. Move the existing `Attempt` type to `src/acp/ask-role.ts`, which already owns `AcpRoleSettings`, `AttemptFailure`, and `attemptOrder` and already imports `AcpRole`, `RoleEntry`, and `AcpPromptResult`; that file needs only a type import of `CommandSettingsSnapshot`. Add `nativeSettings: CommandSettingsSnapshot | undefined` to `Attempt`, and take `type Attempt` through manager.ts's existing `./ask-role.js` import (adding it to that multiline import costs no line). In `run`, capture `this.managers.nativeCommandSettings?.current()` once after the refusal guard and put it on the object literal passed to `this.attempt`. In `attempt`, pass `attempt.nativeSettings` to `runCorePrompt` in the new parameter position. `settleAttempt` needs no code change beyond the spread it already does. The extraction leaves `src/acp/manager.ts` at about 193 counted lines.
- `src/acp/run-prompt.ts`: change `coreSnapshot` to accept `runtime`, `request`, and the captured `CommandSettingsSnapshot | undefined`, deriving the same rows as today from that value and dropping the `managers.nativeCommandSettings?.current()` read; add the captured settings parameter to `runCorePrompt` immediately after `request`, before the session, and pass it to `coreSnapshot`. The function keeps its `Managers` parameter for dispatch, transcript, records, and notifications. Add a type-only import of `CommandSettingsSnapshot` from `../native-commands/settings-types.js`, and move the "read once" comment to the capture site in `run`.
- `src/acp/manager.test.ts`: update the retry/settings case as described under Tests. The `settingsCurrent` stub in `setup()` must return a new `commands` array holding the current row objects on each call, not the shared mutable `settingsRows` array, matching the real manager's publish behavior. The test replaces array entries rather than mutating a row object, so a shallow array copy is enough to keep an already-captured snapshot unchanged; without it, the `splice` before the fallback would rewrite the captured snapshot and the case could not distinguish capture from a re-read.
- `src/acp/run-prompt.test.ts`: the `harness.start` helper captures `options.settings?.current()` once and passes it to `runCorePrompt`; tests that supply no settings pass `undefined`. Re-word the "reads the settings once" case so it describes the captured snapshot being used for every command rather than a read inside `runCorePrompt`. The existing per-prompt agent-access case keeps working because each `start` captures afresh, and the no-manager case still exercises empty rows.
- `product/specs/acp.md`: change line 79's "for that model attempt" to "for that prompt" and replace the snapshot sentences with the prompt-scoped rule: one `managers.nativeCommandSettings.current()` read in `AcpManager.run` before the first model attempt, carried on the attempt record, used by every fallback; no rows when no manager or snapshot exists; a settings change reaches the snapshot from the next prompt, as does a grants or name change. Delete the "A fallback to the next model takes a fresh native-command snapshot" sentence. Keep "built when the model attempt starts": the primer and allow-list are still constructed per attempt, now from the prompt-captured value, so a fallback rebuilds the same rows. Mirror line 29's role-file wording, "read once for each logical prompt and reused by every model attempt for that prompt", rather than inventing a new phrase. Change line 83's "model attempt's snapshot" to "prompt's snapshot" and line 85's "attempt snapshot"/"rest of the attempt"/"mid-attempt" wording to the prompt scope, while keeping the dispatcher live-guard paragraph intact.
- `product/specs/application-commands.md`: keep line 19's "For each ACP model attempt" as the point where the allow-list is built, but replace "captured for that attempt" with "captured for that prompt when it starts"; the intersection itself is still computed per attempt from the same captured access. Change line 41's "An ACP model attempt captures the effective settings when it starts" to the prompt-scoped capture, "whole attempt" to "whole prompt", and "next model attempt" to "next prompt"; change line 43's "mid-attempt" and "rest of the attempt" to the prompt scope. Keep the caller-side `refuseDisabledCommand` guarantee and the workspace-tool sentence.
- No changes to `src/acp/types.ts`, `src/acp/drive-loop.ts`, `src/acp/tool-table.ts`, `src/remote/serve-acp*.ts`, `src/remote/acp-session*.ts`, or the protocol. The snapshot shape is already adequate.

## Tests

Server tests (vitest project `server`), colocated.

- `src/acp/manager.test.ts`, the retry/settings case (currently "keeps one role grant snapshot through retries and reads the next prompt afresh"):
  - Rename it to say both the role grant and native-command snapshot are held for the logical prompt.
  - Keep the first-prompt primer assertions and the fallback primer assertions, and keep the role settings call counts (once before the fallback, twice after the next prompt).
  - Make the mid-prompt change observable: before triggering the fallback with `handlers.error('retry')`, flip `question ask` agent access from off to on (and keep the role grant change to `db sqlite query`). With the captured snapshot the fallback primer still has no allow-list for `question ask`, and `retry.runCommand('question ask "Who?"')` still returns `Command is disabled: question ask.` without calling `dispatchNativeLine`. With the old per-attempt read it would be allowed and would produce an allow-list line.
  - Assert `settingsCurrent` has been called once after the first prompt and still once after the fallback. After `acp.run('tab1', 'ask next')`, assert twice, and keep the next prompt's `DB_PRIMER`/allow-list assertions and its `db sqlite query` dispatch expectation.
  - Keep the final mid-prompt flip of `db sqlite query` agent access and the assertion that `next.runCommand` still dispatches; with the captured snapshot and no live gate re-read, the total stays two reads. That final block continues to pin the prompt-scope rule, not the fallback rule.
  - The `settingsCurrent` stub in `setup()` returns a new `commands` array holding the current row objects on each call, so the `splice` replacements before the fallback cannot reach the array captured by the first `run`. Without this, the splice would rewrite the captured array too, the fallback would see the new rows under either implementation, and the new assertions would fail rather than distinguish capture from a re-read.
- `src/acp/run-prompt.test.ts`:
  - The harness reads settings once when a test prompt starts and passes that value, so "applies an agent-access change from the next prompt, not mid-prompt" still proves the first prompt keeps its captured row and a later `start` sees the new one.
  - The "reads the settings once per prompt however many commands run" case becomes a check that `current()` is called once by the harness for the prompt and stays at one after several `runCommand` calls; the loop itself must never call it. Keep the manager-based form; do not add a snapshot-literal variant, because `runCorePrompt`'s required parameter already makes a read inside it impossible and the extra form would test nothing.
  - The no-manager case passes `undefined` and still lists and dispatches the granted command, proving the empty-rows path.
  - Keep "passes a mid-prompt disabled caller-side command to the dispatcher, whose live guard refuses it" passing unchanged; it pins the one live re-check this subplan keeps.
- Callers of `runCorePrompt`: a repository-wide search finds only `src/acp/manager.ts` (production) and `src/acp/run-prompt.test.ts`. Both are updated here. `AcpManager.prompt` and `AcpManager.promptResult` reach it through `run`, so no other production path exists.
- `src/acp/plugin-session.test.ts` builds a real `NativeCommandSettingsManager` with fixed settings in each test's `setup()` and drives several prompts through `AcpManager.run`; no test changes settings between attempts, so it should pass unchanged. It is included in the focused run because it exercises the full manager-to-loop path.
- `src/native-commands/feature.integration.test.ts` does not call `runCorePrompt`; it builds snapshots from its own settings object and should pass unchanged.

## Out of scope

- Any per-call re-check inside the tool loop. The gate continues to read only the prompt snapshot, and the dispatcher's live guard is the only mid-prompt re-check.
- Role-file behavior or grant timing. `roleSettings` is already read once per prompt; this subplan does not touch it.
- The tab-wide `withoutTools` override's timing or storage. It stays a per-attempt read from the tab runtime; only native-command settings are captured per prompt.
- Wire changes, `AcpRunSnapshot` shape changes, protocol version changes, or far-side loop changes. The remote path already receives the whole snapshot in `acp-run`.
- The remote/far-side path beyond it continuing to consume the same snapshot. No change to `serve-acp`, `serve-acp-loop`, `acp-session`, or `drive-loop`.
- Help pages, user documentation, or subplan 26 itself. Only the two spec files named above are corrected.
- A per-attempt snapshot as a fallback if the prompt-level capture proves inconvenient. The source plan's promise must be restored, not weakened.
