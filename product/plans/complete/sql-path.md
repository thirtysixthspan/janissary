# sql <path> opens the sql tab and opens the named sql database

**Complexity: 7/10** — ~70 added lines across 9 production files, 20 behavioral requirements and 29 test scenarios, driven by the path-keyed connection identity that must stay out of every name-keyed list (p=6.92).

`sql file <path>` opens the SQL browser tab on the SQLite database at the given filesystem path, and `sql database <name>` is the explicit name form that preserves everything the name-based form did before. Bare `sql` still opens or focuses the most recently reached open database, or the first by name when none is open. The old `sql <name> [left|right]` grammar is gone: none of the three forms docks, keywords are lower case only, and the value is the trimmed remainder taken verbatim. A relative file value resolves against the application's project/launch directory through the host's existing `projectFileList` capability, while an absolute value passes through unchanged. Path-backed databases are held by the browser in browser-private, path-keyed handles, stay out of the name registry and every name-keyed surface, carry an explicit payload marker that drives a read-only label with a full-path tooltip in the switcher, and use the file's basename for export and result filenames.

## Design decisions

- The command uses explicit keywords instead of guessing what an argument means: `sql file <path>` opens a database by filesystem path, `sql database <name>` opens a database by its registry name with all of the name form's behavior, and bare `sql` keeps the `lastOpened ?? databases[0]` choice. The first word of the argument says which form it is.
- The keyword is the text up to the first whitespace run and must be the lower-case literal `file` or `database`; a keyword with no separating whitespace (`file/path`) is not recognized. The value is the remainder after that run, trimmed at the ends and taken verbatim, so a path holding interior or repeated spaces survives. There is no trailing dock-word special-case: `sql file <path> left` keeps ` left` as part of the path and reports a missing file, and a name ending in a dock word reaches the ordinary name guard. Only an empty value gets `Usage: sql [file <path>|database <name>]`, as does any unrecognized argument — an old bare name such as `sql shop`, a removed dock word such as `sql left`, an upper-case `FILE`, or a keyword with no value.
- Docking is removed from the SQL plugin entirely. `openDatabase` takes no dock side, the `Dock` type is deleted, all four call sites use the three-argument form, and `dockTab` is removed from the manifest's capabilities. Every SQL tab opened by the command lands in the centre; other plugins keep their own docking through the shared `parseDockArgument`.
- A path that does not exist is refused with `No database file at "<path>".` and opens no tab; no file is created. The `<path>` shown is the resolved absolute path that was checked, so a relative argument and an absolute one report the same way. Existence is checked with `existsSync` before opening, with no file-type pre-check: a directory, a non-SQLite file, or a file another process holds locked is opened and fails on its first read, with the SQLite error recorded as a notification attributed to the tab as `product/specs/sql-database.md` describes. A path removed after opening is reported missing even with a cached handle; unlike a name, the path branch has no live-handle grace.
- A relative `file` value resolves against the application's project/launch directory: the plugin asks the host for the existing `projectFileList()` capability and resolves with `path.resolve(root, value)`, where `root` is `managers.tab.launchDir` — the same directory `initDbDir` bases `.janissary/db/sqlite/` on. The plugin never reads `process.cwd()`, which is the launcher's directory and need not be the project. An absolute value is never re-based: it passes through unchanged. Resolution is independent of which tab the command is typed in. A path under `.janissary/db/sqlite/` is treated as a path like any other, so `sql file .janissary/db/sqlite/shop.sqlite` opens a path-keyed tab distinct from the `sql database shop` tab even though both point at the same file.
- `projectFileList` is asynchronous, so only the relative-value branch becomes asynchronous: `runCommand` is typed `void | Promise<void>` and the command handler returns its result for the host to await, which is already inside the published contract. The absolute-value branch stays synchronous, as do all named and bare forms. The SQL manifest declares `projectFileList` alongside its other capabilities while still claiming no file extensions and no `dockTab`, and `manifest.test.ts` pins all of those declarations. The global process cwd, `src/connections.ts`, the plugin API version, and every host/plugin API file outside the SQL plugin are untouched.
- A path-opened database is identified by its resolved absolute path: the tab key is `sqlite:<absolute path>` from the existing `instanceKeyFor`, and the tab is titled with the file's basename with exactly one trailing `.sqlite` removed case-insensitively, leaving an earlier `.sqlite` and any other extension (such as `.db`) in place. The same path reopened focuses one tab and keeps its payload; two different paths with the same basename remain distinct tabs.
- Path handles live in a `PathHandles` class in `src/database/path-handles.ts`, owned as one private field by `DatabaseBrowser`. `src/connections.ts` is untouched: its name-keyed registry, `getConnection`, `closeConnection`, `listOpenConnections`, `databaseRefs`, and `lastOpenedDatabase` keep their behavior, so a path-backed database cannot enter `connections list`, the database dropdown, tab completion, or the choice made by bare `sql`. `connections close sqlite:<name>` cannot close one; `DatabaseBrowser.dispose()` closes the path handles. `path.isAbsolute(database)` is the only discriminator between a path and a name — a valid registry name can never be absolute.
- The extraction into `src/database/path-handles.ts` is driven by the 200-line `max-lines` limit: `src/database/browser.ts` was already close to it, so the map, its open logic, and its close loop live in one cohesive new module imported directly as `./path-handles.js` under NodeNext, rather than being compacted into the browser.
- Export and result files for a path-backed database are named from the file's basename including its extension (`path.basename(database)`), supplied by the two call sites in `src/database/browser.ts` — `run`'s `openResultFile` callback and `exportObject`'s `exportRows` call. `src/database/export.ts` is unchanged; its helpers apply `safeFileName` and number the files, which keeps CSV/JSON exports and statement results under `.janissary/db/exports/` instead of failing on a name containing path separators. The basename includes `.sqlite`, so a `shop.sqlite` file exports as `shop.sqlite-items-1.csv` even though its tab is titled `shop`.
- `SqlPayload` gains an optional `databasePath?: string | null` marker holding the resolved absolute path on a path-backed tab and absent on a named tab. The client must not infer path-ness from the shape of `payload.database`: a named database whose file was deleted also leaves the dropdown list. `isSqlPayload` accepts the field through `isOptional(isString)`; `payload.database` remains the identity used by topic actions, request matching, and the tab key, so every read, write, and notification path keeps working unchanged. `SQL_PAYLOAD_SCHEMA_VERSION` moves from `1` to `2` together with the `sql` literal in `web/src/plugins/registry.tsx`, keeping server declaration, client registration, and parity test in agreement.
- For a path-backed tab, `DatabaseSwitcher` renders no `<select>` at all: a plain read-only `<span className="sql-database" title={payload.databasePath}>` in the existing slot shows the label, with the full path as its tooltip. The label is derived in a small pure module, `web/src/plugins/sql/database-label.ts`, because the browser bundle cannot use `node:path`: it takes the last `/`-separated segment and removes one trailing `.sqlite` case-insensitively. The branch tests `typeof payload.databasePath === 'string'`, so a `null` field still renders the named select. No key binding, focus order, CSS, or layout change is introduced, and `SqlTab.tsx` is not edited.
- The change is confined to the `sql` command and its tab. `db sqlite query/create/delete/list` keep their name-only behavior, and the SQL plugin still claims no file extensions (`src/plugins/sql/manifest.ts` `fileExtensions: {}`, now alongside `projectFileList`): there is no `open <file>` route, no file picker, and no drag-and-drop.

## Proposed changes

The shipped change lands in these areas:

### 1 — Command grammar

- `src/plugins/sql/activate.ts` `runCommand` trims the argument, splits the first word at the first whitespace run, compares it with the lower-case literals `file` and `database`, and takes the trimmed remainder verbatim. For `file`, an absolute value goes straight to `openExistingFile`; a relative value goes to an async `openRelativeFile` helper that awaits `capabilities.projectFileList()` and resolves the value with `path.resolve(root, value)` before the same existence check and `openDatabase` call. One `openExistingFile(database, capabilities, tabs)` helper owns the `existsSync` check and the `No database file at "<path>".` refusal for both branches. `runCommand` returns `void | Promise<void>` and the command handler returns its result for the host to await; the named and bare forms stay synchronous and route to the name opener or the existing bare `lastOpened ?? databases[0]` choice. An empty value and every unrecognized argument get `Usage: sql [file <path>|database <name>]`. Both `node:path` and `node:fs` are allowed across the plugin boundary; no new parser module was warranted, and the file stays under 200 counted lines.
- `src/plugins/sql/shared-intents.ts` no longer exports `parseSqlArgument` and no longer imports `parseDockArgument` or `Dock`; `isValidDatabaseName` and `isOpenIntent` remain. `src/plugins/sql/manifest.ts` drops `dockTab` from `capabilities`, adds `projectFileList`, keeps `command: 'sql'` and `fileExtensions: {}`, and its comment now says the `open` route is unclaimed while the command serves a path. `src/plugins/sql/manifest.test.ts` pins the command, the empty extension claim, the absence of `dockTab`, and the presence of `projectFileList`.

### 2 — Connection identity

- `src/database/path-handles.ts` (new) exports `PathHandles` with a `Map<string, DatabaseSync>`. `open(path)` checks `existsSync`, reuses a cached handle or opens one with `new DatabaseSync(path)` (converting errors with `errorText`), takes no `allowCreate`, and never creates a file. `close()` closes every handle with errors ignored and clears the map.
- `src/database/browser.ts` imports `PathHandles` and default `path`, holds `private readonly paths = new PathHandles()`, and branches on `path.isAbsolute(database)` in `open`, delegating paths to the path handles and leaving the name branch untouched. `run` passes `path.basename(database)` to `openResultFile`; `exportObject` passes it to `exportRows`; `dispose()` calls `paths.close()`. `src/connections.ts` and `src/database/export.ts` are unchanged.

### 3 — Tab opening, exports and docking removal

- `src/plugins/sql/open-tab.ts` exposes `openDatabase(database, capabilities, tabs)` with no dock parameter. For a path it skips the registry-membership check, uses `sqlite:<absolute path>` as the key, titles the tab from `path.basename` with one trailing `.sqlite` removed case-insensitively, and seeds `payload.databasePath` alongside `payload.database`. A name keeps the membership check, `UNKNOWN_DATABASE`, and its name as the title. The `Dock` type and both `dockTab` calls are gone; the `open` intent in `src/plugins/sql/intents.ts` uses the same three-argument call.
- `src/plugins/sql/tabs.ts` keeps `instanceKeyFor`, `emptyPayload`, and the name-only refs list unchanged. `src/database/export.ts` keeps `safeFileName`, `exportRows`, and `openResultFile` unchanged; the basename is supplied by the callers in `src/database/browser.ts`, so numbered CSV/JSON files and statement results stay under `.janissary/db/exports/`.
- `src/plugins/sql/open-tab.test.ts` (new) covers the path key, basename title, seeded payload, kept payload on reopen, distinct tabs for a shared basename, and the name branch.

### 4 — Client contract, switcher and specs

- `src/plugins/sql/shared.ts` adds `databasePath?: string | null` to `SqlPayload`, validates it with `isOptional(isString)`, and sets `SQL_PAYLOAD_SCHEMA_VERSION = 2`; `web/src/plugins/registry.tsx` sets the `sql` literal to `2` in the same change, so `web/src/plugins/registry.test.tsx` passes unchanged.
- `web/src/plugins/sql/database-label.ts` (new) is the pure label derivation. `web/src/plugins/sql/DatabaseSwitcher.tsx` renders the read-only labelled span with the path tooltip when `payload.databasePath` is a string and the existing select otherwise; `web/src/plugins/sql/DatabaseSwitcher.test.tsx` (new) covers both branches, the label rules, and null/omitted fields.
- Specs updated: `product/specs/sql-database.md` (three forms, exact usage and error lines, verbatim value, read-only label, path boundaries), `product/specs/database.md`, `product/specs/connection.md`, and `product/specs/tab-plugins.md`. `product/specs/launcher.md` keeps its bare `sql` entry.

## UI design

The feature extends the existing SQL browser tab in `web/src/plugins/sql/` — the same surface reached by `sql`, `sql file <path>`, and `sql database <name>`, with its metadata row (database and table controls), data grid, and SQL console. No other UI surface is added.

For a path-backed tab, `DatabaseSwitcher` in `web/src/plugins/sql/DatabaseSwitcher.tsx` does not render a `<select>` at all: it shows a plain, read-only label with the database's basename in the existing `sql-database` slot and styling, with a title/tooltip carrying the full absolute path. There is no misleading selectable list whose value has no matching option. For a named tab the existing select is unchanged. No key binding, focus order, or layout change is introduced; the tab keeps its existing two-pane `Tab` toggle and the metadata row's existing shape, so the label follows the row's current visual convention and no CSS edit is needed.

The client does not guess path-ness from the shape of `payload.database`, because a named database whose file was deleted also leaves the dropdown list. `SqlPayload` carries the optional `databasePath` field; `isSqlPayload` accepts it; `SQL_PAYLOAD_SCHEMA_VERSION` and the client registration literal are both `2`. `payload.database` remains the identity the topic actions and tab key use, so every existing read, write, and notification path keeps working unchanged.

## Out of scope

- Docking from the SQL plugin: no form accepts `left`/`right`, no tab is docked as a side effect of opening one, and the `dockTab` capability is gone; other plugins' docking is unchanged.
- No new UI surface: no file picker, no drag-and-drop, no database-dropdown entry for path-backed databases, and no changes to the grid, console, filters, export controls, or stylesheet.
- No extension of the `db sqlite` command family to paths, and no `.sqlite` file-extension claim or `open <file>` route.
- No path-backed database in `connections list`, tab completion, the name-keyed registry, or a tab's own connections panel, and no way for `connections close sqlite:<name>` to close one.
- No change to the process cwd, `src/connections.ts`, the plugin API version, or any host/plugin API file outside `src/plugins/sql/`, and no reintroduction of trailing dock-word handling.
- No creation of a database at a missing path.
- All other boundaries from `product/specs/sql-database.md` remain in force: the tab does not change a schema from the grid, does not join tables or build queries, shows no statistics panel, and adds no `sqlite:` row to its own connections panel.
