# Add a `web search` command and ACP tool backed by pluggable search providers

**Complexity: 8/10** — ~920 added lines, 23 files edited, 44 requirements, 62 test scenarios (p=8.74)

`web search` gives a person in a shell tab, and an `ask` or `tell` agent in Janissary's autonomous tool loop, one provider-agnostic way to search the web: a query goes in, and a single relevance-ordered, truncated plain-text context comes out, listing each result's title, URL, and snippet. Search backends are plugins behind one normalized `search()` contract, with Tavily and TinyFish bundled, so another backend can be added by registering a plugin without changing the core. Today a role session has no way to look anything up: every harness built-in tool, web search included, is denied (`product/specs/acp.md`, Provider and model), so an agent can only answer from what it already knows or what is in the workspace.

## Design decisions

Each decision comes from the feature text, from existing behavior ("from precedent"), or from a user answer ("user decision").

- **Command (feature text, extended by user decision).** `web search <query> [--results n] [--max-chars n] [--depth basic|advanced] [--provider name]`, a typed application command; `--depth` is the one flag added to the feature text's grammar.
- **Agent access (feature text).** The same capability is offered to ACP `ask` and `tell` sessions as a callable tool taking a required query plus optional result count (default 10), context character budget (default 10000), and provider (default auto-selected).
- **How an agent calls it (user decision).** A native ACP command, `web search`, in the same grammar as the typed command: the agent ends its reply with one `web search <query> [--results n] [--max-chars n] [--depth basic|advanced] [--provider name]` line, a role grants it by its native name, and a primer teaches it. The feature text's tool schema maps onto that grammar: `query` is the query words, `numResults` is `--results`, `contextMaxCharacters` is `--max-chars`, `provider` is `--provider`. No harness function-calling tool, MCP server, or JSON argument form is added.
- **Where an agent's search runs (user decision).** On the host running the ACP loop: the machine running Janissary for a local session, and the remote machine when the ACP connection was opened on the remote. The search's HTTP request leaves from that host, and that host's tokens are used. In the tool table this is a `runsOn: 'workspace'` tool, so it rides the same routing as `file read` (`runWorkspace` in `src/acp/run-prompt.ts` locally, `runWorkspace` in `src/remote/serve-acp-loop.ts` on the far side) and never crosses back to the caller; a far-side step carries the `[<host>] ` tag like any other workspace step. A local fallback session on a remote tab (`AcpSessionManager`) searches through the tab's remote connection, as its file steps do, so the search still leaves from the machine holding the tab's workspace.
- **Where a typed search runs (user decision).** Same rule as the agent's: a local tab's typed search runs on the machine running Janissary, and a remote tab's typed search runs on the remote machine, as `file read` and `file glob` do for a remote tab, so a person and an agent in the same tab get the same providers and tokens. A remote tab's typed search never falls back to the local machine; a dropped or slow connection prints the existing lines `Remote connection unavailable.`, `The remote connection ended.`, or `The remote machine did not answer in time.`.
- **Remote transport for a typed search (user decision).** A new path-free `web-search` read operation in `READ_OPERATIONS` (`src/remote/filesystem/operations.ts`), shaped like `git-pull` and `search`, carries the parsed query and flags and returns `{ text }`; the near side sends it through `withRemoteTabPort` (`src/file-read/remote-tab-port.ts`) as `file glob` sends `glob-paths`. The far side's operation context gains the workspace's merged token set. `REMOTE_PROTOCOL_VERSION` goes up by one (42 → 43 today; one past whatever it is when this lands), so an older peer is refused at the handshake.
- **Other agent surfaces (user decision).** Only `ask` and `tell` role sessions get `web search` in this version. An `agent` run refuses a `janissary web search …` line with `Agent: command not permitted: <command>.` even when a skill grants `web`, the way it refuses `file glob` and the file mutations today (`gateAgentCommand` in `src/acp/tool-table.ts`, `runGrantedAgentCommand` in `src/agent/command-tools.ts`). Monitor personas keep their existing `web_search` opt-in, which approves the harness's own search and is unchanged; conversations and editor persona queries are untouched.
- **Default grants (user decision).** The built-in `ask` and `tell` roles both grant `web search`: ask goes from eight commands to nine, tell from thirteen to fourteen (one more than whatever count tell has when this lands, if `file patch` lands first). Saved roles files are not changed and keep the grants they list. With no provider token configured, a granted search sends nothing anywhere.
- **Provider auto-selection (user decision).** `--provider auto`, the default, walks the registered providers in registry order (Tavily, then TinyFish, then any later-registered plugin), skipping any without a token file, and uses the first. When that provider fails, the search falls back to the next configured provider, as the ACP role model fallback does; the search fails only after every configured provider has been tried.
- **What falls back (user decision).** Any provider failure moves an auto search to the next configured provider: a missing or rejected key (HTTP 401, 402, 403), a quota or rate limit (429, Tavily's 432–434), any other non-2xx status, a timeout, a network error, or a response that does not decode. A successful search with zero results is an answer and does not fall back. An explicit `--provider <name>` uses only that provider and never falls back.
- **One core (feature text).** One core function, `webSearch(query, numResults = 10, contextMaxCharacters = 10000, provider = "auto", depth = "basic") -> text`, serves both the typed command and the agent tool, so they cannot disagree.
- **Provider contract (feature text, extended by user decision).** Each provider is a plugin implementing one normalized `search({ query, numResults, depth })` (`depth` added for the `--depth` flag) returning a flat list of `{ title, url, snippet }`. Tavily and TinyFish are bundled; another backend is added by registering a plugin, without modifying core code. Callers never see a provider's response shape.
- **Where providers come from (user decision).** Bundled only, as with tab plugins and editor plugins: providers ship in the Janissary build and are listed in one static catalog. Adding a backend is a new provider module plus one catalog entry, with no edit to the core pipeline, the command, or the ACP code. There is no filesystem discovery, npm loading, or third-party installation. Providers are trusted code.
- **Core pipeline (feature text).** The core stays provider-agnostic: it removes duplicates, orders by relevance, and truncates the rendered text to the character budget.
- **Domain filtering (user decision).** Nothing configures domain filtering in this version, so none is applied. A caller can still narrow a search with `site:` or `-site:` operators in the query text, which both bundled providers pass through. Configured include/exclude lists are a later change.
- **Output (feature text).** One plain-text context string: a relevance-ordered list rendering each result's title, URL, and snippet inline, formatted for direct insertion into a session prompt.
- **Output format (user decision).** A Markdown list with no header line: each result is a `- [<title>](<url>)` line followed by its snippet on the next line, indented two spaces. The typed command and the agent's tool result print the same text.
- **Query text (user decision).** The query is everything after `web search` up to the first whitespace-separated token that starts with `--`, trimmed, with each whitespace run collapsed to one space. Quotes and operators such as `site:` are kept as typed and sent to the provider, so `"exact phrase"` works. The flags follow the query in any order; a word after the flags that is not a flag's value is a usage error, so a query cannot itself contain a word starting with `--`.
- **Usage line (user decision).** Every malformed form prints exactly `Usage: web search <query> [--results <1-20>] [--max-chars <200-100000>] [--depth basic|advanced] [--provider <name>]` and sends nothing: bare `web search`, an empty query, an unknown or repeated flag, a flag with no value, a `--results` or `--max-chars` that is not a whole number in range, a `--depth` other than `basic` or `advanced`, and a word after the flags. The `web` command claims every line starting with the word `web`, as `file` claims every `file` line (`src/commands/file.ts`), so bare `web` and any other `web <word>` print the same line.
- **Provider names (user decision).** `--provider` names match case-insensitively, and `auto` is reserved for auto-selection. An unknown name prints `Web search: unknown provider "<name>" (available: auto, tavily, tinyfish).`, listing `auto` and then every registered provider in registry order, and sends nothing.
- **Failure lines (user decision).** Mirrors the ACP role model fallback wording. When exactly one provider was tried and it failed, the output is `Web search failed (<name>): <reason>.`. When more than one was tried and all failed, it is `Web search: every provider failed.` followed by one `- <name>: <reason>` line per attempt, in order. A reason is `HTTP <status> <status text>` (just `HTTP <status>` when the text is empty), `timed out after <n> s`, `invalid response`, or the first line of the network error. A search that succeeds after a fallback prints only its results.
- **Query length (user decision).** The core does not cap query length. A provider's own limit (Tavily refuses queries over 400 characters, TinyFish over 2000) shows up as that provider's HTTP 400 failure, and an auto search falls back to the next provider.
- **No results (user decision).** A successful search left with no results, whether the provider returned none or every one was dropped as a duplicate or for its URL, prints `No results for "<query>".` with the query as sent. It is an answer, not a failure, so it does not fall back.
- **Timeout (user decision).** Each provider attempt may take 30 seconds, reusing `PROVIDER_TIMEOUT_MS` from `src/models/providers/result.ts`; its failure reason is `timed out after 30 s`. An auto search that falls back can therefore take up to 30 seconds per configured provider.
- **Search depth (user decision).** A `--depth basic|advanced` flag, default `basic`, is passed to the provider as a normalized `depth` request field; each provider maps it onto its own option or ignores it. Tavily sends `search_depth: "basic"` (1 credit) or `"advanced"` (2 credits); TinyFish has no depth option and ignores it. A value other than `basic` or `advanced` (matched case-insensitively) is a usage error.
- **Provider request options (user decision).** Beyond depth, the bundled providers send their cheapest defaults and nothing else: Tavily `topic: "general"` and `max_results` equal to `--results`, with no answer, raw content, or images; TinyFish only `query`, so it defaults to US/English web results, page 0.
- **Cancellation (user decision).** An agent search's request is tied to the prompt's abort signal (the `signal` the ACP invocation already carries), joined with the attempt's timeout, so cancelling or resetting the prompt aborts the in-flight HTTP request at once, starts no further fallback attempt, and the late result is suppressed like any cancelled tool step. A typed search has no cancellation and runs until it answers or times out.
- **Completion (user decision).** Command-bar Tab completion completes `web` to `web search` (only while the completion policy allows `web search`, as `browser` subcommands are filtered today); after the query, a word starting with `-` completes to the flags not yet used (`--results`, `--max-chars`, `--depth`, `--provider`); the word after `--depth` completes to `basic` or `advanced`; and the word after `--provider` completes to `auto` and every registered provider name. Nothing is completed for the query or for `--results`/`--max-chars` values.
- **No provider configured (user decision).** With no token file for any provider, an auto search prints `Web search: no provider configured.`; an explicit `--provider <name>` whose token file is missing prints `Web search: provider "<name>" is not configured.`. Nothing is sent. `help web` documents where the token files go.
- **Result count (user decision).** `--results` takes a whole number from 1 to 20 and defaults to 10. Each provider attempt is exactly one HTTP request; the core keeps at most that many results after dropping duplicates and bad URLs, so a search can return fewer. TinyFish, which has no count parameter, returns its first page and the core cuts it to the count.
- **Character budget (user decision).** `--max-chars` takes a whole number from 200 to 100000 and defaults to 10000.
- **Duplicates (user decision).** Two results are duplicates when their URLs match after lowercasing the scheme and host, dropping the `#fragment`, and dropping one trailing `/` from the path; query strings are kept. The first, higher-ranked occurrence is kept.
- **Relevance order (from the contract).** The provider contract returns results in the provider's own relevance order and carries no score, so the core keeps that order; there is no re-ranking.
- **Normalizing results (user decision).** Before rendering, every run of whitespace (newlines included) in a title or snippet becomes one space and the ends are trimmed; `[`, `]`, and `\` in a title are backslash-escaped; spaces and parentheses in a URL are percent-encoded; an empty title is replaced by the URL. A result whose URL is not an absolute `http:` or `https:` URL is dropped and does not count toward the result total.
- **Truncation (user decision).** The output keeps as many whole results as fit within `--max-chars`, in order, and when any were left out ends with the line `(showing <k> of <n> results; raise --max-chars for more)`; the budget includes that line. When even the first result does not fit, its snippet is cut and ends with `…` so that at least one result's title and URL always appear; if the first result's link line alone is longer than the budget, it is printed whole anyway, with no snippet.
- **Atomic (feature text).** One call, one result; no multi-step navigation and no follow-up fetching of result pages.
- **Freshness (feature text).** The tool does not infer freshness; for time-sensitive queries the caller includes the year in the query terms.
- **No date in the primer (user decision).** The primer tells the agent to include the year for time-sensitive searches but states no date or year itself; the agent relies on its own knowledge of the date. The year in the primer's example query is illustrative only, not a statement of the current year.
- **Primer (user decision).** When a role grants `web search`, the web tool's primer is exactly these lines:
  - `To search the web, end your reply with one line:`
  - `web search <query> [--results <1-20>] [--max-chars <200-100000>] [--depth basic|advanced] [--provider <name>]`
  - `The result is a Markdown list of up to 10 results by default, each a title linked to its URL with a snippet beneath. For time-sensitive searches, include the year in the query; the search does not infer freshness.`
  - `--depth advanced gives better snippets but costs more; use it only when basic results are not enough.`
  - `Search only when the answer needs current or external information; never put file contents or secrets in a query.`
  - `Example: web search node.js permission model 2026 --results 5`
- **Credentials (feature text, from precedent).** Each provider's token is read from `.janissary/<service>-token`, e.g. `.janissary/tavily-token`, following the file convention `src/project/tokens.ts` already uses: the project's `.janissary/` first, then the user's `~/.janissary/`, a whitespace-only file counting as absent.
- **Tokens on each host (user decision).** `tavily` (file `tavily-token`, env `TAVILY_API_KEY`) and `tinyfish` (file `tinyfish-token`, env `TINYFISH_API_KEY`) become rows in `PROJECT_TOKENS` (`src/project/tokens.ts`), so they follow every rule the harness tokens already follow: read once at startup, project `.janissary/` first and `~/.janissary/` second; forwarded to a remote machine at workspace provisioning, where a forwarded value wins over the remote's own file and the remote's own file is the fallback (`src/remote/serve-provision.ts`). As with every non-GitHub row in that table, the two variables are also set in the environment of every process the table's credentials reach (`src/sandbox/environment.ts`): workspaced shells, harnesses, and ACP agents through `workspaceCredentialEnv`, and ACP agents outside any workspace, monitors included, through `agentCredentialEnv`. That exposure was put to the user with this full reach and kept (user decision): the rows carry their variables like every other harness credential, and no row gets an empty `env` list. A search on a remote machine uses the merged token set of the workspace it runs in. Because tokens are read once at startup, a token file added while Janissary runs takes effect at the next restart, as a new harness token does; reading the files on each search is the upgrade path if that proves annoying.
- **Plugin shape (user decision).** A new feature directory `src/web-search/`. `providers/catalog.ts` lists one static manifest per bundled provider — its id (the name `--provider` and every message use), the provider API version it was written against, the `PROJECT_TOKENS` name it uses, and an `activate` function that dynamically imports its module. The registry reads manifests only, which is all that `--provider` validation, the unknown-provider line, completion, the no-provider lines, and the API version check need; a provider whose manifest names a different API version is refused without importing anything, and a compatible module is imported the first time a search uses it and reused afterwards (Node's module cache, no cache of our own). Every call across the boundary is guarded. A `fixture-v1` provider and a compatibility test freeze API version 1.
- **Plugin failure (user decision).** When a provider module fails to import, requires a different provider API version, or its `search` throws anything other than a normal HTTP, timeout, network, or decoding failure, that attempt fails with reason `provider failed: <first line of the error>` (or `requires provider API <n>` for a version mismatch), so an auto search falls back as usual. The provider is then disabled for the rest of that server process: auto skips it, an explicit `--provider <name>` prints `Web search failed (<name>): <reason>.` without sending anything, and one notification, `Web search provider "<name>" disabled: <reason>.`, appears in the notifications tab, as editor plugin failures do. On a remote machine the provider is disabled in the far-side process and the reason appears only in failure lines, since the far side has no notifications tab. A disabled provider stays disabled until the server restarts; there is no re-enable command, since a bundled provider only breaks with a bad build.
- **Provider capability (from `ai/guidelines/plugins.md` §1).** A provider's `search` receives the normalized request and a narrow capability object: its own API key, a `fetch` function, and the abort signal. It never reads token files, `Managers`, or any other host state, which is also what lets tests inject a fake `fetch`.
- **Versioned, documented plugin API (feature text, `ai/guidelines/plugins.md`).** The provider plugin contract carries its own API version, a static declaration, a fixture plugin, a failure test, and a reference page for plugin authors.
- **Role sessions keep built-in tools denied (from precedent).** A harness's own web search stays off (`src/acp/internal-tools.ts`); agents search only through Janissary's command, so grants, command settings, and connection records govern every search.

## Proposed changes

The search core is a new feature directory that knows nothing about tabs, ACP, or the remote channel; the typed command, the local loop, the far-side loop, and the remote operation each call the same `webSearch` with the tokens of the host they run on. Everything else is wiring into registries that already exist.

### New `src/web-search/` feature directory (server)

- **`contract.ts`** — the provider plugin contract, versioned and import-free so a fixture can be written against it: `WEB_SEARCH_PROVIDER_API_VERSION` (1); `WebSearchRequest` (`query`, `numResults`, `depth: 'basic' | 'advanced'`); `WebSearchResult` (`title`, `url`, `snippet`); `WebSearchCapability` (`apiKey`, `fetch`, `signal`); `WebSearchProvider` (`search(request, capability)` resolving to `WebSearchResult[]`); `WebSearchProviderManifest` (`id`, `apiVersion`, `token` — a `ProjectTokenName` — and `activate()` resolving to the module's provider); the API version lives on the manifest only, so it is checked before anything is imported; and `ProviderRequestError`, the one error type a provider throws for an expected failure (HTTP status, timeout, network error, undecodable response) carrying its failure reason. The module's header documents what `ai/guidelines/plugins.md` §5 requires: resolution is by name or by first-configured in catalog order, attempts run sequentially with each awaited, an empty array means a successful search with no results, and any other throw is a plugin failure.
- **`providers/catalog.ts`** — the ordered manifest list, `[tavilyManifest, tinyfishManifest]`. The registry reads only this; `activate` is `() => import('./tavily.js')` and so on.
- **`providers/http.ts`** — the shared request step both bundled providers use: joins the capability's `signal` with `AbortSignal.timeout(PROVIDER_TIMEOUT_MS)` (`src/models/providers/result.ts`), calls `capability.fetch`, turns a non-2xx response into a `ProviderRequestError` of `HTTP <status> <status text>`, a timeout (`isTimeout`) into `timed out after 30 s`, any other rejection into its `firstLine`, and a body that is not JSON into `invalid response`. An abort from the prompt's signal is rethrown as an abort, not a failure, so cancellation never falls back.
- **`providers/tavily.ts`** — `POST https://api.tavily.com/search` with `Authorization: Bearer <apiKey>` and body `query`, `max_results` (= `numResults`), `search_depth` (= `depth`), `topic: "general"`. Decodes `results[]` into `{ title, url, snippet: content }`, refusing a body without a `results` array as `invalid response`; entries missing a string `url` are skipped.
- **`providers/tinyfish.ts`** — `GET https://api.search.tinyfish.ai?query=<query>` with `X-API-Key: <apiKey>`; ignores `depth`. Decodes `results[]` into `{ title, url, snippet }` in returned order with the same refusal rule.
- **`registry.ts`** — `createProviderRegistry(manifests)` returns an object that owns the disabled set, so a test builds its own registry over a fixture catalog instead of resetting shared state. Its methods: `providerNames()` (manifest ids, catalog order); `resolveAttempts(name, tokens)` returning the ordered providers to try (one for an explicit name, every configured, non-disabled provider for `auto`) or the unknown-provider, not-configured, or no-provider line; `runAttempt(manifest, request, capability)` which checks the manifest's `apiVersion` against `WEB_SEARCH_PROVIDER_API_VERSION` first (a mismatch is a plugin failure with reason `requires provider API <n>`, and nothing is imported), then activates the module, calls `search` inside a guard, and classifies the outcome as results, an expected failure (a `ProviderRequestError`), an abort, or a plugin failure. A plugin failure adds the manifest id to the disabled set and calls the caller's `reportDisabled(name, reason)` once. `search.ts` holds the one process-wide registry over `providers/catalog.ts`; creating it does no I/O and imports no provider, so the module top level stays side-effect free.
- **`render.ts`** — pure: `normalizeResults` (whitespace, title escaping, empty-title fallback; each URL parsed with the WHATWG `URL` constructor, dropped when it throws or its `protocol` is not `http:`/`https:`, and taken as its `href` with `(` and `)` additionally percent-encoded, since `URL` already encodes spaces), `dedupeResults` (the key is that `URL` with `hash` cleared and one trailing `/` dropped from `pathname`; `URL` has already lowercased scheme and host), and `renderResults(results, total, maxChars)` producing the Markdown list, the truncation note, and the first-result snippet cut.
- **`search.ts`** — `webSearch(request, deps)` where `request` is the parsed command (`query`, `numResults`, `maxChars`, `depth`, `provider`) and `deps` is `{ tokens, fetch, signal?, reportDisabled? }`. Resolves attempts, runs them in order until one succeeds, then normalizes, dedupes, cuts to `numResults`, and renders; or formats the single-failure line or the every-provider-failed list. Returns one string. No `Managers`, no tab, no channel, so both hosts call it directly.
- **`command.ts`** — two predicates for two kinds of text, as `AcpTool` separates `match` from `isCommandLine`: `isWebCommandLine(line)` (`/^web(\s|$)/i`, any line whose first word is `web`), which the `web` command and both `runWorkspace` routes use so a malformed `web` line is still answered with usage; and `isWebSearchReplyLine(line)`, which recognizes an agent's reply line only when it starts with lowercase `web search` followed by whitespace or the end of the line. The reply-line rule is deliberately case-sensitive, unlike the file and browser predicates, because a model's final answer often begins a sentence with "Web search …" and the extractor reads the reply's last recognized line as a command; the primer always shows the lowercase form. Also `WEB_SEARCH_USAGE`, `WEB_SEARCH_PRIMER` (the primer text under Design decisions), and `parseWebSearch(line)` returning the parsed request or the usage line, applying the query and flag rules under Design decisions. Its flag loop follows `scanArguments`/`scanFlag` in `src/file-glob/command.ts` (a scanner per flag that refuses a repeat or a missing value), and `--results` and `--max-chars` go through `positiveInteger` (`src/positive-integer.ts`) before their range check. The ranges are exported constants (`WEB_SEARCH_MAX_RESULTS`, `WEB_SEARCH_MIN_CHARS`, `WEB_SEARCH_MAX_CHARS`, defaults beside them) that the `web-search` operation's `valid` also uses, as `glob-paths-operation.ts` imports `FILE_GLOB_MAX_LIMIT`.
- **`tab-search.ts`** — `searchWebInTab(managers, label, line, signal?)`, shaped like `globFilesInTab` (`src/file-glob/tab-glob.ts`): parse first, returning the usage line without touching anything; then `localReadRoot(managers, label)` (`src/file-read/tab-read.ts`) decides the side — a defined root is a local tab, so call `webSearch` with `getProjectTokens()`, the global `fetch`, the signal, and a `reportDisabled` that calls `notify(managers, 'plugin-failure', label, …)`; an undefined root is a remote tab, so send the `web-search` operation through `withRemoteTabPort(managers, label, 'web-search', …)` and return its text. A rejected remote request prints its message unchanged, as `globRemotePaths` does through `rejectionLine`, which is how the existing connection lines reach the user.
- **`fixture-v1/`** — a fixture provider written against API version 1 and a compatibility test that loads it through `runAttempt`, as `src/plugins/fixture-v1/` does for tab plugins.

## Out of scope

- Fetching result pages; that is the separate `web fetch` feature (feature text, the next backlog entry).
- Multi-step search or navigation (feature text).
- Inferring freshness, stating the current date, or rewriting the query with a date (feature text, user decision).
- Configured domain filtering (user decision); `site:` operators in the query still work.
- Provider plugins from outside the build: filesystem discovery, npm packages, third-party loading (user decision).
- A core query-length cap (user decision).
- Paging a provider to reach `--results` (user decision).
- Provider options beyond `--depth`: topics, locations, languages, dates, answers, raw content, images (user decision).
- `web search` in `agent` runs, monitor personas, conversations, and editor persona queries (user decision).
- Cancelling a typed search (user decision).
- A JSON argument form, a harness function-calling tool, or an MCP server (user decision).
- Enabling any harness's built-in web search tool (from precedent).
