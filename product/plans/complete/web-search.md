# Add a `web search` command and ACP tool backed by pluggable search providers

**Complexity: 8/10** — fourteen feature slices, with the completed subplans and repair plans folded in

`web search` gives a person in a shell tab, and an `ask` or `tell` agent in Janissary's autonomous tool loop, one provider-agnostic way to search the web: a query goes in, and a single relevance-ordered, truncated plain-text context comes out, listing each result's title, URL, and snippet. Search backends are plugins behind one normalized `search()` contract, with Tavily and TinyFish bundled, so another backend can be added by registering a plugin without changing the core. Today a role session has no way to look anything up: every harness built-in tool, web search included, is denied (`product/specs/acp.md`, Provider and model), so an agent can only answer from what it already knows or what is in the workspace.

## Design decisions

Each decision comes from the feature text, from existing behavior ("from precedent"), or from a user answer ("user decision").

- **Command (feature text, extended by user decision).** `web search <query> [--results n] [--max-chars n] [--depth basic|advanced] [--provider name]`, a typed application command; `--depth` is the one flag added to the feature text's grammar.
- **Agent access (feature text).** The same capability is offered to ACP `ask` and `tell` sessions as a callable tool taking a required query plus optional result count (default 10), context character budget (default 10000), and provider (default auto-selected).
- **How an agent calls it (user decision).** A native ACP command, `web search`, in the same grammar as the typed command: the agent ends its reply with one `web search <query> [--results n] [--max-chars n] [--depth basic|advanced] [--provider name]` line, a role grants it by its native name, and a primer teaches it. The feature text's tool schema maps onto that grammar: `query` is the query words, `numResults` is `--results`, `contextMaxCharacters` is `--max-chars`, `provider` is `--provider`. No harness function-calling tool, MCP server, or JSON argument form is added.
- **Where an agent's search runs (user decision).** A granted search runs on the side that owns the tab, not on the host running the ACP loop. A local tab searches on the machine running Janissary, with that machine's tokens; a remote tab searches on that tab's remote host, in that workspace, with that workspace's merged tokens. A local-fallback ACP session on a remote tab (`AcpSessionManager`) still searches on the remote host, because `searchWebInTab` decides from the tab's `remote` field, and prints `Remote connection unavailable.` when the tab has no ready channel. A remote-hosted loop searches on the far side with the workspace's merged tokens. The far-side step carries the `[<host>] ` tag; a local-fallback session's workspace step is untagged.
- **Where a typed search runs (user decision).** Same rule as the agent's: a local tab's typed search runs on the machine running Janissary, and a remote tab's typed search runs on the remote machine, as `file read` and `file glob` do for a remote tab, so a person and an agent in the same tab get the same providers and tokens. A remote tab's typed search never falls back to the local machine; a dropped or slow connection prints the existing lines `Remote connection unavailable.`, `The remote connection ended.`, or `The remote machine did not answer in time.`.
- **Remote transport for a typed search (user decision).** A new path-free `web-search` read operation in `READ_OPERATIONS` (`src/remote/filesystem/operations.ts`), shaped like `git-pull` and `search`, carries the parsed query and flags and returns `{ text }`; the near side sends it through `withRemoteTabPort` (`src/file-read/remote-tab-port.ts`) as `file glob` sends `glob-paths`. The far side's operation context gains the workspace's merged token set. `REMOTE_PROTOCOL_VERSION` moves from 43 to 44 for both of this feature's wire changes at once: the two new token names on the provisioning map and the `web-search` operation, so an older peer is refused at the exact-version handshake. A web search is added to the long-running request set, because a fallback across two providers can exceed the default 60-second deadline.
- **Other agent surfaces (user decision).** Only `ask` and `tell` role sessions get `web search` in this version. An `agent` run refuses a `janissary web search …` line with `Agent: command not permitted: <command>.` even when a skill grants `web`, the way it refuses `file glob` and the file mutations today (`gateAgentCommand` in `src/acp/tool-table.ts`, `runGrantedAgentCommand` in `src/agent/command-tools.ts`). Monitor personas keep their existing `web_search` opt-in, which approves the harness's own search and is unchanged; conversations and editor persona queries are untouched.
- **Default grants (user decision).** The built-in `ask` and `tell` roles both grant `web search`: ask goes from nine commands to ten, and tell grants all fifteen native commands. Saved roles files are not changed and keep the grants they list. A saved `tell` without the grant gets no web tool and no web primer, so a model-emitted `web search` line stays prose in the answer; it never reaches the gate. With no provider token configured, a granted search sends nothing anywhere.
- **Application command settings (from precedent).** The builtin `web` command has its own parentless Commands-tab row, and the native `web search` row has the parent `web` with its own Enabled and Agent access settings. A typed `web search …` line resolves to the longer native row exactly as a typed `file write` line does, so disabling `web search` refuses the typed command as well as the agent tool, while disabling `web` disables both.
- **Provider auto-selection (user decision).** `--provider auto`, the default, walks the registered providers in catalog order (Tavily, then TinyFish), skipping any without a token file, and uses the first enabled one. When that provider fails, the search falls back to the next configured, enabled provider, as the ACP role model fallback does; the search fails only after every configured provider has been tried. A configured provider disabled earlier is skipped until no enabled provider remains, and then its stored failure lines are printed.
- **What falls back (user decision).** Any provider failure moves an auto search to the next configured provider: a missing or rejected key (HTTP 401, 402, 403), a quota or rate limit (429, Tavily's 432–434), any other non-2xx status, a timeout, a network error, a response that does not decode, or a plugin failure. A successful search with zero results is an answer and does not fall back. An explicit `--provider <name>` uses only that provider and never falls back.
- **One core (feature text).** One core function, `webSearch(request, deps) -> text`, serves both the typed command and the agent tool, so they cannot disagree. `request` is the parsed command (`query`, `numResults`, `maxChars`, `depth`, `provider`); `deps` is `{ tokens, fetch, signal?, reportDisabled? }`. The defaults come from `parseWebSearch`; no consumer applies its own. No `Managers`, no tab, and no channel enter the core.
- **Provider contract (feature text, extended by user decision).** Each provider is a plugin implementing one normalized `search({ query, numResults, depth })` returning a flat list of `{ title, url, snippet }`. `depth` was added for the `--depth` flag. Tavily and TinyFish are bundled; another backend is added by registering a plugin, without modifying core code. Callers never see a provider's response shape. The contract module carries `WEB_SEARCH_PROVIDER_API_VERSION = 1`, the request/result/capability/module/manifest types, and `ProviderRequestError` for one expected provider failure.
- **Where providers come from (user decision).** Bundled only, as with tab plugins and editor plugins: providers ship in the Janissary build and are listed in one static catalog. Adding a backend is a new provider module plus one catalog entry, with no edit to the core pipeline, the command, or the ACP code. There is no filesystem discovery, npm loading, or third-party installation. Providers are trusted code.
- **Provider registry (user decision).** `createProviderRegistry(manifests)` owns the disabled set and is created once process-wide by the search core. `providerNames()` lists manifest ids in catalog order. `resolveAttempts(name, tokens)` returns either the ordered manifests to try or the line to print. Names match case-insensitively and `auto` is reserved. An explicit name is checked unknown, then disabled, then not configured: a disabled provider prints `Web search failed (<id>): <stored reason>.` even when its token file is gone. `auto` returns `Web search: no provider configured.` only when no provider has a token; when configured providers exist but all are disabled, it prints their stored failure lines without sending anything. Creating the registry does no I/O and imports no provider.
- **Guarded activation and attempts (user decision).** `runAttempt` checks the manifest's API version before importing anything. A mismatch fails with `requires provider API <n>` and disables the provider. An activation failure always disables, whatever the error class, including a `ProviderRequestError`, because a module that cannot import has not made an API call. A module without a `provider.search` function fails with `provider failed: module has no provider`. A `search` resolving to something other than an array fails with `provider failed: search did not return an array`. Every other throw from `search` is `provider failed: <first line>`; a thrown `ProviderRequestError` is an expected failure with its message and does not disable. The abort check runs before every classification: when the capability's signal is aborted, the original rejection is rethrown unchanged and nothing is disabled or reported. A disabled provider keeps the first reason, calls `reportDisabled` once, and stays disabled until the server restarts.
- **Failure lines (user decision).** One formatter, `formatFailures`, serves both the core and the registry so the two cannot drift. When exactly one provider was tried and failed, the output is `Web search failed (<name>): <reason>.`. When more than one was tried and all failed, it is `Web search: every provider failed.` followed by one `- <name>: <reason>` line per attempt, in order. A reason is `HTTP <status> <status text>` (just `HTTP <status>` when the text is empty), `timed out after 30 s`, `invalid response`, the first line of a network error, `provider failed: <first line>`, or `requires provider API <n>`. A search that succeeds after a fallback prints only its results.
- **Shared HTTP step (decision).** Both bundled providers use one `requestJson` step. It joins the capability's signal with `AbortSignal.timeout(PROVIDER_TIMEOUT_MS)` and passes the joined signal to the injected `fetch`. A non-2xx response's body is not read: the reason is its status line. A 2xx body is read with `response.text()` and parsed with `JSON.parse`, so a cut body classifies as an abort, a timeout, or a network failure, and only a JSON parse failure is `invalid response`. An abort of the capability's own signal is rethrown unchanged and wins over a timeout. Neither provider reads the global `fetch`, token files, `process.env`, or any other host state.
- **Bundled provider requests (user decision).** Tavily sends `POST https://api.tavily.com/search` with `Authorization: Bearer <key>` and exactly `query`, `max_results` (= `--results`), `search_depth` (= `--depth`), and `topic: "general"`. TinyFish sends `GET https://api.search.tinyfish.ai?query=<query>` with `X-API-Key: <key>` and ignores `--depth`. Both keep the provider's returned order; TinyFish's `position` and Tavily's `score` are ignored. Both decode `results[]` into `{ title, url, snippet }`, using `content` for Tavily and `snippet` for TinyFish. A non-string title or snippet becomes an empty string; an entry that is not an object or lacks a string `url` is skipped; a body without a `results` array is `invalid response`. Neither provider trims its list to the result count or sends domain filters; `site:` and `-site:` travel in the query. Neither caps query length; a provider's own refusal arrives as its HTTP 400.
- **Core pipeline (feature text).** On the winning result list the core normalizes, drops duplicates, cuts to `numResults`, and renders one string. It never re-ranks: the provider's relevance order is kept.
- **Normalizing results (user decision).** Every run of whitespace (newlines included) in a title or snippet becomes one space and the ends are trimmed. `[`, `]`, and `\` in a title are backslash-escaped; spaces and parentheses in a URL are percent-encoded; an empty title is replaced by the URL. A result whose URL is not an absolute `http:` or `https:` URL is dropped and does not count toward the total.
- **Duplicates (user decision).** Two results are duplicates when their normalized URLs match after lowercasing the scheme and host, dropping the `#fragment`, and dropping one trailing `/` from the path; query strings are kept. The first, higher-ranked occurrence is kept. The dedupe key is built from a fresh `URL`, so the kept result keeps its own spelling.
- **Output format (user decision).** A Markdown list with no header line: each result is a `- [<title>](<url>)` line followed by its snippet on the next line, indented two spaces. A result with no snippet prints only its link line. Lines are joined with one `\n`, with no blank line between results and no trailing newline. The typed command and the agent's tool result print the same text.
- **Truncation (user decision).** The output keeps as many whole results as fit within `--max-chars`, in order, and when any were left out and the first result's link line leaves room for the note, it ends with `(showing <k> of <n> results; raise --max-chars for more)`; the budget includes that line. `<n>` is the count after normalizing, deduping, and cutting, so it matches what the search could have printed. When even the first result does not fit, its snippet is cut and ends with `…` so that at least one result's title and URL always appear; the note is dropped when it cannot fit alongside the link line, and kept without a snippet when the two fit but a snippet line does not; if the first result's link line alone is longer than the budget, it is printed whole anyway, with no snippet. Lengths are JavaScript string lengths, and `…` counts as one character. A cut never ends on a lone high surrogate.
- **No results (user decision).** A successful search left with no results, whether the provider returned none or every one was dropped as a duplicate or for its URL, prints `No results for "<query>".` with the query as sent. It is an answer, not a failure, so it does not fall back.
- **Query text (user decision).** The query is everything after `web search` up to the first whitespace-separated token that starts with `--`, trimmed, with each whitespace run collapsed to one space. Quotes and operators such as `site:` are kept as typed and sent to the provider, so `"exact phrase"` works. The flags follow the query in any order; a word after the flags that is not a flag's value is a usage error, so a query cannot itself contain a word starting with `--`.
- **Usage line (user decision).** Every malformed form prints exactly `Usage: web search <query> [--results <1-20>] [--max-chars <200-100000>] [--depth basic|advanced] [--provider <name>]` and sends nothing: bare `web`, `web foo`, bare `web search`, an empty query, an unknown or repeated flag, a flag with no value, a `--results` or `--max-chars` that is not a whole number in range, a `--depth` other than `basic` or `advanced`, and a word after the flags. The `web` command claims every line starting with the word `web`, as `file` claims every `file` line (`src/commands/file.ts`). Flag names match exactly and in lowercase; `--results=5` and a bare `--` are unknown. A second flag consumes a value that starts with `-` but not one that starts with `--`.
- **Provider names (user decision).** `--provider` names match case-insensitively, and `auto` is reserved for auto-selection. An unknown name prints `Web search: unknown provider "<name>" (available: auto, tavily, tinyfish).`, listing `auto` and then every registered provider in catalog order, and echoes the name as typed. Lines about a known provider print its manifest id, so `--provider Tavily` without a token reads `provider "tavily" is not configured.`.
- **Result count (user decision).** `--results` takes a whole number from 1 to 20 and defaults to 10. Each provider attempt is exactly one HTTP request; the core keeps at most that many results after dropping duplicates and bad URLs, so a search can return fewer. TinyFish has no count parameter and returns its first page; the core cuts it.
- **Character budget (user decision).** `--max-chars` takes a whole number from 200 to 100000 and defaults to 10000.
- **Search depth (user decision).** `--depth basic|advanced`, default `basic`, is passed to the provider as a normalized `depth` field. Tavily sends `search_depth: "basic"` (1 credit) or `"advanced"` (2 credits); TinyFish ignores it. The value is matched case-insensitively and stored lowercase; any other value is a usage error.
- **Timeout (user decision).** Each provider attempt may take 30 seconds, reusing `PROVIDER_TIMEOUT_MS`; its failure reason is `timed out after 30 s`. An auto search that falls back can therefore take up to 30 seconds per configured provider.
- **Cancellation (user decision).** An agent search's request is tied to the prompt's abort signal joined with the attempt's timeout, so cancelling or resetting the prompt aborts the in-flight HTTP request at once, starts no further fallback attempt, and the late result is suppressed like any cancelled tool step. The core rejects with the abort on every abort it can observe: before resolution (so a resolution line never replaces an abort), before each attempt, after a successful result arrives, and before final failure lines are formatted. A typed search has no cancellation and runs until it answers or times out; a remote search has no cancel message, so a local-fallback session's late result is only suppressed.
- **Completion (user decision).** The command bar completes `web` to `web search` only while the completion policy allows it, and completes nothing under `web` when either the `web` or `web search` row is disabled. After `web search`, a word starting with `-` completes to the flags not yet used (`--results`, `--max-chars`, `--depth`, `--provider`) but only after the query: the dash must not be the first word after `web search`, so `web search -` leaves the line unchanged. The word after `--depth` completes to `basic` or `advanced`; the word after `--provider` completes to `auto` and every registered provider name, read from the manifests without activating a provider. The query, `--results` and `--max-chars` values, and arguments of any other `web` subcommand get no candidates and never fall back to filesystem completion. Candidate matching is case-sensitive, like every other completion.
- **No provider configured (user decision).** With no token file for any provider, an auto search prints `Web search: no provider configured.`; an explicit `--provider <name>` whose token file is missing prints `Web search: provider "<name>" is not configured.`. Nothing is sent. `help web` documents where the token files go.
- **Credentials (feature text, from precedent).** Each provider's token is read from `.janissary/<service>-token`, e.g. `.janissary/tavily-token`, following the file convention `src/project/tokens.ts` already uses: the project's `.janissary/` first, then the user's `~/.janissary/`, a whitespace-only file counting as absent.
- **Tokens on each host (user decision, revised for security).** `tavily` (file `tavily-token`, env `TAVILY_API_KEY`) and `tinyfish` (file `tinyfish-token`, env `TINYFISH_API_KEY`) are rows in `PROJECT_TOKENS` (`src/project/tokens.ts`), so they follow the harness tokens' loading and forwarding rules: read once at startup, project `.janissary/` first and `~/.janissary/` second; forwarded to a remote machine at workspace provisioning, where a forwarded value wins over the remote's own file and the remote's own file is the fallback (`src/remote/serve-provision.ts`). Their exposure stops there. Both keys are read by the Janissary server process, which runs every search, and neither is injected into spawned shells, harnesses, or ACP agents: the rows carry `spawn: false`, so `workspaceCredentialEnv` and `agentCredentialEnv` (`src/sandbox/environment.ts`) leave both variables out, and an ambient copy is scrubbed from the confined path by `ENV_SCRUB_PATTERNS` (`src/sandbox/paths.ts`) and dropped from the pass-through path. The far-side Janissary process still searches with the forwarded token or its own file; only the spawned environments are empty of it. Because tokens are read once at startup, a token file added while Janissary runs takes effect at the next restart. Every configured row is forwarded on the provisioning frame, and a remote rejects an unknown name by failing the whole frame, which is why this feature moves `REMOTE_PROTOCOL_VERSION` once for both new rows and the new operation.
- **Provider capability (from `ai/guidelines/plugins.md` §1).** A provider's `search` receives the normalized request and a narrow capability object: its own API key, a `fetch` function, and the abort signal. It never reads token files, `Managers`, or any other host state, which is also what lets tests inject a fake `fetch`.
- **One request object per attempt (decision).** The core builds the provider-facing request and the capability inside the attempt loop, copied from the parsed command, so a provider that mutates its request cannot change what a later fallback provider gets. The objects are not frozen and the contract stays mutable; the per-attempt copy confines a mutation to the attempt that made it.
- **Plugin shape (user decision).** A new feature directory `src/web-search/`. `providers/catalog.ts` lists one static manifest per bundled provider — its id (the name `--provider` and every message use), the provider API version it was written against, the `PROJECT_TOKENS` name it uses, and an `activate` function that dynamically imports its module. The registry reads manifests only, which is all that `--provider` validation, the unknown-provider line, completion, the no-provider lines, and the API version check need; a provider whose manifest names a different API version is refused without importing anything, and a compatible module is imported the first time a search uses it and reused afterwards (Node's module cache, no cache of our own). A `fixture-v1` provider and a compatibility test freeze API version 1 with the literal `1`, so moving the constant fails the fixture.
- **Plugin failure (user decision).** An activation failure, a module without a search provider, a non-array search result, or a `search` throwing anything other than an expected `ProviderRequestError` disables the provider for the rest of that server process. Auto skips it; an explicit `--provider <name>` prints `Web search failed (<name>): <reason>.` without sending anything. When every configured provider is disabled, auto prints those stored failure lines. A disabled provider stays disabled until the server restarts; there is no re-enable command, since a bundled provider only breaks with a bad build.
- **Disabled-provider notification (user decision).** The registry calls the caller's `reportDisabled(name, reason)` once per disabled provider; the caller decides how to show it. A local search posts one notification, `Web search provider "<name>" disabled: <reason>.`, attributed to the tab, through the `plugin-failure` event, even when a later provider succeeds. It is not added to the tab's transcript, and the search output prints only the provider that answered, so the notification is the only report when a fallback covers the disable. A remote search passes no `reportDisabled`, and its output also prints only the answering provider, so a provider disabled before a successful fallback is reported nowhere; a later failure line names it only in an explicit search of it or in auto once every configured provider is disabled.
- **Versioned, documented plugin API (feature text, `ai/guidelines/plugins.md`).** The provider plugin contract carries its own API version, a static declaration, a fixture plugin, a failure test, and a reference page for plugin authors. The reference page also tells a provider author to add a `PROJECT_TOKENS` row of its own, with the matching specs and user documentation, and states that every new row moves the remote protocol version because the whole configured map travels on the provisioning frame.
- **Role sessions keep built-in tools denied (from precedent).** A harness's own web search stays off (`src/acp/internal-tools.ts`); agents search only through Janissary's command, so grants, command settings, and connection records govern every search.

## Proposed changes

The search core is a new feature directory that knows nothing about tabs, ACP, or the remote channel; one tab-adapter module chooses the local or remote side, and the typed command, the local loop, the far-side loop, and the remote operation each call the same `webSearch` with the tokens of the host they run on. Everything else is wiring into registries that already exist. `master`'s `file grep` feature is kept beside this one, so the native vocabulary is fifteen commands and ask grants ten of them.

### New `src/web-search/` feature directory (server)

- **`contract.ts`** — the provider plugin contract, versioned and import-free so a fixture can be written against it: `WEB_SEARCH_PROVIDER_API_VERSION` (1); `WebSearchRequest` (`query`, `numResults`, `depth: 'basic' | 'advanced'`); `WebSearchResult` (`title`, `url`, `snippet`); `WebSearchCapability` (`apiKey`, `fetch`, `signal`); `WebSearchProvider` (`search(request, capability)` resolving to `WebSearchResult[]`); `WebSearchProviderModule` (`provider`); `WebSearchProviderManifest` (`id`, `apiVersion`, `token` — a `ProjectTokenName` — and `activate()` resolving to the module's provider); and `ProviderRequestError`, the one error type a provider throws for an expected failure. The API version lives on the manifest only, so it is checked before anything is imported. The module header documents the extension-point rules: resolution by name or first-configured in catalog order, sequential awaited attempts, an empty array as an answer, and the expected-failure versus plugin-failure split.
- **`providers/http.ts`** — `requestJson(capability, url, init)`: joins the capability's signal with `AbortSignal.timeout(PROVIDER_TIMEOUT_MS)`, calls `capability.fetch`, turns a non-2xx response into `HTTP <status> <status text>`, a timeout into `timed out after 30 s`, another rejection into its first line, an aborted capability into the original rejection, and a non-JSON or empty body into `invalid response`. It reads a 2xx body with `response.text()` then `JSON.parse`, so a cut body classifies as a transport failure rather than a decode failure.
- **`providers/decode.ts`** — `decodeResults(body, snippetKey)` maps `results[]` into `{ title, url, snippet }`, using `content` or `snippet` as the snippet field, turning a non-string title or snippet into `''`, skipping entries without a string `url`, and refusing a body without a `results` array as `invalid response`.
- **`providers/tavily.ts`** — `POST https://api.tavily.com/search` with the bearer key and exactly `query`, `max_results`, `search_depth`, and `topic: "general"`; decodes `content`.
- **`providers/tinyfish.ts`** — `GET https://api.search.tinyfish.ai?query=<query>` with `X-API-Key`; ignores depth and decodes `snippet`.
- **`providers/catalog.ts`** — `tavilyManifest`, `tinyfishManifest`, and the ordered `webSearchProviderCatalog`; ids `tavily` and `tinyfish`, both at the current API version, each activating its own module.
- **`registry.ts`** — `createProviderRegistry(manifests)` with `providerNames`, `resolveAttempts`, and `runAttempt`, as decided above. The disabled state is a closed-over `Map<string, string>`, so a test builds its own registry rather than resetting shared state. `runAttempt` checks the manifest version first, separates activation classification from search classification, and keeps the abort check first in both. The catalog's ids, order, lowercase spelling, and versions are pinned by a test that never calls `activate`.
- **`failure-lines.ts`** — `formatFailures` for one failure and for the every-provider-failed list, used by both the registry's resolution lines and the core's final output.
- **`render.ts`** — pure `normalizeResults` (whitespace, title escaping, empty-title fallback, URL validation and encoding), `dedupeResults` (fresh `URL`, fragment cleared, one trailing slash dropped from `pathname`), and `renderResults(results, total, maxChars)` (the Markdown list, the truncation note, and the first-result snippet cut). `total` is passed verbatim as `<n>`, and an empty list renders `''`; the core never calls it empty because it prints the no-results line instead.
- **`search.ts`** — the one process-wide registry, `webSearchProviderNames()` for completion, and `runWebSearch(registry, request, deps)` / `webSearch(request, deps)`. It returns a resolution line unchanged; checks the signal before resolution, before each attempt, after a result, and before final failure lines; builds a fresh provider request and capability per attempt; stops on the first results; rethrows an abort outcome's original error; records each failure and formats the final lines. `renderSearch` normalizes, dedupes, cuts to `numResults`, returns `No results for "<query>".` when empty, and otherwise renders with the cut length as the total.
- **`command.ts`** — `WEB_SEARCH_USAGE`, `WEB_SEARCH_PRIMER`, the range and default constants, `WebSearchDepth`, `WebSearchCommand`, `isWebCommandLine` (`/^web(\s|$)/i`), `isWebSearchReplyLine` (lowercase `web`, whitespace, lowercase `search`, then whitespace or end of line), and `parseWebSearch`. The parser is pure, tokenizes with the file-glob scanner's shape, claims `web` and `search` case-insensitively, takes the query up to the first `--` token, scans flags after it, applies the range and whole-number checks, lowercases `--depth`, keeps `--provider` as typed, and fills the four defaults. The reply-line predicate is deliberately case-sensitive, unlike the typed parser, because a model's final answer often begins a sentence with "Web search …" and the extractor reads the reply's last recognized line as a command.
- **`tab-search.ts`** — `searchWebInTab(managers, label, input, signal?)`: parse first and return the usage line without touching a tab or port; ask `localReadRoot` for the side; a local tab calls `webSearch` with `getProjectTokens()`, `globalThis.fetch`, the signal, and a `reportDisabled` that posts the `plugin-failure` notification; a remote tab sends `port.webSearch(parsed)` through `withRemoteTabPort` and returns the port's text, turning a rejection into its `errorText` message. It never catches the local search's abort rejection, so the ACP loop's existing late-result suppression handles it.
- **`fixture-v1/`** — a frozen provider written against API version 1 with a literal `apiVersion: 1`, plus a compatibility test that registers it in a registry, checks its names, and runs one attempt against an injected `fetch`. It is not in the production catalog.

## Out of scope

- Fetching result pages; that is the separate `web fetch` feature (feature text, the next backlog entry).
- Multi-step search or navigation (feature text).
- Inferring freshness, stating the current date, or rewriting the query with a date (feature text, user decision).
- Configured domain filtering (user decision); `site:` operators in the query still work.
- Provider plugins from outside the build: filesystem discovery, npm packages, third-party loading (user decision).
- A core query-length cap (user decision).
- Paging a provider to reach `--results` (user decision).
- Provider options beyond `--depth`: topics, locations, languages, dates, answers, raw content, images (user decision).
- `web search` in `agent` runs, monitor personas, conversations, and editor persona queries (user decision).
- Cancelling a typed search (user decision).
- Re-enabling a disabled provider without a restart (user decision).
- Migrating saved roles files to add `web search` (user decision).
- Freezing the provider request object or narrowing what a provider may do with it (decision); each attempt only gets its own copy.
- A JSON argument form, a harness function-calling tool, or an MCP server (user decision).
- Completing query text, `--results` or `--max-chars` values, or any other `web` subcommand's arguments (user decision).
- Enabling any harness's built-in web search tool (from precedent).
