# System schedules 02: explicit schedule notification contract

**Complexity: 3/10** — one config gate and four notice helpers reuse the existing notification queue, delivery surfaces, and focus-link path.

This adds the notification contract before startup or the schedule owner emits it. It does not own the startup or firing state machines that decide when to emit.

## Goal

Add the default-on, focus-independent `system-schedule-fire` event and its notice helpers before startup or the schedule owner needs to emit it. The authoritative behavior and wording are in `product/plans/ready/add-system-schedules.md:72–77` (“Every firing, missed firing, and missing runscript” and the four message templates).

## Decisions and dependencies

- Dependency: 01 for the hidden-tab focus behavior. Reuse its rebased startup baseline. Plans 03 and 08 depend on this contract for startup failures and schedule firing, missed-run, and missing-script notices; they are the only event-source callers added later.
- Add `system-schedule-fire` as an explicit event, keep it out of the ambient map, and keep it in the exhaustive explicit-event and sound-category maps. Its one toggle is `notifications.events.systemScheduleFire`, default `true`; it is the only explicit event with a config toggle. A false value suppresses the event before it reaches the queue, record, toast, or native delivery. The existing `schedule-fire` event stays ambient, default-off, and focus-suppressed.
- On a fresh config, include the new key with value `true`. When an existing config omits `notifications`, `events`, or this key, or supplies a malformed value, decoding uses `true` in memory while preserving valid neighboring toggles. An explicit `false` stays false. Loading an older config does not rewrite it or prompt for migration; the next ordinary config write preserves its existing raw keys as it does today.
- The four message bodies are exact. A firing reads `System schedule <name> ran: script <runscript-name>`; `<name>` is the schedule id and the command shown is its stored `script <runscript-name>` invocation, not its expanded lines. This reports that the runscript was enqueued, not that its lines completed. A missed run reads `System schedule <name> missed its run at <time>; not run (app was closed).`; `<time>` is that entry's missed `nextRun`, formatted by `fmtNextRun`. A missing file reads `System schedule <name> could not run: script ".janissary/scripts/<runscript-name>.rs" is missing.` A shell-start failure reads `System shell could not start: <reason>.`; reduce the reason with `errorFirstLine` so it is one line without terminal punctuation before the final period.
- Export one notice helper per outcome: `notifySystemScheduleRun`, `notifySystemScheduleMissedRun`, `notifySystemScheduleMissingScript`, and `notifySystemShellStartFailure`. Each helper calls `notify` with event `system-schedule-fire`, origin label `system`, and `openTab` target `system`. The startup, firing, and immediate `execute` paths report a shell-start failure once per failed ensure attempt, not once in both the ensure helper and its caller. Successful immediate `execute` and individual runscript lines do not post this event.
- If startup fails before a managed system tab exists, still hold and record the notice under label `system`; the notification queue accepts an origin label without a matching tab. Its link focuses and reveals the managed system tab when one exists. A focus request for a missing tab is a no-op, and notification creation must not manufacture a placeholder tab.
- Reuse the existing explicit feed, toast, and native-alert delivery. The event has warning sound category in the single category table. Existing ambient and recording notices from the system shell retain their ordinary behavior, as do explicitly authored `notify` lines and their `manual` event. No per-line error notice or new delivery channel is added.
- The notification queue is process-local. `.janissary/notifications.json` is an append-only record and is never loaded to replay notices after restart; each newly detected missed run must enter the live pipeline as a fresh event.
