# Shell tab text transcript

**Complexity: 6/10** — a new server manager wrapping a headless-terminal row writer with asynchronous-parse flush ordering, an extraction out of the recorder, an RPC rename across server and web, and a new pushed per-tab field and metadata-row button; every piece has a close precedent, which keeps it out of the 7+ range.

## Summary

Write a readable plain-text transcript of every shell tab's terminal, alongside the asciicast recording that already exists, so what a shell session showed stays inspectable after the tab closes without replaying a `.cast` file, and give the shell tab an **Open transcript** button that opens it. The backlog entry reads verbatim: *"Write a readable, output-only terminal transcript for shell tabs alongside the existing asciicast recording, so command output remains inspectable after the tab closes. Parse the PTY stream as terminal output rather than stripping escape codes from raw bytes, and do not persist user input or its terminal echo; if the implementation cannot distinguish echoed input safely, omit it. Store the text transcript under `.janissary/shell-transcripts/`, bound its size, and clear/preserve it on the same fresh-launch and `--relaunch` lifecycle as recordings. Honor `recordShellTabs: false`. This covers transcript creation and retention only; making the transcript available to the launcher ACP summarizer is a separate feature."*

Questioning narrowed and in two places reversed that text: the transcript is the terminal's full normal-screen text — prompts and typed command lines included — rather than output only (decision 3), the file itself is uncapped with only memory awaiting disk and awaiting parse bounded (decision 7), and the tab gains a retrieval button (decision 8).

The recording already captures everything a shell prints, but as a timed byte stream full of escape sequences; it is unreadable as text. The transcript is the same session rendered as the lines a person saw.

## Design decisions

1. **Parsed as terminal output, not escape-stripped.** Established by the feature text. The PTY stream is fed through a server-side `@xterm/headless` terminal, as `HarnessScreenReader` already does for harness tabs (`src/harness/screen.ts`), and what is written is that terminal's rendered rows (`translateToString(true)`, which trims only the cells the program never wrote, so spaces a program printed, including the space after the `> ` prompt, are kept), so colours, cursor movement, carriage-return redraws and other control sequences never reach the file.
2. **One file per shell session, under `.janissary/shell-transcripts/`.** The directory is established by the feature text. The file is `<sanitized-label>-<ISO-timestamp>.txt`, named by the shared `harnessArtifactFilename` (`src/harness/artifact-name.ts`) exactly like a harness transcript, so two shell tabs never collide. A tab's transcript and its recording are named alike, but the writer and the recorder each take `Date.now()` at construction, so their timestamps may differ by a few milliseconds; threading one start time through both was not worth it. The file is created lazily on the shell's first output, like the recording, and a shell finished before any output leaves no file.
3. **The transcript is the shell's full normal-screen text as displayed, prompts and typed command lines included.** (User answers, rounds 4–5; supersedes the backlog's "output-only".) Every row the terminal draws on its normal screen is written: the `> ` prompt and the command typed at it, each command's output, output a background job prints while zsh is at its prompt, and whatever the startup files print before the first prompt. There are no separators, timestamps or annotations — the prompt lines already mark where each command begins, so the file reads as a plain-text replay of the session.
4. **Input is persisted as the terminal echoed it, and the spec says so.** (User answer, round 5; deliberately departs from the backlog's "do not persist user input or its terminal echo; if the implementation cannot distinguish echoed input safely, omit it".) No attempt is made to tell echoed input from output. A secret typed on a command line (`export TOKEN=…`) or echoed by an interactive program inside a command (a python REPL, `read`) lands in the transcript. A password typed at a prompt that disables echo (`sudo`, `ssh` and `psql` passwords) prints nothing, and the recorder writes only output, resize and exit events, never input, so that password reaches neither the transcript nor the recording. The specs' and user docs' older claim that such a password reaches the recording was corrected to these terms. The mitigations are the recording's: the file is under the project's own `.janissary/`, is never served over the network or handed to a client except when the user presses **Open transcript**, and is cleared at the next fresh launch. `recordShellTabs: false` is the opt-out.
5. **Rows are written as displayed, one file line per screen row, once, when the cursor first moves below them.** (User answers, rounds 3, 5 and 6.) A line longer than the terminal is wide is written as the rows it wrapped onto, so the file follows the tab's width at the time. A row is appended the first time the cursor moves below it — so **Open transcript** during a long-running command shows its output so far — and is never revisited: a row a program later redraws (a multi-line progress display, a zsh completion menu) keeps the form it had when first written, and `clear` removes nothing already written. A row redrawn by carriage returns before the cursor leaves it, such as a single-line progress bar, is written once in its final form. Three imperfections are accepted (decision 15): after a program erases the screen below rows already written, the row above the cursor can be written a second time in its current form; rows that auto-wrapped between such an erase and the next line feed keep only their last row; and a single unbroken line longer than 1000 terminal rows keeps only the row it ends on.
6. **Full-screen programs leave nothing in the transcript.** (User answer, round 3.) Whatever a program draws on the terminal's alternate screen (vim, less, top) is not written; normal-screen output before and after it still is.
7. **The file has no size cap; only memory waiting for disk or for the parser is bounded.** (User answers, rounds 1–2; the backlog's "bound its size" is met this way.) The transcript stops for the rest of the session, after the rows already finished, in three cases: an unwritable directory (the file never opens), more than 4 MiB waiting to reach disk (`MAX_PENDING_APPEND_BYTES`, the recorder's limit, now shared through `BoundedAppendFile`), or output arriving faster than the headless terminal parses it (more than `MAX_UNPARSED_CHARS`, 4 Mi characters, handed to xterm and not yet parsed). The last keeps the writer far below xterm's own 50,000,000-character watermark, past which xterm throws "write data discarded" from every `write`. After a failure the cursor's unfinished row is not written, since it may be the start of output that was dropped. Each case raises the failure notification (decision 10). The file otherwise grows for as long as the shell runs, and is bounded in time by the fresh-launch clear.
8. **An `Open transcript` button on the shell tab's metadata row, drawn with the clipboard icon, behaving like the harness tab's.** (User answers, rounds 1–2.) It mirrors the harness tab's existing button (`web/src/harness/HarnessTabMeta.tsx`: class `tab-open-transcript`, `viewCaptureIcon` — the regular-weight `faClipboard`): tooltip and accessible name `Open transcript`, placed after the **Show diff in the workspace** button (drawn only on a workspaced shell) and before the connections window button, the order `HarnessTabMeta` uses. It is never disabled. Pressing it opens the file as it stands in an editor tab named after the file (`<label>-<timestamp>.txt`), as the harness button's editor tab is. Once drawn it stays after a failure and opens whatever was written, and a docked shell's button works the same way. With `recordShellTabs: false` there is no transcript and the button is not drawn.
9. **Cleared at a fresh launch and preserved across `--relaunch`; `recordShellTabs: false` writes nothing.** Established by the feature text. The directory is a new `always: false` entry in `STATE_DIRECTORY_ENTRIES` (`src/state/dirs.ts`), and the transcript is installed on exactly the terminals a shell recording is installed on, behind the same gate (`TabManager.recordTerminal`, `src/tab/manager.ts`): the launch `janus` shell, every `shell` tab, remote shells and remote siblings, but not a PTY started with `!` from another tab.
10. **A write failure records one `shell transcript failed` line in the notifications feed for that tab and leaves the shell unaffected.** (User answer, round 2.) A new notification kind beside `shell-recording-failed`: lower-case, listed in `EXPLICIT_EVENTS` so focus suppression cannot swallow it, with the `error` sound category. It is recorded at most once per open tab however many of that tab's writers fail. A failure that surfaces only after the tab has closed records nothing, whether the shell exited first or the close released the writer, and a later tab reusing the label is reported afresh. A writer released by a reinstall under the same id reports nothing either, since its tab speaks through the newer writer. The recording is independent: either can fail without stopping the other.
11. **The unfinished line is flushed when the session ends.** (User answer, round 4.) When the tab closes or zsh exits, whatever is on the cursor's row — a prompt waiting for input, a progress bar — is written as-is, then the file is closed. At application shutdown the app waits up to one second (`SHELL_TRANSCRIPT_SHUTDOWN_WAIT_MS`) for every open transcript to write its final row and close, so quitting neither loses the last prompt nor hangs on a stalled disk. A crash or `SIGKILL` loses the unflushed tail, as it does for the recording.
12. **Remote shells get a transcript on the same terms as local ones.** (User answer, round 3.) Because the transcript is installed wherever a shell recording is, a remote shell or remote sibling gets its transcript written locally under `.janissary/shell-transcripts/` and shows the same button.
13. **Application command replies are left out.** (User answer, round 4.) A reply such as `help`'s, and the command line echoed above it, are drawn by the browser rather than printed by zsh, so they never pass through the PTY and never reach the transcript.

### Implementation decisions

14. **A separate `shellTranscript` manager in `src/shell/transcript/`, not a `HarnessRuntime` member.** (User answers, implementation rounds 1–2.) `ShellTranscriptManager` is a new `Managers` member owning one writer per shell PTY: `install(ptyId, label)`, `closeTab(label)` (listed in `MANAGER_TAB_RELEASE`), release of a writer on its PTY's `exit` event, and disposal of every writer at shutdown. `managers.shell` is already the unrelated line-oriented `ShellManager`, so the new key is `shellTranscript`. `TabManager.recordTerminal` calls `install` on the same line, behind the same `recordsTerminal` and `recordShellTabs` conjuncts, as `registerShellObservers` — so the transcript is installed on exactly the terminals that are recorded, remote shells included, and the recording and transcript stay independent observers of the same bus. Failure state is kept per open tab rather than per label (decision 10): each writer captures its tab's state object at install, and `closeTab` discards it.
15. **Rows are detected by a forward-only marker on the next row to write.** (User answer, implementation round 1.) A `TranscriptRowTracker` keeps one xterm marker (`terminal.registerMarker(0)`, an `IMarker` whose `line` follows its row as the buffer scrolls, trims and reflows) rather than a raw absolute index, which would drift by one row per line once the scrollback is full. With `C` the cursor's absolute row, each `onLineFeed` in the normal buffer does one of three things: with the marker alive and `marker.line ≤ C − 1`, it writes rows `marker.line … C − 1` and re-registers the marker on the cursor's row; with the marker alive and `marker.line ≥ C` (the cursor has moved back up over rows already written, as a multi-line redraw does), it writes nothing and leaves the marker where it is; with the marker disposed (trimmed away, erased by `ED 0`/`ED 2` as `clear` or a zle redraw does, or wiped by a reset), it writes only row `C − 1`, the row the line feed just finished, then re-registers. A reset hook (`parser.registerEscHandler({ final: 'c' })`) disposes the marker on `RIS` and lets xterm's own reset run, because a reset otherwise leaves the marker at its old index over a wiped buffer. Auto-wrapped rows, which advance without a line feed, are picked up by the next flush. The headless terminal keeps a 1000-row scrollback so rows scrolled off since the last line feed are still readable; while the alternate buffer is active nothing is written and the normal buffer's marker stays put.
16. **The button reaches the server through the existing transcript RPC, renamed `openTranscriptFileFor`.** (User answer, implementation round 1.) `openHarnessTranscriptFor` becomes `openTranscriptFileFor`, with no compatibility alias: client and server ship together. Its controller resolves the label's harness tailer file first and the shell tab's remembered `tab.transcript` (decision 17) second, opening whichever it finds through `managers.openFile.edit`, which names the editor tab after the file, and silently no-opping otherwise. No new protocol method; the rename runs through every place the method name appears.
17. **The client learns of the transcript from a pushed `transcript` path on the tab record.** (User answers, implementation rounds 1–2.) The writer's `onOpened(path)` callback sets `tab.transcript` on the tab with that label, if it still exists, and emits one `state: dirty` broadcast so the button appears at once rather than on the next unrelated broadcast. `buildTabView` copies the field onto the plugin envelope's `PluginTabView.transcript` only (never onto a harness payload), and the plugin client capabilities gain `transcript?: string` and `openTranscript?()`, supplied together or not at all — the `recording` / `openRecording` precedent exactly. The writer opens the file on the shell's first output, writing an empty string so it exists before any line feed, which zsh's prompt provides at once, so in practice the button appears as the shell starts. Under `recordShellTabs: false` no writer exists, the field is never set, and the button is never drawn; the client never reads the setting.
18. **The bounded append file is extracted from `HarnessRecorder` and shared.** (User answer, implementation round 2.) The recorder's lazy-open, single-stream, pending-byte-limited, fail-once append logic moves into one module, `BoundedAppendFile`, which both the recorder and the transcript writer use, so the 4 MiB rule has a single implementation. Its `dispose()` returns a promise so shutdown can wait for the transcript's last bytes; the recorder ignores it.

## Proposed changes

Prose only. Names are contracts, not code.

### Shared bounded append file (decision 18)

- New `src/bounded-append-file.ts`, beside `src/atomic-write.ts`, exporting `BoundedAppendFile` and `MAX_PENDING_APPEND_BYTES` (4 MiB, moved from the recorder's `MAX_PENDING_RECORDING_BYTES`, which no longer exists). The constructor is positional, `(resolvePath, maxPendingBytes, onFailure)`, and does no I/O. `resolvePath` is called once, at open time, and is responsible for ensuring the directory exists, so the module imports only `createWriteStream` from `node:fs` and the recorder's backpressure test's `node:fs` mock still applies.
- `write(line)` opens one append stream on the first call, refuses and abandons on a line whose UTF-8 bytes would push `writableLength` past the limit, and is a no-op after a failure or dispose. A synchronous throw from the open and an asynchronous stream `'error'` abandon too. Abandon destroys the stream and fires `onFailure` exactly once.
- `isOpen()` is true from a successful open until abandon or dispose. `openedPath()` names the file once a stream has been created, is kept after abandon and dispose, and is cleared only when the open itself threw. There is no `onOpened` hook: callers check `openedPath()` after their first write.
- `dispose()` returns a `Promise<void>` that resolves when the stream emits `'close'`, at once when no stream is open, and never rejects; a second call returns the same promise.
- `src/harness/recorder.ts` replaces its own stream handling with one `BoundedAppendFile`, keeping its header-then-`onOpened` ordering and gating resize and exit events on `isOpen()` so they never lazily create a file with no header. Its behavior is unchanged, and it ignores the dispose promise. `src/harness/recorder-backpressure.test.ts` imports the renamed constant from the new module.

### Transcript directory (decisions 2, 9)

- New `src/shell/transcript/transcript-file.ts`, in the shape of `src/harness/transcript-file.ts`: `initShellTranscriptDirectory` to `<project>/.janissary/shell-transcripts`, `ensureShellTranscriptDirectory`, `shellTranscriptPath(label, startedAt)` through `harnessArtifactFilename` with a `.txt` extension, and `clearShellTranscriptDirectory`, which removes nothing before init and ignores a throwing removal.
- `src/state/dirs.ts` — a new `shellTranscript` entry (`always: false`) after `harnessTranscript`, and its key in `KNOWN_STATE_DIRECTORY_KEYS`.

### Writer and row tracker (decisions 1, 3, 5–7, 11, 15)

- New `src/shell/transcript/writer.ts` — `ShellTranscriptWriter(ptyId, label, cols, rows, onFailure, onOpened, maxUnparsedChars = MAX_UNPARSED_CHARS)`. It creates an `@xterm/headless` terminal (the CommonJS default-import workaround from `src/harness/screen.ts`) with a 1000-row scrollback and `allowProposedApi: true`, a `BoundedAppendFile` whose path factory ensures the directory and returns `shellTranscriptPath(label, startedAt)`, and a `TranscriptRowTracker` whose sink writes each flush as one `write` call, only while the file is open. It subscribes to the `pty` bus for its id.
- `data`: an empty chunk is ignored. The first chunk opens the file by writing the empty string, then calls `onOpened(openedPath())` once if a path came back. A chunk that would push the unparsed count past `maxUnparsedChars` fails the writer instead of being written; an accepted chunk adds its length and passes a per-chunk callback that subtracts it once parsed.
- `resize` is queued behind output already received (`write('', cb)` then `term.resize`), so rows that arrived before it still wrap at the old width.
- Every `term.write` goes through one `queue` helper that catches xterm's "write data discarded" throw and returns `false`; a refused write fails the writer, so nothing throws into the bus.
- `fail()` is idempotent across the unparsed cap and the file's own failures: it runs the finishing path and fires `onFailure` once. It does not dispose the file up front, so chunks already accepted are still parsed and their finished rows reach the file while it stays writable.
- Exit, `dispose()` and failure share one finishing path, guarded so it runs once: unsubscribe from the bus at once, then `term.write('', cb)` so every chunk already queued is parsed first; in the callback, the tracker's final flush (skipped after a failure), `file.dispose()`, then `term.dispose()`. If xterm refuses even the drain write, the file and terminal close at once without the final flush. `dispose()` returns one promise per writer that settles once the file has closed, and never rejects.
- New `src/shell/transcript/row-tracker.ts` — `TranscriptRowTracker(term, sink)`, the forward-only marker logic of decision 15, the reset hook, and `finish()`: in the normal buffer, with the marker alive and `marker.line ≤ C` it writes `marker.line … C`; with it alive and past the cursor's row it writes nothing (that row was already written); with it disposed it writes row `C` only. The cursor row is written as-is even when blank, so a waiting `> ` prompt is written as `> `. Its class comment states the accepted imperfections.
- **Remote shells** need no special case: `spawnRemotePluginTerminal` is handed the same recorded PTY id, and `recordTerminal` installs on that id, so the writer sees the same `pty` bus events the recorder does.

### Manager (decisions 10, 11, 14, 17)

- New `src/shell/transcript/manager.ts` — `ShellTranscriptManager`, constructed with `managers`. It holds a map from PTY id to `{ label, writer }`, a map from open tab label to `TabFailureState` (`{ notified: boolean }`), and a `WeakSet` of released writers, and subscribes to the `pty` bus's `exit`.
- `install(ptyId, label)` first releases any writer held for that id, so a reattached remote sibling never writes every row into two files, then captures the label's current failure state (creating it if absent) and builds a writer with `managers.pty.spawnDimensions()`. Its `onFailure` reports only when the writer is not released and the captured state is still the label's current one (an identity check, not a presence check), and `reportFailure` notifies `shell-transcript-failed` once per state. Its `onOpened` looks the tab up by label at call time, and when found sets `tab.transcript` and emits `state: dirty`.
- `closeTab(label)` releases every writer held under that label (marking it released and disposing it without awaiting), then deletes the label's failure state, so any late failure from a writer of that tab, exited or released, is dropped, and a later tab reusing the label starts fresh.
- A `pty` `exit` only drops the entry for that id. The writer's own exit listener runs its finishing path, and a failure from it still reports while its tab is open.
- `dispose()` unsubscribes, disposes every writer and clears the map. With no writers it returns nothing; otherwise it returns a promise that resolves when every writer's dispose has settled or after `SHELL_TRANSCRIPT_SHUTDOWN_WAIT_MS` (1000 ms), whichever comes first, and never rejects.
- The manager exposes no path lookup; the tab record is the single source.
- `src/managers.ts` — `shellTranscript: ShellTranscriptManager` in `ManagerRegistry`; `'shellTranscript'` in `MANAGER_DISPOSE_ORDER` directly after `'harness'` and before `'shell'` and `'pty'` (group 1, with the group comment saying it must flush while the shells it mirrors are alive and that its disposal is awaited), and in `MANAGER_TAB_RELEASE` after `'harness'`. `src/controller/create-managers.ts` constructs it directly after `managers.harness`.
- `src/tab/manager.ts` — `recordTerminal` calls `this.managers.shellTranscript.install(ptyId, label)` beside `registerShellObservers`, under the same condition, and its comment says the transcript follows the recording's gate exactly.
- `src/tab/types.ts` — optional `transcript?: string` on the `Tab` record after `recording`, commented like it.
- Hand-built `Managers` test fixtures cast through `unknown` gain a `shellTranscript` stub, since the typecheck cannot name them: `src/tab/manager.test.ts`, `src/tab/cleanup.test.ts`, and the plugin fixtures in `src/plugins/launch-tab.test.ts`, `terminal-refusal.test.ts`, `grouping.test.ts`, `notifications.test.ts`, `teardown.test.ts`, `update-tab.test.ts` and `launcher/host-lifecycle.test.ts`.

### Implementation order

Each step leaves typecheck and tests green on its own. The feature was delivered as eight subplans following this order, then four repairs, all folded into this plan.

1. Extract `BoundedAppendFile` and move `HarnessRecorder` onto it, with `src/harness/recorder.test.ts` unchanged and green.
2. Rename `openHarnessTranscriptFor` → `openTranscriptFileFor` everywhere, behavior unchanged.
3. The `shell-transcript-failed` notification kind — inert until step 6 fires it.
4. The transcript directory module and its `src/state/dirs.ts` entry.
5. `ShellTranscriptWriter`, `TranscriptRowTracker` and the unparsed-output cap, with their tests.
6. `ShellTranscriptManager`, `Tab.transcript`, the promise-returning disposes, its `Managers` registration, and the install call in `TabManager.recordTerminal`.
7. `PluginTabView.transcript`, the `state: dirty` broadcast on open, and the shell branch in `openTranscriptFileFor`.
8. The client: capabilities, `PluginBody`, the icon re-export, and the `ShellTabMeta` button.
9. Specs, `help.md` and documentation.

## Out of scope

- Making the transcript available to the launcher ACP summarizer — a separate feature.
- Filtering echoed input or secrets out of the transcript (decision 4).
- A total size cap or rotation of the file (decision 7), and PTY flow control that would pause the shell while the transcript catches up.
- Separators, timestamps or exit statuses in the file (decision 3).
- Alternate-screen content (decision 6) and application command replies (decision 13).
- Reflecting later redraws of rows already written (decision 5).
- One shared start time for a tab's transcript and recording (decision 2).
- Reporting a failure that surfaces after its tab has closed (decision 10).
- Preserving the unflushed tail across a crash or `SIGKILL`, and awaiting `HarnessRecorder`'s disposal at shutdown (decision 11).
- A compatibility alias for the old `openHarnessTranscriptFor` name (decision 16).
