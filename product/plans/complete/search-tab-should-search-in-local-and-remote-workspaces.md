# Search tab should search in local and remote workspaces

**Complexity: 7/10** — seven new host capabilities plus an `originTab()` extension across five tab kinds, a remote channel joined and released in place on an existing tab, a wire field on the default-menu RPC, a payload schema bump, and two files already at the size limit that must be split first.

The search tab only ever searched the project's launch directory. That's the wrong place when the text you're after lives in a workspace clone: a workspaced harness or agent edits its own clone, local or on another host, and the launch directory never sees those edits. Right-clicking a line in that harness and choosing **Search for this** searched the launch directory, so it found the old code or nothing. This feature makes the search follow the workspace. A search started from a workspaced tab searches that workspace, lists that workspace's matches, and opens a match from that workspace.

## Design decisions

Established by the feature text:

- `Search for this` in a workspaced harness or agent tab, local or remote, searches that tab's workspace rather than the launch directory.
- The results come from that workspace, and opening a result opens the file in that workspace.

Settled with the user:

- **There is still one search tab.** It doesn't multiply per workspace. A route started from a workspaced tab re-scopes the one tab to that tab's workspace, and its results replace whatever the tab showed before.
- **Three routes follow the workspace of the tab they start from:** **Search for this**, a typed `search` or `search <phrase>` in a workspaced tab's command bar, and **Cmd+Shift+F** (Ctrl+Shift+F elsewhere) while focus is in a workspaced tab.
- **Five kinds of tab carry a workspace for these routes.** A shell or harness tab that owns a clone, an agent monitor tab (`Agent: <task>`) whose run executes in a workspace, local or remote, an editor tab whose file lives in a clone (a local one, or one materialized from a remote workspace), and a file navigator rooted inside a clone, local or remote. An agent monitor keeps pointing at its run's workspace after the run ends; once that workspace has been released and removed, it's refused as no longer available. A local agent run outside any clone searches the launch directory. The search tab itself is one more origin: **Search for this** on a selection inside it keeps its current scope rather than jumping back to the launch directory. Every other tab searches the launch directory.
- **A workspace that hasn't landed yet is refused.** When the clone is still running, or a remote tab's far side hasn't answered, nothing opens and nothing is searched. The refusal goes to the notifications feed, not to the transcript, and reads exactly `Search: the workspace of "<name>" is not ready yet.`
- **An origin whose workspace is gone is refused too.** An editor, navigator, or agent monitor tab whose clone was removed, or whose remote session ended, doesn't fall back to the launch directory. Nothing is searched, and the notifications feed reads exactly `Search: the workspace of "<name>" is no longer available.`
- **`<name>` is the workspace label** in both notifications: the clone's own label, such as `claude-2` for `$workspace/claude-2`, whichever tab the route came from. A remote tab whose far side hasn't answered is named by the channel entry's workspace label, or by the tab's own label when the entry doesn't know one; a gone record whose channel entry was released is named by the tab's own label.
- **The header names the scope.** It shows the root in the diff tab's abbreviated form: `$root` for the launch directory, `$workspace/<name>` for a local clone, and the host first for a remote workspace. The tab's title stays **search** whatever the scope.
- **A bare route from another scope re-scopes and reruns.** When a bare `search` or the chord comes from a different scope than the open tab's, the tab moves to the new scope and reruns the query, toggles, and narrowing fields already in it against the new root. From the same scope it only focuses the tab. A route carrying a phrase searches that phrase in its own scope. A re-scope with an empty query runs nothing, republishes the tab with no rows so nothing from the old scope stays clickable, and shows `Type to search`.
- **A re-scope keeps the tab's own state.** The term history and the include and exclude fields carry over. Only closing the tab forgets them; a tab rebuilt after a close starts at the launch directory.
- **A remote scope holds its session.** While the search tab is scoped to a remote workspace it joins that workspace's channel, the way a remote diff tab or remote file navigator does. It releases the channel when it re-scopes elsewhere or closes. A local scope holds nothing, so the clone still goes when its last tab closes.
- **A failed join keeps the old scope.** When the target's channel can't be joined (the source rides no channel, is reconnecting, or the attach refuses), the route notifies the no-longer-available line, searches nothing (not even a phrase it carried), and the tab keeps its previous scope. The order is release-then-join, because one tab holds one channel entry; so a previous remote scope is rejoined through its own `ride`, and if that rejoin fails too the tab falls back to the launch directory as an ordinary re-scope. A search still running in the kept scope when the failed route arrived was cancelled by the re-scope, so it is started again there and settles rather than staying in its searching state.
- **A result opens only from the scope that produced it.** The session remembers the scope that produced the listing root, set only by the scan currently feeding the tab, so a cancelled scan's late listing never moves the root. A local or launch row opens by its path even after a re-scope. A remote row opens only while its producing scope is still the tab's scope; after a re-scope its channel has been released, so a stale remote row opens nothing, silently.
- **A workspace that goes away closes the tab.** When the scoped workspace's clone is removed, or its remote session ends, the search tab closes itself, the way a workspace diff does. Any search still running is abandoned. Nothing is said about it: the tab that owned the workspace closing, or the session ending, already explains it. The server closes it, not the client, so it closes even while no browser is connected. That's why the plan adds `closeOwnTab` rather than reusing the diff tab's client-side `capabilities.close()`. An offline or provisioning workspace is not gone. Closing the tab the search started from closes the search tab only for a local clone; a remote session is held by the search tab itself. When closing would quit the application, `closeOwnTab` does nothing and the tab stays open on its gone scope.
- **Remote files are searched on their host.** The `search-text` remote filesystem operation lists the workspace with the same gitignore-aware file list as a remote navigator, filters candidates, checks file size and binary content, and runs the shared matcher on the far side. It returns only the capped matching rows in one response; candidate file contents do not cross the channel. This adds a remote protocol operation and `remoteWorkspaceSearch` host capability. Unlike local scans, remote rows appear together when the operation completes. Streaming and cancellation frames remain future work if remote scan time warrants them.
- **"Which workspace is this tab in" is answered by the host's `originTab()` record**, extended to editor, navigator, and agent monitor tabs, so every plugin gets the same answer.
- **The search tab joins and releases a remote channel in place.** It keeps its label and strip position across re-scopes, rather than being closed and relaunched.
- **The default-menu action and the chord name the tab they came from.** The default-menu action's origin used to be whichever centre tab was active, which is wrong for a right-click inside a docked sidebar tab. This changes the origin of every default-menu entry, so **Chat about this** is also attributed to the tab the selection is in.

Established by existing behavior:

- The search tab is a single tab with instance key `search`, titled **search**, searching a gitignore-aware file list (`product/specs/search-tab.md`).
- A workspace diff closes itself when its workspace disappears, and a remote diff joins and releases the channel its tab rides (`product/specs/diff-tab.md` § Opening the tab, § A workspace on another host).
- A remote workspace's files reach a local editor through the same materialization cache a remote file navigator uses, so a save from that editor writes back over the channel for as long as the materializing tab holds it (`src/plugins/remote-capabilities.ts`).
- Closing a tab whose record carries `remote` releases its channel reference (`src/tab/cleanup.ts`, the `MANAGER_TAB_RELEASE` walk calling `managers.remote.closeTab`).

## Proposed changes

### 1. Host: the workspace an origin tab is in

`src/plugins/origin-workspace.ts` exports one function, `originWorkspace(managers, tab)`, answering `{ workspace?, provisioning, workspaceLabel? }`. `originTab()` in `src/plugins/line-capabilities.ts` calls it in place of its old inline `workspaceDir` and `provisioning` lines and spreads the answer into the record, omitting `provisioning` when false and `workspaceLabel` when undefined; the launch-shell branch still answers no workspace. Record builders shared by the rules live in `src/plugins/origin-workspace-records.ts` (`localWorkspace`, `remoteWorkspace` delegating to `channelWorkspace(managers, rideLabel, host)`, `goneWorkspace(dir, label)`, `ridingTabFor(managers, host, dir)`, `localCloneOf(path)`), and the agent monitor, editor, and navigator rules live in `src/plugins/origin-workspace-kinds.ts`. Every manager method is called optionally, so the partial fake managers existing tests hand in stay valid.

`TabPluginOriginTab.workspace` is now the exported `OriginWorkspace` type: `{ dir; offline?; label; display; ride?; host?; gone? }`. `label` is the workspace label, `display` is `abbreviateWorkspaceDir(dir)` (or `''` for an empty dir), `ride` is the label of an open tab riding a remote workspace's channel, `host` is that tab's remote host string, and `gone` is set, and only then, when the tab points at a workspace that no longer exists. A gone record never also reports `provisioning`. The record also gains a top-level optional `workspaceLabel`, set beside `provisioning` when a remote tab's far side has not answered and so there is no `workspace`, so a caller can name it in the not-ready refusal. The top-level `remote` and `provisioning` flags keep their meaning for shell and harness tabs; all fields are additive and `TAB_PLUGIN_API_VERSION` does not change. The diff plugin's `openSibling` (`src/plugins/diff/activate.ts`) also returns early on `origin.workspace.gone`, so a diff tab is never opened on an empty dir or a dead channel.

`WorkspaceManager` gets one read-only method, `tracks(dir)`, answering `this.refs.has(dir)`. A provisioning clone is tracked; the last `release` untracks it.

The rules, per tab kind (the three new kinds are dispatched after the `workspaceDir` check and before the `!tab.remote` return, since none of them sets `tab.remote`):

- **Shell and harness tabs**, and any tab carrying `workspaceDir`: a local clone's label is the clone directory's basename. A remote one's dir and label come from `managers.remote.workspaceOf` / `workspaceLabelOf`, and `ride` is the tab itself. With no directory yet the answer is `provisioning: true` with `workspaceLabel`.
- **A plugin tab that rides a channel** (its record carries `remote`, as a joined search or diff tab does): the channel's workspace with `ride` the tab itself. `gone` is set when `tab.sessionTerminated` is set (keeping the entry's dir, label, `ride`, and `host`) or `managers.remote.get(label)` is undefined (`dir: ''`, the tab's own label).
- **Agent monitor tabs** (`AGENT_MONITOR_PLUGIN_ID`): the bound run's `view()` through `tab.plugin.agentRunId`. `AgentManager` keeps a run in `runs` while any monitor is bound, so the view outlives the run's end. A missing run is `gone`. `host === 'Local'` goes through `localCloneOf`: a path under the workspaces directory follows the clone rule (tracked → the clone, untracked → `gone`), and anywhere else answers no workspace, since a run without a clone works in the caller's cwd. Any other host rides `ridingTabFor(view.host, view.workspace)`, the first live label-keyed channel entry with that host and directory whose tab is still open; with none (the lease released, or a run-only `on <host>:<path>` connection), it's `gone` with the run's dir and host.
- **Editor tabs**: a remote-cache file resolves through `remoteFileFor` to the tab that materialized it. While that tab's channel exists it rides that tab, with the host from `managers.remote.addressOf`; once the channel is gone it's `gone`, labelled from `workspaceLabelOf` or the record's root basename; an orphaned cache file with no record is `gone` with the editor's own label. There is no fallback to another riding tab: the record is forgotten when the materializing tab's port is disposed, so such a fallback could never fire. A local file goes through `localCloneOf` and the clone rule; outside the workspaces directory it answers no workspace.
- **File navigator tabs**: a remote navigator (`tab.files.remote` set) rides its own channel, with the host from `tab.files.remote`; `provisioning` with `workspaceLabel` while the channel has no directory, and `gone` once the channel is gone. A local navigator's root is `tab.files.absoluteRoot` (not the display-abbreviated `root`) through `localCloneOf` and the clone rule.

### 2. Host: new capabilities

All additive, each named in `TAB_PLUGIN_CAPABILITY_NAMES` (`src/plugins/api-capabilities.ts`). `src/plugins/api.ts` sat at the 200-line `max-lines` limit, so signatures moved into type modules intersected into `TabPluginServerCapabilities`: `src/plugins/api-remote-workspace.ts` (`TabPluginRemoteWorkspaceCapabilities`: `readWorkspaceChangeSet`, `materializeRemoteFile`, and the five remote capabilities below), `src/plugins/api-project.ts` (`TabPluginProjectCapabilities`: `projectFileList`, `openInEditor`, `workspaceTracked`), and `src/plugins/api-own-tab.ts` (`TabPluginOwnTabCapabilities`: `setUnread`, `setBusy`, `dockTab`, `snapshotTab`, `closeOwnTab`).

`src/plugins/context.ts` was at 195 code lines, so `projectFileList` and `openInEditor` moved verbatim out of `createPluginContext` into `src/plugins/project-capabilities.ts`, spread back in the way `lineCapabilities` is. `src/plugins/file-capabilities.ts`, a stale unreferenced copy, is left untouched.

- **`projectFileList(root?)`**: with no argument, today's call. With a root inside the launch directory it lists that directory with `listProjectFiles` and answers `{ root: path.resolve(root), paths }`. A root outside the launch directory answers `{ root: '', paths: [] }`. Local clones live under the launch directory, so they pass.
- **`workspaceTracked(dir)`**, beside it: `managers.workspace.tracks(path.resolve(dir))` for a directory inside the launch directory, false otherwise or while disabled. It's how a plugin that holds a local scope but rides nothing learns its clone is gone.
- **`remoteWorkspaceFileList(instanceKey)`**: the gitignore-aware list of the remote workspace this plugin's own tab (by instance key, through `pluginTabByInstanceKey`) rides, as `{ root, paths }` through `port.search(root)`. Null when there is no such tab, it rides nothing, the port isn't ready, or the plugin is disabled; a failed listing rejects, so the scan reports it.
- **`readRemoteWorkspaceFile(instanceKey, relPath, maxBytes)`**: one file of that workspace as UTF-8 text, after a `port.statRows` size check. Null when the tab rides nothing, the stat row is missing or over `maxBytes`, either call throws, or the resource is no longer live after the read. Both remote reads live in `src/plugins/remote-capabilities.ts` (which now takes `declaration`) and address the plugin's own tab, because the scan outlives the call that started it, and the tab that started it may be the harness the user right-clicked in.
- **`remoteWorkspaceSearch(instanceKey, request)`**: searches the plugin's own remote workspace on its host using the shared search implementation and returns the capped matching rows. Null when the plugin tab no longer rides an available remote workspace; a failed operation rejects. The operation is added to `src/remote/filesystem/operations.ts` as `search-text`, and `src/file-navigator/search-text.ts` performs the scan on the far side.
- **`joinRemoteWorkspace(instanceKey, sourceLabel)`** and **`releaseRemoteWorkspace(instanceKey)`**, in `src/plugins/remote-join-capabilities.ts`. Join attaches this plugin's own open tab to `sourceLabel`'s channel and copies a fresh `{ address, host }` of the source's `remote` onto the tab record, so the existing close path releases it. It answers false, changing nothing, when disabled, there's no own tab or source tab, the source has no `remote` or no channel, the source is reconnecting (checked before attaching), or the attach refuses. Release calls `managers.remote.release(tabLabel)`, clears the record's `remote`, and drops its port with `releasePluginRemoteResource`; on a tab riding nothing or an unknown key it's a no-op. Both emit a `state` dirty only after a change.
- **`closeOwnTab(instanceKey)`**, in `src/plugins/own-tab-capabilities.ts`: finds the tab addressed like `dockTab` and fires `void managers.tab.closeTab(index)`, the ordinary close path that runs cleanup and releases any channel. It is a no-op for an unknown key, another plugin's tab, while disabled, and when `closeQuitsApp` says the close would quit the app. It is callable from a `notify` handler and never awaited there.

The developer docs' capability count rose from forty to forty-seven over these additions, and `src/plugins/documentation.test.ts` extends its `COUNT_WORDS` table through `forty-seven`.

### 3. Search plugin

The manifest (`src/plugins/search/manifest.ts`) adds `notifyUser`, `originTab`, `materializeRemoteFile`, `remoteWorkspaceFileList`, `readRemoteWorkspaceFile`, `remoteWorkspaceSearch`, `joinRemoteWorkspace`, `releaseRemoteWorkspace`, `workspaceTracked`, and `closeOwnTab` to `capabilities`, and declares `notifications: ['tabs']`.

`src/plugins/search/scope.ts`, pure and importing only types from `../api.js`:

- `SearchScope` = `launch` | `local` with `dir`, `label`, `display` | `remote` with `dir`, `label`, `display`, `host`, `ride`. `display` carries the origin's `workspace.display`, since the plugin can't abbreviate a directory itself; a riding record without a host maps to `host: ''`.
- `scopeFrom(origin)` answers a scope, a refusal (`not-ready` or `gone` with its label), or `keep`, tested in this order: the search tab's own origin keeps; a `gone` workspace refuses (before the `ride` test, since a gone riding record still carries `ride`); `provisioning` refuses not-ready, labelled `workspace.label`, else `workspaceLabel`, else the origin's own label; a workspace with `ride` is remote (the test is `ride`, not the top-level `remote` flag, because an editor of a materialized remote file rides without being a remote tab); one without is local; no workspace or a null origin is launch.
- `sameScope(a, b)`: same kind, and the same `dir` for local, the same `host` and `dir` for remote. Two riding tabs onto one remote workspace are the same scope.
- `refusalLine(reason, label)` builds both notification lines, so their wording lives in one place; `scopeDisplay(scope)` answers `$root` or the scope's `display`.

`src/plugins/search/scope-ride.ts` exports `enterScope(target, previous, capabilities)`: release, then join the target's `ride` for a remote target; on a failed join, keep a local or launch previous scope, rejoin a remote previous scope through its `ride`, and fall back to `launch` when that also fails. It answers the scope the tab ended up on and whether the target's join failed. Release and join go through the session's kept capabilities, since both are addressed by instance key.

`src/plugins/search/scope-files.ts` exports `scopeFileAccess(scope, capabilities)`: `launch` lists `projectFileList()`, `local` lists `projectFileList(dir)` and reads from disk as before, and `remote` supplies a `remoteSearch` callback that calls `remoteWorkspaceSearch('search', request)`. The remote scan returns its capped rows after the far-side operation completes.

`src/plugins/search/scope-gone.ts` exports `scopeGone(scope, rows, capabilities)`: false for `launch`, asking nothing; `!workspaceTracked(dir)` for `local`; for `remote`, the search tab's own row (by `plugin.id` and `plugin.instanceKey` both `search`) is asked `originTab(row.label)`, and only `gone: true` counts. No own row is not gone.

`SearchSession` (`src/plugins/search/session.ts`) holds the current scope, starting at `launch`, and the scope that produced its listing root (`rootScope`).

**Every route uses its own call's capabilities.** `sessionFor` keeps the capabilities of the first call ever made, and that object's origin is the tab of that first call; once that tab closes, its `openOrFocusTab` returns early and its `openInEditor` is attributed to the wrong tab. Closing a workspaced harness is exactly the common case here. So `open(argument, capabilities)` and `openMatch(relPath, line, capabilities)` take the calling route's capabilities as a required parameter, and `command`, `defaultMenuAction`, and the `open` intent in `activate.ts` pass theirs. The capabilities kept on the session stay for what's addressed by instance key or needs no origin: `updateTab`, the settings, the project file list, remote search, join, and release.

- `open(argument, capabilities)` resolves `scopeFrom(capabilities.originTab())`. On a refusal it calls `capabilities.notifyUser` with the line and returns before opening anything. Otherwise it opens or focuses the tab; the factory, which runs only when the tab is being built, cancels any scan and resets the scope to `launch` along with everything else it resets. It notes whether the payload was still `searching`, then re-scopes. A changed scope cancels the running scan, goes through `enterScope`, and on success sets the payload's `scope` and `host` (`host` cleared explicitly for launch and local, since `payloadOf` spreads the old payload). A failed join notifies the no-longer-available line and, when a scan was interrupted, reruns the kept scope's request, then returns. Otherwise a phrase is searched in the new scope, a bare route that moved reruns the current request (or republishes empty rows when the query is blank), and a bare route in the same scope only focuses.
- `run` takes its file access from `scopeFileAccess` for the scope current when it is called, so a query typed in the tab also searches the current scope. Local and launch scopes list files and match them through the local worker; a remote scope calls `remoteWorkspaceSearch` and receives its capped rows when the host finishes. It keeps the handle `startScan` returns in a local `scan`, and the `listFiles` wrapper sets `root` and `rootScope` only when `this.scan === scan`, so a cancelled scan's late listing never overwrites the root.
- `openMatch` joins the root and checks `isInsideRoot` first. A row whose `rootScope` is local or launch opens through the route's `openInEditor`. A remote row opens only when `sameScope(rootScope, scope)`: then `materializeRemoteFile(relPath)` on the route's capabilities and `openInEditor` on the answered path, as `DiffTab.openFile` does; a null answer, synchronous or from the promise, opens nothing.
- `checkScope(event, capabilities)` handles a `tabs` delivery whose `event.tabs` includes `search`: when `scopeGone` says yes, it cancels the scan and calls `closeOwnTab('search')`, with no `note` and no `notifyUser`. `activate.ts`'s `notify` handler returns for other topics and calls it only on an existing session, never building one. The `tabs` topic is coalesced over `TABS_NOTIFICATION_WINDOW_MS` after a `state` dirty, which lands after the tab-close path's deferred `workspace.release`, so the clone is already untracked when the handler reads it.
- `dispose` and the tab closing both cancel the scan. Closing releases the channel through the host's own cleanup.

`ScanOptions` (`src/plugins/search/scan.ts`) gains an optional `remoteSearch(request)` callback returning matching rows or null. When present, the scan sends the query and filters through that callback, drops a late response after cancellation, and publishes the completed result set as one batch. The remote host reuses the shared matcher, path filters, row builder, file-size limit, binary check, and 250-row cap; local scans retain their bounded, ordered streaming path.

`SearchPayload` (`src/plugins/search/shared.ts`) gains `scope: string` (`$root`, or the origin's `workspace.display`) and optional `host`. `isSearchPayload` requires `scope` and accepts an absent or string `host`. `SEARCH_PAYLOAD_SCHEMA_VERSION` is 2, and the literal in `web/src/plugins/registry.tsx` matches it. `emptyPayload()` sets `scope: '$root'`.

### 4. Routes name the tab they came from

- `DefaultMenuRunRequest` (`src/protocol/plugin.ts`) gains optional `tab`, and the ingress guard in `src/client-params/plugin.ts` accepts it through `optionalString`. `src/message/plugin.ts` passes it through to `controller.runDefaultMenuSelectionAction(selection, action, tab)`. `PluginControllerAdapter.runDefaultMenuSelectionAction` (`src/controller/plugin-adapter.ts`) takes the third argument, and `originOf(managers, tab)` uses the exact `managers.tab.byLabel(tab)` match as the origin, falling back silently to the active tab when `tab` is absent, empty, or names no open tab.
- One shared helper, `enclosingTabLabel(target)` in `web/src/shared/tab-label-lookup.ts`, answers the nearest `[data-tab-label]` ancestor-or-self. `useDefaultContextMenu` captures the right-clicked element's label into `pending` when the menu opens and the focused element's label for the `Cmd+I` path, and adds `tab` to the run request only when defined. `chordTabLabel` uses the same helper.
- The `projectSearch` chord in `metaChordOpener` (`web/src/useWindowKeys.ts`) sends `search` with `tab` set to the event target's enclosing label, and no `tab` when focus rests on the page. `runCommand` in `web/src/App.tsx` takes an optional second `tab` argument and adds it to the params only when defined; its type is widened in `web/src/pickers/picker/key-bindings.ts`, `overlays-state.ts`, and `usePickerOverlays.ts`.
- `TabBodyDiv` in `web/src/MountedViewLayers.tsx` and the harness body in `web/src/harness/HarnessTabLayer.tsx` carry `data-tab-label`. In `web/src/Sidebar.tsx` the `.sidebar-body` div carries it only while the current entry is a core view (files or notifications), since a docked plugin body already carries its own and naming it there would make its label enclose the sidebar's strip. ### 5. Search tab client

## Out of scope

- One search across the launch directory and every open workspace at once, in a single result list.
- A control on the search tab for pointing it at a different workspace. Only the routes above change its scope.
- Searching a clone none of whose tabs is open. It's removed when its last tab closes anyway.
- Searching a remote tab's directory outside its provisioned workspace.
- Searching the workspace of a remote agent run on a run-only SSH connection (`agent on <host>:<path> ...`), which no tab rides. Its monitor is refused with the no-longer-available notice.
- Quick Open, the diff tab, and every other launch-directory feature keep their current scope.
- A far-side text-search operation for remote workspaces.
- Keeping the tab open with a "workspace gone" state when its close is refused because it is the last tab.
- Telling the user why a stale remote row opened nothing, or keeping an old remote channel alive to serve stale rows.
- Deleting the unreferenced `src/plugins/file-capabilities.ts`.
