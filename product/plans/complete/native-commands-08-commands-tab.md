# Native commands: Commands tab and command

**Complexity: 5/10** — a new center-opening plugin combines a strict command grammar with exact errors, a topic-backed settings loop, accessible checkbox navigation, and small inventory corrections, without new protocol or persistence.

## Goal

Let users inspect and edit global and native-agent availability in the Commands tab or through the `commands` command.

## Decisions and dependencies

- Depends on completed units 1–2 (canonical inventory and `nativeCommandSettings`), unit 4 (dispatch refusal), and unit 7 (the `commands` topic), all published on this branch. Units 5–6 precede this one in the feature sequence but are not API dependencies. Unit 9 consumes the same topic for Roles; unit 10 owns client intercepts and shortcuts.
- Use the existing `nativeCommandSettings` manager through the host topic only. Do not add a second settings reader, cache, topic, wire type, dispatch rule, completion filter, or ACP path. `TAB_PLUGIN_API_VERSION` stays 3; the new plugin's payload schema starts at 1.
- Bare `commands` opens a new tab in the center and focuses an existing one wherever the host placed it; the plugin never docks or undocks itself. Declare no `dockTab` capability and no `left`/`right` form, so `commands left` is a usage error. The host's generic `tab dock` can still dock any plugin tab, so the layout must remain usable when `capabilities.dock` is non-null. The activation's required `opener` is `noFileOpener('commands')`; the command handler is the only route.
- Edit forms `commands enable|disable [agent|global] <command>` do not open or focus the tab. Omitted selector means global. The text after the optional selector must match a canonical name, alias, or declared fixed form exactly after trimming, collapsing whitespace, and case-folding; trailing words are not ignored, so `commands disable quit now` is `Unknown application command: quit now.` A leading `agent` or `global` is the selector only when at least one more word follows; otherwise `agent` is the command name (so `commands disable agent` disables `agent` globally) and `global` is a missing command (usage).
- Successful edits and already-set values are silent. The topic's `set` action re-reads before saving, uses the effective file, and applies save-before-apply, so the command handler does not call `refresh` before an edit. It can save a child setting while a parent is disabled; the child remains effectively disabled.
- Exact replies: `Usage: commands [enable|disable [agent|global] <command>].` for malformed or missing forms; `Unknown application command: <command>.` with the typed remaining text trimmed and whitespace-collapsed but preserving case; `Not a native ACP command: <canonical>.` from the topic for `agent` on a non-native row; and the service's `commands.json at <path> is unusable — fix the file before editing commands.` or `Could not write commands.json at <path>.` for those cases.
- The `commands` command can disable itself. Its row is an ordinary row; while its tab is open the toggle can re-enable it, and the plugin never closes the tab on that publication. Once the tab is closed, the disabled command is refused at dispatch like any other, so recovery requires editing the effective `commands.json` file. Do not add a special recovery command.
- Re-read the effective file when the tab opens: call the topic's synchronous `refresh` action, then read `topicData('commands')`, then open the tab. Never call `refresh` from the `notify` handler or the topic read path; the topic's `read` is `current()` only.
- The settings manager is application-wide, rooted at the application's project root. Do not resolve a project from the invoking tab or add per-project state; the payload's `source` and `path` name the effective file.
- Follow the Models and Roles patterns without cross-feature client imports. The topic contract is `CommandSettingsSnapshot` verbatim; the plugin reaches that type only through `CommandsTopicNotification['data']` re-exported from `src/plugins/api.ts` (never `../native-commands/`), and maps it to an import-free client payload. The plugin also cannot import `src/application-commands.ts` (the plugin boundary at `eslint.plugin-boundaries.mjs:30-40` allows only `../api.js`, `../files.js`, `../error-text.js`, the two documented openers, and the search matcher modules), so it resolves names and canonical parents from the topic snapshot's `name`, `aliases`, and `forms` rows. Keep each new file under the 200-code-line limit by extracting the command parser and payload mapping from `activate.ts`, and the row and navigation helper from `CommandsTab.tsx`. Server relative imports use `.js`; the shared contract imports nothing.

## Inventory and payload decisions

- `listApplicationCommands` currently walks every registry entry through `BUILTIN_FORMS`, so the core and generated plugin commands that share a name each produce a builtin row: `search transcript` twice and `!` twice. Build the builtin rows from the registered core commands (`src/commands/index.ts:45` `coreCommands`; export it if needed), not from the combined registry. Skip the `shell`/`!` declaration: `!` is not an application command and is already skipped by `src/native-commands/dispatch-policy.ts:12`. Keep the plugin `shell` row, which controls the `shell` command only. This changes no dispatch, completion, or settings semantics.
- Keep the intentional duplicate-name form rows: `ask`/`ask reset`, `tell`/`tell reset`, and `search`/`search transcript` share a canonical setting key. The table renders each row, and toggling either form row writes that canonical name; both rows repaint from the publication. Do not deduplicate them in the client.
- The payload row carries `name` (canonical setting key), `label` (display and accessible name), saved and effective flags, optional canonical `parent`, and optional `nativeTool`. `toPayload` sets `label` to `name` when the row's `forms` contains `name`, otherwise to its first form (`ask reset`, `tell reset`, `search transcript`). It canonicalizes `parent` by matching the parent form against the snapshot rows' `name`, `aliases`, and `forms` and using that row's `name`; if none matches, it keeps the form. It drops `parent` when it equals `name`, so the note names the toggle the user can actually change (`db sqlite query` names `db`, not `db sqlite`). The client guard validates a nonempty `label`.

## Proposed changes

1. Add `src/plugins/commands/{manifest,shared,activate,parse-command,payload}.ts` and `web/src/plugins/commands/{index.tsx,CommandsTab.tsx,CommandRow.tsx,useCommands.ts,commands-keys.ts,commands.css}`. Register the manifest in `src/plugins/catalog.ts`, the literal dynamic server import in `src/plugins/loaders.ts`, and the literal dynamic client import plus schema literal in `web/src/plugins/registry.tsx`. The manifest declares `id: 'commands'`, `command: 'commands'`, `notifications: ['commands']`, `payloadSchemaVersion: 1`, and exactly `openOrFocusTab`, `updateTab`, `topicData`, `topicAction`, `rejectRequest`, `reportFailure`; it declares no `dockTab` and no aliases.
2. `parse-command.ts` is the server-side grammar from the decisions above and takes the current topic rows as input; it matches the remaining text exactly against each row's `name`, `aliases`, and `forms` after normalization and returns that row's canonical `name`. `payload.ts` maps the topic's `CommandsTopicNotification['data']` to the client payload and validates the topic data, importing that type from `../api.js` rather than reaching into `../native-commands/`. `activate.ts` handles bare `commands` by calling `topicAction({ topic: 'commands', action: 'refresh' })`, then `topicData('commands')`, validating with `isCommandsData`, reporting `invalid commands topic data` on failure, and calling `openOrFocusTab('commands', ...)` with title `commands`. It handles edit forms by reading `topicData('commands')` for name resolution (no `refresh` is needed for the static inventory), calling the awaited `topicAction` `set` arm, and rejecting with its refusal. It handles `notify` by ignoring other topics and invalid data, and calling `updateTab('commands', () => ({ payload: toPayload(data) }))` with no title. It exposes one `set` intent through `defineIntents('commands', isCommandsPayload, ...)` whose payload is `{ name, setting: 'enabled' | 'agentAccess', value }`; success returns `null`, a refusal becomes `rejectRequest`.
3. `CommandsTab.tsx` renders the source line, problem line, refusal line, and a Models-style grid inside a horizontal scroll container. Rows come in the server's canonical-name order; do not re-sort by label. Show `Enabled` for every row and `Agent access` only for rows with `nativeTool`; when rows exist the Agent access column is always present because the inventory always includes native rows, and its cell is blank for non-native rows. Key each row by `label`, because form rows share a canonical `name`. Checked state is the saved `enabled`/`agentAccess`, never the effective flags. Accessible names are `Enabled: <label>` and `Agent access: <label>`. Show `Editing <path>` for `home`/`project`, `No commands file in effect` for `default`, the snapshot `problem` beneath it, the latest refusal in a `role="alert"` line that clears on the next toggle attempt, and `No commands` for empty rows. Do not add a loading state: `refresh` and `topicData` are synchronous and the tab is created with a complete payload; the host's lazy-chunk fallback is the only loading surface.
4. Pending saves are a set keyed by `name:setting`; every row sharing that canonical setting disables together, and no other setting is affected. Do not optimistically flip a checkbox: it changes only when the next successful publication arrives. On failure, clear pending, keep the last successful checked state, and show the refusal. A row is parent-disabled when its canonical `parent` names another payload row whose `effectiveEnabled` is false; both of its toggles are disabled and the row is dimmed regardless of the child's own saved value. A self-disabled row with no disabled parent keeps Enabled interactive so it can be re-enabled, but its Agent access is disabled because `effectiveEnabled` is false. Agent access is also disabled when its saved `agentAccess` is true but `effectiveAgentAccess` is false because a native parent denies it. Dim the row and show `Disabled by parent command: <parent>.` when a disabled parent makes the row globally unavailable; when only a parent's agent access denies the row, disable Agent access and show the note without dimming the row. Use the payload's canonical `parent` and resolve it against the payload rows.
5. Use native checkboxes, so Space toggles without a key handler. Handle only Up and Down: focus the same toggle in the previous/next row, falling back to that row's Enabled toggle when the matching toggle is absent or disabled, skip rows where both toggles are disabled, and stop at the first/last row. `preventDefault` and `stopPropagation` for those two keys; leave Enter, Space, Escape, and every other key to the browser and host. Escape has no Commands-specific action. Keep the grid horizontal at every pane width with `overflow-x: auto` and a `min-width`; do not branch on `capabilities.dock` (it is null unless the user docks the tab with the host's `tab dock`). Follow Models' spacing, borders, muted rows, and theme colors.
6. Update the specs and user docs: add a `### commands` section to `product/specs/application-commands.md` and a new `product/specs/commands-tab.md` linked from it; add `commands` and `roles` to the `defineIntents` list at `product/specs/tab-plugins.md:158`; leave `product/specs/keyboard-navigation.md` and `product/specs/tabs.md` unchanged because the first lists application-wide bindings and the second describes plugin tabs generically, while this tab's Up/Down and layout belong in `commands-tab.md`; add the `commands` row and a `### commands` section to `help/commands.md` (do not add a `help/commands-tab.md` page: `help/commands.md` is the `help commands` index); update the one-page-per-command check at `src/commands.test.ts:236-249` to exclude `commands` from the compared command names as it already excludes the `commands` page; add the row and section to `documentation/user-documentation/command-bar/commands.md`; add `documentation/user-documentation/tab-types/commands.md` and its sidebar entry after Roles in `documentation/.vitepress/config.mts:116-117`. The developer tab-plugin topic docs are already current from unit 7.
