# File navigator detail modes

**Complexity: 4/10** — spans server and web with one new RPC and one new profile field, and correctness depends on catching the three `files` payload sites and the already-open early return in `openFilesCommand`; every piece copies an existing pattern, and the only new module is a small stat-cache helper.

Add a detail button to the file navigator's metadata row that cycles the tree's rows through four display modes: filename only (today's display, and the default), filename plus a right-aligned human-readable size (`22b`, `24k`, `32M`, `5G`), filename plus a last-modified timestamp (`Jul 13 23:29`), and filename plus a permission string (`drwxr-xr-x`). Today a navigator row shows nothing but its name and git coloring, so answering "which of these is the big one" or "which did I touch last" means leaving the tree for a shell. The mode is also settable from the command line — `files with size` — and round-trips through profiles, so a saved workspace reopens its trees in the detail mode they were saved in.

## Design decisions

- **Four modes, in this cycle order**: `name` → `size` → `modified` → `permissions` → `name`. `name` is the default for a newly opened navigator and reproduces today's display exactly.
- **Mode names are one vocabulary**: `name`, `size`, `modified`, `permissions` — the same four words are the command keyword, the profile key's value, and the subject of the button's tooltip. There is no second spelling anywhere.
- **Per navigator, not app-wide**: each file navigator tab has its own mode. Clicking the button in one navigator never changes another's.
- **Mode is server-owned state**, held on the tab's `FilesTabState` beside `expanded` and `root` — not client-local like the dock cycle. It has to be server-side for `profile save` to capture it and for the command keyword to set it.
- **Button tooltip names the next mode**, the way the dock-cycle button's tooltip names its destination: `Show size`, `Show modified`, `Show permissions`, `Show name only`.
- **Command form is `files with <mode>`** — an explicit `with <mode>` clause parsed exactly like the existing `in <label>` and `on <side>` clauses: optional, at most once, order-independent, so `files with size on left` and `files on left with size` are the same command. Because it is a keyword clause and not a bare word, a directory named `with` or `size` needs no escaping.
- **The keyword applies to whatever navigator the command acts on** — newly opened, focused, redocked, or retargeted. Re-running `files with modified` on an already-open tree switches that tree's mode, making the command a second route to the same state the button reaches.
- **Profile key is `details`**, sitting alongside `dock`, `path`, `expanded`, `cursor`, `anchor`, and `selected` in a `files` tab entry. `profile save` omits it when the navigator is in the default `name` mode, the way `expanded` is omitted when empty; `profile launch` restores it.
- **Rows with no meaningful value render blank**: directory rows and the `..` row show nothing in `size` mode, and any row whose stat fails shows nothing in every mode — the same quiet degradation the tree already applies when git status can't be determined. No dash, no placeholder, no error.
- **Timestamps always show the time**: `Jul 13 23:29` regardless of the file's age. The year is never shown, so every timestamp is the same width.
- **Permissions mode shows the permission string only** — `drwxr-xr-x`, on both file and directory rows. Owner and group are not shown.
- **A too-narrow navigator drops the value**: below a minimum body width the detail value is hidden entirely and rows read as filename-only, rather than squeezing the name. The mode itself is unchanged — widening the sidebar brings the values back.
- **Values are right-aligned** so they line up as a visual column, but no header row or column rule is added.
- **Stat lazily, cached per rebuild**: `FileNavigatorRow` carries optional `size`, `modified`, and `mode` fields, populated from a per-tab cache that is invalidated when the tab's watcher fires. A navigator in `name` mode stats nothing at all.
- **`lstat`, not `stat`**: the tree already renders a symlink as a leaf file (`readDirSorted` in `src/file-navigator/index.ts:16`, "A symlink (file or directory) reports as a file"), so the detail values describe the link itself and a broken symlink yields a failed stat rather than an error — matching the existing `exists()` helper in `src/file-navigator/filesystem.ts:5`, which also uses `lstatSync`.
- **`details` is optional on the wire**: `FileNavigatorView.details` is `FileNavigatorDetail | undefined`, read as `'name'` when absent. Fifteen files construct a `files` view payload (server sites plus test fixtures); an optional field keeps every existing fixture compiling instead of forcing a mechanical edit across all of them.
- **A rename-in-progress row keeps its detail value**: the inline rename input already occupies the same `flex: 1` slot the name span does (`.files-rename-input`, `web/src/theme.css:794`), so the value stays put on the right and needs no special case.

## Proposed changes

**Shared types.** Add an exported `FileNavigatorDetail` union — `'name' | 'size' | 'modified' | 'permissions'` — to `src/tab/types.ts`, re-exported through `src/types.ts` and `src/protocol.ts` alongside `FileNavigatorRow` and `FileNavigatorView` (both are listed by name in the import/export lines at `src/protocol.ts:3` and `:7` and in the `src/tab/types.js` re-export at `src/types.ts:8`; miss either and the web app can't import the type through `@shared/protocol`). Extend `FileNavigatorRow` (`src/tab/types.ts:117`) with three optional fields: `size` (bytes, number, file rows only), `modified` (epoch milliseconds, number), and `mode` (the numeric stat mode, number). Each is present only when the tab's current detail mode needs it and the stat succeeded. Extend `FileNavigatorView` (`src/tab/types.ts:137`) with an optional `details?: FileNavigatorDetail`, read as `'name'` when absent. Keeping raw numbers on the wire rather than preformatted strings keeps formatting a client concern, testable without a server.

**Server — state and stat cache.** Add `details: FileNavigatorDetail` to `FilesTabState` (`src/file-navigator/state.ts:10`), defaulting to `'name'`, plus a `stats` map from tree-relative path to a cached stat record (or a miss marker for a failed stat). Add a new module — `src/file-navigator/stats.ts` — exporting one function with a narrow contract: rows in, rows out, cache mutated. It takes the tab state and the visible row list, fills each row's `size`/`modified`/`mode` from the cache, `lstat`-ing only paths not already cached, and returns the rows untouched when the mode is `'name'`. `pruneAndBuildRows` (`src/file-navigator/rebuild.ts:17`) gains the call, placed after `markGitStatus` so both per-row decorations compose in one place — widen its local `RebuildableState` type (`src/file-navigator/rebuild.ts:8`) with the two new fields. Invalidation needs no function of its own: `scheduleRebuild` (`src/file-navigator/manager.ts:265`) clears `state.stats` directly, one line at the one call site, so an on-disk change re-stats exactly once per debounce window. Relative imports in `src/` carry the `.js` extension (NodeNext).

**Server — command clause.** Extend `parseFileNavigatorArgs` (`src/file-navigator/args.ts:5`) to consume an optional `with <mode>` clause inside its existing clause loop, at most once, alongside `in` and `on`, returning an added `details?: FileNavigatorDetail` in its result type. Only the four mode words count — an unrecognized word after `with` means the clause never matched, so the text stays in the path target and `files with-notes` or a directory named `with` still resolve as paths. Because the clause regex matches a fixed alternation of literals, like the existing `on\s+(left|right)` one, it stays clear of `security/detect-unsafe-regex`.

**Server — applying the mode on open.** `openFilesCommand` (`src/file-navigator/open-command.ts:14`) has three exits that each need the parsed mode, and the middle one is easy to miss:

- The already-open branch at `src/file-navigator/open-command.ts:42` (`const existing = managers.tab.tabs.find(...)`) returns after redocking. This is the branch the "re-running applies the mode" decision lands on: set the existing tab's `details` in its `FilesTabState` and rebuild before returning.
- The waiting-for-creation branch (`src/file-navigator/open-command.ts:46`) and the normal open branch (`:56`) each construct a `FilesTabState` literal — add `details` to both.
- The normal branch builds its initial payload with `buildRows(root, expanded)` *before* `tabs.set(...)`, so a `with <mode>` open would render one undecorated frame. Move the `tabs.set(...)` call above `openFilesTab` and build the initial rows through the same `stats.ts` decoration, so the first paint already carries values.

`open.ts:38` (the metadata-row 📁 button's fresh open) needs no clause support: a navigator opened that way starts in `name`, and a retarget keeps the existing tab's mode because the state record survives.

**Server — payload sites.** Three payload constructions carry rows and so need `details: state.details`: `src/file-navigator/manager.ts:255` (`onDirCreated`), `src/file-navigator/manager.ts:282` (`rebuild`), and the normal-open `openFilesTab` call at `src/file-navigator/open-command.ts:56`. The waiting-for-creation payload (`src/file-navigator/open-command.ts:47`) has `rows: []` and needs nothing — `onDirCreated` sets the mode when the directory appears. The pass-through in `src/tab/view.ts:83` spreads the whole object and needs no change either.

**Server — RPC.** Add `fileNavigatorSetDetail` with params `{ index: number; details: FileNavigatorDetail }` to the `RpcCall` union in `src/protocol.ts`, beside `fileNavigatorCollapseAll` (`src/protocol.ts:236`). The button needs its own RPC rather than sending a `files with <mode>` command the way New file/New directory send `command` messages (`web/src/FileNavigatorTab.tsx:70`–`:78`): the `files` command appends a transcript entry to the issuing tab and, for a bare invocation on an already-open root, undocks and focuses the tree — neither of which a click on a header button should do. Follow that message's existing full path: add the method name to the `FileNavigatorMessage` union at `src/message-handler-file-navigator.ts:14`, a `case` beside `case 'fileNavigatorCollapseAll':` (`src/message-handler-file-navigator.ts:28`), the routing entry in `src/message-handler.ts:91`, a one-line delegate on `Controller` (`src/controller.ts:165`), a function in `src/controller/file-navigator.ts` beside `fileNavigatorCollapseAll` (`src/controller/file-navigator.ts:13`), and a `setDetail(label, details)` method on `FileNavigatorManager` that writes the state and rebuilds. There is one protocol file — the web app imports it as `@shared/protocol` — so no mirror needs editing.

**Server — profile.** Add `details?: FileNavigatorDetail` to `ProfileFilesEntry` (`src/profile/types.ts:67`); to `filesProblems` (`src/profile/schema.ts:116`) add `checkField(value, 'details', 'string', loc)` plus a `checkDetails` helper written like `checkDock` (`src/profile/schema.ts:29`), rejecting anything outside the four names with the matching message shape (`` `${loc}: details must be "name", "size", "modified" or "permissions"` ``). Add a `details` key to `writeFilesEntry` (`src/profile/save-entries.ts:90`), read through a new `detailOf(label)` accessor on `FileNavigatorManager` that mirrors `expandedPaths(label)` (`src/file-navigator/manager.ts:213`), and omitted when the value is `'name'` so a default-mode tree writes no key. On launch, extend `filesCommand` (`src/profile/files.ts:17`) to append `with ${entry.details}` to its clause list — the entry is already replayed as a literal `files …` command, so the parser change above is the whole restore path and no separate apply step is needed. Order the clause before the trailing `path`, since `path` must stay last.

**Web — rendering.** Add a `web/src/file-navigator-detail.ts` module holding the cycle order (`nextDetail`) and tooltip text (`detailTooltip`), directly mirroring `web/src/dock-cycle.ts`, plus three pure formatters. Each returns the empty string for a missing input, which is what makes the blank-row rule fall out rather than needing a special case at the call site.

- **Bytes** to `22b`/`24k`/`32M`/`5G`: same largest-unit-under-1024 loop as `humanSize` (`src/openers/size.ts:2`), but single-letter and undecimated. This deliberately differs from `humanSize`'s `1.4 MB`/`812 B` spelling, which the backlog entry did not ask for and which is roughly twice as wide — width is what decides whether the value survives in a sidebar. `humanSize` is server-side and stays the spelling used everywhere else; if the two ever need to converge, this formatter is the one to delete.
- **Epoch milliseconds** to `Jul 13 23:29`: build it from `Intl.DateTimeFormat` (`month: 'short'`, `day: 'numeric'`, `hour`/`minute` 2-digit, `hour12: false`) and strip the separator it inserts, rather than hand-rolling a month-name table. `fmtNextRun` (`src/schedule/display.ts:10`) is the closest existing formatter but is 12-hour (`Jul 13 11:29pm`) and lives server-side, so it is a precedent for the shape, not something to import.
- **A numeric stat mode** to `drwxr-xr-x`: the type character from the mode's file-type bits plus the nine permission bits. Nothing in the stdlib or the repo renders this; it is the one genuinely new formatter.

`FileNavigatorRowView` (`web/src/FileNavigatorRowView.tsx:24`) takes the tab's current mode and, when the formatter yields a non-empty string, renders a `files-detail` span after the name span. `FileNavigatorHeader` (`web/src/FileNavigatorHeader.tsx:25`) takes the current mode and renders a `files-detail-cycle` button between the dock-cycle button and collapse-all (`web/src/FileNavigatorHeader.tsx:45`–`:63`), whose `title` is `detailTooltip(nextDetail(details))` and whose click sends `fileNavigatorSetDetail`. Unlike the dock button, it renders whether or not the tree is docked. `FileNavigatorTab` (`web/src/FileNavigatorTab.tsx:140`, `:150`) passes `files.details` down to both. Register the button's glyph in `web/src/icons.ts` under a semantic name — `faTableList as fileDetailIcon` fits the existing solid-icon set. Watch the 200-line limit: `FileNavigatorTab.tsx` is at 185 lines and `FileNavigatorHeader.tsx` at 67, so extract rather than compact if the tab file crosses.

**Web — styling.** Add `.files-detail` to `web/src/theme.css` beside the existing `.files-name` rules (`web/src/theme.css:788`): muted color, 12px, `margin-left: auto`, `flex-shrink: 0`, `white-space: nowrap`, tabular numerals so values align into a column. `.files-row` is already `display: flex` with `overflow: hidden` (`web/src/theme.css:766`) and `.files-name` already ellipsizes, so no layout rework is needed. Hide the span below a minimum navigator width with a container query — `container-type: inline-size` on `.files-tab` plus a `@container` rule. This would be the file's first container query (there are none today) and the sidebar is user-resizable (`.sidebar-resize`, `web/src/theme.css:632`), so a media query on viewport width would be wrong here. Container queries cannot be asserted in jsdom, so this behavior is covered by the manual check rather than a unit test.

**Specs.** Update `product/specs/file-navigator-tab.md`: extend the "Header buttons" section with the detail button, its cycle order and tooltips; add the `with <mode>` clause to the "`files in <label>`/`files on <side>`" section, including its order-independence and its application to an already-open tree; add a short subsection under "Tree contents" describing the four modes, the exact value formats, the blank-row rule, and the narrow-width drop; and note in "Saving and restoring a tree's view" that the mode round-trips. Update `product/specs/profiles.md` in two places: the `files`-entry key list (`product/specs/profiles.md:42`, which enumerates `dock`, `in`, and `path` and quotes the equivalent command as `files [in <in>] [on <dock>] [<path>]`) and the saved-view paragraph (`product/specs/profiles.md:48`, "as four keys holding paths relative to that tree's root") — `details` is a fifth key but is not a path and is not best-effort-dropped, so it belongs with `dock`/`in`/`path` rather than in the four-keys sentence.

**Ordering.** Land the shared types and `stats.ts` first (nothing else typechecks without the union), then the server state/payload/RPC changes, then profile save/launch, then the web layer. Each of those four groups leaves typecheck and tests green on its own; splitting the type change from its consumers does not.

## Tests

There is no `src/file-navigator/args.test.ts` today — the clause parser is covered indirectly through `src/commands/files.test.ts`, `src/file-navigator/manager.test.ts`, and `src/profile/files.test.ts`. Add the direct unit test rather than growing those.

- `src/file-navigator/manager.test.ts`: `setDetail` updates the tab's mode and the next rebuild's rows and payload reflect it; `files with modified` on an already-open root switches that tab's mode without opening a second tab; a `with <mode>` open paints values on its first payload, not only after a rebuild.

- `src/profile/save-entries` coverage and `src/profile/files.test.ts`: `profile save` writes `details` for a non-default mode and omits it for `name`; `profile launch` replays it, i.e. `filesCommand` emits the `with` clause before the path. Add a schema case alongside the existing `dock` validation tests: a `details` value outside the four names is reported as a problem.
- `web/src/file-navigator-detail.test.ts` (new): the cycle order wraps, tooltips name the next mode, and each formatter's output is exact — including the `1023b`/`1k` boundary, a midnight timestamp, a directory mode, and the empty string for missing input.
- `web/src/FileNavigatorTab.test.tsx` (which already holds the header-button coverage — there is no `FileNavigatorHeader.test.tsx`): the button renders with the tooltip for the next mode and clicking it sends `fileNavigatorSetDetail`; rows render the detail value in each mode; directory rows and `..` render none in `size` mode; a row missing the field renders none; a view with no `details` renders as `name`.

## Out of scope

- Sorting the tree by the displayed column — rows keep their directories-first, case-insensitive alphabetical order in every mode.
- Owner and group (`username:groupname`) in permissions mode; the permission string alone is shown.
- Showing the year on old timestamps — the time is always shown instead.
- A keyboard chord for cycling the mode; the button and the `files with <mode>` command are the two routes.
- Applying detail modes to any other tree-shaped listing, including the task picker.
- Any change to a directory row's `size` — no child counts or recursive sizes.
