# Add a janissary-hosted agent write tool to the ACP tool loop

**Complexity: 8/10** — ~570 added production lines, 17 existing files, 34 requirements and 48 scenarios (p=8.23).

Give ACP agents a host-provided file write and edit family so they can create and modify workspace files even when their harness's own write tool is denied. For a remote workspace, execution and confirmation happen on its owning machine without materializing a local target, temporary file, or cached copy. The user explicitly permits existing history, transcript, and ACP recording behavior.

The feature shipped as typed `file write <JSON>` and `file edit <JSON>` commands, the same operations as core `ask`/`tell` ACP tools, a tool-text policy on `FileSystemPort.writeFile`, a new `FileSystemPort.editFile`, and a remote `edit-file` operation, all behind remote protocol version 41. The built-in `tell` role grants both mutations by default; `ask` and saved roles do not change, and the autonomous `agent` command refuses both forms.

## Design decisions

The source feature was the first bullet under `## ready` in `product/backlog/features.md`. It had no separate heading; this title uses its opening phrase. Product and implementation decisions below include the user's answers, the two completed plan-review passes, and the decisions made while building and reviewing it.

- Use Layer 2: a primer, an `AcpTool` entry, a command extracted from the reply's last recognized line, and host execution. No new ACP method.
- User decision: extend the existing file command family with `file write <JSON>` and `file edit <JSON>`. Each command takes one JSON object, allowing paths with spaces and escaped multiline content on one command line.
- Contain all writes to the workspace, including symlink resolution. Remote execution never falls back to local filesystem access.
- Use `FileSystemPort` to select local or remote filesystem execution. Remote whole-file writes carry base64 content and an optional expected hash through `write-file`.
- Close edit read, match, replacement, and atomic write on the workspace machine.
- User decision: enforce role grants and command settings, as browser and database tools do, without an additional human approval prompt. Do not add an approval policy setting or mutation approval state.
- User decision: grant `file write` and `file edit` to the built-in `tell` role only. Keep the built-in `ask` grants unchanged. Existing saved roles retain their explicit grants; do not migrate them to add write access. `readRolesFile` writes `DEFAULT_ROLES` only when no roles file exists, and `readRoleSettings` uses a saved role's commands verbatim, so a `tell` saved before this change keeps its ten grants until the user adds the two names.
- User decision: `file write` creates or overwrites a file without requiring a content hash. An optional `expectedHash` requests the editor's conflict check before replacement. Do not require a preceding read or add hash output to file reads for this feature.
- User decision: `file write` creates missing parent directories within the workspace so a nested file can be created in one operation. Directory creation obeys the same containment and symlink rules as the target file, on the machine that owns the workspace.
- User decision: for a local tab without a workspace clone, use the launch/project directory as the contained write root, matching `file read`. A local tab with a clone uses that workspace directory. Remote tabs always use their remote workspace and never fall back to a local root.
- User decision: apply the existing `file read` secret-path exclusions to both writes and edits, including `.env` files and `SECRET_DENY_PATHS`. Reuse that policy on the workspace machine before creating directories or modifying a file.
- Writes and edits refuse any target inside a `.janissary` or `.git` folder below the root, matched by any segment (so nested repositories and submodule checkouts are covered too), with `Protected file`. Grants and command settings are the feature's only enforcement and live in `.janissary/roles.json` and `.janissary/commands.json`, and git runs `.git/hooks/*` and honors `.git/config` outside any sandbox, so a mutating agent must not reach either. Segments are compared after NFKC normalization and lowercasing, so letter case and compatibility spellings such as `.janiſſary` (U+017F LONG S) or a fullwidth `.git` are refused even when the aliased folder does not exist yet. The check runs on the workspace machine on the lexical path and on every resolved path, and every resolved path comes from `realpathSync.native`, which returns the on-disk spelling. So a case-folding alias of an existing folder on a case-insensitive volume and any symlink alias are refused, and no parent folder is created inside them. Reads and editor saves are unaffected, and there is no setting to opt out.
- User decision: support UTF-8 text only, rejecting invalid UTF-8 and binary files. Whole-file writes preserve the supplied text exactly, including its line endings and any leading BOM. Edits preserve untouched text, including line endings and any BOM; do not normalize line endings.
- Text that is not well-formed UTF-16 is refused before it is ever encoded, because UTF-8 encoding would silently turn each lone surrogate into U+FFFD. The tab executor refuses write content or a `newString` holding a lone surrogate as `Not a text file`, and an `oldString` holding one as `No matching text`, before any port call. The remote port's `editFile` repeats the edit checks before sending. Local and remote tabs therefore answer identically, with no filesystem effect and no remote frame.
- A leading U+FEFF in `oldString` or `newString` is text, not an encoding marker. The far side decodes both base64 edit strings with a BOM-keeping fatal decoder, as the local edit and its file decode do, so a remote edit matches and inserts the same text as a local one.
- A path that names a directory is refused as `Is a directory` before any filesystem effect or remote request. That is a path ending in `/` or the platform separator, or one whose final segment is `.` or `..` (such as `notes/.`, `a.txt/.`, or `a/b/..`), because path resolution and the remote port's path mapping would otherwise drop that part and write a file named after the folder. The trailing-separator form always takes this answer. The dot-segment form does not claim a path that still escapes the root lexically, so `..`, `../..`, and `/tmp/.` keep answering `Outside the workspace`. The same `namesDirectory` check runs first in the tab executor, which covers remote tabs, and first in the owning-machine resolver.
- User decision: use fixed 5 MiB limits for files and mutation payloads, matching the existing file-read limit. For edits, check both the existing file and the resulting file. Do not add a size-limit setting.
- User decision: expose the same write and edit operations through typed `file` commands and core `ask`/`tell` ACP tools. Keep the separate autonomous `agent` command's grant model unchanged in this version. Core use still requires the selected role's explicit grants and effective command settings.
- User decision: edits match text exactly, requiring one occurrence by default. Refuse zero matches or multiple matches unless `replaceAll` is explicitly enabled; with `replaceAll`, replace every exact occurrence, still refusing zero matches. Refuse an empty search string. Allow an empty replacement string to delete matched text. An `oldString` that is not well-formed UTF-16 (a lone surrogate) is refused as `No matching text`, so an edit can never split a surrogate pair.
- User decision: write and edit paths are relative to the selected workspace or project root, matching `file read`. Reject absolute paths and paths that escape that root. Do not interpret paths relative to the tab's current directory. The remote port enforces the same boundary as the local one: under the tool policy, and always for an edit, it refuses an absolute path or a relative path that climbs out of the root it was given with `Outside the workspace` before any frame is sent, even when the path would still land inside the remote workspace.
- User decision: successful mutations return one line: `Wrote <path>.` for a whole-file write, or `Edited <path> (<count> replacements).` for an edit, with the literal word `replacements` even for a count of 1. Do not return a diff or resulting content hash. Use the root-relative path supplied by the caller and the actual number of replacements.
- User decision: `file write` accepts an empty content string to create an empty file or empty an existing file, subject to the same containment, secret-path, regular-file, permission, and optional hash checks.
- User decision: reject unknown JSON fields with a usage error before any filesystem changes. A misspelled option must not silently select default behavior.
- User decision: use `No matching text: <path>.` when an edit finds zero matches and `Multiple matches: <path>; set replaceAll to true.` when a single-replacement edit finds multiple matches. Reuse existing one-line filesystem failure vocabulary for other failures, as required by the backlog.
- User decision: expose `file write` and `file edit` as ordinary entries in the existing Roles command picker and Commands table. Inherit their existing layout, controls, keyboard behavior, states, and styling rather than adding a dedicated permissions panel.
- User decision: add a dedicated remote filesystem `edit-file` operation, rather than an edit mode on `write-file`. Reuse the existing operation registry, request/result validation, and port architecture. Bump the remote protocol version so incompatible peers are rejected before either mutation can run.
- Protocol version 41 carries both remote changes in one bump: the `write-file` `policy` selector and the `edit-file` operation. A version-40 peer would drop the selector and apply the editor's looser rules, or refuse `edit-file` as unknown only after the handshake had passed, so the exact-version handshake refuses that pairing first. One version comment above `REMOTE_PROTOCOL_VERSION` in `src/remote/protocol.ts` records both.
- User decision: preserve the existing remote ACP workspace-tool route. The remote-hosted loop executes writes and edits directly through `LocalFileSystemPort` on its own workspace machine. A typed command dispatched from the caller to a remote tab uses `RemoteFileSystemPort`. Do not forward remote ACP workspace mutations through the caller and then back to the remote.
- User decision: enforce the new text, size, secret-path, and parent-creation requirements through an explicit tool-write policy on the workspace machine. Apply that policy to typed file mutations and ACP file tools while preserving existing editor and binary-file write behavior. Do not impose the tool's restrictions on every existing filesystem write.
- User decision: place the new parser and command execution logic in focused modules under `src/file-write/`, extending the existing registered `file` command. Reuse file-read policy and filesystem-port mechanisms without consolidating or migrating all file commands into a new directory.
- User decision after review: preserve normal history, transcript, and ACP recordings, even when command text contains mutation payloads. The no-local-disk requirement applies to remote mutation targets, temporary files, and file-cache materialization; it does not prohibit existing recording behavior. Do not add recording redaction or disable recordings for this feature.
- User decision after review: if parent directories were created before a write failed, leave them in place. Report the failure and preserve any existing target file content. Do not add directory rollback tracking or cleanup of those directories.
- Define regular-file checks and one-line failures. Version any remote frame change so incompatible peers cannot silently ignore mutation semantics.
- The autonomous `agent` command refuses `file write` and `file edit` in both of its paths with the existing `Agent: command not permitted: <command>.` result, with or without a `file` grant, because a skill that grants the whole `file` command would otherwise silently gain writes.
- Malformed remote replies reject rather than resolve. The `edit-file` result decoder accepts success only with a positive safe-integer `replacements` and failure only with a string `reason`; anything else throws `Invalid remote filesystem operation result.`, which rejects the port promise and reaches the executor's rejection mapping, so it is never reported as success.
- `displayPath` escapes bidirectional and invisible formatting controls as well as line-breaking and control characters, so an agent-chosen path cannot render as a different-looking name than the file actually written.
- The ACP tool loop's follow-up prompt names a mutation only by subcommand and path (`file write <path>`, `file edit <path>`, or the bare subcommand when the JSON does not parse), so content and old and new strings of up to 5 MB are not sent back to the agent a second time. Every other command is still named in full. History, transcripts, connection records, and `ranCommand` keep the full command text, as the recording decision above requires.
- The agent primer does not mention `expectedHash`. The value must match the editor's private content fingerprint, which no command prints, so an agent could only guess it and get a misleading changed-on-disk refusal. Typed and programmatic writes still accept it, and `help/file.md` says it is the editor's fingerprint that typed writes normally leave out.
- The whole-file write's expected-hash read and the edit's read share one bounded regular-file read, so the two cannot drift. Both refuse a target that is no longer a regular file before opening it, and a file over 5 MiB by its stat size or by the bytes actually read.
- `file read` and file mutations open a remote tab's filesystem port through one shared helper and name the unavailable outcome with one constant, so the two commands cannot diverge on channel lookup, session naming, or disposal.
- `"ES2024.String"` is added to the `lib` array in `web/tsconfig.json`. The web project typechecks `src/file-navigator/filesystem-port.ts` through its `@shared/*` alias, and the new import chain reaches `String.prototype.isWellFormed`. The change is type-only: the browser never executes this path, and the web lib is not widened to all of `ES2024`.

## Proposed changes

The work lands in three layers: the shared policy and pure command modules, the filesystem helpers and port and remote contracts, and the command, ACP, and role wiring.

### Shared file policy

`src/file-read/policy.ts` holds the policy that `file read` already enforced, extracted so the writer and editor call the same code. It exports `FILE_POLICY_MAX_BYTES` (5 MiB), the `FilePolicyFailure` type (`File not found`, `Is a directory`, `Not a text file`, `File too large (>5 MB)`, `Outside the workspace`, `Secret file`, `Protected file`), `checkLexicalPath(root, requested)` for the pre-I/O absolute, escape, secret-segment, and home-secret checks, `checkRealTarget(realRoot, realTarget)` for physical containment and secret checks, `checkProtectedPath(relative)` for the mutation-only protected-folder check, and `classifyStats(stats)` for directory, non-regular, and size refusal from a `Stats` the caller already holds. `checkProtectedPath` splits a root-relative path on `path.sep` and refuses it when any segment, folded with `normalize('NFKC').toLowerCase()`, is `.janissary` or `.git`. A comment above it states that the reader never calls it. The secret matcher, existing-prefix resolver, and home-secret check stay private. A comment above `checkRealTarget` states its precondition: both arguments must already be canonical `realpathSync` paths (for a missing target, the real nearest existing ancestor joined with the remaining segments), because it does no resolution and an unresolved path would skip symlink containment. `src/file-read/read.ts` composes these checks and keeps its exports; `FILE_READ_MAX_BYTES` is assigned from `FILE_POLICY_MAX_BYTES` because the lint rules forbid re-exports. The BOM-stripping `decodeText` stays private to the reader. Every `file read` result is unchanged.

### Pure command modules

`src/file-write/types.ts` holds the contract: `FileWritePolicy` (`'tool-text'`), `FileWriteRequest`, `FileEditRequest` (with `replaceAll` always present after defaulting), the `FileMutationRequest` union, `FileEditValue` (`{ replacements }`), and the match-failure reasons `NO_MATCHING_TEXT_REASON` and `MULTIPLE_MATCHES_REASON`.

`src/file-write/messages.ts` exports `displayPath`, `writeSuccessLine`, `editSuccessLine`, and `matchFailureLine`. `displayPath` scans code points without a regex. It renders `\n`, `\r`, and `\t` as two-character escapes and renders C0, DEL, C1, U+2028, U+2029, U+061C, U+200E, U+200F, U+202A–U+202E, and U+2066–U+2069 as `\u` plus four lowercase hex digits. Everything else, including backslash, non-BMP characters, and lone surrogates, passes through, so the result never contains a line break.

`src/file-write/command.ts` exports `FILE_MUTATION_PRIMER` (six lines: the one-line form of each command, the single-line JSON and root-relative path rule, `A write creates or overwrites the file and creates missing parent folders.`, and the exact-match and 5 MB rule, with no mention of `expectedHash`), the recognition predicates `isFileWriteCommandLine`, `isFileEditCommandLine`, and `isFileMutationCommandLine` (`/^file\s+write(\s|$)/i` and the `edit` equivalent, prefix-only so invalid JSON is still recognized), `FILE_WRITE_USAGE` (`Usage: file write <JSON>`), `FILE_EDIT_USAGE` (`Usage: file edit <JSON>`), and `parseFileMutation(input)`. The parser extracts the remainder after the subcommand verbatim and parses it with `JSON.parse` and `isRecord`. It rejects with the subcommand's usage line an empty argument, malformed JSON, a non-object, a key outside the subcommand's field set (checked over `Object.keys`, so `__proto__`, `replaceall`, and cross-subcommand fields are usage errors), a missing or wrong-typed field, an empty `path`, and an empty `oldString`. Empty `content`, `newString`, and `expectedHash` are valid. After a request validates, an argument whose UTF-8 byte length exceeds 5 MiB returns `File too large (>5 MB): <path>.`; an oversized invalid argument returns usage. Input that is not `file write` or `file edit` returns `Usage: file write <JSON>` defensively. NUL and lone-surrogate content are data rules left to the executor and the filesystem helpers. `describeLoopCommand(command)` returns the follow-up prompt label: `file write <path>` or `file edit <path>` with the path through `displayPath`, the bare subcommand when `parseFileMutation` refuses the line, and any other command unchanged.

### Filesystem helpers on the owning machine

`src/file-write/target.ts` exports `WriteTarget`, `resolveMutationTarget(root, requested)`, and `createTargetParents(target)`. All three are synchronous and return failures as values. Every real path in the module comes from `realpathSync.native`, so containment, secret, and protected checks compare on-disk spellings and the root stays comparable with every path resolved under it. A private `checkMutablePath(realRoot, realPath)` runs `checkRealTarget` and then `checkProtectedPath` on the root-relative path, and it is used wherever a resolved path is checked. The resolver runs, in order:

1. `namesDirectory(requested)`, exported for the tab executor: `Is a directory` for a trailing separator, or for a final `.` or `..` segment on a path that does not escape lexically.
2. `checkLexicalPath`, then `checkProtectedPath` on the lexical root-relative path.
3. Resolve the real root.
4. Walk up from the destination's parent to the nearest existing ancestor, recording missing segments. An `ENOENT` counts as a missing segment only when `lstatSync` confirms no entry exists. A dangling symlink in the ancestor chain is refused with `checkMutablePath`'s word for its link target (`Outside the workspace`, `Secret file`, or `Protected file`) or otherwise `Not a text file`, before anything is created. Other errors, such as `ENOTDIR` for a file ancestor, `EACCES`, and `ELOOP`, return their `fileOperationReason`.
5. Require the ancestor to be a directory.
6. Run `checkMutablePath` on the real ancestor and the joined destination, before any folder is created.
7. Follow a final symlink and recheck it with `checkMutablePath`; a dangling final symlink is `Not a text file`.
8. Classify an existing target by `statSync` only, never opening it: a directory is `Is a directory` and any other non-regular file is `Not a text file`. Size is left to the callers. Naming the root itself is `Is a directory`.

`createTargetParents` creates the missing segments with a recursive `mkdirSync`, then always rechecks the destination's real parent, the destination, and any symlink there with `checkMutablePath` before returning the real path the caller writes to. Folders created before a later failure stay.

`src/file-write/filesystem.ts` exports `writeToolTextFile(root, relativePath, content, expectedHash?)`. Content is refused as `Not a text file` for NUL or `!isWellFormed()`, and as `File too large (>5 MB)` when its UTF-8 encoding exceeds the limit. Then the target resolves. Then the optional hash check runs: when the target exists, it is read with `readBoundedRegularFile` and decoded as UTF-8 with one leading BOM stripped, and a mismatch is `SAVE_CONFLICT_ERROR`. A missing target skips the check and is created. A read failure such as permission denied reports its `fileOperationReason` rather than passing. Then parents are created, and the bytes are written with `atomicWriteFile`.

`src/file-write/bounded-read.ts` exports `readBoundedRegularFile(realPath)`, the read both helpers share. It stats the path, refuses a non-regular file as `Not a text file` before opening it and a stat size over 5 MiB as `File too large (>5 MB)`, reads the bytes, and refuses a read length over 5 MiB the same way.

`src/file-write/edit-text.ts` holds the pure edit rules. `checkEditReplacement(newString)` refuses NUL or ill-formed text. `decodeEditableText(bytes)` decodes with a fatal, BOM-keeping `TextDecoder` and refuses NUL. `replaceExactText(text, byteLength, oldString, newString, replaceAll)` refuses an empty or ill-formed `oldString`, counts literal non-overlapping matches with `indexOf`, and applies the zero- and multiple-match rules. It then refuses a result whose computed UTF-8 size exceeds 5 MiB before allocating it, and replaces by split-and-join so `$&` and `$1` stay literal.

`src/file-write/edit.ts` exports `editToolTextFile(root, relativePath, oldString, newString, replaceAll)` returning `FileOperationResult<FileEditValue>`. Its check order is: replacement text, target resolution, `File not found` for a missing target (edits never create parents), and then `readBoundedRegularFile`, so a target swapped for a pipe or grown after classification is still refused. Then come the strict decode, the match and result-size rules, and an atomic write to the rechecked destination. Each helper runs validation, hash or match checking, and the rename in one synchronous owning-process call with no await. It does not claim compare-and-swap protection against an independent process.

### Ports and the remote protocol

`FileSystemPort.writeFile` gains a trailing optional `policy?: FileWritePolicy`. `LocalFileSystemPort.writeFile` sends `'tool-text'` to `writeToolTextBytes` in `src/file-write/port-adapter.ts` as its first statement. That adapter refuses a buffer over 5 MiB, decodes with a fatal BOM-keeping decoder (invalid UTF-8 is `Not a text file`), and calls `writeToolTextFile`. Without the policy the existing editor and binary write path is unchanged. `FileSystemPort.editFile(root, relPath, oldString, newString, replaceAll)` always applies the tool rules, takes a required `replaceAll`, and returns `FileOperationResult<FileEditValue>`; the local port delegates to `editToolTextFile`.

`src/file-navigator/remote/port-reads.ts` holds `remoteWriteFile` and `remoteEditFile`, and `RemoteFileSystemPort` delegates to them so `port.ts` stays under the size limit. A private `outsideRoot(root, relPath)` treats a POSIX-absolute path, or one whose `path.posix.relative(root, path.posix.resolve(root, relPath))` is `..` or starts with `../`, as outside. `remoteWriteFile` refuses such a path with `Outside the workspace` before sending, but only under a policy. Otherwise it sends `write-file` with one base64 copy of the content and the optional `expectedHash` and `policy` keys present only when supplied. Editor saves keep mapping and sending as before. `remoteEditFile` always applies the same refusal, then refuses an ill-formed `oldString` as `No matching text` and an ill-formed `newString` as `Not a text file`, before encoding. It sends `edit-file` with the plain mapped `path`, `oldString` and `newString` each as one layer of UTF-8 base64, and the boolean `replaceAll`. `edit-file` joins `write-file` in the ten-minute `LONG_RUNNING` deadline set. Close, connection end, and timeout settle as failure values with the existing reasons. Nothing retries a timed-out or disconnected mutation, a late reply is dropped, and cancellation cannot undo a committed write.

On the far side, `write-file`'s descriptor accepts `policy` only as absent or `'tool-text'`, carries it only when present, and passes it to `context.filesystem.writeFile`, so the far side's `LocalFileSystemPort` repeats every check. The new `src/remote/filesystem/edit-file-operation.ts` descriptor validates `path` as a string, `replaceAll` as a boolean, and `oldString`/`newString` as strict base64 (a round-trip comparison) of UTF-8 decoded with `{ fatal: true, ignoreBOM: true }`, so a leading U+FEFF survives. It decodes them once, declares `paths: (args) => [args.path]` and `refusal: refusedItem`, and runs `editToolTextFile(context.root, …)` directly with no file-cache access. `edit-file` is registered in `RemoteFilesystemOperation`, `RemoteFilesystemArgumentsByOperation`, `MUTATION_OPERATIONS`, and `resultDecoders`. `REMOTE_PROTOCOL_VERSION` is 41. The frame codec does not re-encode argument strings.

### Typed commands

`src/file-write/tab-write.ts` exports `runFileMutation(port, root, input)` and `mutateFileInTab(managers, label, input)`. `runFileMutation` parses and returns any usage or size error unchanged. `applyMutation` then refuses a path for which `namesDirectory` holds as `Is a directory`, and lone-surrogate text as the decisions describe, before any port call. A write goes to `port.writeFile(root, path, <UTF-8 bytes>, expectedHash, 'tool-text')` and an edit to `port.editFile(…)`. A success becomes `writeSuccessLine` or `editSuccessLine`. A `{ ok: false }` result becomes `mutationFailureLine`. A throw or rejection, including a malformed remote reply, becomes `mutationRejectionLine`. `mutateFileInTab` parses first so usage errors read the same everywhere. It then uses `localReadRoot`: a local tab runs `runFileMutation` with a new `LocalFileSystemPort`. A remote tab goes through `withRemoteTabPort(managers, label, 'file-write', run)` in `src/file-read/remote-tab-port.ts`, which `readFileInTab` also uses with the prefix `file-read`. It returns `REMOTE_UNAVAILABLE` (`Remote connection unavailable.`) when the tab has no channel, ready promise, or workspace. Otherwise it opens a `RemoteFileSystemPort` with session id `<prefix>-<n>` from one module counter, runs against the remote workspace, and disposes the port in a `finally`. `src/file-read/tab-read.ts` and `src/file-write/outcome.ts` import that one constant.

`src/file-write/outcome.ts` holds the tab executor's failure mapping, in this order:

1. The two match-failure reasons use `matchFailureLine`.
2. `Remote connection unavailable.`, `ENDED_REASON`, `TIMED_OUT_REASON`, and `CLOSED_REASON` print unchanged, whether they arrive as a failure result or as a rejection's message.
3. `Outside the workspace` and `OUTSIDE_ROOT_REASON` print `Outside the workspace: <path>.`.
4. Every other reason or `Error` message prints `<reason>: <path>.`, with both the reason and the path passed through `displayPath`. This covers the policy words, `SAVE_CONFLICT_ERROR`, `fileOperationReason` text, and `Invalid remote filesystem operation result.`.
5. A non-`Error` rejection prints `fileOperationReason(error)` in the same shape.

File content never appears in output.

`src/commands/file.ts` routes lines that satisfy `isFileMutationCommandLine` to `mutateFileInTab` and everything else to `readFileInTab`, so bare `file`, `file read`, and unknown subcommands keep the read usage line. Its `samples` gain one `file write` and one `file edit` example. Typed commands use ordinary enabled-command dispatch, so a disabled `file write` row refuses with `Command is disabled: file write.`, and no ACP role grant is consulted.

### ACP and the autonomous agent boundary

`'file write'` and `'file edit'` are appended after `'file read'` in `NATIVE_ACP_COMMANDS`. `src/application-commands.ts`, the core snapshot rows, command policy, and the Roles payload already iterate that list, so the Commands table gains two rows with parent `file` and the Roles picker gains two entries with no other change. In `createAcpToolTable`, the file entry keeps its owner, `match`, and `runsOn: 'workspace'`. Its `isCommandLine` also recognizes mutation lines, and its primer is composed from the grants: `FILE_READ_PRIMER` when `file read` is granted, then `FILE_MUTATION_PRIMER` when either mutation is granted, joined by a blank line. ## Out of scope

- New ACP methods or re-enabling harness-native write tools.
- Writes outside the workspace.
- Writes and edits to paths excluded by the existing file-read secret policy.
- Other self-referential or executable control files outside `.janissary` and `.git`, such as a project's harness configuration, and a setting to opt out of the protected-folder refusal.
- Filesystems that fold characters NFKC plus lowercasing does not map, beyond what on-disk name resolution catches for folders that already exist.
- Local temporary files, local file-cache materialization, or local fallback for remote mutation content.
- Fetching a whole remote file locally to perform an edit.
- Additional human approval prompts, configurable approval policies, and mutation approval state.
- Mandatory read-before-write workflows and adding content hashes to file-read output.
- Binary-file mutations, non-UTF-8 text, and automatic newline normalization.
- Extending the separate autonomous `agent` command's grant model or adding its write/edit integration.
- Returning mutation diffs or resulting content hashes in tool output, or exposing the editor's content fingerprint through any command.
- Redacting mutation payloads from normal recordings or disabling existing recording behavior; only the follow-up prompt label is shortened.
- Rolling back newly created parent directories after a failed write.
- Retrying uncertain remote mutations, or adding a lock or queue service.
- Protection against hostile concurrent filesystem changes beyond the existing containment model and the pre-write recheck, including the window between the edit helper's in-read stat and its open.
- Homoglyph and confusable-character detection in displayed paths, and escaping zero-width characters that do not affect direction.
- Tab completion for the new subcommands.
- Streaming, chunking, or files over 5 MiB.
