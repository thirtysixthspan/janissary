# Labelled fenced block

**Complexity: 7/10** — ~110 added lines across 7 existing files, 14 behavioral requirements and 20 test scenarios, driven by a new shared block extractor plus a loop result-type change (p=6.56).

Shift the ACP tool loop from reading a bare command on the reply's last line to reading it from a labelled fenced block. The agent places its one command inside a final block tagged with a known label; the host reads only the last such closed block. This keeps one command per turn while letting prose follow the command, letting arguments span multiple lines, and keeping the matched block out of the displayed reply while the prose around it — including an earlier identical block — stays visible. It matters because the current final-line rule makes an ordinary trailing sentence silently end the loop and forces even multi-line arguments onto a single line.

## Design decisions established by the feature text or existing behavior

- One command runs per turn; this does not change.
- The command comes from a fenced block tagged with a known label, not from the reply's last bare line.
- The label is a fence whose info string is exactly `janissary` (case-sensitive, no extra words); both backtick and tilde fences are accepted, matching the fence types the current extractor already recognizes. A fence with any other info string is an ordinary example and is ignored.
- The host reads only the last such closed block in the reply; an unclosed labelled block is not a candidate and counts as zero commands. The last genuinely closed labelled block wins: a later labelled block left unclosed does not replace or suppress an earlier closed block, which still runs. An unclosed labelled block asks for a correction only when no closed labelled block exists.
- Zero commands or multiple commands in that block are a correctable mistake, not a reason to end the turn: the agent is given the problem and allowed to correct it.
- Both mistakes get the same short feedback sentence, held as one constant in `src/acp/loop.ts`: ``Your reply must contain exactly one command inside a final ```janissary fenced block. Try again.``
- A `janissary ` prefix on the command line inside the block is tolerated and stripped before gating; the primer teaches the bare form.
- Prose after the command no longer terminates the loop.
- Command arguments may span multiple lines inside the block. The whole trimmed block content, newlines included, is the command when the block contains exactly one command-start line; a command-start line is a line whose first word matches a known Janissary command.
- The matched labelled block is removed from the displayed reply while prose outside it is kept, so an earlier identical block or a command repeated in prose outside the block stays visible.
- The core host loop and the agent-driven path converge on the same block rule.
- The old top-of-line `janissary ` marker becomes redundant inside a block.
- There is no bare-line fallback: a final command line outside a closed labelled block is prose and ends the turn as the final answer.
- Correction feedback does not consume the 8-step budget; only commands that actually run do. There is no separate cap on correction attempts — an agent that never emits a valid block can keep being asked to correct itself, which the plan records as a risk rather than adding a new limit.
- A leading `/` on a candidate command line inside the block is recognized by stripping it before the native-command check, while the returned command text keeps the slash so the existing gate and workspace host normalize it. An agent that writes `/file read a.md` in a `janissary` block gets a workspace read rather than a correction.
- The resolution comment above `createAcpToolTable` states that extraction reads the command inside the last closed labelled block and does not depend on table order; it is a comment-only, behavior-neutral correction.
- Every per-tool primer agrees with the command-protocol primer and the shared extractor: a command goes inside a final fenced block whose info string is exactly `janissary`, written without a `janissary` prefix, and prose may follow the block. Each tool keeps its own grammar lines, worked example, and final-answer-and-no-trailing-command sentence.
- The legacy whole-reply extractors (`extractDatabaseCommand`, `extractBrowserCommand`, `extractQuestionCommand`) and their `findLastCommandLine` calls stay as they are; they are not on the ACP loop path.

Together with the feature text these points settle every product decision for this version: the primary flow, the edge cases, the scope boundary, and all user-visible wording. The functional specs (`product/specs/acp.md`, `agent-command.md`, `agent-questions.md`, `notifications.md`, `web-fetch.md`, `web-search.md`) and the advanced-agent user docs describe this same labelled-block rule, so none still teaches command extraction from a bare final line.

## Proposed changes

Add a new pure module `src/acp/command-block.ts` holding the one shared block-aware extractor and its result type. The result type has three variants, because `null` alone cannot tell a final answer from a bad block: `one` (one command plus the span of the block it came from, so the display filter can remove exactly that block), `mistake` (a labelled block was present but held zero or more than one command), and `absent` (no labelled block in the reply). The loop maps these to run a command, send the correction sentence, and end the turn as a final answer respectively. Put this in a new module rather than growing `src/acp/tool-table.ts`, which is already 198 lines long, so the new pure logic does not risk the 200-line `max-lines` limit in `eslint.config.mjs:62`.

The extractor scans for the last closed fence whose info string is exactly `janissary`. Move the existing module-private `openingFence` and `closesFence` helpers out of `src/agent/command-extract.ts:4` into this module rather than re-deriving their backtick and tilde fence rules. Candidate bookkeeping records a candidate only when a labelled fence closes, so the last closed labelled block wins: the internal `Candidate` carries a required close, and `findCandidate` returns both the last closed candidate and an `unclosedLabelled` flag. `extractCommandBlock` returns `{ kind: 'mistake', commands: 0 }` only when an unclosed labelled fence exists and no closed candidate was found; with no candidate at all it returns `absent`, and otherwise it extracts from the last closed candidate. An unclosed labelled fence is present but not closed, so it yields `mistake` with zero commands only when nothing closed exists. For each non-empty line inside the chosen block, strip a leading `janissary ` prefix and an optional leading `/` before testing it as a command-start line; use `nativeCommandName` from `src/acp/native-commands.ts:13` (already the vocabulary test in `toolExtractor` at `src/acp/tool-table.ts:195`) so subagent, tab, notify, question, and the database fall-through are all recognized. The returned command text keeps the leading `/` so the existing gate and workspace host normalize it. Exactly one command-start line means the whole trimmed block content, with internal newlines preserved and the leading prefix stripped, is the one command; zero or more than one yields `mistake`. Preserve the agent path's `allowQuestion` behavior from `src/agent/command-extract.ts:16`: when `snapshot.askUser` is false, a `question ask|approve` line is not a command-start line, so the block is treated as having zero commands and the agent is corrected.

`src/acp/types.ts:84` changes `AcpLoopDeps.extractCommand` from `(text: string) => string | null` to the new result type; `src/acp/loop.ts` reads its three variants. `filterCommandFromDisplay` in `src/acp/loop.ts:82` changes its input from a command string to the matched block span: it removes the opening fence, the block contents, and the closing fence of exactly the block the extractor used, then trims trailing blank lines as it does today. Prose outside that block is kept, so an earlier identical block or a command repeated in prose stays visible; the only newly added copy is the loop's own tool transcript entry.

`src/acp/tool-table.ts` keeps `AcpTool.isCommandLine`, `gateCommand`, and `nativeCommandName` as the definitions of a known command and its permission; `toolExtractor` at `src/acp/tool-table.ts:195` delegates to the shared extractor instead of calling `findLastCommandLine`. Retire `src/agent/command-extract.ts` after its fence helpers move: `src/acp/drive-loop.ts:74` calls the shared extractor directly, passing `snapshot.askUser` as the `allowQuestion` option for the agent kind, so there is no wrapper function and no second fenced-content scan. Do not change `cleanCommandLine` or `findLastCommandLine` in `src/acp/command-line.ts`: `extractDatabaseCommand` (`src/database/primer.ts:30`), `extractQuestionCommand` (`src/question-command.ts:44`), and `extractBrowserCommand` (`src/browser/command.ts:87`) still call `findLastCommandLine` for their own whole-reply extractors, and those stay out of this change.

`src/acp/command-protocol.ts` and `src/agent/command-tools.ts` rewrite their primers to instruct the agent to put its one command in a final fenced block whose info string is exactly `janissary`, with prose allowed afterwards, arguments allowed to span lines, and no bare-line fallback. The same leading-instruction rewrite is applied across every per-tool primer — the five `file`-family primers plus the five forms in `src/acp/file-primer.ts`, the web search and web fetch primers, and the browser, database, question, and notify primers — each stating that one command goes inside a final `janissary` fenced block without a prefix and that prose may follow, while its grammar, guidance, worked example, and final-answer sentence stay unchanged. New relative imports in `src/` use `.js` extensions per the NodeNext rule in `AGENTS.md`.

The remote path runs this same loop on the host that runs the agent: `src/remote/serve-acp-loop.ts:109` calls `driveToolLoop` on the far side. No new protocol message, RPC, or remote frame is needed; the extraction change lands wherever `driveToolLoop` runs.

The functional specs and advanced-agent user docs describe the labelled-block rule throughout: quoted primer blocks carry the current first line naming the `janissary` fenced block, narrative sentences state that a bare final line is prose ending the turn and that zero or more than one command draws the shared correction sentence, the no-stray-copy wording says the matched block is removed while the prose around it and any earlier identical block stay visible, and the unclosed-block wording states that a later unclosed labelled block does not suppress the last closed one. `product/specs/acp.md`, `agent-command.md`, `agent-questions.md`, `notifications.md`, `web-fetch.md`, and `web-search.md`, together with `documentation/user-documentation/advanced-agents/acp-agent.md`, `agent-command.md`, and `agent-questions.md`, all carry this wording.

The shipped contracts live in named artifacts: `extractCommandBlock` in `src/acp/command-block.ts` returns `one` (command plus the matched block span), `mistake` (command count), or `absent`; `CORRECTION_PROMPT` in `src/acp/loop.ts` holds the single correction sentence; `toolExtractor` delegates to the shared extractor with `allowQuestion: true` and keeps the granted-tool ownership check; `driveToolLoop` passes `snapshot.askUser` as `allowQuestion` for the agent kind. `src/agent/command-extract.ts` and `src/agent/command-extract.test.ts` are deleted, and the affected test files that previously fed a bare command line now use a final `janissary` block while keeping their gating, side-selection, and step-count assertions. Both primers, all per-tool primers, and the behaviour specs are updated to the block rule.

## Out of scope

- More than one command per turn: multiple commands in the block are a correctable mistake, not parallel execution.
- A bare-line fallback: a final command line outside a labelled block stays prose and ends the turn.
- A secondary cap on correction attempts. Corrections are deliberately unlimited and do not consume the 8-step budget; the ceiling is an agent that never emits exactly one command in a labelled block and so keeps being asked to correct itself. This version accepts that possibility; if a hung run is observed, the upgrade path is a separate correction counter in `src/acp/loop.ts`, leaving the 8-step command cap unchanged.
- Changing which commands any role or skill grants, or the gate and permission rules.
- New client/server protocol messages, RPCs, or UI; the remote loop host does not change.
- Changing the label, the correction sentence, or the 8-step cap for core prompts and the step behavior for agent runs.
- Changing `extractCommandBlock`, `toolExtractor`, `gateCommand`, or the loop's three-variant handling while aligning the primers.
- Changing `cleanCommandLine`, `findLastCommandLine`, or the three legacy whole-reply extractors.
- New command names, key bindings, or help-page entries; no command or binding changed, so `help/` is untouched.
