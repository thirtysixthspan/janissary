# Find text in a PDF tab

**Complexity: 5/10** — client-only and modeled on the shell's reuse of the find overlay, but it adds progressive text reading, line-aligned match marks over PDF.js's text layer, an offset reveal in both layouts, and small changes to the overlay the editor and shell share.

A PDF tab draws the document's pages and makes their text selectable. This feature gives it the same `Cmd+F` find overlay the editor tab and the shell tab share, pointed at the document's text, so a reader can jump to where a phrase appears instead of paging through by eye. The whole document is searched, every page, and matches are marked on the drawn pages.

## Design decisions

- `Cmd+F` opens the find overlay in an active PDF tab — the current tab among the centre panes, or a PDF tab shown in a sidebar — when the chord reaches it: the current centre tab, or a sidebar tab with focus inside it. Active is what makes the overlay available; whether the chord is answered follows focus. It is the editor tab's overlay (`product/specs/editor-tab.md` § Finding a line), the same one the shell tab reuses (`product/specs/shell-tab.md` § Transcript search).
- `Cmd+F` reaches the PDF tab the way it reaches the shell tab: the PDF plugin's declaration claims the `meta+f` chord, delivered to the client as `claimedChords`. A centre tab's claim moves with the current tab, and a docked tab's claim lasts while its sidebar shows it; only the focused tab label runs the handler, so any other focus leaves the chord to the application.
- The claim is registered whenever the tab is active — the current centre tab, or a sidebar tab while its sidebar shows it — so it describes overlay availability, not chord answering: a docked tab stays claimed while visible, but only the focused label runs the handler. The claim is held while the document is loading or after a failed load too, so `Cmd+F` is consumed there even though the handler opens nothing and the browser's own find bar does not appear.
- The overlay's matching is the editor's: one uninterrupted, case-insensitive occurrence of the typed text, with no regex, case, or whole-word options, and at most ten ranked results.
- The overlay owns its keys while focus is in its input. Every keystroke in the input is swallowed (`rankedOverlayKeys`), so `↑` / `↓`, Page Up / Page Down, and Escape do not also page, scroll, or reset zoom in the PDF view behind it. Outside the input, the PDF view's page keys, Ctrl / Cmd + wheel zoom, and Escape belong to the focused PDF tab. A centre PDF tab owns them while it is the current tab and focus is not inside another labelled tab, which includes focus resting on its page. A docked PDF tab owns them only while focus is inside its own `.pdf-tab`, and clicking its page puts focus there. In the owning tab, Escape closes an open overlay before it can reset zoom. A centre PDF and a docked PDF can both be active at once, so without this rule one key would page both documents or close both overlays.
- The PDF view's text is read in the browser from the document already loaded, once per tab on the first open, and kept until the tab closes. It is never read on the server.
- The document is never written to. Find changes only what is in view.

### What is searched

- The whole document is searched, every page, not only the pages that have been drawn.
- Each searchable line is one visual line of text on a page: PDF.js's text for that page, grouped into the lines a reader sees. Two lines with the same text are two rows.
- A match must sit within one line, as in the editor and the shell tab. A phrase that wraps onto the next line, or a word hyphenated across a line break, is not found. This is a documented limitation, not a bug.
- A document with no text (a scanned PDF of page images, for example) is searched like any other and answers every non-whitespace query with `No matching lines`. There is no separate no-text message.
- A page whose text cannot be read contributes no lines and sends no notification. Find is best-effort over what can be read, the same way a thumbnail that fails to draw does not fail the document (`product/specs/pdf-tab.md` § When a document cannot be rendered).
- `Cmd+F` does nothing while the document is still loading or after it failed to load, the same as the zoom and page keys. It is still swallowed there, so the browser's own find bar does not open either.
- The text is read once per tab, the first time the overlay opens, and kept until the tab closes. The document shown never changes after it is opened (`pdf-tab.md`: "later edits to the file on disk are not reflected until it is opened again"), so there is nothing to re-read.

### Results

- The overlay's input placeholder reads `Search document`; its accessible name is the same string.
- The empty state is the editor's `type to search` hint; a query with no match shows `No matching lines`.
- Each row is one matching line, labelled with its 1-based page number where the editor shows a line number, beside the line's text with the matched characters emphasized. A line too long for the overlay is clipped with an ellipsis rather than wrapped.
- Rows are ranked exactly as the editor ranks them: best-scoring first, ties broken the way the editor breaks them. Only the top ten are listed, so an occurrence outside the ten can only be reached by refining the query.
- While the document's text is still being read and the query is not blank, a muted `Reading pages…` status shows below the rows, or in place of `No matching lines` when there are none yet. It disappears when reading finishes. Results fill in page by page and re-rank as each page arrives.

### Moving to a match

- Highlighting a row with `↑` / `↓` or a click moves the view to that match at once. In single page, the match's page becomes the shown page; in continuous scroll, the stage scrolls so the matched line sits about a quarter of the way down the stage. When the page is zoomed past 100% in single page, the stage also scrolls so the line sits a quarter of the way down. The position readout and the page strip's highlighted thumbnail follow, as for any other page change. No text selection is made, and a click keeps focus in the overlay's input.
- Return moves to the first ranked match, even when another row is highlighted, and the overlay stays open.
- Escape closes the overlay and leaves the view at the last previewed match. It does not reset zoom. With the overlay closed, Escape resets zoom to 100% as today.
- While the overlay is open but focus has left its input (after a click on the page, say), Escape still only closes the overlay, the same as the editor's Escape from the buffer (`editor-tab.md`: "that Escape only closes the overlay and does not also collapse a selection"). The arrow and page keys work on the document as usual while focus is outside the overlay and the tab owns its keys, as set out in the key decision above.
- Closing returns focus to the element that had it before `Cmd+F` was pressed, if that element is still in the document and another text field has not taken focus. A close caused by the tab becoming inactive restores nothing, since focus has already moved.
- Switching away from the PDF tab closes the overlay, and `Cmd+F` on return opens a fresh, empty one. Nothing about the overlay survives a close (`useLineFind`'s existing behavior).
- `Cmd+F` while the overlay is already open keeps it open. With focus in the input, the shared input handler selects the whole query so typing replaces it. With focus outside the input, the PDF find hook focuses the input and selects the query. The browser's find bar never appears.

### Match highlighting on the pages

- While the overlay is open with a query that has non-whitespace text, every occurrence of it on the drawn pages is marked, not only the ten listed. The occurrence behind the highlighted row is marked in a stronger color than the rest.
- Pages drawn later while the overlay is open (scrolled into view, or after a zoom or layout change) get their marks too.
- Closing the overlay clears every mark. The overlay is available only in the tab the host reports active: `PluginTabLayer` passes `active` only to the current centre tab. A split's other pane is visible but not active, so it cannot open find while the first pane's tab is current; making the second pane's tab current closes the first tab's overlay and clears its marks. `DockedPluginBody` passes `active={isVisible}`, so a PDF tab shown in a sidebar is active whenever its sidebar shows it; it and a centre PDF tab can each hold an open overlay, they share the highlight names but not their ranges, so each marks only its own document, and closing one leaves the other's marks in place.

## Proposed changes

The only server change is the one-line manifest claim. There are no wire changes: the claim already travels to the client as `claimedChords`, and everything else is view-local.

### Shared overlay (`web/src/shared/line-find/`)

- `LineFind.tsx`: the input's `aria-label` is its `placeholder`, so every caller gets an accessible name with no new prop (`Search buffer`, `Search transcript`, `Search document`). The placeholder attribute stays, so placeholder queries keep working.
- `LineFind.tsx`: its key handler checks for `Cmd+F` (meta and `f`, no other modifier) before handing the key to `rankedOverlayKeys`; it prevents the default, stops propagation, and selects the whole input value. A capital `F` with Cmd matches; Ctrl, Shift, and Alt combinations do not. `rankedOverlayKeys` is unchanged, since quick-open shares it and has no find chord.
- `LineFind.tsx`: three optional props. `inputRef` is attached to the input, so a caller can focus it and select its query. `rowLabel(result)` returns the dimmed label for a row; when absent the row shows `result.index + 1` as today. `status` is a muted line shown when the query is not empty: below the rows when there are results, and in place of `No matching lines` when there are none. The editor and shell pass none of the three, so they render exactly as today.
- `useLineFind.ts` is unchanged. Its memo re-ranks when a new lines array arrives, and its clamp effect keeps the highlighted row in range as results change.

### PDF plugin

- `src/plugins/pdf/manifest.ts`: `chords: ['meta+f']`, with a comment in the style of the shell manifest's: claimed only while a PDF tab is the active one, and the application leaves `Cmd+F` to the editor everywhere else.
- `web/src/plugins/pdf/pdf-document.ts`: `LoadedPdf` gains `readPageText(index)`, resolving to that page's text items as plain data: each item's string, its `hasEOL` flag, and its top as a fraction of the page's height (from the item's transform through the page's scale-1 viewport, so a rotated page is handled by PDF.js). It reads through `getTextContent()` on the already-fetched page proxy, filters items without `str`, and lets a rejection reach the caller. Nothing outside this module sees a PDF.js type.
- `web/src/plugins/pdf/pdf-find-lines.ts` (new, pure): `pageLines(pageIndex, items)` joins items into lines, ending a line after every item with `hasEOL` and at the end of the page. It keeps every line, empty ones included, because `TextLayer` appends one `<br>` for every `hasEOL` item even when the item's string is empty (`pdfjs-dist/build/pdf.mjs`, `#appendText`), so a line's index on its page is the same number in both models. An empty line never matches, since `contiguousMatch` returns nothing for a blank query and an empty line cannot contain a non-blank one. Each line keeps its text, its page index, its index on the page, and its top fraction (the first item's). The hook concatenates pages' lines in page order into one array, so `useLineFind`'s `index` maps straight back to a line.
- `web/src/plugins/pdf/pdf-find-marks.ts` (new, DOM but React-free): `occurrencesInLayer(layer, query)` walks a drawn `.pdf-text-layer`'s whole subtree in document order, including text and `<br>` elements nested in `.markedContent` wrappers, splitting lines at each `<br>`, and returns a `Range` for every case-insensitive occurrence that sits within one line (a range may cross the spans PDF.js splits a line into), each tagged with its line index on the page and its start offset within that line. Overlapping occurrences are all returned. `paintMarks(ranges, current)` adds ranges to two shared highlights, `pdf-find-match` and `pdf-find-current`, the way `paint` in `reply-selection.ts` does, and returns a function that deletes exactly those ranges; the current range is excluded from the match set by object identity. Each tab adds and removes only its own ranges, so two PDF tabs with open overlays each keep their own marks. Where `CSS.highlights` or `Highlight` is missing, it does nothing.
- `web/src/plugins/pdf/usePdfFind.ts` (new hook, modeled on `useShellTranscriptFind`): owns the read lines, a `reading` flag, a `started` ref, a mounted ref, and the element focused before opening. `open()` records `document.activeElement`, starts reading on the first open only, and calls `useLineFind`'s `open` with an empty query; a second open while already open focuses the input and selects its query instead. Reading walks pages in order, awaits `readPageText` one page at a time, appends each page's lines as a new array, and stops when the hook unmounts; a page whose read rejects contributes nothing. `select(index)` sets the highlighted row and asks the tab to reveal that line's page and top fraction. `close()` closes the overlay and refocuses the remembered element if it is still in the document and another text field has not taken focus. `current` reports the highlighted result's page, line index on the page, and range start for the marks. It is memoized on those three numbers rather than on the lines and results arrays, so a page read that leaves the highlighted occurrence where it was returns the same object and does not trigger a repaint.
- `PdfStage.tsx`: `PdfJump` gains an optional `offset`, a fraction of the page's height. `PdfTab`'s `goToPage(next, offset?)` sets the page and a new jump token, and includes `offset` whenever it is not `undefined`, so a line at the very top of a page still takes the offset path. Header page changes, `pageBy`, `toggleLayout`, and thumbnail selection pass no offset. `PdfStage` also takes an optional `focusable` prop; when it is true the stage renders `tabIndex={0}` and focuses itself on pointer down, so clicking a docked page puts focus inside the docked tab and gives it the keys. A centre stage keeps its markup and focus behavior unchanged.
- `usePdfStageViewport.ts`: with no offset, continuous scroll keeps today's `scrollIntoView({ block: 'start' })`, and single page needs no scroll because it re-lists the page. With one, in either layout it scrolls the stage so the point `offset` of the way down that page's `.pdf-page` element sits a quarter of the stage's client height from its top, clamped by the browser's own scroll limits. The target comes from bounding rectangles rather than `offsetTop`, since the stage is not the page's offset parent: the stage's current `scrollTop`, plus the page rectangle's top minus the stage rectangle's top, plus `offset` times the page rectangle's height, minus a quarter of the stage's `clientHeight`. Single page applies it after the page is listed, so a match on another page shows that page first. The visible-page observer then updates the position readout and the thumbnail as for any other scroll.
- `usePdfPageRender.ts`, `PdfPage.tsx`, `PdfStage.tsx`: an optional `onTextLayer(index)` callback, called after `renderPage` resolves for a page that has a text layer and only while the render is still live. `PdfTab` keeps the callback stable and bumps a counter on each call so the marks re-apply to a freshly drawn or redrawn layer (a zoom or resize redraw replaces the layer's children and with them every old range). The callback is not passed to `PdfThumbnails`, which renders no text layer.
- `web/src/plugins/pdf/usePdfFindMarks.ts` (new hook): while the overlay is open with a non-empty query, for each `.pdf-text-layer` under the stage it reads the page index from the closest `.pdf-page`'s `data-page`, finds occurrences, and paints every occurrence into `pdf-find-match`, and paints the occurrence whose page, line index, and start match the highlighted result into `pdf-find-current` instead. It repaints when the query, the highlighted row, or the text-layer counter changes, and clears everything when the overlay closes or the tab unmounts. Layers with no `.pdf-page` ancestor or an unusable `data-page` are skipped. Each repaint walks every drawn layer; a page keeps its drawn layer once drawn, so that is every page that has been drawn. Repainting only the layer that changed is the documented upgrade if typing ever lags.
- `web/src/plugins/pdf/usePdfKeys.ts`: takes the overlay's open state and a close callback; while the overlay is open, Escape closes it and does not reset zoom. Every other key is unchanged.
- `web/src/plugins/pdf/usePdfKeyOwnership.ts` (new hook): answers whether this PDF tab owns the window keys. It listens for `focusin` and `focusout` on the window and keeps a focus snapshot from `document.activeElement`: whether it sits inside this tab's `.pdf-tab` root, and the label of its nearest `[data-tab-label]` ancestor, if any. An inactive tab owns nothing. An active tab owns the keys while focus is inside its root. Otherwise a centre tab owns them only while focus is in no labelled tab, such as on the document body, and a docked tab does not own them. Focus in another plugin tab, a harness tab, or a files or notifications sidebar therefore belongs to that tab, not to a current centre PDF.
- `web/src/plugins/pdf/PdfTab.tsx`: calls `usePluginChordClaims('pdf', capabilities.label ?? 'pdf', capabilities.claimedChords ?? [], capabilities.active, handler)` with the same arguments shape as `ShellTab.tsx`. The claim is registered whenever the tab is active, so `Cmd+F` is always swallowed there; the handler does nothing unless the document is loaded. It renders `LineFind` as a direct child of `.pdf-tab`, after `.pdf-body` and conditional on `find.findOpen`, with placeholder `Search document`, `rowLabel` returning the line's page number, `status` `Reading pages…` while reading is unfinished, and the shared input ref. The tab stays thin: the hook owns the state, and the tab wires it to the overlay and stage. It also puts a `tabRef` on the `.pdf-tab` root, calls `usePdfKeyOwnership(tabRef, capabilities.active, capabilities.dock !== null)`, and passes `ownsKeys && loaded !== null` to `usePdfKeys` in place of `capabilities.active && loaded !== null`, so only the owning tab's Escape closes its overlay. It passes `focusable={capabilities.dock !== null}` to `PdfStage`. The chord claim keeps `capabilities.active`, because `chordTabLabel` already routes a claimed chord to the focused tab label.
- `web/src/plugins/pdf/pdf.css`: `.pdf-tab` gets `position: relative`, making it the overlay's containing block as `.editor-tab` is for the editor (`theme.css`: "`position: relative` makes it the positioning context for the find overlay"). The two highlight rules are written as `.pdf-text-layer ::highlight(pdf-find-match)` and `.pdf-text-layer ::highlight(pdf-find-current)`, using the theme accent mixed toward transparent at 20% and 45%, setting only `background-color` so the canvas text shows through. Every selector stays rooted in a `pdf-` class.

### Implementation order

The feature is built in four slices, each keeping typecheck and tests green:

1. The shared overlay changes (accessible name, `Cmd+F` select, `rowLabel`, `status`) with their tests and the editor and shell spec lines.
2. `readPageText`, `pdf-find-lines.ts`, and `usePdfFind`, then the manifest claim and the overlay in `PdfTab` with reveal and the Escape change.
3. The text-layer callback, `pdf-find-marks.ts`, `usePdfFindMarks`, and the highlight rules.
4. Specs, help, and user docs, with the end-to-end verification.

## UI design

The feature adds the existing find overlay (`LineFind`, styled by the `.picker` and `.editor-find` rules in `web/src/theme.css`) to the PDF tab body (`web/src/plugins/pdf/PdfTab.tsx`). The editor and shell tabs render it at the bottom of their bodies.

### Placement and layout

- The overlay sits where the editor's and shell's do: anchored to the bottom edge of the PDF tab, spanning its full width (over the page strip too), at most 70% of the tab's height, with the `.picker` shadow and background. The PDF tab body is the overlay's positioning context, as `.editor-tab` is for the editor's.
- Its input sits at the top of the overlay, followed by the result rows. Each row is a dimmed, right-aligned bare page number in the column the editor uses for line numbers, then the line's text with the matched characters in the existing `mark` style. A line too long for the overlay is clipped with an ellipsis.
- Because the overlay covers the bottom of the tab, revealing a match places its line a quarter of the way down the stage, above the overlay.

### Interaction

- `Cmd+F` opens the overlay with an empty, focused input. The element that had focus before is remembered.
- `↑` / `↓`, a click, Return, and Escape behave as set out under Moving to a match. A click keeps focus in the input.
- `Cmd+F` while the overlay is already open keeps it open and selects the whole query, so typing replaces it. With focus outside the input, the chord focuses the input and selects its query. The browser's own find bar never appears. This change is made in the shared overlay, so the editor's and shell's overlays behave the same way while their inputs have focus.
- Escape closes the overlay and returns focus to the element that had it before `Cmd+F` was pressed, usually the document body, so the page and zoom keys keep working. Closing because the tab stopped being active restores nothing, since focus has already moved elsewhere.

### States

- Empty query: the `type to search` hint, no rows, no marks.
- Reading text: the document's text is read when the overlay first opens, and results fill in and re-rank as pages are read. While reading is unfinished and the query is not empty, a muted `Reading pages…` row sits below the results, and takes the place of `No matching lines` until reading finishes.
- No match once every page is read: `No matching lines`.
- Loading or failed document: `Cmd+F` does nothing and the overlay never opens.
- Overflow: at most ten rows; long lines are clipped; a narrow pane or a sidebar dock narrows the overlay with the tab.

### Keyboard and accessibility

- One new binding, `Cmd+F`, claimed only while a PDF tab is the active one. It does not collide with the PDF tab's own keys (`↑` / `↓`, Page Up / Page Down, Escape, Ctrl / Cmd + wheel), and it extends the existing `Cmd+F` row in `help/keys.md` rather than taking a chord from anything else. Ctrl+F is unaffected.
- While focus is in the overlay's input it holds the keyboard; Escape closes it before it can reach the PDF view's zoom reset. With focus outside the input, the page, zoom, and Escape keys belong to the focused PDF tab: a centre PDF while it is current and focus is not inside another labelled tab, and a docked PDF only while focus is inside its own `.pdf-tab`. Clicking a docked page focuses its stage, so the docked tab's keys stay reachable. In the owning tab, Escape still closes the overlay first. With a centre and a docked PDF both showing their overlays, one Escape closes only the focused tab's overlay and one arrow or Page key moves only the focused tab's page.
- The overlay's input gets an accessible name equal to its placeholder: `Search document` here. Since the input is shared, the editor's becomes `Search buffer` and the shell's `Search transcript`.

### Visual consistency

- The overlay is the shared `LineFind` with its `.editor-find` styling, unchanged.
- Marks on the pages use the theme accent: every occurrence at 20% opacity, the occurrence behind the highlighted row at 45%. Both stay translucent so the page's own text shows through, and they are distinct from the text layer's blue selection color. Their rules live in the PDF plugin's own stylesheet, rooted in a `pdf-` class, so nothing outside the tab changes (`product/specs/pdf-tab.md` § Confined to its own tab).

### Code organization

- Client code stays in the PDF plugin's own directory, `web/src/plugins/pdf/`, per `ai/guidelines/react-code-organization.md`: grouping a page's text into lines (`pdf-find-lines.ts`) and finding occurrences in a drawn layer (`pdf-find-marks.ts`) live in React-free modules with colocated tests; the find state (`usePdfFind.ts`) and the marks (`usePdfFindMarks.ts`) live in hooks; `PdfTab.tsx` stays thin, only wiring the hooks to `LineFind` and the stage. The plugin imports `LineFind`, `useLineFind`, `usePluginChordClaims`, and `isTextEntryElement` only from `web/src/plugins/api.ts`, and nothing from another plugin. The marks module copies the few lines of `paint` from the shell plugin rather than importing it, because a plugin may not import another plugin.
- The changes to the shared overlay (selecting the query on `Cmd+F`, the accessible name, a row label other than a line number, and an extra status row) are made in `web/src/shared/line-find/`, where the editor and shell already reach it.
- Everything here is view-local state (whether the overlay is open, its query, the highlighted row, the marks), which `ai/guidelines/architecture-principles.md` §1 lets the client own. The server's tab state is unchanged.

## Out of scope

- Writing to the document in any way (annotation, form filling, signing), as today.
- Regex, case-sensitive, or whole-word matching; the editor's matcher is used unchanged.
- Matches that span a line break, including hyphenated words.
- A match counter (`3 of 17`) or next / previous match buttons in the PDF header.
- A typed command that opens the overlay pre-filled, like the shell tab's `search transcript <pattern>`. A PDF tab has no command bar.
- Marking pages that contain matches in the page strip.
- A separate message for a document with no searchable text.
- A screenshots page, a new documentation page, or a help table section for the PDF tab.
- A plugin API changelog entry. The manifest chord claim is not an API change.
