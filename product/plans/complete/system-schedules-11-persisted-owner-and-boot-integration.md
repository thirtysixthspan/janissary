# System schedules 11: persisted owner and boot firing lifecycle

**Complexity: 6/10** — a durable project owner must coordinate synchronous commits, asynchronous shell/run-script preparation, the existing scheduler tick, boot recovery, queue provenance, and shutdown ordering across server managers.

This is the persisted owner's mutation/tick state machine and its boot/disposal integration. It reuses the completed shell, store, notice, and queue contracts. Grammar, command entry points, aggregate UI, dialog delivery, and final browser E2E follow separately.

## Goal

Implement the project-owned schedule manager, load and recover it before firing begins, and append each due runscript to the managed system shell's FIFO. Source: `product/plans/ready/add-system-schedules.md`.

## Decisions and dependencies

- Dependencies: completed 02–10. Reuse 02's notices, 03/04's `SystemShellManager.ensure()` and PTY recovery, 07's validated store and runscript reader, 08/09's queue provenance and shell consumer, and 10's provenance-only harness naming policy. Plans 12/13 own grammar and command registration; 14 owns aggregate views/actions, 15 the dialog, and 16 full command/browser E2E. Do not implement their surfaces here.
- Add `SystemScheduleManager` as `managers.systemSchedule`, constructed in `src/controller/create-managers.ts` after `tab`, `pty`, and `systemShell` exist. Add it to `ManagerRegistry` and `MANAGER_DISPOSE_ORDER`, immediately after `schedule` and before `systemShell`; never add it to `MANAGER_TAB_RELEASE`. Its state belongs to the project, not a tab label.
- Expose synchronous `load`, `list`, `add`, `cancelByName` (all matches), `cancelByKey` (one row), `clear`, and `dispose`; the tick is deterministic as `tick(now)`. Mutations return success or a domain failure synchronously. Build and validate the full next snapshot, call the 07 store's synchronous atomic `save`, and only then replace memory state, emit `schedules: changed` and `state: dirty`, or acknowledge success. On save failure, retain the old in-memory state and publish nothing. Do not debounce, buffer, or await persistence.
- Keep `ScheduleManager`'s sole one-second interval in `src/schedule/manager.ts` (`start`, `tick`). Make `start()` idempotent and invoke the system owner once per tick with that tick's captured `now`; do not create a second timer or recursive catch-up loop. Existing tab firing, per-harness one-entry-per-tick behavior, lateness notices, resume handling, and hooks remain unchanged. Extract cohesive tab-firing code and update direct imports if adding the owner hook would put a production file over ESLint's 200 counted lines; never compact it.
- Remove the implicit `schedule.start()` from `createController()` (`src/controller.ts`, `createController`). The production sequence in `startServer()` (`src/index.ts`, `startServer`) is: capture one boot cutoff before the first awaited shell preparation; open required `janus` (fatal on failure); await `systemShell.ensure()` (nonfatal); synchronously load and boot-recover the system schedule snapshot using the captured cutoff; then start the one scheduler. No tick may fire before recovery finishes. Keep `controller.reattachSessions()` unconditional and non-awaited after local shell startup and before serving clients; neither system-shell nor store failure may gate it. A failed `janus` launch still shuts down and aborts before remote restore or scheduler start.
- At boot, entries with `nextRun <= cutoff` are missed and never enqueued. Emit one 02 missed notice per missed entry, remove missed one-shots, and advance missed recurring entries with `computeNextRun(entry, new Date(cutoff))` to a strictly future run. Skip the entire closed-app backlog rather than replaying occurrences. Persist the complete recovery snapshot synchronously before publishing it; if that save fails, retain the original due snapshot and do not fire it in this startup. A live-process sleep/wake firing is not a boot miss: enqueue once and advance from that tick's `now`.
- A missing store loads empty. Invalid JSON or invalid v1 data produces one startup diagnostic on stderr, leaves the file untouched, and starts with an empty in-memory owner; a later valid explicit save may replace invalid v1 data. An unsupported version produces one diagnostic, starts with no executable entries, and blocks every save so this process cannot downgrade the file. These errors do not abort Janissary startup. Use the existing `process.stderr` startup reporting path; do not add a notification kind. The store's existing `load` result distinguishes invalid from unsupported versions.
- A live tick claims due entries by immutable `key`, reads the current runscript through `readRunscript(projectRoot, name)`, and calls `systemShell.ensure()` before enqueueing. Serialize async preparation and enqueue batches within the owner, and recheck that the same keyed entry remains current after every await. A synchronous cancel/clear during preparation wins: stale work must neither restore that entry nor enqueue it. Derive the post-fire snapshot from the latest committed owner state, atomically save it, then append the complete batch synchronously. If persistence fails, enqueue nothing and leave the due entry unchanged, so a retry cannot duplicate an already-appended batch. Do not claim crash-proof or exactly-once execution: the tab queue is intentionally in-memory.
- Append each firing's lines as one contiguous FIFO batch through a narrow `TabManager` queue-state method. Reuse 08's `enqueueSystemSchedule` row shape for every line and the same schedule key, and emit one queue/state change after the whole batch; do not call the current single-line method in a loop that exposes interleaving batches. Empty scripts are successful no-op firings: advance/remove the schedule, emit the run notice, and append no rows. Firing notice means enqueued, not completed. The existing shell consumer continues after a failing line; no per-line error notice or line-error stop policy is added.
- If the runscript is missing at fire time, emit 02's exact missing-file notice, remove a one-shot or advance a recurring entry from the firing time, and persist before publishing the outcome. If the script exists but is unreadable or its path is unsafe, report a one-line stderr diagnostic, leave the entry due, and enqueue nothing. If shell ensure fails, `SystemShellManager` already emits the 02 failure notice once for that ensure attempt; do not duplicate it in the schedule owner, and leave the due entry unchanged for retry. A failure for one due entry must not prevent independent due entries from being attempted.
- `dispose()` prevents new ticks and enqueue work, waits for in-flight preparation, and rechecks disposal after each await so an ensure already underway cannot enqueue after shutdown begins. Stop `ScheduleManager` before disposing this owner, and dispose the owner before `SystemShellManager`, PTY, tabs, or their queue. Queued lines are never persisted.
- Keep direct-controller tests deterministic: `createController()` no longer starts a timer implicitly. Tests that exercise elapsed scheduler ticks explicitly call `managers.schedule.start()` after arranging manager state, and dispose through controller shutdown. Audit every `createController(` caller with `git grep`; the current call sites include `src/{agent/manager.test,commands/agent.test,controller.test,managers.test,system-shell.test}.ts`, `src/controller/{create-adapters,create-managers,shell.unsandboxed,workspace-notice}.test.ts`, `src/notifications/system-schedule.integration.test.ts`, `src/plugins/agent-monitor/activate.test.ts`, and `src/tab/hidden-lifecycle.integration.test.ts`. Update only timer-dependent fixtures; the production `startServer` path is the only automatic start.
