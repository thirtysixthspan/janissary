# Answering record id on the ACP prompt result
**Complexity: 3/10** — one optional field on a result type, but it has to survive every way a prompt settles (a plain settle, a model fallback, a cancel or reset, and the rebuilt exhausted error), the file that rebuilds it sits at 198 of 200 counted lines so a helper moves out, and one existing real-records assertion changes; a wrong id would later link the wrong connection tab.

## Goal

Make the `AcpPromptResult` that `AcpManager.promptResult` and `run` hand to their callers carry an optional `recordId`: the durable ACP record that holds the prompt's final block. It is the id of the record that answered, including after a model fallback, and when every model failed it is the record of the last model tried. A refusal carries none. Nothing reads the field yet. Subplan `03-reply-record-and-tell-line` stores it on the settled background reply.

This is the first of eight subplans that split `product/plans/complete/shell-agent-thinking-indicator.md` (the source plan). Later subplans are named by number and slug, for example `02-dispatch-receipt`.

## Design decisions and dependencies

This subplan depends on nothing earlier. `03-reply-record-and-tell-line` consumes the field, and nothing else in the sequence does. `02-dispatch-receipt` also edits `src/acp/response.ts` and lands after this one, so leave `appendAcpBackgroundReply` and the `randomUUID` import exactly as they are here.

Source plan requirements carried here: "Server changes" bullets on `AcpPromptResult`, on `settleAcpPrompt`, and on the `manager.ts` extraction into `ask-role.ts`; "Once the prompt settles" (the link is pinned to the record that answered, and when every model failed it is the last model's); "Once the prompt settles" (an answer, an `ACP error: …`, `ACP: prompt cancelled.`, and `ACP session closed.` all leave a block, so each result carries the id; a refusal leaves none); the server half of the "Tests" list for `manager-fallback.test.ts`, `ask-role.test.ts`, and `response.test.ts`.

- `AcpPromptResult` in `src/acp/types.ts` gains an optional `recordId` on both variants, so a caller needs no cast after narrowing on `answered`. The comment above the type says what it means: the record holding the prompt's final block, present only when the prompt reached a record.
- `settleAcpPrompt` in `src/acp/response.ts` is the only caller of `pending.finish` (verified by search: `src/acp/response.ts:47`). It has three kinds of caller, and all three must carry the id: `runCorePrompt` in `src/acp/run-prompt.ts` (the `finished` handler settles an answer, the `error` handler settles `ACP error: …`), `AcpSessionManager.close` in `src/acp/session-manager.ts` (reset, fatal error, and transport loss settle `ACP session closed.` or the given line), and `AcpManager.cancel` in `src/acp/manager.ts` (settles `ACP: prompt cancelled.`). The `cancel()` wrapper replaces `request.finish` with a function that forwards the same result, so a cancellation carries the id too.
- `settleAcpPrompt` builds a new result object for `pending.finish`: the incoming result's fields plus the id taken from `pending.recordId`, and only when the pending prompt has one; with none it passes the incoming object through untouched. Two traps are closed here. First, never assign the id onto the incoming result: `AcpSessionManager.closeTab` hands one `output` object to every role's `close`, so an assignment would leak the ask role's id onto the tell role's result. Second, read `pending.recordId`, never the role state's `recordId` (`acpRoleRuntime(runtime, role).recordId`): `close` passes `settleAcpPrompt` an `afterSettlement` that runs `closeCoreRecord`, which deletes the role state's id before `pending.finish` runs, and a fallback replaces it. `pending.recordId` is a copy taken when the block was added, so it survives both. The record's own answer text still comes from the original result (`answerCoreRecord` runs first and is not changed).
- `promptCoreRecord` in `src/acp/record-feed.ts` sets `pending.recordId` only once `records.prompt` added a block (verified in `src/acp-records/manager.ts`: `prompt` returns false for blank text or an already-unanswered block). So the paths that never add a block carry no id: `AcpManager.run`'s refusals (a prompt already running, a usage line, the remote session still connecting, `noRoleModels`), `Tab not found`, and the `attempt` guards for a missing tab or entry. They call `onDone` directly and never reach `settleAcpPrompt`. No code change is needed for them. `src/acp/record-feed.test.ts` already pins the refusal case with a live record: 'refuses every overlapping entry point without settling or adding a block' fires the handshake, so a record with a running block exists, and still expects the refusal to resolve with exactly an error and no other key.
- Model fallback needs no change in `settleAttempt` for the answered or single-model case, because each attempt has its own pending prompt (`AcpManager.attempt`) and `settleAttempt` forwards the final attempt's result unchanged. A failed attempt that has another model left never reaches `onDone`, so the failed model's id is never the settled one.
- The id comes from the final attempt alone. A model that fails during its handshake never has a record (`AcpSessionManager.session` calls `beginCoreRecord` only after a successful `onConnect`), so when the last model fails before its handshake the settled result carries no id even though an earlier model's record holds the prompt's block. That is the source plan's "record of the last model tried" read literally. Nothing tracks ids across attempts and the helper never looks back at earlier attempts; the shell then shows no link for that prompt. A test pins this.
- The exhausted case does need a change. `settleAttempt` builds a fresh `{ answered: false, error: exhaustedError(…) }` when `failed && failures.length > 1`, which drops the field. That expression moves to a new exported helper beside `exhaustedError` in `src/acp/ask-role.ts` (66 counted lines today), named `finalAttemptResult`. Its parameters, in order: the attempt's result, whether the attempt failed on its model (the `failed` value `settleAttempt` already computes), the accumulated failures (which already include the current one at the call site), and the role (`attempt.role`). When the attempt failed and the failures number more than one, it returns an unanswered result whose error is the `exhaustedError` text for those failures and that role, carrying the incoming result's `recordId` when it has one. Otherwise it returns the incoming result unchanged (the same object). `ask-role.ts` gains a type-only import of `AcpPromptResult` from `./types.js` (`types.ts` imports only `../project/tokens.js`, so there is no cycle). `src/acp/manager.ts` (198 counted lines) imports the helper and calls it from `settleAttempt` in place of the inline expression. The `exhaustedError` import stays because `start` still calls it (`src/acp/manager.ts:65`). The two-line expression becomes one line and the import list may take one more, so `manager.ts` ends at 197 or 198 counted lines and does not grow. This is the one extraction this subplan owns.
- `AcpPromptResult` is re-exported by the published plugin contract (`src/plugins/api.ts:32`) and returned by `promptAcpResult` (`src/plugins/acp-capabilities.ts`), so the field is visible to plugins from the moment this lands, and `src/plugins/api.ts` itself needs no edit. It is optional and additive: `ai/guidelines/plugins.md` §4 classes an optional field as additive, and `TAB_PLUGIN_API_VERSION` (`src/plugins/api-capabilities.ts`, currently 3) stays put, as the v3 changelog already says of other additive changes. Because the contract changes observably now, the two documents that spell out the result's shape move with it under principle 10 of `ai/guidelines/architecture-principles.md`: the `promptAcpResult(prompt)` bullet in `product/specs/acp.md` (§ Availability and plugin API) and the `promptAcpResult(prompt)` bullet in `documentation/developer-documentation/tab-plugins.md` (§ Server activation). Neither is named by the source plan; they are kept for that reason and no other documentation is added. Keep each bullet's leading `promptAcpResult(prompt)` text unchanged: `src/plugins/documentation.test.ts` (the 'documents every server capability the host actually supplies' case) looks for each capability as a bullet starting `` - `name( `` in the developer page.
- Existing assertions on settled results, verified by reading:
  - `src/acp/manager-fallback.test.ts` mocks `connectAcp` with an implementation that returns a bare session and nothing ever calls the `onConnect` it was handed. So `beginCoreRecord` never runs, no pending prompt gets an id, and every exact assertion in the file (the answer, the exhausted error, the error after a reply, cancel, reset, the refusals, the tell exhaustion) stays valid.
  - `src/acp/manager.test.ts` has two cases that fire the handshake from inside the `connectAcp` mock: 'onConnect callback fires messageBus.emit on session connection' and 'returns provider/model string when a session is connected'. The id reaches their pending prompt, but neither settles a prompt or asserts a result. Every settled-result assertion in the file belongs to a case that never fires the handshake, so the file stays valid.
  - `src/acp/plugin-session.test.ts` is the exception. It uses a real `AcpSessionRecords`, and its `connectAcp` mock calls `options.onConnect()` at once (`setup`), so a prompt there reaches a record. Exactly one assertion compares a settled `AcpPromptResult` for exact equality: 'answers a prompt the loop failed as a refusal, with the line the user is shown' (`promptAcpResult`, then `onError('rate limited')`, expecting `{ answered: false, error: 'ACP error: rate limited' }`). That result now also carries `recordId`, so the expectation is updated (see Tests). Its other `promptAcpResult` cases use `toMatchObject`, and its dispatch assertions compare dispatch replies, not results, so they are unaffected.
  - `src/plugins/launcher/summarizer.test.ts` and `activate.test.ts` mock `promptAcpResult`, and the summarizer reads only `answered`, `error`, and `reply` (`src/plugins/launcher/summarizer.ts`), so they run unchanged.

## Proposed changes

- `src/acp/types.ts`: add the optional `recordId` to both variants of `AcpPromptResult` and extend the comment above the type.
- `src/acp/response.ts`: in `settleAcpPrompt`, hand `pending.finish` a new result carrying `pending.recordId` when the pending prompt has one, as decided above. `answerCoreRecord` keeps receiving the original result.
- `src/acp/ask-role.ts`: add `finalAttemptResult` next to `exhaustedError`, exported, with a comment saying why the id must survive the rebuild, and the type-only import.
- `src/acp/manager.ts`: import the helper and call it from `settleAttempt`. Keep the `exhaustedError` import. The counted line total must be no higher than 198 after the edit.
- `product/specs/acp.md` and `documentation/developer-documentation/tab-plugins.md`: the `promptAcpResult` bullets gain one sentence each. It says a result may also carry an optional `recordId`, the id of the connection record that holds the prompt's final block (the answering model's record, or the last model's when every model failed), and that a prompt that reached no record, such as a refusal, carries none. In the developer page the sentence also keeps the literal shape in the bullet true: either variant may carry the field.

## Tests

Server (vitest project `server`), colocated:

- `src/acp/response.test.ts` (new). Mock `../bus.js` as `manager-fallback.test.ts` does, and use a fake `Managers` with just the pieces `settleAcpPrompt` touches: `tab.byLabel`, `tab.updateRunning`, `tab.deleteBusy`, and `acpRecords.answer`, with a `makeTab` tab whose runtime holds the role state and a pending prompt shaped like the one in `src/tab/view.test.ts` plus `runningEntries`. Cases: `settleAcpPrompt` hands `finish` the result with the pending prompt's `recordId` added, for an answer, an `ACP error: …` line, `ACP: prompt cancelled.`, and `ACP session closed.` (one `it.each`); `acpRecords.answer` still receives the original text; the id is still on the result when `afterSettlement` deletes the role state's `recordId` first, as `closeCoreRecord` does; a pending prompt without a `recordId` gets the identical object (`toBe`) with no `recordId` key; the incoming result object is not mutated (no `recordId` key on it afterwards), which guards the shared `closeTab` object; and when the tab or its pending prompt is gone, `finish` is not called and `afterSettlement` still runs. `03-reply-record-and-tell-line` extends this file for `appendAcpBackgroundReply`.
- `src/acp/ask-role.test.ts`: `finalAttemptResult` keeps `recordId` on the exhausted error when the attempt failed with more than one failure, and the error text equals what `exhaustedError` returns for the same failures and role (including a `tell` role). It returns the same object (`toBe`) for a single failure, for an answered result, and for a not-failed unanswered result such as a refusal even when the failure list holds two entries. An exhausted rebuild from a result with no `recordId` has no `recordId` key. Put these beside the existing 'fallback messages' cases.
- `src/acp/manager-fallback.test.ts`: first hoist the inline `acpRecords` mock object in `setup` into a local that `setup` also returns, so a case can call `begin.mockReturnValueOnce` for a different id per call. Add a small helper that fires `launched(call).onConnect` (the option is optional, so use a non-null assertion as the file already does for `env`). Then add three cases, each firing the handshake explicitly:
  - After a fallback the settled result carries the answering model's record id and not the failed one's: `begin` returns `record-1` then `record-2`, fire `onConnect` on the first session, fail it with `loop(0).error(…)`, fire `onConnect` on the second session, answer it with `answer(loop(1), …)`, and expect `onDone` called with the answered result plus `recordId: 'record-2'`.
  - When every model fails the settled error is the exhausted text and carries the last model's id (`record-2`). In a variant where the second session never fires `onConnect`, the same exhausted text settles with no `recordId` key, pinning the decision above.
  - A cancelled prompt and a reset prompt each carry the id: after `onConnect`, `await acp.cancel('tab1')` resolves the pending `promptResult` with the cancellation line plus the id, and in a second `setup` `acp.close('tab1')` resolves with `ACP session closed.` plus the id. The second is the case that fails if the implementation reads the role state's id instead of the pending prompt's.

  Existing cases in this file and in `src/acp/manager.test.ts` must pass unchanged, per the verification in the design decisions.
- `src/acp/plugin-session.test.ts`: change the expectation in 'answers a prompt the loop failed as a refusal, with the line the user is shown' to also expect `recordId` equal to the id of the only record (`managers.acpRecords.rows()[0].id`). That makes the existing real-records test the end-to-end proof that the id is a real record's. The other assertions in the file are untouched here; `02-dispatch-receipt` changes the dispatch ones.
