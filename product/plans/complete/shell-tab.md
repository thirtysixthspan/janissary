# Shell tab plugin

**Complexity: 7/10** — the first plugin to own a live process, so it carries new contract on both sides (a tab resource, four server capabilities, three client capabilities, two optional declaration fields — `chords`, which inverts the existing "a core chord always wins" rule, and `hostState`, a new push channel), a shared-component signature change, and teardown reasoning across tab close and shell exit.

**Feature description, verbatim from `product/backlog/features.md` `## ready`:**

> a new `shell tab` implemented as a plugin. The tab contains a pseudo terminal that launches zshell. The tab derives the following features from the agent tab: command line, identical metadata bar, same popups, menus and keybindings.

This plan adds a bundled **shell** tab plugin: a tab whose body is a live pseudo terminal running zsh, laid out exactly like an agent tab — the metadata row on top, the terminal where the transcript would be, the command line at the bottom — and reaching the same popups, menus and key bindings the agent tab does.

The reason it is worth building is that Janissary already has all three halves and no way to bring them together. A live full-tab pseudo terminal exists and is host-owned (`web/src/ShellTab.tsx`, `web/src/harness/HarnessTab.tsx`). A plugin tab that owns a whole tab body exists (`src/plugins/`, `web/src/plugins/`). And the agent tab's chrome — the metadata row, the command bar, the pickers, the context menu, the chords — sits in `web/src/shared/` precisely so several tab kinds can share it. What is missing is the seam: the plugin contract has **no pseudo-terminal capability at all**, and the chrome a plugin cannot reach is chrome a shell tab cannot reuse.

The result is a tab with one input path and one output path, which is the shape an agent tab already has. You type into a command line; the line either runs as an application command or is sent to zsh; zsh's screen appears above it. Nothing may be typed into the terminal directly.

## Design decisions

**The tab is named `shell` and is opened by the command `zsh`.** The plugin's id and its `tabLabelPrefix` are both `shell`, so the strip reads `shell`, `shell2`, and so on. `shell` cannot be the command: it is one of the two names reserved as core routes (`ROUTE_NAMES`, `src/plugins/command-adapter.ts:12`) and a plugin claiming it is refused at registration with `reserved tab plugin command claim "shell"` (`:57`) and starts life disabled. `zsh` is free — no core command matches it — and it is what a user would guess.

**The terminal is always zsh, always fully interactive, and always reads the user's rc files.** Every other pseudo-terminal in the application launches `process.env.SHELL || 'bash'` (`src/pty.ts:48`) with rc files deliberately stripped — bash gets `--norc --noprofile`, zsh gets `--no-rcs` (`src/shell/startup.ts:8`). That is right for a shell whose output is scraped for a sentinel and right for nothing else: a terminal that ignores `.zshrc` has no `PATH` additions, no aliases, and no prompt of the user's own. This tab is spawned with an explicit `/bin/zsh` and **no arguments at all** — the only invocation in the application that does not go through `shellCommandArgs` (`src/shell/startup.ts:45`, which would otherwise produce `-i -c <command>`).

**The terminal is an output view. The command line is the only way in.** The terminal is never given keyboard focus; the command bar holds it, a click inside the terminal returns focus to the bar, and the bar is re-focused whenever the tab becomes the visible one. `disableStdin` on the xterm was considered and **not** chosen: the rule wanted is that the bar keeps the focus, not that the terminal structurally refuses input, and a terminal that never holds focus never receives a keystroke either way. A user therefore cannot type into zsh directly, only send it lines.

That decision is what makes the command line the interesting part, because a line typed into it has two possible meanings. **`!` as the first character forces the shell**; with it, the rest of the line is written to zsh and nothing else happens. **Otherwise the line is offered to the application first**: if it resolves to a command with the application's own `resolveCommand`, it runs as that command; if it resolves to nothing, it is written to zsh.

The consequence is accepted rather than designed around: a word that collides with a command name is swallowed by the command. A shell sitting at a `read` prompt, or asking for a password, cannot be sent the word `theme` or `files` without the `!` prefix. No hint is shown and the bar does not warn; `!` is documented in `help.md` — the file the `help` command reads (`src/commands.ts:28`) — as the override, and again in `product/specs/application-commands.md`.

**The tab's body is the terminal, not a transcript.** The metadata row sits above it and the command line below, which is the agent tab's layout with the transcript swapped out. There is consequently nothing for an **Open transcript** button to open, and the shell tab's row does not carry one. The other three body buttons are live: **open file navigator**, **new agent here**, and the host-rendered **split** control.

**The metadata row is the plugin's own markup.** It renders the same `.tab-meta` structure and the same class names as `AgentTabMeta` (`web/src/shared/AgentTabMeta.tsx:35`), so it looks identical, but it is written in the plugin rather than imported — which is the self-contained shape the plugin was chosen for, and the reason it is a copy that can drift. Its actions come from declared capabilities rather than from markup it borrowed. The only glyph it needs beyond its own text is the workspace flag's icon, `workspacedIcon`, which joins the icons already re-exported for plugins at `web/src/plugins/api.ts:49`.

**The connections and schedule windows are the host's, and their rows are pushed only when they change.** `StatusPanels` and `useStatusWindows` are published beside the command bar that is already published, so a shell tab's windows are the same components with the same behaviour as an agent tab's, including the five-second auto-show, the pin and the fade. Rendering both rather than the connections-less `scheduleOnly` the harness tab uses is the deliberate choice here, because a shell tab does own a connection — its zsh is a live `terminal:zsh` entry on the tab, exactly as an inline terminal card is on an agent tab — and the button being wired should list something true.

Their content is host state a plugin cannot read, so the host pushes it. The rows are exactly the ones `buildTabView` already computes for every tab — `connectionsFor(label)` and `scheduleView(label)` (`src/tab/view.ts:10`, `:12`) — so no second computation of either exists. The plugin declares that it wants them, and the host delivers them **only when they differ from what it last pushed to that tab**, calling the plugin's handler, which merges them into the payload with `updateTab`. That is the shape the notification topics already use, and it means a shell tab sits idle rather than being compared on every keystroke-driven state broadcast.

**There is one shell tab per `zsh`, and it closes when zsh exits.** `exit` typed in the terminal, or a stdin that closes, closes the tab — through the plugin's own `close()` capability, which is what that capability exists for, so it happens with no browser attached too once one reconnects and asks. There is no restart affordance and no exited state, because a closed tab is the honest representation of a shell that is no longer running.

**The working directory is the workspace when there is one.** Typing `zsh` in an agent tab that has a `-w` workspace clone starts the shell in that clone, sandboxed exactly as that tab's own shell is; typing it anywhere else starts it in the project root. The plugin learns this from a capability reporting the tab the command was typed in, because a plugin's command handler is given the argument and its capabilities and **no tab context at all** — `command(argument, capabilities)` at `src/plugins/api.ts:180`, wired at `src/plugins/command-adapter.ts:75`.

**The command line recalls the shell's own sent lines, and `Ctrl+R` lists them.** Every line the bar has sent is the complete history, because nothing can be typed anywhere else. `Up` and `Down` walk it exactly as the agent tab's bar walks its tab's command history (`web/src/shared/command-bar/useCommandHistoryRecall.ts`). `Ctrl+R` opens a popup listing it.

`Ctrl+R` belongs to the application today — `APP_CHORDS` maps `'ctrl+r'` to the `history` action (`web/src/shared/app-chords.ts:31`) and `ctrlChordOpener` fires it (`web/src/useWindowKeys.ts:123`). **A declaration may now carry a `chords` claim, and the host honours it while that plugin's tab is the visible one.** The moment another tab is focused, the application's history picker owns `Ctrl+R` again. The claim is static data in the declaration, as every other claim is; the handler is supplied through a context by the mounted body.

**The application's own chords are unchanged, and two of them are already suppressed here.** `Ctrl+A` opens the task picker, `Ctrl+G` the tab navigator, `Cmd+P` quick open, `Cmd+Shift+F` the project search, `Cmd+T` a new agent tab, and the tab-move chords all reach a shell tab exactly as they reach an agent tab. Two do not, for reasons that predate this plugin and that this plan does not change: `Cmd+F` transcript search is gated on `canSearch` (`web/src/useViewSearchState.ts:10`), which is already false for every plugin tab because `'plugin'` is in `VIEW_TAB_KINDS` (`:4`) and a plugin tab has no transcript to search; and `Ctrl+E` is gated on `isAgentTab` in `useQueuePicker.ts:17`, because the queue belongs to agents.

This is also the answer to which chords reach the application rather than the pty: because the terminal never takes focus, the question is the one the agent tab's bar already answers, with the shell's control keys added on top.

**`Ctrl+C`, `Ctrl+D` and `Ctrl+Z` reach zsh as the characters a terminal would send.** With an empty bar, `Ctrl+C` interrupts the foreground shell command, `Ctrl+D` sends end-of-input and `Ctrl+Z` suspends — the only way to stop a runaway command now that nothing can be typed into the terminal. With a selection in the bar, `Ctrl+C` copies it instead, so copying by keyboard is not lost. These are the characters `Shift+Enter` → `ESC CR` already sends on the takeover path (`web/src/shared/terminal/useXterm.ts:85`), one layer down.

**Tab completion is the application's own.** The bar's `Tab` goes through the same `complete` RPC an agent tab's bar uses (`web/src/agent-tabs/command-input/command-completion.ts:9`) and gets the same completion strip. The plugin keeps no list of its own.

**The bar shows a static dot in the plugin's colour and never goes busy.** An agent tab's dot reports that a turn is in flight (`CommandInput.tsx:123` → `label={busy ? 'queue' : undefined}`); a shell has no turn. There is no row label either, so nothing ever reads `queue`.

**A paste fills the bar and stays editable.** A ten-line paste becomes one line of text, subject to the same `!` and command-resolution rules as anything typed. Nothing is written to zsh that the user did not see first.

**The tab is an ordinary plugin tab in every other respect.** It is live and in-memory, never persisted and never restored by `--relaunch` (`product/specs/tab-plugins.md` § Plugin tabs). It docks into either sidebar through the host's control and is splittable through the host-rendered `splitAction`. It claims no file extensions, so it is reachable only by its command and both its openers refuse.

## Proposed changes

**A `spawnTerminal` tab resource.** `TabPluginResources` (`src/plugins/api.ts:53`) gains a `spawnTerminal(options)` method returning the pty id and the size it spawned at. It is a **resource, not a capability**, and that placement is load-bearing: a tab label is allocated by `addPluginTab` only *after* the payload factory has run (`src/tab/creators.ts:20`, called at `src/tab/openers.ts:83`), so a plugin cannot know its own label while spawning, and the resource window `withResources` already opens around the factory is exactly the scope that answers. A call from anywhere else throws, the same way a stashed `registerFile` does. Every acquire therefore has its release in the same object.

`withResources` gains a `terminalId` in the bag it already returns beside `fileRefs`, and `openPluginTab` hands it straight to `adopt`. The spawned pty id never becomes a field on the tab record: `PseudoterminalManager` already indexes every session by id with its owning label, so tab close and exit both find the process without the record carrying anything, and `PluginTabRecord` (`src/tab/types.ts:96`) and `PluginTabView` stay exactly as they are.

**Binding the terminal to the tab's real label.** `PseudoterminalManager` gains an `adopt(ptyId, label)` that re-points a freshly spawned entry at the label `addPluginTab` just allocated, found by plugin id plus instance key (`src/tab/openers.ts:79` already looks a tab up that way). Binding to the real label rather than a synthetic one buys two things for free: `closeTab(label)` kills the shell through the existing `MANAGER_TAB_RELEASE` walk, so no new teardown path exists to forget; and `terminalsFor(label)` lists it, so the row's connections window shows a true `terminal:zsh` entry.

**Closing the tab when the shell exits.** The client's `attachTerminal` handle takes an `onExit` callback, and the plugin calls its own `close()` from it — the capability exists precisely so a plugin can close its own tab, and tab closing is a client action everywhere else. A server-side hook in `handleExit` was considered and dropped: it needs a field on the tab record to find the owner, and it buys only that the tab closes a few milliseconds sooner while a browser happens to be attached. The mount-time status intent below is what covers the case that actually loses a tab — the shell died while no browser was connected.

**Naming zsh itself.** `spawnPty`'s eighth positional parameter is already `shellArgs`, and it hard-codes `process.env.SHELL || 'bash'` at `src/pty.ts:48` with no way to override the binary. That parameter becomes a trailing options bag carrying both the shell path and the argv, which touches exactly three call sites — `PseudoterminalManager.spawn`, `spawnTransport` (which passes `ptyShellArgs()` today, `:61`) and `src/remote/serve-processes.ts:102`. `spawnTerminal` passes `/bin/zsh` and an empty argv. This is the narrowest change that lets a plugin choose a binary: it adds a parameter, not a second spawn path.

**Four new server capabilities.** `TabPluginCapabilityName` (`src/plugins/api-capabilities.ts:10`) and the `CAPABILITIES` record gain:

- `originTab` — returns the label, working directory and optional workspace of the tab a plugin command was typed in. The host already resolves that tab for `note` and `openOrFocusTab` (`src/plugins/context.ts:95`, `:115`); this makes the same resolution readable.
- `dispatchLine` — takes one line, resolves it with the application's own `resolveCommand`, runs it when it matches, and answers whether it did. The plugin writes an unmatched line to the pty itself.
- `completeLine` — the existing `complete` RPC behind a declared capability, returning the same result shape an agent tab's bar receives.
- `terminalRunning` — whether a spawned terminal is still there. A fourth capability the draft did not name, added because the reconnect case has no other route: the exit event was broadcast to nobody, and a plugin tab is in-memory only, so a tab whose shell died while no browser was attached is still there holding the payload of a process that finished minutes ago. The draft assumed the client could hear the exit itself, which it cannot after a reconnect.

The first two are primitives; each reaches its client through exactly one plugin **intent** of the same name, because an intent is the only channel a plugin has to the server: `dispatch` answers `{ dispatched }`, `complete` returns the completion, and `terminal-status` answers `{ running }`. Three intents over three primitives rather than one route that does everything, so each carries its own payload guard and each unknown intent name is a rejection.

All four are additive, `TAB_PLUGIN_API_VERSION` stays at 1, no existing manifest changes, and `restrictToDeclared` (`src/plugins/context.ts:43`) gates each one exactly as it gates `note`.

**Three new client capabilities on `TabPluginClientCapabilities`.** `attachTerminal(ptyId, onData)` returns `{ write(data), resize(cols, rows), onExit(handler), detach() }`, implemented over the client's existing `attachPty` and the three existing PTY RPCs — so the shell plugin is the fourth consumer of a channel that already carries terminal bytes, not a fifth definition of one. Bytes already produced are flushed into `onData` before it returns, so a plugin attaching late still renders what the shell said before it did. `openFileNavigator()` and `launchAgentHere()` send the two tab-scoped RPCs the metadata row's buttons send. They are capabilities rather than `dispatchLine('files')` and `dispatchLine('agent')` because the two are not the same thing: `launchAgentFor` roots the new agent at the named tab's cwd and joins its group through `poolName` (`src/profile/manager.ts:94`), where the bare `agent` command resolves its name and directory differently (`src/profile/new-agent.ts:24`).

All three are **optional**, exactly as `registerDirtyHandle` is (`web/src/plugins/api.ts:113`): a plugin with no terminal behaves as it did before they existed, and fourteen existing plugin test fixtures that build a capability object are not churned for a capability none of them wants.

**Pushing host tab state into a plugin's payload.** A declaration gains an optional `hostState` naming the slices it wants — `'connections'` and `'schedule'`, the two `buildTabView` already produces through `connectionsFor` and `scheduleView` (`src/tab/view.ts:10`, `:12`) — and `TabPluginActivation` gains a matching optional `hostState` handler. The host compares a tab's current rows against the last set it pushed to that tab, and delivers only on a difference; the handler merges them in with `updateTab`, which replaces the payload and leaves the tab's label, position, group and instance key alone.

Two things the draft did not spell out and the implementation needed. The delivery is addressed by **instance key**, not tab label, because `updateTab` takes an instance key and a handler that has to guess one is a handler that can write the wrong tab. And each delivery carries the tab's **current payload**, so the handler merges rather than replaces: the host hands over the value it is about to be asked to replace, and only the plugin knows which fields are its own.

Delivery follows the notification rules already in force (`ai/guidelines/plugins-tabs.md` § Host notifications): only to a plugin that is active and already owns a tab, guarded at 1000 ms, fanned out concurrently with no ordering guarantee, with the handler's return value ignored — a status window cannot influence a host outcome. A slice a declaration does not name is never pushed. The first delivery always happens, because a tab with no pushed rows yet differs from any non-empty set, so a shell tab's windows are populated from the moment it opens without the payload factory needing to read anything.

Both fields are optional, so no existing manifest or activation changes and `TAB_PLUGIN_API_VERSION` stays at 1. The alternative — a capability the client polled on activation — was rejected: it makes a window that is stale by construction, and it puts a round trip on every tab switch. The alternative of dropping the two buttons was rejected in favour of keeping the row complete.

**Two host surfaces published to plugins.** `StatusPanels` and `useStatusWindows` from `web/src/shared/status-windows/`, and `registerTerminalSelection`/`unregisterTerminalSelection` from `web/src/shared/terminal/`. The selection registration is what makes a right-click on a terminal selection offer **Copy** from the app's own context menu, which is the whole of "same menus" here — `useDefaultContextMenu` resolves its terminal source only through that registry (`web/src/context-menu/useDefaultContextMenu.ts:21`). `SelectionOverlay` is deliberately **not** published: the frozen-screen Escape copy-mode it provides is parity with the harness tab rather than anything the agent tab has, so it is out of scope, and `useDefaultContextMenu`'s Escape path works from the registration alone (`:104`).

**`StatusPanels` takes its rows, not the tab.** It currently reads `tab.connections` and `tab.schedule` off a `TabView` (`web/src/shared/status-windows/StatusPanels.tsx:66`), which a plugin does not have. Its two row lists become explicit props and every existing caller passes `tab.connections` and `tab.schedule`. `useStatusWindows`'s `hasConnections`/`hasSchedule` arguments go with them: `StatusPanels` already gates on `connectionRows.length > 0` internally (`:68`), so the caller's flag is the same test stated twice, and dropping it leaves the hook with nothing but the identity it re-arms on. This is the one place the change is not purely additive, and it is a shared component's signature rather than anything the plugin API versions, so `TAB_PLUGIN_API_VERSION` is unaffected.

**A `chords` field on `TabPluginDeclaration`.** An optional list of canonical chord ids in the shape `APP_CHORDS` uses, which the plugin claims while one of its tabs is visible. `validateDeclaration` (`src/plugins/activate.ts`) refuses a malformed id at activation, beside the checks that already refuse an unmatched claim — a typo would otherwise be a claim that can never fire.

The claim rides the tab's **wire view**: `PluginTabView` gains an optional `chords`, read from the host's own declaration when the view is built and omitted when the claim is empty, so a plugin that claims none costs no bytes on every state broadcast. A client keeping its own copy of the claim would be a second place for it to drift from the declaration the host actually enforces.

The handler is supplied through a published `usePluginChordClaims` hook backed by a registry on `PluginHost`. The hook registers while `capabilities.active` and releases when it is not, which is the whole of the precedence rule — a claim exists exactly while the tab the user is looking at is on screen — and `handleChordKeys` consults the registry **before** the application's own table (`web/src/useWindowKeys.ts:188`, `:190`) rather than after.

That inverts the rule the existing comment states — "a plugin's chord is consulted after all of them, so a core chord always wins" (`:180`) — and the inversion is deliberate: the overlay-plugin family cannot fire without the core chord, but a visible plugin tab is a surface the user is looking at, and a chord that silently did nothing there would be worse than one that works. The overlay path at `:193` keeps its position, so the two plugin families stay distinct. A declaration claiming a chord whose body never answers falls through to the application unchanged, which is what makes an inert claim harmless rather than a swallowed key.

**The manifest.** `src/plugins/shell/manifest.ts` declaring id `shell`, version `1.0.0`, `apiVersion` 1, `payloadSchemaVersion` 1, `tabLabelPrefix` `shell`, `command` `zsh`, `chords: ['ctrl+r']`, `hostState: ['connections', 'schedule']`, no file extensions, and capabilities `originTab`, `dispatchLine`, `completeLine`, `openOrFocusTab`, `updateTab`, `rejectRequest`, `reportFailure`. Registered in `src/plugins/catalog.ts` and `src/plugins/loaders.ts`; the client entry and its schema literal go into **both** maps in `web/src/plugins/registry.tsx` and into the pinning list in `web/src/plugins/registry.test.tsx:15`.

**The payload.** `src/plugins/shell/shared.ts` exports `SHELL_PAYLOAD_SCHEMA_VERSION`, a payload carrying the pty id, the working directory as displayed, whether it is a workspace, the spawn size, and the two pushed row lists, plus the guards for the payload and the intent request shape. The module imports nothing, because the client executes these guards through `@shared` and an import could pull NodeNext resolution into the browser graph. That is also why the two row types are re-declared rather than imported from `@shared/protocol` — the pattern `src/plugins/sessions/shared.ts` already follows for `RemoteSessionView`, with `shared.test.ts` pinning the two against each other.

**Activation.** `src/plugins/shell/activate.ts` exports `activate()` with `isPayload`, the command handler and an intent table. The command handler asks `originTab` for the issuing tab, generates an instance key unique to the invocation, and calls `openOrFocusTab` with a factory that calls `spawnTerminal` and returns the payload carrying the id — so two `zsh` commands produce two tabs, and `openPluginTab`'s existing "an instance key already open is focused instead" behaviour (`src/tab/openers.ts:64`) is never reached because the key is always fresh. A bare `zsh` with no argument is the whole grammar; there is no path form. `opener.inline` and `opener.external` both refuse through `noFileOpener('shell')`.

The only intent is a status question the client asks on mount, so a tab whose shell died while no browser was attached closes itself rather than waiting for input that can never arrive. `attachTerminal`'s `onExit` covers the live case; this covers the reconnect. An unknown intent name or a malformed payload is a `rejectRequest`; a payload failing the plugin's own guard is a `reportFailure`.

**The client.** `web/src/plugins/shell/` holds the lazy entry, `ShellTab.tsx` for the body, `useShellTerminal.ts` for the xterm setup, `command-line-rules.ts` for the bar's pure input decisions, `ShellHistoryPopup.tsx` for the `Ctrl+R` list, and `shell.css`. The terminal is built on the published `terminalColors()` with `FitAddon` imported directly from `@xterm/addon-fit` (already a dependency, `package.json:144`), attached through `attachTerminal`, and registered with the selection bridge so a right-click over the screen offers the application's own **Copy**. It is created with **stdin disabled** and no blinking caret: the command bar keeps focus, so a focused caret here would be a second place that looks typeable and is not. The hook owns the single attachment and hands back a `write`, so resizing and typing go out through one subscription rather than two.

The metadata row is the plugin's own markup over the same class names, with the host-rendered `splitAction`, the two capability-backed buttons, and the published status windows. The bar composes the published `CommandBarShell` and `useCommandBarKeys`, and adds three things on top: the `!` prefix and the dispatch-or-send decision, the shell control keys, and the completion strip fed through the `complete` intent.

**Files and folders.** Every new module stays under 200 lines by extraction rather than compaction. The bar's input rules — the `!` prefix, the control keys, the history walk — are pure functions in `command-line-rules.ts` so they are testable without a render; the terminal setup is a hook; the body is markup. Two new host modules exist purely because their hosts were already at the limit: `src/plugins/host-state.ts` because `host.ts` had no room for the second subscription's policy, and `src/plugins/host-channels.ts` because `host.ts` passed 200 on the first.

Two existing files were close enough to plan for rather than discover: `src/pseudoterminal-manager.ts` is 228 raw lines and gained the launch bag, `adopt` and `isRunning`, and `src/tab/openers.ts` is 152 and gained the id threading. Both stayed inside `max-lines`; had either not, the launch-bag normalisation was the piece to extract first, being the one with a clean seam of its own.

**Ordering.** Land the contract first — the tab resource, the four server capabilities, the three client ones, the published surfaces, the `StatusPanels` props change, the `hostState` push and its handler, and the `chords` field with its window-key consult — so the plugin has something to compile against. Then the plugin's server files, then its client files, then the registry entries and the documentation the contract change forces. The client capability type lives in the web project, so its addition lands with the client files rather than with the server ones.

**Docs this change forces.** `documentation/developer-documentation/tab-plugins.md` gains a bullet per new capability, a section on `spawnTerminal` as a resource rather than a capability, and the two new declaration fields; its count sentence changes from eighteen to twenty-two, and its changelog line changes from "Eighteen server and eight client capabilities." to "Twenty-two server and twelve client capabilities.", recording the additive v1 change. `COUNT_WORDS` in `src/plugins/documentation.test.ts:15` stops at `eighteen` and must be extended to reach `twenty-two`, and the test's hand-maintained client literal `'eight'` at `:51` becomes `'twelve'` — the test says itself that the client count is a literal because the server cannot import the web capability object. `product/specs/tab-plugins.md` gains the status-window publication, the `hostState` push channel and its delivery rules, the chord claim and its precedence inversion, and a bundled-shell-plugin section. A new `product/specs/shell-tab.md` describes the tab itself, with `product/specs/shell.md` and `product/specs/tabs.md` cross-referencing it so a reader arriving from either finds it.

`help.md` gains a `zsh` row in the **Commands** table describing what the tab is and that `!` forces the shell, and three rows in the **Key Bindings** table for the shell tab's own bindings — `Ctrl+R` for its own history, `Ctrl+C`/`Ctrl+D`/`Ctrl+Z` for interrupt, end-of-input and suspend — noting that the last three apply while the shell tab's command bar has focus. A binding documented without its scope would be wrong in every other tab, which is why the scope is part of the row.

## Out of scope

- **A new tab `view` discriminant.** The tab is `view: 'plugin'` like every other bundled plugin tab; `src/tab/types.ts:257` gains nothing.
- **A new wire protocol for terminal bytes.** The existing `pty` event and the `ptyInput`, `ptyResize` and `ptyKill` RPCs carry them. `src/protocol/events.ts` and `src/protocol/core-rpc.ts` gain nothing.
- **Changing what `shell` means.** The bare `shell` route stays core. The plugin claims `zsh` and nothing about the existing route moves.
- **Replacing PTY takeover.** `product/specs/shell.md` § Interactive PTY takeover and `web/src/ShellTab.tsx` keep working exactly as they do. This is a separate surface beside it, not a replacement for the transient mode on an agent tab.
- **Typing into the terminal directly.** No click-to-type, no `disableStdin`, no path into zsh that bypasses the command bar.
- **A restart affordance.** The tab closes when the shell exits. There is no exited state and no button to start a fresh shell in the same tab.
- **Recording, relaunch and persistence.** `plugins/live-recordings.ts` filters on `!tab.harness`; a plugin tab is live and in-memory by the existing rule; `--relaunch` does not restore one.
- **A path argument.** `zsh` takes no argument. The working directory follows the issuing tab's workspace, and that is the whole grammar.
- **Escape copy-mode.** The frozen-screen selection overlay the harness and takeover terminals raise on Escape is not published to plugins. Selecting with the pointer and copying from the context menu is the whole of "same menus" here, and the agent tab has no copy mode to be identical to.
- **A shell-selection command.** There is no `select`-style verb, no pipe into another tab, and no way to send a command to another shell tab.
- **Giving the plugin its own `TabView`.** The status windows need two row arrays, not the whole host tab shape.
- **A second definition of the metadata row.** The plugin's row is a copy on purpose. Replacing it with the host's component is the obvious future move and is not made here.

### Declined during gap research

These came out of comparing the planned tab against the mature products for this capability, and each is recorded so a later pass does not raise it again.

- **Keeping the tab after the shell exits.** Zellij's default is the opposite of this plan's: a command pane is held open when its command exits, showing the exit status and offering `Enter` to rerun, with `close_on_exit` as the opt-in (`zellij.dev/documentation/creating-a-layout.html`). tmux has `remain-on-exit` with `respawn-pane` for the same reason (`man7.org/linux/man-pages/man1/tmux.1.html`). Declined; the tab closes on exit.
- **A tab name and metadata row that follow the shell's directory.** Windows Terminal takes the tab title from the shell's title, which on Ubuntu's bash is `user@machine:path`, so `cd` moves it, and it ships `suppressApplicationTitle` as the documented opt-out plus a "set the console title to your current working directory" recipe (`learn.microsoft.com/en-us/windows/terminal/tutorials/tab-title`). Declined; the row shows the directory the tab started in.
- **`zsh <path>`.** Windows Terminal's `new-tab` takes `--startingDirectory`/`-d` and every profile has one (`learn.microsoft.com/en-us/windows/terminal/command-line-arguments`). Declined; `zsh` takes no argument.
- **A guard on a multi-line paste.** iTerm2 ships "Warn before pasting when not at shell prompt?", a character-count confirmation threshold, and a family of "Suppress warning about multi-line paste" toggles (`iterm2.com/documentation-preferences-advanced.html`). Declined; a paste becomes one editable line.
- **Rectangular block selection.** iTerm2 has a `BOX` selection mode (`iterm2.com/3.4/documentation-smart-selection.html`) and WezTerm's `SetSelectionMode` takes `Block` (`wezterm.org/config/lua/keyassignment/CopyMode/SetSelectionMode.html`). Declined — and narrower than it looks: xterm.js already routes a double-click to its word handler and a triple-click to its line handler, so the only missing mode is the rectangle, which no public xterm.js API offers. Block selection is a separate piece of work for every terminal surface at once, not part of a first shell tab.

## Open questions

None. Every decision this plan carried is settled above and each traces to a user answer: the plugin owns its chrome and its metadata-row markup; `zsh` opens a `shell` tab; always zsh, fully interactive, rc files loading; the terminal replaces the transcript; the workspace then the project root; `!` forces the shell and an application command otherwise, with the collision accepted silently; the bar recalls the shell's own sent lines and `Ctrl+R` lists them through a declared chord claim; completion is the application's; the row drops the transcript button; the connections and schedule windows are the host's own, with their rows pushed only when they change; one tab per invocation, closed when the shell exits; the terminal is never focused; the app's chords are unchanged and `Ctrl+C`, `Ctrl+D` and `Ctrl+Z` reach zsh; a paste is editable text; a static dot and no busy state; and the tab resource, the three server capabilities, the three client capabilities, the `chords` claim and the `hostState` claim are the shapes the contract grows.
