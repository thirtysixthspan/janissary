Piece 7.3 adds the `agent` kind; subplans 8 and 10–14 build on both.

The loop's gate decides, for each command an agent emits, whether it may run and on which side. Today that is `toolRunner` in `src/acp/tool-table.ts`, which re-reads live settings on every call through `Managers` (`effectiveCommandSetting(managers.nativeCommandSettings?.current(), row.name)`), and the far side cannot load `Managers`. This piece adds the plain-data snapshot a core prompt will carry and a pure `gateCommand` that decides from that snapshot alone. Both are additive: `toolRunner` keeps serving the loop until subplan 8 switches `runCorePrompt` to the gate.

## Design decisions

- **`AcpRunSnapshot`** lives in `src/acp/types.ts`, beside `AcpLoopDeps`. It is a discriminated union on a `kind` field of plain JSON-safe data (strings, booleans, arrays, plain objects; no functions, `Map`s, or `undefined`-valued fields), so subplan 14 can validate and send it unchanged. Arrays are typed `readonly`. In this piece the union has its one `core` member (`kind: 'core'`); piece 7.3 adds the `agent` member (`kind: 'agent'`), making it the source plan's two-member union.
  - **Shape that keeps 7.3 additive.** Declare `AcpRunSnapshot` in the leading-`|` style of `AcpPromptResult` (`src/acp/types.ts:27`, `export type AcpPromptResult =`), with the `core` member written as an inline object type after a leading `|`. Piece 7.3 then appends one `| { kind: 'agent'; … }` member and touches nothing else in the type. Do not export a separate named core-member type (nothing outside `tool-table.ts` would import it, and knip flags unused exports); where `tool-table.ts` needs the core member alone it writes `Extract<AcpRunSnapshot, { kind: 'core' }>`.
  - `core`: `kind: 'core'`, `role` (typed `AcpRole` — today `'ask' | 'tell'` — imported as a type from `./role.js`; `runCorePrompt` has it as `request.role`), `roleName` (string; the role name `runCorePrompt` passes to `toolRunner` today, `request.roleName` in `src/acp/run-prompt.ts`), `grants` (`readonly string[]`; the role's native command grants, `request.commands`), `rows` (`readonly AcpRunSnapshotRow[]`), and `withoutTools` (boolean; today's source is `runtime.acpWithoutTools === true` in `runCorePrompt`).
  - `rows` is an array of the exported row type `AcpRunSnapshotRow`: `{ name: string; effectiveEnabled: boolean; effectiveAgentAccess: boolean }`, all required. `name` is the **native vocabulary name** — `file read`, `db sqlite query` — never the command registry name `file` or `db`. Its two booleans mirror `EffectiveCommandSetting` (`src/native-commands/policy.ts:5`) field for field, but `types.ts` does not import that type.
  - A core grant is a native name (`file read`); the agent grant vocabulary in piece 7.3 is a registry name (`file`, source decision 22). The gate never translates between them.
- **`gateCommand(snapshot, tools, command)`** is exported from `src/acp/tool-table.ts`. It takes an `AcpRunSnapshot`, a `readonly AcpTool[]`, and the extracted command string, and is pure: no `Managers`, no notification, no I/O, no mutation of its inputs. It returns the exported union `AcpGateDecision` (declared in `tool-table.ts`, beside `gateCommand`), which is either `{ runsOn }` naming the side (typed `AcpTool['runsOn']`, not a new alias), or `{ refusal, refused? }`, where `refusal` is the exact tool-result text (string) and `refused?: 'disabled'` marks a disabled or agent-off refusal. When a refusal is not a disabled one the `refused` key is omitted entirely, never set to `undefined` (the decision is JSON-safe like the snapshot). Its decision logic lives in a module-private core helper named `gateCoreCommand`, with the same `(snapshot, tools, command)` parameters but its snapshot typed `Extract<AcpRunSnapshot, { kind: 'core' }>`, so piece 7.3 can add a second helper for the `agent` kind and turn `gateCommand` into a dispatch on `snapshot.kind`, keeping each function well under the `sonarjs/cognitive-complexity` limit. Decision for this piece: `gateCommand`'s body is a single call to `gateCoreCommand(snapshot, tools, command)` with no `kind` check (with one member the union is assignable to the `Extract` type, and a check on it would be dead code); no `agent` handling, placeholder, or `never` branch exists until 7.3 adds the dispatch.
- **Core order** (source decision 6, today's `toolRunner` order at `src/acp/tool-table.ts`, `export function toolRunner`):
  1. A command whose `nativeCommandName(command)` is undefined, or that no entry of `tools` claims with `match(command)` (tested against the command as given, first match wins, as `toolRunner` does), throws `new Error('No ACP tool matched command: <command>')`. It throws rather than refusing, so the loop's catch (`runAcpToolLoop` in `src/acp/loop.ts`, `h.error(errorText(error))` around `dependencies.runCommand(command)`) turns it into the `error` event as today. The native-name check runs first, so `select 1` throws even though a real table's database entry (`match: () => true`) would claim it.
  2. The row is `snapshot.rows.find((row) => row.name === native)`. A row with `effectiveEnabled` false or `effectiveAgentAccess` false refuses with `Command is disabled: <native>.` and `refused: 'disabled'`. Both cases share that one text today: `disabledCommandMessage` in `src/native-commands/dispatch-policy.ts` (reached through `refuseDisabledCommand`) returns `` `Command is disabled: ${row.name}.` ``, and `toolRunner`'s agent-access branch builds the same `` `Command is disabled: ${row.name}.` ``. This is checked before the grant, so a disabled command the role did not grant still reports the disabled refusal.
  3. A native name missing from `snapshot.grants` refuses with `Command not allowed for role "<roleName>": <native>.` and no `refused` field.
  4. Anything else returns `{ runsOn: tool.runsOn }` for the matched tool.

  A native command with no snapshot row is allowed, matching today's "missing settings manager or setting row allows the command" (`effectiveCommandSetting` defaults both fields to true). `withoutTools` is not consulted by the gate: the driver builds an empty tool list for such a snapshot (subplans 8 and 10), and with no tools every command throws at step 1.
- **Why `<native>` is the right row and refusal name.** Today `toolRunner` resolves `resolveApplicationCommand(native)` and uses its `name`. For every native command that row is the native row itself, whose name is its fixed form (`rows.push({ name, kind: 'native', …` in `src/application-commands.ts`); `src/application-commands.test.ts` pins this for `browser goto`, `db sqlite query`, `question ask`, `question approve`, and `file read` (case "lists the file command as a parentless builtin while the native row owns file read input"). So the gate looks rows up by native name straight from the snapshot and refuses with the native name, and the gate's code imports neither `src/native-commands/policy.ts` nor `src/application-commands.ts`, which would drag the command registry into the far side. Those two imports, `Managers`, `dispatch-policy.js`, notifications, and the invocation context stay in `tool-table.ts` only because `toolRunner` and `dispatchNative` still use them; subplan 8 deletes them with `toolRunner`.
- **Notification is the caller's job.** `toolRunner` calls `notify(managers, 'command-disabled', label, message)` on a disabled refusal (directly, or inside `refuseDisabledCommand`). The pure gate cannot; it marks the refusal `refused: 'disabled'` instead, and the caller raises the notification with the refusal text (subplan 8 in `runCorePrompt`, then subplan 11 in the driver's `ranCommand`). One deliberate tightening: today, when `effectiveEnabled` is false but `refuseDisabledCommand` finds no command or row and returns undefined, `toolRunner` falls through to the agent-access and grant checks; the gate always refuses a row with `effectiveEnabled` false. No native command reaches that fall-through today, so nothing observable changes.
- **The snapshot is the authority** (source decision 4). The gate never reads live settings. Building the core snapshot once per prompt is subplan 8's job.

## Tests

`src/acp/tool-table.test.ts` (test files are exempt from `max-lines`). Add `gateCommand` to the existing `import { createAcpToolTable, toolPrimer, toolRunner, toolExtractor } from './tool-table.js'` line, and import the `AcpTool` and `AcpRunSnapshot` types as needed. Do not use the file's `setup()` helper or `settingsWith` — the gate needs no `Managers` or settings files. Build core snapshots and a hand-built tool list inline, typed as `AcpTool[]`: one `caller` tool whose `match` is `/^browser\b/i`, and one `workspace` tool whose `match` is `/^db\b/i` — the gate only reads `match` and `runsOn`, and each literal also supplies a stub `primer`, `run`, and `isCommandLine` because `AcpTool` still requires them here. A small local factory for a core snapshot with overridable `grants`, `rows`, and `roleName` (defaults: `role: 'ask'`, `roleName: 'ask'`, `withoutTools: false`) keeps the cases short. Assert decisions with `toStrictEqual`, which, unlike `toEqual`, fails on a `refused: undefined` key. Add a `describe('gateCommand')` block after `describe('toolRunner')` (piece 7.3 adds its agent cases to the same block):

- core kind:
  - `select 1` (no native name) and `question ask "x"` (native, but no tool in the list claims it) each throw `No ACP tool matched command: <command>`;
  - a row `{ name: 'db sqlite query', effectiveEnabled: false, effectiveAgentAccess: true }` refuses `Command is disabled: db sqlite query.` with `refused: 'disabled'`;
  - `effectiveAgentAccess` false with `effectiveEnabled` true gives the same refusal and flag;
  - a disabled command missing from `grants` reports the disabled refusal, not the not-allowed one;
  - an enabled `browser goto https://x` missing from `grants`, with `roleName: 'researcher'`, strictly equals `{ refusal: 'Command not allowed for role "researcher": browser goto.' }` (no `refused` key);
  - with `rows: []`, a granted `browser goto https://x` strictly equals `{ runsOn: 'caller' }` and a granted `db sqlite query select 1` strictly equals `{ runsOn: 'workspace' }` — this covers "no row allows" and shows the gate returns the matched tool's own side; a row with both booleans true for the granted command gives the same result;
- purity: calling the gate twice with one deep-frozen core snapshot (`Object.freeze` on the snapshot, its arrays, and rows) returns equal results and does not throw. Piece 7.3 extends this case to a frozen agent snapshot.
