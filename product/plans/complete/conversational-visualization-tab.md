# A visualization tab that is a conversation, and holds more than one chart

**Complexity: 9/10** — a rework of a first-of-its-kind surface on both sides at once: a rewritten wire contract and stored record, a new four-step transformation vocabulary with its own expression parser, a widened agent that may run tools, several charts each owning its own timers and controls, and four client components deleted beside four added. No new dependency and no new host API version; what makes it a 9 is the number of places the single-chart assumption was load-bearing.

Starting from the work in pull request 1440.

## Summary

The visualization tab shipped in #1440 as a form: a metadata row of dropdowns, a column-type review, a sequence of questions the model asked one at a time with one-click suggestions, and exactly one chart at the bottom. The source had to be known before the tab opened, and the tab's own controls decided what the chart did. This change inverts that. A new visualization tab opens as a conversation with nothing in it but a chat and a prompt to name a source; the agent works out how to reach the data itself — including when the source is a web page describing an API rather than a file of values — asks the user what to see in the same chat, draws a chart, and then keeps answering. The tab carries no dropdowns at all: the chat is its only control, the only things that can change a chart are sentences typed into it, and the export and live-update controls belong to the individual charts rather than to the tab. A visualization can hold several charts, and the data behind them can be filtered, sorted, limited, and extended by asking.

## Design decisions established by the feature description

**A new visualization tab is a conversation, not a form.** The description fixes this without ambiguity: "when a conversation tab is created, the chat interface opens without a graph. the user is prompted to provide a web or file URL". So the tab has no pre-entered source, no column review, and no question sequence. It shows one line asking for a URL, and a composer. Everything else arrives through the exchange.

**The source may be a file of values or a page that describes an API.** The description says so twice: "could either go to a static file or web page that describes an API", and "the job of the agent is to figure out how to mechanically access the desired data". The second sentence settles the mechanism. A host that can only fetch a URL and parse it cannot "figure out how to mechanically access" anything; an agent that can run commands can read an OpenAPI document, work out the request it describes, follow pagination, apply a header the documentation mentions, and reshape the result. So the agent gets tools, and the host's job becomes reading what the agent produced and drawing it.

**The chat is the only control, and the charts own the rest.** "No drop downs or other controls except the chat interface should be present in the visualization tab", with one carve-out the description itself makes: "export and live update options should be attached to individual graphs and not be part of the metadata bar". So the metadata row keeps only what is not a control — the name and the source, as text — and each chart carries its own export and live-update controls.

**The chat may suggest changes as clickable buttons.** "the chat may suggest changes via clickable buttons similar to those currently generated". #1440 already produces that row (`followUps`, rendered by `VisualizationChat.tsx` as `.visualization-suggestion` buttons above the composer). It survives unchanged, and it now appears under *every* reply rather than only under a reply that changed a chart, because a reply that only asks a question is exactly the reply a suggestion belongs under.

**The chat modifies both the chart and the data.** "the chat should be able to modify the details of the visualization and the data" and "the user should be able to ask for transformations of the data in the chat". So the reply contract covers the chart's kind, columns, series, aggregate, title and axis labels, and separately the data: which source a chart is drawn from, and a list of transformations applied to it before the marks are built.

**More than one chart.** "the user should be able to produce more than a single graph". A visualization therefore holds a list of charts, and the model can add, replace, and remove them in one reply.

## Autonomous decisions

This run executes `ai/tasks/plan-a-new-feature.md` unattended under `ai/tasks/auto-build.md`, so every question its phases would have put to a user is answered here instead. Each answer is recorded with the evidence it rests on, in the order the decision policy resolves them: the supplied description first, then the binding project instructions and guidelines, then the relevant specs, then verified behavior in this repository. No answer below claims a user approved it.

**Primary flow.** A new visualization tab opens empty. It shows one line — "Paste the URL of a data file, or of a page that describes an API, and tell me what you would like to see." — above the composer. The user pastes a URL and, if they like, a sentence about what they want. That is the whole of the entry. Two secondary routes survive from #1440 because they cost almost nothing and lose nothing: the index's plus control creates a blank visualization the same way, and **Visualize this** in the default context menu creates one and sends the selection as its first message, so selecting a URL anywhere in the application and choosing the menu entry is still the cheapest route in. The context-menu entry is kept rather than dropped because the description does not ask for its removal, and because the feature's own framing — the chat is the interface — is satisfied by a first message rather than by a form field.

**Edge cases.** Each is decided against existing behavior rather than left open.

- *The source cannot be read.* Recorded as an error on the source and shown in the chat's error line, the way a failed conversation turn is (`src/conversations/responder.ts`, `fail`). The plugin is not disabled: a bad URL is a domain outcome, and `reportFailure` is reserved for a broken plugin.
- *The source is a page, not a table.* Not a failure. The host fetches the page, finds it is not a table, stores the document text, and tells the model so; the model is the one who has to turn it into data. This is the API case working as designed, not an error path.
- *The model cannot get the data either.* It answers in prose. The chat shows what it said, there is no chart, and the tab keeps working.
- *The model names a column the data does not have, or a measure that is not numeric, or a transformation over a column that is not there.* That chart is refused, named in the chat beneath the model's own words, and the other charts in the same reply still apply. One bad chart in a reply of four costs one chart.
- *The model names a data file it did not write, or one outside its own workspace.* Refused. A file path is resolved against the visualization's workspace and must land inside it, the same way `fetch.ts:63`'s `insideRoots` resolves a local path against the source roots before reading it.
- *The tab is closed mid-reply.* The in-flight call is dropped and the session killed, the way `VisualizationsManager.releaseClosed` already cancels a closed tab's call. The record and its turns survive, so reopening resumes.
- *The visualization is deleted from the index while its tab is open.* The tab stays open, saying it was deleted, with its composer disabled. This is the resolution `product/specs/conversations.md` already records for the same situation.
- *A re-read fails during live update.* The previous table stays on screen and the reason is recorded beside the chart. Clearing a working chart because one read failed is the wrong trade, and #1440's spec already says so.
- *A user message with no URL in it, before there is any data.* Still sent to the model. The prompt's data section says there is no source yet and asks the model to say what it needs, so the first exchange is a real turn rather than a canned line — and the tab's own prompt line is the cheap path to the same place. The model is called for **every** message, including one whose only content is an address `parseSource` refused; the prompt carries the refusal and its reason rather than the host swallowing the line.
- *A user message with a second URL in it.* The URL becomes the visualization's source — the most recent one wins, so the metadata row always shows what the charts most likely came from — and is read before the model is called, so the model is asked with the data in hand rather than being told to go and get it. The source it replaces is kept if a chart still draws from it, because a file the agent acquired is a dataset in its own right.
- *Two visualizations, or two charts, wanting the same data.* Two visualizations are separate records, as today. Two charts in one visualization share a source by naming it, and each chart's resolved table is what reaches the wire.

**Scope boundary.** Everything the description asks for is in: the chat-only tab, the URL prompt, the agent's mechanical data access including the API case, questions asked in the chat, the chart, the follow-up exchange, the clickable suggestions, chart and data modification, data transformations, several charts, and per-chart export and live update. What leaves is listed in "Out of scope" with the reason for each. Three deserve to be named here. The **model picker** goes because it is a dropdown and the description forbids dropdowns; a visualization now uses the first pair `availableConversationModels()` offers, and the model is still the same ACP channel conversations uses. The **column-type review** goes because it was a form — a per-column dropdown gating the interview — and the model can now declare a column's type in its reply and the user can correct it by asking, which is the control surface the description asks for. The **chart's Order, Show, and Only dropdowns** go because they are dropdowns; what they did survives as two of the four transformations, so nothing is lost but the control.

**Naming and wording.** Fixed exactly, in the application's existing voice.

- the command stays `visualizations`, and the index's empty state stays `No visualizations yet`;
- a title lookup miss stays `No visualization matching "<title>".`;
- the context-menu entry stays `Visualize this`;
- the prompt line above an empty composer is "Paste the URL of a data file, or of a page that describes an API, and tell me what you would like to see.";
- the composer's accessible name is "Ask about the data or the chart";
- a deleted visualization still says "This visualization was deleted.";
- a chart's live-update control is a single button whose tooltip states the current interval and the one a click moves to, beginning "Live update is off — click for every 10 seconds";
- the per-chart export tooltips are "Export this chart as PNG" and "Export this chart as PDF", and the re-read tooltip is "Read the data now";
- a chart's caption keeps #1440's shape — `showing <n> of <total> rows`, `<aggregate> of <y>`, `read <time>` — and adds the transformations it applied after the aggregate, in the order they were applied;
- a chart drawing from a file the agent acquired says so, so a picture is never mistaken for a live feed.

**Implementation decisions.** All four of `2b`'s checks are "yes": this extends a subsystem rather than adding one, it changes the wire shapes and the topic action union, it keeps the timer and streaming paths, and there is no precedent for a chat that is also a chart surface. So the implementation questions were worked too, and each is a decision below rather than an open choice: the domain stays host-owned behind the `visualizations` topic because the plugin import boundary forbids the plugin from reaching ACP or the filesystem at all; the agent's tools arrive through the existing ACP permission seam rather than a new one; the transform vocabulary lives on the server so the client stays a projection; and the work lands in ordered checkpoints that each leave typecheck and tests green.

## Deliberate ceilings

Five corners this plan cuts on purpose, each named so it reads as a decision rather than as an oversight, with the path off it.

- **A visualization's payload is one bounded table per chart, so charts sharing a source pay for it twice.** The bound is the existing 500-row, 32-column cap, and the ceiling is 8 charts. The fix is the delta-and-sequence transport `architecture-principles.md` §8 names, which is an architecture change well outside this feature — the same trade #1440's plan made and recorded for a single table.
- **Live update on a chart the agent acquired is a model call.** A chart on the source is an HTTP fetch and a parse, and paying a model for that would be the wrong trade. A chart on a file is re-asked, which is why the intervals stay the fixed five choices rather than becoming a number, and why the caption says the file is the source. The cheaper path, when it matters, is for the agent to name a plain URL as the chart's data.
- **The prompt carries the last 12 turns, not the whole conversation.** A very long exchange therefore loses its early turns from what the model is asked, though the tab still shows all of them. The upgrade path is a summary of the dropped turns, which is a prompt change and nothing else.
- **A derived column is re-evaluated per row on every resolution.** At 500 rows that is nothing, and it is the reason `derive` needs no cache and no incremental state.
- **A chart is a specification over one table, never a query.** Grouping, pivoting and joins are reachable today by asking the agent to acquire and reshape the data itself, which is the mechanism this feature is built on; expressing them in the host would be a second mechanism for the same job.

## Proposed changes

**Checkpoint 1 — the agent may use tools, and no dependency is added.**

The agent in a visualization has to run commands; nothing else in this change is possible without it. The seam already exists: `connectAcp` asks `decidePermission` about every tool request, and denies unless the caller opted something in (`src/acp/index.ts:69`). `decidePermission` gains one branch ahead of the web-tool classification: a caller that asks for every tool permitted takes the least-privilege allow option, which is the `allow_once` the function already prefers and falls back from. The web-tool path is untouched, so the monitor persona's behaviour is unchanged and its tests keep passing. `AcpOptions` and `AcpSessionPoolHooks` carry that request and the pool passes it into `connectAcp` for the sessions it opens. Conversations opens its sessions without it and stays tool-less, exactly as today.

`package.json` gains nothing, and that matters more here than it did for #1440. The chart is still hand-written SVG, the PDF is still written here, and the one genuinely new piece of computation — the `derive` expression — is a small recursive-descent parser rather than an expression library, because a feature whose appeal is that nothing a model produced ever runs should not add a parser someone else's model wrote.

The widening is real and the spec will say so plainly: a visualization's agent can run commands inside its own workspace, with network access and with reads the Seatbelt profile already allows. That reach is no wider than what the host already grants when it fetches a URL the user pasted, and the profile denies `$HOME` contents and secrets last, so the agent cannot read a credential file the host's own fetch could not have read either. What changes is that the commands are the model's, and the user's own chat message is the only thing that starts them.

**Checkpoint 2 — the grammar of a chart, in one place.**

`src/visualizations/chart-spec.ts` becomes the one definition of what a chart specification may say, because three places need it and three copies is three ways to disagree about what a stored chart means: the store's record guard, the reply parser, and the validator. It already owns `AGGREGATES` and `isAggregate`; it gains `isDataRef`, `isTransform`, and `isChartSpec` — the guards for a chart's data reference, each of its transformation steps, and the chart itself — and keeps `validateChart`, which now runs against the *resolved* table rather than the raw one. Two of the three consumers being moved rather than written is what makes room: `store.ts` and `prompts.ts` each drop their own copies.

The four transformations are exactly these, and no others. `filter` keeps rows where a column compares equal, not equal, greater, greater-or-equal, less, or less-or-equal (`eq`, `ne`, `gt`, `gte`, `lt`, `lte`), contains a substring, or is one of several values (`in`). The value is compared in the column's own type — numerically for a number, as an instant for a date, as a string for text, against a boolean for a boolean — and a value of the wrong shape for the column is refused by name rather than coerced, the same way an unknown aggregate is. `derive` adds one numeric column computed from an arithmetic expression over the existing columns and is appended after them, leaving every other column untouched. `sort` orders rows by one column in one direction, in that column's own type's natural order, with the source order as the tiebreak so a chart is reproducible. `limit` keeps the rows of the first *n* **distinct values of the chart's own x column**, in the order the preceding `sort` left them, and drops every row of the rest.

That last rule is counted in categories rather than in rows on purpose, and it is the rule #1440's spec already records for its **Show** control: a cap counted in rows would drop some of a category's series and leave the rest, which is a chart with a bar of a different height than its neighbour and nothing to explain it. Counting in categories costs the vocabulary nothing, because `resolve` is handed the chart and already knows its `x`. A `sort` followed by a `limit` is therefore a top-N and the reverse a first-N — an ordered list, not a set of settings. A transformation naming a column the table does not have is refused at the gate rather than silently doing nothing, and the steps are applied in order, each validated against the table the previous steps left.

`resolve(source, chart)` is the one function that carries a raw table plus a whole chart to the table that chart is drawn from, and it returns either that table or a reason. The manager calls it whenever a chart is created, a transformation changes, or data is re-read, and `validateChart` is its last step rather than a separate call a caller might forget. It caps the transformation list at **16 steps** and an `in` list at **32 values**, both named bounds for the same reason the row cap is: the payload is re-broadcast on every mutation.

**Checkpoint 3 — the expression behind `derive`.**

`src/visualizations/transform-expression.ts` is new and is a recursive-descent parser over a grammar deliberately that small: a number, a column name, `+`, `-`, `*`, `/`, unary minus, and parentheses. At each position the parser tries the **longest** column name the table has before it tries a number, which is what lets a column called `revenue per month` be written in an expression without quoting or escaping. No names, no calls, no property access, and no `eval` — `security/detect-eval-with-expression` is on for `src/` and this is exactly the place it was written for. A row whose arithmetic cannot be performed — a text where a number was needed, a division by zero — yields an empty cell rather than throwing, which is the same rule `chart/points.ts`'s `numeric` already follows for a measure that is not a number. A name the table does not have, a missing operand, an unbalanced parenthesis and a stray character are all refused by name, so the model is told what to fix rather than shown a chart that quietly omits the column.

**Checkpoint 4 — the wire shapes and the stored record.**

`src/protocol/visualizations.ts` is rewritten around two things instead of one. A **chart** gains an id, a data reference, its transformations, its own live-update interval, and its own resolved table; the five kinds, the columns, the aggregate, the title and the axis labels are unchanged, and `readAt` and `error` ride along as the chart's own view of its data. A **data reference** is either the visualization's own source or a file inside the agent's workspace, and a file's path is on the wire because the caption says which file produced the picture. The window drops `questions`, `pendingQuestionId`, `reviewed`, the tab-level `refreshSeconds`, and the single `chart`, and gains `charts`; `id`, `title`, `deleted`, `source`, `pair`, `turns`, `followUps`, `busy`, and `error` are unchanged. The questions, the review, and the tab-level interval go because the form they belonged to is gone.

There is deliberately **no dataset array on the wire.** A visualization's source and each distinct file path the agent produced are datasets, but they are a server-side concept: the record keeps a resolved table, a read time and a read error per dataset, and `view.ts` copies the two the chart needs onto the chart. A client that had to look a dataset up would carry a second identifier and a lookup that can fail; a chart that carries its own read state cannot. It is also what keeps the payload bound honest: the cost is one bounded table per *chart*, not per dataset, so two charts off one source pay for two tables and the ceiling is stated rather than deduplicated. The ceiling is **8 charts** per visualization, for that reason and no other; the real fix is the transport `architecture-principles.md` §8 names, which is outside this feature.

`src/visualizations/store.ts` follows the wire, with `VISUALIZATION_SCHEMA_VERSION` at 2. A record of version 1 is not migrated: the feature has never shipped, so there is no saved visualization to lose, and a migration would be a second shape to keep true for no user. The existing skip-and-warn scan reports a version-1 directory the way it reports a malformed one. The store's own file is at the ceiling — 199 counted lines — and the grammar move in Checkpoint 2 is what makes room, because its `isChart` copy and the store's record guard both go.

`src/plugins/visualizations/shared.ts` re-declares the new shapes and their guards, stays import-free, and its test pins them against the protocol types exactly as `shared.test.ts` already does — which is now also where the chart, data-reference and transformation guards are pinned against `chart-spec.ts`, so the two copies cannot drift. This file is also at the ceiling at 199 counted lines, and it gets there again: the change removes the question type and its guard, the column-type export, and five intent guards that no longer exist, which is about forty lines, and adds the three new guards, which is about thirty. `VISUALIZATIONS_PAYLOAD_SCHEMA_VERSION` becomes 2, which is a payload-meaning change and therefore the version that carries it; `TAB_PLUGIN_API_VERSION` stays at 1, because the declared capability set — `openOrFocusTab`, `updateTab`, `dockTab`, `topicData`, `topicAction`, `rejectRequest`, `reportFailure` — does not change, and `src/plugins/documentation.test.ts` keeps passing untouched. `web/src/plugins/registry.tsx:85`'s pinned literal moves to 2 with it.

**Checkpoint 5 — the conversation.**

`src/visualizations/prompts.ts` is rewritten and split, because the prompt builder and the reply parser are separable concerns and the file is at 169 counted lines with a larger job than it has now. `prompts.ts` keeps the prompt builders and the shared prose — the role framing, the reply contract, the transformation vocabulary, the follow-up rule — and a new `reply.ts` holds `parseReply` and the guards specific to a reply. `unwrap` and `parseJsonObject` move with the parser, because they are parsing.

The prompt carries: what the user is doing; the source and what it holds, with columns, types, row count and the first eight rows when a table was read, and the document text — capped at **20,000 characters**, well inside the eight-megabyte read bound — when the source is a page; the files the agent has already acquired, with what each parsed to; the charts as they stand; the exchange so far, capped at the last **12 turns**; the reply contract; the four transformations; and the workspace directory, because the agent has to write the data it acquires somewhere the host can read it. A second, much smaller prompt asks the agent to re-acquire the data behind one chart for a live update, names the file, and repeats the chart so the reply is the same specification.

The reply is one JSON object: `say` for the prose, `charts` for the charts to add or replace, `remove` for chart ids to drop, `name` for the visualization's name, and `followUps` for the suggestion row. A chart carrying an id **merges** over the chart it names, so "just change the title" is one field and nothing else moves; a chart whose id names no chart is added as a new chart keeping the id the model gave it, because a reply that asked for a chart and produced nothing is worse than one that made a new one. A chart without an id is a new chart and must be complete. `remove` naming an id that is not there is ignored. `parseReply` narrows through guards and never casts.

`src/visualizations/interview.ts` becomes `src/visualizations/agent.ts`, because "interview" named the form and the module's whole job changed. It keeps what was already right about it — one call in flight per visualization, chunks accumulated and read once rather than coalesced, a rate limit recognized through `isRateLimitError`, a failure recorded on the record with the session closed — and changes what the call is for: there is no opening call and no closing call, only `ask`, and a completion routes a reply to prose, to a merge of charts, or to both.

**Checkpoint 6 — reading, sources, and the per-chart timers.**

`src/visualizations/reading.ts` is rewritten to be keyed by dataset — the source, or a file path — because two charts may read one source through two live-update intervals and a read already in flight is dropped for the dataset, which is the same rule one level down. A read that succeeds stores the table, or the document when the body is not a table, plus the read time; a read that fails stores the reason and leaves the previous table, so a chart drawn from it survives. `src/visualizations/source.ts` gains one pure function: the first address in a line of text, which is how a URL inside a sentence becomes the source without a form field. It hands the line to the existing `parseSource`, so a `javascript:` line and a path outside the two roots are refused by exactly the reason they are refused everywhere else, and a refused address is reported to the model rather than swallowed.

`src/visualizations/refresh.ts` is rewritten to hold a timer per visualization whose next fire is the shortest interval across its charts, and to dispatch on what a chart draws from: a chart on the source re-reads it, and a chart on a file the agent acquired re-asks the agent to re-acquire it. The second is a model call on a timer, which is why the interval choices stay the fixed set #1440 chose — off, ten seconds, thirty seconds, a minute, five minutes — rather than becoming a number, and why the caption says a chart's data came from the agent: a user who sets an interval on such a chart is asking for a model call every interval, and the tab should not pretend otherwise. Nothing is read for a visualization with no tab open, which #1440's spec already promises and which is the reason the manager keeps dropping timers for closed tabs.

**Checkpoint 7 — the host domain and the topic.**

`src/visualizations/manager.ts` keeps its shape and its thin ends and changes what it forwards: `create` takes an optional first message and needs no source, `send` is the whole conversation, `cancel` still stops a stream, and the chart actions are `set-chart-refresh` and `refresh-chart`. `send` is asynchronous — it commits the turn, reads a new source if the message named one, and only then calls the model — and the tab is `busy` for the read as well as the call, so "working" covers the whole of it and a second message is refused throughout. Everything destructive or record-shaped that a tab could do to another record is still refused, and the grant is still exactly the list of things a tab showing one visualization could reasonably do to it.

This file is at exactly 200 counted lines today, so it is the one most likely to need an extraction rather than a trim. The rewrite is close to neutral in action count — eight actions go and five arrive — and the read sequence lives in `reading.ts` and the projection in `view.ts`, so the manager stays a forwarding surface. If it still exceeds the limit, the extraction is the chart-refresh dispatch, which belongs beside the timers in `refresh.ts` rather than in a switch here.

## Out of scope

- **A model picker in the tab.** The description forbids dropdowns, so the visualization uses the first catalogued pair. The ACP channel and the model catalog are untouched; only the control is gone.
- **Hand-renaming a visualization.** Renaming was a double-click on the name, which is a control. The chat can do it instead: a reply may carry a `name`, applied through the same trimming and cap as before, and a chart's title still names an untitled visualization exactly as it does today.
- **A column-type review form.** The model declares the types in its reply and the user corrects them by asking. The four declared types, and only those four, are still what the reader infers and the renderer branches on.
- **The chart's Order, Show and Only controls.** Their capability survives as `sort` and `limit`, and `filter` covers the category filter. Only the dropdowns are gone.
- **Streaming the agent's tool calls into the tab.** The tab shows that work is happening, and the model is asked to say in its own reply how it got the data, which puts the account where a reader expects it. Surfacing raw tool titles would mean a new hook in the ACP client and a new field on the window for something the reply already covers. The upgrade path is the `onTool` hook `PromptHandlers` would take.
- **A model call per live update on a chart that draws from the source.** That re-read is an HTTP fetch and a parse, and paying a model for it would be the wrong trade. Only a chart on agent-acquired data re-asks the agent, and the chart says which kind it is.
- **Grouping, pivoting, joining, or window functions in the transformation vocabulary.** Four steps that compose are what "transformations of the data" asks for; a query language is a different feature with its own parser, its own bounds and its own error surface.
- **Dragging a chart to reorder, resizing one, or splitting the tab into a chart pane.** The description asks for several graphs in one tab, which is a list.
- **Caching a dataset across two visualizations, or sharing one agent session between them.** Each record keeps its own workspace and its own session, which is the isolation the spec already promises.
- **Any change to the index tab beyond the source field becoming a plain plus control.** Its selection, empty state, two-click open, delete confirmation, and docking are the shared ones and stay.
