# Shell reply writers split and marker hooks
**Complexity: 3/10** — a mechanical hook extraction out of a file at 193 of 200 counted lines, plus two small contract additions on the writers (a return value and a row-marker callback); the care goes into which row a marker is taken on (the first row of its line, so it survives a resize in both directions) and the split head write, both checked against xterm's reflow code and pinned by tests, and every existing caller behaves exactly as before.

## Goal

Create room and a seam for the marker work. Move `displayReply` and `echoCommand` out of `web/src/plugins/shell/useShellTerminal.ts` into a new `useShellReplyWriters.ts`, with no change in behavior. Then give the two functions in `write-shell-reply.ts` the means to say what they wrote and to hand back a terminal row marker for the line they wrote, taken on a row that survives a window resize in both directions, so `06-marker-lifecycle` can attach markers to those rows. No caller uses the new return values or callbacks yet.

## Design decisions and dependencies

This subplan is client-only and depends on no earlier subplan. `06-marker-lifecycle` consumes everything defined here. It imports nothing from `04-marker-decoration` (already landed), but the marker row it chooses is written against what that decoration accepts: any row of the echo's logical line, from which `lastRowOf` in `thinking-marker-decoration.ts` walks forward over `isWrapped` rows to the line's last row, so the marker is still drawn after the last character on the line's last row.

Source plan requirements carried here: "Shell client changes" bullets on `write-shell-reply.ts` (`writeShellEcho` returns whether it wrote the echo; `writeShellReply` returns whether it wrote the reply's own command line, so the caller can attach a link to that line; both paths report the row the same way) and on `useShellTerminal.ts` (`displayReply` and `echoCommand` move to a new `useShellReplyWriters.ts`, "the way `useShellTerminalView.ts` was split out", with `useShellTerminal` returning its two writers unchanged); "UI design" States ("A resize re-places them after the echo text reflows"), which the marker-row decision below exists to keep true; "Out of scope" that placement rules stay as they are; "Code organization" (the hook lives in the shell plugin's directory, no import from another feature).

- Extraction owned here: `useShellTerminal.ts` to `useShellReplyWriters.ts`. This is the file-size extraction the source plan names for that file. The hook is `useShellReplyWriters(terminalRef, placementRef, openLinkRef)` with three positional parameters (`06-marker-lifecycle` replaces them with one object), typed `React.RefObject<Terminal | null>`, `React.RefObject<ReplyPlacement>`, and `React.RefObject<((href: string) => void) | undefined>` (the ref `useShellTerminal` already holds for `openLink`), written without a React namespace import as `useShellTerminalView.ts` does. It returns `{ displayReply, echoCommand }` with the signatures `(line, markdown) => void` and `(line) => void` and the bodies they have today. Each is a `useCallback` that lists the refs it reads in its dependency array (the refs are parameters now, so `react-hooks/exhaustive-deps` requires it, as `useShellTerminalView` does); the identities stay fixed for the life of the tab because the refs do, and that matters because `useBackgroundReplies` lists `displayReply` in its effect's dependencies and re-subscribes when it changes. Each callback reads `terminalRef.current` and `placementRef.current` when it is called and captures neither: `placementRef.current` is replaced at every attach (`placementRef.current = placement`) and `terminalRef.current` goes null and back. `ShellTerminalHandle` and its callers do not change in this subplan.
- Counting, measured the way `max-lines` counts (blank and comment-only lines skipped). `useShellTerminal.ts` is 193 counted lines today. The two `useCallback` blocks are 9 of them and leave; the writer import is swapped for the hook import one for one; the call is one new line. It lands on 185, which leaves `06-marker-lifecycle` room for the roughly eight lines it adds. `write-shell-reply.ts` goes from 19 to about 45, and `useShellReplyWriters.ts` is about 20.
- Which row the marker is on (decided). Both writers hand back a marker on the first row of the logical line that holds the echo's last row (the head's last row, for a reply), not on that last row. The reason is how xterm 6.0.0 reflows, read from `node_modules/@xterm/xterm/src/common/buffer/Buffer.ts` and `BufferReflow.ts` (the shipped `lib/xterm.mjs` fires the same events). Narrowing inserts continuation rows after the line's last row (`_reflowSmaller` fires `onInsertEmitter` at the index after it) and `Buffer.addMarker` shifts only markers at or after that index, so no marker moves or is lost. Widening over a wrapped line deletes its trailing rows (`reflowLargerGetLinesToRemove` removes only rows after the first, its loop runs while `i > 0`, and `reflowLargerCreateNewLayout` fires `onDeleteEmitter` for them), and `Buffer.addMarker` disposes any marker inside the deleted range. A marker on a wrapped echo's last row is therefore disposed the moment a widening unwraps the line, and its decoration goes with it, so a still-running `Thinking` marker would vanish; a marker on the first row is never in the deleted range. `markdown-block.ts` has no such problem and is not a precedent for offset `-1`: its marker sits on one of the blank rows its own `\r\n`s created, which are never wrapped.
  - The rule, applied inside the write's completion callback, when the data has been parsed and the cursor is on the row below the line: the cursor's row is `baseY + cursorY` of `terminal.buffer.active`, as `cursorRow` in `prompt-mask.ts` and in `src/shell/transcript/row-tracker.ts` compute it; the line's last row is the row above it; walk up from that row while the row's `isWrapped` is true, stopping at row 0 or at a row `getLine` does not return; the row the walk ends on is the first row; the offset given to `registerMarker` is that row minus the cursor's row, because xterm resolves it as `ybase + y + offset`, the same sum. A line on one row gives `-1`, as before, and a line on three rows gives `-3`. When the cursor is on row 0 (a real echo never leaves it there, but the `fakeActiveBuffer` in `ShellTab.test.tsx` reports it) no row is read and the offset is `-1`.
  - The walk ends on the line's own first row and cannot run into earlier output: both writes begin with `commandHead`, whose `CLEAR_ROW` is `\r` plus `ESC[2K`, and erase-in-line 2 clears the row's wrap flag (`InputHandler.eraseInLine` passes `clearWrap`), even when the cursor had been left on a continuation row. The row below the line is a fresh row with the flag clear (`InputHandler.lineFeed`), which is where the decoration's forward walk stops. `stripTerminalControls` keeps a newline, so a line typed with one is several logical lines; the rule then applies to the last one, the one that holds the last row and the one the decoration places against.
  - The marker is taken in the callback and not when the function is called because the write is parsed later, after any output already queued ahead of it, so at call time the cursor is not yet on the row the line will land on.
  - Accepted costs. The marker is disposed when its first row leaves the scrollback, a few rows before the line's last row would. While the first row is above the viewport and the last row is inside it, xterm hides the decoration's element but still fires `onRender` for an element that exists (`BufferDecorationRenderer._refreshStyle`), and the decoration places it against the last row again, so it stays visible.
- The alternate buffer (decided). The earlier draft of this plan said `registerMarker` returns nothing there. That describes `@xterm/headless`, whose `registerMarker` is typed `IMarker | undefined` and whose `addMarker` returns nothing unless the normal buffer is active. The `registerMarker` in the build the app ships is `buffer.addMarker(ybase + y + offset)` on whichever buffer is active, typed `IMarker` and never undefined, and a marker taken on the alternate buffer is disposed when the program leaves it (`BufferSet.activateNormalBuffer` calls `_alt.clearAllMarkers`). So the callback checks `terminal.buffer.active.type` and does nothing unless it is `'normal'`, as `row-tracker.ts` checks `'alternate'`: no marker is registered and the handler is not called. The result of `registerMarker` is not checked for undefined.
- `writeShellEcho(terminal, placement, rawLine, onMarker?)` returns `true` when it wrote the echo (when `placement.echo` allowed it) and `false` when it skipped it. It still strips terminal controls first and asks `ReplyPlacement` once, as today. When it wrote the echo and `onMarker` is given, the write carries a completion callback that applies the marker-row rule and calls `onMarker` once with the marker. Without `onMarker` the echo is `terminal.write` with exactly one argument, as today. `onMarker` is never called for a skipped echo.
- `writeShellReply(terminal, placement, rawLine, rawMarkdown, openLink, onHeadMarker?)` returns `true` when the reply wrote its own command line (`placement.reply(line)` was true) and `false` when it continued beneath an echo. When it wrote its own line and `onHeadMarker` is given, it first writes `commandHead(line)` on its own, with a completion callback that applies the marker-row rule and calls `onHeadMarker` once, and then lets the reply continue exactly as it does beneath an echo: `insertMarkdownBlock` is called with no head and, when it declines, the styled-text fallback is `formatDispatchedCommand` with no head. Without `onHeadMarker`, or when the reply continues beneath an echo, nothing changes: the reply is one write with the head in it as today, so every existing assertion on `terminal.written` stays valid. This is the decision the source plan left open: a boolean alone cannot say where the line's row is, and in the styled-text fallback the number of rows the body occupies is not known until it is parsed, so the head cannot be located after the fact. Writing the head separately only when a marker is wanted, and only for the replies that will get a link, keeps both paths reporting the row the same way without changing any other write. `ReplyPlacement` is asked once, before any write, and the extra chunk is not a placement write (no `placement.wrote()`), because the placement counts logical writes. The body's first write begins with `CLEAR_ROW`, which is a no-op on the empty row the head left, and the rows the block reserves and the position of its marker come out the same as in the single write.
- Callback contract for `06-marker-lifecycle`. Both callbacks run inside xterm's own write callback. `WriteBuffer.write` parses at once when nothing is queued and the write is the first since a keystroke typed into the terminal itself (`_didUserInput`), so the callback can run before the writer has returned, as it does with every fake terminal whose `write` runs its callback at once; a caller must have whatever its handler reads in place before it calls the writer. A throw inside a write callback escapes `WriteBuffer._innerWrite` before it advances past the chunk, after which xterm stops draining its write queue and the terminal goes dead. So the writers' own callback code is limited to reading the buffer and `registerMarker`, and they do not catch: the handlers passed in must not throw.
- Both functions keep stripping terminal controls from the line and the Markdown, keep calling `ReplyPlacement` in the same order, and keep their current placement outcomes.
- The `IMarker` type comes from `@xterm/xterm`, a package import the plugin lint rule allows (it restricts only `../` other than `../api`, and `@shared/` other than `@shared/error-text` and `@shared/plugins/<id>/shared`). Relative imports in `web/` carry no extension. Every non-test file under `web/src/plugins/shell/` already imports only `../api`, `../shared.css` (in `index.tsx`), `@shared/plugins/shell/shared`, packages, and siblings, and none imports `@shared/protocol`; the new file and the two new imports keep that true.
- Existing tests that must not be disturbed. The split happens only when a caller passes `onHeadMarker`, and no caller does yet, so none can see it. They are, by name: in `useShellTerminal.test.ts`, `falls back to an ANSI reply when the terminal has no screen to place a rendered block on` and `writes a fallback reply without the control sequences its text carried` (each asserts `terminals[0].written.at(-1)` equals one string); in `ShellTab.test.tsx`, `displays a claimed application command and its reply without sending either to zsh`, `echoes an ACP line at once, keeps the bar usable, and repeats the line with its settled reply after other output` (the exact echo string, two writes containing the line, and `written.at(-2)` equal to `'ordinary output\r\n'`), `writes an ACP reply straight beneath its echo when nothing else reached the terminal` (the exact `\r\u{1B}[2KDone\r\n\u{1B}[1m>\u{1B}[22m ` write and one echo), and `writes no late echo for an ACP reply that arrived before its dispatch answer`; and `markdown-block.test.ts`, which calls `insertMarkdownBlock` directly and is not modified (its case for a call with no line pins the body write the split path produces).
- The source plan describes the line's row as "the head row `insertMarkdownBlock` writes". `markdown-block.ts` is not modified: the head is now written by `write-shell-reply.ts` before the block when a marker is wanted, and `insertMarkdownBlock` is called with no head in that case.

## Proposed changes

Land the extraction first, with the existing tests unchanged as its proof, then the writer changes with their tests; typecheck and tests stay green at each step.

- `web/src/plugins/shell/write-shell-reply.ts`: the two return values and the two optional callbacks, as above, and one unexported helper that applies the marker-row rule and the alternate-buffer check, shared by both writers (its name is the implementer's; the rule is not). New imports: `IMarker` as a type from `@xterm/xterm` and `commandHead` from `./shell-prompt`. Update the comment on each function to say what it returns, when its callback runs, and why the marker is taken in the callback on the line's first row. Stays under 200 counted lines (about 45).
- `web/src/plugins/shell/useShellReplyWriters.ts` (new): the hook with the two moved callbacks, calling the writers exactly as `useShellTerminal` did and passing neither callback. `Terminal` and `ReplyPlacement` come in as type-only imports.
- `web/src/plugins/shell/useShellTerminal.ts`: remove the two callbacks and the writer import; import the hook and call `useShellReplyWriters(terminalRef, placementRef, openLinkRef)` where the callbacks were, between `display` and `useShellTerminalView`; return its two callbacks in the same place in the returned object. Keep every exported type and option as it is. It lands on 185 counted lines; if the count is not under 195 after the edit, extract a further cohesive block into a sibling module; do not compact.

## Tests

Client (vitest project `client`), colocated:

- `web/src/plugins/shell/write-shell-reply.test.ts` (new), with its own fake terminal: `write(data, callback)` records the data and runs the callback at once, unless the test has set the fake to hold callbacks until it releases them; `buffer.active` exposes a settable `type`, `baseY`, `cursorY`, and a `getLine(row)` that answers `{ isWrapped }` from a list of flags by absolute row and nothing past it; `registerMarker(offset)` records the offset and returns a marker whose `line` is `baseY + cursorY + offset`. `./markdown-block` is mocked so each test controls what `insertMarkdownBlock` returns and sees what head it was given and how many writes had happened when it was called (screen measuring is `markdown-block.test.ts`'s job). A real `ReplyPlacement` is driven as `reply-placement.test.ts` drives it. The cases:
  - `writeShellEcho` returns `true` and writes `formatEchoedCommand`'s string as the single `write(data)` call with one argument when there is no `onMarker`, and `false` with no write and no `onMarker` call when `ReplyPlacement` says the reply was written first;
  - with `onMarker` and a held callback, nothing is registered and `onMarker` is not called until the callback is released; then `registerMarker` is called once and `onMarker` once with its marker;
  - the offset follows the rule: `-1` for a one-row line; `-3` for a line on three rows (flags false, true, true above the cursor); `-2` when wrapped rows from earlier output lie above a non-wrapped first row (flags true, false, true), so the walk stops at the line's own first row, which is also the embedded-newline case; the walk stops at row 0 when every row above is wrapped; with `baseY` 40 and `cursorY` 9 the offset is relative to row 49 and the walk reads absolute rows; with the cursor on row 0 no row is read and the offset is `-1`;
  - with the alternate buffer active, the callback registers nothing and `onMarker` is not called;
  - `writeShellReply` returns `false` for a reply beneath its own echo and `true` when it repeats its line;
  - with `onHeadMarker` and a repeated line, the head (`commandHead` of the stripped line) is the first write on its own, `insertMarkdownBlock` is then called with no head and had seen exactly that one write, the head's callback applies the same offset rule (check it with a line on two rows) and passes the marker on once, and no other write carries a callback; the same when `insertMarkdownBlock` declines: the next write is `formatDispatchedCommand` with no head, so the line is written once;
  - with `onHeadMarker` but a reply beneath its echo, the callback is never called, `insertMarkdownBlock` gets no head, and the writes are as without it;
  - without `onHeadMarker`, a repeated line is `insertMarkdownBlock` given the line as its head, or when it declines one write containing the head and the body, as today; a line carrying terminal controls reaches the head stripped in both modes.
- `web/src/plugins/shell/write-shell-reply.reflow.test.ts` (new), against the real emulator, because the marker-row decision is a claim about xterm's reflow that a fake cannot prove. A headless terminal of 20 columns by 10 rows. For the echo: write a command line of 30 characters, which with its `> ` prefix wraps to two rows, through `writeShellEcho` with an `onMarker` that resolves a promise, and take `registerMarker(-1)` inside that handler as a control (the cursor has not moved yet, so it lands on the echo's last row). The control pins the premise: if xterm ever stops deleting that row, the test says so and the decision can be revisited. There the walk must end on the row directly above the row that holds the reply's body text, not above the cursor's row, because the body is written beneath the head; flush the write queue (a write of an empty string with a resolving callback) before reading the buffer. The file imports `@xterm/headless` as `src/remote/replay-history.test.ts` does and casts the terminal to the writers' `Terminal` type. ## Out of scope

- Using the new return values or callbacks, the per-terminal entry map, and any marker (`06-marker-lifecycle`).
- The `openConnection` and label options on `useShellTerminal` (`06-marker-lifecycle`).
- Any change to `ReplyPlacement`, `markdown-block.ts`, `thinking-marker-decoration.ts`, or the placement rules.
