# SQL database browser

**Complexity: 8/10** — a new subsystem (a read/write browser over the connection registry) behind a new host topic, roughly twenty new modules across both trees, and the first bundled plugin that *mutates* data: nine topic actions, opaque server-minted row tokens, bound-parameter filtering, two layouts, and a client chunk of its own. No new dependency and no new networked subsystem — the engine is the `node:sqlite` module the app already imports, and the transport is the plugin topic the app already carries.

Janissary can run SQL against a local SQLite database from a command bar — `db sqlite query notes "SELECT * FROM orders"` prints an aligned text table into a transcript (`product/specs/database.md`). That is the whole of it: a command, a paragraph of prose per invocation, and no way to see what a database *contains* before deciding what to query. A user who has just created a database has to know its table names from memory, and a user inspecting one table has to re-type the `SELECT` every time they want a different filter, sort, or page.

This plan adds a bundled tab plugin — reached by the `sql` command — that browses a database instead of querying it blind: a schema navigator listing every table, view, index, and trigger beside a data grid for the selected one, with filtering, ordering, paging, cell editing, row insert and delete, export, a per-column statistics panel, and the generated SQL for whatever the grid is currently showing. It is dockable into either sidebar like the schedules and sessions views, so it can live beside an agent tab rather than replacing it.

The plugin owns none of this. The connection registry, the name rules, the read/write split, and the file location are `src/connections.ts` and `src/database/` exactly as they are today, and the plugin reaches them only through a new `databases` host topic — the same narrow, declared grant the conversations and sessions plugins use. Every statement the grid runs is a prepared statement with bound parameters, and every write is addressed by an opaque server-minted row token, so a client can neither inject a value into a statement nor name a row it was not handed.

## Design decisions

**The command is `sql`, not `db`.** `db` and `database` are already core commands (`src/commands/db.ts`, registered as `database` in `src/commands/index.ts`), and a plugin command claim colliding with a built-in is refused at startup — the plugin would be born disabled. `sql` collides with nothing in the built-in command set, the `schedule`/`harness`/`ssh`/`shell` reserved words, or any bundled plugin's claim (`video`, `audio`, `pdf`, `schedules`, `sessions`, `conversations`, `chat`).

`sql` alone opens or focuses the tab for the most recently opened database. `sql <name>` opens or focuses that database's tab, creating it if absent. `sql left` and `sql right` dock that tab into that sidebar, and bare `sql` on a docked tab undocks it back to the centre — the `schedules [left|right]` grammar verbatim, read through the published `parseDockArgument`. A database actually named `left` or `right` is therefore unreachable by name; that collision is accepted rather than escaped, the same trade the conversations plugin documents for a conversation titled `left`. `sql` with no database and none open reports `No databases. Create one with: db sqlite create <name>`.

**One tab per database, keyed by `sqlite:<name>`.** The instance key mirrors the connection id, so reopening focuses the tab that is already there, and two databases can be browsed side by side. The tab's strip title is the database name. This is the audio plugin's singleton-per-subject shape generalized to N subjects.

**A new `databases` host topic, not a new capability.** A server plugin may import only `../api.js`, `../files.js`, and two named opener helpers (`eslint.plugin-boundaries.mjs:33`), so the plugin cannot reach `src/connections.ts`. A topic is the documented attachment point for exactly this: the plugin declares an interest, the host grants a data slice and a fixed set of actions, and every other dispatch path stays unchanged. The addition is purely additive, so `TAB_PLUGIN_API_VERSION` stays at 1 — `TabPluginNotificationTopic` gains `'databases'`, `NOTIFICATION_TOPICS` gains the matching `true`, `TabPluginNotification` gains a union member, and `TabPluginTopicAction` gains the database actions. Nine actions, each one verb: `create`, `schema`, `query`, `run`, `updateCell`, `insertRow`, `deleteRow`, `stats`, `export`. The request id rides out with the action and comes back on the answer; the plugin mints it with `randomUUID()`, because the host echoes it rather than issuing it and two plugins on one topic would otherwise both mint `q1`.

**The plugin holds no state outside its own tab payload.** `topicAction` is fire-and-forget, so the answer arrives on the next `databases` delivery. The plugin mints a `requestId` with each action, and when a delivery carries a result whose `requestId` matches the one its payload is awaiting, it folds that result into the payload with `updateTab` and re-issues the follow-up the answer implies — a schema read picks the first table and asks for its page, a write re-runs the grid, a statistics read only fills the panel. The follow-up rides out with the request rather than being inferred during the notification, so "what happens once this lands" is part of the request. The one thing the plugin does keep is the last payload it wrote per tab, because a host notification carries no payloads to fold the answer into; that mirror is pruned against the open-tab set on every notification. Apart from that there is no `Map` and no hidden module state, and the payload is a complete description of the view — which is what makes a plugin tab re-servable and profile-capturable with nothing extra. This is the conversations plugin's shape exactly: `ConversationsView` carries per-open-conversation windows, and `DatabasesView` carries request results.

**Results are a capped, most-recent-first list, not a map.** `DatabasesView` is `{ databases, results }`, where `databases` is every database the registry knows (from `listDatabaseFiles()` plus `listOpenConnections()`) and `results` is the most recent 32 results across every request, newest first. A cap is what bounds the payload on the hot broadcast path (`ai/guidelines/plugins.md` §9): a browsing session that has issued a thousand queries publishes thirty-two results, not a thousand. A `requestId` evicted before the plugin folded it in is a lost result, and the plugin recovers by re-issuing — the control every plugin already has.

**Every statement is prepared with bound parameters; only identifiers are interpolated.** The grid's `SELECT`, `WHERE`, `ORDER BY`, and `LIMIT` come from the schema the server itself read, so a column or object name is quoted with doubled `"` and never taken from the client. Filter *values* are bound through `StatementSync.run(...)`, which the existing `db` surface never uses — `src/database/query.ts:34` only calls `.all()` — so this is the first prepared-parameter path in the codebase and is exercised for the first time here. Operator choice decides the binding: `contains` binds a `%value%` pattern for a `LIKE`, `eq`/`ne` bind the value as text, and `gt`/`gte`/`lt`/`lte` bind `Number(value)` when the text parses as a finite number and the value as text otherwise, which is what SQLite's dynamic typing does to a comparison anyway. `isNull`/`notNull` emit `IS NULL`/`IS NOT NULL` and bind nothing. A value that *is* SQL is never concatenated into a statement — the whole point of the generated-SQL drawer is that its text contains no part of any value the user typed.

**A grid with no sort still gets a deterministic one.** `LIMIT ? OFFSET ?` over a query with no `ORDER BY` returns whatever order SQLite happens to produce, which makes paging skip and repeat rows as the underlying data changes. So the grid always orders: by whatever the user has chosen, and otherwise by the object's primary-key columns ascending, falling back to the first column when there is no primary key. The drawer shows the ordering actually used, including the fallback, so a read-only table's `ORDER BY` is never a surprise.

**Safe editing is structural, not advisory.** A row is named on the wire by an opaque `key` the server mints when it returns the page, and the manager keeps the key → primary-key-values mapping for the pages it most recently returned. Every write action takes a key; the manager resolves it and builds its own `WHERE` from the primary key it recorded. A client therefore cannot write a `WHERE` clause, cannot address a row it was not handed, and cannot reach a table without a primary key at all. When a page is re-read the old keys are dropped, and a write naming a dropped key is refused with `That row is no longer loaded. Refresh and try again.` rather than silently hitting a different row.

**A table with no primary key is read-only, and a view is always read-only.** This is the "safe" in safe cell editing: with no primary key there is no statement that can address one row rather than several, and SQLite's `rowid` is not a safe answer because it is reassigned by `VACUUM` and is absent from `WITHOUT ROWID` tables. Such a table's header says `Read-only: "<object>" has no primary key.` and offers no edit, insert, or delete affordance. The console and `db sqlite query` remain the escape hatch, exactly as they are today. A composite primary key is the normal case for it: `PRAGMA table_info` reports a per-column `pk` ordinal, and the grid's `WHERE` uses every column with `pk > 0` in that order, so a composite key is as addressable as a single one.

**`NULL` is a distinct state, not the empty string.** A cell's value is `{ text, isNull }`; a `NULL` renders as a muted `NULL` rather than as an empty cell, so a blank string and a null are never confused in the grid. The cell editor is the host's published `InlineEditInput` plus a `Set NULL` toggle, so writing the four characters `NULL` and writing a null value are two different acts. Enter commits, Escape cancels, blur commits — the `InlineEditInput` contract as it already stands.

**Statistics are a CSS bar chart, on demand, and there is no chart dependency.** `package.json` carries no charting library, and adding one for a column histogram would be a new dependency for a hundred lines of flexbox. The `Stats` control runs one grouped `SELECT` per column — `SELECT col, COUNT(*) FROM t GROUP BY col` capped at 21 rows for the distinct count, plus `COUNT(*)` for the total — and the client renders null count, distinct count, min/max for a numeric column, and one horizontal bar per value when a column has 20 or fewer distinct values. It runs when asked, never on a refresh, because it is one query per column over the whole table and a 200-row page does not need it. It reads its numbers from the page it already has where it can — a null count and a distinct count within one page are lower bounds, not answers, so the panel says so (`within this page`) rather than pretending, and the grouped query is what turns them into real figures when the panel is open.

**Export writes a file beside the databases and serves it through the existing allow-list.** `CSV` and `JSON` run the *full* filtered and ordered query with no limit, streaming it through `StatementSync.iterate()` rather than materializing it — the grid itself materializes only one bounded page, so `.all()` over a whole table would be the one place this feature could exhaust the server's memory. Both writers append to a file handle row by row. The export refuses above a stated ceiling of 1,000,000 rows with `Export too large: <n> rows (limit 1,000,000). Add a filter and try again.`, because a synchronous multi-million-row write would block the event loop for minutes with no way to cancel; the upgrade path, if the ceiling is ever hit in practice, is the same shape the rest of the app uses for long work — a bus event and a progress row — and it is not built now. The file is named `<database>-<object>-<n>.<ext>` under `.janissary/db/exports/`. The plugin registers the file from the payload factory on the `updateTab` that shows it — the only place `resources.registerFile` may be called (`ai/guidelines/plugins-tabs.md`) — and the client renders it through `capabilities.resourceUrl`, so there is deliberately no open-export intent — the reference is already an authenticated `/open/<id>`, and a download link is all it needs. The last five registrations per tab are kept; older files are removed from the allow-list by re-registering with only the recent ones, and the files themselves are left on disk under a project directory the user can clear. Numbering follows the same rule as `nextNumberedSibling` (`src/openers/numbered-sibling.ts:13`) but not that function, which appends `.png` to every name it builds and is about a captured frame beside a video. The export directory is derived from the registry — a sibling of the database directory, through a new `dbExportDir()` in `src/connections.ts` — rather than passed in, so nothing outside that module can name a path under the project database directory: the export action carries a database name and a format, and nothing else.

**The SQL console borrows the application's own command bar.** `CommandBarShell` and `useCommandBarKeys` are published for exactly this ("a plugin whose view takes a line of text renders the one the agent tab renders", `ai/guidelines/plugins-tabs.md`), and they already give Shift+Enter for a new line and ArrowUp/ArrowDown through a caller-supplied history, which the console supplies as its own last fifty statements. Sending routes through the *same* read/write split `db sqlite query` uses — the `READ_QUERY` prefix test at `src/database/query.ts:20` — so a `SELECT` fills the grid and anything else reports `OK.` and a changed-row count. The plugin does not re-derive that test; it imports the constant the module already owns once that constant is exported, so the two surfaces cannot drift.

**The grid pages, it does not scroll.** A page is 100 rows by default and the page size is chosen from 50, 100, or 500; the pager reads `Rows 1–100 of 4,213`, `Rows 101–150 of 4,213`, or `No rows.` for an empty object. Virtual scrolling would mean the server sending a table it cannot size in advance, and a page size a user picks is a thing they can reason about. Changing the page size returns to the first page, since an offset that was valid at one size means nothing at another. The pager shows both totals, because a filtered view where the total is the filtered total and not the table's is the single most confusing thing a data grid can do — the header line is `Rows 1–100 of 4,213 (filtered from 51,882)`.

**Generated SQL is the statement that ran, with its parameters listed beside it.** The grid's `SQL` drawer shows `SELECT … FROM "orders" WHERE "status" = ? ORDER BY "id" LIMIT ? OFFSET ?` and, under it, `Parameters: ["paid", 100, 0]`. It is not an inlined rendering, because a value containing a quote cannot be inlined safely and a copy-paste that silently changes meaning is worse than one that needs filling in. `Copy` writes that pair to the clipboard; `Run` puts the statement in the console and sends it, so a filtered grid becomes the starting point of a hand-written query.

**The centre layout is two columns; a docked layout is one.** In the centre the tab is a fixed-width schema navigator beside a grid that takes the rest. `capabilities.dock` is not `null` in a sidebar, and a sidebar is narrow, so the docked layout is a single column with a `Schema` / `Data` switch at the top and the navigator collapsed to a one-line object name above the grid. The plugin reads `dock` rather than measuring the host's frame, per the client contract.

**A failure is a band, not a blank view.** A query, a write, or a schema read that fails puts the SQLite message in an error band across the top of the area it failed in, and leaves whatever was already there underneath it — a failed refresh keeps the page you were reading. A failed *read* drops the page it was replacing rather than leaving a silently stale one under the message, and a failed write leaves the cell as it was. Nothing disables the plugin and nothing is written to a transcript: a wrong column name in a grid is an ordinary outcome, not a broken one, and the plugin contract's own distinction between a rejection and a failure is exactly this. The only outcomes that cross the failure boundary are the plugin's own, and the plugin has none it can foresee.

**This version browses the project's own database registry by name, and claims no file extensions.** `.janissary/db/sqlite/<name>.sqlite` is the only place a database is reachable from: `dbPath` (`src/connections.ts:15`) derives the path from a validated name, and there is no path-based opener behind it. Claiming `.sqlite`/`.db`/`.db3` in `fileExtensions` would promise `open notes.sqlite` and deliver nothing, because a `.sqlite` file anywhere else on disk is not in the registry. So the plugin claims no extensions and is reached only by `sql`. Reading a database file from an arbitrary path is a separate piece of work with its own trust decision — where a file the user picked is allowed to be written — and is named under Out of scope.

**The tab does not add a `sqlite:` row to the connections panel, and this is a consequence rather than an oversight.** `connectionCatalog` builds a tab's own rows from `DatabaseManager.openDbs(label)`, and attribution is recorded in `runInTab` when a `db` command runs *in that tab*. A plugin tab runs no `db` command, so it records nothing. The connection it opens is still global, so it appears in `connection list` and in tab-completion app-wide as `scope: 'global'`, and `connection close sqlite:<name>` still closes it. Putting a `tab` field on the database topic actions would close the gap — the schedules topic already carries one — but it would hand a client the power to name an arbitrary tab label, which is a wider grant than this feature needs for no user-visible gain it was asked for. Recorded under Open questions.

**No live updates.** The grid re-reads on a user action — a filter, a sort, a page, a refresh, a write — and on nothing else. A `db` command run in an agent tab that changes the data leaves the view showing what it last read, which is why the header carries the total and the `Refresh` control is always present. Wiring the raw state broadcast in as a topic is explicitly forbidden (`ai/guidelines/plugins-tabs.md`: "the raw state broadcast is never one, because it fires on essentially every mutation including per-keystroke shell output"), and there is no other host signal for "this database changed". A `db` command in the same janissary could publish on the bus; that is deferred rather than built, and the cost is one stale view that `Refresh` fixes.

## Proposed changes

**Wire types.** A new domain slice `src/protocol/database.ts` holding the browser's view types, re-exported from `src/protocol.ts` beside the other domains — the house pattern that keeps `src/protocol.ts` a composing module rather than a growing list. It declares `DatabaseRefView` (name, whether a file exists, whether a connection is open), `DatabaseObjectView` (name, kind, and its `DatabaseColumnView` list with name, declared type, not-null, and primary-key ordinal), `DatabaseCellView` (`text` plus `isNull`), `DatabaseRowView` (`key` plus cells), `DatabaseGridQuery` (object, filters, order, limit, offset), `DatabaseFilterView` (column, operator, optional value), `DatabaseOrderView` (column, direction), `DatabaseGridView` (the statement, its parameters, the columns, the rows, the filtered total, the unfiltered total, the offset, the limit, whether the object is writable, and an optional error), `DatabaseColumnStatsView`, and the `DatabaseResultView` union — one discriminant of `schema`, `query`, `write`, `stats`, or `export`, every member carrying the `requestId` and `database` it answers. The `write` member adds the statement it ran, its parameters, and a changed-row count, so the console's `OK.` and the grid's `1 row changed.` are the same number read two ways. `src/protocol.ts` also re-exports them from `src/plugins/api.ts`, because the plugin import boundary forbids a plugin reaching `../protocol.js` (`eslint.plugin-boundaries.mjs:33`) — the same arrangement `AggregatedScheduleView` and the conversation view types already use. Adding a slice changes no RPC: the results ride the existing topic notification, so `RpcCall` and `ClientMessage` are untouched.

Every action carries a `requestId`, including `create` — which answers with a `schema` result, so a database the tab just created arrives with its (empty) object list rather than needing a second round trip.

**Server: the browser modules.** Five new modules under `src/database/`, each one responsibility, because `DatabaseManager` is 82 lines and the browser work is not a rounding error on it.

`src/database/schema.ts` reads a database's objects: `SELECT name, type FROM sqlite_schema WHERE name NOT LIKE 'sqlite_%' AND type IN ('table','view','index','trigger') ORDER BY type, name` for the navigator, and `PRAGMA table_info(<quoted name>)` per object for its columns — the table, view, and index groups the navigator draws, and the trigger group listed but not browsable. It is pure with respect to the caller: it takes an open `DatabaseSync` and returns views, doing no connection management of its own.

`src/database/grid.ts` turns a `DatabaseGridQuery` into a statement and a result page. It builds the `SELECT`/`WHERE`/`ORDER BY`/`LIMIT ? OFFSET ?` text with quoted identifiers and `?` placeholders, collects the bound values in order, runs it with `StatementSync.run(...)` and `.all()`, and takes the column names from `statement.columns()` rather than from `Object.keys(rows[0])` as `src/database/query.ts:11` does — so an object whose first page is empty still renders its header, which a `SELECT` returning nothing would not. It separately runs `SELECT COUNT(*)` with the same `WHERE` for the filtered total, and the unfiltered `COUNT(*)` once per object for the "filtered from" figure, cached against the object so an unfiltered grid pays for it once. It mints one `key` per returned row — an opaque counter-based token, never the primary-key values — and holds the key → primary-key-values map for the pages it has returned, dropping the oldest so the map cannot grow without bound. It also reports whether the selected object is browsable at all, which is what makes a view read-only. Given the object has no primary key it returns the rows and no keys, and the write paths refuse.

The two totals are what let the pager distinguish "this table has four rows" from "your filter matched four of four thousand". An unfiltered grid shows only the first figure; a filtered one shows both, and the unfiltered count is fetched once per object rather than on every query.

`src/database/write.ts` owns the three mutations. `updateCell` resolves a row key, builds `UPDATE "<object>" SET "<column>" = ? WHERE <pk> = ?` with the value bound, and returns the changed-row count. `insertRow` builds `INSERT INTO "<object>" (<cols>) VALUES (?, …)`. `deleteRow` builds `DELETE FROM "<object>" WHERE <pk> = ?`. Each refuses a table with no primary key before it prepares anything, and each takes its object name from the key's own record rather than from the client, so a client cannot name a different table than the one its row came from.

`src/database/export.ts` writes the export. It runs the grid query with the limit removed, streams the rows into either a CSV (`fileSize` shows a small `fileSize` helper precedent at `src/plugins/files.ts:15` for the size string) or a JSON array of objects keyed by column name, and names the file with `nextNumberedSibling` beside the export directory. The CSV writer doubles a quote inside a quoted field and quotes a field containing a comma, a quote, or a newline — the RFC 4180 minimum — and the JSON writer is `JSON.stringify` with no hand-rolled escaping.

`src/database/browser.ts` is the stateful piece: the capped most-recent-first result list, the `requestId` counter the plugin's ids are checked against, and the `view()` the topic's `read` calls. It is where a result is recorded, how a result that failed records the error instead of an empty success, and how the cap drops the oldest.

**Server: `DatabaseManager`.** It gains `listFiles()` delegating to `listDatabaseFiles()` — the one registry call it does not already expose, and the reason a database on disk but never opened has been invisible to every surface so far — and a set of browser methods delegating to the four modules above and recording each result through `browser.ts`. `create(name)` goes through the existing `getConnection` path so a browser-created database lands in the same registry a `db sqlite create` would. It also gains `readView()` for the topic's `read`. Nothing is removed: `runInTab`, `openDbs`, `listOpen`, `close`, `forgetTab`, `closeAll`, and `dispose` keep their behavior, and `src/database/query.ts` keeps rendering its aligned text table for `db sqlite query` exactly as it does — the grid is a second surface, not a replacement.

**Server: the topic.** `src/plugins/api-topics.ts` gains `'databases'` in the union and in the keyed `NOTIFICATION_TOPICS` record — keyed, so a topic in the type without a source is a compile error rather than a name never delivered. `TabPluginNotification` gains its member carrying `DatabasesView`. `TabPluginTopicAction` gains the nine actions, each tagged `topic: 'databases'`, each carrying the `database` it names and the `requestId` it answers under; the four write-shaped ones carry only the opaque row key and the column/value pairs, never SQL. `src/bus.ts` gains a `DatabaseEvent` of `{ type: 'changed' }` beside `ConversationsEvent` and a `databases` key on `BusChannels` — the module is 160 lines and stays inside the limit. `src/plugins/topics.ts` gains the `TOPIC_SOURCES` entry: `subscribe` on the bus channel, `read` as `managers.database.readView()`, `act` as an `actOnDatabases` switch modelled on `actOnConversations`, and an `empty` of `{ databases: [], results: [] }` — the field the conversations entry added, and the reason the disabled-plugin `topicData` fallback needs no change.

**Server: the plugin.** `src/plugins/sql/` with `manifest.ts` (id `sql`, version `1.0.0`, `tabLabelPrefix` `sql`, no `fileExtensions`, `command: 'sql'`, `notifications: ['databases']`, and the capabilities this needs: `openOrFocusTab`, `updateTab`, `dockTab`, `topicData`, `topicAction`, `rejectRequest`, `reportFailure`), `shared.ts` (the payload schema version, the payload and per-intent payload types, and hand-written import-free guards), and `activate.ts`.

`activate.ts` keeps no state. Its `command` reads the dock argument with `parseDockArgument`, resolves the database name (the first argument, or the most recently opened one from `topicData`), and either opens the tab with `openOrFocusTab` or docks it. Its `notify` folds any result whose `requestId` matches the one the payload is awaiting into a new payload via `updateTab`, and issues the follow-up read that result implies. Its `intent` table maps one client intent to one topic action: `open` (the header's database switcher), `select-object`, `set-filter`, `clear-filters`, `set-order`, `set-page`, `set-page-size`, `refresh`, `run` (both the console's send and the drawer's `Run`, which is the same statement through the same intent), `update-cell`, `insert-row`, `delete-row`, `create`, `stats`, and `export`. There is deliberately no `open-export` intent: the export is already an authenticated `/open/<id>` reference, so the client renders a plain download link and the browser does the rest. Each payload is validated by a guard in `shared.ts` before any action is taken, and the plugin checks the thing the sessions plugin checks — that the grid it is about to write to is one its own payload says is writable — before issuing a write, so a client cannot ask for a write the view has already refused. Add the manifest to `src/plugins/catalog.ts` and the loader to `src/plugins/loaders.ts`; `ProductionTabPluginId` makes both compile errors if either is forgotten.

## Out of scope

- **Any engine but SQLite.** The feature text says "sql databases including local sqlite databases"; only SQLite is reachable, and only through the existing registry. Postgres, MySQL, and every other engine are a different connection model, a different credential story, and a different threat boundary.
- **Databases outside `.janissary/db/sqlite/`.** `dbPath` derives the path from a validated name, so there is no path-based opener to claim a file extension with. Opening an arbitrary `.sqlite` file the user picks needs its own trust decision — what a plugin may do with a path it was handed — and is a separate piece of work.
- **Schema mutation from the grid.** No `CREATE`, `ALTER`, `DROP`, or index management in the navigator. The console and `db sqlite query` remain the way to change a schema, exactly as they are today.
- **Joins, a query builder, or a relationship graph.** The grid is one object at a time. Following a foreign key to the row it points at is deferred.
- **Editing a table with no primary key.** Refused rather than approximated with `rowid`, for the reasons given above. A `WITHOUT ROWID` table and a table whose key is a natural key SQLite does not mark are both read-only here.
- **Multiple result tabs for one database.** A second query replaces the grid; there is no tab per result set.
- **Persisted view state, query history, or a saved filter set.** The console's history is the last fifty statements in the tab's own life, client-side, and the grid's filters live in the tab payload.
- **Live updates from another tab's `db` command.** See the design decision on this; the cost is one stale view that `Refresh` fixes.
- **A `sqlite:` row in the browser tab's own connections panel.** See the design decision; the connection is global and reachable app-wide either way.
- **Undo.** A cell edit commits or it does not; there is no revert to the previous value beyond editing it back.
- **A chart library.** The statistics panel is CSS bars, decided above.

## Open questions

- **Should the browser tab list itself in the connections panel?** The answer here is no, with the reason recorded above. If it should, the change is one `tab: string` field on the write-shaped topic actions plus one line in `actOnDatabases`, and it should be weighed against what a client can then name.
- **Should a write to a row whose page has been superseded be offered at all?** The answer here is to refuse it and say so, because a silently retargeted write is the failure this design exists to prevent. The alternative — re-resolving the key by re-running the query and checking the row is still there — trades a clear error for a race.
- **Whether a table's own `rowid` should be shown as a read-only column.** Every SQLite table has one unless it is `WITHOUT ROWID`, and it is genuinely useful when reading a grid, but it is not a declared column and showing it changes what `SELECT *` means to the user. Left out of this version.
- **Whether the statistics panel should cover filters.** It reports on the whole table today. Reporting on the current filter is arguably more useful and is one more `WHERE` in the same grouped query.
