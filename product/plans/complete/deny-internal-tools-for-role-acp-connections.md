# Deny internal tool usage on role-based ACP connections

**Complexity: 7/10** — ~170 added lines across 12 production files, 11 requirements, and 16 test scenarios, including a remote wire-version bump and two new dependencies (p=6.64)

## Goal

Role-based ACP connections — the core `ask` and `tell` sessions — deny every tool the agent harness ships with. The only thing such an agent may do is run the Janissary native commands its role grants and that are enabled for agents in `commands.json`. Before this change the connection only refused the permission requests an agent chose to raise; a harness that runs its own tools without asking, or that auto-approves read-only tools, was not restrained. This plan turns the harness's built-in tools off at launch, keeps the request denial as a second layer and records each denial, tells the model in its primer that it has no built-in tools, and carries the same policy to role sessions hosted on a remote machine.

Feature text: "Configure all role based acp connections to deny all internal tool usage by default. The agent should only be allowed to execute janissary commands that have been enabled for agents in commands.json."

## Design decisions

- "Internal tools" means the tools the harness itself provides to the model — shell, file read/write/edit, search, web fetch and search, sub-agents — not Janissary native commands, which run through the existing tool loop. MCP servers a user configured in their own harness settings are not built-in tools; a call to one raises a permission request and meets layer two.
- The Janissary command gate is unchanged: a role's grants are intersected with effective agent access in `commands.json`, the primer lists only those commands, and each emitted command is re-checked before it runs (`product/specs/acp.md`, `product/specs/application-commands.md`).
- Two layers. Layer one disables the harness's built-in tools at launch so they are never offered to the model. Layer two is the permission-request denial in `connectAcp` (`requestPermission` in `src/acp/index.ts`, `decidePermission` in `src/acp/tools.ts`); its decisions are unchanged, and each denial is now recorded.
- No opt-out. Every `ask` and `tell` connection denies all internal tools, always. `roles.json` gains no field.
- Scope is core `ask` and `tell` sessions only: everything launched through `AcpSessionManager.session` and `acpLaunchForEntry`, local and remote, including plugin-owned ask sessions and the launcher summarizer. Monitor personas (`src/monitor/acp.ts`), conversations (`src/conversations/sessions.ts`), editor persona queries, and autonomous `agent` runs (`src/agent/execute.ts`) keep their launches (`acpLaunchFor`) and permission policies. `acpLaunchFor`'s output is byte-for-byte unchanged, including its `npx @zed-industries/claude-code-acp` claude launch.
- A role entry whose harness has no known deny-all configuration (any harness other than opencode, claude, and codex) still launches if `acpLaunchForEntry` can launch it, protected by layer two alone, with no warning. A key that could not be confirmed against the pinned adapter would be omitted on the same rule; every key below was confirmed.

### Bundled adapters

- Adapters ship in the manifest, not through `npx`. `@agentclientprotocol/claude-agent-acp` and `@agentclientprotocol/codex-acp` are exact-pinned `dependencies` in `package.json`, replacing the deprecated `@zed-industries/*` packages that `acpLaunchForEntry` fetched at runtime. Role launches run the installed copy; opencode stays a binary on the user's `PATH`.
- Pinned versions, chosen by the rule "the newest non-`preview` release published at least 14 days earlier" and passed by `check-malicious-package` (exit 0): `@agentclientprotocol/claude-agent-acp@0.97.0` (`bin` `claude-agent-acp`) and `@agentclientprotocol/codex-acp@2.3.0` (`bin` `codex-acp`). Every configuration key below was confirmed against these versions. Neither package has an install script, so `npm install --ignore-scripts` leaves both runnable. The root `@agentclientprotocol/sdk` (`^1.3.0`) is not bumped; npm nests SDK 2.0.2 under the adapters.
- claude-agent-acp 0.97.0 depends on `@anthropic-ai/claude-agent-sdk@0.3.310`, which ships the Claude CLI as platform `optionalDependencies` and is found with `createRequire`. codex-acp 2.3.0 depends on `@openai/codex@^0.164.0` and runs `@openai/codex/bin/codex.js` through `require.resolve`. Neither finds its CLI through `PATH`.
- A claude entry launches as `claude-agent-acp` with no args and the same `{ ANTHROPIC_MODEL, CLAUDE_THINKING_EFFORT }` env `acpLaunchFor` builds. The adapter reads `ANTHROPIC_MODEL`; neither it nor the deprecated adapter reads `CLAUDE_THINKING_EFFORT`, so the env keeps parity and changes no behavior.
- A codex entry launches as `codex-acp` with no args. codex-acp 2.3.0 is a Node adapter that ignores its argv apart from `--version`, `login`, and `cli`, so the deprecated adapter's `-c key=value` overrides would be silently dropped. It takes its Codex config from the `CODEX_CONFIG` environment variable, a JSON object passed as `config` on every `thread/start`/`thread/resume`. The entry's `model`, and `model_reasoning_effort` when the entry sets an effort, travel there. The launch env wins over an ambient `CODEX_CONFIG` because `connectAcp` spreads `options.env` last, and `CODEX_CONFIG` is not matched by `ENV_SCRUB_PATTERNS`, so it reaches the confined process.
- `locateAcpCommand` searches the install's own `node_modules/.bin` (`path.join(janissaryRoot(), 'node_modules', '.bin')`) after the "command given as a path" check and ahead of the server's `PATH` and the interactive-shell fallback. A hit returns the absolute path. The function runs for every `connectAcp` caller and on a remote host's own install, so a remote role session finds the remote's bundled copy. `.bin` holds no `npx` and no `opencode`, so those launches resolve exactly as before. `.bin` also gains `codex` (from `@openai/codex`), which no `connectAcp` caller launches.
- The server's node on the adapter's `PATH`. Both adapters start with `#!/usr/bin/env node`. The old `npx` launch on a server whose `PATH` lacked `npx` went through the interactive-shell fallback, which handed over the shell's `PATH` and so a `node`; the `.bin` hit skips that fallback. So on a `.bin` hit the returned env is a copy whose `PATH` is `path.dirname(process.execPath)` followed by the original `PATH` (or the directory alone when `PATH` is unset or empty), with the rest of the env kept. The env is returned unchanged, as the same object, when either the server's node directory is literally one of `PATH`'s `:`-separated entries, or the first executable `node` on `PATH` resolves through `realpathSync` to the same file as `process.execPath` (a Homebrew node reached through `/opt/homebrew/bin/node` reports its Cellar path as `process.execPath`). An error from either `realpathSync` falls through to the prepend. A version-manager shim (volta, asdf, mise) resolves to a different file and keeps the prepend. Prepending rather than appending guarantees the shebang runs a node known to work (the adapters need `node >=22`). The path-given, `PATH`-hit, and shell-fallback branches are unchanged. Confined spawns keep the rewritten `PATH` (`scrubEnv` does not match it), and the server node's directory is already in the Seatbelt read allow-list.
- An absolute command inside `node_modules/` already has that whole `node_modules/` carved into the Seatbelt read allow-list (`packageRootDir` in `src/sandbox/harness-spawn.ts`), which covers the adapters' nested native CLIs, so no sandbox change is made.
- Accepted side effect, documented rather than prevented: a server started through an npm script has `node_modules/.bin` on its own `PATH`, so a harness tab from such a dev server whose shell does not put the user's own `codex` earlier on `PATH` would run the bundled `@openai/codex`. A global install and `janus` are unaffected.
- Ceiling: the adapters are assumed to sit under the install's own `node_modules`, which holds for a checkout and a global npm install. A layout that hoists them elsewhere fails to find the `bin` name and reports the agent failing to start (the role's model fallback then tries the next entry); the upgrade path is resolving through `createRequire`, as `src/browser/playwright-paths.ts` `resolvePackageDir` does.
- A server test ties the launch command names to the pinned packages: the command `acpLaunchForEntry` returns for claude and codex must be a `bin` name the installed adapter declares, the root `package.json` must pin it to an exact version, and the installed version must equal the pin. A version bump that renamed a `bin` would otherwise pass every test while role launches moved to an unpinned copy on `PATH` or failed to start.

### Per-harness configuration (layer one)

The new pure module `src/acp/internal-tools.ts` owns the policy. Its comments record, per key, the version and file it was confirmed against.

- **opencode** — `permission: "deny"` merged into the existing `OPENCODE_CONFIG_CONTENT` JSON beside `model`. Confirmed against opencode 2.2.5 (not bundled, so unpinned): its config loader turns a top-level string `permission` into one `*` deny rule that fails every tool call without asking. An older opencode that rejects the single-value form is a known ceiling.
- **claude** — a `sessionMeta` of exactly `{ claudeCode: { options: { tools: [] } } }`, and no extra env. claude-agent-acp 0.97.0 reads `_meta.claudeCode.options.tools` of `session/new` and passes it to the SDK `query` as `tools`; `@anthropic-ai/claude-agent-sdk` 0.3.310 documents `[]` as disabling all built-in tools. Janissary initializes with `clientCapabilities: {}`, so the adapter adds no client-backed file or terminal tools either.
- **codex** — two environment entries, confirmed against codex-acp 2.3.0 and the `@openai/codex` 0.164.0 binary:
  - `INITIAL_AGENT_MODE: "read-only"`, the most restrictive sandbox. The adapter sends `sandboxPolicy` and `approvalPolicy` on every `turn/start` from the session's agent mode, overriding any `sandbox_mode` or `approval_policy` in the config, so the sandbox can only be set through the mode. `read-only` is sandbox `readOnly` without network and approval `on-request` with the user as reviewer, so approvals still reach the client and meet layer two. The default `agent` mode hands approvals to codex's automatic reviewer instead. Only `agent-full-access` uses approval `never`; the module never selects it, never sets an `approval_policy` key, and Janissary never calls `session/set_mode`.
  - `CODEX_CONFIG`: the base JSON (`model`, and `model_reasoning_effort` when set) with `web_search: "disabled"` (the top-level form the codex binary names), a `features` object, and a `tools` object merged in. The adapter itself merges a nested `features` object into the config, which is why the nested shape is used.
- Codex turns off every built-in tool it has a confirmed switch for, not only the shell and web search. Each `features` name is listed by `codex features list`, `--disable <FEATURE>` is documented as `-c features.<name>=false`, and each exposes a model-callable tool (it is in the override list codex 0.164.0 applies to its own tool-free structured thread, or its tool description is in the binary). The twelve features, all `false`, kept in one exported list `CODEX_DISABLED_FEATURES`:
  - on by default: `shell_tool`, `unified_exec` (the shell, both forms), `view_image`, `image_generation`, `multi_agent` (sub-agents), `apps` (ChatGPT connectors), `goals`, `tool_suggest`;
  - off by default but a user's `~/.codex/config.toml` could turn them on, and `CODEX_CONFIG` wins: `multi_agent_v2`, `code_mode`, `request_permissions_tool`, `standalone_web_search`.
- Codex `tools`: `{ update_plan: { enabled: false }, experimental_request_user_input: { enabled: false } }`, the plan-update and ask-the-user tools, which are config keys rather than features.
- Not disabled, because no switch could be confirmed: codex's `apply_patch` (file edits; 0.164.0 has no feature key for it), which under the read-only mode asks for approval and meets layer two; and `sleep_tool`, `browser_use`, `browser_use_external`, `computer_use`, `in_app_browser`, which are valid features but not in codex's tool-free list and with no model-facing tool description found, so they stay on behind layer two. The other features in codex's tool-free list are not tool switches and stay as they are.
- Module shape: `internalToolDenial(harness, baseEnv)` takes the role entry's harness name and its base launch env and returns `InternalToolDenial` (`{ env?: Record<string, string>; sessionMeta?: Record<string, unknown> }`), or `undefined` for any other harness. It takes the base env so the opencode and codex cases return the base JSON with the deny-all merged in. The base value is parsed with `JSON.parse` and narrowed with `isRecord`; an absent key or a non-object starts from `{}`. Deny-all keys are written after the base keys, so they win; a base `features` object keeps its own keys beside the twelve. The module does no I/O. No harness takes its configuration on the command line, so the result has no `args` field.

### Session `_meta` transport

- `AcpOptions.sessionMeta?: Record<string, unknown>` is sent as `_meta` on `session/new` when it is not `undefined`, and the `_meta` key is omitted entirely otherwise, so every other session's request is byte-for-byte as before. The test is `!== undefined`, because the remote server passes an explicit `undefined` for frames without the field. A caller's object is forwarded as given, including `{}`, without inspection.
- The root SDK 1.3.0 declares `_meta` on `NewSessionRequest` and sends params unchanged. The adapters' SDK 2.0.2 turns a non-object `_meta` into `undefined` silently rather than rejecting the request, so the `Record<string, unknown>` type is the guard against a malformed value.
- `AcpLaunch` gains the same optional `sessionMeta`; `AcpSessionManager.session` spreads `...launch` into both `connectAcp` and `createRemoteAcpSession`, so it needs no change.

### Denial record (layer two)

- On the non-autonomous path, whenever `decidePermission` returns `{ outcome: 'cancelled' }` — an undefined or empty `allowedTools`, or an allowlist that does not include the classified tool — `connectAcp` records the denial through `onActivity` as the same `permission_decision` update (`{ sessionUpdate: 'permission_decision', toolCall, outcome }`) the autonomous branch emits, before returning the reply. The record keys off the outcome, not the caller.
- `acpActivity` classifies the update as `permission` and uses the whole update's JSON as its text, so the connection record's entry carries the refused tool call and `{"outcome":"cancelled"}`; the connection tab renders it as indented JSON.
- Only sessions that pass `onActivity` record it: local role sessions, and remote-hosted role sessions, whose `serve-acp` relays every activity as an `acp-activity` frame. Agent runs are always autonomous; monitors and conversations pass no `onActivity`. A request approved by a monitor's allowlist records nothing.
- The early guard at the top of `requestPermission` (killed, no current prompt, or a cancelled prompt) is cancellation bookkeeping, not a policy denial, and records nothing. The autonomous branch is unchanged.

### Primer lines

- The module exports `NO_BUILTIN_TOOLS_LINE` (`You have no built-in tools; use only the commands listed here.`) and `NO_TOOLS_LINE` (`You have no tools; answer in prose.`).
- "Available" means `tools.length > 0 && allowedCommands.length > 0`, computed in `runCorePrompt`. `allowedCommands` alone is not enough: a `withoutTools` session has an empty table but may have a nonempty `allowedCommands`, and it must get the no-tools line.
- With commands available, `NO_BUILTIN_TOOLS_LINE` follows the allow-list line. Otherwise — no grants, every granted command excluded, or a `withoutTools` session such as the launcher summarizer — `NO_TOOLS_LINE` goes where the allow-list line would be, immediately after any group primers that remain. A role with no recognized grants gets no tool table and no group primers, so its primer starts with the no-tools line. The order is: group primers, allow-list line (if any), one of the two lines, `TELL_INSTRUCTION` (tell only), `MARKDOWN_INSTRUCTION`, joined by blank lines. `toolPrimer` is not modified. Remote sessions get the same lines.

### Remote role sessions (protocol 39)

- `sessionMeta` travels on the `acp-open` frame. `RemoteAcpOptions` declares it, `createRemoteAcpSession` destructures it and sends it only when set (the `...(x !== undefined && { x })` pattern of `env`, `offline`, `autonomous`, `effort`), so opencode and codex role sessions, autonomous runs, and every other remote ACP session send the same frame as before. The opencode and codex deny-all already travel in `env`. The autonomous `agent` run's `createRemoteAcpSession` call builds its options field by field and sets no `sessionMeta`.
- `decodeAcpOpen` validates the field with `decodeSessionMeta`, beside `decodeEnv`: absent is `undefined`, a plain object (`isRecord`, including `{}`) is accepted as is, and an array, `null`, or scalar makes the frame malformed. Only the top-level shape is checked, since the frame came through `JSON.parse`. `RemoteAcp.open` in `src/remote/serve-acp.ts` hands `frame.sessionMeta` to `connectAcp`.
- `REMOTE_PROTOCOL_VERSION` goes from 38 to 39. A version-38 remote drops undeclared fields while decoding, so it would start a claude role session with its built-in tools on while both ends looked healthy; exact-version refusal at the handshake prevents that. Both hosts also need the bundled adapters, which the exact-version handshake guarantees.
- An attach's handshake is answered by the freshly started `janus remote-serve` that relays into the parked peer (`relayPeer` in `src/remote/serve-detach.ts`), so it binds the version installed on the host now, not the parked peer's. A version-38 peer parked across an upgrade still answers `attach` and `session-state`, so without a further check a reattached claude role session would reach a decoder that drops `sessionMeta`. So each parked peer records the protocol version it speaks: `PeerRecord` gains an optional `version`, which `DetachedPeer.start` and `setLabel` stamp with `REMOTE_PROTOCOL_VERSION`. `isPeerRecord` still accepts a record without `version` (so a newer relay reads an older record and refuses it as a mismatch rather than as unreadable, and `src/launch-name/leftover.ts` and the capture query keep reading them) but rejects a `version` that is present and not a safe integer. This is an on-host file contract between two processes, not a frame, so it needs no further bump.
- `relayPeer` keeps its `missing`, `invalid`, and dead-pid checks in place (a dead peer of any version is still reported as ended), then refuses a live peer whose record's `version` is not `REMOTE_PROTOCOL_VERSION`, an absent version included, with `ended(false)`: nothing connects to the peer, `RemoteServer` emits no `attach-result` and exits 1, a pressed attach reports the existing "ended before its workspace was ready" failure, an automatic reconnect keeps retrying with backoff, and the session stays parked with its record. The bounded wait in `askSessionState` remains for a peer that accepts an attach and then never answers.
- Terminate path. The refusal must not strand a parked session nobody can end, so version 39 also adds an optional `terminate: true` to the `attach` client frame (`decodeAttach` accepts it only when absent or `true`). `RemoteResume` gains `terminate?: true`, `terminateParkedSession` sets it, and `createRemoteEntry` sends `terminate: true` on that entry's attach only. A terminate attach is never relayed, whatever the peer's version, matching one included: after the `missing`/`invalid`/dead-pid checks and before the version check, `relayPeer` hands off to `terminatePeer` in the new `src/remote/serve-detach-terminate.ts`. It connects to the record's socket and writes `{"type":"attach","session":"<id>"}` only — the oldest encoding, with no `restore`, `origin`, or `terminate`, which every peer that writes a record decodes — then reads the peer's first line, forwards it to stdout unchanged, writes a bare `{"type":"shutdown"}` only when that line decodes as an accepted `attach-result`, and ends the socket's writable side. Everything else the peer sends (its history replay) is dropped; a first line longer than 1024 bytes destroys the socket; `close` reports `ended(false)`. `RemoteServer` records `terminating` from the frame and drops every stdin chunk while a terminate relay is in place, so nothing the local side sends — a role `acp-open` in particular — reaches the peer. Nothing signals the peer's pid, since a recycled pid would hit an unrelated process.
- The version-history comment in `src/remote/protocol.ts` records both version-39 additions, and the version-15 paragraph says the relay's version check, not the session-state wait, is what keeps a peer parked across an upgrade from being reached.

## Proposed changes

- `package.json` / `package-lock.json`: `@agentclientprotocol/claude-agent-acp` `0.97.0` and `@agentclientprotocol/codex-acp` `2.3.0` under `dependencies` at exact versions (`.npmrc` `save-exact=true`), lockfile regenerated with `npm install --ignore-scripts`.
- `src/acp/command-path.ts`: `locateAcpCommand` returns a command containing `/` as given; then looks the name up in the install's `node_modules/.bin` and, on a hit, returns the absolute path with `withServerNode(env)`; then runs the existing server-`PATH` check and interactive-shell fallback unchanged. `withServerNode` and `resolvesToServerNode` are module-private and implement the `PATH` rule in Design decisions. The header comment and the doc comment above `locateAcpCommand` describe the `.bin` step and both conditions that keep the env unchanged.
- New `src/acp/internal-tools.ts`: `InternalToolDenial`, `internalToolDenial`, one helper per harness (`opencodeDenial`, `claudeDenial`, `codexDenial`), `CODEX_DISABLED_FEATURES`, the codex `tools` object, the two primer-line constants, and the per-key confirmation comments. It imports only `isRecord`.
- `src/acp/launch.ts`: `AcpLaunch` gains `sessionMeta?`. `acpLaunchForEntry` builds the base launch in `baseLaunchForEntry` — opencode through `acpLaunchFor`; claude as `claude-agent-acp` with `ANTHROPIC_MODEL` and `CLAUDE_THINKING_EFFORT`; codex as `codex-acp` with `CODEX_CONFIG`; any other harness `undefined` — then spreads `internalToolDenial`'s `env` over the base env and sets `sessionMeta` only when present (claude). `acpLaunchFor` is unchanged.
- `src/acp/types.ts` and `src/acp/index.ts`: `AcpOptions.sessionMeta?`; `ensureSession` adds `...(options.sessionMeta !== undefined && { _meta: options.sessionMeta })` to `conn.newSession`; `requestPermission` records a cancelled non-autonomous outcome through `onActivity` before returning it. The two comments describing the denial say it is recorded. `src/acp/index.ts` stays under the 200-line limit, so no extraction was needed.
- `src/acp/run-prompt.ts`: a `toolsAvailable` local beside `allowedCommands`, and the primer array gains `toolsAvailable ? NO_BUILTIN_TOOLS_LINE : NO_TOOLS_LINE` between `toolPrimer(...)` and the tell instruction.
- Remote `sessionMeta`: `RemoteAcpOptions.sessionMeta?` and the conditional spread on the `acp-open` send in `src/remote/acp-session.ts` (its comment names the session options); `sessionMeta?` on the `acp-open` member of `ClientFrame`; `decodeSessionMeta` and its use in `decodeAcpOpen`; `sessionMeta: frame.sessionMeta` in `RemoteAcp.open`; `REMOTE_PROTOCOL_VERSION = 39` with its version-history entry.

- Terminate path: `terminate?: true` on the `attach` member of `ClientFrame` (its comment says a terminate is never relayed) and in `decodeAttach`; `RemoteResume.terminate?`; `createRemoteEntry` spreads `terminate: true` onto the attach when `resume?.terminate` is set; `terminateParkedSession` sets `terminate: true`; new `src/remote/serve-detach-terminate.ts` `terminatePeer`; `relayPeer` gains a `terminate = false` parameter and returns `terminatePeer(...)` before the version check; `RemoteServer` gains `terminating`, set from `frame.terminate === true` in `attach`, passes `frame.terminate` to `relayPeer`, and drops stdin chunks in `receive` while terminating.

## Implementation order

1. Gate both packages with `check-malicious-package` at the pinned versions, install them with `npm install --ignore-scripts`, and audit `./package-lock.json`; confirm `node_modules/.bin/claude-agent-acp` and `node_modules/.bin/codex-acp` exist.
2. `command-path.ts` `.bin` step and `launch.ts` bundled launches with codex's `CODEX_CONFIG`, with their tests and the bin-name contract test; then the server-node `PATH` handling and its tests.
3. The denial record in `requestPermission`, then the `sessionMeta` transport in `types.ts`/`index.ts`, each with its `index.test.ts` cases.

## Out of scope

- Any opt-out, per-role override, or `roles.json` field for internal tools.
- Changing which native commands a role grants or how `commands.json` agent access is evaluated; changing `toolPrimer`, the allow-list wording, or group primers.
- Monitor, conversation, editor persona, and autonomous `agent` run launches, primers, and permission policies, local or remote, including their adapter packages and their `npx` claude launch.
- Warning the user when a harness cannot be configured, or a user-visible notification for a denial.
- Recording requests refused by the early cancellation guard, and changing `acpActivity`'s text for permission entries.
- Codex built-in tools with no confirmed off switch in 0.164.0 (`apply_patch`, `sleep_tool`, `browser_use`, `browser_use_external`, `computer_use`, `in_app_browser`); user-configured MCP servers in a harness's own settings; opencode builds older than the single-value `permission` form.
- Honoring a claude role entry's effort through the adapter's `effort` session config option.
- Bumping the root `@agentclientprotocol/sdk`; a `createRequire`-based adapter resolution for hoisted layouts; keeping the bundled `codex` bin off the `PATH` of a server started through an npm script; deriving the launch command from the adapter's `bin` field at runtime.
- Moving the server's node ahead of a different `node` listed earlier on a `PATH` that also lists the server's node directory; version-manager shims (they keep the prepend); Windows `PATH` delimiters.
- Validating the contents of `sessionMeta` beyond its top-level shape; any frame change beyond `acp-open`'s `sessionMeta` and `attach`'s `terminate`.
- A version-specific message when an ordinary attach is refused at relay time, bounding an automatic reconnect's retries against a peer that keeps refusing, signalling a parked peer's pid, and the parked-capture query in `src/remote/serve-detach-query.ts`.
