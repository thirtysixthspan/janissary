# Auto accept for detached remote harnesses

**Complexity: 6/10** — a new server-side detection/notification/capture subsystem inside `janus remote-serve` (gate detection, auto-approve injection, busy/ready classification, and captures all relocate off the client) and a new bounded protocol surface with a version bump and a non-attaching on-demand query path into a parked peer; replay-while-detached and delivery-ordering reuse the existing `DetachedPeer.pending`/`emit()` flush and the client's existing `SessionRouter`/`PendingFrames` hold-until-attached pattern rather than needing new coordination machinery, so this is real state-machine reasoning across many files but a narrower net-new surface than a from-scratch queue/store pair would be — server-only (no new web UI surface).

## Summary

Feature text (verbatim, from `product/backlog/features.md`): "auto accept should still operate on remote harnesses that are detached. this will allow harness to continue working in the background while detached. notifications should be queued and replayed when the harness is attached. similarly captures of the harness should be available."

Today, auto-approve, notifications, and screen captures for a harness tab are all computed by watching the *locally streamed* PTY bytes on the client side. `product/specs/remote-server.md`'s "What is computed where" section names screen captures, asciicast recordings, and busy-status detection explicitly as computed this way, but not auto-approve by name — verified against the code instead: `HarnessAutoApprover` (`src/harness/auto-approve.ts`) is driven by the same local `HarnessScreenReader` captures the spec does name, so it is local for the same reason (see Design decision 1). When a remote harness session is detached, the remote host keeps the harness process, its shell, and its workspace running for up to seven days (`product/specs/remote-server.md`, "Lifecycle and cleanup"), but nothing local is watching that stream any more — so auto-approve stops firing, no captures are produced, and any notification that would have fired is simply never generated. This plan closes that gap so a detached remote harness keeps clearing its own permission prompts, and so the user can see on reattachment what happened while they were away (queued notifications, and captures taken during the detached window).

## Design decisions

1. **Auto-approve, notification generation, and capture must run somewhere other than the local client while detached.** Established by existing behavior: `HarnessAutoApprover` (`src/harness/auto-approve.ts`) and `HarnessScreenReader` (`src/harness/screen.ts`) both operate on a locally streamed PTY, and the local PTY stream does not exist while a remote session is detached (no live channel). Where exactly this relocates to is an implementation decision (Phase 2, below).

   Concretely, today `HarnessScreenReader`'s constructor (`src/harness/screen.ts:36`) subscribes to `messageBus.on('pty', ['data', 'exit', 'resize'], …)` filtered by the id it was constructed with — it is never fed bytes directly. For a *local* harness tab, `PseudoterminalManager.spawn` (`src/pseudoterminal-manager.ts:31`) emits `messageBus.emit('pty', { type: 'data', id, data })` (and `:93` for resize, `:201` for exit) as its `spawnPty` `onData`/`onExit` callbacks; for a *remote* harness tab today, the local client's own relay (`src/remote/pty-session.ts:43`) does the same from bytes arriving over the channel — so the reader is always fed via the local process's `messageBus`, never directly. `RemoteProcesses.spawnPty` (`src/remote/serve-processes.ts:69-107`), by contrast, does **not** touch `messageBus` at all today: its `onData` callback only calls `this.send({ type: 'output', id: frame.id, data })` (`:92`), and `janus remote-serve` (`src/remote/serve.ts`, `src/remote/serve-processes.ts`) imports no `bus.js` symbol anywhere. So constructing a far-side `HarnessScreenReader`/`HarnessRecorder`-style observer (Proposed change 1) is not just "point the existing class at the far-side bytes" — `RemoteProcesses` must also start emitting `messageBus.emit('pty', { type: 'data' | 'exit' | 'resize', id, … })` on its own process-local bus, mirroring `pseudoterminal-manager.ts`'s three emit sites exactly, before any `HarnessScreenReader` built against it will ever fire. The `id` used for both the emit and the `HarnessScreenReader`/`HarnessAutoApprover` construction must be `frame.id` (the client-supplied spawn id `RemoteProcesses` already keys `writers`/`resizers`/`entries` by) — not `spawnPty`'s own internal counter id (`src/pty.ts:42`, `pty${++counter}`), which the existing `onData`/`onExit` callbacks already discard via the unused `_id` parameter (`serve-processes.ts:92-93`). Using the wrong id silently produces a reader that never matches any bus event.

2. **The harness process itself already continues running while detached.** Established by existing behavior (`product/specs/remote-server.md`, "Lifecycle and cleanup"): a detached remote session's harness process, persistent shell, and workspace are left intact server-side for up to seven days before expiry. This part of the feature text ("this will allow harness to continue working in the background while detached") is already true today; the gap this plan addresses is that auto-approve/notifications/captures don't keep functioning alongside it.

3. **Notifications must be queued while detached and replayed on attach.** Established by the feature text directly. This is new behavior: `product/specs/notifications.md` currently states the notifications tab has "no backlog" — "nothing that happened before the feed existed is replayed into it." A queue-and-replay mechanism already exists for the general case (any `ServerFrame`, not just raw terminal/transcript output), via the far side's bounded `pending` buffer in `src/remote/serve-detach.ts` — see decision 18: the new notification-carrying frames reuse it directly rather than needing a queue of their own.

4. **Captures taken during the detached window must be made available.** Established by the feature text directly ("similarly captures of the harness should be available"). Today `harness capture <name>` has no remote/server-side execution path — it only operates against the local `HarnessScreenReader`'s in-memory latest capture, which does not exist while detached.

5. **Auto-accept continuing while detached is automatic, not a new opt-in.** If auto-accept is already turned on for a tab when its remote session detaches, it simply keeps working; there is no new "continue while detached" toggle separate from today's auto-accept toggle.

6. **No safety cap on unsupervised approvals.** Auto-accept behaves identically while detached as while attached — no new limit that pauses it after some number of consecutive unsupervised approvals.

7. **Applies to both deliberate Detach and accidental reconnecting.** The harness keeps running server-side in both the deliberate-Detach state and the "reconnecting" state (client auto-retrying after an accidental drop), so this feature's behavior (continued auto-accept, queued notifications, retained captures) is not limited to deliberate Detach.

8. **A stand-down (auto-approve can't resolve a prompt) still fires and queues while detached.** Matches today's safety behavior: the harness pauses waiting on that prompt, and the stand-down notification is queued for replay on attach, same as any other notification.

9. **Captures reuse the existing mechanism and location, with no new browsing UI.** Captures taken during a detached window land in `.janissary/captures/` via the existing convention; there is no new UI to list/browse specifically the captures taken while detached.

10. **`harness capture <name>` works on-demand against a detached session, and automatic captures are also retained.** Two capture paths, both in scope: (a) the user can run `harness capture <name>` against a detached remote session at any time and get a fresh server-side snapshot, same command semantics as today; (b) the background screen-capture pipeline that already runs continuously (feeding auto-approve's gate detection) also persists a capture automatically during the detached window — bounded to one retained capture per detected permission gate, tying volume to the same meaningful events that already drive auto-approve notifications, rather than saving every internal poll. This bound needs no separate cap-enforcement logic: `HarnessAutoApprover.onCapture`'s existing loop guard (`src/harness/auto-approve.ts:104-121`) already calls its `notify` callback at most once per distinct gate occurrence, so a capture carried on that same call is already one-per-gate for free — see decision 19.

11. **Queued notifications and retained captures do not survive session expiry or termination.** If a detached session expires (the existing 7-day window) or is explicitly Terminated before ever being reattached, its queued notifications and captures taken during that window are discarded along with the session — matching today's existing expiry/terminate behavior. Nothing new is added to make them outlive the session.

12. **Replay is indistinguishable from live notifications.** On reattach, queued notifications replay into the notifications tab in their original chronological order, with no visual marking or grouping that sets them apart from notifications that happen in real time.

13. **No new Sessions-tab indicator.** The Sessions tab gains no new badge, count, or other at-a-glance indicator for a session that had activity while detached; the notifications tab (with its replay, per decision 12) is the only place this surfaces.

14. **Gate-detection/auto-approve/capture/busy-status always runs server-side, inside `janus remote-serve`, for remote harnesses — unconditionally, not just while detached.** This replaces today's approach of computing everything client-side from relayed PTY bytes (`product/specs/remote-server.md`, "What is computed where") with a single code path: the far side detects gates, injects approval keystrokes, and generates captures regardless of attach state; the client becomes a consumer of the results (live when attached, replayed when reattaching after detachment) rather than running its own detection. This is a deliberate change to today's already-working attached behavior, chosen over a dual local/server-side design to avoid two parallel detection implementations and a handoff race at the attach/detach boundary. Local (non-remote) harnesses are entirely unaffected — this only changes how remote harnesses are handled.

   This must explicitly include busy/ready status, not only gate-detection: today `HarnessScreenReader`'s capture callback is built by `captureWiring()` (`src/harness/capture-wire.ts:20-33`), which wires the auto-approver *and* `busyStatusHandler` (`src/harness/busy-status.ts:32-61`) off the exact same capture stream, and `busyStatusHandler` drives `managers.tab.addBusy`/`deleteBusy`/`markUnread` — the tab strip's busy dot and unread badge — for harness tabs generally, remote ones included, since `harnessRuntime()` (`src/harness/observers.ts:37-50`) builds one `HarnessScreenReader` per harness tab, local or remote, with no branch on `channel`. If Proposed change 4 stops constructing that reader for remote tabs (to remove the client-side detector per this decision), busy-status tracking and unread-badging for every remote harness tab — attached, reconnecting, or detached — silently regress unless busy/ready classification also moves server-side and is forwarded back to the client as its own signal. There is no reason to treat it differently from gate-detection: it is driven by the identical capture stream this decision already relocates, and leaving it client-side would reintroduce exactly the dual-implementation/handoff-race problem this decision exists to avoid.

15. **`harness capture <name>` against a remote harness must resolve differently depending on whether a local tab still exists.** While attached or reconnecting, the target tab is open (`product/specs/remote-server.md`, "Lifecycle and cleanup": a transport drop keeps tabs open) and `<name>` resolves via `managers.tab.byLabel` exactly as `resolveHarnessTab` (`src/harness/subcommands.ts:13-18`) does today — but per decision 14 the in-memory `latestCapture` callback `captureSubcommand` (`src/harness/subcommands.ts:23-36`) currently reads no longer applies to a remote tab, so this path must instead round-trip the new capture-request frame (Proposed change 3) over the live channel. After a deliberate Detach, by contrast, the session's tabs are already closed ("Detaching one closes every tab and navigator holding its channel" — `product/specs/remote-server.md`, "Lifecycle and cleanup"), so there is no open tab for `managers.tab.byLabel` to find at all; `<name>` must instead resolve against the persisted `RemoteSessionRecord.processes[].label` (`src/sessions/store.ts:27-52`), the same record the Sessions tab's detached rows already read (`src/sessions/manager.ts`, `src/sessions/store.ts`), and the request travels over a new one-off connection into the parked peer rather than requiring a full attach (see decision 16). While reconnecting (transport lost, retries in flight, no live socket at all), an on-demand capture request has nowhere to travel; it fails immediately with a clear error — `No capture available for "<label>" — connection is reconnecting.` — rather than queuing behind the retry, consistent with how Attach on a reconnecting row already means "try now" rather than "wait for it" (`product/specs/sessions-tab.md`, "Actions").

16. **A capture request against a fully detached (parked) session uses a new non-attaching query, not a full attach.** `DetachedPeer.accept()` (`src/remote/serve-detach.ts:104-144`) currently recognizes exactly one frame type before a connection is treated as attached — `attach` itself (`:118-121`); anything else is refused with `attach-result: accepted:false` and the socket is closed. Reusing the existing attach path for an on-demand `harness capture` would attach the peer (claiming its socket via `this.sink`, cancelling `this.expiry`, and driving the full local attach flow that recreates tabs — `src/remote/attach.ts`) just to read one capture, which is a far bigger and more disruptive side effect than the command has today. Instead, `accept()`'s pre-attach branch gains a second recognized frame type — a capture-request — answered over the same socket without ever setting `attached = true`, claiming `this.socket`, or touching `this.expiry`, so the peer stays exactly as parked as it was before the query and its 7-day expiry timer is untouched.

17. **Replayed notifications carry their original detection time, not the reattach time.** `notify()` (`src/notifications.ts:169-193`) always stamps a notification's header with `formatTimestamp(new Date())` — i.e. "now" — with no parameter for a caller-supplied time. Replaying a detached window's queued notifications through this unmodified would make every one of them read as having happened at the moment of reattachment, which defeats decision 12's "original chronological order" (several auto-approvals minutes or hours apart would all show the same reattach timestamp) and undermines the feature's own point — showing the user what happened, and when, while they were away. `notify()` gains an optional timestamp parameter, defaulting to `new Date()` so every existing call site is unaffected; the client's replay handler (Proposed change 4) passes each queued frame's original detection time — the `capturedAt` value already carried on `ScreenCapture` (`src/harness/screen.ts:12, 73`) — through to it via the new frame from Proposed change 3.

18. **Gate-event notification frames need no new queue: `DetachedPeer`'s existing `pending` buffer (`src/remote/serve-detach.ts`) already does the job as-is.** `DetachedPeer.emit(frame: ServerFrame)` (`:53-68`) is generic over every `ServerFrame` variant — it already queues any frame that is not a `pty`-mode `output` into `this.pending`, bounded by `PENDING_BUFFER_BUDGET_BYTES`, and `accept()` (`:131-138`) already flushes the whole thing in arrival order (exit frames sorted last) the instant a peer attaches, then clears it. A new gate-event frame reaches this path for free the moment the far-side wiring (Proposed change 1) calls the same `send`/`emit` callback `output`/`exit`/`transcript` already use (`RemoteServer.emit` → `DetachedPeer.emit`, `src/remote/serve.ts:68, 188`) — no new field, no new bounding logic, and decision 11 (discarded with the session) and decision 12 (delivered once, in original order) already hold for it exactly as they hold for `transcript` today. This does **not** apply to busy-transition frames — see decision 20.

19. **The automatically-retained per-gate capture (decision 10b) travels inline on the gate-event frame itself, not through a separate store or frame.** This mirrors what `notify(message, capture)` already does locally: `HarnessAutoApprover`'s `notify` callback already carries the triggering `ScreenCapture` alongside the message (`src/harness/auto-approve.ts:95, 120`), and `buildAutoApprover` already turns that pair into a `writeCaptureFile` call plus a `notify()` call in one step (`src/harness/auto-approve-wire.ts:17-19`). The far side's gate-event `ServerFrame` (Proposed change 3) reuses that same shape — event kind, tab label, message text, original detection timestamp (decision 17), and an optional raw capture text field, base64-encoded the same way `output`/`transcript` already are (`toWire`, `src/remote/protocol.ts:285-299`) — so the client's translation (Proposed change 4) writes the capture file and calls `notify()` in one step exactly as the local path does today, whether the frame arrived live or was replayed from `pending` after a detach. Only on-demand `harness capture <name>` (decisions 15-16) needs its own request/reply frame pair, since that path asks the far side for a fresh snapshot at an arbitrary moment rather than one tied to a gate event already being reported.

20. **Busy/ready transitions deliver only the current status once on attach — no history, no replay, no queue.** Unlike gate-event notifications (a log of discrete events, where full chronological replay is the point — decision 12), busy/ready status is a continuous "current state" indicator (the tab strip's busy dot and unread badge), not a log; replaying every intermediate flip the harness made while detached would make the busy dot visibly flicker through history the user never needed to see. Busy-transition frames are therefore **not** routed into `DetachedPeer.pending` (the carve-out decision 18 notes) and need no queue at all: the far side's busy/ready classifier (Proposed change 1) already has to retain its current classification to detect the *next* transition (`classifyBusy`, `src/harness/busy-status.ts:7`), so that same retained value is all `accept()` needs — on a successful attach, it sends exactly one busy-transition frame reflecting the live current state, sourced from the classifier's retained value rather than from any buffered history. This is the smaller mechanism per decision 15's non-attaching-query precedent: derive the answer on demand from state already tracked, rather than accumulate and replay events that were never meant to be a log.

## Proposed changes

1. **`src/remote/serve-processes.ts` (far side) — wire a server-side detection pipeline per spawned remote harness.** Alongside the existing `onData` forwarding to `output` frames, `spawnPty` (`:87-99`) also emits `messageBus.emit('pty', { type: 'data', id: frame.id, data })` (and matching `resize`/`exit` emits at the finish/resize sites), mirroring `src/pseudoterminal-manager.ts:31, 93, 201` exactly (see decision 1) — without this, nothing built against `messageBus` ever fires. Against that bus, construct a `HarnessScreenReader` (keyed by `frame.id`, not `spawnPty`'s own internal id — decision 1) and a `HarnessAutoApprover` whose `approve(keystroke)` callback calls the already-existing `input(id, keystroke)` (`:55`), plus a busy/ready classifier reusing `classifyBusy`/`BUSY_TABLE` (`src/harness/busy-status.ts`) off the same capture stream (decision 14), retaining its current classification value (decision 20) rather than discarding it after each transition. The approver's `notify`/capture callbacks call the same `send` callback `spawnPty`'s `onData`/`onExit` already use to emit `output`/`exit` (`:92-93`) with a new gate-event frame carrying the message, timestamp, and capture text — rather than the client-side `notify()`/`writeCaptureFile()` calls it drives today. `RemoteServer.emit`/`DetachedPeer.emit()` already queue and replay this exactly like `output`/`exit` (decision 18). The busy classifier's transitions do **not** go through `send`/`emit` while detached at all (decision 20) — they only update the classifier's retained current-value; a busy-transition frame is sent live while attached, and on reattach `DetachedPeer.accept()` (Proposed change 2) reads the retained current value directly and sends exactly one such frame. This is new wiring analogous to `src/harness/observers.ts`'s `harnessRuntime()` and `src/harness/auto-approve-wire.ts`'s `buildAutoApprover()`, but built against far-side primitives instead of `Managers`.

2. **`src/remote/serve-detach.ts` — extend `DetachedPeer` with a non-attaching capture-request branch and a one-shot current-busy-status send on attach; the notification path needs no new state (decisions 18-19).** `accept()`'s pre-attach branch (`:117-121`) gains a second recognized frame type — a capture-request — answered directly over the connecting socket without setting `attached = true` or touching `this.expiry` (decision 16), so an on-demand `harness capture` against a parked session never claims the peer's socket or cancels its 7-day expiry the way a real `attach` would. Gate-event frames from Proposed change 1 reach `pending` through the existing `emit()` unchanged. Separately, on a successful attach (after the existing `pending`/`ReplayHistory` flush), `accept()` reads the busy classifier's retained current value (decision 20) and sends exactly one busy-transition frame reflecting it — this value is read fresh at attach time, not queued, so it needs no buffer of its own. `src/remote/serve-detach.ts` is already close to the 200-line `max-lines` limit before this change (run `./scripts/run.mjs lint-files` on it early to check); if the new branches push it over, extract into a sibling module (e.g. `src/remote/serve-detach-capture.ts`) the way `src/remote/serve-notice.ts` was split out of `src/remote/serve.ts`, rather than compacting `DetachedPeer` to fit.

3. **`src/remote/protocol.ts` — new narrow frame types, plus the version bump every prior addition to this file has taken.** A `ServerFrame` variant carries a detected/approved gate event (used both for live delivery while attached and for queued replay after detach) with the fields `notify()` needs to reconstruct a client-side notification (event kind, tab label, message text, original detection timestamp per decision 17) plus an optional raw capture text field carried and encoded the same way `output`/`transcript` already are (decision 19) — not a reference to a separately-stored capture. A second `ServerFrame` variant carries a busy/ready transition (decision 14) with the fields `managers.tab.addBusy`/`deleteBusy`/`markUnread` need. A `ClientFrame`/`ServerFrame` request/reply pair covers on-demand capture requests against a remote harness — over the live channel while attached/reconnecting (decision 15), or via the new non-attaching query from Proposed change 2 while fully detached (decision 16). All new types are added to the existing `CLIENT_FRAME_TYPES`/`SERVER_FRAME_TYPES` exhaustiveness tables (`:259-271`) and `toWire`'s encoding switch (`:285-299`) for the new capture-text field. As with every prior addition to this contract, `REMOTE_PROTOCOL_VERSION` (`:90`, currently `17`) bumps to `18`, and the versioned comment history immediately above it (`:20-89`) gains a new numbered paragraph naming each new frame and what a stale peer or stale local build would experience without it — the same pattern versions 1 through 17 already establish, not an optional step.

4. **`src/harness/observers.ts` / `src/harness/auto-approve-wire.ts` / `src/remote/pty-session.ts` / `src/remote/channel-sessions.ts` / `src/remote/channel-pending.ts` / `src/remote/channel.ts` — stop running local detection for remote harness tabs, and route the new frames the same way `output`/`exit` already travel.** `harnessRuntime()` (`:37-50`) branches on `channel`: when present (a remote tab), it skips constructing the `HarnessScreenReader`+`captureWiring()` pair (auto-approve *and* busy-status, per decision 14) that today treats relayed remote PTY bytes as a local stream (fed from `src/remote/pty-session.ts:43`'s bus emission), while still constructing `HarnessRecorder` and the transcript `tailer` exactly as today — asciicast recording and transcript tailing are unaffected by this plan and stay client-side (see Out of scope). `HarnessRuntime`'s `reader` field (`src/harness/runtime.ts:17`) becomes optional (`reader?: HarnessScreenReader`) and `dispose()` guards it the way `recorder`/`tailer` already are (`:28-29`), since a remote tab's runtime no longer has one to dispose.

   In place of the removed local detector, the client becomes a consumer of the new protocol frames from Proposed change 3. Both are process-id-keyed exactly like `output`/`shell-history`/`exit`, so they extend the same three places those already flow through instead of needing new coordination elsewhere: `SessionListener` (`src/remote/channel-sessions.ts:11-17`) gains optional `onGateEvent`/`onBusyTransition` callbacks alongside `onHistory`; `SessionRouter` gains `gateEvent()`/`busyTransition()` methods mirroring `history()`'s three-line shape exactly (`:97-101`) — deliver to the listener if the tab already exists, else `this.pending.hold(frame)` if an attach is still rebuilding tabs; `PendingFrames`' `PendingFrame` type (`src/remote/channel-pending.ts:16`) widens to include the two new variants; and `RemoteChannel.dispatch()` (`src/remote/channel.ts:245-247`) gains two lines routing the new frame types to the router, beside the existing `output`/`shell-history`/`exit` lines. This is what makes a gate-event or busy-transition frame that arrives mid-attach (before the rebuilt tab's listener registers) wait for that listener and then deliver in order, exactly as a `shell-history` frame already does today — no new logic in `src/remote/manager.ts` or `src/remote/attach.ts` is needed for this.

   `createRemotePtySession`'s `channel.attach(id, { onOutput, onExit })` call (`src/remote/pty-session.ts:42-45`) — the same place a remote harness tab's `SessionListener` is built today — gains `onGateEvent`/`onBusyTransition` handlers, wrapped in the same `deliver()` ordering helper already used for `onOutput`/`onExit` (`:38-41`). A gate-event frame is translated into the same local `notify()` call (passing the frame's original timestamp per decision 17, and writing the inline capture text to a file per decision 19) local detection produces today, and a busy/ready-transition frame is translated into the same `managers.tab.addBusy`/`deleteBusy`/`markUnread` calls `busyStatusHandler` produces today — so the notifications tab, capture file location/convention, busy dot, unread badging, and stand-down UX are all unchanged from the user's point of view. Local (non-remote) harness tabs keep their existing wiring untouched.

5. **Docs.** `product/specs/remote-server.md`'s "What is computed where" section (`:271-277`) currently names screen captures, asciicast recordings, and busy-status detection as computed locally, but does not name gate-detection/auto-approve at all — the edit must add gate-detection/auto-approve and busy-status explicitly ("computed server-side in `janus remote-serve`, delivered to the client live or replayed on attach") while leaving asciicast recordings named as still-local, matching Proposed change 4's scope. `product/specs/harness.md`'s auto-approve section (`:126-154`, "How it works" at `:293-319`) gains a note that this applies identically whether the remote tab is attached or was detached/reconnecting. `product/specs/notifications.md` gains a note scoping the new queue-and-replay behavior specifically to detached-remote-harness reattachment, leaving the "no backlog" rule for ordinary tab reopening unchanged.

6. **`src/harness/subcommands.ts` — `harness capture <name>` resolves a remote target through the new frames, by tab when one exists and by session record when it does not.** `resolveHarnessTab`/`captureSubcommand` (`:13-36`) is extended: for a remote harness tab that is still open (attached or reconnecting), the local in-memory `latestCapture` callback it reads today no longer applies (decision 14), so it instead sends the new capture-request frame over the live channel and writes whatever comes back through the existing `writeCaptureFile` path — while reconnecting, with no live socket to send it over, it fails immediately with `No capture available for "<label>" — connection is reconnecting.` (decision 15). For a `<name>` with no matching open tab, a new resolution branch checks the persisted `RemoteSessionRecord.processes[].label` (`src/sessions/store.ts:27-52`, via `SessionsManager`) before falling back to today's "No tab labeled" error; a match opens the new one-off, non-attaching connection from Proposed change 2 to the parked peer, sends the capture-request, writes the reply to a local file the same way, and leaves the session exactly as detached as it was.

## Out of scope

- A new, separate "continue while detached" toggle — this is an automatic extension of the existing auto-accept toggle (decision 5).
- A safety cap that pauses auto-accept after some number of unsupervised approvals (decision 6).
- A new UI to list or browse captures taken specifically during a detached window — captures reuse the existing `.janissary/captures/` mechanism (decision 9).
- Any new Sessions-tab badge, count, or indicator for detached-session activity (decision 13).
- Visual marking or grouping of replayed notifications to set them apart from live ones (decision 12).
- Preserving queued notifications or retained captures beyond the session's existing 7-day expiry or an explicit Terminate — both are discarded with the session, same as today (decision 11).
- Retaining every automatic background screen-capture taken while detached — only one per detected permission gate is kept (decision 10b).
- General notifications-tab reopening (closing and reopening the tab locally, with no remote detach involved) — that remains backlog-free exactly as `product/specs/notifications.md` specifies today; this plan's queue-and-replay is scoped specifically to a detached remote session's reattachment.
- Multiple simultaneous local attach points to the same remote session — this plan assumes the existing single-attach model (`src/remote/manager.ts`) is unchanged.
- Asciicast recording (`HarnessRecorder`) during a detached window — recording stays client-side and unmodified (Proposed change 4); a detached remote harness produces no `.cast` output for the gap, exactly as today, since there is no local process to write one.
- Replaying the full history of busy/ready transitions that happened while detached — only the current status is delivered once on attach; intermediate flips are not queued, logged, or shown anywhere (decision 20).
