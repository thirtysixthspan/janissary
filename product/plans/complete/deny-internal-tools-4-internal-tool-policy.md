# Turn harness built-in tools off at launch for role sessions

**Complexity: 5/10** — ~70 added production lines in one new pure module plus a small merge in `launch.ts`, 10 behavioral requirements (three harnesses' confirmed keys including codex's full tool-feature set, model/effort preserved, no `never` approval, unknown harness untouched), 11 test scenarios across four test files (p=5.45).

## Goal

Role-based ACP connections — the core `ask` and `tell` sessions — deny every tool the agent harness ships with. This subplan adds layer one of `product/plans/complete/deny-internal-tools-for-role-acp-connections.md`: each role entry's launch carries a harness-specific configuration that turns the harness's built-in tools off, so they are never offered to the model. The only thing such an agent may then do is run the Janissary native commands its role grants and that are enabled for agents in `commands.json`. Layer two (the permission-request denial, recorded since subplan 2) stays as the backstop.

Feature text: "Configure all role based acp connections to deny all internal tool usage by default. The agent should only be allowed to execute janissary commands that have been enabled for agents in commands.json."

## Design decisions and dependencies

Builds on subplan 1 (`product/plans/complete/deny-internal-tools-1-bundle-acp-adapters.md`: the bin-named claude and codex launches, the pinned adapter versions the keys below were confirmed against, and codex's model and effort moved into `CODEX_CONFIG`) and subplan 3 (`product/plans/complete/deny-internal-tools-3-session-meta-passthrough.md`: `connectAcp` sends `AcpOptions.sessionMeta` as `session/new` `_meta`, `src/acp/index.ts:132`). Subplan 2's denial record is the layer-two surface this layer sits in front of. All three are already on this branch, so this subplan has no ordering dependency left; subplans 5 and 6 build on it.

- "Internal tools" means the tools the harness itself provides to the model — shell, file read/write/edit, search, web fetch and search, sub-agents — not Janissary native commands, which run through the existing tool loop. MCP servers a user configured in their own harness settings are not built-in tools; any call to one still raises a permission request and meets layer two.
- The Janissary command gate is unchanged: a role's grants are intersected with effective agent access in `commands.json`, the primer lists only those commands, and each emitted command is re-checked before it runs (`product/specs/acp.md`, `product/specs/application-commands.md`).
- Two layers. Layer one disables the harness's built-in tools at launch so they are never offered to the model. Layer two is the existing permission-request denial in `connectAcp` (`requestPermission` in `src/acp/index.ts`, `decidePermission` in `src/acp/tools.ts`), kept as is.
- No opt-out in this version. Every `ask` and `tell` connection denies all internal tools, always. `roles.json` gains no field.
- Scope is core `ask` and `tell` sessions only: everything launched through `AcpSessionManager.session` and `acpLaunchForEntry`, local and remote, including plugin-owned ask sessions and the launcher summarizer. Monitor personas (`src/monitor/acp.ts`), conversations (`src/conversations/sessions.ts`), editor persona queries, and autonomous `agent` runs (`src/agent/execute.ts`, which builds its own `OPENCODE_CONFIG_CONTENT`) keep their current launches (`acpLaunchFor`) and permission policies. `acpLaunchFor` is unchanged.
- A role entry whose harness has no known deny-all configuration (any harness other than opencode, claude, and codex) still launches if `acpLaunchForEntry` can launch it, protected by layer two alone, with no warning. A key that could not be confirmed against the installed harness would be omitted on the same rule; every key listed below was confirmed, so none is omitted.
- No harness takes its configuration on the command line. `codex-acp` 2.3.0 ignores its argv (its entry point in `node_modules/@agentclientprotocol/codex-acp/dist/index.js`, `startAcpServer`, reads only `CODEX_PATH`, `CODEX_CONFIG`, `DEFAULT_AUTH_REQUEST`, and `MODEL_PROVIDER`), so the canonical plan's codex `-c` overrides would be silently dropped. Every codex setting travels in the environment instead. The module's result therefore has no `args` field.

### Confirmed keys, per harness

The module's comments record, per key, the version and the file it was confirmed against, as below.

- **opencode** — merge `permission: "deny"` into the existing `OPENCODE_CONFIG_CONTENT` JSON, beside `model`. Confirmed against opencode 2.2.5 (the `@opencode/cli` binary on the developer's PATH; opencode is not bundled, so there is no pinned copy under `node_modules/`): its config schema declares `PermissionConfig` as either a single `ask`/`allow`/`deny` string or a per-tool object, and the config loader turns a top-level string `permission` into one rule `{ action: "*", resource: "*", effect: "deny" }`; a `deny` rule fails the call with `Permission.BlockedError` without asking. Opencode is unpinned, so a user's older opencode that rejects the single-value form is a known ceiling, not a case this subplan handles.
- **claude** — `sessionMeta` of exactly `{ claudeCode: { options: { tools: [] } } }`, and no extra env. Confirmed against `@agentclientprotocol/claude-agent-acp` 0.97.0, `dist/acp-agent.js` (`const tools = userProvidedOptions?.tools ?? …`, where `userProvidedOptions` is `_meta.claudeCode.options` of `session/new`, passed to the SDK `query` as `tools`), and its pinned `@anthropic-ai/claude-agent-sdk` 0.3.310, `sdk.d.ts` `Options.tools`: "`[]` (empty array) - Disable all built-in tools". Janissary initializes with `clientCapabilities: {}` (`src/acp/index.ts:127`), so the adapter adds no client-backed file or terminal tools either.
- **codex** — two environment entries, confirmed against `@agentclientprotocol/codex-acp` 2.3.0 (`dist/index.js`) and the `@openai/codex` 0.164.0 binary it depends on (`node_modules/@openai/codex-darwin-arm64/vendor/aarch64-apple-darwin/bin/codex`):
  - `INITIAL_AGENT_MODE: "read-only"` — the most restrictive sandbox. The adapter sends `sandboxPolicy` and `approvalPolicy` on every `turn/start` from the session's agent mode (`sendPrompt`, `approvalPolicy: agentMode.approvalPolicy`), which overrides any `sandbox_mode` or `approval_policy` in the config, so the sandbox can only be set through the mode. `AgentMode.getInitialAgentMode` reads `INITIAL_AGENT_MODE`; its `read-only` mode is sandbox `{ type: "readOnly", networkAccess: false }`, approval `on-request`, approvals reviewer `user`. The default mode (`agent`, "Auto review") hands approvals to codex's automatic reviewer instead of the client, so without this entry many approvals would never reach layer two. Only `agent-full-access` uses approval `never`; the module never selects it, and Janissary never calls `session/set_mode` (no caller in `src/`), so the mode stays read-only for the session.
  - `CODEX_CONFIG` — the existing JSON (`model`, and `model_reasoning_effort` when set) with `web_search: "disabled"`, a `features` object, and a `tools` object merged in (lists below). The adapter passes the parsed object as the `config` of `thread/start` (`createSessionConfig`), and itself merges a nested `features` object into it (`forceGitRootTurnDiffPaths`), which is why the nested shape is used. `web_search`: the codex binary's own config message reads "Set `web_search` to `"live"`, `"indexed"`, `"cached"`, or `"disabled"` at the top level". Never add an `approval_policy` key.
- Decision: codex turns off every built-in tool it has a confirmed switch for, not only the shell and web search. The canonical plan's goal is that role connections deny every tool the harness ships with — shell, file read/write/edit, search, web fetch and search, sub-agents — and its three codex settings were the mechanism it guessed, not a ceiling. Non-tool features stay as they are.
- How each codex key was confirmed. Every `features` name below is listed by `codex features list` (0.164.0), and the binary's `--disable <FEATURE>` help says it is "Equivalent to `-c features.<name>=false`", so each is a valid key. Each one also exposes a model-callable tool, on one of these grounds: codex 0.164.0 itself sets it, as `features.<name>`, in the override list it applies to its own tool-free "temporary structured thread" (a string in the binary that runs from `features.apps` to `tools.update_plan.enabled`, followed by `:read-only`); or the tool's own description is in the binary (goals' `create_goal`/`update_goal`/get-goal descriptions, multi-agent's `spawn_agent`).
- Codex `features`, all set to `false`. On by default in 0.164.0:
  - `shell_tool` and `unified_exec`: the shell, both forms. `unified_exec` is the `exec_command`/`write_stdin` form.
  - `view_image`: the image file read tool.
  - `image_generation`: the image generation tool.
  - `multi_agent`: sub-agent spawning (`spawn_agent`, `wait_agent`, and the rest).
  - `apps`: ChatGPT connector (apps) tools.
  - `goals`: the `create_goal`/`update_goal`/get-goal tools.
  - `tool_suggest`: the plugin and connector suggestion tool.
- Off by default, set to `false` anyway because a user's own `~/.codex/config.toml` could turn them on and `CODEX_CONFIG` wins: `multi_agent_v2`, `code_mode`, `request_permissions_tool`, `standalone_web_search`. All four are tool-exposing and in codex's own tool-free list.
- Codex `tools` object, confirmed from the same tool-free list: `tools: { update_plan: { enabled: false }, experimental_request_user_input: { enabled: false } }`. These are the plan-update tool and the ask-the-user tool; they are config keys, not features.
- Not disabled, because no switch could be confirmed:
  - `apply_patch` (file edits): 0.164.0 has no feature key for it. `apply_patch_freeform` is listed as `removed`, and the binary has no `include_apply_patch_tool` key. Under the read-only mode an edit asks for approval and meets layer two.
  - `sleep_tool`, `browser_use`, `browser_use_external`, `computer_use`, and `in_app_browser`: they are valid feature names and on by default. But they are not in codex's tool-free list, and no model-facing tool description for them was found in the binary, so whether they expose a model-callable tool in an app-server session is unconfirmed. They are left on, and any call they make is backstopped by layer two.
  - The other features in codex's tool-free list (`hooks`, `memories`, `shell_snapshot`, `context_management`, `current_time_reminder`, `token_budget`, `deferred_executor`, `code_mode_only`, `enable_fanout`) are not tool switches, or are modifiers or removed, so they stay as they are.

### Module and merge

- Module shape: one pure function, `internalToolDenial(harness, baseEnv)` in the new `src/acp/internal-tools.ts`, takes the role entry's harness name (a `string`, as `RoleEntry.harness` is) and that harness's base launch environment, and returns an exported `InternalToolDenial` of `{ env?: Record<string, string>; sessionMeta?: Record<string, unknown> }`, or `undefined` for any other harness. It takes the base environment so the opencode and codex cases can return `OPENCODE_CONFIG_CONTENT` / `CODEX_CONFIG` as the base JSON with the deny-all merged in (the caller's env spread then replaces the base value with the merged one); this keeps the merge pure and testable in the module. The module does no I/O.
- JSON merge rule (opencode and codex): parse the base value with `JSON.parse` into `unknown` and narrow it with `isRecord` from `src/value-guards.ts` (this keeps `@typescript-eslint/no-unsafe-assignment` quiet); an absent key or a non-object result starts from an empty object. The deny-all keys are written after the base keys, so they win. For codex, `features` is the base `features` object (when it is one) with the twelve feature names above set to `false`, and `tools` is set to the two-entry object above (the base never has a `tools` key). Keep the twelve names in one exported constant list in the module so the test pins the same set. `acpLaunchForEntry` always supplies valid JSON, so no parse-error path is added.
- The two primer lines are not in this subplan; subplan 5 (`product/plans/draft/deny-internal-tools-5-role-primer-lines.md`) adds them to `src/acp/internal-tools.ts` as constants.
- `src/acp/session-manager.ts`: nothing to pass — both launch sites already spread `...launch` (`createRemoteAcpSession(channel, { ...launch, id: …` and `connectAcp({ ...launch, cwd, …`); the change is only that the spread now carries `sessionMeta`. Locally it reaches `connectAcp` (subplan 3). The remote site's spread also carries it, but `createRemoteAcpSession` (`src/remote/acp-session.ts`) destructures only `id, command, args, env, offline, autonomous, effort`, so it drops `sessionMeta` until subplan 6; until then a remote claude role session has layer two only. The opencode and codex deny-all travel in `env`, which the `acp-open` frame already carries, so remote opencode and codex role sessions get layer one now.

## Out of scope

- Any opt-out, per-role override, or `roles.json` field for internal tools.
- Changing which native commands a role grants or how `commands.json` agent access is evaluated.
- Codex built-in tools with no confirmed off switch in 0.164.0 (`apply_patch`, `sleep_tool`, `browser_use`, `browser_use_external`, `computer_use`, `in_app_browser`); they stay behind the read-only mode and layer two.
- User-configured MCP servers in any harness's own settings; layer two handles their calls.
- Supporting opencode builds older than the single-value `permission` form.
- Monitor, conversation, editor persona, and autonomous `agent` run launches and permission policies, including their adapter packages and their `npx` claude launch.
- Warning the user when a harness cannot be configured.
- The primer lines (subplan 5) and the remote `sessionMeta` field (subplan 6).
