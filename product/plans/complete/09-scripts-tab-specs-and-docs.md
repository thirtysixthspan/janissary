# Scripts tab specs and docs
**Complexity: 3/10** — documentation only, with no code, but about a dozen edit sites across eight files, stale topic counts the source plan does not name, and about twenty verbatim strings to match against the code.

## Goal

Write the behavior spec for the tab and update every doc the source plan names. Also update the docs the plugin checklist and the spec rules require, so that the docs match the code once `08` lands.

## Design decisions and dependencies

This subplan depends on `08-scripts-plugin-registration`, so the spec describes the code that exists and not a plan for it.

- `product/specs/scripts-tab.md` is the behavior spec. It lists the exact text of every feed line, every dialog line, and every button label, copied from the code as it now stands. That text matches the source plan except for two wordings the source plan did not have, the execute rejection line `Could not run runscript "<name>".` and the directory line `Could not use the runscripts directory.`, which the failure table quotes as built and the owner has yet to confirm. The filename `scripts-tab.md` is free in `product/specs/`. It covers the edge cases as their own section: an invalid name, a missing row, a clone whose name is taken, a symlinked or non-regular file, an empty or missing directory, a symlinked `.janissary`, a delete while an editor tab holds the file, and a save of that tab after the delete. Save recreates the file through the editor's existing save path. That claim is to be verified in `10`. The spec also records the refresh ceiling and its upgrade path: if the tick ever shows up in profiles, the refresh moves to the state broadcast. The spec states the refresh gate rather than a start and stop lifecycle: the tick reads nothing unless an open tab belongs to a plugin that lists `runscripts` in its notifications, and that check runs before any file or schedule read. The reason is that the plugin API has no hook for a tab closing, since a plugin's `dispose` runs only when the plugin is disabled or the host shuts down (`src/plugins/host.ts`). The tick subscription exists only when some declaration lists `runscripts` (`src/plugins/host-channels.ts`). It names the implementation by module path, as `product/specs/scheduling.md` does for `parseScheduleCommand` in `src/schedule/index.ts`: `ScriptsTab` in `web/src/plugins/scripts/ScriptsTab.tsx`, the `runscripts` topic in `src/plugins/api-topics.ts`, `runRunscriptNow` in `src/commands/execute.ts`, the `ensureDirectory` action in `src/plugins/runscript-topic-actions.ts`, and the refresh in `src/schedule/system/runscript-refresh.ts`.
- Decisions the spec records where the source plan left the behavior open. The `scripts` command sends the `ensureDirectory` action on every run, including a run that only focuses an open tab. A valid name with no file reports `No runscript named "<name>".` from every action that reads it (`execute`, `open`, `clone`, and `delete`). A name that is not a valid runscript name is dropped with no feed line, so the source plan's "not in the catalog, do nothing" is replaced by that rule. A `create` that fails before it picks a name reports `untitled`, and one that fails after the pick reports the picked name. A listing that fails, such as a symlinked `.janissary`, shows the empty state, and the refresh writes no feed line for it, while the `scripts` command reports `Could not use the runscripts directory.` when it runs. A click outside the delete dialog is swallowed and leaves the dialog open, as the schedules dialog does. `y` confirms, Escape and `n` cancel, Enter chooses the highlighted button, which starts on Cancel, and Left and Right switch the highlight. With no row selected, Down selects the second row and Up selects the first, as `nextListSelection` does, and its test pins that. The `execute` read refusal and the listing failure write no stderr cause line, while every other action failure from an exception writes one.
- `product/specs/scheduling.md`, the runscripts paragraph at line 13, gets a pointer to `[[scripts-tab]]` as its last sentence, after `An invalid name creates nothing.`: "The scripts tab lists these files and runs, duplicates, or deletes them; see [[scripts-tab]]." The pointer resolves to `product/specs/scripts-tab.md`, as `[[tab-plugins]]` resolves to `product/specs/tab-plugins.md`. The exclusion paragraph at line 15 gets one clause, inserted before the full stop that ends its first sentence, after "even if no system schedule has been saved": ", and the scripts tab runs the same step each time its `scripts` command runs, but its refresh tick does not repeat it." Without that clause, the spec would say that cataloging always ensures exclusion while the tab's tick reads without that step. The source plan does not ask for this clause, so it is an addition made for accuracy.
- The `help.md` Commands table gets a `scripts` row between `schedules` and `search`, which keeps the table alphabetical, as `src/commands.test.ts` checks. The row text is: `Open the project's runscripts in .janissary/scripts. Run, duplicate, or delete one from its row, or create one with **+**.` It is 122 characters, under the 200 that `src/commands.test.ts` allows for any description.
- `documentation/user-documentation/command-bar/commands.md` gets a `scripts` row in its table, placed directly after the `execute <name>` row because the two belong together. The row reads: `Open a list of the project's runscripts. Use a row's buttons to run, duplicate, or delete one, or **+** to create one.` Its section headed `edit` and `execute` runscripts (the heading carries code formatting) gets one sentence that points at the tab and describes the three row buttons and double-click, in user terms, with the tab and button names in bold as the user-documentation guideline asks. The new row and sentence name no files and no functions. The section's first paragraph already names `.janissary/scripts/<name>.rs`, which predates this change and stays.
- `documentation/user-documentation/command-bar/plugins.md`, the bundled plugin page, gets a `scripts 1.0.0 api=2 state=declared` line in its sample `plugins` output, between the `schedules` and `search` lines, since the manifest declares the current API version. Its plugin-tab sentence gets the scripts list beside the schedules list and `scripts` in the command list. The sample's other lines stay as they are.
- `documentation/developer-documentation/tab-plugins.md` changes the sentence that says v2 defines five topics to say six. It lists the six in the order `src/plugins/api-topics.ts` declares them (`schedules`, `conversations`, `sessions`, `databases`, `tabs`, `runscripts`), and it drops the clause "a sixth kind of state reaches a plugin the same way", which the five-item list never matched. The topic-action paragraph gains one sentence after its code example, as the first sentence of the paragraph that begins "Both are scoped to topics your manifest declared": `runscripts` defines `execute`, `delete`, `clone`, `open`, `create`, and `ensureDirectory`, returns nothing, and sends each failure to the notifications feed. The API changelog gets one bullet in the v2 section, after the `topicAction()` bullet: the new topic is additive, and `TAB_PLUGIN_API_VERSION` stays at 2. The changelog bullet is required by item 9 of the plugin checklist, which asks for a changelog reference on every API change, and a new topic is one. The assertion in `src/plugins/documentation.test.ts` about the changelog's capability count keeps passing, since no capability is added.
- `product/specs/tab-plugins.md` gets three edits, none of which the source plan lists. The count at line 113 says "five kinds of host state" and lists them, so it becomes six and gains the runscripts slice, which is the rows the scripts tab shows. The topic-action paragraph at line 119, which lists topic actions by kind, gets the runscripts actions in one sentence. The intents paragraph at line 147 lists the plugins that declare intents as one table, and `scripts` joins that list, since the scripts plugin uses `defineIntents`. The plugin checklist requires the spec to describe the behavior.
- `ai/guidelines/plugins-tabs.md`, the sentence that says "v2 defines four topics", is stale. It also omits `tabs`. The code, `src/plugins/api-topics.ts`, and the developer docs say five before this change and six after it, so the sentence becomes "six topics" and lists all six. It is fixed here. This is a one-line correction, and the source plan does not list it.

## Proposed changes

- Create `product/specs/scripts-tab.md`. Its sections are: purpose and command; the tab's rows; the live list and the refresh ceiling; row actions; keyboard; the create, clone, delete, and execute behaviors; the failure text table; edge cases, which record the known schedules-tab divergence; and out of scope. The wording is verbatim from the code. The spec lists each feed line and each dialog line once, and says which action produces it.
- Edit `product/specs/scheduling.md` as described above.
- Edit `help.md`, `documentation/user-documentation/command-bar/commands.md`, `documentation/developer-documentation/tab-plugins.md`, `documentation/user-documentation/command-bar/plugins.md`, `product/specs/tab-plugins.md`, and `ai/guidelines/plugins-tabs.md` as described above.

## Tests

No new test files. The existing ordering test in `src/commands.test.ts` and the developer doc assertions in `src/plugins/documentation.test.ts` must pass. That documentation test checks only the capability facts, so the topic sentence and the changelog bullet are checked by reading the developer doc. Before finishing, check the spec's verbatim strings against the code with a plain search. Each string must appear in the code with the same text, and the spec quotes it once. The clone, delete, run, and create failures are built by the `failed` helper in `src/plugins/runscript-topic-actions.ts`, so they are matched against that helper's output rather than as literals. The list to check covers every feed line, the empty state, the dialog title and lines, the button labels, and the tooltips.

## Verification

Run `./scripts/run.mjs check-diff`. Read the new spec once against the source plan and confirm that no requirement from the source is missing. Confirm that `help.md` rows stay in alphabetical order, and that the new help row is under 200 characters.

## Out of scope

- A user documentation page of its own. The command reference is enough for a command that has one tab and no settings. A screenshot is not needed.
- The docs-screenshots tooling.
- Any change to the schedules tab, including its missing keyboard guard. The spec records that as a known divergence while the owner decides (see `product/plans/complete/scripts-schedules-keyboard-divergence.md`).
- Stale content that predates this change in the files this plan edits, such as the duplicate bullets in the v2 changelog and the `api=1` values in the sample `plugins` output.
- Any change to code. If the spec finds a gap in the code, the gap goes back to the subplan that owns it.
