# Connections and connection tabs

**Complexity: 8/10** — a new persisted record subsystem, a new topic and bundled plugin with two views on both sides, a core command moved into a plugin, async shell ACP delivery, an ACP cancel path with a remote frame and protocol bump, and a breaking plugin API v3 with a new frozen fixture.

## Summary

ACP sessions started from a shell tab have no lasting home. A prompt used to stream into a core response panel above the shell's command bar, the exchange lived only in that tab's in-memory log, and once the tab closed or the session reset there was nothing to go back to. The connections popup named the session as `acp:<provider/model>`, but in a shell tab its rows did nothing when clicked.

This feature gives core ACP sessions and autonomous agent runs a persistent place to be monitored and controlled. A new **connections tab** lists every live connection plus every retained ACP and agent record. A **connection tab** shows one record's full interaction: metadata, prompt blocks, thinking, tool, plan, and permission activity, final answers, and lifecycle controls. Tracked records survive their tab, their session, and an application restart, and appear once in the list rather than also as live catalog rows. The ACP response panel leaves the shell tab: a shell that launches an ACP prompt gets on with other work and appends the settled answer once at the current output bottom as rendered Markdown beneath an echo of the exact typed line. The session's row in the connections popup opens its connection tab.

Terms used throughout: the **connections tab** is the list tab. A **connection tab** is a per-record tab. The **connections popup** is the existing floating per-tab window (`ConnectionWindow`, `product/specs/connection.md` § Connection window). The sessions tab for remote sessions (`product/specs/sessions-tab.md`) is unrelated and unchanged.

Source: the first `## ready` entry of `product/backlog/features.md` (an untitled bullet beginning "ACP sessions should be tracked in a new tasks tab"). The user renamed the tabs from "tasks"/"task" to "connections"/"connection".

## Design decisions

### Product

1. The connections tab lists connections. Tracked core ACP sessions and agent runs appear both open and closed, each opening in its own connection tab. Monitor and editor-persona ACP connections are live-only rows: they appear while open, read `Open`, focus their owning tab when opened, and leave no record. A connection tab shows one tracked ACP session's or agent run's transcript, thinking, turn taking, model output, and lifecycle controls.
2. Both tabs are modelled on the conversations plugin: a list tab with a fixed instance key, plus one tab per record keyed by its durable id, fed by a host notification topic (`product/specs/conversations.md`).
3. The ACP response panel is removed from the shell tab. When an ACP prompt is launched from the shell tab, the shell renders only its settled answer.
4. The ACP connection stays listed in the connections popup, as it already is (`acp:<provider/model>`). Clicking that row, pressing Enter on it, or pressing Space opens or focuses its connection tab. Rows carrying a live tab-scoped ACP reference resolve to that tab's current record.
5. The purpose is a persistent place to monitor and control ongoing and past ACP activity. ACP and agent records therefore outlive their tab, their session, and an application restart. A crash may lose the running prompt and its in-flight activity, but retains the record header, first-prompt title, and completed blocks.
6. Tracked ACP sessions are every core tab ACP session, whichever tab drove it, plus every `agent ... execute <task>` run. That covers the shell's `acp <prompt>`, a plugin-owned `startAcp`/`promptAcp`/`promptAcpResult` call such as the launcher's summarizer, and headed or headless, local or remote, including nested agent runs. Local and remote sessions feed the initiating project's recorder. Conversations, monitors, and editor persona sessions keep their own separate ACP consumers and acquire no durable records.
7. The `connections` and `connection` commands open these tabs. The existing `tasks` command keeps opening the task picker. Both names share one parser: bare invocation opens or focuses the singleton connections tab and also returns a docked list to the centre; only plural `connections left` and `connections right` dock it; `list` and `close <kind>:<id>` keep their current output, notifications, and completion. Any other text is a lookup.
8. The connections tab shows every connection kind (sqlite, shell, acp, browser, ssh, terminal) across every tab, plus every retained ACP and agent record. Non-ACP and untracked monitor/persona connections appear only while live and leave the list when closed. Each row shows the connection's title, kind, owning tab, and status in the host's flat order. Opening a non-ACP live row focuses the tab that owns it; opening a tracked record row opens its connection tab. An open ACP record row's close control closes the session; a closed ACP row's control deletes it after confirmation; an agent record row carries no list control.
9. In the shell, `acp <prompt>` runs asynchronously. The shell does not wait on it, and ordinary commands keep working meanwhile. When the final answer is ready, it is appended at the current bottom of the shell output as a rendered Markdown reply, headed by an echo of the exact typed `acp <prompt>` line. That way it reads correctly even after other commands ran in between. Tool steps and thinking appear only in the connection tab.
10. A second `acp <prompt>` while one is running in the same tab is refused with exactly `ACP: a prompt is already running.` and leaves the running prompt alone. Nothing is queued.
11. A core ACP connection tab offers Cancel and Close session. Cancel stops the running prompt and leaves the session open. Close session ends the connection as `acp reset` does. A cancelled prompt stays `Running` until both the native cancellation write and the original provider turn finish, then settles once with `ACP: prompt cancelled.` and becomes `Idle`; the next prompt reuses the same session and record. Reset or close during that drain settles immediately with `ACP session closed.` and closes the record. A closed session's connection tab is read-only and has no prompt input.
12. Closed ACP records are kept per project. At startup, records closed more than 30 days before that startup are pruned; exactly 30 days old and future-dated closures stay. There is no rolling expiry timer and no retention setting. A closed record can also be deleted by hand after `Delete "<title>"?`; an open record cannot be deleted.
13. The connections list is one flat list ordered by the host: live rows by their owning tab's activity, a SQLite row by the most recently active attributed tab, and a record row by its update time. Keyboard movement uses Up, Down, Home, End, and Enter, and a row opens on a second click on the same row. Enter on a row's **Close** or **Delete** control, or on a confirmation dialog button, performs only that control's action and never opens the row. Row identity includes the owning tab, so two tabs exposing the same kind and id stay distinct; a pending confirmation is discarded when rows are reordered or replaced, even at the same length.
14. A live row's open and close controls act on that row's owning tab, not the first row with the same kind and id. A stale or invented owner is refused: the action changes nothing and the refusal shows inline in the list. A SQLite row's close control closes the database app-wide, as `connections close sqlite:<name>` does. Opening a SQLite row focuses the first tab in strip order that has the database attributed, or does nothing when none is. A row action carrying an owner from before an attribution or strip-order change is a silent no-op at the topic and an inline refusal at the list.
15. `connection <text>` first tries `<text>` as a retained record's exact UUID, then the invoking tab's own live `acp:<provider/model>` session, then a live `<kind>:<id>` target, then the complete title of a retained record, newest match first. A live `<kind>:<id>` target prefers the invoking tab's own row when several tabs hold the same connection. Title matching ignores case but compares the whole stored title, including its generated `ACP:` or `Agent:` prefix and every interior space; it is not a prefix, substring, fuzzy, or whitespace-normalized match, and quotation marks are literal text rather than syntax. A closed record and another tab's record can still win the title fallback. No match reports exactly `No connection matching "<text>".` using the complete entered text. Both command names accept the same lookup.
16. The connections tab is titled `Connections`. A core tab ACP session's connection tab and row are titled `ACP: <first line of its first prompt>`; the whole title is capped at 60 characters including the prefix, and an empty first line keeps `ACP`. An agent run is titled `Agent: <task filename>`, without the ACP cap. A live non-ACP row's title is the popup's existing text for it (`bash:~/dir`, `browser:w1 (<mode>)`, `sqlite:<name>`, and so on).
17. The `agent-monitor` tab stays. `agent ... in a tab` keeps opening it. Every agent run, headed or headless, is also listed in the connections tab and opens its own connection tab. Closing or disabling a monitor only detaches observation; it neither terminates the run nor closes its record.
18. Wording: the empty connections list reads `No connections yet`. Deleting a closed row asks `Delete "<title>"?` with Delete and Cancel. The legacy command output remains `No open connections.` when `connections list` finds nothing.
19. A connection tab has a metadata row with the title, kind, model, captured owning tab, status, started and ended times, and the controls available for its status; an agent run also shows its run id and task path. Its body has one block per prompt: the prompt, then its activity entries in order, each labelled `message`, `thought`, `tool`, `plan`, or `permission`, then the rendered final answer. Thought and tool entries start collapsed; other kinds start expanded; activity text stays plain while final answers render as Markdown. A web link in a rendered answer opens as a page tab through the application's link handling and never navigates the app window. An active tab follows new output at the bottom, including streamed text growth on the latest entry, and pauses following while the reader scrolls away.
20. In the connections popup, clicking the tab's own `acp:<provider/model>` row opens its connection tab, in every tab that has one, shell included. Every ACP row that offers a transcript-snapshot button keeps that separate button; pressing the button never opens the record tab. Monitor and editor-persona rows stay snapshot-only where their surface already offers one. A running agent run started from this tab gets its own ACP-kind row in the caller's popup, titled `Agent: <task filename>`, carrying its durable record id and no ACP reference, so it opens the record tab and has no snapshot button. Ownership is matched by the caller incarnation captured at launch, so a run from a closed tab cannot appear under a later tab that reused its label. A durable record id still opens after its session, run, or caller has ended.
21. Row status: a tracked core ACP record reads `Running` while a prompt runs, `Idle` before its first prompt and between prompts, and `Closed` once it ends. An agent run record reads `Running` until it finishes, then `Completed`, `Failed`, or `Terminated`. An ACP session open at quit reads `Closed` after restart. An agent run cut off by quit reads `Terminated`. Every live row reads `Open`.
22. An agent run's connection tab shows a single `Terminate` control in place of Cancel and Close session, only while the run is `Running`. It acts exactly like the agent-monitor's Terminate and ends only that run. The record tab disables the control from the click until the record reports its terminal status and then removes it, while the agent monitor's own Terminate stays visible and disabled through cleanup. A refused control action shows its error in the tab and leaves the record unchanged.
23. A SQLite connection appears as one row per open database, titled `sqlite:<name>`, with its owning-tab column reading exactly `global` whether or not any tab has the database attributed. Its action owner is the first attributed tab label, or empty when none is attributed; focus uses that tab, and an unattributed row's focus is a no-op. Its close control closes the database app-wide and reports the same notification as `connections close sqlite:<name>`. An ssh connection's owning tab is its ssh or remote tab.
24. A connection tab opens with the newest 20 prompt blocks, scrolled to the newest. Reaching the top loads 20 older blocks and preserves the viewport. Older blocks also load automatically while the loaded history fits the viewport, including when a resize makes it fit, until the history scrolls or no older blocks remain. A record with no older blocks ignores the request and keeps its current window, including the empty window of a record with no blocks. Viewport preservation survives streamed activity and new prompt blocks arriving before the older window. A loaded window is held only while its connection tab is open, including while docked or hidden; closing the tab releases it, and reopening loads the newest window again. A closed session's row keeps the owning tab name it had, even after that tab closes.

### Implementation

25. A new bundled tab plugin, `connections`, at `src/plugins/connections/` and `web/src/plugins/connections/`, shaped like the conversations plugin. It is declared in the production catalog and lazy server/client loader maps, so its components, guards, and feature CSS stay in a lazy chunk.
26. The command moves into the plugin. The plugin claims `connections` with alias `connection`. The core `src/commands/connections.ts` entry, `ConnectionManager.run`, and `src/connection/parsing.ts` are deleted, so no second definition remains (architecture principle 5). Once the core entry is gone, neither name is reserved: `createPluginCommands` reserves only registry names and `RESERVED_NON_COMMAND_NAMES` (`['help']`). The pure parser lives at `src/plugins/connections/parse.ts` with its own copy of the six kind names, because a concrete plugin may not import `src/connection/types.js`. `list` and `close` are `connections` topic actions. The `list` action carries the invoking tab's label and returns `listLines(managers, label)` joined by newlines, or `No open connections.`; the plugin writes it with `note`. Command close uses a distinct `closeCommand` action carrying the invoking label and calls public `ConnectionManager.closeTarget(kind, id, label)` without awaiting, preserving the browser branch, `closeConnection`, `connection-closed`/`connection-close-failed` notifications, and the `Could not close connection …` catch. UI `close` remains separate: it validates a current row and owner and never doubles as a command. Close-target completion stays in core through `completeConnectionClose` and `ConnectionManager.completionConnections`; only plural `connections close` offers it.
27. Records live in `src/acp-records/` as `AcpSessionRecords` on `Managers`, with a `dispose`. A record id is a `randomUUID()` minted at `begin`; the transient `acp-<n>` session identity is never used. A core session's id rides `tab.runtime.acpRecordId` and an agent run's rides the run. One versioned JSON document lives at `.janissary/connections/<id>.json`, written atomically. Status is derived, never stored separately: an open core record is `Idle` with no unanswered block and `Running` while its newest block is unanswered; an open agent record is always `Running`; a terminal record uses its outcome. Title derivation, the 60-character cap, folding of adjacent `message`/`thought` chunks, deterministic row ordering, and the window projection are pure functions. Begin saves an empty header; prompt metadata saves the title and completed history without the in-flight block; answer and close save the completed record. Startup recovery rewrites leftover open core records as `Closed` and agent records as `Terminated` without restarting a provider, and prunes only records closed strictly more than 30 days before startup. Storage failures keep the in-memory state, mark it dirty, and retry at the next boundary or disposal; invalid files are excluded and reported once; one bad record never blocks another. Each accepted mutation publishes `connections:changed`. Disposal closes remaining open records as `Closed`, attempts every save, and is idempotent.
28. Activity uses one recorder fed two ways. Core tab sessions forward `onActivity` from both local and remote transports; the local path classifies raw updates with `acpActivity`, while the remote path records the already classified `(kind, text)` from `acp-activity` frames. The feed begins a record at a successful handshake, reserves the first prompt before the handshake, records each prompt, activity, host command and result, and the settled answer or error, and closes the record on reset, tab close, plugin failure, fatal error, or shutdown without inventing an answer. Agent runs begin their record at creation with the original task selector, selected model, copied caller label and name, and run linkage; the first block starts before transport readiness; both activity routes and host command/result steps feed the record; `AgentRun.finish` records the first outcome before cleanup, mapping `completed`/`failed`/`terminated` to `Completed`/`Failed`/`Terminated` and preserving the captured answer, `Agent terminated.`, or `Agent failed.`. Monitor filtering and its bounded activity array stay unchanged.
29. The `connections` topic carries rows plus loaded windows. Rows come from `connectionCatalog` across every open tab, one `global` row per open database, and every ACP record summary. A tracked core ACP session is identified by the tab runtime's `acpRecordId` and replaced by its record row rather than duplicated. Live rows carry the owning tab's `lastActivity` as their ordering timestamp, a SQLite row the greatest activity among attributed tabs or 0, and a record row its `updatedAt`. `connections:changed` and `state:dirty` share one 100 ms coalescing window and each delivery reads the latest state, so streaming never fires per chunk. Full windows are included only for record ids an open connection tab requested; a requested window is pruned when its record disappears or no open plugin tab carries the id, so closing a record tab releases it. The topic exposes ten actions: `load`, `loadOlder`, `list`, `open`, `close`, `closeCommand`, `cancel`, `closeSession`, `terminate`, and `delete`. `load` opens the newest window, `loadOlder` grows it by `ACP_RECORD_WINDOW_SIZE` only while older blocks exist, `open`/`close` validate the current live row and owner, command `closeCommand` preserves legacy close notifications, `cancel` and `closeSession` require the exact live core owner, `terminate` requires a live linked agent run, and `delete` removes only a terminal record. Lifecycle actions are asynchronous and report later status through the topic.
30. Cancel is one framework-free provider-turn control shared by the local and remote adapters. It marks cancellation synchronously, aborts the host loop and the active or queued question while preserving unrelated questions, sends the ACP `session/cancel` notification locally, and forwards a new addressed `acp-cancel` client frame for remote sessions. Remote protocol is 37, and old peers are refused by version. The request stays reserved and `Running` until both the notification write and the original provider turn finish; a handler is published only after both, so a follow-up cannot be clobbered and a failed send closes the failed session with `ACP: cancellation failed: <reason>` rather than claiming success. Cancelling before handshake finishes initialization without sending the cancelled prompt; cancelling an idle session is a no-op. Reset, close, and fatal loss settle and close once, release cancellation waiters, and leave only the appropriate tracked lifecycle closed. There is no cancellation timeout or forced kill of a healthy provider. Transport loss settles pending core requests and closes their records; a later ready channel starts a fresh record.
31. The async answer reaches the shell through the existing background-reply channel. `backgroundReplies` entries gain one optional `line`, set only for completed ACP background entries (the stored input begins with the `acp` token, with or without the command bar's leading slash); monitor replies and ordinary entries keep no line and render under `monitor`. The shell passes `reply.line ?? 'monitor'` to its existing Markdown-capable `displayReply`, so the answer appears beneath the exact typed line. Every way an `acp` prompt settles produces exactly one background reply: the answer, the refusal, `Usage: acp <prompt>.`, an `ACP error: …` line, `ACP session closed.` for reset or Close session, and `ACP: prompt cancelled.` for cancellation. Reset itself is also one completed background reply with its own fresh id and the exact reset line; its no-session message repeats that rule. The snapshot/replay protocol keeps stable ids, so a second page replays each reply once.
32. Removing the panel is a breaking plugin API change, so `TAB_PLUGIN_API_VERSION` is 3. v3 removes `useAcpResponse`, `TabView.acpResponse`, and the deprecated `launchShellHere()` shim, whose removal was already scheduled for v3. A frozen `fixture-v2` sits beside `fixture-v1`; each is refused when it explicitly declares its historical version and round-trips representative behavior when declared at v3. Core ACP sessions, transcript tagging, prompt settlement, cancellation, records, completed background replies, transcript snapshots, and host-rendered docked questions remain. `PluginBody` renders a selected active docked tab's pending question through the core question panel without a response panel, while hidden docked bodies show none and centre questions stay app-owned. Reset remains reachable through `acp reset`, Close session, and `connections close acp:<name>`.
33. The client entry routes `kind: 'list'` payloads to `ConnectionList` and `kind: 'connection'` payloads to `ConnectionTab`. The list renders the host's row order unchanged, renders each row's title or display, kind, captured owner name, and status, and never sorts, dedupes, or derives status or ownership. It sends `open`/`close` with the row's kind, id, and owner, an id-only `open-record` for agent record rows, and id-only `cancel`, `close-session`, `terminate`, `delete`, and `load-older` intents. A refused row action sets the controller's inline `role="alert"` error and leaves no unhandled rejection. A pending delete confirmation is discarded when its row disappears or is replaced. The list's React key and click-confirmation identity use the same owner-aware helper, so duplicate-looking rows cannot collide. The list open and update payloads carry summaries only; a record's loaded window travels only with its record tab.
34. The record view renders the authoritative metadata, blocks, activity labels, collapsed thought/tool details, Markdown answers with fallback, and status-gated controls. It renders an answer's web links through `openLink` and keeps activity text plain. Blocks are keyed by their absolute position (`window.offset + index`), so prepending older history preserves expanded entries and DOM state. The history scroll hook follows the newest output only while active and near the bottom, requests older history at the top once per offset, restores the viewport by the prepended height only when the offset moves toward older history, refreshes its baseline when streamed activity or a new block moves the offset the other way, observes the element with `ResizeObserver` (falling back to window resize) so a taller viewport triggers the same fit-based paging, and honours a record tab's `load`/`loadOlder` window contract. A record tab opened by UUID is created or focused before its window is requested, then refreshed through `updateTab` once the loaded record arrives, so the opening payload keeps its window under the tab-scoped prune. An open record that disappears from topic data closes its own tab; a record present without a window shows the loading state and requests it.
35. The popup path is one RPC, not a second tab opener. `ConnectionView` gains optional `recordId`. `StatusPanels` accepts an optional `onOpenRow` and makes only rows with a `recordId` or a tab-scoped `acpRef` openable by pointer and keyboard; snapshot and close buttons stop propagation and keep their own actions. Shell uses a new optional, tab-bound `openConnection` client capability (additive in API v3, exposing no socket), while editor and harness send `openConnectionRecord` through their existing client. The server resolves a `recordId`, or the tab's current `acpRecordId` for a tab-scoped reference, and dispatches the connections plugin's existing record opener; a missing tab or stale binding is a no-op and never opens a snapshot. The shell plugin's import-free shared contract mirrors `recordId?: string` and its guard accepts only an absent value or a string. A running agent run's caller row is projected from live runs by caller label and incarnation, carries the run's record id and task filename title, and has no `acpRef`.
36. Both command names share one grammar and one lookup. Bare plural or singular opens/focuses the singleton list and returns it to the centre; only plural `left`/`right` dock; `list`, `close`, and any other text keep their reserved meanings; trailing arguments after `list`, `close`, and plural docking stay ignored. The lookup preserves UUID → invoking-tab `acp:<model>` → live `<kind>:<id>` (own tab first) → complete-title precedence and the exact refusal text. `connections list` output is the invoking tab's legacy catalogue, never durable records. Parser errors are command notes, not plugin failures, and keep their exact legacy wording.
37. A shell prompt cancelled through the record tab's Cancel produces exactly one background reply reading `ACP: prompt cancelled.` under its `acp <prompt>` echo, and the session and record UUID are reused by the next prompt.

## Proposed changes

Ordered so the tree stays green. Steps 1 to 3 add server machinery with nothing depending on it yet. Step 4 adds the plugin and its two client views. Step 5 moves the shell and popup. Step 6 removes the panel and breaks the API. Step 7 reconciles docs.

1. **Records.** Add `src/acp-records/` with the record model, validation, store, and `AcpSessionRecords`. The manager offers `begin(source)`, `prompt(id, text)`, `activity(id, kind, text)`, `answer(id, text)`, `close(id, outcome)`, `delete(id)`, `rows()`, and `window(id, count)`. Titles are derived from the source and first prompt; status is derived from the outcome and unanswered block; adjacent `message`/`thought` chunks fold; rows sort newest update first; windows return the newest suffix with `offset` and `hasOlder`; `ACP_RECORD_WINDOW_SIZE`, the 60-character cap, and the 30-day retention interval are shared constants. Startup recovery and prune run in construction. Each accepted mutation emits `connections:changed`; storage failures stay in memory for retry; disposal closes leftovers and is idempotent. Register `acpRecords` on `Managers`, construct it before agent/ACP producers, and dispose it after them. Add `product/specs/acp-records.md`.
2. **Feeds and cancellation.** Add `src/acp/prompt-state.ts`, `src/acp/prompt-control.ts`, `src/acp/record-feed.ts`, and `src/acp/run-prompt.ts`; move accepted loop orchestration out of `AcpManager.run` so every prompt entry shares admission. Begin core records at handshake, bind the pending prompt's record id, classify local activity and record remote classified activity, record host command/result steps, and settle/close through the single session-close path. Add `AcpSession.cancel()` and `AcpManager.cancel(label)` with the two-boundary drain contract. Add `src/agent/model.ts`, `src/agent/record-feed.ts`, and `src/agent/run-cleanup.ts`; resolve an omitted model at creation, preserve the launch task selector, start the record block before readiness, and close in `AgentRun.finish` with the first outcome. Add the `acp-cancel` frame and decoder, dispatch it in `RemoteServer`, settle unavailable sends, and raise `REMOTE_PROTOCOL_VERSION` to 37. Update `product/specs/acp.md`, `agent-command.md`, and `remote-server.md`.
3. **Topic and actions.** Add `src/protocol/connections.ts` for the row/window wire shapes and `src/plugins/api-topics-connections.ts` for the notification and ten action shapes; compose both through their existing owners. Add `src/plugins/connections-topic.ts`, `connections-topic-rows.ts`, and `connections-topic-actions.ts`. Rows cover every open tab's catalogue, one `global` SQLite row per database, and every record summary; tracked ACP live rows are replaced by their record row; ordering uses tab activity or record update time. Subscription coalesces `connections:changed` and `state:dirty` through one 100 ms window, reads latest state at delivery, and cleans both listeners on unsubscribe. Requested windows are stored per `Managers` instance and pruned when the record or its open plugin tab disappears. Promote `ConnectionManager.closeTarget` and implement `list`, `open`, `close`, `closeCommand`, `load`, `loadOlder`, `cancel`, `closeSession`, `terminate`, and `delete` with current-row and owner validation.
4. **Plugin.** Add `src/plugins/connections/`: `manifest.ts`, import-free `shared.ts` with payload and intent guards, `parse.ts` with the six-kind grammar and exact legacy errors, `lookup.ts`, `command.ts`, `tabs.ts`, `record-tabs.ts`, and `activate.ts`. Register the manifest in `src/plugins/catalog.ts` and its literal lazy loader, and add the literal client registry entry. ## Out of scope

- Conversations, monitors, and editor persona sessions keep their own separate ACP consumers (`product/specs/acp.md` § Shared consumers) and are not tracked as records; monitor and persona rows are live-only.
- The sessions tab for remote sessions is unchanged.
- The `agent-monitor` tab is unchanged beyond the same Terminate action it already had; closing it only detaches observation.
- The task picker and its `tasks` command are unchanged.
- No queue of pending `acp` prompts. A prompt in flight still refuses the next.
- No prompt input in a connection tab, and no reopening of a closed session from it.
- No retention setting and no rolling expiry timer. The 30-day limit is fixed and checked at startup.
- Non-ACP connections keep no history.
- No client-side sorting, merging, deduplication, status derivation, or ownership inference; the topic is authoritative.
- No per-connection activity clock; live rows use their owning tab's activity and SQLite uses attributed tab activity.
- No cancellation timeout or forced kill of a healthy provider.
- No prefix, substring, fuzzy, whitespace-normalized, or quoted title matching, and no singular `connection` docking.
- No visible disabled record-tab Terminate through cleanup; that presentation belongs to the agent monitor. Agent record rows have no list control.
- No transcript-snapshot button on shell, harness, or running agent-run popup rows.
- No hidden subplans: this is the feature's single plan.
