# Connections and connection tabs

**Complexity: 8/10** — a new persisted record subsystem, a new topic and bundled plugin with two views on both sides, a core command moved into a plugin, async shell ACP delivery, an ACP cancel path with a remote frame and protocol bump, and a breaking plugin API v3 with a new frozen fixture.

## Summary

ACP sessions started from a shell tab have no lasting home. A prompt streams into the core response panel above the shell's command bar, the exchange lives only in that tab's in-memory log, and once the tab closes or the session resets there is nothing to go back to. The connections popup names the session as `acp:<provider/model>`, but in a shell tab its rows do nothing when clicked.

This feature gives ACP sessions a persistent place to be monitored and controlled. A new **connections tab** lists every connection, and ACP sessions stay listed after they close. A **connection tab** shows one ACP session's full interaction: the transcript, the model's thinking, turn taking, and its output. The pair is modelled on the conversations list and conversation tabs. The ACP response panel leaves the shell tab. A shell that launches an ACP prompt gets on with other work and shows the answer when it arrives. The session's row in the connections popup opens its connection tab.

Terms used throughout: the **connections tab** is the new list tab. A **connection tab** is the new per-session tab. The **connections popup** is the existing floating per-tab window (`ConnectionWindow`, `product/specs/connection.md` § Connection window). The existing sessions tab for remote sessions (`product/specs/sessions-tab.md`) is unrelated and unchanged.

Source: the first `## ready` entry of `product/backlog/features.md` (an untitled bullet beginning "ACP sessions should be tracked in a new tasks tab"). The user renamed the tabs from "tasks"/"task" to "connections"/"connection".

## Design decisions

### Product

1. The connections tab lists connections. ACP sessions appear both open and closed. A connection tab shows one ACP session's transcript, thinking, turn taking, and model output. (Feature text.)
2. Both tabs are modelled on the conversations plugin: a list tab with a fixed instance key, plus one tab per item keyed by its id, fed by a host notification topic (`product/specs/conversations.md`). (Feature text.)
3. The ACP response panel is removed from the shell tab. When an ACP prompt is launched from the shell tab, the shell renders only its answer. (Feature text.)
4. The ACP connection stays listed in the connections popup, as it already is (`acp:<provider/model>`). Clicking that row opens its connection tab. (Feature text.)
5. The purpose is a persistent place to monitor and control ongoing and past ACP activity. ACP session records therefore outlive their tab, their session, and an application restart. (Feature text.)
6. Tracked ACP sessions are every core tab ACP session, whichever tab drove it, plus `agent ... execute <task>` runs. That covers the shell's `acp <prompt>` and a plugin's own `startAcp`/`promptAcp`/`promptAcpResult` calls, such as the launcher's summarizer. Conversations, monitors, and editor persona sessions are not tracked. (User answers.)
7. The `connections` and `connection` commands open these tabs. The existing `tasks` command keeps opening the task picker. Bare `connections` opens or focuses the singleton connections tab. `connections left` and `connections right` dock it, as `conversations` does, and running bare `connections` while it is docked returns it to the centre. `connections list` and `connections close <kind>:<id>` keep their current output, notifications, and completion. (User answers.)
8. The connections tab shows every connection kind (sqlite, shell, acp, browser, ssh, terminal) across every tab. Non-ACP connections appear only while live and leave the list when closed. ACP sessions stay listed after they close, and opening one opens its connection tab. (User answer.)
9. In the shell, `acp <prompt>` runs asynchronously. The shell does not wait on it, and ordinary commands keep working meanwhile. When the final answer is ready, it is appended at the current bottom of the shell output as a rendered Markdown reply, headed by an echo of its `acp <prompt>` line. That way it reads correctly even after other commands ran in between. Tool steps and thinking appear only in the connection tab. (User answers.)
10. A second `acp <prompt>` while one is running in the same tab is refused with today's `ACP: a prompt is already running.` and leaves the running prompt alone. Nothing is queued. (User answer.)
11. A connection tab offers Cancel and Close session. Cancel stops the running prompt and leaves the session open (`Idle`). Close session ends the connection the way `acp reset` does. A closed session's connection tab is read-only. It has no prompt input. (User answers.)
12. Closed ACP sessions are kept per project and removed automatically 30 days after they close. A closed row can also be deleted by hand. An open session cannot be deleted. (User answer.)
13. The connections tab is one flat list ordered by most recent activity. Each row shows the connection's title, kind, owning tab, and status. Keyboard movement (Up, Down, Home, End, Enter) and two-click opening behave like the conversation list. (User answer.)
14. A non-ACP row has a close control that acts exactly like `connections close <kind>:<id>` and is reported the same way. Opening a non-ACP row focuses the tab that owns the connection. Opening an ACP row opens its connection tab. An open ACP row's close control closes its session. A closed ACP row's control deletes it after confirmation. (User answer.)
15. `connection <text>` first tries `<text>` as a `<kind>:<id>` string, the same strings `connections close` takes. An `acp:` id opens the current tab's ACP connection tab. Any other kind focuses the tab owning that connection. Failing that, it opens the ACP session whose title matches case-insensitively, newest first. No match reports `No connection matching "<text>".` Bare `connection` opens the connections tab, like bare `connections`. (User answer.)
16. The connections tab is titled `Connections`. A core tab ACP session's connection tab and row are titled `ACP: <first line of its first prompt>`, capped at 60 characters. An agent run is titled `Agent: <task filename>`, as its monitor tab is today. A non-ACP row's title is the popup's existing text for it (`bash:~/dir`, `browser:w1 (<mode>)`, `sqlite:<name>`, and so on). (User answer; the non-ACP title follows `connection.md`.)
17. The `agent-monitor` tab stays. `agent ... in a tab` keeps opening it. Every agent run, headed or headless, is also listed in the connections tab and opens its own connection tab. (User answer.)
18. Wording: the empty connections tab reads `No connections yet`. Deleting a closed row asks `Delete "<title>"?` with Delete and Cancel. (User answer.)
19. A connection tab has a metadata row with the title, model, owning tab, status, started and ended times, and the Cancel and Close session controls. Its body has one block per prompt. Each block holds the prompt, then its activity entries in order, each labelled `message`, `thought`, `tool`, `plan`, or `permission`, then the rendered final answer. Thought and tool entries start collapsed. An active connection tab follows new output at the bottom the way a conversation tab does. (User answer.)
20. In the connections popup, clicking the tab's own `acp:<provider/model>` row opens its connection tab, in every tab that has one, shell included. Every ACP row keeps its transcript-snapshot button. A running agent run started from this tab gets its own row in the caller's popup, which also opens its connection tab. (User answer.)
21. Row status: an ACP session reads `Running` while a prompt runs, `Idle` while it is open between prompts, and `Closed` once it ends. An agent run reads `Running` until it finishes, then `Completed`, `Failed`, or `Terminated`. An ACP session open at quit reads `Closed` after restart. An agent run cut off by quit reads `Terminated`. A non-ACP row reads `Open`. (User answer.)
22. An agent run's connection tab shows a single `Terminate` control in place of Cancel and Close session. It acts exactly like the agent-monitor's Terminate and is disabled once cleanup begins. (User answer.)
23. A sqlite connection appears as one row per open database, with its owning tab reading `global`. Opening it focuses the first tab, in strip order, that has the database attributed, or does nothing if none does. Its close control closes it app-wide, as `connections close sqlite:<name>` does. An ssh connection's owning tab is its ssh or remote tab. (User answer; ssh follows `connection.md`.)
24. A connection tab opens with the most recent 20 prompt blocks, scrolled to the newest. Reaching the top loads 20 older blocks and preserves the viewport, as a conversation tab does. A closed session's row keeps the owning tab name it had, even after that tab closes. (User answer; the name rule follows decision 5.)

### Implementation

25. A new bundled tab plugin, `connections`, at `src/plugins/connections/` and `web/src/plugins/connections/`, shaped like the conversations plugin. (User answer.)
26. The command moves into the plugin. The plugin claims `connections` with alias `connection`. The core `src/commands/connections.ts` entry and `ConnectionManager.run` (`src/connection/manager.ts`, `async run(command, label, invocation?)`) are deleted, so no second definition remains (architecture principle 5). Once the core entry is gone, neither name is reserved: `createPluginCommands` in `src/plugins/command-adapter.ts` reserves only registry names and `RESERVED_NON_COMMAND_NAMES` (`['help']`, `src/commands/reserved.ts`). The pure parser moves into the plugin as `src/plugins/connections/parse.ts`, carrying its own copy of the six kind names, because a concrete plugin may not import `src/connection/types.js` two levels up. `src/connection/parsing.ts` is deleted, since `ConnectionManager.run` is its only caller. `list` and `close` are `connections` topic actions. `topicAction` already returns `string | undefined` synchronously (`src/plugins/api.ts`, `topicAction(action): string | undefined`). The `list` action carries the invoking tab's label, which the plugin reads from the existing `originTab()` capability. The host answers it with the exact text `ConnectionManager.run` prints today: `listLines(managers, label)` joined by newlines, or `No open connections.`. The plugin writes that text with `note`, which appends it to the invoking tab for the same invocation (`src/plugins/context.ts`, `appendForInvocation`), the way `appendCommandOutput` did. The `close` action runs what is today `ConnectionManager`'s private `close` plus `reportClose`. Those two are promoted to one public `closeTarget(kind, id, label)` that keeps the browser branch (`managers.browser.run(label, 'browser window close <id>')`), the `closeConnection` call, the `connection-closed`/`connection-close-failed` notifications, and the `Could not close connection …` catch. The action starts it without awaiting, because a browser close is async and its notification arrives when the window closes. Usage and validation errors from the moved parser are written with `note`, as today. Close-target completion stays in core: `completeConnectionClose` (`src/completion/target-handlers.ts`) matches the `connections` word in the typed text, and `src/controller/completion.ts` keeps calling `managers.connection.completionConnections`. Neither depends on the registry entry. (User answer; mechanics decided in review.)
27. Records live in a new `AcpSessionRecords` manager on `Managers`, with a `dispose`. A record id is a `randomUUID()` minted when the record begins. The session identity `AcpSessionManager` mints (`acp-<n>`, `src/acp/session-manager.ts`) is a per-process counter and repeats across restarts, so it is never used as a record id. A core tab session's record id rides the tab record as `tab.runtime.acpRecordId` (architecture principle 2), and an agent run's rides the run. It writes one JSON file per session at `.janissary/connections/<id>.json`. A prompt block is written when it completes, and the record again when the session closes. The running prompt's activity is held in memory. At startup the manager rewrites leftover open records as `Closed` (or `Terminated` for an agent run) and deletes records closed more than 30 days ago. (User answer.)
28. Activity uses one recorder fed two ways. `connectAcp` already calls `onActivity` with every update, and the core tab session path starts forwarding it, classified by the existing `acpActivity`. Agent runs already classify the same updates in `src/agent/execute.ts` and post them to the same recorder beside `run.reportActivity`. Remote sessions already send `acp-activity` frames for every session (`src/remote/serve-acp.ts`), so capture needs no remote change. (User answer.)
29. The `connections` topic carries rows plus loaded windows. The rows are every live connection from `connectionCatalog` across tabs, plus every ACP record. Full windows are carried only for sessions an open connection tab has loaded (20 blocks, `loadOlder` for more). `connections:changed` is coalesced into one delivery per 100 ms window, the way the `tabs` topic batches `state:dirty`, so streaming chunks never fire per chunk. (User answer.)
30. Cancel sends the ACP `session/cancel` notification (the SDK's `ClientSideConnection.cancel({ sessionId })` in `@agentclientprotocol/sdk`), aborts the tool loop and its question the way a reset does, settles the prompt as cancelled, and keeps the session. A remote session forwards the cancel over its channel in a new `acp-cancel` frame. (User answer.)
31. The async answer reaches the shell through the existing `onBackgroundReply` channel. `backgroundReplies` entries gain one optional `line` field, the echoed `acp <prompt>`. No Markdown flag is needed. `useBackgroundReplies` already hands each reply to the shell's `displayReply(line, markdown)` (`web/src/plugins/shell/useShellSubmit.ts`), which renders its second argument as Markdown, so the hook passes `reply.line ?? 'monitor'` where it now passes `'monitor'`. Existing monitor replies are unchanged. Every way an `acp` prompt settles produces exactly one background reply: the answer, a refusal (`ACP: a prompt is already running.`), `Usage: acp <prompt>.`, an `ACP error: …` line, and `ACP session closed.` for a reset or Close session. (User answer; the single-field shape and the settled-result rule were decided in review.)
32. Removing the panel is a breaking plugin API change, so `TAB_PLUGIN_API_VERSION` goes to 3. v3 removes `useAcpResponse`, `TabView.acpResponse`, and the deprecated `launchShellHere()` shim, whose removal was already scheduled for v3. A frozen `fixture-v2` is added beside `fixture-v1`, and v2 declarations are refused the way v1 declarations are. (User answers.)
33. The connections tab's live rows come from `connectionCatalog(managers, label)` (`src/connection/catalog.ts`) run for every open tab, keeping each tab's `scope: 'tab'` entries with that tab as owner, plus one row per `managers.database.listOpen()` database with owner `global`. Monitor and editor-persona ACP rows are live connections the catalog already returns. They appear as live-only rows: opening one focuses its tab, its close control runs `closeTarget`, and they keep no record (decision 6). A tracked ACP session appears once, as its record row, not again as a live catalog row. (Decided in review, following decisions 6 and 8.)
34. A sqlite row's focus target is the first tab, in strip order, whose existing `openDbs(label)` (`src/database/manager.ts`) includes that database. No new tracking is added to `DatabaseManager`. (User answer, simplifying decision 23.)
35. A running agent run appears in its caller's popup as an `acp` row with `text` `Agent: <task filename>` and its record id. It carries no `acpRef`, because the transcript snapshot RPC has no agent-run scope, so it shows no snapshot button. Decision 20's "every ACP row keeps its snapshot button" applies only to the rows that have one today; shell and agent-run rows stay without one. (User answer.) `ConnectionView` (`src/protocol/tab.ts`) gains an optional `recordId`. A row with one opens that record's connection tab on click. (Decided in review.)
36. `connections <text>`, for any text other than `list`, `close …`, `left`, and `right`, behaves exactly as `connection <text>` (decision 15), the way `conversations <title>` and `conversation <title>` share a grammar. `connection list` and `connection close …` run the same subcommands, because both names share one parser. A bare `connections` no longer prints `Usage: connections <list|close> [kind:id] …`. (User answer, following the conversations precedent.)
37. When Cancel stops a shell's running `acp` prompt, the shell's background reply under the `acp <prompt>` echo reads `ACP: prompt cancelled.`. (User answer.)

## Proposed changes

Ordered so the tree stays green. Steps 1 to 3 add server machinery with nothing depending on it yet. Step 4 adds the plugin. Steps 5 and 6 move the shell and remove the panel. Step 7 is docs.

1. **Records.** Add `src/acp-records/` with a pure record model (block, entry, status, title derivation, 30-day expiry check) and an `AcpSessionRecords` manager on `Managers`. The manager offers `begin(source)` returning a record id, `prompt(id, text)`, `activity(id, kind, text)`, `answer(id, text)`, `close(id, outcome)`, `delete(id)`, `rows()`, and `window(id, count)`. There is no separate status setter. Status is derived from the record: `Running` while its newest block has no answer, `Idle` once it has one, and the close outcome (`Closed`, `Completed`, `Failed`, `Terminated`) after `close`. Consecutive `message` or `thought` chunks within one block fold into one entry, so a streamed reply is one entry, not hundreds. Writes go to `.janissary/connections/<id>.json` with a `schemaVersion`. Startup recovery and expiry run in the manager's construction path. `dispose` closes every open record as `Closed`. Each mutation emits `connections:changed` on the message bus.
2. **Feeds.** `src/acp/manager.ts` is at 187 raw lines, so the record wiring goes in a new `src/acp/record-feed.ts` that `AcpManager` calls. The feed begins a record when a core tab session's handshake names it, which is the moment `managers.acp.label(label)` starts answering. It records each prompt, forwards the session's `onActivity` (`AcpOptions.onActivity`, `src/acp/types.ts`) through `acpActivity` into the record, and records the final answer. It closes the record when the session closes for any reason: reset, tab close, fatal error, plugin failure, shutdown. Every one of those already passes through `AcpSessionManager.close`/`closeTab`/`closeAll`, so the record close goes there once. The two transports deliver activity in different shapes, and the feed accepts both. A local session hands `onActivity` the raw update, which the feed classifies with `acpActivity`. A remote session's local half (`src/remote/acp-session.ts`, `hooks.onActivity?.(kind, text)`, routed by `src/remote/channel/acp.ts` from each `acp-activity` frame) hands it an already classified `(kind, text)`, which the feed records as is. The tab session's start path passes the hook on both transports. In `src/agent/execute.ts`, at the existing `const activity = acpActivity(update); if (activity) run.reportActivity(...)`, also post the activity to the run's record. Begin the record when the run is created and close it with the run's outcome in the run's settle path (`src/agent/settle-run.ts`). Add `cancel(label)` on `AcpManager`. It calls a new `cancel()` on `AcpSession` (`src/acp/index.ts`), which sends `connection.cancel({ sessionId })`, aborts `tab.runtime.acpPrompt.abort` the way reset does, and settles the prompt with `{ answered: false, error: 'ACP: prompt cancelled.' }` through `settleAcpPrompt` (`src/acp/response.ts`). The remote client's `AcpSession` sends a new `{ type: 'acp-cancel'; id }` `ClientFrame` (`src/remote/protocol-frames.ts`, beside `acp-close`, added to `CLIENT_FRAME_TYPES`), and `serve-acp.ts` calls `cancel()` on that record's session. `REMOTE_PROTOCOL_VERSION` (`src/remote/protocol.ts`, now 36) goes to 37 with a history comment in the file's existing per-version style. An older peer has no cancel, and the version check refuses the mismatch as it does for every bump.
3. **Topic.** Add `connections` to `TabPluginNotificationTopic` and to the `NOTIFICATION_TOPICS` record in `src/plugins/api-topics.ts`. A new topic is additive: the record is keyed by the union, so a missing source is a compile error. `api-topics.ts` is at 181 raw lines, so the `connections` data and action types go in a new `src/plugins/api-topics-connections.ts` that it imports. Its data is the row list (decision 33, with the sqlite focus target from decision 34 and every record's summary) plus the loaded windows. Its actions are `load`, `loadOlder`, `list` (decision 26), `open` (focus the owning tab of a live row), `close` (`closeTarget`, decision 26), `cancel`, `closeSession` (the same `managers.acp.close` path `acp reset` takes), `terminate`, and `delete`. `terminate` starts `managers.agent.finish(runId, 'terminated')` without awaiting, the call `terminateAgentRun` makes in `src/plugins/context.ts`. A topic action is synchronous and cleanup can outlast any handler budget, and the record's `Terminated` status arrives through the topic. `delete` of an open record is ignored. `src/plugins/topics.ts` is at 212 raw lines, so the `connections` source (subscribe, read, act) goes in a new `src/plugins/connections-topic.ts` that `TOPIC_SOURCES` references. It coalesces `connections:changed` into one delivery per `TABS_NOTIFICATION_WINDOW_MS` (100 ms) exactly like `subscribeTabs`. It also fires on `state:dirty` through that same window, because live catalog rows (a shell starting, a browser window opening) change without any record mutation. Each action is a method on `AcpSessionRecords` or an existing owner, never a new label-keyed map.
4. **Plugin.** Add `src/plugins/connections/` with `manifest.ts` (command `connections`, alias `connection`, topic `connections`, capabilities `openOrFocusTab`, `updateTab`, `dockTab`, `topicData`, `topicAction`, `originTab`, `rejectRequest`, `reportFailure`), an import-free `shared.ts` (list and connection payloads, intent guards, schema version), `parse.ts` (decision 26's moved parser, extended with the bare, `left`, `right`, and `<text>` forms of decisions 7, 15, and 36), and `activate.ts` plus a `tabs.ts` modelled on `ConversationTabs` (`src/plugins/conversations/tabs.ts`). The command answers `list` and `close` through the topic actions of decision 26. It resolves `<kind>:<id>` against the topic rows for the invoking tab and titles against the record rows. Register it in `src/plugins/catalog.ts` and `src/plugins/loaders.ts`, and its client in `web/src/plugins/registry.tsx`. In the same step, delete `src/commands/connections.ts` and its entry in `src/commands/index.ts`, `ConnectionManager.run`, and `src/connection/parsing.ts`, and move `src/commands/connections.test.ts` coverage into the plugin's command tests. That way the tree never holds two `connections` definitions, and never none. `listLines` stays in `src/connection/list.ts`, called by the host's `list` action. Add `web/src/plugins/connections/`: `index.tsx`, a `ConnectionList` (rows, keys, two-click open, row controls, delete confirmation), a `ConnectionTab` (metadata row, prompt blocks, collapsed thought/tool entries, follow-bottom, older-block paging), and a `useConnectionController` hook, reusing the conversations plugin's list-key and stick-to-bottom patterns as their own colocated copies (no cross-plugin import).
5. **Shell.** In `src/commands/acp.ts`, `run` starts `managers.acp.promptResult` without awaiting it, and the command keeps `coreResponse: true`, so `useShellSubmit` (`if (!result.coreResponse) displayReply(text, result.output)`) shows nothing at submit. When the prompt settles, the command appends one log entry with `input` set to the typed `acp <prompt>`, `output` set to the settled text (decision 31), and `background` set to a fresh `randomUUID()`. That is how monitor replies are marked (`LogEntry.background`, `src/tab/types.ts`). The settle goes through `src/acp/response.ts` beside `settleAcpPrompt`. `appendAcp`'s `acpEntries` tagging stays, because `settleAcpPrompt` and `src/tab/transcript/events.ts` still use it to find the running entry. Add optional `line` to `backgroundReplies` in `src/protocol/tab.ts`, and project it from `entry.input` in `src/tab/view.ts` (`backgroundReplies: tab.log.flatMap(…)`). Set it only for ACP entries, so monitor replies keep their `'monitor'` line. `src/tab/view.ts` is at 223 raw lines, so if the change pushes it over the lint count, extract the `backgroundReplies` projection into `src/tab/background-replies.ts`. In `web/src/plugins/shell/useBackgroundReplies.ts`, pass `reply.line ?? 'monitor'`. Remove `useAcpResponse` and `{acpResponse}` from `ShellTab.tsx`. `StatusPanels` (`web/src/shared/status-windows/StatusPanels.tsx`) gains an optional `onOpenRow(row)` callback, called when a row with a `recordId` or a `scope: 'tab'` `acpRef` is clicked. `ShellTabMeta.tsx` (`StatusPanels` props near its end) passes `onOpenRow` only. It does not add `onOpenAcpTranscript`, because decision 20 keeps the snapshot buttons where they exist and a shell row has none today; the connection tab is the shell's full view. The editor (`web/src/editor/EditorConnectionsPanel.tsx`) and harness (`web/src/harness/harness-tab-intents.ts`) popups pass `onOpenRow` beside the handlers they already pass. `onOpenRow` sends a core RPC that opens or focuses the connection tab for a record. It is resolved on the server from a `recordId`, or from the tab's `acpRecordId` for a tab `acpRef`, and goes through the connections plugin's opener so the plugin owns its tab. That RPC is defined in `src/protocol/core-rpc.ts` beside `openAcpTranscript` and authorized the same way. `connectionCatalog`'s `acpEntries` adds the tab ACP row's `recordId` and decision 35's agent-run row, which comes from `managers.agent.runs` whose `caller.label` is this tab and whose run is live.
6. **API v3.** Remove `acpResponse` from `TabView` (`src/protocol/tab.ts`), its projection in `src/tab/view.ts` (`acpResponse: acpResponseFor(tab)`), and `acpResponseFor` from `src/acp/response.ts`. Remove `AcpResponsePanel.tsx`, `AcpResponseScope.tsx`, `useAcpPanelActions.ts`, `acp-panel-actions.ts`, `acp-response.css`, and their tests under `web/src/shared/acp/`. ## Out of scope

- Conversations, monitors, and editor persona sessions keep their own separate ACP consumers (`product/specs/acp.md` § Shared consumers) and are not tracked in the connections tab.
- The sessions tab for remote sessions is unchanged.
- The `agent-monitor` tab is unchanged.
- The task picker and its `tasks` command are unchanged.
- No queue of pending `acp` prompts. A prompt in flight still refuses the next.
- No prompt input in a connection tab, and no reopening of a closed session from it.
- No retention setting. The 30-day limit is fixed.
- Non-ACP connections keep no history.
