# Hosts Tab

**Complexity: 8/10** — ~1050 added lines, 21 files edited, 45 requirements, 55 test scenarios (p=8.69)

A **hosts tab** lists saved host configurations — a name, a remote user, a `hostname[:port]` destination, and an optional remote working directory — and opens an ssh tab to the chosen host with one click. The same names become a shorthand everywhere a host is typed today: `ssh <name>` connects with the saved details, and the `on <name>` clause of `shell`, `harness`, and `agent` accepts a saved name in place of a literal address. Today every remote connection is retyped as a raw destination, and anything beyond `[user@]host[:path]` (a port, for one) has to be pushed into `~/.ssh/config`; saved hosts give the user one place to name a machine once and reuse it. The delivered feature is an ordinary bundled tab plugin with row-level create, edit and delete, saved-name completion, and launch-name display in Sessions.

## Design decisions

Each decision comes from the feature text ("feature text"), from existing behavior ("from precedent"), or from a user answer ("user decision").

- **Host configuration fields (feature text).** `name` (a label for the host), `user` (the user name on the remote host), `destination` (`hostname` with an optional `:port`), and `path` (optional; the working directory on the remote machine, `cd`ed into after login).
- **Unique names (feature text).** A host name must be unique across all configurations.
- **Storage (feature text).** Host configurations are stored in `~/.janissary/hosts.json`, overridden by the project's `.janissary/hosts.json`, "similar to how other configuration files are managed". The existing precedent for that pairing is whole-file replacement: a valid project `.janissary/commands.json` or `.janissary/roles.json` replaces the home file entirely (`product/specs/application-commands.md`, `product/specs/roles.md`).
- **Whole-file override (user decision).** Exactly like `commands.json` and `roles.json`: when a project `.janissary/hosts.json` is in effect it replaces `~/.janissary/hosts.json` entirely; the two are never merged. A usable empty project object is a real override holding zero hosts. Name uniqueness is checked within the file in effect.
- **Save target (user decision).** A host created in the modal is written to the file in effect: the project file when one is in effect, otherwise the home file, which the first save creates. Writes are atomic and preserve every other entry; an unusable project file's bytes are left untouched.
- **File shape (user decision).** A JSON object keyed by host name, each value `{ "user"?, "destination", "path"? }`, matching `roles.json` and `commands.json`. Names are compared case-insensitively, so two keys differing only in case are a duplicate, including a name such as `__proto__`, which is handled like any other own key. `hosts list` prints the decoded hosts in this same shape, sorted by folded name.
- **Optional user (user decision).** Only `name` and `destination` are required. A blank or whitespace-only `user` or `path` counts as absent; an explicit non-string value is refused. A blank `user` means ssh's own default (the local account, or a `User` line in `~/.ssh/config`), exactly as `ssh host` behaves today.
- **Name characters (user decision).** A host name is letters, digits, `.`, `-`, and `_` — the `on` address destination set minus `@` and `:`, so a name can never look like an address. `user`, the destination's host, and `path` are validated with the same character sets as the `on` address parser (`src/remote/address.ts`); a port is digits only, from 1 to 65535. Field messages are `Invalid <field> "<value>". Use letters, digits, and . - _ only.` (with `. - _ / ~` for path), `Invalid port "<value>". Use digits only, from 1 to 65535.`, and `Missing destination.`.
- **Malformed file (user decision).** Any problem with a hosts file — invalid JSON, a top level that is not an object, a malformed entry, a missing destination, an invalid field, or a case-insensitive duplicate name — makes that whole file unusable; no entry from it is used. Janissary never rewrites the file to repair it.
- **Malformed project file falls back (user decision).** A project `.janissary/hosts.json` that is unusable does not take effect: the home file is in effect instead (listed, resolvable, and the save target), and a notification reports the bad project file. When the home file is the one in effect and it is unusable, the list is empty, no saved name resolves, and saving is refused.
- **Malformed-file notification (user decision).** `Hosts file <path> is unusable: <problem>.` is posted once per distinct path-and-problem pair — the first read that finds a given file and problem text posts it, and later reads stay quiet until the problem changes, or is fixed and later reappears. It is sent as a manual notification attributed to the tab that ran the command or that is acting, into the notifications feed; it is never written into that tab's transcript. Completion reads the catalog without a notification callback and so neither posts nor changes the memo.
- **Edit and delete (user decision).** Hosts can be created, edited, and deleted from the tab. Editing opens the same modal prefilled; every field, including the name, is editable, and a renamed entry replaces the old key in one atomic write. A new name colliding (case-insensitively) with another host is refused. Delete asks `Delete host <name>?`; confirming removes the entry in one atomic write. Open ssh tabs and sessions are unaffected by an edit or delete.
- **Command grammar (user decision).** `hosts` opens the single hosts tab, or focuses it. `hosts list` prints the hosts in effect as 2-space-indented JSON, an object keyed by name, in the current transcript; it prints `{}` when there are none or the file in effect is unusable. `hosts add <name> <[user@]host[:port]> [path]` creates a host, or replaces an existing one of that name (case-insensitive); a destination may carry one `@` separating a nonempty user, and a bare or repeated `@` or an empty user is a usage error. `hosts remove <name>` deletes one. Any other form is refused with `Usage: hosts [list|add|remove].`; malformed `add`/`remove` forms print `Usage: hosts add <name> <[user@]host[:port]> [path]` and `Usage: hosts remove <name>`. Verbs match regardless of case.
- **Command wording (user decision).** `Host <name> added.`, `Host <name> updated.` (an `add` that replaced an entry), `Host <name> removed.` (with the stored spelling), and `No host named "<name>".` (with the requested spelling).
- **Error wording (user decision).** Save refused because the file in effect is unusable (modal, delete, or `hosts add/remove`): `Cannot save hosts: <path> is unusable — fix it by hand.` Write failure: `Could not write hosts.json at <path>.` Duplicate name on create or rename in the modal: `Host "<name>" already exists.` An edit or delete whose original row has gone: `No host named "<name>".`
- **ssh tab from a saved host (user decision).** An ssh tab opened through a saved host — a row click or `ssh <name>` — is labeled with the host name (disambiguated `-2`, `-3`, … as today). A typed `ssh <name>` records `ssh <name>` in the creator's transcript, as typed; the normalized registry line is sent to the manager while `invocation.line` supplies the transcript text. A row click records nothing anywhere: the hosts tab has no transcript, and the new tab and its recording are the record. An immediate launch error is returned through the dispatch result instead of a log. The connections panel keeps showing `ssh:<destination>` with the real `[user@]host`; the saved spelling travels on the tab for later views only. Only a bare `ssh <name>` looks up a saved host; flags, extra words, a trailing command, or an `@`/`:` address pass to ssh verbatim. A case-insensitive name wins over a literal hostname or `~/.ssh/config` alias of the same spelling, and a saved-name miss from a Hosts row is reported as `No host named "<name>".` without spawning.
- **Saved path and port in an ssh tab (user decision).** The saved port is passed as `-p <port>` before the destination and `--` separates the destination so a leading hyphen is an operand. A saved path asks for a terminal with `-t` and sends one remote command argument: change into the directory, print a diagnostic and continue in the login directory on failure, then start the account's login shell. The whole remote command is one local-shell word, so `$HOME`, `$SHELL` and command separators are expanded only on the remote side; a bare `~` and a `~/` prefix resolve against the remote home with the rest kept literal.
- **Sessions Host column (user decision).** Only a session launched through a saved host — `ssh <name>`, `on <name>`, or a host row — shows that host's name in the Host column; a session started from a typed address keeps the bare host. The name is the one used at launch, recorded with the session (including the parked-session record), and shown for the session's whole life even if the host entry is later renamed or deleted. The tooltip keeps the original destination.
- **Empty state (user decision).** With no saved hosts, or with the file in effect unusable, the tab shows only `No saved hosts`, with no table headings, matching the sessions tab's `No remote sessions`. The plus button still works.
- **Refresh (user decision).** Writes Janissary makes — modal save, row delete, `hosts add`, `hosts remove` — update an open hosts tab immediately through `updateTab` with the written catalog. Hand edits to either file appear on Refresh or when the tab regains focus, like the sessions tab; the tab refreshes on a return to active but not on first open. Running `hosts` again refreshes an already open instance in place. There is no file watcher.
- **Tab completion (user decision).** Saved host names are offered as completions after `ssh ` (only when it is the bare whole line), after `on ` in `shell`, `harness`, and `agent` (verified with each command's own parser), and after `hosts remove `. Matching ignores case, a unique match keeps its stored spelling, several extend the typed prefix, and a trailing space is added only at the end of the line.
- **`on <name>` lookup (user decision).** A token exactly matching a saved name (case-insensitive) uses the saved host, even when it is also a reachable hostname. A token containing `@` or `:` never matches a name and is parsed as an address, as today. The saved endpoint is pinned for the launch: initial connection, transport retries, and a name-refusal retry reuse one resolved address. A saved name that looks like a keyword — `with`, `as`, `in`, `--offline`, or `build-with-ssh` — still reaches the executor as the address rather than becoming a prompt delimiter, label, group clause, or flag. `execute` is a valid saved name in `on execute` when a real `execute <task>` clause follows; `agent on execute task.md` still reports `Agent: missing value for on.`
- **`on <name>` semantics (user decision).** `on <name>` behaves exactly like `on [user@]host[:path]` built from the saved host: `path` is the remote project root, and a host with no path walks up from the ssh login directory. For agent runs, a saved path forces a run-only channel; with no path an established workspace is borrowed only when its full destination matches case-insensitively and its port matches exactly (an omitted port matches only an omitted one).
- **Lookup against an unusable file (user decision).** When the file in effect is unusable, `ssh <name>` and `on <name>` behave exactly as today, treating the token as a literal hostname or alias, and the once-per-problem `Hosts file <path> is unusable: <problem>.` notification is posted. A usable home catalog can still supply the match after a malformed project file is reported.
- **Ports on remote launches (user decision).** A saved host's port is honored by `on <name>` for `shell`, `harness`, and `agent`: the remote ssh command passes it to ssh and precedes a saved destination with `--`. A typed `on <address>` still accepts no port, and a trailing `:2222` there remains a directory name. The port and saved name are written into parked-session records and restored on attach, terminate, and capture queries.
- **Row actions column (user decision).** The table's trailing column is `4em` wide so both the edit pencil and delete trash are fully visible at normal and narrow widths. Ellipsis applies to the four text cells only, never to the row controls; the heading and rows share one grid template and the action span keeps its flex layout so it is not clipped.
- **Opening (feature text).** The `hosts` command opens the hosts tab. The tab is not dockable: a shared hosts-specific exclusion in `canDockTab` blocks both the generic `tab dock` operation and the `setDock` RPC, while the host-rendered Split action still works and other plugins keep their docking behavior.
- **A bundled tab plugin (user decision, replacing the feature text).** The feature text said "core, not a plugin"; the user chose to build it with the tab-plugin machinery as an ordinary bundled plugin, listed by `plugins` like sessions, because that is the lowest-cost route and every capability it needs already exists.
- **Plugin-owned hosts file module (user decision).** The read/decode/write module lives in the plugin and core imports it, the precedent `src/acp/ask-role.ts` set by importing `src/plugins/roles/roles-file.ts`. No new topic or capability.
- **Row launch (user decision).** Opening a host row runs `ssh <name>` through the existing `dispatchLineWithOutput` capability, so the core ssh command is the only place a saved host becomes an ssh spawn. A narrow origin rule at the SSH command and dispatch-manager seams exempts that one command from transcript capture and returns its policy errors through the dispatch result; the Hosts log is never appended to, while other callers, including Shell, keep capture.
- **Address resolution (user decision).** `RemoteAddress` gains optional `port` and `hostName`; saved names are resolved in the execution layer, never in a parser.
- **Listing as JSON (feature text).** `hosts list` lists the host configurations as JSON.
- **Click to connect (feature text).** Opening a host row launches an ssh tab connecting to that host's destination.
- **`ssh <name>` (feature text).** `ssh <name>` looks up the named host configuration and connects with its details.
- **`on <name>` (feature text).** The `shell`, `agent`, and `harness` commands, which accept an `on <address>` clause for remote machines, also accept a host configuration name there.
- **Header (feature text).** The tab has a metadata bar like the sessions tab, with Refresh and Split icon buttons, plus a plus icon button that opens a create-new-host-configuration modal.
- **Table look and feel (feature text).** The hosts table is styled like, and has the same keyboard and mouse interactions as, the sessions tab table.
- **Sessions host column (feature text).** The sessions tab's Host column shows the host configuration name when a configuration matches the row, instead of the ssh destination.

## Proposed changes

### Hosts file module — `src/plugins/hosts/hosts-file.ts`

The pure value layer lives in `src/plugins/hosts/hosts-values.ts`, owned by the plugin and imported by core where core needs saved hosts, exactly as `src/plugins/roles/roles-file.ts` is imported by `src/acp/ask-role.ts` (user decision). It holds:

- A `SavedHost` type `{ name, host, user?, port?, path? }` and a pure `decodeHosts` from parsed JSON to either a name-sorted list of saved hosts or a one-line problem. It rejects a non-object top level (`Hosts catalog is not an object.`), a non-object entry, a missing destination (`Missing destination.`), a name or field outside its character set, a port that is not an integer from 1 to 65535, and case-insensitive duplicate names. Own entries are iterated so a valid name such as `__proto__` is handled like any other; rows are sorted by folded name with saved spelling preserved.
- The character sets: the plugin boundary lint (`eslint.plugin-boundaries.mjs`, first block) forbids a server plugin from importing `src/remote/address.ts`, so this module declares its own patterns — name `[\w.-]`, user and host the `DESTINATION_PATTERN` set without `@`, path the `PATH_PATTERN` set — each a single character class under one quantifier (`security/detect-unsafe-regex`). Parity with `src/remote/address.ts` is pinned by a test in `src/plugins/hosts/hosts-values.test.ts` that runs a shared corpus of accepted and rejected strings through both (tests are exempt from the boundary rule), so a saved host can never resolve to an address `parseRemoteAddress` would reject.
- `validateHostFields(name, user, destination, path)` returns the exact field messages in Design decisions, shared by the modal save intent and `hosts add`. A destination splits at the first colon into a host and an optional digits-only port; a second colon fails. The file decoder runs each entry through this same validator, so there is one set of field rules. `isHostName`, `formatDestination` (`host[:port]`) and `sameHostName` (case-insensitive) are exported for the command, completion, launch and row layers.

The I/O layer in `src/plugins/hosts/hosts-file.ts` holds:

- `readHostsFile(root, home, notify?)`: resolves the file in effect — the project file when it exists and decodes, otherwise the home file — and returns the hosts, the path in effect (the home path when neither file exists), whether that file is usable, and separate `{ path, problem }` entries for every unusable file consulted. A missing path is distinguished from an unreadable one with an `ENOENT` probe; an existing directory at the config path and a failed read are unusable. Built on `readJsonConfigFile` (`src/plugins/files.ts`), the way `readRolesFile` in `src/plugins/roles/roles-file.ts` is. A missing file is not a problem: it reads as zero hosts and usable.
- A process-lifetime map from path to its last reported problem, so each distinct problem is reported once; a usable or missing consulted file clears its path's entry, an unconsulted home file keeps its memo, and omitting the callback (completion) leaves the memo untouched.
- One `serializeHosts` for transcript output and file writes: `JSON.stringify` of the object keyed by name, sorted by folded name, 2-space indented, assembled member by member so numeric and ordinary keys such as `__proto__` keep their order. It prints `{}` for no hosts. `writeHostsFile(path, hosts)` writes it plus a trailing newline through `writeJsonConfigFile` (`src/plugins/files.ts`, which wraps `atomicWriteFile`), creating the parent directory first as `roles-file.ts` does.
- `mutateHostsFile(root, home, notify, change)`: the synchronous read-modify-write entry point. It selects the effective file again immediately before writing, refuses an unusable file with `Cannot save hosts: <path> is unusable — fix it by hand.`, applies the caller's change, and atomically writes the sorted result. A business-rule refusal returns the caller's diagnostic with no write; a directory-creation or write failure returns `Could not write hosts.json at <path>.` It returns the written catalog and path only after replacement succeeds, so callers can repaint from the resulting data.

### Hosts plugin — `src/plugins/hosts/` and `web/src/plugins/hosts/`

An ordinary bundled tab plugin (user decision, replacing the feature text's "core, not a plugin"), shaped like the sessions and roles plugins and listed by `plugins` like them:

- `manifest.ts` follows `src/plugins/sessions/manifest.ts`: id, command and label prefix all `hosts`, `HOSTS_PAYLOAD_SCHEMA_VERSION` (1), an empty `fileExtensions` object, and capabilities `originTab`, `notifyUser`, `note`, `openOrFocusTab`, `updateTab`, `dispatchLineWithOutput`, `rejectRequest`, and `reportFailure`. It declares no topic or dock capability; its command reads no `left|right` argument, which is what keeps it out of the sidebars.
- `shared.ts` (import-free) defines the payload — `filePath` and rows `{ name, user, destination, path }` with absent user or path as empty strings — the intent payloads (`refresh`, `open`, `save` with an optional original name, `delete`), `SaveHostResult` (`{ ok: true, name }` or `{ ok: false, error }`), and their hand-written guards.
- `catalog-commands.ts` holds pure `parseCatalogCommand` and synchronous `runCatalogCommand`: verb and subcommand matching ignore case; `list` returns the serialized catalog as plain output; `add` parses one optional `@` user and validates all fields before any I/O, reporting `added`/`updated`; `remove` reports `No host named "<name>".` on a miss. Open, output, refusal and successful mutation are distinct outcomes, and only a successful mutation carries the written catalog and path for `updateTab`.
- `host-edits.ts` holds `saveHostEdit` and `deleteHostEdit` over `mutateHostsFile`: a create refuses an occupied name, an edit may replace its own original key (including a case-only rename), a collision with another row returns `Host "<name>" already exists.`, and a stale original returns `No host named "<name>".`
- `activate.ts` uses `originTab()?.root` and `homedir()` for all catalog operations and declines a request whose origin has closed. A bare `hosts` reads, publishes with `updateTab`, then opens or focuses the single tab (refreshing an already open instance); other forms run the catalog handler through `note` or `rejectRequest`. Intents: `refresh` re-reads; `open` checks the name against the server-owned payload and the catalog, publishes fresh rows and notifies on a stale row, then dispatches the stored spelling as `ssh <name>` through `dispatchLineWithOutput`, notifying on a refusal or `Could not open host "<name>".`; `save` returns the inline `SaveHostResult`; `delete` notifies failures against the Hosts instance and returns `null`. Read problems are attributed to the answering tab with `{ tab: 'hosts' }` for intents.
- A shared `canDockTab` in `src/tab/dock.ts` excludes the hosts plugin from both `isDockableTab`/the `tab dock` operation and `setDock` in `src/tab/operations.ts`; Split remains available.
- Catalog entry in `src/plugins/catalog.ts`, literal lazy loaders in `src/plugins/loaders.ts` and `web/src/plugins/registry.tsx`. Client: `index.tsx` (default component, `isPayload`), `HostList.tsx`, `HostRowActions.tsx`, `HostForm.tsx`, a pure `hosts-keys.ts` reusing the published `nextListSelection` and restating the sessions click rule, and `hosts.css` matching `sessions.css` with a `4em` action track and text-only ellipsis. `ModalDialog` and `useDialogKeyboard` are published additively through `web/src/plugins/api.ts`; `ConfirmDialog` gains an optional `confirmDisabled` that the shell applies to mouse, `y` and Enter.

### `ssh <name>` — `src/ssh.ts`, `src/ssh-manager.ts`

Two pure helpers in `src/ssh-saved-host.ts` build the invocation. `savedSshName` accepts a case-insensitive command word and exactly one token after trimming; a lone hyphen-prefixed token can name a saved host, while a catalog miss, flags with a destination, a trailing remote command, and a qualified address fall through to the unchanged `parseSshCommand` (`src/ssh.ts`). `buildSavedSshInvocation` returns the real `[user@]host` destination, the stored name as the label, and `SshParsed` options: `-p <port>` when saved, `--` immediately before the destination, `-t` plus one single remote-command option when a path is saved. The remote command changes into that directory (quoting ordinary and leading-hyphen paths, resolving `~` and `~/` against the remote home), prints `janissary: cannot change directory to <path>` and continues in the login directory on failure, then runs `exec "$SHELL" -l`. The pure `shellQuote` moved from `src/harness/index.ts` to `src/shell/quote.ts`, keeping harness output unchanged.

In `SshManager.run` (`src/ssh-manager.ts`), an eligible name is read against the effective file (project root from `Managers`, home from `os.homedir()`) and the reader's diagnostics are forwarded through `notify(managers, 'manual', creatorLabel, message)`. A case-insensitive match wins over a literal hostname or alias; an unmatched name, an unusable file, and a home catalog that rescues a malformed project file follow the shared rules. A Hosts-origin miss returns `No host named "<name>".` without spawning. The command registry entry (`src/commands/ssh.ts`) passes the execution tab label to the manager and uses `invocation.line` as the typed transcript text; a Hosts dispatch bypasses `runDelegated`. A narrow origin check in `src/command/manager.ts` keeps disabled, unavailable and failed Hosts-ssh dispatch errors in the result instead of the Hosts log. `open` takes the named tab as creator when given (group, color, `cwdOf` follow the source), applies `uniqueLabel` to the saved spelling, sets `hostName` beside `destination` on `HarnessView`, copies the builder's full options, and keeps the sessions signal and PTY-exit lifecycle. The connections panel still builds `ssh:<destination>` from the real host.

### `on <name>` — `src/remote/address.ts` and its callers

- `RemoteAddress` (`src/remote/address.ts`) gains optional `port` and `hostName`; its comment records that `address` holds the concrete `[user@]host[:path]` for a resolved name, never the bare name. `parseRemoteAddress` stays pure and unchanged: a token like `devbox:2222` still parses with path `2222` and no port or saved name.
- `resolveSavedHost(token, hosts)` and `resolveRemoteLaunchAddress(managers, originLabel, parsed)` live in `src/remote/saved-host.ts`. A bare case-folded match builds a `RemoteAddress` with the saved destination, host, path, port and stored name; a qualified `@`/`:` token, a miss, or an unusable catalog returns the parsed address. The helper reads the catalog once, forwards its deduplicated problem through `notify(managers, 'manual', originLabel, message)`, and is shared by the three executors. It stays in core so plugin capability declarations do not change.
- harness: `src/harness/manager.ts` resolves `parsed.remote` once after the launch and model checks, attributing notices to the caller label, and passes the resolved address through `open`. `src/harness/command-parse.ts` keeps `findRemoteClause` pure: `onOperandSpan` protects the first `on` operand from `with` splitting and `withoutOnOperand` blanks that token for group, flag and `as` scans, so keyword-like names reach the executor while a real trailing prompt still works.
- shell: `src/plugins/launch-tab-remote.ts` resolves right after parsing on the new-address branch, using `input.origin.label`; the resolved address is captured by the name-refusal retry so a catalog change cannot move a channel mid-launch, and is used for channel setup, payload host, cleanup reports and error messages. The unrelated adoption and join helpers moved to `src/plugins/launch-tab-remote-reuse.ts` to stay under the line limit. The shell plugin's own `remote: { address }` request is unchanged.
- agent: `src/agent/remote-target.ts` resolves after `parseRemoteAddress` and before workspace matching. Endpoint reuse compares the full destination case-insensitively and the port exactly (omitted matches omitted only); a saved path forces a fresh run-only channel at that path. The chosen channel keeps its identity and gains only the run's lease.
- `src/sessions/ssh-bridge.ts`'s `startRemoteLaunch` call needs no lookup: it rebuilds from the record, which now carries `port` and `hostName`.
- `sshRemoteCommand` in `src/remote/entry-factory.ts` is the single builder for `remoteServeCommand` and `remoteCaptureCommand`: it adds `-p <port>` among the ssh options and precedes a saved (`hostName`) destination with `--`, keeping literal commands byte-identical. `createRemoteEntry` closes its connect callback over the address, so the initial connection and `Attach` retries share it.
- `RemoteSessionRecord` (`src/sessions/store.ts`) persists optional `port` (integer 1–65535) and `hostName` (nonempty string) beside `address`; `recordOf` in `src/sessions/snapshot.ts` copies both. Pure `addressFromSessionRecord` in `src/sessions/record-address.ts` restores them through `parseRemoteAddress`; `src/sessions/attach.ts`, `src/sessions/terminate-session.ts` and `src/harness/capture/remote.ts` use it so attach, terminate and parked capture reach the recorded port and name. Old and typed-address records keep their existing behavior.

### Sessions Host column — `src/sessions/rows.ts`, `src/protocol/sessions.ts`

`RemoteSessionView` (`src/protocol/sessions.ts`), `SessionRow` (`src/plugins/sessions/shared.ts`) and `SessionChannel`, `SessionSsh`, `SessionDetached` and `SessionTerminated` (`src/sessions/rows.ts`) gain optional `hostName`, guarded by the existing optional-string check; the payload schema stays at 1. `toPayload` in `src/plugins/sessions/activate.ts` copies it through the adapter shared by open and topic updates. `src/sessions/snapshot.ts` fills it from the channel's or tab's address; `liveRows`, `sshRow`, `detachedRows` and `terminatedRow` project it, and `terminatedRowFrom` in `src/sessions/actions.ts` carries it from the record, so the name survives join, reconnect, park, reattach and termination without a catalog dependency. `web/src/plugins/sessions/SessionRowBody.tsx` renders `hostName ?? host` in both wide and docked rows; the payload keeps the bare host and the tooltip keeps the full destination. A literal launch keeps the bare host even when a saved entry shares the destination. The projection fits within `src/sessions/rows.ts`, so no extraction module was needed.

### Completion — `src/completion/`

`src/completion/hosts.ts` exports `isSavedHostSlot` and a pure `completeSavedHost(cursor, names)` built on `completeWord` (`src/completion/helpers.ts`), modelled on `completeMonitorCommand` in `src/completion/handlers.ts`. The slot predicate rejects an open quote, a cursor inside a token, an address containing `@` or `:`, and a non-name prefix; it offers names at argument 1 of `ssh` only when the rest of the line is whitespace, at argument 2 of `hosts remove` (subcommand case-insensitive), and at the token after `on` in `shell`, `harness` and `agent`. For those three it probes `parseShellArgument`, `parseHarnessCommand` and `parseAgentCommand` with a distinct placeholder in place of the token, so group values, harness capture and prompt targets, and agent task text never request names while text after the cursor is preserved. `completeWord` gained an additive, case-insensitive option that folds matching and ordering but keeps the stored spelling on insertion. `completeCommandLine` (`src/completion/index.ts`) takes a trailing optional names provider `() => string[]` and consults it immediately before filesystem fallback, only in an eligible slot. `complete` in `src/controller/completion.ts` supplies a provider that quietly calls `readHostsFile(managers.tab.launchDir, homedir())` and maps the effective catalog to saved names; an unusable file contributes none and changes no notification memo. `src/agent/command-parser.ts` accepts `execute` as an `on` value when a real final `execute <task>` clause follows.

## UI design

The hosts tab is a non-dockable plugin tab in the centre tab area, titled **hosts**; `hosts` opens it or focuses the one already open. Its table and interactions mirror the sessions tab (`web/src/plugins/sessions/SessionList.tsx`, `sessions-keys.ts`, `sessions.css`).

- **Header (feature text, user decision).** A full-width metadata bar like the sessions tab's, with icon buttons together at the right edge: `Refresh` (rotate icon), `New host` (plus icon), and the host-rendered Split control. There is no dock control.
- **Table (user decision).** Columns Name, User, Destination, Path, then an unlabeled actions column `4em` wide so both row controls show in full. Headings and cells are left-aligned with 12px horizontal padding and share one grid template. Destination shows `host[:port]`; a blank user or path leaves an empty cell. Rows are sorted by name, case-insensitively. Long text cells ellipsize; the action cell never does.
- **Row actions (user decision).** Right-aligned icon-only buttons, styled like `SessionRowActions`: a pencil labelled `Edit host <name>` and a trash labelled `Delete host <name>`, muted at rest and bright on hover. Pressing one does not move the selection or open the row.
- **Opening a row (feature text, from precedent).** One click makes a row current, a second click on the current row opens it, and Enter opens the current row; opening launches the ssh tab for that host. Up and Down move without wrapping; Home and End jump to the ends (`nextListSelection`, `sessionClickSelection` behavior). The list takes focus when the tab becomes active and re-reads the files only on a return to active. Escape on the list does nothing; a focused control handles its own keys.
- **Keyboard (user decision).** `Cmd+N` / `Ctrl+N` on the list opens the New host modal, ignored with Shift or Alt or when a button has focus — the same list-local binding the conversation list uses, so it collides with nothing in `help/keys.md`; it is added there. Edit and delete have no keys.
- **Modal (user decision).** `HostForm` composes `ModalDialog` and `useDialogKeyboard`, titled `New host` or `Edit host <name>`. Four labelled inputs — `Name`, `User`, `Destination`, `Path` — with placeholders `optional` for User and Path and `host[:port]` for Destination; buttons `Save` and `Cancel`. Edit prefills every field. Focus lands on Name; Tab wraps through the fields and buttons; Enter in any field saves via native form submission; Escape or Cancel closes without saving while idle. A validation or save error appears inline above the buttons and the modal stays open; Save is disabled while a save is in flight, and neither Cancel nor Escape dismisses an in-flight form. On success the modal closes and focus returns to the list on the saved row, whether the save reply or the updated snapshot arrives first, following a rename to its new position.
- **Delete (user decision).** The shared `ConfirmDialog` titled `Delete host <name>?` with a `Delete` button. Cancel, `n` and Escape dismiss while idle. Once confirmed the button is disabled and the dialog stays open during the request, including against repeated clicks and `y`/Enter, so the host cannot be deleted twice. The dialog closes on success, a handled refusal or a failed request; the server reports ordinary failures as notifications attributed to Hosts. The row always comes from the authoritative payload.
- **States (user decision).** Empty or unusable: only `No saved hosts`, no headings; the plus button stays enabled and a save is refused inline. There is no loading state: the rows arrive with the tab. Long cells ellipsize; the row tooltip shows the full `[user@]host[:port]` on one line and the path on the next.
- **Code placement (from guidelines).** Client code lives in the plugin's own directory, `web/src/plugins/hosts/`: a pure key module and thin components (list, row actions, form). The form's four field values, its in-flight flag, and its error string are plain `useState` inside the component — no separate hook — because validation happens on the server. Under the client plugin boundary lint it imports only the published `../api`, `../shared.css`, and `@shared/plugins/hosts/shared`, never the sessions plugin's files; the sessions click rule is restated in the hosts key module. The host list, the file in effect, and every validation verdict are server state per `ai/guidelines/architecture-principles.md` §1: the client renders the rows the server sends, emits `save`, `delete`, `refresh`, and `open` intents, and shows the error string a `save` intent returns.

## Out of scope

- Docking the hosts tab into a sidebar (feature text).
- Merging the home and project hosts files (user decision: whole-file replacement).
- Extra ssh options per host — identity file, jump host, arbitrary flags — and importing hosts from `~/.ssh/config` (user decision).
- Reachability or status per host, and launching a shell or harness from a host row (user decision).
- Matching typed addresses against saved hosts for the sessions Host column (user decision: only sessions launched through a saved name show it).
- Repairing a malformed hosts file automatically (user decision).
- Ports in a typed `on <address>` (from precedent; only a saved host's port is honored).
