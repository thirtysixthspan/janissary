# Disable git-sync off the primary branch

**Complexity: 3/10** — the behavior change is one extra condition on a single existing predicate, and everything it needs is either already resolved by the navigator's git-metadata refresh or a two-line addition to `src/git/status.ts`. The number is not lower because correctness depends on catching every entry point into `OpenFileManager` and on the fallback path for opens with no navigator behind them. One new small module (the launch-dir cache), no new subsystem, no new RPC or client-visible field, no UI.

Backlog text, verbatim: *"if the file navigator is on a branch other than the primary branch of the repository, the git-sync functionality should disabled so that the branch files can be edited directly."*

GitHub syncing (`product/specs/editor-tab.md` → "GitHub syncing") is entirely config-driven: a file whose project-relative path is covered by `syncPaths` is always opened from inside the shared `git-sync` workspace clone, never from the project checkout, and its saves commit/pull-rebase/push against `origin/master`. That is the right behavior when the project checkout is sitting on its primary branch and the user is editing the canonical copy of a plan or backlog file. It is the wrong behavior when the checkout is on a feature branch: the user is deliberately working on branch content, and every synced-path file they open silently redirects to a different clone on `master`, so their branch's own copy of that file cannot be edited at all from the file navigator. This plan makes the sync redirect conditional on being on the primary branch, so that off-branch the same file opens as an ordinary editor tab against the real file on disk.

## Design decisions

- **The gate is the existing one.** Syncing is already gated in exactly one place — `OpenFileManager.isSyncPath` (`src/open/file-manager.ts:124`), consulted by both `edit` (line 57) and `openOne` (line 118). Everything downstream keys off `EditorView.sync` being set at all: the save cycle (`src/editor/save.ts:66`), the manual resync RPC (`src/editor/resync.ts:12`), and the status icon in the metadata header all no-op when that field is absent. So a file that does not take the synced open path is an ordinary editor tab in every later respect, with no second place to disable.
- **Off-primary means editing the real file in place.** When the gate declines, `edit`/`openOne` fall through to `openInEditor` against the resolved path in the project checkout — the existing non-synced path, unchanged. No new "disabled sync" mode is introduced; the feature is expressed entirely as the gate answering "no".
- **No new UI toggle, and nothing user-visible announces the state.** Consistent with the spec's "syncing is entirely config-driven — there is no button or toggle anywhere in the editor to turn it on or off for a file," the branch condition is another automatic input to the same gate. Off the primary branch a syncPaths file simply opens as an ordinary editor tab with no sync status icon; the absent icon is the entire signal. No notification, no disabled-state icon, no new `EditorView` field.
- **The governing branch is the opening file navigator's root repo.** For a file activated from a file navigator tab, the gate reads that tab's own root's branch — the same branch the user can already see in the navigator header. A navigator rooted in a nested repository inside the project therefore governs its own subtree, and a navigator rooted outside the project launch dir is moot anyway, since `syncPaths` are launch-dir-relative and a file outside it never matches.
- **Non-navigator opens fall back to the launch dir's branch.** `edit product/backlog/features.md` typed in a shell tab, a profile restoring a saved editor tab, and a plugin opener all have no navigator to read. They use the project root's own checked-out branch instead — the same rule against a different root, so a primary-branch checkout syncs and a feature-branch checkout does not, however the file was opened.
- **Primary branch is the detected default branch, not a hardcoded name.** The comparison target is the remote's default branch, resolved from `origin/HEAD`. A repository whose default branch is `main` therefore counts as on-primary while `main` is checked out. Note the consequence: the sync engine still pushes to `origin/master` (`src/git/sync.ts`), so such a repository enables syncing and then surfaces the existing sync-error state — unchanged from today, and explicitly out of scope here.
- **Anything unclassifiable disables syncing.** A detached HEAD (the literal `HEAD` that `currentBranch` returns), a root that is not inside a git repository, or any git failure all mean the gate cannot positively confirm the primary branch — and all of them disable syncing, so the file opens directly. This is the safe direction: a wrong redirect silently hides the content the user is looking at, while a wrong pass-through only costs the user an automatic push.
- **An unresolvable `origin/HEAD` falls back to `master` or `main`.** `origin/HEAD` is set by `git clone` but is routinely missing in a repository created with `git init` plus `git remote add`, so treating "no detectable default branch" as unclassifiable would silently switch syncing off for a valid project sitting on its main branch. Instead, when the default branch cannot be resolved, the checked-out branch is primary if it is literally `master` or `main`, and not primary otherwise. Neither name is preferred over the other and no remote lookup is attempted — this is a local, offline decision. Detached HEAD and non-git roots are unaffected by this fallback and still disable syncing.
- **The decision is made at open time and never revisited.** A synced tab that is already open when the checkout switches branches keeps its sync workspace path, its status icon, and its save-push cycle until it is closed and reopened. There is no branch-change watcher and no re-pointing of live tabs.
- **The branch value is the one the navigator already cached, refreshed only when the navigator refreshes it.** No git call is added to the open path. The gate reads the branch already resolved by the navigator's existing `gitMetadata` load and held in its view state, so the decision always agrees with what the navigator header displays. A branch switched outside the app is picked up the next time that navigator reloads its git metadata — on open, reroot, pull, or tree refresh — and until then the gate uses the last known value.

## Proposed changes

- `src/git/status.ts` gains a companion to `currentBranch` (`status.ts:81`) that resolves a repository's default branch name by reading `origin/HEAD` locally — no network call, so it costs the same as the reads already in `loadGitMetadata`'s `Promise.all`. It follows that file's established shape exactly: an absolute root in, a short branch name or `undefined` out, never rejecting, `undefined` for a non-repo root, a missing remote, an unset `origin/HEAD`, or any git failure. Adding it keeps `status.ts` (58 effective lines) far under the 200-line limit.
- `GitMetadata` (declared at `src/file-navigator/filesystem-port.ts:53`) gains the detected default branch, resolved in `loadGitMetadata`'s existing `Promise.all` (`filesystem-port.ts:107-109`) alongside `changedPaths`/`currentBranch`/`remoteUrl`. `RemotePort.gitMetadata` (`src/file-navigator/remote-port.ts:80`) must satisfy the widened type; it spreads the far side's reply verbatim, so a remote tree forwards whatever its own host resolved for its workspace. An absent value is not a classification of "unsynced" — `isPrimaryBranch` falls back to exact membership in `master`/`main` when no default is detected, so an absent default with `master` checked out classifies as primary. What keeps remote trees out of the gate is path shape: their files are materialized under `.janissary/remote-files/` and so never match a launch-dir-relative sync path (see Out of scope).
- `FilesTabState` (`src/file-navigator/state.ts:40-44`) gains the detected default branch beside `branch`, written in `refreshGit`'s callback next to `current.branch = branch` (`src/file-navigator/git-refresh.ts:24`). No new refresh trigger and no new coalescing logic: every existing refresh point — open, reroot, pull, tree refresh — already routes through `refreshGit`. **No field is added to `FileNavigatorView` or the protocol**: the value is consumed server-side only, so nothing new crosses to the client.
- The classification itself is one exported pure predicate, added to `src/git/status.ts` next to `currentBranch` — no new module. That file already owns this vocabulary (it is where the "literal `HEAD` for a detached checkout" convention is documented, `status.ts:77-80`) and sits at 58 effective lines, far under the limit. Given a current branch and a detected default branch it answers whether the repository is confirmably on its primary branch: false when the current branch is absent or is the literal `HEAD`; otherwise an exact match against the detected default branch when there is one, and membership in the fixed pair `master`/`main` when there is not. Both the navigator path and the launch-dir fallback call this one function, so the classification rule — including the `master`/`main` fallback — is written and tested once.
- `FileNavigatorManager` gains a read-only accessor alongside `rootOf` (`src/file-navigator/manager.ts:207`) answering, for a tab label, whether that tab is a file navigator whose tree is confirmably on its primary branch — `undefined` when the label is not a navigator tab, so the caller can tell "not a navigator" apart from "navigator, not primary". `manager.ts` is at 181 effective lines against the 200-line limit, so if this accessor pushes it over, extract the label-keyed git accessors into a module beside `git-refresh.ts` rather than compacting the file.
- `OpenFileManager.isSyncPath` (`src/open/file-manager.ts:124`) gains the branch condition in place and takes the issuing tab's label, which both call sites already have (`edit` at `file-manager.ts:57`, `openOne` at `file-manager.ts:118`). It asks `managers.fileNavigator` first; when that returns `undefined` (a shell tab's `edit`, a profile restore, a plugin opener) it falls back to the launch dir's cached pair. It stays synchronous: both inputs are values resolved elsewhere, never a git call made here. No extraction is needed — `file-manager.ts` is at 122 effective lines, and the added condition is a few lines.
- The launch dir's branch pair lives in a small module holding one cached record for `tab.launchDir`, exposing a synchronous read and a fire-and-forget refresh, resolved once where `GitSync` is constructed (`src/controller/create-managers.ts:52`) and refreshed — again fire-and-forget, never awaited — each time the gate classifies a non-navigator open. Deliberate ceiling: the cache is refreshed on use, not watched, so the first non-navigator open after a branch switch made outside the app still sees the previous branch and the one after it is correct. That is acceptable because the navigator path (the flow the feature is actually about) is always current, and the upgrade path if it ever matters is to refresh this value from the same points `refreshGit` already fires rather than to add a watcher.
- `product/specs/editor-tab.md` → "GitHub syncing" is updated to state the branch condition: a config-listed path syncs only while the governing checkout is confirmably on its repository's default branch, and opens as an ordinary editor tab against the real file otherwise, with no sync status icon. It names which checkout governs (the opening navigator's root, else the project root) and records that the decision is made once at open time.
- `product/specs/file-navigator-tab.md` → "Branch metadata" is updated to note that the branch it already displays also determines whether files activated from that tree are opened through GitHub syncing. Nothing changes in what the header renders.

Landing order, to keep `check-diff` green at each step: (1) the default-branch resolver and the pure classifier, both in `src/git/status.ts`, with tests and no callers yet; (2) threading the value through `GitMetadata` → `loadGitMetadata` → `refreshGit` → `FilesTabState`, plus the `RemotePort` signature; (3) the launch-dir cache module; (4) the `FileNavigatorManager` accessor; (5) the condition in `isSyncPath` — the only step that changes observable behavior; (6) the two spec updates.

## Tests

- `src/open/file-manager.test.ts` (extend the existing file): activating a config-listed path from a navigator tab whose branch matches its detected default still routes into the shared sync workspace and opens with `sync: 'provisioning'`; the same activation from a navigator on a feature branch opens an ordinary editor tab targeting the real file under the navigator's root, with no `sync` field; a non-config-listed path is unaffected either way; an `edit` issued from a non-navigator tab follows the launch dir's branch rather than any open navigator's; a `main`-default repository on `main` still syncs.
- `src/git/status.test.ts` (extend) covers both additions. The classifier, as pure cases needing no temp repo: primary on an exact branch/default match; not primary for a feature branch, for the literal `HEAD`, or when the current branch is absent; and, with no detected default branch, primary for both `master` and `main` but for no other name. The default-branch resolver, using that file's existing temp-repo fixture conventions: the configured default for a repo with `origin/HEAD` set, and `undefined` for a repo with no remote, a root outside any repository, and a repo whose `origin/HEAD` is unset. That file's note at `status.test.ts:8` about `init.defaultBranch` varying by machine makes pinning the branch name in each fixture necessary rather than optional here.
- A colocated test for the launch-dir cache module: reads as unconfirmed before its first resolution, reports the resolved pair after a refresh, and stays unconfirmed when the launch dir is not a git repository.
- `src/file-navigator` tests (extend the existing git-metadata/`refreshGit` coverage): the default branch is loaded alongside `branch`/`statuses`/`githubUrl` and written into `FilesTabState`, both branch values update together on a refresh, and a refresh whose tab rerooted mid-flight is still discarded (existing behavior, re-asserted now that a second value rides along).
- No web tests and no protocol test changes: nothing rendered changes and no client-visible field is added.

## Out of scope

- Any change to the sync engine itself (`src/git/sync.ts`) — the shared workspace, its commit/pull-rebase/push cycle, and its `origin/master` target are untouched.
- Syncing a file against a branch other than the sync workspace's own — this plan disables syncing off the primary branch, it does not add per-branch syncing.
- Any user-facing control, indicator, notification, or tooltip announcing that syncing is off because of the branch — the absent sync icon is the only signal.
- Changing which paths are eligible for syncing (`syncPaths` semantics are unchanged).
- Re-evaluating already-open synced tabs when the checkout changes branches, and any branch-change watcher that would drive it.
- Fixing the `main`-default repository case: such a repo now counts as on-primary and enables syncing, then hits the existing `origin/master` sync error exactly as it does today. Making the sync engine target the detected default branch is separate work.
- Remote (SSH-rooted) navigator trees: their branch metadata is unchanged, and `syncPaths` are launch-dir-relative, so no remote file is a sync candidate in the first place.
