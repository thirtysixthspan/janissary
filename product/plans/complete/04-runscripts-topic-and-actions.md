# Runscripts host topic and its actions
**Complexity: 4/10** — a new host topic across the contract, the topic source, a new action module, and one gated host subscription, with six actions whose origin, missing-file, and feed-wording rules have to match the spec.

## Goal

Add `runscripts` as a host topic. It needs contract types, a source that reads rows, subscribes to the change signal, and returns an empty value, and an action module that runs execute, delete, clone, create, open, and the tab-open directory setup. Failures go to the notifications feed.

## Design decisions and dependencies

This subplan depends on `01-runscript-file-operations` (file helpers), `02-shared-runscript-execution` (`runRunscriptNow`), and `03-runscript-tick-refresh` (rows, protocol types, the `runscripts` bus channel). All three are complete in `product/plans/complete/`, so this subplan can start now. It lands the topic, the action module, and the host wiring that `03` deferred. It must land before `05`, because `validateDeclaration` in `src/plugins/activate.ts` refuses any declaration that names a topic the record does not carry.

- `NOTIFICATION_TOPICS` in `src/plugins/api-topics.ts` is typed as a record over the topic union. Adding `runscripts` to either one without a matching source in `TOPIC_SOURCES` in `src/plugins/topics.ts` fails typecheck. So the contract, the source, and the action module land together in this subplan.
- The topic's data is `{ rows }`, and each row carries `name`, `schedules`, and `open`. Rows are sorted by name.
- The topic has six actions. The source plan lists five: `execute`, `delete`, `clone`, `create`, and `open`. The sixth, `ensureDirectory`, is needed because creating `.janissary/` and `.janissary/scripts/` takes the launch directory, and the plugin contract gives a plugin no `Managers` and no path to the launch directory that the scripts plugin would declare (`ai/guidelines/plugins.md`, section 1), so the host action creates them. The command in `05` calls this action before it reads the topic, so the tab's first rows come from a directory that exists. Rejected: running the setup inside the topic read, which would make a read create directories.
- Every action that came from the client carries `origin`, the scripts tab's label. The plugin takes that label from the server-resolved tab, never from the client payload. The source plan says "each action payload carries the issuing tab's label", and this is how it is met.
- A name that fails `isRunscriptName` does nothing, which is what the source plan says for invalid names. One check, made before the action switch, covers the four actions that carry `name` (`execute`, `delete`, `clone`, and `open`), so no reader, path builder, or editor call ever sees an invalid name. `create` and `ensureDirectory` carry no name. The name `create` builds is `untitled` or `untitled-N`, which pass `isRunscriptName` by construction.
- A valid name whose file is absent gets the feed line `No runscript named "<name>".` and the next tick removes the row. The source plan says both "not in the catalog, do nothing" and "a row whose file has gone reports No runscript named", and those two statements conflict. This subplan keeps the second for valid names and reserves "do nothing" for invalid names. It is flagged for the owner.
- Failure text goes to the feed through `notify(managers, 'plugin-note', origin, text)` in `src/notifications/index.ts`. Here `origin` is the scripts tab's label string, the same third argument `notifyUser` passes in `src/plugins/context.ts`, so the event is the one `notifyUser` uses. `plugin-note` is an explicit event (`EXPLICIT_EVENTS`), and `notificationText` returns its detail unchanged, so the text is shown verbatim and no ambient toggle suppresses it. Actions return nothing, as the source plan requires.
- Open does not call `edit <name>`. The `edit` command (`src/commands/edit.ts`, the `existsSync(exactFile)` check) resolves a bare name against the current directory of the tab and prefers an existing file of that exact name there, so a stray file called `deploy` next to the project would open instead of the runscript. The open action passes `openFile.edit` the absolute path that `runscriptFilePath(managers.tab.launchDir, name)` returns, never the relative `.janissary/scripts/<name>.rs`. `editResolved` in `src/open/file-manager.ts` resolves a relative target against the origin tab's working directory, and `openInEditor` stores the path it is given, so a relative path would be stored as a path that the open flag in `03` never matches when that tab is not at the project root. `create script` already passes the absolute `runscript.file` (`src/commands/create.ts`), and clone and create do the same. Open reads the file through `readRunscript` before it opens anything, which is the reader `edit` uses when no stray file of that name exists. A missing file posts `No runscript named "<name>".`. A symlink, a non-regular file, or any other throw from the reader posts `Could not read runscript "<name>".`. Otherwise the result matches `edit <name>`, with the transcript command text `edit <name>`. Open focuses an existing editor tab for the same path, because `openEditorTab` (`src/tab/open-editor-tab.ts`) already matches `tab.editor?.path` by exact string.
- Clone and create open the new file through the same editor call, with the absolute path from `runscriptFilePath`. Their transcript command text is `edit <new name>` for clone and `create script <name>` for create, which matches what the typed commands would show, since `src/commands/edit.ts` and `src/commands/create.ts` pass that typed text to the same call.
- The execute action calls `runRunscriptNow`, which is async and resolves to the failure text or `undefined` (`src/commands/execute.ts`). The action starts the call without waiting on it, because `topicAction` is fire-and-forget, and attaches the feed post to the promise, posting only when the text is not `undefined`. `ensure()` does not reject, because `runEnsure` in `src/system-shell.ts` turns any error into a failed status, so the chain needs no catch of its own.
- Which condition picks which text. Delete posts the missing-file line when `deleteRunscript` returns `false`, and the delete failure line when it throws (a symlink, a non-regular file, a reader failure, or an unlink error other than `ENOENT`). Clone posts the missing-file line when `cloneRunscript` returns `undefined`, and the clone failure line when it throws. Open posts the missing-file line when `readRunscript` reports the file absent, and the read-failure line when it throws. A race that finds the chosen create name taken opens the existing file and posts nothing, because `newUntitledRunscript` returns that name without an error.
- A symlinked `.janissary` reaches the same texts as a symlinked file. The reader throws, and each action posts its own failure text.
- Delete does not close an editor tab that holds the file. The tab keeps its text, as the source plan says.
- A file over the editor's 2 MiB limit (`EDITOR_MAX_BYTES` in `src/openers/editor.ts`) is refused by `openInEditor`, which writes its line to the origin tab's transcript. The source plan names that transcript as the editor path's, so the action adds no feed line for the refusal.
- For the proposed wording of the directory failure, see the Proposed changes section. It is new text, so it needs the owner's confirmation.

## Proposed changes

- In `src/plugins/api-topics.ts`, add `runscripts` to the topic union and to the record, after `tabs`, so the record's key order is `schedules`, `conversations`, `sessions`, `databases`, `tabs`, `runscripts`. The comment above the union asks that each topic carry its own justification, and this one is the scripts tab's live list. Add a `runscripts` variant to `TabPluginNotification` with `data` typed as `RunscriptsView` and with `tabs`. Import `RunscriptsView` into the existing `'../protocol.js'` import at the top of the file, which already brings in `DatabaseGridQuery` and `RemoteSessionView`. Add `runscripts` variants to `TabPluginTopicAction`. Four of them (`execute`, `delete`, `clone`, `open`) carry `name` and `origin`. `create` carries `origin` only. `ensureDirectory` carries `origin` only. `origin` is the scripts tab's label as a string. The file goes from 103 to about 115 code lines. `TAB_PLUGIN_API_VERSION` stays at 2, because the change is additive. `src/plugins/api.ts` (198 code lines) and `src/plugins/api-capabilities.ts` are not touched.
- In `src/plugins/topics.ts`, add a `runscripts` entry to `TOPIC_SOURCES`. Its `subscribe` is `messageBus.on('runscripts', 'changed', fire)`. Its `read` returns `readRunscriptRows(managers)`, imported from `../schedule/system/runscript-rows.js`. Its `act` wraps the new action function in a block, as the `conversations` entry does at line 159, so that the arm returns `undefined`. Its `empty` value is `{ rows: [] }`. The entry and its two imports are the whole change to `topics.ts`, which goes from 160 to about 170 code lines.
- In `src/plugins/runscript-topic-actions.ts` (new), define `runscriptTopicAction(managers, action)`, which returns nothing. It mirrors `scheduleTopicAction` in `src/plugins/schedule-topic-actions.ts` in shape: an early return for a topic other than `runscripts`, then a switch on `action.action`. The name check from the Design decisions runs before the switch. The arms stay short, each one a delegation and its feed post, which keeps the switch clear of the cognitive-complexity warning (`AGENTS.md`, limit about 15). The arms call `runRunscriptNow` (execute), `deleteRunscript` (delete), `cloneRunscript` and then `openFile.edit` (clone), `newUntitledRunscript` and then `openFile.edit` (create), `ensureScriptsDirectory` (ensureDirectory), and `readRunscript` and then `openFile.edit` (open). Feed posts go through `notify`. Every relative import carries the `.js` extension. If the module grows past about 180 code lines, move the editor-open helpers into `src/plugins/runscript-open.ts`.
- The feed texts are the following. Execute uses the text `runRunscriptNow` returns. Delete failure is `Could not delete runscript "<name>".`, and a missing file is `No runscript named "<name>".`. Clone failure is `Could not clone runscript "<name>".`, and a missing source is `No runscript named "<name>".`. Create failure is `Could not create runscript "<name>".`, where the name is the `runscriptName` that `newUntitledRunscript` attaches to its error, falling back to `untitled`. Open of a missing file is `No runscript named "<name>".`. A directory failure from `ensureDirectory` is proposed as `Could not use the runscripts directory.`, which is new wording and needs confirmation.
- In `src/plugins/host-channels.ts`, `subscribeHostChannels` builds a predicate over plugin ids from `declarations`. The predicate finds the declaration whose `id` matches and reports whether that declaration's `notifications` include `runscripts` (`TabPluginDeclaration.notifications` in `src/plugins/api.ts:87` is optional, so the read is `?? []`, as line 31 of `host-channels.ts` already does). If any declaration lists `runscripts`, the function adds `subscribeRunscriptRefresh(managers, predicate)` from `src/schedule/system/runscript-refresh.ts` to the array it returns. Otherwise the array is unchanged. `TabPluginHost.dispose` in `src/plugins/host.ts` releases it with the rest of `subscriptions`. The `runscripts` entry in `TOPIC_SOURCES` is what delivers the change signal to a plugin's `notify` handler, through the `subscribeTabPluginNotifications` call that `host-channels.ts` already makes for every declared topic. The file goes from 32 to about 42 code lines.
- In `src/plugins/api-topics.test.ts` and `src/plugins/topics.test.ts`, extend the existing cases as described under Tests. The record test goes from five topics to six, with `runscripts` appended last, because the test compares the array in key order.

## Tests

- In `src/plugins/runscript-topic-actions.test.ts` (new), with a temporary project directory and fake managers in the style of `src/commands/execute.test.ts`:
  - Feed calls are recorded by mocking `../notifications/index.js` with a recording `notify`, as `src/plugins/notify-user.test.ts` does at its lines 8 and 9. `openFile.edit` is a recording fake. It shows the command text and the absolute path, but it cannot show that a second tab was avoided, so the dedupe case calls `openEditorTab` from `src/tab/open-editor-tab.ts` directly with a plain target object. No test file exists for that function.
  - Execute of a missing runscript posts `No runscript named "<name>".` with the origin label and enqueues nothing. Execute of a present runscript enqueues its lines to `system` and posts nothing. Execute with a system shell that is not ready posts nothing.
  - Delete removes the file and posts nothing. Delete of a missing file posts `No runscript named`. Delete of a symlink posts `Could not delete runscript "<name>".` and leaves the target in place.
  - Clone creates `<name>-2.rs`, opens its absolute path with the command text `edit <name>-2` and the origin label, and posts nothing. Clone with a second copy taken creates `-3`. Clone of a missing source posts `No runscript named`. Clone that throws posts `Could not clone runscript "<name>".`.
  - Create on an empty directory creates and opens `untitled.rs` with the command text `create script untitled`. A second create creates and opens `untitled-2.rs`. A failure posts `Could not create runscript "untitled".`
  - Open of an existing file where an editor tab for the same path is already open focuses that tab and creates no second tab, tested on `openEditorTab` as described above. Open of a missing file posts `No runscript named`. Open of a symlink posts `Could not read runscript "<name>".` and opens nothing. A runscript over the 2 MiB editor limit posts nothing to the feed.
  - An invalid name, such as `Deploy`, `a--b`, or an empty string, does nothing and posts nothing for `execute`, `delete`, `clone`, and `open`.
  - `ensureDirectory` creates `.janissary/` and `.janissary/scripts/`. With a symlinked `.janissary`, it posts the proposed directory wording and does not throw.
  - Every action returns `undefined`.
