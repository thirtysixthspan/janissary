# Dispatch receipt for shell ask and tell
**Complexity: 3/10** — folds two copy-pasted command bodies into one helper and changes what `ask` and `tell` return from dispatch, so correctness rests on catching every reader of that reply: the agent tool loop that prints any defined result, one `plugin-session` assertion, and the command tests' hand-built manager mocks; the shell ignores the receipt until the client lands.

## Goal

Make `ask <prompt>` and `tell <prompt>` answer a dispatch with a receipt `{ replyId, role, name }` as the command's `result`, and make the settled background reply carry that `replyId` as its `background` id, so the shell can later match an echo to its reply by id. Keep granted agents from ever seeing the receipt. Give the shell plugin's import-free contract the receipt type and guard the client will read.

## Design decisions and dependencies

This subplan consumes no export from `01-acp-result-record-id`, which has landed. Both edit `src/acp/response.ts`, but in different places: `01` changed `settleAcpPrompt`, this subplan changes `appendAcpBackgroundReply` and adds the helper. `03-reply-record-and-tell-line` consumes the `appendAcpBackgroundReply` signature set here. `06-marker-lifecycle` consumes the receipt type and `07-client-wiring` the guard.

Source plan requirements carried here: "Server changes" bullets on the shared `ask`/`tell` helper and its receipt, on `appendAcpBackgroundReply` taking the id minted at dispatch, on `src/agent/command-tools.ts`, and on `ShellAcpReceipt` and `isShellAcpReceipt`; "Scope" (applies to `ask` and `tell`, local and remote alike; `ask reset` and `tell reset` get no receipt); "Edge cases" (the same line typed twice is matched by id, never by text, which needs a distinct id per dispatch including a refused one); the server half of the "Tests" list for `ask.test.ts`, `tell.test.ts`, and `command-tools.test.ts`.

- `src/commands/ask.ts` and `src/commands/tell.ts` are identical apart from `name`, `match`, `samples`, and the role. Their shared body moves into one exported function in `src/acp/response.ts` (43 counted lines today), named `runAcpCommand`. Its parameters, in order: the command text, the `{ label, index }` tab, the managers, the optional invocation context, and the role. It returns the receipt synchronously. Both commands shrink to a `run` that calls it with their role and returns its value. The imports they no longer use (`appendAcpBackgroundReply`, `AcpPromptResult`, `errorText`) go, and `runAcpCommand` is imported from `../acp/response.js`, the module they already import from. `Command.run` in `src/commands/types.ts` is typed to allow any return value, so returning the receipt needs no change there.
- What the helper does, in this order: read the line the user typed (`invocation?.line ?? command`, as today); mint the reply id with `randomUUID` and build the receipt; start the prompt exactly as the commands do today (`managers.acp.promptResult(label, command, role, { appendRefusalToTranscript: false })` in a `void`-prefixed chain, settled at most once, a rejection settling as `ACP error: <text>`); return the receipt. The id is minted at dispatch, not at settlement, and the receipt is built before the prompt starts, so a failure building it can never leave a prompt running with no receipt. `ask` used to pass `undefined` for the role and rely on the default; the helper passes the role explicitly, and `DEFAULT_ACP_ROLE` is `'ask'` (`src/acp/role.ts`), so behavior is the same.
- A refusal is learned only when the prompt settles. `AcpManager.promptResult` runs `run` inside the `Promise` executor, so a refusal resolves the promise at once but the helper's settle callback runs on a later microtask, after the helper has returned. A refused dispatch therefore still gets a receipt, and its later reply carries the same id. That is what lets two identical lines be told apart.
- `name` is `acp:<role>:<tab name>` where the tab name is `managers.tab.byLabel(label)?.title ?? label`. `run` receives only `{ label, index }`, so the title is read from the tab manager. Build the string with `recordConnectionName` from `src/plugins/connections/shared.ts` (an import-free contract with no cycle risk, passing `kind: 'acp'`, the role, and the tab name as `ownerName`). Core code under `src/` may import it: `src/acp/` already imports `../plugins/roles/shared.js`, and the only restricted import for core is a plugin's `activate.js` (`eslint.plugin-boundaries.mjs`). That function is the one definition of the connection tab's title, and the answering record's name in `03-reply-record-and-tell-line` uses it too, so the running marker and the link cannot drift.
- Correction to the source plan's reference: the "same `tab.title ?? tab.label` a new record captures as `ownerName`" is captured in `src/acp/session-manager.ts` (`session()`, the `source` object, `ownerName: tab.title ?? label`). `src/plugins/connections-topic-rows.ts:71` computes the same value for the live rows only.
- Receipt type: export a type named `AcpDispatchReceipt` from `src/acp/response.ts` (`replyId: string`, `role: AcpRole`, `name: string`) so the helper, its tests, and the shell plugin's pin test share one server-side definition.
- `appendAcpBackgroundReply(managers, label, input, result, id)` takes the id as a new, required last parameter and stores it as the entry's `background`; it no longer calls `randomUUID` itself, and it has no fallback id, so a caller that forgets the id fails typecheck instead of minting one nothing can match. The `randomUUID` import stays in the file for the helper. The only callers are the two commands, now the helper. Making `id` required breaks both commands' calls until they use the helper, so the `response.ts` edit and both command edits are one step.
- The `coreResponse` branch of `CommandManager.dispatchLine` in `src/command/manager.ts` already returns `...(result !== undefined && { result })`, and `dispatchLine` serves all three entry points: `dispatchLineWithOutput` (the shell's `dispatch` intent, through `src/plugins/line-capabilities.ts`), `dispatchQueuedLine` (the shell's `dispatch-command` intent, through `dispatchQueuedCommand` in `src/plugins/queue-capabilities.ts`, called from `src/plugins/shell/activate.ts`), and `dispatchLineInInvocation` (the agent tool loop). `src/command/manager.ts` needs no edit. The branch comes before the `structuredResult` branch and does not look at it, so `ask` and `tell`, which are core-response and not structured, pass their result through. `src/command/manager.test.ts` ('keeps core-response no-capture behavior while returning a structured result') already pins that branch, so no test is added there. The shell plugin's intent returns the whole reply as JSON-compatible data, and the receipt is three strings, so it crosses the wire with no new message.
- `src/agent/command-tools.ts`: `runGrantedAgentCommand` turns any defined `result` into the tool output, so an agent granted `ask` or `tell` would start seeing the receipt where it sees empty output today. It returns `result.output` whenever `result.coreResponse` is true, checked before the existing `result.result` handling. The core-response commands are exactly `ask`, `ask-reset`, `tell`, and `tell-reset`, and the two resets return nothing, so only the output of `ask` and `tell` is affected, and it stays the empty string it is today. This is the only code that reads `result.result` from a dispatch reply. Every other consumer of a dispatch reply ignores it: the shell client reads `dispatched`, `coreResponse`, and `output` only (`web/src/plugins/shell/useShellSubmit.ts`); the launcher's `run-command` and `dispatch` intents (`src/plugins/launcher/activate.ts`) forward the whole reply, receipt included, to the launcher client, whose `shownFor` returns null for a core response (`web/src/plugins/launcher/launcher-actions.ts`: `if (reply.coreResponse || !reply.output) return null`); the diff plugin's `openMedia` (`src/plugins/diff/tab-state.ts`) dispatches `open` lines and discards the reply; command-bar lines (`CommandManager.dispatch` and `dispatchTo`) discard the command's return value; and `resetAcp` in `src/message/tabs.ts` runs `ask-reset`, which returns nothing. The `command-tools.ts` change must land with the receipt, in this subplan, so no state exists where a granted agent sees the receipt.
- `src/plugins/shell/shared.ts` (148 counted lines, about 160 after): add a `ShellAcpReceipt` type (`replyId: string`, `role: 'ask' | 'tell'`, `name: string`) directly after `ShellDispatchResult`, and an `isShellAcpReceipt` guard beside the module's other guards (after `isShellCommandState`). Both are re-declared there like the module's other shapes, and the guard uses the module's own `isRecord`, so the file keeps no imports. The guard rejects arrays, `null`, a missing or non-string `replyId` or `name`, and any role other than `ask` or `tell`. It tolerates extra fields, as `isShellPayload` does, and does not reject empty strings. Extend the comment above `ShellDispatchResult`, which says nothing about `result` today, to say that a core-response reply may carry the receipt as `result`. The client reads the guard in `07-client-wiring`; until then nothing in production code calls it, and its own test does.
- Existing tests that must change because of the receipt, found by searching the server and client tests for every ask or tell dispatch and every `coreResponse` assertion:
  - `src/acp/plugin-session.test.ts` line 218: `dispatchLineWithOutput('consumer', 'ask hello', 1)` resolves `toEqual({ dispatched: true, output: '', coreResponse: true })`, which now also has `result`. The tab in that harness has no title, so the name uses the label `consumer`.
  - `src/commands/ask.test.ts` and `src/commands/tell.test.ts`: the managers object built by `run` is `{ acp: { promptResult }, tab: { append } }` with no `byLabel`, which the helper calls. The same shape is built inline in each file's 'guards against a competing settlement appending twice' case, which `run` does not cover, so that managers object needs `byLabel` too. The source plan names none of these changes.
  - The `ask reset` and `tell reset` assertions in `plugin-session.test.ts` (lines 336 and 360) stay as they are because those commands return nothing.
- Existing tests that stay valid unchanged: the five command cases in the 'AcpManager — shell refusal output' block of `src/acp/manager-fallback.test.ts` run both commands against a real `AcpManager` whose tab mock already has `byLabel`, and assert `background: expect.any(String)`; the other `ask` dispatches in `plugin-session.test.ts` await the reply without reading it; `src/commands/ask-reset.test.ts` and `src/commands/tell-reset.test.ts` do not touch the helper; the web `ShellTab.test.tsx` and `LauncherTab.test.tsx`, and the server `src/plugins/launcher/activate.test.ts`, mock the dispatch reply with fixed objects and never see a real receipt.
- No spec or documentation file changes in this subplan. The receipt is a server-to-shell detail until `07-client-wiring`, and no existing sentence becomes false: `product/specs/acp.md` § Commands says the dispatcher marks these replies as core-rendered so dispatch adds no immediate terminal line, `product/specs/application-commands.md` § Structured command replies says a reply "may also include the command's structured `result`", and `documentation/developer-documentation/tab-plugins.md` says core responses return `coreResponse: true`; all three stay true. The user-visible behavior is specified by `03` and `07`.

## Proposed changes

- `src/acp/response.ts`: add the exported receipt type and the exported helper; give `appendAcpBackgroundReply` the trailing id parameter; add the imports the helper needs: `recordConnectionName` from `../plugins/connections/shared.js`, `errorText` from `../error-text.js`, and a type-only `CommandInvocationContext` from `../commands/types.js` (the way `src/agent/command-tools.ts` imports it). The file ends near 70 counted lines.
- `src/commands/ask.ts`, `src/commands/tell.ts`: delegate to the helper with their role and return the receipt; drop the unused imports. Names, `match`, `samples`, `available`, and `coreResponse: true` stay as they are.
- `src/agent/command-tools.ts`: return `result.output` when `result.coreResponse` is true, before the existing `result.result` handling.
- `src/plugins/shell/shared.ts`: `ShellAcpReceipt`, `isShellAcpReceipt`, and the extended `ShellDispatchResult` comment, as above.

## Tests

Server (vitest project `server`), colocated:

- `src/commands/ask.test.ts` and `src/commands/tell.test.ts`: give every hand-built managers object `tab.byLabel`, including the inline one in the competing-settlement case. The shared `run` builder returns the command's value as well as `append`, and accepts an optional tab so a case can give it a title. Cases: `run` returns `{ replyId, role, name }` with the file's role; `name` uses the tab's title and falls back to the label when the tab has none; the settled background entry's `background` equals `replyId` (the existing cases assert `expect.any(String)` and now assert the receipt's id); a refused prompt (usage, already running) settles under the same receipt id; two dispatches get different ids; the prompt is started with the right role (`'ask'` explicitly, `'tell'`). The existing rejected-prompt and competing-settlement cases still pass.
- `src/acp/response.test.ts` (created in `01-acp-result-record-id`): `appendAcpBackgroundReply` stores the given id as `background` and no longer invents one (pass a fixed id and assert it appears exactly), with the reply text for an answered result and the error text for an unanswered one.
- `src/agent/command-tools.test.ts`: a granted command whose dispatch reply has `coreResponse: true` and a `result` returns its `output` and not the JSON of `result`; a non-core reply with a string `result` returns that string and one with an object `result` returns its JSON, as before. The file's `snapshot` grants `question`; the new core-response case grants `ask` (`{ ...snapshot, grants: ['ask'] }`), which the real command registry that `runGrantedAgentCommand` consults resolves from `ask hello`.
- `src/plugins/shell/shared.test.ts`: `isShellAcpReceipt` accepts a well-formed receipt for each role and one with an extra field, and rejects `null`, an array, a missing or non-string `replyId` or `name`, and a role such as `'monitor'`. A pin test types a value as the server's `AcpDispatchReceipt` (imported as a type from `../../acp/response.js`) and passes it through the guard for each role, and assigns `ShellAcpReceipt` and the server type to each other the way the file already does for `CompletionResult`. Server test files are excluded from `tsc` (`tsconfig.json` excludes `src/**/*.test.*`), so the assignments alone enforce nothing at typecheck time; the runtime guard checks and the `plugin-session.test.ts` case below are what hold the two shapes together.
- `src/acp/plugin-session.test.ts`: in the case at line 215, await the dispatch reply into a variable and expect `result: { replyId: expect.any(String), role: 'ask', name: 'acp:ask:consumer' }` in place of the old exact object; assert `isShellAcpReceipt(reply.result)` is true (import the guard from `../plugins/shell/shared.js`); and extend the settled-entry assertion so the entry has `background` equal to that `replyId`.
