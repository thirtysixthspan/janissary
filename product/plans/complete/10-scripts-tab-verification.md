# Scripts tab end-to-end and production build verification
**Complexity: 3/10** — no code and no new module. The work is a diff-scoped check, a production web build with a chunk check, the frozen fixture tests, and a two-project manual walk, with any defect it finds routed to the subplan that owns it.

## Goal

Show that the feature works in a running app and in the production bundle. This is the last subplan, and it runs after every code, test, and doc change is in.

## Design decisions and dependencies

This subplan depends on `09-scripts-tab-specs-and-docs`, which depends on everything before it. It runs last and edits no source, test, spec, or doc file of its own. A defect the walk finds is logged as a backlog-style repair against the owning subplan, the orchestrator runs that repair with the owning subplan's test, and the walk steps that depend on it are run again.

- `./scripts/run.mjs check-diff` (`scripts/check-diff.mjs`) runs last, scoped to the working tree. For a change that touches both `src/` and `web/src/`, it runs lint on the lintable files, `npm run typecheck:diff` for both projects, and `vitest --changed` for the server and the client projects. `--changed` runs only the tests whose import graph includes a changed file, so the named test files are also run by path (see Tests). check-diff reads only uncommitted and untracked files. On a clean tree it prints `check:diff: no changes` and runs nothing, and a change made only to Markdown runs nothing either, so an exit status of 0 is not a pass in those cases. The feature is committed on `feature/scripts-tab`, so a clean tree is the expected starting state. This subplan therefore runs check-diff in one of two forms: with the tree uncommitted, or, on a clean tree, by running `npm run typecheck:diff` and the named test files by hand. The report says which form ran. The full `npm run check` remains the human's once-at-the-end gate, as `AGENTS.md` says, and this subplan does not run it.
- The production build is `npm run build:web`, which runs `vite build -c web/vite.config.ts`. Vite's root there is `web/` and `build.outDir` is `dist`, so the output is `web/dist/`, not the repo-root `dist/` that `tsc` writes. Each build empties `web/dist/` first, and `dist/` is gitignored, so a build leaves `git status` unchanged. The server refuses to start without `web/dist/index.html` (`src/main.ts`), so the build finishes before any instance is launched.
- The chunk check finds the chunk that holds the scripts tab by a string that only that code contains. The two strings are `No runscripts yet. Press + to create one.` (the empty state in `web/src/plugins/scripts/ScriptsTab.tsx`) and `Used by a system schedule` (the clock's `title` and `aria-label` in `web/src/plugins/scripts/ScriptRows.tsx`). A search of `src/` and `web/src/` finds each one only under `web/src/plugins/scripts/`, and only in the component and its tests, since tests are not bundled. Each appears in the bundle as a JavaScript string literal, so a search that finds nothing is a failure to investigate, not a pass. The entry chunk is the file that `web/dist/index.html` loads through its `type="module"` script tag, which Vite rewrites from `web/index.html`, whose module script names `/src/main.tsx`. The check does not tell entry from lazy chunks by file name, because the scripts entry is `index.tsx` like every plugin entry, so names do not separate them. A lazy chunk is any other file under `web/dist/assets/` that the entry reaches only through a dynamic `import(`. The check passes when the two strings are found in at least one lazy chunk, neither is found in the entry file, and the entry names the lazy chunk only inside a dynamic `import(` call, never in a leading static `import` statement.
- The source supports that result. In `web/src/plugins/registry.tsx`, the scripts entry is reachable only through `scripts: () => import('./scripts/index')` in `clientPluginLoaders`, and `clientPlugin` wraps that loader in `React.lazy` at module scope, so the import runs only when the tab first renders. The registry test named `reaches the scripts entry only through a dynamic import` checks the same thing in the source text, as the companion to the build check.
- The chunk check cites `ai/guidelines/plugins-tabs.md`, which requires it in two places: the sentence in "Import boundaries and versioning" that says, after changing `web/src/plugins/registry.tsx`, to rebuild and confirm each plugin's modules are still in its own chunk, and item 10 of "Adding a plugin checklist". The comment above `clientPluginRegistry` in `web/src/plugins/registry.tsx` does not mention a build or a chunk, so it is not a source for this check, and this subplan does not edit it. Its claim that `registry.test.tsx` pins every literal is also wrong. That test pins 10 of the 18 literal entries, and agent-monitor, asciicast, audio, launcher, page, roles, search, and sessions are not pinned. That gap predates the scripts feature, so the orchestrator logs it in `product/backlog/technical-debt.md` as a repair, and this subplan does not fix it.
- The manual walk is listed step by step under Verification, and this bullet is its summary. In project A, which has two runscripts: `scripts` lists both in alphabetical order. Clone one, and `<name>-2.rs` appears with the same lines and comments and opens in an editor. Execute a runscript, and its lines run in the system shell. Delete a runscript after confirming, and its file is gone. Press `+` twice, and `untitled.rs` and `untitled-2.rs` open. Create a file in `.janissary/scripts` from a terminal, and it appears in the list within about a second. In project B, which has no `.janissary/` directory: `scripts` creates `.janissary/scripts/`, and the tab shows the empty state line.
- The walk also covers what the source plan implies. A runscript used by a system schedule shows the clock marker and the schedule line in the delete dialog. The schedule then fires as `missing`, which is existing `src/schedule/system/firing.ts` behavior that this feature does not change, and the walk observes that firing only if its next run falls inside the walk. An open editor tab keeps its text after the file is deleted. Saving that tab recreates the file through the editor's existing save path, which the spec states and this walk confirms. After the scripts tab is closed, a runscript created from a terminal is not shown until the tab is reopened, and reopening shows the current list. Whether the refresh reads the directory with no tab open cannot be observed by hand, so the zero-read rule is covered by the unit tests in `03`.
- The walk also carries the focus check from subplan `02`. A Run from the scripts tab must leave the active tab unchanged and must not bring the system shell into view. `02` could not run that check headlessly, so this walk checks it in the running app and reports the result.
- The walk runs in two scratch project directories, never in a project the user works in. Each must sit outside this checkout and outside any Git worktree, meaning `git rev-parse --show-toplevel` fails in it. The scripts directory step runs `ensureSystemScheduleExcluded` (`src/schedule/system/local-exclude.ts`), which writes the Git exclude file of whichever worktree holds the project, so a scratch directory inside this checkout, including the session scratchpad, would change the checkout's own exclude file. Project A holds `deploy.rs` and `lint.rs`, each with one line that appends its name to `ran.txt` in the project, so every run is one countable line. Project B is an empty directory with no `.janissary/`.
- The app is started from the checkout with `node bin/janus.mjs --no-open <scratch-dir>` and stopped with `node bin/janus.mjs stop <scratch-dir>`. The launcher runs the compiled `dist/main.js` when a root `dist/` exists and otherwise runs `src/main.ts` through `tsx`, so the walk does not run after a `tsc` build that would create `dist/`. `--no-open` keeps the host window from opening. The launcher prints the token-gated URL on stdout and records it in `<scratch-dir>/.janissary/log/server.log` as a `__JANUS_URL__` line, and the walk opens that URL in a browser. One instance runs at a time, so the two projects never run together. A live instance holds the lock file `.janissary/lock` in its own directory, and a second start there is refused with a message that suggests deleting the lock. The walk never deletes a lock, never starts or stops an instance in a directory the user works in, and never uses the user's live session, because every instance is started in a scratch directory.
- The `run` skill finds no project skill, since `.claude/` holds only `settings.json` and the repo has no `.claude/skills/`, so it falls back to its built-in patterns. Its curl and chromium-cli examples do not cover this launcher, so the walk uses the launcher above and a browser at the printed URL. An agent inside a Janissary workspace cannot start its own browser (`ai/guidelines/sandbox-e2e-browser.md`), so a person or a browser-capable tool performs the walk.
- The expected results come from `product/specs/scripts-tab.md`, and where the source plan and the spec differ, the spec wins. Three differences matter for the walk. A click outside the delete dialog is swallowed and the dialog stays open, where the source plan said it cancels, and `DeleteScriptDialog.tsx` swallows it. The refresh is gated on an open scripts tab rather than started and stopped with the tab, so the source plan's lifecycle wording is superseded. Two failure lines, `Could not run runscript "<name>".` and `Could not use the runscripts directory.`, are new wording that the spec marks as owner-to-confirm, and the walk does not reach them, so `src/plugins/runscript-topic-actions.test.ts` carries them.
- No source file is added, so the 200-line `max-lines` limit does not apply to this subplan. A defect repair that adds code is subject to that limit in its owning subplan.
- The walk's results are reported in the change description or in the conversation. This subplan does not write a report file.
- After the work is complete, the plan files move from `product/plans/draft/` to `product/plans/ready/` and later to `complete/`, as `AGENTS.md` describes. That move is the owner's call.

## Tests

- The named test files run by path, whether or not check-diff selected them. Server files: `src/commands.test.ts`, `src/commands/execute.test.ts`, `src/plugins/loaders.test.ts`, `src/plugins/documentation.test.ts`, `src/plugins/api-topics.test.ts`, `src/schedule/manager.test.ts`, `src/plugins/runscript-topic-actions.test.ts`, `src/schedule/system/runscript-files.test.ts`, `src/schedule/system/runscript-refresh.test.ts`, `src/schedule/system/runscript-rows.test.ts`, and every `src/plugins/scripts/*.test.ts`. Client files: `web/src/plugins/registry.test.tsx` and every `web/src/plugins/scripts/*.test.ts` and `*.test.tsx`. Server files run with `npx vitest run --project server <files>` and client files with `npx vitest run --project client <files>`. The reason is that `--changed` selects by import graph, so a test that reads a Markdown or docs file is not selected by a change to that file alone.
- The frozen fixture tests. The plugins-tabs guideline's checklist item 10 names them. They are `src/plugins/fixture-v1/compatibility.test.ts` (server) and `web/src/plugins/fixture-v1/compatibility.test.tsx` (client). They exercise the `fixture-v1` plugin, which the guideline keeps frozen, and both run whatever check-diff selects. `src/plugins/adapters.test.ts` runs with them, because its test `does not register the frozen fixture in production` guards the same fixture against the production catalog.
- The topic-count guard in `src/plugins/documentation.test.ts` (added by commit `0c190fb0`) is a unit property. A walk cannot observe a count in a doc, so that test carries it and the walk does not.
- The double-click repair, the keyboard guard, and the delete-dialog keys have unit tests in `web/src/plugins/scripts/ScriptRowActions.test.tsx`, `web/src/plugins/scripts/ScriptsTab.test.tsx` (including the case where Enter on the focused `New script` button sends `create` and not `open`, and the case where Enter on the focused Run button sends `execute`), and `web/src/plugins/scripts/scripts-delete-keys.test.ts`. The walk observes the same behavior in the running app, as Verification lists, and the unit tests carry the rest.
- The walk under Verification is the end-to-end test.

## Verification

Pass criteria:

- `./scripts/run.mjs check-diff` exits with status 0 in the form Design decisions names, and the named test files pass.
- `npm run build:web` exits with status 0 and writes `web/dist/`.
- The chunk check passes as described below, and it names the lazy chunk that holds the strings.
- The frozen fixture tests pass.
- Each manual step below produces its stated result, and the feed and dialog text match `product/specs/scripts-tab.md` word for word.
- A Run from the scripts tab leaves the active tab unchanged.

A defect against any criterion is recorded as a repair against its owning subplan, as Proposed changes lists.

Build and chunk check, run after `npm run build:web` exits 0. Read the module script's `src` in `web/dist/index.html` and call that file the entry. Search `web/dist/assets/` for `No runscripts yet` and for `Used by a system schedule`. Each string must be found in at least one file other than the entry, and neither may be found in the entry. Then search the entry for the lazy file that holds the strings, and confirm that its name occurs only inside a dynamic `import(` call. The report names that lazy file. A string found in the entry, or a scripts chunk named by a static import in the entry, fails the check, and that defect goes to `08-scripts-plugin-registration`, which owns the registry line.

Manual walk, run in the order given, one scratch project at a time. Each step names what it proves. A step the walk cannot reach is recorded as not reached, and the unit test that carries it is named in the report.

Project A, first start. Step 2 must be the first Run after the instance starts, because the first run is the one that opens the system shell (`ensureShell` in `src/system-shell.ts`, which hides the new tab at once through `userCloseTab`).

1. Type `scripts`. The tab opens in the centre with `1) deploy` and `2) lint` in that order and no clock marker. Proves the list and the command.
2. Click Run on `deploy`. One line is added to `ran.txt`, no feed line appears, the active tab stays `scripts`, and the system shell tab is not brought into view. Proves the execute path and the focus check.
3. Double-click Run on `lint`. Exactly one line is added to `ran.txt`, and no editor opens for `lint`. Proves the double-click repair on Run.
4. Click Duplicate on `deploy`. `deploy-2` appears within about a second, its editor opens, and a `diff` of `deploy.rs` and `deploy-2.rs` is empty, comments and blank lines included. Proves clone and its editor hand-off.
5. Double-click Duplicate on `lint`. Exactly one `lint-2.rs` is created, with no `lint-3.rs`, and the `lint` row does not open. Proves the double-click repair on Duplicate and on the row button.
6. Click the `deploy-2` row and press Enter. The editor already open for `deploy-2` is focused, and no second editor opens. Proves Enter on the selected row.
7. With `deploy-2` selected, press Delete. The dialog is titled `Delete runscript "deploy-2"?`, its highlight starts on `Cancel`, and it adds the line `Open in an editor tab. The tab keeps its text.` Press `n`. The dialog closes and the file stays. Proves the dialog text and keys.
8. Press Delete again and click outside the dialog. The dialog stays open. Press Escape. The dialog closes and the file stays. Proves that an outside click is swallowed and that Escape cancels.
9. Press Delete again and press `y`. `deploy-2.rs` is gone from disk, the row leaves the list within about a second, and the selection moves to `lint`. The editor for `deploy-2` still shows its text. Save that editor tab. `deploy-2.rs` is on disk again with the editor's text (compare with `diff` or `cat`), the save shows no refusal or conflict, and the row returns within about a second. Proves the delete, the open-tab line, and the save-after-delete claim. The save is observed on disk, not only in the editor. If the save is refused or shows a conflict prompt, that is a defect against the spec's Delete section.
10. With `lint` selected, move keyboard focus to the `New script` button without clicking it and press Enter. `untitled.rs` opens in an editor, and no editor opens for `lint`. Then click `New script`. `untitled-2.rs` opens. Proves the keyboard guard on a focused + button and the two-press naming.
11. With `lint` selected, move keyboard focus to the Run button of the `deploy` row and press Enter. One line is added to `ran.txt`, and no editor opens for `lint`. Proves the keyboard guard on a row button.
12. From a terminal, create `outside.rs` in `.janissary/scripts` with one line. It appears in the list within about a second. Remove it, and it disappears within about a second. Proves the live list.
13. Create a system schedule that runs `lint` (see `product/specs/scheduling.md`). The `lint` row shows the clock with the tooltip `Used by a system schedule`. Delete `lint` from its row and confirm. The dialog shows `Used by 1 system schedule. It will fire as missing after this.` before confirmation, and `lint.rs` is gone after it. Proves the clock marker and the schedule line.
14. From a terminal, delete `untitled-2.rs`, then click its Run before the next refresh. The feed shows `No runscript named "untitled-2".`, and the row then leaves the list. This depends on timing. If the row is already gone when Run is pressed, the step is recorded as not reached. Proves the missing-file line.
15. Close the scripts tab. Create `later.rs` from a terminal. Reopen `scripts`. `later` is listed. Proves that the reopened list is current.

Stop instance A with `node bin/janus.mjs stop <scratch-dir>`.

Project B, first start.

16. Start an instance on the empty directory. Confirm with `ls -la` that there is no `.janissary/`. Type `scripts`. `.janissary/scripts/` now exists, and the tab shows `No runscripts yet. Press + to create one.` and stays open. Proves directory creation and the empty state.

Stop instance B with `node bin/janus.mjs stop <scratch-dir>`.
