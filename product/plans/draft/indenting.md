# Indenting

**Complexity: 3/10** — one small plugin of pure line transforms plus a narrow change to the editor's core key path (`Tab`/`Shift+Tab` delegation); the contract side is a deletion and a one-clause narrowing, not a new mechanism.

The editor tab has no way to shift a block of code left or right. `Tab` inserts a literal tab character wherever the caret is (`web/src/editor/keys.ts:83`), `Cmd+[` and `Cmd+]` are unbound at every level, and there is no indent action in the key table at all. Reindenting a block today means editing every line by hand.

This plan adds **`indenting`**, the second bundled editor plugin, written against the contract that landed with `commenting` (`product/specs/editor-plugins.md`, `web/src/editor/plugins/`). It contributes two commands — `indent` and `outdent` — that shift the whole lines the selection covers, or the caret's line when nothing is selected, by two spaces. `Cmd+]` indents, `Cmd+[` outdents. `Tab` and `Shift+Tab` reach the same two commands. That needs one addition to the core key path — an explicit, narrow notion of *yielding* a chord the table otherwise claims, so `Tab` can indent a multi-line selection while still inserting a tab character everywhere else — and, on the contract side, one deletion: the rule that a plugin chord must carry Cmd or Ctrl turns out to be a weaker restatement of the rule beside it, and goes away rather than being widened.

Everything the plugin itself does is language-independent — it never reads `request.file` — so there is no syntax table, no extension map, and no per-language behavior of any kind.

## Design decisions

**A new bundled plugin `indenting`, not a change to `commenting` and not a core editor feature.** It ships as `web/src/editor/plugins/indenting/`, declared in `web/src/editor/plugins/registry.ts:15` and loaded lazily by the existing loader map at `:26`. This is the case the editor-plugin family was shaped for and the case `commenting`'s plan explicitly deferred to a second plugin rather than a second extension point. A session that never indents downloads none of it.

**Two commands, four chords.** `indent` is bound to `Cmd+]` and to `Tab`; `outdent` is bound to `Cmd+[` and to `Shift+Tab`. Both declare `needs: 'selection'`, so each receives the whole lines the selection covers, or the caret's line when nothing is selected — the slice is never empty and the plugin never special-cases "nothing selected". Two chords mapping to one command is already expressible: a binding names a command and a chord, and chord matching is by chord, so nothing about the contract needs to change to allow it.

**The unit is two spaces, fixed.** No setting, no per-language width, and no detection of the file's existing indent style. Indent prepends two spaces; outdent removes up to two leading spaces.

**Outdent removes whatever is there, line by line.** A line with two or more leading spaces loses exactly two. A line with one loses that one. A line with none is left alone. Each line is decided independently, so a ragged block still shifts as far left as it can rather than refusing to move; this matches VS Code and means outdent is not a strict inverse of indent for a block that was already flush left.

**A leading tab expands to two spaces.** On any line the shift touches, every tab in the *leading* whitespace becomes two spaces before the shift applies; tabs anywhere else on the line are untouched. Two spaces per tab, so one tab reads as one indent level, consistent with the unit the feature shifts by. This is the one place indenting rewrites text it was not asked to shift, and it is deliberate: without it, a tab-indented line indented by two spaces produces `··\tcode`, an indentation the user cannot then outdent away.

**Blank and whitespace-only lines are skipped, in both directions.** A blank line inside an indented range keeps its exact bytes, so indenting never introduces trailing whitespace and outdenting never fiddles with a line that has no code on it. This is the opposite of `commenting`'s rule, which pads a short line out to the common indent so a commented block reads as contiguous (`web/src/editor/plugins/commenting/line-comment.ts:35` `commentEdit`, `const padding = ' '.repeat(...)`) — there the marker must be visible on every line for the block to read as one comment; here whitespace on an empty line is invisible and only shows up in diffs. A line consisting only of tabs counts as whitespace-only and is skipped, so tab expansion never fires on a line that has no code.

**The slice is whatever the family already hands a `'selection'` binding, including a trailing line the user only touched at column 0.** `selectedLines` (`web/src/editor/plugins/useEditorPlugins.ts:35`) widens the selection to whole lines, so a drag ending at the start of the next line includes that line in the shift. `commenting` behaves the same way, and matching it is more valuable than special-casing an end column here.

**The selection follows the shift, exactly as commenting's does.** A range selection ends up covering the same whole lines it covered before, so repeated presses keep shifting the same block. A bare caret stays put relative to its text, moving right or left by however much its own line shifted, clamped to that line's new length. This is `web/src/editor/plugins/commenting/toggle.ts:13` (`selectionFor`) applied to a different transform, and it is what makes `Cmd+]` then `Cmd+[` return the buffer and the selection to where they started.

**Nothing to do is a silent no-op.** Outdenting a block with no leading whitespace, or a range of only blank lines, produces no edits, so the handler returns `null`: no text changes, no undo step is recorded, and no message appears. However many lines a press does change, one undo restores all of them at once — the applier already guarantees that (`web/src/editor/plugins/apply-edits.ts:63`).

**The core key table gains an explicit yield list; it does not lose `Tab`.** `Tab` and `Shift+Tab` are core bindings, and the plugin path is consulted only where `actionForKey` answers null (`web/src/editor/EditorTab.tsx:129`–`:135`), so a plugin cannot reach them as things stand. Rather than weaken "core bindings always win," `web/src/editor/keys.ts` gains a small, explicitly enumerated predicate — call it `yieldsToPlugins` — answering whether the core table hands a given keydown to the plugin path *in the current editing context*. It answers true for `Shift+Tab` always, and for `Tab` only when the selection spans two or more lines. Everything else answers false. The table still owns the decision; it just states the two chords it is willing to delegate, in the same file a reader already goes to for the binding table.

The ceiling this accepts deliberately: the yield list is a hard-coded two-entry table, not a mechanism a plugin can extend, so a third yielded chord means editing `keys.ts`. That is the point — delegating a core binding is a decision the editor makes about itself, and if the list ever grows past a handful the upgrade is to give a binding a declared "yield condition" the core table reads, not to let declarations claim core chords.

**`actionForKey` itself is unchanged.** The yield predicate is a separate function taking the same `KeyLike` and one boolean — whether the selection spans more than one line — so no existing binding's answer moves and no `KeyAction` variant is added. A boolean rather than a context object: there is one caller and one piece of context, and a parameter object can be introduced if a third yielded chord ever needs something else. `applyKeyAction.ts` is untouched.

**A yielded chord is offered to plugins first and falls back to the core action.** In `onKeyDown`, before dispatching the core action, a yielded keydown is offered to the plugin handler; if a plugin claims it the press is handled and default is prevented, and if none does — because the plugin was disabled, or a future build ships without it — the core action runs exactly as it does today. The fallback needs no new bookkeeping: `bindings()` already filters out a disabled plugin's chords (`web/src/editor/plugins/host.ts:103`, `table.filter((binding) => !disabledPlugins.has(binding.plugin))`), so the handler simply answers false. A broken `indenting` plugin therefore degrades `Tab` to inserting a tab character rather than to doing nothing, which is the behavior the editor has always had and the one a user can most easily recover from. The single press on which the plugin first fails is still consumed — the chord is claimed synchronously and the failure happens after — so the fallback starts from the press after the failure, not the one that caused it.

**The context the yield predicate needs is already in `onKeyDown`'s scope.** `EditorTab.tsx:47` destructures `const { state } = api`; a selection spans more than one line when `state.anchor` is non-null and `state.anchor.line !== state.cursor.line`. No new hook, ref, or prop is introduced to carry it.

**`Cmd+[` is the browser's history-back chord, and the existing synchronous claim already handles it.** `useEditorPlugins` answers whether a plugin claims a chord synchronously and dispatches the handler after (`web/src/editor/plugins/useEditorPlugins.ts:97`, "Answers synchronously so the caller can preventDefault before the handler's own work begins"), so `onKeyDown` calls `preventDefault()` in the same tick and the browser never navigates. Nothing new is needed for this; it is called out because a `Cmd+[` binding that lost that property would silently navigate away from an unsaved buffer.

**No collision with the tab-switching chords.** `Cmd+Shift+[` and `Cmd+Shift+]` move tabs at the window level (`web/src/useWindowKeys.ts:127`–`:128`), and both carry Shift, so their canonical ids differ from the plugin's shift-less `meta+[` and `meta+]`. The editor's `onKeyDown` calls `stopPropagation()` before anything else anyway (`web/src/editor/EditorTab.tsx:127`), so window bindings never see a keydown typed in the editor.

**One refusal rule, not two: delete the modifier check and narrow `claimedByCore`.** Today a chord is refused twice over — once at validation for carrying neither Cmd nor Ctrl (`web/src/editor/plugins/registry.ts:42`, `hasModifier`) and once at host construction for being a chord the core table already claims (`host.ts:82`, `claimedByCore`). Both exist to enforce one invariant: *a plugin may never declare a chord that could not fire*. The modifier rule is the weaker statement of it — an unmodified printable key is refused only because `plainAction`'s default turns it into an insert (`keys.ts:87`), which is precisely what `claimedByCore` already detects. So rather than widen both rules to admit `Tab`, delete the modifier check and its `hasModifier` helper, and narrow `claimedByCore` to mean "claimed by the core table and never yielded to plugins." One predicate then decides the whole question: `Cmd+S` and an unmodified `/` are still refused, `Tab` and `Shift+Tab` are not, and a key the core table never binds at all — `F5`, say — becomes declarable, which is correct and was only ever refused as collateral damage from the coarser rule.

This is a deletion, not a widening: no rule is loosened without something still enforcing the invariant behind it, and both refusals already end in the same place — `validateDeclarations`' rejections are fed straight into `disable` at host construction (`host.ts:74`), so a refused plugin is disabled and reported identically either way. `validateDeclarations` keeps its other two checks (API version, at least one binding) and its duplicate-chord refusal (`registry.ts:64`), which nothing else covers.

**`EDITOR_PLUGIN_API_VERSION` stays at 1.** Every declaration valid under the old rules is still valid, and no request, result, or declaration field changes shape. Accepting strictly more than before is not a breaking change, and bumping the version would disable `commenting` for no reason.

**`Tab` on a selection inside a single line keeps today's behavior.** It replaces the selection with a tab character, because the yield predicate only fires for a selection spanning two or more lines and the core insert action already replaces the selection. This is VS Code's behavior and it costs nothing to keep — `applyKeyAction`'s insert path is unmodified.

**`Shift+Tab` outdents even with no selection.** Today it inserts a tab character, identical to plain `Tab`, which is a binding nobody relies on; making it always outdent gives `Cmd+[` a symmetric partner and matches every editor a user is likely to come from.

**The plugin ignores the file's name.** Indentation is not a language feature here — no auto-indent, no reindent-to-syntax, no language-specific unit. `request.file` is available and unread, which is the contract working as intended: `commenting` branches on it and `indenting` has nothing to branch on.

**The query line and pending suggestions are unaffected without any new code.** `handleSuggestKeyDown` runs before the key table and consumes `Tab` itself on the agent query line, for persona completion and pill focus (`web/src/editor/handleSuggestKeyDown.ts:80`), and it returns early while a suggestion is pending review. A plugin chord is therefore already inert in both states, exactly as `product/specs/editor-tab.md:231` states, and the new yield branch goes after that call so nothing about it changes.

## Proposed changes

**The plugin.** `web/src/editor/plugins/indenting/` holding `index.ts` and `shift.ts` — two files, not the four `commenting` needed, because there is one strategy rather than two and no syntax table at all. `index.ts` default-exports the handler: read `request.command`, delegate `indent` and `outdent` to the transform with the corresponding direction, and return `null` for anything else, which is the same silent no-op an unknown file extension gets in `commenting`. `shift.ts` is the pure transform and the only place indenting's rules live: given the slice's lines, the document line the slice starts at, and a direction, it returns the edits and the width the last touched line ends up with, then the selection those imply — the shape `commenting`'s `toggleLineComments` and `selectionFor` already have between them. The per-line rules are skip a blank or whitespace-only line, expand leading tabs to two spaces each, then prepend two spaces or remove up to two leading spaces. Measuring the leading whitespace is `commenting`'s `indentOf` idea (`line-comment.ts:12`, `line.length - line.trimStart().length`) and needs nothing beyond it.

Each line's edit is a replacement of that line's leading-whitespace range with the new leading whitespace, in absolute document coordinates. A line whose leading whitespace is unchanged contributes no edit at all, so an outdent that can only move some lines produces edits for exactly those lines and the applier's non-overlap check is trivially satisfied.

**The declaration.** Append an `indenting` entry to `editorPluginDeclarations` (`registry.ts:15`) with `version: '1.0.0'`, `apiVersion: EDITOR_PLUGIN_API_VERSION`, and four bindings — `indent` on `{ key: ']', meta: true }` and on `{ key: 'Tab' }`, `outdent` on `{ key: '[', meta: true }` and on `{ key: 'Tab', shift: true }` — all `needs: 'selection'`. Add the matching `indenting: () => import('./indenting/index')` thunk to `editorPluginLoaders` (`:26`), which the existing `satisfies Record<ProductionEditorPluginId, …>` then requires. The registry must not statically import the new implementation module, for the reason its own header comment records and `registry.test.ts:45` pins.

**The yield predicate.** `web/src/editor/keys.ts` (98 lines) exports a predicate over the same `KeyLike` (`:29`) and one boolean for whether the selection spans more than one line. Its table is two entries — `Shift+Tab` unconditionally, `Tab` only when the selection spans lines — and a comment explaining why only these two chords are delegated: they are the only core bindings whose meaning genuinely depends on whether a block is selected. `actionForKey` (`:93`) and `applyKeyAction.ts` are not modified.

**The narrowed refusal.** `chords.ts:44`'s `claimedByCore` already converts an `EditorChord` into the `KeyLike` shape and asks `actionForKey`; it additionally asks the yield predicate with the spans-lines flag set, since a chord yielded in *any* context can fire and must not be refused. That is the whole change to the file besides deleting `hasModifier` (`:30`). Both live in `chords.ts` rather than `registry.ts` because it already imports `../keys`, keeping the dependency direction `registry → chords → keys` as it is. Its comment records that a yielded chord is claimed-but-delegated rather than unbound, since that is the one non-obvious thing about the check afterwards.

**The deleted modifier rule.** Remove the `bare` check from `declarationFault` (`registry.ts:42`–`:45`) and the now-unused `hasModifier` import; `validateDeclarations` keeps its API-version, empty-bindings, and duplicate-chord checks. `hasModifier` goes from `chords.ts` too, along with its `describe` block in `chords.test.ts:41` and its use in `registry.test.ts:38` (which asserts every shipped binding carries a modifier — an assertion the new `Tab` bindings would fail, and which the narrowed `claimedByCore` now covers properly).

**Client wiring.** In `web/src/editor/EditorTab.tsx`, one branch in `onKeyDown` (`:124`) after the suggest handler (`:128`) and before `const action = actionForKey(e)` (`:129`): when the keydown is yielded in the current context and `pluginKey(e)` claims it, `preventDefault()` and return; otherwise fall through exactly as today. The file is 207 raw lines but 182 by the `max-lines` count (which skips blanks and comments), so a four-line branch fits under the 200 cap without an extraction — extract the keydown routing into a module beside it only if the branch grows well past that, following the four hooks the file already extracted for this reason.

**Specs.** Add an "Indenting" section to `product/specs/editor-tab.md` after "Commenting" (`:197`–`:222`), describing the four chords, the two-space unit, the outdent-what-is-there rule, tab expansion, skipped blank lines, the selection behavior, the single-line-selection `Tab` case, and the silent no-op. Amend the "Keyboard input" section (`:93`) where it lists `tab` among the keys the editor handles, and the "Editor plugin bindings" section (`:224`–`:232`) where it states that the editor's own bindings always win — both need the narrow yield exception stated plainly, along with the fallback that an unclaimed yielded chord still runs its core action. In `product/specs/editor-plugins.md`, replace the declaration rule at `:17` (a chord carrying neither Cmd nor Ctrl is refused) with the single rule that survives — a chord the editor's own table claims and never yields is refused — and amend "Chord resolution" (`:19`–`:23`) with the narrow yield exception. Add a "Bundled indenting plugin" section beside the commenting one at `:53`.

**Documentation.** Update `documentation/developer-documentation/editor-plugins.md` where it states the modifier requirement, replacing it with the single refusal rule and naming the two yielded chords. The page's worked example stays `commenting` and `registry.test.ts:62` reads `editorPluginDeclarations[0]`, so appending the new entry leaves those assertions passing untouched.

**Not affected — do not chase these.** No server change of any kind: no protocol message, no `src/plugins/`, no notification type, no `plugins` command entry. `web/src/plugins/` (the tab family) is untouched. `apply-edits.ts`, `host.ts`, and `useEditorPlugins.ts` are untouched — a second plugin is exactly what they were built to carry. `commenting` is untouched.

**Ordering.** Land the pure `shift.ts` and its tests first, then `index.ts`, then the `keys.ts` yield predicate with its tests, then the `claimedByCore` narrowing and the `hasModifier` deletion together (the deletion must not land before the narrowing, or a `Tab` binding would briefly be accepted by validation and then disabled by the host), then the declaration and loader, and finally the `onKeyDown` branch that switches `Tab` on. `Cmd+[`/`Cmd+]` work from the declaration step; nothing about `Tab` changes until the last step. Client modules take no import extension; optional-field reads use `??`.

## Out of scope

- **A configurable indent width.** Two spaces is fixed — no setting, no per-language width, no detection of the file's existing style.
- **Language-aware indentation.** No auto-indent on a new line, no reindent-to-syntax, no bracket or block awareness. The plugin shifts whole lines by a fixed amount and reads nothing about the file's type.
- **Multi-cursor and multiple selections.** Only the single current selection, or the caret's line, is shifted — `EditorState` holds one anchor and one cursor, and a plugin cannot express what the editor cannot represent.
- **Converting a file's indentation.** Leading tabs are expanded only on lines a shift actually touches; nothing normalizes a whole file, and no command to do so is added.
- **Trailing-whitespace cleanup.** Blank lines are left exactly as they are, including any whitespace already on them.
- **Any core binding beyond `Tab` and `Shift+Tab`.** The yield list is those two chords and stays a small explicit table, not a general mechanism a plugin can extend.
- **A server-visible surface.** No protocol message, no `plugins` command entry, no notification beyond the failure report the family already sends.
- **Indent-aware selection niceties.** No "outdent moves the caret to the first non-blank character," no smart Home, no indent guides.
