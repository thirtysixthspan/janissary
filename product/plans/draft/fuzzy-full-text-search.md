# Fuzzy full-text search over an editor tab's buffer

**Complexity: 3/10** — one new hook, one new presentational component, and a keybinding entry, all modeled line-for-line on Quick Open; the only work outside that pattern is one added field on `FuzzyMatchResult` (so duplicate buffer lines stay distinct) and one CSS positioning fix, with no server, protocol, or persistence surface touched.

An editor tab has no way to find a line. `Cmd+F` is inert there — `canSearch` is `!isViewTab && !current?.activePty` (`web/src/useViewSearchState.ts:10`), and an editor tab is a view tab, so the existing transcript SearchBar never applies to it. Finding a string in an open file today means scrolling, or leaving the app.

This plan gives the editor tab a fuzzy line-search overlay modeled directly on Quick Open (`Cmd+P`): `Cmd+F` opens a small overlay with its own text input; typing fuzzy-matches the buffer's lines and lists the ten best, each as a dimmed line number beside the line's text with the matched characters emphasized; arrowing through the results moves the editor caret to the highlighted line **live**, scrolling the buffer behind the overlay, so the user reads the match in context without committing to anything; `Escape` closes the overlay and leaves the caret where the last previewed jump put it. The scope is deliberately one tab kind and one direction: this version searches the active editor tab's own buffer only — not the transcript, not other tabs, not files on disk — and it finds; it does not replace.

## Design decisions

**Editor tabs only.** The overlay exists in the editor tab and nowhere else. Transcript tabs keep the existing regex step-through SearchBar (`web/src/SearchBar.tsx`, `web/src/useTranscriptSearch.ts`) and the `search transcript <pattern>` command unchanged — no chord is rebound, no existing behavior is retired, and `canSearch` keeps meaning exactly what it means today. Markdown, image, ssh, and file-navigator tabs get nothing.

**`Cmd+F` is the trigger, handled inside the editor's own key path.** The editor's `onKeyDown` calls `e.stopPropagation()` (`web/src/EditorTab.tsx:114`, `// Nothing typed in the editor may reach App's global bindings`) precisely so nothing typed in the buffer reaches App's window bindings, which means a window-level handler in `useWindowKeys` would never see `Cmd+F` while the textarea holds focus. The binding therefore lands in `metaAction` (`web/src/editor/keys.ts:32`), where `f` currently returns `null` and falls through to the browser's native find. Handling it there also gives the `preventDefault()` that suppresses that native find. `Ctrl+F` is untouched — it stays the Emacs-style "move right" binding (`web/src/editor/keys.ts:54`, `case 'f': { return { kind: 'move', dir: 'right', … } }`).

**The suggestion surfaces keep owning the keyboard when they have it.** `EditorTab`'s `onKeyDown` calls `handleSuggestKeyDown` first (`web/src/EditorTab.tsx:115`), and the `find` branch goes *after* it, not before. Two consequences, both intended: while a persona suggestion is pending, `Cmd+F` is swallowed along with every other keystroke (`web/src/editor/handleSuggestKeyDown.ts:112`, `if (suggest.pending)`), matching the spec's "every keystroke other than the accept/decline clicks is suppressed"; and while the agent query line holds focus, `Cmd+F` reaches `handleQueryEdit` → `actionForKey` → `suggest.applyQueryAction`, where a `find` action does nothing. The overlay therefore opens only when the buffer itself has focus and nothing is pending. Neither path needs new code — both already `preventDefault()` — but the implementer must not "fix" either by hoisting the `find` branch above `handleSuggestKeyDown`.

**Arrowing previews the jump live; `Escape` leaves the caret there.** `Up`/`Down` move the highlighted row *and* immediately move the editor caret to that line, letting the existing caret-scroll effect (`web/src/EditorTab.tsx:66`–`:82`) bring it into view behind the overlay. There is no separate commit step and no restore-on-cancel: `Escape` closes the overlay and the caret stays on whatever line was last previewed, because a user who arrowed to a line and dismissed the overlay wanted to be at that line. Clicking a row does the same jump.

**Ten results, ranked best-first.** The list is capped at the ten best-scoring lines, the same cap Quick Open uses, sorted by the existing fuzzy score.

**Rows are a dimmed line number plus the line's text, with matched characters emphasized.** `fuzzyMatch` already computes per-result match ranges (`web/src/fuzzy-match.ts:1`, `FuzzyMatchResult = { path; score; ranges }`), so the emphasis is a render of data the matcher already hands back, not new matching work. No component renders `ranges` today — `QuickOpen` ignores them and `TabNavPicker` does its own single-substring highlight (`web/src/TabNavPicker.tsx:41`, `highlightLabel`) — so splitting a line into marked and unmarked segments from a range list is the one genuinely new piece of rendering. It uses the `<mark>` element, the same one `highlightLabel` uses, so the existing accent-on-selection styling applies with one new selector.

**The overlay is a child of `.editor-tab`, which must become a positioned ancestor.** `.picker` is `position: absolute; left: 0; right: 0; bottom: 0` (`web/src/theme.css:481`), and neither `.editor-tab` (`:202`) nor its wrapping `.tab-body` (`:334`) is positioned — the nearest positioned ancestor is the pane grid (`:154`), so an overlay dropped in as-is would span the whole grid, across both panes in a split. `.editor-tab` therefore gains `position: relative`, and the overlay renders as its last child. It is *not* placed inside `.editor-body`: that element scrolls (`:682`, `overflow-y: auto`), so an absolutely-positioned overlay inside it would scroll away with the buffer.

**A long line is truncated with an ellipsis.** One row per matching line, clipped at the overlay's width; no windowing around the match, no wrapping. A match past the clip point is simply not visible in the row — the line number and the jump still identify it.

**Wording names the buffer.** The input's placeholder reads `Search buffer`. An empty query shows a `type to search` hint with no rows; a query matching nothing shows `No matching lines` — the same three states, in the same shapes, as `quickOpenBody` (`web/src/QuickOpen.tsx:28`).

**`Escape` closes it, and so does switching tabs.** Leaving the editor tab closes the overlay, mirroring how transcript search closes on a tab change (`web/src/useTranscriptSearch.ts:26`). Because every editor tab stays mounted across tab switches (`web/src/EditorTab.tsx:28`), this is a reaction to the `active` prop going false rather than an unmount. Reopening the tab shows no overlay; `Cmd+F` opens a fresh one. A live reload of the file from disk while the overlay is open simply re-filters against the new buffer content.

**It searches the live buffer, including unsaved edits.** The source is the editor's in-memory `state.lines`, so a match can be on text that has never been written to disk. Nothing is fetched from the server; there is no new protocol message.

## Proposed changes

**One added field on the matcher's result, not a second matcher.** `fuzzyMatch` returns results keyed by the matched *string* (`FuzzyMatchResult.path`), which is ambiguous the moment two buffer lines are identical — and identical lines (blank lines, closing braces, repeated boilerplate) are the common case in a file, not an edge case. The whole fix is to stop throwing the candidate's position away: `FuzzyMatchResult` (`web/src/fuzzy-match.ts:1`) gains an `index` field, and `fuzzyMatch`'s candidate loop (`:81`, `for (const path of paths)`) carries that index through scoring into the returned results. No new function, no wrapper, no second entry point — Quick Open reads `result.path` and is unaffected by an extra field. The existing tie-break chain (`:89`, score, then length, then `localeCompare`) gains the index as a final tie-break, so two identical lines rank adjacently in a stable, first-in-buffer-first order rather than arbitrarily.

**A find action in the editor key table.** Add a `{ kind: 'find' }` member to `KeyAction` (`web/src/editor/keys.ts:10`) and a `case 'f'` to `metaAction`. `find` is a UI action, not a buffer mutation, so `applyKeyAction` needs no case for it — both of its switches already end in a `default` that does nothing (`web/src/editor/applyKeyAction.ts:45`, `:71`), so a `find` action that reaches it is silently and harmlessly ignored. `EditorTab`'s `onKeyDown` branches on `action.kind === 'find'` after `handleSuggestKeyDown` and before `api.apply`, opening the overlay and returning. This keeps `keys.ts` the single place any editor chord is declared.

**A state hook for the overlay.** A new `web/src/editor/useEditorFind.ts` exporting `useEditorFind`, taking the editor's current `state.lines` (or null, before the file loads) and the `active` flag, and returning the open flag, the query, the capped ranked results, the selected index, and `open`/`close`/`setQuery`/`setSelected` callbacks — the same surface `useQuickOpen` exposes, minus everything about loading and fetching, since the buffer is already in memory. It calls `fuzzyMatch` directly on `state.lines` inside a `useMemo` keyed on `(lines, query)`, and reads the result's new `index` as the line number — no separate result type, no mapping layer, no parallel arrays. The cap is `10`, a module constant (`useQuickOpen`'s `RESULT_CAP` at `web/src/useQuickOpen.ts:5` is not exported). Opening resets the query to empty and the selection to 0. Changing the query resets the selection to 0; a result list that shrinks under the selection clamps it, the way `useTranscriptSearch.ts:21` clamps `matchIndex`. `active` going false closes the overlay. A buffer with no lines yet (file still loading) yields no results and the overlay simply shows its empty-query hint.

Deliberately *not* deferred: `useQuickOpen` wraps its query in `useDeferredValue` (`web/src/useQuickOpen.ts:26`) because it scans a whole project's file list, but one file's lines are orders of magnitude fewer and the scan is a bailing subsequence walk (`web/src/fuzzy-match.ts:12`, `hasSubsequence`). The ceiling is a rescan of every line on every keystroke; if a pathological buffer ever makes typing stutter, the upgrade is to wrap the query in `useDeferredValue` exactly as Quick Open does — a one-line change in this hook, not a redesign.

**The overlay component.** A new `web/src/editor/EditorFind.tsx` exporting `EditorFind`, a near-copy of `QuickOpen`'s structure (`web/src/QuickOpen.tsx:41`): a `.picker` container with an autofocused input and a body function returning one of the three states, plus its own `onKeyDown` that calls `e.stopPropagation()` and handles `ArrowUp`/`ArrowDown` (move selection), `Escape` (close), and `Enter` (`preventDefault` only — the jump has already happened live). Each row renders the line number in a dimmed span and the line's text with the matched ranges wrapped in `<mark>`, using a small module-local helper that walks the range list and emits alternating plain and marked segments — the generalization of `TabNavPicker.highlightLabel` (`web/src/TabNavPicker.tsx:41`) from one substring to many. The component is presentational: it takes results, the selected index, and change/close callbacks, and owns no state.

**Wiring into the editor tab.** `EditorTab` calls `useEditorFind`, renders `EditorFind` as the last child of `.editor-tab` when the overlay is open, and — on every selection change — moves the cursor to the selected result's line (column 0, selection collapsed) through `api.setState`, which makes the existing caret effect at `web/src/EditorTab.tsx:66`–`:82` scroll it into view. Cursor-only moves must not become undo steps: the jump goes through the same "seal, then set" shape `applyKeyAction`'s `move` uses (`web/src/editor/applyKeyAction.ts:81`), via `api.sealUndo()` followed by `api.setState`. `EditorTab.tsx` counts ~140 lines against the 200-line `max-lines` cap (blanks and comments are skipped, per `eslint.config.mjs:60`), so the three additions — the hook call, the `find` branch, the JSX element — fit comfortably; the hook/component split is for cohesion with the rest of `web/src/editor/`, not to dodge the limit.

**Styling.** In `web/src/theme.css`: add `position: relative` to `.editor-tab` (`:202`) per the positioning decision above, and a small `/* Editor find overlay (Cmd+F) */` block beside the Quick Open block (`:504`) covering the input (reuse the `.quick-open .command input` rule's shape), the dimmed line-number span, the row's `overflow: hidden; text-overflow: ellipsis` truncation, and the `<mark>` accent pair mirroring `:512`–`:513`. `.picker`, `.picker-row`, and `.picker-empty` are reused for the frame and empty states rather than duplicated.

**Ordering.** Land the `index` field plus its tests first, with Quick Open's existing tests still green — that step is self-contained and proves the extra field changed nothing. Then the hook, then the component, then the `keys.ts` action and the `EditorTab` wiring (which is the first point where anything is user-visible), then the CSS. Web imports stay extensionless per `eslint.config.mjs`'s bundler-resolution rule for `web/`; the `.js`-extension rule applies to `src/` only, and nothing in `src/` is touched.

**Spec.** Add a "Finding a line" section to `product/specs/editor-tab.md` covering the chord, the live-preview jump, the ten-row cap, the row rendering, the three body states and their exact wording, and the close-on-tab-switch behavior.

- `web/src/fuzzy-match.test.ts` — every result carries its candidate's `index`; two identical candidates both appear with distinct indices, ordered first-in-array-first; the existing cases still pass unchanged (ranking, cap, ranges, and empty-query short-circuit are untouched).
- `web/src/editor/keys.test.ts` — `Cmd+F` resolves to the `find` action; `Ctrl+F` still resolves to "move right" (the Emacs binding at `keys.ts:54`) and is not shadowed; `Alt+F` still resolves to nothing.
- `web/src/editor/useEditorFind.test.ts` (new, beside the other editor hook tests) — an empty query yields no results; a fuzzy query returns matching lines ranked best-first and capped at ten; two identical lines both appear, with distinct line numbers taken from the result `index`; the selected index clamps when the buffer shrinks under it and resets to the top when the query changes; `active` going false closes the overlay; a buffer change while open re-filters.
- `web/src/editor/EditorFind.test.tsx` (new) — renders the `Search buffer` placeholder; an empty query shows `type to search`; a non-matching query shows `No matching lines`; a matching query renders rows with line numbers and emphasized match ranges; `ArrowDown`/`ArrowUp` call the selection callback and `Escape` calls close; a click on a row selects it.
- `web/src/EditorTab.test.tsx` — `Cmd+F` in the buffer opens the overlay and does not insert an `f`; arrowing in the overlay moves the editor cursor to the highlighted result's line; `Escape` closes the overlay and leaves the cursor on that line; switching the tab inactive closes the overlay; typing in the overlay input does not reach the buffer; the jump adds no undo step (`Cmd+Z` right after a jump undoes the last real edit, not the cursor move); `Cmd+F` while a persona suggestion is pending opens nothing.

## Out of scope

- **Find and replace.** No replace field, no replace-all, no confirm-each. Search only.
- **Persistent in-buffer match highlighting.** Matches are shown in the overlay's list only; the editor body itself is never marked up.
- **Cross-tab or project-wide search.** Only the active editor tab's own buffer. Other editor tabs, other tab kinds, and files on disk are untouched — Quick Open (`Cmd+P`) remains the way to reach another file.
- **Regex and case-sensitivity modes.** Case-insensitive fuzzy subsequence matching only, with no toggles.
- **Transcript, markdown, ssh, and file-navigator tabs.** The original backlog entry named a tab's scrollback and output buffers too; this version covers the editor buffer alone, and the existing transcript search is left exactly as it is.
- **A command-bar entry point.** No `find <query>` command; an editor tab has no command bar, and `Cmd+F` is the whole surface.
- **Restoring the caret on cancel.** `Escape` deliberately keeps the previewed jump.
- **Persisting the query.** The overlay opens empty every time; nothing about it survives a tab switch or a relaunch.

## Verification

- `./scripts/run.mjs check-diff` — lints the changed files, incrementally typechecks the web project, and runs the related web tests.
- Manual: launch the app and `edit` a long file (for example `product/specs/editor-tab.md`). Press `Cmd+F` — the overlay opens with a focused `Search buffer` input and a `type to search` hint, and the browser's own find bar does not appear. Type a fuzzy fragment of a line you know is far down the file (e.g. `synhi` for the syntax-highlighting heading) and confirm at most ten rows appear, each with a dimmed line number and the matched characters emphasized. Arrow down through the rows and watch the buffer scroll behind the overlay to each highlighted line. Type a string that matches nothing and confirm `No matching lines`. Clear the query and confirm the hint returns. Press `Escape` — the overlay closes and the caret sits on the last previewed line, ready to type. Reopen with `Cmd+F`, then switch to another tab and back — the overlay is closed and the buffer's scroll position and unsaved edits are intact. Finally, open an agent tab and confirm `Cmd+F` still opens the old transcript SearchBar there, unchanged.
