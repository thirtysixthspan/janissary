# Pull request review task

**Complexity: 2/10** — one new markdown file under `ai/tasks/`, no source, no test, no protocol, no UI. Nearly every mechanism it needs already exists and is reused verbatim: pull request targeting and checkout from `resolve-conflicts.md`, the entry format and dedupe rules from `find-technical-debt.md`, and the commit and push scripts. What takes care is the task file's own rules — the read-only boundary, the dedupe-before-write ordering, and the five review dimensions — not the machinery underneath them.

## Summary

The project has a task that takes an open pull request and makes it mergeable (`ai/tasks/workspace/resolve-conflicts.md`), and it has tasks that read code and record what they find into a backlog (`ai/tasks/research/find-technical-debt.md` and its siblings). It has nothing that takes an open pull request and *reviews* it. Every review today is a human reading a diff on GitHub, and whatever they notice lives in their head or in a comment thread that no later task can act on.

`ai/tasks/pull-request-review.md` closes that gap. Given a pull request — a number, a URL, or the branch currently checked out — it checks the head branch out and sets it up locally exactly the way `resolve-conflicts.md` does, reads the plan the pull request carries and the description the pull request states, and then reviews the proposed diff across five dimensions: whether the description matches what was actually implemented, how faithfully the implementation delivers the plan, what functionality the implementation is missing, what technical debt it introduces, and what security issues it introduces. Every genuine finding becomes a structured entry in `product/backlog/pull-request.md` on the pull request's own head branch, committed and pushed, with the pull request left open.

The task reads, judges, and records. It never edits source code, never edits the pull request's description, never merges or closes anything, and never runs the project's build, lint, test, or quality tooling — a reviewer's judgment is the whole instrument, the same stance `find-technical-debt.md` takes. What it produces is a work queue on the branch itself: a list of issues and proposals, each concrete enough that an agent opening the entry cold can execute it.

## Design decisions

1. **The task file is `ai/tasks/pull-request-review.md`, at the top level of `ai/tasks/`.** That is where the tasks that take a target and run a full cycle against it live — `build-a-feature.md`, `fix-a-bug.md`, `work-an-issue.md`, `resolve-technical-debt.md`, `update-documentation.md`. It is deliberately not filed under `research/`, whose tasks all sweep the whole codebase unprompted and commit to `master`, nor under `workspace/`, whose tasks manipulate branch and pull request state rather than judging content. No registration step follows: `product/specs/task-picker.md` says the picker reads `ai/tasks/` fresh from disk every time it opens, recursing into subdirectories, so the file appears in the Project section the moment it exists.

2. **Findings land in a backlog file on the pull request's own head branch, and nowhere else.** No `gh pr comment`, no `gh pr review`, no inline annotations. The value of the review is a queue a later agent can execute, and GitHub's review thread is not a place any task in this repo reads from. Committing to the head branch also means the findings travel with the pull request — they arrive on `master` with it, or disappear with it if it is abandoned.

3. **The review is read-only judgment, with no tooling.** No `npm run lint`, no `npm run typecheck`, no test run, no `check-diff`, no `pr-check-gate`, not even the diff-scoped fast commands. This mirrors `find-technical-debt.md`'s standing rule and its reasoning: those tools have their own dedicated tasks that consume their output, and this task's job is the judgment a human reviewer makes by reading. Plain read-only navigation — `ls`, `wc -l`, `grep`, `git log`, `gh pr diff` — stays allowed. The honest cost is that a pull request whose branch does not compile can still review clean on every dimension this task checks; the report names that limit rather than papering over it.

4. **Re-running on the same pull request dedupes and appends.** Every entry already in the file, in any section, is a dedupe set; only genuinely new findings are appended to `## development`. This is `find-technical-debt.md` Step 1's rule, and it is what makes a second review after partial fixes useful: it adds what is new without disturbing entries a human has triaged into `## deferred` or `## declined`.

5. **The task creates `product/backlog/pull-request.md` on demand; `janus init` is not changed.** The file is written with the standard `ready`/`development`/`deferred`/`declined` sections when it is missing, matching `backlogFileContent` (`src/project-init.ts:23-25`, which returns `` `# ${name}\n\n## ready\n\n## development\n\n## deferred\n\n## declined\n` ``) byte for byte. It is deliberately not added to that module's `BACKLOG_FILES` list (`src/project-init.ts:20`): a pull-request review backlog is meaningful on a pull request branch and empty noise in a freshly scaffolded project, and leaving the list alone means this change touches no source file, no spec, and no test. `src/project-init.test.ts:31` asserts exactly the six current names and keeps passing untouched.

6. **The backlog file accumulates across pull requests; it is never cleared or scoped to one.** When a reviewed pull request merges, its `pull-request.md` reaches `master`, and the next pull request branches from it carrying those entries. They stay: an entry describes outstanding work, and merging the pull request it was found on does not do that work. Inherited entries count as the dedupe set like any others, and the task never truncates the file, never adds a per-pull-request heading, and never scopes an entry to one pull request. This is how the other six files in `product/backlog/` already behave — they accumulate across many changes and are drained by the tasks that consume them. The accepted cost is dedupe's usual one: a genuinely new finding that closely resembles an inherited entry is skipped as a duplicate.

7. **A clean review commits nothing.** If the pull request matches its description and its plan and the review finds no gap, no debt, and no security issue, no file is created and no commit is made — the report says the pull request reviewed clean. `find-technical-debt.md` already establishes that finding nothing is a valid outcome rather than a prompt to pad the list, and creating an empty backlog file would leave a diff whose only content is four empty headings.

8. **A description that does not match the implementation is recorded, never corrected.** The mismatch becomes an entry whose `Proposal` says exactly how the description should read; `gh pr edit` is never run. The description is the author's own statement of intent, and silently rewriting it to match the code would destroy the very evidence the next reviewer needs to judge whether the code or the description is the thing that is wrong.

9. **Entries say "issue", not "debt".** The first labeled paragraph is `Existing Issue`, and the severity scale it carries is an issue-severity scale. Four of the five dimensions this task reviews — a description mismatch, a plan the implementation did not deliver, missing functionality, a security hole — are not technical debt in any useful sense, and labeling them as such would misdescribe most of the file. The other three labels (`Existing Risk`, `Proposal Risk`, `Proposal`) and all three scores carry over from `find-technical-debt.md` unchanged.

10. **An entry names its dimension in its summary bullet, in plain words.** No `Category:` line and no per-dimension sub-headings under `## development`. The file keeps the flat "`*` bullet list under a `##` heading" shape every other file in `product/backlog/` uses, so an entry here reads the same way an entry in `technical-debt.md` does, and a bullet that opens "Correct the pull request description's claim that…" or "Deliver the plan's…" is already self-describing.

11. **There is no cap on the number of findings.** `find-technical-debt.md` caps a run at 10 because it sweeps an entire codebase and could otherwise run forever; a pull request's diff is bounded, so completeness is achievable and a review that silently dropped findings would be worse than a long file. The task still refuses to pad the list — a marginal finding is dropped for being marginal, not to hit or avoid a number.

12. **Pull request targeting, checkout, and setup are `resolve-conflicts.md`'s, step for step.** The same three-way target resolution (an invocation argument; otherwise `gh pr view` with no argument for the current branch; otherwise `gh pr list` when exactly one is open), the same refusal to proceed on a target that is not `OPEN` or that resolves ambiguously, the same `gh pr checkout <number>` followed by `git pull --rebase`, and the same "execute only Steps 2 and 3 of `prepare-workspace.md`" so dependencies match the branch without switching back to `master`. Two tasks that take a pull request should find it the same way, and a reviewed branch that is also a working checkout is what "set up the branch locally" means in this repo.

    The dependency install is a deliberate, knowing cost, since decision 3 means nothing in the run consumes `node_modules`: `find-technical-debt.md` Step 0 skips `npm install` outright on exactly that reasoning, and this task could too, saving a few minutes per run. It is kept because setting the branch up locally is part of what this task was asked to do, and because it leaves the branch immediately workable for the human or the follow-up task that acts on a finding, rather than making them pay for an install first. The ceiling is that cost; if a run's turnaround ever matters more than leaving a workable checkout behind, drop `prepare-workspace.md` Steps 2 and 3 from Step 1 and nothing else in the task changes.

13. **The commit goes through `pr-commit` and `pr-push-branch`, and the tree is checked before it does.** `scripts/pr-commit.sh` runs `git add -A`, so anything else sitting in the working tree would be swept into the review's commit — the task verifies that `git status --porcelain` names `product/backlog/pull-request.md` and nothing else before committing, and reverts anything else it finds. `pr-check-changes.sh` is not used as that gate: it compares against `origin/master` (`AHEAD=$(git log --oneline origin/master..HEAD)`) and so always reports "something to ship" on a pull request branch, which answers a different question than the one being asked.

14. **The task runs autonomously and leaves the pull request open.** No questions, no waiting for feedback, and the same hard prohibitions `resolve-conflicts.md` carries: never `gh pr merge`, never close the pull request, never push the work to a different branch, never open a replacement.

## Proposed changes

### 1. New file `ai/tasks/pull-request-review.md` — the entire deliverable

One markdown task file, matching the shape and roughly the length of its two closest siblings — `ai/tasks/workspace/resolve-conflicts.md` and `ai/tasks/research/find-technical-debt.md` are 189 and 184 lines. It opens the way every task in `ai/tasks/` opens: a one-paragraph statement of the job, the `./product/` clarification that every path means the project working directory rather than the Janissary installation's own, the no-AI-attribution rule, the "run autonomously" rule, the "stay within the project directory" rule, and an allowed/forbidden pair. Allowed: read any file, check out the pull request's head branch, run read-only `git`/`gh` commands, create and append to `product/backlog/pull-request.md`, and commit and push that one file to the head branch. Forbidden, each with its reason: merging or closing the pull request; working a target that is not `OPEN` or that resolves ambiguously; editing any source, test, spec, config, plan, or documentation file; editing the pull request's title or description; posting a comment or a review to GitHub; running the project's build, lint, test, or quality tooling, including the diff-scoped commands; capping, padding, or otherwise shaping the finding list to a number; and committing anything other than the backlog file.

Its steps, in order:

**Step 0 — Identify the pull request.** `resolve-conflicts.md` Step 0, reused as written: an invocation argument is the target; otherwise `gh pr view --json state,number,headRefName,url` with no argument resolves the current branch's pull request; otherwise `gh pr list --state open --json number,title,headRefName,url` and take it only when exactly one is open. Report the candidates and stop when zero or more than one match, or when the state is not `OPEN`. State the target and how it was identified in one sentence.

**Step 1 — Check out and set up the branch.** `gh pr checkout <number>`, then `git pull --rebase`, then confirm `git branch --show-current` matches the head branch recorded in Step 0, then execute Steps 2 and 3 of `ai/tasks/workspace/prepare-workspace.md` — and only those two, since Step 1 there would switch to `master`. Also confirm the working tree is clean before going further: the commit in Step 5 stages everything, so a stray file present at the start would be swept in.

**Step 2 — Read what the pull request promises.** `gh pr diff <number> --name-only` for a `product/plans/**/*.md` entry, read that plan in full, then `gh pr view <number> --json title,body` for the description. When the diff carries no plan file, the description and the commit subjects from `git log origin/master..HEAD` are the statement of intent instead, the plan-fidelity dimension in Step 3 is judged against those, and the report says so. This step is reconnaissance: no findings are written yet, because three of the five dimensions are meaningless until the promise is known.

**Step 3 — Review the diff across five dimensions.** `git diff origin/master...HEAD` — three dots, the same command `resolve-conflicts.md` Step 5 uses — is the authoritative diff; `gh pr diff` is used only in Step 2 to list names. Read it in full, opening the surrounding files rather than judging hunks in isolation, since a hunk read alone is how a false finding gets recorded. Every file in the diff is in scope, not only `src/` and `web/src/`: a spec that no longer matches the behavior beside it and a documentation page the plan called for and the diff omitted are both findings. When the diff is too large to read at once, list it with `git diff origin/master...HEAD --name-only` and read it file by file rather than sampling it — dropping files silently would defeat decision 11. Form candidate findings under each of these headings; the task file states each dimension as a question with the evidence that answers it:

- *Description fidelity.* Does the description describe what the diff actually does? Findings here are claims the implementation does not support, behavior the diff adds that the description never mentions, and stated limitations that are no longer true.
- *Plan fidelity.* Walk the plan item by item — its goal, each entry in its file-by-file changes, its tests section, and the spec and documentation edits it called for — and confirm each is present in the diff. This is `resolve-conflicts.md` Step 5's walk, with the outcome recorded instead of repaired. An item the plan called for and the diff does not contain is a finding; so is an item implemented in a way the plan's design decisions rule out.
- *Functionality gaps.* Independent of the plan: what does this implementation not handle? Empty states, error paths, cancellation, concurrent use, the second call, the failure of a thing it depends on. A gap the plan explicitly deferred to its own "Out of scope" section is not a finding — the task file says so directly, because an out-of-scope item recorded as a gap is the most likely false positive this review produces.
- *Technical debt introduced.* Only what this diff adds, judged with `find-technical-debt.md`'s lens: the design gap behind the smell rather than the smell itself. Duplication the diff creates, a shape inconsistent with the surrounding code or with `ai/guidelines/`, a file pushed past the 200-line limit, an eroded type boundary, a marker comment left behind, risky logic arriving with no colocated test. Pre-existing debt the diff merely touches belongs in `technical-debt.md` and is out of this file's scope.
- *Security issues introduced.* `ai/tasks/hygiene/improve-security.md`'s *Never do on your own* list, read as a checklist of what to look for rather than what not to touch: input that reaches a filesystem path, a shell command, or a query without validation or sanitisation; a new `eslint-disable` or any other suppression of a security finding; a new or widened regex; an `eval`; any change to auth, crypto, or token handling, including `src/security.ts`; and a secret, token, or credential that is committed, logged, persisted, or put into an environment a less-trusted process can read. Beside those, the shapes this codebase in particular can regress: a widened sandbox carve-in or a loosened Seatbelt profile, a new network surface that binds beyond loopback or authenticates nothing, a new dependency, and a guard that fails open. That task's own reason for recording rather than fixing is this task's too, and worth restating in the task file: a wrong security fix still passes the tests, so nothing downstream would catch it.

**Step 4 — Write the findings.** Read `product/backlog/pull-request.md` if it exists and collect every entry from every section as the dedupe set, then drop every candidate the set already covers, even when worded differently. Do this before touching the file: if no candidate survives, nothing is created, nothing is written, and the run goes straight to the clean report in Step 7 — creating the file first and finding nothing second would leave an empty-headings diff that decision 7 exists to prevent. Otherwise create the file with the standard four sections when it is missing, and append each surviving finding to the end of `## development` in the five-part format below, leaving `## ready`, `## deferred`, and `## declined` and every existing entry byte-for-byte untouched. Then verify: `git status --porcelain` names `product/backlog/pull-request.md` and nothing else, and `git diff` shows only appended lines inside `## development`. Anything else on disk is reverted with `git checkout -- <file>` before Step 5.

The entry format is `find-technical-debt.md`'s, with `Existing Debt` renamed to `Existing Issue` and its scale renamed to issue severity. Nothing is indented and nothing is bolded; a blank line separates an entry's own parts and **two** blank lines separate one entry from the next:

```
* <one sentence, glanceable — names its dimension in plain words>

Existing Issue: <one sentence> Severity: <N>/10

Existing Risk: <N>/10 - <one sentence>

Proposal Risk: <N>/10 - <one sentence>

Proposal: <the detailed plan, with code references an agent can act on>
```

The task file restates what each part carries, since a task must stand alone rather than send its reader to another file mid-run: the summary bullet is the entry's identity line, written as a change rather than a complaint, scoped in words with no paths in it; `Existing Issue` names what is wrong today within the proposal's scope and ends with a trailing `Severity: <N>/10`; `Existing Risk` and `Proposal Risk` each lead with a score, then ` - `, then one sentence, and both are written to stand on their own for a reader who has not reached the `Proposal` yet; and `Proposal` is the long part, written for an agent that has not read the code, naming modules, files, and functions by path and never by line number, and sized as a single unit of work someone could finish in one sitting. Both 1–10 scales are reproduced as the same two tables `find-technical-debt.md` carries, with the severity table reworded from debt to issue. `Proposal Risk` must come in materially below `Existing Risk` or the finding is not worth recording, and the gap is never closed by scoring optimistically.

**Step 5 — Commit and push.** Skip entirely when Step 4 wrote nothing: there is no file and nothing to commit, and the report says the pull request reviewed clean. Otherwise `./scripts/run.mjs pr-commit` with the Conventional Commits subject `chore(backlog): record pull request review findings` — `chore(backlog)` because that is what every finding-recording task in this repo already uses (`chore(backlog): log new technical debt findings`, `chore(backlog): log react organization debt`, `chore(backlog): log complexity hotspots`) — and a body naming the pull request and the finding count. Then `./scripts/run.mjs pr-push-branch origin <branch>`, substituting the literal branch name since each Bash call is a fresh shell. A rejected push is handled the way `resolve-conflicts.md` Step 7 handles it: `git pull --rebase`, resolve preserving both sides, retry, at most three times, and never a bare force-push.

**Step 6 — Confirm the pull request is still open.** `gh pr view <number> --json state,headRefName,headRefOid,url`, confirming the state is `OPEN` and `headRefOid` matches `git rev-parse HEAD`. The task never merges.

**Step 7 — Report.** A fixed-shape report giving the pull request URL and number, the branch, the plan file used or "none in the PR — used the PR body", the count of findings per dimension, the count of candidates dropped as duplicates of existing entries, the commit sha and push result or "clean — nothing recorded", and the standing note that no build, lint, or test tooling was run so a red branch would not have been detected.

### 2. `product/backlog/pull-request.md` — created by the task at run time, not by this change

This plan adds no backlog file to this repository. The file is written by the task on whatever branch it is reviewing, with the same four-section skeleton `backlogFileContent` produces (`src/project-init.ts:23-25`). Its title line is `# pull-request`, matching the lowercase, filename-derived titles the other six backlog files carry.

### 3. No source, spec, configuration, or documentation change

`src/project-init.ts` keeps its six-name `BACKLOG_FILES` list (decision 5). `product/specs/task-picker.md` needs no edit because it describes a directory scan rather than a registry. `product/specs/cli.md`'s `janus init` paragraph, which enumerates the six seeded backlog files, stays accurate for the same reason. The default sync paths already cover the new file — `DEFAULT_SYNC_PATHS` is `['product/backlog/', 'product/plans/']` (`src/config.ts:58`) and a directory entry ending in `/` covers every file under it at any depth (`product/specs/application-config.md`) — so it syncs with no configuration change and none is proposed. `CLAUDE.md`'s Project Structure section names four of the six backlog files as examples rather than as an exhaustive list, so it stays accurate as written.

This plan depends on no other plan landing first, and its one file can land on its own.

## Tests

This change adds one markdown file under `ai/tasks/` and touches no TypeScript, so there is no unit test to write and none to update. `check-diff.mjs` classifies changed files and runs lint only for lintable extensions, `tsc` and tests only when a path starts with `src/` or `web/`; a lone `.md` file outside both matches none of those, so it assembles an empty tool list and exits 0 printing only a blank summary and a `total:` line. That is the correct result here, not a gap. Two existing tests are the relevant guard, and both must keep passing untouched: `src/project-init.test.ts:31` asserts the exact six-name backlog list and the four-section skeleton, which decision 5 deliberately leaves alone, and `src/sync-path-match.test.ts:14` pins that `product/backlog/`-prefixed paths match the default sync paths, which is what makes the new file sync without configuration.

The task's own correctness is established by executing it, which is what the Verification section covers. The behaviors worth exercising there, because they are the ones a reader of the task file could implement wrongly, are: a clean pull request producing no file and no commit; a second run appending only new findings and leaving triaged entries in `## deferred` alone; entries inherited from an earlier merged review surviving untouched and counting as duplicates (decision 6); a pull request carrying no plan file falling back to its description and commit subjects; and the commit containing exactly one file.

## Out of scope

- Posting anything to GitHub — no `gh pr comment`, no `gh pr review`, no inline annotations, no check run (decision 2).
- Editing the pull request's description or title, even when the review finds them wrong (decision 8).
- Fixing anything the review finds. Every finding is recorded as a proposal; executing one is a separate task against the entry.
- Running the project's build, lint, test, or quality tooling to gather evidence, including `check-diff` and `pr-check-gate` (decision 3). A pull request whose branch does not compile can still review clean here.
- Merging, closing, rebasing, or resolving conflicts on the pull request. `ai/tasks/workspace/resolve-conflicts.md` owns making it mergeable and `ai/tasks/workspace/merge-change-to-master.md` owns landing it.
- Adding `pull-request` to `BACKLOG_FILES` in `src/project-init.ts`, or to `product/specs/cli.md` and `CLAUDE.md` (decision 5).
- Recording pre-existing technical debt or security issues that the diff merely touches rather than introduces. Those belong to `find-technical-debt.md` and `technical-debt.md`.
- A task that consumes `product/backlog/pull-request.md` and executes its proposals. That is a natural follow-on, modeled on `resolve-technical-debt.md`, and it is a separate plan.
- Reviewing more than one pull request per run.
- Clearing, truncating, or per-pull-request scoping of `product/backlog/pull-request.md`, and any attempt to keep one pull request's findings from reaching the next branch (decision 6).
- Any per-dimension grouping, `Category:` line, or finding cap in the entry format (decisions 10 and 11).

## Verification

`./scripts/run.mjs check-diff` — expected to run no tools and exit 0, printing only a blank summary line and `total: <n>ms`, since the change is one markdown file outside `src/` and `web/`. Anything else means a file was touched that this plan does not intend to touch.

Manual, the main path: open the task picker with `Ctrl+A` and confirm `pull-request-review` appears in the Project section's file rows (not inside a subdirectory), then run `execute ./ai/tasks/pull-request-review.md <number>` against a real open pull request that carries a plan. Confirm the branch is checked out and its dependencies installed, that `product/backlog/pull-request.md` is created with the four standard sections, that each entry carries all five parts with `Existing Issue` rather than `Existing Debt` and all three scores, that two blank lines separate entries, and that the commit pushed to the head branch contains that one file and no `Co-Authored-By:` trailer. Confirm on GitHub that the pull request is still open and carries no new comment or review.

Manual, the re-run path: run it a second time against the same pull request with no intervening change and confirm it appends nothing and makes no commit. Then move one entry by hand into `## deferred`, run it a third time, and confirm that entry is neither duplicated back into `## development` nor disturbed.

Manual, the inherited-entries path: rather than merging a review to produce them, hand-write a `product/backlog/pull-request.md` on an unreviewed pull request's branch carrying two entries — one describing something that pull request genuinely does wrong, one unrelated — and run the task against it. Confirm both are still present and unmodified, that the matching finding is dropped as a duplicate, and that anything new is appended beneath them (decision 6). This is the same code path a merged review's inherited entries take, without the setup.

Manual, the clean path: run it against a small pull request with an accurate description and no plan — a documentation or dependency bump — and confirm it creates no file, makes no commit, and reports the pull request as reviewed clean with the fallback to the description and commit subjects named in the report.

Manual, the refusal paths: run it against a merged or closed pull request number and confirm it stops without checking anything out; run it with no argument on `master` with more than one pull request open and confirm it lists the candidates and stops.
