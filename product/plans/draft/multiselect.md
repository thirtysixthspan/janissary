# Multiselect

**Complexity: 5/10** — one optional field on `EditorState` and two small pure modules, but multi-caret is a core state-model change every edit, motion, render and mouse path has an opinion about, landing alongside a breaking bump of the editor-plugin contract that all three bundled plugins move to at once.

The editor tab has exactly one caret and one selection. `EditorState` carries a single `cursor` and a single `anchor` (`web/src/editor/model.ts:6`), `lineSelection` computes one highlighted span per line (`web/src/editor/render.tsx:9`), and `Cmd+D` is unbound at every level — `metaAction` has no `d` case (`web/src/editor/keys.ts:33`) and neither does any window-level table. Renaming three occurrences of an identifier in a file means editing each one by hand, or using the find overlay, which is fuzzy, case-insensitive and line-oriented (`web/src/editor/useEditorFind.ts:29`) — it jumps the caret to a line, it does not select an occurrence.

This plan adds `Cmd+D` in the VS Code sense: it selects the next exact occurrence of the current selection *in addition to* the one already selected, and typing, deleting, or pasting then applies at every selection at once. It ships as **`multiselect`**, the third bundled editor plugin, and to make that possible the editor-plugin contract grows from one selection to many: a command receives the whole selection set and answers with a new one. The plugin owns every rule about which occurrences become selections — `Cmd+D` to add the next, `Cmd+U` to drop the last added, `Escape` to collapse back to one. The core editor owns the selection set as state, its rendering, and what typing and cursor movement do when there is more than one of them, because a plugin never sees a printable keystroke or an arrow key.

The two existing bundled plugins move to the new answer shape in the same change. This is a hard version bump, not a compatibility layer: there are three plugins, all in this repository, and a permanent legacy path for a family with no third-party members would outlive its reason to exist.

## Design decisions

**`Cmd+D` adds a selection; it does not move the existing one.** With `foo` selected, the first press selects the next `foo` as well, the second press selects the one after that, and typing replaces all three. A find-next that merely moved the single selection along would be a smaller change and was considered and rejected: it is not what the feature asks for, and the user's own comparison point is VS Code, where the value is the simultaneous edit rather than the navigation.

**With nothing selected, the first `Cmd+D` expands to the word under the caret.** It reuses `wordRangeAt` (`web/src/editor/model.ts:128`), the same run-of-same-class-characters rule double-click already uses, so `Cmd+D` and a double-click always agree about where a word starts and ends. The press after that starts finding occurrences of that word. This is the only case where a press changes the selection without adding to the set.

**Matching is exact and case-sensitive, over the whole document.** The selected text is matched as a literal substring: with `foo` selected, `Foo` is not an occurrence and `foobar` is. No regex, no case folding, no whole-word constraint — including for a selection the plugin itself produced by word expansion, which matches VS Code's plain `Cmd+D` closely enough and avoids a hidden mode where the same selection behaves differently depending on how it came to exist. The fuzzy, case-insensitive matcher behind `Cmd+F` (`web/src/fuzzy-match.ts`, via `useEditorFind.ts:29`) is deliberately not reused: it scores whole lines against a subsequence and cannot answer "where is the next literal `foo`".

**A multi-line selection is a valid search term.** The plugin matches against the document as one string with `\n` between lines and converts absolute offsets back to `Pos`, so a selected two-line block finds its next two-line occurrence with no special case. This falls out of matching on joined text rather than per line, which is why the search works that way.

**Search wraps around the end of the buffer.** The next occurrence is the first match after the most recently added selection; past the last line the search continues from the top. Matches already covered by an existing selection are skipped, so wrapping cannot re-add one. When every occurrence in the buffer is already selected, the press is a silent no-op — the handler answers `null`, which the family already defines as "nothing changed, no undo step, no message" (`web/src/editor/plugins/api.ts:81`).

**Typing, `Backspace`, `Delete` and paste apply at every selection, as one undo step.** Each selection contributes one range replacement — the selection itself when there is one, and otherwise the zero-width point at the caret for typing or the character the single-caret rule would have removed for a delete (`web/src/editor/model.ts:82` `deleteBackward`, `:90` `deleteForward`) — and all of them are applied in one pass (see Proposed changes). The whole multi-edit is one entry in the undo buffer, so one `Cmd+Z` restores all of them; a run of typed characters still coalesces into a single group because `UndoBuffer` snapshots whole states and does not care how many ranges changed (`web/src/editor/undo.ts:11`).

**Arrow keys, `Home`/`End` and shift-extension move every caret independently and keep the set alive.** Each selection is run through the existing `motion.ts` transform on a one-selection view of the state and the results are collected, so no motion rule is reimplemented and none of the wrapped-line behavior is duplicated. Two carets that land on the same position merge into one — otherwise a set converging at a line end would silently start applying the same edit twice.

**Only the primary caret scrolls into view.** The most recently added selection is the primary; it keeps the `caretRef` that `EditorTab`'s scroll effects follow (`web/src/editor/EditorTab.tsx:39` `const caretRef = useRef`, used at `:72` and `:81` `caretRef.current?.scrollIntoView`), and the other carets render a bar and nothing else. Scrolling to every caret at once is impossible and scrolling to an arbitrary one is worse than scrolling to the one the user just created. For the same reason `editor-row-current` (`web/src/editor/render.tsx:76` `isCurrent && 'editor-row-current'`) keeps following the primary caret's line only — several highlighted current-rows would read as noise, not as information.

**Vertical movement with several carets is logical, not visual.** Single-caret ↑/↓ first asks `resolveVertical` for a wrapped-line-aware target (`web/src/editor/applyKeyAction.ts:33` `const target = resolveVertical?.(action.dir)`), which measures the DOM through `caretRef` — and there is exactly one such ref, so it can only ever answer for the primary. With a set active, ↑/↓ therefore use `moveCursor` for every selection including the primary, i.e. logical-line movement. On a file with no wrapped lines this is indistinguishable; on one with wrapped lines a multi-caret ↑ steps a whole logical line where a single caret would step a visual row. That is the accepted cost of not measuring N carets in the DOM on every arrow press.

**Each selection carries its own goal column.** `goalCol` exists so vertical movement across short lines returns to the column the caret started from (`web/src/editor/model.ts:12` `goalCol?: number`). Each record in the set carries its own, set and cleared by the same rules; sharing the primary's would drag every caret to one column the first time the set crossed a short line.

**Undo restores the selection set along with the text.** `UndoBuffer` snapshots whole `EditorState` values, so the set is part of what is recorded and restored with no extra bookkeeping — undoing a multi-caret edit puts the carets back where they were, and the coalescing rules are unchanged.

**`Escape`, a click, `Cmd+F`, a save, and an external reload all collapse back to one caret.** `Escape` and `Cmd+U` are the plugin's (below); the other four are the core's, and three of them come free. Every mouse path already funnels through `setSelection` (`web/src/editor/useEditorMouse.ts:22`, `:36`, `:89`, `:94`), so clearing the set inside `setSelection` covers click, double-click, triple-click, gutter click and drag in one place. An external-change reload calls `api.load` → `fromText` (`web/src/editor/useEditorWatchReload.ts:33`), which builds a fresh state that has no set to begin with. `Cmd+F` and `Cmd+S` need one explicit collapse each, in `EditorTab`'s find branch and in `applyKeyAction`'s save branch — neither currently writes state on that path. Switching away from the editor tab is deliberately *not* a collapse: the tab stays mounted and its buffer state is untouched by a tab switch, so a set survives one exactly as the cursor and selection already do. Only the find overlay closes on `active` going false (`web/src/editor/useEditorFind.ts:42`), and that is the overlay's own rule, not the buffer's.

**The plugin API grows from one selection to many; the version goes to 2 and all three plugins move.** `EditorPluginRequest.selection` becomes `selections`, `EditorPluginResult.selection` becomes `selections`, and `EDITOR_PLUGIN_API_VERSION` becomes `2`. `commenting` and `indenting` answer with a one-element list and are otherwise untouched. Keeping a single-selection field alongside the list would mean two ways to say the same thing and a rule about which wins, in a family whose every member ships in this build; a hard bump costs two small edits now and removes that question permanently.

**Selections are ordered by creation, not by position.** The most recently added is last, and it is the primary — the one `Cmd+D` searches forward from, the one `Escape` keeps, and the one `Cmd+U` drops. Document order is derivable by sorting and is what rendering uses; creation order is not derivable and is what the feature's behavior actually depends on, because wrap-around routinely makes the newest selection the earliest one in the file.

**An answer's selection set is validated as a whole, and overlapping selections are refused.** `applyPluginResult` already refuses an out-of-range position or two overlapping edits and disables the plugin rather than clamping (`web/src/editor/plugins/apply-edits.ts:63`). That rule extends to the list: every selection is range-checked against the edited lines, and two selections sharing any interior are refused, because a multi-caret edit derived from overlapping selections would apply two conflicting replacements to the same text. An omitted `selections` means "leave the set as it is", as the optional field means today; an explicit empty list is refused, since a buffer always has at least one caret.

**The editor hands `Escape` to plugins, but only while more than one selection is active.** `yieldsToPlugins` (`web/src/editor/keys.ts:96`) already exists for exactly this — the editor stating which of its own chords it is willing to delegate, in the file the binding table lives in. It gains `Escape` under that one condition. Its second parameter becomes a small context record instead of the current `selectionSpansLines` boolean, which is the upgrade the indenting plan named when it introduced the boolean. With one selection, `Escape` is the core's as it always was.

**`collapseSelection` clears the set, so a disabled plugin cannot strand carets.** If `multiselect` fails and is disabled mid-session, its chords stop matching (`web/src/editor/plugins/host.ts:103`) and `Escape` falls through to the core action — which must then drop the extra selections, not just the primary's anchor. This is the same degradation `Tab` already has: a broken plugin leaves the chord doing the editor's own reasonable thing rather than doing nothing.

**`Cmd+D` and `Cmd+U` are browser chords, and the existing synchronous claim handles both.** `Cmd+D` bookmarks the page and `Cmd+U` is a view-source chord on some platforms. `useEditorPlugins` answers whether a plugin claims a chord synchronously so the caller can `preventDefault()` before the handler runs (`web/src/editor/plugins/useEditorPlugins.ts:97`), which is the same property that makes `Cmd+[` safe today. Nothing new is needed; it is called out because losing it would navigate away from an unsaved buffer.

**Nothing visible reports how many selections are active.** The highlights are the feedback. No count in the metadata row, and no distinct styling for the primary — the editor shows no counter for anything else, and a caret the user just created by pressing a key does not need to be labelled.

**The plugin imports `wordRangeAt` from the core model rather than defining its own.** It is a pure exported function, `api.ts` already imports `Pos` from the same module, and two independent word rules would let double-click and `Cmd+D` disagree about what a word is on the same character.

**Multi-caret is buffer-only; the agent query line is unaffected with no new code.** `handleSuggestKeyDown` runs before the key table and swallows keys on the query line and under a pending suggestion (`web/src/editor/EditorTab.tsx:128` `if (handleSuggestKeyDown(...)) return;`), so a plugin chord is already inert in both states, exactly as `product/specs/editor-tab.md` states for the existing plugins. `Escape` in particular is consumed there (`web/src/editor/handleSuggestKeyDown.ts:79` `if (e.key === 'Escape') { ... suggest.closeQueryLine(); return true; }`), so handing `Escape` to plugins cannot shadow closing the query line. The find overlay owns its own `Escape` in its focused input (`web/src/editor/EditorFind.tsx:56`), which the buffer's `onKeyDown` never sees, so the overlay's close behavior is likewise untouched.

**Nothing reaches the server.** No protocol message, no persistence, no server module — the only existing server touchpoint stays what it already is, the `editorPluginFailed` report a broken plugin sends (`src/protocol/editor.ts:39`). The whole feature is client-side, as `product/specs/editor-plugins.md` requires of the family.

## Proposed changes

**Selection set in the core model.** `EditorState` (`web/src/editor/model.ts`) gains one optional field — a readonly list of additional selections, each an anchor/cursor pair like the primary, in creation order with the primary conceptually last. The existing `cursor` and `anchor` stay exactly as they are and remain the primary selection, so every module that reads them keeps working untouched; only the paths that must know about several carets change. `fromText` starts with an empty list, `setSelection` clears it (which is what collapses the set on every mouse gesture), and `collapseSelection` clears it as well as dropping the anchor.

**The set's accessors go in `model.ts`, not a module of their own.** Reading the full set as a list with the primary last, replacing it, collapsing to the primary, merging selections that have converged on the same range, and sorting into document order are all a handful of lines each over the state `model.ts` already owns — "the editor's document/cursor/selection state and its pure editing transitions" is its stated job (`web/src/editor/model.ts:1`), and they belong beside `setSelection` and `collapseSelection`, which they are the plural of. At 105 counted lines the file has room for them.

**Two new pure core modules.**

- `web/src/editor/offsets.ts` — `Pos`↔absolute-offset conversion over the joined document, and nothing else. Both the multi-caret edit fold and the plugin's occurrence search need it, so it is written once, in core, and the plugin imports it — the dependency runs plugins → core, as `plugins/api.ts:6` (`import type { Pos } from '../model'`) already establishes. Joining is `toText` (`web/src/editor/model.ts:23` `s.lines.join('\n')`), not a second joiner.
- `web/src/editor/multi-caret.ts` — the two transforms. **Movement** runs each selection through the requested `motion.ts` transform on a one-selection view of the state and merges what converges, so no motion rule is restated and `goalCol` keeps working per selection for free, because the one-selection view carries the field `motion.ts` already reads and writes. **Editing** converts every selection to an offset pair against the joined text, sorts them, and folds left to right — appending the text between one selection and the next, then the replacement, and taking each caret's new offset from the output as it goes. One pass, no coordinate rebasing, and the answer converts back through `offsets.ts`. This is deliberately *not* the back-to-front range-replacement shape of `applyPluginResult` (`web/src/editor/plugins/apply-edits.ts:63`): that one applies edits whose final caret positions the plugin supplied, whereas here the positions are what must be computed, and computing them back-to-front means rebasing every already-computed position by each later edit's delta. `plugins/apply-edits.ts` is therefore left exactly as it is, apart from extending its validation to a list.

**`applyKeyAction.ts` delegates when the set is non-empty.** Its `applyMove` and `applyEdit` branches gain a single guard at the top: with extra selections present, the action goes to `multi-caret.ts` and the result is recorded as one undo entry with the same `EditKind` it would have had (`web/src/editor/applyKeyAction.ts:82` `const edit: Edit = (before, next, kind) => ...`); with none, the existing single-selection path runs unchanged, so the ephemeral query-line surface built on the same `EditSurface` (`web/src/editor/useEditorSuggest.ts`) is untouched — its state never has a set. The `save` branch (`:78`) collapses the set before calling `surface.onSave()`.

**Key table.** `keys.ts` gains no new `KeyAction` variant — multi-caret typing and movement reuse the existing actions. `yieldsToPlugins` takes a context record carrying whether the selection spans lines and whether more than one selection is active, and answers true for `Escape` under the second flag. `claimedByCore` (`plugins/chords.ts`) passes the most permissive context, as it does today, so `Escape` becomes declarable. `EditorTab.tsx` computes the second flag from the state it already destructures and passes it through; its find branch collapses the set before opening the overlay.

**Plugin contract, version 2.** In `plugins/api.ts`: `EDITOR_PLUGIN_API_VERSION` becomes `2`; `EditorPluginRequest.selection` becomes `selections`, a readonly list of `EditorSelection` in creation order, never empty; `EditorPluginResult.selection` becomes `selections`, an optional readonly list. The header comment's statement of the extension point is restated in terms of a selection set. `plugins/useEditorPlugins.ts` builds the request from the full set, and `plugins/apply-edits.ts` validates every returned selection against the edited lines, refuses an explicit empty list and refuses two selections that overlap, applying the same whole-answer refusal as today.

**Bundled `multiselect` plugin, `web/src/editor/plugins/multiselect/`.** Declared in `registry.ts` with three bindings: `select-next-occurrence` on `Cmd+D`, the only one that declares `needs: 'buffer'`, and `drop-last-selection` on `Cmd+U` and `collapse-selections` on `Escape`, both `needs: 'selection'` — they read nothing but the selection set, so copying the whole document for them would be waste the declaration is supposed to make visible. Its `index.ts` is a thin handler dispatching the three commands, using the core `offsets.ts` to convert between positions and offsets rather than carrying its own. One pure module sits beside it, mirroring how `indenting` keeps its transform out of `index.ts` (`web/src/editor/plugins/indenting/shift.ts`): occurrence search — given the document text, a term, a starting offset and the ranges already taken, it answers the next literal match, wrapping past the end and skipping taken ranges, or nothing when there is none. Searching is `String.prototype.indexOf` over the joined text, never a constructed regular expression: the term is arbitrary user-selected text, so a regex would both need escaping and trip `security/detect-unsafe-regex` from `eslint.config.mjs`. `select-next-occurrence` with a single empty selection instead answers with the word range under the caret; `drop-last-selection` answers with the set minus its last element, or nothing when there is only one; `collapse-selections` answers with the primary alone. None of the three ever returns an edit — this plugin only moves selections, which the contract already allows since `edits` may be empty.

**Rendering.** `lineSelection`, `selFrom`/`selTo`, `caretCol` and `caretRef` all keep their current meaning and describe the primary selection only, so every line in a file with no extra selections — and every line in every file today — renders through exactly the code path it does now. Two props are added for the extras: the other selected spans on the line, and the other caret columns on it. Both are compact string encodings rather than arrays, and both are the empty string in the overwhelmingly common case, because `EditorLine` is `React.memo`'d on primitive props (`render.tsx:74`) and a freshly allocated array per line per render would defeat that comparison on every keystroke in a large file. `contentSegments` folds the extra span and caret bounds into the same sorted bounds list it already builds for selection, caret and token boundaries (`web/src/editor/render.tsx:51`–`:54`), so no nesting or new markup is introduced; only the primary caret receives `caretRef`. Decoding the two encoded props into bounds happens in a small helper beside `contentSegments` rather than inside its loop, which already carries a token lookup and two conditionals and is the one function here at risk of tripping `sonarjs/cognitive-complexity`. No CSS changes — every selection uses the existing `editor-sel` class and every caret the existing `editor-caret`. The ceiling this accepts: two encoded strings is the cheapest thing that keeps the existing memo contract, and if a third per-line list ever needs passing, the upgrade is a custom `React.memo` comparator on `EditorLine`, not a third encoded string.

**The other two plugins.** `commenting/index.ts` and `indenting/index.ts` answer with a one-element `selections` list and declare `apiVersion: 2` via the shared constant; their transform modules do not change.

**Landing order — three steps, each green on its own.** The core and the contract are independent, so they land separately rather than as one commit that is only typecheck-clean at the end:

1. The selection set and its accessors in `model.ts`, the two new core modules, the `applyKeyAction` delegation, and rendering. Nothing creates a set yet, so every existing test still describes the whole observable behavior and the new modules are covered by their own unit tests.
2. The version-2 contract: `api.ts`, `apply-edits.ts`, `useEditorPlugins.ts`, and the two existing plugins moved to the `selections` answer in the same step — a half-migrated step does not typecheck, so these are one unit.
3. The `multiselect` plugin, its registry entry, the `Escape` yield, and the collapse points in `EditorTab.tsx` and `applyKeyAction.ts`.

**File-size headroom, checked before starting.** `web/src/editor/EditorTab.tsx` counts 171 lines against the 200-line `max-lines` limit (blanks and comments excluded), so step 3's additions there — one context field, one collapse call in the find branch — must stay small; if that file needs more than a handful of lines, extract the keydown handler into its own module rather than compacting anything. `render.tsx` (70), `applyKeyAction.ts` (69) and `model.ts` (105, before the set accessors) have room. The two new core modules are small and single-purpose; if `multi-caret.ts` grows past the limit, the split to make is movement from editing, not compaction.

**Specs and documentation.** `product/specs/editor-plugins.md` gains the selection-set request and answer, the `Escape` handover condition alongside the existing `Tab`/`Shift+Tab` ones, the refusal rules for a selection set, and a bundled-`multiselect` section. `product/specs/editor-tab.md` gains a "Multiple selections" section describing `Cmd+D`, word expansion, wrap-around, what edits and movement do with several carets, and every way the set collapses; its plugin section gains the third plugin. `documentation/developer-documentation/editor-plugins.md` follows the contract change.

## Out of scope

- `Cmd+Shift+L` (select all occurrences in the buffer at once).
- `Cmd+K Cmd+D` (skip this occurrence and take the next instead) — it would also need a two-key chord sequence the editor does not have.
- `Alt`/`Option`+click to add a caret at an arbitrary position, and any other mouse gesture that creates a selection rather than collapsing the set.
- Column / rectangular selection.
- Any visible count or distinct styling for the primary selection.
- Case-insensitive or whole-word matching, and any option surface for choosing between them.
- Multi-caret on the agent query line.
- Selections surviving a reload or a save — both collapse the set, and restoring one afterwards is not attempted.
- Highlighting every other match of the current selection in the buffer, and any integration with the `Cmd+F` overlay.

## Open questions
