# Survive laptop sleep and resume

**Complexity: 7/10** — the remote half drives the number: a new protocol surface (reattach request/answer) and a far-side peer that has to detach from the ssh stdio it currently dies with and be findable again. The local half is small — two new modules, edits to five existing files, and browser events doing the resume detection.

Backlog text: *"janissary must be able to run on a laptop and survive the latop going to sleep and then resuming."*

Today a laptop sleeping is very close to a quit. `src/index.ts:131`–`:139` (`ws.on('close', …)`) exits the whole process one second after its last client socket closes, so a WebSocket the sleep tears down takes every tab, agent, harness, and shell with it. The web client has no reconnect at all — `JanusClient`'s constructor at `web/src/ws.ts:31`–`:37` opens exactly one socket and, on `close`, calls `drainPending()` and stops. And `product/specs/remote-server.md` states plainly that when an ssh session drops, every tab and navigator using it closes, with "no reconnect, no resume, and no reattach."

This feature makes a sleep survivable end to end. The local server stops treating a dropped socket as a reason to exit; the window reconnects itself and says so in a small indicator while it does; remote sessions outlive the ssh channel that carried them and are reattached to on the far side; and a scheduled command that came due while the machine was asleep runs once on wake and raises a notification saying it ran late. What the user does is nothing at all — they close the lid and open it again, and the session they left is the session they get back.

## Design decisions

**A dropped socket is never a reason to exit — but an idle session still is.** The grace window in `src/index.ts:23` (`CLIENT_RECONNECT_GRACE_MS`) stays, and so does the process exit at the end of it. What changes is that sleep does not count against it: the resume signal below restarts the countdown from the moment of wake rather than letting a night of sleep burn through it. A machine that slept for eight hours and woke up gets the same grace a machine that never slept gets.

**Sleep is detected at both ends, independently.** The server runs a wall-clock watchdog: a periodic tick that compares elapsed wall-clock against the interval it expected, and treats a jump well beyond that interval as "the machine was asleep for this long." The client detects its own resume separately, but hand-rolls nothing for it — the browser already fires `visibilitychange` and `online` on wake, and those (plus the socket's own `close`) are what prompt an immediate reconnect instead of waiting out the next backoff tick. Two mechanisms, deliberately: the server's drives the grace window, the remote reattach, and the late-schedule notification; the client's exists purely to make recovery feel immediate.

*Ceiling on that simplification:* a wake where the window was continuously visible and the network never dropped may fire neither event, and recovery then falls back to the backoff, which reconnects within its ceiling rather than instantly. If that proves common in practice, the upgrade is a timer-drift detector alongside the platform events — worth adding only once the platform events are shown to be insufficient, not before.

**The window reconnects itself, quietly.** The reconnect is not a modal, an overlay, or a dimmed screen. It is a small status indicator — the size and tone of the agent bar's `queue` announcement at `web/src/agent-tabs/command-input/CommandInput.tsx:112` (`label={busy ? 'queue' : undefined}`) — so a reconnect that resolves in under a second is barely noticed and a longer one is still legible. The rest of the UI is left alone.

**The indicator lives in the app shell, not in a command bar.** `CommandBarShell`'s `label` slot is the closest existing precedent for the *look*, but it is the wrong host: only agent tabs and the conversations composer render a command bar (`web/src/agent-tabs/command-input/CommandInput.tsx`, `web/src/plugins/conversations/ConversationComposer.tsx`), so a harness, ssh, editor, or file-navigator tab would show no indicator at all. Connection state is global, so it renders from `AppShell` (`web/src/AppShell.tsx:30`–`:46`, the root layout that is always mounted) into the center column's chrome. With one consumer it colocates beside `AppShell.tsx` rather than going into `web/src/shared/` — `ai/guidelines/react-code-organization.md` §2 promotes to shared on the second consumer, not the first.

**Reconnection never gives up.** Attempts continue with bounded backoff, indefinitely. There is no attempt cap, no self-closing window, and no forced reload. What escalates is the wording: the indicator moves from `Reconnecting…` to `Cannot reach session` once attempts have been failing long enough that the user should know this is not a blip. If the session really is gone — the machine rebooted, the process was killed — the window stays open and reachable rather than closing itself out from under someone who never asked it to.

**The exact wording is fixed here.** The indicator reads `Reconnecting…` while the socket is down, escalates to `Cannot reach session`, and shows `Reconnected` briefly on success before clearing. The late-schedule notification line reads `<command> ran <duration> late (system was asleep)`.

**Reconnect resyncs from state; it does not replay the terminal.** Local harnesses and agents keep running while the window is disconnected, and their PTY output during that window is not buffered for later delivery. On reconnect the client re-runs the `init` it already sends on every socket open (`web/src/ws.ts:35`) and re-renders from the fresh state snapshot, so the tab list, busy flags, transcripts, and selections are all correct — and the terminal shows a gap where the missing bytes were. Buying a continuous terminal would mean a per-PTY server-side buffer with a cap, an overflow rule, and a replay path, for output nobody was watching.

**Nothing is resent.** The rule in `product/specs/websocket-rpc.md` ("Requests outstanding when the connection ends") stands unchanged, and `drainPending()` at `web/src/ws.ts:57`–`:61` already implements it: a request in flight when the connection ends fails as a connection failure, and the reconnect does not replay it. A lost reply does not establish that the server never carried the request out. Nor is user input held across the gap — the existing guards (`send` at `web/src/ws.ts:134`, `request` at `:144`, `saveFile` at `:173`) already drop or refuse work while the socket is not `OPEN`, and that behavior is kept exactly as it is rather than growing a queue that would deliver a burst of stale keystrokes into a live terminal.

**Remote sessions outlive their transport, and the reconnect reattaches to them.** A remote (`on <address>`) tab's far side is a peer janissary installation, so the same rule the local server gets applies there: losing the ssh channel is not the end of the session. The peer keeps its workspace clone and its running processes and waits to be reattached to, and the reconnect re-establishes the ssh transport and rebinds the existing tabs to that still-live peer session — rather than wrapping remote work in tmux or a detached-process-plus-logfile scheme, which would add an external dependency or a second delivery path for the same frames. This reverses `product/specs/remote-server.md`'s "no reconnect, no resume, and no reattach" for remote tabs, and that spec text has to be rewritten as part of the work.

**A scheduled command that came due while asleep runs once, and notifies.** The tick at `src/schedule/manager.ts:46` already compares `Date.now()` against each entry's `nextRun` (`fireDue`, `:147`–`:156`), so an overdue entry fires once on wake and a recurring one recomputes its next run from now via `computeNextRun(e, new Date())` — that behavior is kept exactly as is. What is added is a notification for it, rather than a marker buried in the transcript: a burst of commands firing seconds after the lid opens should be explicable from the notification feed without hunting through tabs.

## Proposed changes

Module placement note: new server modules take root-level `src/` filenames, matching how single-purpose services already sit there (`src/instance-lock.ts`, `src/window-resizer.ts`, `src/state-dirs.ts`). Notably **not** `src/connection/` — that directory is already the `connection` *command* feature (`src/connection/close.ts`, `list.ts`, `manager.ts`) and reusing the name would be actively misleading. New `src/` imports carry the `.js` extension per the NodeNext rule in `CLAUDE.md`; new `web/src/` relative imports stay extensionless.

**A resume signal on the bus.** A new server module `src/resume-watch.ts` exports a small watch object with start and stop, holding a periodic tick and the wall-clock instant it last ran. When the observed gap exceeds the tick interval by more than a threshold, it emits a resume event carrying the slept duration. `src/bus.ts` gains a `system` channel — added to the `BusChannels` type at `src/bus.ts:106`–`:109` — whose event union starts with a single `resumed` member carrying that duration. It is its own channel rather than a reason carried on `state: dirty` for exactly the reason `src/bus.ts:101`–`:103` gives for the `schedules` channel: `dirty` fires on essentially every mutation, and this is a named, low-frequency signal. Everything that has to react to sleep subscribes here; nothing else learns how sleep is detected. This module lands first: the grace timer, the remote reattach, and the late-schedule notification all consume its signal.

**The grace timer stops counting sleep, in place.** The exit-timer logic stays where it is — `exitTimer` at `src/index.ts:52`, cleared on connect at `:110`–`:114`, armed on last-close at `:131`–`:139`. It gains a subscription to the resume signal that, when a countdown is already armed, clears it and re-arms it for the full grace from the moment of wake. That is a handful of lines on top of `src/index.ts`'s ~140 counted lines against the 200-line limit, so it needs no extraction: a separate grace module would be a file, an interface, and a test file for arithmetic that is one `clearTimeout` and one `setTimeout`.

**A reconnecting client, in `ws.ts`.** `JanusClient`'s socket-opening lines move from the constructor body (`web/src/ws.ts:31`–`:37`) into a private connect step the constructor and the reconnect path both call; the socket field becomes reassignable. A `close` that was not caused by `dispose` drains pending requests as it does now, publishes a connection-status change, and schedules a reopen against the policy module below; `dispose` sets a disposed flag first so a deliberate teardown never reopens. Because listeners, pty handlers, and state collectors already live on the client rather than the socket (`web/src/ws.ts:205`–`:215`), they survive the swap untouched, and the `init` the open handler already sends (`:35`) is what resyncs state. This lands the file at roughly 175 of its 200 counted lines; if it does cross, the pre-decided extraction is the socket lifecycle (connect, reopen scheduling, and the close handler) into `web/src/ws-connection.ts`, leaving the RPC surface behind.

The client gains a connection-status subscription in the same shape as `onState`/`onPtyExit`/`onLayout`: register a listener, get an unsubscribe back. `web/src/App.test.tsx`'s mocked `JanusClient` needs the new method, or every app render throws — the same trap `client-state-collectors` hit.

**Reconnect policy as a pure module.** `web/src/reconnect-policy.ts` maps an attempt count to a delay (bounded exponential with a ceiling, never terminating) and to a display phase — reconnecting, escalated, or connected. Keeping it pure means the backoff schedule and the escalation threshold are testable without a socket, a timer, or a render.

**Client-side resume detection, from platform events only.** `web/src/client-page-lifecycle.ts` already owns this page's lifecycle listeners and returns a teardown that removes all of them; it gains `visibilitychange` and `online` beside the existing `pagehide`/`pageshow` pair. Either one firing while the socket is down forces an immediate reconnect attempt and resets the backoff. There is no drift-detection module: the browser already publishes the events that fire on wake, and the socket's own `close` covers the case where the OS tore the connection down.

**The indicator.** `web/src/useConnectionStatus.ts` (root-level, beside the other `use*.ts` hooks) subscribes to the client and exposes the current phase plus the transient post-success state — the hook-bridges-a-service-subscription seam of `ai/guidelines/react-code-organization.md` §6/§7. `web/src/ConnectionStatusLabel.tsx`, colocated beside `AppShell.tsx`, is presentational: it renders the fixed wording for the phase it is handed, or nothing. `AppShell` calls the hook and renders it. Both sit outside `web/src/`'s feature directories — `clientFeatureDirectories` at `eslint.config.mjs:12`–`:22` is an explicit list a new feature directory would have to be added to — and match where `client-page-lifecycle.ts` and `client-state-collectors.ts` already live.

**Late scheduled commands notify.** `src/notifications.ts` gains a `schedule-late` member of `NotificationEventType` (`:24`–`:41`) and an entry in `EXPLICIT_EVENTS` (`:77`–`:90`) — no config toggle, and not focus-suppressed, since a command that fired late is worth reporting even in the tab being watched. `notificationText` (`:127`–`:147`) is an exhaustive switch with no `default` arm, so it will not compile until the new event has a case: that case returns `detail ?? ''`, the same as `file-operation` and `open-unsupported`, with the schedule manager composing the whole line. `src/schedule/manager.ts`'s `fireDue` already has both `now` and the entry's `nextRun`; where the lateness exceeds the same threshold `src/resume-watch.ts` uses, it calls `notify(this.managers, 'schedule-late', tab.label, …)` with the line `<command> ran <duration> late (system was asleep)`. The human-readable duration comes from a formatting helper added to `src/schedule/display.ts` beside `fmtNextRun` — the schedule module's string-formatting home, not `src/schedule/time.ts`, which computes next-run instants. Firing behavior itself is unchanged.

**The remote peer outlives its channel.** `src/remote/serve.ts:27`–`:30` currently treats SIGHUP — what arrives when the ssh channel drops — as equivalent to a kill, tearing down the session and its workspace clone. SIGHUP has to stop meaning that: the peer detaches from the dying stdio, keeps its workspace and its running processes, and waits a bounded time to be reattached to, while SIGTERM and SIGINT keep their current meaning so an explicit kill still cleans up. A never-reattached peer expires on its own after that bounded window, so a workspace clone is never left behind indefinitely. `src/remote/serve.ts` counts about 157 lines, so the detach-and-wait machinery goes in a new `src/remote/serve-detach.ts`, following the `serve-*.ts` split the directory already uses.

Reattachment needs a rendezvous the next ssh connection can find, and the codebase already has the pattern: `src/instance-lock.ts` records a pid in a file under `.janissary/` and answers liveness with the exported `isPidAlive` (`src/instance-lock.ts:4`). The detached peer does the same shape — a record under the far side's `.janissary/` naming its session id and pid — and reuses `isPidAlive` rather than inventing a second liveness check. It deliberately does not take the instance lock itself; `src/remote/serve.ts:18` states that a remote peer holds no lock, and that stays true.

The reattaching `janus remote-serve` invocation reaches the detached peer over a unix domain socket at a path derived from that session id, using `node:net` — stdlib, no dependency, and the same frames on both sides. It pumps frames between its own stdio and that socket, so `src/remote/protocol.ts` gains only two members of the frame union: a reattach request carrying the prior session id, and the peer's accept or refuse answer. Both go through the existing frame decode/encode path rather than a side channel.

**The remote client rebinds instead of closing.** `channelClosed` at `src/remote/manager.ts:211`–`:228` currently marks the entry closed, clears the remote file cache, empties the label and handler maps, and calls each `onClosed()` — which closes the tab (`:188`–`:192`). Channel death instead marks the channel as reconnecting and leaves its tabs, labels, handlers, and cached workspace files in place; the manager re-runs the ssh connect for the same destination and sends the reattach request. An accepted reattach rebinds the existing tabs and navigators to the live peer session. A refused one runs the teardown that exists today, including the `Remote connection to <host> ended.` notice already raised at `:218`. `clearRemoteFileCacheForWorkspace` (`:220`) must run only on that terminal path — clearing it on a channel that is about to be reattached would discard a cache the reattached session still matches. `src/remote/manager.ts` counts about 168 lines, so the reattach state machine goes in a new `src/remote/reattach.ts` rather than growing the manager past the limit.

**Specs.** A new `product/specs/sleep-and-resume.md` describes the behavior as a whole: what survives, what the user sees, and what a genuinely unreachable session looks like. Four existing specs are amended rather than replaced — `websocket-rpc.md` (its "Browser history restoration" section generalizes to any reconnect; the no-resend rule is restated unchanged), `remote-server.md` (the "no reconnect, no resume, and no reattach" sentence is rewritten around reattachment), `scheduling.md` and `notifications.md` (the new `schedule-late` event and its line, added to the "Events that notify" list and to the explicit-events paragraph that enumerates which events have no toggle).

## Out of scope

- **Surviving a full server restart.** Recovering after the janus process itself dies, or the machine reboots. `janus --relaunch` already restores saved tabs from `.janissary/state/`; this version does not automate that path, and the failure case deliberately parks on a reachable window rather than driving a relaunch.
- **Network changes as a separate case.** A Wi-Fi switch, an IP change, or a VPN flap will in practice be carried by the same reconnect machinery, but this version does not design or test for them specifically.
- **Multiple client windows.** Coordinating reconnect when more than one browser window is attached to the same session. This version reasons about the single-window case.
- **Chrome window crash or closure.** Recovering when the Chrome `--app` window (`src/main.ts:117`–`:118`) is killed rather than merely disconnected.
- **Buffering and replaying PTY output across the disconnected gap** — settled above as a design decision, and restated here because it is the most likely thing to be mistaken for an oversight.
- **Resending in-flight requests, or queueing user input typed while disconnected.**
- **Registering a new `web/src/` feature directory.** Everything this plan adds on the client is a root-level service, a colocated component, or an edit to an existing file, so `clientFeatureDirectories` in `eslint.config.mjs` is untouched.
- **A client-side timer-drift detector.** The browser's own wake events cover it; see the ceiling and upgrade path noted under the sleep-detection decision.
- **Any new npm dependency.** The reattach hop uses `node:net`; nothing here needs a package that isn't already installed.

## Open questions

- **Plain `ssh <destination>` tabs.** The reattach mechanism is the remote peer keeping its own session, and a plain ssh tab has no peer on the far side — it is a raw PTY to the host's own sshd (`product/specs/ssh-tab.md`; `product/specs/connection.md` describes it as "the ssh session is the tab's only PTY"). Reattachment as specified cannot apply to it, and the multiplexer approach that would make it possible was explicitly not chosen. The working assumption is that a plain ssh tab reconnects its transport and starts a fresh remote shell in the same tab, with the transcript above it preserved and a visible break marking the reconnect — but that is this plan's inference, not a decision the user made, and it needs confirming before implementation. The alternative is to leave plain ssh tabs on today's behavior entirely.
- **A refused reattach.** When the far side did not survive — the remote host itself rebooted, or the peer's bounded wait expired — the plan runs today's teardown and leaves the tab reporting that the remote session ended. That follows from the "never close a window out from under the user" decision, but it was not asked about directly. Whether the tab should instead offer to relaunch the remote session in place is unresolved.
- **The bounded wait before an unreattached peer expires.** A concrete duration has not been chosen. It trades a leaked workspace clone on the far side against a laptop that slept longer than the window and comes back to a session that is gone.

## Verification

```
$janissary/scripts/run.mjs check-diff
```

Manual check: launch the app, open a couple of tabs including a long-running harness and a remote (`on <address>`) tab, and add a scheduled command due a minute or two out. Close the laptop lid, wait past both the schedule's due time and the grace window, and open it again. The server process is still the same pid; the window shows `Reconnecting…` and then clears; every tab is still there with its transcript; the remote tab's far-side work is intact rather than restarted; and the notification feed carries one `<command> ran <duration> late (system was asleep)` line for the schedule that came due while the machine was asleep.
