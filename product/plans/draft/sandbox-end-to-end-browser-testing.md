# Sandbox end-to-end browser testing

**Complexity: 6/10** — a new subsystem (a Playwright-launched browser-server process's lifecycle) touching both the local and remote harness spawn paths, including a `REMOTE_PROTOCOL_VERSION` bump and race-safe async gating on each side (a browser-start promise that must always resolve, combined with the existing workspace-clone `ready` gate without letting a browser failure trip its tab-closing reject path). Contained to `src/` — no `web/src`, no new persistence — which keeps it out of the 8-9 band, but the concurrency reasoning on both ends keeps it above a routine wiring change. A minimalism pass trimmed a redundant outcome-lookup export and a redundant second env-var-building module; the browserless-vs-Playwright question that was open in an earlier revision is now resolved (below) in favor of Playwright's own `launchServer()` — no new dependency, no Docker.

## Summary

A sandboxed AI working inside a `harness -w` workspace can currently drive arbitrary web content through the `browser` command (Playwright, launched inside that same sandboxed process), but it has no way to open a real browser against janissary's own served web UI to see and click what a user would actually see — that's the gap this feature closes. `harness <name> -b`/`--browser` starts a local Chromium instance via Playwright's own `chromium.launchServer()` API as an ordinary, unsandboxed subprocess on whichever host the harness actually runs on, and hands the sandboxed harness process that instance's websocket connection endpoint through an environment variable. (An earlier revision of this plan called for a self-hosted "browserless" instance instead; that had a verified feasibility gap — no self-hostable, npm-installable browserless server exists — resolved in favor of Playwright's own server/connect API, which needs no new dependency and no Docker. See Design decision 1 and the resolved Open question.) The AI, running inside the sandbox, uses that endpoint to point its own Playwright script (via `chromium.connect(wsEndpoint)`) at that external browser and drive janissary's own web UI for genuine end-to-end testing — clicking, typing, and reading rendered output the way a person would, instead of asserting against React internals or a headless DOM. A new `ai/guidelines/sandbox-e2e-browser.md` document teaches any sandboxed AI how to use the environment variable to connect and drive the browser; this feature ships no test-running command of its own.

The instance is stopped when its harness tab closes, mirroring the existing workspace-clone-cleanup pattern, and is started on the remote host (not the local one) for an `on <address>` harness, since that's where the AI's own sandboxed process — the thing that needs to reach it over the network — actually runs.

## Design decisions

1. **Self-hosted via Playwright's own `launchServer()`, not browserless.io, and not Docker.** `-b`/`--browser` launches a local Chromium instance as a local subprocess that janissary starts and stops itself, using the `launchServer()` API `playwright` (already a project dependency, `package.json:127`) already exposes — no account, no API key, no outbound dependency on a third-party service. This follows directly from the backlog text's "spin up" / "stop" / "start it on the remote machine" lifecycle language, which only makes sense for a process janissary owns, not an always-on hosted account. It supersedes an earlier revision of this plan, which named the "browserless" product specifically; that revision's Open question (a verified feasibility gap — no self-hostable, npm-installable browserless server exists) is resolved here in favor of Playwright's own server/connect API instead of accepting a Docker prerequisite (see the resolved Open question).
2. **No new interactive command — pure connection plumbing.** `-b`/`--browser` is the entire surface: it does not extend the existing `browser` command (which stays local-Playwright-only, used for agent web-fetching, not UI testing) and it adds no new "run this E2E test" command. The AI writes and runs its own Playwright script inside the sandbox, using the environment variable below to connect to the external browser. `ai/guidelines/sandbox-e2e-browser.md` is where this is taught.
3. **Startup failure degrades, it does not fail the launch.** If the local (or, for a remote harness, the remote) browser-server instance fails to start, the harness tab opens and runs normally without E2E browser support — the environment variable is simply not set — and a one-line notice reports it, composed alongside the existing sandbox-isolation and auto-approve-without-workspace notices.
4. **Connection plumbing only — no built-in test runner.** This feature delivers the flag, the instance lifecycle, and the environment variable. Writing, running, and asserting E2E test code is left entirely to the AI's own tooling inside the sandbox.
5. **Flag: `-b` / `--browser`**, a boolean toggle on the `harness` command, alongside the existing `-w`, `-y`, `--offline`, `--model`, `--effort`.
6. **One environment variable**, not two: `JANISSARY_BROWSER_WS_ENDPOINT`, carrying the websocket endpoint `launchServer()`'s returned `BrowserServer.wsEndpoint()` gives back — named in the `JANISSARY_*` style `JANISSARY_NODE` already establishes in `src/sandbox/index.ts`. An earlier revision of this plan (written against "browserless," which does have separate token-based auth) called for this endpoint plus a second, separately-minted `JANISSARY_BROWSER_TOKEN`. Playwright's `launchServer()` has no separate token concept to hand out: the endpoint it returns already embeds its own unguessable, per-launch path segment, which is the only credential a Playwright client needs to `connect()` — layering a second, independent secret on top would mean janissary running its own proxy in front of the websocket to check it, which is real, unrequested complexity for no meaningful security gain over an already-unguessable URL. This is a direct, mechanical consequence of choosing `launchServer()` over browserless (Design decision 1), not a fresh product call — flagged here in case the reduction from two variables to one matters for the guidelines doc's audience.
7. **One browser-server instance per harness tab**, not a shared/pooled instance. Each `-b`-flagged harness gets its own subprocess, isolated from any other E2E-flagged tab, and stopped when that tab closes — the same per-tab isolation model `src/browser/tab.ts` already uses for agent-driven Playwright browsers, applied here to a Playwright-launched server process instead of an in-process browser.
8. **Playwright's own `launchServer()` provides the local browser server** — no new dependency (`playwright` is already in `package.json:127`, already used by `src/browser/`) and no Docker prerequisite. This resolves what was an open, unresolved feasibility gap in an earlier revision of this plan (the `browserless` npm package turned out to be a Puppeteer client SDK, not a spawnable server, and the real self-hosted browserless product is Docker-only) — see the resolved Open question below for the verification detail.
9. **`-b`/`--browser` is independent of `-w`/`--workspace`.** It works standalone; when used without a workspace, a security/context notice is shown, mirroring the existing `auto-approve-without-workspace` warning (`-y` without `-w`) — since without a workspace there's no disposable clone and, on macOS, no sandbox, confining whatever the AI's script does with the connected browser.
10. **All three harnesses support it** — claude, opencode, and codex. Unlike `-y` (which only claude and codex recognize a permission prompt for), there is nothing harness-binary-specific about handing an environment variable to a spawned process, so `-b` is not restricted the way `-y` is.
11. **Works on non-macOS hosts, unconfined.** Playwright's Chromium has no macOS dependency, so `-b` still launches it and injects the environment variable on any OS. The existing sandbox notice (shown whenever isolation isn't actually active) already covers the "unconfined" caveat for any workspaced tab on a non-macOS host; `-b` adds nothing further there.
12. **Guidelines doc: `ai/guidelines/sandbox-e2e-browser.md`.** Placed alongside the project's other binding guideline docs that every agent reads before starting work (per `CLAUDE.md`), since this is standing guidance for any AI doing UI E2E testing, not a one-off task script.
13. **Remote harnesses forward a boolean flag, not a connection endpoint, over the wire.** Following the exact shape `src/remote/protocol.ts`'s `spawn` `ClientFrame` variant already uses for `offline` and `harness` — a fact the remote independently acts on rather than a value the local side computes and hands over — `-b` on an `on <address>` launch adds a `browser?: boolean` field to that frame, sourced from `RemotePtyOptions` (`src/remote/pty-session.ts`), not from `src/harness/remote-launch.ts` (which only bootstraps the ssh channel and workspace clone, and never builds the `spawn` frame — see Proposed changes for the corrected call sites). The remote starts (and stops) its own local browser-server instance and builds its own copy of the environment variable, exactly as `src/harness/scratch-dir.ts`'s `harnessEnv` doc comment already states the general principle: "It names paths that exist only there, so a remote launch builds its own copy of this on the far side rather than being handed one over the wire." This is a frame-shape change, so it moves `REMOTE_PROTOCOL_VERSION` from 8 to 9 and is refused at the handshake by either end running the other version — the same policy every prior field addition to this protocol has followed.
14. **A `-b`-only launch (no `-w`) becomes provisioning-gated, matching a `-w` launch's placeholder-tab UX, instead of staying synchronous.** Today, `HarnessManager.spawnTab` (`src/harness/manager.ts:161-201`) only defers the PTY spawn behind a `provisioning` placeholder tab when `options.ready` (a workspace clone in flight) or `options.remote` is set; a plain `harness claude` with neither spawns its PTY synchronously in the same tick. Starting a local browser-server subprocess is not instantaneous, and its result (the environment variable, or a failure notice) must exist *before* the PTY is spawned — so `-b` alone now also takes the placeholder-tab path. See Proposed changes for the exact mechanism (a browser-start promise that always resolves, combined with any workspace `ready`).

## Proposed changes

### 1. `src/harness/command-parse.ts` — flag parsing

`HarnessParsed`'s first union member (`:8-12`) gains `browser: boolean`. `parseHarnessFlags` (`:55-84`) recognizes `-b`/`--browser` with the same one-line `tokens.some((t) => t === '-b' || t === '--browser')` shape `--offline` already uses (`:66`) — a plain boolean check, not nested branching, so it does not push the function further over the cognitive-complexity limit its own comment already flags it as being near (`:30-31`). Not restricted by harness name (unlike `-y`'s check at `:72-74`) — no rejection branch is added. `parseHarnessCommand`'s doc comment (`:98-118`) gains a sentence for the new flag, matching its existing per-flag documentation style.

### 2. `src/harness/spawn-options.ts` and the `open`/`run` call chain

`SpawnTabOptions` (`spawn-options.ts:7-24`) gains `browser: boolean`. `HarnessManager.run` (`manager.ts:77-86`) passes `parsed.browser` into `open` as a new final positional argument; `open`'s signature (`manager.ts:114-117`, already 9 positional parameters) grows to 10 the same incremental way `remote` was added most recently — this plan does not convert `open` to an options-object signature, since that would be a broader refactor than this feature needs, but implementers should not reorder the existing parameters while adding the new one, given `SpawnTabOptions`'s own doc comment already flags positional transposition as the risk this shape carries.

`openFromProfile` (`:138-152`, `ProfileHarnessEntry`) is **not** touched — see Out of scope. Nothing in the backlog text or the interview asked for profile-launched harnesses to get E2E browser support, so this plan doesn't add it on the codebase's behalf; `SpawnTabOptions.browser` defaults to `false` for a profile-authored `spawnTab` call, same as any option `openFromProfile` doesn't set.

### 3. New module, `src/harness/e2e-browser.ts` — instance lifecycle

Owns the local browser-server subprocess lifecycle, one instance per call (Design decision 7), never through `sandboxSpawn` (it isn't confined and holds no workspace secrets). Two exports, kept intentionally small — an earlier revision of this plan also proposed a separate synchronous outcome-lookup export and a separate `scratch-dir.ts` helper to build the env var(s); both are cut below as unneeded (Rung 6: the outcome is a plain return value, and the env var belongs right where the endpoint is obtained, not in a second module):

- `startE2EBrowser(label: string): Promise<{ env: NodeJS.ProcessEnv } | { notice: string }>` — calls Playwright's `chromium.launchServer()` (no `port` option given, so Playwright picks one itself — no separate free-port-selection logic needed), reads the returned `BrowserServer`'s `wsEndpoint()`, and **always resolves**, never rejects, with either `{ env: { JANISSARY_BROWSER_WS_ENDPOINT: wsEndpoint } }` on success or `{ notice: '<one-line degrade message>' }` on failure (`launchServer()` rejecting, e.g. no display/binary issue on a headless host — unlikely for Chromium but handled the same as any other launch failure). Never rejecting itself is deliberate (Design decision 3: a browser-start failure degrades, it must not trip `wireProvisioning`'s reject → `failSpawn` → tab-closes path). The live `BrowserServer` object needed later by `stopE2EBrowser` is kept in a small internal `label → BrowserServer` map — the only state this module needs, since the outcome itself is simply returned to the caller rather than stored for a later lookup.
- `stopE2EBrowser(label: string): void` — calls the stored `BrowserServer.close()` for `label` and forgets it via the internal map; a no-op if none exists (already stopped, or `-b` wasn't used).

### 4. `src/harness/manager.ts` — wiring the async gate and the env/notice merge

`spawnTab` (`:161-201`) is where `provisioning`/`ready` are decided today (`:163`, `if (!ready) { this.finishSpawn(options); return; }` at `:187-190`). When `options.browser` is set:

- Call `startE2EBrowser(label)`, which returns a promise resolving to the outcome directly (`{ env }` or `{ notice }` — no separate lookup call needed, see §3).
- `provisioning` (`:163`) becomes true whenever `options.ready`, `remote`, **or** `options.browser` is set — a `-b`-only launch now also gets the placeholder-tab treatment (Design decision 14), instead of hitting the old synchronous branch at `:187-190`.
- The value awaited before calling `finishSpawn` combines `options.ready` (if present) with the browser promise via a plain `Promise.all` (stdlib, no new combinator machinery), capturing the browser promise's resolved outcome into a local variable in the same closure that then calls `finishSpawn(options, outcome)` — a genuine workspace-clone failure still rejects and reaches `failSpawn` (closing the tab) exactly as today, since the browser promise itself never rejects and can't suppress that.
- `finishSpawn` (`:207-227`) gains a parameter for this outcome (alongside its existing `remoteNotice?: string` parameter): on `{ env }`, merges that var alongside the existing `harnessEnv(name, cwd)` object already passed into `managers.pty.spawn(...)` (`:216`); on `{ notice }`, folds that one-line string into the existing `notice` composition at `:224` (alongside the isolation/remote/auto-approve-without-workspace notices, joined the same `; `-separated way `remote-server.md` already documents for its own two notices). A launch with no `-b` passes no outcome, unchanged from today.
- The remote branch (`:178-185`, `startRemoteTab`) is unaffected by any of the above — see §5 for what changes on that path instead.
- `stopE2EBrowser(label)` is called wherever the tab's other per-label teardown already happens on close (the same place workspace-clone cleanup is triggered for a `-w` launch), so a `-b`-flagged tab's instance is stopped exactly once, whether the tab closed normally or its provisioning failed.

This keeps `manager.ts`'s own diff to a handful of call-additions rather than new inline logic — the file is already close to the 200-line guideline (~187 non-blank/non-comment lines currently), and the actual lifecycle logic lives in the new `e2e-browser.ts` module instead, per the file-size guideline's "extract, don't compact" rule.

### 5. Remote support — `src/remote/protocol.ts`, `src/remote/pty-session.ts`, `src/harness/manager.ts:215`, `src/remote/serve-processes.ts`

- **`src/remote/protocol.ts`**: bump `REMOTE_PROTOCOL_VERSION` (`:25`) from 8 to 9; add `browser?: boolean` to the `spawn` variant of `ClientFrame` (`:64-74`); extend the frame-validation branch that already checks `offline`'s type the same way for `browser`.
- **`src/remote/pty-session.ts`**: `RemotePtyOptions` (`:8-17`) gains `browser?: boolean`; `createRemotePtySession` (`:27-48`) destructures it and includes it in the `channel.send({ type: 'spawn', … })` literal (`:37-40`) alongside `harness`/`offline`.
- **`src/harness/manager.ts:215`**: the `registerRemotePty(label, channel, { program, command, harness: name, offline })` call gains `browser: options.browser`.
- **`src/remote/serve-processes.ts`**: `RemoteProcesses.spawnPty` (`:47-64`) currently builds and registers its `Entry` synchronously in one step. When `frame.browser` is set, starting the remote's own instance is async (the same `startE2EBrowser`/`stopE2EBrowser` module from §3 is reused here, since the lifecycle logic itself is host-agnostic — only which host it runs the subprocess on differs). To avoid a `kill(frame.id)` racing in before the underlying PTY exists and being silently dropped, `spawn` (`:27-31`) inserts a placeholder `Entry` into `this.entries` immediately (whose `kill` just marks the request as cancelled), and `spawnPty` replaces it with the real session's `Entry` once `startE2EBrowser`'s promise settles and the actual `spawnPty` (from `src/pty.ts`) call happens — unless the placeholder was already marked cancelled, in which case the browser instance is stopped again and no PTY is spawned. On a browser-start failure, the remote proceeds without the env var and folds a notice into the `workspace-ready` server frame's existing `notice` field (`:101`), the same way the remote's own isolation/credential notices already travel back (`serve-notice.ts`, per `remote-server.md`).

### 6. Docs

- **`product/specs/harness.md`** — new subsection documenting `-b`/`--browser`: what it does, the environment variable, the per-tab instance model, the degrade-on-failure behavior, and that it works with or without `-w` and on every harness type.
- **`product/specs/remote-server.md`** — a short addition to the version-history narrative for the bump to 9, matching the style of every prior bump's paragraph (§ Failures).
- **New file, `ai/guidelines/sandbox-e2e-browser.md`** — explains, for any AI running inside a sandboxed harness: how to detect that `-b`/`--browser` was used (`JANISSARY_BROWSER_WS_ENDPOINT` being present in the environment), how to connect a Playwright script to the external browser via `chromium.connect(wsEndpoint)` (not `connectOverCDP` — `launchServer()`'s endpoint speaks Playwright's own protocol, which hands back a full `Browser` object, not a raw CDP attachment), and that janissary's own served web UI is what should be pointed at for UI end-to-end testing (as opposed to the general-purpose `browser` command, which is for agent-driven web fetching, not this).

### 7. `package.json`

No change. `playwright` is already a dependency (`package.json:127`); this feature adds no new package.

## Tests

- `src/harness/command-parse.test.ts` — `-b`/`--browser` parses in short and long form, combines with every other flag/clause in any order, and is accepted for all three harness names (no rejection case, unlike `-y`'s claude/codex-only test).
- `src/harness/e2e-browser.test.ts` (new) — instance start/stop lifecycle against a stubbed `chromium.launchServer()` (mirroring how other subprocess-launching modules in this codebase are tested, not a real Chromium process), covering: successful start returns a well-formed endpoint, a start failure (a rejected `launchServer()` call) surfaces as a `{ notice }` outcome rather than throwing, and `stopE2EBrowser` is idempotent (calling `BrowserServer.close()` once, not erroring on a second call for the same label).
- `src/harness/manager.test.ts` — extend the existing flag-wiring coverage to cover `browser`: the env var present on a successful launch, notice composed and the env var absent on a failed instance start, and the instance's stop function invoked on tab close.
- `src/remote/protocol.test.ts` — the new `browser` field's validation (accepted boolean, rejected non-boolean), and the version-9 handshake refusing a version-8 peer.
- `src/remote/serve-processes.test.ts` — `frame.browser` triggers the remote's own instance start and env-var merge; failure folds a notice into `workspace-ready` instead of failing the spawn.
- Manual: `harness claude -b -w`, confirm a Chromium process launched by `launchServer()` is running on the host and that `JANISSARY_BROWSER_WS_ENDPOINT` is visible inside the sandboxed harness process (e.g. via `env | grep JANISSARY_BROWSER` run through the harness, checked with `harness capture`); confirm that process exits once the tab is closed. Repeat once with `on <address>` to confirm the instance starts and stops on the remote host instead.

## Out of scope

- The browserless.io product, hosted or self-hosted, and Docker as a runtime prerequisite generally — superseded by Playwright's own `launchServer()` (Design decision 1, resolved Open question).
- Extending the general-purpose `browser` command to target the external browser, or any other new interactive janissary command for driving it — the AI's own script, using the environment variable, is the entire surface (Design decision 2 and 4).
- A built-in E2E test runner, or any pass/fail reporting in the transcript — writing and running test code is left to the AI (Design decision 4).
- Sharing or pooling one browser-server instance across multiple harness tabs — every `-b`-flagged tab gets its own (Design decision 7).
- On-demand pulling/downloading of a browser image or binary at runtime — `playwright` (with its already-installed Chromium, from the project's existing `postinstall`/`playwright:install-chromium` step) is a static project dependency, present the same way `node-pty` already is, not fetched lazily (Design decision 8).
- Restricting `-b`/`--browser` to a subset of harness types the way `-y` is restricted to claude/codex (Design decision 10).
- Profile-launched harnesses (`openFromProfile`, `ProfileHarnessEntry`) gaining a `browser` option — the backlog text and the interview only ever describe the interactive `harness` command; this plan doesn't extend the profile schema on the codebase's own behalf. A profile-authored harness simply never sets `SpawnTabOptions.browser`, same as any launch flag a profile entry doesn't specify.

## Open questions

1. **What actually provides the self-hosted browser server.** **Resolved: Playwright's own `chromium.launchServer()`, not the browserless product, and not Docker.** Design decision 8 originally called for a project npm dependency, no Docker, and the backlog text named "browserless.io." Checked against the real npm registry and the `browserless/browserless` GitHub project during an earlier revision of this plan:
   - The `browserless` npm package is a **client SDK wrapping Puppeteer** (its own `package.json` lists Puppeteer as a peer dependency), not a spawnable server — it drives a browser itself rather than exposing a CDP endpoint for something else to connect to, so it does not fit this feature's shape at all.
   - The actual self-hosted browserless product is **Docker-distributed** (`docker run ghcr.io/browserless/chromium`, exposing a CDP websocket at the container's port); no self-hostable npm-installable server was found under the browserless name.
   - `playwright` is already a project dependency (`package.json:127`, already used in `src/browser/`) and its own `browserType.launchServer()` API does exactly what this feature needs — start a local Chromium process and hand back a `wsEndpoint` for another process to `connect()` against — with no new dependency and no Docker requirement, at the cost of it not literally being "browserless."

   Confirmed by direct instruction: use Playwright's `launchServer()`, no Docker. Every design decision, module contract, and test above is now written against that choice — see Design decisions 1, 6, 7, 8, and Proposed changes §3, §6, §7.
2. **Interaction with `--offline`.** `--offline` swaps in a sandbox profile that denies `network*` entirely (`src/sandbox/profile.ts`), which would also block the sandboxed harness process from reaching the browser instance's endpoint, even one running as a local, unsandboxed process on the same host. Whether `-b --offline` together should exempt that endpoint from the denial, or simply be treated as a contradictory combination (with `-b`'s environment variable set but unreachable), was not resolved in the interview and needs a decision before implementation.
