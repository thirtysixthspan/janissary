# Conversations plugin

**Complexity: 8/10** — a first-of-its-kind surface on both sides: a new networked provider subsystem with a new dependency, a new home-level persistence store, the first `conversations` host topic (which turns `TabPluginNotification` into a union and forces a small change to the topic table's disabled-fallback), a streaming push path with cancellation and abort, and two new tabs with their own client chunk.

Janissary has no way to hold an ordinary back-and-forth conversation with a model. The one model surface that exists today is `acp` (`product/specs/acp.md`), which drives a hardcoded OpenCode agent per tab, keeps its session only in memory, and interleaves replies with the tab's shell transcript. This plan adds a bundled tab plugin — reached by the `chat` command — that gives conversations their own home: a singleton list tab ordered by most recent activity, one tab per open conversation, and a JSON file per conversation under `~/.janissary/conversations/` so a conversation survives the process that created it.

Responses come from provider HTTP APIs called directly by the server, rather than from a CLI harness or an ACP agent. A `models` table in `.janissary/config.json` names each selectable model and the environment variable holding its key, so adding a model is a config edit rather than a code change. A conversation runs one model at a time; the model can be switched from the conversation tab's header at any point, and every stored turn records which model answered it. Responses stream into the view as they arrive, and opening a long conversation renders its most recent turns and extends backwards as the user scrolls.

## Design decisions

**Responses come from provider HTTP APIs, called by the server.** Not ACP, not a harness subprocess. The host owns a new `src/models/` subsystem that holds the provider clients, and the plugin never opens a socket or reads a key — it asks the host to send a query and redraws when the host says something changed. This keeps the plugin inside the boundary `eslint.plugin-boundaries.mjs` enforces (a server tab plugin may import only `../api.js`, `../files.js`, and two named opener helpers) and keeps a long-lived networked subsystem in `Managers` with a `dispose`, as `ai/guidelines/plugins.md` §10 requires.

**v1 ships one provider client — Anthropic — behind a provider-keyed config table.** The table's shape is multi-provider from the start, so a second client is an additive change with no config migration, but only `provider: "anthropic"` resolves to a working client in this version. An entry naming any other provider is listed in the model selector as unavailable, with the same treatment as an entry whose key is unset. This is the one place the plan narrows the user's answer: the table format is exactly as chosen, and the second client is deferred rather than designed speculatively. Calls go through the official `@anthropic-ai/sdk` package and its streaming helper; model ids are the current bare aliases (`claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5`) with no date suffix.

**The model table lives in `.janissary/config.json`; keys come from the environment.** A new `models` setting holds a list of entries, each with a display name, a provider, a model id, and the name of the environment variable carrying that provider's key. `DEFAULT_CONFIG` ships a small default list covering the three current Claude models against `ANTHROPIC_API_KEY`. A user-supplied list replaces the default wholesale, exactly as `notifications` and `externalViewers` already do, and there is no runtime command to change it. A model whose named variable is unset is still shown in the selector but cannot be chosen; a conversation whose recorded model is no longer in the table falls back to the first selectable entry for its next query and leaves its stored turns untouched.

**The list tab and the conversation tabs are separate tabs of one plugin.** `chat` opens or focuses a singleton list tab, ordered by most recent activity, exactly as the schedules plugin's list works. Activating a row opens that conversation as its own plugin tab, keyed by the conversation's id, so a second activation focuses the tab that is already open. A **New conversation** entry sits at the top of the list and opens an empty conversation tab. The empty list shows a single `No conversations yet` line above that entry.

**`chat` is the only claimed command.** `chat` opens or focuses the list; `chat left` and `chat right` dock it, and bare `chat` on a docked list undocks it — the `schedules [left|right]` grammar verbatim. `chat <title>` opens the conversation whose title matches case-insensitively, and reports `No conversation matching "<text>".` when nothing does. The dock keywords win over a conversation that happens to be titled `left` or `right`; that collision is accepted rather than escaped, since titles are derived from a first query and the loss is one addressable conversation, not a broken command.

**A conversation is titled from its first query.** The title is the first line of the first query capped at 60 characters; before any query has been sent it reads `New conversation`. Nothing prompts for a title and nothing renames one. The tab's name in the strip is set on the update that records the first query, through the `title` field `TabPluginTabUpdate` already carries (`src/plugins/api.ts:134`). The plugin does **not** truncate for the tab strip: `tabNameMaxLength` is already broadcast to the client (`src/state-event.ts:20`, `src/protocol/events.ts:13`) and truncates every tab's display label, as the comment at `src/config.ts:54` records. The 60-character cap exists only to keep a pasted wall of text out of the stored metadata.

**The model is chosen from the conversation tab's header.** The header holds a dropdown of the configured models, defaulting to the conversation's last-used model and, for a new conversation, to the first selectable entry in the table. Changing it applies from the next query onward; turns already stored keep the model that answered them.

**Responses stream in coalesced chunks, and the coalescing happens at the bus.** The manager accumulates provider deltas into the in-memory turn and emits its `conversations` bus event at most once per 100 ms while a response is in flight, plus once when the turn completes. It does not call the plugin at all — the plugin's subscription is the ordinary topic subscription at `src/plugins/notifications.ts:98` (`subscribeTopic(topic, …)`), so throttling the bus emission is what bounds the plugin's call rate. This is the justification `ai/guidelines/plugins.md` §9 asks for on a push path: the rate is bounded by a timer rather than by provider chunk size, so a fast stream costs the same number of plugin calls as a slow one, and nothing rides the per-keystroke `emitState` path.

**A failed turn is stored; a cancelled one is discarded.** A request that fails — missing key, rate limit, network, or a `refusal` stop reason — records the failure on that turn, which the view renders in place, so the conversation keeps its history and the user can retype the query. Cancelling mid-stream, by Escape in the conversation tab or by closing the tab, aborts the request and drops the partial response: nothing partial is ever written to disk. The host also aborts a request whose conversation no longer has an open tab, checked at the next chunk boundary, so a closed tab cannot leave a stream running.

**Deleting is confirmed; nothing else mutates a conversation from the list.** Deleting a row raises a confirmation dialog first — the shape `DeleteScheduleDialog` already establishes — and removes the file on confirmation. There is no rename and no in-list editing.

**One JSON file per conversation, rewritten atomically.** `~/.janissary/conversations/<id>.json` holds a metadata object — schema version, id, title, created and updated timestamps — followed by an array of turn objects, each carrying its query text and its response with the model and provider that produced it. The file is replaced through `src/atomic-write.ts` after each completed turn and after a recorded failure, so an interrupted write leaves the previous valid file intact, matching the discipline `src/global-history.ts` and the relaunch transcript records already use. Because the file is one JSON document it is parsed whole; the windowing below bounds what crosses to the client, not what is read from disk.

**Home-level storage, not project-level.** Conversations live beside `~/.janissary/history.json` rather than under the project's `.janissary/state/`, so one set of conversations serves every directory `janus` is launched from and an ordinary launch — which recursively deletes the project state directory — never destroys them.

**A conversation opens on its recent turns and extends backwards.** Opening a conversation renders its most recent 20 turns; scrolling to the top of the view asks for the next 20 older ones, until the whole file is rendered. The host holds the loaded window per open conversation and extends it on request; the plugin's payload carries the window plus whether older turns remain.

## Proposed changes

**Config.** `src/config.ts` gains a `models` field on `Config` (`:21`): a list of entries with `name`, `provider`, `model`, and `keyEnv`, plus an exported `DEFAULT_MODELS` constant beside `DEFAULT_EXTERNAL_VIEWERS` (`:59`) and folded into the module-local `DEFAULT_CONFIG` (`:61`). Decoding gets its own `models(value, fallback)` function in `src/config-decode.ts` beside `notifications` (`:32`) and a `models:` line in `decodeConfig` (`:46`): a `models` value that is not an array falls back to the default without disturbing neighbouring settings, and an entry missing any of the four string fields is dropped while its neighbours survive. Add the row to the settings table in `product/specs/application-config.md`.

**Model subsystem.** A new `src/models/` directory holding two modules — there is deliberately no third dispatcher module. `catalog.ts` reads the config entries, resolves each one's key from `process.env`, and reports the selectable set with a reason for each unselectable entry (`no key` or `unsupported provider`); because it is the catalog that decides an entry naming an unknown provider is unselectable, nothing downstream ever has to route by provider, and a second provider becomes a new module plus one branch here. `anthropic.ts` wraps `@anthropic-ai/sdk`, exposing a single streaming function that takes the resolved entry, the conversation's prior turns as messages, the new query, and an `AbortSignal`, and yields text deltas followed by a completion result. It uses the SDK's streaming helper rather than a non-streaming create (required at the `max_tokens` this needs), takes its final message for the stop reason, translates the SDK's own typed error classes (`RateLimitError`, `AuthenticationError`, `APIError` with its `status`) into a small internal failure shape rather than matching on error text, and treats a `refusal` stop reason as a recorded failure rather than a response. Cancellation is a plain `AbortController` — the SDK accepts the signal directly, so there is no cancellation token of our own. `@anthropic-ai/sdk` is the only new dependency; it must clear `./scripts/run.mjs check-malicious-package @anthropic-ai/sdk@<version>` with exit code `0` before install.

**Conversation store.** A new `src/conversations/store.ts` owns the directory (`~/.janissary/conversations/`, created on first use with the same home injection point `initGlobalHistory` uses for testability). It lists conversation summaries — id, title, last activity — by scanning the directory and parsing each file the **first time the list is asked for**, not at startup: the plugin activates lazily and a user who never runs `chat` should pay nothing, per `ai/guidelines/plugins.md` §6. The summaries are then held in memory and updated in place as conversations change. It also reads a whole conversation on demand and writes one atomically through `src/atomic-write.ts`. The scan is a linear parse of every file in the directory; that is fine at the scale a single user's conversation history reaches, and the upgrade path if it ever isn't is a summary index file written alongside the conversations — not needed now and deliberately not built. A malformed file is skipped with a one-time warning and is left untouched on disk, matching how a corrupt `config.json` and a corrupt `history.json` are already handled. The persisted shape carries its own `schemaVersion`, since it outlives the process (`ai/guidelines/plugins.md` §4).

**Conversations manager.** A new `ConversationsManager` at `src/conversations/manager.ts`, added to `ManagerRegistry` (`src/managers.ts:30`) as `conversations` and constructed in `src/controller/create-managers.ts`, with a `dispose` that aborts every in-flight request. It owns the store, the per-conversation loaded window, and the in-flight requests keyed by conversation id, and it is the only thing that fires the new host topic. Its methods cover: create (given an id minted by the plugin), load a window, extend a window backwards, send a query on a conversation, cancel one, set a conversation's model, and delete a conversation. Sending appends the query to the in-memory conversation, starts the provider stream, coalesces deltas onto a ~100 ms tick, fires the topic on each tick, and on completion writes the file and fires once more. It refuses a send for a conversation that already has one in flight.

**Plugin API additions.** All additive, so `TAB_PLUGIN_API_VERSION` stays at 1 (`src/plugins/api.ts:3`, and the comment at `:22` that keying `CAPABILITIES`/`NOTIFICATION_TOPICS` by the union makes a missing entry a compile error rather than a silent gap — add `conversations: true` to `NOTIFICATION_TOPICS` at `:66`). `TabPluginNotificationTopic` (`:62`) gains `'conversations'`; `TabPluginNotification` (`:80`) becomes a discriminated union on `topic` whose new member carries the conversations slice; and `TabPluginTopicAction` (`:90`) gains the conversation actions listed above, each tagged `topic: 'conversations'` so the grant stays tied to the declared topic. The wire-facing view types for the slice — a conversation summary, a turn, and a loaded window — are defined in `src/protocol.ts` and re-exported from `src/plugins/api.ts` beside `AggregatedScheduleView` (`:249`), since the plugin import boundary forbids a plugin reaching into `../protocol.js` directly (`eslint.plugin-boundaries.mjs:33`). `src/plugins/api.ts` measures 135 lines against the 200-line `max-lines` budget, which leaves room for these additions; the view types go in `src/protocol.ts` (52 lines) rather than in `api.ts` to keep it that way.

**Topic table.** Two changes in `src/plugins/topics.ts`. Add a `conversations` entry to `TOPIC_SOURCES` (`:43`) whose `subscribe` is `messageBus.on('conversations', 'changed', fire)`, whose `read` returns the manager's current slice, and whose `act` is a `actOnConversations` switch modelled on `actOnSchedules` (`:27`) — one case per conversation action, each delegating to a `ConversationsManager` method. Add the matching `conversations: ConversationsEvent` channel to `BusChannels` in `src/bus.ts:105`, with `type ConversationsEvent = { type: 'changed' }` beside `ScheduleEvent` (`:104`).

Because `TabPluginNotification['data']` stops being a single array type, two things follow and both are decided here rather than left to the implementer. First, `TopicSource.read` (`src/plugins/topics.ts:15`) and `readTopicData` (`:55`) return the union, and the plugin narrows it with its own guard — the same way `activate.ts` already guards its tab payload. Second, the `topicData` capability currently returns the literal `[]` when the plugin is disabled (`src/plugins/context.ts:148`), which only typechecks while every topic is array-shaped: give `TopicSource` an `empty` field holding that topic's own zero value and return `TOPIC_SOURCES[topic].empty` instead. Nothing else in the dispatch path branches per topic, so `src/plugins/notifications.ts` is unchanged.

**Server plugin.** `src/plugins/chat/` with `manifest.ts` (id `chat`, `tabLabelPrefix` `chat`, no file extensions, `command: 'chat'`, `notifications: ['conversations']`, and the capability set schedules already uses: `openOrFocusTab`, `updateTab`, `dockTab`, `topicData`, `topicAction`, `rejectRequest`, `reportFailure`), `shared.ts` (payload schema version, the list and conversation payload types, and their guards — the module the client imports through `@shared/plugins/chat/shared`), and `activate.ts`. Activation parses the command as schedules does, extended with the title-lookup branch; answers the intents below; and, on a topic notification, updates the list tab and every open conversation tab from the slice it was handed. Add the manifest to `src/plugins/catalog.ts` and the loader to `src/plugins/loaders.ts`.

Intents, each validated by a guard in `shared.ts` and each turning into one topic action: `create` (the plugin mints the id, asks the host to create it, and immediately opens a tab under that id — the host refuses an id it already holds), `open`, `load-older`, `send`, `cancel`, `select-model`, and `delete`. Anything else is a `rejectRequest`. A tab payload that fails the plugin's own guard is a `reportFailure`, as it is in schedules.

**Client plugin.** `web/src/plugins/chat/` with `index.tsx` (the default component plus the `isPayload` guard, dispatching on which payload shape it received), `ConversationList.tsx` (rows with title and last activity, the new-conversation entry, the empty line, and the delete confirmation), `ChatTab.tsx` (header with the title, the model dropdown, and the host-rendered split action, above the turn list and the composer), a keys module for the **list's** row selection mirroring `web/src/plugins/schedules/schedules-keys.ts`, and `chat.css`. The conversation tab gets no keys module of its own — its only chord is Escape-to-cancel, which is one handler in `ChatTab.tsx`. The header uses the shared plugin look from `web/src/plugins/shared.css` rather than restating it, and the model dropdown is a native `<select>`: the platform already gives keyboard navigation, type-ahead, and disabled options, so nothing custom is built for it. Register the lazy entry in `web/src/plugins/registry.tsx` with the schema version literal, and pin that literal against `shared.ts`'s constant in `registry.test.tsx` as the other plugins do.

**Markdown rendering.** Responses render as sanitized Markdown. Rather than add a third copy of the `marked` + `DOMPurify` call, move the plugin-layer copy to `web/src/plugins/markdown-render.ts` and re-export `renderMarkdown` from `web/src/plugins/api.ts`; the markdown plugin and the chat plugin then both import it from `../api`, which is what the client boundary already permits. Core's `web/src/shared/transcript/markdown.ts` stays where it is — the boundary genuinely forbids a plugin reaching it.

**Ordering.** Land in four checkpoints so typecheck and tests stay green at each. First the types and the config: the `models` setting with its decoder, the conversation view types in `src/protocol.ts`, and the API additions in `src/plugins/api.ts` — inert on their own but referenced by everything after. Second the host: the store, the model subsystem, the manager, its `Managers` entry, the bus channel, and the `TOPIC_SOURCES` entry with the `empty` change; at this point the topic exists and is exercisable by tests with no plugin present. Third the server plugin and its catalog and loader entries. Fourth the client chunk, together with the markdown-renderer move — doing the move in its own commit ahead of the client work is also fine, since it touches only the markdown plugin and `web/src/plugins/api.ts`. Every new `src/` import carries the `.js` extension per the NodeNext rule, config and environment lookups use `??` rather than `||` to satisfy `prefer-nullish-coalescing`, and the parsed JSON of a conversation file is narrowed by a guard rather than asserted, to stay clear of `no-unsafe-assignment` and `no-unsafe-member-access`.

**Specs.** Add `product/specs/conversations.md` describing the command grammar, both tabs, model selection, streaming, failure and cancellation, storage, and profile behavior. Add the bundled-plugin section to `product/specs/tab-plugins.md` beside the schedules one, note the new topic and its actions in the "Being told when host state changes" section, and add the `models` row to `product/specs/application-config.md`.

## Out of scope

- **Multi-model fan-out.** A query goes to exactly one model. Sending one query to several models at once, and any side-by-side or stacked comparison of their answers, is deferred.
- **Tool use and attachments.** No tool or function calling, no file or image attachments, and nothing resembling the `db`/`browser` loop the `acp` command drives. A query is text in, text out.
- **Search, export, and usage statistics.** No searching across conversations, no export command, and no token or cost accounting — the separate `centralized model selection and usage statistics` backlog item covers the latter.
- **A second provider client.** The config table is provider-keyed and the dispatcher is written for more than one, but only `anthropic` resolves in this version.
- **Renaming a conversation.** Titles are derived from the first query and never change.
- **A runtime command to edit the model table.** `models` is hand-edited in `.janissary/config.json`, like `syncPaths`, `notifications`, and `externalViewers`.
- **`--relaunch` restore.** Chat tabs are live view tabs like every other plugin tab; the conversations on disk survive, the open tabs do not.
- **Thinking-block display.** Whatever reasoning the model does is not rendered; only the response text is.

## Open questions

- **Editing or resending a past turn.** This was offered as a candidate for deferral and was not selected, so it is genuinely unresolved. The plan as written treats a conversation as append-only from the user's side — no editing a previous query, no branching, no regenerate. If that is wrong, the affected pieces are the conversation payload (turns need addressable ids on the wire), one more intent and topic action, and the store's rewrite path.
- **An open tab whose conversation is deleted from the list.** Deleting is confirmed and removes the file, but the behaviour of a conversation tab that is open at that moment was not settled. Proposed default, pending confirmation: the tab stays open showing what it already had, with the composer disabled and a line stating the conversation was deleted; it is closed by the user like any other tab.
- **Which models ship in `DEFAULT_MODELS`.** The plan assumes the three current Claude models (`claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5`) with `claude-opus-5` first, so an unconfigured user with `ANTHROPIC_API_KEY` set gets a working default. Worth a look before implementation in case a narrower default is wanted.
