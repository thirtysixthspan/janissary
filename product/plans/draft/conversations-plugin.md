# Conversations plugin

**Complexity: 7/10** — a first-of-its-kind surface on both sides: a new home-level persistence store that owns a durable sandboxed workspace per conversation, the first `conversations` host topic (which turns `TabPluginNotification` into a union and forces a small change to the topic table's disabled-fallback), a streaming push path over a per-conversation agent subprocess, and two new tabs with their own client chunk. No new dependency and no new networked subsystem — the response path is the ACP channel janissary already owns.

Janissary has no way to hold an ordinary back-and-forth conversation with a model. The one model surface that exists today is `acp` (`product/specs/acp.md`), which drives a hardcoded OpenCode agent per tab, keeps its session only in memory, and interleaves replies with the tab's shell transcript. This plan adds a bundled tab plugin — reached by the `chat` command — that gives conversations their own home: a singleton list tab ordered by most recent activity, one tab per open conversation, and a directory per conversation under `~/.janissary/conversations/` so a conversation survives the process that created it.

Responses come from the ACP channel the app already speaks (`connectAcp`, `src/acp/index.ts`) rather than from provider HTTP APIs: each conversation gets its own ACP agent subprocess, spawned tool-less and confined by the existing Seatbelt sandbox to its **own** workspace — a directory created empty, holding no clone of the project and nothing else, living inside that conversation's directory so the two are created, carried across runs, and deleted as one. Model selection reuses the per-harness catalog `harness-models.json` already reads, so adding a model is a catalog edit rather than a code change and no API key is ever handled by this plan. A conversation runs one `<harness>:<model>` pair at a time; the pair can be switched from the conversation tab's header at any point, and every stored turn records which one answered it. Responses stream into the view as they arrive, and opening a long conversation renders its most recent turns and extends backwards as the user scrolls.

## Design decisions

**Responses come from the existing ACP channel, driven by the host.** Not a provider HTTP client, not a harness PTY. `connectAcp` (`src/acp/index.ts`) is already agent-agnostic — the caller supplies the command to run — already streams `agent_message_chunk` text through a per-prompt handler, already advertises no fs/terminal capabilities so the agent never calls those back, and already denies every tool permission request when `allowedTools` is empty or absent (`decidePermission`, `src/acp/tools.ts`). A conversation is exactly that shape: text in, text out, no tools. The host owns the sessions and the plugin never spawns a process or reads a credential — it asks the host to send a query and redraws when the host says something changed. This keeps the plugin inside the boundary `eslint.plugin-boundaries.mjs` enforces (a server tab plugin may import only `../api.js`, `../files.js`, and two named opener helpers) and keeps the long-lived subsystem in `Managers` with a `dispose`, as `ai/guidelines/plugins.md` §10 requires. It also means this plan adds **no new dependency**: `@agentclientprotocol/sdk` is already in `package.json`, and no provider SDK is introduced.

The one thing deliberately *not* reused from the `acp` command's path is `runAcpToolLoop` (`src/acp/loop.ts`). That loop exists to let an agent emit `db`/`browser` commands and have the host run them; a conversation has no tools and issues no commands, so it calls `session.prompt` directly with a Markdown primer and nothing else. Reusing the loop would drag the tool primers and the eight-step cap into a surface that has no use for either.

**Each conversation's agent runs in a workspace of its own, under the existing sandbox.** The session is spawned with `cwd` and `workspaceDir` both set to that conversation's workspace — a directory created empty, with no clone of the project and no files at all. `sandboxSpawn` (`src/sandbox/index.ts`) then applies the same Seatbelt confinement a workspaced tab gets (see `product/specs/sandbox.md`): writes denied outside that directory and its private temp sibling, `$HOME`'s contents denied but for the carve-ins, secrets denied last, and the credential-shaped environment variables scrubbed. The tool denial above is what actually stops the agent reading anything; the workspace and the sandbox are the second and third layers, so a future decision to grant a conversation a tool does not silently hand it the project tree. Confinement is best-effort by design — `sandboxSpawn` is a no-op when `sandboxWorkspaces` is off or the host is not macOS — exactly as it is for a workspaced tab, and for the same reason: it is defence in depth over an already tool-less session, not the thing keeping the agent honest.

**The workspace lives inside the conversation's own directory, and the two survive together.** A conversation is a directory under `~/.janissary/conversations/<id>/` holding `conversation.json` and `workspace/`; `workspace.tmp/` appears beside them because `sandboxSpawn` derives `TMPDIR` as `${workspaceDir}.tmp` (`src/sandbox/index.ts:231`), which puts the private temp dir inside the conversation too. This makes "they survive together" the layout rather than a rule anyone has to remember: one `mkdir` creates both, one recursive remove destroys both, and there is no way to delete a conversation and leak its workspace or to sweep workspaces and orphan a conversation. It also puts the workspace in the same home-level, never-swept place the conversation data already argued for below, so it outlives the process, the project directory, and any number of relaunches.

The directory is created on the conversation's **first query**, not when its row is created — the same lazy-activation argument `ai/guidelines/plugins.md` §6 makes and the plan already relies on, so an abandoned `New conversation` leaves neither a directory nor a trust entry behind. Creation is ensure-and-trust and idempotent: make the conversation directory, `workspace/`, and `workspace.tmp/` if absent, then `trustWorkspace` the workspace so the Claude ACP adapter will run there. It runs on every session connect rather than once per process, so a workspace whose trust entry was lost (a user editing `~/.claude.json`, a machine restored from backup) repairs itself on the next query.

**Per-conversation rather than shared, and that buys isolation.** Only `<id>/workspace` is carved into the sandbox profile — `(subpath (param "WORKSPACE"))` appears in both the `file-write*` and the `file-read-data` blocks of `src/sandbox/profile.ts`, by absolute path, so a workspace under `$HOME` is carved in exactly like the project-level one already is. Everything else under `~/.janissary/` stays denied by the blanket `$HOME`-contents rule. A conversation's agent therefore cannot read another conversation's workspace, cannot read any conversation's stored turns, and cannot even read its own `conversation.json`, which sits one directory above its carve-in. A single shared workspace would have given all of them one carve-in between them. The costs are paid deliberately: one trust entry in `~/.claude.json` per conversation, removed again on delete, and one directory pair per conversation on disk. (`parentGitObjectsDir`, `src/sandbox/index.ts:160`, resolves `GIT_OBJECTS` to `<workspace>/.git/objects` in an empty workspace — a path that does not exist, so that carve-in grants nothing here.)

**The model is a `<harness>:<model>` pair drawn from the catalog that already exists.** `harness-models.json` (overridable per project at `.janissary/harness-models.json`) already lists the models each harness offers, read through `modelsFor(harness)` (`src/harness/models.ts`); the selectable set for a conversation is that catalog restricted to the two ACP-capable harnesses, `claude` and `opencode` — the same two `spawnMonitorSession` maps and the same two a persona directive may name. There is deliberately **no new config setting**: the selector is fed by data the app already loads for personas and harness tabs, so adding a model stays a catalog edit and the plan touches neither `src/config.ts` nor `src/config-decode.ts`.

Availability is not computed up front. Whether an agent binary is installed and authenticated is not knowable without running it, so every catalogued pair is offered and a missing or unauthenticated binary surfaces the way it already does for `acp`: as a failed turn carrying the connection error, recorded on the conversation. A conversation whose stored pair has since left the catalog falls back to the first catalogued pair for its next query and leaves its stored turns untouched.

**Cancelling ends the session, not just the turn.** `AcpSession` exposes `prompt` and `kill` and nothing else — there is no per-prompt abort — so Escape in the conversation tab, or closing the tab mid-stream, kills that conversation's agent subprocess and forgets the session. The partial response is dropped and nothing partial is ever written to disk, as before; what is new is the consequence, stated here rather than discovered in implementation: the agent's own accumulated context dies with the subprocess. The same is true of a session that dies on its own — a crashed or missing binary, or simply a restarted app.

The manager therefore treats an absent session as the normal case and re-primes on demand: the first query on a conversation with no live session sends the Markdown primer followed by a replay of the conversation's stored turns, capped at the most recent 20 — the same window the view opens on, so the two numbers stay tied — and then the new query. Later queries on a session that is still alive send the query alone. This is what makes the on-disk file the conversation's real identity and the subprocess merely its current voice, which is also what lets a conversation survive a restart at all.

**The list tab and the conversation tabs are separate tabs of one plugin.** `chat` opens or focuses a singleton list tab, ordered by most recent activity, exactly as the schedules plugin's list works. Activating a row opens that conversation as its own plugin tab, keyed by the conversation's id, so a second activation focuses the tab that is already open. A **New conversation** entry sits at the top of the list and opens an empty conversation tab. The empty list shows a single `No conversations yet` line above that entry.

**`chat` is the only claimed command.** `chat` opens or focuses the list; `chat left` and `chat right` dock it, and bare `chat` on a docked list undocks it — the `schedules [left|right]` grammar verbatim. `chat <title>` opens the conversation whose title matches case-insensitively, and reports `No conversation matching "<text>".` when nothing does. The dock keywords win over a conversation that happens to be titled `left` or `right`; that collision is accepted rather than escaped, since titles are derived from a first query and the loss is one addressable conversation, not a broken command.

**A conversation is titled from its first query.** The title is the first line of the first query capped at 60 characters; before any query has been sent it reads `New conversation`. Nothing prompts for a title and nothing renames one. The tab's name in the strip is set on the update that records the first query, through the `title` field `TabPluginTabUpdate` already carries (`src/plugins/api.ts:134`). The plugin does **not** truncate for the tab strip: `tabNameMaxLength` is already broadcast to the client (`src/state-event.ts:20`, `src/protocol/events.ts:13`) and truncates every tab's display label, as the comment at `src/config.ts:54` records. The 60-character cap exists only to keep a pasted wall of text out of the stored metadata.

**The model is chosen from the conversation tab's header.** The header holds a dropdown of the catalogued `<harness>:<model>` pairs, defaulting to the conversation's last-used pair and, for a new conversation, to the first pair in the catalog. Changing it applies from the next query onward; turns already stored keep the pair that answered them. Because a pair names the agent subprocess itself rather than a request parameter, changing it kills the conversation's current session, and the next query re-primes a fresh one under the new pair by the replay rule above.

**Responses stream in coalesced chunks, and the coalescing happens at the bus.** The manager accumulates the session's `onChunk` text into the in-memory turn and emits its `conversations` bus event at most once per 100 ms while a response is in flight, plus once when the turn completes. It does not call the plugin at all — the plugin's subscription is the ordinary topic subscription at `src/plugins/notifications.ts:98` (`subscribeTopic(topic, …)`), so throttling the bus emission is what bounds the plugin's call rate. This is the justification `ai/guidelines/plugins.md` §9 asks for on a push path: the rate is bounded by a timer rather than by agent chunk size, so a fast stream costs the same number of plugin calls as a slow one, and nothing rides the per-keystroke `emitState` path.

**A failed turn is stored; a cancelled one is discarded.** A request that fails — a spawn that could not find the agent binary, an unauthenticated agent, a rate limit, a dropped connection, or any `onError` from the prompt — records the failure on that turn, which the view renders in place, so the conversation keeps its history and the user can retype the query. Rate-limited text is recognized with the existing `isRateLimitError` (`src/acp/rate-limit.ts`) so a conversation reports the condition in the same words the `acp` command does. A connection-level error means the session is gone, so it is forgotten as well as recorded, matching the discipline `AcpManager` already keeps; the next query reconnects and replays. Cancelling mid-stream, by Escape in the conversation tab or by closing the tab, kills the session and drops the partial response: nothing partial is ever written to disk. Closing the last tab of a conversation with a stream in flight is treated as a cancel, so a closed tab cannot leave a subprocess talking to nobody.

**Deleting is confirmed; nothing else mutates a conversation from the list.** Deleting a row raises a confirmation dialog first — the shape `DeleteScheduleDialog` already establishes — and removes the file on confirmation. There is no rename and no in-list editing.

**One directory per conversation, with one JSON document rewritten atomically inside it.** `~/.janissary/conversations/<id>/conversation.json` holds a metadata object — schema version, id, title, created and updated timestamps, and the conversation's current `<harness>:<model>` pair — followed by an array of turn objects, each carrying its query text and its response together with the harness and model that produced it. The file is replaced through `src/atomic-write.ts` after each completed turn and after a recorded failure, so an interrupted write leaves the previous valid file intact, matching the discipline `src/global-history.ts` and the relaunch transcript records already use. Because the file is one JSON document it is parsed whole; the windowing below bounds what crosses to the client, not what is read from disk. Its siblings in the directory are the workspace and the workspace's temp dir, described above.

Deleting a conversation is therefore one recursive remove of `~/.janissary/conversations/<id>/`, preceded by `untrustWorkspace` on its workspace, and it takes the stored turns, the workspace, and anything the agent left in it. That is the intent — the two are one thing — but it is worth stating plainly, because it is a larger deletion than "remove a transcript".

**Home-level storage, not project-level.** Conversations and their workspaces live beside `~/.janissary/history.json` rather than under the project's `.janissary/state/` or its `.janissary/workspace/`, so one set of conversations serves every directory `janus` is launched from; an ordinary launch — which recursively deletes the project state directory — never destroys them, and neither does the workspace sweep that removes every project-level clone at shutdown.

**A conversation opens on its recent turns and extends backwards.** Opening a conversation renders its most recent 20 turns; scrolling to the top of the view asks for the next 20 older ones, until the whole file is rendered. The host holds the loaded window per open conversation and extends it on request; the plugin's payload carries the window plus whether older turns remain.

## Proposed changes

**No config change.** `src/config.ts` and `src/config-decode.ts` are untouched, and `product/specs/application-config.md` gains no row. The selectable models come from `harness-models.json` through `modelsFor` — a file that already exists, already ships a default, and already takes a project-level override at `.janissary/harness-models.json` with the same load-with-fallback contract `config.json` has.

**ACP launch mapping, extracted.** The harness → `{ command, args, env }` mapping currently lives inside `spawnMonitorSession` (`src/monitor/acp.ts:16`), which takes a whole `Persona` — a name, a body, and a tools list this plan has none of. Move the mapping into a new `src/acp/launch.ts` exporting `acpLaunchFor(harness: PersonaHarness)`, returning `opencode acp` with `OPENCODE_CONFIG_CONTENT` for `opencode` and `npx @zed-industries/claude-code-acp` with `ANTHROPIC_MODEL`/`CLAUDE_THINKING_EFFORT` for `claude`, exactly as today. `spawnMonitorSession` then calls it and keeps its own signature and behavior; the conversations path calls it directly. The same module takes over the `MARKDOWN_INSTRUCTION` constant currently declared module-locally in `src/acp/manager.ts:26` — it says how a reply is rendered, which is now two surfaces' concern rather than one — and `AcpManager` imports it instead of declaring it.

**`WorkspaceManager` is deliberately not involved, and `src/workspace/` gains one parameter.** `provisionWorkspace` (`src/workspace/index.ts:130`) clones the project's `origin`, which is precisely what a conversation must not get, and `WorkspaceManager`'s whole contract is the opposite of what a durable workspace needs: refcount a clone, delete it when the last tab wanting it closes, sweep everything at shutdown (`src/workspace/manager.ts:62`, `:83`). A conversation's workspace must outlive the process, so the conversations store owns its directories outright and neither module gains a conversations entry point. What is reused is the two location-independent helpers: `trustWorkspace(dir, claudeJson)` (`:72`) on ensure, and `untrustWorkspace(dir)` (`:182`) on delete. The one change to `src/workspace/index.ts` is to give `untrustWorkspace` the same optional `claudeJson` parameter `trustWorkspace` already takes — it hardcodes `path.join(homedir(), '.claude.json')` today, which makes the delete path untestable against a temp file and is an asymmetry with no reason behind it.

**Conversation sessions.** A new `src/conversations/sessions.ts` owning one ACP session per conversation id, modelled directly on `EditorAcpManager` (`src/editor/acp-manager.ts`) — lazy connect on first use, reuse thereafter, `has(id)` so the caller can tell a first query from a later one, `close(id)`, and a `dispose` that kills everything. Its `session(id, pair, workspaceDir, hooks)` calls `connectAcp({ ...acpLaunchFor(pair), cwd: workspaceDir, workspaceDir, onError, onConnect })` with `allowedTools` deliberately omitted, which is what makes the session tool-less. `offline` is deliberately never set: it is a per-tab flag on the `agent`/`harness` commands (`src/agent/commands.ts:31`), not a global mode, and a conversation is a network call by definition — so nothing is being overridden. This is its own module rather than part of the manager so `manager.ts` stays inside the 200-line limit, the same split `ai/guidelines/code-guidelines.md` asks for.

**Conversation store.** A new `src/conversations/store.ts` owns `~/.janissary/conversations/` and everything under it, resolved through the same home injection point `initGlobalHistory` (`src/global-history.ts:41`) takes for testability. It lists conversation summaries — id, title, last activity — by scanning that directory for subdirectories and parsing each one's `conversation.json` the **first time the list is asked for**, not at startup: the plugin activates lazily and a user who never runs `chat` should pay nothing, per `ai/guidelines/plugins.md` §6. The summaries are then held in memory and updated in place as conversations change. It also reads a whole conversation on demand and writes one atomically through `src/atomic-write.ts`. The scan is a linear parse of one file per subdirectory; that is fine at the scale a single user's conversation history reaches, and the upgrade path if it ever isn't is a summary index file at the top of the tree — not needed now and deliberately not built. A subdirectory whose `conversation.json` is missing or malformed is skipped with a one-time warning and left untouched on disk, which covers a half-created directory as well as a corrupt one and matches how a corrupt `config.json` and a corrupt `history.json` are already handled; a stray file at the top level is ignored. The persisted shape carries its own `schemaVersion`, since it outlives the process (`ai/guidelines/plugins.md` §4).

The store also owns the workspace half of each conversation directory, since it is what knows the layout. `ensure(id)` creates `<id>/`, `<id>/workspace/`, and `<id>/workspace.tmp/` if absent and calls `trustWorkspace` on the workspace, returning its absolute path; it is idempotent and cheap, so the manager calls it on every session connect rather than tracking whether this run created it. `delete(id)` calls `untrustWorkspace` on the workspace and then removes `<id>/` recursively, so the stored turns and the workspace go together. Nothing else in the codebase removes anything under this tree.

**Conversations manager.** A new `ConversationsManager` at `src/conversations/manager.ts`, added to `ManagerRegistry` (`src/managers.ts:30`) as `conversations` and constructed in `src/controller/create-managers.ts`, with a `dispose` that kills every session through the sessions module's own `dispose` and removes nothing from disk — the workspaces are durable and outlive the process by design. It owns the store, the sessions module, the per-conversation loaded window, and the set of conversations with a turn in flight, and it is the only thing that fires the new host topic. Its methods cover: create (given an id minted by the plugin), load a window, extend a window backwards, send a query on a conversation, cancel one, set a conversation's `<harness>:<model>` pair, and delete a conversation.

Sending calls the store's `ensure(id)` for the conversation's own workspace, appends the query to the in-memory conversation, gets or connects the conversation's session against that workspace, and calls `session.prompt` — with the Markdown primer and the replay of up to the 20 most recent stored turns prepended when the session was not already alive, and with the query alone when it was. `onChunk` accumulates onto the in-memory turn and fires the topic at most once per 100 ms; `onEnd` writes the file atomically and fires once more; `onError` records the failure on the turn, forgets the session, writes, and fires. It refuses a send for a conversation that already has one in flight. Cancelling closes the session through the sessions module and discards the partial without writing. Setting the pair closes the session too, so the next query connects under the new one.

**Plugin API additions.** All additive, so `TAB_PLUGIN_API_VERSION` stays at 1 (`src/plugins/api.ts:3`, and the comment at `:22` that keying `CAPABILITIES`/`NOTIFICATION_TOPICS` by the union makes a missing entry a compile error rather than a silent gap — add `conversations: true` to `NOTIFICATION_TOPICS` at `:66`). `TabPluginNotificationTopic` (`:62`) gains `'conversations'`; `TabPluginNotification` (`:80`) becomes a discriminated union on `topic` whose new member carries the conversations slice; and `TabPluginTopicAction` (`:90`) gains the conversation actions listed above, each tagged `topic: 'conversations'` so the grant stays tied to the declared topic. The wire-facing view types for the slice — a conversation summary, a turn, and a loaded window — are defined in `src/protocol.ts` and re-exported from `src/plugins/api.ts` beside `AggregatedScheduleView` (`:249`), since the plugin import boundary forbids a plugin reaching into `../protocol.js` directly (`eslint.plugin-boundaries.mjs:33`). `src/plugins/api.ts` measures 135 lines against the 200-line `max-lines` budget, which leaves room for these additions; the view types go in `src/protocol.ts` (52 lines) rather than in `api.ts` to keep it that way.

**Topic table.** Two changes in `src/plugins/topics.ts`. Add a `conversations` entry to `TOPIC_SOURCES` (`:43`) whose `subscribe` is `messageBus.on('conversations', 'changed', fire)`, whose `read` returns the manager's current slice, and whose `act` is a `actOnConversations` switch modelled on `actOnSchedules` (`:27`) — one case per conversation action, each delegating to a `ConversationsManager` method. Add the matching `conversations: ConversationsEvent` channel to `BusChannels` in `src/bus.ts:105`, with `type ConversationsEvent = { type: 'changed' }` beside `ScheduleEvent` (`:104`).

Because `TabPluginNotification['data']` stops being a single array type, two things follow and both are decided here rather than left to the implementer. First, `TopicSource.read` (`src/plugins/topics.ts:15`) and `readTopicData` (`:55`) return the union, and the plugin narrows it with its own guard — the same way `activate.ts` already guards its tab payload. Second, the `topicData` capability currently returns the literal `[]` when the plugin is disabled (`src/plugins/context.ts:148`), which only typechecks while every topic is array-shaped: give `TopicSource` an `empty` field holding that topic's own zero value and return `TOPIC_SOURCES[topic].empty` instead. Nothing else in the dispatch path branches per topic, so `src/plugins/notifications.ts` is unchanged.

**Server plugin.** `src/plugins/chat/` with `manifest.ts` (id `chat`, `tabLabelPrefix` `chat`, no file extensions, `command: 'chat'`, `notifications: ['conversations']`, and the capability set schedules already uses: `openOrFocusTab`, `updateTab`, `dockTab`, `topicData`, `topicAction`, `rejectRequest`, `reportFailure`), `shared.ts` (payload schema version, the list and conversation payload types, and their guards — the module the client imports through `@shared/plugins/chat/shared`), and `activate.ts`. Activation parses the command as schedules does, extended with the title-lookup branch; answers the intents below; and, on a topic notification, updates the list tab and every open conversation tab from the slice it was handed. Add the manifest to `src/plugins/catalog.ts` and the loader to `src/plugins/loaders.ts`.

Intents, each validated by a guard in `shared.ts` and each turning into one topic action: `create` (the plugin mints the id, asks the host to create it, and immediately opens a tab under that id — the host refuses an id it already holds), `open`, `load-older`, `send`, `cancel`, `select-model`, and `delete`. Anything else is a `rejectRequest`. A tab payload that fails the plugin's own guard is a `reportFailure`, as it is in schedules.

**Client plugin.** `web/src/plugins/chat/` with `index.tsx` (the default component plus the `isPayload` guard, dispatching on which payload shape it received), `ConversationList.tsx` (rows with title and last activity, the new-conversation entry, the empty line, and the delete confirmation), `ChatTab.tsx` (header with the title, the model dropdown, and the host-rendered split action, above the turn list and the composer), a keys module for the **list's** row selection mirroring `web/src/plugins/schedules/schedules-keys.ts`, and `chat.css`. The conversation tab gets no keys module of its own — its only chord is Escape-to-cancel, which is one handler in `ChatTab.tsx`. The header uses the shared plugin look from `web/src/plugins/shared.css` rather than restating it, and the model dropdown is a native `<select>` of the catalogued `<harness>:<model>` pairs, grouped by harness with `<optgroup>`: the platform already gives keyboard navigation, type-ahead, and grouping, so nothing custom is built for it. Every offered pair is selectable — availability is not knowable before a spawn, so there is nothing to disable. Register the lazy entry in `web/src/plugins/registry.tsx` with the schema version literal, and pin that literal against `shared.ts`'s constant in `registry.test.tsx` as the other plugins do.

**Markdown rendering.** Responses render as sanitized Markdown. Rather than add a third copy of the `marked` + `DOMPurify` call, move the plugin-layer copy to `web/src/plugins/markdown-render.ts` and re-export `renderMarkdown` from `web/src/plugins/api.ts`; the markdown plugin and the chat plugin then both import it from `../api`, which is what the client boundary already permits. Core's `web/src/shared/transcript/markdown.ts` stays where it is — the boundary genuinely forbids a plugin reaching it.

**Ordering.** Land in five checkpoints so typecheck and tests stay green at each. First the two changes to existing modules, which stand alone and alter no behavior: the `src/acp/launch.ts` extraction with `spawnMonitorSession` and `AcpManager` rewired onto it, and the optional `claudeJson` parameter on `untrustWorkspace`. Second the types: the conversation view types in `src/protocol.ts` and the API additions in `src/plugins/api.ts` — inert on their own but referenced by everything after. Third the host: the store, the sessions module, the manager, its `Managers` entry, the bus channel, and the `TOPIC_SOURCES` entry with the `empty` change; at this point the topic exists and is exercisable by tests with no plugin present. Fourth the server plugin and its catalog and loader entries. Fifth the client chunk, together with the markdown-renderer move — doing the move in its own commit ahead of the client work is also fine, since it touches only the markdown plugin and `web/src/plugins/api.ts`. Every new `src/` import carries the `.js` extension per the NodeNext rule, catalog and metadata lookups use `??` rather than `||` to satisfy `prefer-nullish-coalescing`, and the parsed JSON of a conversation file is narrowed by a guard rather than asserted, to stay clear of `no-unsafe-assignment` and `no-unsafe-member-access`.

**Specs.** Add `product/specs/conversations.md` describing the command grammar, both tabs, model selection, streaming, failure and cancellation, the per-conversation sandboxed workspace the agent runs in, what deleting a conversation removes, storage, and profile behavior. Add the bundled-plugin section to `product/specs/tab-plugins.md` beside the schedules one, and note the new topic and its actions in the "Being told when host state changes" section. Add a line to `product/specs/sandbox.md`'s "What gets sandboxed" recording that a conversation's ACP agent is confined to a workspace that belongs to no tab and is not swept at shutdown — the first sandboxed spawn with neither a tab nor a project-level workspace behind it. Note in `product/specs/acp.md` that the `acp` command's per-tab session and a conversation's session are separate uses of the same channel, with no tool loop on the conversation side. `product/specs/application-config.md` is untouched — this plan adds no setting.

## Out of scope

- **Multi-model fan-out.** A query goes to exactly one `<harness>:<model>` pair. Sending one query to several at once, and any side-by-side or stacked comparison of their answers, is deferred.
- **Tool use and attachments.** The session is spawned tool-less and stays that way: no tool or function calling, no file or image attachments, and nothing resembling the `db`/`browser` loop the `acp` command drives — `runAcpToolLoop` is deliberately not reused. A query is text in, text out. This is also what makes the empty workspace sufficient rather than merely tidy.
- **Search, export, and usage statistics.** No searching across conversations, no export command, and no token or cost accounting — the separate `centralized model selection and usage statistics` backlog item covers the latter.
- **A third harness.** Selection is restricted to the two harnesses that already speak ACP, `claude` and `opencode`. `codex` appears in `harness-models.json` but has no ACP adapter wired up, so its models are filtered out rather than offered and failing.
- **Remote conversations.** A conversation's agent always runs on this machine, in this machine's empty workspace. The remote ACP path (`src/remote/serve-acp.ts`, `createRemoteAcpSession`) exists and is deliberately not used — a conversation has no working tree, so there is nothing a remote host would give it.
- **A connections-panel row for a conversation's session.** The panel is per tab and shaped around a tab's own session (`AcpManager.has`, `EditorAcpManager.connectionsFor`); giving a plugin tab a row is its own piece of work.
- **Renaming a conversation.** Titles are derived from the first query and never change.
- **Sharing one workspace between conversations.** Rejected rather than deferred: it would put every conversation's agent inside one carve-in, and it has no home that survives with any single conversation.
- **Garbage-collecting workspaces.** A conversation's workspace is removed when that conversation is deleted and at no other time — no size cap, no age-based sweep, no `chat` subcommand to clear one. The session is tool-less, so nothing should be accumulating there in this version.
- **Seeding a workspace with anything.** It is created empty and stays that way unless an agent writes to it. No README, no project files, no copied configuration.
- **`--relaunch` restore.** Chat tabs are live view tabs like every other plugin tab; the conversations on disk survive, the open tabs do not.
- **Thinking-block display.** Whatever reasoning the model does is not rendered; only the response text ACP streams as `agent_message_chunk` is.

## Open questions

- **Editing or resending a past turn.** This was offered as a candidate for deferral and was not selected, so it is genuinely unresolved. The plan as written treats a conversation as append-only from the user's side — no editing a previous query, no branching, no regenerate. If that is wrong, the affected pieces are the conversation payload (turns need addressable ids on the wire), one more intent and topic action, and the store's rewrite path.
- **An open tab whose conversation is deleted from the list.** Deleting is confirmed and removes the file, but the behaviour of a conversation tab that is open at that moment was not settled. Proposed default, pending confirmation: the tab stays open showing what it already had, with the composer disabled and a line stating the conversation was deleted; it is closed by the user like any other tab.
- **Whether the replay should be the whole conversation rather than twenty turns.** Replaying the most recent twenty ties the primer to the window the view opens on, which is tidy but arbitrary — a long conversation whose session was killed silently loses its early context, and the user has no signal that it happened. The alternatives are replaying everything (unbounded prompt growth) or telling the user the session restarted. Worth settling before implementation.
- **Whether the delete confirmation must say the workspace goes too.** Deleting a conversation now removes a durable working directory along with the transcript. In this version the session is tool-less so that directory should be empty, and the existing `DeleteScheduleDialog`-shaped confirmation says nothing about it. If a conversation is ever given a tool, the dialog is understating what it destroys, and the honest fix — naming the workspace, or naming it only when it is non-empty — is worth deciding now rather than after someone loses something.
- **An open tab whose conversation directory disappears underneath it.** The store tolerates a missing or malformed `conversation.json` when listing, but the behaviour of a conversation tab that is open when its directory is removed by something outside the app was not settled. It is the same shape as the deleted-from-the-list question above and probably wants the same answer.
