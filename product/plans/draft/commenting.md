# Commenting

**Complexity: 5/10** — a new client-side plugin subsystem: a contract, a lazily-loaded registry, chord resolution that must never shadow a core binding, and an edit applier that is a real trust boundary — plus the commenting plugin written against it. It spans only the web project, adds no protocol surface beyond a single fire-and-forget failure report, and leaves `src/plugins/` and `web/src/plugins/` untouched.

The editor tab has no way to comment out code, and no way for anything outside the editor to add an editing command at all. Cmd+/ is unbound at every level — absent from `metaAction` (`web/src/editor/keys.ts:33`) and from the window-level chord tables — so pressing it does nothing. This plan introduces a **new kind of plugin: an editor plugin**, whose contract is *"bind a chord, transform the editor"*: the declaration names a keyboard chord and how much of the buffer the handler needs, and the handler returns the edits to make and where to leave the selection. Commenting is its first member and `Cmd+/` its first chord.

**Editor plugins are implemented entirely on the client.** Declarations, handlers, and the commenting transform all live under `web/src/editor-plugins/`, loaded lazily in the browser. There is no server host, no plugin process, and no request-response on a keypress: a chord fires, the module is already loaded (or is fetched once), the handler runs in-process, and the edit applies. The one thing that crosses to the server is a single fire-and-forget report when a plugin breaks, so a failure still reaches the notifications tab rather than dying silently in the console.

This is a different family from the tab plugins in `src/plugins/`, not an extension of them. That contract is tab-shaped — a declaration claims file extensions for the `open`/`edit` verbs, names a tab label prefix, carries a payload schema version for the payload it ships to its own React body, and every client-to-plugin request is addressed to a plugin's own tab. An editor plugin has none of those things.

## Design decisions

**An editor plugin binds a chord and returns an edit.** The unit of contribution is a *binding*: a chord, a command name, and a declaration of how much of the buffer the handler needs. When the chord fires, the host calls the handler with the requested slice, the current selection, and the file's name; the handler returns a list of range replacements and an optional new selection, or nothing. That is the whole extension point. Commenting declares one binding; a later plugin could declare several, and nothing about the contract is specific to comments.

**The family lives in `web/src/editor-plugins/`.** A top-level client family directory, sibling to `web/src/plugins/` (the tab family's client surface) and named for what it extends, the way `web/src/editor/` is. There is no `src/editor-plugins/` — nothing about an editor plugin runs on the server.

**Running on the client is what makes the contract cheap.** The alternative considered and rejected was a server-side family with the handler reached over an RPC: that costs a round trip on every chord press, a protocol domain, a host, a `Managers` entry, five wiring edges, and a second server plugin family whose machinery would have to be shared with the first. Client-side, the handler is a function call. The editor already owns the buffer, the selection, and the undo stack, so the plugin operates on the data where it lives instead of describing it across a socket twice per press.

**Declarations are a static client module; implementations are lazy.** `web/src/editor-plugins/registry.ts` holds the declaration table as literals plus a loader map of `() => import('./<id>/index')` thunks. The chord table is therefore available synchronously at the first keypress with no plugin code loaded and no request made, which is section 3 of `ai/guidelines/plugins.md` ("declare statically, activate lazily") expressed in the browser. The registry must never statically import an implementation module: doing so pulls the plugin's chunk into the entry bundle and silently defeats the lazy loading, which is the exact trap `web/src/plugins/registry.tsx:67` documents and its `registry.test.tsx` pins. The new registry gets the same guard.

**The first matching press awaits the chunk; later presses do not.** No plugin module is fetched until its chord is first pressed. That press awaits the dynamic `import()`, caches the resolved module for the session, and applies the edit; every later press on any editor tab calls the already-loaded handler directly. A session that never presses a plugin chord never downloads a byte of plugin code.

**Core key bindings always win; a plugin may only claim a chord the editor leaves unbound.** `EditorTab.onKeyDown` already asks `actionForKey` first (`web/src/editor/EditorTab.tsx:127`) and returns early when it answers null. The plugin chord table is consulted only in that null case, so no plugin can shadow Cmd+S, Cmd+Z, or any Emacs-subset chord. A declared chord the core table does claim would simply never fire, so the host reports it once through the failure path rather than leaving it silently dead — a broken plugin must never be indistinguishable from an absent one.

**A declared chord must carry Cmd or Ctrl, enforced when the registry is validated.** `plainAction`'s default turns any single printable character into an insert (`web/src/editor/keys.ts:87`), so `actionForKey` effectively never returns null for an unmodified key. A chord without a modifier could therefore never fire, and declaring one is a plugin-authoring mistake caught at validation rather than discovered by a user pressing a key that types a character instead.

**`web/src/editor/keys.ts` and `applyKeyAction.ts` are not modified.** Because resolution is core-first with the plugin table consulted only on a null answer, there is no new `KeyAction` variant, no `case '/'` in `metaAction`, and no branch in the applier. The entire binding lives in the registry and one new branch in `onKeyDown`. That branch calls `preventDefault()` itself, since the existing early return on a null action deliberately does not.

**A binding declares the slice it needs.** `needs: 'selection'` passes the selected range's text and that range; `needs: 'buffer'` passes the whole document. The host passes exactly that and no more. Even in-process this matters: it is what lets a plugin's contract state its own reach, so a reviewer can see from the declaration alone that commenting never reads the rest of the file. Commenting declares `'selection'`; a future select-next-occurrence command would declare `'buffer'`.

**With no selection, a `'selection'` request passes the caret's line.** The slice is never empty and the plugin never has to special-case "nothing selected" — it always receives a range with text in it. This is also exactly the behavior commenting wants, where Cmd+/ with no selection comments the caret's line.

**The request carries the file's name so a plugin can branch on language.** That is how commenting picks `//` for `.ts` and `#` for `.rb`, and it is why the declaration has no language or extension field: the extension-to-marker table is entirely the commenting plugin's own business. A plugin that does not care about the file type ignores the field.

**Edit positions are always absolute document coordinates.** Even when a plugin asked for only the selection, the request states the document range that slice came from, and every position the plugin returns is interpreted against the whole document. One coordinate system end to end removes the class of off-by-one bugs a slice-relative system invites, at the cost of the plugin doing one addition.

**A plugin may change text and selection, and nothing else.** The result carries range replacements and an optional new selection. There is no save, scroll, rename, close, or open effect, and the plugin is handed no capability object that could reach any of them — everything it is allowed to do travels in its return value. Scrolling needs no effect of its own: setting the cursor scrolls the caret into view through the behavior the editor already has for every cursor move (`product/specs/editor-tab.md`, "Scrolling"). Widening this set later is an additive change.

**Edits apply back-to-front, atomically, as one undo step.** The host sorts the returned edits by start position and applies them from the end of the document backwards, so an earlier edit never shifts a later edit's coordinates. However many ranges a result touched, Cmd+Z restores all of them at once, recorded as the `'other'` edit kind (`web/src/editor/undo.ts:7`) that `applyKeyAction` already uses for every discrete, non-coalescing edit.

**A malformed result is discarded whole and disables the plugin.** An edit naming a position outside the document, or two edits whose ranges overlap, cannot be applied meaningfully, and silently clamping or dropping one would corrupt the user's text without telling anyone. The result is validated against the buffer before anything is touched: on any violation the buffer, selection, and undo stack are left exactly as they were and the plugin is disabled for the session. This is the one place an editor plugin can lose the user's trust, so it fails loudly and changes nothing.

**A `null` result is a silent no-op.** A plugin that has nothing to do — commenting in a `.log` file, an unknown extension, a file with no extension — returns nothing. The buffer is untouched, no undo step is recorded, and no message appears anywhere, matching how the editor already treats a file it cannot syntax-highlight.

**A failure disables that plugin for the session and reports one line to notifications.** A loader that fails to fetch, a handler that throws or rejects, a handler that exceeds its time budget, or a malformed result all disable the plugin: its chords stop resolving and the editor keeps working exactly as it did before it existed. The failure is reported once through a new fire-and-forget `editorPluginFailed` RPC carrying the plugin id, the reason, and the editor tab's `url` — modeled directly on the tab family's `pluginFailed` (`src/message-handler.ts:91`), which exists for the same reason: a client-side plugin's failure has to reach server-owned state to be seen. The server resolves the owning tab with the existing `ownerLabel` helper and calls `notify(managers, 'plugin-failure', …)`, so the line lands in the notifications tab reading `Editor plugin "commenting" disabled: <reason>.` Repeat reports for an already-disabled plugin are dropped client-side, exactly as `web/src/plugins/api.ts:76` deduplicates its own.

**The time budget bounds an async handler, not a synchronous one — stated plainly.** A handler returning a promise is raced against a timeout and a slow plugin is treated as failed. A handler that blocks synchronously cannot be interrupted, and because this runs on the UI thread it would hang the window rather than one request. That is not defended against: bundled editor plugins are trusted code shipped in this repo, per section 8's rule to document the trust level honestly rather than overclaim. The server-side tab host has the same gap in its own `guardPluginCall` — a synchronous loop outruns an `AbortSignal` there too — but the consequence there is a stalled request, and here it is a frozen tab.

**`Pos` stays where it is.** With nothing crossing the boundary but strings, the editor's own position and selection types remain client-only in `web/src/editor/model.ts` and no wire type is introduced for them. The previous server-side design would have had to move `Pos` into the protocol and re-export it; that is no longer needed and no protocol type is added at all beyond the failure RPC's params.

**Duplicate chord claims are refused when the registry is validated.** Two editor plugins claiming Cmd+/ is a conflict: the first claimant in registry order keeps it, the loser contributes nothing and starts disabled with the recorded reason, and the editor still works. This mirrors how `createPluginOpeners` resolves a duplicate extension claim (`src/plugins/opener-adapter.ts:16`) — recorded, not thrown, so one bad manifest never takes the surface down. Because duplicates are refused, array position never breaks a tie beyond that first-wins rule.

**`src/plugins/` and `web/src/plugins/` are untouched.** No shared plugin primitive is generalized, no tab declaration changes, no client loader registry is relaxed, and `TAB_PLUGIN_API_VERSION` does not move. The two families share ideas and no code; the ~13-line timeout race is written once for the client rather than lifted out of `src/plugins/guard.ts`, because sharing a runtime value across the boundary means adding a fourth `@shared` path in three alias declarations (`web/tsconfig.json`, `web/vite.config.ts`, `vitest.config.ts`) for a function that short.

**The `plugins` command stays tab-only.** It reads the server host's declarations (`src/commands/plugins.ts:31`), and the server never loads or knows about editor plugins, so it cannot report their state without the client pushing a status it does not otherwise need to send. A broken editor plugin surfaces in the notifications tab, which is one of the three places section 7 names for exactly this. Listing editor plugins there is deferred rather than faked.

### Commenting, as an editor plugin

**One binding: Cmd+/, `needs: 'selection'`.** Everything below is the commenting plugin's own behavior, implemented in a pure module inside it and covered by its own tests. None of it is part of the editor-plugin contract.

**Cmd+/ toggles whole lines.** The plugin expands the received range to whole lines and acts on that. It uncomments when every non-blank line in the range already starts with the language's line marker, and otherwise comments. Since a request with no selection carries the caret's line, the no-selection case needs no special handling.

**Commenting is additive, not normalizing.** A range holding both commented and uncommented lines comments: every line gains a marker, including the ones that already had one, which end up with two. The inverse press removes exactly one from each and the range is back where it started, so the toggle is a pure inverse of itself at every step.

**Blank lines inside the range are commented too**, so the commented block reads as contiguous. They are excluded from the all-commented test that decides direction — a range of two commented lines separated by a blank still uncomments.

**A marker is followed by one space; uncommenting removes at most one.** `const a = 1;` becomes `// const a = 1;`. Uncommenting removes the marker and one following space when there is one, so a comment hand-written without a space survives the round trip.

**The marker is placed at the shallowest common indent** — the first non-whitespace column of the least-indented non-blank line in the range — and every line including blanks receives it at that column, left-padded where the line is shorter. Code keeps its relative indentation and markers line up. Uncommenting removes the first marker occurrence wherever it sits, so a hand-edited block still uncomments cleanly.

**Block-only languages wrap the whole range in one pair.** Markdown, HTML, and CSS have no line comment, so the toggle wraps the range in a single pair — `<!-- ` before the first line's content, ` -->` after the last line's — and unwraps it on the inverse press. "Already commented" for a block language means the range is exactly wrapped, so a range with a stray marker inside wraps again.

**The returned selection covers the same whole lines**, so a second press is the exact inverse of the first. With no selection the result leaves the caret on its line, shifted by the marker's width.

**Twelve languages, resolved by extension, entirely inside the plugin.** `.js`/`.mjs`/`.cjs`/`.jsx`, `.ts`/`.tsx`/`.mts`/`.cts`, and `.json` use `//`; `.rb`, `.sh`/`.bash`/`.zsh`, `.txt`, `.py`, and `.yml`/`.yaml` use `#`; `.md`/`.markdown` and `.html` use `<!-- -->`; `.css` uses `/* */`. Matching is case-insensitive. `.json` gets `//` deliberately: the result is JSONC rather than strict JSON, which is what a user commenting out a config line wants. Any other extension returns `null`.

## Proposed changes

**The contract.** A new `web/src/editor-plugins/api.ts` exporting `EDITOR_PLUGIN_API_VERSION` (1); an `EditorPluginDeclaration` (`id`, `version`, `apiVersion`, `bindings`); an `EditorPluginBinding` (`command`, `chord`, `needs: 'selection' | 'buffer'`); an `EditorChord` (`key`, and optional `meta`/`ctrl`/`shift`/`alt`); an `EditorPluginRequest` (the command name, the file name, the selection, the document range the slice came from, and the slice's lines); an `EditorPluginEdit` (`start`, `end`, `text`, all in absolute document coordinates); an `EditorPluginResult` (`edits`, optional `selection`); and an `EditorPluginModule` — what a lazily-imported implementation must default-export, namely a `run(request)` returning a result, `null`, or a promise of either. Its trailing comment documents the extension point's four required properties the way `src/plugins/api.ts:251` does for the tab family: resolution is first match by exact chord with duplicates refused at validation; ordering never depends on array position beyond first-wins; the handler is awaited under a per-call budget; and a `null` return means the plugin chose to do nothing, indistinguishable in effect from no plugin claiming the chord. The API version is declared and checked even though both sides ship together, because it is what makes a future out-of-tree plugin's compatibility checkable rather than assumed.

**The registry.** `web/src/editor-plugins/registry.ts` holding the declaration table as literals and a loader map of `() => import('./<id>/index')` thunks keyed by plugin id, mirroring `web/src/plugins/registry.tsx:32` in shape and in the constraint its comment at `:67` records: no implementation module may be statically imported here, or its chunk lands in the entry bundle. A `validate` function checks each declaration once — API version match, at least one binding, every chord carrying Cmd or Ctrl, no duplicate chord across plugins — and records a rejection per plugin rather than throwing, so one bad manifest disables that plugin and leaves the rest working.

**The host.** `web/src/editor-plugins/host.ts` holding the session-scoped state: a per-plugin record (declared, loaded, or disabled with a reason), a `bindings()` accessor answering the validated chord table without loading any implementation, a `run(command, request)` that loads the module on first use, races the handler against its budget, and returns the result, and a `disable(id, reason)` that records the reason and reports it once. Load and call are individually guarded, so a throw, a rejection, a failed chunk fetch, or a budget overrun disables that plugin and leaves the editor and every other plugin running.

**Chord matching.** `web/src/editor-plugins/chords.ts` — pure: canonicalize a `KeyLike` (the shape `actionForKey` already takes, `web/src/editor/keys.ts:29`) and match it against the binding table, returning the binding or null. It also exposes the check that identifies a declared chord the core table already claims, so such a binding is reported rather than silently dead.

**The edit applier.** `web/src/editor-plugins/apply-edits.ts` — pure, and the trust boundary: validate a result against the buffer (every position within the document, no two edits overlapping) and, if sound, apply the edits back-to-front to an `EditorState` and set the returned selection. It returns either the new state or a validation failure, and never partially applies. This module gets the most adversarial tests in the change.

**The hook.** `web/src/editor-plugins/useEditorPlugins.ts` — reports any core-shadowed binding once on mount, and exposes the handler `onKeyDown` calls. That handler matches the chord, builds the slice the binding declared (the selected range's lines, the caret's line when there is no selection, or the whole buffer), awaits `run`, and on a sound result applies it through `apply-edits.ts` and records one `'other'` undo step. A rejected call or an unsound result leaves the buffer untouched and disables the plugin.

**The commenting plugin.** `web/src/editor-plugins/commenting/` holding `index.ts`, `syntax.ts`, and `toggle.ts`. `index.ts` default-exports the `run` handler: resolve the file's extension, return `null` when unknown, otherwise delegate to `toggle.ts`. `syntax.ts` holds the extension → comment-syntax table as data. `toggle.ts` is the pure transform and the only place the commenting rules live: given the range's lines, the range, and a syntax, it returns the edits and the new selection. It is pure and imports only `syntax.ts`, so it is tested directly and heavily. Split `line-comment.ts` and `block-comment.ts` out of it if it approaches the 200-line limit — the two strategies are independent and extract cleanly. The plugin's declaration — one binding, command `toggle-comment`, chord Cmd+/, `needs: 'selection'` — is a literal in `registry.ts`, not in this directory, so that reading the table never loads the plugin.

**Client wiring.** In `web/src/editor/EditorTab.tsx` (164 lines), add one branch to `onKeyDown`: after `actionForKey` returns null, ask the hook whether a plugin binding matches; if one does, `preventDefault()` and dispatch to it, otherwise return as before. `web/src/editor/keys.ts` and `applyKeyAction.ts` are not modified.

**The one server change.** Add `{ method: 'editorPluginFailed'; params: { url: string; plugin: string; reason: string } }` to `EditorRpcCall` in `src/protocol/editor.ts` (8 lines), with a comment in that file's established style noting it is fire-and-forget and exists so a client-side editor plugin's failure reaches the notifications tab. Add `editorPluginFailed: true` to the allowlist in `src/client-message.ts` (97 lines, alphabetical as that list is ordered); a validated fire-and-forget case in `src/message-handler.ts` (175 lines) shaped like `pluginFailed` at `:91`; a method on `EditorControllerAdapter` in `src/controller/editor-adapter.ts` (30 lines) that resolves the tab with the existing `ownerLabel(managers, url)` and calls `notify(managers, 'plugin-failure', label, …)` with the `Editor plugin "<id>" disabled: <reason>.` line; and the matching `declare` in `src/controller.ts` (130 lines). Nothing else on the server changes.

**Not affected — do not chase these.** `src/plugins/` is untouched in its entirety: no capability, declaration, host, catalog, loader, activation, or fixture changes, and `TAB_PLUGIN_API_VERSION` does not move. `web/src/plugins/` is untouched: an editor plugin has no React body, so `clientPluginLoaders`' exhaustive `satisfies Record<ProductionTabPluginId, …>` at `registry.tsx:39` stays as it is. `src/commands/plugins.ts` is unchanged. `src/profile/` reads tab declarations only.

**Specs.** Add a "Commenting" section to `product/specs/editor-tab.md` after "Syntax highlighting", and a short "Editor plugin bindings" section describing how a plugin chord resolves after the core table, that a plugin may change only text and selection, that a malformed result changes nothing, and that a broken plugin reports to notifications and stops responding. Add `product/specs/editor-plugins.md` describing the family the way `product/specs/tab-plugins.md` describes its own: what an editor plugin is, that it runs in the client, the declaration, bindings and chord resolution, the request slice, the result and its validation, lazy loading, and failure behavior. Add one sentence to `product/specs/tab-plugins.md` noting a second family exists and pointing at the new spec. `product/specs/comments.md` is about `##` stripping on the command line and is unrelated — leave it alone, and do not name the new spec "comments".

**Documentation.** Add `documentation/developer-documentation/editor-plugins.md`, structured like `tab-plugins.md` and led by the simplest working example — a declaration with one binding and a handler returning one edit — before the block-comment case, per section 12. State plainly that these run in the browser at the client's trust level and that a synchronous handler is not interruptible. Add the nav entry beside the "Tab plugins" item at `documentation/.vitepress/config.mts:142`, and a second pointer line at `ai/guidelines/plugins.md:5`. `src/plugins/documentation.test.ts` pins the *tab* page and is unaffected; the new page gets its own equivalent test.

**Ordering.** Land the contract and registry first, then the pure `chords.ts` and `apply-edits.ts` with their tests, then the host, then the commenting plugin, then the failure RPC end to end, then the hook, and finally the `onKeyDown` branch that switches it on. Typecheck stays green at each checkpoint, and nothing is user-visible until the last step. The new `src/` imports for the RPC carry the `.js` extension per the NodeNext rule; the client modules do not. Optional-field reads use `??` rather than `||` to satisfy `prefer-nullish-coalescing`.

- `web/src/editor-plugins/commenting/index.test.ts` — each of the twelve languages resolves to its expected syntax, matching is case-insensitive, an unknown extension returns `null`, and a file with no extension returns `null`.
- `web/src/editor-plugins/apply-edits.test.ts` — the trust boundary, tested adversarially: several edits apply back-to-front with correct final text; an edit whose position is past the last line is refused and nothing changes; a negative or reversed range is refused; two overlapping edits are refused; two edits that merely touch at a boundary are allowed; an empty edit list with only a selection change applies; a refused result leaves buffer, selection, and undo stack byte-for-byte unchanged.
- `web/src/editor-plugins/chords.test.ts` — Cmd+/ matches its binding; Cmd+Shift+/ does not match a binding declared without shift; a binding the core table already claims is identified rather than silently dead; canonicalization treats the same chord written two ways as one.

- `web/src/editor-plugins/host.test.ts` — `bindings()` answers the table without invoking any loader; a chord loads its module exactly once across two presses; a loader that rejects disables the plugin and reports once; a handler that throws, rejects, or exceeds its budget disables the plugin and reports once; a second failure from an already-disabled plugin reports nothing; disabling one plugin leaves another's chords working.
- `web/src/editor-plugins/useEditorPlugins.test.ts` — a matching chord passes the declared slice and no more; a `'selection'` binding with no selection passes the caret's line; a `'buffer'` binding passes the whole document; a `null` result changes nothing and records no undo step; a sound result is exactly one undo step; an unsound result leaves everything unchanged and reports the failure.
- `web/src/editor/EditorTab.test.tsx` — Cmd+S still saves and Cmd+Z still undoes with a plugin binding registered, proving core-first resolution; a plugin chord is inert while a suggestion is pending and inert while the agent query line holds focus; an unmatched chord still falls through to the browser as before.
- `src/message-handler.test.ts` — a valid `editorPluginFailed` reaches the controller; invalid params reply with an error and never reach it.
- A server test for the adapter method: the reported failure resolves the owning tab from its `url` and posts one `plugin-failure` notification naming the plugin and reason; an unknown `url` posts nothing and does not throw.
- A test pinning the new developer-documentation page to the code the way `src/plugins/documentation.test.ts` pins the tab page: the documented example declaration matches the contract's required fields, and it names its constants rather than repeating literals.

## Out of scope

- **A server-side editor-plugin host.** Nothing about an editor plugin runs on the server, and no plugin API, catalog, loader, or `Managers` entry is added there.
- **Listing editor plugins in the `plugins` command.** The server does not know them; failures surface in the notifications tab instead.
- **Effects beyond text and selection.** No save, scroll, rename, close, or open-another-file effect.
- **A rendering surface.** No plugin-drawn UI, overlay, menu entry, or React component. If an editor plugin ever needs to render, that is a new extension point and a new decision.
- **Reading or writing anything but the passed slice.** A plugin is handed data and returns data; it gets no capability object, no client, and no file access.
- **Editor plugin commands invoked any way but a chord.** No command-bar entry, no palette, no menu, no profile hook.
- **Chords with no modifier, and shadowing a core binding.** Both are refused, the first at validation and the second at resolution.
- **Defending against a synchronous runaway handler.** The budget bounds a promise, not a blocking loop; bundled plugins are trusted code.
- **Third-party or out-of-tree editor plugins.** Only the bundled `commenting` plugin ships. Nothing is loaded from disk or over the network beyond the app's own lazy chunks, and no way to install one is added. The API version exists so that future can be checkable, not because it is enabled here.
- **Multi-caret or multi-range selection.** The result carries one selection, because `EditorState` holds one anchor and one cursor. A plugin cannot express what the editor cannot represent.
- **Persisting a disabled plugin across a reload.** Disabling is session-scoped; a page reload starts every plugin fresh.
- **Other editor commands.** Indent/deindent, select-next-occurrence, and formatting are not written here, though the contract is shaped so each is a new plugin rather than a new extension point.
- **Normalizing a mixed range**, **comment-aware editing beyond the toggle**, **language detection beyond the extension**, **region-aware syntax inside a mixed file**, and **a configurable marker or spacing** — all commenting-specific, all deferred.
