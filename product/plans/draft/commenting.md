# Commenting

**Complexity: 7/10** — the toggle itself is a pure, easily-tested transform and the client side is two modules, but this introduces the app's **second plugin family**: an editor-plugin contract with its own API version, declaration, capability set, catalog, loaders, host, protocol domain, spec, and reference page, plus two small generalizations of the shared plugin primitives so the two families share one definition of activation and status rather than two.

The editor tab has no way to comment out code. Cmd+/ is unbound at every level — absent from `metaAction` (`web/src/editor/keys.ts:33`) and from the window-level chord tables (`web/src/useWindowKeys.ts` has no `/` case) — so pressing it in a buffer does nothing. This plan binds Cmd+/ to a whole-line comment toggle whose marker is chosen by the file's extension, and delivers the extension-to-marker knowledge through a **new kind of plugin: an editor plugin**, a contract that exists solely to contribute functionality to the editor tab. Commenting is its first member. The editor asks the host for a file's comment syntax the first time the chord is pressed in a tab, caches the answer for that tab's life, and applies the toggle as a single undo step.

The plugin family is the substance of the work. The existing contract in `src/plugins/` is entirely tab-shaped: a declaration claims file extensions for the `open`/`edit` verbs, names a tab label prefix, carries a payload schema version for the payload it ships to its own React body, and every client-to-plugin request is addressed to a plugin's own tab (`PluginIntentRequest.tab`, `src/protocol/plugin.ts:9`; `ownerOf` resolves it via `tab.plugin` at `src/plugins/requests.ts:45`). Commenting has none of those things — no tab, no payload, no client body, no file it opens — so every one of those fields would have to be declared empty, made optional, or worked around. It gets its own contract instead.

## Design decisions

**Commenting is an editor plugin, not a tab plugin.** Fitting it onto the tab contract required three changes whose only purpose was to let a tab plugin pretend it was not one: loosening the required `tabLabelPrefix` so a tabless plugin could omit it, declaring `fileExtensions: {}` and a payload schema version that nothing reads, and relaxing `clientPluginLoaders`' `satisfies Record<ProductionTabPluginId, …>` in `web/src/plugins/registry.tsx:39` because the plugin has no React body to register. A separate contract needs none of them: `src/plugins/` is left completely untouched apart from two shared primitives it already owns, and `web/src/plugins/` is not touched at all. This is the "one definition, one execution path" rule in section 13 of `ai/guidelines/plugins.md` applied to the declaration itself — a tab plugin declares tab things, an editor plugin declares editor things, and neither carries fields that are inert for it.

**Editor plugins live in `src/editor-plugins/`, a sibling of `src/plugins/`.** Not `src/plugins/editor/`: every directory directly under `src/plugins/` is one bundled tab plugin (`audio/`, `image/`, `markdown/`, `page/`, `schedules/`, `video/`), so a family directory there would read as a plugin named "editor". The sibling directory also mirrors `web/src/editor/` on the client side. `ai/guidelines/plugins.md` governs both families; its pointer line at `:5` ("For the concrete bundled tab-plugin contract, read [[plugins-tabs]]") gains a second pointer to the new reference page.

**The family is versioned independently.** A new `EDITOR_PLUGIN_API_VERSION`, starting at 1, governs whether an editor plugin loads, and moves on its own schedule under the section 4 rules — additive changes keep the integer, removals and renames increment it. `TAB_PLUGIN_API_VERSION` is not touched and neither is any tab declaration, which is exactly why the frozen tab fixtures in `src/plugins/fixture-v1/` must keep passing unchanged: that is the proof this change is additive rather than a tab-contract break wearing a new name.

**The declaration carries four fields and nothing else.** `id`, `version`, `apiVersion`, `capabilities`, plus the extension point's own `commentLanguages`. There is deliberately no `payloadSchemaVersion` — no payload crosses to a client, because an editor plugin has no client body — no `tabLabelPrefix`, and no `fileExtensions`, since an editor plugin never claims a verb and never opens anything.

**The v1 capability set is exactly two names: `rejectRequest` and `reportFailure`.** An editor plugin cannot open a tab, serve a file, register a route, write a snapshot, notify the user, or read host state. It answers questions the editor asks and nothing more. This is the narrowest capability object in the app and is the point of a second family rather than a wider first one — section 1 of the guidelines asks for a purpose-built context exposing only what the contract promises, and for commenting that promise is very small. Widening this set later is an additive API change and follows section 4.

**Cmd+/ toggles whole lines.** The chord expands the selection to whole lines and acts on that range. Uncomment when every non-blank line in the range already starts with the language's line marker; otherwise comment. With no selection it acts on the caret's line alone. It is bound in `metaAction` (`web/src/editor/keys.ts:33`) rather than at the window level so the existing `e.preventDefault()` at `web/src/editor/EditorTab.tsx:129` also suppresses whatever the browser would do with the chord. Ctrl+/ is left unbound, consistent with `ctrlAction` reserving Ctrl for the Emacs subset.

**Commenting is additive, not normalizing.** A range holding both commented and uncommented lines comments: every line in it gains a marker, including the ones that already had one, which end up with two. The inverse press removes exactly one marker from each and the range is back where it started. The toggle is therefore a pure inverse of itself at every step, rather than converging mixed ranges to a single state.

**Blank lines inside the range are commented too.** A blank line within the selected range receives the marker so the commented block reads as contiguous. Blank lines are excluded from the all-commented test that decides direction — a range of two commented lines separated by a blank still uncomments.

**A marker is followed by one space; uncommenting removes at most one.** Commenting inserts `<marker><space>`, so `const a = 1;` becomes `// const a = 1;`. Uncommenting removes the marker and one following space when there is one, and leaves the line otherwise untouched, so a line whose comment was hand-written without a space survives the round trip.

**The marker is placed at the shallowest common indent.** For a line-comment language the marker goes at the first non-whitespace column of the least-indented non-blank line in the range, and every other line in the range — blank lines included — receives it at that same column, left-padded with spaces where the line is shorter. Code keeps its relative indentation and the markers line up in a column. Uncommenting removes the first marker occurrence on each line wherever it sits, so a hand-edited block still uncomments cleanly.

**Block-only languages wrap the whole range in one pair.** Markdown, HTML, and CSS have no line comment. For them the toggle wraps the entire selected range in a single open/close pair — `<!-- ` before the first line's content, ` -->` after the last line's — and unwraps that same pair on the inverse press. "Already commented" for a block language means the range is exactly wrapped, so a range with a stray marker inside it wraps again rather than unwrapping.

**The selection survives the toggle.** After a toggle the selection still covers the same whole lines, so a second press is the exact inverse of the first. With no selection the caret stays on its line and shifts by the marker's width, keeping its position relative to the text.

**One toggle is one undo step.** However many lines the press changed, Cmd+Z restores all of them at once. The toggle records an `'other'` edit kind on the tab's `UndoBuffer` (`web/src/editor/undo.ts:7`), which is what `applyKeyAction` already uses for every discrete, non-coalescing edit (`web/src/editor/applyKeyAction.ts:53`), so it never merges into an adjacent run of typing.

**Twelve languages ship, resolved by extension.** `.js`/`.mjs`/`.cjs`/`.jsx`, `.ts`/`.tsx`/`.mts`/`.cts`, and `.json` use `//`; `.rb`, `.sh`/`.bash`/`.zsh`, `.txt`, `.py`, and `.yml`/`.yaml` use `#`; `.md`/`.markdown` and `.html` use `<!-- -->`; `.css` uses `/* */`. Matching is case-insensitive, as `languageForFile` already lowercases at `web/src/editor/highlight/registry.ts:27`. `.json` gets `//` deliberately: the result is JSONC rather than strict JSON, which is what a user commenting out a config line wants.

**Resolution is first match by exact lowercase extension, with duplicate claims refused at registration.** Two editor plugins claiming `.rb` is a conflict, resolved the way `createPluginOpeners` already resolves a duplicate extension claim (`src/plugins/opener-adapter.ts:16`): the first claimant keeps it, the loser contributes nothing and starts life already disabled with the recorded reason, and the app still starts. Because duplicates are refused, array position never breaks a tie. Claims are checked against other **editor** plugins only — an editor plugin claiming `.md` for commenting does not conflict with the markdown tab plugin claiming `.md` for opening, because the two families claim different things.

**The syntax comes from an activated handler, not from static declaration data — deliberately.** `commentLanguages` is a claim list only (extension → `true`); the syntax itself is produced by the plugin's `commentSyntax` handler at request time. Putting the syntax table straight into the declaration would let the host publish a merged table to the client and delete the handler, the RPC, and the activation entirely, which is a materially smaller build — it was considered and rejected, because a declaration-only extension point can never answer anything the host did not already know, and the editor-plugin family exists to prove a plugin can contribute *behavior* to a core surface. The ceiling this accepts is one round trip per file type per tab; the upgrade path, if that ever matters, is to let a declaration carry a static table the host serves without activating, keeping the handler as the fallback for plugins that need to compute an answer.

**The first press awaits; later presses do not.** No request is made when an editor tab opens. The first Cmd+/ in a tab fires the request that activates the plugin and awaits it, then applies the edit. The answer is cached per editor tab, keyed by extension, for that tab's life — including a `null` answer, so an unclaimed extension is never asked about twice. Activating this late means a session that never comments never loads the plugin, which is what section 6 of the guidelines asks for.

**An unavailable syntax is a silent no-op; a plugin failure is reported to notifications.** When the resolved syntax is `null` — an unknown extension, a file with no extension — Cmd+/ does nothing: buffer untouched, no undo step, no message, matching how the editor already treats a file it cannot syntax-highlight. When the plugin itself fails or is disabled, the host reports one line to the notifications feed through the existing `notify(managers, 'plugin-failure', …)` path (`src/notifications.ts`, event type already defined at `:28`), reading `Editor plugin "commenting" disabled: <reason>.` — the tab family's wording with its own noun, built from the shared `pluginFailureReason` helper so the two families trim and normalize a failure identically. The RPC carries the editor tab's label so the notification is attributed to the tab the chord was pressed in.

**Failure containment is simpler than the tab host's.** Disabling a tab plugin has to close that plugin's open tabs (`closePluginTabs`, `src/plugins/teardown.ts`). An editor plugin owns no tabs, no files, and no sockets, so disabling one records the reason, disposes the activation, reports the line, and stops. There is nothing to tear down, which is a direct consequence of the two-capability set above.

**The two families share their primitives rather than duplicating them.** Four things are already family-agnostic and are reused as they stand: `guardPluginCall` (`src/plugins/guard.ts`) for the per-call timeout, `pluginFailureReason` (`src/plugins/failure.ts:6`) for normalizing a thrown reason to one line, the `'plugin-failure'` notification event type, and the module-scope rejection registry (`src/plugins/rejections.ts`), which is keyed by plugin id and works for either family. Two need a small generalization, taken in this change rather than duplicated: `PluginRecord`/`recordStatus` (`src/plugins/status.ts`, 19 lines) gain type parameters for the declaration and activation types, and the load-race-timeout core of `activatePlugin` (`src/plugins/activate.ts:65`, 88 lines) is extracted into a shared helper taking a loader, a timeout, and a validate callback, so the tab family's declaration/activation validation stays where it is and the editor family supplies its own. Neither generalization changes tab-plugin behavior, which the frozen fixtures pin.

**`plugins` lists both families.** A broken editor plugin has to be visible somewhere, and the `plugins` command is where a broken tab plugin already is (`src/commands/plugins.ts:31`). It prints editor plugins after tab plugins, using the same `id version api=N state=… reason=…` line. `statusLine` takes the four fields both declarations share, so it needs no per-family branch.

**`Managers` gains an `editorPlugins` host.** Constructed in `src/controller/create-managers.ts` beside `managers.plugins` at `:43`, per section 10's rule that a long-lived subsystem appears in `Managers` and gets a `dispose`. Note for the implementer: nothing in production calls `TabPluginHost.dispose()` today either — it exists for parity and for tests — so there is no existing teardown call site to hook the new one into and none should be invented here.

**Cmd+/ obeys the editor's existing suppression rules, at no cost.** `handleSuggestKeyDown` runs before the buffer's own dispatch (`web/src/editor/EditorTab.tsx:126`), and both `applyMove` and `applyEdit` end in a `default` fall-through (`web/src/editor/applyKeyAction.ts:45`, `:71`). An unhandled `toggleComment` reaching the query-line surface via `suggest.applyQueryAction` is therefore already a no-op, and the pending-suggestion guard already swallows every keystroke. No new branch is written for either case; the tests below pin both.

## Proposed changes

**Generalize the two shared primitives first.** In `src/plugins/status.ts`, give `PluginRecord` and `recordStatus` type parameters for the declaration and activation types, and keep `TabPluginStatus` as the family-agnostic public shape it already is; the tab host's uses become the parameterized form with its own two types. In `src/plugins/activate.ts`, extract the load race, timeout, duration measurement, and late-arrival disposal from `activatePlugin` (`:65`) into a helper that takes a loader, a timeout, and a validate callback invoked on the resolved activation. `activatePlugin` keeps its current signature and passes its existing `validateDeclaration`/`validateActivation` in, so no tab behavior changes. Both files have ample room (19 and 88 lines). These land before anything else so the editor family can build on them rather than beside them.

**Protocol.** A new `src/protocol/editor-plugin.ts` holding a `CommentSyntax` type — a discriminated union of `{ kind: 'line'; marker: string }` and `{ kind: 'block'; open: string; close: string }`, mirroring how `KeyAction` discriminates in the editor it serves — and an `EditorPluginRpcCall` union with `{ method: 'commentSyntax'; params: { tab: string; extension: string } }`, answering `CommentSyntax | null`. Compose it into `src/protocol.ts` exactly as `src/protocol/plugin.ts` is composed at `:14`, `:20`, and `:64`. The client imports these through the `@shared` alias and never redeclares them in `web/src/`.

**The editor-plugin contract.** A new `src/editor-plugins/api.ts` exporting `EDITOR_PLUGIN_API_VERSION` (1), the `EditorPluginCapabilityName` union of `rejectRequest` and `reportFailure` with the same keyed-record trick `src/plugins/api.ts:26` uses so a name added to the union without a record entry is a compile error, an `EditorPluginRejection` error class, the `EditorPluginDeclaration` type described above, an `EditorPluginServerCapabilities` object carrying only those two functions, an `EditorPluginActivation` with the optional `commentSyntax` handler and an optional `dispose`, and the loader types. Its trailing comment documents the extension point's four required properties, as `src/plugins/api.ts:251` does for the tab family: resolution is first match by exact lowercase extension with duplicates refused at registration; ordering never depends on array position; the handler is awaited under a per-call budget; and a `null` return means this plugin has no syntax for that extension, indistinguishable in effect from no plugin claiming it.

**Family infrastructure.** `src/editor-plugins/catalog.ts` and `loaders.ts`, both exhaustively typed against a `ProductionEditorPluginId` derived from the catalog, mirroring `src/plugins/catalog.ts:12`. `src/editor-plugins/activate.ts` supplying the family's own declaration validation — API version match, capability names known, and a declaration naming `commentLanguages` without a `commentSyntax` handler refused, that last one modeled on the "claims a command but provides no handler" guard at `src/plugins/host.ts:93` — and calling the shared load helper. `src/editor-plugins/claims.ts` building the lowercase extension → plugin id index at registration and calling `rejectContribution` on a conflict. `src/editor-plugins/context.ts` constructing the two-function capability object. `src/editor-plugins/host.ts` holding `EditorPluginHost`: a records map seeded from the catalog and the rejection registry, `declarations` and `statusFor` accessors for the `plugins` command, a `commentSyntax(tabLabel, extension)` request method that resolves the claim, activates lazily, runs the handler through the shared guard, and disables the plugin on a throw, plus `dispose`. It will be substantially shorter than `TabPluginHost` (225 lines) because there are no openers, commands, notifications, selection actions, or tabs to close; if it nonetheless approaches the limit, split the request path into `src/editor-plugins/requests.ts` the way the tab family did.

**The bundled plugin.** `src/editor-plugins/commenting/` holding `manifest.ts`, `shared.ts`, and `activate.ts`. The manifest declares `id: 'commenting'`, the `commentLanguages` claim map covering the twelve languages, and the two capabilities. `shared.ts` holds the extension → syntax table as data, read by both the manifest (for its claim list) and the activation, so there is one definition rather than two that can drift — the same reason `video/activate.ts:18` reads its own manifest. `activate.ts` exports `activate()` returning the `commentSyntax` handler and nothing else. Module top level stays free of side effects, and discovery imports only the manifest.

**Host wiring.** Add `editorPlugins: EditorPluginHost` to `Managers` (`src/managers.ts`, 56 lines) and construct it in `src/controller/create-managers.ts` beside `managers.plugins` at `:43`. Add a `commentSyntax` adapter method in `src/controller/` — a new `editor-plugin-adapter.ts` beside `plugin-adapter.ts`, which is 17 lines and belongs to the tab family — and the matching `declare` line in `src/controller.ts` (130 lines). Add `commentSyntax: true` to the allowlist in `src/client-message.ts` (97 lines, alphabetical as that list is ordered) and a validated case in `src/message-handler.ts` (175 lines) following the deferred-reply shape `projectFiles` already uses at `:148` — an awaited call inside a `try`/`catch`, replying with the result or the caught message as an `error` — rather than `pluginIntent`'s longer `.then(…, …)` block at `:70`, so the case costs about eight lines and needs no extraction.

**`plugins` command.** Widen `statusLine` in `src/commands/plugins.ts` (32 lines) to accept the four fields both declarations share, and print `managers.editorPlugins.declarations` after `managers.plugins.declarations`, each with its own `statusFor` lookup — reading the hosts' own declaration lists rather than the catalogs, for the reason already recorded in that file's comment at `:29`.

**Client — the toggle itself.** A new `web/src/editor/comment/`:

- `toggle.ts` — the pure transform and the only place the commenting rules live. It takes the buffer's lines, the selection range, and a `CommentSyntax`, and returns the new lines plus the new selection. Internally it expands the range to whole lines, decides direction by testing the non-blank lines, computes the shallowest common indent, and applies or removes markers. Split `line-comment.ts` and `block-comment.ts` out of it if it approaches the limit — the two strategies are independent and extract cleanly.
- `useCommentToggle.ts` — one hook owning both the per-tab cache (a map from extension to `CommentSyntax | null`) and the async press handler, returning the single function `EditorTab` calls. The cache and the request are one concern, so they are not split across two modules; `useEditorSuggest.ts` is the precedent — it likewise owns its own state and issues its own `client.request` (`:87`, `:149`). A request that rejects caches nothing, so a later press retries once the plugin recovers.

**Client — wiring.** Add `{ kind: 'toggleComment' }` to the `KeyAction` union in `web/src/editor/keys.ts` and a `case '/'` to `metaAction` returning it. `applyKeyAction` deliberately gains **no** branch: every action it handles is synchronous, the first toggle must await a round trip, and its two `default` fall-throughs already make the action an inert no-op wherever it is dispatched — which is what silences it on the query-line surface. In `web/src/editor/EditorTab.tsx` (164 lines), add a `toggleComment` branch to `onKeyDown` immediately beside the `find` branch at `:130`, delegating to the hook's handler. That handler awaits the syntax for the buffer's extension, returns without touching anything when the answer is `null`, and otherwise records the undo step and sets the new state through `api` — the chord's `preventDefault()` at `:129` has already run synchronously, so the browser never sees it regardless of what the await does.

**`web/src/plugins/` is not touched at all.** That directory is the tab family's client surface — the lazy React bodies, the per-tab capability object, and the loader registry with its exhaustive `ProductionTabPluginId` annotation. An editor plugin has no React body, so it registers nothing there and the annotation at `registry.tsx:39` stays exhaustive and unrelaxed. The hook issues its RPC directly with `client.request`, exactly as the editor already does for its own `editorPersonas` and `editorSuggest` calls.

**Not affected — do not chase these.** `src/plugins/host.ts` gains nothing and needs no relief, despite sitting at 198 of its 200 lines. `src/plugins/context.ts`, `opener-adapter.ts`, `teardown.ts`, `requests.ts`, `notifications.ts`, and every existing manifest are untouched. `src/profile/save-entries.ts:129` and `src/profile/view-tabs.ts` read tab declarations only.

**Specs.** Add a "Commenting" section to `product/specs/editor-tab.md` after "Syntax highlighting", which it parallels — the chord, the toggle rules, the language table, the silent no-op. Add a new `product/specs/editor-plugins.md` describing the family the way `product/specs/tab-plugins.md` describes its own: what an editor plugin is, what it may and may not do, the declaration, the comment-syntax extension point, activation timing, and failure behavior. Leave `product/specs/tab-plugins.md` alone except for one sentence noting that a second plugin family exists and pointing at the new spec. `product/specs/comments.md` describes `##` stripping on the command line and is unrelated — leave it untouched, and do not name the new spec "comments".

**Documentation.** Add `documentation/developer-documentation/editor-plugins.md`, structured like the existing `tab-plugins.md` and led by the simplest working example — a manifest claiming one extension and a handler returning one line marker — before the block-comment case, per section 12. Add its nav entry beside the "Tab plugins" item at `documentation/.vitepress/config.mts:142`. Add the second pointer line to `ai/guidelines/plugins.md:5`. Note that `src/plugins/documentation.test.ts` pins the *tab* doc's capability count and fixture manifest; it is unaffected, and the new page gets its own equivalent test.

**Ordering.** Land the two shared-primitive generalizations first, then the protocol domain file, then the editor-plugin contract and its family infrastructure, then the bundled plugin with its catalog and loader entries, then the host wiring and the RPC edges, then the `plugins` command, and only then the client toggle. Typecheck stays green at each checkpoint. Every new `src/` import carries the `.js` extension per the NodeNext rule, and cache lookups use `??` rather than `||` to satisfy `prefer-nullish-coalescing` — a cached `null` must not be re-fetched as if it were absent.

## Tests

- `web/src/editor/comment/toggle.test.ts` — the bulk of the coverage, all render-free: comments and uncomments a single line with no selection; a multi-line selection round-trips exactly through two presses; a mixed range comments every line and the inverse press restores it; blank lines inside a range receive the marker and are excluded from the direction test; the marker lands at the shallowest common indent with relative indentation preserved; uncommenting tolerates a missing space after the marker and a marker at an unexpected column; a partial-line selection is expanded to whole lines; a block language wraps the whole range in one pair and unwraps it; a range with a stray marker inside wraps rather than unwraps; the selection covers the same lines after the toggle.
- `web/src/editor/keys.test.ts` — Cmd+/ resolves to `toggleComment`; Ctrl+/ and a bare `/` keep their existing results.
- `web/src/editor/comment/useCommentToggle.test.ts` — the first press issues one request and applies the edit when it resolves; a second press in the same tab issues none; a `null` answer leaves buffer, selection, and undo stack untouched; a rejected request caches nothing and a later press retries; one toggle is one undo step.
- `web/src/editor/EditorTab.test.tsx` — Cmd+/ is inert while a suggestion is pending, and inert while the agent query line holds focus, pinning the two suppressions this plan relies on rather than implements.
- `src/editor-plugins/commenting/activate.test.ts` — mirroring `src/plugins/markdown/activate.test.ts`: each of the twelve languages resolves to its expected syntax, matching is case-insensitive, and an unclaimed extension resolves to `null`.
- `src/editor-plugins/host.test.ts` — an extension no plugin claims answers `null` without activating anything; a claimed extension activates the plugin exactly once across two requests; a handler that throws disables the plugin, answers with its failure message, and puts one line in the notifications feed attributed to the editor tab; a request against an already-disabled plugin answers with that plugin's recorded reason; disabling one leaves the tab plugin host untouched; a declaration naming `commentLanguages` without a handler is refused; a declaration requesting an unknown capability is refused; an `apiVersion` mismatch is refused with a message naming both versions.
- `src/editor-plugins/claims.test.ts` — two editor declarations claiming the same extension leave the first contributing and the second recorded as rejected, without throwing; an editor plugin claiming `.md` does not disturb the markdown tab plugin's `open` claim for `.md`.
- `src/editor-plugins/fixture-v1/` plus its compatibility test — the frozen fixture this family must keep loading forever, written in the same change that introduces the extension point, as section 11 requires.
- `src/plugins/fixture-v1/compatibility.test.ts` and `web/src/plugins/fixture-v1/compatibility.test.tsx` — must pass unchanged, which is the proof that the tab contract was not disturbed.

## Out of scope

- **Migrating any existing plugin between families.** The six bundled tab plugins stay tab plugins; nothing moves.
- **Editor-plugin extension points other than comment syntax.** The family ships with exactly one. Indentation, multi-caret, symbol navigation, and formatting are not contributed through it in this version, though it is shaped so adding one is an additive change.
- **A block-comment chord.** No Cmd+Shift+/ that wraps a selection in `/* */` for languages that have both forms. Cmd+/ is the only commenting chord, and it uses the line marker wherever a language has one.
- **Third-party editor plugins.** Only the bundled `commenting` plugin and the frozen fixture ship. The contract is designed so another plugin could claim more extensions, but nothing is loaded from disk and no way to install one is added.
- **A client-side surface for editor plugins.** No React body, no lazy chunk, no client capability object. If an editor plugin ever needs to render, that is a new extension point and a new decision.
- **Normalizing a mixed range.** A range holding both commented and uncommented lines gains a second marker on the already-commented ones rather than converging to one marker each.
- **Comment-aware editing beyond the toggle.** No continuing a comment block on Enter, no reflowing or wrapping a long comment, no jumping between comments.
- **Language detection beyond the extension.** No shebang sniffing, no content heuristics, no per-file override. A file with no extension has no comment syntax.
- **Region-aware syntax inside a mixed file.** An HTML file's embedded `<script>` block comments with `<!-- -->` like the rest of the file; the toggle never consults the highlighter's token stream to pick a different marker per region.
- **A configurable marker or spacing.** The table is fixed in the plugin; nothing in `.janissary/config.json` changes it.
- **Commenting anywhere but an editor tab.** Not in the markdown tab, not in the command bar, not in the agent query line.
- **Unifying the two families' hosts.** They share primitives, not a base class. A generic plugin host abstracted over both is not built here and would need a third family to justify it.
