# Commenting

**Complexity: 8/10** — this is the app's second plugin family *and* a general editor-command contract: a plugin declares a keyboard chord, receives the slice of the buffer it asked for plus the current selection, and returns range edits and a new selection that the editor applies as one undo step. That means a new API version, declaration, capability set, catalog, loaders, host, protocol domain, chord-resolution rules, an edit applier with a real trust boundary, a spec, and a reference page. Commenting itself is then a small plugin written against it.

The editor tab has no way to comment out code, and no way for anything outside the editor to add an editing command at all. Cmd+/ is unbound at every level — absent from `metaAction` (`web/src/editor/keys.ts:33`) and from the window-level chord tables — so pressing it does nothing. This plan introduces a **new kind of plugin: an editor plugin**, whose contract is *"bind a chord, transform the editor"*: the declaration names a keyboard chord and how much of the buffer the handler needs, and the handler returns the edits to make and where to leave the selection. Commenting is its first member, and `Cmd+/` its first chord.

The family is the substance of the work. The existing contract in `src/plugins/` is entirely tab-shaped — a declaration claims file extensions for the `open`/`edit` verbs, names a tab label prefix, carries a payload schema version for the payload it ships to its own React body, and every client-to-plugin request is addressed to a plugin's own tab (`PluginIntentRequest.tab`, `src/protocol/plugin.ts:9`). An editor plugin has none of those things: no tab, no payload, no client body, no file it opens. It gets its own contract instead.

## Design decisions

**An editor plugin binds a chord and returns an edit.** The unit of contribution is a *binding*: a chord, a command name, and a declaration of how much of the buffer the handler needs. When the chord fires, the host activates the plugin and calls its handler with the requested slice, the current selection, and the file's name; the handler returns a list of range replacements and an optional new selection, or nothing. This is the whole extension point. Commenting declares one binding; a later plugin could declare several, and nothing about the contract is specific to comments.

**Editor plugins live in `src/editor-plugins/`, a sibling of `src/plugins/`.** Not `src/plugins/editor/`: every directory directly under `src/plugins/` is one bundled tab plugin (`audio/`, `image/`, `markdown/`, `page/`, `schedules/`, `video/`), so a family directory there would read as a plugin named "editor". The sibling mirrors `web/src/editor/` on the client. `ai/guidelines/plugins.md` governs both families; its pointer at `:5` gains a second entry for the new reference page.

**The family is versioned independently.** A new `EDITOR_PLUGIN_API_VERSION`, starting at 1, governs whether an editor plugin loads and moves on its own schedule under the section 4 rules. `TAB_PLUGIN_API_VERSION` is untouched and no tab declaration changes, which is why the frozen tab fixtures in `src/plugins/fixture-v1/` must keep passing unchanged — that is the proof this is an addition rather than a tab-contract break wearing a new name.

**The v1 capability set is exactly two names: `rejectRequest` and `reportFailure`.** An editor plugin cannot open a tab, serve a file, register a route, notify the user, save, rename, close, read another tab, or reach the file system. It receives a slice of one buffer and answers with edits to that buffer. Everything it is allowed to do to the editor travels in its return value, not through a capability it calls — which is what keeps the blast radius of a bad plugin to one document's text, and makes the whole effect surface reviewable in one type.

**A plugin may change text and selection, and nothing else.** The result carries range replacements and an optional new selection. There is no save effect, no scroll effect, no rename, close, or open. Scrolling needs no effect of its own: setting the cursor scrolls the caret into view through the behavior the editor already has for every cursor move (`product/specs/editor-tab.md`, "Scrolling"). Widening this set later is an additive API change under section 4.

**Edit positions are always absolute document coordinates.** Even when a plugin asked for only the selection, the request states the document range that slice came from, and every position the plugin returns is interpreted against the whole document. One coordinate system end to end removes the class of off-by-one bugs that a slice-relative system invites, at the cost of the plugin doing one addition.

**A binding declares the slice it needs.** `needs: 'selection'` sends the selected range's text and that range; `needs: 'buffer'` sends the whole document. The host sends exactly that and no more, which is section 9's "prefer contracts that hand a plugin the smallest slice it needs" applied to a path the user triggers by hand. Commenting declares `'selection'`. A future select-next-occurrence command would declare `'buffer'` and pay for it honestly.

**With no selection, a `'selection'` request sends the caret's line.** The slice is never empty and the plugin never has to special-case "nothing selected" — it always receives a range with text in it. This is also exactly the behavior commenting wants, where Cmd+/ with no selection comments the caret's line.

**The request carries the file's name so a plugin can branch on language.** That is how commenting picks `//` for `.ts` and `#` for `.rb`, and it is why the declaration has no language or extension field at all: the extension-to-marker table is entirely the commenting plugin's own business. An editor plugin that does not care about the file type simply ignores the field.

**Core key bindings always win; a plugin may only claim a chord the editor leaves unbound.** `EditorTab.onKeyDown` already asks `actionForKey` first (`web/src/editor/EditorTab.tsx:127`) and returns early when it answers null. The plugin chord table is consulted only in that null case, so no plugin can shadow Cmd+S, Cmd+Z, or any Emacs-subset chord. A declared chord that the core table does claim will simply never fire, so the client reports it once through the plugin-failure path rather than leaving it silently dead — a broken plugin must never be indistinguishable from an absent one.

**A declared chord must carry Cmd or Ctrl, enforced at registration.** `plainAction`'s default turns any single printable character into an insert (`web/src/editor/keys.ts:87`), so `actionForKey` effectively never returns null for an unmodified key. A chord without a modifier could therefore never fire, and declaring one is a plugin-authoring mistake caught when the declaration is validated rather than discovered by a user pressing a key that types a character instead.

**`web/src/editor/keys.ts` is not modified.** Because resolution is core-first with the plugin table consulted only on a null answer, there is no new `KeyAction` variant, no `case '/'` in `metaAction`, and no branch in `applyKeyAction`. The entire binding lives in the plugin table and one new branch in `onKeyDown`. That branch calls `preventDefault()` itself, since the existing early return on a null action deliberately does not.

**The chord table is published without activating anything.** Bindings are static declaration data — a chord, a command name, and a `needs` — so the host can answer with the full table having imported no plugin code, which is section 3's whole point. The editor fetches it once per editor tab on mount through an `editorBindings` RPC, exactly as `useEditorSuggest` fetches the persona list at `web/src/editor/useEditorSuggest.ts:87`. Pressing the chord is what activates the plugin, and only that plugin.

**Every press is a round trip; there is no cache.** The previous revision of this plan had the plugin answer a question once per file type and the client transform locally forever. That is no longer possible once the plugin produces the edit, and the trade is deliberate: a cacheable answer cannot express an arbitrary edit, which is the entire point of a keybinding contract. The ceiling accepted is one round trip per press over a loopback socket on a user-initiated path — not a per-keystroke path — with the request carrying only the declared slice. The upgrade path, if a plugin ever proves too slow, is a declaration that also carries a static answer the host can serve without activating, keeping the handler as the fallback.

**Edits apply back-to-front, atomically, as one undo step.** The client sorts the returned edits by start position and applies them from the end of the document backwards, so an earlier edit never shifts a later edit's coordinates. However many ranges a result touched, Cmd+Z restores all of them at once, recorded as the `'other'` edit kind (`web/src/editor/undo.ts:7`) that `applyKeyAction` already uses for every discrete, non-coalescing edit.

**A malformed result is discarded whole and disables the plugin.** An edit naming a position outside the document, or two edits whose ranges overlap, cannot be applied meaningfully, and silently clamping or dropping one would corrupt the user's text without telling anyone. The client validates the result against the buffer before touching it: on any violation the buffer, selection, and undo stack are left exactly as they were and the plugin is disabled through the existing `reportFailure` path. This is the one place an editor plugin can lose the user's trust, so it fails loudly and changes nothing.

**A `null` result is a silent no-op.** A plugin that has nothing to do — commenting in a `.log` file, an unknown extension, a file with no extension — returns nothing. The buffer is untouched, no undo step is recorded, and no message appears anywhere, matching how the editor already treats a file it cannot syntax-highlight.

**Failures report to notifications; the wording follows the tab family with its own noun.** A handler that throws, times out, or returns a malformed result disables the plugin and reports one line through the existing `notify(managers, 'plugin-failure', …)` path (`src/notifications.ts`, event type already defined at `:28`), reading `Editor plugin "commenting" disabled: <reason>.` It is built from the shared `pluginFailureReason` helper so both families trim and normalize a failure identically.

**Failure containment is simpler than the tab host's.** Disabling a tab plugin closes that plugin's open tabs (`closePluginTabs`, `src/plugins/teardown.ts`). An editor plugin owns no tabs, files, or sockets, so disabling one records the reason, disposes the activation, reports the line, and stops. Its chords stop resolving from that point; the editor keeps working exactly as it did before the plugin existed.

**The editor tab is identified by `url`, not by label.** Every existing editor RPC identifies its tab by the `/open/<id>` ref (`src/protocol/editor.ts:11`, `:15`, `:20`, `:29`), which the server resolves through the open-file allow-list. The editor-plugin RPC follows that convention rather than inventing a label-keyed one.

**`Pos` becomes a wire type, imported rather than mirrored.** Positions now cross the boundary, and section 10 forbids redeclaring a wire shape in `web/src/`. The protocol domain file defines the position, selection, and edit shapes, and `web/src/editor/model.ts` imports `Pos` from `@shared/protocol` and re-exports it — so every existing `import type { Pos } from './model'` across the editor keeps working untouched, and there is exactly one definition.

**Resolution is first match by exact chord, with duplicate claims refused at registration.** Two editor plugins claiming Cmd+/ is a conflict, resolved the way `createPluginOpeners` already resolves a duplicate extension claim (`src/plugins/opener-adapter.ts:16`): the first claimant keeps it, the loser contributes nothing and starts already disabled with the recorded reason, and the app still starts. Because duplicates are refused, array position never breaks a tie.

**The two families share their primitives rather than duplicating them.** Four things are already family-agnostic and are reused unchanged: `guardPluginCall` (`src/plugins/guard.ts`) for the per-call timeout, `pluginFailureReason` (`src/plugins/failure.ts:6`), the `'plugin-failure'` notification event type, and the module-scope rejection registry (`src/plugins/rejections.ts`), which is keyed by plugin id and works for either family. Two need a small generalization, taken here rather than duplicated: `PluginRecord`/`recordStatus` (`src/plugins/status.ts`, 19 lines) gain type parameters for the declaration and activation types, and the load-race-timeout core of `activatePlugin` (`src/plugins/activate.ts:65`, 88 lines) is extracted into a shared helper taking a loader, a timeout, and a validate callback. Neither changes tab-plugin behavior, which the frozen fixtures pin.

**`plugins` lists both families.** A broken editor plugin has to be visible where a broken tab plugin already is (`src/commands/plugins.ts:31`). It prints editor plugins after tab plugins using the same `id version api=N state=… reason=…` line; `statusLine` takes the four fields both declarations share, so it needs no per-family branch.

**`Managers` gains an `editorPlugins` host**, constructed in `src/controller/create-managers.ts` beside `managers.plugins` at `:43`, per section 10's rule that a long-lived subsystem appears in `Managers` and gets a `dispose`. Note for the implementer: nothing in production calls `TabPluginHost.dispose()` today either — it exists for parity and for tests — so there is no existing teardown call site to hook the new one into and none should be invented here.

### Commenting, as an editor plugin

**One binding: Cmd+/, `needs: 'selection'`.** Everything below is the commenting plugin's own behavior, implemented in a pure module inside it and covered by its own tests. None of it is part of the editor-plugin contract.

**Cmd+/ toggles whole lines.** The plugin expands the received range to whole lines and acts on that. It uncomments when every non-blank line in the range already starts with the language's line marker, and otherwise comments. Since a request with no selection carries the caret's line, the no-selection case needs no special handling.

**Commenting is additive, not normalizing.** A range holding both commented and uncommented lines comments: every line gains a marker, including the ones that already had one, which end up with two. The inverse press removes exactly one from each and the range is back where it started, so the toggle is a pure inverse of itself at every step.

**Blank lines inside the range are commented too**, so the commented block reads as contiguous. They are excluded from the all-commented test that decides direction — a range of two commented lines separated by a blank still uncomments.

**A marker is followed by one space; uncommenting removes at most one.** `const a = 1;` becomes `// const a = 1;`. Uncommenting removes the marker and one following space when there is one, so a comment hand-written without a space survives the round trip.

**The marker is placed at the shallowest common indent** — the first non-whitespace column of the least-indented non-blank line in the range — and every line including blanks receives it at that column, left-padded where the line is shorter. Code keeps its relative indentation and markers line up. Uncommenting removes the first marker occurrence wherever it sits, so a hand-edited block still uncomments cleanly.

**Block-only languages wrap the whole range in one pair.** Markdown, HTML, and CSS have no line comment, so the toggle wraps the range in a single pair — `<!-- ` before the first line's content, ` -->` after the last line's — and unwraps it on the inverse press. "Already commented" for a block language means the range is exactly wrapped, so a range with a stray marker inside wraps again.

**The returned selection covers the same whole lines**, so a second press is the exact inverse of the first. With no selection the result leaves the caret on its line, shifted by the marker's width.

**Twelve languages, resolved by extension, entirely inside the plugin.** `.js`/`.mjs`/`.cjs`/`.jsx`, `.ts`/`.tsx`/`.mts`/`.cts`, and `.json` use `//`; `.rb`, `.sh`/`.bash`/`.zsh`, `.txt`, `.py`, and `.yml`/`.yaml` use `#`; `.md`/`.markdown` and `.html` use `<!-- -->`; `.css` uses `/* */`. Matching is case-insensitive. `.json` gets `//` deliberately: the result is JSONC rather than strict JSON, which is what a user commenting out a config line wants. Any other extension returns `null`.

## Proposed changes

**Generalize the two shared primitives first.** In `src/plugins/status.ts`, give `PluginRecord` and `recordStatus` type parameters for the declaration and activation types, keeping `TabPluginStatus` as the family-agnostic public shape it already is. In `src/plugins/activate.ts`, extract the load race, timeout, duration measurement, and late-arrival disposal from `activatePlugin` (`:65`) into a helper taking a loader, a timeout, and a validate callback invoked on the resolved activation; `activatePlugin` keeps its signature and passes its existing validators in, so no tab behavior changes. Both files have ample room (19 and 88 lines). These land first so the editor family builds on them rather than beside them.

**Protocol.** A new `src/protocol/editor-plugin.ts` holding: `Pos` (`{ line, col }`); `EditorSelection` (`{ anchor: Pos | null; cursor: Pos }`, matching what `EditorState` already carries); `EditorChord` (`{ key: string; meta?: boolean; ctrl?: boolean; shift?: boolean; alt?: boolean }`); `EditorPluginBinding` (`{ plugin: string; command: string; chord: EditorChord; needs: 'selection' | 'buffer' }`) as the static table entry; `EditorPluginEdit` (`{ start: Pos; end: Pos; text: string }`); `EditorPluginResult` (`{ edits: readonly EditorPluginEdit[]; selection?: EditorSelection }`); and an `EditorPluginRpcCall` union with two methods — `editorBindings` (no params, replies with the binding table) and `editorPluginRun` (`{ url, command, file, selection, range, text }`, replying with `EditorPluginResult | null`). Compose it into `src/protocol.ts` exactly as `src/protocol/plugin.ts` is at `:14`, `:20`, and `:64`. Then change `web/src/editor/model.ts` to import `Pos` from `@shared/protocol` and re-export it, so the editor's existing `Pos` imports are untouched and the type has one definition.

**The editor-plugin contract.** A new `src/editor-plugins/api.ts` exporting `EDITOR_PLUGIN_API_VERSION` (1); an `EditorPluginCapabilityName` union of `rejectRequest` and `reportFailure`, kept honest by the keyed-record trick at `src/plugins/api.ts:26`; an `EditorPluginRejection` error class; the `EditorPluginDeclaration` (`id`, `version`, `apiVersion`, `bindings`, `capabilities` — no payload schema version, no tab label prefix, no file extensions); an `EditorPluginServerCapabilities` carrying only those two functions; an `EditorPluginRequest` (the command name, the file name, the selection, the range the slice came from, and the slice text); and an `EditorPluginActivation` with a `run(request, capabilities)` handler and an optional `dispose`. Its trailing comment documents the extension point's four required properties as `src/plugins/api.ts:251` does for the tab family: resolution is first match by exact chord with duplicates refused at registration; ordering never depends on array position; the handler is awaited under a per-call budget; and a `null` return means the plugin chose to do nothing, which is indistinguishable in effect from no plugin claiming the chord.

**Family infrastructure.** `src/editor-plugins/catalog.ts` and `loaders.ts`, exhaustively typed against a `ProductionEditorPluginId` derived from the catalog, mirroring `src/plugins/catalog.ts:12`. `src/editor-plugins/activate.ts` supplying the family's declaration validation — API version match, known capability names, at least one binding, every chord carrying Cmd or Ctrl, and a declaration with bindings but no `run` handler refused, that last modeled on the "claims a command but provides no handler" guard at `src/plugins/host.ts:93` — then calling the shared load helper. `src/editor-plugins/claims.ts` building the chord index at registration, keyed by a canonical chord string, calling `rejectContribution` on a conflict. `src/editor-plugins/context.ts` constructing the two-function capability object. `src/editor-plugins/host.ts` holding `EditorPluginHost`: a records map seeded from the catalog and the rejection registry, `declarations` and `statusFor` for the `plugins` command, a `bindings()` accessor answering the static table without activating anything, a `run(url, command, request)` method that resolves the binding, activates lazily, invokes through the shared guard, and disables on a throw, plus `dispose`. It will be well short of `TabPluginHost` (225 lines) — no openers, commands, notifications, selection actions, or tabs to close — but if it approaches the limit, split the request path into `src/editor-plugins/requests.ts` as the tab family did.

**The commenting plugin.** `src/editor-plugins/commenting/` holding `manifest.ts`, `syntax.ts`, `toggle.ts`, and `activate.ts`. The manifest declares one binding — command `toggle-comment`, chord Cmd+/, `needs: 'selection'` — and the two capabilities. `syntax.ts` holds the extension → comment-syntax table as data. `toggle.ts` is the pure transform and the only place the commenting rules live: given the range's lines, the range, and a syntax, it returns the edits and the new selection. It is pure and has no imports beyond `syntax.ts`, so it is tested directly and heavily. Split `line-comment.ts` and `block-comment.ts` out of it if it approaches the limit — the two strategies are independent and extract cleanly. `activate.ts` exports `activate()` returning a `run` handler that resolves the file's extension, returns `null` when unknown, and otherwise delegates to `toggle.ts`. Module top level stays free of side effects, and discovery imports only the manifest.

**Host wiring.** Add `editorPlugins: EditorPluginHost` to `Managers` (`src/managers.ts`, 56 lines) and construct it in `src/controller/create-managers.ts` beside `managers.plugins` at `:43`. Add `editorBindings` and `editorPluginRun` to `src/controller/editor-adapter.ts` (30 lines) beside `editorPersonas` at `:16`/`:28`, with the matching `declare` lines in `src/controller.ts` (130 lines). Add both method names to the allowlist in `src/client-message.ts` (97 lines, alphabetical as that list is ordered). Add two cases to `src/message-handler.ts` (175 lines): `editorBindings` replies inline like `editorPersonas` at `:158`, since the table is static and needs no await; `editorPluginRun` follows the deferred-reply shape `projectFiles` uses at `:148` — an awaited call inside a `try`/`catch`, replying with the result or the caught message as an `error` — rather than `pluginIntent`'s longer `.then(…, …)` block, so it costs about eight lines and needs no extraction.

**`plugins` command.** Widen `statusLine` in `src/commands/plugins.ts` (32 lines) to accept the four fields both declarations share, and print `managers.editorPlugins.declarations` after `managers.plugins.declarations`, each with its own `statusFor` lookup — reading the hosts' own declaration lists rather than the catalogs, for the reason already recorded at `:29`.

**Client.** A new `web/src/editor/plugins/`:

- `chords.ts` — pure: canonicalize a `KeyLike` and match it against the binding table, returning the binding or null. The same canonical form the server's claim index uses, so the two agree on what "the same chord" means. Also exposes the check that reports a binding the core table already claims.
- `apply-edits.ts` — pure: validate a result against the buffer (every position in range, no two edits overlapping) and, if it is sound, apply the edits back-to-front to an `EditorState` and set the returned selection. Returns the new state or a validation failure; never partially applies. This is the trust boundary and gets the most adversarial tests in the change.
- `useEditorPlugins.ts` — the hook: fetches the binding table once on mount, reports any core-shadowed binding once, and exposes the handler `onKeyDown` calls. That handler matches the chord, builds the slice the binding declared (the selected range's lines, or the caret's line when there is no selection, or the whole buffer), awaits `editorPluginRun`, and on a sound result applies it through `apply-edits.ts` and records one `'other'` undo step. A rejected request or an unsound result leaves the buffer untouched.

**Client wiring.** In `web/src/editor/EditorTab.tsx` (164 lines), add one branch to `onKeyDown`: after `actionForKey` returns null, ask the hook whether a plugin binding matches; if one does, `preventDefault()` and dispatch to it, otherwise return as before. `web/src/editor/keys.ts` and `applyKeyAction.ts` are not modified.

**Not affected — do not chase these.** `web/src/plugins/` is the tab family's client surface and is untouched: an editor plugin has no React body, so `clientPluginLoaders`' exhaustive `satisfies Record<ProductionTabPluginId, …>` at `registry.tsx:39` stays as it is. `src/plugins/host.ts` gains nothing and needs no relief despite sitting at 198 of its 200 lines. `src/plugins/context.ts`, `opener-adapter.ts`, `teardown.ts`, `requests.ts`, `notifications.ts`, and every existing manifest are untouched, as are `src/profile/save-entries.ts` and `src/profile/view-tabs.ts`, which read tab declarations only.

**Specs.** Add a "Commenting" section to `product/specs/editor-tab.md` after "Syntax highlighting", and a short "Editor plugin bindings" section describing how a plugin chord resolves after the core table, that a plugin may change only text and selection, and that a malformed result changes nothing. Add `product/specs/editor-plugins.md` describing the family as `product/specs/tab-plugins.md` describes its own: what an editor plugin is, the declaration, bindings and chord resolution, the request slice, the result and its validation, activation timing, and failure behavior. Add one sentence to `product/specs/tab-plugins.md` noting a second family exists, pointing at the new spec. `product/specs/comments.md` is about `##` stripping on the command line and is unrelated — leave it alone, and do not name the new spec "comments".

**Documentation.** Add `documentation/developer-documentation/editor-plugins.md`, structured like `tab-plugins.md` and led by the simplest working example — a manifest with one binding and a handler returning one edit — before the block-comment case, per section 12. Add its nav entry beside the "Tab plugins" item at `documentation/.vitepress/config.mts:142`, and the second pointer line at `ai/guidelines/plugins.md:5`. `src/plugins/documentation.test.ts` pins the *tab* page's capability count and fixture manifest and is unaffected; the new page gets its own equivalent test.

**Ordering.** Land the two shared-primitive generalizations, then the protocol domain file and the `Pos` re-export, then the editor-plugin contract and family infrastructure, then the commenting plugin with its catalog and loader entries, then the host wiring and RPC edges, then the `plugins` command, then the client modules, and finally the `onKeyDown` branch that switches it on. Typecheck stays green at each checkpoint. Every new `src/` import carries the `.js` extension per the NodeNext rule, and optional-field reads use `??` rather than `||` to satisfy `prefer-nullish-coalescing`.

## Out of scope

- **Effects beyond text and selection.** No save, scroll, rename, close, or open-another-file effect. A plugin changes one buffer's text and where the selection sits, and nothing else.
- **A client-side surface for editor plugins.** No React body, no lazy chunk, no client capability object, no plugin-drawn UI, overlay, or menu entry. If an editor plugin ever needs to render, that is a new extension point and a new decision.
- **Reading or writing anything but the requested slice.** A plugin cannot ask for another tab's buffer, a file on disk, or the transcript.
- **Editor plugin commands invoked any way but a chord.** No command-bar entry, no palette, no menu, no profile hook. A binding fires from its chord or not at all.
- **Chords with no modifier, and shadowing a core binding.** Both are refused, the first at registration and the second at resolution.
- **Caching a plugin's answer.** Every press is a round trip; no result or slice is memoized.
- **Multi-caret or multi-range selection.** The result carries one selection, because `EditorState` holds one anchor and one cursor. A plugin cannot express what the editor cannot represent.
- **Third-party editor plugins.** Only the bundled `commenting` plugin and the frozen fixture ship. Nothing is loaded from disk and no way to install one is added.
- **Migrating any existing plugin between families.** The six bundled tab plugins stay tab plugins.
- **Other editor commands.** Indent/deindent, multi-caret select-next-occurrence, and formatting are not written here, though the contract is shaped so each is a new plugin rather than a new extension point.
- **Normalizing a mixed range**, **comment-aware editing beyond the toggle**, **language detection beyond the extension**, **region-aware syntax inside a mixed file**, and **a configurable marker or spacing** — all commenting-specific, all deferred.
- **Unifying the two families' hosts.** They share primitives, not a base class. A generic plugin host abstracted over both is not built here and would need a third family to justify it.
