# Commenting

**Complexity: 6/10** — the toggle itself is a pure, easily-tested transform and the client side is two modules, but delivering it "as a plugin" means the first non-tab extension point on the plugin contract: a new declaration field, a new claim registry, a new RPC threaded through five existing edges, a loosened required field, and a host module already two lines from the 200-line limit that must be relieved before anything is added to it.

The editor tab has no way to comment out code. Cmd+/ is unbound at every level — absent from `metaAction` (`web/src/editor/keys.ts:33`) and from the window-level chord tables (`web/src/useWindowKeys.ts` has no `/` case) — so pressing it in a buffer does nothing. This plan binds Cmd+/ to a whole-line comment toggle whose marker is chosen by the file's extension, and delivers the extension-to-marker knowledge through a **new comment-syntax extension point on the tab-plugin contract**, contributed by one bundled `commenting` plugin. The editor asks the host for a file's comment syntax the first time the chord is pressed in a tab, caches the answer for that tab's life, and applies the toggle as a single undo step.

The extension point is the substance of the work. The contract today is entirely tab-shaped: a declaration claims file extensions for the `open`/`edit` verbs, a command name, or a notification topic, and every client-to-plugin request is addressed to a plugin's own tab (`PluginIntentRequest.tab`, `src/protocol/plugin.ts:9`; `ownerOf` resolves it via `tab.plugin` at `src/plugins/requests.ts:45`). Commenting fits none of that. It contributes behavior to a **core** tab that no plugin owns, for extensions other code already claims — `.md` belongs to the markdown plugin (`src/plugins/markdown/manifest.ts:15`) and `.js` to the plain-text editor — so it needs its own declaration field, its own claim registry, and its own RPC rather than a reuse of the intent path.

## Design decisions

**Cmd+/ toggles whole lines.** The chord expands the selection to whole lines and acts on that range. Uncomment when every non-blank line in the range already starts with the language's line marker; otherwise comment. With no selection it acts on the caret's line alone. It is bound in `metaAction` (`web/src/editor/keys.ts:33`) rather than at the window level so the existing `e.preventDefault()` at `web/src/editor/EditorTab.tsx:129` also suppresses whatever the browser would do with the chord. Ctrl+/ is left unbound, consistent with `ctrlAction` reserving Ctrl for the Emacs subset.

**Commenting is additive, not normalizing.** A range holding both commented and uncommented lines comments: every line in it gains a marker, including the ones that already had one, which end up with two. The inverse press removes exactly one marker from each and the range is back where it started. The toggle is therefore a pure inverse of itself at every step, rather than converging mixed ranges to a single state.

**Blank lines inside the range are commented too.** A blank line within the selected range receives the marker so the commented block reads as contiguous. Blank lines are excluded from the all-commented test that decides direction — a range of two commented lines separated by a blank still uncomments.

**A marker is followed by one space; uncommenting removes at most one.** Commenting inserts `<marker><space>`, so `const a = 1;` becomes `// const a = 1;`. Uncommenting removes the marker and one following space when there is one, and leaves the line otherwise untouched, so a line whose comment was hand-written without a space survives the round trip.

**The marker is placed at the shallowest common indent.** For a line-comment language the marker goes at the first non-whitespace column of the least-indented non-blank line in the range, and every other line in the range — blank lines included — receives it at that same column, left-padded with spaces where the line is shorter. Code keeps its relative indentation and the markers line up in a column. Uncommenting removes the first marker occurrence on each line wherever it sits, so a hand-edited block still uncomments cleanly.

**Block-only languages wrap the whole range in one pair.** Markdown, HTML, and CSS have no line comment. For them the toggle wraps the entire selected range in a single open/close pair — `<!-- ` before the first line's content, ` -->` after the last line's — and unwraps that same pair on the inverse press. "Already commented" for a block language means the range is exactly wrapped, so a range with a stray marker inside it wraps again rather than unwrapping.

**The selection survives the toggle.** After a toggle the selection still covers the same whole lines, so a second press is the exact inverse of the first. With no selection the caret stays on its line and shifts by the marker's width, keeping its position relative to the text.

**One toggle is one undo step.** However many lines the press changed, Cmd+Z restores all of them at once. The toggle records an `'other'` edit kind on the tab's `UndoBuffer` (`web/src/editor/undo.ts:7`), which is what `applyKeyAction` already uses for every discrete, non-coalescing edit (`web/src/editor/applyKeyAction.ts:53`), so it never merges into an adjacent run of typing.

**Twelve languages ship, resolved by extension.** `.js`/`.mjs`/`.cjs`/`.jsx`, `.ts`/`.tsx`/`.mts`/`.cts`, and `.json` use `//`; `.rb`, `.sh`/`.bash`/`.zsh`, `.txt`, `.py`, and `.yml`/`.yaml` use `#`; `.md`/`.markdown` and `.html` use `<!-- -->`; `.css` uses `/* */`. Matching is case-insensitive, as `languageForFile` already lowercases at `web/src/editor/highlight/registry.ts:27`. `.json` gets `//` deliberately: the result is JSONC rather than strict JSON, which is what a user commenting out a config line wants.

**Comment syntax is declared as `commentLanguages`, separate from `fileExtensions`.** `fileExtensions` claims the `open` and `edit` verbs, and `createPluginOpeners` refuses a claim already held by core or an earlier plugin (`src/plugins/opener-adapter.ts:16`). A commenting plugin listing `.md` there would be refused outright, and one listing `.js` would hijack opening away from the plain-text editor. A new optional `commentLanguages` field carries the extensions a plugin answers comment-syntax requests for, and is checked for duplicates against other plugins' `commentLanguages` only. The commenting plugin declares `fileExtensions: {}` — already the shape `page` and `schedules` use (`src/plugins/page/manifest.ts:16`, `src/plugins/schedules/manifest.ts:16`).

**`tabLabelPrefix` becomes optional, and is the signal that a plugin opens tabs.** The commenting plugin opens none, and a dummy prefix that is never used would be exactly the "code path the system never takes" that section 13 of `ai/guidelines/plugins.md` rejects. Making the field optional has exactly one production consumer to update — `src/plugins/context.ts:102`, which passes `declaration.tabLabelPrefix` to `openPluginTab` inside the `openOrFocusTab` capability; it becomes `declaration.tabLabelPrefix ?? declaration.id`, a single `??` on a path a tabless plugin can never reach anyway, since it does not request that capability. Every other occurrence of the field is a manifest, a test fixture, or the docs table. Its presence then becomes the honest, declarative answer to "does this plugin contribute tabs", which the client registry parity check below depends on.

**The contract change is additive, so the API version integer stays at 1.** `commentLanguages` and the activation's `commentSyntax` handler are optional additions, and loosening `tabLabelPrefix` from required to optional breaks no existing declaration. Nothing is removed, renamed, tightened, or given a new meaning. Per the rule recorded at `src/plugins/api.ts:5` ("Additive changes keep this integer"), `TAB_PLUGIN_API_VERSION` is untouched and the frozen v1 fixtures must keep loading unchanged.

**A new `commentSyntax` RPC, resolved by declaration rather than by tab.** `runPluginIntent` resolves the owning plugin from the requesting tab's `plugin` record; an editor tab has none, so `ownerOf` would throw, and widening that path to accept a core tab would let any plugin receive intents from tabs it does not own. Instead the client calls a new `commentSyntax` method carrying the extension and the editor tab's label, and the host resolves the single plugin whose `commentLanguages` claims that extension. The reply is the syntax or `null`.

**A duplicate `commentLanguages` claim disables that plugin's contribution; it never throws.** This copies `createPluginOpeners` exactly: the conflict is recorded through `rejectContribution` (`src/plugins/rejections.ts`), the losing plugin contributes nothing and starts life already disabled when `TabPluginHost` reads `contributionRejection` at `src/plugins/host.ts:53`, and the app still starts. Resolution is first match by exact lowercase extension; because duplicates are refused, array position never breaks a tie.

**The syntax comes from an activated handler, not from static declaration data — deliberately.** `commentLanguages` is a claim list only (extension → `true`); the syntax itself is produced by the plugin's `commentSyntax` handler at request time. Putting the syntax table straight into the manifest would let the host publish a merged table to the client and delete the handler, the RPC, and the activation entirely, which is a materially smaller build — it was considered and rejected, because a declaration-only extension point can never answer anything the host did not already know, and commenting is the first extension point meant to prove a plugin can contribute *behavior* to a core surface. The ceiling this accepts is one round trip per file type per tab; the upgrade path, if that ever matters, is to let a declaration carry a static table the host serves without activating, keeping the handler as the fallback for plugins that need to compute an answer.

**The first press awaits; later presses do not.** No request is made when an editor tab opens. The first Cmd+/ in a tab fires the request that activates the plugin and awaits it, then applies the edit. The answer is cached per editor tab, keyed by extension, for that tab's life — including a `null` answer, so an unclaimed extension is never asked about twice. Activating this late means a session that never comments never loads the plugin, which is what section 6 of `ai/guidelines/plugins.md` asks for.

**An unavailable syntax is a silent no-op; a plugin failure is reported to notifications.** When the resolved syntax is `null` — an unknown extension, a file with no extension — Cmd+/ does nothing: buffer untouched, no undo step, no message, matching how the editor already treats a file it cannot syntax-highlight. When the plugin itself fails or is disabled, `reportPluginFailure` (`src/plugins/failure.ts:16`) already does exactly the right thing — it calls `notify(managers, 'plugin-failure', origin.label, message)`, putting one line in the notifications feed. **No new wording is invented:** the line is the existing `pluginFailureMessage` shape, `Tab plugin "commenting" disabled: <reason>.` The RPC carries the editor tab's label as the failure origin so the notification is attributed to the tab the chord was pressed in. `reportPluginFailure` also appends to the origin tab's transcript when that tab exists; for an editor tab that entry is never rendered, which is already true of the plugin tabs `runPluginIntent` passes as its own origin, so no special-casing is added.

**Query-line and pending-suggestion suppression come for free.** `handleSuggestKeyDown` runs before the buffer's own dispatch (`web/src/editor/EditorTab.tsx:126`), and both `applyMove` and `applyEdit` end in a `default` fall-through (`web/src/editor/applyKeyAction.ts:45`, `:71`). An unhandled `toggleComment` reaching the query-line surface via `suggest.applyQueryAction` is therefore already a no-op, and the pending-suggestion guard already swallows every keystroke. No new branch is written for either case; the tests below pin both.

## Proposed changes

**Relieve `src/plugins/host.ts` first.** It is at **198 of 200** lines as `max-lines` counts them (non-blank, non-comment), so nothing can be added to it — not even a two-line delegating method — until something leaves. Extract its private `requestPort()` builder (`:111`–`:120`) into `src/plugins/requests.ts` as a factory taking the host's records, managers, and the three bound callbacks. That module is at 65 lines and is where every other request-path function already lives, so the move is toward its owner rather than into a dumping ground. The freed room is what the new delegating `commentSyntax` method then occupies. This extraction lands before anything else in this plan.

**Contract.** In `src/protocol/plugin.ts`, add a `CommentSyntax` type — a discriminated union of `{ kind: 'line'; marker: string }` and `{ kind: 'block'; open: string; close: string }` — and a `{ method: 'commentSyntax'; params: { tab: string; extension: string } }` member to `PluginRpcCall`, answering `CommentSyntax | null`. Re-export both from `src/protocol.ts:20` alongside the existing plugin types. The client imports them through the `@shared` alias and never redeclares them in `web/src/`.

In `src/plugins/api.ts` (at 135 lines, with room), add an optional `commentLanguages: Readonly<Record<string, true>>` to `TabPluginDeclaration`, keyed by lowercase extension including the leading dot; make `tabLabelPrefix` optional; and add an optional `commentSyntax(extension: string, capabilities: TabPluginServerCapabilities): CommentSyntax | null | Promise<…>` to `TabPluginActivation`. Extend that module's trailing contract comment (`:251`–`:257`) with the extension point's four required properties: resolution is first match by exact lowercase extension with duplicates refused at registration; ordering therefore never depends on array position; the handler is awaited under the same per-call budget every other handler runs under; and a `null` return means "this plugin has no syntax for that extension", indistinguishable in effect from no plugin claiming it. Add a guard modeled on `src/plugins/host.ts:93` refusing a declaration that names `commentLanguages` without supplying the handler.

**Claim registry.** A new `src/plugins/comment-adapter.ts` beside `opener-adapter.ts`, exporting a function that walks the declarations and returns a lowercase extension → plugin id map, calling `rejectContribution` for a plugin whose claim is already held and skipping its remaining claims — the same loop shape as `createPluginOpeners`. It goes in its own module rather than into `host.ts` for the size reason above, and because the openers adapter sets the precedent that a claim registry is its own module.

**Server dispatch.** Add `resolveCommentSyntax` to `src/plugins/requests.ts`, taking the request port, the resolved record, and the extension. It returns `null` when no plugin claims the extension, throws the plugin's failure message when the record is disabled, calls `ensureActive` to activate lazily, and runs the handler through `port.invoke` so a throw disables the plugin rather than the host — the same sequence `runPluginIntent` follows at `:56`–`:72`, minus the tab lookup. Expose it as a `commentSyntax(tabLabel, extension)` method on `TabPluginHost` beside `intent` (`:103`), delegating in the same one-line style. Thread the method through the four remaining edges: add `commentSyntax: true` to the allowlist in `src/client-message.ts` (alphabetical, as that list is ordered), an entry in `src/controller/plugin-adapter.ts` (`:8` type, `:14` binding), the `declare` line in `src/controller.ts:43`, and a validated case in `src/message-handler.ts`. That case follows the deferred-reply shape `projectFiles` already uses at `src/message-handler.ts:148` — an awaited call inside a `try`/`catch`, replying with the result or with the caught message as an `error` — rather than `pluginIntent`'s longer `.then(…, …)` block at `:70`. It is roughly eight lines against that file's 175, so no extraction is needed there and no shared reply helper is introduced for two call sites.

**The bundled plugin.** A new `src/plugins/commenting/` holding `manifest.ts`, `shared.ts`, and `activate.ts`, matching the shape every other bundled plugin uses. The manifest declares `id: 'commenting'`, no `tabLabelPrefix`, `fileExtensions: {}`, the `commentLanguages` map covering the twelve languages, and a capability list of `rejectRequest` and `reportFailure` only — it opens no tab, serves no file, and touches no host state, so it asks for nothing else. `shared.ts` holds the extension → syntax table as data, read by both the manifest (for its claim list) and the activation, so there is one definition rather than two that can drift; `video/activate.ts:18` and `audio/activate.ts:23` already read their own manifest this way. `activate.ts` exports `activate()` returning the `commentSyntax` handler plus the `intent` and `isPayload` members the activation type requires — `intent` rejects every request through `rejectRequest`, since this plugin owns no tab to address one to. Module top level stays free of side effects. Register the manifest in `src/plugins/catalog.ts` and the loader in `src/plugins/loaders.ts`, both of which keep their exhaustive `satisfies Record<ProductionTabPluginId, …>` annotations.

**Client registry parity.** `web/src/plugins/registry.tsx:39` annotates `clientPluginLoaders` with `satisfies Record<ProductionTabPluginId, () => Promise<unknown>>`. Adding `commenting` to the catalog makes that a compile error, since the plugin has no client entry. Relax it to `Partial<Record<…>>` and restore the guarantee it was carrying by adding an assertion to `web/src/plugins/registry.test.tsx` that every catalog declaration **carrying a `tabLabelPrefix`** has a client loader — so a plugin that really does open tabs still cannot ship without its React surface. The existing test at `:19` compares registry keys to loader keys and needs no change.

**Client — the toggle itself.** A new `web/src/editor/comment/`:

- `toggle.ts` — the pure transform and the only place the commenting rules live. It takes the buffer's lines, the selection range, and a `CommentSyntax`, and returns the new lines plus the new selection. Internally it expands the range to whole lines, decides direction by testing the non-blank lines, computes the shallowest common indent, and applies or removes markers. Split `line-comment.ts` and `block-comment.ts` out of it if it approaches the limit — the two strategies are independent and extract cleanly.
- `useCommentToggle.ts` — one hook owning both the per-tab cache (a map from extension to `CommentSyntax | null`) and the async press handler, returning the single function `EditorTab` calls. The cache and the request are one concern, so they are not split across two modules; `useEditorSuggest.ts` is the precedent — it likewise owns its own state and issues its own `client.request` (`web/src/editor/useEditorSuggest.ts:87`, `:149`). A request that rejects caches nothing, so a later press retries once the plugin recovers. Being a hook, it is testable without a render, as `useEditorFind.test.ts` and `useEditorSync.test.ts` already are.

**Client — wiring.** Add `{ kind: 'toggleComment' }` to the `KeyAction` union in `web/src/editor/keys.ts` and a `case '/'` to `metaAction` returning it. `applyKeyAction` deliberately gains **no** branch: every action it handles is synchronous, the first toggle must await a round trip, and its two `default` fall-throughs already make the action an inert no-op wherever it is dispatched — which is what silences it on the query-line surface. In `web/src/editor/EditorTab.tsx`, add a `toggleComment` branch to `onKeyDown` immediately beside the `find` branch at `:130`, delegating to the hook's handler. That handler awaits the syntax for the buffer's extension, returns without touching anything when the answer is `null`, and otherwise records the undo step and sets the new state through `api` — the chord's `preventDefault()` at `:129` has already run synchronously, so the browser never sees it regardless of what the await does.

**`web/src/plugins/api.ts` is not touched.** That module builds the per-tab capability object handed to a plugin's own React body, and commenting has no plugin tab and no client body. The hook issues the RPC directly with `client.request`, exactly as the editor already does for its own `editorPersonas` and `editorSuggest` calls (`web/src/editor/useEditorSuggest.ts:87`, `:149`).

**Not affected — do not chase these.** `src/profile/save-entries.ts:129` classifies a plugin tab by whether its declaration has non-empty `fileExtensions`; commenting opens no tabs, so nothing there changes. `src/plugins/documentation.test.ts` pins the *capability* count in the developer doc; commenting requests no new capability, so those assertions stay green.

**Specs.** Add a "Commenting" section to `product/specs/editor-tab.md` after "Syntax highlighting", which it parallels — the chord, the toggle rules, the language table, the silent no-op. Add the extension point to `product/specs/tab-plugins.md`: the declaration field, the handler, resolution and ordering, async semantics, activation trigger, and the meaning of a `null` return. `product/specs/comments.md` describes `##` stripping on the command line and is unrelated — leave it untouched, and do not name the new section "comments".

**Documentation.** Extend the existing `documentation/developer-documentation/tab-plugins.md` rather than adding a page: a `commentLanguages` row in the Declaration reference table (`:67` area), a `tabLabelPrefix` Required column change from "yes" to "no", a new section covering the extension point led by the simplest example — a manifest claiming one extension and a handler returning one line marker — before the block-comment case, and an entry under `## API changelog` → `### v1` recording the additive change.

**Ordering.** Land the `host.ts` extraction first, then the contract types (`CommentSyntax`, the declaration and activation fields, the optional `tabLabelPrefix` with its one consumer at `src/plugins/context.ts:102`), then the claim registry and server dispatch, then the plugin itself with its two registration edges and the client-registry relaxation, and only then the client toggle. Typecheck stays green at each of those checkpoints. Every new `src/` import carries the `.js` extension per the NodeNext rule, and cache lookups use `??` rather than `||` to satisfy `prefer-nullish-coalescing` — a cached `null` must not be re-fetched as if it were absent.

## Out of scope

- **A block-comment chord.** No Cmd+Shift+/ that wraps a selection in `/* */` for languages that have both forms. Cmd+/ is the only commenting chord, and it uses the line marker wherever a language has one.
- **Third-party comment plugins.** Only the bundled `commenting` plugin ships. The extension point is designed so another plugin could claim more extensions, but nothing is loaded from disk and no way to install one is added.
- **Normalizing a mixed range.** A range holding both commented and uncommented lines gains a second marker on the already-commented ones rather than converging to one marker each.
- **Comment-aware editing beyond the toggle.** No continuing a comment block on Enter, no reflowing or wrapping a long comment, no jumping between comments.
- **Language detection beyond the extension.** No shebang sniffing, no content heuristics, no per-file override. A file with no extension has no comment syntax.
- **Region-aware syntax inside a mixed file.** An HTML file's embedded `<script>` block comments with `<!-- -->` like the rest of the file; the toggle never consults the highlighter's token stream to pick a different marker per region.
- **A configurable marker or spacing.** The table is fixed in the plugin; nothing in `.janissary/config.json` changes it.
- **Commenting anywhere but an editor tab.** Not in the markdown tab, not in the command bar, not in the agent query line.
- **Widening `pluginIntent` to core tabs.** The intent path keeps requiring a plugin-owned tab; commenting gets its own RPC instead.
