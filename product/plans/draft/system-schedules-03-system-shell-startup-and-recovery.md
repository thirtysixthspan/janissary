# System schedules 03: managed system shell startup and recovery

**Complexity: 6/10**

This coordinates guarded shell creation, PTY-generation recovery and profile exclusions over 01's lifecycle and 02's notice contract. It is the shell-lifecycle tranche only; persisted ownership and provenance are delivered separately.

## Goal

Create one hidden, unsandboxed zsh system tab beside `janus` on every startup and keep it usable across hides and shell exits. Source: `product/plans/ready/add-system-schedules.md`.

## Decisions and dependencies

- Dependencies: 01 (identity, visibility, user close) and 02 (failure notice).
- `openLaunchShell` continues to open and validate `janus` first; then it calls a focused `ensureSystemShell(managers)` service on every startup, including an ordinary restart. `janus` remains active and owns initial keyboard focus before remote restoration. A failed system shell is nonfatal and reports the 02 notice; the next ensure from firing or `execute` retries.
- Keep `startServer`'s unconditional, non-awaited `controller.reattachSessions()` after local startup. A parked remote session may add further tabs asynchronously; assert one managed local system shell, not exactly two total tabs. Remote restore must neither adopt a remote shell as system nor create a second managed shell. Preserve its existing independent failure handling and naming disambiguation.
- The service returns the canonical managed tab or a failure outcome. Concurrent ensure calls share one in-flight attempt. It uses the shell plugin's guarded `runCommand` fixed launch origin, project-root cwd, no workspace, and the reserved-label exemption. Check the actual opened label/terminal, not `tabs.length > 0` (which only proves `janus` exists).
- Preserve expected rejection reasons from the guarded plugin call. The current void `runCommand` reports rejections only to an originating transcript, which a failed startup origin lacks. Add a host-internal result-returning companion over the same guarded invocation; retain the existing void command API for other callers. Do not synthesize the underlying reason from a plugin status that is still `active`.
- Ordinary user closes only hide a live system shell. A real zsh exit cannot preserve the dead process: hide the same tab, end its tab-owned timers, then replace its terminal through a guarded shell intent and `updateTab` resource factory. Preserve its queue and tab identity, mint fresh hooks, and resume at a fresh idle prompt. On replacement failure keep it hidden and retry on the next ensure. This gives effect to the source's promise that process exit hides rather than destroys the managed tab.
- The server PTY-exit event is authoritative and generation/id checked. Duplicate client exit/mount-status callbacks must be idempotent and must not close a replacement shell. Shutdown/plugin disable must never schedule replacement or retry. A plugin disabled for a real plugin fault stays disabled until restart; the service may retry the request but must not bypass that boundary.
- Extend the client plugin's existing close capability additively with an optional `{ terminalExited: ptyId }` reason and carry it on the existing close RPC. Shell exit/mount-status uses that reason; the host validates it against the named tab's terminal generation before acting. A stale old-PTY close does nothing. Ordinary process exit keeps the documented direct last-tab quit behavior; it does not open a user-close quit confirmation. Zero-argument user close retains its old contract and system hide behavior.
- Use the existing `MountedViewLayers` retained plugin body, never a headless second shell consumer. Hidden means no drawn terminal, not no terminal emulator/marker processing. No autofocusing hidden command bars, window chord claims, or hidden pickers.
- `profile save` silently excludes the managed system tab whether hidden, revealed, renamed, or reordered. Profile relaunch's matching-label close pass must skip reserved `system` entries before destructive closure and report the reservation. System schedules are handled later and are never profile-captured.
- Also exclude the managed system tab from `profile/view-tabs.ts`'s fallback match for a subjectless shell/plugin entry. If a profile shell command opens nothing, that fallback must not mistake the already-open system shell for its result and move, dock, group or focus it.

## Existing code to reuse

`launch-shell.ts`, `plugins/host.ts` (`runCommand`, `intent`), `plugins/launch-tab-label.ts`, and `plugins/shell/{spawn-shell,activate}.ts` already provide fixed startup naming and resource factories. `tab/openers.ts` already adopts and records terminals created in `updateTab`. `controller/events.ts` relays plugin PTY exits to the client, while the shell's `useShellTabTerminal` and `useShellTerminalStatus` currently call client close. Preserve ordinary shell behavior on those paths.

## Ordered changes

1. Build the single-flight ensure service and fixed system identity. Create it only after the successful launch shell and mark/hide it without changing the final active tab or focus history.
2. Implement the guarded restart intent through existing own-tab/resource capabilities, with fresh PTY/nonce and ordinary recording/transcript registration. Keep expected process-start refusal a rejection, not a plugin failure.
3. Wire id-aware process exit to hide, clear only tab-owned timers, and recover. Integrate mount-time terminal status, client exit, teardown/shutdown guards, and stale callbacks. Keep a failed replacement from causing a tight retry loop.
4. Prove one hidden client mount continues to parse PTY idle/cwd markers, wakes the ordinary shell queue, and doesn't steal launch focus; gate `autoFocus` and active-only listeners accordingly.
5. Exclude system from capture, profile relaunch replacement and subjectless-plugin fallback matching, including hand-authored conflicting profile labels and a failed profile shell launch. Update specs for startup, shell exit, retained queues, and profile exclusions.

## Boundaries

No project schedule storage, creation grammar, postfix policy, or independent queue runner. Core coordinates the managed lifecycle without importing concrete plugin activation. User close preserves resources; actual process exit ends tab timers; destructive teardown releases everything.
