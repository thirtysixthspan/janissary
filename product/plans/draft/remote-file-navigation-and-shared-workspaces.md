# Remote file navigation and shared workspaces

**Complexity: 9/10** — a new bidirectional filesystem protocol surface with a version bump, a synchronous tree engine that has to start reading through an asynchronous port without changing its local behavior, two reference-counted lifetimes (the workspace clone and the ssh channel) replacing two ownership models that are currently "one tab, one thing", remote file content materialized for an opener stack that only knows local paths, and edits across roughly twenty server modules plus the client. It stays at 9 after trimming because none of that is what the trimming touched: containment, watching, debouncing, the cache's directory lifecycle, and the open-a-written-file route are all reused outright now, but the port seam, the two lifetimes, and the wire remain the work.

Make the two metadata-row buttons — 📁 "Open file navigator" and ➕ "New agent" — work the same way on a remote tab as on a local one, and make both of them land *inside the workspace the clicked tab is already using* rather than beside it. Today neither is true. A remote agent or harness tab's working directory is a path on another machine, so its 📁 button opens a tree over a path that does not exist here (`product/specs/remote-server.md` § Out of scope names "Remote file navigator, `open`, and editor tabs" as deliberately local-only), and its ➕ button either roots a local agent at a remote path or, on a workspaced tab, provisions a *second* clone (`product/specs/workspaced-agent.md`, `src/profile/manager.ts:94`) so two agents that ought to be collaborating end up in separate copies of the repository.

After this change a workspace is a thing several tabs share. The ➕ button always joins the launching tab's existing workspace on the launching tab's machine; the 📁 button opens a file navigator rooted in that same workspace, browsing the remote host over the ssh channel the tab already owns when the workspace lives there; and the workspace — with its clone, and on a remote its ssh session — is reference-counted, removed only once the last tab using it has closed. The buttons' tooltips say so.

## Design decisions

1. **A remote tree has full parity with a local one.** Listing, expanding, `..`, branch metadata, git-status coloring, row detail modes, watching, search-by-name, opening and editing a file, new file, new folder, rename, delete, move by drag-and-drop, copy/cut/paste, and undo/redo all work on a remote root, each executed on the far host. There is no read-only mode and no reduced menu: a row's context menu on a remote tree offers what it offers on a local one.

2. **➕ always joins the launching tab's workspace; it never clones.** On any tab that has a workspace — local or remote — the button creates an agent whose working directory *is* that workspace directory, on that workspace's machine, with no `git clone` of its own. This replaces today's inherit-by-cloning behavior (`src/profile/manager.ts:99-113`, and the paragraph in `product/specs/workspaced-agent.md` § Workspace agent tab that documents it). On a tab with no workspace the button is unchanged: a plain agent rooted at that tab's cwd. The `agent -w` / `harness -w` command forms are also unchanged — they still clone, and the button is the only route to a shared workspace.

3. **A workspace is reference-counted and outlives its creator.** Closing the tab that created a workspace no longer removes the clone while other tabs are still using it: the sharing agents stay open and keep working, and the clone is deleted when the last tab holding a reference closes. This is the single behavioral premise the rest of the plan rests on, and it applies identically to a local clone and a remote one.

4. **A remote navigator speaks over the tab's existing ssh channel.** No second ssh session and no second authentication prompt: the navigator's filesystem requests travel as a new frame family on the channel the agent or harness tab already owns (`src/remote/protocol.ts`), and `janus remote-serve` answers them by running the navigator's own filesystem primitives inside the workspace it provisioned.

5. **Channel ownership moves from the tab to the workspace.** `remote-server.md` § Lifecycle and cleanup today says "a remote tab's lifetime is its channel's lifetime"; it becomes "a channel's lifetime is its last user's lifetime". One ssh session and one `remote-serve` process serve a given host-and-workspace; the launching tab, every agent that joined via ➕, and the navigator each hold a reference; the session ends, and the remote clone is removed, when the last reference is dropped. Closing the launching tab therefore does not close the tabs sharing its workspace.

6. **The tie between a navigator and its tab is a remote-only tie.** A navigator opened from a *remote* tab's 📁 button is owned by that tab and closes when it closes — which is what the backlog asks for, and what keeps a tree from outliving the channel it reads through. A navigator opened from a local tab's button, or by the `files` command, keeps today's independent lifetime. The existing retarget rule is otherwise unchanged: clicking 📁 on a second tab still retargets the most-recently-focused navigator in place rather than opening a second one, and doing so transfers the tie — a navigator retargeted from a remote root to a local one stops being owned by anything, and one retargeted onto a remote root becomes owned by that tab.

7. **A dropped channel closes the navigator along with its tabs.** A channel that drops already closes the remote tabs it served; the navigator closes with them, and the notifications feed carries one line saying the connection ended. No disconnected tree is left on screen. An individual operation the far side refuses — a rename, a delete, a move — is not a channel fault and reports through the notifications feed exactly as a local failure does (`src/file-navigator/operation-report.ts`).

8. **Clipboard and drag-and-drop are same-host operations.** File *contents* never cross the wire for a move or a copy. A paste whose clipboard sources live on a different host than the destination tree is refused with a notifications-feed line naming the reason, the clipboard mark stays visible, and nothing is transferred; a drag whose target tree is on another host shows no drop highlight. The clipboard itself stays app-wide, so the marks still render in every navigator — a cross-host paste is refused, not invisible.

9. **Dragging a remote row into a command bar or editor inserts a host-qualified path.** The gesture is unchanged, but a row dragged out of a remote tree inserts `<host>:<absolute path on that host>` — the same `host:path` shape the `on <address>` clause already uses (`product/specs/remote-server.md` § Address grammar) — rather than a path relative to the target tab's working directory, which is meaningless across machines. Local trees are unaffected and keep inserting relative paths.

10. **`files in <label>` is the only command route to a remote tree.** Naming a remote agent or harness tab roots the tree at that tab's remote workspace, reusing the clause that already means "root at that tab's cwd". No new syntax: there is no `files on <address>`, because a tree on a host with no tab there would need a channel with no owner, which decision 5's reference counting has nothing to count.

11. **Both buttons' tooltips name the workspace, and only on a tab that has one.** A tab with a workspace reads "Open file navigator in this workspace" and "New agent in this workspace"; a tab without one keeps today's "Open file navigator here" and "New agent here".

12. **A remote navigator does not survive `profile save`/`profile launch` or `--relaunch`.** Remote agent tabs are already not restored (`product/specs/remote-server.md` § Out of scope), and a profile launch would have to re-authenticate an ssh session to restore a tree onto a clone that no longer exists. A saved profile records the navigator the way it records a remote tab and restores nothing.

13. **The navigator shows where it is looking.** A navigator rooted on a remote workspace carries the same host chip its owning tab's metadata row carries — bare host, full destination in the tooltip, ahead of the path — in its own header, ahead of the root path and branch. This is the backlog's "it will show the location in the metadatabar similar to how it is indicated for harnesses and agents".

14. **Opening a remote file materializes it locally, and saving writes back over the channel.** Double-click, Enter, `open`, and `edit` on a remote row read the file's content over the channel into a local cache file, then hand *that* path to the ordinary opener registry, so the editor, markdown, image, audio, and video tabs open exactly as they do for a local file. This is a decision about mechanism, not a hedge, and it is what makes decision 1 affordable: `OpenFileManager` and every opener resolve a real path on this machine (`src/open-file-manager.ts:2`, `statSync`; `src/openers/index.ts`), plugin openers serve their file to the browser through the file registry (`src/tab/file-registry.ts`), and a "remote path" would have to be threaded through all of it. The cache lives under `.janissary/remote-files/<host>/<workspace-label>/<tree-relative path>`, is cleared at launch the way `.janissary/workspace/` is (`product/specs/state-directory.md`), and is removed when the channel's last reference drops. A save from a cached file writes to the cache and then sends the content over the channel; a failed write reports through the notifications feed and leaves the tab dirty, so nothing is silently lost.

    **`open external` is the one exception** and is refused on a remote row with a notifications-feed line. The cached copy would in fact open in a native application, which is exactly the problem: edits made there would never travel back, since the external route has no save path of its own (`src/openers/os-open.ts`). Refusing is better than handing the user a file that silently discards their work.

15. **The remote runs the navigator's own filesystem code, not a reimplementation.** `remote-serve` imports the existing `src/file-navigator/filesystem.ts`, `stats.ts`, `search.ts`, `watch.ts`, and `src/git-status.ts` and calls them against the workspace it provisioned. The split is the tree *engine* stays local (tab state, expanded set, row building, undo/redo stacks, payload writing) and the *filesystem* moves — so a remote tree and a local tree cannot diverge in sorting, exclusion, naming-collision, or git-coloring behavior, because they run one implementation of each.

16. **`remote-serve`'s capability surface grows, and the spec says so.** Its stated surface today is "provision one workspace clone, run processes inside it, tail a harness transcript, remove the clone on exit" and it explicitly "will not serve files". That sentence changes: it now also reads, watches, and mutates files *inside the workspace it provisioned* and nowhere else. Every path it accepts is resolved against the workspace root and an escaping path is refused, which is the same containment rule the local navigator already applies to its own root (`file-navigator-tab.md` § Closing).

17. **A shared channel means a process must say which tab it belongs to.** `RemoteProcesses` is constructed once per channel with the provisioning label and stamps it into every piped shell's environment as `JANUS_AGENT_NAME` (`src/remote/serve-processes.ts:23,68`, `spawnShell(0, { JANUS_AGENT_NAME: this.label }, …)`). With two tabs on one channel that name would be wrong for the second, so the spawn frame carries the agent name and the holder prefers it, falling back to the provisioning label when absent. This is a contract change and part of the same version bump.

18. **`REMOTE_PROTOCOL_VERSION` moves to 7.** New frames the far end must honor are a contract change by that file's own rule, and an installation that ignored them would provision a workspace and then answer no listing at all. Both ends must be updated together and a stale remote is refused at the handshake, as with every previous bump.

## Proposed changes

### A filesystem seam in the navigator

Introduce a filesystem port — one interface in a new `src/file-navigator/filesystem-port.ts` — naming everything the tree engine asks of a disk: read one directory's entries, stat a batch of rows for the current detail mode, watch and unwatch a directory, read branch/status/GitHub-remote for the root, list the gitignore-aware search candidates, read and write a file's content, and the mutation set (rename, delete, move, copy, create file, create directory) returning the existing `FileOperationResult` shape. Two implementations: a local one that is a thin pass-through to the modules that already do this work synchronously, and a remote one that turns each call into a frame. `FilesTabState` gains the port alongside its `root`, so every existing call site reaches the filesystem through the state it already holds.

The consequence to plan for rather than discover: the remote port cannot answer synchronously, and `rebuild` is synchronous today. The tree engine keeps its synchronous shape and reads from a **per-tab listing cache** — the directory entries, stats, and git status the port has already delivered — while the port fills that cache asynchronously and signals the manager to rebuild when a listing lands, which is the same "schedule a rebuild, emit dirty state" path the directory watchers already use (`src/file-navigator/manager.ts:271-279`, `scheduleRebuild`). A row list for a directory whose listing has not arrived renders as the existing waiting state rather than as an empty directory. The local port's cache is filled inline, so local behavior — including its tests — is unchanged.

**`src/file-navigator/manager.ts` has no room.** It counts 200 lines against the `max-lines` limit of 200 today, so *nothing* may be added to it: the port construction, the listing cache, and the cache-filled-so-rebuild callback all go into new sibling modules that the manager delegates to through the closure-passing pattern it already uses for `navPort()`/`openPort()` (`src/file-navigator/manager-ports.ts`), and any method the change would otherwise grow moves out with them. This is an extraction, never a compaction (`ai/guidelines/code-guidelines.md`). The other files this plan touches have headroom — `src/remote/protocol.ts` counts 82, `frame-decode.ts` 96, `channel.ts` 109, `serve.ts` 130, `src/profile/manager.ts` 114, `web/src/shared/AgentTabMeta.tsx` 110 — but the per-operation validation table will push `frame-decode.ts` hard, so measure it at its step rather than at the end and split the table into its own module if it goes over.

### The remote frame family

Add to `ClientFrame` a filesystem request frame carrying the navigator session id, a request id, an operation name from a closed set, and the operation's arguments; and open/close frames that bind a navigator session to the channel's workspace. Add to `ServerFrame` a reply frame carrying the session id, the request id, and either the operation's result or an error, plus one unsolicited event frame for a watched directory changing. Request/reply is preferred over one frame type per operation because the operation set is large and the alternative would double the size of both the protocol and its decoder; the cost is that validation moves into a per-operation table in `src/remote/frame-decode.ts`, which must enumerate every operation's argument shape so "every frame is validated before dispatch" (`remote-server.md` § Failures) stays true rather than degrading to "the envelope is validated". File content travels base64-encoded like every other payload in that codec.

`src/remote/channel.ts` gains a second id-keyed listener map for navigator sessions, mirroring `attach`/`detach`, with replies routed to it before the switch that ends in `fail` — a filesystem error is never a transport fault. The map is cleared in `closed()` alongside `sessions`.

### The far side

A new module beside `src/remote/serve-processes.ts` owns the navigator sessions: constructed with the emit function and the workspace directory, it dispatches each request to the imported navigator primitives, holds the watch handles through the existing `watchDir`/`unwatchDir` (`src/file-navigator/watch.ts:11,22`) and emits a change event per watch callback, and disposes everything on shutdown before the clone is removed. Containment is not a new check: every request resolves its path through `containedPath` (`src/file-navigator/batch-paths.ts:7`), the same helper the local navigator's move, delete, and paste paths already use to refuse an escaping path, with the workspace directory as the root.

The remote does **not** debounce: a watch event is forwarded as it fires and the existing per-tab debounce in `scheduleRebuild` (`src/file-navigator/manager.ts:271-279`, `DEBOUNCE_MS = 100`) coalesces the burst on this side, exactly as it does for a local tree — one debounce, in the place that already has one. The ceiling that buys: a burst like a remote `git checkout` sends one small frame per event rather than one per 100ms. If that proves chatty in practice, the upgrade is to coalesce inside the far side's watch callback before emitting, with no change to the frame contract or to this side. `src/remote/serve.ts` constructs it in `provision` beside `RemoteProcesses` (`src/remote/serve.ts:120-125`), adds the new cases to its dispatch switch, and refuses a filesystem frame that arrives before provisioning with the exact message `spawn` already gives for that condition — `'No remote workspace has been provisioned.'` (`src/remote/serve.ts:134`) — rather than a second wording for the same fault.

`RemoteProcesses` also gains decision 17's per-spawn agent name: the constructor keeps the provisioning label as the default and `spawnPipe` prefers the name on the frame, so a joined tab's shell gets its own `JANUS_AGENT_NAME`.

### Materializing a remote file

A new module under `src/file-navigator/` owns the local cache decision 14 describes, built in the shape `src/harness/capture-file.ts` already established for exactly this problem — an init that records the directory (`initHarnessCaptureDirectory`, `:7`), a write that ensures it and returns the absolute path (`writeCaptureFile`, `:17`), and a clear (`clearCaptureDirectory`, `:24`) called at launch alongside `clearWorkspaceDir` (`src/workspace/index.ts:200`). Given a navigator session and a tree-relative path it reads the content over the port, writes it under `.janissary/remote-files/<host>/<workspace-label>/<relative path>` — keeping the tree-relative path and its extension so openers still dispatch by extension and two same-named files cannot collide — and returns that path; given a save it writes the cache file and sends the content back. It also removes the cache when the channel's last reference drops.

Opening from there is the existing route, not a new one: the row-open path hands the cached path to `managers.openFile`, the same way `openTranscriptFor` writes a snapshot with `writeCaptureFile` and opens it with `managers.openFile.edit(…)` (`src/controller/transcript.ts:8-13`). `openersForRow` (`src/file-navigator/openers-for-row.ts`) resolves the cached path for a remote tree and the real path for a local one; `OpenFileManager`, the opener registry, and every opener are untouched.

### Reference-counted workspaces

`WorkspaceManager` gains a reference count per clone directory: `create` starts one at a single reference, a new retain/release pair adjusts it, and `remove` becomes "drop this tab's reference; delete the clone when it reaches zero". `removeAll` at shutdown is unchanged. `closeTabResources` calls release rather than remove; the cancel-if-still-provisioning guard stays, but only fires for the tab that created the clone, since cancelling a clone another tab is already working in would be wrong.

`RemoteManager` keeps its label-keyed registry (`src/remote/manager.ts:43`, `entries`) rather than being re-keyed by host and workspace: sharing only ever happens through ➕, which already knows the creator's label, and two independent `on <address>` launches to one host deliberately stay two sessions (see Out of scope), so there is nothing a composite key would match that a label does not. What changes is smaller — an entry gains the set of labels using it, a joined tab registers as an alias onto the creator's entry, `get`/`addressOf`/`transcriptSource` follow the alias, `close(label)` removes that label and closes the channel only when the set empties, and the channel's `onClose` closes every tab still in the set instead of just the one. `connection close ssh:<id>` keeps its meaning — it closes the channel outright and therefore every tab on it, which is worth stating in the connections spec.

### The ➕ button

`ProfileManager.newAgentAt` (`src/profile/manager.ts:94`) loses its clone branch — the `this.managers.workspace.create(resolved)` call and the `wireProvisioning` block that follows it (`:106-125`). When the creator tab has a `workspaceDir`, call `placeAgent` with the creator's own workspace directory as both `cwd` and `workspaceDir`, retain a reference to that clone, and copy the creator's `remote` target onto the new tab when it has one. There is no clone to wait for, so the new tab is not marked busy and posts no "ready" or clone-failure notification; the pool-exhaustion message (`'All agent names are in use.'`) is unchanged.

A joined *remote* tab deliberately skips the whole remote-launch path: no `startRemoteLaunch`, no `setActivePty` takeover, and no `wireProvisioning` (`src/profile/remote-agent.ts:31-45`), because there is no ssh session to authenticate and no workspace to provision — both already exist. Its shell then comes for free: `ShellManager.spawnFor` looks the channel up by tab label (`src/shell-manager.ts:76`, `tab?.remote ? this.managers.remote.get(label) : undefined`), which resolves through the re-keyed registry, and the spawn frame carries no cwd, so `RemoteProcesses` starts it in the shared workspace (`src/remote/serve-processes.ts:47-49`). The one case that must wait is a creator whose own clone — local or remote — is still provisioning: the joined tab is placed immediately and its shell starts when the creator's existing `ready` promise resolves, reusing the creator's wiring rather than adding a second provisioning path.

### Client

`AgentTabMeta` takes the tooltip text for its two buttons from whether the tab carries the workspaced flag, per decision 11 (`web/src/shared/AgentTabMeta.tsx:62,71`, where both titles are literals today). `FileNavigatorHeader` renders the same `RemoteChip` ahead of its path when the tree's root is remote, which means the navigator's tab payload carries the remote target the way an agent tab's does; `RemoteChip` moves out of `AgentTabMeta.tsx` into a shared component so both render one chip rather than two lookalikes. `file-navigator-relative-path.ts` formats the host-qualified path for a remote tree (decision 9) and `file-navigator-drag.ts` consumes it; the drop-target guard in the same module and the paste guard in `file-navigator-clipboard.ts` consult the source and destination hosts (decision 8); `file-navigator-menu-items.ts` drops the plugin selection entry for a remote tree (see Out of scope). Everything else in `web/src/file-navigator/` is unchanged: the client renders rows the server sends and has no idea which machine they came from.

### Implementation order

Each step should leave typecheck and tests green on its own.

1. Reference-counted workspaces, and `closeTabResources` releasing instead of removing. Local-only, independently testable, and the premise for everything else.
2. The ➕ button sharing a local workspace, with its tooltips. Delivers a usable feature on its own with no protocol work at all.
3. The filesystem port and the local implementation, with the tree engine reading through it. A pure refactor — no behavior change, and the existing navigator tests are its guard.
4. Protocol frames, decoders, version bump, and channel routing. Inert until something sends them.
5. The far side's navigator holder, driven end to end against an injected `RemoteServer`.
6. The remote port, the listing cache, and the 📁 button and `files in <label>` opening a remote tree — the step that makes browsing reachable.
7. The remote-file cache, open/edit, and save-back (decision 14), and `open external`'s refusal.
8. Reference-counted channels, the per-spawn agent name (decision 17), and ➕ joining a remote workspace.
9. Specs and documentation.

Steps 1–2 and 3 are independent of each other; 4–6 depend on 3; 7 and 8 depend on 6. This plan conflicts with nothing in flight except `product/plans/draft/add-acp-support-to-remote-agents.md`, which also bumps `REMOTE_PROTOCOL_VERSION` and adds frames to the same three files — whichever lands second takes the next version number and merges its frames alongside the other's.

## Out of scope

- Cross-host file transfer of any kind: copy, cut, paste, drag, and undo/redo all stay within one host (decision 8).
- `files on <address>` — a tree on a host with no agent or harness tab there (decision 10).
- Restoring a remote navigator through `profile launch` or `--relaunch` (decision 12).
- `open external` for a remote file (decision 14), and any remote-side external opener.
- Plugin-contributed selection entries (the audio plugin's "Add to playlist" and any future one) on a remote tree: a plugin's server activation reads paths on this machine, so the entry is not offered when the tree is remote.
- Sharing a workspace between tabs on *different* machines, and any form of ➕ that targets a host other than the launching tab's.
- A `-w`/`--workspace` command-line form for joining an existing workspace by label; the ➕ button remains the only route (decision 2).
- Nested remoting, reconnect/resume after a dropped channel, and ssh options on the clause — all already out of scope in `remote-server.md` and unchanged here.
- Multiplexing one channel across *different* remote workspaces on the same host: the reference count is per host-and-workspace, so two separate remote launches to one host still open two sessions.

## Open questions

1. **Whether a remote-backed editor tab watches the far side for external changes.** Decision 14 settles how a remote file opens and saves. What it leaves open is `EditorWatchManager` (`src/editor/watch-manager.ts`, wired through `managers.editorWatch.closeTab` at `src/tab/cleanup.ts:33`): it watches the *local* cache file, which nothing but janissary writes, so it would never fire for a change made on the remote. The recommended default is that the navigator's own directory watch is the signal — a change event for an open file's path refreshes the cache and drives the existing external-change and resync flow (`src/editor/resync.ts`) — rather than adding a second per-file remote watch. This is a mechanism choice inside an already-decided behavior, so it does not block the plan.
2. **What the 📁 button does on a remote tab whose channel has not attached yet.** Nothing can be listed before the handshake lands. The recommended default is to open the navigator immediately in the existing "Looking for…" waiting state and populate it when the channel attaches, matching how `files` already handles a root that does not exist yet — rather than refusing the click.
