# PDF viewer plugin

**Complexity: 5/10** — the plugin contract does all the structural work (one manifest, one activation, one lazy client chunk, three registration entries), and the browser does the rest of what would have been custom (`IntersectionObserver` for visible pages and the current page, `scrollIntoView` for jumps, PDF.js's own text-layer stylesheet). What is left is one stage with two fit rules, a thumbnail strip reusing the same renderer, and the real risk: bundling a new dependency's worker and font assets so the viewer works offline from the app's own origin.

Backlog text: *"add a pdf viewer plugin that will render a pdf in a new tab type, a pdf tab."*

Today `.pdf` is the codebase's canonical example of a file type **no** opener claims. `product/specs/open.md:48` uses it to explain the fallback — "a PDF reaches the system viewer without any opener claiming `.pdf`" — `src/open/file-manager.ts:104` names it in the same breath, and `open paper.pdf` raises an `open-unsupported` notification rather than showing anything. A PDF can only leave the app.

This feature adds `pdf` as a bundled tab plugin alongside image, markdown, video, audio, page, schedules, and conversations. `open paper.pdf`, `pdf paper.pdf`, `edit paper.pdf`, and activating a PDF row in the file navigator all mount a **PDF tab**: a metadata header above a stage that renders the document with **PDF.js** in the browser, one fitted page at a time by default, with an icon-only header toggle to continuous scroll, a hideable thumbnail strip for jumping between pages, selectable text, and zoom. Pages are navigated with the keys; zoom is a button. A PDF that cannot be rendered says so in the body and reports one line to the notifications feed naming why.

## Design decisions

**PDF.js renders the pages; the browser's own viewer is not used.** The pages are drawn by `pdfjs-dist` into canvases the plugin owns. That is what makes every decision below possible — a browser's built-in PDF plugin comes with its own toolbar, ignores the application theme, cannot be told to show a thumbnail strip or a layout toggle, and behaves differently in each browser the web client runs in. It costs one new runtime dependency, paid only by people who open a PDF: the plugin's client chunk is lazy (`web/src/plugins/registry.tsx:32`–`:40`), so PDF.js is not in the entry bundle and a session that never opens a PDF never downloads it.

**Two layouts, single page first, toggled from the header.** The stage renders either **single page** — one page fitted to the tab with prev/next controls and a `3 / 12` position readout — or **continuous scroll**, every page stacked vertically in one scrolling stage the way the markdown tab scrolls. A tab opens in single page. An **icon-only button** in the header's action group, beside the Split action and styled like the image tab's pen-shaped `Edit image` control (`web/src/plugins/video/VideoTab.tsx:48`–`:62` shows the slot), switches between them; its accessible name and tooltip read `Continuous scroll` when it will switch to continuous and `Single page` when it will switch back. The choice is **per tab and live in-memory** — it is not persisted, not restored by `--relaunch`, and a second PDF tab opens in single page regardless of what the first was switched to, exactly as image zoom and markdown scroll position behave.

**A hideable thumbnail strip, hidden when a tab opens.** A second icon-only header button shows and hides a strip of page thumbnails down the left edge of the tab body; its accessible name and tooltip read `Show pages` when the strip is hidden and `Hide pages` when it is showing, naming what the click will do rather than the current state, exactly as the layout toggle does. It starts hidden, so a newly opened PDF is all document. Clicking a thumbnail jumps to that page — scrolling it into view in continuous layout, making it the shown page in single-page layout — and the current page's thumbnail is highlighted in both. The strip is available in both layouts rather than being a single-page-only page-picker, because it is also how a reader skims a long document they are scrolling.

**Text is selectable and copyable.** PDF.js's text layer is positioned over each rendered canvas, so a passage can be selected with the mouse and copied with the platform's own copy chord. There is no in-app copy button and no "copy all text" action; selection and copy are the browser's, as they are in the markdown tab. Selection is highlighted in a color clearly distinct from the background in every theme, the rule `product/specs/markdown-tab.md:93`–`:95` already states for rendered Markdown.

**Keys navigate, buttons zoom.** ↑/↓ and Page Up/Page Down move between pages in single-page layout and scroll in continuous layout; a plain mouse wheel always scrolls, the way a document scrolls. Zoom is the header's `+` and `−` controls and `Ctrl`/`Cmd`+wheel. `Escape` resets zoom to 100% and returns the view to the fit. This deliberately **departs from the image tab**, where Page Up/Page Down and the bare wheel zoom (`product/specs/image-tab.md:96`–`:102`): an image has one page and nowhere to scroll, so zoom is the only thing those keys could mean, while in a document they already mean something and stealing them would be surprising. It follows the markdown tab's key meanings instead (`product/specs/markdown-tab.md:101`–`:107`) and adds zoom beside them rather than on top of them.

**100% means fitted, and what it fits depends on the layout.** In single page, 100% fits the **whole page** inside the stage — the layout's point is seeing one page at a time. In continuous scroll, 100% fits the page **width**, so scrolling is the only axis that matters. Beyond 100% the page overflows and the stage scrolls in both directions; there is no click-drag panning, because a scrolling stage already reaches the overflow and the image tab's drag-to-pan exists only because its stage does not scroll. Zoom reuses the image tab's documented bounds — 10% steps, clamped to 10%–800%, saturating at the ends (`product/specs/image-tab.md:101`–`:102`) — rather than inventing a second scale, and the current percentage is shown on the view only while it differs from 100%, as the image tab shows it.

**Only the pages on screen are rendered, and the browser decides which those are.** Rasterizing every page of a 500-page document at mount would break the plugin performance budget in `ai/guidelines/plugins.md`, so a page renders when it comes near the viewport and not before. That question — which elements are on screen — is answered natively by **`IntersectionObserver`** with a root margin, so this plugin computes no scroll-offset-to-page-index arithmetic of its own, keeps no render window, and recycles no canvases. The same observer answers the other question the view has: the page whose placeholder most fills the stage is the one the `3 / 12` readout and the highlighted thumbnail name. Page *placeholders* are laid out for the whole document from the page sizes PDF.js reports, so the scrollbar is honest from the first frame and a jump from the thumbnail strip lands in the right place.

*Ceiling on that simplification:* a rendered page keeps its canvas after it scrolls away, so a very long document read end to end grows in memory until the tab is closed. The upgrade, if that ever bites, is to release the canvas of a page far outside the observed margin — a change inside the page component, reachable without revisiting the layout. It is deliberately not built now: a canvas per page at fit scale is small, and the alternative is exactly the bookkeeping this decision removes.

**A PDF that cannot be rendered fails in the body and names the reason in the feed.** The stage is replaced by `Failed to load <name>`, matching the markdown tab's wording for an unreadable registered file (`product/specs/markdown-tab.md:54`–`:55`), and the tab stays open. One line additionally goes to the notifications feed, naming what went wrong: `<name> is password-protected`, `<name> could not be read`, or `Could not display <name>` for anything else. The feed line exists because the tab body is not always on screen — the same reason the audio plugin reports an undecodable track there (`src/plugins/audio/activate.ts:103`). There is **no password prompt**: an encrypted PDF is reported, not negotiated.

**The client names a failure *kind*; the server writes the line.** The failure is detected in the browser, where PDF.js is, but `notifyUser` is a server capability (`src/plugins/api.ts:184`) and the feed's wording is not something a client should be able to dictate. The client sends an intent carrying one value from a closed set — password-protected, unreadable, or other — and the server maps it to the fixed line above. A payload outside that set is a rejected bad request, not a broken plugin, exactly as `src/plugins/video/activate.ts:58` treats a malformed capture payload.

**The plugin claims `.pdf`, the `pdf` command, and the `edit` verb.** Three routes, all reaching the same tab:

- `open paper.pdf` mounts the tab; `open external paper.pdf` still hands the file to the OS, so nothing a user does today stops working.
- `pdf <path>` is a second route into this plugin's own opener, with the same path resolution, wildcard expansion, file cap, and missing-file errors as `open`, following `src/plugins/video/activate.ts:22`–`:28` exactly. `pdf external <file>` on a non-PDF reports the unsupported type rather than handing it to the OS, per `product/specs/tab-plugins.md:25`.
- `editsOwnFiles` claims `edit` for `.pdf`, so `edit paper.pdf` and Shift-activating a PDF row in the file navigator open the viewer. Both consequences `product/specs/open.md:38` records for images follow here: `edit paper.pdf` can no longer open a PDF as raw bytes in the text editor, and there is no escape hatch for that. A PDF has no lines, so a `:line` suffix is parsed and discarded and the path still opens.

**Claiming `edit` and declaring a navigator edit gesture are mutually exclusive, and `edit` wins.** `src/file-navigator/openers-for-row.ts:29` checks `editGesture` *before* the `edit` branch on the next line, so a declaration carrying both would send Shift-activation to `open external` and leave `editsOwnFiles` reachable only by typing the command. Shift-activating a PDF row should show the PDF, so this plugin declares `editsOwnFiles: true` and **no** `editGesture` — the image plugin's shape (`src/plugins/image/manifest.ts:24`), not video's and audio's (`src/plugins/video/manifest.ts:26`).

**The external hand-off honours a configured viewer.** `open external paper.pdf`, and the external route from the file navigator, go through `openFileInConfiguredViewer` (`src/plugins/files.ts:39`–`:48`) with `PDF viewer` as the kind. That reads `externalViewers.pdf` from the application config (`src/plugins/context.ts:151`, keyed by plugin id), so a user who names a preferred PDF application gets it and its name in the confirmation, and everyone else gets `Opening paper.pdf in your default PDF viewer…`. It costs one extra declared capability and no new configuration surface.

**PDF.js's worker and both optional asset bundles ship inside the chunk.** PDF.js parses in a worker, reaches for **character maps** for CJK and unusual text encodings, and reaches for **standard font data** for documents that do not embed their fonts. All three ship: a document that renders wrong is a worse outcome than a chunk that is larger, and the cost falls only on sessions that actually open a PDF, since the whole plugin loads lazily. All of it is resolved from the installed package at build time and served by the app's own web server; nothing is fetched from a CDN at runtime, because the app serves only its own bundled assets and its registered files and a viewer that silently stopped working offline or behind a proxy would be the worst outcome of the three.

The weight is not guessed at and then forgotten: the implementer records the built chunk's size once it exists, which is what a later decision to drop one bundle would need. Dropping the character maps degrades CJK and unusual-encoding documents; dropping the font data degrades documents relying on the standard 14 fonts; neither breaks the viewer, so both remain revisitable without redesign.

**Everything else is inherited from the plugin contract, not decided here.** A PDF tab is a live in-memory view tab: it joins the active tab's group, takes a distinct dot color, carries the file's name, path, and human-readable size plus one registered reference for the bytes, de-duplicates on the file path so reopening focuses the existing tab, shows a close button, docks into either sidebar, is captured and reissued by a profile, and is not restored by `--relaunch`. None of that is written again for this plugin — it is what `product/specs/tab-plugins.md:39`–`:45` already says every v1 plugin tab does.

## Proposed changes

New server modules under `src/plugins/pdf/`, following the directory shape every bundled plugin already uses. Imports carry `.js` per the NodeNext rule in `CLAUDE.md`; client imports stay extensionless.

**`src/plugins/pdf/shared.ts`** publishes the payload contract: a schema-version constant, a `PdfPayload` type carrying the file's name, absolute path, human-readable size, and the registered reference the client fetches bytes from; a `LoadFailure` union naming the three failure kinds; and guards for the payload and for the failure intent's payload, in the shape of `src/plugins/video/shared.ts`. The payload deliberately does **not** carry the configured external viewer's name the way `VideoPayload` does (`src/plugins/video/shared.ts:8`): that field exists so the video view can offer an "Open in <player>" button when the browser cannot decode, and this plugin's failure behavior is a message plus a feed line with no escape-hatch button, so the field would have no reader.

**`src/plugins/pdf/manifest.ts`** declares the plugin: id `pdf`, tab label prefix `pdf`, one claimed extension mapped to `application/pdf`, the `pdf` command, `editsOwnFiles`, and the capability list this plugin actually reaches — `note`, `notifyUser`, `openOrFocusTab`, `openClaimedFiles`, `configuredViewer`, `openExternally`, `rejectRequest`, and `reportFailure`. No `editGesture`, for the reason recorded above. A capability the manifest omits but the code reaches for disables the plugin on first use (`product/specs/tab-plugins.md:15`), so this list is checked against what `activate.ts` actually calls, not copied wholesale from another plugin.

**Registration is three entries, not one, and they land together.** `src/plugins/catalog.ts` gains the import and the array entry — inserted between `pageManifest` and `schedulesManifest`, because `src/plugins/host.test.ts:62` asserts the catalog's ids are already in sorted order. `src/plugins/loaders.ts:4`–`:12` gains the lazy `import('./pdf/activate.js')` entry: that map, not the catalog, is how server behavior is reached, and `eslint.plugin-boundaries.mjs:73`–`:84` makes a static import of an `activate.js` from core a lint error. `web/src/plugins/registry.tsx` gains the matching client loader and registration. Both loader maps are typed `satisfies Record<ProductionTabPluginId, …>`, so the moment the catalog gains `pdf` the project stops typechecking until both are filled in — which is the ordering constraint: manifest, catalog, both loaders, and a minimum client entry are one landing, and nothing between them typechecks. The claimed extension needs no separate content-type registration; `src/index.ts:29` derives it from the manifest.

**The import boundaries are narrow, and PDF.js is on the right side of them.** `eslint.plugin-boundaries.mjs:27`–`:38` limits a server plugin to `../api.js`, `../files.js`, and two named opener helpers; everything this plugin's server half needs is in the first two. `:43`–`:54` limits a client plugin to `../api`, `../shared.css`, and its own `@shared/plugins/pdf/shared` contract. Neither rule restricts external packages, so importing `pdfjs-dist` inside `web/src/plugins/pdf/` is allowed as written — but nothing from the host, the editor, or another plugin is, which is why the view composes the header from the shared stylesheet's classes rather than importing a host component.

**`src/plugins/pdf/activate.ts`** returns the activation: the payload guard; a command handler that refuses an empty argument with a usage line and otherwise re-enters the plugin's own opener; an opener whose external presentation hands the file to the configured or default PDF application, whose inline presentation opens or focuses a tab keyed on the file path, and whose edit presentation is the same call — a PDF has one presentation, and `edit` reaches it rather than the text editor; and an intent handler answering exactly one intent, the client's report that the document failed to load. That handler validates the failure kind against the closed set, composes the fixed line for it, and calls the notifications-feed capability. An unknown intent name or a malformed payload is a rejected request; a tab payload this plugin could not have produced is a reported failure.

New client modules under `web/src/plugins/pdf/`, split to keep every file inside the 200-line `max-lines` limit with rendering, view state, and chrome in separate modules per `ai/guidelines/react-code-organization.md`. A plugin directory is not a client *feature* directory — `clientFeatureDirectories` at `eslint.config.mjs:14`–`:22` is an explicit list that does not include `plugins` — so no cross-feature boundary entry is added for it:

- **`index.tsx`** — the lazy entry: imports the shared plugin stylesheet, the PDF.js text-layer stylesheet, and this plugin's own, then re-exports the tab component as default and the payload guard as `isPayload`, in the shape of `web/src/plugins/video/index.tsx`. **`web/src/plugins/registry.tsx`** gains the matching loader entry and registration, and the schema-version literal the registry test pins against the plugin's own constant.
- **`pdf-document.ts`** — the only module that touches PDF.js. It configures the worker from the installed package, resolves the character-map and standard-font asset paths, loads a document from an authenticated URL, and answers either a loaded document handle or one of the three failure kinds; it also exposes rendering one page into a canvas at a given scale and the page sizes the layout needs. Isolating it here is not tidiness: client tests run in **jsdom** (`vitest.config.ts:76`–`:77`), which has neither a canvas 2D context nor a worker PDF.js can drive, so every other module in this plugin has to be reachable with this one mocked. It is also what makes swapping how the worker is provisioned a one-file change.
- **`pdf-view-model.ts`** — pure functions with no React: clamping and stepping zoom, and deriving the fit scale for a layout from a page size and the stage size. That is all it holds, because `IntersectionObserver` answers which pages are visible and which one is current, and scrolling a page into view is `Element.scrollIntoView` — the three pieces of scroll arithmetic an earlier shape of this plan would have put here are all platform features.
- **`usePdfDocument.ts`** — the hook bridging the loader to the component: loading status, the document handle, page count, and, on failure, the kind plus the one intent call that reports it to the server. It fires that report once per tab, so a re-render cannot spam the feed.
- **`usePdfKeys.ts`** — the key handling, gated on the host's `active` answer so a hidden or split-away PDF tab ignores every key, following `useAudioKeys`.
- **`PdfTab.tsx`** — the tab body: the shared metadata header with the file's name, size, and location, the two toggle buttons and the zoom controls in the action group before the host's split action, and beneath it the thumbnail strip and the stage. It composes; it does not compute.
- **`PdfStage.tsx`** and **`PdfPage.tsx`** — the stage and one page. There is **one** stage and **one** page component, not a path per layout: continuous scroll and single page differ only in which pages the stage lists and which fit rule it applies, so the layout toggle changes two inputs rather than swapping renderers. `PdfPage` owns a canvas, its text layer, and the observer entry that decides when it renders.
- **`PdfThumbnails.tsx`** — the strip. It renders each thumbnail through the same page-render function the stage uses, at a small fixed scale and without a text layer; there is no second rendering path.
- **`pdf.css`** — this plugin's own styling only: the strip, the stage's page spacing, and the theme's selection color. The header, action group, and stage frame come from the shared plugin stylesheet (`web/src/plugins/shared.css`), and the text layer's positioning rules come from the stylesheet `pdfjs-dist` already ships for exactly that, imported from this plugin's entry so it lands in the lazy chunk. Restating that geometry by hand would be reimplementing a file the dependency provides and would drift from it on every upgrade.

**Dependency.** `pdfjs-dist` is added as a runtime dependency. Per `CLAUDE.md` it passes `./scripts/run.mjs check-malicious-package pdfjs-dist@<version>` before anything is installed, and only a clean exit permits the install — `pdfjs-dist@6.3.289`, the current latest, was gated while this plan was written and came back `OK`. The implementer re-runs the gate against whatever version they actually install rather than trusting that result.

**The worker and asset data are emitted by the build, not fetched.** The worker is created from a module-worker URL resolved against the installed package, which is the form Vite recognizes and rewrites into an emitted chunk. The character-map and standard-font directories are emitted as static assets through an addition to `web/vite.config.ts`; `base: './'` (`web/vite.config.ts:10`) keeps their URLs relative, and the server already serves `web/dist` statically, so everything resolves against the app's own origin at whatever path the window was opened at. If emitting those directories proves awkward, the fallback is to drop the font and cMap data and accept degraded rendering for documents that do not embed their fonts — not to fetch them from a CDN, which would break the app offline and behind a proxy.

**Specs.** A new `product/specs/pdf-tab.md` describes the tab as a whole, in the shape of `image-tab.md` and `markdown-tab.md`: the tab data, serving the file, layout, the two layouts and their toggle, the thumbnail strip, zoom and keys, text selection, the failure behavior and its exact lines, and the tab-strip, closing, and grouping treatment that every plugin tab shares. `product/specs/tab-plugins.md` gains a "Bundled PDF plugin" section beside the existing ones. Two existing spec passages become false and are rewritten rather than appended to: `product/specs/open.md:44`–`:52`, where the PDF is the worked example of a type with no opener, needs a different example — a `.zip` is the honest one — and `product/specs/open.md:36`–`:38`, which says the image opener is the only one claiming `edit`, now names two.

**User documentation.** A new `documentation/user-documentation/tab-types/pdf-viewer.md` beside `image-viewer.md` and `video-player.md`, with its sidebar entry in `documentation/.vitepress/config.mts:95`–`:96` beside the existing tab-type entries. Four existing passages are now false or incomplete and are corrected in the same change, all of them found by grepping the docs for `pdf` and for the tab-type link list:

- `documentation/user-documentation/tab-types/opening-files.md:29`,`:33` — uses `open external paper.pdf` as its worked example of handing a file to the OS, and says Janissary has no viewer of its own for a `.pdf`. The example moves to `.zip`.
- `documentation/user-documentation/tab-types/opening-files.md:16` — the list of what kind of tab each file type opens, which needs the PDF viewer link.
- `documentation/user-documentation/tab-types/file-navigator.md:131` — "a PDF goes to your system PDF viewer", which is now only true of the external route.
- `documentation/user-documentation/command-bar/plugins.md:26` — the sentence enumerating which tabs are plugin tabs.

`documentation/developer-documentation/tab-plugins.md` needs no change: it documents the contract and the `fixture-v1` example, and its assertions in `src/plugins/documentation.test.ts` pin capability counts and the fixture manifest, none of which this plugin moves.

**Documentation screenshot.** The new user-doc page gets a screenshot the way the image and markdown pages do: a `data-doc-shot="pdf-view"` attribute on the tab body's root element (as at `web/src/plugins/video/VideoTab.tsx:42`), one entry in `scripts/docs-screenshots/manifest.mjs` beside the `image-tab` and `markdown-tab` entries at `:79`–`:80` opening a sample file, and a small `sample.pdf` added to `scripts/docs-screenshots/fixtures/` beside the existing `sample.png` and `sample.md`.

## Tests

Colocated as `src/**/*.test.ts` (vitest project `server`) and `web/src/**/*.test.ts(x)` (project `client`), matching each touched area.

- `src/plugins/pdf/shared.test.ts` — the payload guard accepts a complete payload and rejects each missing or mistyped field; the failure-kind guard accepts exactly the three kinds and rejects anything else.
- `src/plugins/pdf/activate.test.ts` — `open` on a `.pdf` opens or focuses one tab keyed on the path, registering exactly one file; reopening the same path focuses rather than opening a second tab; `edit` on a `.pdf` reaches the same tab rather than the text editor; `open external` uses the configured viewer when one is set and the default hand-off when it is not; `pdf <path>` re-enters the opener and `pdf` with no argument is a usage rejection; the failure intent produces exactly the three fixed feed lines for the three kinds; an unknown intent name and a malformed failure payload are rejections that leave the plugin running; a foreign tab payload is a reported failure.
- `src/plugins/host.test.ts` — the existing assertions cover the new declaration once it is in the catalog: `:62` requires the ids to stay sorted (so `pdf` goes between `page` and `schedules`), and the declaration-validation cases require every named capability to be one the API defines and every claim to be unique. `src/commands/plugins.test.ts:39` counts `tabPluginCatalog.length` and adapts on its own.
- `src/file-navigator/openers-for-row.test.ts` — a `.pdf` row plainly activated resolves to `open`, and Shift-activated resolves to `edit`, not `open external`. This is the regression guard for the gesture-precedence decision.
- `src/open/file-manager.test.ts` and the open-dispatcher tests — `open paper.pdf` no longer raises `open-unsupported`, and an unclaimed extension still does.
- `web/src/plugins/registry.test.tsx` — the existing parity check covers the new loader entry and pins its schema-version literal against the plugin's constant.

That stub is also how the `3 / 12` readout and the highlighted thumbnail are tested, since both now read from the observer.

## Out of scope

- **In-document search.** No find field, no match navigation, no match highlighting. Deferred explicitly.
- **Printing** and any export of a page or the document to another format.
- **Annotation, form filling, signing, or any editing.** The plugin never writes to the PDF file; `edit paper.pdf` opens the viewer, and nothing in this feature saves anything. There is no unsaved-work state, so the host's save-changes guard is not registered.
- **A password prompt.** An encrypted PDF is reported and not opened; a plan to prompt for and retry with a password is a separate feature.
- **An outline / bookmarks / attachments panel.** The thumbnail strip is the only navigation panel.
- **Page rotation, and clicking through internal or external links in the document.**
- **Persisting the layout, zoom, scroll position, or current page** — across tab switches beyond what staying mounted already gives, across `--relaunch`, or into a profile. A profile records the file, as it does for every plugin tab.
- **Opening a PDF from a web address.** The page plugin owns web targets; this plugin claims an extension.
- **Watching the file for changes.** Like the markdown tab, the tab shows the document as it was when opened.

## Open questions

None. Every piece of user-visible wording is fixed above — the layout toggle's `Continuous scroll` / `Single page`, the thumbnail toggle's `Show pages` / `Hide pages`, the body's `Failed to load <name>`, and the three notification lines — and the optional-asset question is settled in favour of shipping both, with the measurement that would justify revisiting it named rather than deferred to.
