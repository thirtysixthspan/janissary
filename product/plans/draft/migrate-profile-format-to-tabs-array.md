# Migrate the profile format to a `tabs` array

**Complexity: 5/10** — a breaking rewrite of the on-disk format touching the schema, loader, saver, and type surface at once, plus four newly capturable tab kinds and a runtime field rename that reaches into the harness manager; contained by the fact that nothing crosses the wire, the web client is untouched, and every change lands in files that already exist except one new launch module.

## Summary

Feature request (verbatim from `product/backlog/features.md`): "migrate the profile format to include a `tabs` key that is an array of polymorphic tab entries keyed by a type property that distinguishes types of tabs, editor, image, harness, etc. removing the root level indexing of tabs by type."

A profile file today indexes tabs by kind at the root: an `agents` array, a `harnesses` array, an `editors` array, and separate `files`, `notifications`, and `schedules` arrays, each with its own element shape, its own schema checker, and its own launch-order position. The kind of a tab is encoded in which array it sits in, so the file cannot express "these tabs, in this order" — only "these agents, and separately these editors" — and each new tab kind that becomes profile-capable costs another top-level key.

This plan replaces all six arrays with a single ordered `tabs` array whose elements carry a `type` discriminator at the root. `monitors` and `layout` stay top-level, since neither is a tab. The nested `tab` presentation object goes away at the same time: `number`, `color`, `group`, `groupColor`, `pane`, and `focus` become root keys of each entry, which is also the shape the runtime already uses internally. The harness binary, which occupies `type` today, moves to a `tool` key. Four tab kinds that are skipped by `profile save` today — image, markdown, page, and ssh — become first-class entry types, so a session of those tabs round-trips. The change is a hard break: the old keys are simply not read, and the four profiles shipped in `profiles/` are rewritten in the new format.

The runtime side changes far less than the file does. `LoadedProfile` (`src/profile/types.ts:135`) keeps its per-kind lists, so `agent-opener.ts`, `editors.ts`, `files.ts`, `notifications.ts`, and `schedules.ts` continue to receive exactly the lists they receive today — the loader just derives those lists by partitioning one array instead of reading six keys. Nothing here crosses the wire: no protocol type, no RPC, and no file under `web/src/` references any profile type (verified by grepping `web/src` for `ProfileFile`, `ProfileTab`, and the entry types — no hits), so the web client needs no change at all.

## Design decisions

- **One `tabs` array holds every tab-producing entry, discriminated by a root-level `type`.** The ten valid values are `agent`, `harness`, `editor`, `files`, `notifications`, `schedules`, `image`, `markdown`, `page`, and `ssh`. `monitors` and `layout` remain top-level keys with their current shapes, because a monitor may be inline (no tab at all) and layout is window sizing rather than a tab. Every other top-level key stays ignored, as today.
- **Tab presentation is flat.** The `tab` wrapper is removed from the format entirely; `number`, `color`, `group`, `groupColor`, `pane`, and `focus` sit at the entry root alongside `type`. `color` keeps its on-disk name (the runtime field is `dotColor`), so the loader's only remaining rename is that one field. `focus` keeps its two context-dependent meanings unchanged: on a main-area entry it selects the active tab after launch; on a `notifications` entry it selects the visible tab in that sidebar's switcher.
- **`number` still orders the launch; array position only breaks ties.** Entries open in ascending `number`, an entry with no `number` sorts last, and among equals array order decides — exactly today's rule, produced by the stable sort in `mapEntries` (`src/profile/file.ts:56`, `(a.number ?? Infinity) - (b.number ?? Infinity)`). Keep that comparator as-is when the function is rewritten: two unnumbered entries make it return `NaN`, which the spec's `SortCompare` treats as `+0`, so their array order is preserved. Anything "tidier" (e.g. sorting with a large sentinel) must preserve that tie behavior. `profile save` writes an explicit `number` on every main-area entry, so a saved file's array order and numbers agree.
- **A harness entry names its binary with `tool`, on disk and at runtime.** `{ "type": "harness", "tool": "claude", "name": "plan", "model": "claude-opus-5" }`. `ProfileHarnessEntry.type` is renamed to `tool` rather than mapped back to `type` by the loader, because keeping a runtime field called `type` next to a format field called `type` that means something else is exactly the trap this migration exists to remove. That rename reaches four places, all of which must land in the same commit: `isHarnessEntry` (`src/profile/entry-resolve.ts:8`, `return 'type' in e`) becomes a check for `'tool' in e` — still a sound discriminator, since no agent entry has that key; `openHarnessEntry` (`src/profile/entry-openers.ts:28`–`:38`) reads `entry.tool` in its five `entry.type` uses; `HarnessManager.openFromProfile` (`src/harness/manager.ts:141`, `this.spawnTab(entry.type, …)`) passes `entry.tool`; and the `openFromProfile` fixtures in `src/harness/manager.test.ts` (e.g. `:616`, `{ name: 'mystery', type: 'mystery' }`) are updated. The semantic launch-time check is otherwise unchanged: an unknown `tool` value is reported and that one entry skipped, with the message text updated to name the key.
- **Hard break, no compatibility shim.** Nothing reads `agents`, `harnesses`, `editors`, `files`, `notifications`, or `schedules` at the root any more. A file still using them falls under the existing "unrecognized top-level key is ignored" rule and launches as an empty profile. The four files in `profiles/` (`debugging.json`, `features.json`, `multitasking.json`, `planning.json`) are rewritten in the new format as part of this change.
- **An unknown or missing `type` makes the profile malformed.** It is a structural fault like any other: `profile launch` opens nothing and reports malformed, and `profile validate` reports `tabs[2]: type must be one of agent, harness, editor, files, notifications, schedules, image, markdown, page, ssh`. This keeps the existing all-or-nothing shape check honest — a profile is either structurally understood in full or not launched.
- **Image, markdown, page, and ssh tabs become capturable and launchable.** `image` and `markdown` entries carry a `path`, `page` carries a `url`, and `ssh` carries a `destination` plus an `options` array holding the remaining tokens of the original invocation, so a relaunch reconnects with the same flags. These four join the main-area placement pass, so they honor `number`, `group`, `pane`, and `focus` like an editor entry does.
- **The four new types do not author a label.** An image, markdown, page, or ssh tab's label is derived at open time by the same code the `open` and `ssh` commands use (basename, domain plus page number, and `parseSshCommand`'s host-derived label at `src/ssh.ts:41`), so a captured entry has no `name` key and a relaunch gets whatever that derivation plus `uniqueLabel` produces. `agent` and `harness` entries keep their required `name`; `editor`, `files`, `notifications`, and `schedules` entries continue to have none.
- **A relaunch closes an identity-matching markdown, page, or ssh tab before opening it.** Agent and harness entries are pre-closed by label (`closeMatchingTabs`, `src/profile/entry-resolve.ts:18`), but the new types have no authored label to match on, so they are matched by identity instead: `path` for `markdown`, `url` for `page`, and `destination` for `ssh` (`tab.harness?.name === 'ssh' && tab.harness.destination === …`, the same pairing `src/connection/close.ts:31` already uses). Without this, a relaunch would leave the old tab in place and `uniqueLabel` would open a second one beside it under a suffixed label — and for ssh that second tab is a second live connection. `image` needs no such handling: `openImageTab` (`src/tab/openers.ts:22`, `t.image?.path === image.path`) already reuses an open tab with the same path, and the reused tab still flows through the group relocation and candidate list below, so it lands in its authored position anyway. No issuing-tab guard is needed here: none of these tab kinds has a command bar to type `profile launch` into.
- **Launch wording follows the key name.** An empty profile reports `Profile "<name>" has no tabs.` (replacing `has no agents.` at `src/profile/manager.ts:44`), the no-entries-opened fallback in `openProfileEntries` (`src/profile/agent-opener.ts:100`) becomes `Profile "<name>" has no tabs to open.`, and `profile save` reports counts by tab type, e.g. `Saved profile "x": 2 agents, 1 harness, 3 editor tabs, 1 image tab, 1 ssh tab, layout, 1 monitor, 2 docked tabs.`
- **`LoadedProfile` keeps its per-kind lists.** The loader partitions `tabs` into the same fields it exposes today (`entries`, `editors`, `files`, `notifications`, `schedules`) plus one new list for the four view types, so every opener module downstream keeps its current signature and behavior. This deliberately confines the change to the format, its schema, its loader, and its saver.

The resulting file, using `multitasking.json` as the example:

```json
{
  "tabs": [
    { "type": "agent", "name": "janus", "cwd": "$root/", "number": 2, "color": "#5b9cff", "group": 1, "groupColor": "#5b9cff", "focus": true },
    { "type": "harness", "tool": "claude", "name": "feature", "model": "claude-sonnet-5", "workspace": true, "autoApprove": true, "cwd": "$root/workspace/feature", "number": 3, "color": "#5f27cd", "group": 1 },
    { "type": "editor", "path": "$root/product/backlog/issues.md", "number": 4, "color": "#01a3a4", "group": 1, "groupColor": "#5f27cd" },
    { "type": "files", "dock": "left", "path": "$root" }
  ],
  "monitors": [{ "name": "activity", "persona": "activity", "targets": ["group:1"] }],
  "layout": { "window": { "width": 1280, "height": 800 } }
}
```

## Proposed changes

Land them in the order below. Step 1 is independent and can land first; steps 2–5 must land together, because the format types, schema, loader, and saver all change shape at once and typecheck cannot be green in between. The shipped `profiles/*.json` rewrite (step 6) must be in that same commit, or every built-in profile launches empty.

**1. Preserving an ssh invocation for capture.** An ssh tab records only `destination` today (`src/ssh-manager.ts:32`), so its options are unrecoverable at save time. `parseSshCommand` (`src/ssh.ts:34`) returns an additional `options: string[]` — the whitespace-split tokens of `rest` with the destination token removed, which it already computes at `:38`. `HarnessView` (`src/tab/types.ts:56`) gains an optional `sshOptions: string[]`, set by `SshManager.open` when non-empty. Splitting on whitespace does not preserve quoting, so an option whose value contains spaces round-trips as separate tokens; that is accepted rather than solved with a shell-grammar parser. Nothing else reads the new field — the connections panel (`src/connection/manager.ts:22`) and close path (`src/connection/close.ts:31`) keep matching on `destination`.

**2. Format types.** `src/profile/types.ts` replaces the on-disk half of its type surface. `ProfileTab` (`:46`) is deleted; a new `ProfileTabPresentation` type carries the six flat presentation fields and is intersected into each on-disk entry type that supports it. A discriminated union `ProfileTabFile` is added with one member per `type` value: `agent` (the agent-state fields plus `name`), `harness` (`tool`, `name`, `model`, `effort`, `cwd`, `workspace`, `autoApprove`, `offline`, `run`, `schedule`), `editor` (`path`, `in`, `line`), `files` (`dock`, `in`, `path`), `notifications` (`dock`, `focus`), `schedules` (`dock`), `image` (`path`), `markdown` (`path`), `page` (`url`), and `ssh` (`destination`, `options`). `ProfileFile` (`:122`) narrows to `{ tabs?: ProfileTabFile[]; monitors?: ProfileMonitorFile[]; layout?: ProfileLayoutFile }`. The runtime types keep their current flat shapes, with `ProfileHarnessEntry.type` renamed to `tool` per Design decisions. A new `ProfileViewEntry` union covers the four view types with their presentation fields, and `LoadedProfile` (`:135`) gains a `views: ProfileViewEntry[]` field alongside its existing lists. It all stays in `types.ts` — the file is 80 counted lines under `max-lines`'s `skipBlankLines`/`skipComments` (150 raw), and deleting three on-disk types while adding the union lands it around 110, with no need to split it. `src/types.ts:15`–`:18` re-exports these names for the rest of the server; update that list (drop `ProfileTab`, `ProfileAgentFile`, `ProfileHarnessFile`; add `ProfileTabFile`, `ProfileTabPresentation`, `ProfileViewEntry`) or the barrel imports in `file.ts`, `save-route.ts`, and `save-entries.ts` will not resolve.

**3. Schema.** Everything stays in `src/profile/schema.ts`, which is 126 counted lines under `max-lines` (156 raw): the six per-type checkers it already has are reused as-is, four small ones are added for the new view types, and the dispatcher plus the shared presentation check land it around 160 — inside the limit, so no new schema module is created. (If an implementation does overshoot, extract the per-type checkers into `src/profile/schema-tabs.ts` and leave `collectProfileProblems` behind; do not compact.) Its existing `tabProblems` (`:42`) is repurposed: it now rejects a non-object, rejects a missing or unrecognized `type` with the enumerated message from Design decisions, checks the flat presentation fields (its current body, minus the nesting) for every type that allows them, and then `switch`es on `type` into the per-type checker. A flat `switch` is enough — `sonarjs/cognitive-complexity` counts a switch as a single branch point regardless of arm count, so no dispatch table is needed. The list of valid type names lives in one `const` array used both by the switch's default arm and to build the error message, so the ten names appear once (`sonarjs/no-duplicate-string`). `agentProblems` (`:55`) drops its `tabProblems` call, and `harnessProblems` (`:60`) checks `tool` where it checks `type` today. `collectProfileProblems` (`:143`) shrinks to three sections: `tabs` (through the existing `sectionProblems`), `monitors`, and `layout`. Every problem message keeps its location prefix, now `tabs[<i>]` instead of `agents[<i>]`/`editors[<i>]`.

**4. Loader.** `src/profile/file.ts` replaces `mapEntries`, `mapAgent`, and `mapHarness` with a partitioning pass over `tabs`: each element is routed by its `type` into the matching runtime list, with `color` mapped to `dotColor` and the other presentation fields copied through unchanged (no nesting to unwrap any more). `agent` and `harness` elements land in `entries`, which keeps the existing `number`-ordered stable sort described in Design decisions; `editor`, `files`, `notifications`, and `schedules` elements land in their existing lists in array order; the four view types land in the new `views` list. One `switch` on `type` pushing into the right list is the whole mechanism — same reasoning as the schema's dispatcher, and it replaces three mapping functions with one pass. `loadProfile`'s signature, its JSON/structural error handling, and its `{ error }` shape are untouched.

**5. Launching the new view types.** A new `src/profile/view-tabs.ts` exports `openProfileViewTabs(views, managers, issuingLabel, defaultGroup, colorForGroup, notes)` returning `MainAreaCandidate[]`, modeled directly on `openProfileEditors` (`src/profile/editors.ts:20`). For each entry it first closes any identity-matching open tab (per Design decisions), pushing `Relaunched "<label>".` into `notes` exactly as `closeMatchingTabs` does; then it issues the equivalent user command through the existing manager — `managers.openFile.run(\`open <path>\`, issuingLabel)` for `image`, `markdown`, and `page` (the URL branch at `src/open-file-command.ts:25` handles a page target, and `expandUserPath` at `:23` gives `$root`/`~` the same expansion editors get) and `managers.ssh.run(\`ssh <destination> <options…>\`)` for `ssh`; then it relocates the newly active tab into its authored group and pushes a candidate carrying its `number`, `focus`, and `pane`. All four open paths are synchronous and leave the new tab active (`src/tab/openers.ts:21`, `:31`, `:51`; `src/ssh-manager.ts:35`), so `openProfileEditors`' "read `managers.tab.tabs[managers.tab.activeTab]` after the call" pattern is valid here; detect a failed open the same way it does, by comparing `managers.tab.tabs.length` before and after, and report the entry into `notes` and skip it when no tab appeared. `relocateToGroup` is currently private to `editors.ts` (`:10`); export it from there rather than copying it. `openProfileEntries` (`src/profile/agent-opener.ts:30`) calls the new function immediately after `openProfileEditors` at `:72` and spreads its candidates into the same `candidates` array, so the existing `reorderGroupByNumber` and `placeProfileTabs` passes at `:83`–`:84` cover the new tabs with no further change. Its final fallback at `:100` becomes `Profile "<name>" has no tabs to open.`

**6. Capture.** `src/profile/save-route.ts` collapses `CaptureState`'s six entry arrays (`:18`–`:23`) into a single ordered `tabEntries: ProfileTabFile[]`, keeping the per-type counters for the summary. `captureTab` (`:34`) keeps its `switch (tab.view)` shape and its ordering guarantee — `saveProfile` iterates `managers.tab.tabs` (`src/profile/save.ts:30`), so the written array is in tab-strip order, docked tabs interleaved among main-area ones — but each arm now pushes a typed entry: the existing `agent`, `harness`, `editor`, `files`, `notifications`, and `schedules` arms with a `type` added, plus new arms for `image`, `markdown`, and `page`, and the ssh case at `:46` changing from `state.skipped.push(tab.label)` to writing an `ssh` entry from `tab.harness.destination` and `tab.harness.sshOptions`. After this, the only tabs pushed onto `skipped` are an undocked file navigator (`:59`) and an editor tab whose payload is missing (`:54`); the `default` arm becomes unreachable for today's `view` union and stays as the guard for future view types. `src/profile/save-entries.ts`'s three writers stop building a nested `tab` object and instead spread one shared local `presentation(tab, managers)` helper — the same four-field block those writers duplicate inline today at `:21`, `:35`, and `:67` — with new writers added for the four view types, each abbreviating its path through `abbreviatePath` with `{ root: managers.tab.launchDir }` the way `writeEditorEntry` does at `:33`. That file is 57 counted lines (73 raw), so the four small writers and the shared helper leave it well inside the limit. `src/profile/save.ts` (`:36`–`:44`) assembles `root.tabs` from the single array (omitted when empty), keeps `monitors` and `layout` as they are, and `formatSaveSummary` (`:58`) gains parts for the new counts.

**7. Command surface.** `src/profile/manager.ts:44` changes `Profile "<name>" has no agents.` to `has no tabs.`, and its emptiness check at `:43` changes from `loaded.entries.length === 0` to "no tabs of any kind were loaded", so a profile consisting only of an editor tab or a docked navigator launches instead of being called empty. `src/profile/validate.ts` needs no logic change — it reports whatever `collectProfileProblems` returns.

**8. Shipped profiles.** `profiles/debugging.json`, `profiles/features.json`, `profiles/multitasking.json`, and `profiles/planning.json` are rewritten as `tabs` arrays, each preserving its current numbers, colors, groups, and monitor/layout keys exactly.

**9. Specs and docs.** `product/specs/profiles.md` is the larger edit: its Storage section describes the single `tabs` array and the flat presentation fields instead of the `agents`/`harnesses` split and the `tab` object; the "Profile-level file navigator", "editor tabs", "notifications tab", and "schedules tab" sections become descriptions of those `type` values rather than of top-level keys; "Malformed profiles" gains the unknown-`type` rule; `profile launch` and `profile save` pick up the new wording and the four new capturable types. Its skipped-tabs sentence ("an opened image, a web page, a markdown viewer, an ssh connection, a monitor's own reporting tab, or a file navigator that isn't docked") narrows to just the monitor reporting tab and the undocked navigator. `documentation/user-documentation/automation/profiles.md` gets the same treatment for its user-facing examples. `product/specs/ssh-tab.md` notes that an ssh tab is now captured by `profile save` and reconnected by `profile launch` with its original options.

## Out of scope

- Any compatibility path for old-format profiles: no fallback read, no auto-migration on load, no `profile migrate` command. The four shipped profiles are converted by hand; a user's own project profile is rewritten by re-running `profile save`.
- Folding `monitors` or `layout` into `tabs`. Both keep their current top-level keys and shapes.
- Making array position the source of tab order. `number` still orders the launch.
- Changing any semantic launch-time check: unknown tool, unknown model, `autoApprove` on an unsupported harness, and unparseable `schedule`/`run` lines stay per-entry skips with their current messages.
- Shell-accurate parsing of ssh options. Whitespace splitting is the whole mechanism; a quoted option value containing spaces is not preserved.
- Capturing a monitor's own reporting tab, or an undocked file navigator, as a `tabs` entry. Both remain uncaptured (the latter is the subject of its own draft plan, `profile-save-file-navigator-tree-state.md`, which adds keys to a `files` entry — whichever lands second rewrites its keys onto the other's entry shape).
- Capturing any new per-tab state for the four new types beyond what is listed — no image zoom, no page scroll position or history, no markdown scroll offset, no ssh scrollback.
- Restructuring `LoadedProfile` or the opener modules beyond the added `views` list, and any change under `web/src/`.

## Open questions

- Whether `profile save` should write an explicit `number` on the docked `files`, `notifications`, and `schedules` entries. They have no place in the tab strip, so today they carry no presentation at all; this plan keeps that, which means their position in the `tabs` array is the only record of their relative order. Only worth revisiting if sidebar switcher order ever becomes something a profile should pin.
