# Video opener and video tab

**Complexity: 5/10** — a new view-tab surface end to end (payload type, creator, tab-manager opener, client component), each piece a direct copy of the image tab's, plus two changes outside the opener registry that other code depends on: byte-range serving on the shared `/open/<id>` route, and widening the file-navigator opener-command union across four modules.

Video files have no registered opener today, so double-clicking a `.mp4` in the file navigator falls through to the "Edit as text / Open externally" chooser (`src/file-navigator/openers-for-row.ts`) and `open foo.mp4` reports `No opener for ".mp4" files.` This plan registers a video opener that claims the common video extensions and gives them both presentations the opener contract promises: an **inline** presentation that plays browser-decodable formats in a new **video tab** (the default, and what a double-click runs), and an **external** presentation that hands the file to a player configured in `.janissary/config.json` — defaulting to QuickTime Player. Formats the browser cannot decode (`.mkv`, `.avi`, `.wmv`, `.flv`, `.mpg`, `.mpeg`) skip the video tab entirely and go straight to the configured player, so "open a video" always does something useful regardless of container.

Serving a video also needs one change outside the opener: the `/open/<id>` route (`src/index.ts`) currently buffers a whole file and answers 200 with no `Range` support, which makes seeking impossible and loads a multi-gigabyte file into server memory. The route learns byte-range serving as part of this work.

## Design decisions

**Inline plays the browser-decodable set; the rest is routed externally by extension.** The video opener claims `.mp4`, `.m4v`, `.webm`, `.ogv`, `.mov`, `.mkv`, `.avi`, `.wmv`, `.flv`, `.mpg`, and `.mpeg` (case-insensitive, as every opener's extensions are). The first five are the **playable set**: their inline presentation opens a video tab. The remaining six are claimed so that `open` no longer reports them as unsupported, but their inline presentation behaves exactly as their external one — the configured player is launched — since a `<video>` element cannot decode them.

**A decode failure keeps the tab and offers a button, it does not auto-launch anything.** When a video tab is opened for a playable-set file that the browser still cannot decode (an unsupported codec inside an `.mp4`, a corrupt file), the tab body replaces the player with a short message that the video cannot be played in-app, the file's path, and an **Open in \<player\>** button that runs the external presentation for that file. Nothing launches on its own; the user decides. This mirrors the app's existing quiet-degradation habit (the image opener's "No viewer available. The file is at …") while giving the user the one action worth offering.

**The external player is configured through an `externalViewers` map keyed by opener name.** A new `externalViewers` config key holds `{ "video": "QuickTime Player" }` by default — the value is an application name, launched on macOS via the OS `open` command's `-a` flag. Keying by opener name rather than by extension or by a single `videoPlayer` string means images or markdown can be given their own entry later without another top-level config key, and the user never has to enumerate extensions. An empty or missing value means "use the OS default handler" — the current `didOsOpen` behavior. As with `syncPaths` and `notifications`, the key is edited by hand; there is no runtime command to change it.

**Failing to launch the configured player falls back to the OS default, then reports.** If launching the named application fails (it is not installed, the platform is not macOS, the value is empty), the opener falls back to `didOsOpen`; if that also fails, it notes `No video player available. The file is at <path>` in the originating tab — the same shape as the image opener's fallback line. A successful launch notes `Opening <name> in <player>…`.

**The video tab mirrors the image tab end to end.** A `VideoView` payload, a `view: 'video'` tab kind, an `openVideoTab` capability on `OpenContext`, and a `web/src/VideoTab.tsx` component beside `ImageTab.tsx`. The body is a compact metadata header (name, size, path, split button) above a native `<video controls>` element that fills the remaining space — no custom transport UI. Like every other view tab it is live and in-memory: not persisted, not restored on `--relaunch`.

**Shift+double-click on a video row means "open externally", not "edit as text".** The navigator's shift gesture normally forces the plain-text editor, which is useless for a binary video. For video rows the gesture runs `open external` instead — the same kind of per-type inversion Markdown rows already have, where shift shows the rendered preview rather than the editor. This means the opener-resolution result type must carry a third command: `openersForRow` currently returns `{ command?: 'open' | 'edit'; choices }` (`src/file-navigator/openers-for-row.ts:10`) and that union is repeated verbatim at `src/file-navigator/manager.ts:205` (`openers(label, relPath, edit)`), `src/controller/file-navigator.ts:137` (`fileNavigatorOpeners`), and `web/src/useFileNavigatorOpener.ts:16` (the `client.request<…>` type argument). All four widen to `'open' | 'edit' | 'open external'`. The client already builds its command text by string-concatenating the returned command (`web/src/useFileNavigatorOpener.ts:19`, `text: \`${result.command} ${root}/${path}\``), so no client logic changes beyond the type — and `'open external'` is already a legal value of `FileOpenerChoice.command` (`src/protocol.ts:31`), so the chooser path is unaffected.

**A video tab does not round-trip through a profile.** Image, markdown, page, and ssh tabs are re-opened by `openProfileViewTabs` (`src/profile/view-tabs.ts:44`, `buildTarget`); video is deliberately left out of `ProfileViewEntry` in this version, so a saved profile neither records nor restores a video tab. Adding it later is one more `case` in that switch, matching on `tab.video?.path` with `preClose: false` exactly as the `'image'` case does.

**`/open/<id>` gains `Range` support rather than a second video-only route.** The route honors a `Range:` request header by streaming the requested byte window with `206`, `Content-Range`, and `Accept-Ranges: bytes`, and keeps answering `200` with the whole body when no `Range` header is present. Every existing consumer (images, markdown, the editor) is unaffected, and seeking works without a parallel serving path.

## Proposed changes

**Config.** Add an `externalViewers` field to the `Config` type in `src/config.ts` — a record from opener name to application name — with a `DEFAULT_EXTERNAL_VIEWERS` constant of `{ video: 'QuickTime Player' }` folded into `DEFAULT_CONFIG`. Because `loadConfig` shallow-merges the parsed file over the defaults, a user who writes their own `externalViewers` replaces the map wholesale; that is the same semantics `notifications` already has and needs no special handling.

**Launching a named application.** Rather than a second launch function, `didOsOpen` (`src/openers/os-open.ts:7`) takes an optional application name: when one is given and the platform is macOS, the spawned argument list becomes `-a <application> <path>`; every other case is byte-for-byte today's behavior. This is a two-line change inside a 23-line module and keeps every child-process launch for opening files in one place. The "try the named player, then the OS default" fallback is then just two calls at the one call site that needs it, with no new module and no new abstraction.

**The video opener.** A new `src/openers/video.ts` exporting an `Opener` named `video`, registered in `src/openers/index.ts` ahead of the editor opener (order only matters against openers claiming the same extension, which none do). The playable-extension set is module-private — nothing outside the opener needs it, since the navigator branches on the opener's `name` and the server routes by MIME. Its `external` presentation resolves the configured application from `getConfig().externalViewers`, calls `didOsOpen` with it, retries `didOsOpen` with no application if that returns false, and notes the outcome. Its `inline` presentation checks whether the file's extension is in the playable set: if not, it delegates to its own `external`; if so, it stats the file for a human-readable size via `humanSize` (`src/openers/size.ts`) and calls a new `openVideoTab` context capability with the name, absolute path, size, served ref from `registerFile`, and the resolved player name. The module lands around the size of `src/openers/image.ts` (22 lines) plus its extension tables — no extraction is anticipated.

**Opener context.** Add `openVideoTab: (video: VideoView) => void` to `OpenContext` (`src/openers/types.ts:11`, beside `openImageTab`), implemented in `OpenFileManager.buildContext` (`src/open-file-manager.ts:63`) as `openVideoTab: (video) => this.managers.tab.openVideoTab(video)`, exactly as the image line above it does.

**Tab model and wire types.** Add a `VideoView` type in `src/tab/types.ts` carrying `name`, `path`, `size`, `url`, and `player` (the four fields `ImageView` carries at `:66`, plus the configured player's display name so the client's fallback button can name it). Add `'video'` to the `view` union (`src/tab/types.ts:193`) and a `video?: VideoView` payload to `Tab` (beside `:201`), and re-export `VideoView` from `src/types.ts:7` and `src/protocol.ts:3`/`:7` alongside `ImageView`. Add `makeVideoTab` (`src/tab/index.ts`) and `uniqueVideoLabel` (`src/tab/unique-labels.ts`) beside their image counterparts, an `addVideoTab` creator in `src/tab/creators.ts` that titles the tab with the file's name the way `addImageTab` does at `:24`, and an `openVideoTab` in `src/tab/openers.ts` that focuses an existing tab whose `video.path` matches instead of opening a duplicate — a direct copy of `openImageTab`'s shape at `:21`. Surface it as a method on `TabOpeningState` (`src/tab/opening-state.ts`) delegating to `tabOpeners.openVideoTab`; no controller change is needed, since openers reach the tab manager through `OpenContext` rather than through `Controller`.

**Serving.** Move the `/open/<id>` branch out of `serveStatic` (`src/index.ts:69`) into a new `src/open-route.ts` exporting one function that takes the request, response, resolved file path, and security headers — `src/index.ts` is already 146 lines and the range logic would push it against the 200-line limit, so this is a decision, not a contingency. The moved handler stats the file and, when the request carries a satisfiable `Range` header, answers `206` with `Content-Range`, `Content-Length`, `Accept-Ranges: bytes`, and a `node:fs` `createReadStream` piped over that window; an unsatisfiable range answers `416`; no `Range` header keeps the existing whole-file `200`. No dependency is needed or added — `node:fs` covers it, and the project ships no HTTP-serving library. The token check and the registry allow-list stay in `serveStatic` where they are today — range serving must not widen what is reachable. Add the video MIME types to the `MIME` table (`.mp4`/`.m4v` → `video/mp4`, `.webm` → `video/webm`, `.ogv` → `video/ogg`, `.mov` → `video/quicktime`); the non-playable containers need no entry since they are never served.

**Client.** A new `web/src/VideoTab.tsx` rendering the metadata header above a `<video controls>` element whose `src` is the payload's `url` with the session token appended, mirroring `web/src/ImageTab.tsx:17`–`:18`. It **reuses the existing `.image-tab`/`.image-meta`/`.image-name`/`.image-size`/`.image-loc` classes** rather than introducing a parallel `.video-meta` block — the editor and file-navigator tabs already reuse them (`web/src/theme.css:681`, `:734`), and only one new rule is needed to size the media element inside the stage. The component takes the `client` prop the way `FileNavigatorTab` does (`web/src/ViewTabBody.tsx:31`); its `<video>` `onError` handler flips the body to the unplayable state — the message, the path, and an **Open in \<player\>** button naming `video.player`, whose click sends `{ method: 'command', params: { text: 'open external <path>' } }` on the client, the same send the navigator chooser makes at `web/src/useFileNavigatorOpener.ts:27`. Dispatch `tab.view === 'video' && tab.video` to it in `web/src/ViewTabBody.tsx`, keyed on `tab.video.url` like the image branch at `:24`. The video tab is rendered from `ViewTabBody` (not from `MountedViewLayers`), so switching away from a video tab unmounts it and stops playback — the intended behavior in this version, consistent with markdown and image tabs.

**Navigator.** In `src/file-navigator/openers-for-row.ts`, branch on the resolved opener's `name === 'video'`: the plain gesture keeps returning `'open'`, and the `edit` gesture returns `'open external'` instead of `'edit'`. The module already returns a command per gesture, so this is one branch plus the union widening described above, not a new mechanism.

**Ordering.** Land the union widening (`'open external'`) across the four modules in one step so typecheck stays green, and land `VideoView` plus its `view` union entry before the creator, opener, and client changes that reference them. The `/open/` range work is independent of the opener work and can land in either order. Every new `src/` import carries the `.js` extension per the NodeNext rule, and the config lookup uses `??` rather than `||` to satisfy `prefer-nullish-coalescing`.

**Specs.** Update `product/specs/open.md` with a "Video opener" section describing both presentations, the playable/non-playable split, and the config-driven player; add `product/specs/video-tab.md` describing the tab (modeled on `image-tab.md`); note the shift-gesture exception in the mouse/keyboard tables of `product/specs/file-navigator-tab.md`; and add the `externalViewers` row to the settings table in `product/specs/application-config.md`.

## Out of scope

- **Custom transport UI.** Native `<video controls>` only — no bespoke scrubber, speed control, or volume UI.
- **Tab-scoped playback keys.** No space-to-pause / arrow-to-seek / `f`-for-fullscreen layer of the kind the image tab has for zoom; the native controls own the keyboard while focused.
- **Playback-position memory and `--relaunch` restore.** The video tab is live and in-memory like every other view tab; reopening a file starts from the beginning.
- **Audio files.** `.mp3`, `.wav`, `.m4a`, and friends stay unclaimed.
- **Thumbnails or duration in the file navigator.**
- **A runtime command to change the player.** `externalViewers` is hand-edited in `.janissary/config.json`, like `syncPaths` and `notifications`.
- **Transcoding or a bundled decoder** for `.mkv`/`.avi`/`.wmv`/`.flv`/`.mpg`/`.mpeg` — those always go to the external player.
- **Per-viewer configuration for images or markdown.** The `externalViewers` map is shaped to allow it later; only the `video` entry is read in this version.
- **Profile save/restore of a video tab.** `ProfileViewEntry` gains no `video` type, so `profile save` does not record an open video tab and `profile launch` does not reopen one.
- **Keeping playback alive across tab switches.** The video tab unmounts when it is not the visible tab, like every other `ViewTabBody`-rendered view; it is not added to `MountedViewLayers`.
