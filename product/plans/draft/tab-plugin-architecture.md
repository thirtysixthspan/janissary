# Tab plugin architecture

**Complexity: 9/10** — this is a first-of-its-kind server/client extension subsystem with versioned wire types, lazy activation and concurrency control, failure and disposal lifecycles, tooling-boundary changes, and an end-to-end migration of an existing tab.

## Summary

Introduce a narrow, versioned tab-plugin seam for bundled internal plugins, then prove it by moving the existing video opener, video tab, and frame-capture behavior into the first plugin under `src/plugins/video/`. The host discovers static declarations without loading plugin behavior, activates server and client modules only when `open <video-file>` needs them, and keeps current video behavior unchanged while making future internal tab types additive instead of another set of core protocol, tab-model, and React dispatch branches.

## Design decisions

**Video keeps the existing user flow.** `open <video-file>` remains the only video command. A playable video opens and focuses the plugin tab, and opening the same file again focuses the existing tab. V1 adds no `video <path>` command; command contribution is demonstrated by the frozen compatibility fixture instead.

**A plugin failure is contained for the rest of the process.** An incompatible API version, rejected import, activation exception, activation timeout, invalid plugin-produced tab payload, client chunk failure, render exception, or guarded handler failure disables only that plugin until Janissary restarts. The host reports the exact wrapper `Tab plugin "video" disabled: <reason>.` in the originating transcript while that tab still exists and, when the notifications tab is already open, in its feed. It does not retry the disabled plugin during that process.

**Notification delivery keeps the existing no-buffer policy.** A live originating transcript always receives the failure. The notifications feed receives it only when that tab is already open; plugin failures do not recreate a closed origin, create the notifications tab, or buffer events for later.

**V1 is an internal architecture seam, not a plugin marketplace.** Only bundled plugins listed by the application are supported. Third-party discovery, installation, updates, enable/disable UI, hot reload, generic plugin configuration, relaunch persistence, and migration of tab types other than video are deferred.

**The wire seam is generic and versioned.** Core carries one plugin-tab envelope and one plugin-intent RPC. Each plugin owns and validates its versioned payloads and intent data on both sides of the boundary. Adding another bundled tab plugin does not add a new core `TabView` member, RPC variant, or rendering conditional.

## Proposed changes

### 1. Define the v1 tab-plugin contract

Add host-owned contract modules under `src/plugins/` without a barrel file. `src/plugins/api.ts` defines `TAB_PLUGIN_API_VERSION` and the static `TabPluginDeclaration`, activation result, lifecycle, and narrow server/client capability contracts; it references rather than redeclares the generic wire envelope, request, and reply owned by `src/protocol.ts`. Represent the host API as major and minor integers: compatibility requires an equal major and a host minor at least as new as the plugin's declared minimum. The plugin's own semver string remains separate, and each payload contract carries an exact positive-integer schema version. This gives additive host changes a minor path and reserves a major bump for a frozen-fixture break without adding a semver dependency.

The declaration contains the plugin identity and version, required host API version, payload schema version, tab display metadata, opener extension and MIME claims, optional contributed command names, and requested capabilities. A command claim is a case-insensitive first token with a word boundary. Command and opener claims are the v1 activation triggers; do not add a separate trigger language or configurable mount policy. Unloaded declarations never contribute executable match predicates. Everything needed to reject, route to, or display an unloaded plugin is static data, and declaration modules have no top-level side effects.

V1 supports one tab-view extension mechanism. A plugin tab is a live, in-memory center action tab that can split and stays mounted while inactive. The host owns tab chrome, group insertion, focus, pane placement, closing, and visibility. A plugin supplies its display title, label prefix, stable instance key, versioned payload, and body component. Keeping the v1 surface this narrow preserves video playback across tab switches without inventing extension points that the first plugin does not need.

The server capability exposes only transcript reporting, generic plugin-tab opening, tab-scoped served-file registration and lookup, the configured external viewer for that plugin, and detached external opening. Video continues to read file metadata with `node:fs` and reuses `src/openers/size.ts:2` (`humanSize`) as an explicitly documented pure plugin utility rather than adding a host callback. `openPluginTab` receives identity and display metadata first, checks the stable instance key synchronously, and invokes the plugin's payload/resource factory only when a new tab is actually needed. This prevents the current path in `src/openers/video.ts:45` (`context.registerFile(file)`) from allocating another served-file ref before `src/tab/openers.ts:32` discovers that the video is already open.

The client capability exposes only authenticated resource URL construction, a tab-scoped `pluginIntent` request, and a ready-made split-action React node that the plugin may place in its header. This reuses `web/src/SplitTabButton.tsx:5` (`SplitTabButton`) without publishing private host imports to the plugin. Neither side receives `Managers`, `Controller`, a raw WebSocket or `JanusClient`, a tab session object, a generic filesystem capability from the host, or private host UI modules. Enforce that boundary with targeted `no-restricted-imports` rules for plugin server and client directories; Node built-ins, external packages, the host API, and the plugin's own shared contract remain allowed.

Document the extension point's resolution strategy, ordering, async behavior, and empty return behavior in the contract module. Core command routes resolve before contributed commands. Registration rejects a plugin command name that collides with another plugin contribution, any `Command.match` in `src/commands/index.ts:36`, the textual commands in `src/commands.ts:5` (`availableCommands`), or the `shell`, `harness`, `ssh`, and bare `schedule` routes handled ahead of `resolveCommand` at `src/command/manager.ts:65`. An invoked command has one provider. Opener claims use the existing first-match model, but duplicate extension or MIME claims are rejected rather than silently depending on catalog order.

Plugin command and opener handlers are awaited, but separate invocations may run concurrently just as existing opener calls do; v1 adds no host-side work queue. Widen `Command.run` at `src/commands/types.ts:8` to permit an asynchronous result, return the `open` promise from `src/commands/open.ts:37`, carry it through `src/open-file-manager.ts:17` (`run`) and `src/open-file-command.ts:12` (`runOpenCommand`), and preserve sorted glob order by awaiting each matched file before the next. Have `CommandManager.executeCommand` observe rejections, and update the second registry consumer in `src/capture/manager.ts:30` (`dispatchMatchedCommand`) to invoke its callback only after an asynchronous plugin command settles. Existing synchronous commands retain their behavior. Handlers open tabs only through the imperative `openPluginTab` capability; returning void means the handler completed without opening one. A future plugin that requires serialization across separate commands must do so internally or justify an additive contract hook.

### 2. Add static catalogs and guarded lazy hosts

Add the single production declaration list at `src/plugins/manifests.ts`, plus focused runtime modules under `src/plugins/server/` and client-only loader modules under `src/plugins/client/`. The declaration list statically imports pure manifests, never plugin behavior. `src/plugins/server/loaders.ts` maps those declared ids to literal dynamic imports so Node, TypeScript, and Knip can see every possible server module without executing one. A catalog test pins declaration/loader parity; do not eagerly scan behavior loaders at runtime.

The client registry pairs each registered manifest id with one literal dynamic import of `src/plugins/<id>/client/activate.tsx`. This repeats only the small loader map needed to keep server modules out of the web build; the catalog test checks it against the single declaration list. Do not add `import.meta.glob`, runtime path construction, filesystem discovery, or a second client manifest list for this fixed bundled catalog.

Create each `React.lazy` wrapper once in `src/plugins/client/registry.tsx`, outside React render functions, so state snapshots cannot remount a video by recreating its component type. If a loader is absent despite the catalog test, the first matching activation disables that plugin through the normal failure path; extra undeclared loaders are unreachable.

The server host owns compatibility checks, static contribution registration, one in-flight activation promise per plugin, activated state, disabled state, timing, guarded calls, intent routing, and disposal. Concurrent first requests share the same activation. Activation runs exactly once. If a timeout wins while an import or activation later resolves, the late result is ignored and immediately disposed rather than re-enabling the plugin.

Set a 1,000 ms budget for server activation and a 5,000 ms budget for each user-initiated server handler or intent. Client import plus activation shares one end-to-end 5,000 ms deadline rather than two sequential timers. This extension point does not run on per-keystroke, transcript-chunk, or full-state-emission paths. Record actual activation duration and final state through `PluginHost.status(pluginId)`, the single read-only diagnostic method required by tests and the plugin guideline; v1 adds no plural listing API, status command, or screen.

Add the plugin host to `Managers` at `src/managers.ts:34` (`ManagerRegistry`) and construct it through `src/controller/create-managers.ts:32` (`createManagers`) before the managers that consume plugin contributions. Normal shutdown already walks managers in reverse construction order at `src/controller.ts:146` (`shutdown`), so consumers release their references before the plugin host idempotently disposes each activated plugin. V1 defines no observable disposal order between plugins because it supports no plugin dependencies.

Store each open tab's plugin instance key, origin label, and served-file refs on that tab's server-only plugin runtime record, not in another manager `Map<label, ...>`. V1 has no arbitrary per-tab disposer hook because served files are its only tab-scoped acquired resource. Reuse the mutable registry map already exposed by `src/tab/file-registry.ts:17` (`map`) through `src/tab/manager.ts:38` (`openFiles`) to delete refs after failed creation and from `src/tab/cleanup.ts:8` (`closeTabResources`), correcting the current video omission while leaving unrelated refs untouched. Do not add another resource registry or lifecycle API; add a tab-lifecycle hook only when a second concrete resource type requires one.

### 3. Generalize the tab model and wire protocol

Replace `VideoView` at `src/tab/types.ts:77`, `view: 'video'` and `video` at `src/tab/types.ts:214`, their `TabView` counterparts at `src/protocol.ts:75`, and the projection at `src/tab/view.ts:68` with one `view: 'plugin'` and one generic plugin envelope. The wire envelope carries only the plugin id, payload schema version, and JSON-compatible unknown payload. A v1 plugin contributes one tab type, so there is no contribution id; the manifest and activation result already carry host API compatibility, so the wire does not repeat it. Existing top-level `TabView.label` and `title` remain the display identity. The stable instance key, origin label, and resource ownership stay in the server-only tab runtime and are never broadcast. Add contribution ids only if one shipped plugin needs multiple tab types.

The host validates the generic envelope. The selected plugin then validates host-produced tab payloads with the single runtime guard from `src/plugins/<name>/shared.ts` before any server use and again before client rendering. An invalid host-produced payload uses the normal disable path. Invalid client-supplied intent input returns an ordinary RPC validation error without disabling the plugin; only a throw, rejection, timeout, or invalid result from plugin code crosses the failure boundary. Do not add Zod, Ajv, or a second wire definition under the client tree.

Generalize the current video-specific creator and opener path into `openPluginTab` and its generic creator. The host continues to choose the label, dot color, group, pane, insertion position, and active index. Duplicate detection uses plugin identity and stable instance key, preserving the current focus-existing-video behavior without teaching core what a video path is.

Replace `captureVideoFrame` at `src/protocol.ts:234`, its method allow-list entry at `src/client-message.ts:6`, its switch branch at `src/message-handler.ts:71`, and the `EditorControllerAdapter.captureVideoFrame` path at `src/controller/editor-adapter.ts:14` with one `pluginIntent` RPC and a focused plugin controller adapter. The request names the stable tab label, payload schema version, intent name, and unknown payload; the server derives plugin identity and API version from its authoritative open tab rather than trusting duplicate client fields. The generic client capability scopes the label so a concrete plugin component cannot target another tab.

Reserve intent names beginning with `$host/` for the generic client layer. `$host/client-failure` reports a chunk timeout, rejected load, invalid host-produced payload, or render exception even when concrete client code never loaded; all other names route to the activated server plugin. The host deeply validates the generic fields before dispatch, and the plugin validates its own intent and reply payloads. Replies and failures use the existing RPC reply path; no plugin opens another socket or adds an HTTP route.

## Out of scope

- Third-party, user-installed, package-discovered, or filesystem-discovered plugins.
- Plugin installation, update, enable/disable, status, permission, or configuration UI.
- Hot reload, unloading and retrying a disabled plugin before restart, or dynamic catalog changes.
- Sandboxing or process isolation. Bundled internal plugins run with host trust; narrow capabilities contain mistakes but are not presented as a security boundary.
- A general plugin platform for pipelines, notifications, transport, themes, menus, or other extension points. V1 contains only tab views and the opener or command triggers that create them.
- A production `video <path>` command; the existing `open <video-file>` command remains the only user flow.
- Migration of image, Markdown, editor, page, file navigator, notifications, schedules, monitor, harness, SSH, agent, or shell tabs.
- Generic per-plugin configuration. The video plugin only preserves the existing `externalViewers.video` setting.
- Persisting or restoring plugin tabs across `--relaunch` or profiles.
- Changes to video playback, capture naming, external-player behavior, native controls, split support, or background playback.
