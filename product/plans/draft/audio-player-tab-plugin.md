# Audio player tab plugin

**Complexity: 6/10** — a bundled plugin whose server and client halves are close copies of the video plugin's, but carrying three things video did not need: two additive extensions to the v1 plugin API (`updateTab` resources, a selection-action contribution), a new pair of file-navigator RPCs with their protocol entries, and a playlist state machine on the server driven by two client intents.

Audio files have no registered opener today, so `open song.mp3` reports `No opener for ".mp3" files.` and double-clicking an audio row in the file navigator falls through to the "Edit as text / Open externally" chooser. This plan adds a bundled **audio** tab plugin alongside the existing video, image, markdown, page, and schedules plugins. It claims the common audio extensions and the `audio <path>` command, and contributes a **single, long-lived player tab** that owns a playlist rather than one tab per file: opening an audio file when the player is already open appends that file to the queue and jumps to it, so a session accumulates a playlist instead of a row of tabs. The tab shows a metadata and transport header, a player, and the playlist beneath it, is dockable into either sidebar, and is driven by both buttons and key bindings. A new **selection action** contribution lets the file navigator offer **Add to playlist** for a multi-row selection of audio files — the one thing the current navigator cannot express, since its context-menu entries act on a single row.

Two pieces of the v1 plugin API are in the way and are extended here. `registerFile` is reachable only from the `openOrFocusTab` payload factory (`src/plugins/api.ts:113`, `TabPluginResources`), and `updateTab` is documented as unable to serve a new file — but appending a track to an already-open tab is precisely "serve a new file through an update." And a plugin's static declaration has no way to contribute a navigator action that acts on a selection. Both changes are additive to the declaration and capability surface.

## Design decisions

**Opening a second audio file appends it to the playlist and jumps to it.** The player tab keeps whatever is already queued; the newly opened file is added at the end and becomes the playing track immediately. Opening several files in turn — which is what a wildcard `open *.mp3` does, dispatching each match separately in sorted order — therefore builds the queue in that order and leaves the last one playing. This is the whole reason the tab is a singleton: a second `open` never produces a second player.

**The playlist plays straight through and stops on the last track.** When the final entry finishes, playback stops and the playlist and its selection are left exactly as they are, ready to be replayed or advanced by hand. There is no wrap-around and nothing is cleared.

**Removing the playing track advances to the next one.** The entry disappears from the playlist and the following track starts playing. Removing the last remaining entry stops playback and leaves an empty playlist in an open tab. Removing an entry that is not playing never disturbs playback.

**A file the browser cannot decode is dropped from the playlist and playback moves on.** When the player reports a decode error for an entry — an unsupported codec inside a claimed container, a corrupt file — that entry is removed from the queue with a short note in the view and the next track starts. One bad file can never stall a queue. This is a deliberate departure from the video tab, which stops on the failure and offers an **Open in \<player\>** button: a single video is the whole point of its tab, while one track of many is not worth halting a playlist for.

**Extensions the browser cannot play at all are routed to the external player, never queued.** As with video, the declaration claims a wider extension set than it can decode; a claimed extension with no content type (`.wma`) has its inline presentation behave exactly as its external one, so `open track.wma` hands the file to the configured player rather than opening an audio tab holding an entry that can only fail. Shift+double-click on any audio row does the same, through the declaration's `open external` edit gesture — a binary audio file has nothing to edit as text.

**Key bindings are Space, arrows, and Shift+arrows, mirrored by buttons.** While the audio tab is the visible tab, Space toggles play/pause, `←`/`→` seek backward and forward within the current song, and `Shift+←`/`Shift+→` move to the previous and next track. The same five actions are buttons in the transport row, so nothing is keyboard-only. Because a hidden plugin tab stays mounted, the window-level key listener consults the host's visibility answer rather than assuming it is on screen — the condition [[tab-plugins]] already sets for exactly this case.

**The tab is named after the playing track.** The tab strip shows the current track's file name and follows it as playback advances, through the title the plugin supplies to `updateTab`. A user-supplied rename is therefore replaced on the next track change, which is the documented behavior of an update that carries a title.

**The playlist sits beneath the player.** The body stacks a compact metadata and transport header, the player, then the playlist filling the remaining space — the same top-to-bottom stacking the video tab uses, which is what makes the layout survive being docked into a narrow sidebar.

**The tab is dockable into either sidebar.** It is an ordinary plugin tab in this respect: the host's dock control moves it, it lays itself out for the side it is told it is docked to, and playback continues while it is docked, hidden behind another sidebar entry, or in an unfocused split pane — the same background-playback behavior the video tab has.

**The navigator's multi-row action is a generic declaration field, not an audio special case.** The declaration gains an optional **selection action**: a label and an action name a plugin contributes for a selection of files whose extensions it claims. The navigator renders it in the row context menu when the whole selection resolves to one plugin, and the file-navigator module stays free of any knowledge of audio. The alternative — a hard-coded **Add to playlist** entry shown when the selection is all audio — was rejected for putting plugin-specific knowledge into core navigator code that the plugin architecture exists to keep out.

**`audio <path>` is a second route into the plugin's own opener.** Exactly as `video <path>` is: the host runs its ordinary open pipeline pinned to the audio opener, so relative-path resolution, wildcard expansion, the ten-file limit, sorted per-file dispatch, missing-file errors, and transcript attribution are identical to `open <audio-file>`. Bare `audio` prints `Usage: audio <path>`. Multiple tracks are queued from the command line with a wildcard, not with several space-separated paths — a path with no wildcard character is a single literal target, so that grammar is unchanged.

## Proposed changes

**Serving a file from an update.** `TabPluginServerCapabilities.updateTab` (`src/plugins/api.ts:143`) takes a factory that currently receives nothing; it gains the same `TabPluginResources` argument `openOrFocusTab`'s factory receives, so an update may call `registerFile` for a newly queued track. The host records each new reference against the tab being updated, exactly as it does for references registered at open time, so closing the tab — including plugin-failure teardown — releases every track the playlist ever queued and nothing else. This is additive at the type level: an existing zero-argument factory still satisfies the signature, so `TAB_PLUGIN_API_VERSION` stays at 1 and no other plugin changes. The documented invariant that an update cannot begin serving a new file is retired in `product/specs/tab-plugins.md`.

**Selection actions in the declaration.** `TabPluginDeclaration` (`src/plugins/api.ts:95`) gains an optional `selectionAction` field carrying a display label and an action name, and `TabPluginActivation` (`:183`) gains a matching optional `selectionAction` handler receiving the resolved absolute paths and the plugin capabilities. A declaration supplying one without the other is caught in `validateActivation` (`src/plugins/activate.ts:33`, `subscribes to "…" but provides no notify handler`) — the same function and the same moment a `notifications` claim with no `notify` handler is caught, which is at activation rather than at declaration, since that is the first point the host holds the activation. The handler is guarded and deadlined through the existing `src/plugins/guard.ts` path like any other plugin entry point. Both additions are optional fields, so every existing manifest and activation still typechecks and `TAB_PLUGIN_API_VERSION` is unaffected.

**Resolving and running a selection action.** Two new RPCs modeled on `fileNavigatorOpeners` (`src/controller/file-navigator.ts:147`), which takes the navigator's **tab index** — not a label — plus a tree-relative path. The first takes that same `index` and the selected tree-relative paths and answers with the contributed label and action name when every selected path is a file whose extension resolves to one and the same plugin declaration, and with nothing when the selection is empty, mixed, spans a directory, or resolves to a plugin contributing no selection action. Resolution reuses the extension lookup `openersForRow` (`src/file-navigator/openers-for-row.ts:22`) walks; it must not activate the plugin, since opening a menu is not a use of it. The second runs the action: it re-resolves the paths server-side against the navigator's own root, activates the owning plugin, and invokes its handler with absolute paths. The client sends row paths, as it already does when it sends `open <root>/<path>` (`web/src/useFileNavigatorOpener.ts:19`), but never a plugin identity or an action the server did not just offer it. Both methods are added to the client-request union in `src/protocol.ts:297` beside the existing `fileNavigatorOpeners` entry, with their result type declared beside `FileOpenerResolution` (`src/protocol.ts:43`). They are not folded into `fileNavigatorOpeners` itself: that method answers for one row and must stay cheap enough to call on every activation, while these two differ from it and from each other in what they may do — resolving must not activate a plugin, running must.

**Where the resolution logic lives.** The matching logic goes in a new `src/file-navigator/selection-action.ts` beside `openers-for-row.ts`, with `src/controller/file-navigator.ts` holding only the two thin RPC entry points. That module is at 126 effective lines against the 200-line `max-lines` limit, and the resolution rule belongs beside the per-row one it mirrors rather than in the controller either way — this is a decision, not a contingency.

**Navigator menu entry.** `fileNavigatorMenuItems` (`web/src/file-navigator-menu-items.ts:21`) takes an optional contributed selection entry and, when present, renders it as its own group above the **Copy** group, labelled with whatever the plugin declared — the function already returns an array of groups, so this adds an element rather than changing its shape. The query and its state live in a new `web/src/useSelectionAction.ts` hook beside `useFileNavigatorOpener.ts`, which `FileNavigatorTab.tsx` calls when a context menu opens on a row belonging to a multi-row selection, passing the result through `FileNavigatorOverlays` (`web/src/FileNavigatorOverlays.tsx:14`). The hook is a decision forced by the limit: `web/src/FileNavigatorTab.tsx` is already at 168 effective lines. Activating the entry sends the run RPC with the current selection. Every other entry keeps acting on the clicked row alone, so the single-row semantics in `product/specs/file-navigator-tab.md` are untouched.

**The audio manifest.** A new `src/plugins/audio/manifest.ts` declaring id `audio`, tab label prefix `audio`, command `audio`, edit gesture `open external`, a selection action labelled **Add to playlist**, and the extension-to-content-type map: `.mp3` → `audio/mpeg`, `.m4a` → `audio/mp4`, `.aac` → `audio/aac`, `.wav` → `audio/wav`, `.flac` → `audio/flac`, `.ogg` and `.oga` → `audio/ogg`, `.opus` → `audio/ogg`, `.aiff` → `audio/aiff`, and `.wma` with no content type. Capabilities requested: `note`, `openOrFocusTab`, `updateTab`, `openClaimedFiles`, `configuredViewer`, `openExternally`, `rejectRequest`, and `reportFailure`. Registered in `src/plugins/catalog.ts:9` beside the video manifest. **No `MIME` edit is needed**: `pluginContentTypes` (`src/plugins/opener-adapter.ts:38`) derives the served content types from the declaration and `src/index.ts:26` already spreads them into the table, so declaring the map is the whole of it — and `.wma`, declared with no content type, is exactly how `.mkv` and the other undecodable containers stay unserved on the video side. None of these extensions collides with a core opener or another plugin: `src/openers/` now holds only the editor and web-target openers, neither claims an audio extension, and the video plugin claims `.ogv` rather than `.ogg`.

**Payload and guard.** A new `src/plugins/audio/shared.ts` exporting the schema-version constant, an `AudioTrack` type (name, absolute path, served URL), an `AudioPayload` type (the ordered track list plus the current track's index, or `null` when the playlist is empty), and the type guards for the payload and for each intent's request shape — the same shape `src/plugins/video/shared.ts` has. Playlist rows show the track name alone; the size and location of the **current** track appear once in the metadata header, from `humanSize` (`src/openers/size.ts`), so a queued track costs no `statSync` until it is played. The playlist is the server's record of the queue; the client owns transport state (position, paused, volume) and never round-trips it.

**Activation.** A new `src/plugins/audio/activate.ts` whose inline opener, for a playable extension, either opens the player tab under a **constant instance key** — one player, so the key never varies — or, when that tab already exists, appends the file through `updateTab` and makes it current, registering the new track's URL through the update's resources and supplying the new track's name as the title. A non-playable extension delegates to the external presentation, which resolves the configured viewer and launches it with the same three-step fallback and notes the video plugin's `openExternal` uses. The command handler rejects a missing argument with the usage line and otherwise passes its argument to `openClaimedFiles`. The selection-action handler passes each resolved path to `openClaimedFiles` in turn, so a multi-row **Add to playlist** goes through the identical open pipeline a wildcard does. Because the playlist mutation logic (append, remove, advance, current-index bookkeeping) is what most of this file would be, it lands in its own `src/plugins/audio/playlist.ts` as pure functions over the payload, keeping both modules well inside the 200-line limit.

**Intents — two, not four.** The activation answers exactly `select-track` (make an entry current by its path) and `remove-track` (drop an entry, advancing when it was the current one). Each recomputes the payload through the playlist module and pushes it with `updateTab`, supplying the new current track's name as the title so the tab strip follows playback. Three other operations need no intent of their own and get none: a track **ending** is the client sending `select-track` for the following entry, which it can name because it already holds the list; **stopping on the last track** is the client sending nothing at all, which correctly leaves the tab titled after the track that just finished; and a **decode failure** is `remove-track`, since dropping an unplayable entry is the same operation as removing one by hand. The server still owns the queue and validates every path it is given against the tab's own playlist — the client decides only *which* existing entry to move to, never what the playlist contains. An unknown intent name or a malformed payload is a `rejectRequest`, which leaves the plugin running; a tab payload that fails its own guard is a `reportFailure`, matching the video plugin's split.

**Client.** A new `web/src/plugins/audio/` holding the lazy entry beside the other plugins' `index.tsx`, an `AudioTab.tsx` rendering the metadata and transport header above the player and the playlist, and a `Playlist.tsx` for the list itself — rows showing each track's name, the current one marked, click to select, and a remove control per row. The transport row carries previous, seek-back, play/pause, seek-forward, and next buttons; the browser's own `<audio controls>` element supplies the timeline, scrubbing, and volume, so no scrubber, no time display, and no volume control is rebuilt, and seeking rides the byte-range support `/open/<id>` already has. A `useAudioKeys.ts` hook binds the window-level key listener, checks the host's `active` flag (`web/src/plugins/api.ts:14`) before acting rather than reading visibility off the DOM, and is the single place the five bindings are expressed so buttons and keys cannot drift apart. The header consults `dock` (`:18`) to lay itself out for a narrow sidebar, as the capability's own comment directs, rather than measuring the host frame. The end-of-track handler sends `select-track` for the following entry and sends nothing when there is none; the row click sends `select-track`, and both the remove control and the decode-error handler send `remove-track`. The component reuses the existing `.image-tab`, `.image-meta`, and `.image-stage` classes for the header and stage, with new rules in `web/src/theme.css` for the transport row and the playlist. Registered in `web/src/plugins/registry.tsx` at schema version 1.

**Ordering.** Land the two API extensions first — `updateTab` resources, then the selection-action declaration field and its host plumbing — so the plugin has something to compile against; then the manifest, shared types, and activation; then the client body; then the navigator work, whose protocol entries in `src/protocol.ts` must land in the same step as the controller handlers and the client hook that call them, or typecheck breaks at the checkpoint between. Every new `src/` import carries the `.js` extension per the NodeNext rule, and payload field lookups use `??` rather than `||` to satisfy `prefer-nullish-coalescing`.

**Specs.** Add `product/specs/audio-tab.md` describing the tab, the playlist, the transport controls and key bindings, the append-and-jump behavior, the drop-on-decode-failure rule, docking, and background playback — modeled on `product/specs/video-tab.md`. Update `product/specs/tab-plugins.md` with a bundled-audio-plugin section, the selection-action contribution, and the retirement of the "cannot serve a new file through an update" sentence. Update `product/specs/open.md` with an audio-opener section covering both presentations and the playable/non-playable split. Note the **Add to playlist** selection entry in the row-context-menu section of `product/specs/file-navigator-tab.md`.

## Tests

Server tests are colocated as `src/**/*.test.ts`, client tests as `web/src/**/*.test.tsx`, mirroring the video plugin's own test files.

- `src/plugins/audio/playlist.test.ts` — appending to an empty and to a populated playlist; removing the current entry advances to the next; removing the last remaining entry empties the playlist and clears the current index; removing a non-current entry leaves the current track and its index correct; advancing past the last entry stops rather than wrapping.
- `src/plugins/audio/activate.test.ts` — a playable file opens the player tab under the constant instance key; a second playable file updates that tab instead of opening another, registers a URL for the new track, and retitles the tab; a non-playable extension routes to the external player with the configured-viewer fallback chain and never opens a tab; bare `audio` rejects with the usage line; `audio <path>` reaches `openClaimedFiles`; the selection-action handler opens every path it is given; both intents recompute and push the payload with the new title; an intent naming a path the tab's playlist does not hold rejects; an unknown intent name and a malformed intent payload reject without disabling; an invalid tab payload reports failure.
- `src/plugins/update-tab.test.ts` — extend for a factory that registers a file: the new reference is served, is owned by the updated tab, and is released when that tab closes while unrelated registrations survive.
- Declaration validation, extending the existing tests around `validateActivation` (`src/plugins/activate.ts`) — a `selectionAction` label with no handler disables the plugin at activation with that reason, and the audio manifest's extension, command, and content-type claims collide with no other bundled plugin's.
- `src/file-navigator/selection-action.test.ts` — a uniform audio selection resolves to the contributed label; a mixed selection, a selection containing a directory, an empty selection, and a selection of files whose plugin contributes no selection action all resolve to nothing; resolution does not activate the plugin; the run RPC re-resolves paths against the navigator root and refuses a path that escapes it.
- `web/src/plugins/audio/AudioTab.test.tsx` — the playlist renders every entry with the current one marked; clicking a row sends `select-track`; the remove control sends `remove-track`; a decode error on the player sends `remove-track` for that entry; a track ending sends `select-track` for the next entry, and sends nothing when it was the last; the transport buttons call the expected player operations; an empty playlist renders its empty state without a player error.
- `web/src/plugins/audio/useAudioKeys.test.ts` — Space, `←`/`→`, and `Shift+←`/`Shift+→` each perform their action while the tab is visible, and none of them fires while the host reports the tab hidden.
- `web/src/file-navigator-menu-items.test.ts` and `web/src/FileNavigatorOverlays.test.tsx` — a contributed selection entry renders in its own group above Copy and activates with the current selection; no entry renders when none is contributed, and the single-row entries are unchanged either way.
- `web/src/useSelectionAction.test.ts` — the hook queries only for a menu opened on a row inside a multi-row selection, and issues no request for a single-row menu.

## Out of scope

- **Shuffle and repeat modes.** No shuffle, repeat-one, or repeat-all; the playlist plays straight through and stops.
- **ID3 tags and album art.** Playlist rows and the header show file names and sizes, never embedded artist, title, album, or cover art.
- **Waveform and visualizer.** A native timeline only — no waveform scrubber, spectrum display, or any audio analysis.
- **Saving and restoring playlists.** The playlist is live and in-memory like every other plugin tab: not persisted, not restored by `--relaunch`, and not captured beyond the file a profile already records for a plugin tab.
- **Reordering the playlist.** Entries are added at the end and removed individually; drag-to-reorder is not part of this version.
- **An `audio left`/`audio right` docking command.** The tab is dockable through the host's dock control, but the plugin does not place its own tab the way `schedules left` does, and requests no `dockTab` capability.
- **Extending the navigator's Enter and double-click gestures to the whole selection.** Those keep opening the cursor row alone; the multi-row route is the contributed **Add to playlist** entry.

## Open questions

- **Seek step size.** The `←`/`→` bindings and their buttons need a fixed interval; 10 seconds is proposed, matching the step most native players use. Not yet confirmed.
- **Whether widening `updateTab` to register files warrants an API version bump.** It is additive at the type level, so this plan keeps `TAB_PLUGIN_API_VERSION` at 1, but it does loosen a documented invariant. If a bump is preferred, the alternative shape is a separate resource-registering capability granted outside any factory, which the intent handlers could also use.
- **The empty-playlist wording.** The tab stays open with no entries after the last one is removed; the exact text shown in place of the player is not fixed.
- **Whether a dropped undecodable track should leave any lasting trace.** The plan shows a short note in the view as the entry is dropped, but nothing is written to a transcript and the note's persistence is unspecified.
