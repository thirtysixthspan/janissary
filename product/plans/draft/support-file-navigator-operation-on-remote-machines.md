# Support file navigator operation on remote machines

**Complexity: 9/10** — remote shell launch and same-process restoration span the bundled plugin, a new host-owned launcher, a versioned remote process contract, session persistence/reattach, remote metadata UI, and file-navigator path resolution.

The ready-backlog item asks for file navigator operations on remote machines, and the user clarified the intended surface is a bundled shell tab. Janissary already supports remote trees through remote agent and harness tabs, including filesystem mutations over their SSH channels. The bundled shell tab already has a folder action, but it is local-only because the shell cannot yet own a remote channel; the bare `files` command also treats a remote shell's cwd as a local path. This feature adds remote shell ownership and routes both entry points through the existing remote navigator path.

## Design decisions

Established behavior: `files in <label>` and the folder button on a remote agent or harness use that tab's remote workspace and existing SSH channel. Remote trees support the same filesystem operations as local trees, bounded to the provisioned remote workspace. The `files` command normally uses the issuing tab's cwd; a metadata-row folder button opens or retargets at the remote workspace root. The remote-server spec explicitly excludes `files on <address>` without an existing remote agent or harness tab. The bundled shell plugin rejects a remote origin (`src/plugins/shell/open-tab.ts:20-22`, `origin.remote`), even though its metadata already has the folder and new-shell actions (`web/src/plugins/shell/ShellTabMeta.tsx:43-65`). The folder capability sends `openFileNavigatorFor` (`web/src/plugins/api.ts:221-227, 303`), while the bare command treats its source as local (`src/file-navigator/open-command.ts:19-29`, `resolveCwd`).

User decisions: target the bundled shell tab and include the remote-shell capability needed to make that tab remote; support `zsh on <address>` from a local tab and opening remote shell siblings from both a remote harness's repurposed + action and a remote shell's existing “New shell here”/`Cmd+T` actions; use the same validated remote address and workspace-provisioning rules as remote agents; give a standalone remote shell its own channel/workspace and let a sibling opened from a remote harness or remote shell reuse that tab's channel/workspace; for the bare `files` command, use the shell's remote cwd while it is inside the workspace and fall back to the workspace root when outside; keep the existing folder-button rule of opening/retargeting at the remote workspace root; keep remote shell and navigator operations confined to the provisioned workspace; use the exact command spelling `zsh on <address>` and usage text `Usage: zsh [on <address>].`; reuse existing remote-launch failure behavior; repurpose the existing remote harness +/new-agent action to open a shell. Restore remote shell tabs like remote harness tabs after `--relaunch`. The existing shell file button continues to use the host-provided `openFileNavigator` route. Existing remote navigator lifecycle applies: it opens/retargets from the owning tab without stealing focus, closes with that owner or on channel loss, and reports a dropped connection once. Extend the existing bundled shell plugin and remote-session restore path; add an explicit shell identity to remote process/session state so attach restores the same running PTY.

The existing remote-server boundary also rules out nested remoting. A bare `zsh` from a remote shell opens its remote sibling as selected above; `zsh on <address>` from a remote shell remains refused with the exact message `Cannot launch a remote shell from a remote tab.`.

For `files <path>` from a remote shell, `~` expands against the remote user's home; the resulting path still has to be inside the provisioned workspace.

Final user decisions: refuse nested `zsh on <address>` with `Cannot launch a remote shell from a remote tab.`; expand `~` from the remote user's home and apply the existing workspace containment rule.

The user selected a plugin-to-host route for the shell's folder action. Code review found that `ShellTabMeta` already calls the host-provided `openFileNavigator` capability, which sends `openFileNavigatorFor` and delegates to `FileNavigatorManager.openOrRetarget`. Reuse this existing route rather than adding a second intent; add the remote tab/channel data it needs to open a remote root.

Implementation choice settled during planning: remote shell tab creation belongs in a purpose-built host capability, not in generic plugin resources or a new core shell view. `openPluginTab` runs the payload factory before its label is minted, while remote provisioning requires the label first; the host capability reserves that identity and owns the remote channel, process, and tab lifecycle, and the bundled shell plugin keeps its command and presentation.

## Proposed changes

The user chose the bundled shell tab and approved including the remote-shell capability it needs. `zsh on <address>` opens a remote shell with its own provisioned workspace; the remote harness's repurposed + action opens a sibling shell in that harness's existing remote workspace and channel, and a remote shell's existing “New shell here”/`Cmd+T` actions open siblings in their source shell's shared workspace and channel. Both use the existing validated remote address and workspace-provisioning rules. Malformed arguments report `Usage: zsh [on <address>].`; connection and provisioning failures follow `startRemoteLaunch`/`wireProvisioning`'s existing failure path in `src/harness/remote-launch.ts:52-104`, with no local fallback. Keep the shell view in the bundled plugin. Add a purpose-built `openRemoteShell` host capability, declared in `src/plugins/api-capabilities.ts` and restricted through `src/plugins/context.ts:103-141`, that reserves the shell label before creating the channel; this is needed because `openPluginTab` runs its factory before minting the label (`src/tab/openers.ts:109-124`). The capability is additive to the v1 plugin contract, so `TAB_PLUGIN_API_VERSION` stays at 1. The remote harness's new-shell action reaches the same plugin command through a new `launchShellFor` core RPC, while local harness tabs keep their existing `launchAgentFor` behavior (`src/protocol/core-rpc.ts:53-56`, `src/message/tabs.ts:52-55`). The host creates the plugin shell tab in a provisional state so SSH prompts render in its terminal, then swaps the payload to the remote zsh PTY once the workspace is ready through `PseudoterminalManager.registerRemotePty` (`src/pseudoterminal-manager.ts:106-115`). A bare `zsh` from a remote shell or its existing sibling control uses the source tab's remote channel and workspace rather than starting a local shell. Move the existing zsh startup-file generator and directory lifecycle from `src/plugins/shell/` into a host-owned `src/shell/` module; publish the narrow helper through `src/plugins/api.ts` for the bundled plugin and use the shared module from the remote process host without crossing the plugin import boundary. The remote peer owns its startup directory for the peer lifetime. The per-shell nonce travels with the remote spawn and session-state record so cwd reports remain trusted after attach.

`launchShellFor` dispatches the already-declared `zsh` command with the named remote harness as its source; it does not implement a second shell launch path. Add the RPC's type, parameter guard, and message-dispatch case beside `launchAgentFor`. The remote harness alone substitutes this action; local agent and harness rows keep `launchAgentFor` unchanged.

The shell's existing file button uses `openFileNavigator` → `openFileNavigatorFor` (`web/src/plugins/shell/ShellTabMeta.tsx:43-50`, `web/src/plugins/api.ts:221-227,303`) → `FileNavigatorManager.openOrRetarget` (`src/controller/file/navigator.ts:171`, `src/file-navigator/manager.ts:87-99`); preserve this route and make the remote tab record/channel available to it. Bare `files` and `files <path>` commands from a remote shell must resolve relative paths against its remote cwd and use `RemoteFileSystemPort`; `resolveCwd` currently omits the source tab's `remote` target when no `in` clause is present (`src/file-navigator/open-command.ts:19-29`), so extend that branch and reuse `openRemoteTree` (`:56-93,168-179`). The bare command falls back to the workspace root only when cwd lies outside the workspace. Expand `~` with `expandUserPath` (`src/paths.ts:14-24`) using the remote home carried by remote workspace/session state rather than the local host's home, then refuse a resolved target outside the provisioned workspace. Keep the folder-button root rule unchanged: `openRemote` opens/retargets at `RemoteManager.workspaceOf` (`src/file-navigator/open.ts:52-73`). The file navigator uses the remote owner tab's existing lifecycle and current host chip, watcher, notification, and path-containment behavior. Remote shells and their navigators remain workspace-confined; the feature adds no direct `files on <address>` form or arbitrary remote-path browsing. Reuse `RemoteManager`, `PseudoterminalManager.registerRemotePty`, the `files` command, `openRemoteTree`, and `RemoteFileSystemPort` rather than rebuilding remote connection or filesystem operations.

Expose the existing `TabView.remote` data and remote-session control through the shell plugin client capabilities (`src/protocol/tab.ts:18-33,60-80`, `web/src/plugins/PluginBody.tsx:117-137,180-187`) so `ShellTabMeta` can render the same host chip, provisioning indicator, and attach/detach control as other remote tabs. Add an explicit shell-process discriminator, marker nonce, and remote home to the remote spawn/workspace-ready/session-state contract, bump `REMOTE_PROTOCOL_VERSION` (`src/remote/protocol.ts:7-10,166`), extend `RemoteSessionProcess` and `RemoteSessionRecord` to retain the shell's identity, cwd, and remote home, and teach `sessions/attach.ts`, `sessions/restore-tabs.ts`, `sessions/snapshot.ts`, and `sessions/rows.ts` to list and reattach the same PTY as a shell plugin tab. Preserve the detached session's shell kind and identity through `RemoteSessionKind` in `src/protocol/sessions.ts:8` so the sessions tab does not present it as an agent. Do not restore remote file navigators. Update `help.md`, `product/specs/file-navigator-tab.md`, `product/specs/shell-tab.md`, `product/specs/tabs.md`, `product/specs/agents.md`, `product/specs/remote-server.md`, `product/specs/sessions-tab.md`, and `documentation/user-documentation/advanced-agents/remote-agents.md` for the resulting command, button, connection, remote-home expansion, and relaunch behavior.

Implement in dependency order: (1) move the zsh startup helpers to the host-owned shell module and re-export the narrow helper through the plugin API; (2) add shell spawn metadata, remote startup environment handling, validation, and the remote protocol version bump; (3) add the `openRemoteShell` host capability and remote launch service, then route `launchShellFor`, shell sibling commands, and `zsh on <address>` through it; (4) pass remote target/session state to the plugin client and render the existing remote metadata affordances; (5) resolve bare and path-bearing `files` commands through the remote filesystem port; (6) extend session snapshots, persistence, kind display, and attach restoration; (7) update specs, help, and user documentation. Keep the existing `openFileNavigatorFor` RPC and remote filesystem frame family unchanged.

## Out of scope

Direct `files on <address>` without an existing remote shell, agent, or harness tab remains out of scope. Nested remote shell launches are out of scope; a bare `zsh` from a remote shell opens a sibling in the current remote workspace instead. Arbitrary remote paths outside the provisioned workspace remain out of scope. Remote-tree lifecycle follows the existing remote navigator behavior. Remote shell tabs are restored after `--relaunch`, as remote harness tabs are, but are not added to profile save/launch in this version. Existing local shell launch, sibling-shell, and file-navigator behavior remains unchanged.
