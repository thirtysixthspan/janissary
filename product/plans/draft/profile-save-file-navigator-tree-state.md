# Record file navigator tree state in a profile

**Complexity: 6/10** — a new server-to-client request event plus its reply RPC, a restore hint threaded through the tree payload, and capture changes that pull undocked navigators into the tab-placement machinery, across roughly a dozen files on both sides of the wire.

## Summary

Feature request (verbatim from `product/backlog/features.md`): "record the tree state directories open/closed and keyboard focus of the file navigator during `profile save` and restore that state with `profile launch`."

Today `profile save` captures a file navigator as nothing more than a dock side and a root path, so relaunching a saved profile reopens every tree fully collapsed with no row selected. This plan adds the tree's view state to that capture: which directories were expanded, which row held the keyboard cursor, the range anchor, and the full multi-row selection. `profile launch` replays it, re-expanding the directories that still exist and re-highlighting the saved rows.

Two things make this more than a field addition. The expanded set is server state (`FilesTabState.expanded`), but the cursor, anchor, and selection are client-only React state in `useFileNavigatorSelection.ts`, and there is no server-to-client request path today. And `profile save` currently skips a navigator that isn't docked, which this plan changes: undocked trees are captured too, carrying a `tab` presentation object so they reopen in their saved group, order, and pane.

## Design decisions

- **Four values are captured per navigator: `expanded`, `cursor`, `anchor`, `selected`.** All are paths relative to the tree's root, matching the vocabulary the code already uses (`FilesTabState.expanded` server-side, `FileNavigatorSelection`'s three fields client-side). They sit as flat keys on the `files` entry alongside `dock`/`in`/`path`, for example `{ "dock": "left", "path": "$root", "expanded": ["src", "src/file-navigator"], "cursor": "src/file-navigator/manager.ts", "anchor": "src/file-navigator/index.ts", "selected": ["src/file-navigator/index.ts", "src/file-navigator/manager.ts"] }`.
- **The client sends its selection only at save time, never continuously.** No cursor reporting on keystrokes, no debounced blur reporting. `profile save` asks the connected clients for their navigator selections, waits briefly for a reply, and writes the entry without the three selection keys if nothing arrives. This mirrors how `saveProfile` already awaits `buildLayout`'s asynchronous window-bounds read, and it is why a new server-to-client request event is needed rather than a `reportLayout`-style push.
- **Restore is best effort and silent.** Each saved expanded path that still resolves to a directory is expanded; the rest are dropped. A cursor, anchor, or selected path that is no longer a visible row is dropped the same way, leaving the tree with no cursor when nothing survives. Nothing is added to the launch report. This matches `pruneAndBuildRows`, which already drops vanished expanded directories on every rebuild. A navigator whose root does not exist yet (the waiting-for-path case in `src/file-navigator/open-command.ts:44`, `if (!exists)`) therefore restores nothing: no saved path resolves against a root that isn't there, and the restore is not retried when the directory later appears.
- **Restoring the selection does not move keyboard focus.** The saved rows render highlighted and the cursor row is scrolled into view, but which tab is active and which element holds focus stays exactly as the profile's existing `tab.focus` rules decide. A docked navigator is never the active tab, and it should not start stealing focus now.
- **Undocked navigators are captured too.** A `files` entry with no `dock` key already opens into the center strip, so capturing an undocked tree is an entry without `dock`. Those entries also carry a `tab` object (`number`, `group`, `pane`, `color`, `groupColor`), the same presentation object editor entries carry, so a strip tree reopens in its saved group, order, and pane. Docked entries keep `dock` and get no `tab` object, since a docked tree has no place in the strip.
- **One combined count in the save report.** Navigators report as `N file navigator(s)` regardless of docking, and no navigator lands in the "Skipped" list any more. The existing `docked tab` count narrows to the notifications and schedules tabs.

## Proposed changes

Land these in the order below. Protocol and type changes first, then the server, then the client, so typecheck stays green at each checkpoint.

**Profile shape and validation.** `src/profile/types.ts:85` (`export type ProfileFilesEntry`) extends the entry with four optional fields (`expanded` as a string array, `cursor` and `anchor` as strings, `selected` as a string array) plus an optional `tab` of the existing `ProfileTab` type declared at `src/profile/types.ts:46`. `src/profile/schema.ts:86` (`function filesProblems`) checks each new field with the `checkField` helper it already uses for `in`/`path` (`'string[]'` is an accepted kind, as `harnessProblems` shows for `run`/`schedule` at `src/profile/schema.ts:71`) and delegates the `tab` object to the existing `tabProblems`, so `profile validate` reports a malformed entry with the same location context it gives editors.

**Asking the client for its selections.** The one-shot server-to-client path already exists and has four links; copy `layout`'s at each. `src/protocol.ts:153` (`export type ServerEvent`) gains a `CollectTreeStateEvent` (`t: 'collect-tree-state'` plus a numeric request id) alongside `LayoutEvent`, and `RpcCall` gains a `reportFileNavigatorSelection` method whose params carry that id plus one record per navigator: its tab `index` (the same index every other `fileNavigator*` RPC uses), `cursor`, `anchor`, and `selected`. `src/bus.ts:98` (`export type BusChannels`) gains a `fileNavigator` channel whose event is `{ type: 'collect'; id: number }`. `src/controller/types.ts:6` (`Sinks`) gains an optional `sendCollectTreeState`, `src/controller/events.ts:20` subscribes the new channel to it exactly as it subscribes `layout`, and `src/index.ts:59` supplies it as `(event) => broadcast({ t: 'collect-tree-state', ...event })` beside `sendLayout`.

A new module `src/file-navigator/selection-request.ts` owns the round trip and holds the only mutable state involved, playing the same role for tree selections that `src/client-layout.ts` plays for sidebar sizes: a small in-process holder that `profile save` reads. `requestTreeSelections(timeoutMs)` issues a fresh id, emits the bus event, and returns a promise resolving to a `Map<number, selection>` keyed by tab index; `resolveTreeSelections(id, records)` settles the request in flight and ignores any other id, so a late reply to a previous save is discarded. No reply within **250 ms** resolves to an empty map, which is what a save with no client attached (or under `--no-open`) gets. `src/message-handler-file-navigator.ts:12` (`type FileNavigatorMessage`) adds the new method to its `Extract` union and routes it straight into `resolveTreeSelections` with no reply event, mirroring the fire-and-forget cases there.

Two ceilings here, both deliberate. When several browser clients are connected the first reply settles the promise and the rest are ignored, so a save captures whichever window answered first; if per-client trees ever need to be distinguished, the reply would have to carry a client identity and the map would key on it. And a client slower than the 250 ms window costs only its selection keys: `expanded` is read from server state and always saves.

**Reading the expanded set.** `FileNavigatorManager` gains `expandedPaths(label)`, returning that tab's expanded directory paths as a plain sorted array, keeping the private `tabs` map private the way `search` and `openers` already do. The sort is for deterministic file content, since `profiles/` is committable; restore order does not matter, because `buildRows` (`src/file-navigator/index.ts:36`) walks from the root and consults the expanded set rather than replaying insertion order. `src/file-navigator/manager.ts` is at the 200-line limit already (200 counted lines under `max-lines`'s `skipBlankLines`/`skipComments`), so before adding this and `restoreView` below, extract its `openers` method (`src/file-navigator/manager.ts:214`) into a new `src/file-navigator/openers-for-row.ts`, moving its `node:path`, `openerForExtension`, and `FileOpenerChoice` imports with it and leaving a one-line delegation. Per `ai/guidelines/code-guidelines.md`, extract; do not compact.

**Capturing.** `src/profile/save.ts:22` (`saveProfile`) awaits `requestTreeSelections` alongside the `buildLayout` await it already performs, then passes the resulting map into `captureTab`. Its caller at `src/profile/manager.ts:27` already handles the promise (`void saveProfile(...).then(...)`), so the wait only delays the report line. `src/profile/save-route.ts:57` (the `case 'files'` arm) stops branching on `tab.dock`: every navigator produces an entry from a new `writeFilesEntry(tab, managers, selection)` in `src/profile/save-entries.ts`, which sets `path` from `tab.files.absoluteRoot` run through `abbreviatePath` with `{ root: managers.tab.launchDir }` (the same portability treatment `writeAgentEntry` and `writeEditorEntry` give their paths), sets `dock` when the tab is docked, adds a `tab` presentation object when it is not, and folds in `expanded` plus whichever of the three selection fields the client reported. `writeAgentEntry`, `writeEditorEntry`, and `writeHarnessEntry` each build that `tab` object inline today (`src/profile/save-entries.ts:21`, `:34`, `:67`); lift it into one small local helper in that file and have all four call it, rather than adding a fourth copy. Absent values and empty arrays are omitted rather than written, matching the existing reliance on `JSON.stringify` dropping `undefined`. `CaptureState` (`src/profile/save-route.ts:12`) gains a `fileNavigators` counter and stops incrementing `dockedViews` for navigators; `formatSaveSummary` (`src/profile/save.ts:58`) renders it as its own `N file navigator(s)` part, and no navigator is pushed onto `skipped` any more.

**Restoring.** A new `src/file-navigator/restore.ts` exports `restoreTreeView(port, label, view)` taking the same `NavPort` (`src/file-navigator/navigation.ts:7`) the other navigation functions take: it walks the saved expanded paths in order, expanding and watching each one that still resolves to a directory, then records the surviving cursor/anchor/selected paths as a restore hint on the tab's state and rebuilds. The expand-and-watch step is the loop body of `revealPath` (`src/file-navigator/navigation.ts:61`); factor it into a shared helper both call rather than duplicating the `state.expanded.add` plus `port.watchDir` pair. `FilesTabState` (`src/file-navigator/manager.ts:29`) gains a `restore` field holding that hint plus a revision counter, and `FileNavigatorView` (`src/tab/types.ts:134`) gains the matching optional `restore` object. `rebuild` (`src/file-navigator/manager.ts:279`) copies the hint onto the payload it writes; the revision changes only when a new restore is applied, which is what stops the repeated full-state broadcasts from re-applying an old hint. `FileNavigatorManager` exposes `restoreView(label, view)` delegating through its existing `navPort()`.

**Launching.** `FileNavigatorManager.open` and the `openFilesCommand` it delegates to (`src/file-navigator/open-command.ts:12`) start returning the label they opened, redocked, or focused, which every branch there already has in hand (`existing.label`, `waitingLabel`, `newLabel`) and `undefined` on the not-a-directory error path. Both current callers (`src/profile/files.ts:21`, `src/commands/files.ts:13`) ignore a return value today and are unaffected. `openProfileFiles` (`src/profile/files.ts:10`) uses that label to call `restoreView` with the entry's saved tree state, and, for an entry carrying a `tab` object, relocates the tab into its authored group and returns a `MainAreaCandidate` the way `openProfileEditors` (`src/profile/editors.ts:20`, `relocateToGroup`) does. Its signature changes from `void` to that candidate array. `src/profile/agent-opener.ts:71` spreads the result into `candidates` before the `reorderGroupByNumber` and `placeProfileTabs` passes below it, so a captured strip tree lands at its saved number, group, and pane. The call keeps its current position in the launch order, ahead of editors and monitor resolution.

**Client.** A new `web/src/file-navigator-selection-registry.ts` holds each mounted navigator's current selection by tab index in a module-level map, exporting a setter, a clear, and a `collectNavigatorSelections()` returning the reply records. `web/src/ws.ts:39` (`onEvent`) gains a `case 'collect-tree-state'` that calls `collectNavigatorSelections()` and replies through the existing `send`. Import the registry into `ws.ts` directly rather than registering a provider callback from `App.tsx`: there is exactly one caller, the registry is a leaf module importing nothing but protocol types, and the listener indirection `onLayout` uses exists because several components subscribe to layout, which is not the case here. `App.tsx` needs no change at all.

Publishing into the registry happens inside `useFileNavigatorSelection` (`web/src/useFileNavigatorSelection.ts:106`), which takes the tab index as a new argument and clears its entry on unmount. Put it there rather than in `FileNavigatorTab.tsx`: that component is at roughly 191 counted lines against the 200-line limit, while the hook already owns the state being published and is passed `index` from `FileNavigatorTab.tsx:29`'s call site with one changed line.

On the restore side the same hook takes the payload's `restore` hint. When its revision differs from the last one applied, the hook seeds cursor, anchor, and selection from it, filtering every path against the current rows so a vanished row simply drops out; the existing root-change reset and `reconcileSelection` behavior at `web/src/useFileNavigatorSelection.ts:111` is otherwise untouched, and a hint whose revision has already been applied never overwrites a selection the user has since changed. Keep the revision-comparison and path-filtering logic as an exported pure function in that file so it is testable without rendering, matching how `reconcileSelection` and `replaceSelection` are already exported.

**Specs.** `product/specs/profiles.md` updates its "Profile-level file navigator" and `profile save` sections: the new keys, the undocked capture and its `tab` object, the combined count, and the silent best-effort restore. This includes correcting the existing sentence in the `profile save` section that says a file navigator "that isn't docked into a sidebar" is left out of the saved profile. `product/specs/file-navigator-tab.md` notes that a tree's expanded directories and selection round-trip through a profile, alongside the existing statement in "Undoing and redoing a move" that the undo/redo stacks do not.

## Out of scope

- Continuous or blur-triggered cursor reporting. The client sends its selection only in answer to a save-time request.
- Moving cursor/anchor/selection ownership to the server. They stay client state; only the save-time snapshot and the restore hint cross the wire.
- Giving a restored navigator keyboard focus, or changing which tab is active after launch.
- Restoring a tree's scroll offset beyond scrolling the cursor row into view.
- Restoring a navigator's move undo/redo history, which stays in-memory and per-tab as the spec already says.
- Capturing which docked tab is visible in a sidebar's internal tab-switcher, and capturing a navigator's association with the tab it was opened from. Both remain uncaptured, as documented today.
- Any change to the search pop-up's own reveal behavior.
