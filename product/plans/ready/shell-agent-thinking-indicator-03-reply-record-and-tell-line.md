# Answering record and the tell line on settled replies
**Complexity: 3/10** — four small server edits (a log entry field, a reply-view projection, one wire field, one regex) plus an end-to-end test over real records and a plugin-contract changelog line; the regex also changes where every `tell` reply lands in the shell today, which moves one existing assertion and needs a spec sentence.

## Goal

Make a settled background reply say which record answered: store `{ id, name }` on the log entry when the prompt result carries a record id and the record still exists, and project it onto the wire as `record`. In the same step make `tell` replies carry their command line the way `ask` replies do, so a `tell` reply is placed beneath its own echo instead of a `> monitor` one, and `tell reset`'s confirmation lands beneath its own `> tell reset` echo. After this subplan the server half of the feature is complete.

## Design decisions and dependencies

This subplan consumes two earlier contracts, both already in the tree. From `01-acp-result-record-id`: `AcpPromptResult` in `src/acp/types.ts` has an optional `recordId` on both variants, kept on the exhausted error. From `02-dispatch-receipt`: `appendAcpBackgroundReply(managers, label, input, result, id)` in `src/acp/response.ts` takes the id minted at dispatch, and that file already imports `recordConnectionName` from `src/plugins/connections/shared.ts`, the one definition of `acp:<role>:<name>`. `06-marker-lifecycle` and `07-client-wiring` consume the wire field.

Source plan requirements carried here: "Server changes" bullets on `appendAcpBackgroundReply` looking the record up and storing `{ id, name }`, on `LogEntry.backgroundRecord`, on `ACP_INPUT` matching `tell`, on `backgroundRepliesFor` copying the record as `record`, and on `BackgroundReplyView`; "Edge cases" (today a `tell` reply is written beneath `> monitor`; this makes it carry its line; `tell reset` is placed beneath its own echo and still gets no marker); "Once the prompt settles" (a refusal creates no block, so nothing is stored for it; a record deleted mid-prompt stores nothing); the server half of "Tests" for `response.test.ts` and `background-replies.test.ts`; "Documentation" for the `tell` placement sentence. The changelog bullet, the reference sentence, and the plugin spec clause under "The plugin-visible shape" below go beyond the source plan's list and are kept only because a repo guideline requires them.

- `appendAcpBackgroundReply` (`src/acp/response.ts`, 77 counted lines today): when `result.recordId` is set, find the row with that id in `managers.acpRecords.rows()` and store `backgroundRecord: { id, name }` beside `background`. With no `recordId`, `rows()` is never called (the command tests build a managers object with no `acpRecords`). Do the lookup in a small non-exported helper in the same file that answers the pair or nothing, and build the whole entry before the single `managers.tab.append` call. Finding one row with `rows().find` by id is how the repo already reads one record (`managers.acpRecords.rows().find((row) => row.id === action.id)` in `src/plugins/connections-topic-actions.ts`); one pass over the retained records per settled prompt is accepted.
- `name` is `recordConnectionName` applied to the row (its `kind`, `ownerName`, and `role`, which the row can be passed as it stands), giving `acp:<role>:<ownerName>`, the title the record's connection tab takes (`src/plugins/connections/record-tabs.ts`). A row with no `role` would give `acp:<ownerName>`, but `AcpSessionManager.session()` in `src/acp/session-manager.ts` always begins a core record with its role, so that is unreachable here.
- A `recordId` whose row is missing stores nothing. This branch is defensive. The lookup runs on the promise chain that the settlement resolves (`promptResult` in `src/acp/manager.ts`), before any other event-loop turn could carry a delete request, and `AcpSessionRecords.delete` refuses a record that has no outcome yet, so a record can only be deleted after it has closed; no real flow gets the id deleted in between. A unit test with a `rows()` that omits the id is its only proof. A result with no `recordId` stores nothing either. Spread the field in conditionally, the way `src/command/manager.ts` spreads `result` into the core-response reply only when it is defined; never write `backgroundRecord: undefined`, so the entry, the view, and the state broadcast carry no key for a reply without a record.
- Name drift, accepted and not reconciled. The receipt's `name` (02) is built at dispatch from the tab's current title. The link's name here comes from the row's `ownerName`, which `AcpSessionManager.session()` captured as `tab.title ?? label` when the role's session, and so its record, began; `AcpSessionRecords.begin` copies the source and never updates it (the 'mints independent UUIDs…' case in `src/acp-records/manager.test.ts` pins that). The two names differ whenever the tab was renamed (the `rename` command, `renameTab` in `src/tab/operations.ts`) after that record began. That is wider than a rename mid-prompt, because one record serves every prompt of a role until reset or close. The link takes the record's own name on purpose: it is the title of the connection tab the link opens, so the tooltip and the destination agree once the prompt has settled. The running marker's name can lag a rename and is cosmetic and short-lived. Do not read the live tab title here and do not add rename tracking; a test pins the choice.
- `LogEntry` in `src/tab/types.ts` (189 counted lines, verified) gains one optional field, `backgroundRecord?: { id: string; name: string }`, next to `background`, with a comment. That adds one counted line, so the file ends at 190.
- `backgroundRepliesFor` (`src/tab/background-replies.ts`) copies `backgroundRecord` onto the view as `record` whenever the entry has it, whether or not the entry also carries a line, and adds no key otherwise (the same conditional-spread form as `line`). `BackgroundReplyView` in `src/protocol/tab.ts` gains the optional `record: { id: string; name: string }`. The comment above it says only that `line` is optional today; it now also says `record` names the connection record holding the prompt's final block and the title of its connection tab, and is absent for a refusal, a reset confirmation, and a monitor reply. The `{ id, name }` shape is written inline in both files, not shared: the typed copy in `backgroundRepliesFor` fails typecheck if the two drift. `src/protocol.ts` already re-exports the view type and the client reads it through `@shared/protocol`, so the wire type stays defined once (principle 7). No client file changes here: `subscribeBackgroundReplies` (`web/src/plugins/background-replies.ts`) passes each reply through whole, and nothing on the client validates the reply's fields.
- `ACP_INPUT` becomes a pattern that matches `ask` or `tell` as a whole word, case-insensitively, after optional leading whitespace and an optional slash, and its comment follows (it says it mirrors `src/commands/ask.ts`; it now mirrors `ask.ts` and `tell.ts`). `tell-extra` matches, as it does for the command (`match` in `src/commands/tell.ts`); `telling` and `asked` do not. `monitor ask …` input still matches neither because the pattern is anchored at the start. `acp …`, an empty input, and ordinary entries are unchanged. The entries that carry `background` come only from ACP replies (`appendAcpBackgroundReply`), the two resets (`src/commands/ask-reset.ts`, `src/commands/tell-reset.ts`), `monitor ask` (`src/monitor/ask.ts`), and live monitor suggestions (`src/monitor/live-monitors.ts`, empty input), so no other producer is newly matched.
- The user-visible effect of the `tell` fix is real before the client work. `useBackgroundReplies` already writes a reply under `reply.line ?? 'monitor'` and `ReplyPlacement` (`web/src/plugins/shell/reply-placement.ts`) already compares that line with the echo's, so a `tell` reply that carries its line is placed beneath its own echo or beneath a second `> tell …` echo, and `tell reset`'s confirmation lands beneath its own echo. The shell already echoes `tell` lines because both commands are core responses.

The plugin-visible shape. `record` on the reply that `onBackgroundReply` delivers, and `recordId` on the `promptAcpResult` result (01), are optional fields on published plugin contracts, so `ai/guidelines/plugins.md` §12 and its "Before changing the plugin API" checklist apply: the change is classified against §4 and the changelog is updated. Classification: additive optional fields, so the API integer stays 3 (`TAB_PLUGIN_API_VERSION` is untouched, and the v3 changelog already records other additive changes the same way). Decision: this plan carries the changelog line and the reference and spec text, because 01 left the changelog line unassigned and nothing else in the sequence owns it. No test requires an entry, and `src/plugins/documentation.test.ts` constrains where one may go: the current-counts sentence must appear exactly once, in the v3 section, and the v2 section must not gain `openConnection` or an optional `line`. The edits, and only these:

- `documentation/developer-documentation/tab-plugins.md`, `## API changelog` → `### v3`: one new bullet directly after the bullet that records `openConnection` and the optional `line`. It says background replies gain an optional `record` (the record's `id` and the `name` of its connection tab) and the `promptAcpResult` result gains an optional `recordId` on either variant, that both name the connection record holding a prompt's final block and are absent when the prompt reached no record, and that both are additive so the API integer remains v3. It repeats no capability count. The existing `line` bullet (its `acp <prompt>` wording predates the `ask` rename) and the migration bullet are left as written, and so is the v2 section.
- `documentation/developer-documentation/tab-plugins.md`, `## Using core ACP`: the sentence that says `onBackgroundReply` delivers replies "with an optional `line`" gains the `record` clause, including that its `id` is what a plugin passes as a row's `recordId` to `openConnection`, and that a refusal, a reset confirmation, and a monitor reply carry none. This is the reference text for the contract (§12: the exact contract), so the field belongs here.
- `product/specs/tab-plugins.md`, `## API version 3`: the sentence "Background replies gain an optional `line`" that lists the reply's optional fields gains the same `record` clause (principle 10: a published behavior changes with its spec). - `product/specs/shell-tab.md`, § Core ACP connections: in the `ask reset` paragraph ("`ask reset` is echoed and placed the same way…"), add that `tell <prompt>` is echoed and placed exactly like `ask <prompt>`, and that `tell reset` reports once beneath its own exact typed line, like `ask reset`. Nothing about the marker or link; that is `07-client-wiring`. The source plan lists this sentence.
- Deliberately not edited: `product/specs/acp.md` (its § Commands already says a shell `ask` or `tell` prompt's settled reply goes beneath the echo of the line typed, so the `tell` fix only makes the code match it; the `promptAcpResult` bullet in § Availability and plugin API already carries `recordId` from 01; the marker text the source plan puts in § Answers, activity, and questions is 07's), `ai/guidelines/plugins-tabs.md` (it names `onBackgroundReply` without its fields), the help pages and user documentation (`08-docs-and-verification`), and the root `CHANGELOG.md` (generated from commit messages).

## Out of scope

- Changing how `ask reset` and `tell reset` build their replies, or giving them a record or a receipt.
- A marker on `tell reset`. Only its placement changes here, through the line fix.
- Making the running marker's name follow the record's `ownerName` or a rename. The receipt is `02-dispatch-receipt`'s and the divergence is accepted above.
- Help pages and user documentation (`08-docs-and-verification`), and any change to the existing `line` wording in the v3 changelog.
