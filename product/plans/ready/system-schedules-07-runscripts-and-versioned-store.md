# System schedules 07: runscript files and versioned atomic storage

**Complexity: 5/10** — new file-backed services need strict decoding, atomic replacement, path containment, and target-repository Git exclusion.

Validated disk formats, atomic-write failure behavior and arbitrary-project Git exclusion are the substantive work. Scheduler timing, queue delivery and command/UI integration are outside this storage tranche.

## Goal

Provide pure runscript text parsing, project-root runscript lookup/catalog, and durable schedule-file storage for the owner introduced in plan 11. Source: `product/plans/ready/add-system-schedules.md`.

## Decisions and dependencies

- Dependencies: none in code; implement after 03–06 to keep the published sequence linear. Plans 03/04 establish the shell ensure/recovery seam, 05 adds client generation reporting, and 06 isolates profile handling.
- Runscripts live at `<project>/.janissary/scripts/<name>.rs`. A name matches lowercase alphanumeric words separated by single hyphens (`morning-checks`); reject empty names, separators, dot segments, spaces, uppercase variants, and an explicit `.rs` suffix. Resolve the implied extension against the project root, never a tab cwd/workspace. The allowlisted name grammar prevents traversal; also reject symlinks at `.janissary`, `scripts`, or the target `.rs` file rather than following them. Catalog only regular, non-symlink `.rs` files with valid names. Apply the same no-symlink rule to the schedule JSON path before reading or replacing it.
- Parse one complete command per physical line. Split LF and CRLF, ignore blank lines and lines whose first non-whitespace character is `#`, and preserve every other line's command text and inline shell comments (apart from the line terminator). Do not shell-parse, trim command lines, or join multiline constructs. Read the file afresh per request; an empty script is a valid no-op.
- Store schema v1 is `{ version: 1, entries: SystemScheduleEntry[] }`. `SystemScheduleEntry` extends the reused `ScheduleEntry` with an immutable opaque `key` and `script` name. The owner generates a collision-resistant key (use `randomUUID`) once and retains it across updates; `entry.id` remains the displayed/user-managed schedule name, so repeated names get separate keys. `command` is the descriptive invocation `script <name>`, never the expanded file contents. Persist raw `nextRun` and recurrence fields, not formatted display time.
- A missing schedule file loads as an empty v1 store. Malformed JSON and invalid v1 entries return a nonfatal load error, execute nothing, and remain byte-for-byte untouched on load; a later explicit valid save may replace them with a complete validated v1 snapshot. An unsupported version returns a distinct error and blocks writes, so an older process cannot downgrade a newer store; refuse saves both after an unsupported-version load and when the current destination decodes to an unsupported version. Decode only a non-array object with integer `version: 1` and an `entries` array. Each entry requires nonempty `key`, `id`, `command`, and `spec`, finite `nextRun`, and boolean `recurring`; keys are unique. A one-shot has no recurrence fields. A recurring interval has only a positive finite `intervalMs`; a recurring clock entry has only an integer `timeOfDay` hour (0–23) and minute (0–59), with optional integer weekday (0–6). `script` must be a valid runscript name and `command` must equal its descriptive `script <name>` form. Scripts need not exist at load time; missing-at-fire is an owner outcome in 11.
- Use synchronous `atomicWriteFile` for each complete-snapshot mutation. Create the parent directory before saving. Its same-directory temporary file and rename preserve the old destination on write/rename failure and clean up the temporary file; the store returns the failure and does not acknowledge a successful mutation. No pending/debounced write is needed. The owner in 11 serializes mutations; this store does not merge concurrent writers.
- The durable paths are `.janissary/system-schedules.json` and `.janissary/scripts/`, both outside the per-run directories. `clearStateDirectories()` takes no argument and runs every registered `clear` unconditionally, so do not register either durable path for clearing or rely on launch mode or the removed `always` field. This checkout's `.gitignore` ignores `.janissary/`, but `janus` also targets arbitrary projects and `scaffoldProject()` (`src/project/init.ts:61`, `scaffoldProject`) adds no ignore rule. Before the first save or script creation, ensure both paths are ignored: honor effective existing ignore rules; otherwise add narrowly repository-root-anchored entries for the project-root-relative paths to the target repository's local exclude file located with argument-safe `git rev-parse --git-path info/exclude` (run from the project root and resolve relative output against that directory). Resolve paths relative to the Git worktree root, including a project nested below that root, and preserve existing exclude content. Never edit the user's `.gitignore`. If the schedule file or scripts are already tracked, fail with a clear storage error rather than implying an exclude rule untracks them. For non-Git projects, skip Git configuration. Verify actual staging/ignore behavior with Git; the checkout's own ignore is not evidence for arbitrary projects. This is local user-authored execution with ordinary shell authority, not a workspace or an added sandbox.
