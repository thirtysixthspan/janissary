# ACP and agent record feeds, cancellation, and remote forwarding

**Complexity: 5/10** — upper-bound server integration: reuse the implemented recorder and activity protocol, add one cancellation/drain state machine, and bind tab/run ownership and first-outcome settlement across two transports; no new storage subsystem or UI.

## Goal

Feed each tracked core-tab ACP session and every `agent ... execute` run into durable connection records, including activity and final outcomes, and provide an ACP cancel path that works locally and remotely.

- Scope authority is `product/plans/ready/connections-tabs.md:24`, decision 6, and proposed change **Feeds** at line 85. The source remains 8/10. This is the second subplan on `feature/connections-tabs`, PR #1916.
- The dependency is implemented and reviewed: `product/plans/complete/connections-tabs-01-records.md`, commit `3db48d3`, followed by test-isolation repair `0c95b53`. Use `managers.acpRecords`; do not rebuild its APIs, alter its schema, or reopen the completed plan.
- Deliver decision 6's tracked consumers, decisions 16/19/21's feed metadata and statuses, decision 28's local/remote capture, decisions 11/30/37's cancellation and close semantics, and decisions 27/35's tab/run id ownership. Decisions 9–10, 12, 17, and 22 constrain these foundations: keep refusal semantics, existing retention, both headed/headless runs, and existing Terminate ownership. Async shell delivery, popup rows, topic actions, and controls themselves belong to downstream plans; this step does not claim to implement those whole decisions.
- Track every core tab ACP session, including plugin `startAcp`/`promptAcp`/`promptAcpResult` and the launcher's summarizer, plus every created `agent ... execute` run, local or remote, headed or headless, including nested runs. Conversations, monitors, and editor persona sessions remain separate, unrecorded consumers of the shared transport.
- Cancellation preserves the viable provider session, transient session identity, and record UUID. It aborts the host loop immediately, then settles the pending request once the old provider turn has drained. While draining, retain the existing pending request and refuse another prompt with `ACP: a prompt is already running.`. Do not report `Idle` or send another provider prompt while the old one is still active.
- Add only the client frame `acp-cancel`, addressed by the existing remote ACP transport id, and bump `REMOTE_PROTOCOL_VERSION` from 36 to 37. Existing `acp-end`/`acp-error` settle an outstanding remote provider turn; there is no new cancel acknowledgment, prompt queue, or record data on the wire.
- No dependency on the topic or connections plugin. Subsequent work can read `tab.runtime.acpRecordId`, `run.recordId`, retained record rows/windows, and invoke core `cancel`/`close` or existing agent `finish`.

## Feed and ownership contracts

### Core tab sessions

1. Add `src/acp/record-feed.ts` for recorder delegation, with no label-keyed map. Keep the durable id on the owning tab runtime. Capture that runtime object and the session generation in callbacks: tab records can be shallow-copied when another tab closes, while a new tab can reuse a label. A callback is current only when the current tab still has that runtime and the manager still owns that session generation.
2. Begin exactly once after a successful current handshake, at the same boundary that makes `AcpSessionManager.label` available. Copy `ownerLabel`, `title ?? label` as `ownerName`, and the configured provider/model string. Set `acpRecordId` before the connect hook emits state. Handle synchronous mocked connect/error hooks by deferring publication until the returned session is installed; a failed, closed, superseded, or closing owner cannot publish a late record or model label.
3. Reserve each logical request before launching its loop. Keep the stripped user prompt and optional bound record id on its `AcpPendingPrompt` state, defined in the new `src/acp/prompt-state.ts`. Usage/readiness/model/overlap refusals create no block and never answer the existing block. Once accepted, begin its block immediately if a record exists; otherwise the handshake feed starts that pending block before any update is recorded. Do not lose the first prompt or create a block per tool turn, cold-start retry, or primer.
4. `prompt`, `promptResult`, and callback-style `run` must share the same reservation/refusal path. `run` remains a void wrapper delivering the result through its callback; move its accepted-loop body to `src/acp/run-prompt.ts` so it cannot bypass pending ownership. Missing tabs return `Tab not found`. The public `session` transport accessor is not a separate logical feed ingress; production acquisition currently comes only from `start` and the prompt path.
5. Supply local `AcpOptions.onActivity` and remote `RemoteAcpHooks.onActivity` at acquisition in `session-manager.ts`, including sessions first acquired through `start`. Classify raw local updates with `acpActivity`; record remote `(kind, text)` directly. Record message text once from activity, not again from cumulative display chunks. Preserve whitespace chunks and all five kinds. Ignore bookkeeping, idle updates, and stale generations. Keep final native activity on the cancelling block until drain/settlement.
6. Preserve host tool interaction too: the extracted loop orchestration records the dispatched command and its returned result as ordered `tool` entries on the same block, separate from native ACP tool updates. Only current, unaborted requests may dispatch a host tool or publish its result. A tool rejection becomes the ordinary prompt error; it does not strand a block.
7. Extend `settleAcpPrompt` to answer only the pending request's bound record before resolving its caller. Store the exact reply for an answered result and the exact error line for an unanswered result, including `ACP: prompt cancelled.`, `ACP session closed.`, and prompt-level errors. Empty answers still settle. A prompt-level failure keeps its record open; a fatal connection failure settles first, then closes it as `Closed`.
8. `AcpSessionManager.close` owns closing/clearing the runtime's record id after request settlement and before killing/forgetting the transport. Reset, connection close, tab close, plugin failure, fatal error, and shutdown converge here. Repeated closes publish no second terminal mutation. Closing before handshake creates no record. A replacement gets a fresh UUID; a retained closed record is never reassigned to a reused tab label.

## Cancellation and transport contracts

### Shared admission and local transport

- Add required `AcpSession.cancel(): Promise<void>` in `src/acp/types.ts`. It marks cancellation synchronously and resolves after the notification write and the currently admitted provider request reach a terminal boundary. SDK 1.3.0's `ClientSideConnection.cancel` returns `Promise<void>` for sending a notification; it is not confirmation that generation stopped. The original `connection.prompt` completion is the drain boundary. The published 1.3.0 declaration was checked at `https://unpkg.com/@agentclientprotocol/sdk@1.3.0/dist/acp.d.ts`, identifier `ClientSideConnection.cancel`.
- Extract one framework-free `src/acp/prompt-control.ts` for single-provider-turn admission, cancellation state, and drain completion, used by both adapters. It owns its state on each session object, rejects overlap without overwriting handlers, and coalesces repeated cancels. During cancellation, hold the terminal callback until both the notification write and the original provider request have settled, then release the old turn before calling that handler. This ordering makes the far-side terminal frame a drain barrier and lets a handler synchronously start a follow-up without the old request's `finally` clearing its successor. With no active provider turn, cancellation is a no-op locally and sends no native notification that could cancel a later turn.
- `connectAcp` must check the admitted turn and killed/cancelled state after each handshake await and immediately before sending `connection.prompt`. Cancelling before handshake must not subsequently send the cancelled prompt. Finish initialization on the same viable session, publish its handshake/record, then report a synthetic cancelled terminal boundary for that unsent turn. Never send a cancel with an undefined session id or wait for the prompt response before sending a needed notification.
- For an already-sent turn, send SDK `connection.cancel({ sessionId })` and continue consuming the old prompt's terminal response. Final activity updates still belong to that turn. Native permission requests arriving after cancellation return the cancelled permission outcome. Do not mistake notification completion for drain, or route old chunks to new handlers.
- `AcpManager.cancel(label)` returns `Promise<boolean>`: false for no active logical request, true once an accepted request settles, including when reset/fatal closure wins the race. Normalize transport rejection through fatal settlement instead of leaking a rejected manager promise; concurrent calls share the same pending cancellation. Mark it on the pending request, abort its signal immediately, and retain that reservation while awaiting transport drain. Guard all loop handlers with request identity, session generation, and an unaborted signal. On successful drain, use `settleAcpPrompt` once with the unanswered result `ACP: prompt cancelled.`. An idle cancel is a no-op and does not create/start a session.
- Aborting cancels only this request's active/queued question through its signal. Already-running browser/database work is not generally abortable or reversible; cancellation suppresses its callbacks and all follow-up prompts, rather than claiming to undo its side effects. Do not call `questions.cancelTab`, which would cancel unrelated questions.
- Reset/Close wins if it runs while cancellation drains: settle immediately with `ACP session closed.`, close the record, and release the old drain waiter. The cancellation continuation checks its captured pending/runtime/session before doing anything. Fatal error likewise settles/closes once; a cancellation-send failure uses the existing fatal-close path with `ACP: cancellation failed: <reason>` and releases its reservation, rather than claiming the session is safely idle.
- There is no new cancellation timeout or forced process kill on a healthy session. An agent that never returns its original turn stays reserved/cancelling until reset, close, or fatal loss; ordinary commands remain independent. State is `Running` during this drain and `Idle` after successful cancellation settlement. Downstream UI must not promise that Cancel always completes instantly.

### Remote transport and loss

- In `createRemoteAcpSession`, mark the current turn cancelled before sending `acp-cancel`. Retain its routing until its old `acp-end` or `acp-error`; both fatal and nonfatal errors terminate that provider turn and clear it before callbacks. Keep a viable session attached after successful cancellation. A logical request waiting on a host tool can cancel with no provider turn active: send the addressed frame, then resolve without waiting for an end frame that cannot arrive.
- `RemoteServer.dispatch` must route `acp-cancel` to a new `RemoteAcp.cancel(id)` method. The decoder requires a nonempty string id, drops undeclared fields, and admits the new frame in `CLIENT_FRAME_TYPES`. A cancel for a missing, closing, or settled holder is a no-op; a live holder delegates to its session and catches rejection into a session-scoped fatal `acp-error`. It does not emit `acp-closed`, remove the holder, or affect another id sharing the channel.
- `RemoteAcp.prompt` continues to forward the original terminal callback even when a far-side local turn was cancelled before its handshake. That produces the existing `acp-end` with stop reason `cancelled`; it is not a second answer. No-prompt cancel requires no acknowledgment because the channel delivers the cancel frame before any later prompt, and the far-side session marks cancellation synchronously on dispatch.
- A detached/unavailable send must fail a pending cancellation instead of silently dropping it. Extract `RemoteChannel.send`'s existing unavailable-frame switch to `src/remote/channel/unavailable.ts`, including ACP cancel as a fatal session-local failure. Ensure explicit disconnect, transport loss before or after handshake, channel `fail`, and finish settle/detach all ACP listeners even when the channel cannot be reattached. Iterate a snapshot when callbacks can detach themselves.
- The remote adapter must release readiness/cancel waiters on fatal error, kill/release, and transport loss, with callbacks at most once. Core sessions currently supply no `onTransportLost`; wire a core fatal-close hook so a dropped transport cannot leave a pending prompt/record `Running` forever. Autonomous runs retain their existing transport-loss abort path. Late frames for a detached id are ignored; another tab/run sharing the channel is not closed merely because one ACP session failed.
- Do not change the remote sessions-tab restore/recovery policy. A tracked core ACP connection lost with its transport is closed locally; a later core request establishes a new ACP transport id/record after the channel is ready. Only the existing activity frames cross hosts; durable recording is owned by the initiating project's recorder, not by a second far-side recorder.
