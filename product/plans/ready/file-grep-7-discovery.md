## Proposed changes

- Export async `discoverGrepCandidates(target, include, exclude, signal)`. The first argument is the directly imported `GrepSearchTarget`; the second and third are strings, supplied from plan 1's `FileGrepArgs.include` and `.exclude`; the fourth is a required `AbortSignal` owned by plan 8. Its result remains `Promise<string[]>`, containing workspace-root-relative forward-slash paths, with an empty array for no candidates. Do not mirror the target type or accept plan 6's full `ResolvedGrepTarget`: plan 8 handles its `skip` and `failure` variants before this call. No deadline argument or optional injection parameter is added.
- For a directory target, call `listProjectFiles(target.searchDir)` on the parent thread, then pass that directory-relative list through the feature worker adapter. Do not list the workspace root and strip a prefix afterward: the selected directory is the git command's working directory and the fallback walk's root.
- For a file target, derive its parent and basename with native Node path helpers from `target.filePath`. List that parent, retain only entries exactly equal to the basename, then pass that selection through the same adapter. Never include a same-named descendant, a sibling or a direct-file shortcut. A named git-ignored file absent from a successful git listing stays absent even if include names it.
- Preserve `listProjectFiles` exactly: its git command uses cached plus others with exclude-standard, retaining tracked dotfiles and tracked files matching ignore rules, and excluding ignored untracked files. Any git invocation failure, not just being outside a repository, triggers its existing recursive fallback. That fallback skips entries named `.git`, `.svn`, `.hg`, `.DS_Store` or `Thumbs.db` at every level, includes `node_modules` and other dotfiles, ignores gitignore rules, and treats an unreadable directory as empty. Do not promise gitignore enforcement after git failure or add a hidden flag.
- Forward include/exclude unchanged to worker-owned `filterPaths`. Reuse its comma splitting and trimming, empty-field behavior, slash-free any-depth glob attempt, patterns containing a slash anchored to the listing root, plain-name directory expansion, backslash/leading-`./`/trailing-slash normalization and exclude precedence. These are the existing helper's exact Node `path.matchesGlob` rules, not a new glob grammar or validation pass; notably normalization occurs before the helper decides whether a pattern contains a slash. An unmatched bracket can match a literal filename, so do not reject a pattern merely because it looks malformed. Commas always split rather than introducing brace-list support. Preserve all extglob and wildcard behavior, with no complexity check, length cap, pattern rejection, new filter diagnostic or alternate matching engine.
- Only after filtering, prepend `target.prefix` and a forward slash when the prefix is nonempty; an empty prefix returns the listed relative path unchanged. The directory prefix names the selected directory, while a file prefix names its parent. Thus filters under `--path ./src/` see `commands/a.ts`, but output is `src/commands/a.ts`; single-file filters see only `a.ts`. Trust plan 6's normalized prefix rather than reconstructing it from typed `--path` or canonical absolute strings.
- Immediately after listing and the post-listing signal check, stable-deduplicate identical path strings, retaining each path's first occurrence before exact-file selection, filtering and prefixing. Real `git ls-files --cached --others --exclude-standard -z` can emit the same path three times for unmerged index stages 1, 2 and 3; forwarding all three would repeat every matching line and consume the limit incorrectly. Preserve order among distinct paths and do not sort again, case-fold, canonicalize aliases, limit candidates or compute totals. Keep `listProjectFiles` and all its other callers unchanged. Candidate listing may contain stale, symbolic-link or nonregular entries; it is not authorization to read them. Plan 4's reader performs policy, link, regular-file, byte-size and binary checks when plan 5 scans them. Plan 5 therefore receives one candidate per path and preserves one row per matching line in path-then-line order.
- Use `signal.throwIfAborted()` before listing, immediately after its await, immediately before starting the worker adapter and after its await before prefixing/return. The adapter also checks immediately before constructing its worker, closing the boundary between discovery and acquisition. An aborted discovery rejects with the exact `signal.reason`; a default `AbortController.abort()` supplies the standard `DOMException` named `AbortError`. Add no new cancellation error class or formatted result. Listing itself remains unabortable: if it settles after abort, its continuation cannot start filtering, create a worker or return candidates. An unexpected listing rejection remains its original rejection, observed by the caller's losing-promise handler when timeout already won.
- Add `src/file-grep/filter-worker.ts` exporting async `filterGrepPaths(paths, include, exclude, signal)`, taking a readonly string array, two strings and the required `AbortSignal`, returning `Promise<string[]>`. Empty paths or both exactly empty strings return a copied array after the signal check without a worker. Every other nonempty field, including whitespace/comma-only fields, goes to the unchanged helper in the worker. Parent work is limited to signal checks, linear deduplication/selection/prefixing, that empty-input fast path and worker transport/lifecycle; never call or precompile `path.matchesGlob` or `filterPaths` on the parent thread.
- Add `src/file-grep/filter-worker-protocol.ts` defining only `GrepFilterRequest` and `GrepFilterResponse`. The request carries selected-directory-relative `paths`, `include` and `exclude`; the response carries filtered `paths`. Use one request per new worker via `workerData` and one result message, so no request IDs, persistent pool or matcher protocol is needed. `src/file-grep/filter-worker-entry.ts` imports `filterPaths` directly, applies it once to that request and posts the response. It performs no listing, metadata, policy or content work. Uncaught filter errors reach the parent's worker `error` event rather than being converted to empty results.
- Treat entry-side `workerData` as `unknown` before any member access. A private `isGrepFilterRequest` guard in `filter-worker-entry.ts` reuses `isRecord` from `../value-guards.js` and validates a string array plus string `include` and `exclude` fields before invoking the helper; an invalid internal payload throws an ordinary worker error. Likewise keep `isGrepFilterResponse` private to `filter-worker.ts`, using `isRecord` and string-array validation. Neither guard parses or compiles user patterns. Do not use an unchecked cast, `any` assignment or mirrored protocol type to bypass the type-aware lint rules.
- Export `grepFilterWorkerEntry(moduleUrl)` from `filter-worker.ts`, accepting a module URL string and returning the adjacent `filter-worker-entry.ts` URL for a source `.ts` module or `filter-worker-entry.js` for compiled output. Instantiate `Worker` with that static module URL and `workerExecArgv(import.meta.url)` from `../search/matching-worker.js`. Do not use eval, user-controlled entry paths, cwd-relative loaders or the matching-specific `workerEntry`. Keep acquisition, response validation and settlement private to this adapter.
- The adapter validates its unknown message as a response containing an array of strings; a malformed message or an exit before a valid response rejects as an ordinary worker failure. Worker creation and `error` failures propagate unchanged; an ordinary helper/worker failure that wins before abort must reach the existing command/remote error handling, never become no matches, timeout or slow. Select the first result/error/abort once. Remove the abort listener and terminate the acquired worker exactly once on success, abort, error, invalid message or premature exit; observe termination rejection without replacing the selected outcome or leaving an unhandled rejection. Ignore all later values/errors, retaining a guarded worker error observer until exit so a late EventEmitter error cannot escape; release the remaining listeners when termination completes. Check an already-aborted signal before acquisition and recheck after installing the acquired worker's abort listener, so abort during construction also disposes it. Cleanup requests termination promptly and does not await worker shutdown before settling discovery, so a hostile synchronous glob cannot hold the parent hostage.
- Keep ordinary unexpected listing/filter failures as promise rejections; add no catch that turns them into empty candidates or a formatted diagnostic. The existing helper already owns its git failure fallback and unreadable-directory behavior. Empty or fully excluded listings simply return an empty array.
- Own no timer, new controller, content operation or transcript publication. Plan 8 creates a discovery-owned controller and wraps the entire four-argument discovery invocation in plan 5's `withDeadline` from `src/file-grep/deadline.ts`, using the unchanged absolute deadline from resolution and scan. On timeout, plan 8 fixes the timeout outcome first and then aborts that controller, so induced cancellation cannot replace timeout; it also aborts in its discovery cleanup on normal/error exits. The adapter's normal settlement already terminates its worker. No one-second filter budget applies: the existing one-second job limit belongs solely to content matching, while filtering consumes the original overall 30 seconds. A promise race alone cannot preempt synchronous Node glob evaluation; the worker boundary makes the parent's deadline/abort callbacks runnable. This handoff adds no dependency on plan 5 or plan 8 here and requires no shared listing/search change.
