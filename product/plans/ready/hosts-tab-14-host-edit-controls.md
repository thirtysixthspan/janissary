**Complexity: 6/10** — ~180 added production lines across 5 existing files, 11 requirements and 22 scenarios (p=6.437)

## Goal

Expose catalog creation, editing and confirmed deletion in the Hosts tab. Source plan: `product/plans/complete/hosts-tab.md`. Depends on `product/plans/ready/hosts-tab-13-host-edit-intents.md`.

## Implementation

In `web/src/plugins/hosts/HostList.tsx`, fill the header slot between Refresh and Split with a plus button named `New host`, including in the empty state. Follow the modifier checks and default suppression in `web/src/plugins/conversations/ConversationList.tsx:31` (`onKeyDown`) for `Cmd+N` and `Ctrl+N` when the list has focus. The row action slot gets a plugin-local `HostRowActions.tsx`. Use icon-only pencil and trash buttons with accessible names `Edit host <name>` and `Delete host <name>`. Follow the event propagation guard in `web/src/plugins/sessions/SessionRowActions.tsx:53` and the action styling in `web/src/plugins/sessions/sessions.css:42`. A button press leaves the selection unchanged and does not open the row. Keep the rules in the Hosts stylesheet and use ordinary button keyboard activation for these controls.

Build a plugin-local `HostForm.tsx` using `ModalDialog` and the raw-handler form of `useDialogKeyboard`. Publish both through `web/src/plugins/api.ts` with additive exports. `web/src/shared/ModalDialog.tsx:11` (`ModalDialog`) supplies the backdrop and markup. `web/src/shared/useDialogKeyboard.ts:27` supplies app-wide shortcut suppression and outside-click handling. Focus Name after the hook's mount effect focuses the container. Use a form titled `New host` or `Edit host <name>`, with four labelled inputs in Name, User, Destination, Path order and then Save and Cancel. Use `optional` for the User and Path placeholders and `host[:port]` for Destination. Create starts blank and Edit starts with the selected row's fields. Allow normal typing and Tab traversal inside the form, wrapping focus at its ends. Use native form submission for Enter in a field. Escape or Cancel dismisses the form before submission, with no intent sent. Keep fields, pending state and the inline error local to the form.

Request the `save` intent through `capabilities.intent<unknown>` with all four field strings and the original stored name for edits. Narrow the reply using `isSaveHostResult` from plan 13's shared contract. Disable Save and guard submission while the request is pending. Keep the form open until that request settles so cancellation cannot imply that an already dispatched write was withdrawn. Show a failure's returned message above the buttons, re-enable Save, and leave the field values intact. Show a rejected RPC's error inline as well, with `Could not save host.` for an invalid reply. The client capability throws for request rejection at `web/src/plugins/plugin-client-capabilities.ts:54` (`intent`). Validation stays on the server.

On success, close the form and notify `HostList` of the returned saved name. Resolve the name against the authoritative payload, using the exact returned spelling and supporting either arrival order of the save reply and the updated snapshot. Once the row exists, use the public `select` action from `web/src/shared/list-selection.ts:88` to highlight it, clear the Hosts list's prior click identity, and focus `listRef` if Hosts is active. Clear the pending focus target after applying it. Keep the current list rendering and selection rules from plan 11.

Use `ConfirmDialog` from the plugin API with title `Delete host <name>?` and `confirmLabel` set to `Delete`. The public component and `web/src/shared/ConfirmDialogShell.tsx:15` currently have no pending state. Add an optional `confirmDisabled` prop to both and have the shell apply it to the confirm button and the callback passed to `useConfirmDialogKeys`, covering mouse, `y` and Enter. Preserve the default behavior for existing callers. Before confirmation, Cancel dismisses the dialog without an intent. After confirmation, hold the dialog open while awaiting the `delete` intent to prevent a second deletion. Close on success, a handled refusal or request failure. The server publishes ordinary delete errors against Hosts. Keep rows driven by the authoritative payload throughout, including when deletion fails. Keep the form, row actions, list and styles within Hosts, using the published API for host-owned UI.
