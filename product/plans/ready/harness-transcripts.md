# Persist harness transcripts under .janissary/transcripts/harness/ with a configurable retention reaper

**Complexity: 7/10** — 25 requirements, 8 production files, ~18 test scenarios, ~75 added lines (p=6.90)

## Goal

The feature text: "every new harness tab should create a new file in .janissary/transcripts/harness/. The activity of the harness session should be continually appended to the file for the duration of the session. The harness transcript should persist for N number of days where N is determined by a new configuration flag in .janissary/config.json. A log reaper process that runs in the background on launch should be responsible for clearing out transcripts older than n days. harness transcripts should not be removed when the application is halted. harness transcripts should be tested and working with the harnesses for opencode, claude and codex. Prexisting code to save transcripts should be updated and used for the implementation of the current feature."

Today a harness tab's session transcript is written to `.janissary/harness-transcripts/` and the whole directory is deleted at every launch, so a session's history is lost as soon as Janissary restarts. This plan keeps harness transcripts across restarts for a configurable number of days, moves them under `.janissary/transcripts/harness/`, replaces the clear-at-launch sweep with a background reaper that removes only transcripts older than the retention window, and adds a switch to stop writing them at all.

## Requirements

1. A harness tab's transcript file is written to `.janissary/transcripts/harness/<label>-<timestamp>.txt` ("every new harness tab should create a new file in .janissary/transcripts/harness/").
2. Each harness tab writes its own new file, never one shared with or reused from another tab ("every new harness tab should create a new file").
3. Every entry the session produces is appended to the file for the life of the tab ("continually appended to the file for the duration of the session").
4. `.janissary/transcripts/harness/` is not cleared at launch ("should persist for N number of days").
5. No harness transcript is deleted when the application stops ("harness transcripts should not be removed when the application is halted").
6. `.janissary/config.json` gains a `logRetentionInDays` setting (user answer: "logRetentionInDays").
7. `logRetentionInDays` defaults to `7` (user answer: "7 days").
8. A `logRetentionInDays` of `0` makes the launch sweep delete every harness transcript last modified before launch (user answer: "0 = delete at launch").
9. A `logRetentionInDays` that is negative, fractional, or not a number falls back to `7` (user answer: "Other invalid values fall back to 7").
10. `.janissary/config.json` gains a `logEnabled` boolean setting defaulting to `true` (user answer: "add an additional parameter logEnabled that defaults to true").
11. A `logEnabled` that is not a boolean falls back to `true`, as every boolean setting does.
12. With `logEnabled` false, no harness transcript file is written (user answer: "when false, prevents harness transcripts being recorded at all"; "File only").
13. With `logEnabled` false, monitors still receive the harness tab's transcript entries (user answer: "Monitors keep receiving transcript entries in memory").
14. With `logEnabled` false, `harness transcript <name>` reports `No transcript available for "<name>" yet.` (user answer: "File only").
15. A config file that predates either key gains it, with its default, the next time it is loaded, preserving every other key (user answer: "Backfill both keys").
16. A failed backfill write is silent and the session still uses the decoded settings.
17. Once per launch, a background sweep deletes harness transcripts whose last-modified time is more than `logRetentionInDays` days before launch ("A log reaper process that runs in the background on launch"; user answers: "Last modified", "Once per launch").
18. The sweep runs whether `logEnabled` is true or false (user answer: "Yes, still reap").
19. The sweep never delays startup: boot starts it and continues to start the server without waiting for it.
20. The sweep never deletes a file last modified at or after launch, including when `logRetentionInDays` is `0`.
21. The sweep deletes only regular `*.txt` files directly inside `.janissary/transcripts/harness/` (user answer: "Old .txt files").
22. The sweep never removes subdirectories or files with other extensions in that directory (user answer: "Subfolders and other files are never touched").
23. A missing or unreadable `.janissary/transcripts/harness/` directory makes the sweep a no-op.
24. A file whose stat or delete fails is skipped silently, and the sweep continues with the rest (user answer: "A failed stat or delete skips that file silently").
25. The legacy `.janissary/harness-transcripts/` directory is no longer created, written, or cleared (user answer: "Ignore it").

## Design decisions

- Keep lazy file creation in `HarnessTranscriptTailer`; only the directory moves (user answer: "Lazily, first entry"; Assumption 2).
- Name the settings `logRetentionInDays` and `logEnabled` even though they govern only harness transcripts in this version (user answers: "logRetentionInDays"; "Harness transcripts only").
- Decode `logRetentionInDays` with a new non-negative-integer decoder so `0` is a valid value while negatives and fractions fall back to `7` (user answer: "0 = delete at launch"; Existing functionality 4).
- Measure a transcript's age by its file mtime (last append), not by the timestamp in its name, so a long-running or recently ended session is never reaped mid-use (user answer: "Last modified").
- Fix the sweep's cutoff at launch time minus `logRetentionInDays` days and delete only files whose mtime is strictly before it. That is what keeps a file the current run creates from ever qualifying, `0` included (Requirements 8 and 20).
- Sweep once per launch, not on a recurring timer, so an instance left running for days keeps files older than N days until the next launch (user answer: "Once per launch"). Ceiling: retention is enforced only at launch. Upgrade path: call the same wrapper again from an unref'd daily interval started beside it in `main.ts`, with no change to the reaper.
- Put the sweep in a generic module, `src/state/reaper.ts`, that takes a directory, an extension, and a cutoff (user answer: "Generic reaper module").
- `src/harness/transcript-file.ts` owns the harness call into the reaper through a `reapHarnessTranscripts(launchedAt, days)` wrapper, so the directory path and retention arithmetic stay with the directory's owner (user answer: "transcript-file.ts wrapper").
- `src/main.ts` starts that wrapper once, right after `clearStateDirectories()`, without awaiting it and with a rejection handler that swallows, so boot never waits on or crashes from the sweep (user answer: "transcript-file.ts wrapper"; Requirement 19). It reads the retention from the `Config` that `loadConfig(cwd)` already returns, so `main.ts` gains no new config import (Assumption 6).
- `src/harness/transcript-file.ts` imports from `src/state/reaper.ts`, and the reaper imports nothing from `src/harness/`, so the existing `src/state/dirs.ts` → `src/harness/transcript-file.ts` import does not become a cycle.
- Use `node:fs/promises` in the reaper so the sweep yields to the event loop instead of blocking startup (Requirement 19).
- Gate only the file write on `logEnabled`. `harnessRuntime()` reads `getConfig().logEnabled` and passes it to the `HarnessTranscriptTailer` constructor as a `persist` flag; the tailer skips opening its file when the flag is false, still accumulates entries for monitors, and stays free of config reads (user answers: "File only", "Constructor flag").
- Stop clearing harness transcripts at launch by removing the `clear` from the `harnessTranscript` registry entry, the way `remoteSessions` and `notificationRecord` are kept across launches (Assumption 3).
- Leave `.janissary/harness-transcripts/` from older versions untouched, with no migration and no clearing (user answer: "Ignore it"). Ceiling: files an older version wrote there stay until the user deletes them. Upgrade path: a clear-only `STATE_DIRECTORY_ENTRIES` entry for the legacy path.
- Replace `backfillMaxToolTurns` with one `backfillMissingKeys(parsed, defaults)` over a fixed list of `maxToolTurns`, `logEnabled`, and `logRetentionInDays`, keeping `loadConfig`'s single write path (user answers: "Backfill both keys", "Generalize existing").
- Prove claude, codex, and opencode support by a manual run of each harness in Verification, relying on the existing per-harness source tests for parsing (user answer: "Manual run only").
- Record the user documentation update as a follow-up feature candidate, not as part of this plan. User and developer documentation is owned by `update-documentation.md`, not by a feature PR or plan (user answer: "Prose page candidate").

## Preserved behavior

1. `harness transcript <name>` opens the tab's own transcript file in an editor once the tailer has written one. It must not report `No transcript available for "<name>" yet.` while a file exists, and must not open a file from another tab or an earlier run. Test: `src/harness/manager.test.ts` "opens the transcript file in the editor once one exists".
2. Before the tailer has written a file, `harness transcript <name>` reports `No transcript available for "<name>" yet.`. It must not open an empty or missing file. Test: `src/harness/manager.test.ts` "reports no transcript before the tailer has written a file".
3. The harness tab's 📋 button opens the tailer's transcript file. It must not fall through to the tab record or open nothing while the tailer has a file. Test: `src/controller/transcript.test.ts` "opens the tailer's transcript file in an editor tab".
4. The transcript file is created lazily on the first entry. A tab that produces no entry must not leave an empty file in `.janissary/transcripts/harness/`. Test: `src/harness/transcript/tailer.test.ts` "creates no file and holds no entries before the first record".
5. When no session record is found within the deadline, `no harness transcript found` is notified once for the tab. It must not be repeated, and it must not fire for a tab whose source resolved. Test: `src/harness/transcript/tailer.test.ts` "notifies exactly once at the resolve deadline and stops polling".
6. Monitors watching a harness tab receive its accumulated transcript entries. They must not fall back to screen snapshots for a tab whose tailer has entries. Test: `src/monitor/harness-transcript-feed.test.ts` "feeds a harness target its accumulated transcript entries as one block".
7. Captures, recordings, `.janissary/shell-transcripts/`, browser logs, git-failure output, the workspace directory, and the remote file cache are still cleared at every launch. None of them may lose its clear, and only the harness transcript entry may stop being cleared. Test: `src/state/dirs.test.ts` "clears every entry with a clear on every launch".
8. A remote harness tab's transcript blocks, pushed from the far side, reach the local tailer, which writes them locally. A remote tab must not be left without a local transcript. Test: `src/remote/transcript-source.test.ts` "hands the pushed blocks to the next poll".

## Implementation steps

1. **Config settings.** In `src/config.ts`, add `logEnabled: boolean` and `logRetentionInDays: number` to `Config`, a `DEFAULT_LOG_RETENTION_IN_DAYS` constant of `7`, and both defaults to `DEFAULT_CONFIG`. In `src/config-decode.ts`, add a non-negative-integer decoder beside `positiveIntegerValue` that accepts `0` and any positive whole number and falls back otherwise. Decode `logRetentionInDays` with it and `logEnabled` with `booleanValue`. Replace `backfillMaxToolTurns` with `backfillMissingKeys(parsed, defaults)`, which fills every missing key of the fixed list (`maxToolTurns`, `logEnabled`, `logRetentionInDays`) from the defaults and returns undefined when none is missing. Point `loadConfig` at it (`src/config.ts:132`). The write path, notification stripping, and silent failure stay as they are. In `src/config.test.ts`, change the fixture of "honors an explicit max tool turns and does not rewrite the file" to carry all three keys so it still proves a complete file is not rewritten, and change the expectation at the "strips a legacy notifications section" test to include `logEnabled: true` and `logRetentionInDays: 7` (Assumption 9). Build command: `$janissary/scripts/run.mjs check-diff`.
2. **Generic reaper.** Add `src/state/reaper.ts` exporting an async function that takes a directory, a file extension, and a cutoff in epoch milliseconds. It lists the directory's direct entries with file types, and for each regular file whose name ends with that extension and whose mtime is strictly before the cutoff, it deletes the file. It uses `node:fs/promises`. A directory that cannot be listed (missing or unreadable) resolves without doing anything. A failed stat or unlink skips that entry and continues, and the function never rejects. Add `src/state/reaper.test.ts` against a real temporary directory, aging files with `utimes`. Build command: `$janissary/scripts/run.mjs check-diff`.
3. **Move the directory and stop clearing it.** In `src/harness/transcript-file.ts`, change the directory to `.janissary/transcripts/harness`. Remove `clearHarnessTranscriptDirectory`, and add `reapHarnessTranscripts(launchedAt, days)`, which computes the cutoff as `launchedAt` minus `days` whole days and calls the reaper with its own directory and `.txt`. Rewrite the file's header comment, which describes the clear-at-launch policy, to state the retention policy. In `src/state/dirs.ts`, drop the `harnessTranscript` entry's `clear` and keep its `init`, with a comment matching the `remoteSessions` one on why it has no clear. Update `src/state/dirs.test.ts` so the clear assertion no longer expects the harness transcript clear, and asserts that it is absent. Update `src/harness/transcript-file.test.ts`: change the path expectation, delete the `clearHarnessTranscriptDirectory` describe block, and add wrapper tests that mock `../state/reaper.js`. Remove the `clearHarnessTranscriptDirectory` mock from `src/state/dirs.test.ts`. In `src/main.ts`, keep the `Config` returned by `loadConfig(cwd)`, and after `clearStateDirectories()` start `reapHarnessTranscripts(Date.now(), <that config>.logRetentionInDays)` without awaiting it, attaching a rejection handler that ignores the error. Fix the path in the comments of `src/harness/transcript/tailer.ts` and `src/shell/transcript/transcript-file.ts`. Build command: `$janissary/scripts/run.mjs check-diff`.
4. **`logEnabled` gate.** Give `HarnessTranscriptTailer`'s constructor a `persist` boolean. When it is false, `append` still accumulates entries but never opens a file, so `transcriptFile()` stays undefined. Make `persist` the constructor's last parameter so the existing three-argument calls in `src/harness/transcript/tailer.test.ts` only need the new argument appended. In `src/harness/observers.ts`, `harnessRuntime()` imports `getConfig` from `../config.js` and passes `getConfig().logEnabled`, the way `src/tab/manager.ts:247` reads `getConfig().recordShellTabs` when it builds a shell tab's observers. ## Out of scope

- Shell-tab text transcripts (`.janissary/shell-transcripts/`), recordings, captures, and the daily activity log (`.janissary/log/`) keep their current behavior; `logEnabled` and `logRetentionInDays` do not govern them (user answer: "Harness transcripts only").
- No recurring sweep while the app runs; reaping happens once per launch (user answer: "Once per launch").
- No migration or cleanup of a legacy `.janissary/harness-transcripts/` directory (user answer: "Ignore it").
- No runtime command to change either setting; the user edits `.janissary/config.json`, and a change takes effect for tabs opened after the next launch.
- No new automated end-to-end test launching the real harness binaries (user answer: "Manual run only").
- Documentation follow-up feature candidate: update the user documentation's harness transcript section (path `.janissary/transcripts/harness/`, retention by `logRetentionInDays`, `logEnabled`) and the configuration reference. ## Verification

1. `$janissary/scripts/run.mjs check-diff`
2. **Each harness writes a persistent transcript.** In a scratch project, launch Janissary, open `harness claude`, `harness codex`, and `harness opencode`, and send each one prompt. Within a few seconds of each reply, `.janissary/transcripts/harness/` holds one `<label>-<timestamp>.txt` per tab, and `harness transcript <label>` opens it. Quit Janissary and relaunch it in the same project: all three files are still there, unchanged. A failure looks like a missing file for any of the three, a file under `.janissary/harness-transcripts/`, or files gone after the relaunch.
3. **The sweep ages files out.** With Janissary stopped, backdate one transcript by ten days (`touch -t` with a date ten days ago) and leave the others. Relaunch with the default config: within a few seconds the backdated file is gone and the others remain, and the UI opened without waiting. Set `"logRetentionInDays": 0` and relaunch: every file from earlier runs is deleted, and a harness opened in this run still gets a file that survives until the next launch. A failure looks like the backdated file surviving, a current file deleted, or startup stalling.
4. **`logEnabled` off.** Set `"logEnabled": false`, relaunch, open `harness claude`, and send a prompt. No new file appears in `.janissary/transcripts/harness/`. `harness transcript claude` reports `No transcript available for "claude" yet.` A `monitor` on the tab still receives transcript entries. A failure looks like a new file being written or the monitor receiving only screen snapshots. Backdate one older transcript by ten days and relaunch with `logEnabled` still false: the backdated file is still deleted (Requirement 18).
5. **Backfill.** Remove both keys from `.janissary/config.json` and relaunch: the file now holds `"logEnabled": true` and `"logRetentionInDays": 7`, with every other key unchanged.
