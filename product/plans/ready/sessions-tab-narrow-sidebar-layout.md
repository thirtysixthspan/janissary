# Separate layout for the sessions tab in a narrow-width sidebar

**Complexity: 3/10** — one plugin's client-side rendering: a derived boolean, an extracted row module, a scoped CSS variant, and two colocated test files. No server code, no protocol, no persistence, no new state. What makes it a 3 rather than a 2 is that the narrow variant has to override three declarations the existing shared `.session-columns, .session-row` rule sets (`display: grid`, `white-space: nowrap`, `align-items: baseline`) and suppress the existing joined-row cell indent, and that `sessions-style.test.ts` pins the current stylesheet by source text, so a careless edit to an existing rule breaks tests rather than just the layout.

## Summary

The sessions tab can already be docked — `sessions left` and `sessions right` put it into a sidebar, and the manifest carries `dockTab` — but it renders the same six-column grid there that it renders across the full centre pane. Those tracks (`minmax(0, 1fr) 6em minmax(0, 1.5fr) 8em 8em 6em` plus five 12px gaps) need roughly 40em before anything has room; a sidebar clamped to a minimum width and typically opened far narrower than half the viewport cannot give them that. The result is a host column ellipsed to nothing, a `Last activity` column colliding with the action buttons, and rows that no longer read as rows.

This feature gives the sessions tab a second rendering of the same data, laid out for a narrow column, the way the schedules tab already carries a full and a compact rendering of its list. The narrow rendering stacks each session onto two lines instead of compressing it into fewer columns, so nothing a session row carries is dropped from the surface.

## Design decisions established by existing behavior

These are facts the codebase already fixes; they are not open questions.

1. **The tab is already dockable and the docking already works.** `sessions left`/`sessions right` dock it, a bare `sessions` on a docked list returns it to the centre, and any other argument is rejected with `Usage: sessions [left|right]` (`product/specs/sessions-tab.md`). The plugin manifest already declares `dockTab` (`src/plugins/sessions/manifest.ts`). No command, manifest, capability, or protocol change is in this feature.

2. **The host already tells the plugin where it is.** `TabPluginClientCapabilities.dock` is `'left' | 'right' | null`, and its contract comment says in so many words that "a plugin that lays itself out differently in a narrow sidebar reads it here rather than measuring the host's frame or sniffing its DOM" (`web/src/plugins/api.ts:60-63`). Nothing new has to be published to read the placement.

3. **The split control already disappears when docked.** `DockedPluginBody` passes no `onSplit`, so `PluginBody` builds `splitAction` as `null` (`web/src/plugins/PluginBody.tsx:138,155-158`). A docked sessions header therefore already carries Refresh alone; the narrow layout does not have to hide the split button, because the host never hands it one.

4. **The host draws the dock-cycle control, not the plugin.** `DockedPluginBody` renders `DockCycleHeader` above the plugin body. The narrow layout renders nothing of its own for cycling sides, exactly as the schedules tab does not (`product/specs/scheduling.md`).

5. **Sidebar width is user-draggable, ephemeral, and clamped.** It is clamped to a minimum and to roughly half the viewport, resets on relaunch, and is never persisted or sent to the server (`product/specs/sidebars.md`). The narrow layout therefore cannot assume one fixed width — only that the column is narrow and can be dragged wider or narrower at any moment.

6. **Everything the list *does* is placement-independent.** Selection, single-click-then-second-click-to-open, Enter, Up/Down/Home/End without wrapping, the refresh-on-becoming-active effect, the detach/terminate confirmation dialogs, and every row action and its enablement rule live in `SessionList.tsx`, `SessionRowActions.tsx`, and the pure helpers in `sessions-keys.ts`, and are not layout concerns. The narrow rendering changes what is drawn, never what a gesture means.

7. **The state cell reads as its plug and then its word.** The spec fixes this and gives the reason: the colour carries at a glance, and the word is what keeps `detached` apart from `reconnecting` and `provisioning`, which the palette alone does not (`product/specs/sessions-tab.md`). The narrow layout keeps both — it is not free to drop to a plug alone.

## Design decisions settled in this plan

1. **Dock placement is the switch.** The narrow rendering is chosen by `capabilities.dock !== null` and nothing else — the same test the schedules tab makes. A docked list is narrow-rendered at every sidebar width, including one dragged out toward half the viewport; a centre-strip list is wide-rendered even when the centre is split into two panes. No element measurement, no `ResizeObserver`, no pixel threshold: placement is host-owned and already published (established decision 2), and a layout that flips mid-drag is worse than one that is predictable from where the tab sits.

2. **A narrow row is a two-line stacked block, not a compressed line.** The primary line carries the tab's name with the row's action buttons right-aligned. The secondary line, muted and smaller, carries the connection plug, the state word, the host, and the relative activity, in that order. Nothing a row carries is dropped from the surface: the sessions tab exists to answer "what am I running on other hosts", so a rendering that pushes Host into a tooltip loses the question the tab was built for. Giving the buttons a line to themselves is also what keeps them from colliding with a long tab name in a column this narrow. This departs from the schedules tab's single compressed line deliberately — a session row carries five fields and up to three buttons where a schedule row carries three fields and none.

   The row's `Type` (`harness`, `agent`, `ssh`, `navigator`) is the one field with no place of its own in the two lines. It is not dropped: it stays in the row's tooltip, alongside the destination, workspace, and failure reason the tooltip already carries.

3. **No heading band when narrow.** Headings describe columns, and a stacked block has none to describe, so the narrow rendering draws no heading row at all. This is the same reasoning the spec already applies to the empty list, which "omits the table headings because there are no rows for them to describe". The wide rendering's six-column heading band is unchanged.

4. **Grouping is the whole block indented.** A joined row's entire two-line block shifts right by the same 16px the joined row's host cell shifts today, rather than the indent living on one cell. The rule the indent expresses is unchanged — a group stays together wherever its launching row sorts, so one glance shows what a single detach would take with it — and the host still appears on a joined row's secondary line, because in a stacked block it is the block, not an empty leading cell, that carries the grouping.

5. **The narrow layout wraps; it does not truncate.** When the secondary line will not fit, it wraps onto further lines rather than ellipsizing, so a session's host and activity stay readable at the minimum sidebar width. Row heights therefore vary, which the layout accepts as the cost of hiding nothing.

6. **Wrapping moves whole fields.** The secondary line's three chunks — plug-plus-state-word, host, activity — are each unbreakable, and the line wraps between them. A wrap never splits `reconnecting` or a hostname in half, and the plug never separates from the state word it colours, since established decision 7 is that the two are read together.

7. **A field wider than the line is the single exception, and it ellipsizes.** A hostname longer than the sidebar itself has nowhere to wrap; rather than spilling out of the sidebar or being clipped without a marker, that field ellipsizes. The full destination is in the row's tooltip, so nothing is unreachable. This is the only truncation anywhere in the narrow layout.

8. **The tab name ellipsizes.** The primary line stays exactly one line: a long tab name truncates with an ellipsis rather than wrapping, so the row's identity line and its action buttons keep a predictable height and the buttons never move. This is the same treatment `.session-row-name` already gets in the wide layout.

9. **Every action the row offers stays visible.** `SessionRowActions` is reused unchanged in the narrow layout: same icons, same disabled rules (detach while provisioning, terminate and attach while terminating), same `<verb> <name>` accessible labels. The widest case a row can present is three buttons — attach, terminate, and forget on a parked row whose last attempt failed — which fits the primary line beside an ellipsized name. Nothing is revealed on hover, and nothing collapses into an overflow menu: the spec's promise is that a row offers what it can actually do and nothing else, and hiding a destructive verb behind a gesture or an extra click contradicts it.

10. **A hairline divider separates narrow rows.** Each narrow block carries a 1px bottom border in the existing `--border` colour. With variable heights, whitespace alone stops reading as a boundary — a three-line block and the two-line block below it blur into one. The wide rendering needs no divider, because its fixed-height rows already align into columns, and gains none.

11. **The header band is unchanged when docked.** `.session-list-header` keeps its 28px band, its 12px horizontal padding, and its bottom border. It already reduces to Refresh alone with no work (established decision 3), and the host's dock-cycle control sits above it as it does for every docked plugin.

12. **No new user-visible text.** `No remote sessions` stays the empty state; the state words stay `provisioning`, `active`, `reconnecting`, `detached`, and `terminated`; the relative activity keeps its `just now` / `2m ago` / `3h ago` / `5d ago` wording from `relativeActivity`; the action tooltips and accessible labels stay as `SessionRowActions` writes them; and the confirmation dialogs keep their existing titles. The narrow layout re-arranges what the wide one already says and adds no string of its own, so no connection state is ever named two different ways depending on where the tab sits.

13. **The narrow rendering is private to the sessions tab.** Its components and CSS live in `web/src/plugins/sessions/`. The schedules and audio tabs each carry their own docked variant privately today; a third private one is the honest precedent. Nothing is extracted into `web/src/shared/` or added to the published plugin API, and the schedules tab is not moved onto a shared helper.

## Proposed changes

Depends on no other plan, and lands as one change: §1 and §2 are a single extraction-plus-rewire that does not typecheck half-done, §3 is inert until §2 applies the class, and §4–§5 are prose.

`SessionList.tsx` is 161 raw lines, which `max-lines` counts as 141 — the rule is `['error', { max: 200, skipBlankLines: true, skipComments: true }]` (`eslint.config.mjs:86`), so the file is not near the limit and the extraction below is not forced by it. The nearest precedent argues against extracting: `SchedulesTab.tsx` holds its tab component and all four of `FullHeadings`, `CompactHeadings`, `FullRow`, and `CompactRow` in one 171-line file. Extract anyway, deliberately, for two reasons. Both renderings inline would land `SessionList.tsx` around 175 counted lines — legal, but with roughly 25 lines of headroom in the file that is this plugin's centre of gravity, so the next change to the list forces the extraction under time pressure instead. And the split is the right one on the modularization guidance in `ai/guidelines/code-guidelines.md` ("a file should have one clear responsibility"): the list owns selection, focus, intents, and the confirmation dialog, while the new module owns nothing but how one row is drawn. Keep both renderings together in that one module rather than extracting only the narrow one — side by side is what makes the two easy to keep in step, which is the part of the schedules precedent worth copying.

1. **A new `web/src/plugins/sessions/SessionRowBody.tsx`.** Two sibling components, `WideSessionRow` and `NarrowSessionRow`, taking the same props — the `SessionRow`, the `now` timestamp the list computes once per render (`SessionList.tsx:88`, `const now = Date.now()`), and the `onAction` callback the list already hands `SessionRowActions` — and differing only in what they draw inside the row element. `WideSessionRow` renders today's six children (`.session-row-host`, `.session-row-kind`, `.session-row-name`, the `.session-row-state` span wrapping `<ConnectionPlug>` plus the state word, the `.session-row-activity` `<time>`, and `SessionRowActions`) moved out of `SessionList.tsx:134-144` verbatim, with the same class names and the same `dateTime={new Date(row.activity).toISOString()}`. `NarrowSessionRow` renders two wrapper elements: a primary line holding `.session-row-name` and `SessionRowActions`, and a secondary line holding the same `.session-row-state` span, `.session-row-host`, and `.session-row-activity` `<time>`. Reusing those four class names verbatim is what lets the existing colour rules (`sessions.css:30-41`) apply unchanged in both renderings. Both components render `SessionRowActions` with identical props, so decision 9 holds by construction rather than by duplication. Neither owns state, a ref, or an effect.

2. **`SessionList.tsx` picks a rendering and stops drawing cells.** It gains one derived boolean from `capabilities.dock !== null` — the same test `SchedulesTab.tsx:27` makes (`const compact = capabilities.dock !== null`) — adds `session-list-narrow` to the root element's class when it is true, renders the `.session-columns` heading band only when it is false (decision 3, composed with the existing `payload.entries.length > 0` condition at `SessionList.tsx:106`), and delegates each row's children to the component from §1. The row element itself keeps its existing `className`, `data-index`, `data-state`, `role`, `tabIndex`, `title`, and `onClick` exactly as they are — the narrow variant is scoped through the root class, so no per-row modifier is needed and the tests that query `.session-row` by state and position keep working. Everything else in the file is untouched: the selection state, the two effects that clamp and scroll the selection (`:45-57`), the focus-and-refresh effect (`:37-43`), `raise`/`request`/`open`, `onKeyDown`, the click handler, and the `ConfirmDialog`. The `title` template at `:125` gains the row's `kind` (decision 2), which is the file's only content change — added unconditionally, in both renderings, rather than only when narrow. The wide rendering then names the type twice, in its column and in its tooltip, which is harmless; one template that always says the same thing is smaller and less breakable than a tooltip whose contents depend on where the tab is docked.

3. **`sessions.css` gains a narrow variant, scoped under `.session-list-narrow`, and edits no existing rule.** In the shape `schedules.css:39-41` already uses for its compact variant. Three declarations in the shared `.session-columns, .session-row` rule (`sessions.css:18-21`) actively fight a stacked block and must each be overridden in the narrow scope, not edited in place: `display: grid` with the six tracks (the narrow row is a block, not a grid), `white-space: nowrap` (decision 5 needs the secondary line to wrap), and `align-items: baseline`. A fourth collision is the joined indent: `.session-row.joined .session-row-host { padding-left: 16px; }` (`:29`) would indent the host *inside* an already-indented block, so the narrow scope both indents the block (decision 4) and zeroes that cell's padding — `.session-list-narrow .session-row.joined .session-row-host` outranks it on specificity, so the existing rule stays untouched. The rest of the variant: the primary line lays `.session-row-name` against right-aligned actions, with the name's existing `overflow: hidden; text-overflow: ellipsis` (`:31`) given a shrinkable, bounded box so it actually ellipsizes (decision 8) and `.session-row-actions`'s existing `flex-shrink: 0` (`:42`) keeping the buttons at full size; the secondary line is a wrapping flex row (decision 5) whose three children are each individually unbreakable (decision 6) and each fall back to `.session-row-host`'s existing ellipsis treatment (`:30`) when one alone exceeds the line (decision 7); and each block carries a `1px` bottom border in `var(--border)` (decision 10). The `data-state` colour rules (`:38-41`), the `.session-row-state` plug-and-word layout (`:35`), the hover and selected backgrounds (`:25-26`), and the header rules are all reused as they stand. Because nothing existing is edited, every assertion in `sessions-style.test.ts` — including the exact-string matches at `:53-58` and the `grid-template-columns` regex at `:64` — keeps passing unchanged, and that is the point of scoping rather than editing.

4. **Spec: `product/specs/sessions-tab.md`.** The "Row content" section gains a paragraph in the shape of the scheduling spec's "two renderings of the same data" (`product/specs/scheduling.md:49`): the five-column table is what the centre area shows, and a docked list stacks each session onto two lines — the tab's name with its actions, then the plug, state, host, and last activity — with no column headings, the whole block indented for a joined row, the secondary line wrapping rather than truncating at a narrow width, and the type moving into the tooltip. It also records that the rendering follows the tab's placement, not its measured width. The existing sentence "The list header is a full-width metadata bar … containing only Refresh and Split controls together at the right edge" gains the docked case: a docked list's header carries Refresh alone, because the host supplies no split control to a docked tab.

5. **Docs: `documentation/user-documentation/tab-types/sessions.md`.** One sentence added to the existing docking paragraph at `:13` (the one already naming `sessions left` and `sessions right`), saying a docked list stacks each session onto two lines so it reads in a narrow sidebar. No new screenshot, no `data-doc-shot` hook, no new page.

## Tests

Colocated, following the conventions already in this directory — `SessionList.test.tsx` renders the list with a stub `TabPluginClientCapabilities`, and `sessions-style.test.ts` asserts the stylesheet's source text rather than rendered geometry (jsdom computes no layout, so a wrap or an ellipsis can only be pinned as CSS source).

The stub at `SessionList.test.tsx:8-20` hardcodes `dock: null`, and `list()` at `:31-33` takes a whole capabilities value. Give `capabilities()` an optional dock argument defaulting to `null` rather than writing a second stub, so every existing call site is unchanged and a docked test reads `list(entries, capabilities('left').value)`.

- **`web/src/plugins/sessions/SessionList.test.tsx`** — extended with a docked group: a list rendered with `dock: 'left'` draws no `.session-columns` band while the same payload with `dock: null` still draws all five headings (the existing test at `:60-66`); a docked row exposes the name, the state word, the host, and the activity text, so decision 2 is asserted by content rather than by class; the type is absent from a docked row's text and present in its `title`; every action button a row offers is still rendered and still carries its `<verb> <name>` accessible label when docked, including the three-button parked-and-failed row and the two disabled cases (`detach` while `provisioning`, `terminate`/`attach` while `terminating`); the docked empty state still reads `No remote sessions` and still draws no headings; and a joined row still carries the `joined` class when docked. The existing wide-layout, selection, keyboard, click-to-open, and confirmation tests keep `dock: null` and are therefore unaffected by the extraction — which is itself worth confirming, since §1 moves the markup those tests query. One new test pins decision 6 directly: the same arrow-key and second-click sequences select and open the same rows with `dock: 'left'` as with `dock: null`.
- **`web/src/plugins/sessions/sessions-style.test.ts`** — extended with assertions for the narrow variant's source text: every new rule's selector begins with `.session-list-narrow`, so the wide grid cannot have been edited; the narrow row overrides all three of `display`, `white-space`, and `align-items`; the secondary line declares wrapping and its children declare no-wrap; the joined rule both indents the narrow block by 16px and zeroes `.session-row-host`'s padding, so the indent cannot double; and each narrow block declares the `var(--border)` bottom border. The existing assertions stay byte-for-byte, which is what pins "no existing rule is edited" — in particular `:53-58`'s exact-string matches on the shared grid rule and `:64`'s `grid-template-columns` regex.
- No new test file: `SessionRowBody.tsx` is exercised through `SessionList`, matching how `SessionRowActions.tsx` is tested today (it has no colocated test of its own; its buttons are asserted from `SessionList.test.tsx:138,163`).
- No server-side test changes: nothing under `src/` moves, and `SESSIONS_PAYLOAD_SCHEMA_VERSION` does not change, so `src/plugins/sessions/shared.test.ts` is untouched.

## Out of scope

- No command, manifest, capability, or protocol change — docking already works (established decision 1).
- No change to what the server sends: the narrow rendering is a different view of the same `SessionsPayload`, and `SESSIONS_PAYLOAD_SCHEMA_VERSION` does not move.
- No change to any row action, its enablement, its confirmation dialog, or its notification line (established decision 6).
- No width measurement, `ResizeObserver`, or pixel threshold, and therefore no narrow rendering for a narrow centre pane in a two-pane split (settled decision 1).
- No shared or published narrow-list helper, and no change to the schedules or audio tabs (settled decision 13).
- No new user-visible strings, no abbreviated state words, and no abbreviated activity text (settled decision 12).
- No docs screenshot or `data-doc-shot` hook for the docked rendering.
- No change to sidebar width, its clamping, its persistence, or the host's dock-cycle control.

## Verification

`./scripts/run.mjs check-diff` after the change. Note that it does not lint CSS — `lint:css` (stylelint, configured at `web/.stylelintrc.json`) runs only in the human's `npm run check`, so the narrow variant's stylesheet is worth reading once against `stylelint-config-standard` before handing off.

Manual: with at least one remote harness and one tab joined onto its connection, run `sessions` and confirm the centre rendering is unchanged — five headings, six columns, joined host cell indented. Run `sessions left` and confirm the list stacks: no headings, each row two lines, the name and its buttons on the first and the plug, state, host, and activity on the second, a hairline between blocks, and the joined block indented as a whole. Drag the sidebar to its minimum and confirm the secondary line wraps onto further lines rather than truncating, that a wrap never splits a state word or a hostname, and that the tab name ellipsizes instead of wrapping. Point the session at a host whose name is longer than the sidebar and confirm that field alone ellipsizes and the tooltip still gives the full destination. Confirm the header still shows Refresh alone and that Refresh works, that arrow keys, Enter, and second-click open the same rows they open in the centre, and that a detach raised from a docked row shows the same confirmation dialog. Dock it right, then run bare `sessions` and confirm it returns to the centre in the wide rendering. Finally, close every remote session and confirm a docked, empty list reads `No remote sessions` with no heading band.
