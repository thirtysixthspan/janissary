# Native commands: ACP availability and dispatch

**Complexity: 5/10** — ACP tool-table and primer filtering plus a dispatcher contract for long-running native calls, with cancellation and notification parity across browser, database, and question handlers.

## Goal

Apply current global and agent availability to native ACP calls and route them through the ordinary command dispatcher.

## Decisions and dependencies

- Depends on completed units 1–5 (`product/plans/complete/native-commands-01-inventory.md` through `-05-completion.md`). Units 1–4 supply the inventory, settings, notification, and dispatch contracts this plan uses; unit 5 is complete and is not an API dependency. Reuse the canonical inventory in `src/application-commands.ts` (`listApplicationCommands`, `resolveApplicationCommand`), the `nativeCommandSettings` snapshot in `src/native-commands/manager.ts`, the refusal helper in `src/native-commands/dispatch-policy.ts`, and the `CommandManager` dispatch contracts; do not add another inventory, settings reader, native-command resolver, notification event, or result shape.
- The only tool-table construction point is `runCorePrompt` in `src/acp/run-prompt.ts:27-30`, called once per model attempt. `AcpManager.start` (`src/acp/manager.ts:39`) only connects and builds no tool list. `AcpManager.run` reads role settings once per logical prompt (`src/acp/manager.ts:93`) and reuses that grant snapshot across model retries; the next prompt re-reads it (`src/acp/manager.test.ts:116`). There is no session-launch allow-list to update, and no cached list an existing session retains.
- Keep `createAcpToolTable` owner selection on the full `request.commands` grants, not the enabled intersection, so a granted command that is disabled or agent-off is still extractable and returns a refusal instead of becoming a final answer. The table's `AcpTool` shape (`primer`, `match`, `run`, `isCommandLine`) at `src/acp/tool-table.ts:14` stays as declared.
- Compute the primer's allow-list from the intersection of `request.commands` with the current snapshot's `effectiveAgentAccess` (`src/native-commands/settings-types.ts:9`, computed at `src/native-commands/manager.ts:78-95`, which already combines `enabled`, parent `enabled`, `agentAccess`, and parent `agentAccess`). `agentAccess` can only remove commands from the role's grants; it never adds a tool outside `NATIVE_ACP_COMMANDS` or the grant list. Keep every included owner's group primer even when all of its commands are excluded; emit `Only these commands are allowed: <commands>.` only when the intersection is non-empty, and keep the group descriptions alone when it is empty. A role with no recognized grants still gets no table and no primer.
- Check the current settings immediately before every emitted call, before the role-grant check. Resolve the canonical native row and find its snapshot row by canonical `name`, as `disabledApplicationCommand` does at `src/native-commands/policy.ts:9-12`. When `effectiveEnabled` is false, call `refuseDisabledCommand` (`src/native-commands/dispatch-policy.ts:21`) and return its exact `Command is disabled: <command>.` message. When the command is enabled but `effectiveAgentAccess` is false, return the same message and call `notify(managers, 'command-disabled', label, message)` (`src/notifications/index.ts:194`) directly, because `refuseDisabledCommand` checks only `effectiveEnabled` and must stay unchanged for human dispatch. A missing settings manager or row means allowed, matching `src/native-commands/dispatch-policy.ts:16-18`. A command already executing is not interrupted; the next emitted command re-checks.
- Route enabled, granted native calls through `CommandManager` instead of the direct service calls in `src/acp/tool-table.ts:39`, `:48`, and `:57`. Keep `toolRunner` calling the matched `AcpTool.run` as it does today; replace only those three `run` closures with one shared dispatcher helper in `src/acp/tool-table.ts` that builds the `acpTool` invocation from the captured `managers`, `label`, `command`, and prompt `signal`. The file is well under the 200-line limit, so the helper stays there. Add `acpTool?: true` to `CommandInvocationContext` (`src/commands/types.ts:6`) and propagate it in `childInvocationContext` (`src/command/invocation.ts:27`). The ACP invocation must carry `request.abort.signal` and `awaitResult: true`; extend `createInvocationContext` (`src/command/invocation.ts:6`) with an optional options argument for `signal`, `awaitResult`, and `acpTool` rather than using the fresh `AbortController` it mints at `:22`. Do not add a second invocation-context constructor.
- Add one `CommandManager` entry point for this path, `dispatchNativeLine(label, input, invocation)`, reusing the resolution, refusal, execution, and result logic in `dispatchLine` (`src/command/manager.ts:91`) but waiting without the 30-second plugin capture deadline (`src/command/manager.ts:11`, `:62`). Give `dispatchLine`'s `captureLimitMs` an explicit `undefined` no-limit case, matching `executeAndCapture` (`src/capture/execute-and-capture.ts:26-28`), and have `dispatchNativeLine` pass `undefined`; mirror the no-deadline wait already used by the `structuredResult` branch (`src/command/manager.ts:120-129`). Return the existing `{ dispatched, output, coreResponse?, result? }` contract; do not add a second result shape. A pending question or slow browser call must not be settled by the plugin deadline. This entry point is async like the other dispatcher methods, so the db native call completes on a microtask; update the `runCommand` assertion at `src/acp/manager.test.ts:149` to await and revise the `src/acp/loop.ts:51-54` comment so it no longer claims the ACP db path is synchronous.
- Branch the three command handlers on `invocation?.acpTool`: `src/commands/browser.ts:7` returns `managers.browser.run(label, command)` (`src/browser/tab.ts:85`) instead of `runInteractive` (`src/browser/tab.ts:137`); `src/commands/db.ts:8` returns `managers.database.runInTab(label, command)` (`src/database/manager.ts:29`) instead of `appendCommandOutput`; `src/commands/question.ts:6` returns `runQuestionCommand(command, label, managers.questions, invocation.signal)` (`src/question-command.ts:48`) without `startRunning`/`finishRunning`. Every other caller keeps today's interactive or appended behavior. This preserves ACP's single `acp: true` transcript entry from `runCorePrompt` (`src/acp/run-prompt.ts:71`) and avoids duplicate output.
- Convert the dispatch result to the loop's string with the `runGrantedAgentCommand` rule at `src/agent/command-tools.ts:68-71`: return `result.output` for a `coreResponse`, return `result.output` when `result.result` is undefined, and otherwise return the string result, JSON-stringifying a non-string result as that helper does. A `dispatched: false` result throws the existing `No ACP tool matched command` error; it is never fed back as an empty tool result.
- Preserve cancellation: `AcpManager.cancel` aborts `request.abort` (`src/acp/manager.ts:179`), `runCorePrompt`'s `active()` guard (`src/acp/run-prompt.ts:23`, `:52`) stops a new command, and the invocation signal aborts a pending question so it resolves `Question cancelled.` (`src/question-command.ts:48-51`). Browser and database work may still finish; `recordAsyncResult` and the loop's post-await abort check (`src/acp/run-prompt.ts:32-36`, `src/acp/loop.ts:63`) suppress late results and follow-up turns.
- Return `Command is disabled: <command>.` to the ACP loop regardless of notification visibility, and attribute the ambient notification to the originating tab label passed into `runCorePrompt`. Notification suppression changes delivery only, never the tool result.
- Land in this order so each checkpoint typechecks: add the `acpTool` invocation option and `dispatchNativeLine` first, add the three command-handler branches next, then wire `toolRunner` / `runCorePrompt`, then update specs and tests. Keep every touched source file under the 200-line `max-lines` limit and use `.js` extensions on new relative imports. `src/command/manager.ts` is already 184 lines, so keep `dispatchNativeLine` a thin wrapper over `dispatchLine`; if the no-deadline option pushes it over, extract the capture/result plumbing into a focused module rather than compacting.

## Implementation steps

1. Filter the allow-list at prompt construction. In `runCorePrompt`, read `managers.nativeCommandSettings?.current()` when building the primer, intersect `request.commands` with the rows whose `effectiveAgentAccess` is true, and pass that set to `toolPrimer`. Compute the intersection in `NATIVE_ACP_COMMANDS` order and deduplicated, matching the existing `toolPrimer` catalog filter. Change `toolPrimer`'s second argument from raw grants to the enabled allow-list. Keep passing the full `request.commands` to `createAcpToolTable` so its owners, primers, and extraction predicates survive a disabled or agent-off grant. Keep `toolExtractor` unchanged.
2. Add the ACP policy gate in `toolRunner`, extending its arguments with `managers` (it already receives `label`). Keep the existing native-name resolution and matching-tool lookup first, so a command no included tool recognizes still throws `No ACP tool matched command`. Then, before the grant check, resolve the canonical native row from the current snapshot and apply the disabled / agent-off rules above. Then keep the existing `Command not allowed for role "<role>": <native>.` refusal for enabled but ungranted commands. Dispatch enabled granted commands through the shared `AcpTool.run` helper, which calls `managers.command.dispatchNativeLine` with an `acpTool` invocation carrying the prompt signal and `awaitResult`; convert the result with the `runGrantedAgentCommand` pattern.
3. Add the native branches to `src/commands/browser.ts`, `src/commands/db.ts`, and `src/commands/question.ts` as described in the decisions, leaving all other callers unchanged. Add `dispatchNativeLine` to `src/command/manager.ts` without changing the behavior of `dispatchLineWithOutput`, `dispatchQueuedLine`, or `dispatchLineInInvocation`. Do not change `runAcpToolLoop` or the autonomous-agent path in `src/agent/execute.ts`.
4. Update `product/specs/acp.md` "Autonomous tool loop" and `product/specs/application-commands.md` "Native command settings" and "Disabled command dispatch" with the enabled / agent-access intersection, retained group primers, the empty-intersection rule, the per-call gate, the exact refusal, the dispatcher path, and the unchanged browser / database / question outputs and cancellation.
