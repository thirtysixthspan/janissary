# Extract harness transcripts directly from harness dot directories

**Complexity: 7/10** — the number is now almost entirely the three independent storage-format adapters (two incremental JSONL readers over files another process is appending to, plus a SQLite reader against a schema that has already changed once) and the subagent discovery that has no precedent in the repo. Everything around them is deliberately thin: one poll timer, one accessor, one cap, plain strings instead of an entry type, and no cursor type at all. Two behavior-free extractions must land first, one of them because `src/harness/manager.ts` is already at the 200-line limit.

## Summary

A monitored harness tab today contributes only its **latest rendered screen** — `harnessFeedEntries` (`src/monitor/harness-feed.ts:12-26`) asks `HarnessManager.latestScreenText` (`src/harness/manager.ts:45-49`) for the screen reader's de-ANSI'd capture and feeds it once per 30-second flush, deduped by `capturedAt`. `product/specs/monitoring.md:32` states the consequence plainly: "The monitor therefore sees periodic screen snapshots of a harness, not its full linear scrollback." That is fatal for the thing this feature exists to enable — **subagent monitoring**. When a claude harness dispatches a subagent, the parent's terminal shows a collapsed progress line; the subagent's own prompts, tool calls, and results never render on the parent's screen at all, so no screen snapshot, at any frequency, can ever contain them.

Every harness already writes that missing detail to disk, in its own dot directory, in a structured form. This plan adds a per-harness-tab **background tailer** that locates the running session's record in the harness's dot directory, follows it for the tab's lifetime, normalizes each record into harness-agnostic text (including subagent records), and makes the result available to two consumers: a monitor's flush (fed **alongside** the existing screen snapshots, not replacing them) and a new `harness transcript <label>` command that opens the normalized transcript in an editor tab, exactly as `harness capture <label>` opens a screen capture. The normalized transcript is also written under `.janissary/` so it survives the tab, on the same clear-at-launch / preserve-across-relaunch policy `.janissary/recordings/` already uses.

When no session record can be resolved for a tab, the tab silently keeps its existing screen-snapshot behavior and a single line lands in the notifications feed.

## Design decisions

1. **Additive, not a replacement.** A monitored harness tab contributes both its rendered screen (unchanged `harnessFeedEntries` behavior) and its new transcript entries since the last flush. The screen stays because it is the only thing that shows the harness's *current interactive state* — a permission prompt awaiting an answer, a spinner, a TUI panel — which the session file does not record until the turn resolves. The transcript adds the linear history and the subagent detail the screen can never carry. The token cost of the overlap is accepted deliberately.
2. **All three harnesses in v1** — `claude`, `codex`, and `opencode` — behind one reader interface. Their storage formats are genuinely different (see decision 3), so this is three adapters, not one path template. This is the single largest driver of the plan's size, and it is a deliberate scope choice.
3. **Three storage formats, three resolution strategies.** Verified against the harnesses installed on this machine:

   | Harness | Location | Shape | Resolve a tab's session by |
   | --- | --- | --- | --- |
   | `claude` | `~/.claude/projects/<cwd-slug>/<session-uuid>.jsonl` | one JSON record per line | slugify the tab's `cwd` (path separators and `.` → `-`), then take the `.jsonl` in that directory whose mtime first post-dates the PTY spawn |
   | `codex` | `~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-<ISO>-<uuid>.jsonl` | one JSON record per line; the first record is `session_meta` carrying `payload.cwd` | scan the **spawn date's** directory (not the current date's — a tab open across local midnight must still find the file codex named at session start) for `rollout-*.jsonl` files created after the PTY spawn, and match on the `session_meta` record's `cwd` |
   | `opencode` | `~/.local/share/opencode/opencode.db` (SQLite) | `session` / `message` / `part` tables; `session.directory` is the cwd, `session.parent_id` links a subagent session to its parent | query for the newest `session` row whose `directory` equals the tab's cwd and whose `time_created` post-dates the PTY spawn |

   Note the opencode finding: its per-session JSON files under `~/.local/share/opencode/storage/` are **gone** in the current version — only `migration` and `session_diff` remain there, and messages live in `opencode.db`. The opencode adapter is a database reader, not a file reader.
4. **Claude subagents come from a sibling directory, not from the parent's file.** A claude session that spawned subagents has `~/.claude/projects/<cwd-slug>/<session-uuid>/subagents/agent-<id>.jsonl` plus an `agent-<id>.meta.json` carrying `agentType`, `description`, `toolUseId`, and `spawnDepth`. The claude adapter therefore tails the parent `.jsonl` **and** discovers/tails each subagent file that appears in that sibling directory, labeling its entries with the subagent's `agentType` and `description` from the meta file. This is the concrete mechanism by which "subagents can be monitored"; without it the feature does not deliver its stated purpose. For opencode the equivalent is following `session` rows whose `parent_id` is the tailed session; codex has no subagent concept to follow today.
5. **Reading is per-adapter; scheduling is shared — and no cursor ever crosses that seam.** An adapter is constructed per harness tab and exposes exactly one method: "any new text since I last asked?", returning rendered strings. It keeps its own resolution state and its own read position privately — a byte offset for the two JSONL harnesses, a `(time_created, id)` pair for opencode — so there is **no cursor type, no union, and no opaque handle** for the tailer to carry or the interface to declare. The tailer owns only the timer, the accumulated entries, the file, and the notification. No adapter owns a timer.
6. **A background subsystem, not flush-time polling.** A tailer is created per harness tab when its PTY spawns and disposed when the PTY exits, owned by `HarnessManager` in the same map-per-observer pattern it already uses for `HarnessScreenReader` and `HarnessRecorder` (`src/harness/manager.ts:26-39`). It accumulates independently of whether any monitor is watching, so a monitor started mid-session finds a populated buffer and `harness transcript` works on an unmonitored tab.
7. **Normalized text, never raw JSON — and the normalized form is a plain string.** Each record renders to a compact block: role or actor, its text content, and for a tool use the tool name plus its result. Subagent-sourced blocks are prefixed with the subagent's identity (decision 4). There is **no normalized-entry record type**: both consumers want text — the monitor feed wraps it in a `LogEntry`'s `output` (the tab label, its only other tag, comes from the tab, not the record) and the file appends it — and nothing reads an actor, a subagent field, or a source timestamp structurally. Ordering is array order. Ceiling: if a later consumer ever needs to filter or group by actor, introduce the record type then; nothing in this plan's scope does.

   The rendered result is **not** truncated per record. The one cap that exists is at the flush boundary (see the monitor feed below, reusing `cap`), which is where the size actually matters; truncating inside the normalizer would also truncate the persisted file, which is meant to be complete. Ceiling: a single enormous tool result can therefore dominate one flush batch, and the upgrade path if that bites is a per-record cap applied on the feed side only, never in the normalizer.
8. **Current session only.** A tailer follows exactly the one session belonging to its tab's running harness process. It does not backfill earlier sessions in the same cwd, and it does not read a session file from byte 0 that predates the spawn — the spawn timestamp is the floor in all three resolution strategies (decision 3). A monitor started mid-session receives everything the tailer has accumulated *since the tab opened*, which is the tab's own whole life, not the directory's history.
9. **Persisted under `.janissary/harness-transcripts/` — not `.janissary/transcripts/`, which is already taken.** `TranscriptStore` owns `.janissary/transcripts/` today (`src/transcript/store.ts:52`, `transcriptDir = path.join(projectDir, '.janissary', 'transcripts')`), storing per-tab `LogEntry[]` as `<label>.json` under a `VALID_NAME = /^[\w-]+$/` guard (`:14-16`) and wiping the directory via `TranscriptStore.clear()` at fresh launch (`src/main.ts:170`). Writing harness transcripts there would interleave two unrelated file families in one directory and put them at the mercy of each other's clear logic. The new directory is `.janissary/harness-transcripts/`, and each tailer writes `<sanitized-label>-<ISO-timestamp>.txt` into it, following `harnessRecordingPath`'s naming and lifecycle exactly (`src/harness/recording-file.ts:17-21`, label sanitized by `replaceAll(/[^\w-]/g, '-')` and the ISO timestamp's `:`/`.` replaced with `-`): lazily created on the first record, appended through one long-lived stream, cleared at a fresh launch, preserved across `--relaunch`. `harness transcript <label>` opens this file.

   The persisted file is **uncapped**, matching recordings, which have no cap either (`src/harness/recorder.ts` writes until the PTY exits). A long session with a chatty subagent can therefore produce a large file; that is accepted, and the fix if it ever bites is a per-file byte ceiling in the tailer, not a retention sweep. This is separate from the per-flush `cap` on what reaches a monitor, which is not optional.

   The same collision applies to naming inside `src/`: `src/transcript/` already holds `TranscriptStore` and `TranscriptLogger`, which are about **tab** transcripts, an unrelated concept. The new code lives in `src/harness/transcript/` and its class is `HarnessTranscriptTailer`. Do not add anything to `src/transcript/`, and do not name any new symbol `TranscriptStore`-alike.
10. **Failure is a fallback plus one notification.** When resolution finds no session for a tab, or an adapter errors, the tab is left with exactly today's behavior — screen snapshots to monitors, no transcript file — and a single notification line is recorded for that tab, never repeated per retry. The body text is `no harness transcript found`; because `notify` already renders the header as `<time> <tabLabel>:` (`src/notifications.ts:98-101`), the feed line reads `● 8:32pm claude: no harness transcript found`, which is the requested `<label>: no harness transcript found` wording without doubling the label.
11. **The notification is a new event type with no config toggle.** It is a diagnostic about a capability silently degrading, not ambient tab activity, so it belongs with `manual`/`auto-approve`/`question` — the untoggled events (`product/specs/notifications.md:71-74`) — and it is subject to focus suppression's exemption for explicit events. The existing drop-if-closed rule applies unchanged: with the notifications tab closed, the line is dropped.
12. **`harness transcript <label>` mirrors `harness capture <label>`.** Same parse position in `parseHarnessCommand` (`src/harness/command-parse.ts:84-88`, the `if (tokens[0].toLowerCase() === 'capture')` branch), same manager dispatch shape (`src/harness/manager.ts:65`, `if ('capture' in parsed) return this.capture(input, parsed.label)`), same "resolve label → validate → open the file in an editor tab via `this.managers.openFile.edit(input, file, this.managers.tab.cur().label)`" body as `HarnessManager.capture` (`:97-106`). It is a point-in-time open of the file as it stands, not a live view — the same snapshot semantics the monitor context button already has (`product/specs/monitoring.md:17`). Its error strings mirror capture's one-for-one (`product/specs/harness.md:321-325`): `Usage: harness transcript <name>.`, `No tab labeled "<name>".`, `"<name>" is not a harness tab.`, and `No transcript available for "<name>" yet.`

13. **The discriminator is the tailer map, not `tab.harness`.** An **ssh tab also carries a `harness` view object** — `src/ssh-manager.ts:32` builds `{ name: 'ssh', program: 'ssh', ptyId: '', status: 'running', destination }` and calls `makeHarnessTab` with it — so `tab.harness` is truthy for ssh tabs and `tab.view === 'harness'` is true for them too (that is exactly why they are monitorable). Neither test can distinguish a real harness. Both the `harness transcript` command and the monitor feed therefore key off the presence of a **tailer for that tab's `ptyId`**, which only `finishSpawn` ever creates (`src/harness/manager.ts:196` is where its siblings are created; `src/ssh-manager.ts:37` calls only `registerScreenReader`). An ssh tab consequently gets `No transcript available for "<name>" yet.` from the command and contributes nothing to the transcript feed, with no special-casing of the string `'ssh'` anywhere.
14. **Resolution rides the ordinary poll tick — there is no second loop.** A harness's session record does not exist at the instant the PTY spawns; the binary creates it on its first turn. Rather than a dedicated retry loop with its own interval and attempt count, the tailer's single poll timer simply asks its adapter for new text every tick; an adapter that has not resolved yet resolves first and returns nothing. If nothing has resolved by a deadline measured from spawn, the tailer fires the decision-10 notification once and stops polling. That is one timer and two module-level constants (poll interval, resolve deadline), not two timers — and no configuration.
15. **The dot directories are read-only inputs, read from the server process, and a sandboxed `-w` harness still populates them.** Nothing here writes into `~/.claude`, `~/.codex`, or opencode's database. Two facts make this work for workspaced tabs, both verified rather than assumed: the tailer runs unsandboxed in the server process (which already reads and writes `~/.claude.json` for workspace trust, `src/workspace.ts:34-44`), and a **sandboxed** harness is explicitly permitted to write its own session records — `src/sandbox/paths.ts` lists `.claude/projects` (`:13`), `.codex` (`:30`), and `.local/share/opencode` (`:32`) in `HOME_WRITE_CARVEOUTS`, with the file's own comment naming "transcripts" as one of "the session-state paths a sandboxed `claude` writes while running" (`:7-8`). **No sandbox rule changes are needed, and none may be added** — widening `HOME_WRITE_CARVEOUTS` is explicitly out of this plan's scope.
16. **Injection framing is inherited, not re-invented.** Transcript entries reach a monitor through the same buffer every other feed uses, so they are wrapped in that monitor's random delimiter and covered by the existing priming that tells the persona to treat delimited content as data (`product/specs/monitoring.md:40`). This matters more here than for the screen feed: a subagent's transcript carries verbatim file contents and tool output, which is exactly the material an indirect prompt injection rides in on.

## Proposed changes

### A transcript-source layer under `src/harness/transcript/`

A new directory, because the three adapters plus the tailer plus the normalizer will not fit one 200-line module.

**The source interface — one method, no cursor, no entry type (decisions 5 and 7).** A single exported type: an adapter is constructed with the tab's cwd and spawn timestamp, and answers one call returning the rendered strings produced since the previous call (empty when it has not resolved a session yet, or when nothing is new). Resolution state and read position stay private to each adapter, so the interface declares neither. Everything below is an implementation of that one method.

**`claude` adapter.** Slugifies a cwd into the `~/.claude/projects/` directory name, picks the session `.jsonl` by mtime against the spawn floor, and reads new bytes from its private offset, splitting on newlines and holding back a trailing partial line until the newline arrives — the file is being appended to by another process, so a read will land mid-line. Read the new bytes with `node:fs`'s positional read (an `fd` plus a start position, or a `createReadStream` with a `start`), not by re-reading the whole file and slicing: the stdlib already does incremental positioned reads, and a session file grows without bound. Per decision 4 it also scans the `<session-uuid>/subagents/` sibling directory on each read for `agent-*.jsonl` files it is not yet tracking, pairing each with its `.meta.json` for the subagent's `agentType` and `description`, and tails each with its own offset.

**`codex` adapter.** Same partial-line-safe incremental read, over `~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-*.jsonl`, resolved by reading each candidate's first `session_meta` record and comparing `payload.cwd` to the tab's cwd. It tracks one file; codex has no subagent files to discover.

**`opencode` adapter.** Opens `~/.local/share/opencode/opencode.db` read-only via `node:sqlite`, resolves the `session` row by `directory` and `time_created`, and reads new `message`/`part` rows ordered by `(time_created, id)` after its private position. It also picks up `session` rows whose `parent_id` is the tailed session, which is opencode's subagent equivalent.

Two failure modes, one mechanism: opening a database another process is actively writing means WAL-mode reads that can return a transient busy/locked error, and opencode's storage layout has already changed once under this feature's feet, so a future schema will make these queries fail outright. Both are handled by the adapter treating **any** query failure as "nothing new" — a transient lock resolves itself on the next poll, and a permanently unrecognized schema simply never resolves, which routes the tab into the ordinary decision-10 fallback-plus-notification path at the deadline. No separate schema-probe step is needed: a missing table already throws, and the same catch covers it. An unrecognized opencode version therefore degrades to today's screen-only behavior instead of breaking the tab.

**The normalizer.** One module turning each harness's raw record into rendered text: role/actor, content, and for a tool use the tool name plus its result, with no per-record truncation (decision 7). Records that carry no user-meaningful content — claude's `mode` and `file-history-snapshot` lines, codex's `session_meta` — are dropped rather than rendered.

**`HarnessTranscriptTailer`.** Constructed with the tab label, the harness name, the tab's cwd, and the spawn timestamp. It owns the single poll timer and the resolve deadline (decision 14), the accumulated in-memory string list, the append stream to `.janissary/harness-transcripts/` (opened lazily on the first entry, exactly as `HarnessRecorder` opens its own), and `dispose`. It exposes the entries after a given index (for monitors) and its transcript file path (for the command). It does **not** import anything from `src/monitor/`.

**Transcript-file module.** The init/ensure/path/clear quartet for `.janissary/harness-transcripts/` (decision 9), the same shape as `src/harness/recording-file.ts` with a different directory and a `.txt` extension. It wires into the two call sites its sibling already uses: an `init…` call beside `initHarnessRecordingDirectory(cwd)` (`src/main.ts:159`) and a `clear…` call appended to the `if (!args.relaunch) { … }` list (`src/main.ts:170`), which is what gives it the clear-at-fresh-launch / preserve-across-`--relaunch` policy for free.

**Do not hand-roll the filename a third time.** The `<sanitized-label>-<ISO-timestamp>` construction — `replaceAll(/[^\w-]/g, '-')` on the label, `replaceAll(/[:.]/g, '-')` on the ISO string — already exists twice: in `harnessRecordingPath` (`src/harness/recording-file.ts:17-21`) and in `writeCaptureFile`, which that function's own comment says it is "mirroring" (`:14-16`). A third copy is the point at which it should be extracted instead: lift the name builder into one small shared helper the capture, recording, and transcript paths all call, taking the label, the timestamp, and the extension. That is a smaller net change than a third duplicate, and it is the only edit this plan makes to the existing capture/recording modules.

### `HarnessManager` wiring — and the extraction it forces first

**`src/harness/manager.ts` is already at the limit.** It is 280 raw lines, of which ~197 count against ESLint's `max-lines` (`max: 200, skipBlankLines: true, skipComments: true`, `eslint.config.mjs:60`). There is no room even for the trimmed set below — a map, one accessor, a construction line, a disposal pair, a dispatch line, and a new method. This is not a risk to watch — it is a blocker to clear before any of this feature lands, and the fix is the one `CLAUDE.md` mandates (extract into a new module; never compact code, strip comments, or delete spacing).

**Step one is therefore a pure, behavior-free extraction:** move `HarnessManager.capture` (`src/harness/manager.ts:97-106`) into a new `src/harness/subcommands.ts` as a plain function taking the pieces it needs (the managers object plus a way to reach the target tab's latest capture), leaving `run`'s dispatch line (`:65`) delegating to it. Land that with `./scripts/run.mjs check-diff` green and no behavior change, then add `transcript` beside it in the same module. The new module holds both label-targeting subcommands, which is a coherent seam rather than an arbitrary split.

What stays in `HarnessManager` afterwards is small: a `tailers` map beside `screenReaders` and `recorders` (`:26-27`), one construction line in `finishSpawn` beside `this.recorders.set(id, new HarnessRecorder(...))` (`:196`), one disposal pair in the existing `pty` `exit` handler beside the recorder's (`:36-38`), and **one** accessor mirroring `latestScreenText`'s shape (`:45-49`): given a tab label, return that tab's tailer or `undefined`. Callers ask the tailer itself for entries or for its file path — two accessors that each re-do the same label→tab→`ptyId`→map lookup would be the same code twice for one call site each. Returning the tailer still keeps the map private, and the lookup returning `undefined` *is* the decision-13 discriminator: an ssh tab has a `ptyId` but never a tailer.

### Command parsing

`HarnessParsed` (`src/harness/command-parse.ts:7-10`) gains a `{ transcript: true; label: string }` variant beside `{ capture: true; label: string }`, and `parseHarnessCommand` gains the matching branch beside the `capture` one (`:84-88`), with usage error `Usage: harness transcript <name>.`. Both subcommand names are safe by the same argument the existing doc comment makes (`:74-75`): neither is a `HARNESS_COMMANDS` key. The two branches are near-identical, so factor them into one small helper rather than duplicating — `parseHarnessCommand`'s `sonarjs/cognitive-complexity` budget is already partly spent, and `sonarjs/no-duplicate-string` will flag the repeated literal otherwise. At 60 counted lines this file has ample room.

Note the ordering constraint inside `parseHarnessCommand`: `splitWithClause` runs **before** tokenizing (`:80-83`), so a label containing the standalone word `with` is truncated. That is pre-existing behavior shared with `capture`; match it, do not "fix" it here.

### Monitor feed

A new `src/monitor/harness-transcript-feed.ts` beside `harness-feed.ts`, same signature shape: loop `resolveTargetTabs(managers.tab.tabs, targets)`, skip anything without a tailer (decision 13), ask `HarnessManager` for the entries after the index this monitor last consumed, and emit them as `LogEntry` values tagged with the tab label. Cursors are per-monitor, so two monitors watching one tab each receive the full stream.

`FeedState` (`src/monitor/feeds.ts:8-12`) gains a fourth per-tab cursor map — a `Map<string, number>` of last-consumed index, the same shape as `harnessSeen` — which must be added in **both** places its siblings appear: the `MonitorRegistration` type (`src/monitor/manager.ts:36-44`) and the registration literal that initializes all three with `new Map()` (`:96`). `flushFeedEntries` gains the fourth call in its array (`src/monitor/feeds.ts:17-23`), which puts the new entries into both the flush and the seed path for free, since `seedFeedEntries` delegates to it (`:27-29`).

Two ordering points, both decided: within one flush batch a tab's transcript entries precede its screen snapshot, so the batch reads as history-then-current-state — which falls out of putting the new call **before** `harnessFeedEntries` in `flushFeedEntries`'s array. And the whole batch for one tab is passed through `cap` from `src/monitor/feed-diff.ts:6` before buffering, so a harness that emitted a huge burst between flushes cannot blow out the prompt; `cap`'s existing "diff truncated" wording is accepted as-is rather than forked. This is the **only** cap in the feature (decision 7) — the normalizer truncates nothing, so the persisted file stays complete.

`src/monitor/manager.ts` is at ~182 counted lines — the two-line addition fits, but it leaves little headroom, so add nothing else there.

### Notifications

`NotificationEventType` (`src/notifications.ts:11-20`) gains a variant for the unavailable-transcript case. **Three edits, not one**, and the first two are load-bearing for typecheck: a case in `notificationText`'s switch (`:68-80`), which has no `default` and so stops being exhaustive the moment a variant is added; a case in `shouldNotify`'s explicit-events switch beside `manual`/`auto-approve`/`editor-suggest`/`question` (`:34-40`), without which the event silently falls through to the ambient path and is dropped whenever its tab is active or no `NotificationConfig` exists; and the file's leading doc comment (`:6-10`), which enumerates the events in prose. The tailer fires it exactly once per tab, at the point it abandons resolution.

## Implementation order

Each step is independently green under `./scripts/run.mjs check-diff`; steps 1 and 2 must precede everything else.

1. **The `capture` extraction into `src/harness/subcommands.ts`** — no behavior change, no new feature code. This is what makes room in `src/harness/manager.ts` for everything after it.
2. **The shared filename-builder extraction**, then **the `.janissary/harness-transcripts/` directory module** plus its `src/main.ts` wiring. The extraction lands first and green, with the existing capture/recording tests unchanged as its regression net; nothing writes to the new directory yet.
3. **The normalizer** — pure, fully testable with fixtures, no adapters yet. The one-method source interface is a few lines that land with the first adapter, not a step of its own.
4. **The three adapters**, one at a time, each with its own fixture-driven tests. Order them `claude` → `codex` → `opencode`: claude alone delivers the subagent capability the feature exists for, so a stall on the opencode SQLite adapter (see open question 2) does not block the feature's value.
5. **The tailer**, plus the `HarnessManager` map/accessors/disposal and the notification event. At this point transcripts accumulate and persist with no consumer.
6. **`harness transcript <label>`** — parse variant, `subcommands.ts` function, dispatch line, spec.

## Out of scope

- **Non-monitor, non-viewer consumers.** No transcript search, no integration with `history.md`'s `Ctrl+R` recall, no `send`/`msg` access to the extracted transcript, no monitor `ask` grounding beyond what the normal feed already provides.
- **Per-subagent tabs.** Subagent activity is fed and rendered as labeled entries inside one transcript. No dedicated tab per subagent, no tree or timeline view of a subagent hierarchy.
- **Historical and pre-launch sessions** (decision 8) — no importing a past session from a dot directory, no resuming, no reading a session that predates the tab's PTY spawn.
- **A live-updating transcript view.** `harness transcript` opens a point-in-time file, exactly as `harness capture` does.
- **SSH tabs.** They share the harness-view tab shape and are watchable by monitors (`product/specs/monitoring.md:32`), but they run no harness binary and have no dot directory, so they get no tailer and no notification.
- **Any behavior change to the existing screen-capture or asciicast-recording paths.** This plan only adds a third observer beside them. It touches those modules exactly twice, both behavior-free and both landing first, green, on their existing tests: moving `HarnessManager.capture` into `subcommands.ts` (step 1) and lifting the duplicated filename builder into a shared helper (step 2).
- **Making transcript extraction configurable.** No `.janissary/config.json` key; it is on whenever a session resolves.
- **Any sandbox change.** The three dot directories are already write-carved-out (decision 15); `src/sandbox/paths.ts` is not touched.
- **Tab completion for the new subcommand.** `src/completion/handlers.ts:77` completes only `harness … --model <value>`; `harness capture <label>` has no label completion today and `harness transcript <label>` gets none either.

## Open questions

1. **Whether a schema-mismatched opencode deserves a more specific signal than silent degradation.** The behavior is decided — any query failure means "nothing new", so an unrecognized schema degrades to the ordinary `no harness transcript found` path (see the opencode adapter above). What cannot be settled from one installed version is whether that is *enough*: a user on a differently-shaped opencode gets the same message as a user whose harness simply hadn't started a session, with no hint that a version mismatch is the cause. Checking a second opencode version would show whether the shapes differ enough to be worth distinguishing; until then the single message stands.
2. **How far back the codex previous-day scan needs to reach.** Decision 3 fixes resolution on the **spawn date's** directory, which is correct because codex names a rollout file when the session starts. If a codex build is ever observed rotating a running session's file into the new day's directory at midnight, the scan must widen to the spawn date plus the following day. Nothing in the installed version suggests it does; this is recorded so a midnight-boundary bug is recognized rather than re-diagnosed from scratch.
