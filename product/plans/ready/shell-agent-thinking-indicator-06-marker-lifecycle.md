# Running marker and link lifecycle in the shell reply writers
**Complexity: 4/10** — the decision core of the feature: a per-terminal map from reply id to the marker on its echo, settled three ways (link in place, link on the original and the repeated echo, removal), where the marker arrives in a write callback that can run before the writer returns or after the reply has already settled; one hook file plus a small option relocation, no server or protocol change.

## Goal

Teach `useShellReplyWriters` to add a running marker to an ACP echo, to turn it into a link when the reply settles with a record, to put the same link on a repeated command line, and to remove it when the reply settles without a record. Give `useShellTerminal` the per-attach state and the two options this needs. No caller passes a receipt or a reply yet, so the running app is unchanged until `07-client-wiring`.

## Design decisions and dependencies

Source plan requirements carried here: "Shell client changes" bullets on `useShellReplyWriters.ts` (the map of running markers, `echoCommand(line, receipt?)`, `displayReply(line, markdown, reply?)`), on `useShellTerminal.ts` (a fresh map each time a terminal attaches, an `openConnection` option), and on the two click payloads; "While the prompt runs" (a click opens the role's live session, which follows a model fallback because the click names the role and the server resolves it at click time; a click before a record exists does nothing); "Once the prompt settles" (every echo of the line carries the link, the original echo's marker turns into the link in place, a second echo carries the same link, a refusal's marker is removed with nothing in its place, a reply that arrives before its echo gets none); "Edge cases" (a re-attached terminal starts empty; an `ask` and a `tell` at once each keep their own; the same line twice settles each marker by id, never by text; clicking a link after its record is gone does nothing and the link stays); "UI design" States and the Accessible name and tooltip; the `useShellReplyWriters.test.ts` entry in "Tests". Three things here go beyond the source plan and are decisions of this subplan: the set of written reply ids (under `displayReply`), the `label` option (under "The tab's own label"), and the relocation of the option mirroring out of `useShellTerminal.ts` (under "Where the options are mirrored").

This subplan consumes, all read in the tree as it stands after `05`:

- From `02-dispatch-receipt`: the `ShellAcpReceipt` type (`replyId`, `role: 'ask' | 'tell'`, `name`) in `src/plugins/shell/shared.ts`, imported type-only through `@shared/plugins/shell/shared`.
- From `03-reply-record-and-tell-line`: a reply may carry `record: { id, name }` (`BackgroundReplyView` in `src/protocol/tab.ts`), and a reply's `id` equals the receipt's `replyId`.
- From `04-marker-decoration`: `addThinkingMarker(terminal, marker, view)` in `thinking-marker-decoration.ts`, returning a handle with `show(view)` and `remove()`; `ThinkingMarkerView` is `{ kind: 'running' | 'link', name, onOpen }`, where `name` is the bare connection name (the module builds `Open <name>` itself). It accepts a marker on any row of the echo's logical line and finds the line's last row itself, so this subplan never works out a row. It registers the decoration synchronously and defers every geometry read to xterm's render callback; a marker that is already disposed gives an inert handle, not an error.
- From `05-reply-writers-plumbing`: `useShellReplyWriters.ts` as it stands is `useShellReplyWriters(terminalRef, placementRef, openLinkRef)` returning `{ displayReply, echoCommand }`, each a `useCallback` over the refs, passing no callback. `writeShellEcho(terminal, placement, line, onMarker?)` returns whether it wrote the echo, and `writeShellReply(terminal, placement, line, markdown, openLink, onHeadMarker?)` returns whether the reply wrote its own line. Each hands its handler an `IMarker` registered on the FIRST row of the logical line it just wrote (the echo's, or the reply head's), taken inside xterm's write completion callback and not when the writer is called, and not taken at all (the handler is not called) while the alternate buffer is active. `onMarker` is never called for a skipped echo. `onHeadMarker` is called only when the reply wrote its own line, as the writer decides, so a caller passes it without knowing whether the reply will repeat its line; the head is then a chunk of its own. The callback can run before the writer returns, and a throw inside it stalls all terminal output (the comments on both functions in `write-shell-reply.ts` say so).

Decisions:

- Per-attach state. `useShellReplyWriters.ts` exports a type for the per-attach state and a factory for it (`ReplyMarkers` and `createReplyMarkers`): a map from reply id to an entry, and a set of reply ids already written. `useShellTerminal` keeps one in a `markersRef` (`useRef(createReplyMarkers())`, as `placementRef` is made) and replaces its `current` with a fresh one on the line next to `placementRef.current = placement` in the attach effect, so a re-attached terminal starts with none, as the screen itself does. xterm disposes markers and decorations with the terminal, so no cleanup of its own is needed. Both writers still return at once when there is no terminal, as today, before touching this state.
- Entry and settlement. An entry holds the receipt's `role` and `name`, at most one decoration handle (a receipt is honored for one echo, so there is one echo row to draw on; the repeated line's link is drawn once and never held), and a settlement with three values: pending, settled with a link (the record's `id` and `name`), settled with nothing. The settlement is stored on the entry and not inferred from the map, because the row marker arrives in a write callback and the reply can settle before it does.
- The reply type. The reply is typed by an exported alias, `ShellReplyOutcome`, from `useShellReplyWriters.ts`, which `07-client-wiring` uses for `useBackgroundReplies`. Non-test files under `web/src/plugins/<id>/` may not import `@shared/protocol` (the client block of `eslint.plugin-boundaries.mjs`: a relative import may reach only `../api` or `../shared.css`, an `@shared/` import only `error-text` or `plugins/<id>/shared`), so the alias is derived from the capability that delivers replies, which `useBackgroundReplies.ts` already indexes the same way. The derivation: take the non-nullable type of `TabPluginClientCapabilities['onBackgroundReply']` (it is optional), the first parameter of that function (the receiver), and the first parameter of the receiver (the reply), then pick `id` and `record`. This is a derivation and not a local re-declaration of the wire shape, so principle 7 holds. The receipt type `ShellAcpReceipt` and the row type `ShellConnectionRow` come in type-only from `@shared/plugins/shell/shared`, which that rule allows.
- `echoCommand(line, receipt?)`. A receipt is honored when its id is in neither the map nor the written set; a duplicate delivery of an id already there is written as a plain echo and the existing entry is left alone. When it is honored: create the entry (pending, no handle) and put it in the map BEFORE calling `writeShellEcho`, passing the marker handler; if the writer returns false (the placement skipped the echo because this line's reply was the last write), delete the entry. This order is required, not a preference. The handler can run inside the writer, before it returns: xterm parses a write at once when its queue is empty and the write follows a keystroke typed into the terminal itself, and every fake `write` in a test runs its callback at once. An entry created after the writer returned would not exist when the handler runs. A skipped echo never calls the handler, so deleting its entry leaves nothing behind. Without a receipt (`ask reset`, `tell reset`, a command that returned none) no entry exists and the echo is the plain write it is today, with no handler.
- When the row marker arrives. One plain function, defined in `useShellReplyWriters.ts` outside the hook, draws for an entry when the writer hands back its marker, and it reads the entry's settlement at that moment. Pending: draw the running view with `addThinkingMarker` and store the handle on the entry. Settled with a link: draw the link view directly and store nothing, because the entry has left the map. Settled with nothing: draw nothing and dispose the marker it was handed, which would otherwise stay in xterm's marker list until its row left the scrollback. The handler closes over the terminal and the entry of its own `echoCommand` call and never reads `markersRef` or `terminalRef` when it runs, because by then they may name a newer terminal.
- Callback safety. Both handlers (the echo's and the reply head's) run inside xterm's write callback. They are total by construction: they read the entry, call `addThinkingMarker` or dispose a marker, and store the returned handle. `addThinkingMarker` does two things at call time, registers the decoration and subscribes to its render event. The registration throws only when the terminal was built without `allowProposedApi` (`useShellTerminal` sets it) and returns undefined for a disposed marker, which the module turns into an inert handle. No `try`/`catch` is added: swallowing a failure here would leave a spinner that never settles with nothing to explain it, and `ai/guidelines/plugins.md` §7 wants a plugin's failures surfaced, not hidden. The drawing module's later work (placement, content) runs in xterm's render callback, which is not a write callback.
- `displayReply(line, markdown, reply?)`. Without `reply` (an application command's ordinary output from `useShellSubmit`) it writes exactly as today, with no handler. With a `reply` whose `id` has no entry (a reply that arrived before its echo, or one replayed into a fresh screen after a remount) it writes exactly as today and adds the id to the written set. A late receipt for that id then draws nothing. This is a small hardening of the source plan's "a reply that reaches the tab before its echo gets no marker or link": without it, a late echo that the placement did not skip (some other write intervened, as it can for a refusal that outruns its dispatch answer) would draw a marker nothing could settle. With an entry, settle first and write second: delete the entry from the map, add its id to the written set (which also keeps a repeated delivery of the same receipt from starting a second entry), then settle by what the reply carries, then write the reply with the same placement outcome as today.
  - With `reply.record`: the entry's settlement becomes the link, and its handle, if it has one, switches to the link view (`show`). The head handler is passed whenever the reply has a record; the writer calls it only when the reply wrote its own line, and the handler draws the link view for that record on the marker it is handed, keeping no handle. So when the reply continues beneath the original echo, the original's marker turns into the link in place, and when the reply repeats its line, both the original and the second echo carry the same link.
  - Without `reply.record` (a refusal, or a record deleted mid-prompt): the settlement becomes nothing, the entry's handle, if any, is removed (`remove`), and no head handler is passed, so the reply writes as one plain reply.
- Names. The running view's name is the receipt's `name`; the link view's name is the reply's `record.name`. A tab renamed after the role's record began makes them differ; `03-reply-record-and-tell-line` accepted that, nothing here reconciles it, and a test pins that the link uses the record's name.
- Click payloads. A click reads the current option at the moment of the click through refs (a draw-time capture would go stale across a re-render). A running view's click calls `openConnection` with `{ text: <receipt name>, kind: 'acp', acpRef: { scope: 'tab', label: <the tab's own label>, role: <the entry's role> } }` and carries no `recordId`; naming the role and not a record is what lets `src/controller/connection-records.ts` (`openConnectionRecord`) resolve the role's live record when the click happens, so a click after a model fallback opens the new model's record. A link view's click calls it with `{ text: <record name>, kind: 'acp', recordId: <record id> }`. Neither needs a new capability or message: `capabilities.openConnection` already sends `openConnectionRecord`, and that function does nothing when the tab reference names another tab, when the role has no live record yet, or when the record is gone (`dispatchRecord` checks `managers.acpRecords.window`). `src/controller/connection-records.test.ts` pins those no-ops (`no-ops for a missing or expired record id`, `no-ops when the tab or its live record binding has disappeared`, `no-ops when the tab binding points at a record that has since expired`).
- The tab's own label. `plugin-client-capabilities.ts` drops a tab reference whose label is not the tab's own (`if (row.acpRef?.scope !== 'tab' || row.acpRef.label !== label) return;`), so the running click needs `capabilities.label`. The source plan's wiring passes only an `openConnection` option, which leaves the hook no route to the label. `useShellTerminal` therefore also takes an optional `label` option (`label` is optional on the capability), and the running click does nothing when it is absent, as it does when `openConnection` is absent. `07-client-wiring` passes both.
- Where the options are mirrored. `openLink`, `openConnection`, and `label` are read only by the reply writers, so `useShellReplyWriters` takes them as plain values and mirrors each into a ref of its own (the same `useRef` plus `.current =` pairing `useShellTerminal.ts` uses for `exitRef` and `copyTextRef`), and `useShellTerminal.ts` drops its `openLinkRef`. This replaces the source plan's "`openConnectionRef` set from an `openConnection` option, like `openLink`" in `useShellTerminal`, and the reason is the line budget below: three more refs there would land the file at 195 counted lines. The hook's inputs become one object: `terminalRef`, `placementRef`, and `markersRef` (refs owned by `useShellTerminal`, listed in the callbacks' dependency arrays as `05` does) and `openLink`, `openConnection`, `label` (values). The identities of the two writers stay fixed for the life of the tab, because `useBackgroundReplies` re-subscribes when `displayReply` changes.
- Types on the handle. `useShellTerminal.ts` gains `openConnection?: (row: ShellConnectionRow) => void` and `label?: string`. `ShellTerminalHandle` widens to `displayReply(line, markdown, reply?: ShellReplyOutcome)` and `echoCommand(line, receipt?: ShellAcpReceipt)`, with their comments. A `ShellConnectionRow` is assignable to the capability's `ConnectionView` (the kinds and the `ask | tell` roles are subsets of the protocol's; `ShellTabMeta.tsx` already hands `payload.connections` to `StatusPanels`), which `07` relies on. The extra parameters are optional, so `useShellSubmit` and `useBackgroundReplies`, which type the writers with the shorter signatures, still type-check unchanged.
- `useShellTerminal.ts` line budget, measured the way `max-lines` counts (blank and comment-only lines skipped): 185 counted lines today. Net change: one type import for `ShellAcpReceipt` and `ShellConnectionRow`, two option lines, one for the longer parameter destructuring, one for `markersRef`, one for its reset, minus the two `openLinkRef` lines; the writers import and the call to the hook gain names but no lines. That is about +4, landing near 189. No further extraction is planned. `useShellReplyWriters.ts` is 20 counted lines today and is expected near 140 (the types and factory, the views and handlers as plain functions, the three mirrors, the two callbacks). No sibling module is planned; `max-lines` is an error in `check-diff`'s lint, so an overrun cannot pass unnoticed.
- The hook is the only place marker decisions live. `thinking-marker-decoration.ts` only draws, and the components hold no marker logic (`ai/guidelines/react-code-organization.md` §5, §6). The decisions that call no hook (the views, the handlers, the settle step) are plain functions in the same file, not `use*` functions. The shell plugin imports nothing from another feature.

## Tests

Client (vitest project `client`), colocated:

- `web/src/plugins/shell/useShellReplyWriters.test.ts` (new). It renders the hook with `renderHook`, using `initialProps` where a case changes an option, over a real `ReplyPlacement` and a fake terminal it defines itself, built as `05`'s `write-shell-reply.test.ts` builds its own: `write(data, callback)` records the data and the argument count and runs the callback at once unless the test holds it and releases it later; `buffer.active` has `type` (settable), `baseY`, `cursorY` (0, so no row is read and the offset is `-1`), and `getLine`; `registerMarker` returns a distinct marker object with a `dispose` spy each time. `./thinking-marker-decoration` is mocked so each `addThinkingMarker` call (terminal, marker, view) is recorded and each call returns a handle with `show` and `remove` spies; `./markdown-block` is mocked as `05`'s test mocks it, declining by default so the reply is written in the styled-text path (one case accepts it, to show the head chunk is still taken separately). Every case runs the handlers inside the fake's `write`, so a handler that threw would fail the case that triggered it. Cases:
  - an echo with a receipt draws a running view on the marker the fake handed back, with the receipt's name, before `echoCommand` returns; an echo with no receipt draws nothing and is the single one-argument write it is today; an echo the placement skipped (a plain `displayReply` of the same line just before it) draws nothing and leaves no entry, so a later reply with a record for that id is written as one plain write and not a split head;
  - a reply with a record beneath its echo calls `show` with the link view (the record's name) on the echo's handle, draws no new marker, and writes as one chunk; clicking the link calls `openConnection` with `{ text, kind: 'acp', recordId }`;
  - a reply that repeats its line (`placement.wrote()` between echo and reply) shows the link on the original handle and draws a link view with the record's name on the head marker, the head being the first write on its own;
  - a reply without a record calls `remove` on the handle, draws nothing, passes no head handler, and writes as a plain reply;
  - two echoes of the same line with different ids settle independently: a refusal removes only its own handle, and the other later links;
  - an `ask` and a `tell` outstanding at once keep their own roles in their running click payloads, and a running payload has no `recordId` key;
  - a reply for an unknown id writes exactly as a plain `displayReply(line, markdown)` does (no handle operations, no head handler), and a receipt that arrives after its reply was written draws no marker and is written with no handler; a second delivery of an id already in the map is written with no handler and leaves the first entry's handle alone;
  - a reply that settles before the row marker arrives (the test holds the echo's callback): released with a record, the marker is drawn directly as the link and `show` is never called; released without one, nothing is drawn and the marker handed back is disposed; and a held callback released after `markersRef.current` was replaced still draws against its own terminal and leaves the new state empty;
  - the alternate buffer: the echo draws no marker, and a later reply for its id settles without error and without a handle operation;
  - the link name comes from the record even when the receipt's name differs;
  - the running click calls `openConnection` with the tab reference built from the `label` option and the entry's role; with no `label` or no `openConnection` it does nothing and does not throw; after a re-render with a new `label`, `openConnection`, and `openLink`, a click on a view already drawn and the link callback handed to `insertMarkdownBlock` use the new values, and the two writers keep their identity.
- `web/src/plugins/shell/useShellTerminal.test.ts`: after the terminal re-attaches (re-render with a new `ptyId`, as the existing re-attach case does), an `echoCommand` with a receipt made before it and a `displayReply` for the same line and id with a record made after it writes one string, head and body together, to the new terminal, as the existing re-attach case asserts, and nothing more to the old one. With a state that survived the attach, the reply would have found the old entry and split the head into its own write, so the assertion on a single write is what proves the reset (the file's `@xterm/xterm` stub ignores write callbacks, so no marker is drawn either way). The existing cases, including `keeps one identity for its reply writers across a re-render`, pass unchanged.
