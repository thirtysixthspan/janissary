# Native commands: host topic

**Complexity: 4/10** — one additive topic bridges the completed settings service into the plugin contract, with a synchronous refresh, one awaited edit action, and lifecycle/guard rules; no new persistence or UI.

## Goal

Expose one narrow, validated host topic for command inventory, effective availability, and settings edits to activated plugins. The server-owned settings service remains the only authority; the topic is a read and edit transport, not a second policy layer.

## Decisions and dependencies

- Work units 1–6 are complete and published on this branch. This unit consumes the canonical inventory and `nativeCommandSettings` service from units 1–2; units 3–6 are not API dependencies. It must land before the Commands tab (8), Roles restrictions (9), and client integration (10).
- Name the topic `commands`. Its notification data is the service's `CommandSettingsSnapshot` verbatim: `source`, `path`, optional `problem`, and the canonical rows with saved `enabled`/`agentAccess`, effective `effectiveEnabled`/`effectiveAgentAccess`, `parent`, and `nativeTool`. Do not define a parallel view type or recompute effective values; the Commands tab needs the source fields and rows, and Roles needs the same rows' effective flags.
- The topic contract module is server-side and may take a type-only import of `CommandSettingsSnapshot`, following `src/plugins/api-topics-models.ts:1` importing `ModelGroup` from `../models/groups.js`. Do not force it import-free. Browser-facing payload types belong in the Commands and Roles plugin shared modules, which are import-free like `src/plugins/models/shared.ts` and `src/plugins/roles/shared.ts`.
- A synchronous `refresh` action takes no fields and calls `nativeCommandSettings.refresh()`, returning `undefined`, following the Models `refresh` arm at `src/plugins/models-topic.ts:14`. It is how unit 8 re-reads the effective file before its first `topicData('commands')`; the topic read itself stays `current()` only.
- One edit action, `set`: the topic is `commands`, the action is `set`, `name` is any command name, alias, or fixed form accepted by `resolveApplicationCommand`, `setting` is exactly `enabled` or `agentAccess`, and `value` is boolean. It passes the action's `name` and a `CommandSettingsEdit` whose `setting` carries exactly the named boolean; one action changes one toggle, never a partial settings object.
- `agentAccess` is refused for a row whose `nativeTool` is undefined with exactly `Not a native ACP command: <canonical>.` and no write, matching the command-line rule in unit 8. An unresolved name is left to `edit`, which returns `Unknown application command: <name>.`; do not duplicate that message. The completed settings service keeps its behavior; this native-row check belongs in the topic handler.
- The commands edit action is the topic's only awaited arm, following Models Delete (`src/plugins/models-topic.ts:9`, `src/plugins/api-topics-models.ts:14`, `src/plugins/api-topic-action-capability.ts:5`). It always returns a promise, including the native-row refusal, and resolves on failure to that message or the service's exact refusal (every current failure path supplies one), and on success to `undefined`; the plugin maps a defined result through `rejectRequest` as `src/plugins/models/activate.ts:93-100` does. Keep `refresh` synchronous.
- Read is `nativeCommandSettings.current()` only. Never call `refresh()` inside the topic read or subscription path: `refresh()` publishes, and a publish-driven delivery that refreshed again would loop and read the file on every notification. The explicit `refresh` action is the only refresh path; unit 8's Commands opener calls it before its first `topicData('commands')` and before opening the tab.
- Subscribe directly to `nativeCommandSettings.subscribe`, not `messageBus`: the service has no bus event. Adapt the returned unsubscribe function to the `Subscription` shape the topic registry expects.
- The topic registry's `subscribe` currently receives only the fire callback (`src/plugins/topics.ts:23`), while `read` and `act` receive `managers` (`:24-25`). Extend `TopicSource.subscribe` to `(managers, fire)` and `subscribeTopic` to `(managers, topic, fire)`, and update `subscribeTabPluginNotifications` at `src/plugins/notifications.ts:62` to pass `port.managers`; existing bus-based sources take the new first parameter unused, and the commands source uses it for `nativeCommandSettings.subscribe`. Do not add a module-level manager lookup or a bus event.
- Notifications follow the existing delivery policy: only an already-active plugin with at least one open tab receives one, and a notification never activates a plugin. A declaration naming `commands` must supply `notify`; `validateActivation` at `src/plugins/activate.ts:63-69` already refuses one that does not. The initial read is the guarded `topicData('commands')` call, which returns the current snapshot before any change. A disabled plugin gets the topic's empty slice, a no-op `refresh`, and a resolved `undefined` edit, never a manager call.
- Adding a topic is additive: keep `TAB_PLUGIN_API_VERSION` at 3 (`src/plugins/api-capabilities.ts:6-9`). This unit changes no existing plugin payload, so do not bump any payload schema here. The new Commands manifest in unit 8 starts its own `payloadSchemaVersion` at 1 and registers its client entry at the same literal; unit 9 bumps `ROLES_PAYLOAD_SCHEMA_VERSION` from 3 (`src/plugins/roles/shared.ts:1`), updates `isRolesPayload`, and changes the Roles literal in `web/src/plugins/registry.tsx:99` and its pin in `web/src/plugins/registry.test.tsx:37`.
- Reuse the existing ingress guards rather than inventing a new action validator: declarations are checked by `src/plugins/activate.ts:20-28`, capability use by `src/plugins/context.ts:42-55` (`restrictToDeclared`), and topic access by `src/plugins/context.ts:60-67` (`requireDeclaredTopic`). The plugin's own ingress validation (`defineIntents` at `src/plugins/define-intents.ts:36-53` for intents, and the command parser for the command-line form) runs before `topicAction`; the service's `edit` resolves the command and refuses unknown names and unusable files.
- Unit 8's Commands manifest declares `topicData`, `topicAction`, and `updateTab` and names `commands` in `notifications`; unit 9 adds `topicData` and `commands` to the existing Roles manifest. `restrictToDeclared` refuses an undeclared capability, and `requireDeclaredTopic` refuses an undeclared topic.
- `defineDockableList` (`src/plugins/define-list-tab.ts:38`) is the Models list helper, but it accepts `left`/`right` and docks. Do not use it for the center-only Commands tab in unit 8; reuse only its `topicData`/`updateTab` mechanics and follow the center-only opener in `src/plugins/roles/activate.ts:132-139`. This unit supplies only the topic, so no plugin code lands here.
- Land the union/registry entries and type exports before the bridge: `Record<TabPluginNotificationTopic, TopicSource>` will not typecheck until the `commands` source exists, so add the union member, notification/action arms, and registry entry together. The host takes no subscription until a declaration names `commands` (`src/plugins/host-channels.ts:33-36`), so the commands topic is inert until a tab declares it.

## Proposed changes

1. Add `src/plugins/api-topics-commands.ts` with the notification type whose `data` is `CommandSettingsSnapshot`, the `refresh` and `set` actions, and a named edit-action alias for the awaited overloads. Re-export the types from `src/plugins/api.ts` beside the Models exports at `:41`. Keep `api-topics.ts` under the 200-code-line limit by putting the commands-specific types in the new module.
2. Register `commands` in `TabPluginNotificationTopic`, `NOTIFICATION_TOPICS`, the `TabPluginNotification` union, and the `TabPluginTopicAction` union in `src/plugins/api-topics.ts`. Add the `TOPIC_SOURCES` entry in `src/plugins/topics.ts` with read, subscribe, act, and an empty slice with no command rows, `source: 'default'`, and an empty path; keep the entry thin by delegating to a new `src/plugins/commands-topic.ts` so the registry file stays within the limit.
3. Implement `src/plugins/commands-topic.ts`: `readCommandsTopic` returns `managers.nativeCommandSettings.current()`; `subscribeCommandsTopic` adapts the manager's unsubscribe; `runCommandsTopicAction` handles both arms. `refresh` calls `managers.nativeCommandSettings.refresh()` and returns `undefined`. `set` resolves the canonical row, returns a resolved promise carrying `Not a native ACP command: <canonical>.` for `agentAccess` on a non-native row, and otherwise calls `edit` and maps a failed result to its message and a successful one to `undefined`. The module must not call `refresh` on the read path, read a file itself, or recompute effective values.
4. Extend the awaited overloads: add the edit action to `TabPluginTopicActionCapability`, `runTopicAction`, and the local overloads in `topicActionCapability` (`src/plugins/context.ts:74-76`), and exclude it from the synchronous overloads alongside `ModelsTopicDeleteAction`. Extend the disabled branch in `topicActionCapability` to resolve `undefined` for the edit action as it already does for Models Delete. Update the `topicAction` capability comment at `src/plugins/api.ts:290-292` so it no longer says Models Delete is the only asynchronous action. Do not change any existing action's sync/async contract. If the added overloads push `src/plugins/topics.ts` past the 200-code-line limit, keep the commands dispatch in `commands-topic.ts` and extract the overload signatures rather than compacting the registry.
5. Update the topic contract in all three pinned docs. In `product/specs/tab-plugins.md` "Being told when host state changes", change eight to nine kinds, describe the commands slice, the synchronous `refresh` action, and the awaited `set` action, and state that opening reads the current snapshot while delivery is limited to active open tabs. In `documentation/developer-documentation/tab-plugins.md`, update the topic list and count at `:242`, the action documentation at `:250-258`, and the v3 changelog at `:381`. In `ai/guidelines/plugins-tabs.md`, change eight to nine topics and add the commands slice at `:87`, and extend the asynchronous-action guidance at `:89` to name the commands `set` action beside `models/delete`. Update the settings paragraph in `product/specs/application-commands.md:9` to say a successful write publishes the new snapshot to open plugin views; the existing initialization, opening, and pre-edit re-read rules stay unchanged. Do not add continuous file watching.
