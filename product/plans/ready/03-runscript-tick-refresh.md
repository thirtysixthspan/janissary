# Tick-driven runscript list refresh
**Complexity: 4/10** — a host subscription that rebuilds the runscript rows on each scheduler tick and publishes only on change, gated so it reads nothing while no scripts tab is open, plus one new per-tick bus event.

## Goal

Build the runscript rows (name, system schedule count, editor-open flag) in one function. Publish a `runscripts` change signal from the scheduler's one-second tick, only when the rows differ from the last published set and only while a scripts tab is open. The topic source that delivers the signal to the plugin lands in `04-runscripts-topic-and-actions`.

## Design decisions and dependencies

This subplan depends on `01-runscript-file-operations` for `listRunscriptNames`, and on nothing else. The bus union, the protocol file, the `runscriptFilePath` export, the rows module, and the refresh module need nothing from `04`. They land first, in that order, so each step typechecks, and `04` builds on them. The `manager.ts` emission needs only the bus union. The host wiring and its test name `runscripts` as a notification topic. That name is a member of `TabPluginNotificationTopic` only once subplan `04` adds it to `src/plugins/api-topics.ts`, so the host wiring lands with that change. Nothing this subplan adds is visible until a plugin declares `runscripts` in its notifications (subplan `05`).

- The tick is `ScheduleManager.tick` in `src/schedule/manager.ts`. `start()` drives it with `setInterval` every 1000 ms, and `start()` is called at startup from `src/index.ts`. `tick` has no other caller. The method emits a `changed` event only when a schedule changes (`announceChange`, reached only under the `changed` flag), so it needs a per-tick event of its own. The change is one line at the end of `tick`, after the `systemSchedule` call: `messageBus.emit('schedules', { type: 'tick' })`. Rejected: a second interval timer, which the source plan rules out by asking for the scheduler's tick, and a callback list on `ScheduleManager`, because the message bus is the existing way these signals travel.
- `ScheduleManager` is at 198 code lines against the 200-line `max-lines` limit, where blank and comment-only lines do not count (`src/schedule/manager.ts` before this change). The emission adds one line, so the file is at 199 after the change. That emission is the only edit this subplan makes to `manager.ts`. If the implementer finds it needs a second line there, that is a change to this plan: the extra code goes into a helper module, and the plan is updated first.
- The refresh is a host subscription created in `subscribeHostChannels` (`src/plugins/host-channels.ts`). That function already owns the host's channel subscriptions and returns them, and `TabPluginHost.dispose` releases them through its `subscriptions` list. The subscription is taken only when some declaration in `declarations` lists `runscripts` in its `notifications` field (`TabPluginDeclaration.notifications`, typed `readonly TabPluginNotificationTopic[]`, `src/plugins/api.ts:87`). That is the rule the file states for every channel: a build in which no plugin wants a channel takes no subscription for it. The host also builds a predicate over plugin ids. It finds the declaration whose `id` equals the given id and reports whether that declaration's `notifications` include `runscripts`. The predicate is handed to the refresh, which asks only that question. The refresh therefore never receives the declaration list, and `src/schedule/system` imports nothing from `src/plugins`, which no schedule module does today. Rejected: putting the refresh on `Managers`. That would add a manager, a dispose-order entry, and a creation step for a single subscription.
- The source plan says the refresh "starts" with the first scripts tab and "stops" with the last. This is the one place the subplan changes the source plan's wording, and it keeps the behavior the source plan asks for. The plugin API has no tab-close hook: the only activation callback that releases a plugin's work is `dispose`, which runs when the plugin is disposed or disabled, and this subplan adds no hook. The subscription is created once, when the host is built. A tab is admitted when its `plugin` record (`Tab.plugin`, with `PluginTabRecord.id`) has an id the predicate accepts. The id is matched to the declaration id the same way `src/plugins/host-state.ts` matches tabs to declarations (line 72). The refresh does work only while an admitted tab is open. On a tick with no admitted tab, it clears its last-published rows and returns before it reads `managers.systemSchedule` or the file system. That is the same as starting and stopping in effect. Subplan `05` must not start or stop the refresh from the plugin's activation. A disabled plugin needs no special case, because the `disable` method of `TabPluginHost` in `src/plugins/host.ts` closes that plugin's tabs through `closePluginTabs` before it disposes the activation, so the gate sees no tab. Rejected: a refresh that reads the directory for the whole session, which the source plan rejects.
- On each tick with an admitted tab open, the refresh builds the rows through `readRunscriptRows`, which the topic read in `04` also uses. It compares them with the last published rows, element by element over name, schedule count, and open flag. It emits `runscripts` `changed` only on a difference. The refresh gets its names from `listRunscriptNames` and never calls `catalogRunscripts`, `readRunscript`, or `ensureScriptsDirectory`. Each of those writes the Git exclusion through `ensureSystemScheduleExcluded`, and a tick would repeat that write every second. `listRunscriptNames` writes nothing.
- Rows keep the order `listRunscriptNames` returns. That function already sorts by name with `localeCompare` (`src/schedule/system/runscript-files.ts`, `listRunscriptNames`), and `readRunscriptRows` does not sort again, so the comparison has one defined order.
- `listRunscriptNames` throws, rather than returning an empty list, when `.janissary` or `.janissary/scripts` is a symlink (`assertDirectory` in `runscript-files.ts`). `readRunscriptRows` catches any error from that call and returns the empty view, which is the same empty result `cachedRunscripts` gives. It writes nothing to stderr, because a report on every tick would fill the output once a second. The tick handler must not throw. A throwing bus listener is caught by the bus and written to stderr, but the refresh should not depend on that.
- The schedule count for a row is the number of entries in `managers.systemSchedule.list()` whose `script` equals the row's name. That list is copies of the in-memory entries (`src/schedule/system/manager.ts`, `list`), and each entry carries its `script` field (`SystemScheduleEntry` in `src/schedule/system/types.ts`).
- The open flag is true when some tab in `managers.tab.tabs` has an `editor` whose `path` equals `runscriptFilePath(launchDir, name)`, where `launchDir` is `managers.tab.launchDir`. `runscriptFilePath` is a new export of `src/schedule/system/runscript-files.ts` (see Proposed changes). It returns the path `readRunscript` returns as `file`, with no file access and no Git exclusion, so the tick never calls `readRunscript`. The comparison is exact string equality, which is how `openEditorTab` finds an existing tab for the same file (`src/tab/open-editor-tab.ts`, the `tab.editor?.path === view.path` test). An editor stores the path it is given. `editResolved` in `src/open/file-manager.ts` makes a relative target absolute with `path.resolve` against the origin tab's working directory before it reaches `openInEditor`, which stores that path. Subplan `04` must therefore open a runscript with the absolute `runscriptFilePath` result. A relative `.janissary/scripts/<name>.rs` would resolve against the origin tab's working directory, and it would store a path the flag never matches when that tab is not at the project root.
- The row and payload types (`RunscriptRowView` with `name`, `schedules`, and `open`, and `RunscriptsView` as `{ rows }`) live in a new `src/protocol/runscripts.ts`, which follows `src/protocol/schedule.ts`. `src/protocol.ts` re-exports them in one type-only line, placed beside the `./protocol/schedule.js` re-export at line 75, as the schedule views are.
- `cachedRunscripts` in `src/state/listings.ts` is not reused. Its one-second TTL would add up to a second of lag on top of the tick, and it reads the listing through `catalogRunscripts`, which writes the Git exclusion on every call.

## Proposed changes

- In `src/schedule/manager.ts`, the `tick` method emits `{ type: 'tick' }` on the `schedules` channel as its last statement, after the `systemSchedule` call. One line, taking the file from 198 to 199 code lines.
- In `src/bus.ts`, `ScheduleEvent` becomes a union of `changed` and `tick`, and `tick` gets a one-line comment saying it is raised on every scheduler tick, changed or not. No consumer changes. The one `changed` listener, the `schedules` topic source in `src/plugins/topics.ts` (`subscribe`, whose `fire` takes no argument), accepts the wider event type, and the bus selects listeners by type, so a `tick` never reaches it. Nothing switches on `ScheduleEvent`, and the type is not exported. `BusChannels` gains `runscripts` with a `{ type: 'changed' }` event.
- In `src/protocol/runscripts.ts` (new), define `RunscriptRowView` and `RunscriptsView`, following the one-file-per-domain pattern of `src/protocol/schedule.ts`. In `src/protocol.ts`, add one type-only re-export line for it.
- In `src/schedule/system/runscript-files.ts`, export `runscriptFilePath(projectRoot, name)`. It returns the runscripts directory joined with `<name>.rs`, the value `readRunscript` builds for `file` today. `readRunscript` takes its `file` value from this function, so the two cannot drift. The helper does no file access and no Git exclusion. Name validation stays with `readRunscript`, because the tick passes only names that `listRunscriptNames` returned, and that function already filters with `isRunscriptName`.
- In `src/schedule/system/runscript-rows.ts` (new), define `readRunscriptRows(managers)`, which returns a `RunscriptsView`. It calls `listRunscriptNames` inside a catch, counts system schedules per name, sets each open flag from the editor tabs, keeps the order the listing returned, and returns an empty view when the listing throws. Put the pure part in a separate function that takes the names and two lookup functions, one giving the schedule count and one giving the open flag, so the rules can be tested without fake managers.
- In `src/schedule/system/runscript-refresh.ts` (new), define `createRunscriptRefresh(managers, listens, publish)`, which returns an object with `tick()` and `dispose()`. `listens` is the plugin-id predicate described under Design decisions. The refresh keeps the last-published rows in a closure. `tick()` checks the gate first. A tab is admitted when it has a plugin record and `listens` accepts that record's id. When no tab is admitted, `tick()` clears the stored rows and returns without touching `managers.systemSchedule` or the file system. When an admitted tab is open, it builds the rows with `readRunscriptRows`, compares them with the stored rows, and calls `publish` only on a difference. `dispose()` sets a flag that makes every later `tick()` return at once. The `publish` argument defaults to emitting a `runscripts` `changed` event, so tests can inject a spy. Also define `subscribeRunscriptRefresh(managers, listens)`, which subscribes to the `schedules` `tick` event, calls the refresh's `tick`, and returns a `Subscription` whose `unsubscribe` removes the bus listener and then calls `dispose`.
- In `src/plugins/host-channels.ts`, build the plugin-id predicate from `declarations`, and add `subscribeRunscriptRefresh(managers, predicate)` to the subscriptions it returns, only when some declaration lists `runscripts` in its notifications. Otherwise the returned array is unchanged. This edit lands with subplan `04`'s topic-union change (see Design decisions).

## Tests

- In `src/schedule/system/runscript-refresh.test.ts` (new), using a temporary project directory made with `mkdtempSync` under `tmpdir()` and removed in a `finally`, as `src/schedule/system/runscript-files.test.ts` does. The fake managers object carries `tab.tabs`, `tab.launchDir`, and `systemSchedule.list`, and it is cast to `Managers` the way `makeManagers` in `src/schedule/manager.test.ts` is. The `listens` argument is a plain function over plugin ids, so each test passes one that accepts the id of its open tab, or one that rejects it:
  - With no admitted tab open, a tick reads nothing and publishes nothing. A `vi.spyOn` on `listRunscriptNames`, through a namespace import of `./runscript-files.js`, shows it, as `src/schedule/system/manager.test.ts` spies on `firing` through `import * as firing`.
  - An open tab whose plugin id `listens` rejects does not admit the refresh. A tick reads nothing and publishes nothing, even when runscripts exist on disk.
  - The first tick with an admitted tab open publishes when at least one runscript exists, and publishes nothing when none exist.
  - A new file found on a tick publishes once. The next tick with no change publishes nothing.
  - A removed file publishes.
  - A change in a row's system schedule count publishes. A change in its open flag publishes.
  - After the last admitted tab closes, the next tick publishes nothing and clears the stored rows. Reopening publishes the current set again.
  - A symlinked `.janissary` produces an empty list and does not throw from `tick`.
  - After `dispose`, further ticks publish nothing.
  - `subscribeRunscriptRefresh` is driven by `messageBus.emit('schedules', { type: 'tick' })`, and unsubscribing stops that.
- In `src/schedule/system/runscript-rows.test.ts` (new): rows come back sorted by name; counts match only entries whose `script` equals the name; the open flag matches an editor tab on the same absolute path and not on a different file; the listing failure returns an empty view.
- In `src/schedule/manager.test.ts` (existing), in the `ScheduleManager tick` block under fake timers: start the manager, advance one second, and count the `schedules` `tick` emissions through a `vi.spyOn(messageBus, 'emit')` spy restored with `mockRestore()`, as the emit tests in that block already do. One tick emits `tick` once. A tick that fires nothing emits no `changed`, and a tick that fires an entry still emits `changed`, as before.
- In `src/plugins/host.test.ts` (existing): a host built with a fixture declaration whose `notifications` include `runscripts`, under any id, publishes `runscripts` on a `schedules` tick while an open tab's plugin id is that declaration's id. The temporary launch directory holds one runscript. After that host's `dispose`, the same tick publishes nothing. A host built with a declaration whose `notifications` do not include `runscripts` publishes nothing on that tick. Each test disposes the hosts it builds, so no refresh subscription outlives its test.

## Out of scope

- The `runscripts` topic source, its action module, and the plugin. Those are in `04` and `05`. Until 04 lands, the `runscripts` channel has no listener, which is harmless.
- Any change to the tick interval, to firing, or to the way `ScheduleManager` fires entries.
- A file watcher, and any refresh that runs with no admitted tab open.
- Any start or stop call for the refresh from a plugin's activation. The subscription is created by the host and gated by declaration and tab state (see Design decisions).
