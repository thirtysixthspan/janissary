# Remote run clone request lifecycle
**Complexity: 7/10** — ~150 added production lines, 8 existing files, 16 requirements, 104 scenarios (p=7.38)

## Goal

Add the client `run-clone` request and server `run-clone-result` response over the caller's existing channel. A create succeeds only after the far-side clone is ready and returns its directory; a release succeeds without a directory. Register strict wire decoding and correlate each result, including termination and send-failure settlement for a create that has no deadline.

Source: `product/plans/complete/subagent.md`, preserved unchanged as the canonical feature record. This is ordered subplan 15 of 23.

## Implementation steps

1. In `protocol-frames.ts`, define shared `RemoteRunCloneAction` as the two literals `create` and `release`. Add a client `run-clone` member carrying required string `id`, that `action` and string `label`. Add server `run-clone-result` carrying required string `id` and three mutually exclusive result shapes: `dir` only, neither `dir` nor `error`, or `error` only. Express the alternatives in the TypeScript type so directory-plus-error is not a legal produced frame. Neither reply action nor label is added to the wire. Add one entry to each directional catalog. Keep the pair out of `ChannelFrame` and `CHANNEL_FRAME_KEYS`: these are request replies, not tab notifications or addressed ACP traffic.

2. Add `decodeRunClone` and `decodeRunCloneResult` beside agent resolution in `decode-agent.ts`, then route both through the exhaustive `decodeKnownFrame` switch. Request `id` and `label` must pass `nonEmptyString`; `action` must be exactly one of the two literals. Result `id` must be nonempty; supplied `dir` or `error` must be nonempty strings and cannot coexist. An id-only result is valid release completion. Reject missing required fields, nulls, wrong types, empty supplied fields and invalid combinations with `Malformed remote frame "run-clone".` or `Malformed remote frame "run-clone-result".`. Construct only declared properties and preserve admitted values exactly, without trimming, path normalization or extra base64 handling. Wire syntax accepts a nonempty label; plan 14's service applies `workspaceLabelError` before any path or manager side effect. A reply carries no action, so decoding alone cannot reject a release-shaped reply to a create; the request owner does that in step 3.

3. Add `RemoteAgentRequests.runClone(action, label, send)` returning `Promise<string | undefined>` and taking the shared action type. Use a second `PendingRequests` instance typed from the shared `run-clone-result` server member, separate from `AgentSnapshot` requests. Mint a fresh UUID and register before sending so synchronous loopback replies work. Create opens with no deadline or timer; release opens with a 15,000 ms deadline and rejects with `Remote run clone release timed out.`. Capture the action in that request's result continuation, avoiding another action-by-id map. A create resolves to its nonempty directory; release resolves to `undefined`; an error reply rejects with its exact message. Reject a create's id-only reply with `Remote run clone create returned no directory.` and a release's directory reply with `Remote run clone release returned an unexpected directory.`. These settle only the owning request and do not fault the channel. Widen the existing `resolve` input to the two shared reply types and dispatch by the discriminant, so equal ids across the two families cannot cross-settle. Unknown, duplicate and late replies remain no-ops. Extend `failAll` to drain both stores with the supplied message.

4. Catch synchronous `send` throws in both tracker request methods, fail that request's registered entry and return the tracked rejected promise instead of leaving an unreachable pending promise. Preserve an `Error` object; use `errorText` from `src/error-text.ts:1` to wrap other thrown values. Settlement still happens once if the sender answered synchronously before throwing. A failed create send has no timer that could eventually rescue it, so immediate removal of its pending entry is required. Neither send failure nor near-side timeout synthesizes a remote release: the far side may have received the request, and plan 14 deliberately retains clones across lost transport until its shutdown.

5. Add one `RemoteChannel.runClone(action, label)` method with the same `Promise<string | undefined>` result. Like `resolveAgentSnapshot`, reject with `Remote connection unavailable.` before registration or sending unless the channel is fully attached, including during authentication, reconnection and the attaching hold window. Extend the existing one-line agent-result route at `index.ts:230` to pass both result types to `agentRequests.resolve`; keep process, navigator, ACP and tab routing intact. Existing `disconnect` rejects pending requests with `Remote session detached.`, `finish` with `Remote session ended.`, and either `closed` branch with `Remote connection lost.`. Add immediate `failAll('Remote connection lost.')` to `close`, marking the channel closed before callbacks or transport kill; in `fail`, mark closed and drain with that protocol-failure message before invoking `onError` or killing the transport. Move `finish`'s existing drain before its outbound shutdown sequence so a throwing shutdown write cannot strand an earlier create. The request is never replayed after transport replacement; a later fresh call gets a new id. Preserve the existing once-only `onClose`, reconnect and shutdown-drain behavior.

6. `channel/index.ts` currently has 192 ESLint-counted lines. The facade plus immediate termination settlement approaches its ceiling, so extract its existing eight-line filesystem-reply/event block at lines 222–229 into `dispatchNavigatorFrame` in the existing `channel/dispatch.ts`. It takes the decoded `RemoteFrame` and a readonly map of `NavigatorListener`, returns true for those two discriminants even without a listener and false for everything else. Replace the block with one dispatch line at the same position, preserving addressed routing and unknown-session no-ops. This removes seven counted lines before adding the roughly eight facade/lifecycle lines, leaving approximately 193–196 counted lines and headroom below 200 after plan 6, which adds no lines to this file. The current counted sizes of the other touched modules are 168 in protocol-frames.ts, 44 in decode-agent.ts, 88 in frame/decode.ts, 24 in agent-requests.ts, 14 in channel/dispatch.ts and 85 in protocol.ts. Their additions fit below 200; the dispatcher produced by plan 14 also has room for this one request case and its small async helper. Recount all touched production files after the cumulative dependencies land.

7. Extend plan 14's `dispatchAcpFrame` with exactly the client `run-clone` discriminant and a local async `answerRunClone` helper. Return true immediately for the request, leaving clone readiness asynchronous so a release request can arrive while create is pending. Without a provisioned owner, emit one correlated `run-clone-result` error `No remote workspace has been provisioned.`; do not send only `workspace-failed`, which would leave the unbounded request waiting. With an owner, invoke only `runClones.create(label)` or `runClones.release(label)` and map the service's directory-only, empty or error-only result to the same request id. Preserve nonempty service error text; use `Remote run clone <action> failed.` if a failure has no text. Convert an unexpected synchronous service throw or rejected promise through `errorText` to the same error shape, observing the async work. Reuse all semantic validation, readiness, collision, cancellation and release ownership from plan 14. Do not call `provisionRemoteWorkspace` again or rebuild those mechanisms.
