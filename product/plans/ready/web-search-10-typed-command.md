# Web search 10: the typed `web search` command, `searchWebInTab`, and `help web`

**Complexity: 6/10** — ~55 added lines, 13 requirements, 17 test scenarios across the local, remote, and notification paths, 2 production files edited (p=5.89)

The tenth slice of the `web search` feature (source plan: `./product/plans/complete/web-search.md`). It is the first one a person can use. A new `web` command in the command registry claims every `web` line and runs `searchWebInTab`, which parses first, then searches on the side that owns the tab: a local tab calls `webSearch` with this machine's tokens and the global `fetch`; a remote tab sends the `web-search` operation through the tab's remote port and never falls back to the local machine. A provider disabled on the local side posts one notification. The command gets its Commands-tab row, a `help web` page, and the feature's behavior spec.

## Design decisions

Carried verbatim from the source plan where they apply.

- **Command (feature text, extended by user decision).** `web search <query> [--results n] [--max-chars n] [--depth basic|advanced] [--provider name]`, a typed application command.
- **The `web` command.** `src/commands/web.ts` (new), modeled on `src/commands/file.ts`: `name: 'web'`, `match` is `isWebCommandLine`, `run` awaits `searchWebInTab(managers, tab.label, command_)` with no signal (a typed search is not cancellable) and appends `{ input: command_, output }` with `appendCommandOutput(managers, tab.label, …, invocation)` (`src/command/append.ts`), exactly as `file.ts`'s `run` does. Samples `web`, `web search node.js permission model 2026`, and `web search rust async --results 5 --depth advanced` (`src/commands.test.ts` requires every command to have samples that match; bare `web` pins that the command claims it). Registered in `src/commands/index.ts`: imported as `command as web` from `./web.js`, and placed in `coreCommands` directly after `files`. No earlier entry matches a `web` line and no bundled plugin claims `web` (checked against every `src/plugins/*/manifest.ts` `command:`), so `findPriorityConflicts` stays empty.
- **Commands-tab row.** `src/application-commands.ts`'s `BUILTIN_FORMS` gains `web: { name: 'web', forms: ['web'] }`, as `file` has, so the `web` command has its own Commands-tab row and the native `web search` row (`./product/plans/ready/web-search-12-acp-tool.md`) has a parent to sit under. `builtinRows` turns a one-form declaration into one parentless row, as it does for `file`. Disabling `web` in the Commands tab refuses every typed `web` line with the existing `Command is disabled: <command>.`; nothing new is written for that.
- **`searchWebInTab(managers, label, line, signal?)`.** Shaped like `globFilesInTab` (`src/file-glob/tab-glob.ts`): parse first, returning the usage line without touching anything (no `managers.tab.byLabel` lookup, no port, no `webSearch` call); then `localReadRoot(managers, label)` (`src/file-read/tab-read.ts`) decides the side — a defined root is a local tab, so call `webSearch` with `getProjectTokens()`, the global `fetch`, the signal, and a `reportDisabled` that calls `notify(managers, 'plugin-failure', label, …)`; an undefined root is a remote tab, so send the `web-search` operation through `withRemoteTabPort(managers, label, 'web-search', …)` and return its text. A rejected remote request prints its message unchanged, as `globRemotePaths` does through `rejectionLine`, which is how the existing connection lines reach the user. The `signal` parameter exists for the ACP route in `./product/plans/ready/web-search-11-workspace-routes.md`; the typed command never passes one. Resolves to `Promise<string>`.
- **Local side (decision).** `localReadRoot` treats an unknown label or a tab without a workspace as local (it falls back to `managers.tab.launchDir`); the root's value is not used, only whether it is defined, because a search reads no files. The deps object is `{ tokens: getProjectTokens(), fetch: globalThis.fetch, signal, reportDisabled }`, `signal` possibly `undefined`. The local call is not wrapped in a `try`: without a signal `webSearch` does not reject, and with one (slice 11) its abort rejection must reach the ACP loop unchanged so the cancelled step is suppressed.
- **Remote side (decision).** A private `searchRemote(managers, label, parsed)` in the same module, shaped like `globRemotePaths`: inside `withRemoteTabPort(managers, label, 'web-search', async (port) => …)` it returns `await port.webSearch(parsed)`, and on a rejection returns `errorText(error)` (`src/error-text.ts`). `rejectionLine` is not used, because its extra cases (`OUTSIDE_ROOT_REASON`, a typed path) do not apply to a path-free operation and for every other error it returns exactly `errorText`'s message. So `The remote connection ended.`, `The remote machine did not answer in time.`, `The remote file navigator is closed.`, and a far-side error reply all print as their message. `Remote connection unavailable.` is `withRemoteTabPort`'s own return value (`REMOTE_UNAVAILABLE`), not a rejection. The remote side ignores `signal`: the operation has no cancel message (slice 8), and slice 11's loop suppresses the late result. The workspace argument `withRemoteTabPort` passes is not used.
- **Where a typed search runs (user decision).** A local tab's typed search runs on the machine running Janissary, and a remote tab's typed search runs on the remote machine, as `file read` and `file glob` do for a remote tab, so a person and an agent in the same tab get the same providers and tokens. A remote tab's typed search never falls back to the local machine; a dropped or slow connection prints the existing lines `Remote connection unavailable.`, `The remote connection ended.`, or `The remote machine did not answer in time.`.
- **Disabled-provider notification (user decision).** When the registry disables a provider during a local search, one notification, `Web search provider "<name>" disabled: <reason>.`, appears in the notifications tab, as editor plugin failures do. `searchWebInTab`'s `reportDisabled` formats that line and posts it with `notify(managers, 'plugin-failure', label, message)`, the same call `editorPluginFailed` makes in `src/controller/editor-adapter.ts` (`Editor plugin "${plugin}" disabled: ${reason}.`). It does not append the line to the tab's transcript: the search's own output already carries the failure line. `plugin-failure` is an explicit event (`EXPLICIT_EVENTS` in `src/notifications/index.ts`), so it is not focus-suppressed. A remote search posts nothing; the reason appears only in the far side's failure lines.
- **Cancellation (user decision).** A typed search has no cancellation and runs until it answers or times out.
- **Output (user decision).** The typed command and the agent's tool result print the same text.
- **No provider configured (user decision).** `help web` documents where the token files go.
- **Behavior spec.** `product/specs/web-search.md` (new) is the behavior spec for the whole feature: grammar, pipeline, output, every message, providers, tokens, where a search runs. The ACP sections it needs are added by `./product/plans/ready/web-search-12-acp-tool.md`, and a completion section by `./product/plans/ready/web-search-14-completion.md`; this slice writes the typed-command sections only and links `[[acp]]`, `[[remote-server]]`, and `[[workspaced-agent]]` where those specs own the detail.

## Proposed changes

All relative imports carry `.js`; type-only imports use `import type`.

- **`src/web-search/tab-search.ts`** (new, ~30 counted lines) — `searchWebInTab` and the private `searchRemote` as decided above. - **`help/web.md`** (new) — headed `### web`, in `help/file.md`'s shape: the usage line exactly as `WEB_SEARCH_USAGE`; every flag with its range and default (`--results` 1–20, default 10; `--max-chars` 200–100000, default 10000; `--depth basic|advanced`, default `basic`, `advanced` costs more on Tavily and is ignored by TinyFish; `--provider`, default `auto`, names matched case-insensitively); the query rule (up to the first `--` word, quotes and `site:`/`-site:` kept); the output format (`- [<title>](<url>)` with a two-space-indented snippet line, no header) and the truncation note `(showing <k> of <n> results; raise --max-chars for more)`; every failure line (usage, `Web search: no provider configured.`, `Web search: provider "<name>" is not configured.`, `Web search: unknown provider "<name>" (available: auto, tavily, tinyfish).`, `Web search failed (<name>): <reason>.`, `Web search: every provider failed.` with its `- <name>: <reason>` lines, `No results for "<query>".`, and the three remote connection lines); auto-selection and fallback in one short paragraph; token setup for each bundled provider (`tavily-token`, `tinyfish-token` in the project's `.janissary/` or `~/.janissary/`, project first, read at startup so a new file needs a restart); that a provider disabled after a plugin failure stays disabled until restart and posts one notification; and where a search runs on a remote tab (the remote machine, with that workspace's tokens, forwarded tokens winning over the remote's own files). It does not cover the agent tool; slice 13 edits `help/ask.md` and `help/tell.md`.
- **`help/commands.md`** — one table row for `web`, after `video` (the table is alphabetical): `` | `web` | `web search <query>` searches the web through a configured provider (Tavily or TinyFish) and prints a Markdown list of results; see `help web` | ``.

- **`product/specs/application-commands.md`** — after the paragraph on the native `file` rows ("The native `file read`, `file glob`, …"), one sentence: the builtin `web` command has its own parentless row, and disabling it refuses every typed `web` line. - **`product/specs/notifications.md`** — in the `plugin-failure` entry ("a tab plugin is disabled after a fatal failure"), add that the event also carries `Web search provider "<name>" disabled: <reason>.` when a local search disables a provider, attributed to the tab the search ran in, and link `[[web-search]]`.

## Tests

- **`src/web-search/tab-search.test.ts`** (new, vitest `server` project) — `vi.mock('./search.js')` with a `webSearch` mock resolving to a fixed string; `vi.mock('../file-read/remote-tab-port.js')` with a `withRemoteTabPort` mock that either returns `'Remote connection unavailable.'` or calls the callback with a fake port `{ webSearch: vi.fn() }`; `vi.mock('../notifications/index.js')` for `notify`; `vi.mock('../project/tokens.js')` with `getProjectTokens` returning a fixed object; fake managers as in `tab-glob.test.ts` (`FakeTab` with `remote?: unknown`, recording `byLabel` lookups). Cases:
  - Every usage form (`web`, `web foo`, `web search`, `web search x --results 30`) returns `WEB_SEARCH_USAGE`, with no `byLabel` lookup, no `withRemoteTabPort` call, and no `webSearch` call.
  - A local tab (with a workspace, and with none) calls `webSearch` once with the parsed command and deps whose `tokens` is the mocked object and whose `fetch` is `globalThis.fetch`, and returns its text; the given signal is passed through, and no signal leaves `signal` undefined.
  - The local deps' `reportDisabled('tavily', 'provider failed: boom')` calls `notify(managers, 'plugin-failure', <label>, 'Web search provider "tavily" disabled: provider failed: boom.')` once.
  - A local `webSearch` rejection (an abort) propagates unchanged.
  - A remote tab calls `withRemoteTabPort` with the label and `'web-search'`, calls `port.webSearch` with the parsed command, returns its text, and never calls the local `webSearch`.
  - A missing remote connection returns `Remote connection unavailable.` without calling `webSearch`.
  - A port rejecting with `The remote connection ended.` or `The remote machine did not answer in time.` returns that message unchanged.

## Verification

- `$janissary/scripts/run.mjs check-diff`
- Manual, in a scratch project started with `node bin/janus.mjs --no-open <project>`, with `~/.janissary/tavily-token` present and no TinyFish token:
  1. Run `web search node.js permission model 2026 --results 3`. Expect three `- [<title>](<url>)` lines, each with an indented snippet line.
  2. Run `web search node.js --provider tinyfish`. Expect `Web search: provider "tinyfish" is not configured.`.
  3. Run `web search node.js --provider bing`. Expect `Web search: unknown provider "bing" (available: auto, tavily, tinyfish).`.
  4. Run `web search node.js --results 30`, and bare `web`. Expect the usage line for both.
  5. Run `web search node.js permission model --max-chars 200`. Expect fewer results and the `(showing <k> of <n> results; raise --max-chars for more)` line.
  6. Run `help web` and confirm the page; run `commands` and confirm a `web` row.
- Manual, remote: open a remote agent tab (`agent on <host> in a tab execute <task>`, see `help agent`) on a host whose `~/.janissary/` has its own `tavily-token`.
  1. In that tab run `web search node.js --results 3`. Expect results, served by the remote's token even with no local token file.
  2. On the remote, give both providers a token and point `api.tavily.com` and `api.search.tinyfish.ai` at a non-routable address (for example `10.255.255.1` in `/etc/hosts`) so each attempt hangs. Run `web search node.js`. After about 60 seconds expect `Web search: every provider failed.` with `- tavily: timed out after 30 s` and `- tinyfish: timed out after 30 s`, not `The remote machine did not answer in time.` (the long-running deadline from slice 8). Restore `/etc/hosts`.
  3. Drop the connection mid-search and expect `The remote connection ended.`.
