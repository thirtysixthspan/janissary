# Add a `file patch` command for ACP tell sessions

**Complexity: 8/10** — ~680 added lines, 16 files edited, 36 requirements, 50 test scenarios (p=8.29)

`file patch` lets a person or an autonomous ACP agent apply one multi-file change in a single operation: add, update, move, or delete several files at once instead of issuing a separate `file write` or `file edit` for each. The change is a marker-delimited patch text (`*** Add File: <path>`, `*** Update File: <path>`, `*** Delete File: <path>`), applied as one logical transaction: every section applies or none does, so a failed hunk never leaves the tree half-changed. It joins `file read`, `file glob`, `file write`, and `file edit` as a fifth subcommand of the existing `file` command and the existing ACP file tool, and it runs against the same root those commands use — the local workspace, the launch directory, or a remote tab's remote clone — never falling back to the local machine for a remote tab. It lets an agent batch a refactor, such as renaming a module across many files or scaffolding a feature's file set, into one concise, reviewable operation.

## Design decisions

Each decision comes from the feature text, from existing behavior ("from precedent"), or from a user answer ("user decision").

- **Command name.** `file patch`, a subcommand of the existing `file` command (`src/commands/file.ts`), alongside `file read`, `file glob`, `file write`, and `file edit`.
- **Who can run it.** A native ACP command available to `tell` sessions (feature text), and also a typed application command, matching how `file write` and `file edit` are both.
- **Default grants (user decision).** The built-in `tell` role grants `file patch` beside `file write` and `file edit`, going to fourteen commands; the built-in `ask` role does not grant it. Saved roles files are not changed and keep the grants they list.
- **Input form (user decision).** `file patch <JSON>`, where the JSON is one object `{"patchText":"<text>"}` kept on one line with newlines written as `\n`, the same grammar, extraction, and escaping rules as `file write` and `file edit`. No raw multi-line form.
- **Envelope (user decision).** `*** Begin Patch` as the first line and `*** End Patch` as the last line are optional; the text is accepted with or without them, and the primer shows them.
- **Operations.** At minimum add, update, and delete, with a move expressed as a delete of the old path paired with an add of the new path (feature text).
- **Move marker (user decision).** An `*** Update File: <old>` line may be followed directly by `*** Move to: <new>`, optionally followed by hunks, which renames the file and applies the hunks in one section without re-sending the file's content. Delete-plus-add remains a valid way to move.
- **Add sections.** The body after `*** Add File: <path>` is the complete new content of the file, written with every line prefixed by `+` (user decision), as in the Codex and opencode formats, so a content line beginning with `***` is never mistaken for a marker. A body line without the `+` prefix is a malformed-patch error. Adding a path that already exists is an error, unless an earlier section of the same patch deletes or moves away that path, which is how a patch overwrites a file (user decision); the same rule applies to a `*** Move to:` target. There is no overwrite flag. Missing parent folders are created (feature text).
- **Empty sections (user decision).** An Add with no `+` lines creates an empty (zero-byte) file. An Update with neither hunks nor a `*** Move to:` line is `Malformed patch at line <n>: Update File needs a hunk or Move to`, an additional structural problem beside those under Failure wording.
- **Update sections.** The body after `*** Update File: <path>` is a set of `@@` / context / `-` / `+` hunks naming exactly which lines are removed and inserted. A hunk that does not cleanly match the current file content is an error (feature text).
- **Match strictness (user decision).** A hunk's context and `-` lines are first matched against the file exactly; if there is no exact match, the search is retried ignoring trailing whitespace on each line. No further fuzzing (trimmed lines, Unicode punctuation folding).
- **Hunk placement (user decision).** Hunks are searched in order, each search starting after the previous hunk's matched position. An `@@ <text>` header first moves the search to the next line equal to `<text>` (under the same exact-then-trailing-whitespace rule); a bare `@@` does not move it. The first match wins — Codex semantics, so models' existing habits work.
- **Line endings (user decision).** An updated file keeps its existing line ending (a CRLF file stays CRLF, judged from the file's first line ending) and its existing final-newline state. An added file is written with LF line endings and a final newline. An `*** End of File` line inside a hunk anchors that hunk to the end of the file. There is no `\ No newline at end of file` marker.
- **Delete sections.** `*** Delete File: <path>` has no body. Deleting a path that does not exist is an error (feature text).
- **Section order (user decision).** Sections apply in order against an in-memory view of the tree, so a later section sees what earlier sections produced: the same path may appear in several sections (two Updates apply one after the other; an Update then a Delete removes the file), and Delete-then-Add is how the overwrite rule works. Nothing touches disk until every section has applied to the view.
- **Atomicity.** All sections apply as one transaction; any failed section fails the whole patch and the tree is left exactly as it was (feature text).
- **Links and permissions (user decision).** As write and edit: an Update writes through an in-root symbolic link to its target (via `resolveMutationTarget`); a Delete removes the link itself, never its target; a `*** Move to:` renames the link; an Update keeps the file's permission bits; an Add gets default permissions. No mode marker.
- **Emptied folders (user decision).** A folder left empty by a Delete or a Move stays in place; the patch only touches files. A restore after a failure while applying does remove folders the patch itself created.
- **Exact content.** Indentation and newlines in the bodies are preserved exactly (feature text).
- **Success output (user decision).** A header `Patched <n> files:` (`Patched 1 file:` for one) followed by one git-style row per path in order of its first appearance in the patch: `A <path>` for a path that did not exist before and does now, `M <path>` for one that existed before and after, `D <path>` for one that existed before and does not now, and `R <old> -> <new>` for an `*** Move to:` section. Each path is listed once with its net change; a path added and then deleted by the same patch gets no row. File content never appears. Paths are shown as typed, escaped by `displayPath` like write/edit lines.
- **Failure output (user decision).** One line naming the first failing section by its 1-based number and its marker, the reason, and for a hunk mismatch the hunk's first context or `-` line, then `No files were changed.`, e.g. `Patch failed at section 2 (Update File: src/a.ts): No matching text for hunk starting "const x = 1;". No files were changed.` Sections are checked in order and the first failure wins.
- **Failure wording (user decision).** Bad or incomplete JSON prints `Usage: file patch <JSON>` and changes nothing. A structural error prints `Malformed patch at line <n>: <problem>. No files were changed.`, where `<n>` is the 1-based line of the patch text and `<problem>` is one of `unknown marker "<line>"`, `Add File lines must start with "+"`, `hunk lines must start with " ", "-", or "+"`, `Move to must follow Update File`, `missing path`, or `no file sections`. A section failure's reason is one of `File not found` (Update or Delete of a missing path), `File already exists` (Add or Move to an existing path), `No matching text for hunk starting "<line>"`, or the write/edit reasons `Outside the workspace`, `Protected file`, `Is a directory`, `Not a text file`, and `File too large (>5 MB)`. Quoted lines are escaped like `displayPath` so the output stays one line.
- **Remote rejection wording (user decision).** A remote rejection that is not one of the connection lines prints `Patch failed: <reason>.`, with the final period not doubled when the reason already ends in one (for example `Patch failed: Invalid remote filesystem operation result.`), and with no promise about the tree, because the far side may already have applied the patch.
- **Size limits (user decision).** The JSON argument is capped at 5 MB (`FILE_POLICY_MAX_BYTES`), checked before the patch text is parsed and printed as `Patch too large (>5 MB). No files were changed.`, and every file a section reads or writes is capped at 5 MB, reported as `File too large (>5 MB)` for that section. There is no cap on the number of sections or on the total written.
- **Failure while applying (user decision).** Every check runs against the in-memory view before anything touches disk, so normal failures change nothing. If a disk operation fails while the validated patch is being written, the files already changed are restored. When the restore succeeds the line is `Patch failed while applying: <reason>: <path>. No files were changed.`; when the restore itself fails it is `Patch failed while applying: <reason>: <path>. Some files may have been changed.`, without listing them.
- **Commit and restore (user decision).** Validation reads each touched file once (bounded at 5 MB by `readBoundedRegularFile`) and keeps its original bytes in memory. The commit then writes each result with `atomicWriteFile`, unlinks deleted paths, and renames moved ones; on a failure it restores the originals in reverse order and removes folders the patch created. No backup files are written to disk.
- **Concurrency (user decision).** Validation and commit run synchronously, with the sync helpers `writeToolTextFile` and `editToolTextFile` already use, so no other server work (another session's patch, an editor save) can interleave with a patch. Outside processes are not guarded, as with write and edit today. A patch is not cancellable once it starts; an ACP cancel suppresses only its late result, as for write and edit. Ceiling: a patch touching many large files blocks the event loop for its whole run; the upgrade path, if that shows up as lag, is running `applyPatchText` in a worker behind the same `FileSystemPort.applyPatch` contract.
- **Result.** A per-file summary of which files were created, modified, or deleted on success; an informative, actionable error on malformed markers, unknown operations, non-matching hunks, or missing files (feature text).
- **Authorization (from precedent).** The ACP gate grants or refuses `file patch` by its native command name, like `file write` and `file edit`: `Command is disabled: file patch.` or `Command not allowed for role "<role>": file patch.`. Every affected path, including a `*** Move to:` target, is subject to the same path rules as `file write` (`resolveMutationTarget`), and `.git` / `.janissary` paths fail with `Protected file`.
- **Paths outside the root (user decision).** A section whose path or `*** Move to:` target resolves outside the root fails the patch with `Outside the workspace`, exactly as write and edit refuse it. The feature text's external-directory permissions are out of scope; Janissary has no such permission.
- **Agent runs (user decision).** Not in this version. `gateAgentCommand` in `src/acp/tool-table.ts` refuses any `file patch` line with `Agent: command not permitted: <command>.`, with or without the `file` grant, as it refuses `file write`, `file edit`, and `file glob`; `runGrantedAgentCommand` in `src/agent/command-tools.ts` refuses the same lines with the same text as defense in depth, so a patch never runs in the caller's directory.
- **Remote tabs (user decision).** A new `apply-patch` mutation operation in `MUTATION_OPERATIONS` (`src/remote/filesystem/operations.ts`) carries the patch text to the far side, which parses, validates, and commits it with the same local runner a local tab uses and returns the output. The transaction runs entirely on the far side, so a dropped connection cannot leave a half-applied patch. `FileSystemPort` gains an `applyPatch` method (local: run in place; remote: send the operation). The remote protocol goes from version 42 to 43, so a version-42 peer is refused at the handshake. Connection failures print the existing lines (`Remote connection unavailable.`, `The remote connection ended.`, `The remote machine did not answer in time.`) and never fall back to the local disk.
- **Workspace root (from precedent and feature text).** The same root as `file write`: a local tab's workspace or project directory, a remote tab's remote clone only (never the local disk), and in the ACP loop the workspace of the host running the loop (`runsOn: 'workspace'`).
- **Primer (user decision).** When a role grants `file patch`, the file tool's primer includes this text after the mutation primer (or after the glob or read primer when no other mutation is granted), separated by a blank line:
  - `To change several files in one step, end your reply with one line:`
  - `file patch {"patchText":"<patch>"}`
  - ``The patch is applied all-or-nothing. Inside it: `*** Add File: <path>` then the new content with every line prefixed by `+`; `*** Delete File: <path>` with no body; `*** Update File: <path>`, optionally `*** Move to: <new path>`, then hunks: an `@@` line (optionally `@@ <a line that comes before the change>`) followed by lines starting with ` ` (unchanged context), `-` (removed), or `+` (added). Give about 3 context lines around each change.``
  - `Example: file patch {"patchText":"*** Begin Patch\n*** Update File: src/a.ts\n@@\n const a = 1;\n-const b = 2;\n+const b = 3;\n*** Delete File: old.txt\n*** End Patch"}`
  - ``A patch answers `Patched <n> files:` followed by one `A`/`M`/`D`/`R` row per file.``
- **Follow-up prompt (user decision).** The prompt that feeds a patch's result back to the agent names the command as `file patch <path>, <path>, …`, listing each section's path (and a `*** Move to:` target as `<old> -> <new>`) in patch order with no content, or bare `file patch` when the JSON or the patch text is malformed. History, transcripts, and recordings keep the full command, as for write and edit.
- **Completion (from precedent).** Command-bar completion does not offer `patch`, as it offers neither `write` nor `edit`; `FILE_SUBCOMMANDS` in `src/completion/file-read.ts` is unchanged.
- **Documentation.** The exact marker format and hunk syntax are documented in the agent primer and `help/file.md` so an agent can author a patch on its first try (feature text).

## Proposed changes

A patch is one more file mutation, so it rides the existing mutation path end to end: anything that already treats `file write`/`file edit` as a mutation (the ACP file tool, both loop hosts, the agent-run refusals, the follow-up-prompt description) picks up `file patch` through one widened predicate, and only the parse/apply core and the remote operation are new.

### New `src/file-patch/` feature directory (server)

- **`command.ts`** — `isFilePatchCommandLine(line)` (`/^file\s+patch(\s|$)/i`), `FILE_PATCH_USAGE` (`Usage: file patch <JSON>`), `FILE_PATCH_PRIMER` (the primer text under Design decisions), and `parseFilePatchCommand(input)` returning the patch text or a usage/size error line. The JSON object takes exactly one key, `patchText`, a string; any other key, a missing key, or a non-string value is a usage error. The 5 MB argument check uses `FILE_POLICY_MAX_BYTES` and prints `Patch too large (>5 MB). No files were changed.`. Also `describePatchCommand(input)` producing the follow-up-prompt form (`file patch <path>, <old> -> <new>, …`, or bare `file patch`).
- **`parse.ts`** — pure `parsePatchText(text)` returning an ordered list of sections (`add` with content lines, `delete`, `update` with an optional move target and a list of hunks) or a `{ line, problem }` structural error. Strips an optional `*** Begin Patch` first line and `*** End Patch` last line; splits on `\n` (a `\r` before it is dropped so CRLF-typed patches parse); recognizes `*** Add File: `, `*** Delete File: `, `*** Update File: `, `*** Move to: `, `@@`, and `*** End of File` lines; every other `*** ` line is `unknown marker`. Paths are taken verbatim after the marker's `: ` with surrounding whitespace trimmed; an empty one is `missing path`.
- **`hunks.ts`** — pure `applyHunks(text, hunks)` returning new text or the first failing hunk's first context-or-`-` line. Implements the exact-then-trailing-whitespace matcher, the sequential search with `@@ <text>` anchors, and `*** End of File` anchoring. It detects the file's line ending (first `\r\n` vs `\n`) and its final-newline state, works on the split lines, and rejoins with the same ending and final-newline state.
- **`view.ts`** — the in-memory tree view: a map keyed by the resolved real path to `{ original: bytes | absent, current: text | absent }`, plus the list of folders the patch will create. Every section path (and `*** Move to:` target) goes through `resolveMutationTarget` (`src/file-write/target.ts`), which already yields `Outside the workspace`, `Protected file`, `Is a directory`, and `Not a text file` reasons; `target.exists === false` on an Update or Delete is `File not found`, and `true` on an Add or Move-to target (unless the view already holds it as deleted) is `File already exists`. A file is read once, on first touch, with `readBoundedRegularFile` (`src/file-write/bounded-read.ts`, which gives `File too large (>5 MB)`) and decoded with `decodeEditableText` (`src/file-write/edit-text.ts`, fatal UTF-8, so non-UTF-8 is `Not a text file`). A leading BOM is stripped before hunks are matched and put back when the file is written, so a first-line hunk matches without the agent typing a BOM; added files are written without one. Resulting text that contains NUL or an unpaired surrogate, or exceeds 5 MB encoded, is refused with the same reasons `encodeToolText` in `src/file-write/filesystem.ts` uses. Each section applies to the view in order and reports its section-numbered failure.
- **Deleting a link, not its target.** `resolveMutationTarget` follows an existing symbolic link to its target (`checkExisting` → `followSymlink`), so its `realPath` is the wrong thing to unlink for a Delete. The view keeps, alongside the policy-checked target, the entry's own location — the canonical parent folder joined with the requested basename, the way `recheckDestination` builds `destination` — and a Delete unlinks that entry. A dangling link is refused by `danglingEntryRefusal` with `Not a text file`, so it cannot be deleted by a patch (the file navigator can).
- **`commit.ts`** — `commitView(view)`: creates the planned folders, writes each changed path with `atomicWriteFile` (`src/atomic-write.ts`, which keeps an existing file's permission bits — the basis for the "Update keeps permission bits" decision), unlinks deleted entries, and carries out a move with `renameSync` (`node:fs`) of the old entry to the new location, followed by the content write through the moved entry when the section's hunks changed it. `renameSync` keeps the moved file's permission bits and keeps a symbolic link a link, which is what the "Move renames the link" decision asks for and what write-new-then-unlink-old would lose; a relative link target is not rewritten, as with `mv`. On any thrown error it undoes the completed steps in reverse order — renames back, and originals restored with `atomicWriteFile` — removes the folders it created (deepest first, only if empty), and returns which of the two "failed while applying" lines applies. Synchronous throughout, using only sync `node:fs` calls, as `writeToolTextFile` is.
- **`apply.ts`** — `applyPatchText(root, text)`: parse, build and apply the view, commit, and format the success rows (`Patched <n> files:` with `A`/`M`/`D`/`R` rows) or failure line. Synchronous; it is what `LocalFileSystemPort.applyPatch` and the far-side operation both call, so local and remote output are produced by the same code.

### Wiring into the existing mutation path

- **`src/file-write/command.ts`** — `isFileMutationCommandLine` also returns true for `isFilePatchCommandLine`, which is how the ACP file tool's line test, `gateAgentCommand`, `runGrantedAgentCommand`, `src/acp/run-prompt.ts`, and `src/remote/serve-acp-loop.ts` all recognize a patch as a mutation without their own edits. `describeLoopCommand` delegates to `describePatchCommand` for a patch line. `parseFileMutation` is unchanged and never sees patch lines.
- **`src/file-write/tab-write.ts`** — `runFileMutation(port, root, input)` and `mutateFileInTab` branch first on `isFilePatchCommandLine`: parse with `parseFilePatchCommand` (returning its usage or size line without touching the port), then return `await port.applyPatch(root, patchText)`. A thrown rejection whose message is one of the connection lines in `PASS_THROUGH_MESSAGES` (`src/file-write/outcome.ts`) prints that line unchanged, as write and edit do; any other rejection (such as `Invalid remote filesystem operation result.`) prints `Patch failed: <reason>.`. Because `mutateFileInTab` calls `runFileMutation`, both the typed command and the local ACP path (`src/acp/run-prompt.ts`, which already calls `mutateFileInTab` for `isFileMutationCommandLine`) get this branch, and the far-side ACP loop (`src/remote/serve-acp-loop.ts`, which already calls `runFileMutation` with a `LocalFileSystemPort`) gets it too.
- **`src/file-navigator/filesystem-port.ts`** — `FileSystemPort.applyPatch(root, patchText): MaybePromise<string>`; `LocalFileSystemPort.applyPatch` calls `applyPatchText`. The only implementers are `LocalFileSystemPort` and `RemoteFileSystemPort` (`src/file-navigator/remote/port.ts`); test doubles typed as `FileSystemPort` in existing tests gain a stub where the compiler asks for one.
- **`src/file-navigator/remote/port-reads.ts`** — `remoteApplyPatch(request, root, patchText)` sends `apply-patch` with `patchText` base64-encoded UTF-8 (as `remoteEditFile` sends its strings). Patch paths are root-relative on both sides — the remote tab's workspace (`withRemoteTabPort`'s `workspace`) is the far side's `context.root` — so the text is sent unchanged and every containment check happens on the far side. `port-requests.ts` adds `apply-patch` to its operation list.
- **`src/file-navigator/remote/port.ts`** — gains a three-line `applyPatch` method delegating to `remoteApplyPatch`. The file is at the 200-line `max-lines` limit today, so the same change moves the private `createItem` and `pasteRemote` bodies into exported `remoteCreateItem` and `remotePaste` helpers in `port-reads.ts` (taking the `requester()` and `paths` the way `remoteEditFile` does), leaving the public `createFile`, `createDirectory`, and `paste` methods as one-line delegations.
- **`src/remote/filesystem/apply-patch-operation.ts`** (new) — descriptor modeled on `editFileOperation` in `edit-file-operation.ts`: `valid` and `decode` accept exactly a base64 UTF-8 `patchText` (reuse its `decodeBase64Text` by moving it to `argument-checks.ts` and importing it from both), `paths: () => []` (the far side contains each section path itself through `resolveMutationTarget`), no `refusal` (so a near-side connection failure rejects with its reason, as `glob-paths` does), and `run` returns `{ text: applyPatchText(context.root, patchText) }`. Registered in `MUTATION_OPERATIONS` (`operations.ts`), its argument type `{ patchText: string }` and result `{ text: string }` in `protocol-frames.ts`, and a decoder in `result-decoders.ts` requiring a non-empty `text` string.
- **`src/remote/protocol.ts`** — `REMOTE_PROTOCOL_VERSION` 42 → 43 with a comment naming `apply-patch`.
- **`src/acp/tool-table.ts`** — `filePrimer` appends `FILE_PATCH_PRIMER` when `file patch` is granted, after the mutation primer.
- **`src/plugins/roles/shared.ts`** — `file patch` added to `NATIVE_ACP_COMMANDS` after `file edit`, which gives the Commands tab a `file patch` row under `file` and lets the typed command resolve to it.
- **`src/plugins/roles/roles-file.ts`** — the built-in `tell` role's commands gain `file patch`.
- **`src/commands/file.ts`** — no new branch is needed: `isFileMutationCommandLine` already routes to `mutateFileInTab`; a `file patch …` sample is added to `samples`.

### Order of work

Land it in this order so typecheck and tests stay green at each checkpoint: (1) the pure `parse.ts` and `hunks.ts` with their tests; (2) `view.ts`, `commit.ts`, `apply.ts` against temp dirs; (3) `FileSystemPort.applyPatch` on both ports with the `port.ts` extraction, the `apply-patch` operation, and the protocol bump together, since the operation's type union, decoder, and port method must agree; (4) `command.ts`, the widened `isFileMutationCommandLine`, `tab-write.ts`, and `describeLoopCommand`; (5) the vocabulary, tell grant, and primer; (6) help, specs, and user docs. `src/file-write/command.ts` is at 196 counted lines, so its edits are limited to one import, the widened predicate, and the one-line `describeLoopCommand` delegation; anything more goes in `src/file-patch/command.ts`.

- Specs: `product/specs/acp.md` (native command, primer, gate, follow-up naming, remote loop), `product/specs/application-commands.md` (the `file patch` row; "disabling `file` disables all five"), `product/specs/roles.md` (tell grants fourteen), `product/specs/agent-command.md` (refused in agent runs), `product/specs/remote-server.md` (`apply-patch`, protocol 43).

## Tests

## Out of scope

- A raw multi-line patch form in ACP replies or the command bar (user decision).
- External-directory permissions; outside-root paths are refused (user decision).
- Fuzzy matching beyond trailing whitespace (user decision).
- An overwrite flag; overwriting is Delete-then-Add (user decision).
- A `\ No newline at end of file` marker and a file-mode marker (user decisions).
- Removing folders emptied by a patch (user decision).
- `file patch` in `agent` command runs (user decision).
- Command-bar completion of `patch` (from precedent).
- Guarding against outside processes changing files mid-patch, and on-disk backups that survive a crash (user decisions).
- Binary file content (from precedent: tool writes are text only).
- Falling back to the local machine for a remote tab (feature text).

  1. Run `file patch {"patchText":"*** Begin Patch\n*** Add File: notes/new/todo.md\n+# Todo\n*** Update File: src/a.ts\n@@\n const a = 1;\n-const b = 2;\n+const b = 3;\n*** Update File: src/x.ts\n*** Move to: src/y.ts\n*** Delete File: old.txt\n*** End Patch"}`. Expect `Patched 4 files:`, `A notes/new/todo.md`, `M src/a.ts`, `R src/x.ts -> src/y.ts`, `D old.txt`, and the tree to match.
  2. Run a patch whose first section adds `z.md` and whose second updates `src/a.ts` with a `-const b = 99;` line. Expect `Patch failed at section 2 (Update File: src/a.ts): No matching text for hunk starting "const a = 1;". No files were changed.` and no `z.md`.
  3. Run `file patch {"patchText":"*** Delete File: ../outside.txt"}`. Expect `Patch failed at section 1 (Delete File: ../outside.txt): Outside the workspace. No files were changed.`
  4. Run `help file` and confirm the **Patching several files** section.
