# Thinking marker decoration for shell echo rows
**Complexity: 4/10** — the shell's first interactive xterm decoration: it must sit a cell after text that reflows, re-assert its own geometry on every render because xterm resets it, flip between two states in place, hide with the alternate screen, and keep presses away from xterm, all verified only against a fake terminal; there is no server or state logic.

## Goal

Add `web/src/plugins/shell/thinking-marker-decoration.ts`, a module that draws one marker on one terminal row as an xterm decoration, plus its stylesheet rules and its tests. The marker is either `Thinking` with a spinning icon, or a `see thought process` link, and one marker switches between the two in place. It knows nothing about replies, receipts, or connections: it is given a row marker, a state, and a click callback. Nothing calls it until `06-marker-lifecycle`, so the running app does not change.

## Design decisions and dependencies

This subplan is client-only and depends on no earlier subplan. `06-marker-lifecycle` consumes the three exports defined here. `05-reply-writers-plumbing` is independent of it. `07-client-wiring` builds its `ShellTab.test.tsx` terminal stub around two behaviors decided below ("No screen" and "Lifetime"), so those two stay as written.

Source plan requirements carried here: "Shell client changes" bullets on `thinking-marker-decoration.ts` and on `shell.css`; "UI design" for Surface, Placement, Look, Interaction (pointer only, pointer cursor), Accessible name and tooltip, States (hide for a full-screen program, resize re-places, not terminal text), and Motion (the spinner, matching the app's other spinners); "Once the prompt settles" (the link reads `see thought process`, is styled as a link, shows no literal brackets); "While the prompt runs" (`Thinking` is capitalized, has no ellipsis, and carries nothing else); the client-side `thinking-marker-decoration.test.ts` entry in "Tests"; "Code organization" (the xterm drawing lives in this module, in the shell plugin's own directory, with no import from another feature).

- Exports (names chosen here, consumed unchanged by `06`): `addThinkingMarker(terminal, marker, view)` returns a handle with `show(view)` and `remove()`. `view` is `{ kind: 'running' | 'link'; name: string; onOpen: () => void }`. `terminal` is typed with the `Pick<Terminal, 'element' | 'rows' | 'cols' | 'buffer' | 'registerDecoration'>` the module reads, the way `revealTranscriptRow` types its terminal in `transcript-lines.ts`, and `marker` is an `IMarker`; both types come from `@xterm/xterm` with `import type`. The module takes an xterm marker instead of creating one because the two callers get theirs differently: the echo row's marker is registered after the echo is parsed, and the reply head row's after the head is parsed (`05-reply-writers-plumbing`). Registration, timing, and state live in the callers; this module only draws. The marker may be any row of the echo's logical line: the module finds the line's last row itself (see Placement), so it does not depend on which row the caller registered.
- Registration. Drawing follows `insertMarkdownBlock` in `web/src/plugins/shell/markdown-block.ts`: `terminal.registerDecoration` with the marker, `width: 1`, `height: 1`, and `layer: 'top'`, then an `onRender` handler. One cell wide and tall because the module sizes the element itself (next bullets). `layer: 'top'` because xterm's renderer turns it into the `xterm-decoration-top-layer` class (`BufferDecorationRenderer._createElement`), which raises the element's `z-index` from 6 to 7 in `xterm.css`, as for reply blocks; the typings document `layer` only for the colour options, but the class is applied regardless. No `x`, `anchor`, colour, or overview-ruler option is passed (`x` cannot change after registration and a negative one throws). `allowProposedApi` is already on in `useShellTerminal.ts` (`registerDecoration` requires it). `registerDecoration` returns `undefined` when the marker is already disposed (the typings also name the alternate buffer, but `DecorationService.registerDecoration` in the installed xterm 6.0.0 checks only the marker); the handle is then inert.
- What xterm does on every render, and what the module does about it. `BufferDecorationRenderer` (`node_modules/@xterm/xterm/src/browser/decorations/BufferDecorationRenderer.ts`; the shipped `lib/xterm.mjs` has the same order) sets the element's `display`, `width` (`options.width` cells), `height`, `top` (from the marker's own row), and `lineHeight` (the cell height in pixels) and only then fires `onRender`; and after that, when the terminal's dimensions changed (a resize, a font-size or pixel-ratio change), `_renderDecoration` calls `_refreshXPosition`, which sets `style.left` to an empty string. Decisions that follow. The handler applies the module's own `display`, `width`, `top`, and horizontal offset on every render, because xterm overwrites the first three each time. The horizontal offset is a pixel `margin-left` and never `left`, `right`, or `x`: a `left` written in the handler would be erased right after it on every resize, which is the very case the source plan wants to work. The element is `position: absolute` with `left` empty (`xterm.css`), so a margin offsets it from the screen's left edge. The stylesheet sets no `line-height`: xterm's inline pixel value is the cell height and wins, and `--terminal-line-height` is a unitless multiplier (1.2 in `web/src/theme.css`), wrong as a pixel value. Content is built on the first render and rebuilt only by `show`, never on every render, because rebuilding the spinner's svg on each render would restart its animation whenever the terminal draws. The click and `mousedown` listeners are added once, on that first render. xterm creates the element lazily, on the first render with the marker's row inside the viewport, so a `show` before then only updates the module's stored view.
- Placement. On each render the module places the element against the last row of the marker's logical line. `marker.line` is an absolute buffer index, the same index `terminal.buffer.active.getLine` takes. From the marker's row the module walks forward while `getLine(row + 1)` exists and its `isWrapped` is true (`readTranscriptLines` in `transcript-lines.ts` reads wrapped rows the same way). This is an addition to the source plan's "reads the row's text width": when the window narrows, xterm's reflow inserts the new continuation rows directly after the marker's row and does not move the marker (`Buffer._reflowSmaller` fires `lines.onInsert` at the index after the line's last row, and the handler in `Buffer.addMarker` shifts only markers at or after that index), so the marker ends up on an earlier row than the text's last. The module reads that last row and finds its text width in cells by scanning cells from the right, across the smaller of `line.length` and `terminal.cols` (the typings warn that `length` can exceed the columns after a resize), for the last cell whose `getChars()` is not empty. The width is that cell's index plus its `getWidth()`, so a wide character counts two and its empty trailing half is skipped; a row with no such cell has width 0. It does not use `translateToString`: the length of that string is not a cell count. Cell sizes come from the screen the way `position` in `markdown-block.ts` gets row height: `clientHeight / terminal.rows` for rows, and `clientWidth / terminal.cols` for columns. The offset is one cell after the text: (text cells + 1) times the cell width. The element's own width is read from the rendered element (`offsetWidth`) after the module sets its `width` to `auto` and shows it (`display: block`), because a hidden element measures zero and xterm has just set the width to a single cell. When the offset plus that width passes the screen's width, the offset becomes the screen's width minus the element's width, which puts the element at the row's right edge over the last cells (the stylesheet's `background: var(--bg)` keeps it readable over the text), and it is never less than 0. The top is (row minus `viewportY`) times the row height, set by the module because xterm's `top` follows the marker's row, not the last row. Visibility follows `position`: `display: none` while `terminal.buffer.active.type` is not `normal`, or when the row's offset from `viewportY` is outside 0 to `terminal.rows - 1`; otherwise `display: block`. A disposed marker (its `line` is -1) or a missing row (`getLine` returns `undefined`, as when the row left the scrollback) hides the element and places nothing. Keep the arithmetic in small named helpers (the line's last row, the cells a row uses, the offset) so none passes the cognitive-complexity limit of 15. `.harness-body.shell-body` already clips decorations to the terminal body, which bounds the case where the element is wider than the row (the offset is 0 and the overflow is clipped).
- No screen. With no `.xterm-screen` to measure against (no `terminal.element`, as in the `@xterm/xterm` stub of `ShellTab.test.tsx`, whose buffer rows have no `getCell`), the module still fills the content and applies `show`, reads no buffer row, and sets no position and no `display`, leaving the element as xterm made it. `markdown-block.ts` differs here: its `position` hides the block when there is no screen. The difference is deliberate, because `07-client-wiring` finds the marker by role and name in that stub, and testing-library does not find an element with `display: none`. xterm fires a render only after `open()` (`BufferDecorationRenderer` is created there), so a real terminal always has a screen. A screen that exists but has no usable size yet (a width or height that is not finite and positive, as for a tab laid out hidden) hides the element with `display: none`; xterm sets `display: block` again on its next render, which then places it.
- Content. The element carries the class `shell-thinking-marker` and a `data-kind` attribute holding the view's kind (`running` or `link`), which the stylesheet selects on. Inside it is a `span` with the label and, for a running view, the spinner after it. Running: the label `Thinking`, no ellipsis. Link: the label `see thought process`, with no square brackets. The marker carries nothing else, no elapsed time, no model name, no activity kind. The spinner is the first element of `icon(faSpinner, { classes: ['fa-spin'] }).node` (an `HTMLCollection` in the package typings), with `icon` from `@fortawesome/fontawesome-svg-core` and `faSpinner` from `@fortawesome/free-solid-svg-icons`, because a decoration is plain DOM and not React (the React equivalent is `FontAwesomeIcon` with `spin` in `web/src/shared/RemoteSessionButton.tsx`). The library gives that svg the classes `svg-inline--fa fa-spinner fa-spin` and `aria-hidden="true"`, so the icon is decorative. This is the first runtime use of `@fortawesome/fontawesome-svg-core` under `web/src` (the existing imports are type-only); it is already a direct dependency in `package.json`.
- Spinner stylesheet (decided). The spin keyframes, the `fa-spin` rule, and the svg's size (`.svg-inline--fa`, 1em tall) all come from the stylesheet that `@fortawesome/fontawesome-svg-core` inserts into `document.head` the first time an icon's `node` or `html` is read (`ensureCss`, called from the `beforeDOMElementCreation` hook). It is the same stylesheet every `FontAwesomeIcon` in the app relies on. Nothing under `web/` sets `config.autoAddCss` (it defaults to true), and the application's Content-Security-Policy in `src/serve-static.ts` allows inline styles (`style-src 'self' 'unsafe-inline'`), so it is inserted. So `shell.css` ships no keyframes and the module sets no Font Awesome config. Keyframes in `shell.css` alone would not protect a build that turned `autoAddCss` off: the icon's size comes from the same stylesheet, and every other icon in the app would break first, which makes it an app-wide concern. The first check in a browser that the icon turns is in `08-docs-and-verification`. Reduced motion: that stylesheet stops `.fa-spin` under `@media (prefers-reduced-motion: reduce)` (`animation: none !important`), so with that OS setting the spinner is static, like the app's other Font Awesome spinners. The module neither adds nor overrides this. The source plan's "always spins" is therefore not exact; what holds is that the spinner spins as the app's other spinners do. Honoring the setting app-wide stays out of scope.
- State switching. `show(view)` rebuilds the content, the class and `data-kind`, and the `title`, `aria-label`, and `role` attributes on the same element, so a running marker becomes the link without a new decoration or a flicker. It then places the element again at once, because the width changed and nothing else guarantees a render soon (a render follows terminal output or a viewport change, not a `show`). Before the first render `show` only stores the view, and the first render builds from the stored view. The element's click listener, added once, calls the `onOpen` of the stored current view, so it never calls a stale one.
- Accessibility. The element has `role="link"`, and its `title` and `aria-label` are `Open <name>` in both states, with `name` taken from the view (for example `Open acp:ask:shell`). The spinner icon is decorative. There is no tab stop and no key handler: the feature is pointer-only, with no new key binding or command (`help/keys.md` is not affected).
- Presses. The element's own `mousedown` listener (any button) calls `preventDefault()` and `stopPropagation()`, as `onPress` in `holdReplySelection` (`reply-selection.ts`) does for a press on a reply block. Stopping the press keeps it from `.xterm`, whose own listeners (`CoreBrowserTerminal.bindMouse` and the selection service) would start a terminal selection, focus the terminal, and report the press to the program. Preventing the default matters because xterm's handler would have: it calls `preventDefault()` on every press, and without that the browser's default for a press on non-focusable content moves focus off the command bar until the click returns it. The marker is not inside `.shell-output-block`, so `holdReplySelection`'s capture listener ignores it. The capture-phase listener that `holdFocusOffSinglePress` (`press-focus.ts`) puts on the terminal host element (`.harness-body.shell-body`) still runs first and disables the xterm textarea for that press; because the press never reaches xterm, that hold is released by its timeout, the path `press-focus.ts` documents. A click is not stopped: it bubbles to the host element's `onClick` in `ShellTab.tsx`, which gives focus to the command bar, so the draft is kept and the user returns to it.
- Lifetime. `remove()` disposes the decoration and its marker and is idempotent: the handle keeps its own removed flag, and `show` after `remove` does nothing. xterm also disposes markers, and the decorations on them, by itself: when a row scrolls out of the scrollback, when a row is erased (`InputHandler._resetBufferLine` clears the markers on it, as a `clear` does), when the terminal is cleared or disposed, and when a reflow to a wider window deletes the marker's row (`reflowLargerCreateNewLayout` fires the delete event for the trailing rows of a line that unwraps, and the handler in `Buffer.addMarker` disposes any marker in that range). A disposed marker's `line` is -1. After any of these the element is gone; `show` then only updates a detached element and `remove` calls `dispose` on objects xterm already disposed, both safe (`Marker.dispose` returns early when disposed, and the decoration's store disposal is guarded). The module uses only these members of the xterm objects: `registerDecoration`, the decoration's `onRender` and `dispose`, and the marker's `line` and `dispose`, so the fakes in `07`'s stub need no more. The widening case matters to the callers: a marker on a wrapped echo's last row is lost when the window widens enough to unwrap the line, and its handle goes inert, while a marker on the line's first row would survive. Which row the marker is registered on belongs to `05-reply-writers-plumbing`; this module accepts any row of the line.
- Theme. The marker takes the terminal theme's colors through CSS variables, so it follows the light and dark themes as reply blocks do; `--bg` is the terminal's own background (`shellTerminalTheme` in `shell-terminal-theme.ts` reads it).
- Correction to the source plan's reference: the rule that styles links in a rendered reply, `.line.markdown a { color: var(--accent); }`, lives in `web/src/theme.css` (line 550), not in `shell.css`. `shell.css` holds only `.shell-output-block`. That rule sets the colour only; the underline an anchor shows comes from the browser, so a `role="link"` element needs `text-decoration: underline` set explicitly.
- Non-test files in a client plugin directory may import only `../api`, `../shared.css`, `@shared/error-text`, `@shared/plugins/<id>/shared`, packages, and sibling files (the client block of `eslint.plugin-boundaries.mjs`). This module needs only `@xterm/xterm` types, the two FontAwesome packages, and, if the file is split, a sibling file, so it stays inside that rule. Relative imports in `web/` carry no extension (`import-x/extensions` is `never`), and types come in with `import type` (`consistent-type-imports`).

## Proposed changes

- `web/src/plugins/shell/thinking-marker-decoration.ts` (new): the module and its three exports (`addThinkingMarker`, and the `ThinkingMarkerView` and `ThinkingMarkerHandle` types). Helpers stay unexported. Under 200 counted lines. If the file passes 180, move the row helpers (the line's last row, the cells a row uses) and the offset arithmetic into `thinking-marker-placement.ts` in the same directory, with its own test file, and import them back; do not compact.
- `web/src/plugins/shell/shell.css`: a marker block after `.shell-output-block`, with a comment in the file's style saying what it is. `.shell-thinking-marker` sets `color: var(--muted)`, `font-weight: normal`, `font-family: var(--mono)`, `font-size: var(--terminal-font-size)` (the custom properties `createAppTerminal` reads in `web/src/shared/terminal/app-terminal.ts`; a decoration element does not inherit them from xterm, so the text and the spinner are cell-sized), `cursor: pointer`, `white-space: nowrap`, `background: var(--bg)`, and `pointer-events: auto`, as `.shell-output-block` does. It sets no `line-height` (see above). A rule on the marker's `svg` leaves a gap of `0.4em` before the spinner. `.shell-thinking-marker[data-kind='link']` sets `color: var(--accent)` and `text-decoration: underline`. The pointer cursor sits on the base rule, so it shows over both states. No keyframes.

## Tests

Client (vitest project `client`), colocated:

- `web/src/plugins/shell/thinking-marker-decoration.test.ts` (new), with a fake terminal built like `markdown-block.test.ts`: a `.xterm-screen` element with fixed `clientWidth` and `clientHeight`, `rows`, `cols`, a `buffer.active` with `type`, `viewportY`, and a `getLine` that builds rows from strings (`isWrapped`, `length`, and a `getCell(x)` giving `getChars()` and `getWidth()`, with an empty cell beyond the text and a width-2 cell followed by an empty width-0 cell for a wide character), a marker of `{ line, dispose }`, a `registerDecoration` that records its options and returns `{ onRender, dispose }`, and `offsetWidth` mocked with `vi.spyOn(HTMLElement.prototype, 'offsetWidth', 'get')`. A render helper first sets the element's `width`, `top`, and `display` the way xterm does and then calls the handler, so every case also proves the module re-applies its geometry. Cases:
  - the decoration is registered with the marker, `width: 1`, `height: 1`, and `layer: 'top'`;
  - the element sits one cell after the row's text, as `margin-left` in pixels with `width: auto`, the row's `top`, and `display: block`; a wide character counts two cells and trailing empty cells count none; `left` is never set, and after the test clears `style.left` as xterm does on a resize and renders again the offset is unchanged;
  - at the right edge over the last cells when the row is full, and at 0 when the element is wider than the screen;
  - after the row's text changes and it renders again, the element has moved;
  - with a marker row followed by wrapped continuation rows, the element is placed against the last row of the logical line, both when the marker is on the first row and when it is already on the last; a missing row (`getLine` returns `undefined`) hides it;
  - it hides while the alternate buffer is active and returns when the normal buffer does; it hides when the placed row is outside the viewport above or below, shows when the marker's own row is above the viewport but the line's last row is inside, and hides when the marker's `line` is -1;
  - it fills once however often it renders (a child the test appends is not duplicated), a `show` before the first render is honored by it, and the spinner element is not replaced by a later render;
  - with no screen it still fills the content, sets no position and no `display`, and never calls `getLine`; with a screen of zero height it is hidden;
  - it switches from `Thinking` to the link in place on the same element, the link text is `see thought process` with no brackets, the text, `data-kind`, `title`, and `aria-label` change together, and the element is placed again at once (a longer label moves a right-edge offset);
  - in both states it carries `role="link"` and the `Open <name>` title and accessible name;
  - the running label is exactly `Thinking`, the spinner's svg has the `fa-spin` class and is `aria-hidden`, and the link has no svg;
  - a click calls the current view's `onOpen`, once however often the element rendered, a `show` with a new `onOpen` is the one called next, and the click still bubbles and is not default-prevented;
  - a `mousedown` on it is default-prevented and does not reach a listener on the terminal's element;
  - `remove()` disposes the decoration and marker, a second `remove()` and a later `show()` do nothing, and an undefined `registerDecoration` result gives an inert handle whose `show` and `remove` do not throw.
- `web/src/plugins/shell/shell-style.test.ts`: the marker rule is muted, not bold, has the pointer cursor and `white-space: nowrap`, and the link state uses the accent colour with an underline.

## Out of scope

- When a marker is added, which row it goes on, and how it settles (`06-marker-lifecycle`).
- Registering the row markers and returning values from the writers (`05-reply-writers-plumbing`), including which row of a wrapped echo the marker is registered on.
- Re-registering a marker that xterm disposed, for example after a window widening unwrapped its row.
- Reading the receipt or the reply (`07-client-wiring`).
- Keyboard access, elapsed time, model name, activity kind, and the OS reduced-motion setting (the Font Awesome stylesheet already stops the spin under it).
- Any server change.
