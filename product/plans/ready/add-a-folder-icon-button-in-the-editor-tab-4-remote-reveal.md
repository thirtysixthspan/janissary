# Remote reveal

**Complexity: 3/10** — ~40 added lines, 1 file, 5 requirements, 6 test scenarios (p=4.69). One branch in an existing module, but the current-root recompute and the re-root to the workspace root are the two paths that must not drift, and the remote listing's asynchrony makes the user-visible selection depend on `06`.

## Goal

Add the remote half of `revealEditorFile`. A remote cached file reveals in the navigator that produced it, at that navigator's current root, without retargeting any navigator. When a re-root inside the workspace has left the file outside the navigator's current root, the reveal first re-roots that navigator to its remote workspace root and then selects the file there.

## Design decisions and dependencies

This subplan depends on `add-a-folder-icon-button-in-the-editor-tab-1-reveal-target-and-blocked-state` for the blocked rule and on `add-a-folder-icon-button-in-the-editor-tab-3-local-reveal` for the ordered reveal sequence and the hint writer. It replaces the temporary remote guard that `03` leaves at the start of step 2. `05-reveal-rpc` supplies the production caller. The source plan is `./product/plans/complete/add-a-folder-icon-button-in-the-editor-tab.md`; this is its "Remote file", "Remote record lifetime", and "Remote file outside its navigator's current root" decisions.

- The branch is chosen by the record, not by the cache path alone. When `isRemoteCacheFile(editor.path)` holds and `remoteFileFor(editor.path)` returns a record, the file is remote. A cache path with no record was already stopped by `editorRevealBlocked` as `'no-route'`, so it never reaches this branch.
- Only a navigator-made record names a navigator. `materializeRemoteFile` has two production callers: `openNavigatorFile` and `createNavigatorFile` in `src/file-navigator/manager/files.ts` (`:27` and `:45`), which record the navigator's own label and its `state.filesystem`, and the plugin capability at `src/plugins/remote-capabilities.ts:133`, which records whichever plugin tab asked (a diff or search tab) and that plugin's private port. No navigator state is keyed by a plugin tab's label, so a plugin-materialized file takes the missing-state path below and changes nothing. It is still not dimmed, because `editorRevealBlocked` only asks whether a record exists; that enabled-but-inert state is recorded under "Out of scope" and is not changed here.
- The record (`RemoteFileRecord` in `src/file-navigator/remote/file-cache.ts:7`) carries `filesystem`, `root`, `relPath`, and `label`. `root` is the navigator root at the moment the file was materialized, `relPath` is tree-relative to that root, and `label` is the navigator tab's label. A navigator-made record's `filesystem` is the navigator's `state.filesystem` (`manager/files.ts:29`), which is what makes the record the file's live route back to the remote host, so this branch never calls `openOrRetargetLocalAt`, retargets, or attaches anything.
- The remote absolute target is `path.posix.join(record.root, record.relPath)`. Both halves are POSIX paths from the remote host, so the join is POSIX even though the server may run on a platform with another separator.
- Look up `port.states.get(record.label)`. A missing state returns silently: it means the navigator closed after the record was read, or, for a plugin-materialized record, that no navigator was ever named. In normal operation a navigator-made record is forgotten by `forgetRemoteFilesOf` when its port is disposed: `closeTabState` on close (`src/file-navigator/manager/profile.ts:22`) and `releaseRemote` before a retarget to another source or to a local directory (`src/file-navigator/open.ts:96`–`:99`). Plugin records are forgotten with their resource (`src/plugins/remote-capabilities.ts:27`). The comment at `file-cache.ts:47`–`:49` ("once its navigator closes or is re-rooted") also counts a re-root as forgetting, which overstates it: `rerootTree` never disposes the port, so the record survives a re-root, and the recompute below is what makes the record's stale `root` harmless. The missing-state case is therefore a race guard for a navigator record and the steady state for a plugin record.
- Compute the reveal path against the navigator's current root, not the record's root. When `containedAbsolute(state.root, target)` holds (`src/path-containment.ts:16`, the check `retargetEditorTab` makes at `src/tab/retarget-editor.ts:13`), the path is `path.relative(state.root, target)` converted to POSIX separators, and no re-root happens. This is the case after a re-root to an ancestor, where the file gains leading segments.
- When the target is outside the current root, the navigator is re-rooted to `state.remoteRoot` with the existing `reRootTree` sequence (`src/file-navigator/navigation.ts:61`), called with no `entries` argument so the rebuild reads the new root itself. That is exactly how `updateRemoteRoot` re-roots a remote tree (`src/file-navigator/open.ts:83`–`:88`, the `if (state.root !== root)` branch that calls `reRootTree` with no entries). The sequence's `ReRootPort` (`navigation.ts:17`) needs `unwatchDir`, `watchDir`, `setCwd`, `rebuild`, `refreshGit`, and `hasTab`; `03`'s `RevealPort` already carries all six, so the call needs no cast and no port widening. The reveal path is then `path.relative(state.remoteRoot, target)`, converted to POSIX. The navigator's `remoteRoot` is always set by the time one of its files has been opened, because the file could only be opened once the workspace was ready; a missing `remoteRoot` returns silently.
- If the target is not inside `state.remoteRoot` either, the record and the workspace disagree and the call returns silently. `rerootTree` already refuses to move a remote navigator above `remoteRoot` (`src/file-navigator/navigation.ts:112`–`:117`, reporting `outside the remote workspace`), and `containedPath` rejects a `..` relPath when the record is made (`src/file-navigator/remote/file-cache.ts:37`–`:38`), so only a hand-built record reaches this. It is the guard that stops a `..` path from ever reaching `revealPath`.
- The re-root clears the navigator's expanded set, watchers, filesystem cache, git metadata, branch, and flag, exactly as any other re-root does. The reveal's next step re-expands the ancestors, so the end state is the file's ancestors expanded and its hint naming the file in a tree rooted at the workspace root.
- After the path is resolved, the remaining steps are `03`'s unchanged sequence: `revealPath`, write the hint with a fresh revision, and `setActiveTab`. The hint is relative to whatever root the tree now has, which is the current root in the no-re-root case and `remoteRoot` in the re-root case. It carries no `focus` member yet; `06` adds that.
- The hint is written before the remote listing arrives. After a re-root the row set is rebuilt from an empty cache, and even without a re-root a not-yet-expanded ancestor lists asynchronously, so the first payload can carry the hint and no file row. Today's client marks a revision applied on that first payload and `selectionFromRestore` drops a path that is not in `rows` (`web/src/file-navigator/file/navigator-selection.ts:109`–`:111`; the guard is `useFileNavigatorSelection.ts:28`–`:30`). Between `04` and `06` a remote reveal therefore expands the tree without selecting, which is expected: `06-focus-hint-and-held-selection` is what holds the hint until the row exists. This subplan's tests assert the hint and the expanded set, never client selection, and `13-end-to-end-verification` owns the visible outcome.
- Record lifetime is existing behavior and is not changed. `rerootTree` (the user's move up or down inside the workspace) keeps the same filesystem port and therefore the same record, which is why the path is recomputed here. `closeTabState` and `releaseRemote` forget a navigator's records, which is why an orphaned file is blocked in `01`.
- The branch must not release the remote tie, must not attach another tab, and must not open a navigator. `openFilesTab`, `openOrRetargetLocalAt`, `releaseRemote`, and `managers.remote.attach` are never reached from it; in the no-re-root cases `state.root` is unchanged and `refreshGit` is not called, and in the re-root case `state.root` becomes `remoteRoot` with `setCwd` and `refreshGit` reached once.

## Proposed changes

In `src/file-navigator/reveal-editor.ts`:

- Replace the temporary "remote cache file with a record returns" guard with the remote branch described above. Keep the guard's position at the start of step 2, and keep its `isRemoteCacheFile` half as the branch's entry test.
- Add a module-local, unexported helper that turns `path.relative(from, to)` into a POSIX-separated path (`split(path.sep).join(path.posix.sep)`), and use it for both the current-root and the `remoteRoot` result. It assumes containment was already established and does no checking of its own. `01`'s `revealTargetFor` already has this conversion inline for the local rule; leave it there and do not export the helper.
- Import `containedAbsolute` from `../path-containment.js` and `reRootTree` from `./navigation.js`. Do not re-import `isRemoteCacheFile` or `remoteFileFor`: `03` already imports both for the guard being replaced, and `revealPath` and `nextRestoreRevision` are already imported too.
- Keep the local branch after the remote branch, unchanged. A file that is not a cache file always takes the local rule.
- Keep the module under 200 code lines. It is near 110 raw lines after `03` and lands near 150 here; if it crosses the limit, extract the remote branch as one function returning `{ label, relPath }` (or nothing) to a sibling `reveal-editor-remote.ts`, leaving `revealEditorFile`'s shared steps 3 to 5 in place, rather than compacting either function or moving the whole reveal.

## Tests

In `src/file-navigator/reveal-editor.test.ts`, beside the local cases:

- A remote cached file reveals in the navigator named by its record: `state.root` is unchanged, `refreshGit` is not called, `openFilesTab` is not called, and the hint's `cursor`, `anchor`, and `selected` name the file's tree-relative path under a fresh revision.
- After the navigator re-rooted to an ancestor of the record's root, the target is still inside the current root, the reveal path gains the leading segment, and no re-root runs: assert `state.root` unchanged and `refreshGit` not called, with the new ancestor added to `expanded`.
- After the navigator re-rooted into a sibling directory that no longer contains the file, the call re-roots it to `state.remoteRoot`: `state.root` becomes `remoteRoot`, `setCwd` and `refreshGit` are called once with the label, the old `expanded` entries are unwatched and gone, and the hint names the path relative to `remoteRoot`. The re-root's clear is immediately followed by `revealPath`'s re-expansion, so assert the final `expanded` set is exactly the new path's ancestors, never an empty set.
- A record whose `label` names no navigator state — the navigator closed, or a plugin materialized the file — changes nothing: no hint, no activation, no root change.
- A record whose absolute target is outside `remoteRoot` changes nothing.
- Build the record with the real cache helpers and a temporary project directory: `initRemoteFileCache` then `materializeRemoteFile`, the `cachedFile` helper at `src/plugins/origin-workspace.test.ts:255`–`:264`. Build the state with `freshFileNavigatorState`, passing the case's root, the stub filesystem, the `'name'` detail, the remote target, and an owner label, then set `state.remoteRoot`. Choose `root` per case: the record's own root for the no-re-root case, the ancestor for the ancestor case, and the sibling for the re-root case. The stub is a `FileSystemPort`-cast object holding a `dispose` spy, as `src/plugins/origin-workspace.test.ts:255` does. No ssh channel and no real `RemoteFileSystemPort` is needed, because `rebuild` stays a spy in these cases and nothing reads a listing.
- Use `03`'s fake port (`src/file-navigator/restore-command.test.ts:21`–`:30`, extended with `managers`) and give the record that harness's `'files'` label, the key its `states` map uses. Do not drop `setCwd`, `hasTab`, or `unwatchDir`: `reRootTree` calls all three, so a port missing one throws in the re-root case rather than failing typecheck.
- Also assert the record is still present after the reveal (`remoteFileFor(file)`), since the source plan requires the source navigator to remain the file's route back.

## Out of scope

- No change to the remote file record, its lifetime, `materializeRemoteFile`, `forgetRemoteFilesOf`, `releaseRemote`, `closeTabState`, `rerootTree`, `reRootTree`, `revealPath`, or `containedAbsolute`.
- No retarget of the source navigator and no reopening of a route for an orphaned file.
- No change to `editorRevealBlocked`, the `revealBlocked` projection, or the button's enabled state. A file materialized through the plugin capability (`src/plugins/remote-capabilities.ts:133`) carries a record but names no navigator, so its button stays enabled and the reveal does nothing; teaching the blocked rule to check for a live navigator is a change to `01`'s rule, not to this subplan.
- No save or commit behavior; the same record already gates saving.
- No focus flag, client focus, acknowledgement, RPC, or UI. `06`, `07`, and later subplans own those, and the client's hold-until-the-row-arrives behavior is `06`'s.
- No notification, including for a missing navigator state, a plugin materialized file, or a record outside its workspace root.
