# Remote provider session IDs
**Complexity: 7/10** — ~55 added production lines, 8 existing files, 11 requirements, 45 scenarios (p=6.59)

## Goal

Report the provider ID over an addressed `acp-session-started` notification as soon as the far-side `newSession` succeeds, before effort configuration. Retain optional `sessionId` on normal `acp-ready`, sandbox reporting and existing no-ID fixtures. Preserve the existing readiness promise and `onConnect` timing.

Source: `product/plans/complete/subagent.md`, preserved unchanged as the canonical feature record. This is ordered subplan 6 of 23.

## Decisions and dependencies

Dependencies: `product/plans/ready/subagent-5-local-provider-session-ids.md`, which supplies the transport callback and guarded `CoreSession.providerId` storage/accessor and depends on the spec created by plan 1. No later subagent launcher, delivery queue or workspace selector is needed.

The canonical plan's mechanical design carries the ID only on `acp-ready`. The real handshake assigns the provider ID before effort setup (`src/acp/index.ts:135`, `sessionId = response.sessionId`), but sends readiness only after effort setup (`index.ts:149`, `options.onConnect`). An effort failure can therefore lose a successfully reported ID if readiness is its only transport. This unit corrects that mechanism with the earlier notification while preserving every user decision: the first handshake identifies `started`, and a failed outcome uses the latest successful handshake ID, or `null` if none completed. It changes neither public message timing rules nor the canonical source document.

Implement and verify only against existing repository code and the completed earlier dependencies. Other units own their own changes; references to them explain integration boundaries and do not authorize future API calls. Every new production module stays within 200 counted lines, source imports name defining modules directly with .js extensions, and shared wire definitions are imported by the client.

## Implementation steps

1. Add `acp-session-started` to the `ServerFrame` union beside `acp-ready` at `src/remote/protocol-frames.ts:261`, carrying required nonempty `id` (the existing transport address) and `sessionId` (the provider ID). Admit it in `SERVER_FRAME_TYPES`, route it through the exhaustive `decodeKnownFrame` switch, and extend `decodeAcpAddressed` to validate it with `nonEmptyString` from `src/remote/frame/decode-shared.ts:12`. Also add optional `sessionId` to `acp-ready`; omission remains valid, but an empty or non-string value is malformed. Preserve each supplied ID unchanged without trimming, prefixing or base64 encoding; omit the ready property when absent and discard undeclared fields using the existing explicit decoder-return pattern. Reuse the encoder's default branch. This notification is server-only and is routed as ACP traffic, so neither `CLIENT_FRAME_TYPES` nor `CHANNEL_FRAME_KEYS` in `src/remote/channel/types.ts:55` gains an entry.

2. In `RemoteAcp.open`, capture plan 5's `connectAcp.onSessionStarted` ID in a variable scoped to that open invocation and immediately send `acp-session-started` with that ID and the open's transport address. Plan 5 fires this callback once after `newSession` and before effort selection/configuration; do not wait for `onConnect` or retract the notification if effort setup subsequently fails. Keep the existing `onConnect` readiness timing and include the captured ID in normal `acp-ready` when defined, alongside unchanged `sandboxed`. The early notification neither sends readiness nor resolves any readiness promise. A mocked transport that never reports an ID keeps its previous ready-frame shape, and separate opens cannot share captured IDs. Preserve lazy first-prompt initialization for ordinary sessions and existing eager initialization for autonomous callers; add neither an early prompt nor a new readiness wait.

3. Add optional `AcpSessionListener.onSessionStarted` and route the new addressed frame to it in `dispatchAcp`. Widen `onReady` with an optional second provider-ID argument and forward `frame.sessionId`. Add optional `onSessionStarted` to `RemoteAcpHooks`. In the adapter, use one live-guarded, once-only provider-reporting handler shared by the notification and ready fallback, plus an independent readiness-received flag. Mark each flag before invoking its hook. The first live provider ID wins for that adapter; repeated notifications, differing later IDs and the same ID on ready never call the provider hook twice. The first live ready frame alone resolves the existing promise and calls `onConnect` with sandbox state; later ready frames are ignored, including after a ready without an ID. If ready supplies the first ID, report it before resolving readiness and calling `onConnect`, and recheck `live` afterward in case the provider callback closed the adapter. A first notification arriving after a no-ID ready may still report one ID while live, without repeating readiness or `onConnect`. Existing consumers may omit the hook.

4. Preserve lifecycle behavior through the adapter's existing `live` guard and detach paths (`src/remote/acp-session.ts:77`, `detach`; line 142, `release`). Release/kill, remote close, fatal error and transport loss before ready still reject readiness and suppress all retained-listener notifications and ready callbacks afterward. If an ID was reported before that terminal event, the consumer has already observed it; readiness failure does not erase or replace that observation. A nonfatal run error before ready likewise never erases the ID or fabricates readiness. Before any successful `newSession` there is no provider callback. This unit owns callback transport, not run-level first/latest bookkeeping: a consumer retains the first callback for `started` and the latest callback across replacement adapters for an outcome, initialized to `null`. Tests prove that contract with captured callback values, without importing later execution or delivery APIs.

5. Supply the remote session branch of `AcpSessionManager.session` with the same guarded provider-ID recording handler used by the local branch after plan 5. Retain ask/tell isolation, synchronous-construction callback support and stale/closing/replaced runtime rejection. Reuse or factor the existing handler inside this file rather than copying its guard into a different manager. Closing a holder still clears its accessor and a replacement starts without an ID; a run consumer's previously captured ID survives independently. `providerSessionId` remains the holder reader from plan 5; internal session identities, `AcpInfo` and plugin result shapes remain unchanged.
