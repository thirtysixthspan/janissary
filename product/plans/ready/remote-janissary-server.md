# Remote janissary server

**Complexity: 7/10** — a first-of-its-kind surface: a second executable mode (`janus remote-serve`), a framed transport with its own state machine and version handshake, and two adapters that let remote processes satisfy contracts local code already consumes. What holds it at 7 rather than higher is that the transport carries a single process frame family, and both adapters plug into existing contracts (`PtySession`, and the small `ChildProcess` subset `ShellManager` touches), leaving capture, recording, busy status, auto-approve, `send`, `schedule`, monitoring, and shell execution unchanged.

Today every tab janissary opens runs on the machine the server itself runs on: `spawnPty` (`src/pty.ts:29`) is the single chokepoint, and it always spawns a local `node-pty` process. A workspaced launch (`agent -w`, `harness <name> -w`) clones the local repo's `origin` into a local `.janissary/workspace/<label>/`. There is no way to put an agent or a harness on another host — the closest thing, an ssh tab (`src/ssh-manager.ts`), is a raw pass-through terminal with no janissary on the far end.

This plan adds a **remote janissary server**: a `janus remote-serve [<project-dir>]` mode that runs on a remote host inside an ordinary ssh session, speaks a framed protocol over that session's stdin/stdout, and provisions workspaced agents and harnesses from the git repository at its own project root. Locally, `agent` and `harness` gain an `on <address>` clause naming the host; a launch with `on` implies `-w`, since the remote server does nothing but workspaced launches. The resulting tab is deliberately indistinguishable from a local one — same label, same tab strip, same busy dot, same capture/recording/transcript/monitor behavior — except for a host chip at the left of its metadata row.

The design leans hard on one reuse: the remote PTY is surfaced locally as an object satisfying the existing `PtySession` contract (`src/pty.ts:7`). Everything already built on top of a PTY id — the screen reader, the asciicast recorder, busy-status detection, auto-approve, `send`, `schedule`, monitoring, the connections panel — keeps working without knowing the process is on another machine.

## Design decisions

**The clause is `on <address>`, not a flag.** `harness claude on devbox`, `agent on devbox`, `harness claude as build on devbox with fix the tests`. It reads like the existing `as <label>` and `with <prompt>` clauses rather than adding another flag to a command that already carries `-w`, `-y`, `--offline`, `--model`, and `--effort`. Ordering follows the existing rules: `splitWithClause` (`src/harness/command-parse.ts:27`) already peels a trailing `with <prompt>` off before any option scanning, so an `on` inside prompt text is never read as a clause, and the `on` token is found in the remaining `left` portion exactly as `as` is at `:54`.

**`on` implies `-w`; there is no non-workspaced remote launch.** The remote server's only job is to provision a workspace clone from its project root's repository, so a remote launch without a workspace has no meaning. Rather than reject `harness claude on devbox` with an error the user can only fix one way, the clause turns the workspace on implicitly. `harness claude -w on devbox` and `harness claude on devbox` are the same command.

**The address is `[user@]host[:path]`, split at the first colon.** `on devbox`, `on admin@devbox`, `on devbox:/srv/proj`. With no path, the remote server starts in the ssh login directory and walks up for a git root — the same upward walk `findRepoRoot` (`src/workspace/index.ts:24`) already does locally. With a path, the remote server is rooted there. A trailing `:<digits>` is a **path**, not a port: `on` accepts no ssh options at all, so a host needing a non-default port, an identity file, or a jump host is expressed as a `Host` alias in the user's `~/.ssh/config` and named by that alias. This keeps the clause a single unambiguous token instead of re-deriving ssh's argument grammar the way `src/ssh.ts` has to.

**The remote must already have `janus` installed; nothing is shipped over the wire.** The local side runs `ssh -t <destination> janus remote-serve [<path>]`. If `janus` is not on the remote's PATH the launch fails with a message naming the host. No bundle upload, no `npx` fetch, no version negotiation beyond a handshake check — the remote is a peer installation, not a payload.

**One ssh connection per remote tab.** Each remote agent or harness tab owns its own ssh session and its own `remote-serve` process, exactly as each ssh tab owns its own today. No multiplexing, no shared channel, no connection registry. The cost is that authentication happens once per launch; the benefit is that a tab's lifetime and its channel's lifetime are the same thing, so close, kill, drop, and cleanup all collapse into one path.

**Authentication happens inline in the new tab's terminal.** The ssh session is spawned through `spawnPty` with `-t`, so it has a real TTY and ssh's own `password:`, key-passphrase, host-key-verification, and keyboard-interactive/2FA prompts render in the tab's terminal, with keystrokes going straight to the PTY. The tab therefore opens **immediately** in `provisioning` status showing that live session; nothing is validated ahead of the tab. This is the only prompt mechanism — no modal, no askpass, no creator-tab prompt — and it costs no new UI while covering every prompt ssh can raise.

**The channel switches from raw to framed at a handshake line.** Until `remote-serve` starts it has produced, the ssh PTY is a plain terminal. `remote-serve` announces itself with a single sentinel handshake line carrying its protocol version and the resolved remote project root; on seeing it the local side stops echoing bytes to the terminal and starts parsing frames. Frames are newline-delimited JSON with base64 payloads, and `remote-serve` puts its own stdin into raw mode at startup so the remote tty's line discipline neither echoes input nor rewrites output bytes. Base64 means no terminal control byte can ever be mistaken for framing.

**A remote PTY is a local `PtySession`.** The local side constructs an object with the same `id`/`program`/`write`/`resize`/`kill` shape `spawnPty` returns (`src/pty.ts:7`, `PtySession`), where `write` sends an input frame, `resize` sends a resize frame, `kill` sends a kill frame, and inbound output frames are published on the existing message bus as `messageBus.emit('pty', { type: 'data', id, data })` — byte-for-byte what `PseudoterminalManager.spawn` already does at `src/pseudoterminal-manager.ts:27`. The manager stores it in the same `ptys` map (`:11`), so `input` (`:35`), `resizeOne` (`:39`), `kill` (`:47`), `terminalsFor` (`:56`), `closeTab` (`:76`), and `closeAll` (`:81`) all reach it unchanged, and an inbound exit frame is routed into the same private `handleExit` (`:92`) the local `onExit` handler calls, so the exit bus event, the `activePty` clear, and the inline-card status update happen identically. Consequently `HarnessScreenReader`, `HarnessRecorder`, `busyStatusHandler`, `buildAutoApprover`, `send`, `schedule`, and `monitor` all work against a remote harness **with no changes of their own** — this is the decision the whole plan rests on.

**The remote session's `program` is the remote binary's name, not `ssh`.** `terminalsFor` (`src/pseudoterminal-manager.ts:56`) builds the connections panel's `terminal:<program>` row from `session.program`. A remote claude harness therefore reports `terminal:claude`, exactly as a local one does; the ssh transport gets its own `ssh:<destination>` row rather than masquerading as the process row.

**A remote tab's `workspaceDir` stays undefined locally.** This is load-bearing, not incidental: `src/tab/cleanup.ts:18` reads `tab.workspaceDir` on tab close and schedules `managers.workspace.remove(workspaceDir)` against the **local** filesystem. Storing the remote clone's path there would point a local recursive delete at a path that means something entirely different on this machine. The remote path lives only in the tab's cwd (for display) and on the remote server, which owns its own cleanup. Because `src/tab/view.ts:50` derives the `'workspaced'` flag icon from `tab.workspaceDir`, that one expression also reads the tab's remote field, so a remote tab still shows the workspace icon and the metadata row still "appears no different".

**A remote agent tab is live and in-memory; it is not restored by `--relaunch`.** `ProfileAgentEntry` is `AgentState & { pane }` (`src/profile/types.ts:47`), so the `remote` field has to live on `AgentState` (`src/agent/types.ts:3`) — which is also what the state directory persists. Restoring a remote agent tab would resurrect a tab whose workspace was deleted when its channel died and whose cwd does not exist locally, so `TabManager.persist` (`src/tab/manager.ts:95`) skips any state carrying a remote destination. Remote agent tabs therefore behave like harness and ssh tabs across a relaunch: each launch starts fresh. Profiles are unaffected, because `profile save` builds its entries straight from the live `Tab` (`src/profile/save-entries.ts:35`, `writeAgentEntry`) rather than from persisted state.

**Capture, recording, and busy status are computed locally from streamed bytes.** Because the remote PTY's output arrives as ordinary bus data, screen captures land in the local `.janissary/captures/`, asciicast recordings in the local `.janissary/recordings/`, and the busy dot is classified locally. The one exception is `harness transcript`, whose source is the harness binary's own session record in the *remote's* dot directory. Even that needs no new tailing machinery on either side: `TranscriptSource` is a two-method contract, `{ poll(): string[]; resolved(): boolean }` (`src/harness/transcript/source.ts:8`), so the remote runs the ordinary `createTranscriptSource` and pushes each poll's blocks, and the local source is an adapter whose `poll` drains what has arrived. `HarnessTranscriptTailer` (`src/harness/transcript/tailer.ts:19`) is unchanged.

**A remote agent tab needs no second frame family — its shell is just another remote process.** `ShellManager` (`src/shell-manager.ts:25`) already gives each agent tab **one long-lived shell process**, writes command text to its stdin, and reads sentinel-delimited output back (`src/shell.ts:24`, `executeShellCmd`). That is exactly what the process frames already do: spawn a program, write input, stream output, report exit. So a remote agent tab's shell is spawned through the same frames a remote harness is, and `ShellManager.getShell` (`src/shell-manager.ts:46`) returns a remote-backed object in place of a local `ChildProcess`.

Two facts make that object small rather than a shim of its own. First, `executeShellCmd` already appends `2>&1` to every command (`src/shell.ts:53`) — stderr is merged **by the shell**, on the far side — so the protocol never needs to separate streams or carry an exit code, and neither does the local code that consumes it. Second, the members actually touched are a tiny subset: `stdin.writable`/`stdin.write`, `stdout`/`stderr` as `'data'` emitters of utf8 strings, and `kill()`. A pair of `node:stream` `PassThrough`s fed by inbound output frames covers the read side and a small writable covers the write side; `stderr` is a `PassThrough` that never emits, since nothing is ever routed to it. Nothing in `ShellManager`, `executeShellCmd`, or `queryShellPwd` changes.

PTY takeover and inline terminal cards inside a remote agent tab use those same process frames.

**Isolation and credentials are the remote's own.** `remote-serve` applies the same Seatbelt policy the local server applies (`src/sandbox/index.ts`), which means isolation is active when the remote is macOS and inactive otherwise — the existing `sandboxNotice()` line already says so and is appended to the remote tab's terminal unchanged. `--offline` is likewise only meaningful where the sandbox is active. No credentials are forwarded: the remote's own `.janissary/github-token` is what a remote workspace uses, and the initial clone uses whatever transport the *remote* repo's `origin` already has.

**Failures reuse the provisioning-failure path.** The tab is already open as a placeholder, so a failure sets `HarnessView.provisionError` (`src/tab/types.ts:63`) and the tab closes itself after `PROVISION_FAILURE_CLOSE_DELAY_MS`, exactly as a failed local workspace clone does. This covers: ssh's own connect/auth failure text (shown verbatim, since it was already rendering in that terminal), `janus` missing on the remote PATH, the remote path not being a git repository, and the remote repository having no `origin` remote.

**A dropped channel closes the tab.** If the ssh session ends for any reason, the remote tab closes the way a harness tab closes when its process exits. There is no reconnect, no resume, and no reattach. On the remote side the workspace clone is removed when `remote-serve` exits — including on the SIGHUP it gets when the channel drops — so a dropped connection never leaves a clone behind.

**The tab looks local except for a host chip.** The tab's label is derived exactly as it is today (the harness name or the agent name, de-duplicated with `-2`, `-3`, …) — the host does not appear in the label or the tab strip. The metadata row gains a chip showing the bare host at the **left of the row, ahead of the working directory**, so the row reads "where, then what path there". It uses the same chip styling as the existing model/effort chips (`web/src/AgentTabMeta.tsx:17`), with a tooltip carrying the full destination (`Remote: admin@devbox:/srv/proj`). The working directory shown is the remote workspace path.

**Both connections rows are listed.** A remote tab shows `ssh:<destination>` for its transport and `terminal:<label>` for the remote process, so each is visible and separately closable. This adds no new connection kind — both already exist (`src/connection/types.ts:1`).

**Profiles record the destination and omit the cwd.** `ProfileHarnessEntry` and `ProfileAgentEntry` gain an optional `remote` field holding the address string as typed. Both `writeAgentEntry` (`src/profile/save-entries.ts:35`) and `writeHarnessEntry` (`:68`) currently write `cwd: portablePath(cwd, managers)`, which rewrites a path under the local project root as `$root/…`; a remote workspace path is neither under the local root nor meaningful on this machine, so a remote entry omits `cwd` entirely and lets the remote server resolve the workspace afresh at launch. `writeHarnessEntry`'s `workspace: tab.workspaceDir !== undefined` (`:78`) would likewise read false for a remote tab, so it reads true whenever the tab has a remote destination. `profile launch` reconnects with the same destination; an entry whose connection fails is reported and skipped like any other failing entry. Because there is one connection per tab, a profile of several remote tabs raises several authentication prompts — that is accepted, not worked around.

## Proposed changes

**Address parsing.** A new `src/remote/address.ts` exporting a parser that takes the token following `on` and returns the destination (`[user@]host`), the bare host used for the metadata chip, and an optional remote project path — splitting at the first `:` and treating everything after it as a path. It rejects an empty token with a usage message naming the clause.

It also **validates** both parts against a conservative allowed character set (alphanumerics, `.`, `-`, `_`, `@`, `/`, `~`, and `:` as the single separator), rejecting anything else with a message naming the offending address. This is not optional hardening: `spawnPty` builds its child as `$SHELL -lc <command>` (`src/pty.ts:40`–`:41`), so the destination and path are interpolated into a shell command line, and unlike `ssh <destination>` — where the whole line is text the user just typed — an `on` address can also arrive from a profile file on disk. Reject rather than quote, so the rule is one predicate instead of an escaping scheme, and write the pattern without nested quantifiers to satisfy `security/detect-unsafe-regex`.

This module is kept separate from `src/ssh.ts`, whose job is the opposite (modelling ssh's full option grammar to *find* a destination among flags, `src/ssh.ts:17`); this parser accepts exactly one token and no flags.

**Command grammar.** `parseHarnessFlags` (`src/harness/command-parse.ts:38`) learns an `on` token the same way it learns `as` at `:54`: find the index case-insensitively, take the next token, error with a usage string when it is absent. `HarnessParsed`'s launch variant (`:8`) gains an optional `remote` field, and `parseHarnessCommand`'s doc comment (`:73`) gains the clause. Note `parseHarnessFlags` already carries five flags plus `as` and is near the `sonarjs/cognitive-complexity` limit the file was previously split to respect (see the comment at `:37`); the `on` lookup is extracted into its own small helper beside `findFlagValue` (`:15`) rather than added as another inline branch.

`parseAgentCommand` (`src/agent/commands.ts:22`) gains the same clause. It derives the agent's name from "everything after `agent`" via the `stripped` regex chain at `:26`, so `on <address>` must be removed there alongside `-w`/`--workspace`/`--offline` or the address becomes part of the tab name — and `resolveAgentName` (`:5`) at `:10` runs the *unstripped* input through the same "everything after `agent`" match, so it needs the same removal. Both sites are two lines apart in a 36-line file; missing the second is the most likely way to get a tab labelled `bekir on devbox`.

In both parsers a present `remote` forces `workspace` to `true`, so no caller has to remember the implication.

**Remote channel.** A new `src/remote/channel.ts` owning one ssh session's lifetime. It spawns `ssh -t <destination> janus remote-serve [<path>]` through the existing `spawnPty` and runs a small state machine: **authenticating** (bytes pass through to the tab's terminal, keystrokes pass through to the PTY), **handshaking** (the sentinel line has been seen; protocol version and resolved remote root are read), **attached** (bytes are parsed as frames), and **closed**. It exposes a method to send a frame, a callback per inbound frame, and a close notification. Write it as one module; the codec lives in `protocol.ts` and the spawn is a single `spawnPty` call, so there is nothing here that needs splitting until it actually approaches the 200-line limit.

**Frame protocol.** A new `src/remote/protocol.ts` declaring the frame union shared by both sides — it is imported by `remote-serve` and by the local channel, so it is the contract, and it carries an explicit version constant checked at handshake. One process family plus two small extras:

- *Process frames* — spawn a program in the remote workspace, and then input, output, resize, kill, and exit, each keyed by a session id. These back remote harness tabs, remote agent tabs' persistent shells, PTY takeover, and inline terminal cards alike; there is no second family, for the reasons in the design decisions above.
- *Provisioning* — workspace ready, or workspace failed with a message.
- *Transcript* — rendered blocks pushed from the remote's own transcript source.

Encoding is newline-delimited JSON with base64 payloads, which is `JSON.parse`/`JSON.stringify` and `Buffer.from(…, 'base64')` — stdlib, so the codec is a handful of lines inside `protocol.ts` rather than a module of its own.

**Remote PTY session.** A new `src/remote/pty-session.ts` exporting a factory that returns an object satisfying `PtySession` (`src/pty.ts:7`): `write` and `resize` send input/resize frames on the channel, `kill` sends a kill frame, and inbound output frames are published on the message bus under the session's id, exactly as `spawnPty`'s `onData` handler does at `src/pty.ts:50`. Its `program` is the remote binary's name (`claude`, not `ssh`), so `terminalsFor` reports a local-looking `terminal:<program>` row. `PseudoterminalManager` grows a sibling registration method beside `spawn` (`src/pseudoterminal-manager.ts:22`) that puts one of these into the same `ptys` map with the same `{ session, tabLabel }` shape and wires the channel's exit frame to the existing private `handleExit` (`:92`) — `handleExit` is private today, so this method must live on the manager itself rather than in `src/remote/`. Nothing else in the manager changes: `input`, `resizeOne`, `kill`, `terminalsFor`, `closeTab`, and `closeAll` already go through `session.*` and need no remote branch.

One place does need a branch: `openInlinePty` (`src/pseudoterminal-manager.ts:65`) passes `tab?.workspaceDir`/`tab?.offline` into `spawn` for Seatbelt confinement, and a remote tab has neither locally. For a remote tab it instead asks that tab's channel for a PTY, letting the remote server apply its own sandbox — the confinement decision belongs to the machine the process runs on.

**The remote server.** A new `src/remote/serve.ts` plus its own submodules, entered from a `remote-serve` subcommand added to `src/cli-args.ts` beside `stop` and `init`. It runs attached, takes no instance lock, starts no HTTP server, opens no window, and writes nothing to `.janissary/log/`. On startup it puts stdin into raw mode, resolves its project root (the argument, else the login directory walked up via `findRepoRoot`), verifies that root has an `origin` remote, and emits the handshake line — or a workspace-failed frame and a non-zero exit when either check fails. It then services frames: provisioning a workspace clone through the same `WorkspaceManager` the local server uses (`src/workspace/manager.ts:28`), spawning processes inside it through the same `spawnPty` (`src/pty.ts:29`) — which already routes through `sandboxSpawn` — and removing the clone on exit, including on the SIGHUP that arrives when the ssh channel drops. Because it is running on the machine where the harness's session record lives, it builds its transcript source with the existing `createTranscriptSource` (`src/harness/transcript/sources.ts:9`) and pushes what that yields; no remote-specific reading logic is written. Its capability surface is deliberately closed: it will not open tabs, serve files, run arbitrary paths outside the workspace, or accept any frame not in the union.

Its `serve` module is not pre-split: the frame switch, the workspace call, and the process map are each a few lines, and CLAUDE.md's instruction is to extract when a file actually reaches the limit, not to anticipate it.

**Launch wiring.** `HarnessManager.open`/`spawnTab` (`src/harness/manager.ts:115`, `:159`) gain a remote branch. When `remote` is set, `resolveCwd` (`:269`) does *not* call `managers.workspace.create` — no local clone is made and `workspaceDir` stays `undefined` in `SpawnTabOptions`, so `finishSpawn`'s `sandboxNotice()` branch at `:210` must key on the tab being remote rather than on `workspaceDir` if the remote's isolation notice is to appear. Instead the channel is opened, the tab is inserted immediately as a `provisioning` placeholder whose terminal is attached to the ssh PTY, and the `ready` promise `wireProvisioning` (`src/workspace/provision-wire.ts:13`) already consumes is resolved by the channel's workspace-ready frame — or rejected by workspace-failed, which lands in `provisionError` through the existing `failSpawn` (`src/harness/manager.ts:218`) and its `PROVISION_FAILURE_CLOSE_DELAY_MS` (currently 3000 ms, `src/workspace/provision-wire.ts:4`). `finishSpawn` (`:190`) then registers a remote `PtySession` in place of `this.managers.pty.spawn` at `:195`, and everything downstream of it — reader, recorder, tailer, capture handler — is untouched. The agent path takes the corresponding branch in its own tab creation.

**Remote agent shell.** `ShellManager.getShell` (`src/shell-manager.ts:46`) branches on the tab having a remote destination: instead of `spawnShell`, it asks that tab's channel to spawn the login shell in the remote workspace and wraps the resulting session in a `ChildProcess`-shaped object — `stdin` a writable that sends input frames, `stdout` a `node:stream` `PassThrough` fed by output frames, `stderr` a `PassThrough` that never emits, `kill()` sending a kill frame. That object lives in the same `shells` map and flows through `execute` (`:112`), `close` (`:132`), and `closeAll` (`:142`) untouched. The `if (cwd) shell.stdin!.write(\`cd "${cwd}"\`)` line at `:57` is skipped for a remote shell, which the remote server has already started in the workspace. The adapter belongs in `src/remote/shell-session.ts` beside `pty-session.ts`, since both are the same idea applied to the two shapes local code expects.

## Out of scope

- **Non-workspaced remote launches.** `on <address>` always implies `-w`; there is no way to run a remote agent or harness directly against the remote checkout rather than a disposable clone of it.
- **Reconnect, resume, or reattach after a dropped ssh channel.** The tab closes and the remote workspace is removed; a new launch starts a fresh session.
- **A shared or multiplexed connection per host.** One ssh session and one `remote-serve` process per remote tab, and therefore one authentication per launch.
- **Shipping or installing janissary on the remote.** No bundle upload, no `npx` bootstrap; `janus` must already be on the remote's PATH.
- **ssh options on the clause.** No ports, identity files, jump hosts, or arbitrary flags after `on` — those go in the user's `~/.ssh/config` as a `Host` alias.
- **Credential forwarding.** The local `.janissary/github-token` is never sent; a remote workspace uses the remote host's own token and the remote repo's own `origin` transport.
- **A saved directory of remotes.** No `remotes.json`, no alias registry, no tab-completion over previously used hosts.
- **Remote file navigator, `open`, and editor tabs.** These stay local-only; a remote workspace is not browsable or editable through them.
- **A remote-side sandbox where the platform has none.** `remote-serve` applies the existing Seatbelt policy, which means a Linux remote is unsandboxed and says so; no alternative confinement mechanism is introduced.
- **Nested remoting.** A remote tab cannot itself launch `on <another-host>`.
- **`--relaunch` restore of a remote agent tab.** Remote agent tabs are excluded from persisted agent state, so a relaunch brings none of them back.
- **`janus stop`, the instance lock, and logging on the remote.** `remote-serve` takes no lock, writes no `.janissary/log/server.log`, and is not addressable by `janus stop`; it lives and dies with its ssh channel.

## Open questions

- **Can an ACP-backed agent tab be remote in v1, or is a remote agent tab shell-only?** The exec-frame design covers an agent tab's ordinary shell commands, but an ACP session (`src/acp/`) is a long-lived stdio protocol connection to an agent binary, which would need either its own frame family or a nested channel. Shell-only is the smaller v1 and would make `agent … on <host>` reject an ACP-configured agent with a clear message; the alternative is a third frame family. Not resolved.
- **What does `send`/`schedule` do to a remote tab whose channel is still authenticating?** Delivery to a local harness retries on later ticks until the PTY is ready. A remote tab is "ready" in the PTY sense while ssh is still asking for a password, so a scheduled prompt could be typed into the password field. The likely answer is to gate delivery on the channel being *attached* rather than on the PTY existing, but the exact rule was not settled.
- **Version skew between the local server and `remote-serve`.** The handshake carries a protocol version and a mismatch is rejected, but whether that rejection should name the two janissary versions, tolerate a compatible range, or simply say "update janissary on `<host>`" is undecided.
