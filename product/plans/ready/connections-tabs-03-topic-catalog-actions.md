# Connections notification topic and host actions

**Complexity: 5/10** — a new shared topic contract, cross-tab catalog projection, coalesced delivery, loaded record windows, and nine owner-validated actions, with no new persistence or transport state machine.

## Goal

Expose current live connections and persisted ACP/agent records through a coalesced `connections` host topic with narrowly scoped actions for the plugin.

## Decisions and dependencies

- Covers source-plan requirements 8, 13–16, 18, 21, 23–24, and implementation decisions 26, 29, 33–34, 36 as host-side data, catalog, and action behavior.
- Scope authority is `product/plans/ready/connections-tabs.md:24` (decision 6), decisions 13–14 and 21–24, and implementation decisions 26, 29, 33–34, and 36. Preserve the source plan's 8/10 rating and all allocated requirements; this subplan does not implement the plugin.
- Depends on the reviewed and completed records and feeds/cancel subplans: `product/plans/complete/connections-tabs-01-records.md` and `product/plans/complete/connections-tabs-02-acp-feeds-cancel.md`, including the cancellation repair `product/plans/complete/wait-for-both-acp-cancellation-boundaries.md`. Use the implemented APIs and contracts described below; do not reopen their schemas, alter their lifecycle behavior, or rebuild their services. Implement this host topic before the plugin subplan.
- The topic's shared row/window wire shapes live in `src/protocol/connections.ts`, composed through `src/protocol.ts`; topic notification and action types live in the plugin-independent `src/plugins/api-topics-connections.ts` and are composed into `api-topics.ts`. Add all of these contracts and host topic behavior in this subplan so the later concrete plugin consumes a complete, compile-checked contract rather than defining its own types or actions.
- Live rows come from `connectionCatalog(managers, label)` once for each `managers.tab.tabs` entry, preserving each `scope: 'tab'` row's owning label. Omit the catalog's SQLite entries during this pass, then emit exactly one `global` SQLite row per `managers.database.listOpen()` name. Its focus target is the first open tab in strip order whose `openDbs(label)` includes that name, or absent if no tab is attributed. A tab's tracked ACP session is represented by its matching record row, never twice; identify it using the tab runtime's `acpRecordId`, not a reusable label or `acp-<n>` session name. Monitor and editor-persona ACP entries remain live-only rows, owned by the tab whose catalog produced them.
- The topic is one flat list sorted by `orderingTimestamp` descending, then `kind` ascending and `id` ascending for deterministic ties. `ConnectionEntry` has no per-connection timestamp, so use the host's existing tab activity metric without claiming resource-level activity: tab-scoped live rows use the owning open tab's `runtime.lastActivity` (0 means no activity); each global SQLite row uses the greatest `runtime.lastActivity` among open tabs whose `openDbs(label)` includes that database, or 0 if none are attributed; durable ACP/agent record rows use their `updatedAt`. These are timestamps at each resource's owning tab or durable-record granularity, not per-connection activity. The host already exposes the tab metric as `TabActivityEntry.lastActivity` through `tabActivityRows` (`src/plugins/activity.ts`), which reads `tab.runtime.lastActivity` and reports 0 for a tab with no activity. Each live row otherwise carries its connection kind/id, existing catalog display text, owning tab label/name, `Open` status, and any existing `acpRef`; do not synthesize transcript references. Each record row carries the `AcpRecordRow` summary fields (including UUID record id, source kind, title, model, copied owner label/name, optional run id, timestamps, and derived status) and uses its UUID as record identity. Record rows keep the captured owner name after their tab closes. A `load` request exposes the newest 20 blocks; `loadOlder` grows that record's requested window by 20, capped at the available block count. Include full `AcpRecordWindow` data only for record ids requested through these actions, not for every record in every topic delivery. Keep requested window sizes in a `WeakMap<Managers, Map<recordId, count>>` owned by the topic source, prune ids no longer present in `acpRecords.rows()`, and remove an id on successful delete. This avoids label-keyed state and prevents independent controller/test manager instances from sharing loaded-window state.
- Coalesce `connections:changed` and `state:dirty` through one shared subscription timer, delivering the latest state once per `TABS_NOTIFICATION_WINDOW_MS` (100 ms) window. A mixed burst shares one timer. The timer reads current rows/windows at delivery time; unsubscribe removes both listeners and clears the pending timer. Topic actions are synchronous/fire-and-forget. `cancel`, `closeSession`, and `terminate` start their asynchronous cleanup without awaiting it; consume any returned promise rejection so a race after validation cannot become an unhandled rejection. Their changed record/run state arrives through the ordinary topic signals.

## Action contracts

All actions are checked against freshly composed current rows/records before acting. Unknown, stale, mismatched-owner, or inapplicable actions are no-ops and never resolve a label to a different resource after validation. This topic adds no arbitrary focus or manager access.

| Action | Request and behavior |
| --- | --- |
| `load` | Requires a currently existing record id. Set its requested window size to 20, then the caller reads topic data for that record. Repeated loads reset to the initial newest-20 window. |
| `loadOlder` | Requires a record already requested by `load` and still present. Increase its size by 20 up to `totalBlocks`; never create a window request implicitly. |
| `list` | Carries the invoking tab label. Return `listLines(managers, label).join('\n')`, or exactly `No open connections.` when empty. Do not include durable records in this legacy command output. |
| `open` | Names a current live row by kind/id and its owner. Focus only the row's owning open tab using its current strip index. For a SQLite row, focus its computed first-attributed tab; if none is attributed, no-op. A record row is opened by the eventual plugin's record-tab flow, not by this host action. |
| `close` | Names a current live row by kind/id and owner label; call `managers.connection.closeTarget(kind, id, ownerLabel)` without awaiting. SQLite is global, but still must match the current global row. Durable ACP record rows are not close targets for this action. |
| `cancel` | Names a current record id. Accept only a running core ACP record whose current owner tab still has that exact `runtime.acpRecordId`; call `managers.acp.cancel(ownerLabel)` without awaiting. Refuse agent records, idle/closed records, missing owners, and label-reused sessions. |
| `closeSession` | Names a current record id. Accept only an open core ACP record whose owner tab still carries that id; call `managers.acp.close(ownerLabel)` without awaiting, matching `acp reset` session closure. Never close by record owner label alone. |
| `terminate` | Names a current agent record id with a run id. Accept only when `managers.agent.isLive(runId)` and `managers.agent.isAgentRun(runId)` still hold; start `managers.agent.finish(runId, 'terminated')` without awaiting and consume a rejection if the run finishes between validation and dispatch. Do not let an old record id terminate a later run or a non-agent run. |
| `delete` | Names a current terminal record id; call `acpRecords.delete(id)`. Open records, absent records, and stale ids are ignored. Confirmation belongs to the later UI, not this server action. |

The action shapes are discriminated by `topic: 'connections'` and use record UUIDs or the exact current live-row identity. Include owner label on live-row `open`/`close` requests to bind actions to the row the user saw; never trust an action-supplied label as sufficient authorization. Keep actions synchronous: public `closeTarget` can start a browser promise internally, and cancellation/session/run cleanup proceeds through the existing owner lifecycle. Only `list` returns text.
