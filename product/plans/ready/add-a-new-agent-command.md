# Add a new `agent` command.

**Complexity: 9/10** — Independent ACP run ownership, nested delegation, explicit command attribution, remote lifecycle changes, and a lazy monitoring plugin span the server and client.

Execute an AI task in a new autonomous ACP session and return its status and task-dependent response after cleanup. Every run owns or borrows a workspace. Startup supplies selected skill paths and instructions; Janissary enforces those skills' command grants. An optional read-only tab displays provider activity. Use the configured sandbox when available, and post a notice when it is disabled or unavailable.

## Design decisions

### Launch and resolution

- The user enters `agent` with launch clauses followed by mandatory, terminal `execute <ai task> <parameters...>`. The invocation waits for task execution and cleanup. Parameters after the task path belong to the task, including text that resembles launch clauses.
- A local caller launches locally. A remote shell caller inherits its host and execution project unless `on <[user@]host[:path]>` overrides them. A pathless address uses the existing project lookup from the SSH login directory. Agent execution location and Janissary command context are separate: granted commands always use the original caller's captured context.
- Runs are headless unless `in a tab` is present. `in group <name|id>` selects an existing monitoring group; omitted grouping uses the caller's group. Group selection without `in a tab` is accepted and leaves the run headless, but an explicitly invalid group is still rejected.
- Create a fresh workspace by default. `in workspace <label>` borrows an existing workspace on the selected execution host, retaining a run reference even when other tabs use it. Release only the run's reference during cleanup; never delete a workspace another user still holds. A missing repository or origin is a launch failure, without an unworkspaced fallback.
- Resolve project tasks and skills from the provisioned execution workspace, not from uncommitted source-project files. Bare task filenames search recursively under its `ai/tasks/` first, then installed Janissary `ai/tasks/` only when there is no project match. Multiple matches within the chosen source are an error. Explicit task paths select the named file only inside the execution workspace or the execution host's installed Janissary task directory. Resolve relative paths from the execution workspace root and `$janissary` from that host's installation. Check real paths so symlinks cannot escape these roots. Reject outside paths without reading them.
- Repeated `with skill <name>` clauses resolve `skills/<name>/SKILL.md` in the execution workspace first, then the execution host's installed Janissary skills. Identical names are included once. Skills are optional. Do not automatically include a skill referenced by another skill.
- `using model <model id>` overrides the existing ACP default. `with effort <level>` defaults to medium. Reuse the existing OpenCode model catalog and default selection, and validate effort against the provider's advertised session options before sending task instructions. Explicit invalid selections never fall back silently.
- Reject duplicate singleton clauses and unknown or unsupported tasks, skills, groups, workspaces, models, and efforts before task execution. Workspace provisioning and provider negotiation may be needed to perform these checks; a failed check must still release acquired resources.

### Skills, commands, and child runs

- A selected skill's versioned `janissary.json` sidecar declares whole canonical Janissary command names, including all subcommands and arguments. A missing declaration grants no commands. Do not infer grants from prose, use command-prefix grants, or add a YAML parser.
- Define sidecar schema version 1 with a `commands` string list. Validate the object, supported version, and known canonical command names; malformed declarations fail launch. Normalize command names and deduplicate them. Snapshot task text, selected skills, and effective grants before the first task prompt; subsequent edits cannot widen a live run's grants.
- Supply selected skill paths and instructions to follow only those skills. Hard restrictions on skill files and the native skill loader are expressly excluded by the user's clarified answer. Other skill files may remain readable. This policy is an instruction policy for skill use and an enforced host policy for Janissary commands.
- Extend the existing ACP response-line command loop, without an MCP bridge or fixed tool-step cap for agent runs. A request is `janissary <command>` on the final nonempty reply line outside code fences. Also accept bare `question …` there when `ask-user` is selected, for compatibility with that skill. Do not scan earlier lines or execute fenced examples. Authorize each extracted command before invoking the canonical dispatcher. An unpermitted request returns a denial and leaves the task running. Do not inherit the shell ACP consumer's unconditional browser/database/question tool table.
- Execute permitted Janissary commands in the captured caller context, not in the ACP subprocess's workspace context. Native file and shell tools operate in the agent workspace. An explicit host shell escape is not a canonical Janissary command grant.
- Automatically approve this run's ACP permission requests, choosing an offered approval option. Other ACP consumers retain their existing denial or allowlist policies. Neither an unconfined run nor automatic ACP approvals bypass host command grants.
- A selected skill may grant `agent` for child launches. Each child has its own session, model, effort, workspace lease, result, and parent identity. It may select only skills permitted to its parent, with matching source category (project or installed), name, and instruction contents across workspaces or hosts. Compare the resolved instruction contents rather than absolute paths, which differ across hosts and clones. Cap the child's effective command grants at its parent's effective grants, even if the child's sidecar declares more commands. An unmatched skill fails child launch; a broader sidecar cannot expand authority. Parent termination aborts its children; teardown cannot leave a live child behind.
- A question requires both selection of `ask-user` and its `question` command grant. Route it to the original caller's existing question panel for headed and headless runs. Cancel returns `Question cancelled.` to the agent. Abort only the run's active or queued question when terminating it; preserve unrelated questions.

### Ownership, results, and monitoring

- Introduce an independent run owner under `src/agent/`. Its record owns the session, abort signal, workspace and remote references, activity, child runs, and created-tab identities. A manager indexes owners by opaque run ID; do not scatter per-run state across new label-keyed maps or attach execution lifetime to a monitor tab.
- Pass run ownership explicitly through command and tab-opening APIs. Record ownership only when a new tab is allocated. Focusing or updating a pre-existing tab does not adopt it. Preserve context through plugin activation, deferred launches, and wildcard opens; reject late allocations belonging to a run that has already ended. Do not use `AsyncLocalStorage`.
- The first completion, failure, or termination outcome wins and starts cleanup exactly once. Guard late chunks, command results, and provisioning callbacks by run identity and abort state. Closing the caller's tab or losing its remote context terminates the run. Closing the monitoring tab only removes monitoring.
- Return an optional structured command result with `status` (`completed`, `failed`, or `terminated`), `response` (the final task answer or diagnostic), and `cleanupWarnings` (a separate list). The final task answer remains text, including task-supplied JSON text; do not guess a task-specific schema.
- Await cleanup attempts before settling the result. Cleanup errors preserve the original task status and response and add warnings. Stop processes and child runs, abort questions, close only run-created tabs, await their resource releases, and release workspace and remote leases. Preserve existing users' references. Do not roll back ordinary durable effects of permitted commands.
- An ACP/provider error fails the task and triggers cleanup without automatic provider retries. Preserve the shared loop's one cold-start retry when the first reply is empty. If that retry is empty, or a later final answer is empty, fail the run and clean up. This cold-start accommodation does not retry provider errors or restart the task. Preserve unrelated ACP consumers' behavior.
- Implement a lazy bundled `agent-monitor` tab plugin. Its title is `Agent: <task filename>`. The metadata bar shows the full launch command, model/effort and host/workspace facts, status flags, and `Terminate`. No terminal, command bar, direct prompt entry, or ACP session is owned by this plugin.
- Display all activity reported by ACP: received thinking, messages, tool inputs/results/updates, plans, and permission decisions. Only message text participates in command extraction and the final answer; thought and tool events never become commands. Reuse sanitized shared transcript rendering, with tool activity expanded. Apply the owning application's existing `transcriptMaxLines` history limit and drop the oldest entries, while preserving the final response separately from the activity history. Providers can expose only the reasoning they actually report.
- Add a specific monitoring contribution and a tab-scoped `agentRun` projection to the existing plugin contract, following the core ACP response projection pattern. The plugin payload carries its binding, not a second activity-history copy. The core selects the declared contribution, activates it lazily, and binds its tab to one run on the server. The published client API exposes only that tab's typed projection and read-only transcript surface; server capabilities permit terminating that bound run only. A client-supplied run ID cannot select another run.
- Coalesce monitor projection updates and compare a monotonically increasing run revision before delivery. Preserve event order in the owner. Send tab-targeted run updates through the existing authenticated WebSocket instead of broadcasting whole application state for every provider chunk. Include the latest projection in initial/reconnected state. The host owns subscriptions and disposes them with the monitoring attachment. Closing or disabling the monitor plugin leaves the run active; do not disable unrelated plugins or ACP consumers.
- Use configured workspace confinement normally. When disabled or unavailable, proceed and post `Agent: sandboxing is disabled.` only to the notifications feed, for both headed and headless runs. Do not repeat the notice in caller output or monitor content. Command grants remain enforced.

### Approved wording

The termination response is `Agent terminated.`. Question cancellation remains `Question cancelled.`. Errors use `Agent:` and the approved formats `Agent: unknown <kind> "<value>".`, `Agent: unsupported effort "<level>" for model "<model>".`, `Agent: duplicate clause "<clause>".`, `Agent: ambiguous <kind> "<value>": <matching paths>.`, and `Agent: command not permitted: <command>.`. Other execution and cleanup diagnostics use `Agent: <reason>`.

The approved metadata states are `Provisioning`, `Running`, `Waiting for answer`, and `Cleaning up`. Disable `Terminate` once an outcome has been latched and cleanup has begun. Format caller output as `Status: <completed|failed|terminated>`, followed by the response, with each cleanup issue on a separate `Cleanup warning: <reason>` line. Usage is `Usage: agent [launch options] execute <ai task> [parameters...].`; the help entry lists every launch clause and its defaults. All product and implementation choices raised during both improvement passes are resolved in this document.

## Proposed changes

Implement in this order, keeping each checkpoint within the 200-line source limit. New module names below are planned files; references in the reuse table name current files.

1. **Contracts, parser, and resolution.** Add `src/agent/types.ts`, `src/agent/command-parser.ts`, `src/agent/task-resolution.ts`, and `src/agent/skill-grants.ts`. `parseAgentCommand` is pure and handles quoted tokens, arbitrary launch-clause order before `execute`, duplicates, and the untouched parameter tail. Task resolution reads the execution workspace after provisioning and uses `listTasks(executionWorkspace, executionInstallation)` for discovery, filtering source and basename before applying the selected precedence. Add a strict discovery mode for agents so unreadable directories fail rather than silently falling through; preserve the picker's existing tolerant mode. Do not build another directory walker. Validate explicit task real paths against the execution workspace or installed task root before reading; expand only the execution host's documented `$janissary` variable, not arbitrary shell substitutions. Skill resolution reads the selected `SKILL.md` and schema-version-1 JSON sidecar, returns immutable whole-command grants, and rejects invalid declarations. Add a `question` declaration beside the bundled `ask-user` skill. Include `skills/` in `package.json`'s published files so installed fallback actually exists in packaged installations. Where confinement is active, permit read-only access to selected installed skill directories and their support files through existing sandbox path parameters; never carve in the entire installation or override secret denies.

2. **Independent owners and leases.** Add `src/agent/run.ts` (`AgentRun`), `src/agent/manager.ts` (`AgentRunManager`), and focused workspace/cleanup helpers. Mint run IDs with `randomUUID`; each owner holds its own mutable state and `AbortController`. Register `managers.agent` and its caller-close/shutdown hooks. Introduce headless workspace/remote leases using the existing resource services, without a hidden tab. A monitor attaches to the owner without acquiring its execution lifetime. Freeze caller identity/context and verify it is still the same live caller before effects; numeric tab indexes or a recycled label are insufficient.

3. **Typed command results and explicit attribution.** Extend the canonical `Command` contract and `CommandManager` with optional structured results and a server-created invocation context carrying run ID, invocation ID, caller context, and abort signal. Preserve void-returning commands. `agent` launches through this executor and returns only after cleanup. Shell dispatch preserves existing `dispatched`, `output`, and `coreResponse` fields and adds the optional result; format the final response once. A nested invocation receives its child's result directly rather than collecting every transcript append on the shared caller tab. For legacy commands that produce output, correlate capture with the explicit invocation context instead of unrelated caller traffic.

4. **Propagate the context through real allocation paths.** Carry the trusted ownership context through core command handlers, open/edit/harness/file-navigator services, plugin command adapters, `PluginFailureOrigin`, capability construction, deferred `launchTab` callbacks, and `openClaimedFiles`. Check run-originated dispatcher calls centrally so a nested dispatch cannot lose its authorization context. Add ownership metadata only at actual new-tab/resource allocation; preserve de-duplication behavior for existing tabs. Store tab association on the tab runtime, and keep owned resource identities on the run. Revalidate the owner before a deferred allocation. Carry parent identity into nested `agent` launch and compare each child's resolved skill source category, name, and instruction contents against the parent's immutable selection before its task prompt. Intersect child command declarations with the parent's effective grant set.

5. **Extend shared ACP machinery.** Add focused policy, session-configuration, and activity helpers beside `src/acp/index.ts` rather than growing it past the file limit. Extend `AcpOptions`/`AcpSession` additively for an explicitly autonomous connection, an awaited prepare/configure operation, typed session updates, and awaited teardown. Preserve ordinary permission decisions and message callbacks. Resolve model with the extracted existing default resolver, validate advertised effort values (including grouped options and absent/unknown categories), and configure the session before task execution. Do not silently reinterpret session modes as models or ignore unsupported effort, including unsupported default medium. Forward thought/tool/plan/permission activity separately from the reply-text buffer. Reuse `runAcpToolLoop` by supplying an infinite budget through its existing numeric `maxSteps` option; do not add a second loop or another unlimited-mode API. Omitted options retain the current eight-step behavior. Ensure thrown or rejected tool execution settles through the loop's existing error channel instead of leaving a run pending.

6. **Execute granted commands and await questions.** Add `src/agent/command-tools.ts` to derive the agent primer, extractor, and authorized runner from immutable grants and the canonical registry, including the existing pure `help` route. Parse only the final nonempty line outside code fences for the explicit `janissary` marker, or compatible bare `question` when `ask-user` is selected. Retain the emitted line for display filtering and strip the marker only for canonical dispatch. Authorization uses the resolved canonical name, not unchecked prefix matching or a copied registry. Question requests additionally require the selected `ask-user` skill and `question` grant. Make the existing question command await `runQuestionCommand` and expose its result with the run's abort signal; retain its direct-user panel and transcript behavior. Return denials and ordinary command errors to the agent without starting another prompt after abort. Fail an empty final response after the existing first-turn cold-start accommodation. Do not register a second definition of `question` or `agent`.

7. **Remote parity and reported teardown.** Extend `acp-open`/readiness with autonomous policy, configuration requests, and execution-host task/skill resolution results; extend the same ACP family with typed activity and close/release acknowledgments. Update frame declarations, encoders/decoders, channel listeners, server holders, and both protocol tests, then bump the remote protocol. An older peer must refuse instead of ignoring policy fields. Fresh remote workspaces use their own channel; a borrowed workspace retains its existing shared channel without changing other sessions. Agent SSH launches must work without a tab or input surface and fail promptly when authentication requires interaction. Tag run-only leases as ephemeral so caller or execution-transport loss aborts the agent instead of entering ordinary remote recovery or relaunch persistence. Extend remote peer-detach handling to close autonomous sessions and release their references while preserving ordinary shared users. Record cleanup uncertainty as a warning when the far side cannot acknowledge it; bound teardown acknowledgment waits to 10 seconds rather than waiting forever. Do not let the existing 250 ms shutdown drain cut off a pending agent cleanup acknowledgment.

   Add an awaitable, reported workspace-release path instead of relying on error-suppressing `removeWorkspace`. Collect errors and continue releasing later resources. Wait for provisioning cancellation and owned-tab releases before final lease release, so a late clone or a deferred tab release cannot outlive a settled result. Stop the ACP process and its owned descendants, then release resources while remote transport is still live. Keep the existing best-effort workspace API compatible for non-agent callers. 8. **Lazy monitor plugin and documentation.** Add `src/plugins/agent-monitor/manifest.ts`, import-free `shared.ts`, and `activate.ts`; add the lazy client entry and components under `web/src/plugins/agent-monitor/`. Add catalog and literal server/client loader entries. Coalesce run-state publication by revision and ignore unrelated state changes; use a tab-targeted `ServerEvent` over the existing WebSocket for streamed updates and the same projection in initial/reconnected state. Reject obsolete run IDs/revisions when applying updates, and keep the metadata/body/styles in the lazy plugin chunk. Use standard budgets (1000 ms activation, 5000 ms user calls/client load); exempt core termination/cleanup wait using the existing host-work deadline mechanism. Client intents identify only the owning tab; the host derives the associated run. A bad request rejects without disabling the plugin. No new plugin notification topic or host-state delivery queue is needed.

   Keep core wire shapes in `src/protocol.ts` and the plugin binding envelope in its import-free contract, with no client mirrors or cross-feature imports. Do not import host internals. Render reported thoughts/tools verbosely, metadata, and `Terminate`; omit command-bar and terminal capabilities and disable prompt-rerun/input actions in the read-only transcript surface. Update the ACP/workspace/remote/question/tab/plugin/application-command specs, add `product/specs/agent-command.md`, document the JSON grant format and whole-command scope, and add user command documentation plus the alphabetized `help.md` row. Preserve the v2 frozen compatibility fixtures; these optional plugin additions do not remove existing contracts.

## Out of scope

Hard file or native skill-loader isolation, MCP command bridges, a general core-surface framework, `AsyncLocalStorage` attribution, separate agent model/effort catalogs, and a separate remote run frame family are excluded by the user's implementation answers.

Run-listing and headless-cancellation commands, an interactive monitoring terminal or command bar, copying source-project local task/skill edits into a fresh clone, automatic provider retries, adopting pre-existing tabs for cleanup, and running without a workspace are excluded. Do not add the separate backlog feature's built-in child-agent-launching/monitoring skill. Child launches through an explicitly granted `agent` command are included.

Do not promote this file to `ready/` or implement the feature during this planning task. Only the completed draft and the matching feature-backlog removal ship now.
