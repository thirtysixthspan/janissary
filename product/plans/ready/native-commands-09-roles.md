# Native commands: Roles restrictions

**Complexity: 3/10** — an existing plugin consumes the published commands topic and adds a display-only payload field, with no new protocol, persistence, or policy authority.

## Goal

Show effective native command restrictions beside role grants while keeping grants and picker choices intact.

## Decisions and dependencies

- Units 1–8 are complete and published on this branch. Unit 9's API dependency is unit 7's `commands` topic and unit 2's snapshot; unit 8's Commands tab is the manual control surface, not an API dependency. Unit 10 follows and verifies the result in the full integration.
- The server-owned snapshot is the only authority. Roles reads it with `capabilities.topicData('commands')` and maps `effectiveEnabled`/`effectiveAgentAccess`; it never reads `commands.json`, calls the topic's `refresh` action, subscribes to `nativeCommandSettings`, or recomputes parents. The manager's `isEnabled` already folds every ancestor (`src/native-commands/manager.ts:71-77`), and `effectiveAgentAccess` already includes the global check (`src/native-commands/manager.ts:94`).
- Keep `nativeCommands` as the full `NATIVE_ACP_COMMANDS` vocabulary. Add `commandRestrictions: Record<string, 'application-wide' | 'agents'>` with an entry only for a vocabulary command that is currently restricted. A command is `'application-wide'` when `effectiveEnabled` is false, otherwise `'agents'` when `effectiveAgentAccess` is false; application-wide wins when both are false.
- `commandRestrictions` is display state only. It is never written to `roles.json`, never filters the picker, and never refuses an add or remove. A grant added while its command is restricted is stored normally and is dimmed by the republish that follows the edit.
- Add `'commands'` to the manifest's `notifications` after `'models'`, and add `'topicData'` to its capabilities. Do not add `topicAction`: Roles never refreshes or edits the settings. The existing `notify` handler satisfies `validateActivation` (`src/plugins/activate.ts:63-69`). `TAB_PLUGIN_API_VERSION` stays 3.
- Bump `ROLES_PAYLOAD_SCHEMA_VERSION` from 3 to 4 (`src/plugins/roles/shared.ts:1`) because the payload gains a required field. Change the Roles literal in `web/src/plugins/registry.tsx:101` from 3 to 4; the pin at `web/src/plugins/registry.test.tsx:39` already compares against the constant. The manifest reads the constant at `src/plugins/roles/manifest.ts:16`, so it needs no literal change.
- Read the current snapshot whenever a payload is built: the open path, every edit republish, and the models repaint. That is the initial read; later changes arrive only through the manifest's `commands` notification. Do not call `refresh` from the read or notify path.
- The commands notification repaints through the existing `publish` path with `create: false`, reading the current snapshot rather than trusting `event.data`, so a late delivery cannot overwrite a newer snapshot. It sends no title and writes no roles file.
- An invalid commands slice reports `invalid commands topic data` and opens nothing on the open path, following `src/plugins/commands/activate.ts:36-39`; a notification or edit republish treats an invalid slice as `{}` so a topic-contract failure never blocks a roles edit. The disabled-plugin empty slice (`{ commands: [], source: 'default', path: '' }`) also maps to `{}`.
- A restricted grant is dimmed with the new `roles-entry-restricted` class and carries a `title` of exactly `Disabled application-wide` or `Disabled for agents`. Unrestricted rows carry neither. Unknown grants keep the existing `roles-entry-missing` class and `Not a native command` title, because the vocabulary check runs before the restriction lookup. No visible text or icon is added.
- The UI lookup uses `Object.hasOwn` on `commandRestrictions`; stored grants can be arbitrary hand-written strings, and a bare index would read inherited object members for names such as `constructor`.
- The required field, guard, registry literal, and every `RolesPayload` fixture must land in one change; there is no green intermediate state with the old fixtures. The manifest capability/topic and the activation read must also land together, or `topicData` throws `used capability "topicData" without declaring it`.

## Proposed changes

1. Extend `src/plugins/roles/shared.ts` with a `CommandRestriction` type and a required `commandRestrictions` field on `RolesPayload`; update `isRolesPayload` to accept a record whose keys are in `nativeCommands` and whose values are exactly `'application-wide'` or `'agents'`. Bump the schema constant to 4 and keep the module import-free. Change the Roles schema literal in `web/src/plugins/registry.tsx:101` to 4.
2. Add a server-only `src/plugins/roles/command-policy.ts` exporting `commandRestrictionsFrom(data: unknown)`, which returns the restriction map or `undefined` for data it cannot read. It validates only the fields it uses (`commands` as a row list; each row's string `name` and boolean `effectiveEnabled`/`effectiveAgentAccess`), maps only names in `NATIVE_ACP_COMMANDS`, applies the application-wide precedence, and never walks `parent` or reads a file. Use the `.js` suffix on its relative server imports, and keep it out of the client entry so `web/src/plugins/roles/index.tsx` keeps reaching the contract through `@shared/plugins/roles/shared` rather than the server module. Keeping this mapping out of `activate.ts` leaves room under the 200-code-line limit (the activation currently counts 179 code lines).
3. Update `src/plugins/roles/manifest.ts` to declare `'commands'` beside `'models'` and add `topicData` to the capability list. In `src/plugins/roles/activate.ts`, extend `payloadFrom` to take the restriction map and include it; make `publish` read the current snapshot through `topicData('commands')` and use `{}` when the slice is invalid; make the open path read the snapshot before `openOrFocusTab` and report `invalid commands topic data` instead of opening when it is invalid; add a `commands` arm to `notify` that calls the same `publish` path with `create: false`. Leave the models arm and the edit queue unchanged.
4. Thread `commandRestrictions` from `RolesTab` through `RoleCard` to `RoleCommands`. In `RoleCommands`, keep the unknown check first, then apply `roles-entry-restricted` and the exact `title` for a restricted vocabulary command; leave `orderedRoleCommands`, `availableRoleCommands`, `canAddRoleCommand`, the add/remove intents, duplicate handling, and the remove control untouched. Add a `roles-entry-restricted` rule beside `.roles-entry-missing` in `web/src/plugins/roles/roles.css:35` with the same dimming, without changing the missing rule.
5. Update `product/specs/roles.md:84-96` to describe the dimmed grant, both tooltip reasons, application-wide precedence, parent-derived global availability, and that the marker is recomputed from the live Commands topic and never stored in `roles.json`, mirroring the model-catalog marker at `:70-73`. Update `product/specs/tab-plugins.md:128` to name Roles as a second consumer of the commands slice and `:307-309` to mention the `topicData` read. Add one sentence to `documentation/user-documentation/tab-types/roles.md:27` explaining the dimmed grant and the two tooltip strings. Do not edit `product/specs/application-commands.md:9` or `product/specs/commands-tab.md:13`; they already state the settings authority and the saved-versus-effective distinction.
