# Shell replies and connection popup integration

**Complexity: 5/10** — asynchronous ACP settlement must preserve exactly-once delivery across refusal, cancellation, reset, and failure while record opening crosses a new RPC and three popup consumers.

## Goal

Make shell `acp <prompt>` asynchronous, render each settled reply as Markdown at the current bottom of shell output beneath its exact echoed command, and let applicable ACP/agent rows open their connection tab from shell, editor, and harness connections popups without changing the existing transcript-snapshot buttons.

## Decisions and dependencies

- Implements source-plan decisions 9–10, 20, 31, 35, and 37, covering shell settlement and popup integration. The source plan `product/plans/ready/connections-tabs.md` is the full authority for the complete feature; this subplan does not repeat or reopen its decisions.
- Depends on completed subplan 02 for core ACP record ids and settled outcomes, and completed subplans 04a, 04b, and 04c for the connections plugin, row model, and record-tab owner. Use the current `follow-streamed-connection-activity` repair as the verified history-follow behavior; do not rework it here.
- Keep this change on plugin API v2. Do not remove `useAcpResponse`, `TabView.acpResponse`, `launchShellHere()`, or the shell response panel; those removals and API v3 fixture work belong to subplan 06. Keep existing panel and ACP transcript-snapshot behavior during this integration.
- Each `acp` invocation creates one fresh background reply id and appends exactly one completed reply, regardless of whether it produces an answer, is refused, fails, is cancelled, or is closed/reset while pending. `resolveCommand` trims the command and strips a leading slash (`src/resolve.ts`, `resolveCommand`), so carry the original input from `CommandManager.dispatchLine` through invocation-local context to the `acp` command instead of reconstructing it from the normalized command argument. Use that exact typed command as the reply line; malformed/empty invocations echo the actual typed line. The settled output is the result's exact text, including `ACP: a prompt is already running.`, `Usage: acp <prompt>.`, `ACP error: …`, `ACP session closed.`, and the cancellation text `ACP: prompt cancelled.` from source-plan decision 37.
- A refusal does not disturb the active request. Nothing queues. Reset/close settles an outstanding shell request once as `ACP session closed.`; cancellation settles it once as `ACP: prompt cancelled.` and leaves the session open. Later callbacks after settlement must not append a second reply.
- Preserve `acpEntries` tagging: `settleAcpPrompt` still finds the running ACP transcript entry through that identity (`src/acp/response.ts`, `settleAcpPrompt`, and `src/tab/transcript/events.ts`, `acpEntries`). Continue the existing background-reply snapshot/replay protocol: server snapshots retain completed replies, and `useBackgroundReplies` deduplicates replay by stable id (`web/src/plugins/background-replies.ts`, `subscribeBackgroundReplies`; `web/src/plugins/shell/useBackgroundReplies.ts`, `seen`).
- Extend the background-reply shape with optional `line`. Set it only for ACP replies, recognizing the ACP command prefix in the stored input; monitor asks also have a nonempty input (`src/monitor/ask.ts`, `monitor ask`) and must retain the `monitor` fallback. Replies without a line continue to render under `monitor`; the shell's existing `displayReply(line, markdown)` renders output as Markdown (`web/src/plugins/shell/useShellSubmit.ts`, `displayReply`).
- In the popup, a row carrying `recordId` opens/focuses that record's connection tab; a row carrying a tab-scoped `acpRef` opens/focuses the corresponding core ACP connection tab. Preserve the separate snapshot button on surfaces that currently supply its callback. The snapshot action remains `openAcpTranscript` and continues to make a read-only point-in-time transcript; clicking its button must not trigger row opening. Monitor- and editor-scoped ACP rows remain snapshot-only.
- An active agent run appears in its caller tab's popup as an ACP-kind row titled `Agent: <task filename>`, with its durable `recordId`, but no `acpRef`; it therefore opens the run's record tab and has no transcript-snapshot button. Use the existing run caller and record identity (`src/agent/run.ts`, `AgentRun.caller` and `recordId`), not the monitor tab label or a fabricated ACP reference.
- The row-open callback is optional in `StatusPanels`; it is enabled only for `recordId` and tab-scoped `acpRef` rows. The shell's plugin client has no raw socket or core-RPC method today, so add a narrow optional `openConnection` client capability for API v2, bound by the host to that plugin tab's label. This additive capability does not bump the API version. The editor and harness consumers use their existing `JanusClient` to send the same core RPC with their own tab label. Resolve current tab-scoped ownership on the server and no-op if that tab or its live record binding has disappeared. A durable record id remains openable after its session or caller has ended; reject only a missing/expired record. Do not trust a client-provided tab payload as authority.

## Proposed changes

1. **Shell settlement.** In `src/command/manager.ts`, carry the original input through the invocation-local command context; in `src/commands/acp.ts`, start `managers.acp.promptResult` without awaiting it so command-bar dispatch returns immediately, while retaining `coreResponse: true` to suppress an immediate duplicate. On its single settlement callback, append one completed log entry with `input` set to that original input, `output` set to the result text, and `background` set to a new `randomUUID()`. Cover synchronous refusals and failures as well as asynchronous answer, tool-loop error, reset/close, and cancellation outcomes; guard the append so no competing settlement path can emit twice. Do not write the completion as a second ordinary command reply.
2. **Reply projection.** Add optional `line` to the shared background reply type and its `onBackgroundReply` callback in `web/src/plugins/api.ts`, retaining `id` and `output`. Project `entry.input` as `line` only for completed background entries whose input is an ACP command (case-insensitive `acp` token, including a bare usage invocation); leave `monitor ask …` and other background entries without it even when their input is nonempty. If the projection makes `src/tab/view.ts` exceed the 200-line code limit, extract it into the focused `src/tab/background-replies.ts` module and import it directly with the `.js` extension. Update `web/src/plugins/shell/useBackgroundReplies.ts` to call the existing renderer with `reply.line ?? 'monitor'` and `reply.output`. Keep full-state replay and stable-id deduplication intact.
3. **Agent caller row.** Add the active agent-run row to its caller's projected `ConnectionView[]`, carrying `recordId` from the run and its task-filename title, but no `acpRef`. Add optional `recordId` to `ConnectionView` in `src/protocol/tab.ts`. Keep completed runs out of the live popup; their durable rows belong to the connections tab. Preserve every existing row and reference, including editor and monitor ACP rows.
4. **Open-record RPC.** Add the typed core RPC `openConnectionRecord`, with parameters carrying the popup-owning tab label and either a durable `recordId` or a tab-scoped `acpRef`; require the `acpRef.label` to match the owner label and reject monitor/editor scopes. Add its `ack` entry to `src/client-message.ts`, validate its discriminated shape in `src/client-params/core.ts`, route it in `src/message/tabs.ts`, and delegate from `src/controller.ts` to a focused controller feature module if the controller facade would otherwise exceed 200 lines. For a record id, dispatch the existing `connection <recordId>` plugin command in the owning tab. For a tab ACP reference, resolve that tab's current `runtime.acpRecordId` and dispatch `connection <recordId>` there. This reuses the connections command's lazy activation and existing record-tab opener even before the connections list tab has activated the plugin; a missing tab or record is a no-op/rejection, never a second tab-opening implementation. Existing `openAcpTranscript` continues to open snapshots and is not repurposed.
5. **Popup wiring.** Add optional `onOpenRow(row)` to `StatusPanels` and make only supported rows openable: rows with `recordId`, or an `acpRef` whose scope is `tab`. A row's text is keyboard-operable as well as clickable. Keep transcript and close buttons as distinct actions, stopping both buttons' clicks from bubbling into row opening. Shell `ShellTabMeta` calls the new optional `openConnection` capability; add its tab-bound adapter in `web/src/plugins/api.ts` and `web/src/plugins/plugin-client-capabilities.ts` without exposing the socket or a general RPC method. Editor rows use `useEditorConnections.ts` and `EditorConnectionsPanel.tsx`; harness rows use `harness-tab-intents.ts` and `HarnessTabLayer.tsx`. Keep existing editor transcript-snapshot buttons and close controls unchanged; do not add a snapshot button to a surface that does not currently render one. The new optional capability is additive API v2 and does not change `TAB_PLUGIN_API_VERSION`.
6. **Specs.** Update `product/specs/acp.md`, `product/specs/shell-tab.md`, and `product/specs/tab-plugins.md` for asynchronous Markdown replies, the optional reply line, the new tab-bound client capability, and unchanged v2 response-panel behavior. Update `product/specs/connection.md` and `product/specs/agent-command.md` for popup row opening, snapshot-button separation, and the caller popup's running-agent row. Add or update `product/specs/connections-tab.md` to specify how popup opening reaches the record tabs. Update the tab-plugin author reference at `documentation/developer-documentation/tab-plugins.md` for the additive v2 capability without recording an API-version bump. Keep API v3 removals, its compatibility fixture, and unrelated record-tab behavior for their owning plan/previous completed subplans.

## Tests

A close/cancel/error race must not produce two entries, and reset/cancel must leave the session state specified above.
