# documentation

## ready

* pull-request-review (3/10) — Of 20 user-visible facts, 17 are correct and three are missing, with none wrong. The missing facts are that a subplan skips all three closing stages (opening the pull request, the review cycle and the update), that the single-plan route publishes its canonical source plan first and then improves it in place preserving its identity, and that any recovery which changes the branch needs another test/repair cycle, a final update and fresh validation of the new published head while an unsupported primary branch blocks completion. These are specified in `product/specs/pull-request-review.md` and implemented in `ai/tasks/feature/build-a-complex-feature.md`. Add them to the "How a complex feature is staged" and "Testing and final checks" sections of `documentation/user-documentation/workflows/pull-request-review.md`; no help page carries this workflow.

* pull-request-testing (3/10) — Of 21 user-visible facts, 19 are correct and two are missing. The "Which branch runs" section of `documentation/user-documentation/workflows/testing-a-pull-request.md` says preparation, start and stop instructions all come from the pull request's base branch, but `product/specs/pull-request-testing.md` and `ai/tasks/feature/test-pull-request.md` require preparation to be read from `master` (falling back to `$janissary/ai/tasks/workspace/prepare-workspace.md`) while only start and stop come from the base branch, so a tested PR cannot rewrite its own tester. The same section omits that the supply-chain audit uses the installation's own runner rather than the branch's copy, runs no install scripts and installs exactly the audited lockfile. Add both details to that section of `documentation/user-documentation/workflows/testing-a-pull-request.md`; no help page needs editing because `help/tasks.md` has no row for this task.

* task-picker (3/10) — Of 28 user-visible facts, 24 are correct and four are missing, with none wrong. The `auto-build-a-feature` task is undocumented: it accepts a feature description, plans interactively, offers at most ten maturity gaps, opens one pull request and never merges, needs a harness tab with an attached E2E browser, and stops on empty input with `Status: blocked` and `Reason: feature description required`. Also absent are `planning/rate-plan-complexity` (1–10 rating), `planning/rate-plan-complexity-quantitative` (1–9 formula rating) and `planning/decompose-plan` (ordered subplans), plus the small rules that other keys have no effect while the picker is open and that hovering the keyboard-selected row keeps the keyboard highlight. Add these to the "Choosing a feature or issue task" and "What a shipped task does when you pick it" sections and the picker-behavior prose of `documentation/user-documentation/command-bar/tasks.md`, optionally cross-linking `documentation/user-documentation/workflows/product-development.md`. Ground truth is `product/specs/task-picker.md`, `src/tasks.ts` and `web/src/pickers/useTaskPicker.ts`.

* transcript (3/10) — Of 21 verified user-visible facts, 19 are correct and two are missing, with none wrong; an unverified spec detail about a prompt-bar scrollbar indicator was excluded from the count. The missing facts are that the mouse scroll wheel moves the transcript one line per tick, which no user doc or help states, and that a running shell command's transcript entry carries an **open in terminal** action and, if the command ends up in a terminal, reads `(ran in terminal)` once finished. The first belongs in the transcript scrolling portion of `documentation/user-documentation/getting-started/keyboard.md`, the second in the captured-shell portion of `documentation/user-documentation/command-bar/shell.md` or the shell-output section of `documentation/user-documentation/getting-started/tabs.md`. Ground truth is `product/specs/transcript.md`, `web/src/shared/transcript/useTranscriptScroll.ts` and `web/src/shared/transcript/transcript-line.test.tsx`.
