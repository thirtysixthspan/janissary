* Give every wall-clock wait in the suite a budget that is a stated multiple of the interval it actually polls, instead of leaving nine fixed sleeps and forty-six raised timeouts to absorb a loaded machine. — deferred: complexity 8/10, requires an empirical multi-run flake baseline on an idle machine and then spans the vitest config, about ten test files with forty-nine timeout overrides, and the CI workflow.

Existing Debt: Nothing states a per-test time budget, so `vitest.config.ts` sets `hookTimeout: 30_000` on the `server` project and leaves `testTimeout` alone on both `server` and `client` — meaning the real ceiling is vitest's 5s default, unstated and free to move with a vitest upgrade. Against that, forty-six tests across nine files pass an explicit `15_000` timeout and three more pass `30_000`, so the budget is currently expressed as forty-nine local overrides that each say "this test is slow" without saying why. Underneath sit nine genuine fixed sleeps (`setTimeout(resolve, N)` for 250/60/50/30/20/10 ms) and forty-four files polling with `waitFor`, and no `pool`, `fileParallelism`, `maxConcurrency`, `isolate`, or `sequence` setting anywhere in the config, so file-level parallelism is whatever vitest's defaults happen to be on a given machine. The sharpest instance is `src/browser/e2e-ready.test.ts:35`, whose `PATIENCE = 60` is spent both as a sleep and as the `boundMs` for `waitForListening` — while the production probe it waits on runs every `PROBE_INTERVAL = 25` (`src/browser/e2e-ready.ts:16`), leaving the timeout assertion at `:82` roughly two probe attempts to fail on. Severity: 4/10

Existing Risk: 4/10 - A suite that goes red for reasons unrelated to the change under test trains everyone to re-run before believing it, and the re-run that comes back green is read as "fine" rather than as "the signal is broken". That is how a real regression in `src/index.test.ts`, `src/request-boundary.test.ts`, or `src/open/route.test.ts` gets waved through, and `.github/workflows/ci.yml:47` runs `npm run test` exactly once, so nothing upstream catches a rerun-then-green either. The cost is not the flake itself but that it makes every other failure in the suite negotiable.

Proposal Risk: 1/10 - These are test-internal timing and budget changes with no production code involved, and each fix is locally verifiable by re-running the one file. The real hazard is the tempting wrong move rather than the change itself: raising `testTimeout` or `PATIENCE` until the suite goes quiet would convert a visible flake into an invisible slow suite and hide the next genuine hang, so the budgets must be derived from the interval being waited on rather than picked to pass.

Proposal: Start by establishing a real baseline, because the evidence so far is not good enough to act on. Six consecutive `npm test` runs on a machine already saturated by earlier runs produced a rotating failure set — `src/index.test.ts` (16 cases), `src/open/route.test.ts` (9), `src/browser/e2e-guard.test.ts` (8), `src/request-boundary.test.ts` (5), `web/src/App.test.tsx` (2), `web/src/plugins/SessionsDockedHeader.test.tsx` (2), `src/browser/e2e-ready.test.ts` (2), plus `src/workspace/index.test.ts`, `src/remote/serve-root.test.ts`, `src/remote/serve.test.ts`, `src/harness/index.test.ts`, `web/src/plugins/registry.test.tsx`, and `web/src/plugins/PluginTabLayer.test.tsx` — while every one of those files passed when run in isolation, and the failure *messages* were never captured. So: on an idle machine, run the suite five times, record which tests fail and at what rate, and keep the assertion text for each. Treat the two failure shapes as separate problems, because they have different causes: the ones that take a whole file with them (`src/index.test.ts`, `src/request-boundary.test.ts`, `src/open/route.test.ts`, `src/browser/e2e-guard.test.ts`) point at a shared real resource — a bound port, a real child process, a fixed path under the OS temp root — contended between parallel files, whereas the ones that take a single test point at a wall-clock assertion inside it. Then, in this order: (1) Fix the provable class first, the budgets smaller than the interval they poll. In `src/browser/e2e-ready.test.ts`, express `PATIENCE` as a multiple of the `PROBE_INTERVAL` it is racing rather than a bare `60`, and check `src/browser/e2e-guard.test.ts` and the nine real sleeps for the same shape; where a test genuinely needs to wait on a poll, export the interval and derive from it so the two cannot drift apart again. (2) Give the whole-file failures a resource that is theirs alone — bind port `0` per file as `e2e-ready.test.ts:26` already does, and give each file that touches the filesystem its own temp root rather than a shared one — and where a resource genuinely cannot be duplicated, serialize those files instead of hoping. (3) State the budget once: set `testTimeout` explicitly on both the `server` and `client` projects in `vitest.config.ts` so the ceiling is a decision recorded in the config rather than a default, and consider pinning `poolOptions`/`maxConcurrency` for the same reason. (4) Reclaim the forty-nine timeout arguments rather than leaving them as the record of which tests are slow — `web/src/App.test.tsx` alone carries eleven `15_000` overrides and does a dynamic `await import('./App')` inside each test, which hoisting to a module-scope import or a `beforeAll` should make unnecessary. (5) Close the loop in CI by repeating the affected files (vitest's `--repeat`, or a second run of the project) so a flake is caught by the pipeline instead of by a human noticing a red build. Note for whoever picks this up: none of this has been observed on `ubuntu-latest`, only on a loaded macOS box, so the CI repeat in step (5) is also the check that says whether the problem reaches CI at all.
