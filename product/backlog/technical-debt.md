# technical-debt

## ready

* Give the two commands that are still dispatched by inline regular expressions a definition in the command registry, so every path that runs a command agrees on what they are.

Existing Debt: `harness` and `ssh` have no entry in the command registry and are instead matched by two regular expressions ahead of it, in one of the three places that dispatch a command line, with byte-identical bodies that differ only in which manager they call — and a fourth file hand-lists their names so a plugin cannot claim them, with nothing tying that list to the branches it exists to shadow. Severity: 7/10

Existing Risk: 5/10 - The command-capture path has no such branches, so a command sent to another tab, or asked of it as a request, answers `Unknown command: "harness claude"` for the very text that launches a harness when it is typed into that same tab.

Proposal Risk: 2/10 - Both commands would resolve through the registry every dispatcher already consults, leaving only the ordering rule that a longer command name must precede a shorter one that prefixes it, which the registry array already lives with for two other pairs.

Proposal: `CommandManager.run` in `src/command/manager.ts` tests `/^harness\b/i` and `/^ssh\b/i` before calling `resolveCommand`, and each branch appends the input to the transcript, calls `this.managers.harness.run(input)` or `this.managers.ssh.run(input)`, and appends the returned error string — the same three statements twice. Neither name appears in `coreCommands` in `src/commands/index.ts`, so `resolveCommand` in `src/resolve.ts` classifies both as unknown, and so does the registry loop in `CaptureManager.run` (`src/capture/manager.ts`), which is what `AgentCommunicationManager` (`src/agent/communication-manager.ts`) calls for a `command`- or `request`-kind message — the divergence above. `ROUTE_NAMES` in `src/plugins/command-adapter.ts` restates `['schedule', 'harness', 'ssh', 'shell']` by hand to keep a plugin from claiming a name the registry would never reach. Add `src/commands/harness.ts` and `src/commands/ssh.ts` exporting a `Command` with `match` on the first token and a `run` holding the shared append/delegate/append body (factor that body into one helper both call, since it is identical), register both in `coreCommands`, and delete the two branches from `CommandManager.run`. Keep the bare-word special cases where they are for now — bare `harness` opens the launch dialog and bare `schedule` opens the schedule dialog — but move the `harness` one inside the new command's `run` so only `schedule` and `shell` remain ahead of the registry, and reduce `ROUTE_NAMES` to those two. Order matters in `coreCommands`: place the new entries so no shorter name that prefixes them is matched first, the way `acpReset` already precedes `acp` and `monitors` precedes `monitor`. `src/resolve.test.ts` asserts the classification of many commands and should gain `harness`/`ssh` cases; `src/command/manager.test.ts`, `src/harness/manager.test.ts`, `src/ssh.test.ts`, and `src/capture/manager.test.ts` cover the current dispatch and must keep passing — the capture-path behavior is expected to change from "unknown" to "runs", which is the point and wants a new test of its own.


* Have the built-in command classifier report what it decided as a value, instead of encoding "this command is unknown" in the text of the message it returns and re-detecting it by string prefix at three separate call sites.

Existing Debt: One classifier overloads a `string | null` return with three meanings — here is output, this is a known command with nothing to say, and this command is unrecognized — distinguishing the third only by the leading words of a user-facing message, which two callers then re-derive with their own prefix tests and one of which rebuilds a second, differently-worded copy of that same message. Severity: 5/10

Existing Risk: 4/10 - Rewording the unknown-command message — a plain copy edit, with no compiler or test signalling the dependency — makes every unrecognized command classify as a known one carrying output, so the probabilistic route recognition behind it stops running and the route chooser never opens.

Proposal Risk: 2/10 - The decision would be carried in a discriminated result rather than in prose, so the message text becomes editable again; the unreachable branches this exposes still have to be removed by hand rather than reported by the compiler.

Proposal: `getOutput` in `src/commands.ts` returns the help text for `help`, `null` for a dozen named commands, and the string ``Unknown command: "<x>". Type "help" for available commands.`` for everything else. `resolveCommand` in `src/resolve.ts` recovers the third case with `output.startsWith('Unknown command:')`, and `routeUnknownCommand` in `src/capture/router.ts` does the same at its opening guard and then constructs its own shorter `Unknown command: "<x>".` at its final callback — two spellings of one message already. Change `getOutput` to return a discriminated result (`{ kind: 'output'; text } | { kind: 'silent' } | { kind: 'unknown'; text }`, matching the shape `resolveCommand` already exposes) and have both callers branch on `kind`; keep one place that builds the message text so the two spellings collapse. While doing so, delete the branches that can no longer be reached: both callers loop the `commands` registry from `src/commands/index.ts` before ever calling `getOutput` — `src/resolve.ts` in `resolveCommand` and `src/capture/manager.ts` in `CaptureManager.run` — so every `return null` for a name that registry now owns (`clear`, `state`, `hist`, `quit`/`exit`/`close`, `agent`, `msg`, `broadcast`, `acp`, `db`, `connection`, `next`) is dead, leaving only `help`, the empty string, and the unknown fallback. `coreAvailableCommands` in the same file is a separate hand-maintained list that has drifted from that registry (it names `help`, `harness`, and `ssh`, which are not `Command` entries, and omits more than a dozen that are); its only live consumer is the help fallback in `buildHelp`, so rebuild it from `commands` in the same change rather than leaving a second stale list behind. `src/commands.test.ts` and `src/resolve.test.ts` pin the current return values and message text and will need updating to the new result shape; `src/capture/manager.test.ts` pins the routing behavior that must not move.


* Make the order managers are torn down in an explicit, stated list, rather than an accident of the order a different file happens to assign them in.

Existing Debt: Shutdown disposes managers by reversing `Object.keys` over the registry object, which makes JavaScript's property-insertion order the dependency graph — while the file doing the inserting documents that its order is only about construction-time references and implies it is free to change, so two files hold contradictory beliefs about whether that order is load-bearing. Severity: 5/10

Existing Risk: 4/10 - Reordering two lines in the construction file — which its own comment invites — silently reorders teardown, and a manager that sends its shutdown work over a transport another manager owns will find that transport already gone, with the send quietly discarded rather than failing.

Proposal Risk: 2/10 - Teardown order becomes a stated list that a reviewer can check against, though the list is still maintained by hand and a manager added without an entry has to be caught by the test that pins it rather than by the compiler.

Proposal: `Controller.shutdown` in `src/controller.ts` does `Object.keys(this.managers)` and `.toReversed()`, then calls `dispose?.()` on each — so teardown order is exactly the reverse of the assignment order in `createManagers` in `src/controller/create-managers.ts`, whose header comment says only that "later managers may reference earlier ones via `this.managers` at call time, not construction time, so the object need not be fully populated yet". That reverse order is already load-bearing: `managers.remote` is assigned after `managers.pty`, so `RemoteManager.dispose` (`src/remote/manager.ts`, which closes every channel) runs before `PseudoterminalManager.dispose` (`src/pseudoterminal-manager.ts`, whose `closeAll` calls `session.kill()` on each entry) — and a remote PTY's `kill` is `channel.send({ type: 'kill', id })` in `src/remote/pty-session.ts`, which `RemoteChannel.send` in `src/remote/channel.ts` drops silently once the channel is no longer attached. Declare the order explicitly: add a `MANAGER_DISPOSE_ORDER` constant typed `readonly (keyof Managers)[]` beside the registry in `src/managers.ts` — using the same `Record<keyof Managers, true>`-style compile-time completeness check `CLIENT_FRAME_TYPES` in `src/remote/protocol.ts` uses, so a manager added without a position fails the build — have `shutdown` iterate that instead of `Object.keys`, and record beside each dependent pair why it sits where it does (PTYs before the channels they send over; tab and database last). Add the same explicit note to `createManagers`'s header saying its assignment order no longer determines teardown. `src/controller.test.ts` covers construction and adapter coverage and `src/controller/create-managers.test.ts` covers the registry being fully populated; neither pins dispose order today, so this change should add a test asserting the declared order is used and that every registry key appears in it exactly once.


* Drive the two remaining union dispatchers off the exhaustiveness idiom the rest of the codebase already uses, so a value added to either union stops compiling instead of silently doing nothing.

Existing Debt: The project has an established, twice-documented way to make a union's dispatcher exhaustive — a `never`-typed default arm and a `Record<Union, true>` membership table — but the notification eligibility rules and the profile tab-kind validator both predate it and instead use `default` arms that return a falsy answer and a plain `string[]` of type names, so neither is tied to the union it is supposed to cover. Severity: 4/10

Existing Risk: 4/10 - A new notification event compiles, ships, and never reaches the feed because both of the eligibility switches fall through to a default that refuses it, and a new profile tab kind compiles and is then rejected on load with "type must be one of ..." for every profile that uses it — in both cases the build is green and the feature is simply inert.

Proposal Risk: 2/10 - Both dispatchers become compile-time complete, though the remaining hand-written membership lists elsewhere are untouched and the same gap can reappear wherever a new union is introduced without the idiom.

Proposal: The idiom is `unhandledClientMethod(message: never)` in `src/client-message.ts` and `unhandledRemoteFrame(type: never)` in `src/remote/frame-decode.ts`, paired with `CLIENT_FRAME_TYPES`/`SERVER_FRAME_TYPES` in `src/remote/protocol.ts` and `CAPABILITIES`/`NOTIFICATION_TOPICS` in `src/plugins/api.ts`, each with a comment explaining that keying by the union makes an omission a compile error. Two dispatchers do not use it. In `src/notifications.ts`, `NotificationEventType` has sixteen members and `shouldNotify` splits them across two switches — the first returns `true` for the eleven explicit events and ends `default: { break; }`, the second maps the five ambient events to config flags and ends `default: { return false; }` — so a seventeenth member falls through both to `false`; note that `notificationText` in the same file is already exhaustive (no default, and its `string` return type makes a missing case a compile error), which is what makes the inconsistency visible within one file. Replace the two `default` arms with a shared `never`-typed guard, splitting the union into an explicit-events table and an ambient-events table keyed `Record<Ambient, keyof NotificationConfig['events']>` so the second switch becomes a lookup. In `src/profile/schema.ts`, `TAB_TYPES` is a `string[]` listing eleven names that mirror the eleven arms of `ProfileTabFile` in `src/profile/types.ts`, and `PRESENTATION_TYPES` is a second hand-kept `Set` restating nine of them; derive both from the union with `Record<ProfileTabFile['type'], boolean>` tables — the boolean being whether that kind carries the flat presentation fields — and keep `tabProblems`'s message building its list from the table's keys so the wording does not move. `src/notifications.test.ts` covers `shouldNotify` per event but has no case asserting the union is fully covered, and has none at all for `plugin-failure`; add a case per member driven off the table. `src/profile/validate.test.ts` and `src/profile/file.test.ts` exercise `collectProfileProblems` and pin the current messages, so they must keep passing with no wording change.


* Give the tab manager a lookup for finding a tab by its label, so the modules around it stop hand-rolling the same linear scan over its public array and reaching straight into the record it returns.

Existing Debt: The tab manager exposes its tab array as a public, mutable field and offers only an index lookup, so fifty-two call sites across thirty-one modules repeat the same scan for a label and then read or write the returned record's view payload directly — the shape the architecture principles say nothing outside the owner should reach for. Severity: 4/10

Existing Risk: 3/10 - The scan and the payload check are re-derived at each site, so one site's `if (tab?.harness)` guard omitted or written against the wrong payload field mutates or reads a tab the discriminant says has no such view, and only that one code path is affected.

Proposal Risk: 3/10 - Lookups would run through one method that can gain a map or a guard behind it, but the array itself stays public and directly mutable, so a caller can still bypass the accessor and edit a record in place.

Proposal: `TabManager` in `src/tab/manager.ts` declares `tabs: Tab[]` as a public field and provides `findIndex(label)` (an index) and `cur()`, but no by-label lookup, so callers write `this.managers.tab.tabs.find((t) => t.label === label)` — fifty-two occurrences across thirty-one non-test modules, including `src/harness/manager.ts` (five, in `latestScreenText`, `transcriptTailer`, `browserGone`, `markRunning`, and `failSpawn`, four of which follow the scan with a `tab?.harness` check and an in-place mutation), `src/editor/save.ts`, `src/notifications.ts`, `src/capture/manager.ts`, `src/plugins/host.ts`, `src/schedule/manager.ts`, and `src/monitor/manager.ts`. Add `byLabel(label: string): Tab | undefined` to `TabManager` alongside `findIndex`, plus guard-typed accessors built on the predicates already in `src/tab/view-guards.ts` — `harnessTab(label): HarnessTab | undefined`, `editorTab(label)`, `filesTab(label)`, `pluginTab(label)`, `monitorTab(label)` — each returning the narrowed type so a caller gets a non-optional payload or nothing, rather than a `Tab` plus its own optional-chained check. `src/tab/manager.ts` is near the size limit, so put the accessors in a new `src/tab/lookup.ts` and have the manager delegate, matching how `runtime-operations.ts` and `transcript-operations.ts` are already reached. Then migrate the scan-then-check-payload sites first, since those are the ones the guards actually improve — `src/harness/manager.ts`, `src/editor/save.ts` (`finishSave`), `src/editor/resync.ts`, `src/editor/sync.ts`, and `src/monitor/window.ts` — and leave the plain scan-for-a-tab sites for a follow-up rather than sweeping all fifty-two in one change. Behavior must not move: `byLabel` returns the first match exactly as `find` does. `src/tab/manager.test.ts`, `src/harness/manager.test.ts`, `src/editor/save.test.ts`, and `src/editor/resync.test.ts` cover the migrated paths and must keep passing unchanged; several of them reach a tab's payload with a non-null assertion, which is test-side and can stay.
