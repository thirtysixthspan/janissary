## development

* Break `web/src/ws.ts`'s dependency on `web/src/file-navigator-selection-registry.ts`: the protocol client — the app's lowest-level service, and one of the most-churned files in `web/src/` — imports `collectNavigatorSelections()` at line 2 and calls it while answering the `collect-tree-state` request, so a service reaches upward into a feature's client-only React state, violating §8 (each layer imports downward only) and §3 (features and the shared layer must not depend on each other in this direction). The cost is that `ws.ts` cannot be instantiated, tested, or reasoned about without the file navigator's module-level `Map` existing and being populated — `ws.test.ts` already has to import `publishNavigatorSelection`/`clearNavigatorSelection` just to exercise the client — and every future "the server asks the client for some feature's state" RPC will copy this shortcut. Invert the direction: give `JanusClient` a registration seam (`registerStateCollector(name, fn)` or a constructor-supplied collector map) that the file-navigator hook populates, and delete the import from `ws.ts`. Seventy-six files import `ws.ts`, but only its construction site at the app boundary and `ws.test.ts` change. Severity: **high**.

* Move the plugin capability contract off the host component it constructs: `web/src/plugins/api.ts` — the module that defines `TabPluginClientCapabilities` and builds every plugin's capability object — imports React and `SplitTabButton` from `../SplitTabButton`, and line 68 does `React.createElement(SplitTabButton, { onClick: onSplit })` to fill the `splitAction` field. That violates §7 (services are framework-free; they never import React or component modules) and §8 (a service importing a component inverts the layer order), and the cost is concrete: the contract that twenty-two plugin files depend on cannot be unit-tested or reused without React and one specific host button, and every future host-rendered control added to the contract will be welded in the same way. Have the caller supply the node — pass `splitAction` into `createPluginClientCapabilities` as an already-built `React.ReactNode` from the component layer (`PluginBody.tsx`/`PluginTabLayer.tsx`, which already sit above it), leaving `api.ts` with no React import. The exported type is unchanged, so the plugin bodies are untouched; only `api.ts` and its two callers change. Severity: **high**.

* Fix the editor feature's boundary with the agent-tab feature: `web/src/editor/EditorMetaRow.tsx` and `web/src/editor/useEditorConnections.ts` both import `type { StatusWindowButtonProps }` from `../AgentTabMeta` — a type declared inside the agent tab's meta-row component — which is a feature importing another feature and violates §3 (no feature imports another feature); the same boundary is broken in the other direction by `web/src/EditorSaveButton.tsx`, an editor-only control that lives in the flat root with exactly one non-test consumer, `editor/EditorMetaRow.tsx`, against §2 (colocate; promote only on a second consumer). The cost is that the editor cannot be moved, tested, or deleted without the agent tab coming along, and the coupling is invisible because it is type-only, so the next editor file will copy it. Lift `StatusWindowButtonProps` out of `AgentTabMeta.tsx` into a shared module beside `useStatusWindows.ts` (which already owns the matching `StatusWindowHandlers` type) and point `AgentTabMeta.tsx`, `HarnessTab.tsx`, and the two editor files at it; move `EditorSaveButton.tsx` and its test into `web/src/editor/`. Five files import the type and one imports the button, so the change is contained. Severity: **medium**.

* Gather the file-navigator feature into `web/src/file-navigator/`: forty-eight files sharing the `FileNavigator*` / `file-navigator-*` / `useFileNavigator*` naming prefix sit loose in the flat `web/src/` root alongside every other feature's files — the prefix is the feature directory the tree does not have — which is exactly the scatter §1 (organize by feature, not by file type) exists to prevent. The cost is that nothing marks where the feature starts or ends: "does anything outside the navigator use this?" is unanswerable without a grep, `web/src/` root is unscannable at two-hundred-plus files, and each new navigator file makes the next reorganization more expensive. Create `web/src/file-navigator/` and move all forty-eight (components, hooks, pure modules, and colocated tests) into it, updating relative import paths. Only three files outside the set import into it — `Sidebar.tsx` and `ViewTabBody.tsx` import `FileNavigatorTab`, and `ws.ts` imports the selection registry — so the external blast radius is small even though the move itself is wide. Severity: **medium**.

* Stop passing the protocol client into the transcript's presentational renderers in `web/src/transcript-line.tsx`: `OpenFileLink`, `renderMessageTab`, `renderMarkdownLine`, and `renderTextContent` all take a `client: JanusClient` prop and issue protocol calls straight from JSX handlers — a `client.send` of an `edit <path>` command at line 101, a `FILE_LINE_LINK`-driven choice between `edit` and `open` at line 115, and `{ method: 'focusTab' }` at line 159 — which violates §5 (a presentational component takes the data it renders and the callbacks it invokes, never a service instance) and §8 (a component reaching past its hook into a service). The cost is that the command-string rules are untestable without a fake client and unreachable from anywhere else, and every new transcript line type adds another inline protocol call. Replace the `client` parameter on `renderLine` with an intent object (`{ onOpenFile, onEditFile, onFocusTab }`) built once in `Transcript.tsx` from a hook, and move the `edit`/`open` decision into a pure module beside it. Two files reference `renderLine` — `Transcript.tsx` and its test — but `TerminalCard` still needs the client, so plan that hand-off as part of the change. Severity: **medium**.

* Pull the command-history recall state machine and caret-insertion logic out of `web/src/CommandInput.tsx` into modules beside it: at 241 lines the component is over the file-size limit and owns rules that have nothing to do with markup — the `histIndex`/`draftBeforeHistory` recall walk (`recallOlder`/`recallNewer`, lines 102-114), the first-line/last-line caret tests that decide whether ArrowUp/ArrowDown recall or move the caret (lines 134-148), and the `execCommand`-with-fallback text splice duplicated between `insertAtCaret` and `insertNewline` (lines 67-81 and 121-130) — which violates §5 (components render, they do not decide; a rule you would want to unit test is in the wrong place). The cost is that none of these can be tested without rendering a textarea and driving key events, and the file has no room left for the next command-bar feature. Extract the recall walk into a `useCommandHistoryRecall` hook, the caret-line predicates into a pure module, and the splice into a shared helper, all in the same directory; the component's props and both exported types are unchanged, so none of its eight importers are affected. Resolve by running the `ai/tasks/hygiene/improve-modularity.md` task against `web/src/CommandInput.tsx`. Severity: **medium**.
