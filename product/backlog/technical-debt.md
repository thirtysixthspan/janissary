# technical-debt

## ready

* Retarget open editor tabs after every file-navigator operation that moves a path on disk, not only a single-file local rename, so a later save can no longer recreate a file at its old location.

Existing Debt: The navigator has no single "these paths moved" step after a mutation, so each operation picks its own side effects, and only a single-item local rename retargets an open editor, by exact path match, while drag moves, bulk moves, cut-and-paste, undo and redo, directory renames and remote renames leave editors pointing at a path that no longer exists. Severity: 6/10

Existing Risk: 6/10 - A user who drags an open file, or the folder holding it, to another directory and then saves is still writing to the old path: the editor watch ignores a vanished file and the stale-save check writes through to a missing path, so the old file is silently recreated and the moved copy never receives the edits.

Proposal Risk: 2/10 - Editors follow every move the navigator itself reports, but a move made outside the app (a shell `mv`, a branch checkout) still strands an editor on a dead path, because the watch treats a missing file as nothing to report.

Proposal: `retargetEditorTab` in `src/tab/retarget-editor.ts`, reached through `TabManager.retargetEditorTab` in `src/tab/manager.ts`, has exactly one caller: `renameOne` in `src/file-navigator/manager/item-operations.ts`, guarded by `!state.remote`. It matches `candidate.editor?.path === oldAbsPath`, so renaming a directory that contains an open file retargets nothing. `moveOne` in the same file, `moveMany` and `pasteMany` in `src/file-navigator/manager/batch.ts`, and `replayHistory` in `src/file-navigator/manager/history.ts` never retarget, and the bulk wrappers `moveItems`, `pasteItems` and `replayMutation` in `src/file-navigator/manager/mutations.ts` also skip the `liveTranscriptRefusal` guard that `moveItem` and `renameItem` apply. The gap turns into a silent fork because of two lenient fallbacks downstream: `EditorWatchManager.check` in `src/editor/watch-manager.ts` returns quietly when `statSync` fails, and `refuseStaleSave` in `src/editor/stale-save.ts` treats a missing file as "nothing left to lose". Add one `pathsMoved(managers, state, pairs)` helper beside `item-operations.ts` that takes the `{ from, to }` pairs each operation already produces (`MoveEntry` in `src/file-navigator/moves.ts`, `PastePair` in `src/file-navigator/paste.ts`) and, for local trees, retargets every editor tab whose path equals `from` or sits under it, using `containedAbsolute` from `src/path-containment.ts` and rebasing the remainder onto `to`; widen `retargetEditorTab` to a prefix match rather than adding a second retarget function. Call the helper from `renameOne`, `moveOne`, `moveMany`, `pasteMany` in cut mode and `replayHistory`, and run `liveTranscriptRefusal` per source as a preflight in the three bulk wrappers. Leave remote trees for a follow-up step: they need `retargetRemoteFile` (used by `src/editor/rename.ts`) applied by prefix. `src/file-navigator/manager.test.ts` pins the single-file rename retarget and the live-transcript refusals for `move` and `rename`; add cases for a moved file, a renamed directory with an open file inside, a cut-paste, and an undo of a move, plus the bulk live-transcript refusal. Nothing covers save-after-move end to end, so add a test that saves an editor after its file moved and asserts the old path was not recreated.

* Address the file navigator's commit and pull requests by tab label instead of tab index, the rule its own mutating requests already follow, so a tab closing mid-request cannot redirect them to another navigator.

Existing Debt: The navigator's RPC boundary follows two addressing rules at once: moves, deletes, renames and pastes arrive by label and are checked against the open tabs, while commit, nothing-to-commit, pull, reroot, open, reveal, search, toggle and the selection actions still resolve a tab index when the request is handled. Severity: 5/10

Existing Risk: 5/10 - If any tab ahead of a navigator closes while a commit or pull is in flight (a harness tab auto-closes when its process exits), every later index shifts, so the request can land on a different navigator and commit and push that tree's repository, the whole tree when the path list is empty.

Proposal Risk: 2/10 - Commit and pull reach the navigator that sent them or nothing, though the other index-addressed navigator requests keep the same hazard until they move too, and a navigator closed and reopened under the same label within the request's flight would still receive it.

Proposal: The rule is already written in `src/controller/file/navigator.ts` ("The mutating requests below arrive addressed by label rather than tab index, so a tab closing ahead of the navigator cannot redirect them"), and `isOpenTab` there implements it. Yet `fileNavigatorPull`, `fileNavigatorReroot`, `fileNavigatorSetDetail`, `fileNavigatorToggle`, `fileNavigatorCollapseAll`, `fileNavigatorSearch`, `revealFileNavigatorItem`, `fileNavigatorOpeners` and `fileNavigatorOpen` in that file, `fileNavigatorCommit` and `fileNavigatorNothingToCommit` in `src/controller/file/navigator-commit.ts`, and `matchSelectionAction` in `src/controller/file/navigator-selection.ts` all take `index` and resolve `managers.tab.tabs[index]?.label`. In this sitting move the three requests that run git against the tree's repository, commit, nothing-to-commit and pull: change their params in `src/protocol/file-navigator.ts` from `{ index }` to `{ label }`, update their validators in `src/client-params/file-navigator.ts`, the dispatch arms in `src/message/file-navigator.ts` and the signatures in `src/controller/file/navigator-adapter.ts`, and have the wrappers return early on `!isOpenTab(managers, label)`. On the client, `web/src/file-navigator/useFileNavigatorIntents.ts` sends `{ index }` for both; the navigator tab already receives its `label` as a prop, so pass that through instead. Reroot and the selection actions are the next most consequential and can follow in the same shape. `src/client-params/file-navigator.test.ts`, `src/controller/file/navigator.test.ts`, `src/controller/file/navigator-adapter.test.ts` and `web/src/file-navigator/useFileNavigatorIntents.test.ts` pin the current params and need updating rather than deleting; add a server test that closes a tab ahead of a navigator between the send and the handling of a commit and asserts no other navigator was committed.

* Back off and coalesce system-schedule retries while the system shell cannot start, so one failing schedule stops raising a desktop notification and a fresh shell launch every second.

Existing Debt: The spec's "leave the entry due for retry" is implemented as "retry on the next one-second scheduler tick", with no backoff, no coalescing of ticks that arrive while a run is still pending, and no memory that the shell already failed, so both the retry rate and the notice rate are the scheduler's clock rate. Severity: 5/10

Existing Risk: 6/10 - If the shell plugin is disabled for the process, or the shell keeps failing to start because of a broken startup file or a sandbox refusal, every due system schedule retries the launch and posts "System shell could not start" about once a second, and that event defaults to a desktop banner with a warning sound, until the user restarts the app or cancels the schedule.

Proposal Risk: 2/10 - A persistent failure becomes one notice per episode with a capped retry interval, though a shell that fails only intermittently will now fire its schedule up to a minute late instead of on the next second.

Proposal: `ScheduleManager` in `src/schedule/manager.ts` runs `tick` from a one-second `setInterval` and calls `this.managers.systemSchedule?.tick(now)` without awaiting it. `SystemScheduleManager.tick` in `src/schedule/system/manager.ts` appends `runAfter(this.inFlight, now)` on every call, so a slow failing run queues one more `fireDue` per second behind it, each carrying its own stale `now`. `fireSystemBatch` in `src/schedule/system/firing.ts` returns `undefined` when `managers.systemShell.ensure()` is not `ok`, which leaves the entry due. `SystemShellManager.ensure` in `src/system-shell.ts` coalesces concurrent calls but clears `ensurePromise` the moment an attempt settles, and its `fail` calls `notifySystemShellStartFailure` in `src/schedule/system/notices.ts` on every attempt; that posts a `system-schedule-fire` event whose default in `src/notifications/alert-defaults.ts` is `{ desktop: true, sound: 'warning' }`. Make three changes. First, in `SystemScheduleManager.tick`, when a run is already pending, record only the latest `now` and return the in-flight promise, so at most one follow-up run is queued. Second, keep an in-memory per-key `retryAt` that doubles from one second to a sixty-second cap after each failed `ensure` or unreadable runscript and resets on success, and have `fireDue` skip a key whose `retryAt` lies in the future. Third, give `SystemShellManager` a reported-failure flag that suppresses repeat notices until an `ensure` succeeds. The tab-schedule path in `ScheduleManager.fire` already retries silently, which is the precedent for not re-notifying. Update the retry sentence in `product/specs/scheduling.md` to describe the backoff and the single notice. `src/schedule/system/manager.test.ts` covers one failed tick followed by success, each tick awaited; add a sustained-failure case asserting one notice across many ticks, an overlapping-tick case asserting one queued run, and a backoff case. `src/notifications/system-schedule.integration.test.ts` pins the notice text and must keep passing.


* Run the file navigator's and editor's own git actions, pull and commit-and-push, through one shared runner with a deadline, cancellation and terminal prompts disabled, the way git-sync already runs its git.

Existing Debt: The git modules have no shared way to run git, since each promisifies `execFile` itself, and the user-armed pull and commit run `git pull`, `git pull --rebase`, `git stash` and `git push` with no timeout, no abort signal and terminal prompts allowed, while the git-sync runner gives its commands a sixty-second deadline and cancellation and the clone path sets `GIT_TERMINAL_PROMPT=0`. Existing Risk: 5/10 - A push or pull that blocks on a credential or host-key prompt, or on a stalled network, never settles, so the tab stays in its pulling or committing state and refuses every later pull and commit until the server restarts, and a hang inside the rebase step leaves the user's uncommitted changes in a stash they did not make.

Proposal Risk: 2/10 - A hung git is killed and reported through the existing rollback paths, though a push of a large history over a slow link could now be cut off at the deadline and reported as failed when it would eventually have finished.

Proposal: A local navigator pull runs `runPull` in `src/file-navigator/manager/pull.ts`, which arms the pulling flash and calls `state.filesystem.pull`, which for a local tree is `pullRoot` in `src/git/pull.ts` by way of `src/file-navigator/filesystem-port.ts`; a commit runs `src/file-navigator/manager/commit.ts` into `commitRoot` in `src/git/commit.ts`, which the editor's commit in `src/editor/commit.ts` also calls. The remote side already guards this exact failure: `src/file-navigator/remote/port-requests.ts` gives `git-pull` and `git-commit` the ten-minute `LONG_REQUEST_DEADLINE_MS` because otherwise "a pull would stay `pulling` and block every later pull and commit", but on the far host the same `pullRoot` and `commitRoot` keep running after that deadline fires. By contrast `SyncCommandRunner` in `src/git/sync-command.ts` passes `timeout`, `signal` and `killSignal`, and `src/git/clone.ts` sets `GIT_TERMINAL_PROMPT: '0'`. Add a small `runGit(args, cwd, options)` module in `src/git/` that wraps `execFile` with a default deadline matching `LONG_REQUEST_DEADLINE_MS`, `killSignal: 'SIGTERM'`, an optional `AbortSignal`, and an environment of `{ ...process.env, GIT_TERMINAL_PROMPT: '0' }`, so credential helpers keep working exactly as the comment in `commit.ts` requires but git never opens the terminal. Route every call in `pull.ts` and `commit.ts` through it; a timeout rejects like any other git failure, so `pullRebase`'s `rebase --abort` and `rebaseAsideExtraChanges`'s stash pop run unchanged. `SyncCommandRunner` can call the same helper later, but that is not needed for this step. `src/git/pull.test.ts` and `src/git/commit.test.ts` mock `node:child_process` and pin argument order and every rollback path; they keep passing and should each gain an assertion that the options carry the deadline and `GIT_TERMINAL_PROMPT`. Nothing tests a hung git, so add a `runGit` test whose fake `execFile` never calls back, with a short deadline.
