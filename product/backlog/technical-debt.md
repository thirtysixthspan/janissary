## development

* Parse the command-line cursor once into a named record and hand it to every tab-completion handler, instead of threading the same six to eight positional values through each handler and `completeWord`.

Existing Debt: Command-line completion computes the command word, argument index, preceding words, token, text before and after the cursor, and token start once, then passes them positionally to nine handlers and on into `completeWord`, whose seven parameters include three adjacent strings (`before`, `after`, and the kept prefix) and a candidate list, so every new completion restates the same long signature and the parameter meaning is carried by position alone. Severity: 3/10

Existing Risk: 3/10 - Two same-typed arguments transposed in a new or edited handler — `before` and `after`, or the candidate list and the kept prefix — typecheck and ship as a completion that rewrites the wrong half of the line or offers the wrong list, and the misleading `agents` name for what is actually every open tab label invites exactly that kind of slip.

Proposal Risk: 1/10 - Fields are matched by name and a rename is a compile error, and the colocated completion tests pin every handler's output, so the remaining exposure is only in candidate lists the tests do not enumerate.

Proposal: `completeCommandLine` in `src/completion/index.ts` derives `before`, `after`, `tokenStart`, `token`, `preceding`, `command`, and `argumentIndex`, then chains `completeAgentName`, `completeSendTarget`, `completeScheduleTarget`, `completeConnectionClose` (`src/completion/target-handlers.ts`), `completeBrowserCommand` (`src/completion/browser.ts`), `completeMonitorCommand`, `completeSearchCommand`, `completeSyntaxTheme`, and `completeHarnessModel` (`src/completion/handlers.ts`), each taking some subset of those positionally, and every one ends in `completeWord(partial, keepPrefix, candidates, suffix, before, after, tokenStart)` from `src/completion/helpers.ts`. Add a `CompletionCursor` type to `src/completion/types.ts` holding those seven fields, build it once in `completeCommandLine`, and change each handler to `(cursor, candidates)` — the extra list being the one data source it needs (labels, connections, the monitor catalog, themes). Change `completeWord` to `completeWord(cursor, candidates, { keepPrefix?, suffix?, partial? })` so the `broadcast` comma-segment case in `completeAgentName` still overrides the partial, and have `replaceToken` take the cursor too. Rename the `agents` parameter of `completeCommandLine` to `labels`, since `complete` in `src/controller/completion.ts` passes `managers.tab.allLabels()`. `completeFilePath` in `src/completion/fs.ts` can take the cursor in the same change or stay as-is if its extra `input`/`cursor` parameters make that awkward. Delete the handler re-exports at the top of `src/completion/handlers.ts` and import each handler from its defining file in `index.ts`. The completion suites under `src/completion/` (and any caller test of `completeCommandLine`) pin outputs and must pass unchanged; only direct handler-call tests need their arguments rewritten.


* Give in-place transcript rewrites their own bus event and persist on it, instead of overloading the append event, so a silently finished command is saved and the daily log and monitors stop receiving re-emitted entries as new ones.

Existing Debt: The transcript bus has one "entry appended" event, and it is reused for two things that are not appends — finalizing a running entry (emitted with a synthetic `{ input: '', output }` entry that is not in the log, and only when the output is non-empty) and marking an inline terminal card exited (re-emitting an entry already in the log) — so the file store, the daily transcript logger, and monitor subscriptions each receive updates dressed as appends, and the store's comment still claims in-place edits are saved by direct `save()` calls that no longer exist anywhere. Severity: 5/10

Existing Risk: 5/10 - A shell or ACP entry that finishes with empty output (`cd`, `mkdir`, a silent script) is never written back, so the transcript file keeps it as `running: true` and a `--relaunch` restores a tab whose last entry looks like it is still running, while every inline terminal that exits feeds its command line a second time into the daily log and into any monitor watching that tab.

Proposal Risk: 2/10 - Persistence and the two feeds are keyed to events that mean what they say, but the synthetic trailing append that hands a finished command's output to the logger and monitors stays as it is, so its "append that is really a completion" shape remains for a later increment.

Proposal: `TranscriptEvent` in `src/bus.ts` has `entry:appended`, `entries:trimmed`, and `tab:cleared`. `updateRunningEntry` in `src/tab/transcript-events.ts` rewrites the running entry in place and, only when `hooks.trailing && output`, emits `entry:appended` with a synthetic entry; the exit handler in `src/pseudoterminal-manager.ts` rewrites a terminal card's status and re-emits `entry:appended` with that existing entry. `TranscriptStore` in `src/transcript/store.ts` saves only on `entry:appended` and `tab:cleared`; `TranscriptLogger` in `src/transcript/logger.ts` and `subscribeMonitor` in `src/monitor/subscriptions.ts` treat every `entry:appended` as a new line. Add `{ type: 'entry:updated'; tabLabel: string; tab: Readonly<Tab> }` to `TranscriptEvent`; emit it from `updateRunningEntry` whenever it rewrites an entry with `running` false (regardless of output), and from the PTY exit handler in place of its `entry:appended`; subscribe `TranscriptStore` to it so it calls `save(tabLabel, tab.log)`; leave the logger and monitor subscriptions on `entry:appended` only. Keep the existing trailing `entry:appended` emit in `updateRunningEntry` unchanged, since that is how a finished command's output reaches the daily log and monitors. Correct the class comment in `src/transcript/store.ts` to describe the two events it persists on. Tests: add a case to `src/tab/transcript-events.test.ts` asserting an `entry:updated` emit for an empty-output finalize, a `src/transcript/store.test.ts` case that the store saves on it, and a `src/pseudoterminal-manager.test.ts` case that an exit no longer emits `entry:appended`; check `src/monitor/*.test.ts` and `src/transcript/logger.test.ts` for any expectation of the exit re-emit before removing it. Clearing stale `running` flags on rehydrate in `src/tab/rehydrate.ts` is a separate decision and out of scope here.


* Replace the notification entry point's trailing positional options with one named options record, so the feed's open-file link, open-tab link, and detection time can no longer be passed in the wrong slot.

Existing Debt: `notify` has grown a new trailing positional parameter each time a notification gained a capability — `message`, then `openFile`, then `openTab`, then `detectedAt` — so a caller that needs only the last one spells out every `undefined` before it, and the two link targets are adjacent optional strings distinguished by position alone. Severity: 2/10

Existing Risk: 3/10 - A caller that transposes `openFile` and `openTab` typechecks and ships a notification whose click opens a file named after a tab (or focuses a tab named after a path), and the next capability added the same way pushes the 50-plus call sites one more `undefined` further from readable.

Proposal Risk: 1/10 - Options are matched by name so a transposition or rename is a compile error, and the only behavior to keep is that a supplied `detectedAt` still suppresses the toast, which `src/remote/pty-session.test.ts` and `src/notifications/index.test.ts` already pin.

Proposal: `notify(managers, event, tabLabel, message?, openFile?, openTab?, detectedAt?)` lives in `src/notifications/index.ts`. Keep the first four parameters (the common shape at nearly every call site) and fold the rest into a fifth `options?: { openFile?: string; openTab?: string; detectedAt?: Date }`, then update the few callers that pass them: `src/controller/create-managers.ts` (the `question` notification passes `undefined, undefined, label` for `openTab`), `src/remote/pty-session.ts` (`openFile` plus a `detectedAt` for a replayed auto-approve), `src/harness/auto-approve-wire.ts` and `src/harness/browser-gone.ts` (`openFile`). Grep `notify(` across `src/` for any other caller with more than four arguments, and update the matching expectations in the tests that spy on `notify` (`src/remote/pty-session.test.ts`, `src/editor/commit.test.ts`, `src/editor/rename.test.ts`, `src/tab/rename-editor.test.ts`, `src/plugins/conversations/activate.test.ts`, `src/notifications/index.test.ts`) only where they assert the trailing arguments. No behavior changes.

## deferred

* Give every wall-clock wait in the suite a budget that is a stated multiple of the interval it actually polls, instead of leaving nine fixed sleeps and forty-six raised timeouts to absorb a loaded machine. — deferred: complexity 8/10, requires an empirical multi-run flake baseline on an idle machine and then spans the vitest config, about ten test files with forty-nine timeout overrides, and the CI workflow.

Existing Debt: Nothing states a per-test time budget, so `vitest.config.ts` sets `hookTimeout: 30_000` on the `server` project and leaves `testTimeout` alone on both `server` and `client` — meaning the real ceiling is vitest's 5s default, unstated and free to move with a vitest upgrade. Against that, forty-six tests across nine files pass an explicit `15_000` timeout and three more pass `30_000`, so the budget is currently expressed as forty-nine local overrides that each say "this test is slow" without saying why. Underneath sit nine genuine fixed sleeps (`setTimeout(resolve, N)` for 250/60/50/30/20/10 ms) and forty-four files polling with `waitFor`, and no `pool`, `fileParallelism`, `maxConcurrency`, `isolate`, or `sequence` setting anywhere in the config, so file-level parallelism is whatever vitest's defaults happen to be on a given machine. The sharpest instance is `src/browser/e2e-ready.test.ts:35`, whose `PATIENCE = 60` is spent both as a sleep and as the `boundMs` for `waitForListening` — while the production probe it waits on runs every `PROBE_INTERVAL = 25` (`src/browser/e2e-ready.ts:16`), leaving the timeout assertion at `:82` roughly two probe attempts to fail on. Severity: 4/10

Existing Risk: 4/10 - A suite that goes red for reasons unrelated to the change under test trains everyone to re-run before believing it, and the re-run that comes back green is read as "fine" rather than as "the signal is broken". That is how a real regression in `src/index.test.ts`, `src/request-boundary.test.ts`, or `src/open/route.test.ts` gets waved through, and `.github/workflows/ci.yml:47` runs `npm run test` exactly once, so nothing upstream catches a rerun-then-green either. The cost is not the flake itself but that it makes every other failure in the suite negotiable.

Proposal Risk: 1/10 - These are test-internal timing and budget changes with no production code involved, and each fix is locally verifiable by re-running the one file. The real hazard is the tempting wrong move rather than the change itself: raising `testTimeout` or `PATIENCE` until the suite goes quiet would convert a visible flake into an invisible slow suite and hide the next genuine hang, so the budgets must be derived from the interval being waited on rather than picked to pass.

Proposal: Start by establishing a real baseline, because the evidence so far is not good enough to act on. Six consecutive `npm test` runs on a machine already saturated by earlier runs produced a rotating failure set — `src/index.test.ts` (16 cases), `src/open/route.test.ts` (9), `src/browser/e2e-guard.test.ts` (8), `src/request-boundary.test.ts` (5), `web/src/App.test.tsx` (2), `web/src/plugins/SessionsDockedHeader.test.tsx` (2), `src/browser/e2e-ready.test.ts` (2), plus `src/workspace/index.test.ts`, `src/remote/serve-root.test.ts`, `src/remote/serve.test.ts`, `src/harness/index.test.ts`, `web/src/plugins/registry.test.tsx`, and `web/src/plugins/PluginTabLayer.test.tsx` — while every one of those files passed when run in isolation, and the failure *messages* were never captured. So: on an idle machine, run the suite five times, record which tests fail and at what rate, and keep the assertion text for each. Treat the two failure shapes as separate problems, because they have different causes: the ones that take a whole file with them (`src/index.test.ts`, `src/request-boundary.test.ts`, `src/open/route.test.ts`, `src/browser/e2e-guard.test.ts`) point at a shared real resource — a bound port, a real child process, a fixed path under the OS temp root — contended between parallel files, whereas the ones that take a single test point at a wall-clock assertion inside it. Then, in this order: (1) Fix the provable class first, the budgets smaller than the interval they poll. In `src/browser/e2e-ready.test.ts`, express `PATIENCE` as a multiple of the `PROBE_INTERVAL` it is racing rather than a bare `60`, and check `src/browser/e2e-guard.test.ts` and the nine real sleeps for the same shape; where a test genuinely needs to wait on a poll, export the interval and derive from it so the two cannot drift apart again. (2) Give the whole-file failures a resource that is theirs alone — bind port `0` per file as `e2e-ready.test.ts:26` already does, and give each file that touches the filesystem its own temp root rather than a shared one — and where a resource genuinely cannot be duplicated, serialize those files instead of hoping. (3) State the budget once: set `testTimeout` explicitly on both the `server` and `client` projects in `vitest.config.ts` so the ceiling is a decision recorded in the config rather than a default, and consider pinning `poolOptions`/`maxConcurrency` for the same reason. (4) Reclaim the forty-nine timeout arguments rather than leaving them as the record of which tests are slow — `web/src/App.test.tsx` alone carries eleven `15_000` overrides and does a dynamic `await import('./App')` inside each test, which hoisting to a module-scope import or a `beforeAll` should make unnecessary. (5) Close the loop in CI by repeating the affected files (vitest's `--repeat`, or a second run of the project) so a flake is caught by the pipeline instead of by a human noticing a red build. Note for whoever picks this up: none of this has been observed on `ubuntu-latest`, only on a loaded macOS box, so the CI repeat in step (5) is also the check that says whether the problem reaches CI at all.

* Move the command bar's server-completion request out of the agent tab body into the command-input feature where the rest of the completion rules live. — deferred: blocked by `ai/tasks/hygiene/improve-modularity.md`, whose Step 6 quality gate requires the target file's FTA score to drop, but extracting the completion request raises `AgentTabBody.tsx` from 52.67 to 53.03 (the new import outweighs the lines removed), so the playbook restores the file.

Severity: 4/10

Existing Risk: 4/10 - The unwrap semantics (an `ok: false` result silently completes with nothing) exist nowhere but inside a rendered callback, so a change to the completion contract — caching, aborting a stale request — starts life as JSX in the app's most-churned component, and a regression is a broken typeahead in every agent tab.

Proposal: `web/src/agent-tabs/AgentTabBody.tsx` inlines the server completion call. Scope the edit to `web/src/agent-tabs/AgentTabBody.tsx` plus the new module: `web/src/agent-tabs/command-input/CommandInput.tsx` keeps its `complete` prop contract, so no other import changes. `web/src/agent-tabs/command-input/CommandInput.test.tsx` stubs `complete` directly and needs no edit. Resolve by running the `ai/tasks/hygiene/improve-modularity.md` task against `web/src/agent-tabs/AgentTabBody.tsx`.

Severity: **high**. declined: this application is currently limited to running on mac os x.
