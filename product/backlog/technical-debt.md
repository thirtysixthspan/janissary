* Give the web client one "the keyboard is captured" check that every window-level shortcut consults, so Cmd+W and Shift+Tab stop acting on the tab underneath an open plugin overlay.

Existing Debt: Built-in pickers, plugin-contributed overlays and dialogs each announce that they own the keyboard through a different channel (the core overlay registry, the contributed-overlay seam, and the modal counter), and each window-level key listener checks a different subset of the three. Severity: 5/10

Existing Risk: 6/10 - With the clipboard-history overlay open, Cmd+W passes every check the close-tab listener makes and closes the active tab, which for a harness tab means its running agent is gone with no prompt, and Shift+Tab moves focus out from under the same popup.

Proposal Risk: 2/10 - Every shortcut asks the same question, though an overlay kind added later that announces itself through none of the three channels would slip past all of them at once.

Proposal: `useCmdW` in `web/src/useCmdW.ts` listens in the capture phase and returns early only on `e.defaultPrevented || isModalOpen()` or `pickerOpenRef.current || quitConfirmOpenRef.current`. `pickerOpenRef` comes from `useCmdWRefs` in `web/src/useCmdWRefs.ts`, which computes `firstOpenOverlay(overlays) !== undefined`, and `firstOpenOverlay` in `web/src/pickers/overlay-registry.ts` is documented as "deliberately still core-only"; the `useCmdWRefs` comment claiming it asks "the same question the render chain and the keyboard priority chain ask" is therefore no longer true. Contributed overlays, such as the clipboard history under `web/src/overlay-plugins/clipboard-history/`, are seen only by the `default` arm of `dispatchModalKey` in `web/src/useWindowKeys.ts` through `contributedOverlayOnScreen()` from `web/src/shared/contributed-overlays.ts`, and that listener is registered in the bubble phase, after `useCmdW` has already acted. `openModal` in `web/src/shared/modal-open.ts` is called only from `useDialogKeyboard`, and `useSectionNav` in `web/src/useSectionNav.ts` checks only `isModalOpen()`. Add a pure `keyboardCaptured(overlays)` beside `firstOpenOverlay` in `overlay-registry.ts` that is true when `isModalOpen()`, `firstOpenOverlay(overlays)` or `contributedOverlayOnScreen()` says so; have `useCmdWRefs` expose it as the ref `useCmdW` reads, hand the same ref to `useSectionNav` so its Shift+Tab handler consults it, and correct the `useCmdWRefs` comment. `firstOpenOverlay` keeps its meaning, so `web/src/pickers/overlay-registry.test.ts` and the two switch chains are untouched. `web/src/useCmdW.test.tsx` covers the built-in pickers, the quit dialog and `useDialogKeyboard`, and `web/src/useSectionNav.test.ts` has no overlay case; add a contributed-overlay case to each.


* Back off and coalesce system-schedule retries while the system shell cannot start, so one failing schedule stops raising a desktop notification and a fresh shell launch every second.

Existing Debt: The spec's "leave the entry due for retry" is implemented as "retry on the next one-second scheduler tick", with no backoff, no coalescing of ticks that arrive while a run is still pending, and no memory that the shell already failed, so both the retry rate and the notice rate are the scheduler's clock rate. Severity: 5/10

Existing Risk: 6/10 - If the shell plugin is disabled for the process, or the shell keeps failing to start because of a broken startup file or a sandbox refusal, every due system schedule retries the launch and posts "System shell could not start" about once a second, and that event defaults to a desktop banner with a warning sound, until the user restarts the app or cancels the schedule.

Proposal Risk: 2/10 - A persistent failure becomes one notice per episode with a capped retry interval, though a shell that fails only intermittently will now fire its schedule up to a minute late instead of on the next second.

Proposal: `ScheduleManager` in `src/schedule/manager.ts` runs `tick` from a one-second `setInterval` and calls `this.managers.systemSchedule?.tick(now)` without awaiting it. `SystemScheduleManager.tick` in `src/schedule/system/manager.ts` appends `runAfter(this.inFlight, now)` on every call, so a slow failing run queues one more `fireDue` per second behind it, each carrying its own stale `now`. `fireSystemBatch` in `src/schedule/system/firing.ts` returns `undefined` when `managers.systemShell.ensure()` is not `ok`, which leaves the entry due. `SystemShellManager.ensure` in `src/system-shell.ts` coalesces concurrent calls but clears `ensurePromise` the moment an attempt settles, and its `fail` calls `notifySystemShellStartFailure` in `src/schedule/system/notices.ts` on every attempt; that posts a `system-schedule-fire` event whose default in `src/notifications/alert-defaults.ts` is `{ desktop: true, sound: 'warning' }`. Make three changes. First, in `SystemScheduleManager.tick`, when a run is already pending, record only the latest `now` and return the in-flight promise, so at most one follow-up run is queued. Second, keep an in-memory per-key `retryAt` that doubles from one second to a sixty-second cap after each failed `ensure` or unreadable runscript and resets on success, and have `fireDue` skip a key whose `retryAt` lies in the future. Third, give `SystemShellManager` a reported-failure flag that suppresses repeat notices until an `ensure` succeeds. The tab-schedule path in `ScheduleManager.fire` already retries silently, which is the precedent for not re-notifying. Update the retry sentence in `product/specs/scheduling.md` to describe the backoff and the single notice. `src/schedule/system/manager.test.ts` covers one failed tick followed by success, each tick awaited; add a sustained-failure case asserting one notice across many ticks, an overlapping-tick case asserting one queued run, and a backoff case. `src/notifications/system-schedule.integration.test.ts` pins the notice text and must keep passing.


* Run the file navigator's and editor's own git actions, pull and commit-and-push, through one shared runner with a deadline, cancellation and terminal prompts disabled, the way git-sync already runs its git.

Existing Debt: The git modules have no shared way to run git, since each promisifies `execFile` itself, and the user-armed pull and commit run `git pull`, `git pull --rebase`, `git stash` and `git push` with no timeout, no abort signal and terminal prompts allowed, while the git-sync runner gives its commands a sixty-second deadline and cancellation and the clone path sets `GIT_TERMINAL_PROMPT=0`. Severity: 5/10

Existing Risk: 5/10 - A push or pull that blocks on a credential or host-key prompt, or on a stalled network, never settles, so the tab stays in its pulling or committing state and refuses every later pull and commit until the server restarts, and a hang inside the rebase step leaves the user's uncommitted changes in a stash they did not make.

Proposal Risk: 2/10 - A hung git is killed and reported through the existing rollback paths, though a push of a large history over a slow link could now be cut off at the deadline and reported as failed when it would eventually have finished.

Proposal: A local navigator pull runs `runPull` in `src/file-navigator/manager/pull.ts`, which arms the pulling flash and calls `state.filesystem.pull`, which for a local tree is `pullRoot` in `src/git/pull.ts` by way of `src/file-navigator/filesystem-port.ts`; a commit runs `src/file-navigator/manager/commit.ts` into `commitRoot` in `src/git/commit.ts`, which the editor's commit in `src/editor/commit.ts` also calls. None of those invocations carries a timeout or signal, so the coalescing checks (`state.pull === 'pulling' || state.commit === 'committing'`, and `editor.commit === 'committing'`) become permanent locks when git never returns. The remote side already guards this exact failure: `src/file-navigator/remote/port-requests.ts` gives `git-pull` and `git-commit` the ten-minute `LONG_REQUEST_DEADLINE_MS` because otherwise "a pull would stay `pulling` and block every later pull and commit", but on the far host the same `pullRoot` and `commitRoot` keep running after that deadline fires. By contrast `SyncCommandRunner` in `src/git/sync-command.ts` passes `timeout`, `signal` and `killSignal`, and `src/git/clone.ts` sets `GIT_TERMINAL_PROMPT: '0'`. Add a small `runGit(args, cwd, options)` module in `src/git/` that wraps `execFile` with a default deadline matching `LONG_REQUEST_DEADLINE_MS`, `killSignal: 'SIGTERM'`, an optional `AbortSignal`, and an environment of `{ ...process.env, GIT_TERMINAL_PROMPT: '0' }`, so credential helpers keep working exactly as the comment in `commit.ts` requires but git never opens the terminal. Route every call in `pull.ts` and `commit.ts` through it; a timeout rejects like any other git failure, so `pullRebase`'s `rebase --abort` and `rebaseAsideExtraChanges`'s stash pop run unchanged. `SyncCommandRunner` can call the same helper later, but that is not needed for this step. `src/git/pull.test.ts` and `src/git/commit.test.ts` mock `node:child_process` and pin argument order and every rollback path; they keep passing and should each gain an assertion that the options carry the deadline and `GIT_TERMINAL_PROMPT`. Nothing tests a hung git, so add a `runGit` test whose fake `execFile` never calls back, with a short deadline.

Existing Debt: When the core command input gave way to per-plugin command bars, the app shell's textarea ref and drop-handle ref stayed behind and are still threaded through about a dozen hooks and components as the focus and insert fallback, though no element is ever attached to either, while the real routes (per-label insertion and replacement maps and a drop-handle registry) grew up beside them. Severity: 6/10

Existing Risk: 4/10 - Shift+Tab back into the centre on a shell, editor or other plugin tab, and cancelling the quit dialog, focus nothing, and a task pick or paste that falls through to the drop fallback inserts nothing, while the tests for those paths inject a working fake for a ref production never fills and so keep passing.

Proposal Risk: 2/10 - Focus and insertion reach the visible tab's real bar or terminal, though a tab kind that registers no bar handle, such as an image or video tab, still has nothing to focus, now by design rather than by accident.

Proposal: `web/src/App.tsx` creates `inputReference` and `dropReference`, and its comment says the latter is "Assigned `CommandInput`'s insert-at-caret/highlight pair", but no `CommandInput` component exists under `web/src/` and nothing assigns either ref. The live routes are App's `pluginCommandLineInsertions` and `pluginCommandLineReplacements` maps, filled by `useApplicationBarEdits` in `web/src/plugins/shell/useApplicationBarEdits.ts`, the `harnessHandles` map from `useTabHandles`, and `registerCommandBarDrop` in `web/src/file-navigator/command-bar-drop-target.ts`. Add a `focus` entry to the per-label registration the shell bar already makes, so the app holds one label-keyed record of `{ focus, insert }` for command bars beside `harnessHandles` for terminals; have `focusCenterVisibleTab` and `cancelQuit` look the visible tab up there; have the task-pick, populate and paste fallbacks use the insertion record instead of `dropRef`; then delete `inputReference`, `dropReference`, `commandInputRef` and every prop that exists only to carry them, and fix the stale comments in `App.tsx`, `web/src/shared/command-bar/CommandBarShell.tsx` and `web/src/shared/drop-registry.ts` that describe the old wiring. `web/src/useFocusOnTabSwitch.test.ts` ("focuses the command line for any other tab"), `web/src/QuitDialog/useQuitConfirm.test.ts` and `web/src/pickers/useTaskPicker.test.ts` inject a working fake for the dead ref; rewrite them to register a handle, and add an App-level test that Shift+Tab into a shell tab focuses its bar. `web/src/shared/search-bar/`, the only consumer of a `commandInputRef` prop, has no production importer and can be deleted with its tests in the same change.


* Remove workspace clones asynchronously through one reference-counted release path, so closing a workspaced tab stops freezing every other tab for the length of a recursive delete.

Existing Debt: Workspace removal is a synchronous recursive `rmSync` even though the tab-close path's comment describes it as running in the background, since its zero-delay timer only lets the close broadcast go out first, and the reference-counted release is written twice, once swallowing removal errors and once throwing them. Severity: 5/10

Existing Risk: 5/10 - Closing a workspaced harness tab whose clone holds installed dependencies blocks the server's only thread for the whole delete, so every other tab's terminal output, every request and every state broadcast stalls for seconds, and shutdown pays the same cost once per clone.

Proposal Risk: 3/10 - The event loop stays free during removal, but an asynchronous delete opens a window in which a new clone created at the same directory could be deleted from under itself, which is why the old directory must be renamed aside before the delete begins.

Proposal: `closeTabResources` in `src/tab/cleanup.ts` defers `managers.workspace.release(workspaceDir)` inside `setTimeout(async () => …, 0)` and awaits it, with a comment saying the final release "recursively removes a full git clone, slow enough to freeze the UI if run inline". But `WorkspaceManager.release` in `src/workspace/manager.ts` returns `void` and ends in `removeWorkspace` in `src/workspace/index.ts`, which is `rmSync(directory, { recursive: true, force: true })` plus the same for the `.tmp` sibling, so the freeze still happens, just after the broadcast. `acquireAgentLease` in the same manager repeats `release`'s decrement-or-delete logic but calls `removeWorkspaceStrict` and throws, and `removeAll` calls `removeWorkspace` once per clone at shutdown. Give `src/workspace/index.ts` one async `removeWorkspace(directory, { strict })` that first `renameSync`s the clone and its `.tmp` sibling to a unique tombstone name inside the workspace base directory, which frees the original path at once, and then deletes the tombstones with `fs.promises.rm`; because the tombstones live in the base directory, `clearWorkspaceDir` already sweeps any a crash leaves behind. Route `release` and the lease's release through one private `decrement(dir, strict): Promise<void>` so the reference counting exists once, make `release` return that promise, and make `removeAll` and `dispose` await every removal (`Managers` already allows `dispose(): void | Promise<void>`, see `src/managers.ts`). `src/workspace/manager.test.ts` and `src/workspace/index.test.ts` pin the reference counting and the strict versus swallowing behavior. `src/tab/cleanup.test.ts` already mocks `release` as a rejecting promise, a path that only becomes reachable with this change, so it keeps passing and starts to mean something. Add a test that a release followed at once by a new workspace at the same directory leaves the new clone intact.


* Remember that the system-schedule paths are already excluded from git once the check succeeds, so reading or listing runscripts stops spawning five synchronous git processes on the server thread every time.

Existing Debt: Ensuring the system-schedule file and the scripts directory are git-ignored is a one-time setup step with side effects, but it runs inline on every runscript read and catalog with no record that it already succeeded, and one caller has already been rewritten to dodge its cost. Severity: 4/10

Existing Risk: 4/10 - Every Tab completion in any tab, every fire and retry of a system schedule, and every state broadcast while the New-schedule dialog is open blocks the event loop on one `git rev-parse`, two `git ls-files` and two `git check-ignore` calls, which on a large repository or a slow disk shows up as a stall in typing and terminal output.

Proposal Risk: 2/10 - Reads cost nothing after the first success, though a user who later force-adds the scripts directory to git is not warned until the next server start, because the tracked-path check no longer reruns on every read.

Proposal: `ensureSystemScheduleExcluded` in `src/schedule/system/local-exclude.ts` runs `git rev-parse --show-toplevel`, then `git ls-files` and `git check-ignore` for each of the two paths, all through `execFileSync`, and writes `.git/info/exclude` when a rule is missing. `excludeScriptsFromGit` in `src/schedule/system/runscript-files.ts` calls it before `readRunscript`, `catalogRunscripts` and `createRunscript` touch the directory, and `createRunscript` pays it twice. The hot callers are `complete` in `src/controller/completion.ts` on every Tab press, the runscript listing behind the one-second `LISTING_TTL_MS` cache in `src/state/listings.ts`, and `fireSystemBatch` in `src/schedule/system/firing.ts`; `src/schedule/system/runscript-rows.ts` carries a comment explaining that it calls `listRunscriptNames` instead because "the catalog call runs Git commands on every call". `product/specs/scheduling.md` requires that inspecting a runscript for reading or cataloging ensures both paths are ignored and that setup failures are reported without blocking reads, so keep every call site and memoize the success instead: hold a module-level `Set` of project roots for which `ensureSystemScheduleExcluded` returned without throwing, return early for a root already in it, and leave the failure path unmemoized so a tracked path or an unsafe exclude file keeps being reported on every read as today. Export a reset for tests. The workaround comment in `runscript-rows.ts` can then be reduced to the fact that the two calls now cost the same. `src/schedule/system/runscript-files.test.ts` and `src/schedule/system/storage.integration.test.ts` pin the exclusion behavior and the tracked-path refusal; add a case asserting that two reads of one root spawn git once, and one asserting that a failed check is retried on the next read.


* Work out which tabs are on screen once in the web client, using the rule the server already applies to unread badges, so native notifications stop sounding for a tab the user is watching in the split pane.

Existing Debt: The client has no shared answer to "which tabs are visible", so the app shell, the mounted view layers, the centre action area, focus-on-switch and alert placement each re-derive it from the raw snapshot, and alert placement checks only the primary pane even though the server's unread rule already counts the split pane's tab as visible. Severity: 4/10

Existing Risk: 3/10 - With a split open, activity in the second pane plays the warning sound and raises a desktop banner for output the user is looking at, and the next visibility rule, such as a third pane, has to be repeated in five places to stay consistent.

Proposal Risk: 1/10 - Visibility has one definition on the client, though it still mirrors the server's rule rather than receiving it, so a change to unread eligibility on the server needs the client selector changed to match.

Proposal: `createAlertPlacement` in `web/src/notifications/alert-placement.ts` answers `isVisible(label)` from the docked selection or `state?.tabs[state.activeTab]?.label === label` and never consults `secondaryTab`, which `StateEvent` in `src/protocol/events.ts` carries; `web/src/notifications/native-notifications.ts` uses that answer to decide whether to suppress a sound or banner. The visible-centre-tab test is written inline as `selected && !selected.hidden && !selected.dock` in `web/src/App.tsx` and as `candidate && !candidate.hidden && !candidate.dock` in `web/src/MountedViewLayers.tsx`, `web/src/AppCenterActionArea.tsx` derives the second pane's tab from `tabs.at(secondaryTab)` on its own, and `focusCenterVisibleTab` in `web/src/useFocusOnTabSwitch.ts` repeats the hidden and dock guard. On the server, `isUnreadEligible` in `src/tab/transcript/events.ts` already treats the active label and the secondary label as visible. Add a pure `web/src/shared/tab/visible-tabs.ts` exporting `visibleTabs(state)` that returns `{ current, secondary, visibleLabels }` by that rule (it sits in the shared layer because a feature, `notifications/`, and the app shell both consume it, so it must import neither), and have `alert-placement.ts`, `App.tsx`, `MountedViewLayers.tsx` and `AppCenterActionArea.tsx` read from it. `web/src/notifications/alert-placement.test.ts` covers docked and active tabs; add a split-pane case. `web/src/MountedViewLayers.test.tsx` and `web/src/MountedViewLayers.split-dirty.test.tsx` pin the current centre and split rendering and must keep passing; give `visibleTabs` its own unit tests.
