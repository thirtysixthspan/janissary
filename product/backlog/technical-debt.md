* **Proposal:** Derive the remote session's frame decoder from the wire union itself and decode by direction, so neither end can act on a frame the other was never meant to send.
  * **Debt:** The `ClientFrame`/`ServerFrame` unions and the three hand-written lists that decode them — two string sets and a switch — have no compile-time link to each other or to the direction a frame may travel, so a frame added to a union silently falls out of the decoder and either end will decode the other end's frames as its own. — **Debt severity: 7/10**
  * **Refactor:** In `src/remote/protocol.ts`, `CLIENT_TYPES` and `SERVER_TYPES` are hand-written string sets that must be kept in step with the `ClientFrame` and `ServerFrame` unions declared immediately above them, and `decodeFrame` accepts any type found in *either* set regardless of which end is reading. `decodeKnownFrame` in `src/remote/frame-decode.ts` is a third copy of the same list as a switch whose `default` arm answers "Unknown remote frame type", so a new union member typechecks and is then rejected at runtime. Replace all three with one decoder table per direction — `satisfies Record<ClientFrame['type'], Decoder>` and the same for `ServerFrame` — following the `satisfies Record<RemoteFilesystemOperation, OperationDescriptor>` pattern `FILESYSTEM_OPERATIONS` already uses in `src/remote/filesystem-operations.ts` and the `Record<TabPluginCapabilityName, true>` pattern in `src/plugins/api.ts`, and give `decodeFrame` a direction argument so `RemoteChannel.dispatch` in `src/remote/channel.ts` only ever sees server frames and `RemoteServer.dispatch` in `src/remote/serve.ts` only ever sees client frames. Both dispatch switches then keep their `default` arms as genuine unreachable guards rather than as the only thing checking direction. `src/remote/protocol.test.ts` pins the encode/decode round trips and the handshake-version refusal, and `src/remote/channel.test.ts` and `src/remote/serve.test.ts` pin the wording each end produces for an unexpected frame; all three must keep passing.
  * **Risks:**
    * **Existing:** A frame type added to one union without a decoder entry compiles clean and fails only at runtime on the far side of an ssh connection, as a channel-level fault that kills the tab — and until it is caught, either end will act on a frame only the other end was supposed to receive. — **Existing risk: 6/10**
    * **Refactoring:** The direction split moves which arm answers a wrong-direction frame, so a test asserting the channel's current "Unexpected remote frame" wording may start seeing the decoder's "Unknown remote frame type"; and a table entry transcribed with the wrong validator would quietly loosen a frame's argument checks, which nothing would catch for the frames only exercised end to end against a real remote.
    * **Proposed:** The unions and the tables agree by construction, but which direction a frame belongs to is still asserted by the table it is written into rather than derived from the union it came from, so a frame filed under the wrong direction would still compile. — **Proposed risk: 3/10**

* **Proposal:** Make the remote file navigator honor the refusal contract it declares when the connection fails, not only when a path falls outside the tree.
  * **Debt:** `FileSystemPort` states that a method whose result can express failure never rejects, and the remote implementation satisfies that for containment refusals but rejects for every transport and server-side fault, so the same user action reports a per-path result locally and a bare error remotely. — **Debt severity: 6/10**
  * **Refactor:** The interface comment in `src/file-navigator/filesystem-port.ts` divides the methods in two: those returning `FileOperationResult`, `MoveManyResult`, `DeleteManyResult`, `PasteManyResult`, or `ReplayResult` report every refusal as a value and "a rejection from the first group is a bug in the implementation". `RemoteFileSystemPort` in `src/file-navigator/remote-port.ts` routes all of them through one private `request`, which rejects on three paths that have nothing to do with containment: `dispose()` and `onClose()` reject every pending call, `request` throws when the port is already closed, and `onReply` rejects whenever the reply carries an `error`. The server produces that `error` for anything thrown out of an operation — `RemoteFileNavigators.request` in `src/remote/serve-file-navigator.ts` catches and converts, and its own `pasteSources` throws for an out-of-tree source rather than returning a refusal, with wording that differs from `OUTSIDE_ROOT_REASON`. Have `request` take the operation's refusal shape and map a rejection into it, reusing the builders already in `src/remote/filesystem-refusal-shapes.ts` (`refusedItem`, `refusedMoveMany`, `refusedDeleteMany`, `refusedPaste`, `refusedReplay`) so a dropped connection during a batch move comes back as `failedPaths` plus a reason, exactly as a local batch does; leave the raw-data methods (`readDirectory`, `statRows`, `readFile`, `search`, `watch`) rejecting, which is what the interface says they should do. Fold `pasteSources`' containment check into the same refusal the `refuse` gate already applies. `src/remote/file-navigator-refusal-contract.test.ts` covers the out-of-tree cases for rename, move, delete, and batch delete and must keep passing; add the transport cases — a channel closed mid-request, a reply carrying an error — beside them.
  * **Risks:**
    * **Existing:** An ssh connection dropping mid-operation rejects a `moveMany` the type says cannot reject, so the client is told the whole batch failed as one opaque error while the remote may have already moved some of the files — the navigator's view and the remote filesystem disagree and the user has no per-path report to reconcile them from. — **Existing risk: 7/10**
    * **Refactoring:** Turning rejections into values removes the signal the current callers may be leaning on; `mapMaybe` in `src/file-navigator/manager-batch.ts` and the reporters in `src/controller/file-navigator.ts` treat a resolved result as "the operation ran", so a transport failure mapped to a refusal shape must not be recorded on the tab's undo stack, and `pushing` it there would let a later undo replay a move that never happened.
    * **Proposed:** The mutating methods report failure the way callers already branch on, but the classification is per-method rather than derived, so a method added to `FileSystemPort` without a refusal shape falls back to rejecting again. — **Proposed risk: 3/10**
