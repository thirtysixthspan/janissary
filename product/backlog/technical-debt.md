* Remove workspace clones asynchronously through one reference-counted release path, so closing a workspaced tab stops freezing every other tab for the length of a recursive delete.

Existing Debt: Workspace removal is a synchronous recursive `rmSync` even though the tab-close path's comment describes it as running in the background, since its zero-delay timer only lets the close broadcast go out first, and the reference-counted release is written twice, once swallowing removal errors and once throwing them. Severity: 5/10

Existing Risk: 5/10 - Closing a workspaced harness tab whose clone holds installed dependencies blocks the server's only thread for the whole delete, so every other tab's terminal output, every request and every state broadcast stalls for seconds, and shutdown pays the same cost once per clone.

Proposal Risk: 3/10 - The event loop stays free during removal, but an asynchronous delete opens a window in which a new clone created at the same directory could be deleted from under itself, which is why the old directory must be renamed aside before the delete begins.

Proposal: `closeTabResources` in `src/tab/cleanup.ts` defers `managers.workspace.release(workspaceDir)` inside `setTimeout(async () => …, 0)` and awaits it, with a comment saying the final release "recursively removes a full git clone, slow enough to freeze the UI if run inline". But `WorkspaceManager.release` in `src/workspace/manager.ts` returns `void` and ends in `removeWorkspace` in `src/workspace/index.ts`, which is `rmSync(directory, { recursive: true, force: true })` plus the same for the `.tmp` sibling, so the freeze still happens, just after the broadcast. `acquireAgentLease` in the same manager repeats `release`'s decrement-or-delete logic but calls `removeWorkspaceStrict` and throws, and `removeAll` calls `removeWorkspace` once per clone at shutdown. Give `src/workspace/index.ts` one async `removeWorkspace(directory, { strict })` that first `renameSync`s the clone and its `.tmp` sibling to a unique tombstone name inside the workspace base directory, which frees the original path at once, and then deletes the tombstones with `fs.promises.rm`; because the tombstones live in the base directory, `clearWorkspaceDir` already sweeps any a crash leaves behind. Route `release` and the lease's release through one private `decrement(dir, strict): Promise<void>` so the reference counting exists once, make `release` return that promise, and make `removeAll` and `dispose` await every removal (`Managers` already allows `dispose(): void | Promise<void>`, see `src/managers.ts`). `src/workspace/manager.test.ts` and `src/workspace/index.test.ts` pin the reference counting and the strict versus swallowing behavior. `src/tab/cleanup.test.ts` already mocks `release` as a rejecting promise, a path that only becomes reachable with this change, so it keeps passing and starts to mean something. Add a test that a release followed at once by a new workspace at the same directory leaves the new clone intact.


* Remember that the system-schedule paths are already excluded from git once the check succeeds, so reading or listing runscripts stops spawning five synchronous git processes on the server thread every time.

Existing Debt: Ensuring the system-schedule file and the scripts directory are git-ignored is a one-time setup step with side effects, but it runs inline on every runscript read and catalog with no record that it already succeeded, and one caller has already been rewritten to dodge its cost. Severity: 4/10

Existing Risk: 4/10 - Every Tab completion in any tab, every fire and retry of a system schedule, and every state broadcast while the New-schedule dialog is open blocks the event loop on one `git rev-parse`, two `git ls-files` and two `git check-ignore` calls, which on a large repository or a slow disk shows up as a stall in typing and terminal output.

Proposal Risk: 2/10 - Reads cost nothing after the first success, though a user who later force-adds the scripts directory to git is not warned until the next server start, because the tracked-path check no longer reruns on every read.

Proposal: `ensureSystemScheduleExcluded` in `src/schedule/system/local-exclude.ts` runs `git rev-parse --show-toplevel`, then `git ls-files` and `git check-ignore` for each of the two paths, all through `execFileSync`, and writes `.git/info/exclude` when a rule is missing. `excludeScriptsFromGit` in `src/schedule/system/runscript-files.ts` calls it before `readRunscript`, `catalogRunscripts` and `createRunscript` touch the directory, and `createRunscript` pays it twice. The hot callers are `complete` in `src/controller/completion.ts` on every Tab press, the runscript listing behind the one-second `LISTING_TTL_MS` cache in `src/state/listings.ts`, and `fireSystemBatch` in `src/schedule/system/firing.ts`; `src/schedule/system/runscript-rows.ts` carries a comment explaining that it calls `listRunscriptNames` instead because "the catalog call runs Git commands on every call". `product/specs/scheduling.md` requires that inspecting a runscript for reading or cataloging ensures both paths are ignored and that setup failures are reported without blocking reads, so keep every call site and memoize the success instead: hold a module-level `Set` of project roots for which `ensureSystemScheduleExcluded` returned without throwing, return early for a root already in it, and leave the failure path unmemoized so a tracked path or an unsafe exclude file keeps being reported on every read as today. Export a reset for tests. The workaround comment in `runscript-rows.ts` can then be reduced to the fact that the two calls now cost the same. `src/schedule/system/runscript-files.test.ts` and `src/schedule/system/storage.integration.test.ts` pin the exclusion behavior and the tracked-path refusal; add a case asserting that two reads of one root spawn git once, and one asserting that a failed check is retried on the next read.


* Work out which tabs are on screen once in the web client, using the rule the server already applies to unread badges, so native notifications stop sounding for a tab the user is watching in the split pane.

Existing Debt: The client has no shared answer to "which tabs are visible", so the app shell, the mounted view layers, the centre action area, focus-on-switch and alert placement each re-derive it from the raw snapshot, and alert placement checks only the primary pane even though the server's unread rule already counts the split pane's tab as visible. Severity: 4/10

Existing Risk: 3/10 - With a split open, activity in the second pane plays the warning sound and raises a desktop banner for output the user is looking at, and the next visibility rule, such as a third pane, has to be repeated in five places to stay consistent.

Proposal Risk: 1/10 - Visibility has one definition on the client, though it still mirrors the server's rule rather than receiving it, so a change to unread eligibility on the server needs the client selector changed to match.

Proposal: `createAlertPlacement` in `web/src/notifications/alert-placement.ts` answers `isVisible(label)` from the docked selection or `state?.tabs[state.activeTab]?.label === label` and never consults `secondaryTab`, which `StateEvent` in `src/protocol/events.ts` carries; `web/src/notifications/native-notifications.ts` uses that answer to decide whether to suppress a sound or banner. The visible-centre-tab test is written inline as `selected && !selected.hidden && !selected.dock` in `web/src/App.tsx` and as `candidate && !candidate.hidden && !candidate.dock` in `web/src/MountedViewLayers.tsx`, `web/src/AppCenterActionArea.tsx` derives the second pane's tab from `tabs.at(secondaryTab)` on its own, and `focusCenterVisibleTab` in `web/src/useFocusOnTabSwitch.ts` repeats the hidden and dock guard. On the server, `isUnreadEligible` in `src/tab/transcript/events.ts` already treats the active label and the secondary label as visible. Add a pure `web/src/shared/tab/visible-tabs.ts` exporting `visibleTabs(state)` that returns `{ current, secondary, visibleLabels }` by that rule (it sits in the shared layer because a feature, `notifications/`, and the app shell both consume it, so it must import neither), and have `alert-placement.ts`, `App.tsx`, `MountedViewLayers.tsx` and `AppCenterActionArea.tsx` read from it. `web/src/notifications/alert-placement.test.ts` covers docked and active tabs; add a split-pane case. `web/src/MountedViewLayers.test.tsx` and `web/src/MountedViewLayers.split-dirty.test.tsx` pin the current centre and split rendering and must keep passing; give `visibleTabs` its own unit tests.
