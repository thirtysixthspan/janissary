* Split the harness sandbox's argument and environment builder from the host check that decides whether to confine, so its credential-scrub and token-injection tests run on every platform, CI included.

Existing Debt: `sandboxSpawn` both asks whether this host can confine and assembles the `sandbox-exec` invocation, so 28 tests that only inspect the returned arguments and environment are gated on a darwin-only availability check, while CI runs on Linux. Severity: 6/10

Existing Risk: 6/10 - A regression in the credential scrub, the per-harness token injection or the `ai/`, `scripts/` and `security/` read carve-ins passes CI and every Linux run and is caught only if someone runs the suite on a Mac first, and a new profile parameter with no `-D` binding is checked against just four hard-coded names.

Proposal Risk: 2/10 - The builder's output is pinned on every platform and every profile parameter is checked against a binding, leaving only real kernel confinement, which genuinely needs macOS, under the darwin-only live tests.

Proposal: In `src/sandbox/index.ts`, `sandboxSpawn` calls `sandboxWillConfine(dir)` from `src/sandbox/confinement.ts` and returns early on a host that cannot confine; everything after that check only computes paths, the `-D` parameter list, the profile string and the scrubbed environment. The browser path already has the right shape: `browserSpawn` in `src/sandbox/browser/spawn.ts` receives the `confinable` decision as an argument, and neither `src/sandbox/browser/spawn.test.ts` nor `src/sandbox/browser/profile.test.ts` skips a test, while 28 cases in `src/sandbox/index.test.ts` are `it.skipIf(!sandboxAvailable())` and `.github/workflows/ci.yml` runs on `ubuntu-latest`. Move the post-check body into `confinedHarnessSpawn(options, dir, command, args, env)` in a new `src/sandbox/harness-spawn.ts`, taking `homeDParams` with it, and leave `sandboxSpawn` with the probe and the dispatch. Point the skipped cases that only read `result.args` and `result.env` at the builder and drop their skip, keeping one skipped case that asserts `sandboxSpawn` wraps through `sandbox-exec` on a confining host. Replace the `includes every -D param the profile references` test, which checks only `WORKSPACE`, `TMPDIR`, `HOME` and `GIT_OBJECTS`, with the derived check `src/sandbox/browser/profile.test.ts` already uses (collect every `(param "…")` the profile string names and assert each has a `-D` binding), run for online, offline and one installed-skill directory. Before relying on the builder under Linux, confirm that `darwinUserCacheDir` in `src/sandbox/resolve.ts`, `resolveExecutableDirs`, `serverNodeDirs` and `playwrightPackagePaths` return a value there rather than throwing, since a throw would fail the unskipped tests rather than any behavior. The live confinement tests (`src/sandbox/live.sandbox.test.ts`, `src/sandbox/pty.sandbox.test.ts`, `src/sandbox/keychain.sandbox.test.ts`) stay macOS-only and untouched.


* Give the "is this path inside that root" check one neutral home and route the dozen hand-written versions across the server through it.

Existing Debt: Containment is decided in at least a dozen places under four different rules, because the two shared helpers live inside features (`containedAbsolute` in the file navigator, `isInsideRoot` in the plugin host), so remote code reaches into the file navigator for one and everyone else writes the check inline. Severity: 5/10

Existing Risk: 5/10 - These checks decide what a workspace, plugin, agent run or remote request may touch, and they already disagree on whether an empty root contains anything, whether the root itself counts, and whether a child named `..notes` is outside, so a fix to one version never reaches the others.

Proposal Risk: 2/10 - One tested rule and a strict variant serve every caller, though the plugin-facing `isInsideRoot` keeps its own empty-root answer on purpose and no lint rule stops a future caller from writing the check inline again.

Proposal: `containedPath` and `containedAbsolute` sit in `src/file-navigator/batch-paths.ts`, whose own comment says they were published so the navigator, the remote filesystem and the serve process clamp with one rule, and four remote modules import them from there (`src/remote/filesystem/path-containment.ts`, `src/remote/filesystem/refusal.ts`, `src/remote/serve-file-navigator.ts`, `src/remote/serve-processes.ts`); `isInsideRoot` in `src/plugins/files.ts` is a separate resolved-prefix rule that answers false for an empty root, where `containedAbsolute('', x)` answers true for anything under the process directory. Inline `path.relative` versions sit in `selectedInstalledSkillDirs` in `src/agent/execute.ts` and the skill-directory filter in `src/sandbox/index.ts` (the same strict rule written twice), in `src/agent/skill-grants.ts`, `src/agent/task-resolution.ts` and `src/open/file-manager.ts`, and prefix versions in `src/file-navigator/paste.ts`, `src/file-navigator/index.ts` and `src/file-navigator/remote/file-cache.ts`, while `src/plugins/origin-workspace-records.ts` tests `relative.startsWith('..')`, which wrongly rejects a child named `..notes`. Move `containedPath` and `containedAbsolute` verbatim into a new `src/path-containment.ts`, add a `containedStrictly` variant that excludes the root, update every importer to the new module directly rather than re-exporting (per `ai/guidelines/imports-and-barrel-files.md`), keep `isInsideRoot` in `src/plugins/files.ts` as a thin wrapper that applies its empty-root rule and then calls the shared helper (plugins may import that module and nothing else of the host's), and replace the inline versions listed above. Add `src/path-containment.test.ts` pinning the root itself, `..`, `../x`, a `/repo-evil` sibling beside `/repo`, a `..notes` child, an absolute relative path and an empty root. Existing coverage is `src/plugins/files.test.ts`, `src/file-navigator/batch.test.ts`, `src/remote/filesystem/operations.test.ts`, `src/file-navigator/remote-cwd.test.ts` and `src/open/file-manager.test.ts`; the sandbox skill-directory case in `src/sandbox/index.test.ts` runs only on macOS, so check that replacement by hand or land the sandbox builder split first.


* Resolve a tab's working directory through one tab-manager method with one fallback, so commands, openers and the file navigator agree on where a relative path lands.

Existing Debt: A tab's runtime `cwd` stays unset until its shell reports one, and the fallback for that case is chosen per call site, `?? process.cwd()` in about twenty places and `?? managers.tab.launchDir` in six, which differ whenever `janus <dir>` is started from another directory because nothing changes the process directory to the project. Severity: 5/10

Existing Risk: 5/10 - In a tab with no recorded cwd, a relative `open` or `edit` target resolves against the directory `janus` was launched from while `$root` expands against the project, and the `files` command and the folder button root the navigator in different places, so a file can be opened or created somewhere the user did not mean.

Proposal Risk: 2/10 - Every migrated path-resolving site falls back to the project directory and a test pins the no-cwd case, though the process-spawning sites left for a follow-up still fall back to the server process's own directory until they move.

Proposal: `TabManager.cwdOf` in `src/tab/manager.ts` returns the runtime `cwd`, which `makeTab` in `src/tab/index.ts` leaves unset, and `TabManager.launchDir` is the project directory (`projectDir ?? process.cwd()`); `src/main.ts` never calls `chdir`, and `product/specs/cli.md` already says the resolved target directory is the default root for shell commands, harness tabs and file-navigator roots for the whole session. Sites falling back to `process.cwd()` include `src/commands/edit.ts` (which in the same three lines resolves against `process.cwd()` but expands `$root` with `launchDir`), `src/open/file-manager.ts` (three places), `src/open/file-command.ts`, `src/file-navigator/open-command.ts` (two), `src/play/run.ts`, `src/profile/view-tabs.ts`, `src/profile/agent-opener.ts`, `src/controller/completion.ts`, `src/editor-suggest/handler.ts` and the cwd the client is shown in `src/tab/view.ts`; sites falling back to `launchDir` are `src/agent/manager.ts`, `src/command/manager.ts`, `src/file-navigator/open.ts`, `src/plugins/activity.ts`, `src/plugins/launch-tab-remote.ts` and `src/plugins/line-capabilities.ts`. Add `workingDirOf(label)` to `TabManager` returning `cwdOf(label) ?? launchDir`, plus a `resolveTabPath(managers, label, target)` beside it that does the `expandUserPath` and `path.resolve` steps the open and edit paths each write out, then migrate the path-resolving sites above and the six `launchDir` sites to them. This changes behavior only for a tab with no recorded cwd in a server started on a directory other than its own, which is the case `product/specs/cli.md` already describes, so no spec change should be needed. Leave the process-spawning fallbacks (`src/acp/manager.ts`, `src/shell/manager.ts`, `src/ssh-manager.ts`, `src/monitor/session.ts`, `src/harness/manager.ts`, `src/connection/catalog.ts`) for a follow-up. Every existing test stubs `cwdOf` with a value (`src/open/file-manager.test.ts`, `src/commands/edit.test.ts`, `src/play/run.test.ts`, `src/file-navigator/open-command.test.ts`), so nothing covers the fallback; add cases to `src/commands/edit.test.ts` and `src/file-navigator/open-command.test.ts` where the tab has no cwd and the project directory differs from `process.cwd()`.


* Give each remote session entry one owner for its readiness, ending and usability checks, starting with the teardown sequence and cache-owner key copied across the remote, file-navigator and plugin layers.

Existing Debt: The remote entry is a plain mutable record whose state transitions nobody owns, so its readiness is four loose fields settled from seven places under three different guards, its ending sequence is written out four times, and callers outside the remote layer rebuild its file-cache owner key and decide whether it is usable by hand. Severity: 6/10

Existing Risk: 5/10 - The next ending path or per-entry resource will miss one of the hand-copied steps and leave a stale record in the sessions list or a remote file cache that is never cleared, and one changed copy of the cache-owner key silently stops cached files being cleared when the session ends.

Proposal Risk: 3/10 - The ending sequence, readiness settlement and cache-owner key each have one definition, but the entry stays a record other modules write directly, so later increments still have to move its remaining transitions behind methods.

Proposal: The entry type, `isEstablished`, `markEntryEnded`, `terminateRemoteEntry` and `dropTerminatedSessionRecord` live in `src/remote/attach.ts`, a file named after its `Attach` backoff class that imports a type from `src/remote/manager.ts`, which imports it back. The sequence of capturing `channel.sessionId`, then `channel.finish()`, `channelClosed`, `channel.closeAfterShutdown()` and `dropTerminatedSessionRecord` appears in `RemoteManager.release` and `RemoteManager.finishUnreferencedEntry` in `src/remote/manager.ts` (identical apart from a `closed` guard) and in `terminateRemoteEntry`, with `closeAll` as a fourth variant. Readiness is `ready`, `resolveReady`, `rejectReady` and `settled`, settled from five sites in `src/remote/entry-factory.ts` and one each in `src/remote/resume.ts` and `src/remote/manager-closed.ts`, guarded by `!entry.closed`, `!entry.settled` or both. The cache owner `{ destination, workspaceRoot, workspaceLabel }` is built literally in `src/remote/attach.ts`, twice in `src/file-navigator/manager/files.ts` and once in `src/plugins/remote-capabilities.ts`, and whether an entry is usable has three versions that read different fields: `isEstablished`, the check in `RemoteManager.acquireAgentLease`, and `establishedLabel` in `src/agent/remote-target.ts`. As a first increment, make the last-reference branch of `release` call `finishUnreferencedEntry`; add `settleEntryReady(entry, result)` beside `isEstablished` with a single guard (already settled or closed means do nothing) and call it from every settle site, leaving the after-settlement `reportRemoteRefusal` branch in `entry-factory.ts` at its call site; add `remoteCacheOwner(entry)` and use it at the four literal sites; and give `acquireAgentLease` and `establishedLabel` one shared usability predicate. Covered by `src/remote/manager.test.ts`, `src/remote/resume.test.ts`, `src/remote/attach.test.ts`, `src/file-navigator/manager/files.test.ts` and `src/plugins/remote-capabilities.test.ts`; `src/agent/remote-target.ts` has no colocated test, so add one that pins which entries `establishedLabel` will reuse before changing its predicate.


* Let a tab plugin ask which of its own tabs are still open, so the per-tab copies the SQL and diff plugins keep are pruned when their tabs close instead of being reused on reopen.

Existing Debt: The host owns plugin tab records but gives a plugin no close signal, no payloads on notifications and no way to list its own open tabs, so stateful plugins keep their own maps keyed by instance key and prune them only when a notification arrives, which never happens once their last tab has closed. Severity: 5/10

Existing Risk: 4/10 - Closing the last SQL tab and reopening the same database brings back the stale payload, including any pending request whose answer was dropped, and skips the schema request, while closing a remote diff tab and running `diff` on its source tab again opens a local tab without rejoining the remote channel, so the tab reports that the remote host did not answer.

Proposal Risk: 2/10 - Both plugins prune against the host's own answer before reusing anything, though each plugin still has to remember to ask, and the launcher's and conversations plugin's notification-only pruning stays until they adopt it too.

Proposal: Notifications in `src/plugins/notifications.ts` reach only plugins that own at least one tab (`ownedTabs(...).length > 0`), as `ai/guidelines/plugins-tabs.md` specifies. `SqlTabs` in `src/plugins/sql/tabs.ts` says it is pruned against the open-tab set on every notification so nothing outlives its tab, but its only prune is in the `notify` handler in `src/plugins/sql/activate.ts`, and `openDatabase` in `src/plugins/sql/open-tab.ts` reopens from `tabs.read(key)` whenever an entry exists. `DiffSession.tabs` in `src/plugins/diff/session.ts` is cleared only in `dispose`, and `openRemoteWorkspace` treats a surviving entry as an open tab and refocuses through `openOrFocusTab` instead of `launchTab`. Add an `ownTabKeys(): readonly string[]` capability: declare it on `TabPluginOwnTabCapabilities` in `src/plugins/api-own-tab.ts`, implement it in `src/plugins/own-tab-capabilities.ts` with the same plugin-id scan `TabManager.pluginTabByInstanceKey` uses, add its name to the capability union and `CAPABILITIES` in `src/plugins/api-capabilities.ts`, and add it to the capability list in `documentation/developer-documentation/tab-plugins.md`, whose prose count `src/plugins/documentation.test.ts` checks against a number-word list that currently stops at forty-seven. Declare it in the SQL and diff manifests, call `tabs.prune(capabilities.ownTabKeys())` in the SQL command path before `openDatabase`, and prune `DiffSession.tabs` before `tabFor` and before the `existing` check in `openRemoteWorkspace`. Nothing tests close-then-reopen today, so add those cases to `src/plugins/sql/activate.test.ts` and `src/plugins/diff/activate.test.ts`, plus a capability case to `src/plugins/context.test.ts`. Carrying `{ instanceKey, payload }` on each notification's `tabs`, which would let `SqlTabs` drop its payload copy entirely, is a separate API change for later.

Existing Debt: Each remote request and reply family keeps its own map, timer and close handling with no shared primitive behind them, so the five families already behave differently (capture has no deadline, agent resolution waits 15 seconds, session-state queries and ACP release are silently dropped while detached and wait out their timers) and every new family also has to add a case to the channel's `send()` refusal switch. Existing Risk: 4/10 - `harness capture <name>` on a remote tab whose far side never answers waits until the channel closes with nothing on screen, and the next request family that forgets one of the three behaviors leaves a hung promise or a silent wait.

Proposal Risk: 2/10 - Capture and agent resolution share one tested tracker and capture gains a deadline, while the file-navigator port, the session-state query and ACP release keep their own bookkeeping until later increments move them.

Proposal: `CaptureRequestTracker` in `src/remote/channel/capture.ts` settles `undefined` on close and fails a request the channel could not send, but sets no timer, and its header still says requests are correlated by spawn id alone because the wire carries no separate request id, while the code keys by `request` and `src/remote/channel/capture.test.ts` tests overlapping requests by request id. `RemoteAgentRequests` in `src/remote/channel/agent-requests.ts` builds a hand-rolled deferred with a 15-second timer and rejects on `failAll`; `RemotePortRequests` in `src/file-navigator/remote/port-requests.ts` has per-operation deadlines; `askSessionState` in `src/remote/resume.ts` holds a single slot with a 30-second wait; and the ACP release in `src/remote/acp-session.ts` has its own 5-second timer. `RemoteChannel.send` in `src/remote/channel/index.ts` refuses only `filesystem-request`, `acp-open`, `acp-prompt` and `capture-request` while detached and drops every other frame silently. * Build every xterm terminal in the web client through one shared factory, so the harness, shell and recording terminals stop drifting apart on metrics, clipboard and theme handling.

Existing Debt: Terminal construction lives inside three React hooks instead of a framework-free factory in the shared terminal layer, so each tab type copied the parts it knew about and behavior has already split: only the harness terminal answers OSC 52 clipboard requests and remaps Shift+Enter and Alt+arrow keys, only the shell terminal follows theme switches, and all three re-read the same CSS variables with the same hard-coded fallbacks. Severity: 4/10

Existing Risk: 4/10 - A program in a remote or SSH shell tab that copies through OSC 52 silently copies nothing, harness and recording terminals keep the colors they mounted with after a theme change, and the next terminal fix lands in one of three places.

Proposal Risk: 2/10 - All three terminals share construction, metrics and clipboard handling, though key remapping and theme following still differ by tab type until someone decides which terminals should have them.

Proposal: `new Terminal(` appears in `useXterm` (`web/src/shared/terminal/useXterm.ts`), `useShellTerminal` (`web/src/plugins/shell/useShellTerminal.ts`) and `useAsciicastTerminal` (`web/src/plugins/asciicast/useAsciicastTerminal.ts`), each reading `--mono`, `--terminal-font-size` and `--terminal-line-height` with the same 13.5 and 1.2 fallbacks. Only `useXterm` registers the OSC 52 handler (through `osc52ClipboardText` in `web/src/shared/terminal/terminal/osc52.ts`, with a comment saying that without it a remote harness's copy silently does nothing) and applies `shiftEnterSequence` and `altArrowSequence` from `web/src/shared/terminal/terminal/keys.ts`, while only `useShellTerminal` installs a `MutationObserver` on `data-theme` to re-apply `shellTerminalTheme()` from `web/src/plugins/shell/shell-terminal-theme.ts`, even though shell tabs also run remote and SSH PTYs. Add a framework-free `createAppTerminal(container, options)` in a new `web/src/shared/terminal/app-terminal.ts` that reads the metrics once, constructs the `Terminal`, registers OSC 52 when a `copyText` option is given, installs the theme observer when a `theme` function is given, and returns the terminal with one `dispose()` that removes what it installed; use it in all three hooks, and publish it to the concrete plugins through `web/src/plugins/api.ts`, since they may import nothing else of the host's (an additive export, so `TAB_PLUGIN_API_VERSION` does not move). The shell tab gaining OSC 52 through its existing `copyText` capability is a visible change worth a line in `product/specs/shell-tab.md`; leave key remapping and theme following for harness and recording terminals as explicit follow-up decisions rather than switching them on here. Covered by `web/src/shared/terminal/useXterm.test.tsx`, `web/src/plugins/shell/useShellTerminal.test.ts`, `web/src/plugins/asciicast/useAsciicastTerminal.test.ts` (which pins the CSS reads and both fallbacks) and `web/src/shared/terminal/terminal/osc52.test.ts`; add `web/src/shared/terminal/app-terminal.test.ts` for the factory, including that `dispose()` disconnects the observer and the OSC handler.
