* Construct `JanusClient` at the app boundary and give it a teardown: `web/src/App.tsx:34-35` builds the protocol client inside its own render body (`clientReference.current ??= new JanusClient()`), which violates §7 (services are instantiated at the edge and passed down; components never construct services), and `web/src/ws.ts:34-38` opens the WebSocket and registers its `message` and `open` listeners in the constructor with no `dispose()` anywhere in the class, which violates §7's explicit-lifecycle rule that acquisition comes with matching teardown. The cost is already being paid in the test suite: because the instance cannot be injected, `web/src/App.test.tsx:36` has to `vi.mock('./ws')` with a hand-written fake class, and that fake has drifted from the real service — its locally re-declared `ServerStateListener` (lines 18-24) is missing the `activeTabNameMaxLength` parameter `ws.ts:10` passes, and its `LayoutListener` (lines 27-32) accepts a `'schedules'` focus value the real one does not — so the largest test file in `web/src/` asserts against a shape the app no longer has. Move construction into `web/src/main.tsx`, make `client` a required prop on `App`, export the `StateListener` and `LayoutListener` types from `ws.ts` so no caller re-declares them, add a `dispose()` that closes the socket and clears the listener sets and pty handlers, and have `main.tsx` own that call. Fifty-eight production files import `./ws`, but every one of them already receives the client as a prop, so only `ws.ts`, `main.tsx`, `App.tsx`, and `App.test.tsx` change. Severity: **high**.

* Gather the transcript feature into `web/src/transcript/`: `Transcript.tsx`, `transcript-line.tsx`, `transcript-intents.ts`, `ansi.ts`, `file-link.ts`, `markdown.ts`, and `useTranscriptScroll.ts` all sit loose in the flat `web/src/` root alongside every other feature's files, which is §1 (organize by feature, not by file type — a directory name should name a piece of the product). These are not root-level shared utilities: grepping each one shows `ansi.ts`, `file-link.ts`, and `markdown.ts` have exactly one consumer apiece, `transcript-line.tsx`, which itself has exactly one consumer, `Transcript.tsx`, and `transcript-intents.ts` is imported only by those two and `file-link.ts` — a closed cluster that §2 says should be colocated rather than spread across the shared root. The cost is that the root gives no signal which of its two hundred files belong to the transcript, so an author touching ANSI rendering has to grep to learn whether anything else depends on it, and a generic-sounding name like `markdown.ts` invites a second feature to import it and cement the wrong boundary. Move the seven files with their colocated tests — `Transcript.test.tsx`, `transcript-line.test.tsx`, `transcript-intents.test.ts`, `ansi.test.ts`, `file-link.test.tsx`, `markdown.test.ts`, `useTranscriptScroll.test.ts` — into `web/src/transcript/`, flip their intra-cluster imports to `./` and their imports of `icons.ts`, `ws.ts`, and `TerminalCard.tsx` to `../`, and repoint the four outside importers: `AgentTabBody.tsx`, `InactiveAgentTabBody.tsx`, and `NotificationsTab.tsx` for `Transcript`, and `App.tsx` for `useTranscriptScroll`. Leave `useTranscriptSearch.ts` and `TerminalCard.tsx` where they are — both have consumers outside the transcript. It is all import-path churn with no behavior change. Severity: **medium**.

* Pull the docked-tab selection rules out of `web/src/Sidebar.tsx` into a hook beside it: the component derives its docked entries inline at line 72, then runs two effects that decide which one is showing — lines 76-80 select whichever tab was not in the previous label set, lines 84-87 let a profile's declared `focusView` override that — and lines 90-92 resolve the current entry, its strip index, and the docked plugin list, all before any markup is reached. That is §5 (components render, they do not decide): "which docked tab is visible" is the sidebar's actual behavior, and it can only be exercised by rendering the whole sidebar, including `FileNavigatorTab` and `DockedPluginBody`. What the shape hides is visible in the same lines — `entries` is rebuilt as a fresh array on every render and then listed as a dependency of both effects, so both re-run on every render rather than when the docked set changes. `Sidebar.tsx` is among the most churned files in `web/src/`, so every future dock behavior lands in this same body. Extract the entry derivation and both effects into `useSidebarSelection(tabs, side, focusView)` in a new module, memoize the entry list there, and leave `Sidebar.tsx` with the resize handlers and the markup. Its props and its two exports are unchanged, so none of the files that render it are affected. Resolve by running the `ai/tasks/hygiene/improve-modularity.md` task against `web/src/Sidebar.tsx`. Severity: **medium**.
