Severity: 5/10

Proposal Risk: 2/10 - Teardown order becomes a stated list that a reviewer can check against, though the list is still maintained by hand and a manager added without an entry has to be caught by the test that pins it rather than by the compiler.

* Drive the two remaining union dispatchers off the exhaustiveness idiom the rest of the codebase already uses, so a value added to either union stops compiling instead of silently doing nothing.

Existing Debt: The project has an established, twice-documented way to make a union's dispatcher exhaustive — a `never`-typed default arm and a `Record<Union, true>` membership table — but the notification eligibility rules and the profile tab-kind validator both predate it and instead use `default` arms that return a falsy answer and a plain `string[]` of type names, so neither is tied to the union it is supposed to cover. Severity: 4/10

Existing Risk: 4/10 - A new notification event compiles, ships, and never reaches the feed because both of the eligibility switches fall through to a default that refuses it, and a new profile tab kind compiles and is then rejected on load with "type must be one of ..." for every profile that uses it — in both cases the build is green and the feature is simply inert.

Proposal Risk: 2/10 - Both dispatchers become compile-time complete, though the remaining hand-written membership lists elsewhere are untouched and the same gap can reappear wherever a new union is introduced without the idiom.

Proposal: The idiom is `unhandledClientMethod(message: never)` in `src/client-message.ts` and `unhandledRemoteFrame(type: never)` in `src/remote/frame-decode.ts`, paired with `CLIENT_FRAME_TYPES`/`SERVER_FRAME_TYPES` in `src/remote/protocol.ts` and `CAPABILITIES`/`NOTIFICATION_TOPICS` in `src/plugins/api.ts`, each with a comment explaining that keying by the union makes an omission a compile error. Two dispatchers do not use it. In `src/notifications.ts`, `NotificationEventType` has sixteen members and `shouldNotify` splits them across two switches — the first returns `true` for the eleven explicit events and ends `default: { break; }`, the second maps the five ambient events to config flags and ends `default: { return false; }` — so a seventeenth member falls through both to `false`; note that `notificationText` in the same file is already exhaustive (no default, and its `string` return type makes a missing case a compile error), which is what makes the inconsistency visible within one file. Replace the two `default` arms with a shared `never`-typed guard, splitting the union into an explicit-events table and an ambient-events table keyed `Record<Ambient, keyof NotificationConfig['events']>` so the second switch becomes a lookup. In `src/profile/schema.ts`, `TAB_TYPES` is a `string[]` listing eleven names that mirror the eleven arms of `ProfileTabFile` in `src/profile/types.ts`, and `PRESENTATION_TYPES` is a second hand-kept `Set` restating nine of them; derive both from the union with `Record<ProfileTabFile['type'], boolean>` tables — the boolean being whether that kind carries the flat presentation fields — and keep `tabProblems`'s message building its list from the table's keys so the wording does not move. `src/notifications.test.ts` covers `shouldNotify` per event but has no case asserting the union is fully covered, and has none at all for `plugin-failure`; add a case per member driven off the table. `src/profile/validate.test.ts` and `src/profile/file.test.ts` exercise `collectProfileProblems` and pin the current messages, so they must keep passing with no wording change.
