## development

* `src/file-navigator/moves.ts` implements undo/redo for file moves and pastes — `applyStackMove` (lines 50-93) and `applyStackPaste` (lines 165-202) branch across `overwrite-all`/`skip-conflicts` policies and partial success/failure, calling `rmSync(..., { recursive: true })` and `renameSync`/`copyItem` against real files — with no test file covering it; its sole caller `manager-history.ts` also has none, while the sibling `manager-batch.test.ts` only exercises the forward `moveMany`/`pasteMany`/`deleteMany` paths and every other module in `file-navigator/` has a colocated test. Add a test file for `moves.ts` covering the conflict-policy branches and partial-failure paths, following the temp-dir pattern already used in `manager-batch.test.ts`. Severity: **high**.
* `src/harness/command-parse.ts` has no colocated test file even though `parseHarnessCommand` and its helpers (`findFlagValue`, `splitWithClause`, `parseHarnessFlags`, `parseLabelSubcommand`, lines 15-107) parse flags, the `with <prompt>` clause, and `capture`/`transcript` subcommands across several distinct error-return paths, while 11 other files in `src/harness/` (e.g. `auto-approve.ts`, `busy-status.ts`, `capture-file.ts`) all have one. Add `command-parse.test.ts` covering the flag-parsing and error-return branches. Severity: **medium**.
* `src/protocol.ts` is 365 lines — nearly double the 200-line guideline in `ai/guidelines/code-guidelines.md` — and holds every tab-view field, RPC method params, and view type across the file-navigator, schedule, monitor, editor, and plugin domains in one `TabView`/`StateEvent`/`RpcCall` union (lines 84-363); it is the highest-churn file in the repo over the last 60 days (84 commits), so every new feature's RPC additions land in the same file. Split it into per-domain files (e.g. file-navigator RPCs, schedule RPCs, editor RPCs) re-exported from `protocol.ts` so unrelated features stop colliding on the same file. Severity: **medium**.
* `src/harness/manager.ts` duplicates a 12-argument positional parameter list for `spawnTab` (lines 154-158) between its two call sites, `open()` (line 127) and `openFromProfile()` (line 143) — several adjacent parameters share a type (`offline`/`autoApprove` both booleans, `model`/`effort` both optional strings), so a transposition of two adjacent args at either call site would compile silently. Introduce a `SpawnTabOptions` object to group these fields so the call sites can't drift out of argument-order sync. Severity: **medium**.
* Upgrade the xterm.js set — `@xterm/headless` 5.5.0 to 6.0.0 (a runtime dependency, `^5.5.0`), `@xterm/xterm` 5.5.0 to 6.0.0 and `@xterm/addon-fit` 0.10.0 to 0.11.0 (both declared as devDependencies but bundled into the web build by Vite, so they ship to users) — none of which the declared ranges can reach, so all three have to be widened together; they are versioned in lockstep and must move in one change. v6 has been out seven months, so the release is settled. Only three non-test files import them: `src/harness/screen.ts` (the headless terminal behind `HarnessScreenReader`), `web/src/useXterm.ts` (the shared `Terminal` + `FitAddon` setup that `HarnessTab`, `ShellTab`, and `TerminalCard` all go through), and `web/src/main.tsx` (which imports `@xterm/xterm/css/xterm.css`, a path the viewport rework may have moved). The loud breaking changes barely touch us — the removed `windowsMode` and `fastScrollModifier` options, the deleted Canvas renderer addon, and the relocation of `overviewRulerWidth` under `overviewRuler` are all unused here. The dangerous ones are silent: the viewport and scrollbar were rebuilt on VS Code's `base/` platform, the alt→ctrl arrow mapping was removed (the app hand-rolls its own key translation in `useXterm.ts`, including the `Shift+Enter` → `ESC`+`CR` sequence that `product/specs/shell.md` and `product/specs/harness.md` both document), and `src/harness/screen.ts` depends on two fragile details that need re-verifying rather than trusting — its `scrollback: 0` plus `allowProposedApi` buffer read, and the documented CommonJS default-import workaround that v6 may have changed by shipping ESM. This is behavior-sensitive: the headless terminal's rendered text is what drives busy/ready recognition, permission-gate detection, and auto-approve, so a translation change there is a silent misclassification of harness state rather than a red build — `product/specs/harness.md` (busy/ready status, screen capture), `product/specs/shell.md`, and `product/specs/harness-recording.md` hold the behavior that must survive. Effort is moderate and mostly verification rather than code; xterm.js publishes 6.0.0 release notes covering every breaking change. Resolve by running the `ai/tasks/hygiene/update-package-outside-range.md` task against `@xterm/xterm` at 6.0.0. Severity: **medium**.
* Upgrade `@agentclientprotocol/sdk` from 0.28.1 to 1.3.0 — a runtime dependency whose `^0.28.1` range cannot reach the 1.x line, so the range has to be widened. The gain is leaving a pre-1.0 pin of a protocol SDK: 1.0.0 shipped in June 2026 and three minors have landed since, carrying the protocol schema forward (v1.16.0), while 0.28.x receives none of it — an agent that has moved to a newer protocol version is the failure this eventually causes. The blast radius is small and concentrated: `src/acp/index.ts` and `src/acp/tools.ts` are the only non-test importers, using `ClientSideConnection`, `ndJsonStream`, `PROTOCOL_VERSION`, the `Client` interface, and the `ToolCallUpdate`/`PermissionOption`/`RequestPermissionOutcome` types. The SDK's big rewrite happened in 0.27.0, *before* the installed version, and 1.3.0 still exports `ClientSideConnection` (now carrying an `@deprecated` tag pointing at the fluent `client().connectWith()` API), `ndJsonStream`, and `Client`, so the upgrade itself should be close to mechanical; converting to the fluent API is a separate decision, not part of this item. The silent change to watch is `PROTOCOL_VERSION` — it is re-exported from the schema and its value moves with the schema release, so the version this project negotiates with the agent during `initialize` changes without any code change of ours. `product/specs/acp.md` describes the connection lifecycle, permission denial, and reply streaming that must behave identically afterwards; note that it also calls the feature an experimental, read-only MVP, which is why this rates low despite being a runtime dependency. Effort is small. Resolve by running the `ai/tasks/hygiene/update-package-outside-range.md` task against `@agentclientprotocol/sdk` at 1.3.0. Severity: **low**.
