* Translate ACP activity through one shared mapping for local and remote agent runs, and move the run's readiness wait into a shared helper so its untested failure paths get tests.

Existing Debt: The ACP-update-to-activity mapping exists twice with different rules, the local agent run forwarding every raw `sessionUpdate` kind with a JSON dump of its content while the remote host reduces updates to the five kinds the spec names with plain text, and the same local function hand-rolls a readiness race that duplicates the remote target's `abortable` and has no test on any failure branch. Severity: 4/10

Existing Risk: 4/10 - The agent monitor shows a local run's thoughts as `agent_thought_chunk` followed by raw JSON, plus update kinds the spec leaves out, while the same task run remotely shows clean text, and a regression in the readiness timeout, abort or empty-answer branch could hang an autonomous run or misreport its outcome with no test noticing.

Proposal Risk: 2/10 - Both hosts produce the spec's five activity kinds from one tested function and the readiness and failure branches are pinned, though local runs will stop showing update kinds they show today, which someone may have been reading.

Proposal: `product/specs/agent-command.md` says monitor activity includes reported message, thought, tool, plan and permission updates. `RemoteAcp.open` in `src/remote/serve-acp.ts` implements that with its private `activityKind` and a text extraction (string content, then `content.text`, then JSON), and `src/remote/serve-acp.test.ts` pins `agent_thought_chunk` becoming `thought`; the local `onActivity` in `executeAgentRun` (`src/agent/execute.ts`) instead passes `update.sessionUpdate` through unchanged and JSON-stringifies everything except text message chunks, and `AgentRun.reportActivity` in `src/agent/run.ts` and the activity entries of `AgentRunView` in `src/agent/types.ts` accept any string, which `web/src/plugins/agent-monitor/view.tsx` prints above the text. Move the mapping into a new `src/acp/activity.ts` exporting `acpActivity(update)` (returning `{ kind, text }` or `undefined`) and an `ACP_ACTIVITY_KINDS` const array, make `RemoteAcpActivityKind` in `src/remote/protocol-frames.ts` an alias of its type, use the array for the membership check in `decodeAcpActivity` in `src/remote/frame/decode-acp.ts` (dropping its `kind as RemoteAcpActivityKind` cast), narrow the activity kind on `AgentRunView`, and call it from both `RemoteAcp.open` and the local `onActivity`. In the same change, replace the readiness race in `executeAgentRun` and `abortable` in `src/agent/remote-target.ts`, which both race a promise against an abort signal and a 15-second timer with a hand-rolled deferred under a `prefer-promise-with-resolvers` suppression, with one `awaitReady(promise, signal, timeoutMs, timeoutMessage)` in a new `src/agent/readiness.ts`, and give the twice-written `Agent: sandboxing is disabled.` notice one helper. `src/agent/execute.test.ts` covers only success paths and `src/commands/agent.test.ts` mocks `executeAgentRun` out, so add fake-timer cases to `src/agent/execute.test.ts` for the readiness timeout, an abort while waiting, a connection error before and during the tool loop, the empty-answer failure, and a local thought chunk arriving as `thought` with plain text; add `src/acp/activity.test.ts` for the mapping itself and keep `src/remote/serve-acp.test.ts` and `src/remote/acp-session.test.ts` passing.


* Give the remote channel one pending-request primitive that owns the request id, the deadline, refusal while detached and settlement on close, and move the capture and agent-resolution trackers onto it.

Existing Debt: Each remote request and reply family keeps its own map, timer and close handling with no shared primitive behind them, so the five families already behave differently (capture has no deadline, agent resolution waits 15 seconds, session-state queries and ACP release are silently dropped while detached and wait out their timers) and every new family also has to add a case to the channel's `send()` refusal switch. Severity: 5/10

Existing Risk: 4/10 - `harness capture <name>` on a remote tab whose far side never answers waits until the channel closes with nothing on screen, and the next request family that forgets one of the three behaviors leaves a hung promise or a silent wait.

Proposal Risk: 2/10 - Capture and agent resolution share one tested tracker and capture gains a deadline, while the file-navigator port, the session-state query and ACP release keep their own bookkeeping until later increments move them.

Proposal: `CaptureRequestTracker` in `src/remote/channel/capture.ts` settles `undefined` on close and fails a request the channel could not send, but sets no timer, and its header still says requests are correlated by spawn id alone because the wire carries no separate request id, while the code keys by `request` and `src/remote/channel/capture.test.ts` tests overlapping requests by request id. `RemoteAgentRequests` in `src/remote/channel/agent-requests.ts` builds a hand-rolled deferred with a 15-second timer and rejects on `failAll`; `RemotePortRequests` in `src/file-navigator/remote/port-requests.ts` has per-operation deadlines; `askSessionState` in `src/remote/resume.ts` holds a single slot with a 30-second wait; and the ACP release in `src/remote/acp-session.ts` has its own 5-second timer. `RemoteChannel.send` in `src/remote/channel/index.ts` refuses only `filesystem-request`, `acp-open`, `acp-prompt` and `capture-request` while detached and drops every other frame silently. Add `src/remote/channel/pending-requests.ts` exposing `open(id, { deadlineMs?, onTimeout })`, `settle(id, value)`, `fail(id, reason)` and `settleAll(fn)` with unref'd timers, move `CaptureRequestTracker` and `RemoteAgentRequests` onto it without changing their public methods (which also removes one more `prefer-promise-with-resolvers` suppression), and correct the `capture.ts` header. Giving capture a deadline changes what `harness capture` reports for a silent far side (the live path in `src/harness/subcommands.ts` has no timeout, unlike the parked path's `DETACHED_CAPTURE_TIMEOUT_MS` in `src/harness/capture/remote.ts`), so make it its own step with a sentence in `product/specs/remote-server.md`. Covered by `src/remote/channel/capture.test.ts`, `src/remote/channel/agent-requests.test.ts` and `src/remote/channel/index.test.ts`; add a fake-timer case for the new capture deadline.


* Build every xterm terminal in the web client through one shared factory, so the harness, shell and recording terminals stop drifting apart on metrics, clipboard and theme handling.

Existing Debt: Terminal construction lives inside three React hooks instead of a framework-free factory in the shared terminal layer, so each tab type copied the parts it knew about and behavior has already split: only the harness terminal answers OSC 52 clipboard requests and remaps Shift+Enter and Alt+arrow keys, only the shell terminal follows theme switches, and all three re-read the same CSS variables with the same hard-coded fallbacks. Severity: 4/10

Existing Risk: 4/10 - A program in a remote or SSH shell tab that copies through OSC 52 silently copies nothing, harness and recording terminals keep the colors they mounted with after a theme change, and the next terminal fix lands in one of three places.

Proposal Risk: 2/10 - All three terminals share construction, metrics and clipboard handling, though key remapping and theme following still differ by tab type until someone decides which terminals should have them.

Proposal: `new Terminal(` appears in `useXterm` (`web/src/shared/terminal/useXterm.ts`), `useShellTerminal` (`web/src/plugins/shell/useShellTerminal.ts`) and `useAsciicastTerminal` (`web/src/plugins/asciicast/useAsciicastTerminal.ts`), each reading `--mono`, `--terminal-font-size` and `--terminal-line-height` with the same 13.5 and 1.2 fallbacks. Only `useXterm` registers the OSC 52 handler (through `osc52ClipboardText` in `web/src/shared/terminal/terminal/osc52.ts`, with a comment saying that without it a remote harness's copy silently does nothing) and applies `shiftEnterSequence` and `altArrowSequence` from `web/src/shared/terminal/terminal/keys.ts`, while only `useShellTerminal` installs a `MutationObserver` on `data-theme` to re-apply `shellTerminalTheme()` from `web/src/plugins/shell/shell-terminal-theme.ts`, even though shell tabs also run remote and SSH PTYs. Add a framework-free `createAppTerminal(container, options)` in a new `web/src/shared/terminal/app-terminal.ts` that reads the metrics once, constructs the `Terminal`, registers OSC 52 when a `copyText` option is given, installs the theme observer when a `theme` function is given, and returns the terminal with one `dispose()` that removes what it installed; use it in all three hooks, and publish it to the concrete plugins through `web/src/plugins/api.ts`, since they may import nothing else of the host's (an additive export, so `TAB_PLUGIN_API_VERSION` does not move). The shell tab gaining OSC 52 through its existing `copyText` capability is a visible change worth a line in `product/specs/shell-tab.md`; leave key remapping and theme following for harness and recording terminals as explicit follow-up decisions rather than switching them on here. Covered by `web/src/shared/terminal/useXterm.test.tsx`, `web/src/plugins/shell/useShellTerminal.test.ts`, `web/src/plugins/asciicast/useAsciicastTerminal.test.ts` (which pins the CSS reads and both fallbacks) and `web/src/shared/terminal/terminal/osc52.test.ts`; add `web/src/shared/terminal/app-terminal.test.ts` for the factory, including that `dispose()` disconnects the observer and the OSC handler.
