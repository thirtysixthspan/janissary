# bugs

## ready

* the unread badge should not be shown until the tab is no longer busy. For example, when a harness asks a permission prompt expecting a response from the user, that should trigger the unread flag, but if the auto approval cause the harness to continue, the flag should no longer be shown.

* Move focus off Submit with one Tab in a free-text question panel, instead of two

Existing Bug: In the free-text question panel the first Tab after the answer field lands on Submit and the very next Tab leaves focus on Submit, so a second identical press is needed to reach Cancel, where the spec promises Tab moves forward between the panel's buttons and wraps from the last back to the first. Severity: 4/10

Existing Risk: 3/10 - It costs one wasted keypress on every free-text question, and the panel is small enough that a user who has tabbed once usually types and presses Enter instead, so the stall is easy to walk past rather than notice.

Proposal Risk: 2/10 - Whatever replaces the seeded counter has to leave the approval panel's already-correct order intact, and a row that derives its position from real focus could put the first Tab out of the answer field somewhere other than Submit — a one-keypress difference the panel's own focus tests would show.

Proposal: The spec promises that "Tab moves focus forward between the panel's buttons (each approval option, or Submit, plus Cancel), wrapping from the last button back to the first instead of leaving the panel". Reproduce it against a scratch project directory with the app on a loopback address: in an agent tab type `question ask "Your name?"`, confirm focus is in the `Answer` field, then press Tab four times, reading `document.activeElement` after each. Expected: Submit, Cancel, Submit, Cancel. Observed: Submit, Submit, Cancel, Submit — the second press leaves focus on Submit. Reproduced in two consecutive panels in one session. The approval form is unaffected: `question approve "Pick a colour" red green blue` walks Cancel → red → green → blue → Cancel → red exactly as specified. The cause is the roving index `useAnswerButtons` keeps in `web/src/useAnswerButtons.ts`, which is seeded once and afterwards advanced only by its own handler. `QuestionPanel` in `web/src/QuestionPanel.tsx` calls `useAnswerButtons(2, 1)` for the ask form, so the row starts believing focus is on `Cancel` at index 1, but that panel puts initial focus in the `Answer` input through `autoFocus`, and the input is a sibling of the `.modal-actions` div the handler is attached to — so the first Tab is the browser's own traversal into `Submit` and never reaches the handler. The second Tab does reach it and computes `(1 + 1) % 2 === 0`, which is `Submit` again. Seed the ask row to index 0 so it matches the first button, or better, have `useAnswerButtons` derive the next index from whichever of its refs currently holds focus rather than from a separate counter, which also stops any other browser-default traversal into the row from desyncing it. `web/src/QuestionPanel.test.tsx` has a focus test for the ask form's initial field and a Tab-and-arrow cycle test for the approve form, but nothing walks Tab through the ask form's two buttons; a regression test should render an `ask` panel, focus the `Answer` field, press Tab to reach `Submit`, and assert that one further Tab reaches `Cancel`.

* Stop the command line accepting input while the route chooser is open, so the first Enter is not swallowed

Existing Bug: While the route chooser is open the command input still takes focus and text, and pressing Enter resolves the chooser instead of submitting what was typed, so the command the user just entered is not run and the chooser's highlighted route runs instead, where the spec promises the chooser is modal and the command input is disabled. Severity: 6/10

Existing Risk: 6/10 - Typing a command rather than picking a row is the natural answer to "which route?", so anyone who does it loses that command every time, and the wrong thing runs in its place — a shell command the user never chose, or a prompt sent to a live agent.

Proposal Risk: 4/10 - `useWindowKeys` claims every keystroke for whichever overlay is open, so an input that is disabled while the chooser holds the keyboard leaves a user who expected to type with no way back to the command line until they resolve or cancel, and the disabled state has to be released when the server reports `route: null`.

Proposal: The spec promises that the chooser "is **modal**: the command input is disabled while it is open" and that the overlay's own keys are "**Up/Down** move the selection, **Return** picks, **Escape** cancels". Reproduce it against a scratch project directory with the app on a loopback address: in an agent tab type `zzz qqq xxx`, which no recognizer claims confidently, and confirm a `.picker` titled `route: zzz qqq xxx` appears with `acp (agent prompt)` highlighted; then click the command line, type `notify typed-during-chooser`, and press Enter. Expected: the command line is disabled, so the text cannot be entered and the only thing Enter can do is pick the highlighted route. Observed: the textarea reports `disabled === false` and `readOnly === false` with the chooser open, the typed text lands in it verbatim, the chooser is still open afterwards, and Enter then closes the chooser and runs the chooser's route — the transcript gains a `zzz qqq xxx` prompt line followed by the agent's Markdown reply — while the command line still reads `notify typed-during-chooser` and the notification feed stays empty, so the typed command was neither run nor queued. Every other chooser promise holds in the same session: `acp (agent prompt)` is the highlighted row on open, ArrowUp and ArrowDown move the selection between `shell` and `acp (agent prompt)`, Return with an empty command line runs the highlighted route, Escape dismisses without running anything, and a click on a row runs that route as its explicit `shell …` form. The cause is that `CommandInput` in `web/src/agent-tabs/command-input/CommandInput.tsx` renders `CommandBarShell` without passing `disabled`, and `CommandBarShell` in `web/src/shared/command-bar/CommandBarShell.tsx` only forwards that prop to its `<textarea>` when a caller supplies it, so nothing ever disables it. `RouteChooser` in `web/src/pickers/RouteChooser.tsx` renders the overlay and nothing else, and `useRouteChooser` in `web/src/pickers/useRouteChooser.ts` keeps the open or closed `RouteChooserView` without exposing anything the command bar could bind to. Meanwhile `dispatchModalKey` in `web/src/useWindowKeys.ts` claims every keystroke while a `route` overlay is open and hands `Enter` to `handleRouteChooserKey` in `web/src/keyboard-handlers.ts`, so the key that would submit the command line is consumed at the window level before the textarea's own handler can act on it. Bind the open chooser to the command bar — pass `disabled` from `CommandInput` while `route` is non-null, and release it when the server reports `route: null` — so the documented modality is the real one rather than the overlay merely claiming keys. `web/src/pickers/RouteChooser.test.tsx` and the chooser cases in `web/src/useWindowKeys.test.ts` cover the overlay's own keys and neither renders the command bar, so nothing asserts the input's state while the chooser is open; a regression test should render both together, assert the textarea is disabled with a chooser open and enabled once `route` is null, and assert that text typed while it is open never reaches the server as a command.

* Reject a non-http scheme passed to open as an invalid address, instead of reading it as a file path

Existing Bug: `open file:///etc/passwd`, `open data:text/html,…` and `open javascript:alert(1)` are each treated as a relative file path and answered with `no such file` for a path mangled onto the working directory, where the spec promises any scheme other than `http` and `https` is rejected as an invalid address. Severity: 3/10

Existing Risk: 3/10 - Only a user who already knows the `page` keyword would try this, and the wrong message points at a nonexistent file rather than at the address they typed, so the fix that seems obvious — checking the file is really missing — sends them further down the wrong path.

Proposal Risk: 2/10 - Widening the test to any `scheme:` prefix also catches a local file whose name contains a colon, which is legal on disk, so the classification has to stay narrower than the URL grammar without losing the rejection.

Proposal: The spec promises that "Only `http` and `https` addresses are viewable; any other scheme (for example `javascript:`, `data:`, or `file:`) is rejected. An argument without a scheme and without the `page` keyword is treated as a file path, not a web address — the `page` keyword is what makes a bare address a web page." Reproduce it against a scratch project directory with the app on a loopback address, typing each into an agent tab: `open file:///etc/passwd`, `open data:text/html,<b>x</b>`, and `open javascript:alert(1)`. Expected: a message reporting the address is invalid, and no tab opened. Observed: each is resolved against the tab's working directory and answered `open: <project-dir>/file:/etc/passwd: no such file`, `open: <project-dir>/data:text/html,<b>x</b>: no such file`, and `open: <project-dir>/javascript:alert(1): no such file` respectively — the `file:` URL is even collapsed from `file:///etc/passwd` to `file:/etc/passwd` on the way. Nothing unsafe happens, because the resolved path stays under the project directory rather than reaching `/etc/passwd`, and the tab strip is unchanged; the `page` form does it right, with `open page javascript:alert(1)` answering `open: invalid URL "javascript:alert(1)"`. The cause is the classification line in `parseOpen` in `src/commands/open.ts`, which decides a target is a web address with `isPage || /^https?:\/\//i.test(target)`, so a target carrying any other URI scheme never reaches the web opener and falls through to the file-path branch. The scheme rejection the spec describes already exists in `normalizeWebUrl` in `src/openers/web-target.ts`, which returns `unsupported scheme in "<raw>"` for anything matching `^[a-z][a-z\d+\-.]*:` that is not `http:` or `https:` — it is simply never called for these inputs. Have the classifier treat a target that carries a URI scheme as a web address whatever the scheme is, so `normalizeWebUrl` produces the rejection, and keep a colon-bearing local path that is not a scheme on the file branch. `src/openers/web-target.test.ts` covers `normalizeWebUrl` directly and `src/commands/open.test.ts` covers the usage and `page`-keyword paths; neither asserts what a non-http scheme does without the keyword, which is the case that regressed, so a regression test should assert that `open file:///x` and `open javascript:1` are both answered as an invalid address and open no tab.

* Make `profile save` create the project profiles directory instead of failing with a raw ENOENT

Existing Bug: On a project that has never had a `profiles/` directory, `profile save <name>` fails with `Profile command failed: ENOENT: no such file or directory, open '<project-dir>/profiles/<name>.json.<uuid>.tmp'` and writes no profile, where the spec has the save capture the running session into `profiles/<name>.json` and names `initProfileDir` as what establishes that directory. Severity: 7/10

Existing Risk: 6/10 - Every fresh project fails on its first `profile save`, and the message names a temporary file rather than the missing directory, so the user has to guess that a plain `mkdir profiles` is the missing step before the whole feature becomes usable.

Proposal Risk: 3/10 - Creating the directory at startup puts a new top-level `profiles/` into every project directory, which some users will not want committed, and the save must still degrade cleanly when that directory is read-only rather than failing the way it does now.

Proposal: The spec promises that "Project profiles live in a top-level `profiles/` directory (`initProfileDir` in `src/main.ts`), kept separate from `.janissary/` so they are committable and are **not** cleared on launch", and that `profile save <name>` "Captures the running session into a single `profiles/<name>.json`". Reproduce it against a fresh scratch project directory with the app on a loopback address: open a file so there is something to capture (`newfile prof.md`), then type `profile save scratchprofile`. Expected: a saved-profile report naming the tabs captured. Observed: `Profile command failed: ENOENT: no such file or directory, open '/…/work/profiles/scratchprofile.json.5caf6ba8-db1b-4f06-ab3d-dd660fff4df9.tmp'.`, no file written, and `profile validate scratchprofile` then reporting `No profile named "scratchprofile".`. The counterfactual pins the cause: after `shell mkdir -p profiles` in the same session and with nothing else changed, the same save reports `Saved profile "scratchprofile": 1 editor tab, layout. Window size not captured (no window open).`, `profile validate scratchprofile` reports `Profile "scratchprofile" is valid.`, and `profile list` shows `scratchprofile` ahead of the built-ins. `initProfileDir` in `src/profiles.ts` only assigns `projectProfileDir` and `janissaryProfileDir` from their base directories and returns — it never creates either, so nothing at startup establishes the project directory. The save path goes through `saveProfile` in `src/profile/save/index.ts`, which hands the file to `atomicWriteFile` in `src/atomic-write.ts`; that writes `<file>.<randomUUID()>.tmp` next to the target and renames it, so with no `profiles/` directory the very first `writeFileSync` throws ENOENT, the temp file is removed, and the error propagates to the transcript. Create the project directory in `initProfileDir` (or have the save ensure it exists before writing), and keep reporting a write failure as a message that names the profile rather than the temp path. `src/profiles.test.ts` and the `src/profile/` suite all stage their fixtures by creating `profiles/` themselves — `src/profile/file.test.ts`, `manager.test.ts` and `validate.test.ts` each `mkdirSync(path.join(root, 'profiles'))` before writing — so nothing covers a project that has none; a regression test should point the profile directory at a fresh root and assert that `profile save` writes `profiles/<name>.json` without the directory having been made first.
