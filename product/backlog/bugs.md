* Keep Shift+Tab inside a pending question panel, on the answer buttons and the answer field

Existing Bug: The first Shift+Tab pressed in a pending question panel moves keyboard focus out of the panel and into the tab's command line — in both the approval and the free-text form, and from every button — where the spec promises it steps backward between the panel's buttons and wraps. Severity: 5/10

Existing Risk: 5/10 - Every keyboard user meets this the first time they reach for the backward key in a panel, nothing on screen says the panel lost focus, and because focus lands in the command line of a tab that is busy waiting for the answer, the next thing typed is queued as a command instead of answering the question.

Proposal Risk: 3/10 - The panel's own handler has to win over a capture-phase window listener without taking the chord away from the section cycling that listener exists for, and a fix claiming the chord more broadly than the panel's own controls would leave a keyboard user with no way out of a panel at all; the free-text form also has to keep Shift+Tab out of the answer field landing somewhere sensible.

Proposal: The spec promises "Shift+Tab moves backward the same way, wrapping from the first to the last" alongside Tab moving between the panel's buttons "instead of leaving the panel". Reproduce it against a scratch project directory with the app on a loopback address: in an agent tab type `question approve "Ship it?" yes no`, confirm `document.activeElement` is the panel's `Cancel` button, then press Shift+Tab. Expected: focus moves to `no`, the last option. Observed: focus leaves the panel and lands on the `textarea` inside `.command`, the tab's command line, and further Shift+Tabs stay there or cycle to another application section. Reproduced twice from `Cancel` and twice from the first option, then again in the free-text form, where Shift+Tab from `Cancel` and from the `Answer` field behave the same way. Plain Tab, ArrowLeft and ArrowRight all behave as specified from the same panels, so the chord is the only thing broken. The cause is `useSectionNav` in `web/src/useSectionNav.ts`, which registers its Shift+Tab handler on `globalThis` in the capture phase and stands down only when `isModalOpen()` is true or the event target matches `[data-claims-shift-tab]`. `QuestionPanel` in `web/src/QuestionPanel.tsx` renders `ModalDialog` with `modal={false}`, and `ModalDialog` in `web/src/shared/ModalDialog.tsx` renders no backdrop and never calls `useDialogKeyboard`, so `openModal()` in `web/src/shared/modal-open.ts` is never called for a question panel and `isModalOpen()` stays false. The capture listener therefore runs first, calls `preventDefault()` and `stopPropagation()`, and the panel's own handler — `useAnswerButtons` in `web/src/useAnswerButtons.ts`, attached to `.question-panel-options` and `.modal-actions` — never sees the key. The idiomatic fix is the escape hatch already built for this exact collision: mark the panel's focusable controls with `data-claims-shift-tab` as `web/src/editor/EditorTab.tsx` does for its buffer, and widen `claimsShiftTab` in `web/src/useSectionNav.ts` from `target.matches(...)` to a `closest(...)` walk so the attribute can sit on the row container instead of on every button and on the `Answer` input. `web/src/useAnswerButtons.test.ts` covers the backward move with Shift+Tab and `web/src/QuestionPanel.test.tsx` covers the forward cycle, but both render the panel with `useSectionNav` unmounted, so no test puts the two in one tree; a regression test should render the panel inside the app shell, focus `Cancel`, press Shift+Tab and assert focus is on the last option and still inside `.question-panel`, and a second should do the same from the `Answer` field.


* Move focus off Submit with one Tab in a free-text question panel, instead of two

Existing Bug: In the free-text question panel the first Tab after the answer field lands on Submit and the very next Tab leaves focus on Submit, so a second identical press is needed to reach Cancel, where the spec promises Tab moves forward between the panel's buttons and wraps from the last back to the first. Severity: 4/10

Existing Risk: 3/10 - It costs one wasted keypress on every free-text question, and the panel is small enough that a user who has tabbed once usually types and presses Enter instead, so the stall is easy to walk past rather than notice.

Proposal Risk: 2/10 - Whatever replaces the seeded counter has to leave the approval panel's already-correct order intact, and a row that derives its position from real focus could put the first Tab out of the answer field somewhere other than Submit — a one-keypress difference the panel's own focus tests would show.

Proposal: The spec promises that "Tab moves focus forward between the panel's buttons (each approval option, or Submit, plus Cancel), wrapping from the last button back to the first instead of leaving the panel". Reproduce it against a scratch project directory with the app on a loopback address: in an agent tab type `question ask "Your name?"`, confirm focus is in the `Answer` field, then press Tab four times, reading `document.activeElement` after each. Expected: Submit, Cancel, Submit, Cancel. Observed: Submit, Submit, Cancel, Submit — the second press leaves focus on Submit. Reproduced in two consecutive panels in one session. The approval form is unaffected: `question approve "Pick a colour" red green blue` walks Cancel → red → green → blue → Cancel → red exactly as specified. The cause is the roving index `useAnswerButtons` keeps in `web/src/useAnswerButtons.ts`, which is seeded once and afterwards advanced only by its own handler. `QuestionPanel` in `web/src/QuestionPanel.tsx` calls `useAnswerButtons(2, 1)` for the ask form, so the row starts believing focus is on `Cancel` at index 1, but that panel puts initial focus in the `Answer` input through `autoFocus`, and the input is a sibling of the `.modal-actions` div the handler is attached to — so the first Tab is the browser's own traversal into `Submit` and never reaches the handler. The second Tab does reach it and computes `(1 + 1) % 2 === 0`, which is `Submit` again. Seed the ask row to index 0 so it matches the first button, or better, have `useAnswerButtons` derive the next index from whichever of its refs currently holds focus rather than from a separate counter, which also stops any other browser-default traversal into the row from desyncing it. `web/src/QuestionPanel.test.tsx` has a focus test for the ask form's initial field and a Tab-and-arrow cycle test for the approve form, but nothing walks Tab through the ask form's two buttons; a regression test should render an `ask` panel, focus the `Answer` field, press Tab to reach `Submit`, and assert that one further Tab reaches `Cancel`.
