* Persist an agent's working directory as a path, so an agent brought back by relaunch gets a working shell

Existing Bug: From the second command in a tab onward the `cwd` written to `.janissary/state/<name>.json` is a blob of the shell's raw terminal output rather than a working directory, and an agent restored by `--relaunch` then cannot start a shell at all. Severity: 8/10

Existing Risk: 8/10 - Anyone whose login shell is zsh meets this on every `--relaunch`, and the agent comes back unable to run a single command until they open a new tab, with only a garbled line in the tab's header to hint at the cause.

Proposal Risk: 5/10 - The pwd answer shares its buffer with real command output, so debris removal that drops one line too many would leave a tab in the wrong directory, and silencing zsh's line editor changes what a promoted interactive program sees on its tty.

Proposal: The spec promises that "Each agent state file stores `name`, `dotColor`, `active`, `number` (the tab's position), `cmdHistory[]`, `log[]` (the full transcript), `cwd` (the shell's working directory), `context[]` (informational messages received from other agents), and `commandQueue[]`". Reproduce it with a scratch project directory and the default `interactiveShellDetection` on, under zsh: start the app, and in the root `janus` tab run `echo one`, wait for it to finish, then run `echo two`, and read `.janissary/state/janus.json`. Expected: `cwd` is the project's own path. Observed: after the first command it is correct, and after the second it is the string `padded` (the tail of the previous command's output), a newline, that command's `__JS_END_0_1790473374070__` sentinel, another newline, zsh's highlighted `%` prompt with its SGR escape codes, then `pwd`, then `echo "`, stored with its `\r\n` line endings and escape sequences intact; the tab's header row renders the same string in place of the working directory. The transcript shows the same debris on every command. Then stop the app, start it again with `--relaunch`, and run any command in the restored tab. Observed: the entry ends `(shell exited)`, the next command does the same, and the stored `cwd` never repairs itself, so the tab is dead for the rest of the run. Three things combine. `SEED_COMMAND` in `src/shell/pty-session.ts` is `"stty -echo 2>/dev/null; PS1=''; PS2=''"`, and zsh does not read `PS1` — it prompts with `PROMPT` — so the prompt stays and, with ZLE still active, the shell also redraws each input line it reads. `queryShellPwd` in `src/shell/index.ts` returns `buffer.slice(0, endIndex).trim()`, which is everything the shell printed before the `__PWD_…__` marker with no filtering, and from the second command onward that window holds the previous command's tail, its sentinel, the prompt, and the terminal's echo of the `pwd` line itself; `ShellManager.execute` passes that to `onPwd`, `ShellManager.run` hands it to `TabManager.setCwd`, `setCwd` in `src/tab/runtime-operations.ts` stores whatever it is given, and `buildAgentStateFromTab` in `src/tab/agent-state.ts` persists it as `cwd`. `stripShellSentinels` in `src/shell/sentinel-strip.ts` already knows how to remove exactly this debris, through `PWD_COMMAND_LINE` and `dropPwdDebris`, but it is wired only to restored remote output from `ShellManager.appendRestoredOutput`. The relaunch damage follows from that value: `ShellManager.getShell` calls `spawnFor`, which calls `spawnPtyShellFor` and hands the persisted `cwd` to `spawnPty` in `src/pty.ts`, which passes it to `pty.spawn` as the process working directory; a path that is not a directory cannot be entered, so the shell exits at once and never comes back. A scratch probe confirms it: `pty.spawn('/bin/zsh', ['--no-rcs'], { cwd: <that string> })` exits with code 1 and no output, while the same spawn with the real path is still running a second later. For a piped shell the same value is instead written as `cd "<blob>"` by `ShellManager.spawnFor`. Fix it by having `queryShellPwd` keep only the answer — the last path-shaped line before the marker — or by running the existing sentinel and pwd debris removal over the live result as well as the restored one, and by extending `SEED_COMMAND` so zsh is quiet too (`PROMPT=''`, `RPROMPT=''`, and ZLE off) while bash keeps `PS1`/`PS2`. Then guard the value on the way in and out: have `setCwd` keep only a string that is an existing directory, and have `spawnPtyShellFor` fall back to `process.cwd()` when the persisted `cwd` is not a directory, so a bad value can never again kill a restored shell. `src/shell/index.test.ts` exercises `queryShellPwd` only with a clean `/home/user\n__PWD_4_3000__\n` buffer, so a regression test should feed it a PTY-shaped buffer — leftover command output, a sentinel, a prompt, the echoed `pwd`, the path, then the marker — and assert the result is the bare path; a second should assert that a path-less buffer still yields `''`. `src/shell/pty-session.test.ts` asserts the seed string contains `stty -echo`, `PS1=''`, and `PS2=''` but nothing asserts the shell actually went quiet, so a test pinning `PROMPT`/`RPROMPT` in the seed would fail today. `src/shell/sentinel-strip.test.ts` already covers the debris removal, so wiring that routine into the live pwd result is covered by its existing cases once `queryShellPwd` uses it. re-observed on 2026-09-26: tab completion is the first thing a user notices, because every path relative to the tab's working directory stops completing and does so silently. In the root `janus` tab of a fresh instance, with fixtures `alpha.md`, `alps.md`, `beta.txt`, `docs/index.md` and `.hidden-note` in the tab's working directory and no shell command run yet, `be` + Tab completed to `beta.txt␣`, `docs/i` + Tab to `docs/index.md␣`, `d` + Tab to `docs/`, and `.h` + Tab to `.hidden-note␣`; then `echo one` and `echo two` were run, and the same four completions returned the line untouched with no candidate strip, while `~/home-a` + Tab still completed to `~/home-alpha.txt␣` because that path never consults the tab's `cwd`. The tab's metadata bar changed from `$root/` to `/…/temp/find-bugs/work __JS_END_1_1790475320882__ \x1b[1m\x1b[7m%… pwd echo "`, and `.janissary/state/janus.json` held the same blob in `cwd`. The mechanism is `completeFilePath` in `src/completion/fs.ts`: it hands the token to `splitToken` in `src/completion/helpers.ts`, whose `readdirSync` throws on the blob path, and the `catch` returns the line unchanged, so the failure is indistinguishable from "no match" to the user. re-observed on 2026-09-26: every `open` in the tab fails too, so no view tab can be reached at all once the blob is stored. In the root `janus` tab of a fresh instance whose project directory holds `notes.md` and `long-editor-file-name-here.txt`, run any one shell command and then `open notes.md`. Expected: a markdown view tab for `$root/notes.md`. Observed: no tab, and the transcript entry `open: /Users/anonymouscoward/dev/janissary/.janissary/workspace/e2etests/pwd` followed by `echo "/notes.md: no such file` — the blob resolved as a directory and the file lookup failed against it; `open long-editor-file-name-here.txt` fails the same way, while `files` (which takes no path) still opens. The blob reaches this path through the same `onPwd` → `setCwd` chain the entry already names, and `open`'s resolver joins its argument onto `managers.tab.cwdOf(label)`, so one corrupt `cwd` takes out path completion and every file-opening command in the same tab.


* Complete a bare `~` in the command line into the home directory, instead of dropping the tilde and completing a relative path

Existing Bug: Pressing Tab on a lone `~` replaces it with the home directory's own name as a relative path — `~` became `home/` under a home directory named `home` — where the spec promises "Supports tilde (`~`) expansion to the user's home directory." Severity: 5/10

Existing Risk: 5/10 - `ls ~<Tab>` and `cd ~<Tab>` are everyday gestures, and the line is silently rewritten to a sibling path that usually does not exist in the tab's working directory, so the command then fails and the user has to delete the wrong text and retype the tilde.

Proposal Risk: 2/10 - Correct expansion makes the home directory's own entries the candidates where today its parent's are, so a home holding nothing but dotfiles would offer nothing at all until a dot is typed, which is a limitation rather than the wrong path.

Proposal: The spec promises that path completion "Supports tilde (`~`) expansion to the user's home directory." Reproduce it in the root `janus` tab of an instance whose working directory holds `alpha.md`, `album.md`, `alps.md`, `beta.txt`, `docs/index.md`, `zeta-one/`, `zeta-two/`, `.config/` and `.hidden-note`, and whose `HOME` holds `home-alpha.txt`, `home-bravo/`, `home-cassidy.md`, `home-celeste.md`, `mid-apple.txt`, `mid-banana.txt`, `zebra.txt` and `.zebra.txt`; type `~` and press Tab. Expected: the home directory's entries, with the tilde intact — `~/` + Tab does exactly that, giving `~/home-` and a candidate strip of `home-alpha.txt  home-bravo`. Observed: the line becomes `home/`, the home directory's base name with a trailing slash and no tilde, and the candidates come from the home directory's *parent*; reproduced three times on two fresh instances, and the result is the same however many entries the home directory holds. On a machine where the working directory has no sibling of that name, `~` + Tab finds nothing at all and simply does nothing. `~/home-a` + Tab, `~/home-b` + Tab, `~/mid` + Tab, `~/z` + Tab, `~/.z` + Tab, `~/home-bravo/n` + Tab and `/etc/host` + Tab all complete correctly, so only the token with no slash of its own is affected. Two lines cause it. `splitToken` in `src/completion/helpers.ts` expands a leading `~` to `homedir() + token.slice(1)` and then splits that expansion at its last slash, so a bare `~` yields the home directory's *parent* as the directory to list and the home directory's base name as the partial, confirmed by calling it directly: `splitToken('~', cwd)` is `{ dir: '/Users', base: 'anonymouscoward' }`. `completeFilePath` in `src/completion/fs.ts` then rebuilds the token from `typedDirPrefix = token.slice(0, token.length - base.length)`, which is `slice(0, -n)` for a bare tilde and so yields `''` — the tilde is gone before the completed name is appended. Expand the tilde in `splitToken` against the *typed* slash instead of the expanded one: a token that starts with `~` and contains no further slash should give `{ dir: homedir(), base: token.slice(1) }`, and `completeFilePath` should rebuild the token from the prefix `splitToken` reports rather than from a length subtraction over the expanded path, so a bare `~` comes back as `~` plus the completed name. `src/completion/helpers.test.ts` covers `splitToken` for a bare name, a last-slash token, a trailing slash, an absolute path, a bare `/` and `~/proj`, but never a bare `~`; `src/completion/index.test.ts` runs the same six fixture shapes through `completeCommandLine` with a real temporary directory and does not reach the tilde at all. A regression test should assert that `splitToken('~', cwd)` lists the home directory rather than its parent and that `completeCommandLine('~')` returns a `newInput` of `~` followed by the completed entry, plus a second case for a home directory holding one visible entry so the trailing `/` is covered.


* Make Tab complete the token on a continuation line of a multi-line command, as it does on the first

Existing Bug: Tab does nothing on the second and later lines of a command typed with Shift+Enter, where the spec promises that "When the `Tab` key is pressed, the shell attempts to complete the token immediately preceding the cursor" and the same token on the first line completes normally. Severity: 5/10

Existing Risk: 5/10 - Anyone writing a command over two lines gets a dead Tab on every continuation line and types paths out by hand, and because the failure is silent it reads as "Tab is broken" rather than "this line is not a completion context".

Proposal Risk: 2/10 - Once the server breaks tokens on newlines, every handler sees a continuation line as a real argument position, so a command split across lines starts completing arguments it silently ignored before, which is the intended reading but a behaviour change a command with a label-shaped continuation would notice.

Proposal: The spec promises that "When the `Tab` key is pressed, the shell attempts to complete the token immediately preceding the cursor", and the token immediately preceding the cursor on a continuation line is the one after the newline. Reproduce it in the root `janus` tab of an instance whose working directory holds `alpha.md`, `alps.md`, `beta.txt` and `docs/index.md`: type `ls`, press Shift+Enter, type `do`, press Tab. Expected: `docs/`, which is what the same `do` completes to on the first line. Observed: the line stays `ls\ndo`, no candidate strip appears, and Tab cannot be pressed into usefulness — the second press leaves the line exactly as the first did. The same happens for `cat alpha.md`, Shift+Enter, `be` (expected `beta.txt␣`, observed unchanged), and it is not only paths: `msg janus` on the first line and `n` on the second completes nothing either, because the argument context is lost along with the token. Reproduced five times across two fresh instances, each with an untouched tab working directory, where `d` + Tab on one line returned `docs/` in the same session. The two sides disagree about where a token starts. `handleTabCompletion` in `web/src/agent-tabs/command-input/command-completion.ts` takes the text after the last of `' '`, `'\t'` and `'\n'`, so the client treats a continuation line as its own completion context and asks the server to complete `do`. `readCompletionCursor` in `src/completion/cursor.ts` computes `tokenStart` from the last `' '` and `'\t'` only, so the server's token for that same request is `\ndo` and its `preceding` is empty; no handler matches an empty command, and `completeFilePath` in `src/completion/fs.ts` looks for a directory entry beginning with a newline, finds none and returns the line unchanged. Confirmed by calling the built function directly: `readCompletionCursor('ls\ndo', 5)` reports `tokenStart: 0`, `token: 'ls\ndo'`, `preceding: []`, while `completeCommandLine('ls\ndo')` returns the line untouched. Add `'\n'` to the boundary scan in `readCompletionCursor` so the token and the argument position both come from the continuation line; no client change is needed, since the client's own token slice and its guard against completing an empty token are already right. `src/completion/cursor.test.ts` covers a space boundary and a tab boundary and should gain a newline case asserting the token and the `preceding` words of a continuation line, and `src/completion/index.test.ts` should gain a case running `completeCommandLine('ls\ndo')` against its real temporary directory and asserting `docs/index.md`-style completion; on the client, `web/src/agent-tabs/command-input/command-completion.test.ts` and the "does not attempt completion for an empty token at the start of a new line" case in `web/src/agent-tabs/command-input/CommandInput.test.tsx` already pin the half that works.

* Keep the whole name a user typed for `agent <name>`, instead of cutting it to the tab strip's display length

Existing Bug: `agent alpha-bravo-charlie` opens a tab named `alpha-bravo-char` — the name is truncated to 16 characters with no ellipsis, in the focused tab as well as an unfocused one, and the truncated text becomes the tab's identity. Severity: 6/10

Existing Risk: 6/10 - Anyone who names agents after what they do opens a tab they cannot address by the name they typed, and the first refusal they meet quotes a name they never wrote; two names that share a first 16 characters collide, so the second launch is refused for a reason invisible in what they typed.

Proposal Risk: 3/10 - With the name no longer clipped, the launch-name check, the workspace folder, the state file, and the `name-2` suffix path all carry up to 50 characters instead of 16, so a path component grows and a user who lowered `tabNameMaxLength` to tidy the strip starts seeing full names in routing messages and refusals.

Proposal: The spec promises that "`agent <name>` creates a tab with the given name (always lowercased)", and separately that a long name is a display concern — "A tab name longer than its display limit is shortened with a trailing `…`", "The active tab uses `activeTabNameMaxLength`, which defaults to 50 characters, so focusing a tab reveals more of a long name", and "File-backed tabs keep the complete filename in their tab state and apply these limits only while rendering the strip." Reproduce it with a scratch project directory that is its own git repository — a default `agent` clones the project's `origin`, so point that at a small local fixture repository — and put a file named `long-editor-file-name-here.txt` in the project directory: start the app and run `agent alpha-bravo-charlie` in the root `janus` tab. Expected: a tab labelled `alpha-bravo-charlie`, shown in full while it is focused and as `alpha-bravo-cha…` when it is not. Observed: a tab labelled `alpha-bravo-char` — exactly `name.slice(0, 16)`, no ellipsis — in both states; its readiness line reads `Agent "alpha-bravo-char" ready. (workspace: $root/workspace/alpha-bravo-char)`, its state file is `.janissary/state/alpha-bravo-char.json`, and its clone is `.janissary/workspace/alpha-bravo-char`. The same strip shows the display path working: `open long-editor-file-name-here.txt` gives a tab reading `long-editor-file-name-here.txt` while focused and `long-editor-fil…` while not, so the limit and the ellipsis are applied correctly for a file-backed tab and skipped entirely for a typed agent name. The typed name is then unroutable and unlaunchable. `close alpha-bravo-charlie` in the `janus` tab prints `No tab named "alpha-bravo-charlie".`, and `agent alpha-bravo-charlot` — a different, free name — is refused with `Cannot launch "alpha-bravo-char": a tab named "alpha-bravo-char" is already open.`, quoting a name the user never typed. Reproduced on three fresh instances. The cause is `nameFrom` in `src/agent/commands.ts`, whose last expression is `words.slice(1).join(' ').toLowerCase().slice(0, getConfig().tabNameMaxLength)`: it applies the strip's inactive *display* budget to the stored name, and both `parseAgentCommand` and `resolveAgentName` build the tab's label from it. `tabNameMaxLength` is a display value — `src/config.ts` documents it as "which only truncates the tab strip's *display* label", and the strip applies it in `truncateTabLabel` in `web/src/tab-label.ts` via `TabItem` — so nothing downstream expects a clipped label. Drop the `slice` from `nameFrom` and let `truncateTabLabel` do the display work the spec describes; if a hard cap on the label is genuinely wanted, it belongs to a separate limit applied to the label rather than to the display length, and it should be enforced where the label is created so `agents.md`'s `Cannot launch "<name>"` lines quote what the user typed. The truncation is deliberate and pinned, so this is a decision to overturn rather than a slip: `src/commands/agent.test.ts` has a case per entry point named "truncates an explicit name to the configured max length" and "truncates the name to the configured max length", both asserting `parseAgentCommand('agent abcdefghijklmnopqrstuvwxyz')` and `resolveAgentName` return `abcdefghijklmnop` with the comment "16 chars, the default tabNameMaxLength", and both have to change with it. Replace them with a case asserting the whole lowercased string survives, and add one to `src/launch-name/local.test.ts` asserting `agent alpha-bravo-charlie` and `agent alpha-bravo-charlot` resolve to distinct labels rather than colliding on the first 16 characters. `web/src/tab-label.test.ts` already covers the display truncation, including the ellipsis budget, so nothing there needs to change.
