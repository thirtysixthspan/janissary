* Show the `<message>` placeholder in the bare `notify` usage reply in the shell tab's transcript

Existing Bug: Typing bare `notify` in a shell tab renders the reply as `Usage: notify .` instead of `Usage: notify <message>.`, dropping the angle-bracket placeholder. Severity: 3/10

Existing Risk: 2/10 - A user who omits the message gets a usage line that no longer names the argument it asks for, so the reply stops working as a hint on the one path where it is the only feedback; every other usage reply is unaffected.

Proposal Risk: 2/10 - Loosening the literal-usage matcher to accept leading whitespace could send other replies that merely begin with a blank line down the literal path and change their markdown rendering; a regression test over the leading-newline case keeps that contained to this shape.

Proposal: The spec promises in `product/specs/application-commands.md` that "The same is true of every single-line `Usage:` reply: the renderer treats it as command text rather than Markdown, so placeholders such as `<path>` and `<prompt>` survive alongside the flags around them." Reproduce on a freshly built app launched against scratch state: type `notify` with no message into the shell tab's command bar and read the reply beneath the echoed line. Expected: `Usage: notify <message>.`. Observed: `Usage: notify .`, with the whole `<message>` token gone. In the same build `tab focus` shows `Usage: tab focus <name>.` and `commands nope` shows `Usage: commands [enable|disable [agent|global] <command>].`, both with placeholders intact, so the defect is specific to replies that arrive with a leading newline. A captured WebSocket `rpc-reply` for the bare `notify` dispatch carries `{"dispatched":true,"output":"\nUsage: notify <message>."}`: the server sends the right text prefixed by a newline. The `run` function in `src/commands/notify.ts` appends the command echo as an entry with empty `output` and then appends the usage as a second entry with empty `input`; `executeAndCapture` in `src/capture/execute-and-capture.ts` collects each appended entry's `output` and `dispatchInTab` in `src/command/manager.ts` joins them with `\n`, which produces that leading newline. On the client, `literalUsage` in `web/src/shared/transcript/markdown.ts` gates on `/^Usage: [^\n]*\n?$/`, so a reply starting with `\n` is rejected, `marked` reads the bare `<message>` as an HTML tag, and `DOMPurify` drops it. Make `literalUsage` ignore leading and trailing whitespace when deciding a reply is a single-line usage message, escaping the angle brackets in the trimmed content while leaving the surrounding whitespace alone, so a leading newline from a multi-entry capture no longer defeats it. Attaching the usage to the echo entry in `src/commands/notify.ts` instead would work too, but the client-side change also covers any other command that appends usage as a second entry. `web/src/shared/transcript/markdown.test.ts` covers placeholder survival for single-line usage replies and `src/commands/notify.test.ts` covers the bare-command path; a regression test should render `\nUsage: notify <message>.` through `renderMarkdown` and assert the visible text is `Usage: notify <message>.`, and a shell-tab test should assert that exact text appears after a bare `notify`.

* Show the `<address>` placeholder in the shell command's unknown-option usage reply

Existing Bug: Typing `shell --bogus` renders the reply as `Unknown option "--bogus". Usage: shell [name] [-w|--workspace|--no-workspace] [--offline] [on ] [in group <name|id>]`, dropping the `<address>` placeholder named by the spec. Severity: 3/10

Existing Risk: 2/10 - A user who mistypes a shell flag gets a usage line whose `[on ]` slot is blank, so the hint no longer names the remote-address argument; the rest of the command is still readable.

Proposal Risk: 2/10 - Escaping angle brackets in a usage segment embedded after other text could change rendering of unrelated replies that happen to mention `Usage:` mid-line; a regression test over the prefixed form keeps the change to that shape.

Proposal: The spec states in `product/specs/shell-tab.md` that an unknown option is refused with `Unknown option "<word>". Usage: shell [name] [-w|--workspace|--no-workspace] [--offline]` followed by `[on <address>]` on the next line, so the user should see the `<address>` placeholder. Reproduce on a freshly built app started against scratch state: type `shell --bogus` into the shell tab's command bar and read the reply beneath the echoed line. Expected: the full usage with `[on <address>]` visible. Observed: `[on ]`, and the captured HTML is `<p>Unknown option "--bogus". Usage: shell [name] [-w|--workspace|--no-workspace] [--offline] [on </p><address>] [in group &lt;name|id&gt;]<p></p>\n</address>` — `<address>` became a real HTML element that split the paragraph, while `<name|id>` survived because `|` is not a valid tag character. By contrast `shell on` alone renders `Usage: on <[user@]host[:path]>.` intact, because that reply starts with `Usage:`. The server text is correct: `SHELL_USAGE` in `src/plugins/shell/parse-argument.ts` is the single-line string with `[on <address>]`, and `parseShellArgument` in that file prefixes it with `Unknown option "--bogus". ` when returning the error. On the client, `literalUsage` in `web/src/shared/transcript/markdown.ts` gates on `/^Usage: [^\n]*\n?$/`, so a reply that only contains a usage sentence after a prefix is not escaped; `marked` then reads `<address>` as an HTML tag and `DOMPurify` drops it. Apply the literal escaping to a single-line `Usage:` segment wherever it occurs in the reply, not just at position zero, while keeping the existing whole-line fast path; alternatively emit the usage on its own line in the rejection so the current matcher applies. This is separate from the existing `notify` entry: that reply begins with a newline, so its proposed leading-whitespace relaxation would not fix this one, which begins with `Unknown option`. `src/plugins/shell/parse-argument.test.ts` asserts the exact server string and `web/src/shared/transcript/markdown.test.ts` covers literal-usage rendering; a regression test should render a prefixed usage reply containing `[on <address>]` and assert the visible text keeps the placeholder, and a shell-tab test should assert the same for the rendered `shell --bogus` reply.

* Show `open` errors in the active shell tab when a file is missing or an address is invalid

Existing Bug: Commands routed through the file opener report their errors only into the transcript log, so `open missing.txt`, `open javascript:alert(1)`, and `video notes.md` produce no visible reply at all in a shell tab. Severity: 6/10

Existing Risk: 5/10 - A mistyped path, an unsupported URL scheme, or a wrong media type fails silently, so the user has no explanation and can only guess whether the command ran.

Proposal Risk: 3/10 - Routing these messages through the command reply could duplicate lines in transcript-style tabs that already render appended log entries; a regression check should cover both a shell tab and a transcript view.

Proposal: The spec promises in `product/specs/open.md` that errors are "surfaced before any opener runs — in the active tab," including "Unviewable or malformed web address — a message reporting the address is invalid" and "File does not exist — a not-found message", and `product/specs/open.md`'s video section says a non-video file "is reported rather than opened". Reproduce on a built app started against scratch state holding `notes.md`: from the launch shell type `open missing.txt`, then `open javascript:alert(1)`, then `video notes.md`. Expected: a message under each echoed line naming the missing path, the invalid URL, and the non-video file. Observed: the echo and prompt only; the phrase appears nowhere in the page body, the notifications feed is empty, and no tab opens. A captured WebSocket trace shows the server does produce the text: a `tab-view-updated` frame carries a buffer line `open: <abs path>/missing.txt: no such file`, while the matching `rpc-reply` is `{"dispatched":true,"output":""}`. As a control, `play notes.md` renders `play: notes.md: not a playable file` correctly in the same build. The `note` callback in `buildContext` and the missing-file and pinned-opener refusals in `openOne` in `src/open/file-manager.ts` append transcript entries with `managers.tab.append` and no invocation id; `executeAndCapture` in `src/capture/execute-and-capture.ts` filters `entry:appended` events by invocation id, so `dispatchInTab` in `src/command/manager.ts` returns an empty `output`. The shell tab's submit path in `web/src/plugins/shell/useShellSubmit.ts` renders that RPC output through `writeShellReply` in `web/src/plugins/shell/write-shell-reply.ts` and does not render the tab's `bufferLines` in its PTY, so the appended error is invisible. The invalid-URL error reaches the same dead end through `capabilities.note` in `src/plugins/page/activate.ts`. Carry the invocation id through these error appends, using the same command-output path that makes `play` visible, or return the error text as the command's output so `executeAndCapture` collects it; do not substitute a notification, since the spec keeps only the unsupported-extension error there. `src/controller.test.ts` already asserts these messages exist in tab text server-side; a regression test should assert the visible terminal reply in a shell tab for at least a missing file and an invalid URL.

* Suppress consecutive duplicate commands in a shell tab's own history picker

Existing Bug: Running the same command twice in a row in a shell tab lists it twice in that tab's Ctrl+R history picker. Severity: 2/10

Existing Risk: 2/10 - A repeated command takes two rows in the picker and reads as two distinct invocations, but nothing is lost and the command itself still works.

Proposal Risk: 2/10 - Deduping the shell's client-side history could hide a deliberate repeat a user expects to recall; a test with both immediate repeats and repeats separated by another command keeps the change to consecutive duplicates only.

Proposal: The spec states in `product/specs/history.md` that "If a command matches the last entry in the tab's history, it is not appended again." Reproduce on a freshly built app started against scratch state: from the launch shell type `notify dupcmd`, press Enter, type the same line again and press Enter, then type `notify othercmd` and press Enter; press Ctrl+R and read the rows. Expected: `notify dupcmd` once, then `notify othercmd`. Observed: `notify dupcmd`, `notify dupcmd`, `notify othercmd`. A captured trace confirms the server's tab state is not the source of the extra row: `cmdHistory` arrives empty in the state frames, because the shell tab's Ctrl+R is claimed by the shell plugin and opens `ShellHistoryPopup` (`web/src/plugins/shell/ShellHistoryPopup.tsx`) over the client-side `sent` list, not the generic picker fed by `getRecentHistory` in `web/src/pickers/recent-history.ts` (which does dedupe globally). `ShellTab.tsx` adds command-bar lines through `appendShellHistory` in `web/src/plugins/shell/shell-history.ts`, and `useTerminalCommandHistory.ts` uses the same helper for terminal commands; that helper currently only trims the line and appends it, so it never compares against the previous entry. The server-side equivalent, `recordHistory` in `src/tab/history.ts`, already skips a repeat with `tab.cmdHistory.at(-1) !== trimmed`. Make `appendShellHistory` return `previous` unchanged when `entry === previous.at(-1)`, preserving its existing empty-line handling, so the shell's own history follows the same rule as the tab history. `web/src/plugins/shell/shell-history.test.ts` already covers trimming and empty lines; extend it with an immediate-repeat case and add a shell-tab check that two submissions of one line produce a single picker row, plus a separated-repeat case that keeps both rows.

* Strip `##` command comments before a shell-bar line is recorded or run

Existing Bug: A shell tab's command bar sends `##` comments through verbatim, so `## note ## notify x` produces `zsh: command not found: ##` instead of running `notify x`. Severity: 5/10

Existing Risk: 4/10 - A documented way to prefix or trail a command with a note fails on the main command surface, leaving a confusing shell error and raw comment text in the tab's history.

Proposal Risk: 3/10 - Stripping in a shared dispatch path could alter lines where `##` is legitimately shell text, such as inside quotes or an expansion; tests should cover quoted and mid-line cases before changing the rule.

Proposal: The spec says in `product/specs/comments.md` that "Before a submitted command is saved to history or executed, `##`-delimited comments are stripped from it by `stripComments`", with a terminated comment removed wherever it appears and an unterminated one removed from `##` to end of line, and that a line stripped to empty is discarded. Reproduce on a built app started against scratch state: in the launch shell type `## note ## notify stripped-test` and press Enter, then `notify tail ## drop-this`, then `## only comment ##`. Expected: a toast for `stripped-test`, a toast for `tail` with the trailing comment gone, and no output for the comment-only line; history should hold the stripped commands. Observed: the terminal shows `zsh: command not found: ##` for the first and third lines, the second toast reads `tail ## drop-this`, and the shell history picker lists all three raw lines including the `##` text. The helper itself is correct: `stripComments` in `src/tab/utils.ts` has direct unit coverage in `src/tab/index.test.ts`, and `recordHistory` in `src/tab/history.ts` calls it for the CLI path. The web shell's submit path in `web/src/plugins/shell/useShellSubmit.ts` sends the unmodified line as the `dispatch` RPC, and `CommandManager` in `src/command/manager.ts` records and dispatches it without ever calling `stripComments`, so the shell receives `##` as a command. Apply the strip in the shared command-manager entry points before history recording and dispatch, or at minimum in the shell submit path, keeping the existing whitespace-collapse and empty-input behavior. A regression check should drive a shell tab with a prefixed comment, a trailing unterminated comment, and a comment-only line, and assert both the visible command result and the stripped history rows.
