## development

* Make the window shortcuts work while an editor tab holds the keyboard focus

Existing Bug: Every shortcut the window key handler owns is dead while an editor tab has focus — Cmd+Shift+[ and Cmd+Shift+] do not switch tabs, Ctrl+G opens no tab navigator, Ctrl+R no history picker, Ctrl+E no command queue, Cmd+P no Quick Open, Cmd+T no agent tab, and Ctrl+Left / Ctrl+Right do not reorder the tab — while the same chords work from every other tab. Severity: 6/10

Existing Risk: 6/10 - Every editor session is affected, and nothing says so: Shift+Left/Right and Shift+Tab are supposed to be selection and outdent inside the editor, so a user whose shortcut does nothing concludes the chord is not there rather than that the tab stole it, and the one chord the editor spec names as the replacement for Shift+arrows is among the dead.

Proposal Risk: 4/10 - Letting the window handler see editor keydowns also lets it see the editor's own, so every overlap has to be settled deliberately — Ctrl+Left must keep meaning line-start in the buffer rather than reorder the tab, Ctrl+P and Ctrl+N must keep scrolling the buffer rather than the transcript, and Escape must keep collapsing a multiple selection instead of resetting a scroll position the editor does not have.

Proposal: The spec promises that "switching tabs while the editor has focus uses Cmd+Shift+[ / Cmd+Shift+] instead (see Tabs), so the horizontal and vertical arrow pairs behave consistently", that "Cmd+P | Open the Quick Open file finder from any focused tab", that "Ctrl+G | Open the fuzzy tab navigator", and that an editor tab's close confirmation appears when the close comes from "the Cmd+W / Ctrl+W keyboard shortcut"; the file navigator's own keyboard section states the contrast, that chords "are not captured by the tree and reach the normal window-level bindings instead". Reproduce it against a scratch project directory holding a text file, with the app on a loopback address: run `edit alpha.txt`, confirm keyboard focus is in the editor's buffer, then press each chord in turn and watch the tab strip and the overlay area. Expected: Cmd+Shift+] activates the next tab, Ctrl+G opens a `.picker` titled `nav`, Ctrl+R one titled `history`, Cmd+P one titled `quick-open`, Cmd+T adds a new agent tab, and Ctrl+Left / Ctrl+Right move the editor tab one position in the strip. Observed: every one of them leaves the tab strip byte-identical and opens no overlay — measured on eleven chords, with `document.activeElement` asserted to be the editor's `textarea.editor-textarea` before each press. The same chords from the root `janus` tab in the same session all work: Ctrl+Right reorders the strip, Ctrl+G opens the `nav` picker with the rows listed, Cmd+T adds a pool-named agent tab. Cmd+W is the one chord that survives, and it raises the editor's unsaved-changes dialog with `Save (y)` selected — which is the clue to the cause. `onKeyDown` in `web/src/editor/useEditorInteractions.ts` calls `event.stopPropagation()` on its first line, unconditionally and with no comment, before it decides whether the key is even one of its own. That kills the native event's propagation past the React root, and `useWindowKeys` in `web/src/useWindowKeys.ts` listens on `globalThis` in the bubble phase, so it never runs. `useCmdW` in `web/src/useCmdW.ts` registers the same event with `{ capture: true }`, which is why Cmd+W is unaffected. Fix by not stopping propagation for keys the editor did not claim — the handler already returns early for an action it does not recognise, and `preventDefault` already covers what the editor does own — and then settle the overlaps the spec gives the editor explicitly, so `keys.ts` stays the single place that says what the buffer binds. A regression test belongs beside `actionForKey`: assert that a keydown the editor does not bind still reaches a window-level listener, which no test covers today (`web/src/editor/useEditorInteractions.ts` has no test file, and nothing under `web/src/editor/` asserts on `stopPropagation`). `web/src/keyboard-handlers.test.ts` covers the window side and would need a case per chord the editor must not shadow.
