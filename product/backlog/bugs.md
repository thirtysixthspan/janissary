# bugs

## ready

* Make `profile save` create the project profiles directory instead of failing with a raw ENOENT

Existing Bug: On a project that has never had a `profiles/` directory, `profile save <name>` fails with `Profile command failed: ENOENT: no such file or directory, open '<project-dir>/profiles/<name>.json.<uuid>.tmp'` and writes no profile, where the spec has the save capture the running session into `profiles/<name>.json` and names `initProfileDir` as what establishes that directory. Severity: 7/10

Existing Risk: 6/10 - Every fresh project fails on its first `profile save`, and the message names a temporary file rather than the missing directory, so the user has to guess that a plain `mkdir profiles` is the missing step before the whole feature becomes usable.

Proposal Risk: 3/10 - Creating the directory at startup puts a new top-level `profiles/` into every project directory, which some users will not want committed, and the save must still degrade cleanly when that directory is read-only rather than failing the way it does now.

Proposal: The spec promises that "Project profiles live in a top-level `profiles/` directory (`initProfileDir` in `src/main.ts`), kept separate from `.janissary/` so they are committable and are **not** cleared on launch", and that `profile save <name>` "Captures the running session into a single `profiles/<name>.json`". Reproduce it against a fresh scratch project directory with the app on a loopback address: open a file so there is something to capture (`newfile prof.md`), then type `profile save scratchprofile`. Expected: a saved-profile report naming the tabs captured. Observed: `Profile command failed: ENOENT: no such file or directory, open '/…/work/profiles/scratchprofile.json.5caf6ba8-db1b-4f06-ab3d-dd660fff4df9.tmp'.`, no file written, and `profile validate scratchprofile` then reporting `No profile named "scratchprofile".`. The counterfactual pins the cause: after `shell mkdir -p profiles` in the same session and with nothing else changed, the same save reports `Saved profile "scratchprofile": 1 editor tab, layout. Window size not captured (no window open).`, `profile validate scratchprofile` reports `Profile "scratchprofile" is valid.`, and `profile list` shows `scratchprofile` ahead of the built-ins. `initProfileDir` in `src/profiles.ts` only assigns `projectProfileDir` and `janissaryProfileDir` from their base directories and returns — it never creates either, so nothing at startup establishes the project directory. The save path goes through `saveProfile` in `src/profile/save/index.ts`, which hands the file to `atomicWriteFile` in `src/atomic-write.ts`; that writes `<file>.<randomUUID()>.tmp` next to the target and renames it, so with no `profiles/` directory the very first `writeFileSync` throws ENOENT, the temp file is removed, and the error propagates to the transcript. Create the project directory in `initProfileDir` (or have the save ensure it exists before writing), and keep reporting a write failure as a message that names the profile rather than the temp path. `src/profiles.test.ts` and the `src/profile/` suite all stage their fixtures by creating `profiles/` themselves — `src/profile/file.test.ts`, `manager.test.ts` and `validate.test.ts` each `mkdirSync(path.join(root, 'profiles'))` before writing — so nothing covers a project that has none; a regression test should point the profile directory at a fresh root and assert that `profile save` writes `profiles/<name>.json` without the directory having been made first.

## development

* Make `janus --relaunch` wait for the server it just started, instead of reporting the previous run's address and hiding a failed start

Existing Bug: Under `--relaunch` the launcher takes the previous run's `__JANUS_URL__` line, still in the appended server log, as the new server's readiness signal and exits 0 within a tenth of a second, so `--no-open` prints the old run's address and a startup failure never reaches the terminal or the exit code, where the spec promises the launcher waits for the new server and relays a failure with the server's own exit code. Severity: 5/10

Existing Risk: 5/10 - Every `--relaunch` after a first run in a directory is affected because the log always holds an earlier marker, so a relaunch that fails (a port already taken, another instance holding the lock) looks like a success with no window and no message, and a script reading the `--no-open` address connects to a dead port.

Proposal Risk: 2/10 - Scanning only what this run appended depends on an offset taken before the server starts, so a log truncated underneath the launcher (a concurrent normal launch reopens it with `w`) could leave the offset past the end and has to be handled as "nothing yet" rather than waiting out the 20-second timeout or missing the new marker.

Proposal: The spec promises in `product/specs/cli.md`, Startup sequence, that "The launcher watches `.janissary/log/server.log` for the `__JANUS_URL__` line. Once it appears, the launcher exits 0 and prints nothing to the terminal — except under `--no-open`, where it prints the server URL … If the server process exits before that line appears, the launcher relays the tail of the log to the terminal and exits with the server's own exit code", and that "`.janissary/log/server.log` is truncated at the start of a normal launch and appended to under `--relaunch`"; its Startup failures section promises the failed-to-start banner is written "to both `.janissary/log/server.log` and the terminal". Reproduced from a checkout at `master@9f3879b4` after `npm run build`, with a scratch `HOME` and a scratch project directory `work`: `node bin/janus.mjs --no-open --port=51001 work` printed `http://127.0.0.1:51001/?token=…` and exited 0. With that instance still running, `node bin/janus.mjs --no-open --relaunch --port=51001 work` printed the same `http://127.0.0.1:51001/?token=…` and exited 0, while the log gained `janissary 0.15.0 — failed to start: port 51001 is already in use.` and its guidance, which never reached the terminal. The identical command without `--relaunch` printed that banner to the terminal and exited 1, as specified. A successful relaunch is misreported too: `node bin/janus.mjs --no-open --relaunch --port=51002 work` printed the first run's `http://127.0.0.1:51001/…` address, though the log shows the new server came up at `http://127.0.0.1:51002/…`. (In that run the new server took over the instance lock instead of being refused, because the sandbox denied the liveness probe and the spec treats an unsignalable lock as stale. Outside a sandbox the lock should refuse it, which is one more startup failure the same mechanism would hide, though that variant wasn't observed.) The mechanism doesn't need a previous run at all. Any `server.log` that already contains a `__JANUS_URL__` line reproduces it under `--relaunch`. The cause is `awaitReady` in `bin/janus.mjs`, which polls the whole log every 100 ms and resolves on `content.split('\n').find((candidate) => candidate.startsWith(URL_MARKER))`, the first marker in the file, while the launcher opens the log with `openSync(logPath, arguments_.includes('--relaunch') ? 'a' : 'w')`. Under `--relaunch` the first poll finds an earlier run's line before the child has written anything, and once `finish` has settled, the child's later `exit` is ignored. Taking the last marker instead (as `readAppUrl` in `scripts/e2e/session.mjs` does) would still race the new server. The fix is to note the log's size once it is opened (`fstatSync(logFd).size` after the append-mode `openSync`), have `awaitReady` search only the content after that offset (treating a file now shorter than the offset as having no new marker yet), and relay the tail of that same slice when the child exits first. `scripts/janus-launcher.test.mjs` covers only the invalid-project-directory case. A regression test should create a scratch project whose `.janissary/log/server.log` already holds `__JANUS_URL__ http://127.0.0.1:1/?token=stale`, hold a port with a test listener on `127.0.0.1`, and run the launcher with `--relaunch --no-open --port=<that port>`, asserting exit 1, the `already in use` banner on stderr, and no `token=stale` on stdout. A second case should relaunch successfully and assert that the printed address is the new server's, not the seeded one.
