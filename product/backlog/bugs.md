# bugs

## ready

* `close <name>` throws away unsaved image edits without asking. the spec says the save-changes dialog "covers every close path — the tab's × button, `Cmd+W`, and typing `close` or `exit`" (`product/specs/image-tab.md:184`), and `product/specs/editor-tab.md:196` says the same for an editor buffer: "The dialog appears whether the close comes from the tab strip's × button, the Cmd+W / Ctrl+W keyboard shortcut, or typing `close` / `exit` at the command line." reproduced on master@63ef941 against a scratch project directory: `open alpha.png`, click **Edit image**, click **Rotate right** (the tab strip now shows the unsaved marker), then type `close alpha.png` at an agent tab's command line — the image tab disappears immediately, no dialog, and the rotation is gone with it. `exit alpha.png` behaves identically. every other path raises the dialog on the same state: the tab's own × button, `Cmd+W`, a bare `close`, and the × button on a *non-active* image tab holding unsaved edits all show "Do you want to save changes to this file?" with **Save (y)**, **Don't Save (n)** and **Cancel (Esc)**, and leave the tab in the strip. a user cannot type a bare `close` for an image tab at all — the tab has no command bar — so the named form is the only way to reach the promise from the keyboard, and it is the one form that skips it. cause: the command bar's interception chain in `web/src/agent-tabs/command-input/useCommandBarSubmit.ts:49` tests `trimmed === 'close' || trimmed === 'exit'` with no argument and consults `guardRef` for the active tab only; anything with a name falls through to `runCommand`, so the server runs it, where `src/commands/close.ts:27` resolves the name and calls `managers.tab.closeTab(...)` directly. the dirty answer lives only in the browser — `tabHandles` in `web/src/App.tsx`, reached through the `registerDirtyHandle` capability — so no path on the server can ask whether the tab is dirty, and the tab is removed with its operation list still in memory. an unsaved editor buffer goes the same way, so this is not specific to the image plugin. likely fix: intercept the named form on the client as well, where `tabs` and the label-or-alias match rule are already in hand, and route it through the same guarded `closeTab(index)` the × button uses; the alternative is for the server to ask the client that holds the handle before removing a tab. either way the guard is worth a test at the command-bar level, since the existing coverage is per-component (`CloseSaveGuard.test.tsx`, `useCommandBarSubmit` callers) and both pass while the two halves disagree.

* a file saved from the image editor can no longer be opened by the app. the spec promises "Every save is a **PNG**, whatever the source format was", that "an **SVG rasterizes** at the size it was rendered, losing its vector nature", that "Each is replaced by the flattened PNG output", and that "The edits stay live and the tab keeps that original identity, so work can continue and be saved again" (`product/specs/image-tab.md:159-165`); it also promises that the registered reference is answered "with a content type derived from its extension" (`:50`). for an SVG those two promises cannot both stand, and the extension wins: reproduced on master@63ef941, `edit vector.svg` on a 300×150 vector, **Rotate right**, **Save** — the header says `Saved vector.svg`, the editor keeps working, and the file on disk is 3940 bytes of PNG (`89 50 4e 47`, a 150×300 raster). then, in a fresh app instance that has never fetched the file, `open vector.svg` opens an image tab whose header still names `vector.svg` and still reports `283 B` while the stage shows a 1252×16 broken image: the `<img>` reports `naturalWidth: 0`, `naturalHeight: 0`, never decoded. fetching the tab's own reference with `cache: 'no-store'` answers `200` with `Content-Type: image/svg+xml` and the PNG bytes, and the identical bytes copied to `renamed.png` open as a 150×300 image served as `image/png`. so the user saves a picture, the app reports success, and the file the app itself wrote is the one file the app can no longer display. cause: `saveImageEdit` in `src/plugins/image/edit.ts:6` writes the PNG data URL over the tab's original path unconditionally and never restates what the file now is, while the response type is derived from the extension — `pluginContentTypes` in `src/plugins/opener-adapter.ts:39-56`, spread into the MIME map at `src/serve-static.ts:20` — so the reference keeps answering `image/svg+xml` for PNG bytes. this is not a browser sniffing quirk that a raster extension would survive by luck: SVG is an XML type, so a mismatched MIME type is a hard refusal, which is why `.svg` fails where the other eight extensions would quietly work. the stale `283 B` in the header is the same gap seen from the other side: the payload's `size` is read when the file is registered, and a save does not re-register it. likely fix: have the save restate what it wrote — `resources.registerFile` mints the reference the payload carries, so the plugin needs a way to update the registered file's type to `image/png` (and the tab payload with it) after a successful write, or the server should derive the response type from the bytes it is about to send. the spec needs a sentence either way: it currently promises both extension-derived content types and a PNG behind every save, and does not say which one wins when a saved SVG is opened again.

* a git-synced editor tab silently deletes merged work when it saves. this happened for real: commit `dd632561` ("sync: documentation.md") removed 116 lines from `product/backlog/documentation.md` that its own parent already contained, in a straight fast-forward with no conflict, no error, and no notification. the cause is the order of operations in `src/git/sync.ts`. a save runs `git add -A`, then `git commit -m "sync: <filename>"`, and only *then* `git pull --rebase origin <branch>`, then `git push` (`saveSync`, and `commitIfChanged`/`pullRebase`/`push` beneath it). the stale content is therefore already sealed into a commit object before the remote is contacted, and because the previous cycle's pull left the shared clone up to date, the pull is a no-op and the push is a clean fast-forward. nothing in the chain can notice. the sequence that produced the damage: a synced tab opened `product/backlog/documentation.md` and loaded 12 lines; the 116 records landed upstream and reached the shared clone on some later pull, leaving 129 lines on disk; the open tab was never told, because `src/git/` never calls `editorWatch.refresh` and the only call site anywhere is the manual resync in `src/editor/resync.ts`, so the `mtimeMs` change never arrived, `useEditorWatchReload` never set `conflictPendingRef`, and the overwrite-confirmation dialog never appeared; the user pressed save; `src/editor/save.ts` called `atomicWriteFile(targetPath, content)` with no expected-hash or expected-mtime argument — the RPC contract at `src/controller/editor-adapter.ts` does not carry one — writing 12 lines over 129; `markSaved` then moved the watcher's baseline to the mtime of the file the stale buffer had just written, blinding that tab to the pull that followed. four separate gaps each of which alone would have prevented it, in rough order of value: (1) `src/editor/save.ts` writes the buffer without comparing it to what is on disk, and nothing records what the buffer was loaded from, so an editor tab and the file it is editing have no shared identity to check against — an expected-hash or expected-mtime argument threaded through the save RPC is the real fix; (2) the commit precedes the pull, so moving the pull ahead of the commit, or refusing to commit when the pull brought in a change to the same file, turns silent loss into a visible conflict; (3) `commitIfChanged` runs a repo-wide unscoped `git add -A` with no pathspec, even though the shared `git-sync` clone holds *every* synced file, so a save can commit any untracked file or unrelated modification in that clone — `src/git/commit.ts` already handles this correctly with a `-- <pathspec>` and the comment explaining why, and the save path should use the same helper; the `filename` argument to `saveSync` is currently used only for the commit subject and never reaches the pathspec. (4) the save path never calls `editorWatch.refresh`, so `product/specs/editor-tab.md`'s claim that "another synced file finishing a save … refreshes automatically" is unimplemented and depends entirely on an `fs.watch` event that the watch manager's own comment says a git-driven replace can silently miss. two smaller things fall out of the same investigation and are worth fixing together: a save-cycle push that *is* rejected as non-fast-forward gets no retry, no rebase and no rollback, just `tab.editor.sync = 'error'`, and no notification at all, which contradicts both the spec's "otherwise reported through the notifications tab" and the sync icon's own tooltip reading "GitHub sync: error — see notifications" — the manual commit-icon path does notify, the automatic one does not; and `src/config.ts`'s comment on `syncPaths` still says "Empty by default" while the value two lines below it is `['product/backlog/', 'product/plans/']`, which is why the default is easy to get wrong. note that `product/backlog/documentation.md` and `product/plans/` are the two paths the default covers, so a plan or backlog file opened in an editor tab is exposed to this by default, not by opting in. `src/git/sync.test.ts` pins the commit-before-pull ordering as intended behaviour and mocks `child_process` throughout, so no test exercises real clone state, staleness, cross-file staging, or the watch-miss case; the regression test that matters is a stale buffer over fresh upstream content, which none of the existing tests can express. affected files are recoverable from the remote history, but the window is silent: nothing in the app reported this at the time, so the only reason it surfaced is that a later audit read the file and noticed the records had gone.

* a theme change whose config write fails reports that it applied for the session, and then does nothing. `theme <name>` and `syntax theme <name>` both return the message `Theme set to "<name>" for this session (config write failed — won't persist).` — the `syntax theme` form reads `Syntax theme set to …` — on the failure branch of `setTheme` in `src/commands/theme.ts` and its twin in `src/commands/syntax.ts`. the branch is reached whenever `updateConfig` returns false, and `updateConfig` in `src/config.ts` returns false from inside its `catch` *without* assigning `config = next`, so the in-memory config still holds the old theme. the next state event publishes `theme: getConfig().theme` from that unchanged value, the client renders the old theme, and the user is told the opposite. expected: either the change applies for the session and the message is true, or the message says the theme did not change. the honest reading of the intent is the first — a session-scoped change is what the wording already promises and what a user who typed the command wants, so assigning `config = next` in a `finally`, or having `updateConfig` take an "apply even if the write fails" option the theme commands pass, would make the message accurate; failing that, the message should drop "for this session" and say the theme is unchanged. it is a narrow path to reach, needing `.janissary/config.json` unwritable or its containing directory read-only, but when it happens the user is actively misinformed about the state of the app, and the message is the only signal they get. the user documentation currently describes the actual behaviour rather than the message's claim, in the `## theme` section of `documentation/user-documentation/command-bar/commands.md`, so whichever way this is fixed that section has to be revisited in the same change: if the theme starts applying for the session, the paragraph explaining that it does not has to go, and if only the message changes, the wording it quotes has to change.

* the back and forward buttons in an embedded web page tab do nothing. they are implemented as `contentWindow.history.back()` and `contentWindow.history.forward()`, but the frame is loaded with `src={page.url}`, so on any real site the iframe is cross-origin and `history` is not a cross-origin accessible window property; reading it throws inside the click handler, the button appears inert, and nothing reaches the transcript or the notifications feed. it works only when the embedded address is same-origin with the app itself, which is nobody's normal case. the two tests in `web/src/plugins/page/PageTab.test.tsx` that assert the call passes because jsdom's frame is a same-origin `about:blank`, so the failure is not exercised. expected: the buttons move the embedded page through its own history, which is what their tooltips and `documentation/user-documentation/tab-types/web-pages.md` both describe. likely fix: stop reaching across the origin from the parent, post a message to the frame and let the extension's content script call `history.back()` and `history.forward()` on the far side. `postMessage` crosses origins freely, the content script already runs in every frame and already posts up to the page tab, and this only needs a `message` listener added to `chrome-extension/content-script.js`. that leaves the buttons depending on the bundled extension, the same dependency the address-following feature already has. the alternative is to remove the two buttons, since a page tab without working back and forward is not otherwise broken. whichever is chosen, the user documentation has to be updated in the same change, because it now describes the broken behavior as the real one: `documentation/user-documentation/tab-types/web-pages.md` lists back and forward among the header controls and then says they reach into the page's own history, which a site on another origin won't let the app touch, so on most pages they do nothing. if the buttons start working, that sentence goes and the page says they move the embedded page through its own history; if the buttons are removed, the sentence goes the other way, the control list drops them, and so does the advice to get back to an earlier page with the address field or the page's own links instead. the postMessage fix also leaves the buttons depending on the bundled extension, so fold that into the paragraph that already explains the extension is what lets the address and label follow navigation, rather than leaving the two features described as having different requirements. `product/specs/embedded-web-page.md` asserts the same capability the docs used to claim, so it needs the same decision and the same edit.
