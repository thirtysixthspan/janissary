# bugs

## ready

* the header's new directory button picks the wrong row when the name it wants is already taken: it creates `untitled-2` correctly, then selects the directory that was already there and opens its rename field. the spec says "If a collision meant the directory was created under a different name (`untitled-2`, …), it is not auto-selected or auto-renamed — the user selects and renames it like any other row." reproduction: in a scratch tree create a directory named `untitled`, open that tree with `files <path>`, press Escape to clear the selection, then click the header's new directory button. expected: a new `untitled-2` directory appears in the tree, unselected and with no rename field, and the existing `untitled` row is left alone. observed: `untitled-2` does appear, both on disk and as a row, but the row above it, the pre-existing `untitled`, becomes the selection and the keyboard cursor, and its name turns into a text field already filled with `untitled`. typing a name and pressing Enter then renames the directory that was there before rather than the one just created, which is the whole reason the field opens pre-selected. reproduced twice on two separate scratch trees, and the no-collision case behaves as the spec describes: the created row is the one that gets selected and renamed. the cause is that the client guesses the path the new directory will take instead of reading back the one the server used. `createNewDirectory` records `newDirectoryTargetPath(targetDir)`, which is always `<target>/untitled` (`web/src/file-navigator/file/navigator-menu-actions.ts:61-64`, `web/src/file-navigator/file/navigator-new-file.ts:29`), and sends the request with `client.send`, which does not wait for a reply. the effect in `FileNavigatorTab` then looks that pending path up by path equality through `findPendingNewDir` (`web/src/file-navigator/FileNavigatorTab.tsx:66-72`, `web/src/file-navigator/file/navigator-new-file.ts:7-10`), so when the server picked `untitled-2` the lookup finds the older `untitled` row and selects it. the comment above the effect expects the collision case never to fire at all, which only holds when nothing already sits at the guessed path. the server does know the real name: `createNavigatorDirectory` returns `result.value.path` (`src/file-navigator/manager/files.ts:49-57`) and the controller passes it back (`src/controller/file/navigator.ts:202-206`), so the reply the client throws away is the answer. likely fix: send the request with `client.request(...)` and use the returned path as the pending one, so the auto-select and auto-rename land on the row that was actually created, and drop the guess from `newDirectoryTargetPath` entirely.

* in a narrow tree the detail value keeps its column and the filename is what gets cut. the spec says "The filename always takes precedence over the value: when a row cannot fit both — a long name, a squeezed sidebar — the name keeps its full width and the value gives way, shrinking and then disappearing behind it rather than truncating the name." reproduction: dock a tree into the left sidebar with `files left <path>` (the sidebar is 300px wide by default), then click the header's detail button once to reach size mode. expected: a row whose name does not fit keeps its name readable and loses the `2b` value. observed: in a 296px row, `a-fairly-long-but-plausible-file-name-here.txt` is given a 270px name box against 364px of natural width and rendered with `text-overflow: ellipsis`, so a quarter of the name is gone, while the `2b` value stays fully drawn at the row's right edge; an 81-character name in the same tree behaves the same way (270px box, 610px of text). a 22-character name in the same sidebar shows both, so this only appears once a row cannot fit both, which is the case the spec names. the cause is the width cap on the name at `web/src/theme.css:899`, `.files-name { flex: 0 0 auto; max-width: 100%; overflow: hidden; text-overflow: ellipsis; }`. capping the name at the row's own width is what truncates it, and once the name has shortened itself there is nothing left for `.files-detail` to give way, even though that is the shrinkable rule (`flex: 0 1 auto; min-width: 0`, `web/src/theme.css:903-906`). the comments above both rules describe the promised behaviour instead: the filename owns the row, and the value yields until it disappears entirely. likely fix: drop `max-width: 100%` and the ellipsis from `.files-name` and let `.files-row { overflow: hidden }` do the clipping, so `flex: 0 1 auto; min-width: 0` on `.files-detail` is what collapses when the two cannot both fit. the mode is untouched either way, so widening the tree or moving to a shorter row brings the value straight back.

## development

* Persist an agent's working directory as a path, so an agent brought back by relaunch gets a working shell

Existing Bug: From the second command in a tab onward the `cwd` written to `.janissary/state/<name>.json` is a blob of the shell's raw terminal output rather than a working directory, and an agent restored by `--relaunch` then cannot start a shell at all. Severity: 8/10

Existing Risk: 8/10 - Anyone whose login shell is zsh meets this on every `--relaunch`, and the agent comes back unable to run a single command until they open a new tab, with only a garbled line in the tab's header to hint at the cause.

Proposal Risk: 5/10 - The pwd answer shares its buffer with real command output, so debris removal that drops one line too many would leave a tab in the wrong directory, and silencing zsh's line editor changes what a promoted interactive program sees on its tty.

Proposal: The spec promises that "Each agent state file stores `name`, `dotColor`, `active`, `number` (the tab's position), `cmdHistory[]`, `log[]` (the full transcript), `cwd` (the shell's working directory), `context[]` (informational messages received from other agents), and `commandQueue[]`". Reproduce it with a scratch project directory and the default `interactiveShellDetection` on, under zsh: start the app, and in the root `janus` tab run `echo one`, wait for it to finish, then run `echo two`, and read `.janissary/state/janus.json`. Expected: `cwd` is the project's own path. Observed: after the first command it is correct, and after the second it is the string `padded` (the tail of the previous command's output), a newline, that command's `__JS_END_0_1790473374070__` sentinel, another newline, zsh's highlighted `%` prompt with its SGR escape codes, then `pwd`, then `echo "`, stored with its `\r\n` line endings and escape sequences intact; the tab's header row renders the same string in place of the working directory. The transcript shows the same debris on every command. Then stop the app, start it again with `--relaunch`, and run any command in the restored tab. Observed: the entry ends `(shell exited)`, the next command does the same, and the stored `cwd` never repairs itself, so the tab is dead for the rest of the run. Three things combine. `SEED_COMMAND` in `src/shell/pty-session.ts` is `"stty -echo 2>/dev/null; PS1=''; PS2=''"`, and zsh does not read `PS1` — it prompts with `PROMPT` — so the prompt stays and, with ZLE still active, the shell also redraws each input line it reads. `queryShellPwd` in `src/shell/index.ts` returns `buffer.slice(0, endIndex).trim()`, which is everything the shell printed before the `__PWD_…__` marker with no filtering, and from the second command onward that window holds the previous command's tail, its sentinel, the prompt, and the terminal's echo of the `pwd` line itself; `ShellManager.execute` passes that to `onPwd`, `ShellManager.run` hands it to `TabManager.setCwd`, `setCwd` in `src/tab/runtime-operations.ts` stores whatever it is given, and `buildAgentStateFromTab` in `src/tab/agent-state.ts` persists it as `cwd`. `stripShellSentinels` in `src/shell/sentinel-strip.ts` already knows how to remove exactly this debris, through `PWD_COMMAND_LINE` and `dropPwdDebris`, but it is wired only to restored remote output from `ShellManager.appendRestoredOutput`. The relaunch damage follows from that value: `ShellManager.getShell` calls `spawnFor`, which calls `spawnPtyShellFor` and hands the persisted `cwd` to `spawnPty` in `src/pty.ts`, which passes it to `pty.spawn` as the process working directory; a path that is not a directory cannot be entered, so the shell exits at once and never comes back. A scratch probe confirms it: `pty.spawn('/bin/zsh', ['--no-rcs'], { cwd: <that string> })` exits with code 1 and no output, while the same spawn with the real path is still running a second later. For a piped shell the same value is instead written as `cd "<blob>"` by `ShellManager.spawnFor`. Fix it by having `queryShellPwd` keep only the answer — the last path-shaped line before the marker — or by running the existing sentinel and pwd debris removal over the live result as well as the restored one, and by extending `SEED_COMMAND` so zsh is quiet too (`PROMPT=''`, `RPROMPT=''`, and ZLE off) while bash keeps `PS1`/`PS2`. Then guard the value on the way in and out: have `setCwd` keep only a string that is an existing directory, and have `spawnPtyShellFor` fall back to `process.cwd()` when the persisted `cwd` is not a directory, so a bad value can never again kill a restored shell. `src/shell/index.test.ts` exercises `queryShellPwd` only with a clean `/home/user\n__PWD_4_3000__\n` buffer, so a regression test should feed it a PTY-shaped buffer — leftover command output, a sentinel, a prompt, the echoed `pwd`, the path, then the marker — and assert the result is the bare path; a second should assert that a path-less buffer still yields `''`. `src/shell/pty-session.test.ts` asserts the seed string contains `stty -echo`, `PS1=''`, and `PS2=''` but nothing asserts the shell actually went quiet, so a test pinning `PROMPT`/`RPROMPT` in the seed would fail today. `src/shell/sentinel-strip.test.ts` already covers the debris removal, so wiring that routine into the live pwd result is covered by its existing cases once `queryShellPwd` uses it.
