# bugs

## ready

* re-opening a file that already has an editor tab with a `:line` suffix focuses the tab but leaves the cursor where it was. the spec says "If the new open request includes a line number, the existing tab's cursor moves to that line." reproduction, in a scratch project directory served on 127.0.0.1: create a ten-line `lines.txt` whose lines read `row 1` through `row 10`, then from an agent tab run `edit lines.txt:5`. the fresh open works: the caret lands on line 5, the gutter reads 5, the row reads `row 5`. click line 1 to put the caret there, then run `edit lines.txt:8`. expected: the caret moves to line 8. observed: the tab takes focus (the hidden textarea is `document.activeElement`) and exactly one `lines.txt` tab exists, so the duplicate-open branch is what ran, but the caret is still on line 1 and the gutter still reads 1. the root cause is that `editor.line` has exactly one consumer on the client, and it only runs on a tab's first load: `useEditorFile` passes `editor.line - 1` to `api.load` in its load effect (`web/src/editor/useEditorFile.ts:67` for a new file, `:75` for a fetched one), and that effect's dependencies are `editor.url`, `editor.name` and `editor.sync`, so a tab that only changes `line` never re-runs it, and it would return early anyway on `api.stateRef.current !== null`. the server does its half correctly, writing `existing.editor.line = view.line` in the duplicate branch of `openEditorTab` (`src/tab/openers.ts:131`) and re-broadcasting, so the new line number reaches the client and is then dropped. `EditorTab`'s initial-scroll effect (`web/src/editor/EditorTab.tsx:82-88`) is the other reader of `editor.line`, and it is behind an `initialScrollDone` ref, so it cannot pick the change up either. likely fix: an effect that watches `editor.line` and, when it changes on a tab whose buffer is already loaded, moves the cursor to `line - 1` and scrolls that row into view, the same shape as the initial scroll. the duplicate branch on the server could then stop mutating `line` on an existing view once the client acknowledges it, otherwise the two will disagree about who owns the cursor.

* answering the overwrite-confirmation prompt leaves the editor tab with no keyboard focus at all, so the buffer stops taking typing and Ctrl+S stops reaching the editor. the spec says "Cancel (Esc): dismisses the dialog and leaves the buffer as-is, still unsaved. The next save attempt shows the same prompt again." reproduction: open a text file in an editor tab, type so the buffer is dirty, change the same file on disk from outside the app so the watcher notices, then press Cmd+S. "This file changed on disk. Overwrite it with your changes?" appears with Overwrite (y) and Cancel (Esc). press Escape. expected: the buffer is as it was, still unsaved, and the next save attempt raises the same prompt again. observed: the dialog is gone and the file on disk is untouched, but `document.activeElement` is now `<body>`, not the editor's hidden textarea. typing `zz` afterwards changes nothing in the buffer, and a following Cmd+S does nothing at all: no prompt, no save, no error. the only way to get another attempt is to click the metadata header's save button with the mouse, which does bring the prompt back, and pressing `y` there writes the file, after which focus is on `<body>` again and the keyboard is still dead. the cause is that `useDialogKeyboard` focuses the dialog on mount and removes its capture-phase listeners on unmount without ever putting focus back (`web/src/shared/useDialogKeyboard.ts:34-50`), and nothing else in the editor's path restores it: `OverwriteConflictDialog` is mounted by `EditorTab` (`web/src/editor/EditorTab.tsx:166-168`) and both of its answers run through `useEditorFile`, where `dismissConflict` only clears `conflictOpen` and `overwrite` only writes the file. the sibling dialog gets this right, which is what makes the gap obvious: `CloseSaveGuard`'s Cancel and its post-failure path both call `handle?.focus()` (`web/src/CloseSaveGuard.tsx:63` and `:79`), and that is the behaviour the spec describes for its own Cancel. likely fix: refocus the buffer when the conflict dialog closes, either at the end of `dismissConflict` and `overwrite` in `web/src/editor/useEditorFile.ts` or through an effect in `EditorTab` keyed on `file.conflictOpen` going false, so both answers and the Escape path land back in the textarea.

* the default right-click menu on an editor selection has no Paste entry. the spec says "Right-clicking an editor selection leaves that selection unchanged and offers Copy, Paste, and Chat about this in the default context menu". reproduction: open a plain-text file, double-click a word so the word is selected, then right-click inside the selection. observed: the menu opens with exactly two rows, Copy and Chat about this, separated by one divider, and the selection is preserved as the spec asks. Paste is simply absent, even though the editor is the one surface in the app with somewhere to paste to: the spec devotes a paragraph to pasting into the buffer, and a paste target exists right up until the right-click takes it away. the mechanism is the secondary mouse button. `useEditorMouse`'s `onMouseDown` returns immediately for any button that is not the primary one (`web/src/editor/useEditorMouse.ts:58-59`), so it neither focuses the textarea nor calls `preventDefault()`; the browser's own right-mousedown default then moves focus off the textarea, `resolvePasteTarget` finds no text-entry element among either the click target or `document.activeElement` (`web/src/context-menu/default-menu-target.ts:40-44`), and `defaultMenuGroups` omits the entry it cannot act on. the left button works today only because that path does call `preventDefault()` and does refocus. with no selection the same right-click opens no menu at all, which does match the spec. likely fix: in the editor body's mousedown handler, preventDefault the secondary button (or call the focus callback for it) so the textarea keeps focus, or refocus the textarea on `contextmenu` before the menu resolves its target. the same lost focus is why typing stops working after a right-click in an editor tab, so the one change fixes both.

* Cmd+/ twice does not return a commented block to its original text when the range contains a blank line. the spec says "Pressing Cmd+/ twice therefore always returns the text to exactly what it was." reproduction: in a `.ts` file select three whole lines where the first and third are indented two spaces and the middle one is empty, for example `  const a = 1;` / (blank) / `  const b = 2;`, then press Cmd+/ twice. the first press gives `  // const a = 1;` / `  // ` / `  // const b = 2;`, which is right: the marker sits at the shallowest indent and the blank line is commented too so the block reads as contiguous. the second press brings both code lines back exactly, and the blank line comes back as two spaces. the buffer is dirty afterwards, having been clean before either press, so a user who toggles a block and puts it back is left with an edit they never made. the cause is in the line-comment strategy: `commentEdit` pads any line shorter than the common indent out to the marker column and inserts `padding + marker + ' '` (`web/src/editor/plugins/commenting/line-comment.ts:35-47`), so a blank line gains two spaces of padding, while `uncommentEdit` removes only the marker and one following space (same file, `:49-59`) and leaves that padding behind. the same happens to a line that holds only a few spaces. likely fix: make the uncomment edit take the whole leading run of whitespace with the marker when everything before the marker is padding the comment step added, which restores the round trip without changing where markers land. the alternative is to stop padding and put a blank line's marker at column 0, which reads less like a block and needs the spec's "The marker goes at the first non-whitespace column of the least-indented line in the range" relaxed for blank lines, so it is the worse of the two.

* Shift+Tab does not outdent in an editor tab; it does nothing at all, because an app-wide focus-cycling chord claims the key first. the spec says "Tab and Shift+Tab reach the same two commands: Tab indents whenever the selection spans more than one line, and Shift+Tab outdents in every case." reproduction: open a file whose first line is `  alpha`, put the caret on it, press Shift+Tab. observed: the text does not change, and no tab character is inserted either, which is the tell: if the editor's own key bindings had run, Shift+Tab would have fallen through to inserting a tab. the same buffer and the same caret position outdent correctly under the other chord, Cmd+[ turns `  alpha` into `alpha`, and a tab-indented line behaves the same way, Cmd+[ takes `\talpha` to `alpha` while Shift+Tab leaves it alone. a keydown trace pins where it goes: the Tab keydown with `shiftKey` set does reach the editor's textarea, but with `defaultPrevented` already true during the capture phase on `window`, and it never reaches the editor's own handler, so neither the indenting plugin's outdent nor the editor's fallback can run. that is `useSectionNav`, which claims Shift+Tab across the whole application as its "cycle keyboard focus across the currently-present application sections" chord and runs in the capture phase on `globalThis`, calling `preventDefault()` and `stopPropagation()` (`web/src/useSectionNav.ts:61-70`). its own comment says the capture phase is deliberate, so it wins ahead of xterm and ahead of the browser's focus traversal, and the editor's textarea handler is further down the same road. it already stands down while a modal dialog is open; it does not stand down for an editor tab. the net effect for a user is a dead key: in a layout with only the centre section present the chord refocuses the visible tab, so Shift+Tab appears to do nothing whatsoever. likely fix: let the editor claim the chord first, the way the modal case already does, by having `useSectionNav` return early when the event target is inside an editor tab (the editor root carries `data-doc-shot="editor-view"`), and keep the section cycle for the surfaces that do not use Shift+Tab. a plain Tab is a different chord from the yielded Shift+Tab, so indenting a multi-line selection with Tab keeps working either way.

* intermittent bug likely due to a race condition: on launch the window and UI are displayed but the command line does not have the keyboard focus and clicking on the command line does not recover the focus. the app must be restarted by closing the window. In rarer cases, the window opens but the UI fails to render entirely. again the app must be restarted by closing the window.
