# features

## ready

## development

* add an ACP skill to allow an agent to spin up other agents with different models, pass them ai tasks (form the repository) to execute and access to monitor the transcript as the agent works, and to recieve the response.

* The diff tab (`product/specs/diff-tab.md`) shows every working-tree change against `HEAD` the way GitHub's files-changed view does, but nothing in it can act on what it shows: the spec says plainly that nothing in the tab "stages, discards, or commits." VS Code's Source Control diff editor can stage or revert a single hunk or a selected range of lines straight from the diff, which is often where a review actually ends. In Janissary the last step means leaving for a shell and typing `git add -p` or `git checkout -p`, even though the diff is already on screen. Closing the gap would add per-hunk and per-line stage and revert actions that apply through the git index and refresh the view after each one. Complexity: medium.

* Shell and harness terminals have no find. The shell tab spec says `Cmd+F` does nothing there, because the terminal is not a searchable in-tab transcript (`product/specs/shell-tab.md`), and the harness spec lists no search key at all. The transcript can be searched, but a harness's output is a live PTY, so the long run where you most want to find the line that failed has no route except scrolling. iTerm2's Cmd+F opens a find field over the tab's scrollback, and xterm.js, which every harness, ssh, and PTY-takeover tab already runs on, ships an official search addon (`@xterm/addon-search`). Closing the gap would bind a find bar with next and previous and match highlighting to the terminal surfaces, built on that addon. Complexity: low-medium.

* Quick Open (`Cmd+P`, `product/specs/quick-open.md`) stops at ten rows. The spec says the list "is capped to the top 10 best-scoring matches," and it describes no way to see past the tenth. In a project with several hundred files, a name like `types` or `index` can rank eleventh, and the only way to reach it is to type a longer query. VS Code's Quick Open lists every match and scrolls through them, so the file you want is one arrow key away rather than one more keystroke away. Closing the gap would make the list scrollable or paged, with the best matches still at the top. Complexity: low.

* The search tab (`product/specs/search-tab.md`) finds text across the project, but it never says how much it found. The header shows no count of matches or files, and a search quietly stops at 250 matches. The include and exclude fields split on commas only, so neither field can narrow by a brace list. VS Code's Search view accepts `{}` grouping in the same glob fields, such as `{**/*.html,**/*.txt}`, and its panel reports how many results and files a search produced. A count is the cheapest way to tell a complete result from one that stopped at the cap. Closing the gap would add the count to the header, a notice when the cap is reached, and brace-group parsing for the include and exclude fields. Complexity: low-medium.

* The markdown tab (`product/specs/markdown-tab.md`) takes a snapshot of its file when it opens, and later edits on disk "are not reflected until it is opened again." The editor tab in the same app does the opposite: an external change loads automatically when the buffer has no unsaved edits (`product/specs/editor-tab.md`), and the file navigator already watches visible directories and refreshes within about a second. The case that bites is the common one, where an agent rewrites a plan while the markdown is still open and the view keeps the old text. Obsidian picks up outside changes to an open note, so a reader will expect the same here. Closing the gap would reuse the navigator's watcher to re-render the tab when its file changes, and keep the scroll position when the content has not moved. Complexity: low.

* The markdown tab also leaves relative links going nowhere. Links to other local files, such as `./architecture.md` or `docs/setup.md`, are not resolved, so a README or a plan that points at its siblings is a page of dead links even though each target is one click away in the navigator. GitHub's renderer and Obsidian both resolve those links against the file's own folder. The serving rule is the real constraint: the spec says only files the user has explicitly opened are served, and the architecture principles require every served file to pass an explicit allow-list. A resolved link would therefore need to add its target to that list at the moment of the click, or hand it to the existing `open` path. Complexity: medium.

* The clipboard-history popup (`product/specs/clipboard-history.md`) keeps the last fifteen in-app copies and pastes one at the caret. The spec lists what it leaves out: previewing the selected entry, searching or filtering the popup, deleting an entry, and pinning an entry. Paste, the macOS clipboard manager, searches its history as you type, pinned items included, and Maccy filters its list as you type too. Janissary's popup gives you arrow keys over a fixed list that drops its oldest entry, so finding an older copy means scrolling past everything newer. Closing the gap would add type-to-filter to the popup, a delete key for one entry, and a pin that exempts an entry from the fifteen-entry limit. Complexity: low-medium.

* Quitting with unsaved work gives one button. When any tab holds unsaved work, `quit` opens "You have unsaved changes. Close anyway?" and confirming "discards whatever was unsaved; there is no per-file save prompt here" (`product/specs/quit-confirmation.md`). A single editor tab gets a Save, Don't Save, Cancel dialog on close (`product/specs/editor-tab.md`), so the per-file choice exists right up until the app itself is closing. VS Code's close-window prompt names each dirty file and asks about each one. Closing the gap would walk the dirty tabs through that same three-button dialog one after another before the quit proceeds, using the registry of unsaved work the app already keeps. This is lower traffic than the rest, but a wrong click loses work. Complexity: medium.

* The PDF tab (`product/specs/pdf-tab.md`) is a clean, read-only viewer, but it can't find text and can't jump by section. The spec says so on both counts: "There is no in-document search," and "there is no document outline, bookmark list, or attachments panel." macOS Preview, the viewer most people will compare it with, has a Table of Contents view and a Find command. For a forty-page paper, the only routes now are scrolling and the thumbnail strip. Closing the gap would add a find bar over the text layer and a sidebar built from the document's outline, falling back to the page strip for PDFs that have none. Complexity: medium, since the usual PDF renderers expose both search and the outline tree.

* The SQL tab (`product/specs/sql-database.md`) commits each cell edit as it finishes, and the spec is blunt about the result: "It does not undo. A cell edit commits or it does not." DataGrip's result grid keeps edits pending until you submit them, lets you revert a selected cell or a scope of cells, and can preview the DML a submit would run. Janissary's grid has the cell editor and the write path, but a wrong value in a row is a write the user cannot take back inside the tab. Closing the gap would hold grid edits pending until a submit key sends them, add a revert for the selected cell or the whole pending set, and show the statements before they run. Complexity: medium.

* Sending diff-tab comments back to the agent that wrote the change. Vibe Kanban's review step lets a reviewer comment on a line of an agent's diff and returns that feedback to the agent to act on, and Superset sends a rejected diff back to its agent for another pass instead of merging it. Janissary's diff tab takes a `+` comment on any line, but those notes "remain local to this tab, and are not sent to an external service" and are forgotten when the tab closes (`diff-tab.md` § Comments), so the agent that produced a change never hears the objection and the user retypes it into the harness. Adopting it would mean a "send comments to harness" action on the diff tab that formats each saved comment with its file and line and delivers the text to the harness whose workspace the diff came from, through the delivery path `send` already uses for running harnesses (`send.md`). Complexity: low-medium.

* Sending one line to a whole tab group at once. tmux's `synchronize-panes`, iTerm2's Shell > Broadcast Input (to the panes of the current tab or of all tabs) and Warp's Synchronized Inputs all fan one typed command out to several sessions. Janissary's `send <label> <text>` names exactly one tab (`send.md`); tabs can already be grouped under a shared colored band (`tabs.md` § Tab grouping), but nothing treats a group as a target, so running the same instruction across a set of harness tabs takes one `send` per tab. Adopting it would mean a group name in place of a label, a visible marker on every tab of a group that is broadcasting (iTerm2 uses a background stripe for this), and a confirmation listing the target tabs before a line reaches more than one of them. Warp's reported bug, where commands also ran in the directories of closed panes, is the reason the target list has to be shown. Complexity: low-medium.

* User-defined triggers on tab output. iTerm2's per-profile Triggers apply a regular expression to every line a session prints and run an action on each match: highlight the text, make it a link, capture the line to the Toolbelt, bounce the Dock icon, or post a notification. Janissary's notifications come from a fixed list of recognized events (`notifications.md`), and the only explicit event with a configuration toggle is `systemScheduleFire`, so a user cannot ask to be told when a build tab prints `FAIL` or to mark `ERROR` lines in a long-running shell. Every tab's output already passes through the transcript and the append-only log (`transcript.md`, `append-only-log.md`), so matching would read a stream that already exists. Adopting it would mean a per-tab list of pattern and action pairs, set through a `trigger` command and the config file, with a small action set (notify, highlight, capture to the notifications feed) and a per-tab match cap so a noisy process cannot flood the feed. Complexity: medium.

* Landing or discarding a workspace's work before its clone is removed. Conductor and Superset each give an agent its own git worktree, show that agent's diff when it finishes, and then merge the branch after review or send the agent back to iterate. Janissary's workspaces are disposable clones of `origin` (`workspaced-agent.md`) whose work survives only if the agent pushes it: the clone is removed in the background when its last tab closes, and leftover cleanup removes a folder "even with uncommitted or unpushed work in them" (`workspaced-agent.md` § Last tab close, § Leftover folders). The diff tab can show what a workspace holds, but nothing asks about a workspace's git state before its clone goes. Adopting it would mean a check on last-reference close that lists uncommitted changes and unpushed commits and offers to commit and push them to a named branch, keep the clone, or discard it, with merging into the source checkout as a later step. Complexity: medium.

* Rewinding a harness workspace to an earlier turn. Claude Code's `/rewind`, opened with a double Escape, restores files and conversation to an earlier prompt using checkpoints it takes before each edit, and offers "code only" and "conversation only" variants. Janissary's harness tabs run claude, codex and opencode in PTYs (`harness.md`), and nothing reverts what a harness changed in its clone: the file navigator's undo stack covers moves and not deletes or renames (`file-navigator-tab.md`). The harness spec already tracks when a turn starts and ends through busy-to-idle transitions (`harness.md` § Busy/ready status), and a workspace is a git clone, so a snapshot per turn would give a rewind point without a new subsystem. Adopting it would start with a code-only rewind of the clone to the snapshot taken before a chosen turn; the conversation half stays with the harness CLI, which the app cannot rewind from outside. Complexity: medium-high.

* A git history and branch panel. lazygit's panels list the commits on the current branch, show the files a selected commit changed, switch and create branches, and stash and apply changes, with undo built on the reflog. Janissary's file navigator shows the checked-out branch in its header and offers pull and commit-to-origin (`file-navigator-tab.md` § Branch metadata, § Committing to origin), and the diff tab compares only against `HEAD`. There is no commit log, branch list, stash, or checkout, so checking what a workspace committed, or moving the project checkout onto another branch, means leaving for a terminal. Adopting it would mean a read-only git tab first (commit list, per-commit file list rendered by the diff tab's renderer, branch list), with checkout and stash added later under the same guard the file navigator already applies to pull and commit. Complexity: medium-high.

* Pushing questions and approval requests to a phone. ai-agent-notifier and pygmy send "finished" and "needs attention" alerts from coding agents to ntfy, Telegram or Discord, and the common DIY version is a Claude Code Stop hook that posts to an ntfy topic with curl. Janissary's notifications go only to the in-app feed, toasts, desktop alerts and the bell (`notifications.md`). An agent question has no timeout and holds one pending slot per tab (`agent-questions.md`), and a harness permission prompt only stops its busy dot and badges it unread (`harness.md`), so a user away from the window can leave an agent blocked for hours without knowing. Adopting it would mean an optional ntfy or generic webhook channel in `application-config.md`, limited to a short allowlist of events (question, harness needs approval, schedule failed), sending the tab name and event title and nothing more, with the topic treated as a secret. Complexity: low-medium.

* A predicted next command on an empty command bar. Warp's Next Command suggests the next shell command from the tab's recent history, git branch, exit code, directory and the last block's output, and Tab, the right arrow or Ctrl-F loads it into the input line. Janissary's ghost text completes only what the user has typed, as an exact prefix of a recorded command (`history.md` § Ghost text suggestion), and the history does not record exit status, so nothing appears on an empty bar or after a failed command. Adopting it would start with a heuristic that needs no model, such as ghosting the command that most recently followed the same failure, or the last command run in this directory, accepted with the right arrow the spec already uses. Recording each entry's exit status is the prerequisite, and an ACP-backed suggester could come later. Complexity: medium.

* centralized model selection and usage statistics

* Durable flows across relaunch - capture exit information from a harness and be able to use it to restart a session. a relaunch harness picker. workspace dir would need saved and re-created.

* Searching what every tab said, the way iTerm2's Find Globally searches the scrollback of all open tabs at once and Exposé Tabs (`Cmd+Opt+E`) tiles every tab so a search can highlight the one holding the match, and the tmux plugins built on the same idea — `tmux-search-panes` full-text searches the live contents of every pane in every window of every session and jumps to the hit, and `tmux-omni-search` wraps that in an fzf preview with the matching line highlighted. Janissary's search is scoped to the tab issuing it: `Cmd+F` and `search transcript <pattern>` search the current tab's transcript, the `hist` picker walks one tab's last hundred commands with no filtering at all (`history.md` § History picker), and the tab navigator lists displayed names and numbers and nothing else (`tab-navigator.md`). With a dozen agents running, the question a user actually has is "which tab said that", and answering it means scanning the strip for a stopped blink or a flag. A search overlay spanning every open tab's transcript and command history, listing hits with the tab they came from and jumping to the tab and line on Return, would close it. Complexity: medium.

## declined

* long term durable transcripts - send trascripts off to seperate github repo? other durable storage options? 

* Rate-limit awareness for harness tabs — a recognized rate-limit screen, the reset time it states, and a fleet-wide summary of how many tabs are parked and until when — the way amux detects Claude Code's rate-limit prompt across every registered session, records the reset time, badges each blocked session `Rate-limited until HH:MM`, shows a header pill reading `N of M rate-limited, reset HH:MM`, and steers a resume message to each still-parked session once the reset passes. Janissary's `rate-limited` notification event covers ACP queries only, on a best-effort text match, is off by default, and records no reset time (`notifications.md`); a rate-limited harness tab just stops blinking and badges unread, indistinguishable from one that finished its work. Adopting this would mean reading the rate-limit screen out of the captures `harness.md` already takes, parsing the reset time, and showing it on the tab's metadata row and in a summary. Complexity: medium. Decision: harnesses already support auto resume.

* A saved directory of SSH hosts with tags/groups and one-click connect, the way Termius and Royal TSX maintain a host list with saved keys and connection options instead of retyping a destination each time. Janissary's `ssh <destination> [options]` (`product/specs/ssh-tab.md`) is a thin passthrough to the real `ssh` binary with no saved-host concept — every connection is typed from scratch, with tab-completion only covering already-open ssh tabs' labels/destinations, not a saved list of hosts never yet connected to in this session. Determination: Out of scope at the moment

* A floating, transient terminal overlay for a quick one-off shell command, the way Zellij's floating panes let a user pop open a temporary pane without disturbing the current layout, then dismiss it. Janissary's closest equivalent is PTY takeover (`product/specs/shell.md`), which replaces the whole tab body for an interactive program, or opening a whole new tab — there is no lightweight way to run one quick command in a small overlay without leaving the current tab's context or committing to a new tab. Determinination: nope

* Reusable, parametrized command "workflows" invocable from a command palette, the way Warp's Team Workflows turn a common command into a shared, versioned, named primitive any user can run and tune. This is distinct from janissary's existing `profiles/` (which launch a whole tab topology — harnesses, editors, layout) and `ai/tasks/*.md` (agent prompts run via the task picker, `product/specs/task-picker.md`): a workflow would be a lightweight, parametrized single-command template (e.g. a shell one-liner with placeholders) saved and invoked inline in any tab's command bar, without spinning up a new tab. Determination: nope

* The editor (`product/specs/editor-tab.md`) only supports one caret and one active selection, while VS Code's core editor supports multiple independent cursors for simultaneous edits and column selection. Closing this gap would add multi-caret creation (including keyboard and mouse gestures), rectangular selection, per-caret insertion/deletion, and coherent undo, rendering, and paste behavior. Complexity: medium-high. Determination: nope

* The editor (`product/specs/editor-tab.md`) has syntax highlighting and fuzzy search within the current buffer but no language-aware symbol navigation, while VS Code combines language services with Go to Symbol, Go to Definition/References, Peek, Outline, and breadcrumbs. Closing this gap would add a pluggable language-service/indexing layer and editor commands for symbol search, definition/reference jumps, and the current file's symbol outline. Complexity: high. Determination: the editor is general purpose not specifically a code editor.

* The browser automation feature (`product/specs/browser.md`) exposes goto, rendered content, eval, and screenshots but does not retain an inspectable action history or browser diagnostics; Playwright Trace Viewer provides a timeline with DOM snapshots, screenshots, console messages, network requests, and action details. Closing this gap would add an opt-in per-window trace/inspection mode with a replayable timeline and links from each action to its DOM, console, network, and screenshot evidence. Complexity: high. Determination: low value at this point in time.

* The shell transcript (`product/specs/shell.md`, `product/specs/transcript.md`) is line-oriented and can rerun a prompt by double-click, but it does not expose command-level duration, exit status, or a selectable command-plus-output block; iTerm2's shell integration supplies command selection and an info panel with duration, status, resend, copy, share, and named marks. Closing this gap would track command boundaries and completion metadata, then add block selection with copy/rerun/bookmark actions and a compact command-info view. Complexity: medium. 

* An "attention" jump to the next tab that is waiting on the user, the way claude-tmux ships `claude-tmux next-attention` and an `A` filter that narrows its dashboard to the panes blocked on a permission request, a notification, or a question. Janissary already knows which tabs those are: a recognized harness permission prompt stops the busy dot and badges the tab unread (`harness.md` § Busy/ready status), an agent question is a per-tab pending panel (`agent-questions.md`), and any new content delivered to a hidden tab raises the unread badge (`tabs.md` § Unread badge) — but nothing acts on that knowledge, because `next` and the tab navigator walk every non-docked tab in strip order, so the only route to a blocked tab is scanning the strip for a stopped blink or a flag icon. An `attention` command and chord that focuses the next tab in one of those states and skips the rest would make the detection pay off. Complexity: low-medium.

* Per-tab permission rules for a harness instead of the single all-or-nothing auto-approve toggle, the way Claude Code evaluates three ordered rule lists — deny, then ask, then allow — with specifiers like `Bash(npm run build)`, `Read(./.env)` and `WebFetch(domain:example.com)`, glob patterns inside them, and a `/permissions` view listing every rule and the file it came from. Janissary's `harness.md` § Auto-approve permissions offers exactly one bit per tab: a recognized prompt is answered automatically, and the spec's own justification is that the disposable workspace clone keeps that low-risk. That leaves the interesting cases unexpressible — approving the read-only and build commands in an unattended overnight run while still stopping to ask about `git push`, `rm -rf`, or a network call, which is the configuration that would make `--no-workspace` tabs and background agents far less nerve-wracking. A per-tab list of allow/ask/deny patterns the auto-approve path consults before it answers would close it. Complexity: medium.

* Clickable links in terminal output and in the transcript, the way WezTerm turns a URL in the scrollback into a link through its `hyperlink_rules` — regex, a format string with capture-group placeholders, and an optional highlight group — and also honours the OSC 8 escape sequence, and its built-in defaults already cover bracketed URLs and bare `user@host` addresses. xterm.js, which every harness, ssh, and PTY-takeover terminal already runs on, ships both halves: a `WebLinksAddon` that pattern-matches URLs and a `linkHandler` for OSC 8, plus a hover popup showing the real destination when the visible text is not the URL. Janissary renders `file:line` patterns as clickable links (`transcript.md` § Clickable file:line links) but a web address in output or in a markdown reply is inert text, and the destination — a page tab — already exists through `open <url>`. Enabling link handling on the terminal surfaces and adding URL matching alongside the file-link rule is the whole of it. Complexity: low-medium.

* Schedules triggered by a change rather than by a clock, the way GitHub Actions runs a workflow on `push` narrowed by `paths:` and `paths-ignore:` glob filters, so a job fires only when the files it cares about are the ones that moved. Janissary's scheduler is time-only in all five of its forms — `at`, `on <date>`, `every <N>`, `every day at`, `every <weekday> at` (`scheduling.md` § Schedule forms) — so the natural "run this when *that* changes" automation has no form at all and the user can only approximate it by polling on a short interval. The material is already running: every visible directory of every open file navigator is watched and refreshed within about a second (`file-navigator-tab.md` § Watching), and the scheduler already has a one-second tick, debouncing, a queue that drains per tab, and a schedule window that reports each entry's next run. A `schedule <name> when <paths> <cmd>` form taking the same include/exclude globs the search tab already uses would close it. Complexity: medium.

* Catching up and reporting a schedule whose owning tab was not open, the way a systemd timer with `Persistent=true` runs the trigger it missed while the machine was down and reports it, and anacron exists for the same reason under cron. Janissary already handles the machine-asleep case carefully — an overdue entry runs once on wake and records `<command> ran <duration> late (system was asleep)` in the notifications feed (`scheduling.md` § Sleep and overdue commands) — but the far more common case in a tab-based workspace is the tab simply not being there: a firing for an agent that is not currently open as a tab is skipped with no record at all, leaving the entry in the state file to run whenever that tab next opens and happens to be due, and a harness tab's schedule is memory-only and simply ceases to exist when the tab closes. A recurring `standup` silently skipping every day because the tab was closed is the failure this closes, by running the missed entry on reopen the way the sleep path already does, and by saying so when it cannot. Complexity: low-medium.

* Images drawn in terminal output, the way iTerm2 renders them inline from its own `ESC ] 1337 ; File=…` protocol — its `imgcat` and `imgls` tools exist purely to feed it — and xterm.js, already the terminal under every harness, ssh, and PTY-takeover tab, ships an official addon implementing SIXEL and the iTerm inline image protocol with a kitty-graphics handler behind it. An agent that generates a chart, a screenshot, or a diff image and writes it to its output today produces an escape sequence the terminal drops, so the user sees nothing where the picture should be and no route to it; the image plugin tab (`image-tab.md`) can only show a file the user already knows the path of. Turning on inline image rendering for the terminal surfaces would let the tool the agent already used be seen. Complexity: low-medium.

* Replacing what search finds, the way Zed's project search pairs its global search with replace-next, replace-all and `$1` capture-group substitution, and VS Code offers replace-in-files from the same panel as find-in-files; Helix's long-standing absence of the same feature is the standing counter-example. Janissary can find text in two places and change it in neither: the search tab searches the project's files with regex, case and whole-word toggles and include/exclude globs but has no replace field, no replace-all and no rename-from-results (`search-tab.md` § The results), and the editor's `Cmd+F` overlay is a ten-row case-insensitive subsequence preview with no regex and explicitly "no separate commit step" (`editor-tab.md` § Finding a line) — so even a single-buffer substitution means selecting the text and retyping it. A sweep across a repository or a rename of a symbol used in forty places is exactly what a fleet of agents is asked to do, and the only route today is `sed` typed into a shell. Complexity: medium.

* Undoing a delete or a rename in the file navigator, the way Finder and VS Code's explorer both place a destructive file operation on an undo stack. Janissary already has such a stack for the operations it grew organically: moves are per-tab undo/redo with one bulk move counted as a single step (`file-navigator-tab.md` § Undoing and redoing a move). The two destructive actions are carved out of it — "A user-initiated deletion is not covered by undo/redo", and a rename "is not added to the move undo/redo stack and cannot be reversed with `Cmd+Z`" — so what stands between the user and a lost file is a confirmation dialog (`Delete "<name>"?`) that protects against a mistyped keystroke and nothing else. An agent working in the same workspaced clone deletes a file the navigator had open, and the row is simply gone: no route back, and no notice beyond the deleted name. Pushing deletes and renames onto the history that already exists, holding the previous contents in memory for as long as that history does, would close it. Complexity: low-medium.
