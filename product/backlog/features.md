## ready

* Add a command `file glob ...` accessible to ACP sessions ask and tell - The glob tool locates files by matching their paths against a glob pattern, returning the set of matching file paths without reading any file contents. It accepts a pattern argument written in glob syntax (for example **/*.ts for recursive TypeScript files, src/**/*.test.ts for tests under a src directory, or packages/core/*.{ts,tsx} for brace-expanded extensions), along with an optional path argument that scopes the search to a specific directory (defaulting to the current working directory when omitted), an optional hidden boolean that controls whether dotfiles and hidden directories are included (typically excluded by default), and an optional limit integer that caps the number of returned results (with a sensible default such as 100). The tool searches the filesystem using ** to match zero or more directory segments, * to match within a single path segment, ? to match a single character, and {a,b} alternation for multiple suffixes; it must respect the requested limit by truncating results once the threshold is reached, and it should terminate within a bounded search timeout (commonly around 30 seconds) rather than walking indefinitely across very deep or broad trees. The return value is an ordered list of matching relative or absolute file paths (typically newline- or list-delimited), and when nothing matches it returns an empty result rather than an error, while a missing or invalid path should produce a clear error indicating the directory does not exist. The tool should never follow symlinks into cycles, should skip paths that are excluded by standard ignore rules (such as .git, node_modules, and other VCS-ignored directories) unless explicitly configured otherwise, and should prioritize fast, shallow directory scanning so it can be used repeatedly and cheaply by an agent to discover filenames before reading or editing them. For permission tracking, the tool reports the requested pattern (rather than the search path) as its resource identifier so that authorization rules can grant or deny access based on what is being searched for, and it is intentionally distinct from a grep-style tool: glob matches only file paths by name, never file contents, leaving content search to a separate tool. A robust reimplementation should therefore expose pattern (required), path, hidden, and limit as parameters, return sorted/stable path results, enforce the limit and timeout, honor ignore rules and symlink safety, and document the exact glob semantics (specifically the meaning of ** and whether matching is case-sensitive) so an AI can predictably discover, select, and act on files in a large repository. Operations should act on the relevant workspace (local, remote, sandboxed or not) without the need to recourse to the local machine. 

* Add a command `file grep ...` accessible to ACP sessions ask and tell - The grep tool searches the textual contents of files and returns the locations where a given pattern matches, complementing glob (which matches file paths) by matching what is inside files. It accepts a required pattern argument that uses regular-expression syntax by default (for example log.*Error, function\s+\w+, or TODO), and an optional literal boolean that, when true, treats the pattern as a fixed literal string rather than a regex (useful for searching text like request timed out without escaping metacharacters). Optional narrowing arguments include path to restrict the search to a specific directory (defaulting to the current working directory), include to filter candidate files by a glob such as *.ts or *.{js,jsx}, caseSensitive to control case-insensitive matching (commonly defaulting to case-insensitive), and limit to cap the number of returned matching lines (with a typical default such as 100). The output for each match is a list of results, each carrying the file path, the line number, and a short preview of the matching line (often with the matched substring highlighted or delimited), allowing an agent to jump straight to the relevant source location; the preview should be truncated sensibly for very long lines and binary files should be skipped or reported as non-text rather than searched. The tool should respect standard ignore rules (skipping .git, node_modules, and other VCS-ignored or hidden directories unless configured otherwise), avoid following symlink cycles, and terminate within a bounded search timeout (commonly around 30 seconds) so it can be called frequently and cheaply during exploration. When no matches are found it returns an empty result rather than an error, whereas an invalid or missing path should yield a clear error; a malformed regex should also produce a helpful error message describing the pattern problem rather than silently returning nothing. For permission tracking, the tool reports the requested pattern (not the search path) as its resource identifier so that authorization rules can grant or deny access based on what is being searched for, while access to the actual files read during matching is governed separately. A faithful reimplementation should therefore expose pattern (required), literal, path, include, caseSensitive, and limit as parameters; return file path, line number, and a preview for each match; enforce the limit, timeout, ignore rules, and symlink safety; and document the exact regex engine semantics (e.g., line-oriented matching, whether it defaults to case-sensitive, and whether \s, \w, and lookarounds are supported) so that an AI can reliably locate specific code, configuration values, or error messages across a large repository and then follow up with read or edit on the reported files.  Operations should act on the relevant workspace (local, remote, sandboxed or not) without the need to recourse to the local machine. 


* Add a command `file edit ...` accessible to ACP tell sessions - The edit tool performs a focused, in-place text change to an existing file by locating an exact block of text and replacing it with different text, complementing write (which creates or wholly overwrites a file) and patch (which applies multi-file changes in one operation). It accepts three core arguments: path (the target file), oldString (the exact text to find), and newString (the replacement, which must differ from oldString), plus an optional replaceAll boolean that, when true, replaces every occurrence of oldString in the file instead of requiring a single match. The default behavior is to require that oldString appears exactly once in the file; if it appears multiple times the tool fails with an error asking the caller to supply more surrounding context to disambiguate, and if it appears zero times the tool fails with a "not found" error rather than silently doing nothing. The match must preserve whitespace precisely — including indentation, tabs, and newlines — because the tool does exact string comparison, not fuzzy or regex matching; this means the caller should reproduce the target text character-for-character, typically by first reading the file. On success the tool rewrites only the matched region, leaving all other content byte-for-byte intact, so the change is minimal and localized, and it may optionally run a configured formatter on the file afterward. The tool should return a clear success or failure result (ideally including the line or a short diff context for confirmation), and it must handle common edge cases safely: refusing to edit a file that has not been read first (to prevent hallucinated matches), rejecting empty oldString, and producing a distinct error when the path does not exist or is a directory rather than a regular file. It should never create a new file — that is write's job — and it should not follow or modify symlinks in a way that corrupts the target. For permission tracking the tool reports the target path as its resource identifier, and edits outside the active project location are additionally checked against external-directory permissions. A faithful reimplementation should therefore expose path, oldString, newString, and replaceAll; enforce unique-match semantics by default with replaceAll as the escape hatch; fail loudly on zero or multiple matches with actionable guidance to provide more context; preserve surrounding content and formatting exactly; distinguish "not found", "not unique", and "bad path" as separate, informative errors; and document that it performs literal string replacement only, so that an AI can make surgical, safe edits to source files without accidentally rewriting unrelated lines or clobbering the whole file.  Operations should act on the relevant workspace (local, remote, sandboxed or not) without the need to recourse to the local machine. 


* Add a command `file patch ...` accessible to ACP tell sessions - The patch tool applies a single, multi-file change in one operation, allowing an AI to add, update, move, or delete several files atomically instead of issuing many separate edit/write calls. Its primary input is patchText, a structured block that is divided into sections delimited by marker lines: *** Add File: <path> for creating a new file, *** Update File: <path> for modifying an existing file, and *** Delete File: <path> for removing a file, where each path is typically a repository-relative path such as src/utils.ts. For Add File and Update File sections, the body that follows the marker is the complete new content for that file (for adds) or, for updates, a unified-style diff or a set of @@/context/-/+ hunks that specify exactly which lines are removed and inserted, while Delete File sections contain no body because the entire file is removed. The tool must parse these markers robustly, apply all sections as a single logical transaction, and report which files were created, modified, or deleted, returning a clear error for any section whose target path is missing (for update/delete), already exists unexpectedly (for add, unless overwriting is intended), or whose diff hunks do not cleanly match the current file content — in which case the whole patch should fail rather than leaving the tree partially modified. The tool should support moving a file by pairing a Delete File of the old path with an Add File of the new path (or a dedicated move marker), preserve the exact indentation and newlines supplied in the bodies, and handle directory creation for nested paths. For permission tracking, the tool reports every affected path as its resource (using the same permission action as edit/write), and paths outside the active project location are additionally validated against external-directory permissions. A faithful reimplementation should therefore accept a single patchText argument containing the marker-delimited sections; support at minimum the three operations add, update, and delete (with move expressed as delete-plus-add); apply the changes atomically with rollback on any failed hunk; validate each target path and diff match; return a per-file summary of applied changes with informative, actionable errors on malformed markers, unknown operations, non-matching hunks, or missing files; and document the exact diff syntax and marker format so that an AI can batch a large refactor — such as renaming a module across many files or scaffolding a new feature's file set — into one concise, reviewable, and reversible operation.  Operations should act on the relevant workspace (local, remote, sandboxed or not) without the need to recourse to the local machine.
