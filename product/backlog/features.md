* Add a command `file patch ...` accessible to ACP tell sessions - The patch tool applies a single, multi-file change in one operation, allowing an AI to add, update, move, or delete several files atomically instead of issuing many separate edit/write calls. Its primary input is patchText, a structured block that is divided into sections delimited by marker lines: *** Add File: <path> for creating a new file, *** Update File: <path> for modifying an existing file, and *** Delete File: <path> for removing a file, where each path is typically a repository-relative path such as src/utils.ts. For Add File and Update File sections, the body that follows the marker is the complete new content for that file (for adds) or, for updates, a unified-style diff or a set of @@/context/-/+ hunks that specify exactly which lines are removed and inserted, while Delete File sections contain no body because the entire file is removed. The tool must parse these markers robustly, apply all sections as a single logical transaction, and report which files were created, modified, or deleted, returning a clear error for any section whose target path is missing (for update/delete), already exists unexpectedly (for add, unless overwriting is intended), or whose diff hunks do not cleanly match the current file content — in which case the whole patch should fail rather than leaving the tree partially modified. The tool should support moving a file by pairing a Delete File of the old path with an Add File of the new path (or a dedicated move marker), preserve the exact indentation and newlines supplied in the bodies, and handle directory creation for nested paths. For permission tracking, the tool reports every affected path as its resource (using the same permission action as edit/write), and paths outside the active project location are additionally validated against external-directory permissions. A faithful reimplementation should therefore accept a single patchText argument containing the marker-delimited sections; support at minimum the three operations add, update, and delete (with move expressed as delete-plus-add); apply the changes atomically with rollback on any failed hunk; validate each target path and diff match; return a per-file summary of applied changes with informative, actionable errors on malformed markers, unknown operations, non-matching hunks, or missing files; and document the exact diff syntax and marker format so that an AI can batch a large refactor — such as renaming a module across many files or scaffolding a new feature's file set — into one concise, reviewable, and reversible operation.  Operations should act on the relevant workspace (local, remote, sandboxed or not) without the need to recourse to the local machine. 

* The web search feature is a minimal, provider-agnostic web search capability that is surfaced in Janissary as the command web search <query> [--results n] [--max-chars n] [--provider name] and simultaneously registered to ACP ask and tell sessions as a callable web search tool with a JSON schema exposing a required query string plus optional numResults (int, default 10), contextMaxCharacters (int, default 10000), and provider (default auto-selected), embodying the common core shared by Codex, opencode, and Claude — a query string in, a single relevance-ordered, truncated text context out, with provider differences fully internalized. Search backends are supplied through a plugin framework in which each provider is a plugin implementing a single normalized search({ query, numResults }) method that returns a flat list of { title, url, snippet } results, with bundled providers Tavily and tinyfish available out of the box and additional backends addable by registering a new plugin without modifying core code; the core layer stays provider-agnostic, applying any configured domain filtering, deduplicating, relevance-ordering, and truncating the results to the max-chars budget. The tool executes as a single-call, atomic operation and returns a single plain-text context string — a relevance-ordered list rendering each result's title, url, and snippet inline, formatted for direct insertion into the session prompt, with the structured SearchResult[] flattened and normalized internally so callers never encounter provider-specific response shapes. For time-sensitive queries the current year is treated as 2026, so callers include the year in the query terms rather than relying on the tool to infer freshness. A faithful minimal replication is therefore fully described by the function web-search(query, numResults=10, contextMaxCharacters=10000, provider="auto") -> text, where the same core function serves both the web search ... CLI command and the ACP tool, and providers are pluggable behind a single search() interface with Tavily and tinyfish included. auth tokens for search serves stored in tokens in .janissary/{service}-token like .janissary/tavily-token. search providers plugin api should be documented and versioned.

* Assistant: The web fetch feature is a minimal, mode-flexible URL-fetching capability surfaced in Janissary as the command web fetch <url> [--format markdown|text|html] [--mode local|remote] [--timeout s] [--prompt p] [--max-chars n] [--provider name] and registered to ACP ask and tell sessions as a web_fetch tool whose JSON schema exposes a required url string plus optional format ("markdown"|"text"|"html", default "markdown"), mode ("local"|"remote", default "local"), timeout (int, default 30, max 120), prompt (extraction instruction), maxChars (int, default 10000), and provider (default auto-selected), and it shares the plugin framework and core pipeline — registry, domain filtering, dedup, and truncation — with the existing web search feature so that a single provider plugin supplies both capabilities. The core is described by web_fetch(url, format="markdown", mode="local", timeout=30, prompt=null, maxChars=10000, provider="auto") -> text: in local mode a built-in node-fetch transport makes the direct HTTP(S) connection from the Janissary machine (auto-upgrading HTTP to HTTPS and converting the body to Markdown locally), which means it can reach localhost/LAN hosts and honors the host's firewall, VPN, and proxy rules but leaks the machine's IP and cannot solve bot challenges; in remote mode the request is delegated to a provider's server-side fetch endpoint — Tavily's extract and TinyFish's api.fetch.tinyfish.ai (full-browser rendering returning clean Markdown/JSON/HTML) — which brings provider-side browser/proxy machinery to bear on JS-heavy pages and, to a non-guaranteed degree, bot detection, at the cost of being blind to the operator's private network. Providers are plugins exposing a superset of the search contract, { name, search(params) -> {title,url,snippet}[], fetch(params) -> {url,format,content} }, with Tavily and tinyfish bundled and additional backends addable by registration without core changes; the core normalizes every provider's response shape into a single FetchResult, applying any configured domain filtering, then returns a single plain-text string — the page content as Markdown (or text/html), optionally narrowed by prompt, truncated to max-chars, with oversized pages summarized rather than returned verbatim. The operation is read-only, single-call, and atomic, taking a fully-formed valid URL and never writing files or following multi-step navigation; for time-sensitive retrieval the current year is treated as 2026 so callers include it in query context rather than relying on the tool to infer freshness. A faithful minimal replication therefore needs only web_fetch(url, format, mode, timeout, prompt, maxChars, provider) -> text, where mode selects between local node-fetch and remote provider-API fetching, and the same core serves both the web fetch ... command and the ACP tool, with Tavily and tinyfish available behind the shared plugin fetch() interface.
