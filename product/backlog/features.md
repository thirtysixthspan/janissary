# features

## ready

* support shell tab to operate on remote machine. us 'on' syntax to launch on remote machine just like for agents. when clicking + button on remote harness, a remote shell tab should open in the harness workspace. the remote shell must be sandboxed by default.  

* A new type of AI task that runs in a workspaced agent tab, can spawn and terminate new agent tabs and harness tabs as part of doing its work. the first task would be to call plan-a-new-feature, then build-a-feature, then pull-request-review, then work-an-issue on the pull-request backlog until the backlog is clear. 

* add an ACP skill to allow an agent to spin up other agents with different models, pass them ai tasks (form the repository) to execute and receive the transcript as the agent works, and to recieve the response.

## development

## deferred

* Bundle janissary as a mac application that can be dowloaded and installed into /Applications and launched from an icon in the toolbar.

* integrate https://github.com/nolabs-ai/nono to replace ai and browser sandboxes.

* long term durable transcripts - send trascripts off to seperate github repo? other durable storage options? 

* centralized model selection and usage statistics

* Durable flows across relaunch - capture exit information from a harness and be able to use it to restart a session. a relaunch harness picker. workspace dir would need saved and re-created.

* An OS-level notification, and a terminal bell, when a tab needs the user or finishes, the way Claude Code fires a `Notification` hook with the types `permission_prompt`, `idle_prompt`, `agent_needs_input`, and `agent_completed` and offers `preferredNotifChannel: "terminal_bell"` for terminals that cannot raise a banner — documented explicitly so that "you can switch to other work while a long task runs" — and the widely used `claude-code-hooks` setup goes further, posting a desktop banner and focusing the exact terminal tab on click, suppressed when that tab is already the focused one. `notifications.md` § Delivery model states plainly that there is "still no sound and no OS-level notification": the only surfaces are an in-window toast and the notifications feed, both invisible the moment the window is behind another application, which is exactly when a fleet of background agents is finishing. Raising a native notification for the events Janissary already detects, suppressed when the owning tab is the app's focused tab, would close this. Complexity: low-medium.

* Reopening a tab closed by mistake, the way Warp restores recently closed tabs with `⌘+Shift+T` within a configurable grace period (60 seconds by default) and offers the same from the new-tab button's menu. In Janissary `close`/`exit`, the strip's ×, and `Cmd+W` are all final: the command kills the tab's shell, ACP session, browser, PTYs, and scheduled timers, removes its workspace clone, and drops its in-memory state (`tabs.md` § `close` command), and the deferred durable-flows entry covers restarting a *harness* across relaunch rather than undoing a close inside the run. Keeping a short in-memory ring of recently closed tab descriptors — kind, label, working directory, host, and for a workspaced tab the clone path — plus a `reopen` command and chord that recreates one would recover the common accident without touching the workspace lifecycle rules. Complexity: medium.

* Searching what every tab said, the way iTerm2's Find Globally searches the scrollback of all open tabs at once and Exposé Tabs (`Cmd+Opt+E`) tiles every tab so a search can highlight the one holding the match, and the tmux plugins built on the same idea — `tmux-search-panes` full-text searches the live contents of every pane in every window of every session and jumps to the hit, and `tmux-omni-search` wraps that in an fzf preview with the matching line highlighted. Janissary's search is scoped to the tab issuing it: `Cmd+F` and `search transcript <pattern>` search the current tab's transcript, the `hist` picker walks one tab's last hundred commands with no filtering at all (`history.md` § History picker), and the tab navigator lists displayed names and numbers and nothing else (`tab-navigator.md`). With a dozen agents running, the question a user actually has is "which tab said that", and answering it means scanning the strip for a stopped blink or a flag. A search overlay spanning every open tab's transcript and command history, listing hits with the tab they came from and jumping to the tab and line on Return, would close it. Complexity: medium.

## declined

* Rate-limit awareness for harness tabs — a recognized rate-limit screen, the reset time it states, and a fleet-wide summary of how many tabs are parked and until when — the way amux detects Claude Code's rate-limit prompt across every registered session, records the reset time, badges each blocked session `Rate-limited until HH:MM`, shows a header pill reading `N of M rate-limited, reset HH:MM`, and steers a resume message to each still-parked session once the reset passes. Janissary's `rate-limited` notification event covers ACP queries only, on a best-effort text match, is off by default, and records no reset time (`notifications.md`); a rate-limited harness tab just stops blinking and badges unread, indistinguishable from one that finished its work. Adopting this would mean reading the rate-limit screen out of the captures `harness.md` already takes, parsing the reset time, and showing it on the tab's metadata row and in a summary. Complexity: medium. Decision: harnesses already support auto resume.

* A saved directory of SSH hosts with tags/groups and one-click connect, the way Termius and Royal TSX maintain a host list with saved keys and connection options instead of retyping a destination each time. Janissary's `ssh <destination> [options]` (`product/specs/ssh-tab.md`) is a thin passthrough to the real `ssh` binary with no saved-host concept — every connection is typed from scratch, with tab-completion only covering already-open ssh tabs' labels/destinations, not a saved list of hosts never yet connected to in this session. Determination: Out of scope at the moment

* An in-app diff/merge review UI for a workspaced agent's changes, comparable to Conductor's per-worktree result view and amux's "smart merging" (auto-commit and merge cleanup across parallel branches). Janissary can run any number of `agent -w`/`harness -w` tabs, each with its own git clone (`product/specs/workspaced-agent.md`), but has no way to view a diff of what a given workspace changed, or to merge/cherry-pick it back into the root repo, without leaving the app and inspecting the clone directories by hand. A `workspace diff <label>` command opening a read-only diff view (reusing the editor tab's syntax highlighting) would close this gap. Determination: nope users should not need to know git so intimately

* Multi-user, read-only shared session viewing, the way tmux's multi-attach lets a second person view (and optionally drive) the same session, and Warp's Team Workflows share execution across a team. Janissary already ships a web client serving every tab over HTTP, but the spec surface (`product/specs/tabs.md`, `product/specs/connection.md`) describes a single-user session with no notion of a second, remote viewer watching a running harness or agent tab live — a natural extension given the app is already a served web app rather than a purely local terminal UI. Determination: Cool but low priority.

* A floating, transient terminal overlay for a quick one-off shell command, the way Zellij's floating panes let a user pop open a temporary pane without disturbing the current layout, then dismiss it. Janissary's closest equivalent is PTY takeover (`product/specs/shell.md`), which replaces the whole tab body for an interactive program, or opening a whole new tab — there is no lightweight way to run one quick command in a small overlay without leaving the current tab's context or committing to a new tab. Determinination: nope

* Reusable, parametrized command "workflows" invocable from a command palette, the way Warp's Team Workflows turn a common command into a shared, versioned, named primitive any user can run and tune. This is distinct from janissary's existing `profiles/` (which launch a whole tab topology — harnesses, editors, layout) and `ai/tasks/*.md` (agent prompts run via the task picker, `product/specs/task-picker.md`): a workflow would be a lightweight, parametrized single-command template (e.g. a shell one-liner with placeholders) saved and invoked inline in any tab's command bar, without spinning up a new tab. Determination: nope

* The editor (`product/specs/editor-tab.md`) only supports one caret and one active selection, while VS Code's core editor supports multiple independent cursors for simultaneous edits and column selection. Closing this gap would add multi-caret creation (including keyboard and mouse gestures), rectangular selection, per-caret insertion/deletion, and coherent undo, rendering, and paste behavior. Complexity: medium-high. Determination: nope

* The editor (`product/specs/editor-tab.md`) has syntax highlighting and fuzzy search within the current buffer but no language-aware symbol navigation, while VS Code combines language services with Go to Symbol, Go to Definition/References, Peek, Outline, and breadcrumbs. Closing this gap would add a pluggable language-service/indexing layer and editor commands for symbol search, definition/reference jumps, and the current file's symbol outline. Complexity: high. Determination: the editor is general purpose not specifically a code editor.

* The browser automation feature (`product/specs/browser.md`) exposes goto, rendered content, eval, and screenshots but does not retain an inspectable action history or browser diagnostics; Playwright Trace Viewer provides a timeline with DOM snapshots, screenshots, console messages, network requests, and action details. Closing this gap would add an opt-in per-window trace/inspection mode with a replayable timeline and links from each action to its DOM, console, network, and screenshot evidence. Complexity: high. Determination: low value at this point in time.

* The shell transcript (`product/specs/shell.md`, `product/specs/transcript.md`) is line-oriented and can rerun a prompt by double-click, but it does not expose command-level duration, exit status, or a selectable command-plus-output block; iTerm2's shell integration supplies command selection and an info panel with duration, status, resend, copy, share, and named marks. Closing this gap would track command boundaries and completion metadata, then add block selection with copy/rerun/bookmark actions and a compact command-info view. Complexity: medium. 

* An "attention" jump to the next tab that is waiting on the user, the way claude-tmux ships `claude-tmux next-attention` and an `A` filter that narrows its dashboard to the panes blocked on a permission request, a notification, or a question. Janissary already knows which tabs those are: a recognized harness permission prompt stops the busy dot and badges the tab unread (`harness.md` § Busy/ready status), an agent question is a per-tab pending panel (`agent-questions.md`), and any new content delivered to a hidden tab raises the unread badge (`tabs.md` § Unread badge) — but nothing acts on that knowledge, because `next` and the tab navigator walk every non-docked tab in strip order, so the only route to a blocked tab is scanning the strip for a stopped blink or a flag icon. An `attention` command and chord that focuses the next tab in one of those states and skips the rest would make the detection pay off. Complexity: low-medium.

* A preview of the highlighted tab's content inside the tab navigator, the way tmux's tree mode splits the window and shows "a preview of the area around the cursor in each pane" beneath the tree, and claude-tmux's dashboard offers the same as a togglable `p` preview pane. `nav` / `Ctrl+G` (`tab-navigator.md`) lists only displayed names and tab numbers, so choosing between three busy agents means remembering which is which — the one thing the strip's colored dots and unread flags exist to answer at a glance. The material is already in hand: the latest rendered screen of every harness and ssh tab is held in memory for `harness capture` and for monitor feeds (`monitoring.md` § Transcript access), and an agent tab's last few transcript lines are its own. Complexity: medium.

* A shared, agent-writable notes surface, the way amux's Notes tab is "a document store that every session can read and write" for shared context, research notes, and handoff documents between agents, and Claude Code keeps per-project memory files agents read and extend. In Janissary cross-agent knowledge moves only as `msg`/`broadcast` text appended to a recipient's `context[]` (`messaging.md`), which lives and dies with that tab; the only durable shared knowledge is the repository's own `AGENTS.md` and whatever an agent commits to its own workspace clone, so a finding one agent establishes is invisible to a sibling agent and to the next run. A small per-project note store an agent can append to through a command, browsable as a tab, would give the fleet somewhere to put what it learns. Complexity: medium.

* Per-tab permission rules for a harness instead of the single all-or-nothing auto-approve toggle, the way Claude Code evaluates three ordered rule lists — deny, then ask, then allow — with specifiers like `Bash(npm run build)`, `Read(./.env)` and `WebFetch(domain:example.com)`, glob patterns inside them, and a `/permissions` view listing every rule and the file it came from. Janissary's `harness.md` § Auto-approve permissions offers exactly one bit per tab: a recognized prompt is answered automatically, and the spec's own justification is that the disposable workspace clone keeps that low-risk. That leaves the interesting cases unexpressible — approving the read-only and build commands in an unattended overnight run while still stopping to ask about `git push`, `rm -rf`, or a network call, which is the configuration that would make `--no-workspace` tabs and background agents far less nerve-wracking. A per-tab list of allow/ask/deny patterns the auto-approve path consults before it answers would close it. Complexity: medium.

* Clickable links in terminal output and in the transcript, the way WezTerm turns a URL in the scrollback into a link through its `hyperlink_rules` — regex, a format string with capture-group placeholders, and an optional highlight group — and also honours the OSC 8 escape sequence, and its built-in defaults already cover bracketed URLs and bare `user@host` addresses. xterm.js, which every harness, ssh, and PTY-takeover terminal already runs on, ships both halves: a `WebLinksAddon` that pattern-matches URLs and a `linkHandler` for OSC 8, plus a hover popup showing the real destination when the visible text is not the URL. Janissary renders `file:line` patterns as clickable links (`transcript.md` § Clickable file:line links) but a web address in output or in a markdown reply is inert text, and the destination — a page tab — already exists through `open <url>`. Enabling link handling on the terminal surfaces and adding URL matching alongside the file-link rule is the whole of it. Complexity: low-medium.

* Context-window occupancy and summarization for the sessions Janissary hosts itself, the way Claude Code pairs a live occupancy indicator with `/context` to diagnose what is filling the window, `/compact` to summarize it, and an automatic compaction that fires on approach to the limit and gives up after three consecutive failures rather than looping. Janissary's own ACP sessions have no equivalent: `acp` accumulates every prompt and reply until it either dies or is thrown away wholesale by `acp reset` (`acp.md`), and a conversation does the same, starting a fresh session that replays the twenty most recent turns (`conversations.md` § Sessions, failures, and cancellation). Nothing tells a user how full a session is, so the only warning is the model's own degradation or a hard failure partway through. Reporting occupancy on the session's chip and compacting to a summary — or letting the user ask for it — would make a long-lived agent tab survivable. Complexity: medium-high.

* An approval level and a model control for a tab's own ACP session, the two session controls the Agent Client Protocol defines: `setSessionMode`, which changes how much the agent may do without asking, and `unstable_setSessionModel`, which changes the model mid-session — both surfaced as ordinary UI by Gemini CLI's ACP mode and by JetBrains AI Assistant's ACP settings. Janissary exercises neither. Its permission handler denies every ACP tool-permission request, with only a persona's narrow web-tool allowlist as an exception (`monitoring.md` § Persona web tools), and the model is chosen once at connect from the harness catalog with no way to change it while the tab runs (`acp.md` § Which model runs). This is a per-session control on a session janissary already owns, not a central model picker — the model an ACP session runs is currently the one thing about it the user cannot influence at all. Complexity: medium.

* Exposing the application's own capabilities to an ACP agent as tools over the protocol, the two-way integration ACP was designed around: Gemini CLI's ACP mode documents that a client may implement an MCP server, hand its connection details in the `initialize` handshake, and have the agent discover and call those tools, and JetBrains exposes the same through `use_idea_mcp` with an `idea_mcp_allowed_tools` allowlist to restrict what the client offers. Janissary is the richer side of that bargain and offers the agent nothing: an ACP agent's entire tool surface is the three commands its primer teaches it — `browser`, `question`, and `db` (`acp.md` § Database and browser assistance) — even though the tab's own file navigator, editor, schedule, tab, and connection commands are all right there and reachable by the human standing next to it. Registering the commands a session may expose, filtered by the same sandbox boundary the tab already runs under, would let an agent open a file, inspect another tab, or add a schedule without a bespoke grammar per capability. Complexity: high.

* Schedules triggered by a change rather than by a clock, the way GitHub Actions runs a workflow on `push` narrowed by `paths:` and `paths-ignore:` glob filters, so a job fires only when the files it cares about are the ones that moved. Janissary's scheduler is time-only in all five of its forms — `at`, `on <date>`, `every <N>`, `every day at`, `every <weekday> at` (`scheduling.md` § Schedule forms) — so the natural "run this when *that* changes" automation has no form at all and the user can only approximate it by polling on a short interval. The material is already running: every visible directory of every open file navigator is watched and refreshed within about a second (`file-navigator-tab.md` § Watching), and the scheduler already has a one-second tick, debouncing, a queue that drains per tab, and a schedule window that reports each entry's next run. A `schedule <name> when <paths> <cmd>` form taking the same include/exclude globs the search tab already uses would close it. Complexity: medium.

* Catching up and reporting a schedule whose owning tab was not open, the way a systemd timer with `Persistent=true` runs the trigger it missed while the machine was down and reports it, and anacron exists for the same reason under cron. Janissary already handles the machine-asleep case carefully — an overdue entry runs once on wake and records `<command> ran <duration> late (system was asleep)` in the notifications feed (`scheduling.md` § Sleep and overdue commands) — but the far more common case in a tab-based workspace is the tab simply not being there: a firing for an agent that is not currently open as a tab is skipped with no record at all, leaving the entry in the state file to run whenever that tab next opens and happens to be due, and a harness tab's schedule is memory-only and simply ceases to exist when the tab closes. A recurring `standup` silently skipping every day because the tab was closed is the failure this closes, by running the missed entry on reopen the way the sleep path already does, and by saying so when it cannot. Complexity: low-medium.

* Putting a workspaced clone onto a chosen branch, and getting work back out of it when an agent has gone wrong, the way VS Code's source control view and GitHub Desktop both make branch switching, stashing, and discarding inline actions on the repository rather than something to do in a shell. Janissary's file navigator reads git thoroughly and never writes the branch: its header shows the checked-out branch, colors rows by status, pulls, commits, and pushes, and a commit always lands on whatever branch the clone happens to be sitting on (`file-navigator-tab.md` § Branch metadata and § Committing to origin). A `-w` clone is created fresh from `origin`, so pointing a workspace at an existing feature branch, recovering work an agent abandoned, or throwing its changes away are all manual steps outside the app — the same work `profile launch` and `agent -w` set a user up to do. A branch control on the navigator header and a discard or stash action for the current changes would close it. Complexity: medium.

* Images drawn in terminal output, the way iTerm2 renders them inline from its own `ESC ] 1337 ; File=…` protocol — its `imgcat` and `imgls` tools exist purely to feed it — and xterm.js, already the terminal under every harness, ssh, and PTY-takeover tab, ships an official addon implementing SIXEL and the iTerm inline image protocol with a kitty-graphics handler behind it. An agent that generates a chart, a screenshot, or a diff image and writes it to its output today produces an escape sequence the terminal drops, so the user sees nothing where the picture should be and no route to it; the image plugin tab (`image-tab.md`) can only show a file the user already knows the path of. Turning on inline image rendering for the terminal surfaces would let the tool the agent already used be seen. Complexity: low-medium.

* A palette over the application's own commands, the way Warp's Command Palette (`⌘+P`) searches workflows, prompts, notebooks, keyboard shortcuts, settings and sessions in one list, narrowing with typed prefixes (`workflows:`, `files:`, `sessions:`, `actions:`), and iTerm2's Open Quickly (`Cmd+Shift+O`) searches tab titles, command names, hosts and directories — and, entered with a leading `/`, lists every command the application answers to. Janissary's command surface is large and entirely undiscoverable: `open`, `files`, `search`, `edit`, `nav`, `hist`, `agent`, `acp`, `queue`, `msg`, `broadcast`, `send`, `schedule`, `monitor`, `monitors`, `sessions`, `conversations`, `sql`, `connection`, `browser`, `db`, `profile`, `harness`, `tasks`, `notifications`, `theme` and the rest are documented only by `help`, which reads a markdown file out of the repository (`application-commands.md`), while every fuzzy finder that does exist covers exactly one narrow set of things — Quick Open for files (`quick-open.md`), `nav` for tab names (`tab-navigator.md`), `hist` for commands this tab already ran (`history.md`), the task picker for task files (`task-picker.md`). The list is already materialized: the command registry the router resolves every input against (`command-routing.md` § Recognizers) is the same source `help`'s generated fallback enumerates. One overlay that fuzzy-matches commands, their usage strings and their argument names, and inserts rather than submits on Return the way the task picker does, would make the app's own vocabulary learnable without leaving the keyboard — and is distinct from the declined reusable-workflows idea, which is about authoring new templates rather than reaching the ones already shipped. Complexity: medium.

* Attaching a picture to an agent prompt, the way Claude Code accepts images three ways — drag a file into the input, paste a screenshot from the clipboard, or reference it with `@path` — showing each attachment as an `[Image #N]` placeholder with an in-terminal preview and enforcing real limits (5 MB and 8000×8000 px per image, up to 100 images and 32 MB per request); Warp's agent input carries image attachments on the same multiline editor it uses for prompts and shell commands. Janissary holds both halves of the plumbing and no path between them: an `image` tab can display a picture (`image-tab.md`), `browser shot` writes a viewport PNG and hands it to Preview outside the app (`browser.md` § Actions), and the Agent Client Protocol the agent tabs already speak defines image content blocks — but nothing turns a file, a screenshot, or a pasted clipboard image into one, so the only way to show an agent what something looks like is to describe it or paste a path as text. Reviewing an agent's layout change is the everyday case the capability exists for, and the `-b` end-to-end browser makes the picture easy to produce and impossible to send. Complexity: medium.

* Interrupting a turn in flight, the way Claude Code's `Esc` "stop[s] the current response or tool call mid-turn so you can redirect" and "Claude keeps the work done so far" — cancelling the turn rather than the session, keeping the accumulated context so the next message can redirect the work, and then sending anything that was queued while the turn ran. Janissary's agent tabs have no equivalent: while an `acp` turn streams there is nothing to press and nothing to type, the command queue only engages on an already-busy tab, and the small list of commands that bypass that queue contains no stop (`agent-command-queue.md` § Queueing and draining and § What never queues), while the only way to abandon a turn is `acp reset`, which "kills the current tab's ACP subprocess and forgets the session" and discards the accumulated context with it (`acp.md` § `acp reset` command). The conversation tabs already have the interaction — Escape cancels a streaming reply and discards the partial turn (`conversations.md` § Sessions, failures, and cancellation) — so the app knows the shape of it and does not offer it on the surface where long unattended runs actually happen. An interrupt that stops the current turn, keeps the session and its context, and leaves the command line ready for a redirect would close it. Complexity: medium.

* A per-project environment file that every tab in the fleet inherits, the way direnv checks the current directory and its parents before each prompt for a `.envrc` (or `.env`), loads the exports it finds into a subshell, and unloads them again on leaving the directory — with `direnv allow` as the explicit grant that stops a freshly cloned repository from exporting whatever it likes. Janissary spawns each tab's shell with the environment otherwise left alone (`shell.md` § Shell command execution), so the only variables a tab reliably gets are the ones the app adds for every spawn: the install root, the workspace temp dir, provider credentials and git identity (`sandbox.md` § Environment scrubbing). A project's API keys, `DATABASE_URL`, `PATH` additions or tool version pins therefore have to be retyped per tab or handled by each agent in turn, and across a workspaced fleet every agent sits in a fresh clone with no memory of the last one's environment — the injected tokens are the only variables guaranteed to agree. Reading a project env file (or honouring `.envrc`) at shell, harness and ACP spawn, gated on the same explicit-allow idea direnv uses, would give every tab in a project the same starting environment without editing anyone's shell profile. Complexity: low-medium.

* Replacing what search finds, the way Zed's project search pairs its global search with replace-next, replace-all and `$1` capture-group substitution, and VS Code offers replace-in-files from the same panel as find-in-files; Helix's long-standing absence of the same feature is the standing counter-example. Janissary can find text in two places and change it in neither: the search tab searches the project's files with regex, case and whole-word toggles and include/exclude globs but has no replace field, no replace-all and no rename-from-results (`search-tab.md` § The results), and the editor's `Cmd+F` overlay is a ten-row case-insensitive subsequence preview with no regex and explicitly "no separate commit step" (`editor-tab.md` § Finding a line) — so even a single-buffer substitution means selecting the text and retyping it. A sweep across a repository or a rename of a symbol used in forty places is exactly what a fleet of agents is asked to do, and the only route today is `sed` typed into a shell. Complexity: medium.

* Queuing a message for a harness that is busy, and being able to see and withdraw it, the way Claude Code accepts a message while it is still working — "Claude Code queues the message instead of interrupting the turn, and lists the queued entries above the input box until it sends them" — and sends the whole queue immediately once the turn is interrupted (`code.claude.com/docs/en/interactive-mode`). Janissary's agent tabs have a real queue for this, with `queue` and a `Ctrl+E` popup listing what is pending, and harness tabs are explicitly excluded from it: "Non-agent tabs (harness, image, page, markdown, editor, files, monitor) have no queue" (`agent-command-queue.md` § What never queues). The one route in, `send`, is fire-and-forget — "there is no read-back of the target's output into the sender's transcript" (`send.md` § Output) — so a follow-up typed at a Claude Code tab that is mid-build is neither confirmed, nor listed, nor withdrawable, and the user cannot tell a harness that received it from one that never saw it. Extending the queue popup that already exists to harness tabs, so a pending `send` is visible and removable until the target goes idle, would close it. Complexity: low-medium.

* Acting on a set of tabs in one command, the way tmux's target grammar names a selection rather than one pane — `-t <name>` accepts a glob so a single `send-keys -t 'agent*'` or `kill-window -t agents` reaches every match, the special tokens `{start}`, `{end}`, `{next}`, `{previous}` and `{current}` stand in for a range, `-f <filter>` narrows a command to those whose format string matches, and `kill-session -g` destroys every session in a session group at once. Janissary targets exactly one tab almost everywhere: `close <name>` takes the first match in strip order (`tabs.md` § `close`), and `queue`, `send`, `schedule … in <tab>` and `msg` each resolve a single label or display alias (`agent-command-queue.md`, `send.md`, `scheduling.md` § Targeting another tab). `broadcast` is the only command that takes a set, and `group:<n>` the only set-shaped target anywhere — available to monitors alone (`monitoring.md` § Starting a monitor) — while a tab's group is inherited from whichever tab created it or handed out by a profile, with nothing to form one by hand (`tabs.md` § Tab grouping). Regrouping five agents and restarting them, or closing everything left in group 3, is a sequence of single-tab commands typed one at a time. Letting the target words that already exist name a group or a glob wherever a bare label is accepted would close it. Complexity: medium.

* Undoing a delete or a rename in the file navigator, the way Finder and VS Code's explorer both place a destructive file operation on an undo stack. Janissary already has such a stack for the operations it grew organically: moves are per-tab undo/redo with one bulk move counted as a single step (`file-navigator-tab.md` § Undoing and redoing a move). The two destructive actions are carved out of it — "A user-initiated deletion is not covered by undo/redo", and a rename "is not added to the move undo/redo stack and cannot be reversed with `Cmd+Z`" — so what stands between the user and a lost file is a confirmation dialog (`Delete "<name>"?`) that protects against a mistyped keystroke and nothing else. An agent working in the same workspaced clone deletes a file the navigator had open, and the row is simply gone: no route back, and no notice beyond the deleted name. Pushing deletes and renames onto the history that already exists, holding the previous contents in memory for as long as that history does, would close it. Complexity: low-medium.
