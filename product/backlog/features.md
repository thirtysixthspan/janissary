# features

## ready

* Add a single-select multiple-choice question to the question tool. The tool currently offers only `ask` (a free-text field) and `approve` (one button per label), so an agent cannot present a real choice list or offer a free-form alternative alongside choices (`product/specs/agent-questions.md`, `src/questions.ts`, `web/src/shared/questions/QuestionPanel.tsx`). Introduce a `question choose "<question>" <option> [<option> …]` command and a matching Janissary question-tool kind that render the labels as a radio-style single-answer list, always offer "Type your own answer" as an alternative to the listed options, and return one value — the chosen label or the typed text — to the caller. Include command parsing and the agent primer (`src/question-command.ts`, `QUESTION_PRIMER`), the role/command inventory, the protocol and panel UI with its keyboard navigation, and the functional spec, so the feature is usable end to end on its own. Estimated complexity is medium because the panel and the command/tool surface must land together.

* Add a multi-select checkbox question to the question tool. Extend the question surface with a `question pick "<question>" <option> [<option> …]` command and Janissary tool kind that render the labels as checkboxes, accept any number of selections, and always offer "Type your own answer" as an alternative that returns the typed text instead of a list. Deliver the structured answer result end to end in this item — the protocol and answer type, `Questions.answer` validation, `QueuedQuestion.resolve`, and the RPC wire format must carry either one value or a list of selected labels — along with the panel UI, command parsing, primer, role/command inventory, and spec, while the existing `ask`/`approve` behavior and keyboard navigation keep working. Estimated complexity is medium-high because the answer type changes end to end and every consumer must stay green.

* Let one question call ask several questions at once. The question manager currently holds one pending question per tab with a queue, and both the `question` command and the Janissary question tool accept a single question (`src/questions.ts`, `src/question-command.ts`, `web/src/shared/questions/QuestionPanel.tsx`, `product/specs/agent-questions.md`). Accept an array of questions per call, each with a short header, its own kind and options, and its own id, so the panel presents them as one grouped form and returns one consolidated, id-correlated result, with Cancel and per-tab queueing still working. Include the command and tool syntax, primer, protocol, panel UI, role/command inventory, and spec in this item so batching functions end to end. Estimated complexity is high because grouping changes answer correlation, cancellation, and focus handling across tabs.

## development

* Persist the orchestrator's recorded state to a file. build-a-complex-feature.md Step 6.2 asks the orchestrator to keep the full text of every backlog entry and the head SHA in context before repairs. Across dozens of fresh subagents that is fragile. Have the task write them to ./temp/ (entry text, head SHA, classification) and read from there.

* Save and restore workspace checkpoints. Cline can compare a saved checkpoint against project files and restore the files while keeping the conversation. Janissary's disposable workspace clones isolate changes, and the Diff tab shows their current Git changes (`product/specs/workspaced-agent.md`, `product/specs/diff-tab.md`). Let users mark a checkpoint in a workspaced harness, preview the changes a restore would make, and confirm restoring those files so they can try another approach in the same session. Estimated complexity is high because a restore must account for tracked and untracked changes and concurrent edits. [Cline checkpoints](https://github.com/cline/cline/blob/main/docs/core-workflows/checkpoints.mdx)



* Run a project setup script when a new workspace is provisioned. Conductor runs a repository-specific setup script after checkout to install dependencies or generate files. Janissary provisions a clean clone for a workspaced shell or harness, and profiles can launch a sequence of application commands (`product/specs/workspaced-agent.md`, `product/specs/profiles.md`). Let a project opt into a setup script that runs inside each new workspace before its first shell or harness starts, and show setup progress and failures alongside clone progress. Estimated complexity is high because setup has to participate in readiness and cancellation on both local and remote hosts. [Conductor workspace setup scripts](https://www.conductor.build/docs/reference/scripts#setup-scripts)

* Show model token usage on connection records. LangSmith shows input and output token counts for individual runs and rolls them up for a trace. Janissary retains prompts and activity in its ACP connection and agent-run records, and its monitor reports context size in bytes (`product/specs/acp-records.md`, `product/specs/connections-tab.md`, `product/specs/monitoring.md`). Add per-prompt counts and connection totals wherever the underlying harness reports usage, with a clear unavailable state for other sessions. Estimated complexity is medium-high because the records span several harnesses and local and remote runs. [LangSmith token and cost breakdowns](https://docs.langchain.com/langsmith/cost-tracking#token-and-cost-breakdowns)

## deferred

* Show a run history for system schedules. GitHub Actions lists past runs by workflow and opens each run's status and logs. Janissary's Schedules tab lists upcoming occurrences, and the firing notice means the runscript was queued (`product/specs/scheduling.md`, `product/specs/notifications.md`). Give each system schedule a retained history of its occurrences, with queued, completed, failed, or missed outcomes and a link to the relevant output when available. Estimated complexity is high because each queued line needs to contribute to the outcome of the right occurrence. [GitHub Actions run history](https://docs.github.com/en/actions/how-tos/monitor-workflows/view-workflow-run-history)

* Expose role tools to ACP models as direct MCP tools
Every tool a role grants to an ACP session becomes a real MCP tool advertised straight to the model in the provider's tool list, with no Code Mode indirection. The model calls those tools through the provider's native tool-calling channel; OpenCode executes them against a Janissary-owned MCP server; the server runs the corresponding Janissary role tool and returns the result. The same works for local and remote ACP sessions, and each tool call and result is rendered as a tool entry in the connection transcript. The current mechanism — primed text commands extracted from the model's final reply line, run by `runAcpToolLoop`, with `acp-tool-request`/`acp-tool-result` frames on the remote channel — is removed entirely.

* Bundle janissary as a mac application that can be dowloaded and installed into /Applications and launched from an icon in the toolbar.

* Durable flows across relaunch - capture exit information from a harness and be able to use it to restart a session. a relaunch harness picker. workspace dir would need saved and re-created.

* the SQL browser's console (`product/specs/sql-database.md`) has no completion at all ("Tab here does not complete a word: there is nothing in this tab for a word to be completed against"), and the spec rules out a query builder or statistics panel; DBeaver's SQL Assist autocompletes table and column names, SQL keywords and functions from the database catalog, and its ER diagrams and visual query builder make the schema explorable and composable. Closing this means adding schema-aware autocomplete to the console using the connection's own catalog, with an ER diagram view of the selected database as a larger follow-on. Complexity: medium for autocomplete, high for a diagram view.

* the editor tab (`product/specs/editor-tab.md`) colors text for a handful of languages but offers no code navigation: no go-to-definition, symbol outline or breadcrumbs, no bracket matching or folding, and indentation is a fixed two spaces with nothing auto-closing as you type. VS Code's editor jumps to a symbol's declaration with F12, lists every symbol in the Outline view, highlights matching brackets and folds regions, and auto-closes brackets and quotes. Closing this means wiring a language server or a lightweight symbol index for the editor's supported languages so symbols can be jumped to and listed, plus the cheaper editor affordances IDE users treat as table stakes. Complexity: high.

* Jump between commands and copy their output in shell scrollback. iTerm2's shell integration can move to the previous or next command and select the output of one command as a block. Janissary's shell tab already recognizes command-start and prompt markers, offers line-based scrollback search, and copies manually selected terminal text (`product/specs/shell-tab.md`). Use those markers to support previous and next command navigation and copy a completed command's output without its prompt. Estimated complexity is medium because the markers and output ranges must stay aligned as the terminal wraps lines and trims scrollback. [iTerm2 command selection](https://iterm2.com/documentation-command-selection.html)

## declined


* Compare two Git revisions in the Diff tab. VS Code's Source Control Graph can compare a selected commit with a branch or tag through a reference picker. Janissary's Diff tab shows working-tree changes, staged changes, or the most recent commit against its first parent (`product/specs/diff-tab.md`). Add a base and target picker for available branches, tags, and commits so users can review a workspace branch against its base without checking out either revision. Estimated complexity is medium because the picker can feed the existing multi-file diff view. [VS Code commit comparison](https://code.visualstudio.com/docs/sourcecontrol/history#compare-a-commit-with-a-branch-or-tag)

* Branch a saved conversation from a completed turn. The Claude Agent SDK can fork a session up to a selected message into an independently resumable thread. Janissary saves completed conversation turns and can seed a new chat with selected text through Chat about this (`product/specs/conversations.md`, `product/specs/context-menu.md`). Add a turn action that opens a new conversation carrying the history through that turn, with its own session and private workspace, so a user can explore an alternative from the same context. Estimated complexity is medium because the branch can reuse the existing conversation history and replay model. [Claude Agent SDK session forking](https://platform.claude.com/cookbook/claude-agent-sdk-05-building-a-session-browser)

* Jump directly to the most recent unread tab. cmux has a shortcut that focuses the workspace with the newest unread notification. Janissary marks background tabs unread, lets users find tabs by name or number, and links to tabs from some notification types (`product/specs/tabs.md`, `product/specs/tab-navigator.md`, `product/specs/notifications.md`). Add a keyboard action that focuses the most recently badged eligible tab, so a user can respond to a waiting harness without hunting through tab names or opening the feed. Estimated complexity is low-medium because tab activation already exists and the unread state would need recency ordering. [cmux notifications](https://cmux.com/docs/notifications#notification-panel)

* the search tab (`product/specs/search-tab.md`) searches the whole project with regex, case and whole-word toggles but is read-only and shows no match tally ("There is no tally: the header shows no count of matches or files"); VS Code's Search view has a Replace box beside the query, previews a diff of the pending edits, and replaces one match, all in one file, or across the workspace, alongside a "N results in M files" count. Closing this means adding a replace field with a diff preview and per-match/per-file/replace-all actions, a result count in the header, and some signal for when the silent 250-match cap is hit. Complexity: medium-high.

* the history picker (`product/specs/history.md`) lists recent commands for Up/Down navigation only, and the global history carries no context beyond the command text; iTerm2's shell integration exposes a searchable command-history popup, while Atuin fuzzy-searches a context-rich history recording the directory, exit code and duration of every command. Closing this means giving the picker a query field with fuzzy/substring filtering over the global history and showing the directory and result of each command on its row, so a command from another tab or an earlier run can be found by typing rather than by walking a capped list. Complexity: medium.

* the file navigator's Search files pop-up (`product/specs/file-navigator-tab.md`) matches a case-insensitive substring of the filename only, ranks by prefix then shortest path, and exposes a single best match with no result list; VS Code's Quick Open does fuzzy subsequence matching over the full relative path and shows a ranked list you can arrow through. The application's own global Quick Open (`product/specs/quick-open.md`) already implements that fuzzy path ranking and ten-row list — closing this means reusing the same matcher and result presentation inside the navigator's pop-up so searching a tree feels like Go to File rather than one best guess. Complexity: low-medium.

* the markdown tab (`product/specs/markdown-tab.md`) renders a one-time snapshot with no heading navigation, no clickable relative links and no update when the file changes on disk ("later edits to the file on disk are not reflected until it is opened again"); Obsidian's reading view has an Outline/table of contents, live internal links with backlinks and page previews, and VS Code's Markdown preview follows the source as it is edited. Closing this means building a heading outline with jump-to-heading, resolving relative links (images and .md files) into open actions, and watching the source file so the rendered view refreshes on external change. Complexity: medium.

* the browser command (`product/specs/browser.md`) can navigate, read rendered text, eval JavaScript and take a viewport screenshot, but exposes no inspection of what happened — no DOM snapshot, network request list, console messages or locator picker; Playwright's Inspector and Trace Viewer provide all of these with a timeline you can step and scrub through. Closing this means recording a lightweight trace per window (requests, console output, DOM snapshots) and adding subcommands or a viewer tab that lists and inspects it, so browsing by the user or an agent can be debugged after the fact rather than only through `browser eval`. Complexity: high.

* the diff tab (`product/specs/diff-tab.md`) is deliberately read-only ("nothing in the tab stages, discards, or commits"), so acting on a reviewed change always means leaving the tab for a shell or the file navigator; VS Code's Source Control view and diff editor let you stage or revert an individual hunk or selected lines right where you are reading them. Closing this means adding per-hunk stage/discard actions that use the same git plumbing the navigator's commit-to-origin already relies on, with the affected row updating in place after the operation. Complexity: medium.

* the editor tab (`product/specs/editor-tab.md`) has a Cmd+F find overlay, but matching is case-insensitive contiguous substring with "no regex, case, or whole-word options" and no replace — VS Code's editor find has all three toggles, a replace field with replace-one/replace-all, and a visible match count. Closing this means adding the toggles and a replace row to the editor's find overlay, with in-buffer highlighting and one undo step per replace, much as the project search tab already offers regex/case/whole-word toggles for the whole codebase. Complexity: medium.
