# features

## ready

* Shift the ACP tool loop from reading a bare command on the reply's last line to reading it from a labelled fenced block, while still allowing only one command per turn. The agent is told to place its one command inside a final block tagged with a known label; the host reads only the last such closed block and treats zero or multiple commands in it as a correctable mistake rather than ending the turn. Prose after the command no longer terminates the loop, arguments can span multiple lines, and a command echoed twice no longer leaves a stray copy in the transcript. The two extraction paths — the core host loop and the agent-driven path that today ignores fenced content — converge on the same block rule, and the old top-of-line marker becomes redundant inside a block.

* Expose role tools to ACP models as direct MCP tools
Every tool a role grants to an ACP session becomes a real MCP tool advertised straight to the model in the provider's tool list, with no Code Mode indirection. The model calls those tools through the provider's native tool-calling channel; OpenCode executes them against a Janissary-owned MCP server; the server runs the corresponding Janissary role tool and returns the result. The same works for local and remote ACP sessions, and each tool call and result is rendered as a tool entry in the connection transcript. The current mechanism — primed text commands extracted from the model's final reply line, run by `runAcpToolLoop`, with `acp-tool-request`/`acp-tool-result` frames on the remote channel — is removed entirely.
Design decisions
1. **MCP is the tool channel; ACP is the session channel.** ACP has no "client executes an arbitrary tool" request, and OpenCode's ACP mode explicitly does not support MCP over ACP. Janissary therefore runs a real MCP server and passes its connection config in `mcpServers` on `session/new`. ACP remains responsible only for prompts, session updates, and permission decisions.
2. **One MCP server per ACP connection, owned by the connection.** `connectAcp` starts the server before the `initialize`/`newSession` handshake and closes it in `kill()`, `shutdown()`, and on the ACP child's `exit`/`error`. This gives the server exactly the lifetime of the ACP connection and one isolated port and token per session. The server is bound to `127.0.0.1` on an ephemeral port with a random bearer token passed in the HTTP `headers` of the `mcpServers` entry.
3. **The server lives in the process that owns the ACP client.** Locally that is the main Janissary process; for a remote tab or agent it is the `janus remote-serve` process, because `RemoteAcp.open()` in `src/remote/serve-acp.ts:39` is where the remote `connectAcp` runs. This keeps `connectAcp` the single creation point for local and remote sessions and gives the MCP tool handlers direct access to the host's Janissary services.
4. **Helpers are not spawned and the workspace is not the server's sandbox.** The server runs in the owner process and reaches workspace-side tools through the existing workspace-aware executors (which already use `tab.workspaceDir` or the run's execution directory). We do not add a `janus mcp-serve` child or a second sandbox boundary; Seatbelt confinement of the ACP agent is unchanged.
5. **The server's tool set comes from the role snapshot, not from config.** `AcpManager.run` already snapshots the role's `commands` grants and the effective native-command settings once per prompt (`src/acp/manager.ts:132`, `src/acp/run-prompt.ts:37`). That snapshot is converted into an MCP tool list containing only granted, enabled tools. A `withoutTools` session gets no MCP server at all: no tools, no port, no `mcpServers` entry.
6. **OpenCode Code Mode is removed with a permission rule, not a server flag.** ACP's `McpServer` schema has no `codemode` field, so an ACP-declared server is always Code Mode. OpenCode's documented way to force direct tools is to deny `execute` with resource `*`, which removes Code Mode and lists the MCP tools directly. `opencodeDenial` in `src/acp/internal-tools.ts:60` must change from the V1 `permission: 'deny'` string to V2 ordered `permissions` rules: deny `*` so no built-in or provider tool runs, deny `execute` so Code Mode is gone, then allow `janissary_*` so our tools pass. The last matching rule wins, and the MCP permission action is `<server>_<tool>` with resource `*`, so a server named `janissary` and tools named `db_sqlite_query` etc. give actions like `janissary_db_sqlite_query`.
7. **Permission handling stays deny-by-default for everything else.** `requestPermission` in `src/acp/index.ts:99` keeps denying any tool that is not ours; the allow rules in decision 6 should prevent a prompt for our tools, but the handler also recognizes the `janissary` server prefix as a narrow backstop. Monitor personas keep their existing `web_search`/`web_fetch` allowances; those are provider tools, not role tools.
8. **One tool definition module is the single source of truth.** A new `src/acp/mcp/tool-definitions.ts` maps each of the 18 `NATIVE_ACP_COMMANDS` in `src/plugins/roles/shared.ts:3` to an MCP tool name, a description derived from `help/*.md`, and a JSON input schema derived from the existing command grammars and `COMMAND_FORMS`. The repo has no input schemas today, so they are authored here and reused by the server, the snapshot filter, and the tests.
9. **Tool execution keeps the existing dispatchers.** Each MCP tool handler calls the same code the text loop called: `dispatchNativeLine` for `db`, `browser`, `question`, and `subagent`; the workspace runners for `file` and `web`. The gate logic in `src/acp/tool-table.ts` moves into the handler: a disabled or ungranted tool returns an MCP error result rather than executing. This preserves the current refusal messages and the dispatcher's own live disabled-command guard.
10. **Remote caller-side tools cross the remote channel as MCP calls.** With the MCP server in `janus remote-serve`, workspace tools run on the remote, but `db`, `browser`, `question`, and `subagent` must run on the local host. The existing `acp-tool-request`/`acp-tool-result` frames are kept and repurposed to carry a tool name plus JSON arguments and a `CallToolResult`-shaped result, instead of a command string and its output. No text command ever crosses the channel.
11. **The text-command loop and its protocol are deleted.** `runAcpToolLoop`, the last-line command extractor, the command-protocol and tool primers, the text tool table, the eight-step cap and its trailing message, the `acp-run`/`acp-turn`/`acp-tool-step`/`acp-run-end` step frames, and the `acp: true` command/reply transcript pairs all go away. Model turns become ordinary `session/prompt` calls whose tool calls arrive as ACP `tool_call`/`tool_call_update` updates. The remote protocol version is bumped once for the new and removed frames.
12. **Tool activity is structured end to end.** `AcpActivity` gains an optional `tool` payload carrying `toolCallId`, name, arguments, status, result, and error. `acpActivity` in `src/acp/activity.ts:20` builds it from ACP tool-call updates instead of JSON-stringifying `update.content`. The payload travels through `AcpRecordEntry`, `coreActivity`, the remote `acp-activity` frame, and the web `ConnectionActivity` type. Existing records without the field stay valid.
13. **The transcript renders real tool cards.** `ConnectionHistory.tsx` and `ToolCallBlock.tsx` render name, arguments, status, and result from the structured payload; a call and its result share one collapsible section, paired by `toolCallId`. Inline `<function_calls>` parsing in prose stays as a separate, view-local format for agents that emit XML in text.
14. **Questions remain synchronous from the model's point of view.** `question ask`/`approve` become ordinary MCP tools whose handler awaits the existing question panel and returns the answer as the tool result. No follow-up prompt, primer, or final-line protocol is involved.
15. **Errors are MCP errors.** A refused or failed tool returns `{ isError: true, content: [...] }` with the existing refusal text, so the model sees the same wording it sees today and can recover in the same turn.

Risks and things to verify during implementation
- OpenCode issue #61265: MCP tools from `session/new` were missing on the first model step before 2.2.6 (fixed by #60490). Confirm the installed version includes the fix; its two-second connect wait helps but is not a substitute.
- ACP-declared servers cannot set `codemode: false`; the whole direct-tool goal rests on the `execute` deny rule. Verify it against the installed OpenCode before building the rest of the UI work.
- Permission action wildcard matching (`janissary_*`) must be confirmed; if it does not match, enumerate one allow rule per tool from the descriptor.
- `@modelcontextprotocol/sdk` is NodeNext ESM; confirm it imports cleanly under this project's `tsconfig` and Node version before committing to the transport API.
- A role's `commands` include names whose grammars are permissive (for example the database fall-through). JSON schemas must be strict enough that the model cannot call an unintended subcommand.
- `question` and `subagent` calls are long-running; MCP call timeouts and ACP prompt cancellation must not orphan a pending answer or child session.


## development

## deferred

* Bundle janissary as a mac application that can be dowloaded and installed into /Applications and launched from an icon in the toolbar.

* Durable flows across relaunch - capture exit information from a harness and be able to use it to restart a session. a relaunch harness picker. workspace dir would need saved and re-created.

* the SQL browser's console (`product/specs/sql-database.md`) has no completion at all ("Tab here does not complete a word: there is nothing in this tab for a word to be completed against"), and the spec rules out a query builder or statistics panel; DBeaver's SQL Assist autocompletes table and column names, SQL keywords and functions from the database catalog, and its ER diagrams and visual query builder make the schema explorable and composable. Closing this means adding schema-aware autocomplete to the console using the connection's own catalog, with an ER diagram view of the selected database as a larger follow-on. Complexity: medium for autocomplete, high for a diagram view.

* the editor tab (`product/specs/editor-tab.md`) colors text for a handful of languages but offers no code navigation: no go-to-definition, symbol outline or breadcrumbs, no bracket matching or folding, and indentation is a fixed two spaces with nothing auto-closing as you type. VS Code's editor jumps to a symbol's declaration with F12, lists every symbol in the Outline view, highlights matching brackets and folds regions, and auto-closes brackets and quotes. Closing this means wiring a language server or a lightweight symbol index for the editor's supported languages so symbols can be jumped to and listed, plus the cheaper editor affordances IDE users treat as table stakes. Complexity: high.


## declined

* the search tab (`product/specs/search-tab.md`) searches the whole project with regex, case and whole-word toggles but is read-only and shows no match tally ("There is no tally: the header shows no count of matches or files"); VS Code's Search view has a Replace box beside the query, previews a diff of the pending edits, and replaces one match, all in one file, or across the workspace, alongside a "N results in M files" count. Closing this means adding a replace field with a diff preview and per-match/per-file/replace-all actions, a result count in the header, and some signal for when the silent 250-match cap is hit. Complexity: medium-high.

* the history picker (`product/specs/history.md`) lists recent commands for Up/Down navigation only, and the global history carries no context beyond the command text; iTerm2's shell integration exposes a searchable command-history popup, while Atuin fuzzy-searches a context-rich history recording the directory, exit code and duration of every command. Closing this means giving the picker a query field with fuzzy/substring filtering over the global history and showing the directory and result of each command on its row, so a command from another tab or an earlier run can be found by typing rather than by walking a capped list. Complexity: medium.

* the file navigator's Search files pop-up (`product/specs/file-navigator-tab.md`) matches a case-insensitive substring of the filename only, ranks by prefix then shortest path, and exposes a single best match with no result list; VS Code's Quick Open does fuzzy subsequence matching over the full relative path and shows a ranked list you can arrow through. The application's own global Quick Open (`product/specs/quick-open.md`) already implements that fuzzy path ranking and ten-row list — closing this means reusing the same matcher and result presentation inside the navigator's pop-up so searching a tree feels like Go to File rather than one best guess. Complexity: low-medium.

* the markdown tab (`product/specs/markdown-tab.md`) renders a one-time snapshot with no heading navigation, no clickable relative links and no update when the file changes on disk ("later edits to the file on disk are not reflected until it is opened again"); Obsidian's reading view has an Outline/table of contents, live internal links with backlinks and page previews, and VS Code's Markdown preview follows the source as it is edited. Closing this means building a heading outline with jump-to-heading, resolving relative links (images and .md files) into open actions, and watching the source file so the rendered view refreshes on external change. Complexity: medium.

* the browser command (`product/specs/browser.md`) can navigate, read rendered text, eval JavaScript and take a viewport screenshot, but exposes no inspection of what happened — no DOM snapshot, network request list, console messages or locator picker; Playwright's Inspector and Trace Viewer provide all of these with a timeline you can step and scrub through. Closing this means recording a lightweight trace per window (requests, console output, DOM snapshots) and adding subcommands or a viewer tab that lists and inspects it, so browsing by the user or an agent can be debugged after the fact rather than only through `browser eval`. Complexity: high.

* the diff tab (`product/specs/diff-tab.md`) is deliberately read-only ("nothing in the tab stages, discards, or commits"), so acting on a reviewed change always means leaving the tab for a shell or the file navigator; VS Code's Source Control view and diff editor let you stage or revert an individual hunk or selected lines right where you are reading them. Closing this means adding per-hunk stage/discard actions that use the same git plumbing the navigator's commit-to-origin already relies on, with the affected row updating in place after the operation. Complexity: medium.

* the editor tab (`product/specs/editor-tab.md`) has a Cmd+F find overlay, but matching is case-insensitive contiguous substring with "no regex, case, or whole-word options" and no replace — VS Code's editor find has all three toggles, a replace field with replace-one/replace-all, and a visible match count. Closing this means adding the toggles and a replace row to the editor's find overlay, with in-buffer highlighting and one undo step per replace, much as the project search tab already offers regex/case/whole-word toggles for the whole codebase. Complexity: medium.
