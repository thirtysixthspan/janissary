# features

## ready

* Add a command `file glob ...` accessible to ACP sessions ask and tell - The glob tool locates files by matching their paths against a glob pattern, returning the set of matching file paths without reading any file contents. It accepts a pattern argument written in glob syntax (for example **/*.ts for recursive TypeScript files, src/**/*.test.ts for tests under a src directory, or packages/core/*.{ts,tsx} for brace-expanded extensions), along with an optional path argument that scopes the search to a specific directory (defaulting to the current working directory when omitted), an optional hidden boolean that controls whether dotfiles and hidden directories are included (typically excluded by default), and an optional limit integer that caps the number of returned results (with a sensible default such as 100). The tool searches the filesystem using ** to match zero or more directory segments, * to match within a single path segment, ? to match a single character, and {a,b} alternation for multiple suffixes; it must respect the requested limit by truncating results once the threshold is reached, and it should terminate within a bounded search timeout (commonly around 30 seconds) rather than walking indefinitely across very deep or broad trees. The return value is an ordered list of matching relative or absolute file paths (typically newline- or list-delimited), and when nothing matches it returns an empty result rather than an error, while a missing or invalid path should produce a clear error indicating the directory does not exist. The tool should never follow symlinks into cycles, should skip paths that are excluded by standard ignore rules (such as .git, node_modules, and other VCS-ignored directories) unless explicitly configured otherwise, and should prioritize fast, shallow directory scanning so it can be used repeatedly and cheaply by an agent to discover filenames before reading or editing them. For permission tracking, the tool reports the requested pattern (rather than the search path) as its resource identifier so that authorization rules can grant or deny access based on what is being searched for, and it is intentionally distinct from a grep-style tool: glob matches only file paths by name, never file contents, leaving content search to a separate tool. A robust reimplementation should therefore expose pattern (required), path, hidden, and limit as parameters, return sorted/stable path results, enforce the limit and timeout, honor ignore rules and symlink safety, and document the exact glob semantics (specifically the meaning of ** and whether matching is case-sensitive) so an AI can predictably discover, select, and act on files in a large repository.

* Add a command `file grep ...` accessible to ACP sessions ask and tell - The grep tool searches the textual contents of files and returns the locations where a given pattern matches, complementing glob (which matches file paths) by matching what is inside files. It accepts a required pattern argument that uses regular-expression syntax by default (for example log.*Error, function\s+\w+, or TODO), and an optional literal boolean that, when true, treats the pattern as a fixed literal string rather than a regex (useful for searching text like request timed out without escaping metacharacters). Optional narrowing arguments include path to restrict the search to a specific directory (defaulting to the current working directory), include to filter candidate files by a glob such as *.ts or *.{js,jsx}, caseSensitive to control case-insensitive matching (commonly defaulting to case-insensitive), and limit to cap the number of returned matching lines (with a typical default such as 100). The output for each match is a list of results, each carrying the file path, the line number, and a short preview of the matching line (often with the matched substring highlighted or delimited), allowing an agent to jump straight to the relevant source location; the preview should be truncated sensibly for very long lines and binary files should be skipped or reported as non-text rather than searched. The tool should respect standard ignore rules (skipping .git, node_modules, and other VCS-ignored or hidden directories unless configured otherwise), avoid following symlink cycles, and terminate within a bounded search timeout (commonly around 30 seconds) so it can be called frequently and cheaply during exploration. When no matches are found it returns an empty result rather than an error, whereas an invalid or missing path should yield a clear error; a malformed regex should also produce a helpful error message describing the pattern problem rather than silently returning nothing. For permission tracking, the tool reports the requested pattern (not the search path) as its resource identifier so that authorization rules can grant or deny access based on what is being searched for, while access to the actual files read during matching is governed separately. A faithful reimplementation should therefore expose pattern (required), literal, path, include, caseSensitive, and limit as parameters; return file path, line number, and a preview for each match; enforce the limit, timeout, ignore rules, and symlink safety; and document the exact regex engine semantics (e.g., line-oriented matching, whether it defaults to case-sensitive, and whether \s, \w, and lookarounds are supported) so that an AI can reliably locate specific code, configuration values, or error messages across a large repository and then follow up with read or edit on the reported files.
