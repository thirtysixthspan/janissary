# features

## ready

* Move janissary's ACP tool loop — the primer, last-line command extraction, and AcpTool dispatch currently run in runCorePrompt on the local host even when the tab's ACP client is hosted on a remote machine — to the far side, so that command execution (and not merely the ACP subprocess) happens where the workspace actually lives. Today a remote ACP tab runs the agent on the remote host but parses its replies, matches commands against the tool table, and dispatches browser, db, and any future file read locally, which means every result must either be reconstructed remotely or silently reads/acts on the wrong machine; this item would move Layer 2 into the far-side ACP service so the remote server owns the primer it injects, the command it extracts from each reply, the tool it runs, and the output it feeds back, returning to the local side only streamed text, final answers, and tool activity for display. The change needs acp-open to carry the role's command grants and command-settings snapshot (or a way for the far side to resolve its own equivalent), a far-side tool table bound to that host's managers and workspace so file read and other host-side tools resolve remote paths under remote containment, and a protocol bump because a peer that ignores the new fields would look healthy while executing the wrong tool set; question is the deliberate exception — the human is local, so question registration and approval must remain on the local side and round-trip through a frame rather than being answered remotely. Benefits are correctness for all host-side tools on remote tabs, one code path for local and remote command loops, no full-file base64 round trips for reads, and the ability to reuse the remote filesystem and database managers the plugin capabilities already expose; risks are protocol-version churn, keeping role grants and native-command settings synchronized between both hosts, and preserving the existing cancellation, retry, record, and activity semantics that currently assume a local loop.

* Add a file read native ACP tool so janissary, rather than the harness, can serve file contents to agents. Agents end a reply with agent read <path> [--offset <line>] [--limit <lines>]; janissary parses the command, resolves and bounds-checks the path against the tab's workspace, reads the requested line range as UTF-8 text, and returns numbered lines (with a truncation notice when capped), or a single-line error for missing, binary, oversized, or out-of-workspace files. The tool is granted per role like browser, question, and db, appears in the ACP primer only when granted, and uses the existing AcpTool table, native-command vocabulary, and command settings, giving every harness identical read semantics, workspace-boundary enforcement, secret-file policy, and auditability instead of relying on each harness's built-in read. Read should be strictly limited to files in the workspace. File reads happen on remote machines closed loop without piping the read to the local machine.   

* Add a janissary-hosted agent write tool to the ACP tool loop — a file write/file edit family mirroring the ergonomics of opencode's write/edit and Claude's Write/Edit — so every harness, including one whose own write tool is blocked by janissary's permission policy, can create and modify files through the host, with the decisive requirement that the write execute as a closed loop on the machine that owns the workspace and never touch the local machine. The tool is Layer 2 only — a primer line, an AcpTool entry, a command grammar parsed from the reply's last line, and a host-side run — not a new ACP method, and it resolves the target through the tab's FileSystemPort: LocalFileSystemPort for a local tab, RemoteFileSystemPort for a remote tab, which already maps the root- and workspace-relative path and issues a filesystem-request with the existing write-file operation (path, content, optional expectedHash); the far side's RemoteFileNavigators then applies its own LocalFileSystemPort.writeFile, which containment-checks with containedPath, resolves symlinks, enforces expectedHash conflict detection, and commits through atomicWriteFile on the remote disk, returning a FileOperationResult that the local side only formats for the agent. Crucially, the local process must never materialize the content on its own disk: the bytes are base64-encoded across the remote channel, written remotely, and confirmed remotely, with no temp file, no file-cache entry, and no fallback to local node:fs, so a remote tab cannot silently write to the wrong filesystem even when the tab label, cwd, or file navigator cache exist locally. For edits, the read-modify-write should also close remote-side rather than pulling the whole file local, either by extending write-file with an edit variant or adding a new edit-file operation taking path, oldString, newString, and replaceAll, so the far side reads, matches, replaces, and atomically writes within one request and the local side sends only the replacement text; both variants need size caps, UTF-8/newline handling, a regular-file and containment check, and the existing one-line error vocabulary for outside-root, not-found, conflict, and permission failures. Writes are consequential, so the design should gate them behind the role grant and command settings like browser/db, and optionally require an explicit human approval through the existing question approve channel — which stays local because the human is local — showing the resolved remote path and operation before the request crosses the channel; and the remote protocol frame changes, if any, must be versioned so a peer that ignores an added edit mode or new fields cannot appear healthy while doing the wrong thing. The payoff is parity with native harness writes on remote tabs, one uniform containment/conflict policy for every harness, correct behavior when the agent's own write tool is denied, and a write path that is auditable and provably remote, at the cost of a protocol bump, a second (edit) operation or an extended one, extra framing for content, and the same round-trip latency every janissary tool already pays. writes must be contained to the workspace.
