# pull-request

* Stop reporting a description conflict when the description that changed was the one this tab just saved

Existing Issue: Every successful description edit leaves the one refusal line under the source line reading `The description of "documentation" changed elsewhere — showing the stored one.`, even though this client wrote that description and nothing anybody typed was displaced. Severity: 5/10

Existing Risk: 5/10 - Saving any role description reports a conflict the user did not cause, so a correct save reads as a rejected one and the user retypes it or stops trusting the tab's line.

Proposal Risk: 2/10 - Comparing the republished value against the draft as well as the baseline leaves the line for the one case it is written for, a draft another client displaced.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1668 "Stop reporting a description conflict when the description that changed was the one this tab just saved". Generated step G5, read verbatim as "Rename `research` to `PLANNING` so the tab shows a refusal line, then make an edit the server accepts — change `documentation`'s description — and confirm the refusal line has gone."; reproduced 2 of 2, the second time as the last step of its batch on a freshly created home file, so it is consistent rather than order-dependent. Replication: run `roles` from an agent tab on a fresh scratch home so the tab shows the five default cards, click the `research` card's name field (`.roles-tab:visible input[aria-label="Name of role research"]`), fill it with `PLANNING` and press Enter so the tab shows `A role named "PLANNING" already exists.`, then click the `documentation` card's description field (`.roles-tab:visible input[aria-label="Description of role documentation"]`), fill it with `Docs written and kept current.` and press Enter. Expected per product/specs/roles.md, "A refused edit": "The line clears on the next edit the tab raises, whether that edit is accepted or refused, so a message never lingers over a state it no longer describes", and per "A description the tab did not write", which raises that line only for "the stored description does move under an open draft". Observed: the accepted edit lands — the field and `~/.janissary/roles.json` both hold `Docs written and kept current.` — and the duplicate-name refusal does clear, but the `documentation` card immediately raises `The description of "documentation" changed elsewhere — showing the stored one.` in its place, so every description save ends on a conflict line. Root cause: `useRoleDraft` in `web/src/plugins/roles/useRoleDraft.ts` runs its render-phase adjustment whenever `baseline !== authoritative` and sets `setConflicted(draft !== baseline)`; after this client commits its own text the republished authoritative value differs from the old baseline while the draft is the text just submitted, so the hook reports a conflict although nothing displaced anybody's typing. `RoleCard` in `web/src/plugins/roles/RoleCard.tsx` raises the line from a `useEffect` keyed on that `conflicted`. Likely fix: require both halves before reporting — `setConflicted(draft !== baseline && draft !== authoritative)` — so a republished value that is the draft itself is followed silently, while a value that arrives under a genuine active draft still replaces it and reports. The name field is unaffected in practice because the card is keyed by the role name and remounts on a rename. A regression test should render `RoleCard`, commit a description edit, republish the payload carrying the text just written, and assert the description input holds that text with no refusal raised, then republish a different text under an active draft and assert the refusal appears.
