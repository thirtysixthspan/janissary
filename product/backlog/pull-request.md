# pull-request

* Deliver the node-on-PATH fix plan's promise that a server whose PATH already holds its node sees no change, which a symlinked node such as Homebrew's currently breaks.

Existing Issue: The bundled-adapter branch decides whether PATH already holds the server's node by comparing `path.dirname(process.execPath)` with PATH entries as literal strings, but `process.execPath` is the symlink-resolved path (a Homebrew node on `/opt/homebrew/bin` reports `/opt/homebrew/Cellar/node/<version>/bin/node`), so a server whose PATH resolves its own node through a symlinked directory still has a Cellar or install directory prepended to every claude and codex role agent's PATH. Severity: 3/10

Existing Risk: 3/10 - On a common macOS setup every role agent, and every command its tools run, gets an extra directory ahead of the user's PATH whose `npm` and `npx` can differ from the ones the user's PATH selects, which contradicts the plan's design decision and the spec's sentence that PATH is left alone when it already holds the node.

Proposal Risk: 1/10 - A node reached only through a version-manager shim (volta, asdf, mise shims) still resolves to a different file than `process.execPath`, so those setups keep getting the prepend, which is the plan's deliberate behavior for a PATH whose node is not the server's.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1983 "leave a bundled adapter's PATH unchanged when its first node already resolves to the server's own node through a symlink". In `src/acp/command-path.ts`, `withServerNode` returns the env unchanged only when `path.dirname(process.execPath)` is literally one of the `:`-separated PATH entries. Keep that check, and add a second one: find the first executable `node` on the given PATH with the existing `findOnPath('node', searchPath)`, and when it exists and `realpathSync` of it equals `realpathSync(process.execPath)` (wrap both in a try/catch that falls through to the prepend on error), return the same env object, because `#!/usr/bin/env node` already runs the server's node there. Only the `.bin` branch of `locateAcpCommand` calls `withServerNode`, so the path-given, PATH-hit, and shell-fallback branches are unaffected. Update the header comment and the doc comment above `locateAcpCommand` to say "when PATH does not already resolve `node` to the server's own node", and make the same wording change in the "Provider and model" paragraph of `product/specs/acp.md`, which today says "when that PATH does not already list it". In `src/acp/command-path.test.ts`, add a case that creates a temp directory holding a `node` symlink to `process.execPath`, passes `PATH: '<that dir>:/nonexistent-a'` for `claude-agent-acp`, and asserts `located.env` is the same object; the existing bundled cases (`resolves a command the install bundles…`, `prefers the bundled copy…`, `keeps the environment of a bundled command…`, `gives a bundled command with no PATH…`, `starts a bundled node script…`) must keep passing unchanged. Verify with `$janissary/scripts/run.mjs check-diff`.


* Make the shell-fallback test's assertion that the server's node is not added hold on every machine, as the node-on-PATH fix plan promised, rather than only on one whose PATH lacks the server's node.

Existing Issue: The interactive-shell fallback case now asserts `located.env.PATH` equals `${binDir}:${process.env.PATH}`, but the stand-in shell builds its PATH from the test runner's own `process.env.PATH`, which on a typical nvm setup already lists `path.dirname(process.execPath)`, so a regression that applied the node prepend to the fallback branch would leave that PATH unchanged and the test would still pass. Severity: 2/10

Existing Risk: 3/10 - An accidental move of the prepend into the fallback branch would put the server's node ahead of the nvm node a user's rc file chose for `opencode` and every other shell-located agent, and it would pass CI or a developer run whenever npm runs under the same node the PATH lists.

Proposal Risk: 1/10 - The assertion becomes deterministic, and only a stand-in shell that ignores the fixed PATH it is given would make it vacuous again, which the exact-equality check itself would expose.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1983 "pin the shell-fallback test's no-node-added assertion with a fixed shell PATH that lacks the server's node". In `src/acp/command-path.test.ts`, the case `resolves a command only the user's interactive shell finds, despite a banner` uses `userShellAdding(binDir, 'Welcome back')`, whose script prepends `binDir` to the inherited `$PATH`, so the resulting PATH contains whatever the runner's PATH holds, including `serverNodeDir` under nvm. Give `userShellAdding` an optional base-PATH argument (or add a sibling helper) so the stand-in script sets `PATH="${binDir}:<base>"` instead of `PATH="${binDir}:$PATH"`, call it in that case with a base such as `/nonexistent-a`, and assert `located.env.PATH` equals `${binDir}:/nonexistent-a` exactly and does not include `serverNodeDir`. Every other caller of `userShellAdding` keeps its current behavior. Do not change production code; `locateAcpCommand` in `src/acp/command-path.ts` must keep returning the shell's PATH untouched on that branch. Confirm the test is effective by temporarily wrapping the fallback branch's env in `withServerNode`, seeing the case fail, and reverting, then verify with `$janissary/scripts/run.mjs check-diff`.
