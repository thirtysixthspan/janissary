# pull-request

* Make the asciicast player's keyboard chords work after the recording is clicked into

Existing Issue: Every chord the player documents — Space and `p`, `.`, `,`, `[` and `]` — stops responding for the rest of the tab's life once the recording itself is clicked, because that click focuses xterm's hidden helper textarea and the key handler refuses any key whose target is a text entry. Severity: 6/10

Existing Risk: 6/10 - Clicking the recording is the first thing a user does with a player, and after it the transport answers only the mouse, so a user pressing Space to pause concludes the feature is broken rather than that a key was missed.

Proposal Risk: 2/10 - The player has no text field of its own and the only textarea it owns is the one xterm creates for it, so exempting that one leaves nothing a chord could steal; the residual risk is a future surface adding a real text field to this tab.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1515: asciicast player chords stop working once the recording is clicked into". Step D3 of the description's **How to verify** ("Press `.` a few times, then `,`. Position moves one recorded event at a time and playback is paused") fails after the click, and so do the chords behind steps 2 and 3 of the same list. Replication: start the app, type `play <file>.cast` for any recording from an agent tab so the asciicast tab opens with playback running and focus on `document.body`; press `.` and observe the transport's play button flip from Pause to Play and the scrub value jump to the next recorded event, then press Space and see it flip back — both work here. Click anywhere inside `.asciicast-stage`; `document.activeElement` is now `TEXTAREA.xterm-helper-textarea`; press `.` and Space again and nothing happens: the play button stays Pause and the scrub value only drifts forward with untouched playback, which is the tell. Expected: every documented chord keeps working after the click, since `product/plans/complete/in-app-recording-replay.md` § Design decisions promises "Every control is a button as well as a chord — Space or `p` plays and pauses, `,` and `.` step, `[` and `]` change speed — so nothing is keyboard-only", and both the `play` row's chord table and `documentation/user-documentation/tab-types/recording-player.md` list them. Observed: all five chords are dead from that point on, consistently, in 2 of 2 runs. Root cause: `web/src/plugins/asciicast/AsciicastTab.tsx`, the `onKey` handler built in the component's `useMemo`, whose second guard is `if (target && (target.tagName === 'INPUT' || target.tagName === 'TEXTAREA')) return false;` — it cannot tell the terminal's own helper textarea from a field a person is typing into, and it also treats every `<input>` as text entry, so the seek bar (`input[type=range]`) swallows chords while focused too. The codebase already has the right predicate in `web/src/shared/text-entry.ts` (`isTextEntryElement`, shared by the context menu, the paste capability, and the overlay seam), but a concrete client plugin may import only `web/src/plugins/api.ts`, `../shared.css`, and its own contract under `eslint.plugin-boundaries.mjs`, so it never got to use it. Likely fix: publish `isTextEntryElement` through `web/src/plugins/api.ts` beside the `terminalColors`, `isMacPlatform`, and `ConfirmDialog` re-exports that file already carries for the same reason, and in `onKey` ignore the key only when the target is a real text entry that is not `.xterm-helper-textarea`. A regression test should render `AsciicastTab` with an xterm focused, dispatch a `keydown` for `.` on the helper textarea, and assert the scrub value advanced by one recorded event and playback paused — the case this guard was written to protect is a text field the player does not have.
