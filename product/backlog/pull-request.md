# pull-request

* Report a regular expression that will not compile on the transcript instead of showing it as a search with no matches.

Existing Issue: With the regular expression toggle on, a query such as `[unclosed` settles as `No matches found for "[unclosed".` in the search tab and nothing is written to any transcript, although the spec and the description both promise a rejection on the transcript the search was started from. Severity: 6/10

Existing Risk: 5/10 - A user who mistypes a pattern is told the project has no matches rather than that the pattern is broken, so they can walk away believing a string is absent from the codebase when it is not.

Proposal Risk: 2/10 - Once a compile failure is told apart from an empty pattern, the remaining risk is only which transcript the report lands on, which a test pinning the origin label would make visible.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1481: report an uncompilable search regex on the transcript instead of settling as no matches". Replication: description step 9 of **How to verify** ("In regex mode enter `[unclosed`. Confirm the rejection appears on the transcript, no scan starts, and `plugins` still lists the search plugin as `active`."), failed 2 of 2 on a fresh app. Start the app on a scratch project that is its own git repository (the file list comes from `git ls-files`, so a directory inside the ignored `temp/` lists nothing), press Cmd+Shift+F from the `janus` agent tab, click the `.*` button (`.search-toggles button[aria-label="Regular expression"]`), type `[unclosed` into the search bar, wait a second, then click the `janus` tab and read its transcript. Expected, per `product/specs/search-tab.md` ("One that will not compile is reported on the transcript the search was started from, and the search tab keeps working") and the description's example output `[unclosed: Invalid regular expression: /[unclosed/: Unterminated character class`. Observed: the search tab body passes through an empty state to `No matches found for "[unclosed".`, the `janus` transcript holds nothing beyond its startup banner, and `plugins` prints `search 1.0.0 api=1 state=active` (that half passes). Root cause: `compileMatcher` in `src/plugins/search/compile-matcher.ts` catches the `SyntaxError` inside `safe` and `bounded` and returns `null`, the same answer it gives for an empty or zero-width pattern; `run` in `src/plugins/search/scan.ts` treats a `null` matcher as a finished search with no rows; `SearchSession.run` in `src/plugins/search/session.ts` has already published the `searching` state by then; and the `search` intent in `src/plugins/search/activate.ts` never compiles the query itself, so nothing ever rejects or notes. Likely fix: have the matcher distinguish "will not compile" (carrying the engine's message) from "nothing to search for"; in `SearchSession.run`, when the pattern will not compile, start no scan, publish the tab in its `error` state with that message, and `note` it on the originating transcript as the spec requires, keeping the plugin active. Regression test in `src/plugins/search/activate.test.ts`: a `search` intent with `regex: true` and query `[unclosed` never calls `projectFileList`, publishes `state: 'error'` with a message containing `Invalid regular expression`, calls `note` with that message, and leaves the plugin usable for a following valid search; plus a `compile-matcher.test.ts` case telling the two refusals apart.


* Update the search bar's query when a `search <phrase>` command reaches a search tab that is already open.

Existing Issue: Running `search todo` while the search tab is open searches for `todo` and fills the results with `todo` matches, but the search bar keeps showing the previous query, so the bar and the results disagree. Severity: 5/10

Existing Risk: 5/10 - The next toggle click or filter edit reruns the stale query still shown in the bar, silently replacing the results the user just asked for, and the command a user reaches for most often is the one that desynchronises the tab.

Proposal Risk: 3/10 - Syncing the bar from the server risks overwriting a query the user is mid-way through typing when a server update lands, which a test typing during an update would show.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1481: show the query a search command seeded in an already-open search tab's bar". Replication: plan step from `product/plans/complete/search-tab.md` **Verification** ("type `search todo` and confirm the same", meaning the tab opens with the search bar focused as Cmd+Shift+F does, with that query), failed 2 of 2 on a fresh app. On a scratch project that is its own git repository, press Cmd+Shift+F from the `janus` agent tab, type `checkTokenList` in the search bar and let it settle, click the `janus` tab, type `search todo` in its command bar and press Return. Expected: the search tab is active, its bar is focused and reads `todo`, and the rows are `todo` matches; the spec says `search <phrase>` "opens it and searches for that phrase straight away". Observed: the tab is active and focused and holds 101 rows whose highlighted match is `todo`, but the bar (`.tab-body:visible .search-tab textarea`) still reads `checkTokenList`. Root cause: `SearchTab` in `web/src/plugins/search/SearchTab.tsx` copies `payload.query`, `include`, `exclude`, and the three modes into `useState` once, at mount, and never reads them again; `SearchSession.open` in `src/plugins/search/session.ts` seeds the query through `run`, which updates the payload of the tab that is already mounted, so only the first `search <phrase>` (the one that creates the tab) reaches the bar. The history list is seeded the same way, so the command's term is not recorded either. Likely fix: have the client adopt a query the server seeded, for example by carrying a seed counter or the seeded query in the payload and resetting the bar's query (and recording it in the history) when it changes, rather than re-reading `payload.query` on every update, which would fight the user's own typing. Regression test in `web/src/plugins/search/SearchTab.test.tsx`: rerender the mounted tab with a payload whose seeded query changes to `todo` and assert the textarea reads `todo` and ArrowUp recalls it, while a payload update that only appends rows leaves a partly typed query alone.


* Clear the search results when the query is emptied after a search that found matches.

Existing Issue: Deleting the whole query after a search that found matches leaves every row of the old search on screen instead of clearing them and showing `Type to search`. Severity: 4/10

Existing Risk: 4/10 - The tab shows results for a query that is no longer in the bar, so a user can open a match believing it answers what the bar says, and the empty-query state the spec defines is only reachable from a search that found nothing.

Proposal Risk: 2/10 - Sending the empty query costs one extra intent per clear and the server already settles it without reading the project, so the only exposure is an initial-mount empty query being sent, which the existing first-value guard should keep covered.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1481: clear the search results when the query is emptied". Replication: generated step from this test run, failed 2 of 2 on a fresh app. On a scratch project that is its own git repository, open the search tab with Cmd+Shift+F, type `compileMatcher` and wait for the 21 rows to settle, then select the bar's text and delete it all, and wait about a second. Expected, per `product/specs/search-tab.md` ("An empty query clears the results rather than searching for nothing.") and `ResultTable`'s own `Type to search` state. Observed: the bar is empty but all 21 `compileMatcher` rows remain and no `.search-empty` message appears. Description step 11 passes only because it clears the query after a search that found nothing, when there are no rows to remove. Root cause: the debounce effect in `SearchBar` in `web/src/plugins/search/SearchBar.tsx` calls `onSearch` only when `debounced.trim() !== ''`, so an emptied query never reaches the server, the payload keeps the previous rows, and `ResultTable` in `web/src/plugins/search/ResultTable.tsx` renders rows whenever there are any, without looking at the query. The server already handles an empty query correctly: `activate.test.ts` pins that a `search` intent with `query: ''` settles as done without listing the project, and `SearchSession.run` publishes it with `rows: []`. Likely fix: let the settled empty query through to `onSearch` (keeping the guard that skips the value the tab opened with) and leave the history untouched for an empty term. Regression test in `web/src/plugins/search/SearchTab.test.tsx`: after a search, change the bar to an empty string, advance past the debounce, and assert a `search` intent with `query: ''` is sent and no history entry is recorded.


* Forget the search tab's query, results, and term history when the tab is closed.

Existing Issue: Closing the search tab and opening it again, with Cmd+Shift+F or a bare `search`, brings back the previous query, its rows, and that query in the arrow-key history, although the spec says closing the tab forgets the history along with the query. Severity: 3/10

Existing Risk: 3/10 - Stale results reappear in what looks like a fresh tab, and the spec now describes the opposite of what the app does, so the next change to this area is built on a false premise.

Proposal Risk: 2/10 - Resetting only when the host builds a new tab keeps the focus-an-open-tab path unchanged, so the one thing to watch is the spec's other sentence about a bare `search` landing the user back where they were, which applies only while the tab is still open.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1481: reset the search tab's query, rows, and history when it is closed and reopened". Replication: generated step from this test run, failed 2 of 2 on a fresh app. On a scratch project that is its own git repository, open the search tab with Cmd+Shift+F, type `compileMatcher` and let its 21 rows settle, close the tab with its `.tab-close` control, then run `search` (or press Cmd+Shift+F) from the `janus` agent tab, click the search bar, and press ArrowUp. Expected, per `product/specs/search-tab.md` ("The list is the tab's own, and closing the tab forgets it along with the query."): an empty bar, no rows, `Type to search`, and ArrowUp recalling nothing. Observed: the reopened bar reads `compileMatcher`, the 21 rows are back, and ArrowUp recalls `compileMatcher`. Root cause: `SearchSession` in `src/plugins/search/session.ts` lives as long as the plugin, not the tab, and `open` hands its retained `this.payload` to the `openOrFocusTab` factory, which the host runs only when it creates a new tab; `SearchTab` in `web/src/plugins/search/SearchTab.tsx` then seeds its query and its history from that payload. The spec's sentence "A bare `search` leaves the tab showing whatever it last searched for" is about focusing a tab that is still open, and that path does not run the factory. Likely fix: inside the factory in `SearchSession.open`, cancel any scan and reset `this.payload` to `emptyPayload()` carrying the remembered modes (`this.saved`), seeded with the command's query when one was given, so a tab the host has to build starts empty while a focused tab keeps its state. Regression test in `src/plugins/search/activate.test.ts`: run a search, then call `command('')` with an `openOrFocusTab` fake that invokes the factory as a new tab would, and assert the factory's payload has an empty query and no rows while the saved modes are kept; plus a case where the fake does not invoke the factory and the previous payload is untouched.
