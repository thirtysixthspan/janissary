* Make a second launch refuse to start so the running instance stays the one the latest log names

Existing Issue: Description How to verify step 3 and plan Verification step 3 expect a second launch against a running instance to be refused, but it exits 0, prints a fresh address, and repoints latest.log at the new run. Severity: 7/10

Existing Risk: 6/10 - In a sandbox that denies signalling child processes, two instances share one project directory and the first instance's log is no longer reachable through the latest link, defeating the per-run log contract this change promises.

Proposal Risk: 4/10 - Distinguishing a sandbox-denied liveness probe from a dead or foreign process keeps the lock's deliberate cross-account behavior, leaving only the rare recycled-pid case where the lock is judged stale.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2203 "Make a second launch refuse to start so the running instance stays the one the latest log names". Step D3 (description, How to verify step 3; echoed by plan Verification step 3), verbatim: "The link moves only after readiness. Do: while one instance is running, record `readlink` of `latest.log`; start a second launch against the same directory and read the link again. Expect: the second launch is refused with the already-running message, the link still names the first run's file, and that first file still holds its `__JANUS_URL__` line." Reproduce with the scratch project `<scratch>/work`: start `HOME=<scratch home> node bin/janus.mjs --no-open <scratch>/work`, take the address from `<scratch>/work/.janissary/logs/server/latest.log`, confirm it answers HTTP 200, note `readlink` of latest.log and the pid in `.janissary/lock`, then run the same launch command a second time. Expected: non-zero exit, `another janus instance is already running in this directory` on stderr, the link and first log byte-for-byte unchanged — promised by product/specs/cli.md "Another janus instance is already running against the same target directory: the message names the directory and the live process ID" and by the plan's "keeps latest.log on the earlier run until the new server prints its readiness marker". Observed twice, consistently (2 of 2), in two separate batches with the first app confirmed at HTTP 200 immediately before the second launch: exit 0, empty stderr, a fresh URL on stdout, latest.log moved from the first run file to the second, and the first log unchanged. Root cause: `src/instance-lock.ts`'s `isOwnInstanceAlive` catches every error from `process.kill(pid, 0)` and returns false; in this tab's sandbox that probe answers EPERM even for the app's own child, so `acquireLock` treats the live lock as stale and takes it, `src/main.ts` boots a second server, and `pointLatestLog` in `bin/server-log.mjs` repoints the link. The sandbox restriction is confirmed by running `kill -0` on the recorded pid, which returns EPERM, and by the base stop task's note that a confined process can be denied the right to signal its own children. Likely fix: make the liveness probe recognize a process this user started in this sandbox despite EPERM — for example by recording an ownership marker beside the pid or using a liveness signal the sandbox permits — while keeping the documented behavior for a genuinely foreign pid. A regression test should start a second launcher in a sandboxed child where `process.kill(pid, 0)` returns EPERM and assert a non-zero exit with the already-running message and an unchanged latest.log. re-observed on 2026-11-23: session-ending step D11 hit the same cause when `node bin/janus.mjs stop <project-dir>` answered `no running janus instance` against a live app that returned HTTP 200 both before and after the stop, leaving latest.log on the last run's file; ending a websocket client was what finally stopped it.

Proposal Risk: 2/10 - Naming the stable link instead leaves the rest of the recipe untouched and matches the per-run logs the launcher actually writes.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2203 "Point the base-branch testing instructions at the latest log instead of the removed shared server log".
