# pull-request

* Keep a reveal from overriding a row the user pressed before the navigator applies it.

Existing Issue: Clicking Reveal in file navigator and then pressing an already selected row before the reveal's row arrives still selects the revealed file, so the press is silently overridden; it reproduced 2 of 2 runs (the main batch after D1–D15, and the rerun alone). Severity: 4/10

Existing Risk: 4/10 - On a slow or remote tree, a user's immediate second click is undone by a selection they did not ask for, and keyboard focus is taken from where they put it.

Proposal Risk: 2/10 - The fix adds a request timestamp or an interaction timestamp to the reveal path, and an over-eager comparison could drop a legitimate reveal on a slow server; a unit test that delivers the hint before and after a press pins both outcomes.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2009 "Keep a reveal from overriding a row pressed before its hint arrives". The step is P6 from the plan's Verification: "Manual, pending click: reveal a file into a large tree, then press on a row that is already selected before the reveal's row appears. The earlier selection stays, the reveal's row is not selected when it arrives, and the tree takes no second focus." Reproduction: in the scratch app, open `temp/reveal-check/nested/notes.md` and reveal it, then click the `temp` row in the navigator; open `temp/reveal-check/large/deep/target.md` in an editor; click the `tab-body:visible .editor-reveal-button` and, in the same JavaScript task, dispatch a `mousedown` with `button: 0` on the `.files-tab [data-path="temp"]` row, so the press reaches the tree before the `revealInFileNavigator` round trip returns. The expected result is promised by the plan's design decision: "if the user moves the tree's cursor or presses on any row first — including a row that is already selected — or the navigator is re-rooted or retargeted in the meantime, the pending selection is dropped rather than yanking the selection away afterwards." Observed in both runs: after 1.2 s the navigator had `temp/reveal-check/large` expanded, `temp/reveal-check/large/deep/target.md` was the cursor and only selected row, and `temp` was no longer selected; a control probe that let the hint arrive first (with a missing target file) showed the pending drop does work, so the gap is the pre-arrival case. Root cause: `dropPendingFocus` in `web/src/file-navigator/useFileNavigatorSelection.ts` only acts when `focusHint?.outcome === 'pending'`, and `focusHint` is undefined until the server's hint has arrived and `recordFocusOutcome` has recorded it; when the hint arrives, the effect resets `userMoved.current` to false for the new revision, so the earlier press is forgotten and `focusHintStatus` in `web/src/file-navigator/file/navigator-selection.ts` returns `ready` once the row exists, applying the selection. Likely fix: carry the reveal request time on the hint (or have `revealInFileNavigator` set a short-lived client expectation) and compare it with a tree-interaction timestamp in `useFileNavigatorSelection`, dropping the hint when the press is newer; alternatively remember a press that occurs between the click and the hint's arrival and consult it when the hint is recorded. A regression test should dispatch a mousedown on an already-selected row before delivering the focus hint, then deliver the hint with its cursor row present, and assert the earlier selection is kept, the revealed row is not selected, and focus is not moved.


* Correct the pull request's restart step to reload the page at the server's new token-gated URL.

Existing Issue: The description's step 16 expects a page that stays open to reconnect after a server restart, but the app mints a fresh session token on every boot, so the still-open page stays on "Reconnecting…" and can never re-authenticate; the plan's "after a restart" verification carries the same wrong expectation. Severity: 2/10

Existing Risk: 2/10 - A reviewer following the step by hand sees a dead page and cannot tell whether the feature or the step is wrong, and the acknowledged-revision behavior the step claims to verify is never exercised.

Proposal Risk: 1/10 - A rewritten step could still imply the revision floor is observable from a browser reload; keeping that sentence out and naming the test coverage is what keeps it honest.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2009 "Correct the pull request's restart testing step". The step is D16 from the description's How to verify: "With the page still open, restart the server process and wait for the page to reconnect. Reopen a file navigator, whose label the client already knows, and an editor on a nested file, then click the folder button." Reproduction: in the scratch app open `temp/reveal-check/nested/notes.md` and reveal it, run `quit` in the shell command bar and confirm with `y`, then start the app again with the same scratch directory and `--port=<the old port>`; the open page shows `Reconnecting…` for at least eight seconds, clicking the folder button changes no navigator, and the restarted server is only reachable at the newly logged URL. Cause: `src/main.ts` passes `makeToken()` to `startServer` on every boot and `web/src/shared/ws/ws-connection.ts` reconnects to the page's existing `location`, whose query string carries the previous token, so the upgrade is refused; the client's acknowledged-revision floor lives in a module-level map in `web/src/file-navigator/useFileNavigatorRevealFocus.ts`, so a page opened at the new URL is a fresh document with an empty floor. The step as it should read in the description's How to verify: "Restart the app: run `quit` in the command bar, confirm, then start it again with the same scratch command. Open a page at the newly printed address, reopen a file navigator and an editor on a nested file, and click the folder button. Expect: the navigator retargets and selects the file with the tree focused, exactly as in step 1. (The acknowledged-revision floor surviving a restart is not observable from a browser reload; it is covered by the server and client tests.)" A regression test is not applicable to a description edit; the existing `nextRestoreRevision` and client-floor tests already pin the revision behavior.
