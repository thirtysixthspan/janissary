# pull-request

* Catch a failed pause or resume from the Schedules tab icon so it does not raise an unhandled browser error

Existing Issue: Pressing the Pause/Resume icon when the store save fails leaves the row unchanged but emits an unhandled `[pageerror] could not save system schedules` in the browser console. Severity: 5/10

Existing Risk: 5/10 - A failed save surfaces as an uncaught client error, so an operator riding out a maintenance window sees what looks like a tab crash and cannot trust the silent-failure contract the feature promises.

Proposal Risk: 2/10 - Once the rejected intent is consumed, only a warning remains in the console and the visible row behavior is already correct.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2253 "Catch failed pause and resume intents in the Schedules tab". Generated step G4: from a scratch project whose `.janissary/scripts/ping.rs` contains `echo ping`, run `schedule system ping every 1m script ping`, open `schedules`, make `.janissary/` unwritable with `chmod 555 .janissary`, click `Pause schedule ping` once, restore the mode, and watch the browser console. Expected: the failed save leaves the row active, its icon and Next Run unchanged, with no other message — "A Pause or Resume that fails to save leaves the row as it was, with its icon and Next Run unchanged, and shows nothing else, matching a failed Delete today" (plan UI design 16). Observed on commit 665191f1 in two batches: the store bytes and row stayed unchanged and no toast appeared, but the console logged `[pageerror] could not save system schedules` in both. Root cause: `web/src/plugins/schedules/SchedulesTab.tsx` `togglePause` fires `void capabilities.intent(entry.paused ? 'resume' : 'pause', ...)` and never handles a rejection; `src/plugins/schedules/activate.ts` `pause` and `resume` intents call `capabilities.rejectRequest(error)` when `src/plugins/schedule-topic-actions.ts` returns the manager's `could not save system schedules` failure; `web/src/plugins/plugin-client-capabilities.ts` `intent` converts that failed result into a thrown `Error`, leaving a rejected promise unhandled. The repository already ships `web/src/plugins/fire-intent.ts` `fireIntent`, which awaits the intent and emits a `console.warn` on failure. Likely fix: fire the tab's pause and resume intents through `fireIntent` (and apply the same handling to `confirmDelete`), so a domain rejection is consumed rather than escaping as an unhandled rejection. A regression test should assert that a rejected pause or resume intent leaves the row unchanged and produces no unhandled rejection or `[pageerror]`, with a console warning acceptable.
