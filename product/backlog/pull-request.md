# pull-request

* Make the shell plugin survive opening its first tab, which currently overflows the stack and disables it before any tab appears.

Existing Issue: `zsh` is accepted and then reports `Tab plugin "shell" disabled: Maximum call stack size exceeded.` in the notifications feed, leaving no shell tab at all. Severity: 10/10

Existing Risk: 8/10 - The feature is unreachable in normal use: every `zsh` invocation disables the plugin for the session, so the tab never opens and the user is left with a refusal instead of a shell.

Proposal Risk: 3/10 - Publishing the fingerprint map before delivering means a delivery that throws still leaves the tab looking pushed, so that one change is not retried until something else differs; the fingerprint is cleared nowhere, so a later genuine difference still delivers.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1526: stop the host-state push from re-entering itself and disabling the shell plugin". Steps P1 through P10, P12, P13 and G1 through G5 all fail from this one cause; only P11 passed. Reproduce by starting the app on a scratch project directory and typing `zsh` in the first tab: the notifications feed gains `Tab plugin "shell" disabled: Maximum call stack size exceeded.` and the tab list stays at one tab. The cause is in `dispatch` in `src/plugins/host-state.ts`: it takes `const pushed = lastPushed.get(record) ?? new Map<string, string>()`, records a tab's fingerprint into it, starts `void deliver(...)`, and only reaches `lastPushed.set(record, pushed)` after the loop finishes. The shell plugin's `hostState` handler in `src/plugins/shell/activate.ts` calls `capabilities.updateTab` synchronously, which runs `updatePluginTab` in `src/tab/openers.ts` and emits `state: dirty` inline, and `messageBus.emit` in `src/bus.ts` is synchronous. So the first delivery re-enters `dispatch` before the fresh map has ever been published, the re-entrant pass reads `undefined` again, builds another empty map, and delivers again — unbounded recursion, caught as a thrown error that crosses the plugin failure boundary and disables it. Publish the map into `lastPushed` before the delivery loop rather than after it, or hoist the per-record map creation above the loop and set it immediately, so a re-entrant pass sees the fingerprint just recorded. Checked and ruled out: `fingerprint` covers only the two row lists, so the payload `updateTab` writes cannot itself change the comparison; `deliver`'s `await` does not help, because the shell handler is synchronous up to its emit. A regression test should assert that one `state: dirty` with a changed row list produces exactly one `hostState` call, in `src/plugins/host-state.test.ts`, which currently cannot catch this because its fixture handler never emits.


* Make the shell tab's mount-time liveness question reach the plugin at all, which currently fails on every mount.

Existing Issue: Every shell tab logs `[pageerror] Plugin intent "terminal-status" failed`, so the question the tab asks on mount never reaches the plugin and the case it exists for — a shell that exited while no browser was attached — is never detected. Severity: 7/10

Existing Risk: 6/10 - A tab whose process died minutes ago stays open holding the payload of a shell that is gone, waiting for input that can never arrive, and the failure is invisible to the user because the rejection is unhandled rather than reported.

Proposal Risk: 2/10 - Sending `null` instead of `undefined` relies on the transport preserving an explicit null, which the serialization does; if a future transport drops nulls as it drops undefineds the same failure returns, so the plugin's own guard should keep accepting both.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1526: send a payload the pluginIntent param guard accepts for the terminal-status question". Observed in the browser console as five `[pageerror] Plugin intent "terminal-status" failed` lines during a run that opened several shell tabs, and confirmed without a browser: `web/src/plugins/api.ts`'s `intent` sends `params: { tab: label, intent: name, payload }`, `web/src/rpc-exchange.ts` serializes with `JSON.stringify`, which drops a key whose value is `undefined`, so the wire carries `{ tab, intent }` with no `payload` key at all; `isPluginIntentParams` in `src/client-params/plugin.ts` requires `Object.hasOwn(value, 'payload')`, so `src/message/plugin.ts` throws `Invalid pluginIntent params` and the client's `intent` helper turns the failed result into the error the console shows. `isEmptyShellIntent` in `src/plugins/shell/shared.ts` already accepts both `undefined` and `null`, so the wire shape the guard wants is one the plugin is prepared for. Send `null` from the `terminal-status` call in `web/src/plugins/shell/ShellTab.tsx`, or relax the transport so an absent payload is distinguishable from a dropped one. Attach a rejection handler to that call: it currently has none, which is why a routine refusal becomes an unhandled rejection and a `[pageerror]` rather than anything the tab or the log can act on; the `dispatch` call in the same file already reports through `capabilities.reportFailure` and the `complete` call does not. `src/plugins/shell/activate.test.ts` cannot catch this because it invokes the activation's `intent` directly and so never passes through the client's serialization. A regression test should assert that a payload-less intent survives `JSON.stringify` of the request params and reaches the activation's table.
