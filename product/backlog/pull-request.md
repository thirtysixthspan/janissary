# pull-request

* Assert that the new PDF asset route in the dev server resolves inside the installed package, rather than relying on its URL pattern to imply it.

Existing Issue: The `janus-pdfjs-assets` middleware added to `web/vite.config.ts` builds a filesystem path by joining two capture groups of a request URL onto the resolved `pdfjs-dist` directory and reads it with `readFileSync`, with no assertion that the result stays inside that directory and no handling for a read that fails; the filename group also admits `..`, and a missing file throws out of the handler instead of falling through. Severity: 3/10

Existing Risk: 3/10 - The containment holds today only because the pattern happens to exclude a path separator, so a later widening of that character class to admit a nested asset directory would turn a developer's dev server into a file-read surface, and in the meantime an unresolvable asset name answers with a server error rather than a not-found.

Proposal Risk: 1/10 - An explicit containment check is only as good as the base path it compares against, so it still needs to resolve symlinks rather than compare raw strings if `node_modules` is linked.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1076: contain the dev-server pdfjs asset route to the installed package". In the `pdfjsAssets` plugin in `web/vite.config.ts`, after matching `PDFJS_ASSET_ROUTE`, resolve the candidate path and assert with `path.relative` that it stays under the resolved `packageRoot` without escaping, calling `next()` rather than answering when it does not; tighten the filename capture so a bare `..` cannot match; and wrap the `readFileSync` so a missing or unreadable asset calls `next()` and lets Vite answer its own not-found instead of throwing out of the middleware. Set a response content type while there, since the handler currently answers with none. Leave `generateBundle` alone: it reads from `readdirSync` over the package's own directories and never sees a request, so it carries none of this. This file has no colocated test and the project's vitest projects cover `src/` and `web/src/` only, so verify by running the dev server and confirming that a real cmap path still serves, that a `..` or nonexistent name falls through to Vite's own 404, and that a PDF with CJK text still renders in dev.
