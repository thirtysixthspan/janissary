# pull-request

* Keep the instance lock held and `janus stop` working when the sandbox denies both signal probes and process-table reads

Existing Issue: A second launch is admitted against a directory with a live instance and `janus stop` reports `no running janus instance`, so the second launch steals `latest.log` and the running app cannot be stopped from the CLI. Severity: 8/10

Existing Risk: 8/10 - In this sandbox any launch can admit a second server into the same directory, the second one repointing `latest.log` away from the live instance, while the documented stop command leaves both servers running.

Proposal Risk: 3/10 - A wrong replacement owner check is visible in the same scenario, either refusing a legitimate first launch or still leaving stop powerless, so it will not pass unnoticed.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2203 "Keep the instance lock held and janus stop working when the sandbox denies both signal probes and process-table reads". Step D3 (description) verbatim: "The link moves only after readiness. Do: while one instance is running, record `readlink` of `latest.log`; start a second launch against the same directory and read the link again. Expect: the second launch is refused with the already-running message, the link still names the first run's file, and that first file still holds its `__JANUS_URL__` line." Step D11 (description, session-ending) verbatim: "Stop the instance. Do: run `janus stop <project-dir>` and read the link and logs afterwards. Expect: the address is no longer reachable, `latest.log` still names the last run's file, and that file still holds its `__JANUS_URL__` line." To replicate, make a scratch git project with `.janissary/config.json` holding `{"logEnabled": false, "logRetentionInDays": 7}`, point `HOME` at a scratch home, run `node bin/janus.mjs --no-open <project-dir>`, record the pid in `.janissary/lock` and the `readlink` of `.janissary/logs/server/latest.log`, then rerun the same launch and run `node bin/janus.mjs stop <project-dir>`. The promise is `product/specs/cli.md`: "A process owned by the current user is still live even when a sandbox denies the signal probe, so its lock is held and the second launch is refused", and "A process owned by the current user counts as alive even when a sandbox denies the signal probe." Observed consistently 2 of 2: the second launch exits 0 with a fresh address and empty stderr, `latest.log` moves from the first run's file to the second's while the first log stays byte-for-byte unchanged; `janus stop` exits 0 printing `no running janus instance for <project-dir>` and the first address still answers HTTP 200 after 1.6 seconds. Root cause, confirmed in a fresh app batch: `isOwnInstanceAlive` in `src/instance-lock.ts` gets `EPERM` from `process.kill(pid, 0)` and calls `pidBelongsToCurrentUser` in `src/process-owner.ts`, which runs `execFileSync('ps', ['-p', String(pid), '-o', 'uid='], ...)`; this harness sandbox denies executing `ps` with `EPERM`, so the helper returns false and the live owned pid is called stale. `acquireLock` in `src/instance-lock.ts` then calls `clearIfStale` and admits the second launch, and `stopInstance` in `src/stop-instance.ts` asks the same function and prints the no-running message. A probe against a known live pid measured `process.kill` EPERM, `ps` EPERM, `pidBelongsToCurrentUser` false, `isOwnInstanceAlive` false. Likely fix: give the liveness check an owner signal this sandbox permits, or treat an EPERM probe as alive when the lock pid was recorded by this account while keeping the documented cross-account stale takeover for pids positively shown to belong to another uid; leave the lock file a bare pid. A regression test should mock the signal probe as EPERM and the owner query as unavailable, then assert `acquireLock` still refuses the second launch and `stopInstance` still signals, without weakening the existing foreign-owner takeover cases.
