# pull-request

* Deliver the plan's promised rollback for a path the patch vacates and then re-creates, so a failed commit restores its original bytes instead of silently deleting it.

Existing Issue: `buildPatchChanges` in `src/file-patch/changes.ts` keeps a recorded delete entry only when its place is absent at the end or was explicitly deleted, so when a move vacates a path and a later section deletes the moved copy and re-creates the vacated path, the entry holding that path's original bytes or link text is dropped while the re-creation's `freshContent` has `original: undefined`; a commit-time failure then unlinks the re-created path, or a rename into it overwrites the original with no undo, even though the failure line reports `No files were changed.` Severity: 7/10

Existing Risk: 6/10 - A disk-full, permission, or vanished-path failure during commit of such a patch silently deletes the original file or symbolic link while telling the user nothing changed, and the plan, help page, and pull request description all promise that a failed patch restores every file.

Proposal Risk: 2/10 - The change unlinks a path that the patch's own net change already removes and restores it through the existing delete undo, so the residual hazard is one extra unlink/restore cycle on an uncommon patch shape, covered by the same undo path the other delete cases use.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2011 "keep a vacated path's original bytes in the patch change list". In `src/file-patch/changes.ts`, drop the `(!place.exists || record.removedByDelete.has(place))` clause from the delete filter in `buildPatchChanges` so every `record.deletes` entry whose place `existed` and is not the origin of an active move chain is kept, and say in a comment that the entry is the only holder of the original bytes, mode, and link text for restore; `src/file-patch/moves.ts`'s `moveSection` already records it when it vacates a source, and `src/file-patch/commit.ts` already unlinks deletes before renames and writes and records a delete undo in `src/file-patch/restore.ts`, so the success path only gains an unlink of a file the patch's net change removes while the failure path regains its original. `src/file-patch/rows.ts` reads places and chains, not this list, so `A`/`M`/`D`/`R` output is unchanged. Add colocated cases: in `src/file-patch/sections.test.ts` assert `changes.deletes` names the vacated path for `*** Update File: b` / `*** Move to: c` / `*** Delete File: c` / `*** Add File: b` / `+new` and for the same shape with `*** Update File: a` / `*** Move to: b`; in `src/file-patch/commit.test.ts` run that patch with a `writeFile` failure injected after the re-creation and assert `b` is restored byte-for-byte with its mode and `c` is absent, then repeat with `b` a symbolic link and assert `readlinkSync` returns its target; keep `restores prior writes, moves, deleted links and modes`, `handles replacement, vacated paths, exchanges and intermediate folders`, `deletes, moves and updates links without replacing their targets`, and the destination-new row case passing untouched.
