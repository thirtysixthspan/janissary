Existing Issue: `src/visualizations/reading.ts`'s `applyRead` returns early on a failure without advancing the dataset's `readAt`, and `src/visualizations/refresh.ts`'s `waitOf` computes `Math.max(entry.seconds * 1000 - (now - entry.readAt), 0)`, so a dataset that failed to read is permanently due and `poll` re-arms the timer at `0` with no backoff. Proposal Risk: 3/10 - A failed read still leaves the chart on screen and still records its reason; what changes is that the next attempt is an interval away rather than immediately, and a chart on a busy agent is skipped rather than retried in a tight loop.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1440: stop the live-update poll re-arming at zero after a read fails". In `src/visualizations/reading.ts`, make `applyRead` set `dataset.readAt = now` on the failure branch as well as the success branch, so a failed attempt counts as an attempt and the next one is a full interval away; keep leaving the previous table and recording the reason exactly as now. In `src/visualizations/manager.ts`, change `dueFor` to use `this.index.live(id)` rather than `this.index.find(id)`, so a deleted record contributes nothing to the poll. Then add the coverage that would have caught it: in `src/visualizations/manager.test.ts`, extend the existing `'re-reads on the interval it was given, and a failed re-read keeps the chart'` case to advance the clock by a second interval after the failure and assert the read count has not grown, and add a case asserting a deleted record with an armed interval is not read again while its tab is open.
