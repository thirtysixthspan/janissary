# pull-request

* Close the security gap where a bundled adapter missing from the install's own dependencies falls through to whatever same-named adapter is on PATH, running role sessions without their built-in-tool denial.

Existing Issue: When `claude-agent-acp` or `codex-acp` is not in the install's `node_modules/.bin` (a checkout updated without `npm install`, a remote host in the same state, or the hoisted layout the plan names as its ceiling), the command lookup continues to the server's PATH and then the interactive shell's PATH and runs any unpinned copy it finds there, although the plan says such a layout "fails to find the bin name and reports the agent failing to start". Severity: 6/10

Existing Risk: 5/10 - An older or deprecated codex adapter installed globally under the same `codex-acp` name ignores `CODEX_CONFIG` and `INITIAL_AGENT_MODE`, so a role session starts with codex's shell and default sandbox turned on, and a user sees a healthy session with no sign that layer one is off.

Proposal Risk: 2/10 - Role launches either run the pinned copy or fail and fall back to the role's next model; the residual risk is a user whose role launches now fail visibly where an unpinned copy used to run, which the failure message and the fallback line make plain.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1983 "make a bundled ACP adapter name fail closed instead of falling through to PATH when the install's node_modules/.bin lacks it". In `src/acp/command-path.ts`, add a module-level set of the bundled adapter names (`claude-agent-acp`, `codex-acp`, the names `baseLaunchForEntry` in `src/acp/launch.ts` returns; export one constant from `launch.ts` or a small shared module and use it in both places so the names cannot drift). In `locateAcpCommand`, after the `.bin` lookup misses, return `{ command, env }` unchanged for a name in that set without consulting `findOnPath(command, env.PATH)` or `interactiveShellPath`, so the spawn fails with ENOENT and `connectAcp` reports the agent failing to start, which the role's model fallback already handles. The decision runs on whichever host executes the agent, so a remote host gets the same rule with no frame or protocol change. Extend `src/acp/bundled-adapters.test.ts` so the set equals the commands `acpLaunchForEntry` returns for claude and codex. Add cases to `src/acp/command-path.test.ts` (which mocks `../janissary-root.js` with a temp install root): with an install root whose `.bin` lacks `codex-acp`, a `PATH` directory holding an executable `codex-acp` and a stand-in user shell (`userShellAdding`) that adds another one both leave the command as the bare name and the env as the same object; an unbundled name such as `opencode` still resolves through PATH and the shell fallback exactly as the existing cases assert. Update the `locateAcpCommand` doc comment and header comment, the sentence in `product/specs/acp.md` that says a bundled adapter's command is found in `node_modules/.bin` ahead of PATH (say a missing bundled adapter fails the entry rather than running a copy from PATH), and the "Ceiling" bullet of `product/plans/complete/deny-internal-tools-for-role-acp-connections.md` only if the work task's rules allow plan edits; the existing command-path, launch, and manager-fallback suites must keep passing unchanged.
