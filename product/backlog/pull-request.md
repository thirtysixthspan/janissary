# pull-request

* Make the asciicast player's keyboard chords work after the recording is clicked into

Existing Issue: Every chord the player documents — Space and `p`, `.`, `,`, `[` and `]` — stops responding for the rest of the tab's life once the recording itself is clicked, because that click focuses xterm's hidden helper textarea and the key handler refuses any key whose target is a text entry. Severity: 6/10

Existing Risk: 6/10 - Clicking the recording is the first thing a user does with a player, and after it the transport answers only the mouse, so a user pressing Space to pause concludes the feature is broken rather than that a key was missed.

Proposal Risk: 2/10 - The player has no text field of its own and the only textarea it owns is the one xterm creates for it, so exempting that one leaves nothing a chord could steal; the residual risk is a future surface adding a real text field to this tab.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1515: asciicast player chords stop working once the recording is clicked into". Step D3 of the description's **How to verify** ("Press `.` a few times, then `,`. Position moves one recorded event at a time and playback is paused") fails after the click, and so do the chords behind steps 2 and 3 of the same list. Replication: start the app, type `play <file>.cast` for any recording from an agent tab so the asciicast tab opens with playback running and focus on `document.body`; press `.` and observe the transport's play button flip from Pause to Play and the scrub value jump to the next recorded event, then press Space and see it flip back — both work here. Click anywhere inside `.asciicast-stage`; `document.activeElement` is now `TEXTAREA.xterm-helper-textarea`; press `.` and Space again and nothing happens: the play button stays Pause and the scrub value only drifts forward with untouched playback, which is the tell. Expected: every documented chord keeps working after the click, since `product/plans/complete/in-app-recording-replay.md` § Design decisions promises "Every control is a button as well as a chord — Space or `p` plays and pauses, `,` and `.` step, `[` and `]` change speed — so nothing is keyboard-only", and both the `play` row's chord table and `documentation/user-documentation/tab-types/recording-player.md` list them. Observed: all five chords are dead from that point on, consistently, in 2 of 2 runs against a hand-written recording and again in 2 of 2 runs against a live `opencode` session, where `document.activeElement` was still `TEXTAREA.xterm-helper-textarea` and the play button stayed Pause across `.` `,` `.` while the clock drifted forward with untouched playback. Root cause: `web/src/plugins/asciicast/AsciicastTab.tsx`, the `onKey` handler built in the component's `useMemo`, whose second guard is `if (target && (target.tagName === 'INPUT' || target.tagName === 'TEXTAREA')) return false;` — it cannot tell the terminal's own helper textarea from a field a person is typing into, and it also treats every `<input>` as text entry, so the seek bar (`input[type=range]`) swallows chords while focused too. The codebase already has the right predicate in `web/src/shared/text-entry.ts` (`isTextEntryElement`, shared by the context menu, the paste capability, and the overlay seam), but a concrete client plugin may import only `web/src/plugins/api.ts`, `../shared.css`, and its own contract under `eslint.plugin-boundaries.mjs`, so it never got to use it. Likely fix: publish `isTextEntryElement` through `web/src/plugins/api.ts` beside the `terminalColors`, `isMacPlatform`, and `ConfirmDialog` re-exports that file already carries for the same reason, and in `onKey` ignore the key only when the target is a real text entry that is not `.xterm-helper-textarea`. A regression test should render `AsciicastTab` with an xterm focused, dispatch a `keydown` for `.` on the helper textarea, and assert the scrub value advanced by one recorded event and playback paused — the case this guard was written to protect is a text field the player does not have.

* Show `live` on a recording whose session is still recording, not only on the seconds while its bytes are arriving

Existing Issue: The metadata line's `live` badge tracks whether the most recent poll brought new bytes, so a live harness session that is sitting idle — the normal state between two prompts — shows no badge at all, which is indistinguishable from a session that has finished. `product/specs/harness-recording.md:172-173` promises "while the session is still recording … the metadata line reads `live`", and step D1 of the description's **How to verify** says the tab "opens and plays; the metadata line reads `claude · claude · started <time>` with a `live` badge" — but on a real running session the badge is absent whenever the last 750 ms of polling found nothing new, which for an agent waiting on your next prompt is most of the time. Severity: 4/10

Existing Risk: 4/10 - The badge is the only signal that a harness is still recording, and the plan leans on it for exactly that: `product/plans/complete/in-app-recording-replay.md:165-167` argues that a live recording "shows the same duration without the badge once they stop, which is true of a live recording whose session has finished and false of nothing". In practice it is also false of a session that is alive and waiting for you, so the disambiguation the plan claims does not hold, and the fallback it names on the next line — an exit status — is the event that never arrives (see the item above). A user who opens a recording to check on a run that is still going gets no badge and reads it as finished.

Proposal Risk: 4/10 - The two roads out of this diverge sharply in cost, and the spec, the plan and the description currently back different ones. Narrowing the promise to "growing" is a wording change in `product/specs/harness-recording.md` and the description, plus nothing in code, but it enshrines a badge that lies about liveness. Broadening it to session-liveness is a behaviour change with a real obstacle: `finished` is computed once, by the opener, at `web/src/plugins/asciicast/open.ts`, from whether a live tab held the file at that moment, and nothing re-publishes it afterwards — so the tab has no signal to drive a continuous badge from, and a recording of a session that stopped later would need a fresh payload or a subscription. The residual risk either way is picking the cheap wording change and leaving users to guess.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1515: the asciicast live badge is absent while a live session waits for input". Decide the semantics first, because this is a promise three documents make differently, then make the code and the words agree. Replication: start the app, run `harness opencode --no-workspace --no-browser as livebox`, prompt it until it has produced output, then `play livebox` and let the session sit idle; the metadata line reads `opencode · livebox · started 8:27pm · 1:32` with no `live` badge although the tab is live and the recording is still open for append. Then send another prompt and watch it reappear. Observed: badge absent while the session is idle, present within a poll interval of each burst of output, absent after the session stops — in 2 of 2 runs. Root cause: `web/src/plugins/asciicast/AsciicastTab.tsx` renders the badge from a `growing` value that `usePlayback` returns from "the most recent poll brought new bytes", which is a statement about the last 750 ms rather than about the session; the tab does hold the fact it needs, because the payload's `finished` flag is already the opener's answer to "is a live tab still writing this file" — computed at `src/plugins/asciicast/activate.ts:37` from `capabilities.isRecordingLive(file)` — and it is consulted for the live-hold behaviour at `web/src/plugins/asciicast/AsciicastTab.tsx:28` while being ignored for the badge, which renders from `growing={source.growing}` at `:69`. If the broader reading is chosen, make that flag live rather than captured once — re-derive it per poll the way the host already derives `isRecordingLive` for `open` — and keep the plan's badge-after-duration behaviour for recordings that do carry an exit status, since that half starts working once the item above lands.
