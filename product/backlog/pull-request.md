# pull-request

* Close the security gap where the pre-install supply-chain gate audits the Janissary installation's lockfile instead of the lockfile of the project about to be installed.

Existing Issue: The new task tells the run to audit with the installation's own script runner before installing, and that script resolves the lockfile from its own location on disk, so in the ordinary workspace setup it inspects a copy belonging to the installation rather than the project — and where the installation is an installed package, which ships no lockfile at all, it exits with a data error and the rule that only success permits installation can never be satisfied. Severity: 7/10

Existing Risk: 6/10 - A run either refuses to install anything at all, or an agent that watches the gate fail on every run learns to wave it through, and either way a dependency the blocklist would have caught reaches an unattended install.

Proposal Risk: 2/10 - The gate then reports on the tree actually being installed, but the blocklist is only as current as the campaigns recorded in the repository, so a campaign disclosed after the last update still passes it.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1327: audit the project under test's own lockfile before the pre-install dependency install". The install step in the new task's Step 0 sends the run through the installation's runner, and `scripts/run.mjs` dispatches by a path relative to the runner's own directory while `scripts/check-malicious-package.mjs` derives its repository root from its own `import.meta.url` and reads the lockfile joined onto that root, so `--audit` always reads the installation's copy whatever the working directory is; `src/sandbox/environment.ts` sets the `janissary` variable to the install root of the running app, which on a workspace tab is the install rather than the workspace clone, and `package.json`'s `files` list publishes no lockfile at all, so an installed Janissary has nothing for the audit to read. Teach the gate to audit a lockfile it is handed, resolving a relative path against the working directory and reporting which file it read, keeping today's no-argument behaviour and every exit code exactly as they are — 0 clean, 2 blocked, 3 quarantined, 1 unreadable — and give the new form its own coverage beside the script, since no test file for the gate exists today. Then change the task's install step to audit the project under test: its own lockfile, through the project's own runner when it has one, which is the arrangement `AGENTS.md` already describes, and through the installation's runner with the project's lockfile named explicitly when it does not. Say there what each non-zero exit means, so a 2 or 3 stops the run and a 1 is a failed check rather than permission to install, matching the rule the repository guide already states. The install itself does not change: it stays `npm install --ignore-scripts` followed by the three rebuilds, and no browser is ever fetched.

* Stop the run when the app under test cannot be kept on loopback, rather than exposing it to the network for the length of the run.

Existing Issue: The new task tells the run to serve web apps on the loopback address using the project's own local-only option, but it never establishes that such an option exists, never checks the address the process actually bound, and names no other reason to stop, so a project whose documented start command binds every interface is started and driven anyway. Severity: 5/10

Existing Risk: 5/10 - The app under test, holding whatever fixtures and scratch state the run put in it, answers on every interface for as long as the run lasts, on a tab that is not necessarily confined, and nothing in the report says it was ever exposed.

Proposal Risk: 2/10 - The run still starts servers, but only ones it has confirmed bind loopback only, and a project that cannot be told to bind locally now costs an untested line instead of an exposure.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1327: refuse to drive a web app that is not bound to loopback". The discovery step in the new task says to serve web apps on the loopback address using the project's own local-only option, and the build-and-start step confirms readiness from the process's output and a real response; nothing establishes the bound address, and nothing says what to do when the project has no such option, though a documented start command that binds every interface is ordinary — a Python development server, a container-oriented `uvicorn --host 0.0.0.0`, and a bundler dev server started with a host flag all behave that way. The tab is not always confined either: the attached-browser guideline and `src/sandbox/environment.ts` both record configurations with no sandbox boundary, through workspaces configured with sandboxing off, a non-macOS remote, or a launch without a workspace, and the run is unattended in all of them. Add to the discovery step that a web project under test must be startable with an explicit loopback address named in its own instructions, and that when no such form can be determined the run stops with that reason before starting anything, recorded as an environment limitation rather than a start failure to retry. Add to the start step that the discovered command must name the loopback address, and that readiness reads the address from the server's own startup output when it prints one; do not add a process or socket inspection step, because `ai/tasks/take-documentation-screenshots.md` records that process inspection is not a pre-approved command in this repository and an unattended run would sit waiting on an approval, so the confirmation has to come from the command line and the output. Put the bound address on the app line of the report so a reader can see what was exposed, and add a line to the forbidden list making a non-loopback bind a stop rather than a note. The Janissary worked example already satisfies this — `src/index.ts` defaults the server host to the loopback address, `src/security.ts` rejects non-loopback request origins, and `scripts/docs-screenshots/scratch.mjs` binds loopback explicitly — so the rule is for other projects, and the report shape does not change.


* Keep two runs of the task from sharing one scratch directory, one stash stack, and one checkout of the project.

Existing Issue: Nothing in the new task stops a second run while one is still in flight, because the command queue that serializes task execution is per tab rather than per project, so two agent tabs open on the same project directory both drive the same fixed scratch path, the same working tree, and the same checkout of the primary branch. Severity: 5/10

Existing Risk: 5/10 - The run that finishes first deletes the shared scratch directory out from under the run still testing inside it, so a live instance, its log, and the evidence a reproduction depends on disappear mid-run and that run goes on to report against an app that is no longer there.

Proposal Risk: 2/10 - A second run now stops before it touches anything and says why, leaving the residual exposure to two runs in separate clones, which share no directory and only contend for the same branch.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1327: exclude a second concurrent run of the spec-testing task". Give the run a lock it takes before it changes anything and releases at teardown: a lock file in the repository's common git directory, so two tabs on one project and two workspaces of the same repository contend for the same lock, carrying the run's identity and the object ID of the stash it recorded. Take it in the preparation step beside the stash, and when it is already held, stop before changing the tree, with no install, no stash, and a report that names the holder. Release it in the teardown step and in the recovery rules for a stop, so no exit path can leave the project locked against the next run, and give the report a status that distinguishes this stop from the others. Make the collision explicit in the start-failure list as an environment cause in the same class as a port held by another process, so a launch that fails against the per-directory instance lock the other run holds is reported as unfiled rather than researched as a startup bug; the existing catch-all may already carry an agent that far, but the list should not depend on it. The stash rules stay as they are, since locating this run's stash by object ID already stops a run from popping another run's, and the scratch path stays fixed, because exclusion is what makes one fixed path safe. The task picker spec and the bugs backlog do not change, and the report shape is unchanged.
