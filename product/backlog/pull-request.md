# pull-request

* Plan fidelity: preserve the connection-history viewport when new prompt blocks arrive while an older page is loading.

Existing Issue: `web/src/plugins/connections/useConnectionHistoryScroll.ts` stores only the offset at which an older-page request started and treats any later offset change as the arrival of that older window, but a new prompt block increases `window.offset`, so the effect applies the stored height delta and clears the restoration before the older blocks arrive. Severity: 4/10

Existing Risk: 4/10 - A reader who is at the top of a live session's history when a new prompt starts is pushed away from the top by the new content, and when the older page finally arrives its viewport is no longer preserved, so paging and reading a busy session lose the reader's place.

Proposal Risk: 1/10 - Distinguishing an offset decrease from an offset increase leaves the true older-page path unchanged; the ambiguity of an update carrying both changes is the only case the new test must pin.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1916 "preserve the connection-history viewport when new blocks arrive during paging". In `web/src/plugins/connections/useConnectionHistoryScroll.ts`, record the requested window's offset and compare the new window's identity rather than merely detecting a change: apply the stored height delta and clear the restoration only when the first rendered block moved toward older history (the absolute position decreased, for example `offset < requestedOffset`), and when the offset increased because new blocks arrived, refresh the stored baseline height and keep the restoration pending so the eventual older window still restores. Thread `window.totalBlocks` or the first block's `startedAt` from `web/src/plugins/connections/ConnectionTab.tsx` into the hook if needed to distinguish the two cases, and retain the current active/follow-threshold behavior and the rejection handler's clearing of both refs.
