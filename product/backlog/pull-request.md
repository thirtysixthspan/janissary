# pull-request

* Make a persona session launched under a custom role reach its ACP session instead of failing before any model is called

Existing Issue: A persona declaring a custom role such as `research` never reaches its model; the editor reports `researcher: ACP error: Invalid ACP record source.`, its pill reads `no suggestion`, and no inline edit appears. Severity: 9/10

Existing Risk: 9/10 - Every persona session that uses a custom role fails at startup, so the feature's central promise — that any role resolving from the effective roles file configures a persona — holds for none of them, while editor, monitor and launcher paths all share the failing entry point.

Proposal Risk: 3/10 - Record sources must accept arbitrary role strings without loosening the built-in validation of the core ask/tell path, or custom-role records become unqueryable and silently mislabeled.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2170 "Custom-role persona sessions fail with Invalid ACP record source". D1 (description, How to verify step 1): "Editor suggestion uses the declared role's model — Do: place the caret at the start of an otherwise-empty line below the text, press `>`, type `researcher rewrite this sentence in one sentence`, and press Enter. Wait for the reply." Setup: scratch project `.janissary/roles.json` with a custom `research` role whose single entry is an enabled claude model and whose commands grant `file read`; `ai/personas/editor/researcher.md` with first line `[//]: # role: research` and body `You are a careful researcher.`; open `notes.md` in the editor and send the `>` request. Expected, from the description: "an inline preview of the proposed edit appears in the buffer" and from the canonical plan "suggestions go through `promptPersonaRole` with the persona's body and role". Observed on two fresh app instances (2 of 2): the pill reads `no suggestion`, no hunk is inserted, and the notifications feed carries exactly `researcher: ACP error: Invalid ACP record source.`. G3 (generated), which declares `[//]: # role:   RESEARCH  ` to exercise trimmed, case-insensitive resolution, resolves the custom role but hits the same failure; the steps that need a custom-role session (D2, D3, D4, D5, D7, D11–D15) share the cause even where no model credentials were available to reach a reply. Root cause: `src/acp/persona-role.ts` `promptPersonaRole` casts the declared role with `role as AcpRole` and passes it as `roleName` to `beginCoreRecord` in `src/acp/record-feed.ts`; `beginCoreRecord` calls `records.begin(source)`, where `isRecordSource` in `src/acp-records/validation.ts` accepts a `role` only when it is listed in `ACP_ROLES = ['ask', 'tell']` from `src/acp/role.ts`. A custom role string therefore throws `Invalid ACP record source.`, which the `catch` in `promptPersonaRole` returns as `ACP error: Invalid ACP record source.` before any launchable entry is used. Likely fix: carry the declared role in a string-valued field of the record source and have `isRecordSource` validate a nonempty string for that field, or tag custom-role records with the default role while storing the declared name separately, leaving ask/tell validation unchanged. A regression test should drive `promptPersonaRole` with a custom role and assert that it reaches the launchable entries and opens a connection record rather than returning an error, and that an ask/tell record still validates.


* Show the full persona load-error text in the transcript instead of dropping its `<role>` placeholder

Existing Issue: The malformed-directive load error is rendered as `Persona "researcher": expected first line [//]: # role: .`, missing the literal `<role>` placeholder, so the exact message the description and plan promise cannot be found. Severity: 4/10

Existing Risk: 5/10 - A verifier matching the documented error string sees a different line, and the correct directive syntax is hidden from the one place the failure is reported, making a malformed persona harder to repair.

Proposal Risk: 2/10 - Escaping the placeholder must not change other transcript rendering or break markdown links elsewhere; a narrowly scoped escape at the transcript line boundary keeps that risk contained.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2170 "Persona load-error text loses its <role> placeholder when rendered". D8 (description, How to verify step 8): "A missing or malformed role directive fails to load and the persona is not offered — Do: change the first line of `researcher.md` to the old directive `[//]: # claude:Sonnet:high`, save it, then in a fresh editor `>` query type `> research` and press Tab, and run `monitor researcher` from the shell. Expect: the persona name is not completed or offered, no session opens, and the load failure reads exactly `Persona \"<persona>\": expected first line [//]: # role: <role>.`." G4 (generated) uses a `researcher.md` with no directive line at all and the same expectation. Inputs: scratch project with `ai/personas/monitor/researcher.md` carrying the malformed first line, then no first line; run `monitor researcher` from the janus shell tab. Expected per the description and canonical plan requirement 11: the exact string `Persona "researcher": expected first line [//]: # role: <role>.`. Observed on two fresh app instances: the rendered shell output is `<p>Persona "researcher": expected first line [//]: # role: .</p>` — completion correctly omits the persona and no session opens, but the placeholder is gone. Root cause: `parseDirective` in `src/persona-parsing.ts` throws the message containing `<role>`; `loadPersona` in `src/personas.ts` and `monitor.start` in `src/monitor/manager.ts` surface it unchanged through `errorText` in `src/error-text.ts`; `renderLine` in `web/src/shared/transcript/transcript-line.tsx` then injects markdown HTML with `dangerouslySetInnerHTML`, where `<role>` is parsed as an HTML tag and contributes no text. Likely fix: escape angle brackets in transcript text before markdown rendering, or render this line as plain text, so the literal placeholder stays visible. A regression test should assert that the rendered transcript text contains the full literal `expected first line [//]: # role: <role>.` while existing markdown-link assertions keep passing.
