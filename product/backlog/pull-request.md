# pull-request

* Close the security gap where a remote claude role session reattached to a peer parked across a remote upgrade still starts with its built-in tools on, which the version-39 handshake claim says cannot happen.

Existing Issue: The version-39 comment in the remote protocol module and the new "Protocol version 39" spec paragraph both say the exact-version handshake refuses a host that would drop `sessionMeta`, but an attach's handshake is answered by the freshly installed relaying `remote-serve` rather than the parked peer, and a version-38 peer still answers `attach` and `session-state` normally, so a tab reattached to a peer parked before the remote was upgraded sends its role `acp-open` to a version-38 decoder that silently drops `sessionMeta` and launches the Claude adapter with its built-in tools on. Severity: 5/10

Existing Risk: 4/10 - After a remote upgrade, any reattached remote shell tab whose ask or tell role runs claude quietly regains Read, Glob, Grep, and the other built-in tools that need no permission inside the remote workspace, while the help pages, specs, and connection tab all say the session has none.

Proposal Risk: 2/10 - A peer record written by a build that predates the version stamp, or a stamp the relay misreads, would refuse an attach that used to succeed, so the user has to relaunch the parked session instead of reattaching; a test of the mismatch path is what would show this going wrong.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1983 "refuse to relay an attach into a parked peer whose protocol version differs, so a version-38 peer cannot silently drop a role session's sessionMeta". Today `relayPeer` in `src/remote/serve-detach.ts` reads the parked peer's record through `readPeerRecord` in `src/remote/peer-record.ts` and relays bytes into its socket with no version check, and `RemoteServer.attach` in `src/remote/serve.ts` reports only accepted or terminated. Add a `version?: number` field to `PeerRecord` in `src/remote/peer-record.ts`, written as `REMOTE_PROTOCOL_VERSION` from `src/remote/protocol.ts` by both `writePeerRecord` calls in `src/remote/serve-detach.ts`; keep `isPeerRecord` accepting a record without the field (but rejecting a non-integer one) so a newer relay can still read an older record, and have `relayPeer` treat a missing or different `version` as a mismatch and end the relay through the non-terminal path (`ended(false)`, which `RemoteServer.attach` turns into a nonzero shutdown with no `attach-result` refusal), so the session stays parked rather than being declared gone. This is an on-host file contract, not a wire frame, so `REMOTE_PROTOCOL_VERSION` stays 39. Then correct the version-39 comment in `src/remote/protocol.ts` and the attach paragraph in `product/specs/remote-server.md` (the one beginning "The handshake check is narrower for an attach than for a launch", which still says an older peer refuses the query by name) to say that a peer parked under another version is refused at relay time. Add cases to `src/remote/peer-record.test.ts` (a record round-trips with its version; a record with no version still reads as valid; a non-integer version reads as invalid) and to the `relayPeer` attach cases in `src/remote/serve.test.ts` (a record with a missing or different version never connects to its socket and ends without an `attach-result` refusal). The existing attach cases in `src/remote/serve.test.ts` cover the matching-version path and must keep passing once their fixture records carry the version; nothing covers how the local attach flow in `src/remote/attach.ts` and `src/remote/resume.ts` reports a relay that exits without an `attach-result`, so confirm by reading that it leaves the session parked with a failure message rather than closing it, and say so in the fix plan.
