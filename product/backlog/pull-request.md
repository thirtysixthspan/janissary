# pull-request

* Handle the loss of per-command host and refusal metadata when a reply's commands run in parallel.

Existing Issue: The new parallel launch calls `runCommand` for every command in a batch before any result settles, but the command gateway forwards one mutable step slot, so every `ranCommand` event of a batch carries the last-launched command's workspace and refused values instead of its own. Severity: 7/10

Existing Risk: 7/10 - A batch mixing caller and workspace commands, or an enabled command after a disabled one, tags results with the wrong host and can fire a false "command disabled" notification or suppress a real one, leaving misleading command records in the activity log.

Proposal Risk: 2/10 - Binding each result to its own gate decision is a contained change in the command gateway, and existing single-command event-order and refusal tests pin the current metadata, so little risk remains after the change.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2137 "preserve per-command host and refusal metadata for parallel ACP batches". In src/acp/drive-loop.ts, `gatedRunner` records each `DrivenStep` into a single shared `step` variable through its `remember` callback, and `driveToolLoop`'s `ranCommand` wrapper reads that slot when the loop reports a result. Because src/acp/loop.ts now calls `runCommand` for every command in a batch before any settle completes, the slot holds only the last-launched command's decision. Carry the gate decision with the specific command's result instead of a shared slot — for example, return the `DrivenStep` alongside the output from `gatedRunner` and pass it through the loop's result, or key stored metadata to the exact `runCommand` invocation (not a command-string map, which breaks when the same command appears twice) and have the `ranCommand` wrapper consume the entry for the command that completed. Keep the `startCommand` arguments as they are; they are already emitted with the correct per-command metadata at call time. Add a test in src/acp/drive-loop.test.ts that drives one reply containing two async commands routed to different hosts (one caller, one workspace) and asserts each `ranCommand` event carries its own `workspace` value, plus a case mixing a disabled command with an enabled one to confirm the disabled notification is raised only for the disabled command. The existing single-command routing, workspace-tagging, and refusal tests in src/acp/drive-loop.test.ts, and the parallel-launch and error-result tests in src/acp/loop.test.ts, cover the behavior that must not move.
