* Make the grid's cell editor take a typed value on a cell that already reads NULL

Existing Issue: Double-clicking a cell that reads `NULL` opens an editor whose `Set NULL` box is already ticked and whose field is pinned empty, so typed characters never appear and Enter writes `NULL` again, on every run. Severity: 7/10

Existing Risk: 6/10 - Filling in a missing value looks like it saved and did not, so a user tidying incomplete rows believes the data is complete when the database still holds nulls.

Proposal Risk: 1/10 - Unticking on the first keystroke makes the typed text the value, and a test that opens the editor on a null cell and types is what would hold it there.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1467: the grid's cell editor discards typed text on a cell that already holds NULL". Failing step D4 (description), verbatim: "Double-click a `status` cell, type a value, press Enter, and confirm the row updated. Toggle **NULL** on a `total` cell and confirm the cell reads `NULL` in a muted style. Press Escape in an editor and confirm nothing was sent." Reproduce from a project with no database: `db sqlite create shop`; `sql shop`; from another tab `db sqlite query shop "CREATE TABLE orders (id INTEGER PRIMARY KEY, customer TEXT NOT NULL, status TEXT, total REAL)"` and `db sqlite query shop "INSERT INTO orders (id, customer, status, total) VALUES (1, 'ada', NULL, 10.0)"`; press `Refresh` in the `shop` tab and choose `orders` from the table dropdown; double-click the third cell of the first row, the `status` column that reads `NULL`, type `recovered` and press Enter. Expected, per `product/specs/sql-database.md`: "A cell holds either text or null, and they are drawn differently … The editor has a **NULL** toggle, so writing a null and writing the four characters `NULL` are two different acts. The toggle is part of the value being edited rather than a write of its own — it takes effect when the editor commits, the same way the typed text does." Observed on 8f2fb12 in three consecutive runs: the editor opens with `Set NULL` checked and the field's value empty, after typing nine characters the field still reads empty, and Enter leaves the cell reading `NULL`. The same run's control, a cell holding `open`, takes the typed text and commits it, and unticking `Set NULL` first makes a typed value commit, so the defect is specific to a cell that already holds null. Cause: `web/src/plugins/sql/CellEditor.tsx` seeds its `isNull` state from `cell?.isNull` and passes `value={isNull ? '' : text}` to the host's `InlineEditInput`, a controlled input, so React restores the empty string on every keystroke and `onCommit` sends `isNull ? null : text`; `web/src/plugins/sql/InsertForm.tsx` deliberately takes the opposite approach, its toggles "off until the user turns it on". Likely fix: untick the toggle on the first keystroke, or seed `isNull` false and let the field's emptiness be the only sign of null, and stop pinning the field's value to `''` while the toggle is ticked. A regression test belongs in `web/src/plugins/sql/DataGrid.test.tsx`: render a row whose cell is `{ text: '', isNull: true }`, open its editor, type into `.sql-cell-input`, press Enter, and assert `update-cell` carries the typed string rather than a null.


* Name the database on every notifications line its sql tab reports

Existing Issue: Every line the sql tab reports into the notifications feed reads `1:19pm sql: no such table: nosuchtable` while the tab's own name in the strip is `shop`, because the line is attributed to the tab's internal label rather than its name. Severity: 5/10

Existing Risk: 5/10 - With two databases open the feed shows `sql` and `sql2` and neither says which database a failed statement, a row count or a query result came from, so a user has to visit each tab to find out.

Proposal Risk: 1/10 - Attribution falls back to the label for a tab that has no title, which is the path `src/plugins/notify-user.test.ts` already covers.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1467: a notification from a sql tab is attributed to `sql` rather than to the database". Failing step G3 (generated), verbatim: "With `shop` showing a page of `orders`, type `SELECT * FROM nosuchtable` into the SQL console and press Enter. Confirm the tab still shows the same grid with no error message of its own, and read the notifications feed line the failure produced." Reproduce from a project with no database: `db sqlite create shop`; `sql shop`; `db sqlite query shop "CREATE TABLE orders (id INTEGER PRIMARY KEY, customer TEXT NOT NULL, status TEXT, total REAL)"` and one `INSERT`; press `Refresh` and choose `orders`; open the notifications tab; type `SELECT * FROM nosuchtable` into the `SQL >` console and press Enter; read the newest feed line. Expected, per `product/specs/sql-database.md`: "Every notification the tab reports — a result, a count, or a failure — is formatted like any other line in the feed and attributed to the database's tab, so it reads `● 8:32pm shop: …` with the tab's colour on the dot." Observed on 8f2fb12 in two runs: the line renders `<span class="message-tab">sql</span>` followed by the message, reading `1:19pm sql no such table: nosuchtable`, while the tab strip names the same tab `shop`; the grid itself was correctly left exactly as it was. Cause: `notifyUser` in `src/plugins/context.ts` passes `own?.label ?? origin.label` to `notify`, and `addPluginTab` in `src/tab/creators.ts` gives a plugin tab `label = uniquePluginLabel(tabs, labelPrefix)` — `sql`, then `sql2` — while the payload's title (`shop`) goes into `title`, which is what the tab strip and a feed line's header draw; `src/plugins/notify-user.test.ts` builds its fixture with `label: 'shop'`, a label `addPluginTab` never produces, so the suite pins a value the app cannot have. Likely fix: attribute to the tab's displayed name, `tab.title` falling back to `tab.label`. A regression test should build its fixture through `addPluginTab`, or assert against a tab whose `label` is the prefix and whose `title` is the database name, so the two cannot drift apart again.
