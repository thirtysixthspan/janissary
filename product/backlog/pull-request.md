# pull-request

* Make the agent command's result appear in the shell tab that ran it

Existing Issue: Running `agent` from a shell tab's command bar shows only the echoed input line, because its `Status:` line and response reach the activity log but never the screen, so the spec's caller-transcript promise fails for every launch this run exercised. Severity: 8/10

Existing Risk: 6/10 - A user who runs an agent task from a shell tab sees no status or response, so success and failure look the same and a task that already changed the project can be run again by mistake.

Proposal Risk: 3/10 - After the fix the reply shows for any run that finishes inside the capture window, but a run that outlasts the current 30-second dispatch capture would still lose its reply until the structured path bypasses that limit as the plan requires.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1672 "Show the agent command's result in the shell tab that ran it". Replication: start the app with `HOME=<scratch home> node bin/janus.mjs --no-open <scratch work dir>` and drive its janus shell tab through the attached browser, typing each line below into the command bar, one at a time, and pressing Enter: `agent execute` (generated step G1, spec "Launch grammar": "An invocation without a nonempty task after execute" yields "Agent: missing task after execute."); `agent in group nosuch execute x.md` (G2, spec "Run monitoring": an unknown selector yields `Agent: group "nosuch" does not exist.` before any run is created); `agent in workspace nosuch execute x.md` (G3, spec "Run ownership": yields `Agent: unknown workspace "nosuch".` with no clone created); `agent in a tab` (G4, yields "Agent: missing execute clause." with no monitor tab); and the additional cases `AGENT IN A TAB IN A TAB EXECUTE x.md` (G5, `Agent: duplicate clause "in a tab".`), `agent execute "x.md` (G6, `Agent: malformed quoted value.`), `agent in group "two words" execute x.md` (G7, `Agent: group "two words" does not exist.`), `agent with effort high with effort low execute x.md` (G8, `Agent: duplicate clause "with effort".`), and `agent in group "" execute x.md` (G9, `Agent: missing value for in group.`). Expected: each reply appears on the shell tab's screen beneath its line, as the spec's "the caller transcript shows Status: <...>" requires. Observed: each of G1 to G9 appends `Status: failed` and the exact expected response to the tab's entry in `<project-dir>/.janissary/log/<date>.json`, but the screen shows only the echoed input line; the batch and a rerun on a freshly started app both failed this way (2 of 2), and the same step in the same tab shows `help`'s reply, so shell replies do render in general. Cause: `CommandManager.dispatchLine` in `src/command/manager.ts`, in its `structuredResult` branch, returns `{ dispatched: true, output: '', result }` whenever the command returns a value, discarding the entries `executeAndCapture` in `src/capture/execute-and-capture.ts` collected for the invocation. `agent` is the only `structuredResult` command, and its `command.run` in `src/commands/agent.ts` appends the formatted reply through `appendCommandOutput` in `src/command/append.ts` under the caller's invocation, so the reply is captured and then dropped. `useShellSubmit` in `web/src/plugins/shell/useShellSubmit.ts` calls `displayReply` with that empty output, so nothing is drawn. Ruled out: the parser and resolver, since the activity log holds the exact expected responses, and the group and workspace checks, since no tab or clone was created. Not reproduced here: a run that outlasts the 30-second capture limit, which needs ACP and provider credentials; the same branch applies `DISPATCH_CAPTURE_LIMIT_MS`, which the plan says agent results must bypass. Fix: return the captured output together with the structured result, and exempt agent structured results from the capture limit, leaving the client's display path as it is. Regression test: a `src/command/manager.test.ts` case in which a `structuredResult` command returns a value and appends an invocation-scoped entry, asserting that entry is in the returned `output`, plus a shell-tab client test in `web/src/plugins/shell` asserting that a dispatched reply with output renders beneath its line.
