# pull-request

* Make `janus stop` end a live instance when the sandbox denies signals to detached processes

Existing Issue: `janus stop` exits 1 with `kill EPERM` against a live instance and leaves that instance still answering on its address, so the documented CLI stop cannot end the session in this sandbox. Severity: 8/10

Existing Risk: 8/10 - The only documented way to stop an instance fails while its lock, listener and log all still say it is running, so an operator has no supported command to end it and can only fall back on a browser disconnect.

Proposal Risk: 4/10 - A permission-free shutdown channel is a new local control path that must stay scoped to the instance's own directory and token, or it could be used to stop another project's server.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2203 "Make janus stop end a live instance when the sandbox denies signals to detached processes". Step D11 (description, session-ending) verbatim: "Stop the instance. Do: run `janus stop <project-dir>` and read the link and logs afterwards. Expect: the address is no longer reachable, `latest.log` still names the last run's file, and that file still holds its `__JANUS_URL__` line." To replicate, make a scratch project directory with `.janissary/config.json` holding `{"logEnabled": false, "logRetentionInDays": 7}`, point the child `HOME` at a scratch home, run `node bin/janus.mjs --no-open <project-dir>`, read the address from `<project-dir>/.janissary/logs/server/latest.log` and the pid from `<project-dir>/.janissary/lock`, then run `node bin/janus.mjs stop <project-dir>` and after 1.5 seconds request the address again and re-read the link and log. The promise is `product/specs/cli.md`: "it reads the instance lock (`.janissary/lock`) for the target directory ... and, if the recorded process ID is alive, sends it SIGTERM — triggering the same graceful shutdown sequence above", and the step expects the address no longer reachable. Observed consistently 2 of 2 after two fresh starts: stop exits 1 with empty stdout and exactly `janissary 0.22.0 — failed to start: kill EPERM` on stderr, the address still answers HTTP 200 after 1.5 seconds, the lock is still present, and `latest.log` and the first run's log are byte-for-byte unchanged. Root cause: the owner-query repair works — `pidBelongsToCurrentUser` in `src/process-owner.ts` returns `undefined` when this sandbox denies `ps` with EPERM, and `isOwnInstanceAlive` in `src/instance-lock.ts` returns `pidBelongsToCurrentUser(pid) !== false`, so `stopInstance` in `src/stop-instance.ts` no longer prints `no running janus instance` and reaches `process.kill(pid, 'SIGTERM')`. That signal is denied too: the server was spawned detached (`bin/janus.mjs`) and is not a child of the stop process, so the OS returns EPERM; `process.kill` throws before the SIGTERM handler registered in `src/main.ts` can run, and `boot()`'s catch in `src/main.ts` formats it through `formatFatal` in `src/startup-errors.ts` as `failed to start: kill EPERM` with exit 1. A direct `ps -p 1 -o uid=` answers "operation not permitted" in this sandbox, while a plain WebSocket client connecting to the same instance and disconnecting makes it exit cleanly through its last-client shutdown, so the server itself is stoppable. Likely fix: give `stopInstance` a permission-free fallback alongside SIGTERM — write a stop-request sentinel under the target `.janissary/` that the running server polls and answers by calling its own shutdown path, so a sandbox that denies cross-process signals can still end its own instance; keep the bare-pid lock, the exact already-running and no-running messages, and the foreign-owner takeover intact. A regression test should mock `process.kill` to throw EPERM and assert that `stopInstance` still ends the live instance through the fallback while a positively foreign pid still gets the no-running message and no shutdown.
