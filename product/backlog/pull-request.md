# pull-request

* Share the home-file-over-project-file resolution, partial-loss decode, and one-line problem reporting between the launcher and roles config files instead of shipping a second copy.

Existing Issue: `src/plugins/roles/roles-file.ts` repeats, almost line for line, the precedence, candidate walk, partial-loss counting, and problem-line composition that `src/plugins/launcher/commands-file.ts` already implements for `launcher.json` — including the home path join, the project-beats-home rule, the drop-and-count decode, and the `— showing …` fallback phrasing — and the two can now drift apart with nothing to notice, so a fix to how a broken config file is reported would land in one plugin and leave the other describing itself differently. Severity: 4/10

Existing Risk: 4/10 - The second copy is the one that goes stale: a user who relies on the roles tab being corrected to describe a broken project file correctly can end up with the launcher and the roles tab answering the same situation in two different words, and each future change to the shared rule has to be found and applied twice.

Proposal Risk: 2/10 - The two callers keep their own decode and their own wording hooks, so the shared module is a path-and-reporting seam rather than a new abstraction either plugin has to understand.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1668 "share the home-over-project config file resolution between the launcher and roles plugins". Extract the parts the two already agree on into a new module `src/plugins/config-file.ts` that takes the file name, the home and root directories, and a decode callback returning either the decoded value plus a dropped count, or undefined, and answers the resolved `{ path, source, decoded, dropped, problem }` for one candidate; the fallback chain, the creation attempt when neither file exists, and the final "— showing …" phrasing live there. `src/plugins/roles/roles-file.ts` and `src/plugins/launcher/commands-file.ts` then supply their own decode and default-entry functions and keep their own public signatures — `readRolesFile(home, root)` and `readLauncherFile(home, root)` must not change, because `src/plugins/roles/roles-file.test.ts`, `src/plugins/roles/activate.test.ts`, and the launcher's `commands-file.test.ts` all call them and their assertions on the exact problem strings must keep passing unchanged. The shared module is host plugin infrastructure under `src/plugins/`, so it is reachable from both plugins without touching either plugin import boundary. Note in the new module's comment why the two plugins share it and what stays per-plugin, and add the roles-specific creation of the default file as the caller-supplied default rather than inside the shared module, since the launcher creates its file through a different exported function.
