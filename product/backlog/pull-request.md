Existing Issue: An end attempt on a parked session reattaches far enough to send `shutdown`, and the accepted branch of `endParkedSession` in `src/sessions/end-session.ts` calls `RemoteManager.close` before its own `finish({ ended: true })` — but `close` runs the launch handlers' `onClosed` sweep synchronously, and the end channel's own handler is registered on that entry, so `onClosed` settles the promise with `{ ended: false, reason: 'The connection to <host> closed.' }` first and the success branch never fires. Severity: 6/10

Existing Risk: 6/10 - Every end that actually works is presented to the user as a failure: the row never becomes ended, the record survives with a failure reason on it, and the user retries against a host whose peer is already dead, learning nothing from the first attempt.

Proposal Risk: 2/10 - The outcome ordering is then pinned by tests, but a settlement that arrives through a different funnel than the one the tests fake — the peer refusing mid-shutdown, say — still has to land on the row correctly, so the row's final states need checking together.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1143: an end attempt that succeeds resolves as a failure and keeps its record". Make the accepted branch of `endParkedSession` settle the outcome before the channel's teardown can speak: either resolve `{ ended: true }` first and call `managers.remote.close(label)` after, or rework `endParkedSession`'s handlers so `onClosed` only settles when the attempt has not already been answered by `onResult` — one settled flag checked by both. Proposal Risk: 2/10 - Making the store's shape account-safe is a small change, but whichever option is taken records a decision about a directory layout two installations and one shared directory have to agree on, so it wants a deliberate answer rather than a incidental patch.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1143: the sessions record's no-second-writer guarantee is narrower than the lock now enforcing it".
