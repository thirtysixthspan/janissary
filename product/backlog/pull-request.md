# pull-request

* Deliver the plan's promise that a docked file navigator is left in place by a reveal, which the current activation undocks into the centre strip.

Existing Issue: The reveal ends by calling `TabManager.setActiveTab` on the navigator, and that path runs `revealTab`, which calls `applyDock(..., null, ...)` for any tab carrying `dock` and so undocks the navigator and makes it the active centre tab before `setActiveTabOp`'s dock guard can return. Severity: 7/10

Existing Risk: 7/10 - Once the reveal RPC lands, every reveal from the default docked navigator will pull it out of the sidebar and cover the editor the user was working in, the exact disruption the plan's "docked navigator is a no-op" decision exists to prevent, though the user can re-dock it.

Proposal Risk: 2/10 - A dock check before activation keeps the sidebar case untouched while still activating a centre-strip or hidden navigator; the only residual is that a navigator that closes between opening and activation stays a silent no-op, as it already is.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2009 "keep a docked file navigator docked when a reveal activates it". No port or type change is needed: `RevealPort` already carries `managers`, and `05`'s `revealPort()` composition stays as specified.
