# pull-request

* Forget the search tab's query, results, and term history when the tab is closed.

Existing Issue: Closing the search tab and opening it again, with Cmd+Shift+F or a bare `search`, brings back the previous query, its rows, and that query in the arrow-key history, although the spec says closing the tab forgets the history along with the query. Severity: 3/10

Existing Risk: 3/10 - Stale results reappear in what looks like a fresh tab, and the spec now describes the opposite of what the app does, so the next change to this area is built on a false premise.

Proposal Risk: 2/10 - Resetting only when the host builds a new tab keeps the focus-an-open-tab path unchanged, so the one thing to watch is the spec's other sentence about a bare `search` landing the user back where they were, which applies only while the tab is still open.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1481: reset the search tab's query, rows, and history when it is closed and reopened". Replication: generated step from this test run, failed 2 of 2 on a fresh app. On a scratch project that is its own git repository, open the search tab with Cmd+Shift+F, type `compileMatcher` and let its 21 rows settle, close the tab with its `.tab-close` control, then run `search` (or press Cmd+Shift+F) from the `janus` agent tab, click the search bar, and press ArrowUp. Expected, per `product/specs/search-tab.md` ("The list is the tab's own, and closing the tab forgets it along with the query."): an empty bar, no rows, `Type to search`, and ArrowUp recalling nothing. Observed: the reopened bar reads `compileMatcher`, the 21 rows are back, and ArrowUp recalls `compileMatcher`. Root cause: `SearchSession` in `src/plugins/search/session.ts` lives as long as the plugin, not the tab, and `open` hands its retained `this.payload` to the `openOrFocusTab` factory, which the host runs only when it creates a new tab; `SearchTab` in `web/src/plugins/search/SearchTab.tsx` then seeds its query and its history from that payload. The spec's sentence "A bare `search` leaves the tab showing whatever it last searched for" is about focusing a tab that is still open, and that path does not run the factory. Likely fix: inside the factory in `SearchSession.open`, cancel any scan and reset `this.payload` to `emptyPayload()` carrying the remembered modes (`this.saved`), seeded with the command's query when one was given, so a tab the host has to build starts empty while a focused tab keeps its state. Regression test in `src/plugins/search/activate.test.ts`: run a search, then call `command('')` with an `openOrFocusTab` fake that invokes the factory as a new tab would, and assert the factory's payload has an empty query and no rows while the saved modes are kept; plus a case where the fake does not invoke the factory and the previous payload is untouched.
