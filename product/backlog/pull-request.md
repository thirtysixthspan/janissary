# pull-request

* Give a remote harness's live auto-approval notifications a toast, distinguishing them from ones replayed after a reattach.

Existing Issue: `createRemotePtySession`'s `onGateEvent` handler in `src/remote/pty-session.ts` always passes `new Date(capturedAt)` as `notify()`'s `detectedAt` argument, which unconditionally marks every remote auto-approve notification as `replayed` in `src/notifications/deliver.ts`, so a live auto-approval happening right now never toasts — only queued-while-detached auto-approvals were meant to skip the toast. Severity: 6/10

Existing Risk: 5/10 - A user working with a remote harness tab in the background gets no corner notification when auto-approve fires, so an unattended action against their real files goes unnoticed until they happen to check the notifications feed, defeating the purpose of a toast for a workspaced but unsandboxed operation.

Proposal Risk: 2/10 - The distinction between live and replayed delivery now depends on which `SessionRouter` path a frame takes, so a future change to that routing could silently reintroduce the bug if it is not covered by a test asserting the boolean each path passes.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1169: give a remote harness's live auto-approval notifications a toast, distinguishing them from ones replayed after a reattach". `src/remote/channel-sessions.ts`'s `SessionListener.onGateEvent` type currently takes `(message, capturedAt, capture?)`; add a `replayed: boolean` parameter (placed before the optional `capture`) so callers can tell the two delivery paths apart. In `SessionRouter.attach()`'s claim loop, the branch handling `frame.type === 'gate-event'` delivers frames held in `this.pending` while a tab was still being rebuilt after a reconnect — pass `replayed: true` there. In `SessionRouter.gateEvent()`, the live-delivery method called whenever a listener is already registered for the id, pass `replayed: false`. Then in `src/remote/pty-session.ts`'s `createRemotePtySession`, update the `onGateEvent` callback to accept the new `replayed` parameter and pass `replayed ? new Date(capturedAt) : undefined` as `notify()`'s trailing `detectedAt` argument, instead of always passing `new Date(capturedAt)`; update the surrounding comment, which currently says the translation is "stamped with the original detection time (not now)" unconditionally. Update `src/remote/channel-sessions.test.ts`'s `describe('SessionRouter — gate-event', …)` block to assert the boolean each path passes (`gateEvent()` → `false`, the held-then-`attach()`-claimed case → `true`). Update `src/remote/pty-session.test.ts`'s two existing gate-event tests (currently titled around "stamped with the original detection time") to reflect that a listener already registered before the frame arrives is the live path and must now produce `notify()` calls with `detectedAt` left `undefined`, and add a new test exercising the replay path — using the same `sessionId`-set-before-handshake pattern `src/remote/channel.test.ts`'s `describe('RemoteChannel — frames for an id with no listener yet', …)` uses to enter the attaching/hold state, receiving a `gate-event` frame before `createRemotePtySession` registers its listener — asserting `notify()` is called with `detectedAt` equal to `new Date(capturedAt)` in that case. `src/notifications/deliver.test.ts`'s existing coverage of `replayed` behavior in `deliverNotification` does not need to change, since this fix only corrects which callers pass `replayed: true`.
