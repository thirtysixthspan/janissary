# pull-request

* Guard the newly executable export command against overwriting the hosts catalog it reads from.

Existing Issue: The new command dispatch in `src/plugins/hosts/activate.ts` routes `hosts export <file>` into `runSshIntent` in `src/plugins/hosts/ssh-intents.ts`, which resolves any transcript operand to an absolute path and calls `exportSshHosts` with no check that the target is the project or home `hosts.json` that supplied the catalog being exported. Severity: 6/10

Existing Risk: 6/10 - An operand such as `hosts export ~/.janissary/hosts.json` makes `writeSshConfigFile` replace a usable catalog with an ssh-config section, so every saved host is silently destroyed while the transcript reports a successful export and the tab keeps showing the stale rows.

Proposal Risk: 2/10 - A path-equality guard before the write leaves both catalog files byte-for-byte intact and every ordinary ssh-config target untouched; the only residual hazard is a spelling or symlink mismatch in the comparison, which resolving both paths to their real paths removes.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 2242 "guard the hosts export command against overwriting its own catalog". In `src/plugins/hosts/ssh-intents.ts`, after `targetOf` resolves an export operand and before calling `exportSshHosts`, compare the resolved absolute path with both catalog locations, `path.join(root, '.janissary', 'hosts.json')` and `path.join(home, '.janissary', 'hosts.json')`, resolving existing paths through `realpathSync` so a symlinked or `..`-spelled operand cannot slip past; on a match, use the existing `report` helper to refuse with a message naming the catalog and stating that an export cannot target it, and return without calling `exportSshHosts` or `writeSshConfigFile`. Apply the same comparison to the import path if its source can be a catalog file, since a JSON catalog read as an ssh config yields a misleading summary rather than a real import. Extend `src/plugins/hosts/activate.test.ts` with cases that run `hosts export ~/.janissary/hosts.json` and `hosts export $root/.janissary/hosts.json` against fixtures with usable home and project catalogs, asserting the exact refusal, that both catalog files are byte-for-byte unchanged, that the mocked `writeFileSync` was not called, and that no tab update or open happened. Keep the existing successful import and export cases in that suite passing untouched, along with the target-read and target-write failure cases in `src/plugins/hosts/export-ssh.test.ts` and `src/plugins/hosts/import-ssh.test.ts`, which pin the surrounding behavior. Place the guard in the runner or in `exportSshHosts`, but not in both, so the rule has one owner for the command and the later intent caller alike.
