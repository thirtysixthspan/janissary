# pull-request

* Handle the headless terminal's unparsed-output limit in the shell transcript writer, so a fast output burst stops the transcript through its failure path instead of silently dropping chunks, throwing from `dispose()`, or crashing the server.

Existing Issue: The writer feeds every PTY chunk to `@xterm/headless` with no backpressure, and xterm 6's write buffer throws `write data discarded, use flow control to avoid losing data` from every `write` (including the empty `write('', cb)` the finishing path and resize use) once more than 50,000,000 characters are queued unparsed; the writer handles none of this, so it breaks the subplan's promises that every write failure fires `onFailure` once and never throws into the bus, and that in-memory pending output is bounded by the 4 MiB `BoundedAppendFile` rule. Severity: 7/10

Existing Risk: 6/10 - The project has no PTY flow control, and the writer's per-line work (a `translateToString`, a marker re-registration and a file write per line feed) makes parsing short-line floods such as `yes` or `cat` of a large log slower than the PTY delivers them, so a shell tab can queue about 100 MB of strings, lose later chunks from its transcript with only a stderr line per chunk and no `onFailure`, leak its file stream and terminal when `finish()` throws before registering its drain callback (so `dispose()` throws to its caller too), and, if the file's own 4 MiB limit trips during that parse, throw out of xterm's timer-driven parse loop as an uncaught exception that takes down the server.

Proposal Risk: 3/10 - The backlog is capped and every overflow goes through the single fail-once path, but the cap is a new threshold that fires on legitimate heavy output and ends that session's transcript early, which is the accepted Decision 7 behaviour carried over to a second buffer.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1675 "bound the shell transcript writer's unparsed xterm backlog and route overflow through its fail-once path". In `src/shell/transcript/writer.ts`, `ShellTranscriptWriter` should count the characters it has handed to `this.term.write` and not yet seen parsed: add `data.length` in `onData`, and pass a per-chunk callback to `term.write(data, cb)` that subtracts it (xterm's `WriteBuffer` runs each chunk's callback right after that chunk is parsed). Before writing, if the count plus the new chunk would exceed a named constant well below xterm's 50,000,000-character discard watermark (reusing `MAX_PENDING_APPEND_BYTES` or a sibling constant beside `SCROLLBACK_ROWS`, with a comment naming the xterm watermark it stays below), stop the transcript as a failure instead of writing. The writer then needs its own fail-once guard: today `fail()` relies on `BoundedAppendFile`'s once-only `onFailure`, so add a `failed` flag that makes `fail()` idempotent across both sources, and have `fail()` make `this.file` stop accepting writes (for example by calling `this.file.dispose()` up front, which leaves the already-written content in place). Make the finishing path unable to throw: wrap `this.term.write('', …)` in `finish()` (and the one in `onResize`) in a try/catch whose fallback runs the same close-out synchronously (call `this.tracker.finish()` only if the buffer is safe to read, then `this.file.dispose()` and `this.term.dispose()`), so `dispose()` never throws and the file stream is always released. Keep the "Can run inside a line-feed handler" comment on `fail()` accurate. Add cases to `src/shell/transcript/writer.test.ts`: emit enough synchronous `data` events to exceed the new cap before xterm parses (the parse is asynchronous, so back-to-back emits accumulate), then assert `onFailure` was called exactly once, no `emit` threw, the transcript holds only a prefix of complete rows, and a later `dispose()` does not throw; use a test-only smaller cap if the real value would make the test slow, through a constructor option or an exported constant the test can override, without widening the public surface subplan 05 relies on. The existing writer tests (sentinel, exit/dispose once, unwritable directory) must keep passing unchanged, and `src/bounded-append-file.test.ts` covers the file's own limit.
