# pull-request

* Make the SQL browser render the answer it asked for, and stop it disabling itself on the next one

Existing Issue: Every `sql <name>` opens a tab that stays on `Loading…` with `No tables.` even when the database has tables, and the first topic action that folds a non-empty schema answers with `Tab plugin "sql" disabled: Maximum call stack size exceeded.`, which closes the tab and disables the plugin for the rest of the session. Severity: 9/10

Existing Risk: 9/10 - The whole feature is unreachable: no navigator row, no grid, no console read, because the tab never shows an answer, and a user who presses Refresh loses the tab and the plugin for the rest of that Janissary session.

Proposal Risk: 2/10 - Reordering the mirror write ahead of the request removes the re-entrant fold, and a fold that issues a request nothing can answer is a visible failure rather than a silent one, but a fix that only changes `openDatabase` would leave the second request able to recurse, which is what a test that folds one non-empty answer twice would catch.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1467: the sql plugin never renders its first answer and disables itself on the next topic action". Steps D2, D3, D4, D5, D6, D7, D8, D9, D10, D11, D12, D13, D14, D15, D16, D17, D18, P1 and G1 through G21 all fail on this, and D1 and D19 pass. Replication, from a clean project: run `db sqlite create shop`, then `db sqlite query shop "CREATE TABLE orders (id INTEGER PRIMARY KEY, customer TEXT NOT NULL, status TEXT)"` and `db sqlite query shop "INSERT INTO orders (id, customer, status) VALUES (1,'ada','open'),(2,'bo','paid')"`, then `sql shop`; the tab opens and the grid header reads `Loading…`, the navigator reads `No tables.`, the header has no columns and the body no rows, although the table exists and the connection is open. Press **Refresh** in the pager; within a second the tab is gone and a toast and a transcript line read `Tab plugin "sql" disabled: Maximum call stack size exceeded.`, and `sql shop` afterwards does nothing because the plugin stays disabled. Consistent, not intermittent: reproduced in 3 of 3 app instances, twice in the same run (D2 and D6, where the second **Refresh** was the trigger) and once each in two single-step probes; on an empty database the tab is the same but never crashes, because no answer ever names a table. The spec promises the opposite in product/specs/sql-database.md: "`sql <name>` opens or focuses that database's tab" and "The navigator lists every table, view, index, and trigger in the database", and the plan in product/plans/complete/sql-database-browser.md makes the same claim. Root cause, and the ordering the whole design depends on: `deliver` in `src/plugins/sql/activate.ts` issues a tab's next request before recording that request in the plugin's own mirror, and `capabilities.topicAction` reaches `actOnDatabases` in `src/plugins/topics.ts`, whose `messageBus.emit('databases', ...)` is synchronous and whose only listener, the `dispatch` in `src/plugins/notifications.ts`, calls the plugin's `notify` synchronously (`guardPluginCall` in `src/plugins/guard.ts` calls the handler before its first `await`). So the re-entrant `deliver` reads the mirror as it was *before* the fold, finds the answer that was just consumed still in the capped result list, folds it a second time, and `fold` in `src/plugins/sql/fold.ts` calls `foldSchema`, which calls `issue('query', ...)` from `src/plugins/sql/tabs.ts`, which issues another request and re-enters again with the same stale mirror: unbounded synchronous recursion, a `RangeError`, and the plugin disabled by `disable` in `src/plugins/host.ts`. The same ordering loses the first answer outright: `openDatabase` in `src/plugins/sql/open-tab.ts` calls `issue('schema', ...)` before `tabs.write(key, payload)` and before `openOrFocusTab`, so `ownedTabs` in `src/plugins/notifications.ts` is empty when that answer is emitted and the notification is dropped, leaving the tab awaiting a request id nobody will ever answer — which is why the tab is one request behind forever and why the empty-database case never recovers either. Ruled out: the client, since the tab renders correctly and the plugin is server-side only; the transport, since the first answer does reach the server and appears in the topic's result list; the cap, since the answer being re-folded is always within the last 32 results. Likely fix: record the request in the mirror before it leaves for the host — write the payload carrying the new `pending` in `openDatabase` in `src/plugins/sql/open-tab.ts` before `issue('schema', ...)` runs, and in `deliver` in `src/plugins/sql/activate.ts` write the payload whose `pending` is the new request before `fold` runs, or have `fold` return the payload with its follow-up already recorded and issue the follow-up from `activate.ts` after the write; and make the re-issue branch in `deliver` write the re-issued payload before issuing, so a lost answer cannot recurse. A regression test in `src/plugins/sql/activate.test.ts` should assert that a `schema` answer naming a table folds the tab to that table and issues exactly one `query` follow-up even when the notification that carried the answer re-enters, and that `openDatabase` leaves the tab with the schema already folded rather than a `pending` nothing will answer; a test in `src/database/browser.test.ts` is not the place for it, since the request bookkeeping is the plugin's.
