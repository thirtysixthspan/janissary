# pull-request

* Splice a pasted entry into the command bar at the selection the user actually made, rather than one character before it.

Existing Issue: Pasting a clipboard entry into the command bar replaces the wrong span when a selection is present. With `replace ME please` in the bar and `ME` selected at 7–9, choosing an entry from the popup yields `replacespliced-payloadE please`: the splice replaced `" M"` at 6–8 instead of `"ME"` at 7–9, so the space before the selection was consumed and the `E` survived. The selection itself is correct at the moment of the keypress — reading it back with the popup open reports `selectionStart: 7` and `selectionEnd: 9` — and the same step splices correctly at a bare caret, where `open ` becomes `open spliced-payload`. Observed 1 of 2 in the step run; on the rerun of the same steps the value did not change at all, so the two observations are recorded rather than merged into one defect. Step D5, "Paste into a command bar mid-sentence", promises the selection "is replaced, not appended to", and `spliceIntoTextarea` in `web/src/shared/command-bar/textarea-splice.ts` is the one function both readings go through: it reads `element.selectionStart` and `element.selectionEnd`, calls `setSelectionRange` with them, and then `document.execCommand('insertText', false, text)`, falling back to a manual splice on the `value` React passed in. `insertAtCaret` in `web/src/agent-tabs/command-input/CommandInput.tsx` closes over that `value`, so the two branches read the caret from different places. The editor's own handle has a separate `pasteAtCaret` beside `insertAtCaret` in `web/src/editor/useEditorDrop.ts` precisely because a paste leaves the caret at the start of the pasted text while a drop leaves it at the end; the command bar has no such pair and routes a paste through the drop function. Severity: 6/10

Existing Risk: 5/10 - A user who selects a word to replace it with a copied value gets the space before the word eaten and the word's last letter left behind, which reads as the paste landing in the wrong place and costs the correction by hand; because the rerun produced no change at all rather than the same shifted text, there is also a path where the paste silently does nothing, and a user who hits it has no way to tell which of the two happened.

Proposal Risk: 4/10 - Replacing the `execCommand` branch with a plain value splice gives one caret source and removes the branch's platform dependence, but it drops a path that puts the caret synchronously right after the inserted text without a `requestAnimationFrame` round-trip, so a regression test has to pin that timing or a fast typist's next keystroke lands in the wrong place.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1499: splice a pasted command-bar entry at the selection the user made". In `web/src/shared/command-bar/textarea-splice.ts`, give the command bar a paste path that reads the caret from one place: take `element.selectionStart` and `element.selectionEnd` once, build the result as `value.slice(0, start) + text + value.slice(end)`, and set both `element.selectionStart` and `element.selectionEnd` to `start + text.length` before dispatching the `input` event, which is what the existing fallback branch already does. Then decide whether the `document.execCommand` branch is still wanted at all: if it stays, it must take the same computed `start` rather than re-reading the element after `setSelectionRange`, and if it goes, the comment explaining that it exists to avoid a `requestAnimationFrame` round-trip needs replacing with the timing argument for the direct assignment. In `web/src/agent-tabs/command-input/CommandInput.tsx`, give `CommandInput` a `pasteAtCaret` beside `insertAtCaret` on the `CommandInputDropHandle`, so a paste is a named path rather than a drop that happens to leave the caret somewhere else, and add `pasteAtCaret` to `CommandInputDropHandle` in `web/src/shared/drop-handles.ts` and to the object `CommandInput` publishes to `dropRef`. `createPasteCapability` in `web/src/paste-into-surface.ts` should call the new member for the command-bar branch the way it already calls `pasteAtCaret` for the editor branch, rather than routing both through `insertAtCaret`. Cover it in `web/src/shared/command-bar/textarea-splice.ts`'s own test with a selection in the middle of a string, asserting both the resulting value and that the caret sits immediately after the inserted text, and add a case where `value` and `element.value` disagree so the branch that ignores React's copy is caught. The existing tests in `web/src/agent-tabs/command-input/useCommandBarSubmit.test.ts` and `web/src/paste-into-surface.test.ts` must keep passing; `web/src/paste-into-surface.test.ts` already asserts the command bar is the last fallback and needs no change beyond the renamed call. Separately, establish why the rerun produced no change at all, since that is a different symptom from a one-character shift: instrument `spliceIntoTextarea` to record the caret it read and the value it received on both runs, and treat it as the same defect only if the caret was already stale when the function was called.
