# pull-request

* Close the remote whole-tree commit's staging-scope hole: from a navigator rooted below the remote workspace root, the header button stages and pushes the entire workspace rather than only the tree.

Existing Issue: The remote `git-commit` operation runs `context.filesystem.commit(context.root, ...)` on the far side, where `context.root` is the `RemoteFileNavigators` instance's own root — the workspace root passed at `src/remote/serve.ts` when the channel is created — and the header button's whole-tree form lands there as an empty `paths` list, so `LocalFileSystemPort.commit` stages `git add -A -- .` with `cwd` at the workspace root. For a remote navigator rooted at a subdirectory (say `<workspace>/src`), the commit carries every change in the workspace — files the tree never showed — while the button reports success. Severity: 8/10

Existing Risk: 7/10 - A user commits from a narrow tree and silently publishes unrelated changes from outside it to `origin`, which can leak local work — or uncommitted credentials or scratch files they never touched — into a pushed commit that is hard to retract once remote-peer review or CI has consumed it.

Proposal Risk: 2/10 - The fix adds one argument to an operation this pull request already introduced behind a version bump, so no deployed protocol surface changes shape, but the remote path-mapping layer is subtle enough that a regression test must pin the sub-rooted case or it silently reverts.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1128: scope the remote whole-tree commit to the navigator's own root". The whole-tree form sends `paths: []` from `remoteGitCommit` in `src/file-navigator/remote-port-git.ts`, and the far side stages `.` at its own root — the workspace root — because `RemoteFileNavigators` has only one root and no per-navigator one (`src/remote/serve-file-navigator.ts` builds `context.root` from `this.root`). Fix it by naming the tree on the wire instead of trusting an empty list to mean "the tree": extend `RemoteFilesystemArguments` in `src/remote/protocol.ts` with an optional root marker, have `remoteGitCommit` derive the navigator root's workspace-relative prefix with `RemotePortPaths.to` (src/file-navigator/remote-port-paths.ts) when `relPaths` is empty, send it, and reject the request if it lexically escapes the workspace; on the far side, `git-commit`'s entry in `MUTATION_OPERATIONS` (src/remote/filesystem-operations.ts) validates the marker and passes it on so the commit runs staged at that subtree rather than the workspace root. Include the change in the same `REMOTE_PROTOCOL_VERSION = 13` bump this pull request already performs (both hosts must be on 13 regardless), and extend the version-history paragraph to say the marker exists. Tests: a `src/file-navigator/remote-port.test.ts` case asserting a sub-rooted whole-tree commit sends the root marker rather than an empty path list with no prefix; a `src/remote/file-navigator-refusal-contract.test.ts`-style case asserting a marker naming a path outside the workspace is refused; and a `src/git/commit.test.ts` assertion that a commit whose paths arrive as a workspace-relative subdirectory prefix stages `-- .` under that subtree, not above. The existing `src/git/commit.test.ts` whole-tree regression guard ('scopes the whole-tree form to the tree root') and the manager commit tests must keep passing untouched.

* Prevent a pull and a commit in the same file navigator tab from running concurrently, since each holds git's index lock and the two actions coalesce only against themselves.

Existing Issue: `runPull` guards on `state.pull === 'pulling'` and `runCommit` guards on `state.commit === 'committing'`, and neither checks the other's in-flight flag, so with a long pull running, pressing the header commit button — or confirming the row-menu message field — starts a `git commit` that collides with the concurrent `git pull` on git's index and `HEAD` lockfiles. Severity: 4/10

Existing Risk: 5/10 - One of the two git commands fails with a lockfile error mid-run, and the user reads it as their commit or pull having lost work: the commit case is worse than the pull's, because a failed push-armed commit is a message the user composed that appears to have vanished even though the local commit survives.

Proposal Risk: 2/10 - The added guard makes one entry point briefly unresponsive while the other action runs, with no error shown, so a test pinning the "reports nothing" behavior across both actions is what keeps the change from reading as a hang.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1128: coalesce a commit with an in-flight pull, and vice versa". In `src/file-navigator/manager-pull.ts`'s `runPull` entry guard, treat `state.commit === 'committing'` the same as `state.pull === 'pulling'` — return early, post nothing — and mirror that in `src/file-navigator/manager-commit.ts`'s `runCommit` by returning early when `state.pull === 'pulling'`. The empty-or-whitespace cancel path in the message field stays client-side, so a coalesced field confirmation silently closes with no RPC, matching the pull button's existing quiet coalescing. Tests: extend the `src/file-navigator/manager.test.ts` cases this pull request added (the 'second click while one is in flight is ignored and posts nothing' bullet) with one commit-while-pulling and one pull-while-committing case each declaring no notification and no status change, next to the existing `src/file-navigator/manager-pull.ts` coalescing coverage; the pull's own test file's argument expectations in `src/git/commit.test.ts` and `src/git/pull.test.ts` must stay untouched.


* Stop a commit that fails before it creates a commit object from leaving every change it staged sitting in the user's git index with no mention of it.

Existing Issue: `commitRoot` stages with `git add -A` as its first step and never unwinds that, so a `git commit` that rejects — a pre-commit hook that refuses, an unconfigured `user.email`, a message git will not take — leaves every change under the tree root, or every path the row menu named, staged in the user's own repository, while the only thing reported is `Could not commit: <git error>`, which says nothing about the index having been rewritten on their behalf. Severity: 4/10

Existing Risk: 5/10 - The next commit the user makes from a terminal silently carries everything the button staged for them, which is how an unrelated change — a scratch file, a local config edit, a half-finished refactor — reaches `origin` inside someone else's commit, by which time nothing connects it back to a button click that reported failure.

Proposal Risk: 3/10 - Unwinding the index is itself a mutation of the user's state, so an unwind that runs when they had staged something by hand would destroy that staging; the whole safety of the change rests on the "only when the index was clean beforehand" pre-check, and if that check is not pinned by a test the remedy is worse than the defect it replaces.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1128: do not leave a failed commit's staging behind". In `src/git/commit.ts`, run the module's existing `git diff --cached --quiet` probe once more *before* `stage` and remember whether the index was already dirty. If the `git commit` step rejects and the index was clean beforehand, run a bare `git reset` (mixed, no pathspec, `cwd` at the tree root) to put it back, swallowing a failing reset the way `pullRebase` in that same file already swallows a failing `git rebase --abort`, and re-throw git's original error unchanged. If the index was already dirty beforehand, leave it alone and let the user be told: add a second failure variant to `src/file-navigator/commit-report.ts` beside `commitFailureText`, reached from `src/file-navigator/manager-commit.ts`, whose line names that the staging was left in place. The steps after the commit object exists — `pull --rebase` and `push` — must not unwind anything, since by then the commit is real and the current behavior is right. Tests: in `src/git/commit.test.ts`, whose recording `execFile` mock already drives failures by subcommand, add a case where the commit fails over a previously clean index and a trailing `reset` runs with the original error still thrown; a case where the index was already dirty and no `reset` runs; and a case where the rebase fails and no `reset` runs. The existing 'aborts a failed rebase and still rejects with git's own error' and 'does not mask the rebase error when the abort itself fails' cases must keep passing, though the expected call sequence in 'stages, checks, commits, rebases, and pushes in that order' gains the pre-probe and needs updating with it. Spec and docs: add a sentence on what a failed commit leaves behind to the "Committing to origin" section of `product/specs/file-navigator-tab.md` and to "Committing your changes to origin" in `documentation/user-documentation/tab-types/file-navigator.md`.


* Name the header commit button's default message after every change the commit will carry, rather than only the changed rows the tree happens to be showing.

Existing Issue: `changedFilePaths` in `web/src/file-navigator/file-navigator-commit-message.ts` counts only non-directory rows the payload is currently rendering, while the header button commits everything under the tree's root, and `markGitStatus` deliberately rolls a collapsed directory's changes up onto the directory row — which that filter drops — so a tree whose changed files sit inside collapsed directories opens the field pre-filled with `commit: 0 files`, the value `FileNavigatorTab.test.tsx` now pins, or names a single visible file while the commit carries several more. Severity: 4/10

Existing Risk: 4/10 - The default exists to be accepted with one keystroke, so the wrong count is what lands in the repository's permanent history and on `origin`, where the one sentence meant to explain a change instead misdescribes it and cannot be corrected without rewriting pushed history.

Proposal Risk: 2/10 - The count then comes from the server's git-status map rather than from what is on screen, so it can disagree with what the user can see for as long as a refresh is in flight — a smaller and more explainable gap than the current one, but still a number the user did not verify.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1128: base the header commit's default message on every change under the tree root". The server already holds the answer: `FilesTabState.gitStatuses` in `src/file-navigator/state.ts` is the full changed-path map for the tree's root, scoped by `changedPaths` in `src/git/status.ts`, not merely the visible rows. Carry its size to the client — add an optional changed-count field to `FileNavigatorView` in `src/tab/types.ts` beside `commit`, write it in `writeRebuiltPayload` in `src/file-navigator/manager-payload.ts` next to `commit: state.commit` and leave `writeCreatedPayload` alone exactly as `pull` and `commit` are treated, and re-export nothing new since the type already crosses through `src/protocol.ts`. In `web/src/file-navigator/FileNavigatorTab.tsx`, have `commitEverything` build its default from that count instead of from `changedFilePaths(files.rows)`, through a new count-taking helper in `web/src/file-navigator/file-navigator-commit-message.ts` that reads `commit: <n> files` with a singular `commit: 1 file`; the row-menu form keeps `defaultCommitMessage` and its name-the-single-file behavior untouched. `changedFilePaths` then has no caller and should be deleted along with its test. Tests: replace the `commit: 0 files` expectation in `FileNavigatorTab.test.tsx`'s 'opens the commit-message field rather than sending anything' case and the `commit: README.md` expectation in the whole-tree case beside it, since the whole-tree default stops naming a file; add helper cases for zero, one, and several; add a `src/file-navigator/manager.test.ts` case that the rebuilt payload carries the count for a change inside a collapsed directory, which is the case that fails today. Spec: `product/specs/file-navigator-tab.md`'s "Committing to origin" section currently says the header button's default is named after "the changed files the tree is currently showing" and that one file is named outright — both sentences change with this, as does the matching paragraph in `documentation/user-documentation/tab-types/file-navigator.md`.


* Re-prime the commit-message field when it is re-opened for a different target while already on screen, instead of leaving the previous invocation's text sitting over the new commit's paths.

Existing Issue: `FileNavigatorCommitPopup` seeds its input from `defaultMessage` through `useState`, which reads that prop only on mount, and because the field deliberately survives a blur, `useFileNavigatorCommit.request` can replace the pending commit while the same popup element stays mounted at the same position in `FileNavigatorOverlays` — so choosing `Commit to origin` on a row, clicking back onto the tree, and then clicking the header's commit button leaves the earlier single-file text in the field while the paths that will travel with it have become the whole-tree form. Severity: 4/10

Existing Risk: 4/10 - Enter then writes a permanent, pushed commit whose message names one file while the commit carries every change under the tree root, and unlike an unread default this one was read: the user saw a message that described the commit they asked for a moment ago and had no way to tell it no longer described the one they were about to make.

Proposal Risk: 2/10 - Remounting the field on a re-target discards text the user had begun typing, which is the exact loss the no-blur-dismiss decision exists to prevent, so the work has to choose deliberately between "a re-target is a new field" and "a re-target is refused while one is open" and pin whichever it chooses, or the fix trades a wrong message for a lost one.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1128: re-prime the commit-message field when it is re-targeted while open". Give `PendingCommit` in `web/src/file-navigator/useFileNavigatorCommit.ts` a monotonically increasing request id set by `request` — an id rather than the paths, since two requests can legitimately name the same paths — and pass it as `key` on the `FileNavigatorCommitPopup` element in `web/src/file-navigator/FileNavigatorOverlays.tsx` so React remounts the field and re-seeds it from the new default. If the project would rather protect a half-typed sentence, the alternative is to make `request` a no-op while a pending commit is already open; either way the choice belongs in `product/specs/file-navigator-tab.md`'s "Committing to origin" section, which today describes only how the field opens and closes and is silent on being re-targeted. While in the same area, check the overlap the persistence also creates: `.files-commit-popup` and `.file-search-popup` share one `top`/`right`/`z-index` rule in `web/src/theme.css`, so opening Search files over an open commit field draws the two cards on top of each other — close the commit field when the search pop-up opens, or offset one of them. Tests: a `FileNavigatorOverlays.test.tsx` case that rerendering with a new pending commit shows the new default rather than the old text, and a `FileNavigatorTab.test.tsx` case that a row-menu commit followed by a header commit click shows the whole-tree default; `FileNavigatorCommitPopup.test.tsx`'s 'keeps its text and sends nothing when it loses focus' case is the behavior that must not move and must pass untouched.


* Share the file navigator's three-state button-flash machine between the pull and the commit rather than keeping two copies of it.

Existing Issue: `src/file-navigator/manager-commit.ts` restates `src/file-navigator/manager-pull.ts` almost line for line — its own `FLASH_MS`, its own `settle`, its own `rest`, its own still-rooted guard, and its own entry guard — differing only in which pair of `FilesTabState` fields it writes, so one state machine now exists in the tree in two independent copies that know nothing of each other. Severity: 3/10

Existing Risk: 4/10 - Each copy reasons only about its own field pair, which is precisely how the two actions came to coalesce against themselves and not against each other (already on file above), and a third such button — fetch, sync, stash — would copy the machine a third time and introduce a third pair the first two would likewise not know about.

Proposal Risk: 3/10 - A shared helper is more indirect than two plain modules, and written as a generic keyed by field-name strings it would erode the checking that currently makes each status field's name meaningful, so the value of the change depends on keeping the parameterization concrete rather than clever.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1128: share the file navigator's button-flash state machine between pull and commit". Extract a module beside the two — `src/file-navigator/manager-flash.ts` — holding `FLASH_MS`, the `settle`/`rest` pair, and the still-rooted guard, parameterized by a small descriptor of explicit read/write functions over a `FilesTabState` rather than by string keys, so the field names in `src/file-navigator/state.ts` stay checked by the compiler. Rewrite `manager-pull.ts` and `manager-commit.ts` to hold only what is genuinely each one's own: the entry guard's subject, the port call, the report text from `pull-report.ts` or `commit-report.ts`, and what a settled outcome triggers — `clearFilesystemCache` plus `refreshGit` for the pull, `refreshGit` for a landed commit, and neither for a nothing-to-commit result, which settles straight to rest. Have `closeTabState` in `src/file-navigator/manager-profile.ts` clear its timers through the same descriptor list, so a future third status cannot be forgotten there the way it currently could be. The separate `PullContext` and `CommitContext` types stay separate, as the plan decided. This is a refactor with no behavior change: the existing pull cases in `src/file-navigator/manager.test.ts` and the commit cases this pull request added there — flash timing, settle-to-rest, coalescing, tab-closed-mid-flash, notification-posted-after-close — are the contract, and passing them untouched with no new assertions is what finishing this looks like.
