# pull-request

* Give every mark an accessible name and the series a palette that survives colour-vision deficiency, so a chart is not a picture only a sighted colour-perceiving reader can read.

Existing Issue: the root `<svg>` in `web/src/plugins/visualizations/chart/ChartSvg.tsx` already carries `role="img"`, a `<title>` and a `<desc>` built from the same marks, and the data table under the card already sets `scope="col"`, but no individual mark is labelled and the series ramp is five theme tokens — `var(--accent)`, `var(--success)`, `var(--running)`, `var(--error)`, `var(--muted)` — in which a success green and an error red can carry two series of one chart, where Observable Plot emits a per-mark `aria-label` on each mark's `<g>`, an `ariaDescription` for the long form and an `ariaHidden` option for marks that are decorative or redundant (https://observablehq.com/plot/features/accessibility) and Datawrapper simulates a categorical palette against all three forms of colour-vision deficiency and warns inline when pairs become indistinguishable (https://www.datawrapper.de/accessibility). Severity: 5/10

Existing Risk: 5/10 - A screen-reader user hears the chart's name and then a long description and then nothing per data point, and a reader with deuteranopia or protanopia is given two series in two colours that are the same colour to them, with a legend as the only way to tell which is which — and WCAG 1.1.1 names exactly this shape as a failure, asking for a text alternative, and 1.4.1 asks for a visible non-colour alternative even when both colours pass contrast.

Proposal Risk: 3/10 - Labelling every mark makes the accessibility tree large on a 500-mark chart, so the labels have to be bounded to what is readable rather than exhaustive, and changing the palette changes every existing chart's appearance in both themes, which the style contract test will insist on.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1440: label each mark for assistive technology and give the series a colour-vision-safe palette". Put a short per-mark label on the `<g>` of every point, slice and segment in `web/src/plugins/visualizations/chart/ChartSvg.tsx` and `web/src/plugins/visualizations/chart/CartesianChart.tsx`, naming the x value, the y value and the series where there is one, and mark the grid and axis furniture `aria-hidden`; generate them beside `describeChart` in `web/src/plugins/visualizations/chart/describe.ts` so the spoken name and the drawn mark come from one place. Replace `SERIES_COLOURS` in both chart files with a set of custom properties defined in `web/src/plugins/visualizations/visualizations.css` for the light and dark themes, chosen to stay distinguishable under deuteranopia, protanopia and tritanopia and to keep 3:1 against the chart background in both, and add a shape or dash difference so the two are told apart without colour at all; `visualizations-style.test.ts` already pins that file's contents, so extend that contract. Verify with a web case in `web/src/plugins/visualizations/VisualizationChartCard.test.tsx` asserting a rendered mark's `<g>` carries a label naming its x and y values, a case asserting the grid carries `aria-hidden`, a case in `web/src/plugins/visualizations/visualizations-style.test.ts` asserting no literal colour reaches the new properties, and a contrast case computing each series colour against both theme backgrounds.

* Export a chart as SVG and as the rows behind it, so a chart can leave the application without losing its precision or its data.

Existing Issue: a card offers PNG and PDF only, and the PDF is a rasterized image of the same SVG at twice the size, where Vega's view exposes `toSVG`, `toCanvas(scaleFactor)` and `toImageURL('png' | 'svg', scaleFactor)` (https://vega.github.io/vega/docs/api/view/), `vl-convert` ships `vl2svg`, `vl2png`, `vl2pdf` and `vl2url` (https://github.com/vega/vl-convert), and Datawrapper's footer offers "Get the data" as a locale-formatted CSV of the visualised data alongside the image downloads (https://www.datawrapper.de/blog/footer-options-let-readers-download-and-embed-your-datavis). Severity: 5/10

Existing Risk: 5/10 - A chart destined for a document, a review or a repository comes out as a raster at one fixed scale, so it blurs when scaled and cannot be edited or diffed, and the rows behind it are reachable only by reading the table on screen and copying them by hand, which is the one export a screen-reader user most needs.

Proposal Risk: 2/10 - Both are pure additions to `web/src/plugins/visualizations/export/download.ts` with no change to what the tab renders, and the CSV is generated from the same marks the table is generated from, so it cannot disagree with the chart.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1440: export a chart as SVG and as the CSV of its plotted rows". Add `exportSvg` in `web/src/plugins/visualizations/export/download.ts`, serializing the on-screen `<svg>` with the theme custom properties already resolved by `chartProperties` into literal values, and `exportCsv`, writing the same rows and columns that `dataTableFor` in `web/src/plugins/visualizations/chart/describe.ts` produces, with a header row and a header comment naming the chart, its transformations and the source. Put a button for each on the card beside the two existing ones in `web/src/plugins/visualizations/VisualizationChartCard.tsx`, matching the per-chart rather than per-tab framing of the existing exports, and keep the vector PDF for a later change rather than attempting selectable text here. Verify with unit cases in `web/src/plugins/visualizations/export/download.test.ts` for the CSV's quoting of a value containing a comma, a quote and a newline, and for the serialized SVG carrying no unresolved `var(--…)`; a card case in `web/src/plugins/visualizations/VisualizationChartCard.test.tsx` asserting both buttons exist per chart; and a case asserting the CSV's row count equals the caption's row count for a truncated source.
