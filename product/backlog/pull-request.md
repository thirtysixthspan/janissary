# pull-request

* Let the roles tab keep editing the home roles when the project's roles.json is the broken one

Existing Issue: With a corrupt or partly damaged `.janissary/roles.json` in the project, the roles tab falls back to the healthy home file, shows the problem line, and then refuses every edit with `roles.json at <home file> is unusable — fix the file before editing roles.` — naming a file that is fine and is the very file the tab would write. Severity: 6/10

Existing Risk: 6/10 - A user whose project holds a hand-edited or half-written roles.json cannot change a single role from the tab until they find and delete that file, and the refusal points at the home file instead, so the fix is not obvious from what the tab says.

Proposal Risk: 2/10 - Scoping the refusal to the file actually in effect leaves the fallback editable and the tab still read-only in the two cases the file genuinely cannot back.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1668 "Let the roles tab keep editing the home roles when the project's roles.json is the broken one". Description step D8, read verbatim as "Corrupt the effective roles file (invalid JSON). Confirm the tab falls back — to the home file, and failing that to the defaults — shows one problem line, refuses edits with `roles.json at … is unusable — fix the file before editing roles.`, and leaves the broken file untouched."; reproduced 2 of 2, the second time as the only step in its batch, so it is consistent rather than order-dependent. Replication: delete any roles file, run `roles` from an agent tab so the home file is created with the five defaults, then write the two bytes `{` and a newline plus the text ` this is not json` into `<project-dir>/.janissary/roles.json`, close the roles tab, run `roles` again, click the first tab to return to the agent tab if needed, and fill the `research` card's name field (`.roles-tab:visible input[aria-label="Name of role research"]`) with `r2` and press Enter. Expected per product/specs/roles.md, "When a file does not decode": "While any file in effect is in that state — nothing decoded, or something dropped — every edit is refused with `roles.json at <path> is unusable — fix the file before editing roles.`", and the same section's "a broken project file falls back to the home file" leaves the home file whole and therefore not in that state. Observed: the source line reads `Editing <home>/.janissary/roles.json`, the problem line reads `roles.json is not valid JSON at <project-dir>/.janissary/roles.json — showing the home roles file.`, all five cards render from the home file, and the rename is refused with `roles.json at <home>/.janissary/roles.json is unusable — fix the file before editing roles.` — the broken project file's bytes are left untouched, but the healthy home file is called unusable and cannot be edited while it is in effect. The same refusal happens when the project file is only partly damaged. The second half of the step passes: breaking the home file as well shows the five defaults under `No roles file in effect` with `roles.json is not valid JSON at <home>/.janissary/roles.json — showing default roles.` and refuses edits as specified. Root cause: `readRolesFile` in `src/plugins/roles/roles-file.ts` folds a broken earlier candidate's problem into the read of the file it falls back to, returning `{ ...attempt.read, problem: "<broken problem> — showing the home roles file." }` with `path` still the fallback's own path; `edit` in `src/plugins/roles/activate.ts` then refuses on `read.problem !== undefined` and interpolates `read.path`, so a problem raised about one file marks a different, healthy file unusable. Likely fix: carry the broken file's path beside the problem — a `unusablePath` field set only when the file in effect itself decoded nothing or dropped something — and refuse on `read.source === 'default' || read.unusablePath === read.path`, naming that path in the message; the fallback read keeps its problem line so the tab still shows what it skipped. A regression test should assert that a project file holding `{` beside a healthy home file leaves the tab editable and that the rename reaches the home file, and that a partly damaged file in effect still refuses every edit byte-for-byte.

* Stop reporting a description conflict when the description that changed was the one this tab just saved

Existing Issue: Every successful description edit leaves the one refusal line under the source line reading `The description of "documentation" changed elsewhere — showing the stored one.`, even though this client wrote that description and nothing anybody typed was displaced. Severity: 5/10

Existing Risk: 5/10 - Saving any role description reports a conflict the user did not cause, so a correct save reads as a rejected one and the user retypes it or stops trusting the tab's line.

Proposal Risk: 2/10 - Comparing the republished value against the draft as well as the baseline leaves the line for the one case it is written for, a draft another client displaced.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1668 "Stop reporting a description conflict when the description that changed was the one this tab just saved". Generated step G5, read verbatim as "Rename `research` to `PLANNING` so the tab shows a refusal line, then make an edit the server accepts — change `documentation`'s description — and confirm the refusal line has gone."; reproduced 2 of 2, the second time as the last step of its batch on a freshly created home file, so it is consistent rather than order-dependent. Replication: run `roles` from an agent tab on a fresh scratch home so the tab shows the five default cards, click the `research` card's name field (`.roles-tab:visible input[aria-label="Name of role research"]`), fill it with `PLANNING` and press Enter so the tab shows `A role named "PLANNING" already exists.`, then click the `documentation` card's description field (`.roles-tab:visible input[aria-label="Description of role documentation"]`), fill it with `Docs written and kept current.` and press Enter. Expected per product/specs/roles.md, "A refused edit": "The line clears on the next edit the tab raises, whether that edit is accepted or refused, so a message never lingers over a state it no longer describes", and per "A description the tab did not write", which raises that line only for "the stored description does move under an open draft". Observed: the accepted edit lands — the field and `~/.janissary/roles.json` both hold `Docs written and kept current.` — and the duplicate-name refusal does clear, but the `documentation` card immediately raises `The description of "documentation" changed elsewhere — showing the stored one.` in its place, so every description save ends on a conflict line. Root cause: `useRoleDraft` in `web/src/plugins/roles/useRoleDraft.ts` runs its render-phase adjustment whenever `baseline !== authoritative` and sets `setConflicted(draft !== baseline)`; after this client commits its own text the republished authoritative value differs from the old baseline while the draft is the text just submitted, so the hook reports a conflict although nothing displaced anybody's typing. `RoleCard` in `web/src/plugins/roles/RoleCard.tsx` raises the line from a `useEffect` keyed on that `conflicted`. Likely fix: require both halves before reporting — `setConflicted(draft !== baseline && draft !== authoritative)` — so a republished value that is the draft itself is followed silently, while a value that arrives under a genuine active draft still replaces it and reports. The name field is unaffected in practice because the card is keyed by the role name and remounts on a rename. A regression test should render `RoleCard`, commit a description edit, republish the payload carrying the text just written, and assert the description input holds that text with no refusal raised, then republish a different text under an active draft and assert the refusal appears.
