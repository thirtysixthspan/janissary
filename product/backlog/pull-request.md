* Give shell-tab recording an explicit opt-out, so a user who does not want a shell's echoed output on disk has a way to decline it rather than only a documentation note explaining that it happens.

Existing Issue: This pull request makes shell-tab output the third kind written in plaintext to `.janissary/recordings/`, and because zsh echoes what is typed back into the terminal and that echo is part of the recorded output stream, a password entered at a `sudo` or `psql` prompt now reaches the file — a tab kind where credentials are routinely typed, and the one recorded kind where this is true — while no setting, no warning at the point of exposure, and no recorded decision exists beyond a note in the spec and the user documentation. Severity: 6/10

Existing Risk: 6/10 - A user who types a credential into any shell tab has it written to plaintext on disk with no way to decline, and the only warning is documentation they have to have found already.

Proposal Risk: 4/10 - Recording cannot avoid the echo without disabling the shell's own echo, which would break the terminal, so the exposure itself remains; what the opt-out removes is the undecided part, leaving a documented default rather than an undocumented one.

Proposal: Execute ./ai/tasks/work-an-issue.md "PR 1549: add a config opt-out for shell tab recording". Add `recordShellTabs: boolean` to `Config` in `src/config.ts`, defaulting to `true` in `DEFAULT_CONFIG`, with a comment naming the consequence it trades against — that a shell echoes what is typed, so its recording captures credentials — exactly as the existing `sandboxWorkspaces` comment states what it isolates. Gate the registration in `TabManager.recordTerminal` on it alongside the `recordsTerminal` declaration check, so a project with the flag off installs no recorder for a shell tab and the tab's metadata row draws no recording flag at all, which is the state an agent tab is already in. Document the key in the user documentation next to the shell-recording paragraph that currently states the exposure, and add it to `product/specs/harness-recording.md` § Scope so the spec says what happens when it is off rather than only what happens when it is on. `src/config.ts` merges a partial config over the defaults and leaves an invalid file untouched with a warning, so a missing key already resolves to the default and no migration is needed; `src/config.test.ts` covers the default and merge behavior and should keep passing untouched, with one case added for the new key defaulting to true. Existing behavior must not move for harness and ssh tabs, which have no echo of their own and keep recording whatever this key says.
