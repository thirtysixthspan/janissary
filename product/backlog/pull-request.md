# pull-request

* Refuse edits while the roles file is only partly damaged, so the next edit does not silently delete the malformed parts the tab reported as dropped.

Existing Issue: A file that decodes partly is served with the roles and entries that decoded and one line counting what was dropped, but `edit()` in `src/plugins/roles/activate.ts` reads that same partly decoded list and then `writeRolesFile` in `src/plugins/roles/roles-file.ts` rewrites the whole file from it, so the first edit after the problem line appears — a description change, an added model, a reorder — permanently removes the malformed role or entry the tab had just reported, and no second line says so. Severity: 5/10

Existing Risk: 5/10 - A hand-edited file with one damaged entry loses it the moment the user makes an unrelated edit, and because the tab showed the problem line earlier and then looks healthy afterwards, the loss looks like the tab fixed the file rather than as data the user never agreed to discard.

Proposal Risk: 2/10 - Editing is paused only while a partly damaged file is in effect, and the existing refusal message already tells the user exactly what to do about it.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1668 "refuse edits while the roles file is partly damaged". In `src/plugins/roles/activate.ts`, `edit()` already refuses when the read answered `source: 'default'`; widen that condition to also refuse when the read carries a `problem` line, using the same wording the fully unusable case already uses (`roles.json at <path> is unusable — fix the file before editing roles.`) so one message covers both states, or add the count from the problem line when it is the partial-loss message so the reader knows how much is at stake. `RolesRead.problem` is already carried through to the payload, so no type changes are needed. In `product/specs/roles.md`, the "When a file does not decode" section currently says the well-formed parts are served and the damaged ones dropped; add that while the damage stands, edits are refused and the file is left exactly as it is. If a reviewer prefers editing to stay available, the alternative is to write back only the roles and entries the user actually touched and copy every untouched one verbatim from the raw parsed file — more code and a second decode path, which is why refusing is proposed. Cover both states in `src/plugins/roles/activate.test.ts`: a partly damaged file refuses an edit, its bytes are unchanged, and a clean file still accepts one. The existing partial-loss cases in `src/plugins/roles/roles-file.test.ts` must keep passing untouched.

* Render an effort the catalog does not offer as its own option, so a hand-written entry does not look unset.

Existing Issue: `decodeEntry` in `src/plugins/roles/roles-file.ts` accepts any effort string, and `product/specs/roles.md` documents that a value outside `low`, `medium`, `high`, `xhigh`, and `max` is passed through verbatim like `harness --effort`, but the entry row in `web/src/plugins/roles/RoleCard.tsx` renders a `<select>` whose options are only `default` plus the catalog's levels, so a stored effort such as `ultra` matches no option and the row shows an empty dropdown — indistinguishable from the default the user would get by clearing it. Severity: 3/10

Existing Risk: 3/10 - A user who hand-wrote an effort the catalog does not list opens the tab, sees an entry that looks like it has no effort, and either believes the file is wrong or clears the field and loses the value, all without being told the value is not one the tab offers.

Proposal Risk: 1/10 - The fallback option is only added for the values already stored, so a value the tab never rendered cannot reach it.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1668 "render an effort outside the catalog as its own option". In `web/src/plugins/roles/RoleCard.tsx`, the effort `<select>` maps the payload's `catalog.efforts` into options above a `default` option; when the entry's `effort` is a nonempty string that is not in that list, render one extra option carrying that exact string between `default` and the catalog levels, marked with the plain value rather than a translated label, so the stored value is visible and selecting `default` still clears it. No server change is needed — the value decoded fine and the fix is presentational. Add a case to `web/src/plugins/roles/RolesTab.test.tsx` whose payload carries `effort: 'ultra'` and assert the select's value is `ultra` and that switching it to `default` still raises `set-entry-effort` with `effort: null`. The existing effort cases in that file must keep passing untouched.

* Share the home-file-over-project-file resolution, partial-loss decode, and one-line problem reporting between the launcher and roles config files instead of shipping a second copy.

Existing Issue: `src/plugins/roles/roles-file.ts` repeats, almost line for line, the precedence, candidate walk, partial-loss counting, and problem-line composition that `src/plugins/launcher/commands-file.ts` already implements for `launcher.json` — including the home path join, the project-beats-home rule, the drop-and-count decode, and the `— showing …` fallback phrasing — and the two can now drift apart with nothing to notice, so a fix to how a broken config file is reported would land in one plugin and leave the other describing itself differently. Severity: 4/10

Existing Risk: 4/10 - The second copy is the one that goes stale: a user who relies on the roles tab being corrected to describe a broken project file correctly can end up with the launcher and the roles tab answering the same situation in two different words, and each future change to the shared rule has to be found and applied twice.

Proposal Risk: 2/10 - The two callers keep their own decode and their own wording hooks, so the shared module is a path-and-reporting seam rather than a new abstraction either plugin has to understand.

Proposal: Execute ./ai/tasks/feature/work-pull-request-issue.md 1668 "share the home-over-project config file resolution between the launcher and roles plugins". Extract the parts the two already agree on into a new module `src/plugins/config-file.ts` that takes the file name, the home and root directories, and a decode callback returning either the decoded value plus a dropped count, or undefined, and answers the resolved `{ path, source, decoded, dropped, problem }` for one candidate; the fallback chain, the creation attempt when neither file exists, and the final "— showing …" phrasing live there. `src/plugins/roles/roles-file.ts` and `src/plugins/launcher/commands-file.ts` then supply their own decode and default-entry functions and keep their own public signatures — `readRolesFile(home, root)` and `readLauncherFile(home, root)` must not change, because `src/plugins/roles/roles-file.test.ts`, `src/plugins/roles/activate.test.ts`, and the launcher's `commands-file.test.ts` all call them and their assertions on the exact problem strings must keep passing unchanged. The shared module is host plugin infrastructure under `src/plugins/`, so it is reachable from both plugins without touching either plugin import boundary. Note in the new module's comment why the two plugins share it and what stays per-plugin, and add the roles-specific creation of the default file as the caller-supplied default rather than inside the shared module, since the launcher creates its file through a different exported function.
